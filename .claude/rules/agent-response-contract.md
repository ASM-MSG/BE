# Agent Response Contract — 에이전트 응답 컨트랙트

에이전트(오케스트레이터·서브에이전트)가 작업을 마칠 때 응답에 반드시 포함해야 하는 형식 계약.
내용이 아니라 **형식**에 대한 규칙이다. 이름이 비슷한 `response-pattern.md`는 API 공통 응답
포맷이라 이 문서와 무관하다.

**왜 있나** (2026-08-29 멘토 리뷰, MSG-527): 에이전트가 잘못 동작했을 때 어떤 룰을 적용했고
어떤 스킬을 불렀고 왜 그 경로를 골랐는지가 기록에 없으면 되짚을 수단이 없다. 두 번째 목적이
더 실질적이다 — **컨텍스트가 깨지면 에이전트는 이 형식을 제일 먼저 잃어버린다.** 그래서 형식
자체가 유실 탐지기다. 작업 마무리 응답에 작업 기록 절이 없거나 카나리 규칙이 깨져 있으면 그
세션은 이미 규칙을 놓친 상태다: 결과물을 그대로 믿지 말고 세션을 다시 시작한다. 리뷰를 통째로
건너뛴 사고가 결과를 보고서야 발견된 적이 있다 — 이 컨트랙트가 있었으면 "Applied skills: 없음"이
그 자리에서 보였을 것이다.

## 적용 범위

**작업을 수행한 턴의 마무리 응답에 MUST.** 작업 = 파일 생성·수정·삭제, 외부 시스템 기록
(지라·컨플루언스·PR·푸시), 서브에이전트 실행 중 하나라도 한 것. 순수 질답·조회 턴에는 붙이지
않는다 — 매 턴에 붙으면 소음이 돼서 아무도 안 읽고, 그러면 탐지기 역할도 죽는다.
카나리 규칙(아래)은 턴 종류와 무관하게 항상 적용된다.

서브에이전트는 오케스트레이터에게 반환하는 **최종 보고**에 같은 4항목을 포함한다.
오케스트레이터만 지키면 하위 에이전트 동작은 여전히 안 보인다.

## 작업 기록 절 — MUST 4항목

작업 마무리 응답의 끝에 아래 4항목을 이 이름 그대로 적는다. **항목이 비어도 생략하지 않는다** —
생략하면 "안 적은 것"과 "없는 것"이 구분되지 않아 탐지가 안 된다.

- **Applied rules**: 이번 작업에 실제 적용한 룰(문서명 + 해당 조항). 읽은 문서를 나열하는 게
  아니라 판단에 실제로 쓴 것만 적는다.
- **Applied skills**: 실제 호출한 스킬 목록. **안 불렀으면 "없음"이라고 명시한다.**
- **Why this routing**: 요청의 어떤 문구와 태스크 분류 때문에 그 룰·스킬을 골랐는지 한두 문장.
- **수정하지 않은 파일**: 작업 범위에 인접해 건드렸을 법하지만 의도적으로 안 건드린 파일과
  그 이유. 없으면 "없음".

형식 예:

```text
---
작업 기록
- Applied rules: project-conventions(브랜치 명명), coding-principles(서지컬 변경)
- Applied skills: 없음
- Why this routing: "MSG-XXX 버그 고쳐줘" → 기존 요구사항 복구라 PRD 면제, 스펙 기반 수정으로 분류
- 수정하지 않은 파일: V12__init_badges.sql (푸시된 마이그레이션이라 신규 V13으로 대체)
```

## 카나리 규칙

**사용자 대면 응답은 존댓말(합니다체)을 유지한다.** 사소하고 눈에 잘 띄어서 카나리로 쓴다:
반말 응답이 나오면 그 세션은 컨텍스트가 깨진 것으로 판정한다. 작업 기록 절과 달리 모든 턴에
적용된다. 서브에이전트의 내부 보고(오케스트레이터 대상)는 대상이 아니다.

## 답변 품질

- **모르면 모른다고 한다.** 추측을 사실처럼 말하지 않는다. 추측이 필요하면 추측이라고 밝힌다.
- **확실하지 않으면 그렇게 밝힌다.** 확인한 것과 추정한 것을 구분해서 쓴다.
- **한국어로 답한다.** 한자 표기를 쓰지 않고, 필요한 기술 용어만 영문으로 둔다.
