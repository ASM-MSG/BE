# 마무리 절차 (Phase 5)

통합 확인(빌드·리뷰·Codex)이 끝난 뒤의 마무리 체크리스트. 순서대로 수행한다.

1. 변경된 파일 목록과 함께 요약 보고 (Owner별 구현 내역, 리뷰 통과 여부, 남은 이슈).
2. 이번 작업으로 패키지·계약 인터페이스·엔티티가 planned → partial → built로 바뀌었으면
   `.claude/docs/status.md`의 해당 행을 갱신한다 (구현 현황 문서가 낡지 않게).

2-1. **SRS 상태 갱신과 추적 매트릭스 재생성 (필수, 2026-08-14 신설)**. 구현이 요구사항 상태를
   바꿨으면 `docs/srs.md`의 해당 FR 행을 갱신하고, `docs/srs-changelog.md`에 행을 하나 붙이고,
   `scripts/generate-rtm.sh`를 실행해 `docs/rtm.md`를 재생성해 **같은 브랜치에 함께 커밋한다.**
   CI에 RTM 신선도 검사가 있어 rtm 재생성을 빠뜨리면 빌드가 깨진다.

   - **상태를 올리기 전에 테스트에 `// 검증: FR-XXX-NN` 주석부터 단다.** rtm 스크립트는 그 주석
     줄로만 요구와 테스트를 잇는다(`grep -rlE "// *검증:"` — 파일 단위라 클래스당 한 줄이면 된다).
     주석 없이 상태만 `계획`에서 `진행 중`·`구현됨`으로 올리면 그 요구가 **검증 공백**으로 분류돼
     "구현됐는데 대응 테스트가 없다" 목록에 올라간다. `계획`·`폐기`는 테스트 부재가 정상으로
     처리되므로 상태를 올리는 순간에만 문제가 된다.
   - **요구사항 상태와 그 검증 테스트는 같은 커밋에 들어가야 한다.** 문서 전용 브랜치에서 상태만
     올리면 그 브랜치에 테스트가 없어 공백이 영구히 남는다.
   - 일부만 구현했으면 `구현됨`이 아니라 `진행 중`으로 두고 남은 범위와 담당 티켓을 근거란에
     적는다. 다 된 것처럼 보이는 행이 다음 사람을 오도한다.
   - 배경: MSG-390이 이 절차 없이 머지돼, 구현된 요구가 `계획`으로 실리고 연결 테스트 0건인
     상태가 develop에 들어갔다. 뒤늦게 상태만 올린 문서 브랜치는 CI가 막았다.
3. `docs/spec/MSG-{번호}.md` 하단에 `## 작업 로그` 섹션을 append한다(없으면 생성). 이번 실행에서
   완료한 모듈, 내린 구현 결정, 리뷰 반영 사항, 제안한 커밋 메시지를 날짜 헤더 + 불릿 한 줄들로
   누적 기록한다 — 덮어쓰지 않고 항목만 추가한다(부분 재실행 시 이력 보존). status.md가 "현재 상태"라면
   여기 작업 로그는 "티켓별 시간순 이력"으로 역할을 분리한다.

   **런타임 동작 기록 (필수, 2026-08-03 사용자 지시)**: diff 요약만으로는 나중에 코드를 다시
   읽어도 보이지 않는 실행 시점 사실을 함께 남긴다 — 구현 대부분을 에이전트가 짜므로, 운영
   디버깅과 기술 설명(리뷰·면접)에서 문서만으로 복원 가능해야 한다. 해당되는 항목만 쓰고
   억지로 채우지 않는다:
   - **데이터 저장 위치** — 이번 작업이 새로 쓰거나 바꾼 저장소 전부: 테이블·컬럼(마이그레이션
     파일명), Redis 키 형식·TTL, S3 키 경로 등
   - **실행 쿼리** — 핵심 Repository 메서드가 실제 날리는 SQL. JPA 파생 쿼리는 생성 SQL을
     실측해 적고(메서드명 추정 금지), native는 원문. 전부가 아니라 판정·집계 등 핵심만
   - **예외 흐름** — 어떤 실패가 어디서 `ApiException(XxxErrorCode)`로 던져지고
     `GlobalExceptionHandler`가 어떤 developCode·HTTP로 변환하는지. 핸들러 밖에서 터지는
     예외(필터·스케줄러·비동기 스레드)는 누가 잡거나 삼키는지 명시
   - **빈 동작** — 신설·변경 빈의 생명주기 특이점: `@PostConstruct`/`@PreDestroy`, 스케줄러
     주기·스레드, 자체 executor, 트랜잭션 프록시 경계(자기 호출 함정·afterCommit 훅 등)
4. 커밋 메시지 후보를 `MSG-{번호} {타입}: {요약}` 형식으로 제안한다 — **실제 커밋은 사용자가
   명시적으로 요청할 때만** 수행한다(하네스가 자동으로 커밋/푸시하지 않는다).
5. 스폰된 팀원들에게 `SendMessage`로 종료를 알린다.
6. push·PR 생성은 사용자가 요청할 때만 수행한다. **PR 제목은 커밋 메시지와 동일 형식**
   (`MSG-{번호} {타입}: {요약}` — 타입 생략 금지), **본문은 반드시
   `.github/PULL_REQUEST_TEMPLATE.md`의 헤더 구조 그대로 작성한다**(🎫 관련 티켓 / 작업 내용 /
   🤔 고민한 내용 / 👀 리뷰 포인트) — 자유 형식 섹션 금지. 변경 파일·테스트 수는 "작업 내용",
   핵심 쿼리 실소스·기술적 트레이드오프는 "🤔 고민한 내용", 자신 없는 부분은 "👀 리뷰 포인트"에
   녹인다 (템플릿 미준수로 반복 지적 — PR #70, 2026-07-29).
