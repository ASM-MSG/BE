# Spec Writer

MSG-XX 티켓을 `docs/spec/MSG-XXX.md` 스펙 문서로 만드는 단일 작업 스킬. 실행 모드는
**서브 에이전트** — 이 작업은 결과 하나(파일)만 만들면 끝나는 선형 작업이라 팀 통신
오버헤드가 필요 없다.

## 실행 절차

1. **티켓 맥락 확보 (게이트 판별의 입력)**: **기존 스펙 `docs/spec/MSG-{번호}.md`가 있으면 먼저 읽고**,
   대화에 티켓 설명이 있으면 그대로, 없으면 Jira MCP(`mcp__claude_ai_Atlassian_Rovo__getJiraIssue`)로
   MSG-XX 조회를 시도한다. **게이트보다 먼저다** — 공유 PRD 지목("선행 정본: MSG-239-prd.md" 같은
   문구)이 기존 스펙 상단·티켓 설명에 있어서, 안 읽고 게이트를 돌리면 커버되는 티켓("MSG-201 스펙
   수정해줘" 류)을 "PRD 없음"으로 오판해 중복 PRD를 만든다.
   조회 실패는 여기서 멈출 사유가 아니다 — 확보된 맥락만 들고 게이트로 간다.
2. **PRD 게이트 (필수, 건너뛰기 금지)**: 이 티켓을 **커버하는 PRD**의 존재를 확인한다.
   **선판별 수신**: 호출 측(spec-driven-dev Phase 0)이 자기 게이트에서 이미 확정한 PRD 경로
   (상태 확인·승인 포함) 또는 면제 근거를 전달해 오면, 아래 판별을 반복하지 않고 그 결과를
   그대로 쓴다 — 같은 게이트를 두 번 돌리는 중복만 생략하는 것이지 게이트 없이 진행하는 게
   아니다. 전달이 없으면(단독 호출) 아래를 직접 판별한다.
   스펙은 PRD의 "무엇을/왜"에 "어떻게"를 붙이는 문서라, PRD 없이 쓰면 요구사항을 스펙 작성자가
   즉석에서 지어내게 된다. 판별 순서: ① 전용 `docs/prd/MSG-{번호}-prd.md` ② 1에서 확보한 맥락
   (대화·티켓 설명·기존 스펙)이 정본으로 지목하는 **공유 PRD**(부모 기능 PRD에 이 티켓 범위가
   실제로 들어 있는지 확인 — 예: MSG-201은 `MSG-239-prd.md`가 커버) ③ 아이디어 단계의
   `docs/prd/{kebab-slug}.md`.
   - **있음** → 헤더 `상태:`를 본다 — 판정은 **첫 토큰(공백 전까지) 완전 일치** 기준
     (`검토됨 (부연)` 허용, `검토됨아님` 류 변형 불허), **헤더가 없거나 첫 토큰이
     `초안`/`검토됨`/`확정` 어느 것도 아니면 `초안`으로 취급**(fail-closed,
     spec-driven-dev 게이트와 동일 규칙). `초안`(취급 포함)이면 승인 전이다 — 요약·미해결 질문을 보고하고,
     **미해결 질문이 남아 있으면 답을 PRD에 반영한 뒤** 명시적 승인을 받아 `검토됨`으로 갱신하고
     사용한다(존재 ≠ 승인, 질문 남긴 채 승격 금지 — spec-driven-dev 게이트와 동일 규칙).
     승인된 PRD는 그 **실제 경로**를 요구사항 정본으로 최우선 사용한다(PRD만으로 착수 충분 —
     티켓 설명은 보조 맥락). 대화 내용이 PRD와 어긋나면 PRD를 갱신할지 사용자에게 확인한다 —
     스펙에서 조용히 다르게 쓰지 않는다.
   - **없음** → **먼저 면제 여부를 판단한다** — 기준은 CLAUDE.md "개발 파이프라인" 절이 단일 정본
     ("이 작업이 제품 요구사항을 새로 만들거나 바꾸는가", 설정/의존성 갱신도 요구사항을 바꾸면
     면제 아님). 순서 중요: 이 판단 전에 prd-writer를 부르면 면제 티켓도 무조건 PRD를 만들게 된다.
     **면제면** 근거를 사용자에게 한 줄 알리고 PRD 없이 착수한다(프롬프트에 면제 근거 명시).
     **면제가 아니면** `prd-writer` 스킬을 실행해 PRD를 만들고, 사용자 확인을 받은 뒤 스펙에
     착수한다. PRD도 티켓 설명도 없어 prd-writer 조차 쓸 재료가 없으면 사용자에게 되묻는다 —
     추측하지 않는다.
3. **기존 스펙 확인**: `docs/spec/MSG-{번호}.md`가 이미 있으면 — **호출 측이 "사용자가 스펙 갱신을
   이미 승인함"을 전달했으면(조정 흐름) 이 확인을 생략**하고 그 마커를 프롬프트에 그대로 싣는다.
   전달이 없을 때만 덮어쓰기 전에 diff를 요약해 사용자에게 갱신 의사를 확인한다 — 이미 받은
   승인을 다시 묻지 않는다.
4. `.claude/agents/spec-writer.md`에 정의된 에이전트를 호출한다:

```
Agent(
  subagent_type: "spec-writer",
  prompt: "{게이트에서 확인한 실제 PRD 경로} 를 요구사항 정본으로 먼저 읽어라 — 스펙은 PRD의 FR/비기능에
           '어떻게'만 붙이고, PRD와 어긋나게 쓰지 마라. 보조 맥락: {티켓 설명/Jira 조회 결과/대화 확정
           사항 — 있으면 전달}. docs/spec/MSG-{번호}.md 스펙 문서를 작성하라.
           .claude/rules/glossary.md 용어를 기준으로 쓰고, .claude/docs/infrastructure.md 패키지
           구조를 참고해 Owner A/B/공동을 판정하라."
)
```

프롬프트의 **PRD 경로는 생략 금지** — 절차 2의 게이트가 확인만 하고 여기서 안 넘기면 에이전트는
티켓 텍스트만 보고 요구사항을 재창작한다(게이트 무력화). 면제 경로(PRD 없음)로 왔을 때만 PRD 문장을
빼고 면제 근거를 한 줄 대신 넣는다. **절차 3에서 기존 스펙 갱신 승인을 받았으면 "사용자가 스펙
갱신을 이미 승인함"도 프롬프트에 명시**한다 — 안 넣으면 에이전트가 덮어쓰기 확인을 다시 물어
방금 받은 승인을 반복하는 교착이 된다.

5. **완료 정의 검사 (기계, 필수)**: 에이전트가 파일을 반환하면 Codex 리뷰보다 **먼저**
   `python3 scripts/check-spec.py docs/spec/MSG-{번호}.md`를 실행한다. 이 스크립트가 아래
   "완료의 정의"의 기계 항목(S1~S10)을 돌려 항목마다 PASS/FAIL/WARN/INFO와 증거(줄 번호·실측값)를
   찍는다. 에이전트 정의에는 Bash가 없으므로 실행은 이 스킬(호출 측) 몫이다.
   - **FAIL이 있으면 절차 6의 `SendMessage`와 같은 방식으로 원저자 에이전트에게 항목 코드·줄 번호를
     보내 고치게 하고 재실행한다.** 통과할 때까지 Codex 리뷰로 넘어가지 않는다. 줄표·각주 불일치·AC
     번호 같은 형식 결함을 Codex 라운드(상한 4회)에 쓰는 것은 낭비다.
   - 첫 실행에서 FAIL이 2건 이상이면 고치기 전에 **원인을 한 줄로 진단**한다(에이전트 프롬프트
     누락인지, 템플릿이 낡았는지, 규칙이 SKILL.md·agents/spec-writer.md 어디에도 없는지). 같은 항목이
     티켓을 바꿔 가며 반복되면 그 자리에서 리마인더가 아니라 규칙을 고치고 `CLAUDE-changelog.md`에
     행을 붙인다.
   - WARN·INFO는 고치지 않아도 되지만 보고에서 지우지 않는다. 지우면 다음 사람이 확인 안 된 것을
     확인된 것으로 읽는다.
6. **Codex 교차 리뷰 (필수, 생략 금지)**: 완료 정의 검사를 통과한 스펙에 대해, 사용자에게 보고하기
   **전에** 리뷰를 돌린다. 절차·라운드 상한·플러그인 부재 처리는
   `.claude/skills/spec-driven-dev/references/codex-review-loop.md`를 읽고 그대로 따르되 두 가지를
   치환한다 — 수정 지시 대상은 개발 에이전트가 아니라 **방금 스펙을 쓴 spec-writer 에이전트**이고,
   수렴 판정 대상은 빌드가 아니라 **스펙 문서 자체**다.
   - **재개 주소는 절차 4의 `Agent` 호출이 반환한 `agentId`다.** 이 스킬은 이름 없이 스폰하므로
     팀 규칙의 "이름이 곧 식별자"가 적용되지 않는다. `SendMessage(to: "{agentId}", ...)`로 재개하면
     그 에이전트가 자기 트랜스크립트를 그대로 이어받는다(완료 상태여도 재개된다). **고칠 절과 근거만
     보내고 스펙 전체 재작성은 시키지 않는다.**
   - **재개는 비동기다. 완료 통지를 받기 전에 다음 라운드를 돌리지 않는다.** `SendMessage`는 즉시
     반환하므로, 통지를 안 기다리면 다음 리뷰가 옛 스펙이나 절반만 고쳐진 스펙을 읽는다. 라운드를
     헛되이 쓰거나 더 나쁘게는 "신규 지적 없음"을 잘못 선언하게 된다. 수정 완료 통지를 받고 나서
     리뷰를 재실행한다.
   - 새 스펙 파일은 untracked라 diff에 안 잡힌다. 리뷰 전에 `git add -N docs/spec/MSG-{번호}.md`로
     노출시킨다. 이 한 줄을 빼면 리뷰가 "변경 없음"을 보고 아무것도 안 읽는다.
   - 지적은 **먼저 코드·문서로 사실 확인**한 뒤 사실인 것만 넘긴다. 스펙 리뷰의 오탐은 주로
     "규칙 인용 오적용"이다(예: 초안 PRD용 게이트 조항을 승인된 PRD에 적용). 채택하지 않은 지적은
     사용자 보고에 근거와 함께 남긴다.
   - 하네스 파일 등 이 티켓과 무관한 미커밋 변경이 함께 잡히면 그 지적은 분리해 별도 보고한다
     (수렴 판정에서 제외 — 참조 문서의 스코프 주의와 같은 규칙).
7. **재검사 후 보고**: 리뷰 반영이 끝난 파일에 `check-spec.py`를 **한 번 더** 돌린다. 리뷰 라운드의
   수정이 줄표나 각주 고아를 다시 만든 실측이 있다(MSG-608: 결정 종결 메모 3줄에 줄표, 각주 2번
   정의만 남음). 그 출력 **전문**을 보고 하단에 붙이고, 에이전트가 반환한 결과(생성된 파일 경로 +
   Owner 판정 + 미해결 질문 유무)와 **리뷰 결과(적발·반영 항목, 미채택 지적과 그 근거)** 를
   요약해 보여준다. 미해결 질문이 있으면 구현 착수 전에 먼저 해소하도록 안내한다.
   FAIL이 남은 채로 보고하지 않는다. 사용자가 "그냥 두자"고 한 항목만 그 말을 인용해 남긴다.

## 완료의 정의

"읽어 보니 괜찮다"는 검증이 아니다. 아래 항목이 전부 증거와 함께 확인됐을 때 스펙이 완료다.
기계 항목은 `scripts/check-spec.py`가 판정하고(항목 정의와 등급은 그 파일 상단 docstring이 정본,
여기 사본을 두지 않는다), 사람 항목은 스킬이 파일을 읽고 판단해 보고에 한 줄씩 적는다.

**기계 항목 (check-spec.py, FAIL이면 미완료)**: S1 파일명·제목 번호 / S2 Owner / S3 정본 PRD 실존·승인
또는 면제 선언 / S4 FR·NFR ID가 SRS 표에 실존 / S5 AC 형식·번호 / S6 필수 절 8종 / S7 본문 줄표 0건 /
S8 각주 참조·정의 1:1 / S9 변경 파일 경로(WARN) / S10 미종결 질문(INFO).

**사람 항목 (스킬이 판단, 보고에 근거 한 줄)**:
- **H1 PRD 범위 일치**: 스펙의 성공 기준 각 AC가 PRD의 FR/US 중 어느 것을 구현하는지 대응되고, PRD에
  없는 요구를 스펙이 새로 만들지 않았다. 대응이 안 되는 AC가 있으면 PRD 갱신 여부를 사용자에게
  묻는다(절차 2의 "조용히 다르게 쓰지 않는다"와 같은 규칙).
- **H2 판정 가능성**: AC 문장마다 "무엇을 보면 통과인지"가 있다. 수치 요구에는 값과 단위가 있고
  "적절히", "빠르게", "충분히" 같은 말이 없다(srs-writer 작성 원칙과 동일).
- **H3 계약 변경 노출**: 계약 인터페이스 4종 시그니처가 바뀌면 `## 계약 변경`에 따로 적혀 있고,
  안 바뀌면 "없음"이다. 본문 어딘가에 흘려 쓰고 절은 "없음"인 상태가 가장 위험하다.
- **H4 용어**: glossary.md 용어와 어긋나는 쓰임(점령의 개인/전역, 방문과 수집 혼용)이 없다.

**보고 형식**: 기계 항목은 스크립트 출력 전문, 사람 항목은 `H1 PASS (AC-01~05 ↔ PRD FR-1~3, 신규 요구
없음)`처럼 판정과 근거를 한 줄. 확인하지 못한 항목은 "미확인"이라고 적는다. 생략과 미확인은 달라야
탐지가 된다(응답 컨트랙트와 같은 규칙).

낡은 것(AC 없음, 줄표 본문, PRD 게이트 전)이 다수라 아무거나 참고하면 낡은 형식을 베낀다.

## 후속 처리

사용자가 스펙 확인 후 "이제 개발 시작해줘"라고 하면 `spec-driven-dev` 스킬로 넘어간다 —
이 스킬이 직접 구현까지 하지 않는다.

## 테스트 시나리오

- **정상 흐름 (PRD 있음)**: "MSG-42 스펙 만들어줘" + `docs/prd/MSG-42-prd.md` 존재 →
  게이트 통과, 에이전트 프롬프트에 그 경로 명시 → `docs/spec/MSG-42.md` 생성 → `check-spec.py`
  실행, FAIL 0 확인(FAIL이면 원저자 수정 후 재실행) → `git add -N` 후 Codex 리뷰 → 지적 사실 확인 →
  원저자 에이전트가 해당 절 수정 → 재리뷰가 신규 지적 없음 → `check-spec.py` 재실행 → 스크립트
  출력 전문 + H1~H4 판정 + 적발·반영 내역과 함께 사용자 보고.
- **검사 실패 흐름**: 생성된 스펙에 `check-spec.py`가 `FAIL S7 본문에 줄표 (3줄: [75, 117, 254])`,
  `FAIL S8 참조 없는 정의 ['2']`를 찍음 → 2건이라 원인 한 줄 진단(수정 라운드가 문체 조항을 안
  거침) → 원저자에게 줄 번호와 함께 수정 요청 → 재실행 FAIL 0 → 그제야 Codex 리뷰.
- **게이트 흐름 (PRD 없음, 새 기능)**: "MSG-43 스펙 만들어줘, 티켓 내용은 [스폰서 격자 입찰 API]"
  + PRD 없음 → 면제 아님(새 API) → `prd-writer` 먼저 실행 → 사용자 확인 후 스펙 착수.
- **면제 흐름**: "MSG-44 스펙 만들어줘 — Flyway 버전 충돌 가드 CI" + PRD 없음 → 제품 요구사항을
  만들지도 바꾸지도 않는 작업이라 면제, 근거 한 줄 알리고 에이전트 프롬프트에 면제 근거를 넣어 착수.
- **에러 흐름**: "MSG-77 스펙 만들어줘"만 입력 + PRD 없음 + 티켓 설명 없음 + Jira 미연결 →
  요구사항 확보 불가 — 사용자에게 되묻고 진행하지 않음.
