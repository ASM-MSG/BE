# Backend Audit — 백엔드 전수 감사

2026-09-07 박원형 멘토링의 결론은 "기능은 달렸으니 실제 쿼리·트랜잭션 동작을 확인하고 팀이
코드를 설명할 수 있게 재정비하자"였다. 멘토는 일부 코드만 보고 말했으므로 같은 지적이 레포 어디에
또 있는지, 그리고 지적이 사실인지(추측인지)를 전수로 가려야 한다. 이 스킬은 그 감사를 **반복
가능하게** 만든다 — 10월 8일 다음 멘토링 전에 한 번 더 돌려 전후를 비교하는 것이 목적이다.

이 스킬은 **고치지 않는다.** 산출물은 검토 보고서 하나이고 리팩터링·티켓 발행은 사람이 보고서를
읽고 결정한다. 이유는 멘토 스스로 "전체 코드를 이해한 상태가 아니라 오판 가능성이 있다"고 했기
때문이다 — 감사 결과도 결함 목록이 아니라 **검토 목록**이며, 보고서는 항목마다 사실과 추측을
가른다.

## 렌즈 8개

| ID | 별칭(인자로 쓰는 말) | 질문 |
|---|---|---|
| `native` | 네이티브, native | native 108건 중 PostgreSQL 전용이라 불가피한 것과 JPQL·파생 쿼리로 갈 수 있는 것은? |
| `plan` | 실행계획, SQL, 인덱스 | 주요 API가 **실제로** 실행하는 SQL은 무엇이고 인덱스를 타는가, 반복 실행(N+1)은 없나? |
| `tx` | 트랜잭션, 영상저장 | `@Transactional` 안에서 S3·HTTP·Kafka·Redis·메일을 부르는 곳은? 커넥션을 얼마나 오래 잡나? |
| `osiv` | OSIV | OSIV가 켜져 있는데 끄면 어디가 깨지나(트랜잭션 밖 지연 로딩)? |
| `tz` | 시간대, 타임존, Clock | 서버·JVM·JDBC·DB 컬럼·`Clock`의 시간대 기준이 한 줄로 설명되나? |
| `calls` | 호출구조, 계층, 진입점 | 서비스→서비스 호출 방향·순환·트랜잭션 진입점과 롤백 범위는? |
| `naming` | 명명, 가독성 | View·Projection·ResponseDto의 역할 구분, 긴 필터·변환 메서드, 흩어진 상수는? |
| `iface` | 인터페이스, 분리 | 구현체가 하나뿐인 Service 인터페이스 중 계약(도메인 경계)이 아닌 것은? |

인자 없이 부르면 8개 전부. `/backend-audit 트랜잭션 OSIV`처럼 별칭을 나열하면 그 렌즈만 돈다
(별칭은 부분 일치·대소문자 무시로 위 표에 맞춘다). 렌즈별 검토 기준·함정·이미 규칙으로 막힌 것은
`references/lenses.md`에 있다 — **각 렌즈 에이전트가 자기 절만 읽는다**, 리더는 미리 다 읽지 않는다.

## 전제

- `plan` 렌즈(그리고 그 캡처를 읽는 `tx`)의 실측은 로컬 PostgreSQL이 떠 있어야 한다
  (`docker compose ps postgres`). 안 떠 있으면 그 렌즈는 정적 분석만 하고 보고서에 "미실측"을
  남긴다 — 실측 없는 판단을 실측처럼 쓰지 않는다.
- 작업 브랜치에서 돈다 (develop 직접 수정 금지, 보고서도 파일이다). 커밋은 사용자 몫.
- 스크립트는 `scripts/`에 있고 실행 전 읽지 않아도 된다. 세 개다:
  `inventory.sh`(정적 기준선 카운트), `capture-sql.sh <라벨> -- <명령>`(DB 로그로 실제 실행문·
  횟수·소요 캡처), `explain.sh "<SQL>"`(EXPLAIN ANALYZE). 뒤의 둘은 `pg-container.sh`로 로컬
  컨테이너를 compose 라벨로 고른다 — 서버 스택(`fillmap-postgres-dev/-prod`)이 같은 호스트에
  보여도 잡히지 않고, 후보가 하나가 아니면 실행을 거부한다.

## 워크플로우

### 1. 기준선

`scripts/inventory.sh > /tmp/backend-audit/inventory.md` 를 먼저 돌린다. 렌즈 에이전트 8개가
같은 grep을 반복하지 않게 하고, 보고서 헤더의 숫자(커밋·native 수·@Transactional 수)를
한 출처에서 가져오기 위해서다. 숫자는 기준선일 뿐이고 판정은 파일을 열어서 한다.

이전 보고서가 `docs/audit/`에 있으면 최신 것의 경로를 기억해 둔다 — 3단계에서 전후 비교에 쓴다.

### 2. 렌즈 에이전트 병렬 실행 — 렌즈 8개를 에이전트 4개로 묶는다

렌즈마다 에이전트를 하나씩 띄우지 않는다. 같은 파일을 읽는 렌즈끼리 묶으면 읽기가 한 번으로 끝나고,
tx·osiv·calls는 어차피 서비스 호출 그래프 하나를 공유한다. 묶음은 고정이다:

| 에이전트 | 렌즈 | 함께 묶는 이유 |
|---|---|---|
| `query` | native · plan | 둘 다 리포지토리 쿼리를 읽고, plan의 실측 대상은 native 분류에서 고른다 |
| `boundary` | tx · osiv · calls | 셋 다 서비스 호출 그래프와 `@Transactional` 경계를 재료로 쓴다 |
| `time` | tz | 설정·마이그레이션 중심이라 다른 렌즈와 파일이 안 겹친다 |
| `shape` | naming · iface | 둘 다 Service·DTO 파일의 분포를 센다 |

선택된 렌즈가 속한 에이전트만 `Agent`(general-purpose)로 **한 턴에 전부** 스폰한다. 렌즈 하나만
골라도 그 에이전트는 그 렌즈만 본다. `model`은 지정하지 않는다(판단 작업이라 세션 모델 상속 —
`subagent-orchestration.md`). DB 로깅 토글(`capture-sql.sh`)은 **`query` 에이전트만** 켠다 — 두
에이전트가 동시에 켰다 끄면 서로의 캡처가 끊긴다. `boundary`의 소요 실측은 `/tmp/backend-audit/*.log`에
이미 캡처된 것을 읽고, 없으면 "미실측"으로 둔다.

서브에이전트가 없는 도구(Codex 등)에서는 같은 세션이 네 묶음을 순서대로 돈다 — 스크립트와 보고
형식은 도구를 가리지 않는다.

각 에이전트 프롬프트에 넣을 것:

- 맡은 렌즈 ID들과 `references/lenses.md`의 **해당 절만** 읽으라는 지시, `inventory.md` 경로.
- 읽기 전용이라는 점. 코드를 고치지 않고, 스크립트(`capture-sql.sh`·`explain.sh`)는 실행해도 된다.
- **하위 에이전트를 더 띄우지 않는다.** 렌즈 에이전트가 파일 묶음별로 다시 에이전트를 나누면
  같은 렌즈 안에서 판정 기준이 갈리고 토큰이 몇 배로 든다(초기 시험 실행에서 tx 렌즈 하나가
  3개로 갈라져 각각 20만 토큰을 썼다). 범위가 크면 25개 상한으로 접는다.
- 보고 형식(아래) — 렌즈마다 따로 한 블록씩. 항목마다 `파일:줄`, **관찰(사실)과 판단(해석)을 다른
  칸에**, 실측했으면 실측값, 못 했으면 "미실측". 추측은 "추측:"으로 시작한다.
- **"왜 이렇게 됐나" 근거 찾기**: 항목의 클래스·패턴으로 `docs/spec/`·`docs/prd/`·`.claude/rules/`·
  `../LLM-WIKI/04-decisions/`를 grep해 결정 문서를 링크한다. 없으면 "근거 문서 없음"이라고 적는다 —
  멘토가 가장 강조한 것이 "AI가 짜서 이렇게 됐다로 끝내지 말라"이므로, 근거 문서가 없는 항목은
  그 자체가 팀이 설명 못 하는 지점이다.
- 렌즈가 이미 규칙으로 막고 있는 것(예: 맨 `LocalDateTime.now()` 금지)은 "규칙으로 차단됨 — 위반
  0건"처럼 한 줄로만 적고 항목을 만들지 않는다.
- 범위 상한: 렌즈당 항목 25개 이내. 넘치면 우선순위 상위만 적고 나머지는 "같은 패턴 N곳"으로 접는다.
  보고서는 팀이 읽고 토론하는 자료라 길면 안 읽힌다.

렌즈 에이전트 보고 형식:

```text
## 렌즈: {ID}
### 요약 (3줄 이내)
### 발견
| # | 위치 | 관찰(사실) | 근거(실측값·문서 링크) | 판단 | 우선순위 |
### 규칙으로 차단됨
### 실측 로그 (plan·tx만) — capture-sql.sh 출력 요약, 원본 경로
### 한계·미확인
```

우선순위 기준은 세 단계다. **P1** 실측 또는 코드로 문제가 확인됨(느린 플랜, 트랜잭션 안 S3 호출,
OSIV 끄면 깨질 곳). **P2** 코드상 위험하나 실측 못 함 또는 상황 의존. **P3** 정리·가독성 제안.

### 3. 보고서 조립

`references/report-template.md` 틀로 `docs/audit/{YYYY-MM-DD}-backend-audit.md`를 쓴다.
일부 렌즈만 돌렸으면 파일명 끝에 렌즈 ID를 붙인다(`-tx-osiv`). 조립할 때 할 일:

- **교차 병합**: 같은 파일이 여러 렌즈에 나오면(예: `VideoServiceImpl`이 tx·osiv·calls에) 한
  항목으로 합치고 렌즈 태그를 나열한다. 팀은 파일 단위로 고치지 렌즈 단위로 고치지 않는다.
- **전후 비교**: 이전 보고서가 있으면 "이전 감사 대비" 절에 해소·신규·유지 항목을 센다.
- **팀 설명 자료** 절: 핵심 흐름(영상 저장·격자 뷰포트·이벤트 영상 목록·뱃지 지급)마다 "왜 이렇게
  했나"의 근거 문서 링크를 모은다. 근거가 없는 흐름은 그대로 "없음"으로 남긴다.
- 에이전트가 "추측"이라 한 것은 보고서에서도 추측으로 남긴다. 리더가 사실로 승격하지 않는다.

### 4. 마무리

코드를 고치지 않았고 티켓도 만들지 않았음을 밝히고, 보고서 경로·P1 개수·미실측 렌즈를 알린다.
응답 끝에 `agent-response-contract.md`의 작업 근거 4항목을 붙인다.

## 하지 않는 것

- 코드·설정 수정, 마이그레이션 추가, 티켓 발행. 보고서가 유일한 산출물이다.
- dev/prod DB 접속. 실측은 로컬 컨테이너에서만 한다 — 로컬은 행 수가 적어 플래너가 Seq Scan을
  고를 수 있으니 플랜 판정에 `rows=`를 같이 적고 "dev 실측 필요"를 표기한다.
- 멘토 제안(QueryDSL·Command/Query 분리·비동기 분리)의 채택 여부 판단. 보고서는 그 판단에
  필요한 현황과 근거를 준다.
