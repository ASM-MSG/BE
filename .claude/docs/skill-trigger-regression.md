# 스킬 자동 호출 회귀 확인 (MSG-529)

스킬 description을 고치면 자동 호출 동작이 바뀌는데, 바뀌었는지 확인하는 절차가 없으면 조용히
깨진다. 스킬이 안 불리면 오류가 나는 게 아니라 **규칙이 빠진 결과물이 그냥 나온다** — 리뷰를
통째로 건너뛴 사고와 같은 형태다. 이 문서가 그 확인 절차의 정본이다.

## 판정 근거 — hook 호출 로그

`.claude/settings.json`의 PostToolUse hook(matcher `Skill`)이 모든 스킬 호출을
`.claude/logs/skill-calls.jsonl`에 남긴다(gitignore 대상, 한 줄 = 한 호출).
플러그인 스킬도 `plugin:skill` 이름으로 같이 잡힌다.

```json
{"ts": "2026-08-31T06:53:39+00:00", "session": "...", "skill": "prd-writer", "args": "MSG-999"}
```

판정은 응답 텍스트가 아니라 **이 로그로** 한다. 모델의 자기 보고(응답 컨트랙트의 Applied
skills)는 컨텍스트가 깨지면 같이 사라질 수 있지만, 로그는 모델 협조와 무관하다. 둘을 대조하면
거짓 보고(적었는데 실제로는 안 부름)까지 잡힌다.

## 언제 돌리나

스킬 description(SKILL.md frontmatter)을 고치는 PR에서, **고친 스킬의 문장 세트만** 돌린다.
전수 확인은 비용 대비 이득이 없다. 결과는 아래 기록 양식으로 PR 본문에 남긴다.

## 절차 (문장당 1회)

1. 로그의 현재 끝을 확인한다: `wc -l .claude/logs/skill-calls.jsonl` (파일이 없으면 0).
2. **새 세션**을 열고 문장을 그대로 입력한다. 기존 세션 재사용 금지 — 앞 대화가 판정을 오염시킨다.
3. 스킬 호출 여부가 갈리는 즉시 세션을 중단한다(Esc). 작업이 실제로 진행될 필요는 없다 —
   판정 대상은 Skill 호출 발생 여부 하나다.
4. 로그에 새로 붙은 줄을 본다: `tail -5 .claude/logs/skill-calls.jsonl`. 해당 스킬이 찍혔으면
   "호출", 없으면 "미호출".
5. 기대와 비교해 기록한다. 기대가 "미호출"인데 찍혔으면 과잉 호출로 실패다 — 단순 질문에
   PRD 게이트가 걸리면 우회 유인이 생긴다.

## 문장 세트

description의 트리거 예시를 출발점으로 삼았다. 미호출 문장은 근처 개념의 조회·읽기·상태
질문이다 — 스킬은 문서를 만들거나 절차를 시작할 때 불려야지, 읽고 답할 때 불리면 안 된다.

### prd-writer

| 문장 | 기대 |
|---|---|
| "MSG-999 PRD 만들어줘" | 호출 |
| "요구사항 문서 정리해줘" | 호출 |
| "개발 전에 문서부터 정리하자" | 호출 |
| "이 아이디어 PRD로 뽑아줘" (티켓 없는 아이디어) | 호출 |
| "MSG-363 PRD 읽고 요약해줘" | 미호출 |
| "PRD 문서 어디에 있지?" | 미호출 |

### spec-writer

| 문장 | 기대 |
|---|---|
| "MSG-999 스펙 만들어줘" | 호출 |
| "스펙 문서 정리해줘" | 호출 |
| "MSG-999 스펙 다시 써줘" | 호출 |
| "MSG-341 스펙 보고 설명해줘" | 미호출 |
| "스펙에 성공 기준이 뭐라고 돼 있지?" | 미호출 |

### spec-driven-dev

| 문장 | 기대 |
|---|---|
| "MSG-999 개발 시작" | 호출 |
| "스펙대로 개발해줘" | 호출 |
| "MSG-999 이어서 개발" | 호출 |
| "MSG-999 리뷰 반영해서 다시" | 호출 |
| "MSG-999 개발 어디까지 됐지?" | 미호출 |
| "이 파일 오타 하나만 고쳐줘" | 미호출 |

### srs-writer

| 문장 | 기대 |
|---|---|
| "이 요구사항 SRS에 등재해줘" | 호출 |
| "전체 요구사항 뭐뭐 있지?" | 호출 |
| "이 정책 이렇게 확정됐어, 반영해줘" | 호출 |

| "srs.md 열어서 보여줘" | 미호출 |

## 체이닝 확인 2건

스킬 하나가 다른 스킬을 연쇄로 부르는 경로도 로그로 확인한다. 로그에 두 스킬이 순서대로
찍혀야 통과다.

1. **spec-driven-dev → prd-writer**: PRD·스펙이 없는 티켓으로 "MSG-999 개발 시작" →
   로그에 `spec-driven-dev` 다음 `prd-writer`가 찍힌다 (게이트 동작).
2. **prd-writer → srs-writer**: PRD 작성을 리서치 단계까지 진행 → 로그에 `prd-writer` 다음
   `srs-writer`가 찍힌다 (SRS 대조 소프트 편입).

체이닝 확인은 실제 작업이 어느 정도 진행돼야 하므로, 존재하지 않는 티켓 번호(MSG-999)를 써서
파일이 만들어지기 전에 중단한다.

## 기록 양식 (PR 본문용)

| 문장 | 기대 | 실제 | 판정 |
|---|---|---|---|
| "MSG-999 PRD 만들어줘" | 호출 | 호출 | 통과 |
| "PRD 문서 어디에 있지?" | 미호출 | 호출 | **실패 (과잉)** |

실패가 있으면 description을 다시 고치고 실패한 문장만 재확인한다.
