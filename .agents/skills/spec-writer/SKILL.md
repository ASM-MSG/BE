# Spec Writer

MSG-XX 티켓을 `docs/spec/MSG-XXX.md` 스펙 문서로 만드는 단일 작업 스킬. 이 환경에는 서브
에이전트가 없으므로 **같은 세션에서 순서대로 직접 수행한다**. 결과가 파일 하나뿐인 선형
작업이라 위임할 이유도 없다.

## 실행 절차

1. **티켓 맥락 확보 (게이트 판별의 입력)**: **기존 스펙 `docs/spec/MSG-{번호}.md`가 있으면 먼저 읽고**,
   대화에 티켓 설명이 있으면 그대로, 없으면 이 환경에서 쓸 수 있는 Jira 연동으로
   MSG-XX 조회를 시도한다. **게이트보다 먼저다** — 공유 PRD 지목("선행 정본: MSG-239-prd.md" 같은
   문구)이 기존 스펙 상단·티켓 설명에 있어서, 안 읽고 게이트를 돌리면 커버되는 티켓("MSG-201 스펙
   수정해줘" 류)을 "PRD 없음"으로 오판해 중복 PRD를 만든다.
   조회 실패는 여기서 멈출 사유가 아니다 — 확보된 맥락만 들고 게이트로 간다.
2. **PRD 게이트 (필수, 건너뛰기 금지)**: 이 티켓을 **커버하는 PRD**의 존재를 확인한다.
   **선판별 수신**: 호출 측(spec-driven-dev Phase 0)이 자기 게이트에서 이미 확정한 PRD 경로
   (상태 확인·승인 포함) 또는 면제 근거를 전달해 오면, 아래 판별을 반복하지 않고 그 결과를
   그대로 쓴다 — 같은 게이트를 두 번 돌리는 중복만 생략하는 것이지 게이트 없이 진행하는 게
   아니다. 전달이 없으면(단독 호출) 아래를 직접 판별한다.
   스펙은 PRD의 "무엇을/왜"에 "어떻게"를 붙이는 문서라, PRD 없이 쓰면 요구사항을 스펙 작성자가
   즉석에서 지어내게 된다. 판별 순서: ① 전용 `docs/prd/MSG-{번호}-prd.md` ② 1에서 확보한 맥락
   (대화·티켓 설명·기존 스펙)이 정본으로 지목하는 **공유 PRD**(부모 기능 PRD에 이 티켓 범위가
   실제로 들어 있는지 확인 — 예: MSG-201은 `MSG-239-prd.md`가 커버) ③ 아이디어 단계의
   `docs/prd/{kebab-slug}.md`.
   - **있음** → 헤더 `상태:`를 본다 — 판정은 **첫 토큰(공백 전까지) 완전 일치** 기준
     (`검토됨 (부연)` 허용, `검토됨아님` 류 변형 불허), **헤더가 없거나 첫 토큰이
     `초안`/`검토됨`/`확정` 어느 것도 아니면 `초안`으로 취급**(fail-closed,
     spec-driven-dev 게이트와 동일 규칙). `초안`(취급 포함)이면 승인 전이다 — 요약·미해결 질문을 보고하고,
     **미해결 질문이 남아 있으면 답을 PRD에 반영한 뒤** 명시적 승인을 받아 `검토됨`으로 갱신하고
     사용한다(존재 ≠ 승인, 질문 남긴 채 승격 금지 — spec-driven-dev 게이트와 동일 규칙).
     승인된 PRD는 그 **실제 경로**를 요구사항 정본으로 최우선 사용한다(PRD만으로 착수 충분 —
     티켓 설명은 보조 맥락). 대화 내용이 PRD와 어긋나면 PRD를 갱신할지 사용자에게 확인한다 —
     스펙에서 조용히 다르게 쓰지 않는다.
   - **없음** → **먼저 면제 여부를 판단한다** — 기준은 AGENTS.md "개발 파이프라인" 절이 단일 정본
     ("이 작업이 제품 요구사항을 새로 만들거나 바꾸는가", 설정/의존성 갱신도 요구사항을 바꾸면
     면제 아님). 순서 중요: 이 판단 전에 prd-writer를 부르면 면제 티켓도 무조건 PRD를 만들게 된다.
     **면제면** 근거를 사용자에게 한 줄 알리고 PRD 없이 착수한다(면제 근거를 스펙 상단에 남긴다).
     **면제가 아니면** `prd-writer` 스킬을 실행해 PRD를 만들고, 사용자 확인을 받은 뒤 스펙에
     착수한다. PRD도 티켓 설명도 없어 prd-writer 조차 쓸 재료가 없으면 사용자에게 되묻는다 —
     추측하지 않는다.
3. **기존 스펙 확인**: `docs/spec/MSG-{번호}.md`가 이미 있으면 — **호출 측이 "사용자가 스펙 갱신을
   이미 승인함"을 전달했으면(조정 흐름) 이 확인을 생략**하고 그대로 진행한다.
   전달이 없을 때만 덮어쓰기 전에 diff를 요약해 사용자에게 갱신 의사를 확인한다 — 이미 받은
   승인을 다시 묻지 않는다.
4. **`.codex/agents/spec-writer.toml`을 읽고 그 역할 정의대로 직접 작성한다.** 이 환경에는 서브
   에이전트를 스폰하는 수단이 없으므로 위임하지 않고 같은 세션에서 쓴다. toml의 지시(용어 기준,
   Owner 판정 근거, 출력 구성)가 곧 작성 규칙이다.

   착수 전에 아래를 손에 쥔다. 하나라도 비면 그 상태로 쓰지 말고 절차 1~3으로 돌아간다.

   - **게이트에서 확인한 실제 PRD 경로** — 스펙은 PRD의 FR과 비기능에 "어떻게"만 붙인다.
     경로를 놓치면 티켓 텍스트만 보고 요구사항을 재창작하게 되어 게이트가 무력해진다.
     면제 경로로 왔으면 PRD 대신 면제 근거 한 줄을 근거로 삼는다
   - **보조 맥락** — 티켓 설명, Jira 조회 결과, 대화에서 확정된 사항
   - **기존 스펙 갱신 여부** — 절차 3에서 승인을 받았으면 덮어쓰기를 다시 묻지 않는다

   작성 기준은 `.claude/rules/glossary.md` 용어이고, Owner A/B/공동 판정은 **AGENTS.md "협업 원칙"의
   패키지 목록**을 근거로 한다. `.claude/docs/infrastructure.md`는 패키지 구조를 이해하는 참고 자료이지
   오너 배정의 근거가 아니다 — 그쪽이 낡으면 엉뚱한 도메인에 일이 배정된다.

5. 작성 결과(파일 경로 + Owner 판정 + 미해결 질문 유무)를 사용자에게 요약해 보여준다.
   미해결 질문이 있으면 구현 착수 전에 먼저 해소하도록 안내한다.

## 후속 처리

사용자가 스펙 확인 후 "이제 개발 시작해줘"라고 하면 `spec-driven-dev` 스킬로 넘어간다 —
이 스킬이 직접 구현까지 하지 않는다.

## 테스트 시나리오

- **정상 흐름 (PRD 있음)**: "MSG-42 스펙 만들어줘" + `docs/prd/MSG-42-prd.md` 존재 →
  게이트 통과, 그 경로를 요구사항 정본으로 삼아 `docs/spec/MSG-42.md` 작성.
- **게이트 흐름 (PRD 없음, 새 기능)**: "MSG-43 스펙 만들어줘, 티켓 내용은 [스폰서 격자 입찰 API]"
  + PRD 없음 → 면제 아님(새 API) → `prd-writer` 먼저 실행 → 사용자 확인 후 스펙 착수.
- **면제 흐름**: "MSG-44 스펙 만들어줘 — Flyway 버전 충돌 가드 CI" + PRD 없음 → 제품 요구사항을
  만들지도 바꾸지도 않는 작업이라 면제, 근거 한 줄 알리고 그 근거를 스펙 상단에 남기고 착수.
- **에러 흐름**: "MSG-77 스펙 만들어줘"만 입력 + PRD 없음 + 티켓 설명 없음 + Jira 미연결 →
  요구사항 확보 불가 — 사용자에게 되묻고 진행하지 않음.
