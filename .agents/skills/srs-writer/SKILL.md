# SRS Writer

프로젝트 전역 요구사항 명세 `docs/srs.md` 하나를 만들고 계속 갱신한다. 실행 모드는 **인라인** —
등재할 요구는 대화에 흐르는 맥락에서 나오고 정합 판정에 문서 전체를 봐야 해서, 서브에이전트로
격리하면 맥락을 잃고 기존 항목과 어긋난 것을 등재한다.

## 문서 4종의 역할 경계

| 문서 | 질문 | 단위 | 담당 |
|------|------|------|------|
| SRS (`docs/srs.md`) | 서비스가 충족해야 할 요구사항 전체가 무엇인가 | **전역 1개** | **srs-writer (이 스킬)** |
| PRD (`docs/prd/*.md`) | 이 기능을 무엇을·왜 만드는가 | 기능/티켓 | prd-writer |
| 스펙 (`docs/spec/MSG-XXX.md`) | 어떻게 구현하는가 | 티켓 | spec-writer |
| 코드 | 구현 | | spec-driven-dev |

파이프라인: **SRS 등재 → PRD → (지라 티켓) → 스펙 → 구현**.

SRS는 티켓마다 쓰는 문서가 아니다. **전역 1개를 계속 갱신하는 living document**이고 티켓은 ID를
참조만 한다. 티켓별로 쓰면 PRD와 내용이 대부분 겹쳐 문서 부담만 늘고, 정작 "지금 서비스 요구사항
전체가 뭐냐"에는 여전히 답하지 못한다.

**게이트는 소프트다.** SRS 등재가 PRD 착수의 차단 조건은 아니다. prd-writer 리서치 단계에서
대조하고 신규 요구면 등재한다. 스톱 게이트를 하나 더 만들지 않는 이유는 요구사항을 새로 만드는
작업이 어차피 PRD 게이트를 통과하기 때문이다. 문서 단계가 늘수록 우회 유인이 커진다.

## 요구사항 ID 체계

```text
FR-{영역코드}-{2자리}    기능 요구사항    예: FR-GRID-01, FR-BADGE-07
NFR-{분류}-{2자리}       비기능 요구사항  예: NFR-PERF-01, NFR-SEC-03
```

영역코드는 기능 영역(GRID·ZONE·REGION·SEARCH·HOTZONE·VIDEO·COLLECT·BADGE·STREAK·MISSION·
NOTI·FRIEND·MOD·AUTH·USER)이고 NFR 분류는 PERF·SEC·DATA·OPS 넷이다. 새 영역이 필요하면
SRS 상단 영역 목록에 추가하고 쓴다.

**ID는 불변이고 재사용하지 않는다.** 요구가 폐기되면 행을 지우지 말고 상태를 `폐기됨`으로 바꾸고
근거에 무엇이 대체했는지 적는다. 지우면 그 ID를 참조하던 PRD·티켓·테스트가 미아가 되고, 번호를
재사용하면 과거 문서가 엉뚱한 요구를 가리킨다. 번호는 영역 안에서 이어 붙이고 중간이 비어도
메우지 않는다.

## 상태 값

| 상태 | 의미 |
|------|------|
| `구현됨` | 코드에 있다. 근거는 티켓 번호 |
| `진행 중` | 티켓이 열려 있고 작업 중 |
| `계획` | 확정됐지만 착수 전 |
| `폐기됨` | 더는 유효하지 않다. 근거에 대체 항목 ID |

구현 여부의 정본은 `.claude/docs/status.md`와 코드다. SRS 상태가 그것과 어긋나면 SRS를 고친다
(AGENTS.md의 "검증 가능한 사실은 코드가 이긴다"와 같은 규칙).

## 모드 판별

`docs/srs.md`의 존재와 요청 내용으로 셋 중 하나를 고른다.

1. **초판 생성** — `docs/srs.md`가 없다. `references/backfill.md`를 읽고 그대로 실행한다.
   기존 구현 전체에서 요구사항을 역산하는 1회성 대형 작업이라 절차를 분리해 뒀다.
2. **등재** — 새 요구사항 추가. 가장 흔한 모드. 아래 절차.
3. **갱신** — 기존 항목의 상태·문장·근거 수정 (구현 완료, 정책 변경, 폐기).

## 등재 절차

1. **중복 확인**: 해당 영역 절을 읽어 같은 요구가 이미 있는지 본다. 같은 요구를 다른 문장으로 두 번
   등재하면 나중에 둘이 어긋나고, 어느 쪽이 정본인지 판정할 근거가 문서 안에 없다. 기존 항목을
   세부화하는 것이라면 새 등재가 아니라 그 항목의 문장을 다듬는 갱신이다.
2. **충돌 확인**: 기존 항목과 모순되는지 본다. 모순이면 확정일로 최신을 가린다 (AGENTS.md의 위키
   충돌 처리와 같은 규칙 — 우열을 못 가리면 양쪽을 병기해 사용자 판단으로 올리고, 임의로 한쪽을
   지우지 않는다). 낡은 쪽은 `폐기됨`으로 바꾸고 근거에 대체 ID를 적는다.
3. **문장 작성**: 검증 가능한 명제문으로 쓴다. 구현 결정(테이블·클래스·라이브러리·캐시 방식)은
   넣지 않는다. 사용자에게 보이는 정책과 대외 계약은 구현처럼 보여도 요구사항이다.
4. **ID 부여·등재**: 해당 영역의 다음 번호를 붙여 표에 추가한다. 근거에 티켓 번호와 확정일을 적는다.
5. **보고**: 등재한 ID와 문장을 사용자에게 알린다. 이 ID를 이후 PRD와 티켓이 참조한다.

## 무엇이 요구사항인가

이 구분이 SRS 품질의 대부분을 결정한다. 판정 기준은 **"구현을 통째로 바꿔도 이 문장이 그대로
유효한가"** 하나다. 유효하면 요구사항이고, 같이 바뀌면 구현 결정이다.

| 요구사항 | 구현 결정 (SRS에 넣지 않는다) |
|---|---|
| 핫구역은 최근 48시간 업로드 신호가 상위 50 안이면서 최소 3 이상인 격자다 | Redis Sorted Set 6시간 버킷에 저장한다 |
| 격자는 전국 어디서나 100×100m다 | EPSG:5179 평면에서 좌표를 100으로 나눈다 |
| 영상 삭제로 그 격자의 영상이 0이 되면 점령이 즉시 롤백된다 | user_grids row를 DELETE한다 |

경계가 헷갈리는 두 부류는 요구사항으로 친다. **사용자 가시 정책**(미점령 격자는 점선 격자망만
상시 표시)과 **대외 계약**(뷰포트 응답은 점령 격자만 담는다, 비친구 조회는 관계·계정 존재를
은닉하는 단일 실패 응답)이다. 클라이언트가 의존하므로 서버가 마음대로 바꿀 수 없고, 바꾸려면
합의가 필요한 것은 전부 요구사항이다.

## 문서 구조

목차는 **ISO/IEC/IEEE 29148(구 IEEE 830) 표준**을 따른다. 골격은 `assets/srs-template.md`에
있고 초판 작성이나 구조 개편 때 그것을 읽어 쓴다. 요구사항 목록만 있는 축약형으로 만들지 않는
이유는 이 문서의 독자에 멘토와 심사자가 포함되고, 제약 조건이나 가정·의존성처럼 요구사항 목록에
안 담기는 정보가 실제로 판단에 쓰이기 때문이다.

표준을 따르되 두 가지는 지킨다. **레포에 이미 정본이 있는 절은 채우지 말고 링크로 대체한다**
(용어집은 glossary, 아키텍처는 architecture.md). 복사하면 정본이 둘이 되어 한쪽만 갱신된다.
그리고 **수치나 방침이 정해지지 않은 절은 지어내지 말고 비운 채 그 사실을 한 줄로 밝힌다**.

## 작성 원칙

- **수치를 보존한다.** 100×100m, 최대 30초, 상위 50, 스트릭 3·7·30일처럼 확정된 값은 문장에
  남긴다. "적절한 개수"로 뭉개면 검증할 수 없고, 나중에 값을 바꿀 때 무엇이 바뀌었는지 안 남는다.
- **용어는 `.claude/rules/glossary.md`를 따르고 재정의하지 않는다.** SRS에 용어 사전을 또 만들면
  둘이 어긋나고, 정본이 둘이 되는 순간 둘 다 신뢰를 잃는다. 용어 절은 glossary를 가리키는 링크로 끝낸다.
- **문체**: 독자가 팀원·멘토라 외부 문서다. korean-humanizer 기준(줄표 금지, 읽히는 문장)으로 쓰고
  작성 후 줄표를 grep해 자가검증한다. 각주는 문서 상단 개요에 필요한 만큼만 단다 — 본문이 표
  위주라 tech-term-footnotes의 3~7개 목표를 억지로 채우지 않는다.

## 변경 이력 남기기

등재나 갱신을 마치면 **`docs/srs-changelog.md`에 행을 하나 붙인다.** `docs/srs.md` 본문에는
이력 표가 없다. 같은 자리에 여러 브랜치가 행을 붙여 매번 충돌하던 것을 파일로 떼어 union
병합으로 돌렸기 때문이다.

그 파일은 **추가만 한다.** 기존 행을 고치거나 지우면 union 병합이 그것을 중복 행으로 남긴다.
이미 적은 이력이 틀렸으면 지우지 말고 정정하는 행을 새로 붙인다.

## 후속 처리

1. 등재·갱신한 ID 목록을 보고한다.
2. 새 기능을 등재했으면 PRD 작성으로 이어갈지 묻는다. 이 스킬이 PRD까지 쓰지 않는다.
3. 초판이나 대규모 갱신이면 사용자 검수를 요청한다. 커밋은 사용자 몫이다.

## 테스트 시나리오

- **등재 흐름**: "뱃지를 미션 종류별로 나누기로 했어" → BADGE 영역 확인 → 기존 미션 합산 요구를
  `폐기됨`으로, 종류별 요구를 새 ID로 등재 → ID 보고 후 PRD 제안.
- **갱신 흐름**: "MSG-351 배포됐어" → 해당 항목 상태를 `계획`에서 `구현됨`으로, 근거에 티켓 추가.
- **충돌 흐름**: 등재하려는 요구가 기존 항목과 모순 → 확정일 비교 → 최신이 이기고 낡은 쪽 폐기.
  날짜로 못 가리면 양쪽 병기해 사용자에게 확인.
- **조회 흐름**: "지금 알림 관련 요구사항 뭐뭐 있지" → NOTI 영역 절을 읽어 ID·문장·상태로 답한다.
  등재 없이 조회만 하는 것도 이 스킬의 정상 사용이다.
- **에러 흐름**: "SRS 갱신해줘"만 있고 무엇을 등재할지 불명 → 되묻고 진행하지 않는다.
