# MSG-193: 신고 블라인드 처리 (BLINDED 전환과 해제)

**Owner**: B (video 패키지)

> PRD: `docs/prd/MSG-192-prd.md` (MSG-192, MSG-193 공유 PRD, 상태 검토됨, 2026-08-06 강정민 승인)
> 이 스펙은 PRD의 MSG-193 몫(FR-6에서 FR-11)만 다룬다. 신고 접수 API, moderation 패키지,
> V27 마이그레이션은 전부 MSG-192 소유라 여기서 다루지 않는다.

## 개요

운영 판단으로 영상을 `VideoStatus.BLINDED`로 전환하고 다시 `ACTIVE`로 해제하는 상태 전이
로직을 video 패키지의 서비스 레이어(`VideoModerationService`)로 만든다. 노출 차단 자체는
새로 만들 것이 없다. 재생 경로(MSG-206)와 모든 노출 경로가 이미 BLINDED를 거르고 있어서,
이 티켓의 실질은 전이 규칙과 그 순간의 파생 정리(도감 대표 재선정) 하나, 그리고 기존
필터들이 실제로 즉시 동작하는지 확인하는 회귀 통합 테스트다.

## 배경과 목표

부적절한 영상을 내릴 운영 수단이 지금은 DB 수동 UPDATE뿐이다(PRD §1). 신고 접수(MSG-192)로
문제 영상이 모이면, 관리자가 조치할 수단이 이 티켓의 전환과 해제다. HTTP 노출은 하지 않고
후속 관리자 API(MSG-195)가 이 서비스를 호출한다. 관리자 인증 체계가 없는 상태에서
엔드포인트를 열면 누구나 남의 영상을 내릴 수 있기 때문이다(PRD §4 보안).

## 성공 기준

1. `blind(videoId)` 호출로 ACTIVE 영상이 BLINDED로 저장되고, `unblind(videoId)` 호출로
   BLINDED 영상이 ACTIVE로 돌아온다.
2. 전환 직후 같은 영상에 대해 타인 재생은 404, 격자 전역 대표와 전역 목록과 격자별 내
   영상 리스트에서 제외가 통합 테스트로 확인된다(FR-9). 소유자 단건 조회는 상태를 볼 수
   있으나 재생 URL이 발급되지 않는다(MSG-206 구현 그대로, 수정 없음).
3. 전환된 영상이 도감 대표였다면 남은 ACTIVE 영상으로 대표가 재선정되고, 해제 시 대표를
   원복하지 않는다(FR-10).
4. 전환과 해제 어느 쪽도 user_grids의 점령 row와 video_count를 바꾸지 않는다(FR-11).
5. DELETED 영상, 존재하지 않는 영상, 이미 목표 상태인 영상에 대한 호출은 아래 D3의
   에러코드로 명시적으로 실패한다(FR-8). 조용히 넘기는 멱등 성공은 없다.
6. 이 티켓의 diff에 컨트롤러, DTO, 마이그레이션, 계약 인터페이스 변경이 없다.

## API 명세

이번 범위에 HTTP 엔드포인트가 없다(D1). 외부 계약 대신 서비스 인터페이스가 명세다.

```java
// video/service/VideoModerationService.java (신규)
public interface VideoModerationService {

	/** ACTIVE 영상을 BLINDED로 전환한다. 대표였다면 남은 ACTIVE 영상으로 대표를 재선정한다. */
	void blind(long videoId);

	/** BLINDED 영상을 ACTIVE로 해제한다. 대표는 원복하지 않는다. */
	void unblind(long videoId);
}
```

호출자 파라미터에 관리자 식별자를 두지 않는다. 누가 눌렀는지의 기록(감사 이력)은 MSG-195의
관리자 처리 흐름과 reports 상태 갱신이 담당할 영역이라 이번 범위 밖이다.

실패 케이스(양쪽 메서드 공통 구조):

| 상황 | 예외 | developCode | HTTP (MSG-195가 노출할 때) |
|------|------|-------------|---------------------------|
| 영상 row 없음 | `ApiException(VIDEO_NOT_FOUND)` | 3404 (기존) | 404 |
| status = DELETED | `ApiException(VIDEO_NOT_FOUND)` | 3404 (기존) | 404 |
| 이미 목표 상태 (blind에 BLINDED, unblind에 ACTIVE) | `ApiException(ALREADY_IN_TARGET_STATUS)` | 3409 (신규) | 409 |

```java
// video/exception/VideoErrorCode.java 에 상수 1개 추가
ALREADY_IN_TARGET_STATUS(3409, HttpStatus.CONFLICT, "이미 해당 상태의 영상입니다"),
```

## 도메인 로직

### 전이 규칙 (FR-6, FR-7, FR-8)

| 현재 상태 | blind | unblind |
|-----------|-------|---------|
| ACTIVE | BLINDED로 전환 | 3409 실패 |
| BLINDED | 3409 실패 | ACTIVE로 전환 |
| DELETED | 3404 실패 | 3404 실패 |

트리거는 관리자 수동뿐이다(D2). 신고가 몇 건 쌓여도 자동 전환하지 않으며, 지라 설명의
"신고 누적 임계" 문구는 폐기됐다(2026-08-06 사용자 확정).

### 잠금과 실행 순서 (blind)

삭제 경로(MSG-243)와 같은 규칙으로 `VideoRepository.findWithLockById`(비관적 잠금[^1])를
재사용해 상태 전이를 직렬화한다(D4). 잠금 없이 일반 로드로 짜면 동시 삭제 트랜잭션과
읽기 후 쓰기가 겹쳐, 삭제가 커밋된 영상을 블라인드가 되살리는 식의 상태 클로버링이 생긴다.

```java
@Override
@Transactional
public void blind(long videoId) {
	Video video = videoRepository.findWithLockById(videoId)
		.orElseThrow(() -> new ApiException(VideoErrorCode.VIDEO_NOT_FOUND));
	if (video.isDeleted()) {
		throw new ApiException(VideoErrorCode.VIDEO_NOT_FOUND);   // 존재 은닉[^2]과 같은 결: 삭제는 없음으로 취급 (D3)
	}
	if (video.getStatus() == VideoStatus.BLINDED) {
		throw new ApiException(VideoErrorCode.ALREADY_IN_TARGET_STATUS);
	}
	video.markBlinded();
	// 대표였다면 재선정 (FR-10). reselectCover의 WHERE 가드(cover_video_id = :deletedVideoId)가
	// 대표가 아니었으면 no-op으로 만들어 주므로 호출 측 분기가 필요 없다 (D5).
	videoRepository.reselectCover(video.getUserId(), video.getGridId(), videoId);
}
```

`markBlinded()`가 native 쿼리보다 먼저 와야 한다. Hibernate가 native 쿼리 실행 전에 영속성
컨텍스트를 자동 flush[^3]하므로 재선정 서브쿼리(`status = 'ACTIVE'` 후보 선정)가 방금 가린
영상을 다시 고르지 않는다. 삭제 경로의 `markDeleted()` 순서 주석과 같은 원리다
(`VideoServiceImpl.deleteVideo` 294행 부근).

unblind는 같은 골격에서 가드 방향만 반대다. 잠금 로드, DELETED와 미존재는 3404, ACTIVE면
3409, 통과하면 `markActive()`. 대표 재선정 호출이 없다(원복 없음, FR-10).

### 엔티티 전이 메서드 (D7)

`Video`의 status 필드는 setter가 없으므로 기존 `markDeleted()` 관례대로 도메인 메서드를
추가한다. 상태 검증은 서비스가 잠금 아래에서 하므로 엔티티 메서드는 값 대입만 한다.

```java
/** ACTIVE -> BLINDED (MSG-193). 전이 가드는 VideoModerationService가 잠금 아래에서 수행한다. */
public void markBlinded() {
	this.status = VideoStatus.BLINDED;
}

/** BLINDED -> ACTIVE 해제 (MSG-193). */
public void markActive() {
	this.status = VideoStatus.ACTIVE;
}
```

### 바뀌지 않는 것들 (FR-11)

블라인드는 삭제가 아니다. soft delete[^4] 경로가 하는 파생 정리 중 대표 재선정 하나만
공유하고 나머지는 전부 하지 않는다.

- 점령과 video_count 불변: `decrementVideoCount`, `deleteUserGridIfEmpty` 호출 없음.
  점령 롤백은 삭제 전용이다(glossary 규칙).
- 수집률 캐시(`regionStatsCommandService.refresh`) 호출 없음: 점령 격자 집합이 안 변하므로
  분자와 분모 모두 그대로다.
- S3 객체 삭제 없음: 해제로 되돌릴 수 있어야 하므로 파일은 그대로 둔다.
- 핫스코어 차감 없음: 핫스코어는 근사값이라 삭제도 차감하지 않는 것과 같은 정책이다
  (glossary 핫구역 항목).
- 스트릭과 뱃지 회수 없음: 둘 다 업로드 시점 훅만 있고 소급 차감이 없다(MSG-200 §D4,
  MSG-239 FR-5). 블라인드 경로에 훅을 배선하지 않는다.

### 노출 차단은 기존 필터가 수행 (FR-9)

이 티켓은 조회 쿼리를 한 줄도 수정하지 않는다. 이미 전부 대비돼 있다.

- 재생(MSG-206): `getVideoPlayback`이 first-match로 BLINDED 타인 404, 소유자는 통과하되
  `status != ACTIVE`라 재생 URL 미발급 (`VideoServiceImpl` 494행 부근).
- 격자 전역 대표와 전역 목록, 탐색 집계: native 쿼리 전부 `status = 'ACTIVE'` 고정
  (`findGlobalCover`, `findGlobalVideos*`, `findExploreGrids*`, 집계 2종).
- 격자별 내 영상 리스트: `findByUserIdAndGridIdAndStatusOrderByCreatedAtDesc(.., ACTIVE)`.
- 친구 격자 목록과 도감 조회 경로(usergrid): 마찬가지로 `status = 'ACTIVE'` 필터.

그래서 이 티켓의 핵심 검증은 새 필터 구현이 아니라, 전환 즉시 위 경로들에서 실제로
사라지는지의 회귀 통합 테스트다.

## D-결정

- **D1. HTTP 미노출, 서비스 레이어까지만**: 전환과 해제는 `VideoModerationService`로만
  만들고 컨트롤러를 열지 않는다. 호출 주체는 MSG-195 관리자 API다. 관리자 인증 부재
  상태의 공개 엔드포인트 금지(2026-08-06 사용자 확정, PRD §4).
- **D2. 관리자 수동만**: 자동 블라인드 임계 없음. 지라의 "신고 누적 임계" 문구 폐기
  (2026-08-06 사용자 확정, PRD 비목표).
- **D3. 에러코드는 3xxx 2종으로 수렴**: 상태 전이는 video 도메인 소유라 moderation
  11xxx가 아니라 `VideoErrorCode`에 둔다. 미존재와 DELETED는 기존 3404 `VIDEO_NOT_FOUND`
  재사용이다. 재생 경로가 DELETED를 소유자에게도 404로 숨기는 "삭제는 없음 취급" 원칙과
  결이 같고, 관리자에게도 "이미 없는 영상"이라는 정보로 충분하다. 이미 목표 상태만 신규
  3409 `ALREADY_IN_TARGET_STATUS`(CONFLICT)로 구분한다. FR-8이 조용한 멱등 성공을
  금지하므로 실패는 항상 명시적이다.
- **D4. 잠금은 findWithLockById 재사용**: blind와 unblind 양쪽 다 삭제 경로(MSG-243)와
  같은 행 잠금으로 직렬화한다. 새 잠금 메커니즘을 만들지 않는다. 동시성 재현 테스트는
  추가하지 않는다. 같은 잠금 지점의 직렬화는 `VideoDeleteConcurrencyTest`가 이미
  결정적으로 검증하고 있어서다.
- **D5. 대표 재선정은 기존 reselectCover 재사용**: 신규 쿼리 없음. WHERE 가드 덕에 대표가
  아니면 no-op이라 무조건 호출한다. 유일한 영상을 블라인드하면 서브쿼리가 NULL을 주어
  대표가 비는데, 이는 도감 계약이 허용하는 상태다(coverVideoId null).
- **D6. 해제는 상태 복귀만**: 대표 원복 없음(FR-10), 그 외 파생 갱신도 없음. 점령,
  video_count, 수집률, 핫스코어, 스트릭, 뱃지 전부 전환과 해제 양쪽에서 불변(FR-11).
- **D7. 전이는 엔티티 도메인 메서드로**: `Video.markBlinded()`와 `markActive()`를 기존
  `mark{상태}` 관례로 추가한다. 검증은 서비스, 대입은 엔티티로 역할을 나눈다.

  누가 하는지는 MSG-195 관리자 처리 흐름에서 확정한다. 이번 범위는 영상 상태 전이만이다.

[^1]: 비관적 잠금(pessimistic lock): SELECT 시점에 행 잠금(FOR UPDATE)을 걸어 다른
    트랜잭션의 같은 행 접근을 커밋까지 대기시키는 방식. 삭제와 블라인드처럼 서로 다른
    쓰기 축이 같은 영상 행을 두고 경쟁할 때 전이를 한 줄로 세운다.
[^2]: 존재 은닉: 권한이나 상태 때문에 막힌 요청에 403 대신 404를 돌려줘 리소스의 존재
    자체를 숨기는 응답 방식. 이 코드베이스에서는 삭제된 영상을 소유자에게도 404로 답하는
    재생 경로가 그 선례다.
[^3]: 자동 flush: Hibernate가 native 쿼리를 실행하기 전에 영속성 컨텍스트에 쌓인 엔티티
    변경을 DB로 먼저 내보내는 동작(FlushMode.AUTO). 이 순서 보장 덕에 대표 재선정
    서브쿼리가 방금 바꾼 status를 보고 판단한다.
[^4]: soft delete: 행을 실제로 지우지 않고 상태 컬럼(DELETED)만 바꿔 지운 것으로 취급하는
    삭제 방식. 블라인드는 이와 달리 파일과 파생 데이터를 전부 보존해 되돌릴 수 있게 한다.
[^5]: 비정규화(denormalization): 조회 때마다 계산하는 대신 결과값(격자 대표 영상 id)을
    별도 컬럼에 미리 저장해 두는 설계. 원본(videos 상태)이 바뀌면 이 사본을 따라 고쳐야
    하는 의무가 생기는데, 대표 재선정이 바로 그 의무다.

**런타임 동작 기록**

- 데이터 저장 위치: 새 저장소 없음. `videos.status` 전이와 `user_grids.cover_video_id`
  재선정만 일어난다. 마이그레이션도 없다(BLINDED 값은 V1 CHECK부터 있었다).
- 실행 쿼리 (통합 테스트 SQL 로그 실측):
  - 잠금 조회: MSG-192와 같은 `for no key update` (같은 `findWithLockById`).
  - 전이: `update videos set status=? where id=?`. markBlinded()의 더티체킹 UPDATE가
    reselectCover 네이티브 쿼리 실행 직전 자동 flush로 먼저 나간다. 이 순서가 정합의
    핵심이다. 재선정 서브쿼리가 방금 바뀐 status를 보고 후보를 고른다.
  - 대표 재선정 (네이티브 원문): `UPDATE user_grids ug SET cover_video_id = (SELECT v.id
    FROM videos v WHERE v.user_id = ? AND v.grid_id = ? AND v.status = 'ACTIVE' ORDER BY
    v.created_at, v.id LIMIT 1) WHERE ug.user_id = ? AND ug.grid_id = ? AND
    ug.cover_video_id = ?`. WHERE 가드 덕에 대표가 아니면 0행 no-op이고, 유일 영상을
    블라인드하면 서브쿼리가 NULL을 줘 대표가 빈다(도감 계약이 허용하는 상태).
- 예외 흐름: 미존재와 DELETED는 3404(존재 은닉), 이미 목표 상태는 3409 CONFLICT를
  `ApiException`으로 던진다. 지금은 HTTP 노출 경로가 없어 핸들러 변환이 일어나지 않고,
  MSG-195가 엔드포인트를 열면 `GlobalExceptionHandler`가 404와 409로 변환하게 된다.
- 빈 동작: HTTP 미노출이라 `VideoModerationService` 참조처는 구현체와 테스트뿐(리뷰 실측).
