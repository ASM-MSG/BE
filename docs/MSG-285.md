# MSG-285: 영상 공개범위 FRIENDS(친구만 보기) 확장

**Owner**: B

**요구사항 정본**: `docs/prd/MSG-285-prd.md` (검토됨 — 2026-08-03 사용자 승인, FR-5는 2026-08-03
403 동일 처리로 정정 완료). 이 스펙은 PRD의 FR-1~9·비기능에 "어떻게"만 붙인다.

**Owner 판정 근거**: 변경 파일 전부가 Owner B 패키지다 — `com.msg.fillmap.video.*`(Visibility·
VideoServiceImpl·VideoErrorCode·DTO·Controller), `com.msg.fillmap.friend.*`(FriendService·
FriendshipRepository). video→friend 소비는 B-내부 의존이라 A/B 계약 인터페이스 신설이 필요 없다.

## 개요

영상 공개범위를 PUBLIC/PRIVATE 2값에서 FRIENDS(친구만 보기) 3값으로 확장한다.
FRIENDS 영상은 소유자 본인과 ACCEPTED 친구(MSG-185, 방향 무관)만 재생할 수 있고,
비친구에게는 **PRIVATE 비소유자와 완전 동일하게 403**("비공개 영상입니다")으로 거부한다.
목록 노출(친구에게 FRIENDS 영상을 보여주는 조회 경로)은 **비목표** — MSG-187 친구 레이어와
함께 재설계한다. 이번 티켓은 값·지정·재생 판정의 계약 선행이다.

## 배경 · 목표

- "아는 사람에게만 보여주고 싶은" 영상이 현재는 PRIVATE(아무도 못 봄) 아니면 PUBLIC(전원 공개)뿐이다.
- 친구 관계 API(MSG-185)가 완료돼 선행 조건이 해소됐다 — 업로드 지정(MSG-204)·더보기 변경(MSG-162)
  때 미뤄둔 3값째를 붙인다.
- 목표: FRIENDS 지정(업로드·변경) + 재생 판정(본인·ACCEPTED 친구만) + 비친구 403 거부 + 전역 노출 무변경 검증.

## 성공 기준

1. `POST /api/videos` visibility에 `"FRIENDS"`를 보내면 저장되고, `PATCH /api/videos/{id}/visibility`로
   FRIENDS ↔ PUBLIC/PRIVATE 전환이 된다 (FR-1·2)
2. FRIENDS 영상 재생(`GET /api/videos/{id}`): 소유자 200, ACCEPTED 친구(방향 무관) 200,
   비친구 **403**(PRIVATE 비소유자와 동일) — 비친구 응답에 presigned URL이 실리지 않는다 (FR-3~5)
3. 친구 삭제 직후 같은 요청이 403이 된다 — 캐시 없이 요청 시점 실시간 판정 (FR-6)
4. 전역 노출 쿼리(`VideoRepository`의 `visibility = 'PUBLIC'` 등식 9곳)가 무변경으로 FRIENDS 행을
   제외한다 — 격자 대표 영상·전역 목록·탐색 집계에 FRIENDS 영상이 잡히지 않음을 테스트로 검증 (FR-7)
5. 허용 외 값은 기존 3420으로 실패하고, 에러 메시지·Swagger가 3값을 안내한다 (FR-8)
6. FRIENDS 업로드도 점령·도감·스트릭·핫스코어에 기존과 동일하게 반영된다 (FR-9)
7. 마이그레이션 V20 적용 후 FRIENDS 행 INSERT가 CHECK를 통과하고, 기존 행은 무변경이다

## API 명세

**신규 엔드포인트 없음** — 기존 3개 API의 허용 값만 확장한다.

### 1. `POST /api/videos` (업로드 확정, MSG-204)

- `VideoUploadRequestDto.visibility`: `"PUBLIC" | "PRIVATE" | "FRIENDS"` (대소문자 무관), 생략(null) 시
  PUBLIC — **기본값 무변경** (§D6)
- 실패: 허용 외 문자열 → `400 / developCode 3420 INVALID_VISIBILITY` (기존과 동일, 메시지만 3값)
- Swagger 필드 문구 갱신: `"공개범위. PUBLIC, PRIVATE, FRIENDS 중 하나. 생략 시 PUBLIC"`

### 2. `PATCH /api/videos/{videoId}/visibility` (공개범위 전환, MSG-162)

- `VideoVisibilityRequestDto.visibility`: 3값 허용. 같은 값 재전환 멱등 성공(기존 계약 유지)
- 실패 케이스 무변경: 비소유자 3403, 삭제 영상 3404, 허용 외 값 3420
- Swagger 갱신: DTO 클래스·필드 `@Schema` + `VideoController.setVisibility` description
  ("PUBLIC↔PRIVATE" → "PUBLIC·PRIVATE·FRIENDS 간 전환")

### 3. `GET /api/videos/{videoId}` (단건 재생, MSG-206)

- 접근 판정에 FRIENDS 분기 추가 (아래 도메인 로직). 응답 스키마 무변경
- **비친구의 FRIENDS 영상 요청 → `403 / developCode 3403 VIDEO_FORBIDDEN` + "비공개 영상입니다"** —
  PRIVATE 비소유자와 완전 동일 처리(§D1, 신규 에러코드 없음). 재생 URL·presign 미발급
- 존재하지 않는/삭제 영상 404, BLINDED 타인 404는 기존 규칙 그대로 (FRIENDS와 무관)
- Swagger 갱신: `getPlayback` description의 "비공개(타인)는 403" → "비공개·친구만 공개(타인/비친구)는 403"

## 도메인 로직

glossary 용어: **친구 관계** = friendships의 ACCEPTED 행 1개(방향 무관 양방향, MSG-185 §D3
"행 존재 = 활성 관계"). **친구 공개(FRIENDS)** = 이번 티켓으로 glossary 등재할 3값째 공개범위.

### 재생 판정 확장 — `VideoServiceImpl.getVideoPlayback` (핵심 회귀 지점)

현재 분기는 `visibility == PRIVATE && !owner`만 막는다 — enum에 FRIENDS만 추가하면 이 분기를
그냥 지나쳐 **비친구에게 presigned URL이 발급된다**(PRD 비기능·보안). PUBLIC만 통과가 명시되는
형태로 재구성한다:

```java
// 기존 판정 순서 유지: 1 존재/DELETED(404) → 2 BLINDED(타인 404) → 3 visibility → 4 status·READY 발급
} else if (!owner) {
	switch (video.getVisibility()) {
		case PUBLIC -> { }
		case FRIENDS -> {
			if (!friendService.isFriend(video.getUserId(), userId)) {
				// §D1: PRIVATE 비소유자와 완전 동일 — 기존 403 재사용, 신규 에러코드 없음
				throw new ApiException(VideoErrorCode.VIDEO_FORBIDDEN, "비공개 영상입니다");
			}
		}
		case PRIVATE -> throw new ApiException(VideoErrorCode.VIDEO_FORBIDDEN, "비공개 영상입니다");
	}
}
```

- 실측 확정: 거부 예외는 `VideoErrorCode.VIDEO_FORBIDDEN(3403, HttpStatus.FORBIDDEN)` + 기존
  PRIVATE 분기의 메시지 override `"비공개 영상입니다"` 그대로 — PRIVATE/FRIENDS 실패 응답이
  바이트 단위로 동일하다 (기본 메시지 "본인의 영상만 처리할 수 있습니다"는 수정 거부 뉘앙스라
  조회 맥락 override를 유지, MSG-206 선례)
- enum-exhaustive switch — 4값째가 생기면 컴파일 에러로 판정 재검토를 강제한다 (§D3)
- BLINDED 우선순위 유지: FRIENDS 영상이 BLINDED면 친구여도 기존 규칙(타인 404)이 먼저다
- 친구 판정은 FRIENDS && 비소유자일 때만 1회 호출 — PUBLIC·PRIVATE·소유자 경로는 쿼리 0회
- 조회수(§D5): 기존 규칙 그대로 — URL 발급 && 타인이면 +1. 친구의 FRIENDS 재생도 증가한다

### 친구 여부 판정 — `FriendService.isFriend` 신설 (B-내부)

```java
/** 두 사용자가 ACCEPTED 친구인가 — 방향 무관 대칭 판정 (MSG-285 FR-4·6). 요청 시점 실시간 조회. */
boolean isFriend(Long userId, Long otherUserId);
```

- **기존 `findPair` 재사용 금지** (§D2): `@Lock(PESSIMISTIC_WRITE)`가 걸린 쓰기용 조회라
  재생 판정(읽기)에 쓰면 요청마다 friendships 행 잠금(`SELECT … FOR UPDATE`)이 걸린다.
  잠금 없는 읽기 전용 exists를 `FriendshipRepository`에 신설:

```java
@Query("""
	SELECT COUNT(f) > 0 FROM Friendship f
	WHERE f.status = com.msg.fillmap.friend.entity.FriendshipStatus.ACCEPTED
		AND ((f.id.requesterId = :a AND f.id.addresseeId = :b)
			OR (f.id.requesterId = :b AND f.id.addresseeId = :a))
	""")
boolean existsAcceptedPair(@Param("a") Long a, @Param("b") Long b);
```

- **병렬 머지 노트**: 병렬 진행 중인 MSG-186(친구 목록·프로필)도 동일 시그니처·동일 쿼리 텍스트의
  `existsAcceptedPair`를 `FriendshipRepository`에 추가한다(두 스펙 간 합의 완료 — 2026-08-03).
  늦게 머지되는 브랜치가 리베이스에서 중복 선언 하나만 제거하면 된다
- 성능(PRD 비기능): OR 두 방향 모두 복합 PK `(requester_id, addressee_id)` 인덱스 단건 lookup —
  "동일 쌍 최대 1행" 불변식(V19 `uq_friendships_pair`) 하에서 결과 0~1행. 재생 p95 영향 미미
- `FriendServiceImpl.isFriend`는 `@Transactional(readOnly = true)` — `getVideoPlayback`의 쓰기
  트랜잭션에서 호출되면 기존 트랜잭션에 참여(REQUIRED 전파, 문제없음)
- FR-6(친구 삭제 즉시 차단)은 이 실시간 조회로 자동 충족 — 캐시·비정규화 없음
- 의존 방향: video → friend 단방향 신규. friend는 user만 참조하므로 순환 없음 (실측 확인)

### 지정 경로 — `parseVisibility` (무변경)

`Visibility.valueOf` 기반이라 enum에 FRIENDS 상수를 추가하면 업로드(`saveVideo`)·전환(`setVisibility`)
둘 다 자동 허용된다. 파싱 로직 수정 없음 — 에러 메시지 상수만 갱신.

### FR-9 (기록 사실 무변경) — 코드 수정 없음, 테스트로 검증

`saveVideo`의 점령(`upsertUserGrid`)·뱃지·스트릭·핫스코어 훅은 visibility를 분기 조건으로 쓰지
않는다(실측). FRIENDS 업로드도 PUBLIC/PRIVATE과 동일 경로 — 회귀 테스트만 추가한다.

## 데이터 모델

- **엔티티**: `video/entity/Visibility` enum에 `FRIENDS` 상수 추가. 컬럼 `VARCHAR(10)`이라
  'FRIENDS'(7자) 수용 — 컬럼 무변경
- **마이그레이션**: `V20__videos_visibility_friends.sql` 신규 (현재 최신 V19 다음)

```sql
-- CHECK 제약은 ALTER 불가 — DROP 후 3값으로 재생성. 기존 행 데이터 무변경.
ALTER TABLE videos DROP CONSTRAINT chk_videos_visibility;
ALTER TABLE videos ADD CONSTRAINT chk_videos_visibility
	CHECK (visibility IN ('PUBLIC', 'PRIVATE', 'FRIENDS'));
```

- **인덱스 무변경** (§D4): 부분 인덱스 `idx_videos_grid_popular … WHERE visibility = 'PUBLIC'` 유지 —
  목록 노출이 비목표라 FRIENDS를 태울 조회가 없다
- **운영(PRD)**: ADD CONSTRAINT는 기존 행 전체 검증 스캔 — MVP 데이터 규모에서 순간 잠금 수용.
  FRIENDS 행 생성 후 구버전 롤백 시 CHECK 위반 — 릴리스 노트 명시(뒤로 못 돌리는 마이그레이션)

  `VideoController` — `setVisibility` description·`getPlayback` description(403 케이스에 FRIENDS 포함)
- `.claude/rules/glossary.md` — MVP 확정 용어에 **친구 공개 (FRIENDS)** 등재(PRD 변경 파일):
