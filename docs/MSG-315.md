# MSG-315: 주간 활동 요약 알림

**Owner**: B (notification, usergrid, video 도메인만 건드리며 전부 Owner B 소관)

> 요구사항 정본: `docs/prd/MSG-313-prd.md` (알림 다양화 공유 PRD, 상태 검토됨). 이 스펙은 그중
> 주간 요약(MSG-315)에 해당하는 FR-5, FR-6, FR-7, FR-8, FR-9의 "어떻게"만 정한다.
> 영상 준비 완료(MSG-313)와 뱃지 임박(MSG-314)은 이미 구현되어 develop에 있으므로 범위가 아니고,
> 여기서는 선례로만 인용한다.

## 개요

일요일 저녁마다 지난 일주일 동안 활동이 있었던 사용자에게 활동 요약 푸시를 보낸다. 요약 수치는
새로 수집한 격자 수와 올린 영상 수 두 가지다. 신설 요소는 넷이다. `NotificationCategory`의 WEEKLY
값, 카테고리 CHECK를 다시 정의하는 마이그레이션 1건, 주간 집계 배치 스케줄러 1개, 컨슈머 전송률
switch의 WEEKLY 분기다. 발송 파이프라인(MSG-179)과 알림 설정(MSG-180)은 코드 변경 없이 그대로
승계하고, 배치의 뼈대는 스트릭 리마인드 배치(MSG-181)를 그대로 따른다.

## 배경 · 목표

활동이 쌓여도 주간 단위로 되짚어 주는 장치가 없어서, 앱을 며칠 안 열면 도감이 채워지는 재미가
잊힌다(PRD 문제 상황). 지금 알림은 사건이 생긴 순간에만 나가므로, 조용한 한 주를 보낸 사용자를
다시 데려오는 경로가 비어 있다.

목표는 셋이다. 지난 일주일 활동이 있던 사용자가 주 1회 요약 푸시를 받는다. 같은 주에 두 번 가지
않는다. 새 알림 종류를 알림 설정에서 따로 끌 수 있다.

## 성공 기준

- 일요일 저녁(KST) 배치가 돌면, 그 주에 격자를 수집했거나 영상을 올린 사용자의 WEEKLY 알림이
  outbox[^1]에 기록되고 기존 파이프라인이 발송한다.
- 활동이 없던 사용자에게는 행이 생기지 않는다(FR-6).
- 같은 주에 배치가 두 번 이상 돌아도 사용자당 행은 1건이다(FR-5 재실행 멱등).
- 요약 수치가 그 주의 실제 활동과 맞는다. 삭제한 영상은 빠지고, 지난주 이전 활동은 섞이지 않는다.
- 설정 조회(GET preferences)에 WEEKLY가 포함되고, PATCH로 끄면 컨슈머가 발송을 skip 한다.
- 마이그레이션 후 기존 4종 카테고리 행은 그대로이고, WEEKLY INSERT가 CHECK를 통과한다.
- 아래 "테스트 시나리오"가 전부 green.

## API 명세

신규 API는 없다. 기존 알림 설정 API 두 개의 응답에 WEEKLY 항목이 하나 늘어난다.

- `GET /api/notifications/preferences`, `PATCH /api/notifications/preferences/{category}`
- 응답 구조(`NotificationPreferenceResponseDto`)는 그대로다. 카테고리 목록이 enum 선언 순 합성이라
  WEEKLY가 5번째 항목으로 자동으로 붙고 기본값은 enabled=true다.
- `PATCH .../WEEKLY` 토글도 파싱이 `valueOf`라서 코드 변경 없이 동작한다.
- 카테고리가 늘어난 사실은 FE에 공유해야 한다(PRD 비기능 호환 항목, MSG-313과 같은 절차).

## 도메인 로직

### D1. 발송 시점: 일요일 19시와 19시 30분(KST)

```java
@Scheduled(cron = "0 0,30 19 * * SUN", zone = "Asia/Seoul")
```

- 요일은 PRD FR-5의 일요일 저녁 확정을 따른다.
- 시각이 19시대인 이유는 다른 배치와 겹치지 않기 때문이다. 실측한 기존 스케줄은 스트릭 리마인드가
  `0 0 20-23 * * *`(KST 20시부터 23시까지 매시 발화)이고, 스테일 토큰 정리가 `0 0 4 * * *`,
  핫구역 진입 검출이 10분 주기 고정 지연이다. 리마인드는 "20시 정각 1회"가 아니라 20시부터 23시까지
  이어지는 재발화 창이므로, 그 창 전체를 피하려면 저녁 중에서도 20시 이전이어야 한다.
- 30분 뒤 재발화 1회를 두는 이유는 부분 실패 회복이다(PRD 비기능 운영 항목). 첫 발화에서 어떤
  사용자의 기록이 실패해도 두 번째 발화가 같은 주 안에서 재시도하고, 이미 기록된 사용자는 이벤트
  키 멱등[^2]이 흡수해 중복이 되지 않는다. MSG-181이 확립한 "재발화가 곧 재시도"와 같은 방식이다.
- 두 번째 발화까지 끝나도 20시 리마인드 창까지 여유가 남아, 요약 발송 물량이 리마인드 앞을 막고
  있을 확률을 낮춘다(D6).
- 예외는 사용자 단위로 격리한다. 한 명의 기록 실패가 나머지 대상의 요약을 막지 않으며, 실패 건수와
  마지막 예외를 warn 로그로 남긴다. StreakRemindScheduler의 루프 형상을 그대로 따른다.
- 게이트는 `@ConditionalOnProperty(prefix = "fillmap.notification", name = "enabled")`다. 로컬과 CI는
  스케줄러 빈 자체가 뜨지 않으므로 테스트는 인스턴스를 직접 만들어 메서드를 호출한다.

### D2. 집계 창: KST 이번 주 월요일 0시부터 실행 시각까지

- 주의 시작은 KST 월요일 0시다(PRD FR-5의 "KST 월~일"). 발송이 일요일 저녁이므로 창은 지금 끝나가는
  주를 가리키며, 사용자가 받는 문장과 실제 기간이 어긋나지 않는다.
- 창의 끝은 배치 실행 시각이다. 운영에서는 미래 시각 행이 없어 상한이 사실상 무의미하지만, 상한을
  두면 창이 명시되고 테스트가 고정 시계로 결정적이 된다(D7 참조). 공유 DB에서 다른 테스트가 만든
  현재 시각 행이 집계에 섞이는 것도 이 상한이 막는다.
- 그 대가로 일요일 19시 이후 활동은 그 주 요약에 잡히지 않는다. 다음 주 창이 월요일 0시부터
  시작하므로 이 5시간은 어떤 요약에도 들어가지 않는다. 넛지는 보장이 아니라 기회라서 이 손실은
  받아들인다(MSG-314 D3의 "이월하지 않는다"와 같은 정책). 도감과 스트릭 같은 실제 기록에는
  당연히 그대로 반영된다.

**시간대 처리는 다른 두 알림과 다르다. 원본 컬럼의 저장 관례가 다르기 때문이다.**

| 컬럼 | 쓰기 경로(실측) | 저장되는 값 |
|---|---|---|
| `videos.created_at` | Hibernate `@CreationTimestamp`(기본 소스 VM) | JVM 기본 존 벽시계 |
| `user_grids.first_collected_at` | `VideoRepository.upsertUserGrid`의 `now()` | 세션 타임존 캐스트[^3] 결과, 즉 JVM 기본 존 벽시계 |
| `notifications.created_at` | `NotificationRepository.insert` | 명시 UTC (MSG-314 D4가 고침) |

MSG-314가 UTC로 고정한 것은 `notifications.created_at` 하나이고, 집계 재료인 위 두 컬럼은 여전히
JVM 기본 존 벽시계로 저장된다. pgjdbc 세션 타임존이 JVM 기본 존을 따르고 Hibernate의 VM 소스도
같은 존을 쓰기 때문에 두 컬럼의 관례는 서로 일치한다. 따라서 임계값을 UTC로 바인딩하면 KST로 도는
JVM 배포에서 창이 9시간 어긋난다. 임계값은 KST 주 시작을 절대 시각으로 잡은 다음 저장 존으로
환산해 바인딩한다.

```java
private static final ZoneId KST = ZoneId.of("Asia/Seoul");

LocalDate todayKst = LocalDate.ofInstant(clock.instant(), KST);
ZonedDateTime weekStartKst = todayKst.with(TemporalAdjusters.previousOrSame(DayOfWeek.MONDAY))
	.atStartOfDay(KST);
// 저장 존 = JVM 기본 존 (위 표). UTC 로 도는 배포에서는 이 환산이 항등이라 기존 UTC 바인딩과 결과가 같다.
LocalDateTime weekStart = weekStartKst.withZoneSameInstant(ZoneId.systemDefault()).toLocalDateTime();
LocalDateTime now = LocalDateTime.ofInstant(clock.instant(), ZoneId.systemDefault());
```

원본 컬럼의 쓰기 경로를 UTC로 바꾸는 근본 수정은 이 티켓 범위 밖이다. 기존 행이 어느 존으로 쓰였는지
행마다 달라져 소급 해석이 불가능해지고, 업로드 경로 전체를 건드려야 한다. 배포 시간대를 바꾸면 그
주의 집계가 한 번 어긋난다는 천장은 그대로 남으며, 이는 문서로만 남기고 감수한다.

### D3. 대상 조회와 집계는 한 쿼리로

대상 판정(활동이 있었는가)과 요약 수치(몇 개인가)가 같은 재료라서 쿼리를 나눌 이유가 없다. 두
테이블의 이번 주 행을 각각 1로 세어 사용자별로 합산한다. 결과에 들어온 사용자는 정의상 활동이 있는
사용자이므로 FR-6(활동 없으면 발송 없음)이 필터 없이 성립한다.

```sql
SELECT t.user_id AS "userId",
       sum(t.grid_delta)::int AS "gridCount",
       sum(t.video_delta)::int AS "videoCount"
FROM (
    SELECT user_id, 1 AS grid_delta, 0 AS video_delta
    FROM user_grids
    WHERE first_collected_at >= :weekStart AND first_collected_at < :now
    UNION ALL
    SELECT user_id, 0, 1
    FROM videos
    WHERE created_at >= :weekStart AND created_at < :now AND status <> 'DELETED'
) t
GROUP BY t.user_id
```

- 위치는 `UserGridRepository`다. 이 리포지토리는 이미 도감 요약에서 videos를 조인해 읽고 있어
  선례가 있고, 배치가 소비하는 지식이 도감과 영상 활동이기 때문이다. 프로젝션 인터페이스
  `WeeklyActivityProjection`(userId, gridCount, videoCount)은 `StreakRemindProjection`과 같은 형상으로
  둔다. COUNT 계열이 bigint라 `::int` 캐스트로 Integer 프로젝션에 맞춘다(도감 요약 쿼리 선례).
- 영상 카운트가 `status <> 'DELETED'`인 이유는 도감 요약이 이미 같은 기준을 쓰기 때문이다
  (MSG-152 D6, 삭제는 제외하고 블라인드는 포함). 삭제한 영상을 "올린 영상"으로 세면 사용자가 지금
  보는 도감과 숫자가 어긋난다.
- 격자 카운트는 별도 필터가 필요 없다. 점령 롤백이 `user_grids` 행 자체를 지우므로(video_count가 0이
  되면 삭제) 남아 있는 행이 곧 현재 진실이다.
- 인덱스는 새로 만들지 않는다. 두 테이블 모두 시간 컬럼 단독 인덱스가 없어 순차 스캔이 되지만,
  주당 두 번 도는 배치라 MVP 규모에서 비용이 문제되지 않는다. videos가 수백만 행으로 커지면
  `created_at` 인덱스 신설이 다음 수순이다.

### D4. 이벤트 키: ISO 주차[^4]

```text
WEEKLY:{ISO 주 기반 연도}-W{두 자리 주차}
예: WEEKLY:2026-W32
```

- 계산은 KST 오늘 날짜에서 `IsoFields.WEEK_BASED_YEAR`와 `IsoFields.WEEK_OF_WEEK_BASED_YEAR`를 읽는다.
  ISO 주는 월요일에 시작하므로 집계 창의 주 시작과 정확히 같은 주를 가리키고, 일요일은 그 주의
  마지막 날이라 19시 발화와 19시 30분 발화가 같은 키를 만든다.
- 연말 경계는 주 기반 연도가 흡수한다. 예를 들어 2026-12-28은 2026-W53이고, 2027-01-01은 같은 주라
  역시 2026-W53이다. 달력 연도를 쓰면 이 주가 두 키로 쪼개져 같은 주에 두 번 발송될 수 있다.
- 기존 키 관례(`BADGE:{badgeId}`, `HOTZONE:{KST일자}:{gridId}`, `REMIND:{KST일자}`,
  `BADGE_NEAR:{badgeId}`, `VIDEO:{videoId}:{원본키 꼬리}`)와 같은 결로 사건의 자연 식별자를 쓴다.
- 키 길이는 15자라 `event_key VARCHAR(100)`에 여유가 크다. MSG-313이 겪은 키 길이 초과 사고와 같은
  위험이 없다.
- 중복 차단은 DB가 한다. `uq_notifications_user_event UNIQUE (user_id, event_key)`와 insert의
  ON CONFLICT DO NOTHING이 재발화와 배치 재실행을 조용히 흡수한다(FR-5 "같은 주 중복 없음").

### D5. 문구와 수치 0 처리

기존 4종의 형상은 트리거가 title과 body를 하드코딩하고 존댓말 안내체를 쓰는 것이다. WEEKLY도 같다.

| 조건 | title | body |
|---|---|---|
| 격자 수가 1 이상 | 이번 주 활동 요약 | 새 격자 {N}개를 수집하고 영상 {M}개를 올렸어요. 도감에서 확인해 보세요 |
| 격자 수가 0 | 이번 주 활동 요약 | 영상 {M}개를 올렸어요. 다음 주에는 새 격자도 채워 볼까요? |

- 격자 수가 0인 갈래가 필요한 이유는 재방문 업로드만 한 주가 흔하기 때문이다. "새 격자 0개"라고
  말하는 요약은 넛지를 깎는다.
- 반대 경우(격자 수가 1 이상인데 영상 수가 0)는 분기를 만들지 않는다. 도달할 수 없기 때문이다.
  이번 주에 새로 생긴 도감 행은 그 격자의 첫 영상이 이번 주 업로드라는 뜻이고, 그 영상을 지우면
  video_count가 0이 되어 행 자체가 사라진다. 행이 남아 있다면 이번 주에 올라온 미삭제 영상이
  최소 하나 있다. 즉 영상 수는 항상 격자 수 이상이다.
- 두 수치가 동시에 0인 경우는 대상 조회에서 이미 걸러진다(D3).
- glossary 기준으로 "수집"과 "도감"만 쓰고 "점령"은 쓰지 않는다.
- FCM 페이로드는 title과 body뿐이다. 도감 화면으로 보내는 딥링크 데이터는 기존 4종에도 없어서 이번
  범위에 넣지 않는다.

### D6. 발송량과 파이프라인의 만남 (FR-9)

주간 배치는 다른 트리거와 성질이 다르다. 나머지는 사용자 행동을 따라 흩어져 발생하는데 이것은 한
시점에 전 활동 사용자 몫이 한꺼번에 쏟아진다. 그래서 상한을 걸지 않겠다는 판단에 근거를 붙인다.

- 컨슈머 switch에는 `case WEEKLY -> null`(상한 없음)을 넣는다. 이 switch는 exhaustive[^5]라 카테고리를
  추가하면 컴파일이 깨지므로 판단을 빠뜨릴 수 없다. 상한이 필요 없는 이유는 트리거가 이미 주당 1건
  이상 만들 수 없기 때문이다(이벤트 키가 주 단위). 발송 단계에서 한 번 더 세는 것은 같은 규칙을 두
  곳에 두는 일이 된다. `NotificationProperties.RateLimit`에 키를 추가하지 않는다.
- 처리 속도 실측 근거: 릴레이는 5초 고정 지연에 배치 100건이라 분당 최대 1,200건을 발행하고,
  컨슈머는 파티션 1개에 리스너 스레드 1개, `max.poll.records`가 10이다. 건당 작업은 DB 단문 몇 개와
  FCM 멀티캐스트 1회이며 FCM 왕복이 지배적이다. 왕복을 넉넉히 200ms로 잡으면 분당 300건 안팎이
  병목이 된다.
- 그래서 대상이 1,000명이면 대략 3분에서 4분, 10,000명이면 30분 남짓에 걸쳐 빠진다. 주간 요약은
  분 단위 지연이 무해한 알림이므로 배치 분할이나 페이징을 넣지 않는다. outbox 자체가 버스트를
  흡수하는 큐 역할을 한다.
- 다만 토픽이 단일 파티션이라 요약 물량 뒤에 들어온 영상 준비 완료 알림이 뒤에서 기다리게 된다
  (선두 차단[^6]). 일요일 19시를 고른 것이 여기서도 이득인데, 20시 리마인드 창까지 1시간 예산이
  있고 그 시간이면 위 처리 속도로 약 18,000건을 소화한다.
- 천장과 승격 경로는 명시해 둔다. 주간 활동 사용자가 1만 명을 넘어가면 발송 시각을 앞당기는 것이
  가장 싸고, 그다음이 토픽 파티션 증설과 컨슈머 병렬화, 마지막이 배치를 나눠 시간에 흩뿌리는 것이다.
- 대상 목록을 한 번에 메모리로 받는 것도 같은 규모에서만 유효하다. 사용자 1만 명이면 수백 KB라
  문제가 없고, 십만 단위가 되면 커서 페이징으로 바꾼다.

### D7. 설정 (FR-7)

설정 API는 `NotificationCategory.values()` 순회로 응답을 합성하므로 WEEKLY 추가만으로 조회와 토글이
자동으로 늘어난다. 서비스 코드는 손대지 않고 검증 테스트만 추가한다. 컨슈머의 `isEnabled`도 PK
존재 확인 단문이라 그대로 동작한다. 다만 기존 통합 테스트 두 개가 카테고리 4종을 튜플로 하드코딩하고
있어서 5종으로 갱신해야 한다(실측: `조회는_카테고리_4종_전부를_반환한다`,
`카테고리를_off하면_isEnabled가_false다`).

### 처리 순서

```text
1. KST 오늘로 주 시작을 구하고, 저장 존 기준 임계값 두 개(weekStart, now)를 만든다 (D2)
2. findWeeklyActivity(weekStart, now) 로 대상과 수치를 한 번에 읽는다 (D3)   <- 활동자만 나온다
3. 대상마다
   3-1. 격자 수에 따라 body 를 고른다 (D5)
   3-2. record(userId, WEEKLY, "WEEKLY:{ISO 주차}", "이번 주 활동 요약", body)
   3-3. 예외는 잡아서 세고 다음 사용자로 넘어간다 (사용자 단위 격리, D1)
4. 실패가 있었으면 warn 로그를 남긴다. 19시 30분 재발화가 같은 주 안에서 재시도한다
```

## 테스트 시나리오

통합 테스트는 실 PostGIS로 돌린다(Flyway 실행이 V26 CHECK를 자연 검증한다). 파이프라인 하류(릴레이,

**WeeklySummarySchedulerTest** (신규, 실 PostGIS, 스케줄러를 직접 생성해 메서드 호출)

고정 시계는 `2002-01-13T10:00:00Z`(KST 2002-01-13 일요일 19시)로 잡는다. 이 날짜 기준 주 시작은
KST 2002-01-07 월요일 0시이고 이벤트 키는 `WEEKLY:2002-W02`다. 과거 고정 시각이라 공유 DB의 현재
데이터가 창(주 시작 이상, 실행 시각 미만)에 들어오지 않아 결정적이다. 시드 행의 타임스탬프는

- 집계 창을 "직전에 완료된 월~일 주"로 잡을 수도 있었지만, 일요일 저녁 발송과 묶으면 데이터가
  일주일 묵은 요약이 된다. 지금 끝나가는 주를 실행 시각까지 자른 창으로 확정했고, 그 대가인
  일요일 저녁 5시간 사각지대는 D2에 명시했다.
- 시간대 바인딩은 레포의 UTC 바인딩 관례를 그대로 따르지 않는다. 집계 재료 두 컬럼이 UTC가 아니라
  JVM 기본 존 벽시계로 저장되기 때문이며, 실측 근거는 D2의 표에 있다.

[^1]: outbox: 알림을 곧바로 외부(FCM)로 보내지 않고 DB 테이블(`notifications`)에 먼저 기록해 두는
  패턴이다. 릴레이가 그 테이블을 폴링해 Kafka로 발행하므로, 기록만 커밋되면 발송은 나중에라도
  반드시 시도된다. 주간 배치처럼 한꺼번에 쏟아지는 물량에서는 이 테이블이 완충 큐 역할도 한다.
[^2]: 멱등: 같은 작업을 여러 번 실행해도 결과가 한 번 실행과 같은 성질이다. 여기서는
  (user_id, event_key) UNIQUE 제약과 ON CONFLICT DO NOTHING이 재발화와 재실행을 1건으로 접어 준다.
[^3]: 세션 타임존 캐스트: timestamptz 값을 timestamp 컬럼에 넣을 때 PostgreSQL이 접속 세션의
  타임존으로 벽시계를 환산하는 동작이다. JDBC 세션은 JVM 기본 시간대를 따르므로, 같은 코드가
  UTC 서버와 KST 서버에서 9시간 다른 값을 저장한다.
[^4]: ISO 주차(ISO-8601 week): 월요일에 시작하고 첫 목요일이 든 주를 그 해의 1주로 세는 국제 표준
  주 번호다. 연말 경계에서는 주가 걸친 두 달력 연도 대신 "주 기반 연도" 하나에 귀속되므로, 한 주가
  두 개의 키로 쪼개지지 않는다.
[^5]: exhaustive switch: enum의 모든 값을 다뤘는지 컴파일러가 검사하는 switch 식이다. 카테고리를
  추가하면 컴파일이 깨지므로, 전송률 정책을 정하지 않은 채 새 카테고리가 발송 경로에 흘러드는 일이
  구조적으로 막힌다.
[^6]: 선두 차단(head-of-line blocking): 한 줄로 처리되는 큐에서 앞의 항목이 오래 걸리면 뒤의 항목이
  준비돼 있어도 기다리게 되는 현상이다. 알림 토픽이 파티션 1개라 주간 요약 물량이 뒤따르는 다른
  알림의 발송 시각을 밀어낸다.
