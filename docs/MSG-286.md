# MSG-286: AI 프리체크 탈락 영상 즉시 실패 처리 (BE 소비)

**Owner**: B (video 도메인 — `com.msg.fillmap.video.*`)

> 요구사항 정본: `docs/prd/MSG-286-prd.md` (상태: 검토됨, 2026-08-03 성민 승인). 이 스펙은 PRD
> FR-1~6·비기능에 "어떻게"만 붙인다. AI 응답 계약 정본: FillMap-AI 레포
> `docs/prd/MSG-284-prd.md` FR-4~6.

## 개요

AI가 프리체크 탈락시킨 영상(암흑·렌즈 가림)은 `status=DONE` + `precheck={passed:false, reason}` +
`highlights=[]`로 5초 만에 끝나지만, BE는 `precheck`를 안 읽어 DONE 경로로 들어가 블러본
다운로드 409 → null → 타임아웃 경로로 빠진다. 그래서 사용자는 30분(PT30M) 뒤에야 FAILED를 본다.
폴러가 `precheck.passed == false`를 읽어 **즉시 FAILED로 수렴**시키고, 탈락 사유 코드(`too_dark`
등)를 영상 단위로 남겨 시스템 오류 FAILED와 구분한다. 새 ProcessingStatus는 만들지 않는다
(PRD 비목표 — 탈락도 FAILED 수렴 + 사유 코드 구분).

## 배경 · 목표

촬영이 잘못된 영상을 올린 사용자가 실패를 수 분 안에 알게 한다 — 30분 침묵 후 실패는 시스템
오류로 오해된다 (PRD §2). 목표: 탈락 영상이 다음 폴링 주기(≤30초) 안에 실패 확정 + 사유 코드가
남는다. FE 노출 API는 비범위(별도 협의).

## 성공 기준

1. 탈락 응답(`precheck.passed == false`)을 받은 폴 사이클에서 즉시 `markBlurFailed` — 타임아웃
   대기 없음, `downloadBlurred` 호출 없음 (FR-1·FR-6)
2. `videos.fail_reason`에 사유 코드(콜론 앞 안정 식별자, 예 `too_dark`)가 남는다 — 시스템 오류
   FAILED는 NULL이라 구분된다 (FR-4)
3. `precheck` 필드 부재(AI 구버전)·`precheck: null`(판정 전)·`passed: true`는 기존 경로 그대로
   (FR-2·FR-3): DONE 소비·409 대기·타임아웃 모두 불변
4. AI 명시 FAILED 즉시 실패·404 미제출 복귀(MSG-283) 기존 테스트 전부 green 유지 (FR-5)
5. `reason`이 null·미지 코드·비정상 길이여도 실패 처리 자체는 동작한다 (PRD 엣지)

## API 명세

없음 — 백엔드 내부 폴러 동작 변경. API 표면·응답 포맷 불변. FE 노출은 비범위(PRD §2 비목표).

### D1. `AiClient` — precheck 파싱 (계약 매핑 확장)

`AiJobResult`에 `Precheck` 컴포넌트를 추가한다:

```java
/** 프리체크 판정 (MSG-284 FR-4). reason 은 계약 원문 그대로 — 코드 추출은 소비 지점(폴러) 몫. */
public record Precheck(boolean passed, String reason) {
}

public record AiJobResult(AiJobStatus status, List<List<Double>> highlights, boolean notFound,
	Precheck precheck) {

	/** precheck 부재 호환 생성자 — 기존 생성부(테스트 다수)와 404 경로가 그대로 쓴다. */
	public AiJobResult(AiJobStatus status, List<List<Double>> highlights, boolean notFound) {
		this(status, highlights, notFound, null);
	}
}
```

파싱은 `highlights(response)`와 같은 관례의 private 메서드:

- `response.path("precheck")`가 missing/null → `null` (FR-3: 필드 부재 = 판정 안 함,
  판정 전 `precheck: null`도 동일 취급 — 계약상 구분할 이유가 없다)
- `passed`가 boolean이 아니면(malformed precheck 객체) → `null` — `asBoolean()` 기본값 false로
  탈락 오판하면 정상 영상이 즉시 실패한다. 오탐 0 우선(PRD 비기능 판정 성격)과 방향을 맞춰
  판정 불능은 기존 경로로 보낸다 (`parseStatus`의 UNKNOWN 방어와 같은 P2-b 계열)
- `reason`은 null이면 null, 있으면 원문 문자열 그대로 — **콜론 뒤 진단 수치를 파싱하지 않는다**
  (PRD 비목표, MSG-284 계약: 콜론 앞만 안정 식별자)

`downloadBlurred()`의 409 → null 처리는 **변경 없음** — 탈락 잡은 D2 분기가 이 경로에 아예
넣지 않는다 (실측 3).

### D2. `AiBlurPoller` — 탈락 즉시 실패 분기

MSG-283이 분리한 독립 if 대열에 합류한다. **위치: FAILED 뒤, DONE 앞** (실측 2):

```java
if (result.status() == AiJobStatus.FAILED) { ... }          // 기존 (FR-5 불변 — 최우선 유지)
if (result.precheck() != null && !result.precheck().passed()) {
	// 프리체크 탈락 = 그 파일로 재시도해도 같은 판정 (AI 임계값은 오탐 0 보수적) — 재검증 없이 즉시 수렴.
	log.warn("AI 프리체크 탈락 — 즉시 실패: videoId={} jobId={} reason={}",
		video.getId(), video.getAiJobId(), result.precheck().reason());
	statusWriter.markBlurFailed(video.getId(), video.getAiJobId(), video.getBlurringStartedAt(),
		failReasonCode(result.precheck().reason()));
	return;
}
if (result.status() == AiJobStatus.DONE) { ... }            // 기존 — 이제 passed=false 는 여기 못 온다
```

- **DONE 앞인 이유**: 탈락 잡은 status=DONE(MSG-284 FR-5)이라 DONE 블록에 먼저 걸리면
  `complete()` → `downloadBlurred` 409 → null → 타임아웃 경로 — 지금 버그 그대로다. 앞에 서면
  다운로드 시도 자체가 없다 (FR-6).
- **FAILED 뒤인 이유**: FAILED와 탈락이 동시에 오는 조합은 계약상 없다(탈락은 DONE). 혹시 오면
  기존 FAILED 경로가 이겨 사유 없는 시스템 실패로 남는다 — FR-5(기존 동작 불변)를 최우선으로
  두는 순서다. 프리체크 자체 실패(영상 열기 불가 등)도 계약상 `FAILED`+`error`로 오므로(MSG-284
  FR-8) 이 분기와 무관하게 기존 FAILED 경로가 처리한다.
- **status 조건을 걸지 않는 이유**: 판정은 precheck 필드로만 가른다(FR-2). 계약 위반으로
  PROCESSING+passed=false가 와도 탈락 확정이므로 기다릴 이유가 없다.
- 404(notFound) 결과는 편의 생성자로 만들어 precheck=null — 분기 상호작용 없음.

사유 코드 추출은 폴러의 private 헬퍼 하나로 (소비 지점 단일화):

```java
/** reason 원문("too_dark: std 3.18 < 10.0")에서 콜론 앞 코드만. null/blank 는 폴백, 64자 절단. */
private String failReasonCode(String reason) {
	if (reason == null || reason.isBlank()) {
		return "precheck_failed";   // 계약 위반(탈락인데 사유 없음)이어도 시스템 오류(NULL)와는 구분 (FR-4)
	}
	String code = reason.split(":", 2)[0].strip();
	return code.length() > 64 ? code.substring(0, 64) : code;
}
```

- **미지 코드도 그대로 저장** — BE에 코드 화이트리스트·enum 매핑을 두지 않는다. PRD 엣지
  "원문 코드 보존, 매핑 실패가 실패 처리를 막지 않는다"를 구조적으로 충족한다 (매핑이 없으니
  실패할 매핑도 없다). 코드 목록 관리는 AI 레포 계약 소관.
- **64자 절단** — 콜론 없는 비정상 장문 reason이 VARCHAR(64)를 넘겨 INSERT가 터지면 실패
  처리가 막힌다(엣지 요구 위반). trust boundary 방어.

`failIfTimedOut`(L200)·FAILED 분기(L131)의 기존 `markBlurFailed` 호출은 사유 인자에 `null`을
넘긴다 — NULL = 시스템 오류 (FR-4 구분).

### D3. `VideoStatusWriter.markBlurFailed` — 사유 파라미터 추가

신규 메서드가 아니라 **기존 시그니처에 파라미터 추가** (호출부 폴러 2곳뿐 — 실측 4):

```java
@Transactional(propagation = Propagation.REQUIRES_NEW)
public void markBlurFailed(Long videoId, String expectedJobId, LocalDateTime expectedStartedAt,
	String failReason)
```

- 가드(행 잠금 + `isCurrentBlurJob` + startedAt 일치)는 그대로 — 가드 skip 시 사유도 안 남는다
  (교체/삭제로 대상이 아니게 된 영상에 옛 잡의 사유를 밀지 않는다, 기존 P1/P2 일관).
- 통과 시 `video.markFailed(failReason)` 호출.
- 별도 상태 기계·신규 메서드를 만들지 않는다 — 탈락도 기존 FAILED 전이·가드에 수렴한다
  (PRD 비기능 데이터 정합).

### D4. `Video` 엔티티 — `failReason` 필드

```java
/** 실패 사유 코드 (MSG-286). 프리체크 탈락 시 콜론 앞 코드(too_dark 등), NULL=시스템 오류 실패. */
@Column(name = "fail_reason", length = 64)
private String failReason;

/** 변환 실패. 재시도는 없고 기록만 남긴다 (MSG-65 D8). 사유 없는 실패(인코딩·타임아웃)는 이쪽. */
public void markFailed() {
	markFailed(null);
}

/** 사유 있는 실패 (MSG-286 프리체크 탈락). */
public void markFailed(String failReason) {
	this.failReason = failReason;
	this.processingStatus = ProcessingStatus.FAILED;
}
```

- 기존 `markFailed()` 호출부(인코딩 실패 `VideoStatusWriter.markFailed`)는 무수정 — 오버로드
  위임으로 NULL 기록.
- **`replaceFile()`에 `this.failReason = null;` 추가** — 사유는 원본 파일에서 파생된 값이다.
  탈락 후 사용자가 파일을 교체하면 새 시도(UPLOADED 복귀)에 옛 사유가 남으면 안 된다
  (blurred/highlights/aiJobId와 같은 초기화 대열, 실측 6). FAILED는 종결 상태라(재시도 없음,
  MSG-65 D8) 교체 외의 재진입 경로가 없어 이 한 곳이면 충분하다.

-- V16__videos_fail_reason.sql
-- MSG-286: AI 프리체크 탈락 사유 코드. NULL = 시스템 오류 실패(타임아웃·AI FAILED·인코딩 실패).

ALTER TABLE videos
	ADD COLUMN fail_reason VARCHAR(64);

COMMENT ON COLUMN videos.fail_reason IS '실패 사유 코드 — 프리체크 탈락 시 콜론 앞 안정 식별자(too_dark 등), NULL=시스템 오류 (MSG-286)';

## 테스트 시나리오

모듈 단위 작업으로 분할 (각각 독립 등록 가능). 모듈 1·2는 상호 독립, 모듈 3은 1·2 선행 필요.

### 모듈 1 — `AiClient` precheck 파싱 (`AiClientTest` 추가, MockRestServiceServer 관례)

- `프리체크_탈락_응답이면_passed_false와_reason_원문을_매핑한다`
  — body `{"status":"DONE","highlights":[],"precheck":{"passed":false,"reason":"too_dark: std 3.18 < 10.0"}}`
  → `precheck().passed()==false`, `reason()` 원문 그대로(콜론 뒤 포함), status DONE
- `프리체크_통과_응답이면_passed_true_reason_null로_매핑한다` — `{"passed":true,"reason":null}` → passed true, reason null
- `precheck_필드가_없으면_null로_매핑한다` — 구버전 응답(기존 테스트 body 형태) → `precheck()==null` (FR-3)
- `precheck가_null이면_판정_전으로_보고_null로_매핑한다` — `"precheck":null` → `precheck()==null`
- `precheck의_passed가_boolean이_아니면_null로_매핑한다` — malformed `{"reason":"x"}` → null (오탐 방어)
- 기존 테스트(DONE·FAILED·UNKNOWN·404·409) 무수정 green — 편의 생성자·트리 파싱 호환 확인 (FR-5)

### 모듈 2 — `Video` + `VideoStatusWriter` 사유 기록 (`VideoStatusWriterTest`·엔티티 테스트 추가)

- `사유와_함께_실패하면_FAILED와_사유_코드가_기록된다`
  — `markBlurFailed(id, "job-1", startedAt, "too_dark")` → FAILED + `getFailReason()=="too_dark"`
- `사유_없이_실패하면_failReason은_null이다` — 기존 3인자 호출부 대응(4번째 null) → FAILED + NULL (FR-4 구분)
- `가드가_거부하면_사유도_기록되지_않는다` — 교체(`replaceFile`) 후 옛 잡 사유 → skip, failReason null 유지
- (엔티티, `VideoBlurTransitionTest` 관례) `교체하면_실패_사유가_초기화된다`
