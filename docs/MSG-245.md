# MSG-245: [BE] CI Flyway 가드 보강 — 적용된 V 파일 삭제·리네임 감지

**Owner**: 인프라(공통) — 도메인 코드 변경 없음, CI 설정만

## 개요

`ci.yml`의 "Flyway V 파일 수정 검사"(MSG-130)가 `--diff-filter=M`만 잡아서, 이미 적용된
V 파일의 **삭제(D)·리네임(R)은 통과**한다. diff-filter를 `MDR`로 확장하고 리네임을 R로
분류하도록 `--find-renames`를 명시한다. 신규 추가(A)와 `flyway-rewrite` 라벨 우회는 유지.

## 배경 · 목표

- 출처: Codex 교차 리뷰 (2026-07-24, P1).
- 신규 CI DB는 V 파일이 삭제·리네임돼도 빌드가 된다. 그러나 기존 배포 DB는
  `validate-on-migrate=true`라 applied 마이그레이션이 unresolved(삭제·버전 리네임) 또는
  description mismatch(설명부 리네임)로 보고돼 **기동 실패** — MSG-66(V1 재작성, dev
  32시간 다운)과 같은 계열의 구멍이다. 복구 절차 정본: `.claude/docs/deploy.md`
  "DB 마이그레이션 (Flyway)" 절.
- 목표: 수정뿐 아니라 삭제·리네임도 CI에서 차단.

## 결함 지점

`.github/workflows/ci.yml:60` — `git diff --name-only --diff-filter=M` (스텝 전체: 55~69행)

```
changed=$(git diff --name-only --diff-filter=M \
  "origin/${{ github.base_ref }}...HEAD" -- 'src/main/resources/db/migration/V*__*.sql')
```

## 성공 기준

- 라벨 없는 PR에서 기존 V 파일 삭제 → CI fail (삭제된 구경로 표시)
- 라벨 없는 PR에서 기존 V 파일 리네임 → CI fail (R + 경로 표시)
- 신규 V 파일만 추가하는 PR → CI pass (A는 필터 밖)
- `flyway-rewrite` 라벨 PR → 스텝 자체 skip (기존 동작 유지)

## 수정 방향

`ci.yml` 해당 스텝의 diff 명령만 교체. base 비교 기준(`origin/${base_ref}...HEAD`
merge-base 3점 diff)과 pathspec, 라벨 우회 조건(`if:`)은 그대로 둔다.

```bash
changed=$(git diff --name-status --find-renames --diff-filter=MDR \
  "origin/${{ github.base_ref }}...HEAD" -- 'src/main/resources/db/migration/V*__*.sql')
if [ -n "$changed" ]; then
  echo "::error::이미 적용된 Flyway V 파일이 수정·삭제·리네임됐습니다 — validate 불일치로 서버가 기동 실패합니다."
  echo "$changed" | sed 's/^/  /'
  echo "새 V 파일(V11__ ...)로 전진 수정하세요."
  echo "재작성이 불가피하면 'flyway-rewrite' 라벨 + .claude/docs/deploy.md 의 DB 정리 절차."
  exit 1
fi
echo "V 파일 수정·삭제·리네임 없음"
```

설계 근거 (git diff 동작 전제):

- **`--find-renames` 명시**: git 2.9+는 `diff.renames` 기본 on이라 R 분류가 되지만,
  러너 git 설정에 의존하지 않도록 명시한다. 만약 리네임 감지가 꺼지면 리네임은 D+A로
  분해되는데 D가 `MDR` 필터에 걸리므로 **어느 쪽 전제여도 차단은 된다** — 명시는
  메시지 정확성(R로 표기)을 위한 것.
- **`--name-only` → `--name-status` 교체**: R 상태는 `R100\t구경로\t신경로`처럼 유사도
  점수가 붙는다. `--name-only`는 리네임 시 신경로만 출력해 "무엇이 사라졌는지"가
  메시지에서 빠진다. `--name-status` 출력을 그대로 찍으면 상태·구경로·신경로가 모두
  보이고, R100 파싱용 grep/정규식이 아예 필요 없다. 비어있음 판정(`[ -n "$changed" ]`)은
  출력 포맷과 무관하게 동일하게 동작한다.
- **디렉터리 밖 이동 케이스**: V 파일을 `db/migration/` 밖으로 옮기면 pathspec이
  신경로를 배제해 리네임 쌍이 깨지고 구경로가 D로 잡힌다 — 역시 차단됨.
- **A(신규 추가) 계속 허용**: `MDR`에 A가 없으므로 `V11__xxx.sql` 추가 PR은 통과.

## 테스트 시나리오

CI 워크플로라 JUnit 테스트 대상이 아니다. 로컬 시뮬레이션과 CI 실증을 구분한다.

### 로컬에서 검증 가능 (diff 명령 조각 시뮬레이션)

임시 브랜치에서 실제 조작 후, 가드의 diff 명령을 base를 `origin/develop`으로 바꿔
직접 실행해 출력 확인. 실행 후 브랜치 폐기.

1. **삭제 감지**: `git rm src/main/resources/db/migration/V10__streak_badges_seed.sql`
   → 커밋 → 명령 실행 → `D\t...V10__streak_badges_seed.sql` 출력(비어있지 않음 = fail 경로)
2. **리네임 감지**: `git mv V10__streak_badges_seed.sql V10__streak_seed.sql` → 커밋 →
   `R100\t구경로\t신경로` 출력 확인
3. **수정 감지 (회귀)**: 기존 V 파일에 주석 한 줄 추가 → `M\t...` 출력 확인
4. **신규 추가 통과**: `V11__noop.sql` 추가만 → 출력 없음(pass 경로)
5. **디렉터리 밖 이동**: V 파일을 `src/main/resources/`로 `git mv` → D로 출력 확인

### CI에서만 실증 가능 (실제 PR)

- 라벨 없이 V 파일을 삭제/리네임하는 드래프트 PR → "Flyway V 파일 수정 검사" 스텝 fail 확인
- 신규 V 파일만 추가하는 PR(실제 다음 티켓의 마이그레이션이면 충분) → 스텝 pass 확인
- `flyway-rewrite` 라벨을 단 드래프트 PR → 스텝이 skip되는지 확인 (라벨 우회 회귀)

드래프트 PR은 확인 후 머지 없이 닫는다.
