# MSG-341: 격자 이름("서면 A-14")을 서버가 계산해 격자 조회 응답에 포함

**Owner**: 공동 (계약 인터페이스 신설: Owner A 제공, Owner B 소비)

> 요구사항 정본: `docs/prd/MSG-341-prd.md` (상태: 검토됨, 2026-08-07 승인. Codex 리뷰 2라운드 정정 반영본 기준)
> 이 티켓은 MSG-234 §D3("표시명은 클라이언트 로컬 계산, 서버는 문자열을 만들지 않는다")의 **결정 변경**이다.
> 명명 규칙 자체(행 A는 북단, 열 1은 서단, 행정동 폴백은 번호 없음)는 그대로고, 계산 주체만 서버로 옮긴다.

## 개요

격자를 담아 내려가는 조회 응답 9종에 구역 이름(`zoneName`, 예 "서면")과 구역 내 위치 코드(`zoneCell`, 예 "A-14") 두 필드를 추가한다. 계산은 신설 계약 인터페이스 `ZoneNameQueryService`(Owner A)가 zones 테이블 48행을 읽어 정수 산술로 수행하고, 이름 문자열은 DB에 저장하지 않는다. 구역 밖 격자는 두 필드가 모두 null이며, 클라이언트의 폴백 재료(`regionName`)는 응답마다 가용성이 달라 PRD 5절 폴백 표를 따른다. 그 표에 따라 영상 업로드 확정과 재생 응답에는 `regionName`(nullable)도 함께 추가한다.

## 배경 · 목표

지도 홈 격자 카드의 제목("서면 A-14")을 지금은 FE가 zones 캐시와 명명 규칙 자체 구현으로 만들어야 하고, Android와 iOS도 같은 규칙을 한 벌씩 더 구현해야 한다. MSG-325 진행 중 FE가 "조립만 하고 규칙은 갖지 않게 해달라"고 요청했다(PRD 1절).

목표는 **격자 이름을 표시하는 모든 화면**에서 클라이언트 3종이 명명 규칙 없이 응답 필드 조립만으로 이름을 만들 수 있게 하는 것이다. 라벨을 그리지 않는 지도 오버레이 응답(뷰포트, 핫구역)은 폴백 이름 요구가 없어 `zoneName`과 `zoneCell`만 갖고, 그 격자의 라벨이 필요한 상호작용(격자 클릭)은 단일 격자 조회와 by-grid 경로가 담당한다(PRD 2절 목표). FE 조립 규칙은 한 줄이다: `label = zoneName ? zoneName + " " + zoneCell : regionName` (regionName의 출처는 응답마다 다르고, 아래 "적용 대상 응답 9종" 표의 폴백 열이 그 확정본이다).

## 성공 기준

1. FR-1의 9종 응답 전부에 `zoneName`과 `zoneCell`이 실린다. 구역 안 격자는 두 값이 픽스처[^1] `zone-naming.json`의 분리 기대값(`expectedZoneName`, `expectedZoneCell`)과 정확히 일치하고, 구역 밖 격자는 둘 다 null이다 (FR-2, FR-3).
2. 미점령 격자를 단일 격자 조회로 봐도(occupied=false, grids row 유무 무관) 이름이 동일하게 계산된다 (FR-4).
3. 한 격자가 두 구역에 겹치면 priority 내림차순, 동률이면 zoneKey 사전순 타이브레이크[^2]로 하나만 선택된다 (FR-5).
4. zones가 재시딩(기동 시)으로 바뀌든 zone 수동 삭제(MSG-259 D-8의 공식 제거 절차, 재기동 없음)로 바뀌든, 별도 이름 갱신 배치 없이 이후 응답에 반영된다 (FR-6).
5. 항목 수와 무관하게 요청당 zones 로드는 상수 회다. 항목마다 zones를 DB에서 다시 조회하는 N+1 구조가 아니어야 한다 (FR-8). 뷰포트 최대 페이지 5,000건 기준 응답 시간 증가는 측정 오차 수준이다 (비기능 성능).
6. 업로드 확정과 재생 응답의 `regionName`은 다른 응답들의 `regionName`과 같은 축(격자 저장 라벨)의 값이라 화면 간 폴백 이름이 어긋나지 않는다 (FR-3, 5절 폴백 표).
7. OpenAPI 명세에 각 필드의 의미와 null 조건이 기술된다 (FR-7).

아래 "테스트 시나리오"가 1~6의 검증 수단이다.

## API 명세

엔드포인트 신설과 요청 형식 변경은 없다. 기존 응답에 필드를 얹는 하위 호환 확장[^3]만 있다.

### 추가 필드

| 필드 | 타입 | 적용 응답 | null 조건 | 설명 |
|------|------|-----------|-----------|------|
| `zoneName` | String | 9종 전부 | 구역 밖 격자면 null | 격자가 속한 구역의 이름 (zones.name, 예 "서면") |
| `zoneCell` | String | 9종 전부 | 구역 밖 격자면 null | 구역 내 위치 코드 "{행}-{열}" (행은 A~Z 1글자, 열은 1부터 정수, 예 "A-14") |
| `regionName` | String | 업로드 확정, 재생만 | 무귀속(해상 등)이거나 미판정이면 null | 격자 중심점 행정동 이름. 구역 밖 격자의 폴백 라벨 재료 |

`zoneName`과 `zoneCell`은 항상 쌍이다. 하나만 null인 상태는 없다. 세 필드 모두 `@Schema`에 `nullable = true`와 null 조건, 폴백 용도를 설명으로 달고, `requiredProperties`에도 함께 넣는다 (FR-7). Jackson 기본 직렬화라 값이 null이어도 키는 항상 응답에 나가므로 required는 "키 존재"를 뜻하고, nullable과 required는 병기가 정답이다. 레포 실행형 가드 `ResponseSchemaNullabilityTest`(MSG-319)가 이를 강제하며 `UserProfileResponseDto::email`이 선례다. (정정 2026-08-07: 초판의 "requiredProperties 미포함" 지시는 MSG-319가 폐기한 배타 취급의 재발이라 리뷰에서 반려됐다.)

응답 예시 (단일 격자 조회, 구역 안):

```json
{
  "gridId": "39064_112225",
  "occupied": true,
  "videoCount": 3,
  "zoneName": "서면",
  "zoneCell": "I-6"
}
```

구역 밖이면 `"zoneName": null, "zoneCell": null`이고 나머지는 기존과 같다. 업로드 확정 응답의 구역 밖 예시:

```json
{
  "videoId": 1001,
  "gridId": "41642_110458",
  "processingStatus": "UPLOADED",
  "occupied": true,
  "newBadges": [],
  "completedMissions": [],
  "zoneName": null,
  "zoneCell": null,
  "regionName": "서울특별시 강남구 역삼1동"
}
```

에러 케이스 변경 없음. 이름 계산은 검증을 통과한 격자 인덱스에 대한 순수 산술이라 새 실패 경로가 없고, 기존 에러(INVALID_GRID_ID, INVALID_VIEWPORT 등)는 이름 계산 이전에 던져진다. `regionName` 조회도 무귀속이면 null일 뿐 예외가 아니다.

## 도메인 로직

용어는 glossary.md 기준이다. 여기서 만드는 이름은 격자의 **표시명** 구성 요소이고, 점령이나 방문 같은 상태·이벤트와 무관하다. 격자는 논리 개념이므로 grids row가 없어도 이름이 계산된다.

### 명명 산술 (MSG-234 §D2 규칙 불변, 실행 주체만 서버로)

격자 인덱스 `(gridY, gridX)`가 어느 구역 사각형(`minGridY <= gridY <= maxGridY`이고 `minGridX <= gridX <= maxGridX`) 안이면:

- 행 문자 = `'A' + (maxGridY - gridY)` (A가 사각형 북단. zones의 남북 26행 캡 CHECK가 Z 초과를 막는다)
- 열 번호 = `gridX - minGridX + 1` (1이 사각형 서단)
- `zoneName` = 그 구역의 `name`, `zoneCell` = `"{행 문자}-{열 번호}"`

어느 사각형에도 안 들면 결과는 NONE(두 필드 null)이다. 행정동 폴백 문자열 조립은 서버가 하지 않는다. 조립은 FE 몫이고, 폴백에 번호를 붙이지 않는 규칙도 불변이다 (FR-3). 겹침은 priority 내림차순, 동률은 zoneKey 사전순으로 하나를 고른다 (FR-5).

### D-1: 계약 형태는 요청 스코프 스냅샷[^4] (`resolver()` 방식)

```java
// zone/service/ZoneNameQueryService.java: 신설 계약 (A 제공, B 소비)
public interface ZoneNameQueryService {

	/** zones 전체를 1회 로드한 불변 리졸버를 만든다. 목록 응답은 요청당 이걸 한 번만 받아 격자마다 산술한다. */
	ZoneNameResolver resolver();
}

// zone/service/ZoneNameResolver.java: 불변 스냅샷. 사각형 매칭 + 행렬 산술 (순수 함수, DB 미접근)
public final class ZoneNameResolver {

	/** 매칭 없으면 ZoneCellName.NONE (null 아님). 소비처는 분기 없이 두 필드를 그대로 DTO에 옮긴다. */
	public ZoneCellName name(long gridY, long gridX) { ... }
}

// zone/service/ZoneCellName.java
public record ZoneCellName(String zoneName, String zoneCell) {
	public static final ZoneCellName NONE = new ZoneCellName(null, null);
}
```

단건 메서드 `name(gridY, gridX)`를 계약 최상위에 두지 않는 이유: 응답 항목마다 zones 조회가 나가는 N+1 사용법을 계약 수준에서 봉쇄해 FR-8(요청당 상수 회 로드)을 구조로 보장하기 위해서다. 소비처는 매핑 시작 시 `resolver()`를 한 번 받고(zones SELECT 1회), 항목마다 `resolver.name(y, x)`를 부른다. 단건 응답(단일 격자, 업로드 확정, 재생)도 같은 패턴 한 줄이다. 반환을 Optional이 아니라 NONE 상수로 한 것도 같은 이유다. 소비처 매핑 9곳 전부에서 null 분기 없이 `n.zoneName(), n.zoneCell()` 두 게터를 꽂으면 끝난다.

리졸버는 생성 시 구역 목록을 priority 내림차순, zoneKey 사전순으로 정렬해 두고 첫 매칭을 반환한다. 정렬 1회로 타이브레이크가 해소되고, 격자당 비용은 최대 48회 사각형 정수 비교로 상수다.

### D-2: zones 읽기는 매 요청 조회. 프로세스 내 캐시 없음 (FR-6, FR-8)

- **채택**: `resolver()` 호출마다 `zoneRepository.findAll()` (요청당 1회).
- **기각**: 프로세스 내 캐시(TTL 또는 무기한 + 무효화 훅).
- **근거**: zones는 48행, 정수 8컬럼이다. 풀스캔이 밀리초 미만이고 PG 공유 버퍼에 상주한다. 캐시가 아끼는 것은 요청당 미세 쿼리 1개인데, 치르는 비용은 무효화 설계다. zones 변경 경로는 두 갈래다. 재시딩은 기동 시에만 돌아(MSG-259 D-8) 캐시로도 안전하지만, zone 수동 삭제(같은 D-8의 공식 제거 절차)는 재기동 없이 일어나므로 무기한 캐시면 영영 반영이 안 되고 TTL 캐시면 FR-6("이후 응답에 반영")이 TTL만큼 늦는다. 매 요청 조회는 두 경로 모두에서 FR-6을 즉시 충족하고, 무효화 전략이라는 결정 자체를 없앤다.
- **FR-8 충족 구조**: N+1 금지는 D-1의 계약 형태가 보장한다. `resolver()` 1회 = zones 로드 1회이고, 항목 계산(`name`)은 DB에 안 간다.
- **성능 셈**: 뷰포트 최대 페이지 기준 추가 비용은 zones SELECT 1회 + 최대 5,000 × 48 사각형 비교(비교당 정수 4쌍)다. 마이크로초 수준이라 비기능 목표(측정 오차 수준) 안이다.
- **승격 경로**: zones가 수백 행대로 늘거나 실측에서 이 쿼리가 보이면 그때 짧은 TTL 캐시를 얹는다. 그 시점에 수동 삭제 반영 지연(TTL 상한)을 운영 규칙으로 함께 문서화해야 한다.

### D-3: 기존 계약 테스트의 참조 구현을 실물로 승격

`ZoneNamingContractTest`는 "서버에 ZoneNamer가 없는 동안" 참조 구현(contains, label, pick, displayName)을 테스트 안에 유지한다고 스스로 명시하고 있다(주석 L29~30). 이번 티켓이 바로 그 종료 지점이다. 테스트 내부 참조 구현을 삭제하고, 픽스처 케이스를 실물 `ZoneNameResolver`에 넣어 검증하도록 개편한다. 규칙 정본은 계속 픽스처 파일 하나다(비기능 데이터 정합).

### D-4: 픽스처에 분리 기대값을 가산하고 서버 테스트는 그것만 소비 (FR-2)

기존 `expected`는 폴백까지 포함한 통짜 문자열이라 분리 필드(zoneName, zoneCell) 검증에 쓸 수 없다. `zone-naming.json`의 각 케이스에 `expectedZoneName`과 `expectedZoneCell`을 가산 추가한다(구역 매칭 없는 케이스는 둘 다 null). 기존 `expected`는 그대로 유지되어 FE와 모바일 소비자는 영향받지 않는다.

- 서버 테스트 판정: `resolver.name(y, x)`의 결과가 `(expectedZoneName, expectedZoneCell)`과 정확히 일치.
- 픽스처 자체 모순 방지 가드: 케이스마다 두 표기의 정합을 함께 검증한다. `expectedZoneName`이 있으면 `expectedZoneName + " " + expectedZoneCell == expected`, null이면 `expected == regionName`(폴백) 또는 `expected == null`이어야 한다. 분리 기대값과 통짜 기대값이 어긋난 채 픽스처가 갱신되는 사고를 테스트가 막는다.

### D-6: 업로드 확정과 재생 응답의 `regionName`은 저장 라벨(grids.region_code) equi 조회로 얻는다

- **채택**: `VideoRepository`에 native 조회 1개 신설 (쿼리 계약을 여기 명시한다):

  ```java
  /** 격자 저장 라벨의 행정동 이름. grids row 없음(이론상 도달 불가) 또는 region_code NULL(무귀속)이면 empty. */
  @Query(value = """
  	SELECT r.region_name FROM grids g
  	JOIN regions r ON r.region_code = g.region_code
  	WHERE g.grid_id = :gridId
  	""", nativeQuery = true)
  Optional<String> findRegionNameByGridId(@Param("gridId") String gridId);
  ```

  업로드 확정은 `upsertGrid` 직후에 호출한다. upsert는 region_code 판정과 저장까지만 하고 이름을 반환하지 않으므로, 이 이름 변환 조회 1회가 추가로 필요하다(PRD 5절 명시). 신규 격자도 그 INSERT에서 라벨이 이미 저장돼 있어 같은 트랜잭션에서 바로 읽힌다. 재생은 `video.getGridId()`로 같은 쿼리를 호출한다. 결과 empty면 응답 `regionName`은 null이다.
- **기각**: `RegionQueryService.resolveByPoint(lat, lng)` 재호출.
- **근거**: 폴백 표의 다른 응답들(도감 목록, 카드 리스트, 친구 최근 격자)의 `regionName`은 전부 격자 축(grids.region_code 경유) 값이다. 재생 경로에는 애초에 좌표가 없어 격자 축이 유일한 선택이고, 업로드 경로도 좌표 축(영상 좌표)으로 판정하면 경계 격자에서 격자 축과 다른 동이 나와 화면 간 폴백 이름이 어긋날 수 있다(성공 기준 6). 비용은 geospatial 연산 0회, 단건 PK equi SELECT 1회라 무시 가능한 수준이다(PRD 5절과 동일 판단). video 도메인이 grids와 regions를 native로 조인하는 것은 `findExploreGridsLatest`, `getRegionExploreSummary` 등 기존 선례 그대로라 크로스 오너 인터페이스 신설이 필요 없다.

[^4]: 스냅샷: 한 요청을 처리하는 동안 고정된 데이터 사본. 여기서는 zones 48행을 요청당 1회 읽어 불변 리졸버에 담고, 그 요청의 격자 수천 건이 같은 사본으로 계산되게 한다. 페이지 중간에 zones가 바뀌어 항목끼리 이름 기준이 갈리는 일도 막는다.
[^5]: 뷰 객체: 서비스가 컨트롤러(또는 다른 도메인 서비스)에 돌려주는 내부 전달용 record. HTTP 응답 DTO와 분리해 서비스 간 계약을 HTTP 형식에서 독립시킨다. 이 코드베이스에서는 `GridCellView`처럼 `View` 접미사를 쓴다.

**런타임 동작 기록**

- 데이터 저장 위치: 없음. 이름은 저장하지 않고 요청 시 계산한다(비정규화 없음). 읽는 저장소는 기존 zones(48행), grids.region_code, regions뿐이고 마이그레이션도 없다
- 실행 쿼리: ① `ZoneNameQueryServiceImpl.resolver()`가 `ZoneRepository.findAll()`(`select z from Zone z` 파생, zones 전행)을 요청당 1회. 항목 계산은 DB 미접근(FR-8) ② `VideoRepository.findRegionNameByGridId`(native): `SELECT r.region_name FROM grids g JOIN regions r ON r.region_code = g.region_code WHERE g.grid_id = :gridId`. 업로드 확정(upsertGrid 직후)과 재생에서 각 1회, 무귀속이면 empty이고 응답 regionName은 null
- 예외 흐름: 신규 실패 경로 없음. 이름 계산은 기존 검증(INVALID_GRID_ID, INVALID_VIEWPORT 등) 통과 후의 순수 산술이다. ZoneCellName 혼합 null은 IllegalArgumentException을 던지는 방어선인데 정상 경로에서 도달 불가하고, 도달하면 GlobalExceptionHandler 최후 절이 500 INTERNAL_SERVER_ERROR로 변환한다. 재생 경로의 이름 계산과 regionName 조회는 접근 제어 분기(존재, BLINDED, visibility) 뒤라 거부된 요청에서는 실행되지 않는다
- 빈 동작: `ZoneNameQueryServiceImpl`은 자체 `@Transactional(readOnly = true)`라 트랜잭션 없는 소비처(hotzone Redis 조회, search 카카오 프록시)에서도 독립 동작한다. 캐시, 스케줄러, 생명주기 훅 없음. 리졸버는 요청 스코프 불변 객체라 페이지 처리 중 zones가 바뀌어도 그 요청 안에서는 항목 간 이름 기준이 일관된다
