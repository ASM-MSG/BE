# MSG-223: 미션 완료 판정·스탬프 발급

**Owner**: B (mission·video·badge 전부 Owner B — infrastructure.md 기준)

> 요구사항 정본: `docs/prd/MSG-219-mission-prd.md` (상태: 검토됨, 2026-07-30 성민 승인) — 이 스펙의
> 범위는 그중 **FR-11~19 (완료 판정·스탬프 발급)** 다. 축제 적재(FR-1~5, MSG-224)·코스 시드
> (FR-6~10, MSG-225)는 스코프 아님.
> 상세 근거: 위키 `04-decisions/미션 후속 결정 코스 포토스팟 방식.md` (cf-23396353) · V6 스키마(MSG-166).

## 개요

미션 대상 격자에 조건을 충족하는 영상 업로드가 확정되면 서버가 자동으로 미션을 판정하고
스탬프(`user_missions`)를 발급한다. 5종 미션(COURSE·AREA·EVENT·THEME·CONTINUOUS)을 유형별 전략
클래스 없이 **단일 판정 쿼리 하나**로 처리하고(FR-13), 스탬프 발급 시 MISSION_COUNT 뱃지 축을
활성화하며(FR-17), 완료 스탬프를 업로드 응답에 동봉한다(FR-19). 신규 API 엔드포인트·신규 DDL 없음.

## 배경 · 목표

미션 인프라는 절반만 있다 — V6 스키마와 활성 미션 조회(MSG-222)는 준비됐지만 미션 격자에 영상을
올려도 아무 일도 일어나지 않는다(판정·보상 부재). 이 티켓이 발견 → 참여 → **보상**의 마지막 고리를
잇는다. 목표: 도감(면적)과 별개의 수집 축(스탬프북=개수)을 열고, V9가 예약한 MISSION_COUNT 뱃지
축을 이행한다.

## 성공 기준

아래 "테스트 시나리오"가 이 기준의 검증 수단이다.

1. 활성 미션 대상 격자에 기간 내 `recorded_at` 영상 업로드 → `user_missions` 1행 생성 + 업로드
   응답 `completedMissions`에 해당 미션 포함 (FR-11·19)
2. 미션 미해당 격자 업로드(지배 경로) → 추가 쿼리 1회(후보 역조회)로 조기 종료,
   `completedMissions` 빈 배열 (FR-18·비기능 성능)
3. 기간 밖 `recorded_at` 영상(작년 기록)은 카운트되지 않고, 무기간 미션(코스)은 과거 영상도
   인정된다 (FR-12)
4. 같은 격자 재방문은 distinct 카운트라 진행이 늘지 않는다 — target_count는 "서로 다른 격자 수" (FR-13)
5. 같은 미션의 스탬프는 사용자당 1개 — 동시 업로드 경합에서도 중복 발급·중복 응답 없음 (FR-14)
6. 영상을 삭제해도 발급된 스탬프는 유지된다 — 삭제·교체 경로 무변경 (FR-15)
7. `user_grids`는 미션 판정이 일절 건드리지 않는다 — 점령은 기존 업로드 흐름의 몫 그대로 (FR-16)
8. 스탬프 1·5·10개째에 MISSION_COUNT 뱃지가 `newBadges`로 함께 동봉된다 (FR-17)
9. `./gradlew test` green

## 도메인 로직

용어: 스탬프 발급의 근거는 **방문**(videos 이벤트)이지 **점령**(user_grids 상태)이 아니다.

### D1. 판정 시각 컬럼 = `videos.recorded_at` (티켓 "uploaded_at" 문구의 확정 해석)

티켓 설명의 "uploaded_at"은 videos에 없는 컬럼이다. 실제 후보는 `recorded_at`(촬영 시각)과
`created_at`(업로드 시각)이며, **`recorded_at`으로 확정**한다. 근거:

- 선행 결함 정리 MSG-242가 "교체 시 `recordedAt` 엔티티 반영 — **미션 기간 판정(MSG-223) 선행**"으로
  명시돼 있다(status.md video 섹션) — 판정이 recorded_at을 읽는다는 전제의 선행 작업.
- FR-12의 목적("작년 기록으로 오발급 차단")과 정합: 작년 축제 때 찍은 갤러리 영상을 올해 축제
  기간에 업로드하면 `created_at` 기준으론 통과하지만 `recorded_at` 기준으론 차단된다. "그 기간에
  그곳에서 찍었다"가 축제 미션의 의미다.
- 한계(수용): `recordedAt`은 클라이언트 신고값(갤러리 메타데이터)이다. 위조 가능성은 갤러리 업로드
  좌표 신뢰와 같은 클래스로 MVP 수용 — PRD 보안 요구는 "발급 직접 호출 API 부재"까지다.

### D2. 판정 흐름 — 쿼리 2개 + INSERT (PRD 시퀀스 다이어그램 그대로)

트리거는 `VideoServiceImpl.saveVideo`의 업로드 확정 훅(badge·streak 배선 지점, MSG-155와 같은
트랜잭션)이며, `MissionAwardService.awardOnUpload(userId, gridId)` 호출 1줄이다.

**1단계 — 후보 역조회** (`idx_mission_grids_grid` V6 기존). 활성 술어는 `findActive`와 동형,
이미 받은 스탬프는 후보에서 제외:

```sql
SELECT m.id
FROM mission_grids mg
JOIN missions m ON m.id = mg.mission_id
WHERE mg.grid_id = :gridId
  AND (m.start_at IS NULL OR m.start_at <= statement_timestamp() AT TIME ZONE 'UTC')
  AND (m.end_at IS NULL OR statement_timestamp() AT TIME ZONE 'UTC' <= m.end_at)
  AND NOT EXISTS (SELECT 1 FROM user_missions um
                  WHERE um.user_id = :userId AND um.mission_id = m.id)
```

빈 결과(대부분의 업로드)면 **여기서 조기 종료**(FR-18) — 판정 쿼리를 실행하지 않는다.
`statement_timestamp()`는 MSG-200 선례(트랜잭션이 S3 복사를 끼고 길어질 수 있어 `now()`의
트랜잭션 시작 시각 고정을 피한다). `AT TIME ZONE 'UTC'` 부가는 필수다 — `timestamp <=
timestamptz` 비교는 세션 타임존으로 캐스트돼 KST 세션에서 9시간 스큐가 난다(리뷰 실측,
2026-07-30 구현 반영·StreakRepository 동일 패턴). **이 SQL을 복사하는 후속 작업(MSG-224 시더 등)도
동일 규칙 준수.**

**2단계 — 단일 판정 쿼리** (설계검토 확정 — 유형 5종 무분기, FR-13). 후보 전부를 한 번에:

```sql
SELECT m.id AS mission_id, m.title, m.type
FROM missions m
JOIN mission_grids mg ON mg.mission_id = m.id
JOIN videos v ON v.grid_id = mg.grid_id
	AND v.user_id = :userId
	AND v.status <> 'DELETED'
	AND (m.start_at IS NULL OR v.recorded_at >= m.start_at)
	AND (m.end_at IS NULL OR v.recorded_at <= m.end_at)
WHERE m.id IN (:candidateIds)
GROUP BY m.id, m.title, m.type, m.target_count
HAVING COUNT(DISTINCT v.grid_id) >= m.target_count
```

- 기간 조건이 `IS NULL OR` 형태라 무기간(코스, start/end null)은 조건이 자연 생략된다(FR-12) —
  코드 분기 없음. 경계는 양끝 포함(`findActive`·BETWEEN 동형).
- `status <> 'DELETED'`: 삭제 영상은 판정 근거에서 제외 — 위키 결정 "영상 삭제로 조건 미달이
  돼도 [기발급 스탬프는] 유지"가 삭제 제외를 전제한다. BLINDED는 포함 — 촬영 사실은 유효하고
  블라인드는 노출 문제다.
- 방금 업로드한 영상은 `saveAndFlush`로 이미 flush돼 같은 트랜잭션의 이 쿼리가 본다.
- 규모: 후보 미션의 대상 격자는 축제 81(9×9)·코스 5~8곳 — 격자별 videos 조회는 인덱스 범위.

**3단계 — 스탬프 발급** (FR-14·15). 충족 미션마다:

```sql
INSERT INTO user_missions (user_id, mission_id) VALUES (:userId, :missionId)
ON CONFLICT DO NOTHING
```

영향 행 1인 것만 `completedMissions`에 담는다 — 동시 업로드 경합에서 상대 트랜잭션이 먼저
발급했으면 내 INSERT는 0이고 "이 요청으로 새로 획득한" 게 아니므로 응답 제외
(`BadgeAwardServiceImpl.insertIgnoreConflict` §D5 패턴 미러, PostgreSQL이 conflict 판정 전 선행
커밋을 대기하므로 경합 안전). `completed_at`은 컬럼 DEFAULT.
**`user_grids`에는 어떤 쓰기도 없다**(FR-16) — 가짜 격자 삽입 절대 금지.

**4단계 — MISSION_COUNT 뱃지** (FR-17). 새 스탬프가 1개 이상일 때만:

```java
badgeAwardService.award(userId, BadgeConditionType.MISSION_COUNT, userMissionRepository.countMyStamps(userId));
```

metric = 내 스탬프 총수(`COUNT(*)::numeric FROM user_missions WHERE user_id = :userId`).
비회수라 단조 증가 — 뱃지 비회수 원칙과 정합. BadgeAwardService는 범용 진입점 `award(type, metric)`
그대로 사용, badge 도메인 코드 수정 없음(시딩만, 데이터 모델 참조).

### D3. 시간 계약 — UTC 순간 비교, KST 변환은 시드 몫

DB TIMESTAMP는 UTC 저장(glossary 규칙). `missions.start_at/end_at`도 **UTC 순간**이다 — 축제
"7/1~7/5 (KST)"를 `start_at='2026-06-30 15:00:00'`, `end_at='2026-07-05 14:59:59'`로 넣는 변환은
시더(MSG-224) 몫이고, **이 스펙의 판정은 순수 순간 비교만 한다**(존 로직 없음). KST 경계 판정
예시가 테스트 계약이다: 7/1 00:10 KST(=6/30 15:10 UTC) 촬영 영상은 인정, 6/30 23:50 KST는 불인정.

### D4. 트리거 범위 — saveVideo만, 교체·삭제 무변경

- **삭제**: 스탬프 비회수(FR-15)라 회수 훅이 없다. 이후의 새 판정에서만 삭제 영상이 제외된다(D2).
- **교체**: 판정 트리거가 아니다 — 격자 불변(기존 GRID_MISMATCH 규칙)이고, 갱신된 `recordedAt`은
  다음 업로드가 트리거한 판정이 읽는다(MSG-242가 그 정합을 선행 확보). 교체를 트리거에 넣는 확장은
  근거 티켓 없이는 하지 않는다.
- **활성 미션만 판정**(1단계 술어): 축제 종료 후 업로드는 그 기간에 찍은 영상이라도 스탬프가 없다 —
  "기간 내 업로드 확정"(FR-11)이 트리거 조건이고, 이래서 스탬프가 영속이어야 한다(만료 후 재계산
  복원 불가).

### 모듈 1 — 스탬프 영속층 (`UserMission`·`UserMissionRepository`·V12)
