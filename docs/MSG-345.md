# MSG-345: 웹 카카오 로그인 인가 코드 교환

**Owner**: B (auth 도메인, CLAUDE.md 협업 원칙 기준)

> 요구사항 정본: `docs/prd/MSG-345-prd.md` (상태: 검토됨, 2026-08-08 승인). 이 스펙은 PRD의
> FR-1~7과 비기능 요구사항에 "어떻게"만 붙인다. 발단은 지라 MSG-325의 FE 코멘트(2026-08-07
> 최규호)로, FE는 인가 요청에 `scope=openid`를 넣고 카카오 콘솔 REST 키에
> `http://localhost:5173/oauth/kakao/callback` 등록을 마친 상태다. 인가 요청의 nonce는
> 서버 발급값을 쓴다(2026-08-08 확정, 보안 절).

## 개요

웹 프론트가 카카오 JS SDK로 받은 인가 코드[^1]를 서버에 보내면, 서버가 REST API 키로 카카오
토큰 엔드포인트를 호출해 OIDC ID 토큰을 얻고, 기존 소셜 로그인과 완전히 같은 검증과 발급
경로(`OidcLoginService.login`)를 태워 토큰 세트를 돌려준다. 신규 엔드포인트 하나, 교환 컴포넌트
하나, 에러 코드 두 개가 전부다. 기존 모바일 경로(`POST /api/auth/oauth/{provider}`)는 변경 없다.

## 배경 · 목표

카카오 정책상 인가 코드를 토큰으로 바꾸는 호출은 서비스 서버가 REST API 키로 해야 하는데,
현재 서버에는 그 교환 경로가 없어 웹 카카오 로그인이 끊겨 있다(PRD 1절). MSG-325 지도 홈
실연동을 포함한 웹 전체가 로그인 위에서만 성립하므로 이 티켓이 선행 과제다. 목표는 웹 프론트가
서버 호출 한 번으로 기존 소셜 로그인과 동일한 토큰 세트를 받는 것이다.

## 성공 기준

1. 웹 FE가 유효한 인가 코드와 redirect URI로(발급받은 nonce 쿠키 동반)
   `POST /api/auth/oauth/kakao/code`를 호출하면
   200과 함께 액세스 토큰(body), 리프레시 토큰(HttpOnly 쿠키[^5]), `X-Device-Id` 응답 헤더를
   받는다. 형태와 전송 규칙은 기존 `POST /api/auth/oauth/kakao`와 구분 불가능하게 같다 (FR-2).
2. 무효한 코드(만료, 재사용, redirect URI 불일치), ID 토큰 누락, nonce 불일치는 모두 401
   하나(`developCode 2423`)로 수렴하고, 카카오의 KOE 코드[^4]는 서버 로그에만 남는다
   (FR-5, FR-6, FR-8). 사용자 재시도로 해소되지 않는 카카오 거절(레이트 리밋, 설정 오류)은
   2423이 아니라 2502로 분류된다.
3. 카카오 무응답이나 5xx는 502(`developCode 2502`)로 응답하며, 연결과 읽기 타임아웃이 있어
   무한 대기하지 않는다 (FR-7, 비기능 성능).
4. 기존 모바일 경로와 이메일 로그인, 재발급의 동작과 테스트가 전부 그대로 통과한다.
5. 교환으로 얻은 ID 토큰도 기존 검증기(`kakaoJwtDecoder`[^3])의 서명, issuer, audience 검증을
   전부 통과해야만 로그인된다. 검증 완화 없음 (FR-3).

## API 명세

### `POST /api/auth/oauth/kakao/nonce` (신규, 인증 불요, 웹 전용)

로그인 직전 FE가 호출하는 nonce 발급 API다. 서버는 난수를 만들어 body로 반환하면서 같은
값을 HttpOnly 쿠키로도 심는다. 이 이중 전달이 결속의 핵심이다(보안 절).

**응답**: `KakaoNonceResponseDto` (신규). `data.nonce`와 `Set-Cookie` 값이 같다.

| 쿠키 속성 | 값 |
|---|---|
| 이름 | `OAUTH_NONCE` |
| Max-Age | 600초 (10분 안에 로그인을 마치면 된다) |
| 고정 속성 | HttpOnly, Path는 `/api/auth/oauth/kakao` 한정 |
| 프로파일 분기 | 공통(dev, prod): `Secure; SameSite=None` (크로스사이트 배포 가정, 리프레시 쿠키와 동일). local: `SameSite=Lax`에 Secure 없음 |

리프레시 쿠키(`Secure; SameSite=None` 고정)를 그대로 미러링하지 않는 이유: 그 쿠키는 로컬
웹 개발을 앱 모드(body 전달)로 우회하는 선행 결정이 있었지만(MSG-135 확정 결정 8), nonce
쿠키는 보안 장치 자체라 우회 경로를 둘 수 없다. `Secure; SameSite=None`이면 http 로컬에서
브라우저가 쿠키를 저장하지 않아 웹 로그인이 항상 2423으로 죽는다(Codex 리뷰 반영,
2026-08-08). localhost는 5173과 8080이 같은 사이트로 취급돼 Lax로 충분하고, 분기는
`oauth.kakao.nonce-cookie-secure` 프로퍼티 하나가 결정한다(true면 None+Secure, false면
Lax+비Secure).

요청 body 없음. 재호출하면 새 값으로 덮어쓴다(진행 중이던 이전 로그인 시도는 무효가 된다).

### `POST /api/auth/oauth/kakao/code` (신규, 인증 불요)

FE 제안 경로를 그대로 확정한다. 기존 `POST /api/auth/oauth/{provider}`와는 경로 세그먼트
수가 달라 매핑 충돌이 없다. 카카오 외 제공자의 코드 교환은 PRD 비목표이므로 경로에 `kakao`를
고정하고 `{provider}` 변수를 두지 않는다.

**요청 헤더** (기존 소셜 로그인과 동일):

| 헤더 | 필수 | 설명 |
|---|---|---|
| `X-Client-Type` | 아니오 | `web`(기본) 또는 `app`. 리프레시 토큰 전송 방식 결정 |
| `X-Device-Id` | 아니오 | 없으면 서버가 UUID를 생성해 응답 헤더로 반환 |

**요청 body**: `KakaoCodeLoginRequestDto` (신규, `auth/dto/`)

```json
{
	"code": "vBv8oXbeLnDF2mkw...",
	"redirectUri": "http://localhost:5173/oauth/kakao/callback"
}
```

| 필드 | 타입 | 검증 | 설명 |
|---|---|---|---|
| `code` | String | `@NotBlank` | 카카오 콜백으로 받은 1회용 인가 코드 |
| `redirectUri` | String | `@NotBlank` | 인가 요청에 썼던 redirect URI 그대로. 서버는 화이트리스트 없이 교환 호출에 전달만 한다(FR-4). 정확 일치 검증 주체는 카카오다 |

**요청 쿠키**: `OAUTH_NONCE` 필수. 발급 API가 심은 값이 자동으로 동반된다(FE는 fetch에
credentials 포함만 하면 된다). 부재하면 카카오 왕복 없이 2423으로 거절한다.

**성공 응답**: `LoginResponseDto` 재사용, 신규 응답 스키마 없음. 웹은 리프레시가
`Set-Cookie`(HttpOnly)로 내려가 body의 `refreshToken`이 null이다.

```json
{
	"developCode": 200,
	"message": "성공",
	"data": {
		"accessToken": "eyJhbGciOiJIUzI1NiJ9...",
		"refreshToken": null
	}
}
```

**에러 케이스**:

| 상황 | HTTP | developCode | 메시지 |
|---|---|---|---|
| `code` 또는 `redirectUri` 누락 | 400 | 400 | `@Valid` 필드별 메시지 |
| 무효 인가 코드: 카카오 4xx 중 `error=invalid_grant`(만료, 재사용, redirect URI 불일치) | 401 | 2423 | 유효하지 않은 인가 코드입니다 |
| 토큰 응답에 `id_token` 없음(`scope=openid` 누락) | 401 | 2423 | 위와 동일, FR-6이 요구하는 단일 수렴 |
| `OAUTH_NONCE` 쿠키 부재, 또는 ID 토큰의 nonce 클레임이 쿠키 값과 불일치·부재 | 401 | 2423 | 위와 동일(보안 절) |
| `invalid_grant`가 아닌 카카오 4xx(레이트 리밋 KOE237, 앱 키·설정 오류 invalid_client 등) | 502 | 2502 | 소셜 로그인 제공자 오류입니다. 잠시 후 다시 시도해주세요 |
| 카카오 5xx, 연결 실패, 타임아웃 | 502 | 2502 | 위와 동일 |
| 교환은 됐지만 ID 토큰 검증 실패 | 401 | 2421 | 기존 `INVALID_ID_TOKEN` 그대로, 신규 아님 |

4xx를 전부 사용자 오류(2423)로 뭉개지 않는 이유: 레이트 리밋과 앱 설정 오류는 사용자가 다시
로그인해도 해소되지 않는 운영 장애다. 사용자 재시도로 풀리는 실패(`invalid_grant` 계열)만
2423이고, 나머지는 제공자 오류(2502)로 분류해 모니터링에 걸리게 한다 (Codex 리뷰 반영,
2026-08-08). 판별 키는 카카오 에러 응답 body의 `error` 필드다.

### 카카오 토큰 엔드포인트 호출 (서버 → 카카오, 외부)

`POST https://kauth.kakao.com/oauth/token`, `Content-Type: application/x-www-form-urlencoded;charset=utf-8`

| 파라미터 | 값 |
|---|---|
| `grant_type` | `authorization_code` 고정 |
| `client_id` | REST API 키 (`oauth.kakao.client-id`) |
| `redirect_uri` | 요청 body의 `redirectUri` 그대로 |
| `code` | 요청 body의 `code` 그대로 |

client_secret은 이번에 보내지 않는다. 콘솔의 카카오 로그인 시크릿이 OFF임을 실측(2026-08-03)
했고 PRD 8절에서 미도입이 승인됐다. 나중에 켜면 프로퍼티와 폼 파라미터 하나씩 추가하면 된다.

성공 응답 JSON에서 `id_token` 필드만 꺼내 쓴다. `access_token` 등 나머지 필드는 소비하지
않는다(사용자 정보는 ID 토큰 클레임으로 충분, 기존 검증기 입력과 동일).

### 보안: 로그인 위조 방지(state, nonce)의 책임 분담 (Codex 리뷰 반영, 2026-08-08)

인가 요청과 콜백 화면은 FE가 소유하므로, 서버는 state[^6]를 발급하거나 대조할 수 없다.
로그인 CSRF(공격자가 자기 인가 코드를 피해자 브라우저로 완주시켜 피해자를 공격자 계정에
로그인시키는 수법) 방어의 state 생성과 콜백 대조는 FE 책임으로 확정한다. FE 전달 사항:
`Kakao.Auth.authorize` 호출 때 state를 생성해 보관하고, 콜백에서 대조가 실패하면 이 API를
호출하지 않는다.

서버 쪽 보조 방어는 이미 있다. 이 API는 JSON body를 받으므로 브라우저발 크로스사이트
요청은 CORS preflight에서 차단되고, 허용 오리진은 기존 CORS 설정이 관리한다.

nonce[^7]는 서버가 발급하고 쿠키로 결속한다 (3차 정정, 2026-08-08 사용자 확정). 경위:
1차엔 미도입했고, 2차엔 FE가 body로 함께 보내는 방식으로 도입했는데, 후속 리뷰가 그 방식의
허점을 짚었다. 요청 body에 함께 실려 오는 nonce는 공격자도 자기 코드에 맞는 자기 값을 보낼
수 있어 자기 증명에 그친다. 대조가 방어가 되려면 기대값이 요청 밖, 즉 사용자의 브라우저에
결속돼 있어야 한다.

확정 설계: 로그인 직전 FE가 발급 API를 부르면 서버가 난수를 body로 주면서 같은 값을
HttpOnly 쿠키로도 심는다. FE는 그 값을 인가 요청에 넣고, 로그인 요청에는 아무것도 더 보내지
않는다(쿠키가 자동 동반). 서버는 교환으로 받은 ID 토큰의 nonce 클레임을 쿠키 값과 대조한다.
공격자가 자기 인가 코드를 피해자 브라우저에 주입해도 그 코드의 ID 토큰에는 공격자 쪽
nonce가 박혀 있고 피해자의 쿠키와 일치할 수 없으므로, FE의 state 검증 실수와 무관하게
서버가 기각한다. 크로스사이트 페이지는 우리 도메인의 쿠키를 읽지도 심지도 못하므로 이
결속은 브라우저가 보증한다.

쿠키 부재, 클레임 부재, 불일치는 전부 2423으로 수렴한다. 서버는 발급값을 저장하지
않는다(무상태, Redis 불요). 재사용 창은 쿠키 수명 10분과 로그인 성공 시 즉시 만료로 좁힌다.
nonce는 교환 요청(/oauth/token)의 파라미터가 아니다. 인가 요청과 ID 토큰 클레임에만
존재한다.

## 도메인 로직

### 흐름

```text
AuthController.issueOauthNonce (신규)
  난수 생성 → body 반환 + OAUTH_NONCE 쿠키 심기 (NonceCookies)

AuthController.oauthCodeLogin (신규)
  1. OAUTH_NONCE 쿠키 부재 → 2423                                  (카카오 왕복 전에 차단)
  2. resolveDeviceId(deviceIdHeader)                               (기존 헬퍼 재사용)
  3. kakaoAuthCodeExchanger.exchange(code, redirectUri, 쿠키값)    (신규, 카카오 왕복 1회 + nonce 대조)
  4. oidcLoginService.login(KAKAO, idToken, deviceId)              (기존 그대로, 변경 없음)
  5. X-Device-Id 헤더 + nonce 쿠키 만료 + applyTransport(…)        (기존 헬퍼 재사용)
```

컨트롤러가 교환과 로그인을 순서대로 호출하는 구조는 PRD 6절 클래스 다이어그램을 그대로
따른 것이다. 부수 효과로 카카오 HTTP 왕복이 `OidcLoginService.login`의 `@Transactional`
경계 밖에서 끝나므로, 외부 API 지연이 DB 커넥션 점유로 번지지 않는다.

### `KakaoAuthCodeExchanger` (신규, `auth/oidc/`)

PRD 6절의 이름을 그대로 확정한다. 시그니처는
`String exchange(String code, String redirectUri, String nonce)`, 반환값은 nonce 대조까지
통과한 ID 토큰 원문이다. 구현 규칙:

- HTTP 호출은 spring-web 내장 RestClient[^2]만 쓴다. 신규 의존성 없음,
  `spring-boot-starter-oauth2-client` 도입은 PRD 비목표라 금지다.
- 폼 인코딩 요청과 JSON 응답 파싱(`tools.jackson.databind.JsonNode`)은 search 도메인
  `KakaoLocalClient` 어댑터 선례를 따른다. 이 컴포넌트는 호출과 파싱만 하고, 타임아웃과
  baseUrl 조립은 구성 클래스 소관이다.
- 예외 매핑:
  - 카카오 4xx 응답(`RestClientResponseException`, 4xx): warn 로그에 HTTP 상태와 응답 body의
    `error`, `error_code`(KOE)를 남긴다. body의 `error`가 `invalid_grant`면
    `ApiException(INVALID_AUTHORIZATION_CODE)`, 그 외(레이트 리밋, invalid_client 등 사용자
    재시도로 해소되지 않는 거절)는 `ApiException(OAUTH_PROVIDER_ERROR)`를 던진다.
  - 카카오 5xx 응답, 연결 실패, 타임아웃(`ResourceAccessException` 포함 그 외
    `RestClientException`): warn 로그 후 `ApiException(OAUTH_PROVIDER_ERROR)`.
  - 2xx인데 `id_token` 필드가 없거나 공백: warn 로그("scope=openid 누락 의심")를 남기고
    `ApiException(INVALID_AUTHORIZATION_CODE)`. FR-6이 요구하는 FR-5와의 단일 수렴이다.
  - nonce 대조(보안 절, PRD FR-8): 받은 id_token의 payload를 서명 검증 없이 파싱해 `nonce`
    클레임을 기대 nonce(컨트롤러가 쿠키에서 꺼내 넘긴 값)와 비교한다. 불일치나 부재면 warn
    로그("nonce 불일치" 사실만, 값 원문 금지) 후 `ApiException(INVALID_AUTHORIZATION_CODE)`.
    서명·issuer·audience 검증은 직후 기존 검증기가 그대로 수행하므로 여기서는 파싱만으로
    안전이 깎이지 않는다(위조 토큰은 다음 단계에서 기각된다).
- 로그 금지 항목(비기능 보안): 인가 코드 원문, ID 토큰 원문, 액세스 토큰 원문. redirect URI와
  카카오 에러 필드는 남겨도 된다(카카오 에러 응답 body에는 위 원문들이 들어 있지 않다).

### `AuthErrorCode` 추가 (2xxx 대역, 빈 코드 확인 완료)

현재 사용 중인 코드는 2401, 2402, 2403, 2411, 2421, 2422, 2431, 2432, 2433이다. 다음 둘을
추가한다:

```java
INVALID_AUTHORIZATION_CODE(2423, HttpStatus.UNAUTHORIZED, "유효하지 않은 인가 코드입니다"),
OAUTH_PROVIDER_ERROR(2502, HttpStatus.BAD_GATEWAY, "소셜 로그인 제공자 오류입니다. 잠시 후 다시 시도해주세요"),
```

2423은 소셜 로그인 그룹(242x)의 다음 빈 자리다. 2502는 업스트림 장애를 502로 내리는 search
도메인 선례(`SEARCH_UPSTREAM_ERROR` 5502)를 auth 대역에서 미러링한 값이다.

### 구성: RestClient 빈과 프로퍼티

**`KakaoOidcProperties`에 `@NotBlank String tokenUri`와 `boolean nonceCookieSecure` 필드
추가.** 토큰 엔드포인트 URI의 위치는 공통 `application.yml`로 확정한다. issuer와 jwk-set-uri가
이미 공통에 있는 같은 호스트의 공개 고정값이라 프로파일별로 갈릴 이유가 없다:

```yaml
oauth:
  kakao:
    issuer: https://kauth.kakao.com
    jwk-set-uri: https://kauth.kakao.com/.well-known/jwks.json
    token-uri: https://kauth.kakao.com/oauth/token   # 신규
    nonce-cookie-secure: true                        # 신규, local만 false로 오버라이드
```

프로파일 반영 결과(PRD 비기능 운영): token-uri는 모든 프로파일이 공통값을 상속한다.
nonce-cookie-secure는 공통 true에 local 프로파일만 false 한 줄을 얹는다(위 발급 API 절의
쿠키 분기). `application-local.yml`은 gitignore 대상이라 추적되는 정본은
`application-local.yml.example`이다. example에 false를 넣어 새 로컬 셋업이 그대로 물려받게
하고, 이미 로컬 파일을 가진 개발자는 같은 한 줄을 직접 얹는다(이 머신의 로컬 파일은 이번
작업에서 함께 갱신). dev, prod 파일 변경과 **신규 환경변수는 0**이다.
`.claude/docs/deploy.md`의 설정 항목에 두 키를 반영한다.

**RestClient 빈은 전용 구성 클래스 `KakaoTokenClientConfig`(신규, `auth/oidc/`)에 둔다.**
`AiConfig`, `SearchConfig`, `NotificationConfig`가 확립한 클라이언트별 구성 클래스 선례를
따른다. 빈 이름은 `kakaoTokenRestClient`, 타임아웃은 로그인이 검색과 같은 동기 사용자
경로이므로 `SearchConfig`와 동일하게 연결 1초, 읽기 3초 상수로 시작한다(카카오 정상 응답은
수백 ms). baseUrl은 `properties.tokenUri()`.

주입 주의 2가지:

1. 완성 RestClient 빈이 `kakaoLocalRestClient`에 이어 두 개가 되므로 by-type 단독 주입이
   깨진다. 주입 필드명을 빈 이름과 일치시켜 by-name으로 해소한다. `KakaoLocalClient`는 이미
   필드명이 빈 이름과 같아 코드 변경이 없고, `SearchConfig`의 "완성 RestClient 빈은 현재 이것
   하나" 주석만 사실에 맞게 한 줄 갱신한다.
2. `RestClient.Builder` 빈은 만들지 않는다. `AiClient`가 Builder를 by-type으로 주입받고 있어
   두 번째 Builder 빈은 기동 모호성을 만든다(SearchConfig 주석에 기록된 제약).

## 미해결 질문

없음. PRD 8절의 client_secret 미도입 승인으로 열린 질문이 소진됐고, 스펙에서 확정한 값은
경로(`/api/auth/oauth/kakao/code`), 에러 코드(2423, 2502), 토큰 URI 위치(공통 application.yml),
타임아웃(연결 1초, 읽기 3초)이다.

[^1]: 인가 코드: OAuth 인가 서버가 로그인 직후 콜백 URL로 돌려주는 1회용 짧은 코드. 그 자체로는 신원 정보가 없어 토큰 엔드포인트에서 진짜 토큰으로 바꿔야 하며, 이 교환을 서버가 대행하는 것이 이 티켓의 전부다.
[^2]: RestClient: Spring 6.1부터 spring-web에 내장된 동기 HTTP 클라이언트. 이미 AI 서버 호출과 카카오 로컬 검색이 쓰고 있어 신규 의존성 없이 외부 API를 부를 수 있다.
[^3]: kakaoJwtDecoder: 카카오 공개키 목록(JWKS)을 내려받아 ID 토큰의 서명을 확인하고 issuer와 audience까지 검사하는 기존 검증 빈. 교환으로 얻은 토큰도 이 검증을 그대로 통과해야 하므로 서버가 위조 토큰을 받아들일 여지가 없다.
[^4]: KOE 코드: 카카오 인증 서버가 실패 응답에 담는 자체 에러 코드(무효 코드 KOE320 등). 원인 추적에는 필요하지만 클라이언트에 내리면 카카오 내부 사정이 우리 API 계약에 새므로 서버 로그 전용이다.
[^5]: HttpOnly 쿠키: 자바스크립트가 읽을 수 없는 쿠키. XSS로 스크립트가 뚫려도 리프레시 토큰을 탈취당하지 않게 하는 웹 전용 전송 방식으로, 기존 로그인 3종이 이미 쓰고 있는 규칙을 그대로 따른다.
[^6]: state: 클라이언트가 인가 요청에 실어 보내고 콜백에서 돌려받아 대조하는 1회용 난수. 콜백에 도착한 응답이 내가 시작한 로그인의 결과인지 확인하는 장치라, 인가 요청을 발행한 쪽(FE)만 검증할 수 있다.
[^7]: nonce: 인가 요청에 실으면 제공자가 ID 토큰 클레임으로 되돌려 주는 1회용 난수. 그 ID 토큰이 지금 이 브라우저에서 시작된 로그인의 결과인지 묶어 주는 장치로, state와 달리 토큰을 최종 소비하는 서버가 대조할 수 있다. 이 스펙에서는 서버가 발급해 쿠키로 결속한다.
