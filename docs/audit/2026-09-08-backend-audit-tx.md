1. **행사 시작 알림(TX04):** 전역 잠금을 잡고 회차별 전체 구독자에게 알림을 기록한다. 구독자가 늘수록 한 트랜잭션의 SQL이 늘어난다.
2. **일괄 시드 적재(TX05~07):** 파일 파싱·전체 쓰기·격자 갱신을 묶는다. 미션 하나의 정합성과 모든 미션을 한 번에 커밋할 필요는 따로 따져야 한다.

영상 확정(TX01~03)은 책임이 많지만 핵심 상태를 함께 커밋해야 하는 근거가 있다. **29개 업무 SQL을 확인했으나, 이 수치만으로 분리나 성능 결함을 결론 내리지 않았다.**

## 7. 한계와 검증

- 정적 검토는 선언·클래스 적용 메서드·템플릿 구간을 포함했다. 전체 실행 경로를 런타임으로 검증한 것은 아니다. 원장의 호출자는 타입 기반 소스 검색이며 같은 이름의 오버로드 인수 타입, 동적 빈 조회·리플렉션은 완전히 해석하지 않았다.
- 상세 21개 흐름으로 묶었고 나머지 단건·설정·조회 경로는 TX21과 전체 원장에 남겼다. 유지 판정도 대량 데이터에서 무조건 빠르다는 뜻은 아니다.
- 실측은 영상 신규 저장 한 시나리오뿐이다. 대량 구독자·시드·조회·실제 S3/Redis 대기와 연결 풀 점유는 미실측이다. Hibernate 추가 조회·flush·cascade·트리거의 비용도 다른 경로에서는 정적 추정에 포함된 한계다.
- afterCommit은 자동 비동기도, 연결 반환 완료도 아니다. REQUIRED 합류 시 호출자 격리 수준을 따르며 readOnly 자체가 일관된 스냅샷을 보장하지 않는다.
- 기존 inventory.sh는 주석까지 세어 TX를 155개로 표시하고 후반부에서 종료 코드 1을 반환했다. 이번 143개 선언은 별도 소스 추적으로 보정했다. 스크립트 수정은 이번 범위에서 제외했다.
- 스킬 수정: 업무량·반복 상한·원자성·분리 조건·전체 검토 원장을 필수화했다. 외부 I/O만으로 P1을 붙이는 규칙과 자기 호출·afterCommit 설명도 바로잡았다. frontmatter의 기존 YAML 인용 오류도 수정했다.
- 스킬 검증: quick_validate 통과. 새 세션 8개에서 호출 기대 5건과 미호출 기대 3건 모두 hook 기록과 일치했다. 새 업무량 문장도 포함했다. [회귀 증거](/tmp/backend-audit/tx-trigger-regression.md)의 session ID와 hook 26~30행을 대조했다. CLI 종료 코드 1은 max-turns 1에 따른 의도적 종료였다.
- 문서 검증: 파일 링크·줄 번호, 흐름 수·우선순위 수, 줄표·상투어·번역체 검색과 문장 검토를 수행했다. 임시 실측 파일은 영구 보관물이 아니므로 수치·집계 기준·재실행 명령을 본문에 남겼다.

[^atomic]: 원자성은 관련 변경이 모두 성공하거나 모두 취소되는 성질이다. 업무가 많아도 이 계약이 필요하면 같은 트랜잭션에 둘 이유가 된다.
[^required]: REQUIRED는 이미 열린 트랜잭션이 있으면 합류한다. 따라서 서비스 호출 수와 실제 커밋 횟수는 다르다.
[^lock]: advisory lock은 코드가 정한 키로 획득하는 DB 잠금이다. 트랜잭션 잠금은 커밋·롤백까지 유지되므로 뒤의 반복 작업도 경합 시간에 영향을 준다.
[^outbox]: outbox는 전송할 내용을 업무 변경과 함께 DB에 기록하고 나중에 전송하는 방식이다. 알림 INSERT가 곧 FCM·Kafka 네트워크 전송을 뜻하지 않는다.
[^pool]: 연결 풀은 DB 연결을 재사용하는 저장소다. 풀에서 연결을 빌려 반환하기까지의 시간은 SQL 실행 시간이나 로그의 BEGIN~ROLLBACK 구간과 다를 수 있다.
