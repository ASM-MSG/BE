## 1. 영상 인코딩 비교

- dev API와 AI EC2의 인코딩 워커만 사용했다. 운영 서버는 변경하지 않았다.
- 두 노드 이미지가 모두 `sha-e30c586`임을 확인했다. 한 노드 조건에서는 AI EC2의 인코딩 워커만 정지했다.
- 실제 crowd 영상 한 편에서 10·19·29초 구간을 잘라 같은 파일을 양쪽 조건에 사용했다. 입력별 SHA-256과 크기는 원자료에 있다. 여러 촬영 장면·코덱을 대표하는 평가셋은 아니다.
- 블러가 꺼진 조건이다. 삭제 전 36건 모두 ai_job_id가 비어 있고 READY임을 DB에서 확인했다.
- 순서는 1노드 → 2노드 → 2노드 → 1노드이며 각 조건에서 동시 3건·6건을 제출했다. 총 36건 전부 READY·COMPLETED, 모두 시도 1회였다.
- 표의 시간은 클라이언트에서 사전서명 발급·S3 업로드를 시작한 뒤 모든 영상의 종결을 관측할 때까지다. 순수 인코딩 시간과 다르다. 조건별 두 회의 평균이며 첫 실행의 콜드 비용도 포함한다.

| 동시 업로드 | 한 노드 평균 | 두 노드 평균 | 단축 |
|---|---:|---:|---:|
| 3건 | 54.491초 | 27.189초 | 50.1% |
| 6건 | 100.696초 | 60.070초 | 40.3% |

- 개별 영상의 확정 응답부터 READY 관측까지 시간도 별도 저장했다. DB 작업 등록~완료 시간에는 큐 대기가 포함된다. 별도 선점 시작 시각이 없으므로 대기와 FFmpeg 실행 시간의 비중은 이번 데이터로 분리하지 않았다.
- 종결 관측은 SSH DB 조회와 0.5초 폴링을 사용해 관측 지연이 포함된다. 소표본이므로 모집단 p95·p99 또는 장기 처리량을 주장하지 않는다.
- CPU·스왑은 시험 도중부터 vmstat로 보조 수집했다. 전체 구간 수집이 아니므로 전후 최대 자원 비교의 근거로 사용하지 않는다. CPU 크레딧 잔량도 통제하지 않았다.
- 신규 테스트 전용 계정으로 비공개 영상을 만들고, 완료 후 계정 삭제 API를 호출했다. S3 개별 객체 삭제 여부는 별도 전수 확인하지 않았다.

### 워커 종료 복구

| 시험 | 관측 상태 | 결과 |
|---|---|---|
| 정상 종료 | AI가 선점한 시도 1 작업이 PENDING·시도 0으로 반납 | BE가 시도 1로 이어받아 완료 |
| 강제 종료 | AI 시도 1의 PROCESSING 상태가 그대로 남음 | 해당 시험 행의 임대를 만료시킨 뒤 BE 시도 2가 완료 |

각 시험에서 19초 영상 3건, 총 6건이 모두 READY·COMPLETED로 끝났다. 정상 종료 시험은 선점을 관측한 직후 신호를 보냈으며 FFmpeg 실행 중임을 별도로 확인하지 않았다. 강제 종료 직전 영상 상태는 ENCODING이었다. 강제 종료에서는 자동 재시작 정책을 잠시 끄고 마지막에 원래 `unless-stopped`로 복구했다.

강제 종료 후 운영 기본 임대 35분을 실제로 기다리지는 않았다. 자기 시험 행의 lease_until만 과거로 바꿔 만료 회수 분기를 검증했다. 따라서 회수 후 다른 노드에서 완료된 사실은 주장할 수 있지만, 여기서 잰 43초를 운영 장애 복구 SLA로 쓸 수 없다.

시험 후 인코딩 워커가 running·healthy·unless-stopped임을 확인했다. dev 미종결 작업 0건, 시험 영상 ID 240816~240857의 잔존 DB 행 0건을 확인했다. 총 42개 시험 영상은 전용 계정 삭제 API로 정리했다.

## 2. 행사 시작 알림

### 순수 기록 성능

- 로컬 PostgreSQL 16.4의 별도 DB `fillmap_tx_bench_20260917`, Redis DB 14를 사용했다. 기본 로컬 DB와 운영 데이터는 부하 데이터로 사용하지 않았다.
- JDK 21.0.2, 테스트 JVM 힙 2GiB, Hikari 풀 2개, JaCoCo를 켠 조건이다.
- 대조군은 현행 앱 안에서 `70829e28`의 구독자 전량 조회·사용자별 기록 반복문을 재현했다. 과거 앱 전체를 체크아웃한 비교는 아니다. 개선군은 실제 현행 `recordEventStart`를 호출한다.
- 준비 실행 1회 후 신규 기록 3회 중앙값이다. 합성 데이터 생성·삭제·ANALYZE·결과 검증은 시간에서 제외했다. 두 구현을 별도 JVM에서 순서대로 실행했다.

| 구독자 | 이전 방식 | 일괄 기록 | Hibernate SQL prepare 전후 |
|---|---:|---:|---:|
| 1천 명 | 267.504ms | 27.225ms | 1,005 → 5 |
| 1만 명 | 12,537.884ms | 173.405ms | 10,005 → 5 |

모든 표본에서 알림 수·서로 다른 사용자 수·구독 수가 입력 수와 같았고 발송·종료 정리 트랜잭션이 모두 커밋됐다. 같은 이벤트를 다시 실행해도 알림 수는 유지됐다. SQL prepare는 Hibernate가 문장을 준비한 횟수이며 네트워크 왕복 수와 동일한 지표가 아니다.

원자료: [일괄 기록](../../load-test/evidence/2026-09-17/fanout-bulk.txt), [이전 방식](../../load-test/evidence/2026-09-17/fanout-legacy.txt)

### 혼합 부하와 잠금

- 혼합 부하는 실제 HTTP 행사 상세 조회 클라이언트 2개, 응답 후 10ms 대기, 10초 창이다. 부하가 응답 속도에 따라 달라지는 closed-loop[^2] 시험이다. 응답 200과 실제 행사 제목을 모두 검사한다.
- 알림 기록 자체는 개선군에서 빨리 끝나므로 같은 10초 창 중 조회와 겹치는 시간이 다르다. 동시 작업 한 회가 사용자 요청에 주는 영향을 보는 시험이며 동등한 DB 포화 실험은 아니다.
- 5만 건 제어 경합에서는 실제 DB 잠금 대기를 확인했고 경쟁 잠금 획득 문장 820.922ms, 발송 TX 외곽 886.385ms, 알림 50,000건을 관측했다. 삽입 진입을 잠시 보류하는 제어가 포함돼 순수 성능 표와 합산하지 않는다.
- 5만 건 구독자의 계정 CASCADE 정리에는 추가 시간이 들었다. 정리 시간은 발송 성능에 포함하지 않았다.


준비 실행을 제외한 상세 조회 3회 결과다. 오류가 있으면 별도 집계하며 지연 백분위는 성공 응답만의 값이다.

| 알림 기록 방식 | 조회 건수 | 오류 | 회차별 조회 p95 | 알림 기록 중앙값 |
|---|---:|---:|---|---:|
| 이전 반복 저장 | 4,295 | 0 | 3.674, 3.84, 2.978ms | 12449.219ms |
| 일괄 기록 | 3,867 | 0 | 6.183, 4.587, 6.094ms | 190.645ms |

**이 부하에서는 상세 조회 지연 개선을 입증하지 못했다.** 이전 방식도 재실행에서 오류 없이 처리됐으며 조회 p95가 일괄 기록보다 낮았다. 알림 기록·DB 연결 점유 감소와 API 지연 개선을 동일한 성과로 묶지 않는다. 표본 순서, 워밍업, JVM 상태 영향을 분리하지 않았으므로 이 차이를 개선 코드의 회귀로 단정하지도 않는다.

## 3. 알림 장애 경계

실제 PostgreSQL과 EmbeddedKafka를 사용했다. 외부 FCM은 발송 횟수를 세는 대역이다. 사람에게 실제 푸시를 보내지 않았다.

| 주입한 실패 | 관측 |
|---|---|
| 접속 불가능한 브로커 주소 | outbox[^1] 100건 PENDING 유지. 실제 시험 브로커로 복구 후 100개 레코드 확인, 발송 100회, SENT 100행. 종결 후 추가 재소비는 발송하지 않음 |
| Kafka 발행 성공 후 DB PUBLISHED 갱신 실패 | 실제 DB 트리거가 첫 갱신을 거절. 재발행으로 브로커 레코드 2개, 순차 소비의 외부 발송 1회, SENT 1행 |
| 외부 발송 성공 후 DB SENT 갱신 실패 | DB 행은 미종결로 남고 재시도에서 외부 발송 2회 발생. 최종 SENT 1행. 이후 종결 메시지 재소비는 추가 발송 없음 |

**외부 발송과 DB 종결은 원자적이지 않다.** DB 행 중복 방지와 이미 종결된 메시지의 재소비 방어는 확인했지만, 외부 발송까지 정확히 한 번이라고 할 수 없다. 동시 중복 소비와 실제 단말 도착 여부도 이번 신규 시험의 검증 대상은 아니다.

기존 테스트의 발송 실패 재시도·DEAD 격리·잘못된 메시지 뒤 정상 소비·스테일 발행 복구·행사 틱 롤백·다음 틱 복구도 함께 실행했다. 테스트용 재시도 간격은 운영의 약 4분 백오프를 압축하므로 운영 복구 시간 실측이 아니다.

## 4. 후속 검증: 고정 요청률과 푸시 표시 경계

### 조회 시험 방법

기존 closed-loop 시험에 더해 open-loop[^4] 시험을 추가했다. 초당 200건과 500건을 각각 10초 동안 예정 시각에 제출한다. 각 조건은 준비 실행 1회와 측정 3회이며, 요청마다 실제 상세 응답의 상태와 본문을 확인한다. 알림 1만 건 기록을 같은 시점에 시작한다.

- 200건/초는 이전 방식 → 일괄 방식, 500건/초는 일괄 방식 → 이전 방식 → 이전 방식 → 일괄 방식 순서다. 500건/초는 실행 순서를 뒤집어 반복한다. 200건/초는 순서 효과를 분리하지 못한다.
- 지연은 예정 시각부터 응답 종료까지 계산한다. 부하 발생기의 제출 지연도 별도 집계하며, 실패 요청도 전체 지연 표본과 오류 수에 남긴다.
- 실제 HTTP를 사용하지만 부하 발생기와 앱은 같은 JVM이다. 외부 네트워크와 별도 부하 발생기를 사용한 운영 용량 시험은 아니다.
- 테스트 풀은 2개이고 dev 설정은 10개다. 합성 행사 상세 한 건을 비로그인 상태로 조회하므로 전체 API·실사용 데이터 분포를 대표하지 않는다.
- `BENCH_HTTP_RATE=200` 또는 `500`, `BENCH_IMPLEMENTATION=legacy` 또는 `bulk`를 지정하고 `benchmarkFixedArrivalHttpDuringFanout`를 선택하면 재현할 수 있다.

### 조회 시험 결과

| 요청률 | 실행 묶음 | 이전 방식 조회 p95 | 일괄 방식 조회 p95 | 이전 방식 알림 틱 | 일괄 방식 알림 틱 |
|---|---|---:|---:|---:|---:|
| 200건/초 | 이전 → 일괄 | 3.385ms | 4.145ms | 12,128.327ms | 211.929ms |
| 500건/초 | 일괄 → 이전 | 2.626ms | 2.643ms | 12,911.526ms | 242.010ms |
| 500건/초 | 이전 → 일괄 | 2.998ms | 2.310ms | 13,290.891ms | 239.336ms |

표는 각 실행의 측정 3회 중앙값이다. 조회 열은 **회차별 p95의 중앙값**이며 전체 요청을 합친 p95가 아니다. 준비 실행을 제외한 72,000건과 포함한 96,000건 모두 오류 0건이었다. 매 회차 알림도 10,000행인지 확인했다. 각 회차 전 별도 사전 조회 30건은 이 요청 수에서 제외했다.

**조회 지연 개선은 입증하지 못했다.** 500건/초 첫 비교는 차이가 없고 역순에서는 일괄 방식이 빨랐다. 200건/초에서는 반대로 일괄 방식이 더 느렸다. 개선이 나온 회차만 골라 일반적인 API 개선율로 쓰지 않는다. 이미 수 ms인 상세 조회에 근거 없이 캐시나 쿼리 변경을 추가하지 않았다.

자소서에는 다음처럼 조건을 붙여 쓸 수 있다: “행사 알림을 일괄 기록하도록 개선하고, 로컬에서 1만 건 기록과 초당 500건 상세 조회를 함께 실행해 개선 방식의 측정 요청 3만 건에서 오류 0건을 확인했다.” 운영 최대 처리량이나 이전 대비 조회 성능 향상을 뜻하지 않는다.

시험 6회 모두 빌드·시험 성공. 전용 DB의 users·notifications·event_occurrences·event_series 잔존 행은 각각 0건이다. 신규 시험 코드의 DB 제한·요청 수·실패 집계·준비 실행 분리·정리 흐름을 별도 점검했고, Java 줄 길이와 `git diff --check`도 통과했다. 기존 제품 코드가 바뀌지 않아 앞서 통과한 73건 전체를 다시 실행하지는 않았다.

원자료: [회차별 출력과 집계](../../load-test/evidence/2026-09-17/http-arrival-summary.json). 같은 디렉터리의 `http-arrival-*.txt`에 각 실행의 준비 회차와 측정 회차를 모두 보존했다.

### 푸시의 변경 필요 범위

현재 서버는 FCM 메시지에 제목과 본문만 보내므로 재시도 때 같은 업무 알림인지 웹이 식별할 수 없다. 웹의 전경 수신은 매번 새 로컬 일련번호로 토스트를 추가한다. 백그라운드 수신은 notification 메시지를 직접 다시 표시한다. [FCM 공식 수신 규칙](https://firebase.google.com/docs/cloud-messaging/web/receive-messages)에 따르면 이 메시지는 SDK가 자동으로도 표시한다. 이 경로는 코드와 공식 규칙으로 확인했으며 실제 브라우저 중복 횟수는 아직 측정하지 않았다.

현재 SRS의 FR-NOTI-03·NFR-DATA-03에는 중복 푸시가 없다고 쓰여 있지만, 기존 `notification-prd.md` 5.2절은 발송 성공 후 DB 실패 구간의 중복을 허용한다. 이번 장애 시험은 후자와 일치한다. 보장 범위를 승인 없이 축소하거나, 구현되지 않은 보장을 완료로 표시하지 않았다.

[웹 중복 표시 개선안](../prd/notification-display-deduplication.md)은 이 시험 후 성민 승인을 받았다. 서버 재시도는 유지하고 같은 알림의 식별자를 수신 측까지 전달해, 열린 탭과 현재 남아 있는 브라우저 알림의 중복 적재를 줄이는 제안이다. 외부 전송 횟수 1회, 모든 장애에서 단말 표시 1회를 보장하는 설계는 아니다. 이 시험 단계에서는 제품 코드를 변경하지 않았고, 승인 후 구현 결과는 후속 스펙을 따른다.

## 최종 검증과 변경 범위

- 알림 소비·릴레이·신규 장애 경계, 행사 스케줄러, 인코딩 폴러·작업 저장소 관련 테스트 **73건, 실패·오류·건너뜀 0건**. 전체 제품 테스트 스위트는 실행하지 않았다.
- 구현과 별도 점검으로 시험 대상 DB 제한, 실제 HTTP 본문 검증, 실패 요청 집계, 워커 복구·재시작 정책 복원, 정리 대상을 확인했다. 제품 서비스·API·마이그레이션 파일 변경은 없다.
- Python 도구 문법 검사, Java 120자 제한 검사, `git diff --check`, 보고서 줄표·상투어 검색을 수행했다.
- 원자료: [최종 테스트 집계](../../load-test/evidence/2026-09-17/regression.json), [장애 시험 출력](../../load-test/evidence/2026-09-17/faults-final.txt), [잠금 관측](../../load-test/evidence/2026-09-17/lock-and-fault-initial.txt).
- 사용 스킬: korean-humanizer, tech-term-footnotes. 후속 푸시 제안에는 prd-writer를 적용하고 srs-writer 절차로 기존 요구를 조회했다. 코딩 검증은 convention-reviewer 체크리스트로 같은 세션의 별도 점검을 수행했다. 서브에이전트와 외부 메시지 전송 도구는 사용하지 않았다.
- 보고서·부하 도구만 작업 트리에 남겼고 커밋하지 않았다. 시작 전에 존재하던 AGENTS.md 수정과 다른 미추적 파일은 수정하지 않았다.

## 재현

1. Docker PostgreSQL·Redis를 기동하고 별도 DB를 만든다: `docker exec fillmap-postgres createdb -U user fillmap_tx_bench_20260917`.
2. 순수 기록: `BENCH_IMPLEMENTATION=bulk BENCH_FANOUT_SIZES=1000,10000 ./gradlew -I load-test/tx-workload/verification.init.gradle test --rerun-tasks --tests '*EventFanoutBenchmark.benchmarkActualSchedulerFanout'`. `legacy`로 바꿔 대조군 실행.
3. 혼합 조회: 같은 명령의 테스트 선택을 `*EventFanoutBenchmark.benchmarkConcurrentHttpDuringFanout`로 바꾼다. 고정 요청률은 `BENCH_HTTP_RATE=500`을 더하고 `*EventFanoutBenchmark.benchmarkFixedArrivalHttpDuringFanout`를 선택한다.
4. 장애 경계: `./gradlew -I load-test/tx-workload/verification.init.gradle test --tests '*NotificationCrashWindowTest'`.
5. dev 비교: 승인된 시험 시간에 `python3 load-test/encoding-ab.py INPUT.mp4 RESULT.json`. 실제 dev 계정·비공개 영상 생성과 워커 중지가 포함된다.
6. dev 종료 복구: `python3 load-test/encoding-recovery.py VIDEO_19S.mp4 RESULT.json`. 강제 종료 시험은 해당 시험 작업의 임대[^3] 만료를 앞당긴다. 운영 기본 35분의 회수 시간으로 인용하지 않는다.

## 시행착오와 한계

- 최초 장애 시험은 알림 기능을 끈 컨텍스트에 KafkaTemplate이 없어 기동 실패했다. EmbeddedKafka 전용 producer를 명시적으로 만들고 재검증했다.
- 최초 혼합 조회는 고정된 미래 행사 시각 때문에 빈 목록을 조회했다. 성능 주장에 사용하지 않았다. 이후 visible_from만 바꾸려던 시험은 DB 날짜 제약에 걸렸다. 실제 UTC 기준 행사 시각과 실제 상세 응답 검증으로 수정했다.
- 첫 실제 상세 조회 대조군 실행에서 30초 HTTP 타임아웃이 발생해 실행이 실패했다. 이를 성공 표본에서 빼고 무시하지 않도록 오류 수 집계를 추가했다. 같은 상세 조회 재실행에서는 이전 방식도 성공했으므로 타임아웃 감소 효과를 주장하지 않는다.
- 이번 변경은 검증 도구뿐이다. 외부 발송 중복의 제품 정책·아키텍처는 변경하지 않았다.
- 지속 부하, 12건 이상 동시 입력, 여러 원본 영상·코덱, 일시적인 S3 장애, 실제 FCM 429·5xx·단말 수신은 후속 검증으로 남는다.

## 자소서에 사용할 표현

- 기존 두 서버에 DB 작업 선점 방식의 영상 인코딩을 분산하고, 동일 영상 표본의 6건 동시 업로드 시험에서 전체 완료 시간을 평균 100.7초에서 60.1초로 단축했다.
- 행사 알림의 사용자별 반복 저장을 일괄 기록으로 개선하고, 로컬 1만 명 시험에서 기록 중앙값을 12.54초에서 0.173초로 줄였다.
- 메시지 발행·외부 전송·DB 기록 사이에 장애를 주입해 복구를 검증하고, DB 중복 방지와 외부 푸시 중복 가능성의 경계를 확인했다.

[^1]: outbox는 업무 처리와 함께 DB에 저장한 발송 대기 기록이다. 브로커 접속이 실패해도 기록을 남겨 나중에 다시 보낼 수 있다.
[^2]: closed-loop는 이전 요청이 끝나야 다음 요청을 보내는 부하 방식이다. 서버가 느려지면 실제 요청률도 줄어들어 고정 유입률 시험과 다르다.
[^3]: 임대는 워커가 작업을 점유할 수 있는 유효기간이다. 워커가 사라져도 임대가 만료되면 다른 워커가 회수할 수 있다.

[^4]: open-loop는 이전 응답 완료와 무관하게 미리 정한 시각에 요청을 제출하는 방식이다. 서버 지연으로 유입량이 저절로 줄어드는 문제를 피한다.
