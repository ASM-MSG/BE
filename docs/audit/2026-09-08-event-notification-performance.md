# 행사 시작 알림 일괄 기록 개선 실측

구독자 5만 명의 알림 기록이 **400.387초에서 0.705초**로 줄었다. 행사 잠금과 전체 발송 트랜잭션을 유지하면서 구독자 엔티티 조회와 사용자별 INSERT를 회차별 `INSERT SELECT` 한 문장으로 바꿨다. 알림 5만 건, 사용자별 중복 0건, 발송과 종료 정리의 두 커밋을 확인했다.

이전 5만 명 값은 JFR과 잠금 관찰을 포함한 단발 진단값이다. 새 값은 그 계측이 없는 단발이므로 정확한 개선 배수나 운영 처리량으로 해석하지 않는다. 1천·1만 명은 이전과 같은 준비 실행 1회와 신규 기록 3회 방식으로 비교했다.

## 전후 비교

기준 코드는 `70829e28`이며 기존 측정의 애플리케이션 코드는 `3fde2f19`와 같다. 개선 코드는 `feature/MSG-583-event-notification-performance`의 작업 트리다. 환경은 Apple M5, 메모리 32GiB, JDK 21.0.2, 테스트 힙 2GiB, Hikari 2개, JaCoCo 포함, PostgreSQL 16.4, shared_buffers 128MB다. 별도 DB에 같은 행정동 3,558건을 넣었다.

| 구독자 | 이전 신규 기록 | 개선 신규 기록 | 개선 3회 범위 | SQL prepare[^prepare] 전후 |
|---|---:|---:|---:|---:|
| 1천 명 | 485.607ms | **22.082ms** | 21.295~22.406ms | 1,005 → 5 |
| 1만 명 | 17,261.651ms | **157.728ms** | 157.491~159.047ms | 10,005 → 5 |
| 5만 명 | 400,387.237ms | **704.659ms** | 단발 | 50,005 → 5 |

1천·1만 명은 신규 기록 3회의 중앙값이다. 데이터 생성·삭제·ANALYZE·정합성 조회는 측정 구간에서 제외했다. 자동 예약 작업을 취소하고 실제 서비스와 repository로 `tick()`을 호출했다. 외부 푸시 전송 시간은 포함하지 않는다.

| 구독자 | 개선 첫 발송 TX 시간 | 개선 연결 점유 합계[^pool] | 중복 재실행 전후 |
|---|---:|---:|---:|
| 1천 명 | 19.885ms | 22ms | 590.011 → 9.856ms |
| 1만 명 | 153.227ms | 157ms | 16,086.384 → 51.184ms |
| 5만 명 | 699.620ms | 705ms | 기존 대응 샘플 없음 |

연결 반환은 모든 샘플에서 2회였다. 중복 재실행은 규모별 1회이며, 개선 후에도 기존 알림 수가 유지되고 SQL prepare는 5회였다. 5만 명에서 중복 실행을 추가로 측정하지 않았다.

## 잠금과 데이터 보존

별도 제어된 경합에서 발송 연결 PID `56021`에 경쟁 연결 `56031`이 실제로 차단됐음을 `pg_blocking_pids()`로 확인했다. 같은 `event_seed` 잠금 획득 문장은 **718.321ms**, 발송 TX 외곽은 **788.674ms**였고 알림은 5만 건이었다.

이 시나리오는 발송 TX가 잠금을 얻은 뒤 INSERT 진입을 잠시 보류하고, 경쟁 연결의 차단을 확인하면 기록을 진행한다. 제어 대기와 추가 SQL이 포함되므로 순수 성능 표와 섞지 않았다. 이전 자연 경합의 334.367초와 동일한 시점에서 요청한 비교값도 아니다. 잠금[^lock]을 제거한 것이 아니라, 기록을 빨리 끝낸 뒤 해제하는 동작을 검증한 결과다.

| 보존 계약 | 검증 결과 |
|---|---|
| 수신 대상 | 시작 전·정각 포함, 정각 1마이크로초 뒤 제외, 다른 회차 제외, 시작·종료·24시간 경계 검증 |
| 중복 기록 | 기존 행의 제목·상태·기록 시각 보존, 일정 변경 시 기존 규칙대로 새 키 생성 |
| 틱 전체 원자성 | 두 번째 회차에서 실제 NOT NULL 오류를 내면 첫 회차까지 롤백, 종료 정리는 성공, 다음 틱에서 복구 |
| 일정 변경 경합 | 기존 재시드 경쟁 테스트 통과, 잠금 대기 후 연기된 회차의 옛 시작 알림 없음 |
| 취소·탈퇴 | 먼저 완료된 취소·탈퇴는 제외, 기록 후 탈퇴는 구독·알림 연쇄 삭제 |

구독 취소와 진행 중인 기록을 새로 직렬화하지 않았다. INSERT의 문장 스냅샷에 보인 구독은 이후 취소돼도 이번 틱의 수신 대상일 수 있다. 동시 탈퇴의 외래 키 오류가 틱 전체를 롤백할 가능성도 기존대로 남는다. 상세 계약은 [스펙](../spec/MSG-583.md)에 있다.

## 원인과 해결

| 단계 | 내용 |
|---|---|
| 증상 | 구독자 5만 명의 시작 알림이 400.387초 동안 처리되고 행사 일정 변경도 같은 잠금에서 대기했다. |
| 가설 | 사용자별 SQL 왕복과 전량 로딩된 구독자에 대한 반복 flush[^flush]가 함께 비용을 키운다. |
| 검증 | 이전 N+5 prepare 및 flush 실행 스택을 확인했다. 같은 벤치를 개선 후 실행하니 모든 규모에서 5 prepare, 5만 명 704.659ms와 알림 5만 건을 확인했다. |
| 결론 | 구독자별 호출과 엔티티 관리를 제거한 뒤 처리 시간과 연결 점유가 크게 줄었다. 두 원인의 시간 비중은 각각 분리하지 않았다. |
| 해결 | 기존 알림 repository에 회차별 `INSERT SELECT ... ON CONFLICT DO NOTHING`을 추가했다. 전체 틱의 잠금·롤백·종료 정리 경계는 유지했다. |

DB 로그를 켠 1천 명 검증에서 발송 TX는 잠금·후보 SELECT·INSERT SELECT의 업무 SQL 3회, 정리 TX는 잠금·DELETE 2회였다. 드라이버 메타데이터와 BEGIN·COMMIT, parse·bind 중복은 제외했다. 구독자 전량 SELECT와 사용자별 INSERT는 없었다. 로그를 켠 실행의 시간은 성능 표에서 제외했다.

별도 5만 행 `EXPLAIN (ANALYZE, BUFFERS)`는 실제 삽입 50,000건·충돌 0건, 실행 686.502ms를 기록했다. 구독 테이블 전체가 해당 회차이므로 Seq Scan을 선택했고, 충돌 판정에는 `uq_notifications_user_event`를 사용했다. 외래 키 트리거는 50,000회·296.677ms였다. 반복적인 앱 호출이 사라져도 행별 DB 검사는 남는다. 이 실행은 롤백했으며 서비스 시간 표와 합치지 않았다.

측정 행·실행 SQL·실행 계획·빌드 결과는 [검증 원문](../../load-test/tx-workload/event-performance-results.txt)에 보존했다. 전체 로그는 `/tmp/backend-audit/event-perf-measured.txt`, `event-perf-lock-measured.txt`, `event-perf-db.log`, `event-perf-full-build.txt`에 있다.

## 검증과 재현

- 변경 전 테스트 9건 성공, 신규 SQL 회귀 테스트는 기존 구현의 INSERT 6회 때문에 실패했다.
- 구현 후 관련 5개 테스트 묶음 42건 성공, 전체 `./gradlew build` 성공: 총 3,054건, 실패·오류 0건, 건너뜀 6건.
- 순수 알림 벤치와 제어된 경합 벤치는 각각 성공했다. 초기 벤치 시도는 전체 테스트가 남긴 행사 2건을 DB 격리 조건이 감지해 실패했으며, 해당 합성 행사와 장소를 정리하고 재실행했다.
- 초기 구현 검증은 기존 단건 알림 테스트의 lambda 2곳 때문에 컴파일에 실패했다. mock으로 치환한 뒤 전체 빌드가 통과했다.
- 독립 스펙·구현 리뷰 통과. 벤치의 DB 이름 검사와 발송 연결의 시간 제한 지적 2건은 수정 후 재검토했다.
- 추가 Codex 리뷰는 스펙·구현 단계 모두 `gpt-6-astra requires a newer version of Codex` 오류로 실패했다. 통과로 계산하지 않았다.
- AC-583-01~05를 테스트와 RTM에 연결했다. 기존 RTM의 NFR 마커 형식 경고와 다른 티켓의 미커버 AC 2건은 이번 범위 밖이다.

별도 감사 DB가 필요하다. [기존 준비 절차](2026-09-08-backend-audit-tx-load.md#6-재현-방법)와 [벤치 설정](../../load-test/tx-workload/bench.init.gradle)을 사용한다. 순수 성능과 경합은 각각 실행한다.

```bash
./gradlew -I load-test/tx-workload/bench.init.gradle test --tests '*EventFanoutBenchmark.benchmarkActualSchedulerFanout'
```

```bash
./gradlew -I load-test/tx-workload/bench.init.gradle test --tests '*EventFanoutBenchmark.benchmarkEventWriteLockContentionDuringFiftyThousandFanout'
```

규모 환경변수만 바꿔 같은 테스트를 다시 실행할 때는 `--rerun-tasks`를 붙여 Gradle의 실행 생략을 피한다. [실행 계획 SQL](../../load-test/tx-workload/event-start-explain.sql)은 psql의 `ON_ERROR_STOP=1`을 켜고 별도 감사 DB에서 실행한다. 5만 명을 넣어 실제 INSERT 계획을 확인한 뒤 롤백한다.

종료 시 합성 사용자·알림·행사·구독이 모두 0건임을 확인하고 별도 DB를 삭제했다. DB SQL 로깅은 먼저 `-1`로 복구했다. 처음 비어 있던 Redis DB15에 전체 테스트가 남긴 키 44개도 정리해 0개를 확인했다.

전체 테스트 중 기존 `EncodingWorkerContextTest`는 하드코딩된 원본 `fillmap` 주소를 그대로 사용했다. 해당 DB의 인코딩 작업은 실행 전후 모두 0건이었다. 대량 합성 데이터와 SQL 로깅은 별도 감사 DB에만 적용했고 dev·운영에는 접속하지 않았다.

이번 변경은 행사 시작 알림에 한정했다. 축제 시드와 미션 캐시 조회의 기존 측정값은 개선 결과가 아니며, 후속 작업 대상으로 남는다.

[^prepare]: Hibernate가 JDBC 문장을 준비한 횟수다. DB가 실제 실행한 업무 SQL 수는 별도 로그로 대조한다.
[^pool]: 연결 풀에서 빌린 연결을 반환할 때까지의 시간 합계다. 발송과 종료 정리의 연결 사용을 합산하므로 이를 2로 나눈 값이 발송 시간은 아니다.
[^lock]: 같은 키를 얻으려는 트랜잭션은 먼저 얻은 쪽의 커밋이나 롤백까지 기다리는 PostgreSQL 잠금이다.
[^flush]: JPA가 관리하는 엔티티의 변경을 확인하고 DB에 반영하는 과정이다. 이번에는 전량 구독자 엔티티와 반복 호출을 함께 제거했다.
