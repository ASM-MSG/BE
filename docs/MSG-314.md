# MSG-314: 뱃지 획득 임박 알림

**Owner**: B (badge와 notification 도메인만 변경, 둘 다 Owner B 소관)

> 요구사항 정본: `docs/prd/MSG-313-prd.md` (알림 다양화 공유 PRD, 상태 검토됨). 이 스펙은 그중
> 뱃지 임박(MSG-314)에 해당하는 FR-3, FR-4, FR-7, FR-9의 "어떻게"만 정한다. 영상 준비 완료(MSG-313)와
> 주간 요약(MSG-315)은 다른 레인의 스펙이 다루며 이 문서의 범위가 아니다.

## 개요

다음 뱃지 티어까지 진행 수치가 정확히 1 남은 순간(예: 업로드 9개, 10개 뱃지까지 1개), 업로드 직후
그 사용자에게 푸시 알림을 기록한다. 획득 알림(결과 보상)과 짝이 되는 행동 유도 넛지다.
기존 발급 판정 엔진(`BadgeAwardServiceImpl.award()`)에 임박 판정을 얹고, 기록은 기존 알림
outbox[^1] 파이프라인(MSG-179)에 그대로 태운다. 신규 API, 신규 스키마, 컨슈머 변경이 전부 없다.

## 배경 · 목표

- 뱃지는 획득한 뒤에만 알림이 간다. 목표까지 1개 남은 순간이 행동 전환 확률이 가장 높은
  시점인데 그때는 아무것도 하지 않는다 (PRD 문제 상황).
- 목표: 다음 뱃지까지 1개 남은 사용자가 그 사실을 업로드 직후 푸시로 안다 (PRD FR-3).
- 같은 뱃지에 대한 임박 알림은 사용자당 생애 1회, 하루 전체로는 1건까지만 기록한다 (FR-4, FR-9).
- 카테고리는 기존 BADGE를 재사용해 설정 화면에서 획득과 임박이 한 토글로 묶인다 (FR-4, 2026-08-05 확정).

## 성공 기준

1. 업로드로 어떤 축의 진행 수치가 다음 티어 값보다 정확히 1 작아지면, 업로드와 같은 커밋으로
   `notifications`에 (userId, BADGE, `BADGE_NEAR:{badgeId}`) 행이 남고 기존 파이프라인이 발송한다.
2. 같은 뱃지의 임박 행은 어떤 경로(재업로드, 점령 롤백 후 재접근, 스트릭 끊김 후 재도달)로도
   두 번 생기지 않는다.
3. 하루(KST 자정 경계)에 임박 행은 사용자당 1건을 넘지 않는다. 서로 다른 뱃지가 같은 날
   동시(동시 요청 포함)에 임박해도 마찬가지다. 다음 날에는 다른 뱃지의 임박이 기록될 수 있다.
4. 알림 설정에서 BADGE를 끄면 임박도 발송되지 않는다 (기존 컨슈머의 설정 필터가 그대로 처리).
5. DB 스키마, API 응답, 계약 인터페이스, 컨슈머 코드가 전부 무변경으로 남는다.

## API 명세

신규 및 변경 없음.

- 알림 설정 조회와 토글(GET/PATCH preferences)은 카테고리 enum 순회 합성이라 그대로다. BADGE
  토글 하나가 획득과 임박을 함께 끈다 (PRD FR-4, FR-7).
- 업로드 응답(`VideoUploadResponseDto`)도 무변경이다. 임박은 응답에 싣지 않고 푸시로만 간다.
  응답의 `newBadges`는 지금처럼 실제 획득분만 담는다.

## 도메인 로직

### D1. 판정 규칙: 발급 엔진에 임박 판정을 얹는다

임박 판정은 `BadgeAwardServiceImpl.award(userId, type, metric)`의 끝(지급 루프 뒤)에 얹는다.
업로드 트랜잭션의 모든 뱃지 판정(업로드 수, 격자 수, 수집률, 스트릭, 미션)이 이 메서드 하나로
모이므로(실측: `VideoServiceImpl.saveVideo`, `StreakCommandServiceImpl`, `MissionAwardServiceImpl`
전부 업로드 트랜잭션 안에서 호출), 여기 한 곳에 얹으면 "업로드 직후 즉시, 발급과 같은 재료"라는
PRD 확정이 자동으로 성립한다. `record()`는 호출자 트랜잭션에 참여하므로(전파 REQUIRED 실측)
커밋이 곧 기록 보장 시점이다 (PRD 비기능 "전달 보장").

**임박의 정의**: 같은 축(type)에서 아직 못 받은 티어 중 `condition_value`가 정확히 `metric + 1`인
뱃지가 존재한다. 판정 쿼리는 `findEligible`과 같은 재료로 신설한다 (`BadgeRepository.findNearMiss`):

```sql
SELECT b.id AS "badgeId", b.code, b.name, b.description, b.icon_url AS "iconUrl"
FROM badges b
WHERE b.condition_type = :type
  AND (b.condition_value->>'value')::numeric = :metric + 1
  AND NOT EXISTS (SELECT 1 FROM user_badges ub WHERE ub.user_id = :userId AND ub.badge_id = b.id)
```

- **쿼리 신설이지 엔티티 매핑 확장이 아니다.** `Badge`의 `conditionValue` 미매핑은 MSG-239의
  관례다 (실측: 엔티티 주석이 Grid.geom 선례를 들어 "판정은 전부 native SQL에서 캐스트로
  소비한다"고 명시). 매핑을 여는 쪽이 오히려 관례 위반이므로 native 쿼리로 통일한다.
- 티어 값은 축 안에서 서로 다르므로(V9, V10, V12 시딩 실측) 후보는 호출당 최대 1건이다.
  SELECT 목록을 `findEligible`과 같게 맞춰 `EligibleBadgeProjection`을 재사용한다.
- **획득과 임박은 같은 호출에서 서로소다.** 지급 조건은 `value <= metric`, 임박 조건은
  `value = metric + 1 > metric`이라 한 뱃지가 둘 다에 걸릴 수 없다. 티어에 도달한 업로드는
  획득 알림만 남긴다.
- **축 범위**: 정수 개수 축(UPLOAD_COUNT, TOTAL_GRIDS, STREAK_DAYS, MISSION_COUNT)에 적용한다.
  REGION_PERCENT는 판정을 건너뛴다(서비스에서 type 검사 한 줄). 수집률은 소수 rate라 등식이
  사실상 성립하지 않고, 성립해도 "1 남음"이 1%p 남음이라는 뜻이 돼 문구와 넛지 의미가 어긋난다.
  PRD가 축을 열거하지 않으므로 이 기본값은 미해결 질문 1로 확인받는다.

### D2. 생애 1회: 이벤트 키가 DB에서 강제한다

이벤트 키는 `BADGE_NEAR:{badgeId}`. 기존 관례(획득 `BADGE:{badgeId}`, 리마인드 `REMIND:{KST일자}`,
핫구역 `HOTZONE:{KST일자}:{gridId}`)와 같은 결이다. `uq_notifications_user_event UNIQUE
(user_id, event_key)` 제약(V21 실측)과 insert의 ON CONFLICT DO NOTHING[^2]이 "같은 뱃지 생애
1회"(FR-4)를 DB 수준에서 강제한다. 점령 롤백으로 격자 수가 줄었다 다시 임박 구간에 들어와도,
스트릭이 끊겼다 같은 일수에 재도달해도, 행이 이미 있으므로 재기록이 조용히 무시된다.

### D3. 하루 1건 상한과 경합 해소 (FR-9, PR #114 리뷰 봇 P2 반영)

상한은 발송 단계가 아니라 기록 단계(트리거)에서 건다. 컨슈머 `rateLimited()`의 상한 축이
(userId, category)뿐이라(실측) BADGE를 재사용하면 획득(무제한)과 임박(1건/일)을 발송 쪽에서
구분할 수 없기 때문이다 (PRD FR-9 확정).

**실측 결론: 키 하나로 두 축을 다 잡을 수 없다.** notifications의 유니크 제약은
(user_id, event_key) 하나뿐이다 (V21 실측). 키에 KST 일자를 넣으면(`BADGE_NEAR:{일자}`) 하루
1건은 원자적으로 잡히지만 어느 뱃지였는지가 키에서 사라져 생애 1회를 걸 수 없고, 뱃지 ID를
넣으면(`BADGE_NEAR:{badgeId}`) 생애 1회는 잡히지만 하루 1건이 select-then-act[^3]로 남는다.
두 축은 서로 다른 제약이라 하나의 유니크 키로 동시에 표현되지 않는다.

**확정 설계**: 생애 축은 뱃지 ID 키(D2)에 맡기고, 하루 축은 사용자 단위 advisory 트랜잭션
잠금[^4]으로 select-then-act를 직렬화한다.

```sql
SELECT pg_advisory_xact_lock(hashtextextended('badge_near:' || :userId, 0))
```

- 레포에 같은 패턴이 이미 3곳 있다 (실측: `badge_featured:`, `region_stats:`, `video_confirm:`
  접두 잠금). 접두 `badge_near:`로 용도를 분리하고, 메서드는 `UserBadgeRepository`에 둔다
  (`acquireFeaturedLock` 선례 바로 옆).
- 잠금은 **임박 후보가 있을 때만** 잡는다. 대부분의 업로드는 후보 0건이라 추가 비용이 인덱스드
  SELECT 1회로 끝난다. 업로드 트랜잭션의 S3 복사는 뱃지 훅보다 앞이라(실측) 잠금 보유 구간은
  트랜잭션 꼬리의 짧은 순수 DB 구간이다.
- 잠금 획득 후 "오늘 KST에 기록된 BADGE_NEAR 행이 있는가"를 확인하고 없을 때만 기록한다.
  동시 업로드 둘이 서로 다른 뱃지로 임박하면 잠금이 줄을 세워 후행이 선행의 커밋을 본다
  (선행이 롤백되면 후행이 정당하게 기록한다). 한 업로드 안에서 여러 축이 연속으로 임박하면
  뒤 호출의 확인 쿼리가 같은 트랜잭션의 미커밋 행을 보고 스킵한다.
- 상한에 밀린 임박은 이월하지 않는다. 다음 진행 변화 시점에는 대부분 티어에 도달해 획득으로
  넘어가므로 임박 순간 자체가 소멸한다. 넛지는 보장이 아니라 기회라서 이 손실은 허용한다.

존재 확인 쿼리는 `NotificationRepository`에 범용 형태로 신설한다:

```sql
SELECT count(*) FROM notifications
WHERE user_id = :userId AND event_key LIKE :prefix || '%' AND created_at >= :threshold
```

`countRecordedSince(userId, "BADGE_NEAR:", threshold)`. 발송 여부(status)는 보지 않는다. 상한은
기록 단계 규칙이므로 발송 실패나 SKIPPED 여부와 무관하게 "오늘 기록했는가"만 센다.
(user_id, event_key) 유니크 인덱스가 prefix 검색을 받친다.

### D4. 일 경계와 created_at 스큐 수정

일 경계는 KST 자정이다 (glossary 스트릭 규칙, 컨슈머 `rateLimited` D8 선례와 동일). 임계값은
애플리케이션이 KST 오늘 자정을 UTC로 변환해 바인딩한다. 오늘 날짜 산출은 `Clock` 주입으로
테스트에서 고정한다 (`VideoServiceImpl` 선례).

**전제가 되는 수정 하나**: `notifications.created_at`은 DDL DEFAULT CURRENT_TIMESTAMP인데,
timestamptz 값이 timestamp 컬럼에 들어갈 때 세션 타임존 캐스트[^5]가 적용돼 KST JVM 배포에선
KST 벽시계가 저장된다 (실측: `markSent` 주석이 이 함정을 명시하고, 그래서 sent_at과
published_at만 명시 UTC로 기록한다). 일 상한 판정이 created_at을 읽으므로 이대로면 환경별로
9시간 스큐가 난다. 따라서 `NotificationRepository.insert`가 created_at을 명시적으로 쓴다:

```sql
INSERT INTO notifications (user_id, category, event_key, title, body, created_at)
VALUES (:userId, :category, :eventKey, :title, :body, statement_timestamp() AT TIME ZONE 'UTC')
ON CONFLICT (user_id, event_key) DO NOTHING
```

판정 대상인 BADGE_NEAR 행은 전부 이 수정 이후에 쓰이므로 판정이 자기일관이다. 기존 행 소급은
없고, created_at을 조건으로 읽는 코드는 현재 없으므로(실측: 릴레이는 id 순서, 상한 카운트는
sent_at) 다른 경로에 영향이 없다. 잠재 스큐의 근본 수정을 겸한다.

### D5. 문구, 설정, 상한 값

- 문구: title `뱃지 획득 임박`, body `'{이름}' 뱃지까지 딱 하나 남았어요`. 획득 문구
  (`'{이름}' 뱃지를 획득했어요`)와 나란한 결이고, 개수 축과 일수 축(스트릭) 모두에서 읽힌다.
  glossary UI 금칙어(점령, 정복)를 쓰지 않는다.
- 상한 값 1은 상수다. 판정이 "오늘 기록 존재 여부"라 개수 설정의 자리가 없고, PRD가 1건/일로
  확정했으므로 `NotificationProperties`에 키를 추가하지 않는다 (PRD 변경 파일 목록의
  "추가 여부는 스펙" 항목에 대한 답: 추가하지 않음). 상한을 늘릴 일이 생기면
  `countRecordedSince >= N` 비교로 바꾸며 그때 키를 만든다.
- 컨슈머, 설정 API, `NotificationCategory` enum, 릴레이, FCM 센더는 전부 무변경이다. BADGE는
  이미 CHECK 제약과 컨슈머 switch(무제한 분기)에 있으므로 재사용에 코드가 들지 않는다.

### 처리 순서 (award 끝에 얹는 흐름)

```text
1. type == REGION_PERCENT 이면 종료 (D1 축 범위)
2. findNearMiss(type, metric, userId) 가 0건이면 종료   <- 대부분의 업로드가 여기서 끝
3. acquireBadgeNearLock(userId)                          <- advisory 잠금, 커밋 시 자동 해제
4. countRecordedSince(userId, "BADGE_NEAR:", KST 오늘 자정의 UTC) > 0 이면 종료 (하루 1건)
5. record(userId, BADGE, "BADGE_NEAR:{badgeId}", "뱃지 획득 임박", "'{이름}' 뱃지까지 딱 하나 남았어요")
   -> 커밋과 함께 outbox 확정, 이후는 기존 릴레이/Kafka/컨슈머/FCM 흐름
```

## 데이터 모델

| created_at | 명시 UTC (D4 수정 이후) |

## 테스트 시나리오

JUnit 5, 한국어 메서드명. 판정과 상한은 서비스 통합 테스트, 경합은 동시성 테스트
(`RegionStatsConcurrencyTest` 선례)로 검증한다.

- `다음_티어까지_1개_남은_업로드는_임박_알림을_기록한다` (예: 9번째 업로드 후 RECORDER_10 임박 행)
- `티어에_도달한_업로드는_획득만_기록하고_임박은_기록하지_않는다` (서로소 검증, D1)
- `같은_뱃지의_임박_알림은_생애_1회만_기록된다` (같은 키 재기록이 0행으로 무시)
- `점령_롤백으로_임박_상태를_다시_만들어도_재기록되지_않는다` (FR-4 "오가도 반복 없음")
- `하루에_임박_알림은_사용자당_1건만_기록된다` (서로 다른 뱃지, 같은 KST 날)
- `한_업로드에서_두_축이_동시에_임박해도_1건만_기록된다` (같은 트랜잭션 내 순차 스킵, D3)
- `다음_날에는_다른_뱃지의_임박이_기록될_수_있다` (Clock 전진 후 재판정)
- `수집률_축에서는_임박을_판정하지_않는다` (D1 축 범위, 미해결 질문 1 확정 전 기본값)
- `임박_후보가_없는_업로드는_잠금_없이_지나간다` (2번에서 종료하는 다수 경로)
- `동시_업로드가_서로_다른_뱃지로_임박해도_하루_1건이_지켜진다` (스레드 2개, advisory 잠금 직렬화)
- 발송 단계(BADGE 토글 off 시 SKIPPED 등)는 기존 컨슈머 테스트가 커버하므로 신규 작성하지 않는다.

## 미해결 질문

1. **임박 판정 축의 범위 (성민 확정 필요)**: PRD FR-3은 "진행 수치가 정확히 1 남으면"이라고만
   하고 축을 열거하지 않는다. 이 스펙의 기본값은 다음과 같다.
   - 포함: UPLOAD_COUNT, TOTAL_GRIDS, MISSION_COUNT, 그리고 STREAK_DAYS. 스트릭은 개수가 아니라
     연속 일수 상태값이지만 "내일 하루만 더 올리면"이라는 넛지로 유효하고, 끊김 후 재접근의
     반복은 생애 1회 규칙이 흡수한다.
   - 제외: REGION_PERCENT. 소수 rate라 등식이 사실상 성립하지 않고, "하나 남음" 문구가 1%p
     남음과 맞지 않는다. 포함으로 확정되면 판정식(예: `value - 1 <= metric < value`)과 전용
     문구를 별도로 정의해야 하므로 범위가 달라진다.
   기본값대로 진행해도 되는지, 특히 STREAK_DAYS 포함과 REGION_PERCENT 제외가 제품 의도와 맞는지
   확인을 요청한다.

[^1]: outbox: 알림 요청을 외부 시스템에 바로 쏘지 않고 비즈니스 트랜잭션과 같은 DB 커밋으로
  테이블에 먼저 남기는 패턴. 커밋되면 기록이 보장되고, 별도 릴레이가 그 행을 읽어 발송하므로
  업로드 성공과 알림 유실이 분리되지 않는다.
[^2]: ON CONFLICT DO NOTHING: PostgreSQL INSERT가 유니크 제약과 충돌하면 에러 대신 0행으로
  조용히 끝나는 절. 같은 (userId, eventKey) 재기록이 예외 없이 무시되는 근거라, 앱 코드의 사전
  중복 검사 없이도 생애 1회가 성립한다.
[^3]: select-then-act: 조건을 조회로 확인한 뒤 별도 문장으로 쓰는 2단 패턴. 두 트랜잭션이
  동시에 조회 단계를 통과하면 둘 다 조건을 만족한다고 믿고 써 버려 상한이 뚫린다. PR #114
  리뷰가 지적한 경합이 정확히 이 형태다.
[^4]: advisory 트랜잭션 잠금(pg_advisory_xact_lock): 테이블 행이 아니라 임의의 숫자 키를 잠그는
  PostgreSQL 기능. 같은 키를 잡으려는 트랜잭션은 앞선 트랜잭션이 커밋 또는 롤백할 때까지
  대기하므로, 사용자 단위로 실행 순서를 줄 세울 수 있고 트랜잭션이 끝나면 자동 해제된다.
[^5]: 세션 타임존 캐스트: timestamptz 값을 timestamp 컬럼에 넣을 때 PostgreSQL이 접속 세션의
  타임존 설정으로 벽시계를 환산하는 동작. JDBC 세션이 JVM 기본 타임존을 따르므로 KST 서버에서는
  UTC가 아니라 KST 문자반 시각이 저장돼, UTC 임계값과 비교하면 9시간 어긋난다.
