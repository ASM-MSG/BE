## 개요

격자에 "그 격자 중심점이 속한 행정동"을 **쓰기 시점에 1회 판정해 `grids.region_code`에 저장**하고, 그 저장값을 두 조회 경로가 **순수 equi-join**으로 소비한다.

```
[원인] 전역 격자 등록(lazy insert, 격자 생애 1회)
        → grids.region_code = 중심점 ST_Covers 판정 (Owner A 규칙, upsertGrid 호스팅)

[소비 ①] 갤러리 목록 GET /api/collections/grids  (기존, 153)
          → 항목마다 regionName 추가 (grids·regions equi-join, geospatial 0)

[소비 ②] 동 단위 내 영상 GET /api/collections/videos?regionCode=  (신설)
          → 그 행정동 격자들에 올린 내 영상 리스트 (videos⨝grids equi-join, geospatial 0)
             FE 동선: 격자 클릭 → by-grid(동+탐험률, 153) → regionCode 로 본 API 호출
```

**귀속 축은 전부 격자 중심점**(153/155/93과 동일). 목록 라벨·동 단위 영상·by-grid 탐험률이 **항상 같은 행정동**을 가리켜 어긋날 여지가 없다. 무귀속(해안) 격자는 `region_code = NULL` → 목록 `regionName = null`, 동 단위 조회 미포함.

## 배경 · 목표

- **사용자/제품 관점**: (1) 갤러리 목록 셀에 "역삼1동"처럼 **어디서 수집했는지**를 보여준다(153이 예약한 목록 라벨). (2) 격자를 탭해 by-grid로 동+탐험률을 본 뒤, **그 행정동에서 내가 수집한 영상을 동 단위로 모아보기** 한다. 지금은 격자 단위(127 my-videos)만 있어 동 단위는 불가하다 — 격자→행정동 매핑이 저장돼 있지 않고(155는 계산-판정만), 조회 경로 geospatial은 금지라 라이브 판정도 못 한다.
- **목표**:
  1. `grid_id → region_code`(격자 중심점 행정동)를 **쓰기 시 1회 판정·저장**해 조회를 순수 equi로 만든다.
  2. 갤러리 목록에 `regionName`(nullable)을 **그 한 필드만** 추가한다(기존 계약 무변경 — DoD).
  3. **동 단위 내 영상 조회 API**를 신설한다(격자 축 귀속 — 영상 좌표가 옆 동이어도 격자 소속 동으로 집계, 내 영상만, 최신순).
  4. 목록 라벨·동 단위 영상·by-grid 탐험률의 **귀속을 중심점 축 하나로 일치**시킨다(저장값 = 155/93의 라이브 판정값).

## 성공 기준 (관찰 가능)

1. **첫 업로드로 격자가 전역 등록되면** `grids.region_code`에 그 격자 **중심점**이 속한 행정동이 기입된다. 무귀속(해안)이면 `NULL`.
2. **판정은 격자 생애 1회**: 이미 등록된 격자에 재업로드/타 사용자 점령해도 `region_code`는 재판정되지 않는다(불변).
3. **저장값 = 라이브 판정값**: `grids.region_code`가 그 격자의 `by-grid` 귀속(153 `resolveByPoint(center)`)·`refreshRegionStats`(155) 귀속과 **같은 행정동**이다(경계 격자 포함).
4. **V5 백필 멱등**: `region_code IS NULL` 행만 판정해 채우고, 재실행(flyway clean 후)해도 같은 값으로 수렴. `regions` 미시딩 환경은 no-op.
5. **갤러리 목록**: 각 항목에 `regionName`(그 격자 중심점 행정동 이름)이 붙는다. `region_code`가 NULL이면 `regionName = null`. **`regionName` 추가 외 나머지 필드·정렬·30 상한은 153과 동일**(계약 무변경 — DoD).
6. **동 단위 내 영상**: `GET /api/collections/videos?regionCode=`(인증)가 그 행정동 **격자들**에 올린 **내** ACTIVE 영상을 `created_at DESC`로 반환. **영상 좌표가 옆 행정동이어도 격자 소속 행정동 기준으로 포함**된다(격자 축 — DoD).
7. 동 단위 조회에 **타 사용자 영상 미포함**, 그 행정동에 내 영상이 없거나 미존재 regionCode면 **빈 배열 200**(DoD).
8. **조회 경로 geospatial 0**: 목록(①)·동 단위(②) 모두 순수 equi/PK-join(쿼리 문자열에 `ST_` 없음). 판정 geospatial은 **쓰기 경로(upsertGrid)·백필(1회)에서만**.
9. 크로스오너 계약 4종 Java 시그니처 불변. **신규 에러 코드 없음**. 공유 로컬 DB 미오염, 전체 테스트 green.

## 결정 (Decisions)

### D1 — 라벨 기입 지점 = **lazy insert(`upsertGrid`)에 판정 인라인**, 격자 생애 1회. 규칙은 Owner A 자산, 호스팅은 B 레포

- **결정**: `grids.region_code`는 `VideoRepository.upsertGrid`(전역 격자 등록, 격자 생애 1회의 유일한 지점)의 `INSERT`에서 중심점 판정 서브쿼리로 채운다. 판정 규칙은 155/93과 동일(`ST_Covers(boundary_geom, center) ORDER BY region_code LIMIT 1`). **재판정을 막으려** `INSERT … SELECT … WHERE NOT EXISTS(격자 존재)` 형태로 두어, 서브쿼리가 **실제 삽입 시(신규 격자)만** 평가되게 한다(재방문은 short-circuit → 판정 0회). `ON CONFLICT (grid_id) DO NOTHING`은 동시 삽입 레이스 방어로 유지.
- **근거**:
  1. **함수 종속의 자연 지점**: `region_code`는 격자 중심점의 함수라 **격자 row가 태어나는 그 문장**에서 함께 쓰는 게 원자적이고 정확하다. `WHERE NOT EXISTS`로 "격자 생애 1회"(티켓 비용 근거, GIST p50 0.053ms) 그대로 — 재방문마다 판정하지 않는다.
  2. **B는 이미 grids를 쓴다**: `upsertGrid`가 이미 `grid_id/grid_y/grid_x/center_geom/bbox_geom`을 B 레포에서 native로 삽입한다(66 선례). `region_code`는 **B가 이미 하는 grids 쓰기에 컬럼 하나 더**일 뿐 — 새 테이블 크로싱이 아니다.
  3. **판정을 이미 있는 center로**: 서브쿼리가 쓰는 중심점은 `upsertGrid`가 이미 만드는 `ST_MakePoint(centerLon, centerLat)`와 같은 점이라 추가 입력이 없다.
- **단일 진실 원천 유지**: 규칙 SQL은 93·155(둘 다 `RegionRepository`)에 이미 있고, 여기서 B 레포에 4번째 사본이 생긴다. **드리프트 방지는 SQL 위치가 아니라 일치 테스트로 고정**한다 — `라벨은_by_grid_귀속과_같은_행정동이다`(같은 격자를 155로 점령시켜 recompute 귀속·저장 라벨·by-grid가 세 곳 다 같은 행정동인지). 이는 153이 `중심점_귀속은_155_refreshRegionStats와_같은_행정동을_고른다`로 93↔155를 고정한 방식과 동일. **Owner A가 판정 프래그먼트를 리뷰**(§계약 변경).
- **기각**:
  - **(b) 155 `refresh` 경로에서 grids UPDATE**(Owner A 자기완결): `refresh`는 **첫 점령·롤백**마다 도는데(사용자마다·롤백마다) 라벨은 격자 생애 1회면 족해 **호출 조건과 라벨 필요 조건이 어긋난다**(멱등 no-op으로 무해하나 stats recompute에 라벨링 관심사를 얹어 응집이 흐려짐). 라벨은 격자의 탄생(lazy insert)에 붙는 게 맞다.
  - **(c) A 전용 라벨 계약 메서드 신설 + B가 호출**: 새 크로스오너 계약 + 추가 왕복 — INSERT가 인라인으로 할 수 있는 판정에 과하다.

### D2 — V5 마이그레이션 = **컬럼 + 멱등 백필 한 파일**. 백필은 `region_code IS NULL` 행만, 자동·재실행 안전

- **결정**: `V5__grids_region_code.sql`에 `ALTER TABLE grids ADD COLUMN region_code VARCHAR(10) REFERENCES regions(region_code)`(nullable) + **백필 `UPDATE … WHERE region_code IS NULL`**(판정 규칙 동일)을 함께 둔다. 수동 스크립트 반려.
- **근거**:
  1. **자동·멱등**: 배포 시 Flyway가 실행, `WHERE region_code IS NULL`이라 재실행(flyway clean 후)해도 같은 값 수렴. 해안 격자는 재판정해도 NULL(안정), 미판정 격자는 채워짐 — NULL의 두 의미("해안" vs "미판정")가 **재판정 시 동치라 무해**.
  2. **실행 순서 안전성(중요)**: Flyway는 앱 기동 초기(RegionSeeder 런타임 시딩 **전**)에 돈다. 그럼 백필이 빈 regions를 볼 수 있으나 — `regions`는 **영속 테이블**이라 *격자가 있는 환경*(과거 배포에서 154 시더가 이미 3,558행 시딩)에는 V5 시점에 regions가 **이미 차 있다** → 기존 격자가 정상 백필된다. *신규/테스트 환경*은 regions 미시딩이지만 **격자도 없어** 백필이 no-op이어도 옳고, 이후 신규 격자는 upsertGrid가 채운다. 그래서 "미시딩 환경은 no-op → lazy 기입이 채움"이 성립.
- **기각**: 수동 스크립트 — 배포 단계에서 잊히기 쉽고, 멱등 백필은 마이그레이션에 두는 게 안전.
- **보정 (2026-07-23, Codex 리뷰 P1)**: 위 근거 2의 "격자 있는 환경엔 regions 완비" 전제는 운영 순서 가정일 뿐 강제가 아니다 — 시딩 플래그 기본 off + 격자 생성(업로드)은 regions 무관이라, **격자는 있는데 regions 가 빈 환경**이 성립한다. 그 환경에선 V5 백필(Flyway, 시더 이전)이 no-op 으로 끝나고 `upsertGrid`는 기존 격자를 건너뛰어 라벨이 **영구 NULL** 로 남는다. → **`RegionSeeder.run`이 시딩 직후 같은 멱등 백필(`RegionRepository.backfillGridRegionCodes`)을 1회 실행**해 닫는다. `IS NULL`에 **`EXISTS`(실제 라벨될 행만) 가드**를 겹친다 — `IS NULL`만이면 무귀속(해안) 격자가 시딩 켠 기동마다 NULL→NULL 재기록(행 잠금·dead tuple·허위 카운트)되기 때문(Codex 2차 지적). 라벨 완비 환경에선 진짜 0행 no-op.
- **비용 ceiling**: 백필은 격자마다 `ST_Covers` 1회(현재 격자 수로 유한, MVP 소량·GIST). `ponytail: 배포 시점 grids 가 대량이면 스로틀 배치로 분리. MVP 격자 수엔 인라인 UPDATE 로 충분.`

### D4 — 갤러리 목록 = **`regionName` 1필드만 추가**(grids·regions equi-join). 그 외 153 계약 불변

- **결정**: `getCollectionGrids`에 `LEFT JOIN grids g ON g.grid_id = ug.grid_id LEFT JOIN regions r ON r.region_code = g.region_code`를 더해 `r.region_name`을 `regionName`(nullable)으로 낸다. `CollectionGridProjection`/`View`/`ResponseDto`에 `regionName` 1필드 추가. **정렬·30 상한·나머지 필드·gridY/gridX 산출(`GridEncoder.decode`)·cover presign은 전부 153 그대로.**
- **근거**:
  1. **저장값 소비라 geospatial 0**: 라벨을 미리 저장했으니 목록은 PK/equi-join뿐(153 D2가 라벨을 생략한 이유였던 "조회 30 geospatial"이 소멸). 153 D5의 "grids 미조인"을 여기서 **필요에 의해 뒤집되**, geospatial 없는 equi 조인이라 ADR 정합.
  2. **regionName = by-grid 라벨**: `grids.region_code`(=중심점 판정)의 이름이라 목록 라벨과 격자 클릭 by-grid가 같은 동(153 축 불일치 우려의 근본 해소).
  3. **최소 변경(DoD)**: "목록 regionName 추가 외 기존 계약 무변경" — 딱 한 필드.
- **null 처리**: `region_code` NULL(해안/미판정)이거나 regions에 없으면 `regionName = null`. LEFT JOIN이라 격자·라벨이 없어도 목록 행은 유지.

### D5 — `grids.region_code` **인덱스 미추가**

- **결정**: V5는 인덱스를 만들지 않는다.
- **근거**: 어떤 조회도 **region_code 주도가 아니다**. 동 단위 영상은 `idx_videos_user_created(user_id, …)`로 **내 영상**을 몰아 잡고 grids를 PK로 조인해 `region_code`를 필터한다(사용자 영상 수가 구동 상한). 갤러리 목록은 `user_grids`(내 30행)를 grids PK로 조인. 백필은 1회 풀스캔. FK 정합은 참조되는 `regions.region_code`(PK) 쪽 인덱스로 충분 — 참조하는 grids 쪽 인덱스는 FK에 불필요.
- `ponytail: "한 행정동의 모든 격자"를 region_code 주도로 훑는 조회가 생기면 그때 idx_grids_region_code 추가. 지금은 없어 불필요 인덱스 금지.`

### D6 — 155 `refreshRegionStats` equi-join 단순화 = **비스코프**(후속 분리)

- **결정**: `refreshRegionStats`의 `ST_Covers` LATERAL을 `g.region_code` equi-join으로 바꾸는 최적화는 **본 티켓에서 하지 않는다**.
- **근거**:
  1. **스코프 봉쇄**: 본 티켓 핵심은 라벨의 쓰기·읽기다. recompute 재작성은 별도 정합면(NULL 라벨 = 기존 해안 no-op과 **등가인지**, `RegionStatsRecomputeTest` 전건 재검증)을 가져 라벨 롤아웃과 섞으면 리스크.
  2. **동작하는 코드**: 155는 지금 `ST_Covers`로 정확하다. 바꿀 강제 사유(버그) 없음.
  3. **선결 조건**: equi 단순화의 정확성은 **모든 격자가 신뢰성 있게 라벨됨**에 의존(NULL 격자를 equi가 해안 취급 → 기존 ST_Covers는 정상 귀속했을 수 있음). 프로덕션 라벨 완비가 확인된 뒤 후속에서 교체.
- `ponytail: 후속 티켓에서 refreshRegionStats 의 두 ST_Covers 를 g.region_code equi 로 치환 + WHERE region_code IS NOT NULL 가드, RegionStatsRecomputeTest 등가 통과가 게이트.`

### D7 — Grid 엔티티 `region_code` **미매핑**(전부 native)

- **결정**: `grid/entity/Grid`에 `region_code` 필드를 매핑하지 않는다.
- **근거**: 접근이 전부 native다 — 쓰기(upsertGrid), 읽기(목록/동 단위 조인), 백필(마이그레이션). JPA read 경로가 없다. `ddl-auto=validate`는 미매핑 컬럼을 문제 삼지 않는다(Grid의 `center_geom/bbox_geom`, Region의 `boundary_geom` 미매핑 선례). 매핑하면 미사용 필드.
- `ponytail: region_code 를 JPA 로 읽는 경로가 생기면 그때 필드 추가. 지금은 native 로 족함.`

```sql
    ST_SetSRID(ST_GeomFromText(:bboxWkt), 4326)::geography,
    (SELECT r.region_code FROM regions r                                   -- ← A 규칙(93/155 동일)
       WHERE ST_Covers(r.boundary_geom, ST_SetSRID(ST_MakePoint(:centerLon, :centerLat), 4326)::geography)
       ORDER BY r.region_code LIMIT 1)
WHERE NOT EXISTS (SELECT 1 FROM grids WHERE grid_id = :gridId)
ON CONFLICT (grid_id) DO NOTHING
```
- **생애 1회**: 재방문(격자 존재)은 `WHERE NOT EXISTS`가 0행 → 서브쿼리 미평가 → 판정 0회. 신규 격자만 GIST `ST_Covers` 1회. (`ON CONFLICT`는 동시 삽입 레이스 방어.)
- **무귀속**: 덮는 행정동 없으면 서브쿼리 NULL → `region_code = NULL`(FK는 NULL 허용).
- **시그니처 불변**: 파라미터 동일, 반환 void 유지(재방문은 부작용 0). *허용 대안*: `VALUES(...)` 유지 + 서브쿼리 컬럼(단, `ON CONFLICT`가 VALUES를 먼저 평가해 재방문마다 GIST 1회 — 비용 무시가능하나 "생애 1회" 근거가 약해져 `SELECT … WHERE NOT EXISTS` 권장).

### 백필 — `V5__grids_region_code.sql` (Owner A, 멱등)
```sql
UPDATE grids g SET region_code = (
    SELECT r.region_code FROM regions r
      WHERE ST_Covers(r.boundary_geom, g.center_geom)                       -- 저장된 center_geom
      ORDER BY r.region_code LIMIT 1)
WHERE g.region_code IS NULL;
```
- 저장된 `center_geom` 사용 → upsertGrid 인라인과 **같은 규칙·같은 점**. `IS NULL` 가드로 멱등·no-op 안전(§D2).

### ① 갤러리 목록 regionName — `UserGridRepository.getCollectionGrids` (Owner B, geospatial 0)

```sql
SELECT
```

### ② 동 단위 내 영상 — `UserGridRepository`(native) + `UserGridQueryService.getRegionVideos` (Owner B, geospatial 0)
```sql
SELECT
    v.id AS "videoId", v.grid_id AS "gridId", v.thumbnail_url AS "thumbnailKey",
    v.processing_status AS "processingStatus", v.duration_sec AS "durationSec",
    v.created_at AS "createdAt"

JOIN grids g ON g.grid_id = v.grid_id
WHERE g.region_code = :regionCode          -- 격자 축 귀속(영상 좌표 아님)

```

### 조회 경로 ADR 정합
- 목록(①)·동 단위(②) 모두 geospatial 0(저장된 라벨을 equi로 소비). 판정 `ST_Covers`는 **쓰기(upsertGrid, 격자 생애 1회)·백필(1회)**에서만 — 155/93이 세운 "저빈도 쓰기 경로 geospatial 허용, 조회/핫패스 금지"에 정합. v6 ADR의 region-grid "비연결"은 *조회 geospatial 금지* 취지였고, **쓰기 시 저장 + equi 조회**가 바로 그 취지의 실현이다.

## 계약 변경

**크로스오너 계약 4종(`GridQueryService`·`HotZoneService`·`UserGridQueryService`·`UserOidcCommandService`) 및 `RegionQueryService`/`RegionStatsCommandService`의 A↔B 소비 Java 시그니처는 전부 불변.** 그러나 본 티켓의 실질 계약면은 **Java 인터페이스가 아니라 신설 공유 컬럼**이다 — **grid-dev ↔ auth-dev 상호 확인 필수**.

### 신설 공유 컬럼 `grids.region_code` (A↔B 경계면)
- **A(권위·쓰기 규칙)**: 판정 규칙(`ST_Covers … ORDER BY region_code LIMIT 1`)은 Owner A 자산이다. V5 마이그레이션과 upsertGrid에 들어갈 판정 프래그먼트를 **A가 리뷰**하고, `findContainingRegion`/`refreshRegionStats`와 규칙이 어긋나지 않음을 확인한다.
- **B(호스팅·소비)**: 프래그먼트를 `upsertGrid`(B 레포)에 호스팅하고, 목록 `regionName`·동 단위 영상 필터에서 `grids.region_code`를 **읽는다**.
- **일치 계약**: 저장값 = `by-grid`/`refreshRegionStats` 라이브 판정값(같은 중심점·같은 규칙). **일치 테스트로 고정**(§D1·테스트 모듈 1·3).
- **규칙 드리프트 방지**: A가 타이브레이크(`ORDER BY region_code`)를 바꾸면 B 호스팅 사본·V5 백필까지 함께 갱신해야 하며, 일치 테스트가 누락을 잡는다.

### B-내부 read 확장 (non-breaking, A 미소비 — 형식적 확인)
- `UserGridQueryService`: `CollectionGridView`에 `regionName` 필드 추가(반환형 확장) + `getRegionVideos(long userId, String regionCode)` **신설**. 둘 다 `CollectionController`만 소비(Owner A 미소비) → non-breaking. 규칙상 계약 인터페이스 변화라 명시.

### 신규 에러 코드
**없음.** 동 단위 조회는 미존재 regionCode = 빈 배열 200(§D3), 누락 = 400 global, 미인증 = 401 global. `RegionErrorCode`(6400/6404)·`usergrid` 도메인 대역에 추가하지 않는다.

## 테스트 시나리오 (JUnit5 + AssertJ · 한국어 백틱 메서드명 · 모듈 단위)

> **테스트 격리(MEMORY 'shared local DB' · 93/152/154/155/156/153 §격리 원칙)**: **합성 fixture만** 쓴다 —
> 자기 유저 신규 생성 + 합성 `region_code` **`99950`~`99959` 대역**(`m167` 접두 이름, 실존 3,558행과 무충돌) + 알려진 **소형 boundary 폴리곤** + 그 폴리곤 안/밖에 **중심점**이 오도록 잡은 합성 `grids`(center_geom 지정) + `user_grids`/`videos`.
