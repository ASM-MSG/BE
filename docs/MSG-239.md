**Owner**: B
— `com.msg.fillmap.badge.*` 신설(콘텐츠/도감 축 — user·video·usergrid와 같은 B 계열), 훅 배선 대상

## 개요

badges 마스터를 시딩하고, 업로드 요청 흐름 안에서 해당 축 뱃지만 판정·지급하는 엔진을 만든다.

```
POST /api/videos (업로드, 기존)
  ├─ videos INSERT · user_grids UPSERT · (첫 수집 시) region_stats refresh   ← 기존 배선 (66/155)
  ├─ [신규 훅] BadgeAwardService
  │    ├─ 항상:      UPLOAD_COUNT 판정 (내 videos 행 수)
  │    └─ 첫 수집 시: TOTAL_GRIDS 판정 (내 user_grids 행 수)
  │                  REGION_PERCENT 판정 (refresh 직후 그 행정동의 region_stats.progress_rate)
  └─ 응답: VideoUploadResponseDto + newBadges[] 동봉 (FR-9)

PUT /api/badges/featured (신규)   대표 뱃지 집합 교체 (최대 2개, 획득 뱃지만 — FR-8)
```

STREAK_DAYS·MISSION_COUNT는 판정 훅 선행이 없어 **시딩·지급 모두 이번 범위에서 제외**한다(§D2 —
PRD 미션 축 원칙 "시딩은 훅과 함께 활성화"를 두 축에 일관 적용). 단 `MISSION_COUNT` CHECK 확장은
V9에서 미리 한다 — 값 확장일 뿐 사용자 노출이 없고, 미션 티켓이 스키마를 안 건드리게 된다.

## 성공 기준 (관찰 가능)

1. V9 적용 후 `badges`에 활성 3축 11종이 시딩되어 있다(code 유일). STREAK_DAYS·MISSION_COUNT·SPECIAL row는 **없다**(§D2).
2. 업로드 응답에 이번 요청으로 **새로 획득한 뱃지 목록**이 동봉된다 — 첫 업로드(=첫 수집)면 `EXPLORER_1`이 응답에 실린다.
3. 같은 행동을 반복해도(동시 요청 포함) `user_badges`에 중복 row가 생기지 않는다 — PK + `ON CONFLICT DO NOTHING`(FR-3).
4. 하나의 행동으로 여러 티어를 동시에 충족하면 전부 지급된다(FR-4 — 소급 시딩 직후 시나리오 포함).
5. 영상 삭제로 수집이 롤백돼도 `user_badges`는 불변이다(FR-5 — 삭제 경로에 뱃지 코드 0줄).
6. 판정은 행동으로 도달 가능한 축만 조회한다 — 재방문 업로드는 UPLOAD_COUNT만, 첫 수집은 3축(FR-2, 전수 스캔 금지). 판정 쿼리에 `ST_` 없음.
7. `PUT /api/badges/featured`로 획득 뱃지 중 최대 2개를 대표로 지정/해제(빈 배열)할 수 있고, 미획득 뱃지 지정은 7403, 3개 이상·중복은 400이다. DB가 사용자당 대표 2개 초과를 물리적으로 차단한다(partial UNIQUE — §D6).
8. V9의 소급 블록이 기존 데이터(user_grids·videos·region_stats)로 활성 3축을 일괄 지급하고, 소급분은 `notified_at IS NULL`(미확인), 동기 지급분은 `notified_at` 즉시 기록이다(FR-9·10).
9. 크로스오너 계약 4종 Java 시그니처 불변. 공유 로컬 DB 미오염, 전체 테스트 green.

## 결정 (Decisions)

### D1 — 티어 = badges row 분리, condition_value = `{"value": N}` 단일 포맷 (PRD 확정의 구현 상세)

- **결정**: 티어당 별도 row(연결 컬럼 없음 — PRD 확정). `condition_value`는 전 축 공통
  `{"value": N}` — TOTAL_GRIDS/UPLOAD_COUNT는 개수, REGION_PERCENT는 퍼센트(10=10%),
  STREAK_DAYS는 일수, MISSION_COUNT는 스탬프 수. 판정 SQL은
  `(b.condition_value->>'value')::numeric <= :metric` 하나로 전 축 동형이다.
- **code 체계**: `{축}_{수치}` — `EXPLORER_1/10/50/100/500` · `RECORDER_10/50/100` ·
  `REGION_MASTER_10/25/50`. (미래: `STREAK_3/7/30` · `MISSION_1/5/10`.) 수치가 code에 들어가
  시딩 값 컨펌으로 티어가 바뀌면 code도 함께 바뀐다 — 배포 전(데이터 무참조)이라 무비용.
- **기각**: 축별 JSONB 키 분화(`{"percent":…}`·`{"days":…}`) — 판정 쿼리가 축마다 갈라져
  엔진이 조건 타입별 분기를 갖게 된다. 단일 키면 엔진은 (type, metric) 쌍만 안다.

### D2 — 선행 의존 스코프: STREAK_DAYS·MISSION_COUNT·SPECIAL은 **시딩·훅 모두 제외**, CHECK 확장만 선반영 (티켓 위임 미확정 해소)

- **결정**:
  - **STREAK_DAYS**: 시딩·판정 훅 모두 **MSG-200에 위임**. MSG-200이 streaks 갱신 로직을 만들 때
    갱신 직후 `BadgeAwardService` 호출 + `STREAK_3/7/30` 시딩(+소급) 마이그레이션을 함께 넣는다.
  - **MISSION_COUNT**: 동일 — 미션 판정 엔진 티켓(user_missions 스탬프 생성)이 스탬프 INSERT 직후
    호출 + 시딩을 함께. **CHECK 확장만 V9에서 미리** 한다(값 확장은 노출 0·미션 티켓의 스키마 손대기 제거).
  - **SPECIAL**: 미시딩 — 지급 규칙이 뱃지별 개별 명시(FR-10)인데 오픈 기념의 규칙(가입 시점? 오픈 주간
    업로드?)이 미정. 오픈 준비 티켓에서 규칙 확정과 함께 시딩.
- **근거**: PRD 라인업 표의 미션 축 원칙("훅 없이 시딩만 하면 획득 불가 뱃지 노출 — 시딩은 지급 훅
  배선과 함께 활성화")을 세 축에 일관 적용. 훅 없는 시딩은 MSG-201 조회에서 영원히 미획득인 뱃지로
  보인다 — 획득 불가 목표는 보상 시스템의 신뢰를 깎는다.
- **엔진 설계 함의**: `BadgeAwardService.award(userId, conditionType, metric)`은 축 무관 동형이라
  (D1) 후속 티켓의 배선은 "metric 계산 + award 호출 1줄 + 시딩 SQL"뿐이다 — 이 티켓이 엔진을,
  후속이 배선을 갖는 구조가 자연 분업이 된다.

### D3 — 훅 = `saveVideo` 안 2지점, 같은 트랜잭션 동기 판정 (FR-2 "요청 흐름 안" 구현)

- **결정**: `VideoServiceImpl.saveVideo`에서
  1. `upsertUserGrid` 이후 **항상**: `UPLOAD_COUNT` 판정 — metric = 내 `videos` 행 수(status 무관 —
     방문 이벤트 누적, 아래 근거).
  2. `!alreadyOccupied`(첫 수집)일 때 추가로: `TOTAL_GRIDS`(metric = 내 `user_grids` 행 수) +
     `refresh(userId, gridId)` **직후** `REGION_PERCENT`(§D4). — refresh 배선(155)과 같은 블록.
  - 전부 **업로드 트랜잭션 참여**(155 선례) — 별도 트랜잭션/비동기 없음. 지급 실패(제약 위반 외 예외)는
    업로드 롤백과 함께 간다: 판정 SQL은 read + `ON CONFLICT DO NOTHING`이라 실질 실패 표면이 없다.
  - **삭제·교체 경로 훅 없음**: 비회수(FR-5)라 삭제는 무관, 교체는 videos 행 수·수집 불변이라 도달
    가능한 뱃지가 없다(FR-2 역방향 적용).
- **UPLOAD_COUNT metric = `COUNT(*) FROM videos WHERE user_id`(status 무관)**: glossary "방문 =
  videos 1 row = 1 방문" — 업로드 이벤트는 발생 사실이고 soft delete(DELETED 행 보존·undelete 없음)라
  행 수가 곧 생애 업로드 수다. ACTIVE만 세면 "지웠다 다시 올리기"로 같은 뱃지 구간을 재통과하는
  기형이 생기고, 비회수 원칙(획득 이력은 과거 행동의 사실)과도 이쪽이 정합.
- **기각**: 커밋 후 비동기 지급(afterCommit) — 응답 동봉(FR-9)이 불가능해지고, MVP 판정 비용은
  인덱스드 카운트 2~3개라 동기로 충분. 이벤트 리스너/도메인 이벤트 추상화 — 호출 지점 1곳에 과함.

### D4 — REGION_PERCENT 판정 = refresh가 물질화한 `region_stats.progress_rate`를 같은 트랜잭션에서 읽기 (재계산 0)

- **결정**: 첫 수집 시 `refresh(userId, gridId)`(기존 배선)가 그 격자 귀속 행정동의 progress_rate를
  물질화한 **직후**, badge repository가
  `SELECT rs.progress_rate FROM region_stats rs JOIN grids g ON g.region_code = rs.region_code
  WHERE rs.user_id = :userId AND g.grid_id = :gridId`로 읽어 metric으로 쓴다. 같은 트랜잭션이라
  refresh의 UPSERT가 보인다. 무라벨(해안) 격자는 refresh가 no-op → 행 없음 → 판정 skip(0행 = 미판정).
- **근거**: "단일 행정동 수집률" 조건에서 이번 행동으로 임계를 새로 넘을 수 있는 행정동은 **이 격자의
  귀속 행정동뿐**이다(FR-2 해당 축 한정의 지역 버전) — 전 행정동 스캔 불요. 수집률 계산 로직을
  복제하지 않고 155/236이 물질화한 값을 소비만 한다(ST_Covers 0, 계산 단일 원천 유지).
- **계약면**: `region_stats`는 A의 쓰기 도메인(RegionRepository) — B의 badge repo가 읽기 전용 native로
  소비하는 최초 지점이다. 167/238의 "B가 공유 데이터를 native equi로 소비, A는 리뷰" 선례를 따른다
  (§계약 변경). Java 계약 신설 기각 — native 1왕복 read에 계약+왕복은 과함(238 §D5 동일 논리).
- **비고**: progress_rate는 155가 `ROUND(collected*100/total, 2)`로 물질화한 값 — 판정도 이 값 기준
  (표시용 100 clamp는 156 read 소관, 판정엔 원값·100 초과여도 50 임계 충족이라 무영향).

### D5 — 지급 엔진 = 후보 SELECT + `ON CONFLICT DO NOTHING` INSERT 2단, 신규 획득분 반환 (FR-3·4 구현)

- **결정**: `BadgeAwardService.award(userId, BadgeConditionType type, BigDecimal metric)` →
  `List<EarnedBadgeResponseDto>`:
  1. **후보 조회**: `SELECT b.* FROM badges b WHERE b.condition_type = :type AND
     (b.condition_value->>'value')::numeric <= :metric AND NOT EXISTS (SELECT 1 FROM user_badges ub
     WHERE ub.user_id = :userId AND ub.badge_id = b.id)` — 충족했는데 미보유인 티어 전부(FR-4).
     0건이면 즉시 빈 리스트(대부분의 업로드가 이 경로 — 판정 비용 = 인덱스드 카운트 + 이 SELECT).
  2. **지급**: 후보 id들로 `INSERT INTO user_badges (user_id, badge_id, notified_at)
     VALUES (:userId, :badgeId, now()) ON CONFLICT DO NOTHING` — 동시 요청이 같은 후보를 계산해도
     PK가 최후 방어선(FR-3·NFR 데이터 정합). 동기 지급이므로 `notified_at = now()`(§D8).
  3. 후보 리스트를 그대로 반환 — 경합에서 상대 트랜잭션이 먼저 넣은 극단 케이스는 응답에 한 번 더
     실릴 수 있을 뿐(중복 row는 불가) — 무해, 수용.
  - `BadgeConditionType` enum(badge/entity — PascalCase/SCREAMING_SNAKE) 6종(MISSION_COUNT 포함,
    CHECK와 동기).
- **엔티티 매핑**: `Badge` = id·code·name·description·iconUrl·conditionType 매핑,
  **conditionValue 미매핑**(판정 전부 native — Grid.geom·missions.path 선례. JSONB 타입 매핑 의존성
  회피). `UserBadge` = 복합 PK(`UserBadgeId`)·earnedAt·notifiedAt·featuredRank —
  `@NoArgsConstructor(PROTECTED)`, UserGrid 패턴.
- **기각**: 단문 `INSERT…SELECT…RETURNING`(1왕복) — Spring Data `@Modifying`이 결과 행을 못 돌려줘
  비표준 우회가 필요하다. 2단이 관례적이고 테스트 가능, 왕복 1회 차이는 무의미. / 전 축 뱃지 전수
  판정 — FR-2 명시 금지.

### D6 — 대표 뱃지 = `user_badges.featured_rank SMALLINT`(1·2) + **교체(replace-set) API 단일 엔드포인트**, DB partial UNIQUE가 2개 상한 강제 (FR-8 저장 구조·API 확정)

- **결정**:
  - **저장**: `user_badges`에 `featured_rank SMALLINT NULL` 추가 — non-null = 대표, 값 = 표시 순서(1·2).
    `CHECK (featured_rank IN (1, 2))` + **partial UNIQUE `(user_id, featured_rank) WHERE featured_rank
    IS NOT NULL`** — 사용자당 rank 1·2 각 1개, 즉 **최대 2개를 DB가 물리 강제**(NFR 인가·정합의 스키마
    버전. 앱 코드 카운트 검사 불요 — DB 제약 > 앱 코드).
  - **API**: `PUT /api/badges/featured`, body `{"badgeIds": [3, 7]}` — **집합 교체** 시맨틱(멱등).
    배열 순서 = featured_rank 순서. 빈 배열 `[]` = 전부 해제. 선택/해제/순서변경이 엔드포인트 하나로
    끝난다. 서비스: `pg_advisory_xact_lock('badge_featured:' || userId)`(155 선례 패턴) → 전 해제
    UPDATE → 요청 순서대로 rank 1·2 UPDATE(보유 검증 겸함 — affected 0 = 미보유 → 7403 롤백).
  - **검증**: `@Size(max = 2)` → 초과는 global 400. 중복 badgeId → 7400. 미보유(user_badges에 없음,
    미존재 badge 포함) → 7403 — 존재/보유를 구분하지 않는다(남의 획득 여부 탐색 방지 겸 단순화).
- **근거**: 개별 지정/해제 2 엔드포인트는 "2개 상한 + 순서"를 클라이언트-서버 왕복 상태머신으로
  만든다(선택 중 상한 초과 처리, 순서 변경 = 해제+재지정 2호출). 교체 시맨틱은 요청 자체가 ≤2라 상한
  경합이 구조적으로 없고, FE의 "대표 뱃지 편집 → 저장" UX와 1:1이다.
- **경로 `/api/badges`**: badge 도메인 리소스 루트 신설. 위키 draft의 `GET /api/collections/badges`
  계획과 무관 — 조회 경로는 MSG-201이 그때 확정(경로 접두사가 소유권·배치를 강제하지 않음, 127 선례).
- **기각**: 별도 `user_featured_badges` 테이블 — 획득 뱃지의 속성일 뿐인데 테이블·FK·조인이 늘어난다.
  `users`에 컬럼 2개 — 뱃지 도메인 데이터가 user로 새고 보유 검증이 FK로 안 걸린다.

### D7 — `BadgeErrorCode` = **7xxx 대역 신설**, 상수 2개

- **결정**: `badge/exception/BadgeErrorCode` —
  `INVALID_FEATURED_BADGES(7400, BAD_REQUEST, "대표 뱃지 요청이 올바르지 않습니다")`(중복 badgeId),
  `BADGE_NOT_EARNED(7403, FORBIDDEN, "획득한 뱃지만 대표로 설정할 수 있습니다")`.
- **근거**: 사용 중 대역 1xxx~6xxx 실사(선행 상태 표) — 다음 빈 대역 7xxx. 위키의 도감 5xxx 제안은

### D8 — 미확인 플래그 = `user_badges.notified_at TIMESTAMP NULL` — null = 미확인 (FR-9 비동기 지급분)

- **결정**: 동기 지급(업로드 응답 동봉) = `now()` 기록, 소급 지급(V9·향후 시딩 마이그레이션) = NULL.
  **확인 처리(NULL → 시각 기록)는 MSG-201 조회 API 소관** — 이 티켓은 컬럼과 기록 시맨틱까지.
- **기각**: `is_new BOOLEAN` — 언제 확인했는지가 사라진다. 타임스탬프면 boolean을 파생(`IS NULL`)할 수
  있고 역은 불가, 컬럼 수는 같다.

### D9 — 소급 지급 = **시딩 마이그레이션 동반 set-based SQL 블록** (FR-10 "절차 형태" 확정)

- **결정**: 소급은 별도 잡/배치가 아니라 **뱃지를 시딩하는 그 마이그레이션 파일 안의 set-based
  `INSERT…SELECT…ON CONFLICT DO NOTHING` 블록**으로 한다. V9가 활성 3축을 소급하고(§V9 SQL),
  이후 새 뱃지 시딩(V10+)도 같은 패턴을 복제한다 — "상시 규칙"의 형태 = 마이그레이션 템플릿.
- **근거**:
  1. **원자성**: 시딩과 소급이 한 마이그레이션 트랜잭션 — "뱃지는 있는데 소급 전" 중간 상태가 배포에
     존재하지 않아, 기존 사용자가 다음 행동 때 하위 티어를 우르르 받는(FR-4가 처리하긴 하는) 어색한
     경험 자체가 없다.
  2. **`ON CONFLICT DO NOTHING`이라 재실행 안전** — 실패 복구 시 같은 SQL을 다시 돌려도 무해(멱등).
  3. 재실행 가능 잡(어드민 엔드포인트/CommandLineRunner)은 트리거·인가·플래그 게이트가 따라붙는다 —
     시딩 자체가 마이그레이션인데 소급만 잡으로 빼면 실행 순서 보장도 스스로 해야 한다. YAGNI.
- **경계**: 소급은 기존 데이터로 판정 가능한 축만(FR-10) — 활성 3축은 user_grids·videos·region_stats로
  전부 가능. SPECIAL은 뱃지별 규칙을 그 시딩 마이그레이션에 개별 명시(§D2).
- `ponytail: 사용자 수가 커져 마이그레이션 내 소급 풀스캔이 배포 시간을 위협하면 그때 비동기 잡으로 승격 — MVP 규모(집계 3개)엔 set-based 한 방이 옳다.`

### D10 — 시딩 수치·이름 = BE 제안값으로 확정 기술, 변경은 SQL 값 수정 1곳 (PRD §8 컨펌 병행 대응)

- **결정**: 아래 §V9 SQL의 11종(수치 = PRD 표의 BE 제안값, name/description = 본 스펙 제안)으로
  시딩한다. 팀 컨펌으로 수치·문구가 바뀌면 **V9 배포 전엔 V9 값 수정, 배포 후엔 UPDATE 마이그레이션** —

  **NULL 시딩**(에셋 확정 시 UPDATE — Open Q1).

### 1. 판정·지급 엔진 (`BadgeAwardService.award` — badge/service, §D5)

```
award(userId, type, metric):
  candidates = badgeRepository.findEligible(type, metric, userId)   -- 충족 & 미보유 (native, 아래)
  if empty → []                                                     -- 지배적 경로, 쿼리 1회로 종료
  for c in candidates:
      userBadgeRepository.insertIgnoreConflict(userId, c.id)        -- ON CONFLICT DO NOTHING, notified_at = now()
  return candidates → EarnedBadgeResponseDto 매핑
```

```sql
-- findEligible (BadgeRepository, native)
SELECT b.id AS "badgeId", b.code, b.name, b.description, b.icon_url AS "iconUrl"
FROM badges b
WHERE b.condition_type = :type
  AND (b.condition_value->>'value')::numeric <= :metric
  AND NOT EXISTS (SELECT 1 FROM user_badges ub WHERE ub.user_id = :userId AND ub.badge_id = b.id)
ORDER BY (b.condition_value->>'value')::numeric
```

```sql
-- insertIgnoreConflict (UserBadgeRepository, @Modifying native) — PK가 FR-3 최후 방어선
INSERT INTO user_badges (user_id, badge_id, notified_at)
VALUES (:userId, :badgeId, now())
ON CONFLICT DO NOTHING
```

### 3. 대표 뱃지 교체 (`BadgeFeaturedServiceImpl` — §D6)

```
@Transactional replaceFeatured(userId, badgeIds):
  badgeIds 중복 검사 → 7400
  userBadgeRepository.acquireFeaturedLock(userId)          -- pg_advisory_xact_lock('badge_featured:'||userId)
  userBadgeRepository.clearFeatured(userId)                -- UPDATE … SET featured_rank = NULL WHERE user_id
  for (rank = 1..N):
      updated = userBadgeRepository.setFeaturedRank(userId, badgeIds[rank-1], rank)
      if updated == 0 → throw 7403                         -- 미보유 (트랜잭션 롤백 — 부분 적용 없음)
  return 적용 결과 (badges 조인 rank 순)
```

  교체를 사용자 단위 직렬화(경합 시 unique 위반 500 방지 — 155 lock 선례).
