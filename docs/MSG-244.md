# MSG-244: [BE] prod Redis 설정 정합 — 포트 6380·비밀번호 기본값 + 헬스체크 비번 전달

**Owner**: 인프라(공통) — 도메인 코드 변경 없음, 설정 파일만

## 개요

Codex 교차 리뷰(2026-07-24)에서 발견된 prod Redis 설정 결함 2건(P1+P2)을 수정한다.
prod 앱 프로파일과 `docker-compose.server.yml`의 redis-prod 정의가 서로 어긋나 있어,
이대로 prod 앱을 띄우면 인증 전체(토큰 검증·로그인·재발급 — MSG-135의
`RedisRefreshTokenStore`/`RedisInvalidatedTokenStore`)가 실패한다.

## 배경 · 목표

- EC2 1대에서 dev/prod를 컨테이너로 격리 운용 중 (멘토 지시, 2026-07-16 멘토링 —
  redis-dev=6379 비밀번호 없음, redis-prod=6380 requirepass 필수). 팀 위키
  `05-meetings/2026-07-16 박원형 멘토 멘토링.md`와 대조 완료, 상충 없음.
- 이번 수정은 그 격리 원칙을 **앱 설정까지 관철**하는 선행 정합이다. prod 앱 가동
  (인스턴스 확장) 전에 잡아야 한다.

## 성공 기준

1. prod 프로파일이 기본값만으로 dev Redis(6379)에 붙을 수 없다 — 포트 기본 6380,
   비밀번호 미설정 시 기동 실패(fail-fast).
2. `PROD_REDIS_PASSWORD`만 주입하면 redis-prod 컨테이너가 healthy로 전환된다.

## 결함 지점

| # | 파일:라인 | 결함 |
|---|---|---|
| 1 | `src/main/resources/application-prod.yml:23` | `port: ${REDIS_PORT:6379}` — 기본값이 dev Redis 포트. env 미주입 시 dev Redis에 접속 |
| 2 | `src/main/resources/application-prod.yml:20-29` | `spring.data.redis.password` 항목 자체가 없음 — requirepass 걸린 redis-prod에 NOAUTH 실패 |
| 3 | `docker-compose.server.yml:75` | 헬스체크 `redis-cli -a "$$PROD_REDIS_PASSWORD" ping` — `$$`는 compose 보간 이스케이프라 **컨테이너 셸**이 확장하는데, 그 변수를 service environment에 안 넘겨 빈 비밀번호로 인증 → 정상 컨테이너가 영구 unhealthy |

## 수정 내용

### 1. application-prod.yml — Redis 블록

```yaml
  # Redis — EC2 docker-compose.server.yml 의 fillmap-redis-prod (6380, requirepass 필수)
  data:
    redis:
      host: ${REDIS_HOST}
      port: ${REDIS_PORT:6380}
      password: ${REDIS_PASSWORD}
      timeout: 2000ms
      lettuce: (기존 유지)
```

- `REDIS_PASSWORD`에 **기본값을 두지 않는다** — 미설정 시 placeholder 해석 실패로 기동
  즉시 드러나게 한다. 같은 파일의 `JWT_REFRESH_SECRET`(MSG-135)·`S3_BUCKET_VIDEO` 선례와 동일 원칙.
- 기존 주석 "Redis (ElastiCache) — 활성화는 추후"는 사실과 다름(MSG-135부터 토큰 저장소로
  실사용, 실제 배포는 EC2 컨테이너) — 수정 라인에 걸쳐 있으므로 함께 갱신.

### 2. docker-compose.server.yml — redis-prod 헬스체크

```yaml
    healthcheck:
      test: [ "CMD", "redis-cli", "-a", "${PROD_REDIS_PASSWORD}", "ping" ]
```

**선택안: 호스트 값 보간** (environment 명시 전달안 기각). 근거:

- 이 compose 파일의 기존 스타일이 전부 호스트 보간이다 — 같은 서비스의 `command`(69행)가
  이미 동일 변수를 `${PROD_REDIS_PASSWORD:?...}`로 보간하고, postgres-dev/prod 헬스체크도
  `${DEV_DB_USER:-dev}` 등 호스트 보간을 쓴다.
- environment 전달안은 라인이 늘고 비밀번호가 컨테이너 env에 중복 노출된다 —
  이미 `command`에 노출돼 있어(둘 다 `docker inspect`로 보임) 보안 이득도 없다.
- `CMD` exec form은 redis-dev 헬스체크(60행) 선례를 따르며, 셸 파싱이 없어
  비밀번호에 셸 특수문자가 있어도 안전하다 (`CMD-SHELL` + 따옴표 조합보다 견고).
- `redis-cli -a`의 stderr 경고("Using a password...")는 무해 — 헬스체크는 exit code로 판정.

## 테스트 시나리오

설정 전용 티켓 — JUnit 테스트 없음, 검증은 렌더 확인 + 스모크로 대체.

### 로컬에서 가능

1. **compose 렌더 확인**:
   `PROD_DB_PASSWORD=x PROD_REDIS_PASSWORD=secret123 docker compose -f docker-compose.server.yml config`
   → redis-prod healthcheck에 `secret123`이 리터럴로 보간되고 `$PROD_REDIS_PASSWORD`
   리터럴이 남지 않는지 확인.
2. **redis-prod 단독 healthy 재현**:
   `PROD_REDIS_PASSWORD=secret123 docker compose -f docker-compose.server.yml up -d redis-prod`
   → `docker inspect -f '{{.State.Health.Status}}' fillmap-redis-prod`가 healthy 전환
   (수정 전 코드로는 unhealthy 재현 → 수정 후 healthy 확인).
3. **prod 프로파일 부팅 스모크**:
   - `REDIS_PASSWORD` **미주입** 부팅 → placeholder 해석 실패로 즉시 기동 실패 (fail-fast 확인).
   - 전체 env 주입(DB는 로컬 postgres-prod 5433 활용, `REDIS_HOST=localhost`,
     `REDIS_PORT` 미지정 → 기본 6380) 부팅 → `GET /actuator/health`에서 redis `UP`
     (actuator 의존성 있음 — Redis health indicator 자동 활성).

### EC2에서만 가능

4. `.env`의 `PROD_REDIS_PASSWORD`로 redis-prod 재생성 → healthy 전환 확인.
5. prod 앱 가동 시점(인스턴스 확장 후): health redis `UP` + 로그인·토큰 재발급·로그아웃
   플로우 정상 (NOAUTH 미발생).
