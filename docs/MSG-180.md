# MSG-180: 알림 설정 API — 카테고리별 수신 on/off + 발송 필터 완성

**Owner**: B

> PRD(정본): `docs/prd/MSG-178-prd.md` (상태: 검토됨) — 알림 묶음 4티켓 공유 PRD. 이 스펙은
> **FR-7(카테고리별 수신 on/off 저장·조회, 기본 전부 on = opt-out) · FR-8(off 카테고리 발송
> 단계 필터)** 만 다룬다. FR-8의 발송 쪽 절반(컨슈머의 isEnabled 조회 → SKIPPED "PREF_OFF"
> 전이)은 MSG-179가 이미 구현 완료(docs/MSG-179.md D7) — 180의 몫은
> `NotificationPreferenceServiceImpl`(현재 무조건 true 스텁) 내부를 실제 설정 조회로 교체 +
> 설정 저장/조회 REST API + 저장 스키마 신설이다. **인터페이스 시그니처와 컨슈머 호출부는
> 무변경**(D7 규약).
> 카테고리 = BADGE·HOTZONE·REMIND 3종 고정(PRD FR-7 · `NotificationCategory` enum 실측 일치).
> 친구 활동 알림은 PRD 비목표 — 이 스펙에서 카테고리를 추가하지 않는다.

## 개요

IA "설정 > 알림 설정" 화면의 백엔드. 사용자가 카테고리별 수신 여부를 저장·조회하고, off
카테고리의 알림은 컨슈머가 발송 전에 걸러 SKIPPED로 기록한다(이벤트 기록은 남되 발송 안 함).

Owner 판정: `com.msg.fillmap.notification.*` 단독 확장. infrastructure.md 목표 구조에는
notification이 없으나 CLAUDE.md 협업 원칙이 `com.msg.fillmap.notification.*`을 Owner B로
등재(MSG-178) — **B** 확정. Owner A 도메인 접점 없음.

## 배경 · 목표

- 179 파이프라인은 설정 필터 지점(D7)을 인터페이스로 뚫어 두고 전부-허용 스텁으로 돌고 있다 —
  사용자가 알림을 끌 방법이 없다. 알림 피로는 앱 삭제로 이어지는 최악의 리텐션 신호라
  opt-out 창구는 발송 트리거(MSG-181)보다 먼저 있어야 한다.
- 목표: 설정 저장·조회 API + 스텁의 실구현 교체로 FR-7·FR-8을 종결한다.

## 성공 기준

1. **기본 전부 on** (FR-7): 설정을 한 번도 만지지 않은 사용자(저장 행 0)는 GET에서 3종 모두
   `enabled: true`, `isEnabled`도 전부 true — opt-out 모델.
2. **저장·조회** (FR-7): PATCH로 바꾼 상태가 GET과 `isEnabled`에 즉시 반영된다. 같은 값
   재저장은 멱등(오류 없이 같은 상태).
3. **발송 필터 종결** (FR-8): off 사용자의 해당 카테고리 알림이 컨슈머에서 SKIPPED
   "PREF_OFF"로 종결된다 — 179의 배선 + 이 티켓의 실구현으로 요구사항 완성.
4. **접점 무변경**: `NotificationPreferenceService.isEnabled` 시그니처와
   `NotificationConsumer` 호출부가 diff에 나타나지 않는다(D7 규약).

## 결정

### D1. 저장 모델 — off 행만 저장 (`notification_opt_outs`, 행 부재 = on)

"기본 전부 on"을 표현하는 세 가지를 대조해 **off 행만 저장**으로 확정:

- **off 행만 저장 (채택)**: (user_id, category) 행 존재 = 그 카테고리 수신 거부. 기본값이
  스키마에 내장(행 부재 = on)돼 시딩·백필이 0이고, 카테고리가 늘어도 마이그레이션 없이 자동
  on(opt-out 정합). `isEnabled` = PK 단건 exists 1문장.
- 가입 시 3행 시딩: 가입 훅 + **기존 유저 백필** 2개 코드 경로 — PRD 비기능 "기존 테이블
  소급 없음"과 충돌 방향이라 기각.
- enabled BOOLEAN 행 upsert: "명시적 on"을 표현할 수 있으나 현 요구사항(전부 opt-out)에
  쓸모가 없다 — 기각(YAGNI).

**선례 실측**: 이 레포는 "행 부재 = 초기 상태"가 관례다 — grids lazy insert(glossary),
streaks(첫 업로드 이벤트 때 upsert — 행 부재 = 스트릭 0), push_tokens(행 부재 = 토큰 없음).
테이블명은 행의 의미 그대로 `notification_opt_outs`(명사 복수 소문자) — `_preferences`로
지으면 "행 = 설정값"으로 오독된다(행은 거부 표식이다).

### D2. `V22__notification_opt_outs.sql`

**실측**: develop 마이그레이션은 V21(`V21__notifications.sql`)까지 — **V22 확정**.
⚠️ 구현 PR 직전과 **PR 열림~머지 창**에 develop을 재확인할 것 — V16 선점 사건에 이어
MSG-179는 "PR 직전 재확인"을 지켰는데도 열림~머지 사이에 V20을 선점당해 V21로 리네임했다.

```sql
-- 알림 수신 거부 (MSG-180). 행 존재 = 해당 카테고리 off, 행 부재 = on (FR-7 opt-out 기본 전부 on).
CREATE TABLE notification_opt_outs (
	user_id    BIGINT      NOT NULL REFERENCES users(id) ON DELETE CASCADE,
	category   VARCHAR(10) NOT NULL,
	created_at TIMESTAMP   NOT NULL DEFAULT CURRENT_TIMESTAMP,

	PRIMARY KEY (user_id, category),
	CONSTRAINT chk_notification_opt_outs_category CHECK (category IN ('BADGE', 'HOTZONE', 'REMIND'))
);
```

- 복합 PK (user_id, category): 서러게이트 id 제거 관례(V1 v6 설계 — user_grids·user_badges·
  friendships 동형). CHECK 제약은 V21 chk_notifications_category와 동일 관례.
- FK CASCADE: push_tokens·notifications 선례 — 계정 삭제 시 정리 코드 0줄.
- **추가 인덱스 없음**: PK가 user_id 선두라 isEnabled 단건 exists · GET 사용자 목록 ·
  CASCADE 삭제를 전부 커버한다 (V21 idx_notifications_user는 FK가 인덱스 선두가 아니어서
  따로 만든 경우 — 여긴 해당 없음).
- created_at: 전 테이블 공통 관례 + "언제 껐나" 운영 신호. updated_at은 없다 — 행은
  생성/삭제만 되고 갱신되지 않는다.

### D3. API 형상 — GET 조회 + PATCH 단건 토글

**실측 선례**: `VideoController`의 `PATCH /{videoId}/visibility`가 정확히 동형이다 —
단일 값 전환, 멱등("같은 값 재전환은 멱등하게 성공"), 변경 후 상태 반환. 설정 화면의
인터랙션(토글 스위치 1개 조작 = 요청 1개)과 1:1이고, 구현이 쿼리 1문장이라 PUT 전체
교체(서버 diff 계산 필요)보다 단순하다. 컨트롤러는 `PushTokenController` 관례 축자 —
`@AuthenticationPrincipal AuthPrincipal` 주입, `SuccessResponse` 반환, 얇은 3-layer.

`category` 경로 변수는 String으로 받아 **서비스에서** `toUpperCase(Locale.ROOT)` 파싱
(`PushTokenServiceImpl.parsePlatform` 선례 축자 — Jackson/컨버터 400 대신 도메인 코드,
터키어 로케일 차단 포함). 실패 시 10420(D4).

**SecurityConfig 무변경**: `anyRequest().authenticated()`가 기본이라 신규 경로 등록이
필요 없다(permitAll 목록에 안 넣는 것이 곧 인증 필수 — PushTokenController 선례 실측).

### D4. developCode — `INVALID_CATEGORY(10420)` 신설

**실측**: notification 대역은 10xxx(response-pattern.md 정본 표 등재 완료),
`NotificationErrorCode`에는 10400 INVALID_PLATFORM 하나뿐 — 다음 번호로 **10420** 확정.
400류 두 번째부터 42x를 쓰는 관례(video 3420 INVALID_VISIBILITY — 같은 "허용 목록 외
문자열" 계열, auth 2422)를 따르고, 10401은 401(UNAUTHORIZED) 연상이라 피한다.

```java
INVALID_CATEGORY(10420, HttpStatus.BAD_REQUEST, "category 는 BADGE, HOTZONE, REMIND 중 하나여야 합니다"),
```

구현 시점에 `NotificationErrorCode` 현재 값을 재확인한다(병렬 레인 방어).

### D5. 서비스 — 기존 `NotificationPreferenceService` 확장, Impl 실구현 교체

별도 서비스를 만들지 않는다 — 도메인 언어가 같고(수신 설정), PushTokenService(등록/해제
한 인터페이스) 관례와 일치. **isEnabled 시그니처는 그대로 두고** REST용 메서드 2개만 추가:

```java
public interface NotificationPreferenceService {

	/** 사용자가 이 카테고리 알림을 받는지. (기존 — 시그니처·컨슈머 호출부 무변경, 179 D7) */
	boolean isEnabled(Long userId, NotificationCategory category);

	/** 카테고리 3종 전체의 수신 상태 — 저장 행이 없는 카테고리는 on (FR-7 opt-out). */
	NotificationPreferenceResponseDto getPreferences(Long userId);

	/** 단건 토글 (멱등) — category 는 대소문자 무시 파싱, 목록 외면 10420. 변경 후 전체 상태 반환. */
	NotificationPreferenceResponseDto update(Long userId, String category, boolean enabled);
}
```

Impl 교체 내용:

- `isEnabled` = `!optOutRepository.existsById(new NotificationOptOutId(userId, category))` —
  파생 쿼리 없이 JpaRepository 기본 메서드, PK 단건 히트.
- `getPreferences` = 사용자 off 행 조회 후 `NotificationCategory.values()` 순회 합성
  (enum 선언 순 BADGE·HOTZONE·REMIND 고정 — CHECK·FE 표시 순과 일치).
- `update` = 파싱 → off면 `INSERT ... ON CONFLICT DO NOTHING`, on이면 `DELETE` (둘 다
  native 1문장·멱등 — PushTokenRepository.upsert/deleteByTokenAndUser 선례) → 변경 후
  상태 반환. `@Transactional`(modifying native 요건 — PushTokenServiceImpl 선례).

**캐시 없음 — DB 조회 확정 (실측 근거)**: `NotificationConsumer.consume()`은 알림 1건당
isEnabled를 정확히 1회 호출하고, 컨슈머는 단일 파티션·단일 인스턴스에 `max.poll.records=10`
이다. 발송량 자체가 사용자·일 상한(HOTZONE 1·REMIND 1, BADGE 희소 — FR-12)으로 눌려 있어
초당 수십 건 규모도 안 된다. PK 단건 exists에 캐시를 얹을 이유가 없다. 호출 문맥:
컨슈머는 쓰기만 TransactionTemplate 개별 트랜잭션으로 감싸므로 isEnabled는 비트랜잭션
컨텍스트의 자동커밋 단문 SELECT — 트랜잭션 전파 이슈 없음.

## API 명세

공통: 인증 필수(Bearer — SecurityConfig 기본), 응답은 `ApiResponseDto` 래핑
(`SuccessResponse.of(...)`), 실패는 `ApiException` → GlobalExceptionHandler.

### 1. 알림 설정 조회

`GET /api/notifications/preferences`

성공 200:

```json
{
	"developCode": 200,
	"message": "성공",
	"data": {
		"preferences": [
			{ "category": "BADGE", "enabled": true },
			{ "category": "HOTZONE", "enabled": false },
			{ "category": "REMIND", "enabled": true }
		]
	}
}
```

- 항상 3종 전부 반환(저장 행 없는 카테고리는 true 합성) — FE는 부재 처리 불요.

### 2. 카테고리 수신 토글

`PATCH /api/notifications/preferences/{category}`

- `category`: BADGE·HOTZONE·REMIND (대소문자 무시)
- body: `{ "enabled": false }`

| 케이스 | 응답 |
|---|---|
| 성공 (같은 값 재전환 포함 — 멱등) | 200, data = 변경 후 전체 상태(조회와 동일 DTO) |
| category 목록 외 (`FRIEND` 등) | 400 · developCode **10420** INVALID_CATEGORY |
| enabled 누락/null | 400 · 공통 BAD_REQUEST (`@Valid` `@NotNull`) |
| 미인증 | 401 · 공통 UNAUTHORIZED |

DTO (컨벤션: XxxRequestDto/XxxResponseDto, 파일명 일치):

```java
public record NotificationPreferenceUpdateRequestDto(@NotNull Boolean enabled) { }

public record NotificationPreferenceResponseDto(List<CategoryPreferenceDto> preferences) {
	public record CategoryPreferenceDto(NotificationCategory category, boolean enabled) { }
}
```

- 요청의 category는 String 경로 변수(도메인 코드 파싱 — D3), 응답의 category는 enum 직렬화
  (출력엔 파싱 실패가 없다 — PushTokenRequestDto의 "String으로 받는 이유" 주석과 같은 논리).

## 도메인 로직

```text
[설정 화면]                                  [발송 파이프라인 — 179 기구현]
GET  preferences ─ off 행 조회 + 3종 합성      컨슈머 consume(id)
PATCH {category} ─ off: INSERT ON CONFLICT       └ isEnabled(userId, category)   ← 이 티켓이 실구현
                 ─ on:  DELETE                        └ false → SKIPPED "PREF_OFF" (FR-8, 기록은 잔존)
```

- 용어(glossary): HOTZONE = "핫구역". off는 **발송만** 막는다 — outbox 기록(방문·뱃지 등
  이벤트의 흔적)은 SKIPPED 상태로 남아 운영 집계에 잡힌다(FR-8 "기록은 남되 발송 안 함").
- 판정은 발송 시점 실시간 — 기록 시점(record)에는 설정을 보지 않는다. off 중 쌓인 알림이
  on 복귀 후 재발송되는 일은 없다(이미 SKIPPED 종결 — 컨슈머 멱등 2차 방어와 동일 원리).
