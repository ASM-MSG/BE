# MSG-128: 관측 스택 구축 — 부하테스트 기반 A/B 판정

**Owner**: A (KangJeong) — 인프라. 부모 에픽: MSG-49 "시스템 기반 인프라"

> 소비처: MSG-73(viewport 조회 전략 A/B) 최종 채택을 **실측 부하테스트**로 결정하기 위한 관측.
> 관련: MSG-73(relates) · k6 스크립트 `load-test/k6/viewport-ab-benchmark.js`(이미 있음).
> ⚠️ 앱 서버는 **t3.small(2 vCPU · 2GB RAM)** — 관측 스택을 여기 상시로 올리지 않는다(§핵심 결정).

---

## 개요

MSG-73의 viewport 조회는 접근 A(정수 범위 스캔·btree)와 B(GIST 공간쿼리)를 둘 다 구현하고
`?strategy=A|B`로 열어뒀다. 지금까지의 비교는 **EXPLAIN(ANALYZE) 단일 실행**뿐이라 잠정치다
(트랜잭션 내 시드·워밍 캐시·단일 유저·동시성 미측정). **실측 부하테스트 + 관측**으로 최종 채택을 정한다.

이 티켓은 그 부하테스트를 **관측 가능하게** 만드는 스택을 구축한다.

```
[대상: t3.small · 상시 경량]              [관측: 대상 밖 · 부하테스트 때만]
Spring app ─ /actuator/prometheus ─┐
PostgreSQL ─ postgres_exporter ────┼─(원격 scrape)→ Prometheus → Grafana(A/B 대시보드)
k6 (대상 밖) ─(load)→ 앱 ───────────┘  k6 ─(remote_write)→ Prometheus
```

## 핵심 결정

| # | 항목 | 결정 |
|---|---|---|
| D1 | 스택 성격 | **상시 운영 모니터링이 아니라 부하테스트용 임시 스택.** 끝나면 내린다. 상시 관측·알림(Alertmanager)은 스코프 밖 |
| D2 | 배치 | **관측(Prometheus/Grafana)·부하생성(k6)은 대상 서버 밖.** t3.small엔 경량(Actuator + postgres_exporter)만 상시. 이유: ①2GB에 다 올리면 빠듯 ②**부하 중 같은 박스의 관측이 자원을 뺏어 측정을 왜곡(관측자효과)** |
| D3 | 실행 위치 | **두 가지 다 준비해 비교한다** — (a) **로컬**(빠른 반복·개발용, 단 인터넷 경유라 네트워크 지연이 섞임) (b) **같은 AWS 리전 임시 EC2**(깨끗한 측정, 채택 근거용). 같은 docker-compose로 둘 다 |
| D4 | 시드 방식 | EXPLAIN 때의 "트랜잭션 내 시드" caveat를 극복한다 — **커밋된 데이터 + `VACUUM ANALYZE`** 후 부하. 부하는 실제 HTTP(`/api/grids?...&strategy=`) 경유(쿼리 직접 아님) |
| D5 | 메트릭 소스 | 앱 Actuator/Micrometer(HTTP 지연·Hikari·JVM) + postgres_exporter/pg_stat_statements(쿼리시간·인덱스 스캔) + k6(RPS·p95/p99·에러율) → 한 Prometheus로 모음 |

## 산출물

### A. 앱 (레포 커밋 · t3.small 상시 · 경량)

1. `build.gradle`: `org.springframework.boot:spring-boot-starter-actuator`, `io.micrometer:micrometer-registry-prometheus`.
2. `application.yml`: `/actuator/prometheus` 노출.
   ```yaml
   management:
     endpoints.web.exposure.include: health,info,prometheus
     metrics.tags.application: fillmap
     endpoint.prometheus.access: read_only
   ```
3. `global/config/SecurityConfig`: `/actuator/health`·`/actuator/prometheus` 접근 허용 규칙.
   - ⚠️ `SecurityConfig`는 Owner B 소유(global) — **최소 변경 + 사전 공유**(§계약 변경). prod에선 IP 제한/basic auth 권장(스코프 노트).

### B. 관측 스택 (레포엔 구성만 · 실행은 부하테스트 때)

`monitoring/` 디렉토리 신설:
- `monitoring/docker-compose.yml` — Prometheus + Grafana + postgres_exporter (+ 필요 시 node_exporter).
- `monitoring/prometheus/prometheus.yml` — scrape 대상: 앱 `:8080/actuator/prometheus`, `postgres_exporter:9187`. k6 remote-write receiver 활성화.
- `monitoring/grafana/provisioning/` — datasource(Prometheus) + **대시보드(A/B 비교)**: strategy별 p95/p99·RPS·에러율(k6), DB 쿼리시간·인덱스 스캔, 앱 HTTP·Hikari.
- 환경변수로 **대상 주소**(로컬 `host.docker.internal` vs 임시 EC2 앱 사설IP) 전환.
- k6 실행: `k6 run --out experimental-prometheus-rw load-test/k6/viewport-ab-benchmark.js`.

### C. 문서 (runbook)

`monitoring/README.md` — 로컬/임시 EC2 각각 기동 절차, 시드(커밋+VACUUM ANALYZE) 방법, k6 실행, Grafana 확인, A/B 판정 → 결과를 `docs/MSG-73` 작업 로그/블로그에 반영.

## 측정·판정 기준

동일 시드·동일 뷰포트 분포에서 `strategy=A`와 `strategy=B`를 각각 부하:
- **처리량(RPS)** · **지연 p95/p99** · **에러율** (k6) — 1차 판정
- **DB 쿼리 실행시간·인덱스 스캔 종류**(btree vs GiST, pg_stat_statements) — 원인 규명
- **앱 HTTP 지연·Hikari 풀 포화·CPU**(Actuator) — 병목 위치
- 조건 변주: 뷰포트 크기(줌), 다중 사용자 분포, 콜드/워밍 → EXPLAIN caveat 극복

→ 낮은 지연·높은 처리량 쪽을 기본 경로로 채택하고 `?strategy` 고정/제거. 근거를 블로그 "본선" 섹션으로.

## 검증

1. **로컬**: `monitoring/docker-compose up` → Prometheus targets에서 앱·exporter `UP` → Grafana 대시보드에 메트릭 표시.
2. 앱 `/actuator/prometheus`가 200 + 메트릭 노출(SecurityConfig 통과) 확인.
3. 커밋된 데이터 시드 + `VACUUM ANALYZE` 후 `k6 run` → Grafana에서 strategy A/B의 p95/RPS가 실시간으로 구분되어 보임.
4. **임시 EC2**(같은 리전): 동일 compose로 재현, 네트워크 오염 없는 수치 확보.
5. A/B 판정 결과를 `docs/MSG-73` 작업 로그·블로그에 기록.
