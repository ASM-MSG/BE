# MSG-154: regions 행정동 시딩 파이프라인

**Owner**: A (`com.msg.fillmap.region.*`) — 순수 Owner A(KangJeong). 계약 인터페이스 변경 없음(§계약 변경 참조).

> 지역별 수집률(`GET /api/regions/stats`)·행정동 검색의 **선행 데이터 과제**. `regions` 테이블이 비면
> Region API 전체가 동작하지 않는다. 이 티켓은 **엔티티 + 리포지토리 + 시더**까지다 — **API·컨트롤러는 없다**(MSG-155/156 소관).
> `regions` 테이블·인덱스(`idx_regions_boundary` GIST, `idx_regions_parent`)는 `V1__init.sql`에 **이미 존재**하므로 Flyway 마이그레이션은 없다.
> glossary상 '수집률(Progress Rate)'은 원래 Phase 2였으나 PO 결정으로 MVP 범위에 편입(Figma "수집률 서울 34%" 근거). 단 이 티켓은 수집률 산출이 아니라 그 **분모 데이터(`total_grid_count`)의 적재**만 담당한다.

---

## 개요

행정동 경계(GeoJSON)를 `regions` 테이블에 1회 시딩해, 이후 수집률·행정동 검색 API가 읽을 마스터 데이터를 확보한다.
행정동별 `boundary_geom`(MULTIPOLYGON)과 그 안에 들어가는 100×100m 격자 수(`total_grid_count`)를 **시딩 시 1회 계산**해 저장한다.

```
[MSG-154] GeoJSON(전국 행정동 경계) ──시더──▶ regions row × 약 3,558
            adm_cd2 → region_code, adm_nm → region_name,
            geometry → boundary_geom, ST_Area(boundary_geom)/셀면적 → total_grid_count
[MSG-155/156] regions 를 읽어 수집률/검색 API 제공        (이 티켓 밖)
```

멘토 피드백(Confluence 'DB')과 기존 ADR에 일치한다: **geospatial 연산은 실시간 트랜잭션 경로에서 금지, 사전 레이블링**.
영상의 행정동 판정은 업로드 시 1회(`videos.region_code`, MSG-66 완료), 격자 수 산출도 시딩 시 1회다.
region↔grid **다대다 매핑 테이블은 만들지 않는다**(현 구조 유지: 영상이 `region_code`를 직접 보유).

## 배경 · 목표

- **사용자/제품 관점**: "강남구 25% 수집", "서울 34%" 같은 지역 수집률·행정동 검색은 행정동 경계와 그 지역의 전체 격자 수라는 정적 데이터를 전제로 한다. 이 데이터가 없으면 Region 화면 전체가 빈 값이다.
- **목표**:
  1. `region` 패키지 신설(entity·repository·seeder) — 기존 코드 없음(status.md: `region` ❌ 미생성).
  2. 전국 행정동 경계 GeoJSON을 `regions`에 **멱등(idempotent)** 하게 적재.
  3. 각 행정동의 `total_grid_count`를 경계 면적 기반으로 **시딩 시 1회** 산출·저장.
  4. 시딩은 로컬 공유 DB에서 실행되므로, **통합 테스트를 오염시키지 않는 실행·테스트 격리 방식**을 확정.

## 선행 상태 (V1__init.sql — 실스키마 확인 결과)

`regions` 테이블과 인덱스가 **이미 존재**한다. 이 티켓은 스키마를 만들지 않고 그 스키마에 맞춰 엔티티를 정의하고 데이터를 채운다.

```sql
CREATE TABLE regions (
    region_code      VARCHAR(10) PRIMARY KEY,
    region_name      VARCHAR(100) NOT NULL,
    parent_code      VARCHAR(10),
    boundary_geom    GEOGRAPHY(MULTIPOLYGON, 4326) NOT NULL,
    total_grid_count INTEGER NOT NULL DEFAULT 0
);
CREATE INDEX idx_regions_boundary ON regions USING GIST (boundary_geom);
CREATE INDEX idx_regions_parent   ON regions (parent_code);
```

| 사실 | 근거 | 이 티켓에서 |
|---|---|---|
| `regions` 테이블·GIST 인덱스 존재 | `V1__init.sql` L53–61 | 마이그레이션 불필요, 엔티티만 매핑 |
| `boundary_geom`은 `NOT NULL` | 위 스키마 | 시더가 반드시 채워야 함(빈 insert 불가) |
| JTS + Hibernate Spatial 사용 중 | `video/entity/Video.geom`이 `org.locationtech.jts.geom.Point` + `columnDefinition="geography(Point,4326)"` | geometry 처리 선택지 존재(도메인 로직 참조) |
| geospatial은 native 쿼리로 | `grid` 도메인 관례(Grid는 geom 미매핑, 공간 쿼리는 native) | 시더 UPSERT를 native SQL로 |
| 격자 상수 | `com.msg.fillmap.grid.GridConstants` — `GRID_LAT_STEP=0.0009`, `GRID_LNG_STEP=0.00115` | `total_grid_count` 셀 면적 산출의 기준 |

## 성공 기준 (관찰 가능)

1. 전국 시딩 실행 후 `SELECT COUNT(*) FROM regions` ≈ **3,558**(GeoJSON feature 수와 일치, ±소수 — 유효하지 않은 feature 제외분).
2. 모든 row의 `boundary_geom`이 `NOT NULL`이고 유효한 MULTIPOLYGON이다(`ST_IsValid` 통과, `GEOMETRYTYPE = 'ST_MultiPolygon'`).
3. 모든 row의 `total_grid_count > 0`이고, 샘플 행정동이 sanity check를 통과한다(§도메인 로직 예시: 여의도동 ≈ 800대 격자).
4. **시더를 두 번 실행해도** `regions` COUNT·값이 동일하다(멱등, ON CONFLICT UPSERT). 재실행 시 원본 속성 변경분은 반영된다.
5. 시더는 **지정 프로파일/플래그에서만** 동작하고, 일반 앱 기동·통합 테스트에서는 실행되지 않는다(§테스트 격리).
6. `region` 패키지 신설(entity·repository·seeder). `videos`·`user`·`grid` 런타임 코드 미변경. `GridQueryService` 등 계약 인터페이스 시그니처 불변.
7. 스키마 변경 없음(`V1__init.sql` 그대로). 전체 테스트 green.

## 결정 (Decisions)

### D1 — 범위 = **전국** + `total_grid_count` = **면적 근사**

- **범위: 전국 행정동 약 3,558개**(`adm_cd2` 기준). 서울 제한 안 함.
  - 근거: 원본 GeoJSON이 전국 단위이고, `total_grid_count`를 **격자 열거가 아닌 면적 근사**로 구하면 계산량 문제가 사라진다(서울 제한의 이유였던 격자 열거 비용이 소멸).
- **산출 방식: 면적 근사** — 격자 열거가 아니라 경계 면적을 셀 면적으로 나눈다.
  ```sql
  total_grid_count = ROUND( ST_Area(boundary_geom) / :cellAreaM2 )
  ```
  - `ST_Area(GEOGRAPHY)`는 m² 반환. `:cellAreaM2` = **10000**(100×100m 명목 셀 면적)을 기본값으로 한다(티켓 제안식과 동일).
  - **격자 열거(대안) 반려**: 행정동 bbox를 `GridConstants`로 정수 격자 범위로 환산 후 셀마다 `ST_Contains` 판정하는 방식은 정확하지만, 3,558개 행정동 × 셀당 point-in-polygon = 멘토가 금지한 "루프 안 geospatial" 비용. 표시용 분모에는 과하다.
- **근사 오차 한계(문서화)**:
  - *체계 오차(상수 편향)*: 명목 셀은 10000m²지만 실제 셀은 한국 위도에서 `GRID_LAT_STEP × GRID_LNG_STEP` ≈ 100m × 101.6m(서울) ~ 104.7m(부산) ≈ **10,150 ~ 10,470m²**다. 10000으로 나누면 `total_grid_count`가 **약 +1.5%(서울) ~ +4.7%(부산) 과대계상**된다(동서 경도 늘어남 때문).
  - *경계 부분셀 잡음*: 경계에 걸친 부분 셀을 면적이 분수로 흡수 → 격자 수 C인 행정동에서 상대 오차 `O(1/√C)`(수백~수천 셀이면 대략 1~4%), 평균적으로 편향 없음.
  - *합산 판정*: `total_grid_count`는 수집률의 **분모(표시용)**이지 정밀 카운트가 아니므로 한 자릿수 % 오차는 허용. 정밀도가 필요하면 격자 열거로 전환(MSG-93 영역).
  - **선택 여지(리뷰에서 확정)**: 서울 체계 편향을 없애려면 `:cellAreaM2`를 `GridConstants` 기준 한국 셀 면적(≈10150)으로 두는 상수 한 줄 교체로 가능. MVP 기본값은 명목 **10000** 권장(단순·티켓식과 일치), 상수는 조정 가능한 튜닝 노브로 남긴다.

### D2 — 적재 방식 = **멱등 시더(프로파일/플래그 게이트)**, native UPSERT

- **Flyway 마이그레이션 반려**: 수십 MB GeoJSON을 버전드 SQL로 넣는 건 부적절(checksum·repo 비대, V 파일 불변 규칙과 충돌). 또한 `regions` 테이블은 이미 V1에 있어 새 V 파일 사유 자체가 없다.
- **채택: 멱등 시더**(`ApplicationRunner`/`CommandLineRunner`), **`@Profile("seed")` 또는 `fillmap.region.seed.enabled=true`로 게이트**. 기본값 off — 일반 부팅·`test`·`local`·`dev`·`prod` 자동 기동에서 실행되지 않는다.
  - 실행 예: `SPRING_PROFILES_ACTIVE=local,seed ./gradlew bootRun` (또는 전용 Gradle task).
  - **멱등성**: row별 native `INSERT ... ON CONFLICT (region_code) DO UPDATE`. 두 번 실행해도 row가 늘지 않고 값이 수렴한다(성공 기준 4).
- **수동 스크립트(대안) 반려 사유**: 별도 스크립트는 DB 커넥션·PostGIS 함수 접근을 앱과 중복 구성해야 함. 앱 컨텍스트 안의 게이트된 시더가 기존 DataSource·트랜잭션·리포지토리를 그대로 재사용해 더 적은 코드.

### D3 — GeoJSON 파일 확보 = **다운로드 스크립트 + 외부 경로 + `.gitignore`**

- **출처**: 공개 데이터셋 `vuski/admdongkor` 저장소의 `HangJeongDong_ver20260701.geojson`(전국 행정동 경계, `adm_cd2` 속성 포함).
- **저장소에 커밋하지 않는다**(수십 MB). 대신:
  - **경로 규약**: 외부 파일 경로 `data/region/HangJeongDong_ver20260701.geojson`. 프로퍼티 `fillmap.region.seed.geojson-path`로 오버라이드(기본값 위 경로).
    - `src/main/resources`에 넣지 않는 이유: 클래스패스 번들 시 JAR이 수십 MB 비대해지고, 1회성 시드에 불필요.
  - **다운로드 스크립트**: `scripts/download-region-geojson.sh` — `curl`로 raw GitHub URL에서 내려받아 `data/region/`에 저장. URL은 스크립트 변수로 파라미터화(`HangJeongDong_ver20260701.geojson` 기본).
  - **`.gitignore`**: `/data/region/*.geojson` 추가.

## 데이터 모델

**Flyway 마이그레이션 불필요.** `V1__init.sql`의 `regions`가 이미 필요한 컬럼·인덱스를 전부 보유(선행 상태 표 참조).

### `region/entity/Region` (신규)

`grid.entity.Grid`와 같은 관례로 **geometry는 엔티티에 매핑하지 않는다**(read 미사용, write는 native UPSERT). 매핑 컬럼:

| 필드 | 컬럼 | 타입 | 비고 |
|---|---|---|---|
| `regionCode` | `region_code` | `@Id` String(10) | `adm_cd2` |
| `regionName` | `region_name` | String(100) | `adm_nm` |
| `parentCode` | `parent_code` | String(10), nullable | 시군구 코드(§도메인 로직) |
| `totalGridCount` | `total_grid_count` | int | 시딩 시 산출 |

- `boundary_geom`은 **엔티티 미매핑**(NOT NULL이지만 JPA persist를 쓰지 않고 native UPSERT로 채우므로 문제 없음). 후속 티켓(MSG-93/155)이 공간 조회를 필요로 하면 그때 JTS `MultiPolygon`으로 매핑(JTS는 이미 프로젝트에 존재).
- 컨벤션: `@NoArgsConstructor(access = PROTECTED)`, `@Getter`, `@Setter` 지양.

### `region/repository/RegionRepository extends JpaRepository<Region, String>`

- 읽기: `count()`(검증용, JpaRepository 기본).
- 쓰기: native UPSERT `@Modifying @Query(nativeQuery = true)`. GeoJSON geometry 문자열과 속성을 바인딩, PostGIS가 geometry 파싱·면적 산출을 한 문장에서 처리:
  ```sql
  INSERT INTO regions (region_code, region_name, parent_code, boundary_geom, total_grid_count)
  VALUES (
      :regionCode, :regionName, :parentCode,
      ST_Multi(ST_GeomFromGeoJSON(:geometryJson))::geography,
      ROUND( ST_Area(ST_Multi(ST_GeomFromGeoJSON(:geometryJson))::geography) / :cellAreaM2 )
  )
  ON CONFLICT (region_code) DO UPDATE SET
      region_name      = EXCLUDED.region_name,
      parent_code      = EXCLUDED.parent_code,
      boundary_geom    = EXCLUDED.boundary_geom,
      total_grid_count = EXCLUDED.total_grid_count
  ```
  - `ST_Multi`로 Polygon/MultiPolygon 입력을 모두 MULTIPOLYGON으로 정규화(스키마 타입과 일치).
  - `ON CONFLICT` = 멱등성(D2). 재실행 시 값 수렴.

## 도메인 로직

### 시딩 파이프라인 (`region/seed/RegionSeeder` + `RegionGeoJsonReader`)

1. 게이트 확인: `seed` 프로파일/플래그 아니면 아무 것도 안 함(early return).
2. `fillmap.region.seed.geojson-path`의 GeoJSON `FeatureCollection`을 스트리밍/역직렬화(Jackson). 파일 없으면 명확한 예외로 조기 실패.
3. 각 `feature`에서 추출:
   - `region_code` = `properties.adm_cd2`
   - `region_name` = `properties.adm_nm`
   - `parent_code` = **시군구 코드** = `region_code` 앞 5자리(`LEFT(adm_cd2,5)`). 파생 불가면 null.
     - ⚠️ 정확한 자릿수/속성명(`adm_cd2` vs `sgg` 등)은 실제 GeoJSON 속성 스키마로 확인해 확정(§미해결 질문 Q1).
   - `geometryJson` = `feature.geometry` 노드의 JSON 문자열(그대로 `ST_GeomFromGeoJSON`에 바인딩).
4. 필수 속성(`adm_cd2`/`adm_nm`/`geometry`) 누락 feature는 **건너뛰고 카운트 로깅**(전량 실패 방지).
5. row별 native UPSERT 호출(배치). `:cellAreaM2`는 상수(D1, 기본 10000).
6. 완료 후 적재 건수·건너뛴 건수 로깅(DoD COUNT 검증 근거).

### `total_grid_count` 산출 규칙 (D1 구현)

- `total_grid_count = ROUND(ST_Area(boundary_geom) / cellAreaM2)`, `cellAreaM2 = 10000`.
- **sanity check 예시**(성공 기준 3):
  - 면적 1km²(=1,000,000m²) 행정동 → 약 **100** 격자.
  - 여의도동(≈8.4km²) → 약 **840** 격자.
  - 서울시 전체 합계(≈605km²) → 약 **6만** 격자대.
- `GridConstants`와의 일관성: 셀 면적 상수는 `GRID_LAT_STEP`·`GRID_LNG_STEP` 정의(한국 위도 100×100m 근사)에 근거한다. 명목 10000 vs 한국 셀 ≈10150의 편향은 D1에 문서화.

### 멘토 피드백 정합 (Confluence 'DB')

- 실시간 경로 geospatial 없음 — `total_grid_count`는 시딩 시 1회 산출(사전 레이블링), 조회 경로에서 재계산 안 함.
- region↔grid 매핑 테이블 없음 — 영상이 `region_code`를 직접 보유하는 현 구조 유지.
- H3 미사용.

## 테스트 시나리오 (JUnit5 + AssertJ · 한국어 백틱 메서드명)

DB를 쓰는 모듈은 실 PostGIS(`local` 프로파일 + Flyway V1)를 사용한다. 순수 로직 모듈은 DB 없이 단위 테스트.

### 모듈 1 — `RegionGeoJsonReader` (GeoJSON 파싱, 순수 단위)
- `FeatureCollection에서_adm_cd2를_region_code로_추출한다`
- `adm_nm을_region_name으로_추출한다`
- `adm_cd2_앞_5자리를_parent_code로_파생한다`
- `geometry_노드를_JSON_문자열로_그대로_추출한다` (ST_GeomFromGeoJSON 입력용)
- `필수속성_누락_feature는_건너뛴다` (전량 실패 방지)

### 모듈 2 — `RegionRepository` (native UPSERT, DB 통합 · 격리 fixture)
- `행정동_한건을_UPSERT하면_boundary_geom이_NOT_NULL로_저장된다`
- `저장된_geometry는_유효한_MultiPolygon이다` (ST_IsValid · GEOMETRYTYPE)
- `같은_region_code로_다시_UPSERT하면_row가_늘지않고_값이_갱신된다` (멱등)
- `Polygon입력도_ST_Multi로_MultiPolygon으로_정규화된다`

### 모듈 3 — `total_grid_count` 산출 (면적 근사)
- `면적_1제곱킬로미터_경계는_약_100개_격자로_산출된다` (1,000,000/10,000)
- `여의도동_규모_경계는_수백개_격자로_sanity_check된다`
- `boundary가_클수록_total_grid_count가_단조증가한다`

### 모듈 4 — `RegionSeeder` (멱등성·게이트, DB 통합 · 합성 fixture)
- `시더를_두번_실행해도_regions_COUNT가_동일하다`
- `시더_재실행시_변경된_속성이_UPSERT로_반영된다`
- `seed_프로파일이_아니면_시더는_실행되지_않는다`
- `GeoJSON파일이_없으면_명확한_예외로_실패한다`

### 모듈 5 — 테스트 격리 (시딩이 공유 DB를 오염시키지 않음)
- `시딩테스트는_합성_region_code만_사용하고_실데이터_row를_건드리지_않는다`
- `@Transactional_롤백으로_공유DB에_잔여_seed가_남지않는다`

> **격리 원칙(성공 기준 5 · MEMORY 'shared local DB')**: 시딩 관련 DB 테스트는
> **합성 fixture(예: `region_code = "TESTDONG01"`) + `@Transactional` 롤백**만 사용한다.
> `regions`를 **truncate하지 않는다** — `videos.region_code`·`region_stats.region_code`가
> 공유 DB에서 이 테이블을 FK 참조하므로, 전체 삭제는 타 테스트를 깨고 NonUniqueResult를 유발한다.
> 대량(3,558행) 전국 시딩은 테스트가 아니라 게이트된 시더 수동 실행(DoD 검증)으로만 수행한다.

### DoD 수동 검증 (전국 시딩 후, 게이트 실행)
- `SELECT COUNT(*) FROM regions;` ≈ 3,558.
- 샘플 행정동(예: 여의도동) `total_grid_count` sanity(수백대).
- `SELECT COUNT(*) FROM regions WHERE NOT ST_IsValid(boundary_geom::geometry);` = 0.
