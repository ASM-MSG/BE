## 개요

친구 에픽(MSG-172)의 선행 조건인 **친구 관계 수명주기 전체**를 구현한다:
고정 친구 코드 발급(가입 시 자동 + 기존 가입자 마이그레이션 백필) → 코드로 상대 확인·요청 →
수락/거절 → 삭제. `friendships` 테이블은 V1에 이미 있고(코드 참조 0건), 엔티티 매핑부터 신규다.

## 배경 · 목표

- 닉네임은 중복 허용(MSG-203)이라 검색으로 상대를 특정할 수 없고, 카카오 친구 연동은 비즈 앱
  전환이 선행돼야 해서 **고정 친구 코드** 방식으로 확정됐다 (2026-08-03, MSG-172 코멘트).
- 이 티켓이 끝나면 친구 목록/프로필(MSG-186)·친구 도감(MSG-187)·공개범위(MSG-285)가 착수 가능하다.
- 스코프 제외(PRD 비목표): 그룹, 친구 목록 조회, 차단(BLOCKED), 코드 재발급, QR/공유 링크,
  일회성 초대 링크.

> 참고: 위키 `03-specs/Social API 예정.md`(2026-07-17 초안)는 이 PRD로 대체된다 — 초안의 최대
> 블로커("상대 특정 불가")가 친구 코드로 해소됐고, 초안의 7xxx 에러 대역 제안은 badge(MSG-239)가
> 선점해 무효다. 위키 갱신은 마무리 단계 몫.

## 성공 기준

- 신규 가입(LOCAL·KAKAO 양쪽)·기존 가입자 모두 8자 친구 코드를 가진다 (NOT NULL + UNIQUE).
- API 7종이 아래 명세대로 동작하고, 에러 케이스가 지정된 developCode로 응답한다.
- 거절·삭제 후 `friendships`에 잔여 행이 없다 (행 존재 = 활성 관계 불변식, D3).
- 역방향 PENDING 상태에서의 요청이 자동 수락으로 수렴한다 (FR-8).
- 계정 삭제 시 관련 행이 CASCADE로 사라진다 (FR-14 — V1 FK `ON DELETE CASCADE` 기존 보장,
  코드 변경 불요).
- 전체 테스트 green (`./gradlew test`).

## 확정 설계 (D1~D4 — 재결정·변경 금지)

### D1. 마이그레이션 `V18__users_friend_code.sql`

> ⚠️ **버전 번호만 조정**: 승인된 플랜의 파일명은 V17이었으나 실측 결과
> `V17__videos_fail_reason.sql`이 이미 존재한다. Flyway 버전 충돌은 기계적 사실이므로
> **V18**로 번호만 올린다 — SQL 내용·4단 구조는 무변경.

순수 SQL 4단 (선례 `V5__grids_region_code.sql`의 "무엇을·왜·재실행 시 거동" 주석 관례 준수):

```sql
-- 1) 컬럼 추가 (nullable — 백필 전 단계)
ALTER TABLE users ADD COLUMN friend_code VARCHAR(8);

-- 2) 기존 가입자 백필 — 상관 서브쿼리로 행마다 새 코드 생성.
--    WHERE u.id IS NOT NULL 은 상관 강제 장치다: 이 조건이 없으면 서브쿼리가 외부 행을
--    참조하지 않아 PostgreSQL 이 InitPlan 으로 1회만 평가 → 전 행 동일 코드 → UNIQUE 실패.
UPDATE users u SET friend_code = (
	SELECT string_agg(substr('ABCDEFGHJKLMNPQRSTUVWXYZ23456789', floor(random() * 32)::int + 1, 1), '')
	FROM generate_series(1, 8)
	WHERE u.id IS NOT NULL);

-- 3) NOT NULL 승격
ALTER TABLE users ALTER COLUMN friend_code SET NOT NULL;

-- 4) 전역 유일 제약 — 랜덤 충돌의 백스톱.
--    수십 행 기준 충돌 확률 ~1e-9, 만에 하나 실패하면 마이그레이션 재실행으로 수렴.
ALTER TABLE users ADD CONSTRAINT uq_users_friend_code UNIQUE (friend_code);
```

- **코드 형식** (PRD 비기능 보안 확정): 혼동 문자 I·O·0·1 제외 알파벳 32종
  `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`, 8자 — 탐색 공간 32⁸ ≈ 1.1조. 무차별 대입으로 계정
  존재를 열거하기 어렵다.
- `COMMENT ON COLUMN users.friend_code` 한 줄 추가 (V5 관례).

### D2. 신규 가입 코드 생성 — User 엔티티 내부화

- `User` 엔티티에 `friendCode` 필드 추가 + **private `@Builder` 생성자 내부에서
  `generateFriendCode()` 호출**. 생성 규칙(알파벳 32종·8자)은 엔티티의
  `private static final` 상수 + `private static final SecureRandom`.
- 팩토리 `createLocalUser` / `createOAuthUser` **시그니처 무수정** — 두 팩토리가 같은 private
  생성자를 지나므로 가입 경로 2곳(`AuthService.signup:36`, `OidcLoginService.registerNewUser:73`)이
  자동 커버된다. **auth 서비스 코드 변경 0줄** (PRD §7의 "User 팩토리 내부화 여부"는 내부화로 확정).
- **충돌 재시도 없음** — DB UNIQUE(`uq_users_friend_code`)가 백스톱. 충돌 시 가입 트랜잭션이
  제약 위반으로 실패하고 사용자 재시도로 수렴한다. 엔티티에 `ponytail:` 주석으로 천장 명시
  (예: `// ponytail: 충돌 재시도 없음 — 32^8 공간에서 확률 ~1e-9, DB UNIQUE 백스톱. 실측 충돌 시 재시도 루프 추가`).

### D3. 행 수명 불변식 — "행 존재 = 활성 관계"

- **거절·친구 삭제 모두 행 DELETE.** `REJECTED`는 영속되지 않는다.
- 효과 1: 중복 검사가 status 분기 없는 **존재 확인**으로 단순화된다.
- 효과 2: "거절당한 행이 남아 역방향 재요청 시 UPDATE가 필요한" 버그 클래스가 통째로 사라진다
  (FR-11 "거절 후 재요청 허용"이 코드 없이 성립).
- `FriendshipStatus` enum은 **PENDING·ACCEPTED 2종만** 정의. DB CHECK
  (`chk_friendships_status`: 4종 허용)는 **무수정** — 넓은 CHECK에 좁은 enum은 위반이 아니므로
  마이그레이션 불요. REJECTED·BLOCKED는 차단 기능 후속 티켓에서 필요 시 enum에 추가.
- `responded_at`은 **수락 시에만** 기록 (거절은 행이 사라지므로 기록 지점 자체가 없음).

### D4. API 7종

전부 인증 필수(`SecurityConfig anyRequest().authenticated()`가 `/api/friends/**`를 이미 커버 —
설정 변경 불요), 응답은 `SuccessResponse.of(...)` HTTP 200 고정, 에러는
`ApiException(FriendErrorCode)` → `GlobalExceptionHandler` 변환. 상세는 아래 "API 명세".

## API 명세

베이스: `FriendController` — `@RequestMapping("/api/friends")`.
principal은 `@AuthenticationPrincipal AuthPrincipal principal` → `principal.userId()`
(UserController 선례).

### 1. 내 친구 코드 조회 — FR-1

```text
GET /api/friends/code
→ 200 { developCode: 200, message: "성공", body: { friendCode: "AB3DE7GH" } }
```

- `FriendCodeResponseDto(String friendCode)` — `@Schema(requiredProperties = {"friendCode"})`
  (MSG-308 관례).
- 로직: `userRepository.findById(principal.userId())` → `user.getFriendCode()`.
  유저 없음은 인증 통과 후엔 불가능한 경로지만 기존 관례대로 `UserErrorCode.USER_NOT_FOUND`(1404).

### 2. 코드 미리보기 — FR-3

```text
GET /api/friends/preview?code={friendCode}
→ 200 body: { nickname: "채우미" }
에러: 코드 없음 → 9404 FRIEND_CODE_NOT_FOUND
```

- `FriendPreviewResponseDto(String nickname)`.
- **advisory 전용** — 확인 화면("OOO님에게 요청을 보낼까요?")용이며, POST가 전 검증을
  재수행한다. 따라서 자기 코드·이미 친구인 상대의 코드도 미리보기는 성공한다(단순 조회).
- 로직: `userRepository.findByFriendCode(code)` (신규 쿼리 메서드) → 닉네임만 노출.

### 3. 친구 요청 — FR-4~8

```text
POST /api/friends/requests
body: { "friendCode": "AB3DE7GH" }
→ 200 body: { status: "PENDING" }    (신규 요청)
→ 200 body: { status: "ACCEPTED" }   (역방향 PENDING 자동 수락 — FR-8)
에러:
  자기 자신           → 9400 SELF_FRIEND_REQUEST
  코드 없음           → 9404 FRIEND_CODE_NOT_FOUND
  이미 친구(ACCEPTED) → 9409 ALREADY_FRIENDS
  내가 보낸 요청 대기 → 9410 FRIEND_REQUEST_ALREADY_PENDING
```

- `FriendRequestCreateRequestDto(String friendCode)` — `@NotBlank`.
- `FriendRequestCreateResponseDto(FriendshipStatus status)` — FE가 "요청 보냄"과 "바로 친구 됨"
  화면을 구분하는 유일한 신호.
- 검증·분기 순서 (트랜잭션 1개):
  1. `findByFriendCode` → 없으면 9404
  2. `target.getId().equals(principal.userId())` → 9400
  3. 양방향 조회 `findPair(me, target)` (아래 리포지토리) — 행 존재 시 status 분기:
     - `ACCEPTED` (방향 무관) → 9409
     - `PENDING` + 내가 requester → 9410
     - `PENDING` + 내가 addressee(역방향) → **자동 수락**: `friendship.accept()`
       (status=ACCEPTED, respondedAt=now, 더티 체킹 UPDATE) → `ACCEPTED` 반환
  4. 행 없음 → `Friendship.request(me, target)` INSERT (PENDING) → `PENDING` 반환

### 4. 받은 요청 목록 — FR-9

```text
GET /api/friends/requests/received
→ 200 body: [ { requesterId: 3, nickname: "채우미", profileImageUrl: "https://…", requestedAt: "2026-08-03T12:00:00" }, … ]
```

- `ReceivedFriendRequestResponseDto(Long requesterId, String nickname, String profileImageUrl,
  LocalDateTime requestedAt)` — `profileImageUrl`은 nullable(`@Schema(nullable = true)`),
  `requestedAt` = `friendships.created_at`.
- `requesterId`는 수락/거절 호출의 경로 변수로 그대로 쓰는 키다.
- JPQL 생성자 프로젝션 — User를 FK 매핑 없이 Long 조인 (승인 플랜 확정):

```java
@Query("""
	SELECT new com.msg.fillmap.friend.dto.ReceivedFriendRequestResponseDto(
		f.id.requesterId, u.nickname, u.profileImageUrl, f.createdAt)
	FROM Friendship f, User u
	WHERE u.id = f.id.requesterId AND f.id.addresseeId = :userId AND f.status = 'PENDING'
	ORDER BY f.createdAt DESC
	""")
List<ReceivedFriendRequestResponseDto> findReceivedRequests(Long userId);
```

- 정렬: 최신 요청 우선(`created_at DESC`). V1 인덱스 `idx_friendships_addressee(addressee_id,
  status)`가 WHERE를 커버한다. 페이징 없음 — 받은 요청은 소량 전제(수십 건 천장), 필요 시 후속.

### 5. 요청 수락 — FR-10·13

```text
POST /api/friends/requests/{requesterId}/accept
→ 200 body: null
에러: 해당 요청 없음 → 9414 FRIEND_REQUEST_NOT_FOUND
```

- 조회 키 = **`(requesterId, principal.userId())` 복합 PK** — 수신자 본인 검증을 조회 키가
  구조적으로 강제한다(FR-13). 타인의 요청은 키가 달라 애초에 조회되지 않는다.
- `findById(new FriendshipId(requesterId, me))` → 없거나 status가 PENDING이 아니면 9414
  (이미 ACCEPTED인 관계의 재수락도 9414 — "대기 중 요청"이 없으므로).
- 수락: `friendship.accept()` — status=ACCEPTED, respondedAt=now.

### 6. 요청 거절 — FR-11·13

```text
POST /api/friends/requests/{requesterId}/reject
→ 200 body: null
에러: 해당 요청 없음 → 9414 FRIEND_REQUEST_NOT_FOUND
```

- 조회 키·검증은 수락과 동일. 거절 = **행 DELETE** (D3). 보낸 쪽 통지 없음, 상대 재요청 가능.

### 7. 친구 삭제 — FR-12·13

```text
DELETE /api/friends/{userId}
→ 200 body: null
에러: 관계 없음 → 9424 FRIENDSHIP_NOT_FOUND
```

- `findPair(me, userId)` 양방향 조회 → `ACCEPTED` 행이면 DELETE, 없거나 PENDING이면 9424
  (대기 중 요청 취소는 이 API 범위 밖 — PRD에 보낸 요청 취소 FR 없음).
- principal이 항상 조회 조건에 들어가므로 관계 당사자만 삭제 가능(FR-13).

신설 근거를 클래스 주석에 남김 — 에코는 느슨한 관례라 9409/9410처럼 의미 구분 우선 허용,

## 도메인 로직

glossary 기준 서술 — 친구 관련 용어는 glossary "Phase 2+ 미확정" 절에만 있으므로 이번 범위의
용어를 아래 "용어 제안"으로 남긴다 (glossary 신설은 별도 PR 리뷰 몫).

- **친구 코드**: 사용자 1명당 고정 1개, 가입 시점 부여, 전역 유일, 재발급 없음(후속).
  코드 소유자만 `GET /code`로 확인 — 코드 자체는 사용자가 임의 채널(카톡 등)로 공유한다.
- **관계의 방향**: `friendships` 행은 (requester, addressee) 방향이 있지만, **동일 쌍의 행은
  방향 무관 최대 1개**(PRD 비기능 데이터 정합). 애플리케이션이 `findPair` 양방향 조회 +
  존재 확인으로 강제한다.
  - `ponytail:` 알려진 천장 — 서로 동시에 요청하는 극단 레이스에서 A→B·B→A 2행이 생길 수
    있다(복합 PK는 같은 방향만 막음). 승인 설계에 대칭 제약이 없으므로 앱 검증으로 두고,
    실측 발생 시 `UNIQUE (LEAST(requester_id, addressee_id), GREATEST(…))` 인덱스 마이그레이션이
    업그레이드 경로다. 이 주석을 서비스 코드에 남긴다.
- **자동 수락(FR-8)**: 역방향 PENDING에서의 요청 = 양쪽 다 추가 의사 표명 → 기존 행을
  ACCEPTED로 승격. 새 행을 만들지 않으므로 "최대 1행" 불변식이 유지된다.
- **수락 시 양쪽 친구 성립(FR-10)**: 별도 역방향 행 INSERT 없음 — ACCEPTED 행 1개가 양방향
  관계를 표현하고, 이후 조회(MSG-186)는 양방향 UNION으로 읽는다.
- **트랜잭션**: 쓰기 API(요청·수락·거절·삭제) 각각 `@Transactional` 1개. 조회는 readOnly.
- **행 잠금 (Codex 리뷰 반영, 2026-08-03)**: `findPair`·수락/거절 조회(`findWithLockById`)는
  `PESSIMISTIC_WRITE`(PG `FOR NO KEY UPDATE`) — 같은 행에 대한 동시 수락/거절/자동수락이
  직렬화되고, 늦은 쪽은 갱신된 상태를 읽어 9414(또는 9409)로 수렴한다. 잠금은 항상 행 1개라
  데드락 순서 문제 없음. (INSERT 경합인 상호 요청 레이스는 별개 — 기존 ponytail 수용 유지)
- **계정 삭제 정합(FR-14)**: V1 FK 양쪽 `ON DELETE CASCADE` — MSG-205 계정 삭제가 DB 위임
  방식이므로 추가 코드 없음.
