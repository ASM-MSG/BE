# 핫구역 집계 대안 비교

2026-09-17, `feature/MSG-494-performance-verification`에서 실행한 로컬 비교 실험이다.
**과거 DB 구현을 Redis로 교체한 이력이 아니다.** MSG-183부터 Redis 버킷을 사용했다.
이번에는 DB 집계 비교군을 만들어 기존 선택의 비용과 한계를 검증했다. 서비스 코드는 바꾸지 않았다.

**현재 설계를 유지하되, Redis가 유일한 해답이라고 설명하지 않는다.** 같은 기간의 집계는 Redis가 약 9.5배 빨랐다.
DB도 30초 캐시와 동시 재계산 방지를 붙이면 100 requests/s를 실패 없이 처리했다.
현재 방식의 강점은 재계산 비용과 만료 순간의 지연이고, 비용은 추가 메모리와 42~48시간 근사다.

## 비교 조건

| 항목 | 조건 |
|---|---|
| 대상 | 저장소에서 전국 상위 50개를 구하는 경로. HTTP API 전체 아님 |
| 데이터 | 고정 난수 183, 최근 72시간 업로드 신호 10만/100만 건, 격자 1천/1만 개 |
| 분포 | 신호 20%는 100개 격자, 나머지는 전체 격자에 균등 배분 |
| 기준 시각 | 2026-09-17 03:00 UTC로 고정. DB 48시간, 기존 6시간 버킷은 이 시점에 45시간 포함 |
| DB | PostgreSQL 16, 전용 컨테이너 1 CPU/1 GiB, fsync 기본값 유지 |
| Redis | Redis 7, 전용 컨테이너 1 CPU/512 MiB, 디스크 영속화 끔 |
| DB 인덱스 | `occurred_at INCLUDE (grid_id)` 커버링 인덱스[^1], 적재 후 VACUUM ANALYZE |
| 캐시 | DB 집계 결과와 Redis 합산 결과 모두 TTL 30초[^2] |
| 비교 순서 | 기본 4개 전략 3회. 정방향, 역방향, 순환 순서로 교대 |
| 부하 | 100 requests/s, 회당 33초. 먼저 캐시를 채우고 약 30초 뒤 자연 만료를 포함 |
| 대기 상한 | 실행 스레드 16개, 실행+대기 32건. 넘으면 누락으로 기록, DB 쿼리 제한 2초 |
| 원시 지표 | 성공 지연, 서비스 시간, 예약 시각, 타임아웃, 수용하지 못한 요청을 별도로 기록 |

전용 포트는 PostgreSQL `127.0.0.1:15438`, Redis `127.0.0.1:16388`이다.
개발 서버와 기존 로컬 DB/Redis 데이터는 수정하지 않았다. 두 컨테이너와 부하 발생기는 같은 노트북에서 실행했다.

## 무엇을 같게 맞췄나

- 두 저장소에 동일한 업로드 신호를 적재했다. DB는 원본 행, Redis는 시간별 격자 점수로 표현했다.
- Python 원본 집계와 DB 정확한 48시간 집계를 비교했다. 별도로 DB 조회 기간을 버킷과 같은 45시간으로 맞춰 Redis 결과와도 일치하는지 검사했다.
- 점수 내림차순, 동점은 격자 ID 내림차순으로 맞췄다. PostgreSQL 문자열 정렬은 `COLLATE "C"`를 사용했다.
- Redis의 증분 및 캐시 생성 Lua는 서비스 소스에서 직접 읽는다. 캐시 조회는 서비스처럼 Lua 실행 후 상위 50개 조회로 나눴다.
- 이번 성능 표본은 상위 50개 점수가 모두 최소 임계 3 이상이다. 뷰포트 필터와 행정동 이름 조회는 비교 대상에서 제외했다.

DB 비교군은 `videos` 전체 스키마 대신 업로드 신호의 `id`, `grid_id`, `occurred_at`만 저장한다.
삭제 없는 신호를 가정하며, 실제 영상 삭제 정책과 상태 조건을 구현한 대체 서비스가 아니다.
현재 Redis는 업로드 확정 후 커밋 시점에 증분한다. DB의 영상 생성 시각과 그 시점 사이의 차이도 이번 합성 데이터에는 없다.

## 단일 요청 비용

워밍업 5회 후 60회 측정한 중앙값이다. 큐 대기 없는 저장소 호출 비용이며 운영 API 지연으로 인용하면 안 된다.

| 신호 수 / 격자 수 | DB 매번 48h 집계 | DB 매번 45h 집계 | Redis 매번 합산 | DB 결과 캐시 적중 | Redis 합산 캐시 적중 |
|---|---:|---:|---:|---:|---:|
| 10만 / 1천 | 5.276ms | 4.783ms | 0.655ms | 0.120ms | 0.294ms |
| 100만 / 1만 | 50.734ms | 47.377ms | 4.966ms | 0.126ms | 0.418ms |

동일한 45시간을 집계해도 100만 건에서는 DB 47.377ms, Redis 4.966ms로 약 9.5배 차이가 났다.
**미리 점수를 누적하는 효과는 확인했지만, 캐시 적중 요청은 DB 집계 결과를 캐시한 쪽이 빨랐다.**
DB 캐시는 문자열 GET 한 번이고, 현재 Redis 경로는 캐시 확인과 점수 목록 조회로 두 번 왕복한다.
DB 실행 계획은 인덱스가 있어도 병렬 순차 스캔[^3]을 선택했다. 읽는 범위가 전체 신호의 약 2/3인 조건이며 인덱스를 강제하지 않았다.

## 고정 도착률에서 확인한 캐시 효과

100만 신호/1만 격자, 100 requests/s에서 각 방식에 3,300건씩 3회 요청했다.
지연과 CPU 시간은 회차별 값의 중앙값이다. 실패 수는 세 회차 합계다.

| 방식 | 성공 / 9,900건 | 수용 못 함 / DB 타임아웃 | 성공 요청 p95 | 성공 요청 p99 | Redis CPU 시간 / 회차 |
|---|---:|---:|---:|---:|---:|
| DB 매번 집계 | 27 | 9,088 / 785 | 4,389ms | 4,389ms | 0.198초 |
| DB 집계 + 단순 30초 캐시 | 9,629 | 236 / 35 | 5.746ms | 10.986ms | 0.513초 |
| Redis 매번 합산 | 9,900 | 0 / 0 | 10.768ms | 14.249ms | 15.855초 |
| 현재 Redis + 30초 캐시 | 9,900 | 0 / 0 | 6.671ms | 7.354ms | 0.930초 |
| DB 집계 + 30초 캐시 + 동시 재계산 방지 | 9,900 | 0 / 0 | 5.692ms | 6.587ms | 0.532초 |

- **Redis 합산 결과 캐시 효과:** 같은 요청량에서 재계산은 회차당 3,300회에서 1회로 줄었다. 초기 캐시 생성은 계측 전이다. Redis CPU 시간은 약 94.1%, 성공 요청 p99는 약 48.4% 줄었다.
- **DB 무캐시:** 이 자원/실행 계획/동시성 설정에서 100 requests/s를 감당하지 못했다. 성공 표본이 극히 적어 성공 지연으로 Redis와 배수를 비교하지 않는다. 별도 10 requests/s 확인에서는 330건 전부 성공, p95 64.002ms였다. 이를 DB 일반 처리 한계로 확대하지 않는다.
- **DB 단순 캐시:** 평소 캐시 적중은 빠르지만 만료 때 여러 요청이 동시에 집계를 실행했다. 만료 구간(예약 시각 29~32초)의 성공 요청 p99 중앙값은 1,876.516ms였고, 실패 271건도 발생했다. 전체 성공 p99만 보면 이 문제가 가려진다.
- **현재 Redis 캐시:** 같은 만료 구간 p99 중앙값은 7.869ms였다. Lua 안에서 캐시 존재 확인과 재계산을 한 번에 처리해, 세 회차 모두 재계산 1회였다.

DB 캐시의 동시 재계산을 막는 비교군도 추가했다. 캐시가 없으면 프로세스 내 락[^6]을 잡고 캐시를 다시 확인한 뒤 한 요청만 집계한다.
이 비교군도 **9,900건 전부 성공**했다. 평소를 포함한 전체 p99는 6.587ms로 현재 Redis보다 낮았고,
만료 구간 p99는 179.497ms로 현재 Redis의 7.869ms보다 높았다. “DB로는 이 부하를 감당할 수 없다”는 결론은 기각한다.
세 회차 모두 계측 중 DB 집계 결과 SET 1회를 확인했다. DB CPU 시간 중앙값은 회차당 0.347초였다.
이 추가군은 기본 실험 뒤 연속 3회 실행했으므로 순서 효과를 완전히 제거한 비교는 아니다.
단일 프로세스 락이므로 여러 API 인스턴스로 확장하면 재계산 조율 방식도 달라져야 한다.

## 정확도

별도 난수 233으로 시나리오당 10만 건을 만들고, 버킷 시작 직후/3시간 뒤/끝나기 1초 전을 비교했다.
정확한 최근 48시간 상위 50개와 겹치는 비율이다. 실제 사용자 분포의 추정치가 아니다.

| 6시간 버킷의 입력 분포 | 시작 직후, 42h | 3시간 뒤, 45h | 종료 1초 전, 약 48h |
|---|---:|---:|---:|
| 격자별 균등 분포 | 70% | 78% | 100% |
| 같은 50개 격자가 꾸준히 인기 | 100% | 100% | 100% |
| 46~47시간 전 특정 격자에 신호 집중 | 2% | 80% | 100% |

균등 분포에서는 버킷 시작 직후 신호 약 12.5%를 제외했다. 마지막 시나리오에서는 신호가 오래된 구간에 몰려 약 51.9%를 제외했다.
**시간 폭 오차가 최대 6시간이라고 점수 오차도 최대 12.5%인 것은 아니다.**
47시간 전 업로드 3건만 있는 격자는 정확한 집계에서는 최소 임계를 넘지만, 버킷 시작 직후에는 제외되는 경계 사례도 확인했다.

동점 영향은 원시 자료의 `tie_aware_top50`로 따로 남겼다. 정확한 50위 점수 이상이면 동점 대안으로 인정한 지표다.
기본 표는 Redis와 같은 결정적 동점 정렬을 적용한 집합 일치율[^4]이다. 순서 전체가 같다는 뜻은 아니다.
1시간/3시간 버킷의 정확도도 같은 입력으로 검사했으며 `accuracy.json`에 함께 보관했다.

이 근사는 기존 `docs/spec/MSG-233.md` D2에서 허용한 동작이다. 새로운 결함으로 단정하지 않는다.
다만 “정확한 최근 48시간 랭킹”이나 “분포와 무관하게 정확도 손실이 작다”는 설명은 사용할 수 없다.

## 버킷을 잘게 나누면

같은 100만 신호를 1/3/6시간 단위로 다시 적재했다. 매번 합산 캐시를 지운 뒤 서비스 Lua와 상위 50개 조회를 60회 실행했다.
각 결과는 같은 기간을 읽는 DB 집계와 일치했다. 정확도 시나리오 27개도 실제 Redis Lua 실행 결과와 대조해 통과했다.

| 버킷 폭 | 합산 키 | 선택한 버킷 메모리 | 재계산+상위 조회 중앙값 | 균등 분포, 경계 직후 상위 50 일치율 |
|---|---:|---:|---:|---:|
| 1시간 | 48 | 29,951,421 bytes | 12.779ms | 88% |
| 3시간 | 16 | 14,325,862 bytes | 7.131ms | 78% |
| 6시간 | 8 | 7,948,185 bytes | 5.276ms | 70% |

1시간 버킷은 6시간보다 메모리 약 3.8배, 재계산 시간 약 2.4배를 썼다.
46~47시간 전 업로드 집중 사례의 경계 직후 상위 50 일치율은 2%에서 100%로 높아졌다.
균등 분포의 동점 대안을 인정하면 1시간 92%, 6시간 74%였다.

메모리 수치는 선택된 키의 `MEMORY USAGE` 합이며, 자료구조와 키 길이 때문에 앞 절의 6시간 메모리와 소폭 다르다.
기준 시각이 03:00이므로 비용 실험에서 1시간은 47h, 3/6시간은 45h를 포함한다. 완전히 같은 포함 기간의 성능 비교는 아니다.
1시간 방식도 정확한 48시간 집계는 아니며, **6시간이 정확도까지 포함해 최적인 것으로 입증되지는 않았다.**

## 쓰기와 저장 공간을 읽는 법

100만 신호를 담은 최소 DB 테이블과 인덱스는 123,387,904 bytes였다.
조회에 쓰는 Redis 8개 버킷은 8,168,186 bytes, 합산 결과는 1,011,872 bytes였다.
**Redis를 쓴다고 영상 DB를 삭제하는 것은 아니므로 이 차이를 시스템 저장 비용 절감률로 쓰면 안 된다.**
원본 행 저장과 점수 요약 표현의 차이이며 DB 디스크와 Redis 메모리도 같은 자원이 아니다.

`writes.json`에는 DB INSERT, Redis 증분, DB INSERT 후 Redis 증분을 각각 500회 잰 결과가 있다.
DB INSERT는 디스크 영속성을, 이번 Redis는 메모리 기록만 제공하므로 서로 대체 가능한 쓰기로 취급하지 않는다.
실제 서비스는 DB 커밋 뒤 별도 executor에서 Redis를 갱신하며, 이번 동기 호출 비용은 업로드 API 응답 시간 개선 증거가 아니다.

## 선택과 포트폴리오 표현

- **이번 변경:** 비교 도구, 원시 결과, 보고서만 추가했다. 이미 구현된 Redis 버킷과 30초 캐시는 유지한다.
- **유지 근거:** 현재 허용된 근사 정책 안에서 만료 시점 지연과 DB 재집계 비용을 줄였다. DB 대안으로 교체해야 할 성능 근거는 이번 실험에서 나오지 않았다.
- **선택의 한계:** DB 결과 캐시와 동시 재계산 방지도 충분히 빠르다. 정확한 48시간이 필요하면 검토할 수 있는 대안이다. 실제 적용 전에는 영상 삭제 이후의 신호 보존 정책까지 맞춰야 한다.
- **정확도 개선 후보:** 실제 업로드 분포에서 오래된 특정 시간대에 신호가 몰린다면 1시간 버킷을 검토한다. 합성 표본의 일치율로 제품의 허용 오차를 임의로 확정하지 않는다.
- **규모 한계:** 기존 `2026-09-14-hotzone-scale-sweep.md`는 격자 수를 늘린 실험이다. 이번 “신호 100만 건/격자 1만 개”와 그 문서의 “격자 약 100만 개”는 서로 다른 조건이다.

포트폴리오에 쓸 수 있는 불릿:

> 핫구역 집계를 인덱스 기반 SQL, DB 결과 캐시, Redis 시간 버킷으로 비교 검증. 로컬 100만 업로드 신호에서 동일 45시간 집계 중앙값 47.4ms 대비 Redis 합산 5.0ms를 확인하고, 캐시 만료 구간 지연과 집계 정확도 손실을 함께 평가했다.

> Redis 합산 결과의 30초 캐시 유무를 비교해, 초당 100회 조회에서 Redis CPU 시간 94.1%, p99 48.4% 감소를 확인했다. 현재 방식은 세 회차 총 9,900건을 실패 없이 처리했다. 수치는 저장소 경로 비교이며 운영 API 실측은 아니다.

> 1/3/6시간 버킷의 순위 일치율과 자원 비용을 비교했다. 1시간 버킷은 6시간보다 메모리 약 3.8배, 재계산 시간 약 2.4배가 필요했으며, 오래된 업로드 집중 표본에서는 상위 50 일치율이 2%에서 100%로 높아졌다.

사용하면 안 되는 표현: “운영 DB 병목을 Redis로 해결”, “핫구역 API 9.5배 개선”, “정확한 48시간 랭킹 보장”, “Redis만 100 requests/s 처리 가능”.

## 실행 기록과 한계

- 첫 100만 건 적재는 조회용 2초 제한이 COPY에도 적용돼 중단됐다. 적재에만 60초를 적용하고 처음부터 다시 실행했다. 실패한 적재 결과는 성능 표에 섞지 않았다.
- 부하 모델은 응답을 기다리지 않고 고정 시각에 요청을 예약한다[^5]. 지연에는 Python 실행기 대기도 포함한다. macOS의 타이머와 스레드 스케줄링 비용이 있어 마이크로벤치와 부하 지연의 절대값은 다르다.
- 실패한 요청을 성공 지연 백분위수에 넣지 않았다. 성공 지연만 보고 성능이 좋다고 해석하지 않도록 타임아웃과 누락 수를 같이 본다.
- 실측 조회 범위는 저장소까지다. 인증, Spring, 네트워크 서비스 홉, DTO 변환, 뷰포트 필터, 구역 이름 DB 조회는 포함하지 않았다.
- 실측 부하 중에는 신호를 추가하지 않았다. 쓰기 혼합 부하, 장애 복구, Redis 신호 유실은 이번 검증 범위 밖이다.
- 신호 수 100만은 72시간 누적 합성 표본이며 실제 FillMap 사용량이 아니다. 운영 성능과 비용으로 환산하지 않는다.
- 현 서비스는 Redis 장애와 대기열 포화 시 핫구역 신호 유실을 허용한다. 정확한 DB 원본 집계와 내구성까지 같다고 설명할 수 없다.
- `korean-humanizer`, `tech-term-footnotes` 적용. 작성 후 줄표와 상투어 검색, 수치 대조를 별도 실행했다.

[^2]: TTL은 캐시가 자동으로 만료되는 시간이다. 만료 후 첫 요청은 결과를 다시 계산해야 한다.
[^3]: 순차 스캔은 테이블 행을 훑는 방식이다. 많은 행을 읽는 집계에서는 인덱스 접근보다 싸다고 판단될 수 있다.
[^4]: 집합 일치율은 정확한 집계의 상위 50개 중 근사 집계에도 포함된 격자의 비율이다. 점수 오차나 순서 일치율과 다르다.
