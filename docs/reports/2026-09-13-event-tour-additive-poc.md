# 행사 범위·투어 추천 추가 도입 기술검증

검증일: 2026-09-13 / 기준 커밋: `02c89042` / 실험 코드와 결과는 미커밋 워킹트리

## 판정

**기존 격자·행사·경로 기능을 유지하면서 추가할 수 있습니다.** 다만 PDF의 새 Venue 구조를 그대로 옮기는 방식은 현재 코드와 중복됩니다. 기존 행사 위치에 정밀 경계를 연결하고, 행사 내부의 구간·출입구·관람 지점을 추가하는 방향이 적합합니다. 이는 기술검증에 따른 제안이며 확정된 제품 설계가 아닙니다.

바로 제품에 넣을 수 있다는 판정은 아닙니다. 실제 영상 위치, 긴 행사장의 신청 범위, 검수된 보행 데이터가 필요합니다. 이번 작업은 독립 실험이며 BE API·스키마·제품 요구사항은 바꾸지 않았습니다.

## 공간 조회에서 확인한 차이

실제 청계천 중심선에 편측 20m 경계를 만들고 주변에 합성 좌표 100,000개를 배치했습니다. 좌표 변환은 현재 `GridConstants`의 EPSG:5179 정의를 사용했습니다. 공개·정상·처리 완료 조건을 만족하는 영상은 85,287건입니다.

| 조회 방식 | 결과 건수 | 정확한 판정과 차이 |
|---|---:|---:|
| 경계와 겹치는 격자만 조회 | 3,838 | 경계 밖 2,885건 포함 |
| 경계로 직접 좌표 판정 | 953 | 기준 |
| 격자로 후보 축소 후 같은 경계 판정 | 953 | 양방향 ID 차집합 0건 |

**격자는 후보를 줄이는 용도로 재사용하고, 좁은 경계의 최종 판정은 실제 좌표로 해야 합니다.** 격자 점령·도감 규칙은 이 조회와 분리할 수 있습니다.

추가로 재현한 누락 사례는 다음과 같습니다.

- 게시 당시 격자 절반만 존재했다고 가정하면, 그 격자만 연결한 목록에서 경계 안 영상 493건이 빠졌습니다. 현재 격자는 처음 필요할 때 생성되므로[^2] 행사 경계의 전체 셀을 계산하는 방식이 필요합니다.
- 경계를 편측 20m에서 40m로 넓히고 셀 목록을 갱신하지 않으면 새 경계 안 영상 75건이 빠졌습니다. 경계와 셀 목록을 함께 갱신해야 합니다.
- 경계 안 953개 좌표를 각각 자기 격자 중심으로 바꾸면 555개가 경계 밖으로 판정됐습니다. 실제 행사 영상은 행사 위치의 대표 격자를 쓰므로 이 숫자는 실서비스 오차율이 아니라 좌표 손실의 재현입니다.
- 다리 위·아래처럼 평면 좌표가 같으면 2차원 공간 판정에서 구분되지 않았습니다. GPS 확인 횟수를 늘려도 이 문제는 해결되지 않습니다.

영상 피드의 공개 범위·삭제·블라인드·차단 조건과 기존 `event_videos` 연결을 유지해야 합니다. 행사에 명시적으로 연결된 영상과 단순히 경계 안에서 촬영한 영상은 서로 다른 조회 근거입니다.

최종 실행에서 같은 953개 ID를 반환하는 세 조회를 비교했습니다.

| 조회 | SQL p50 | SQL p95 | 실제 사용한 계획 |
|---|---:|---:|---|
| 직접 경계 판정, 기존 인덱스 형태 | 105.89ms | 110.63ms | 공개 조건을 통과한 행 전체 검사 |
| 격자 후보 + 경계 판정 | 8.92ms | 10.30ms | 격자 키 인덱스로 후보 축소 |
| 직접 판정 + 실험용 공간 인덱스 추가 | 86.97ms | 93.25ms | 공간 인덱스[^6] 사용 |

기존 격자 인덱스의 선두 키와 공개 조건을 모사한 임시 인덱스에서 효과를 확인했습니다. 모든 실제 인덱스·데이터 분포를 복제한 실험은 아닙니다. 청계천처럼 가늘고 굽은 범위에서 이 방식이 유효했으며, 다른 행사장이나 운영 부하에서도 항상 우세하다고 단정할 수 없습니다. 제품 DB에 새 인덱스는 만들지 않았습니다.

## 투어 실험

OSM 수로 중심선을 20개 구간으로 나눴습니다. **출입구 11곳, 이동속도 70m/분, 구간별 관람 2분, 출입 각 2분은 모두 실험용 가정**입니다. 수로 중심선은 실제 보행 경로가 아닙니다.

| 출발점 | 시간 예산 | 선택 구간 수 | 계산된 총시간 | 방향 |
|---|---:|---:|---:|---|
| 상류 쪽 노드 0 | 30분 | 2 | 19.80분 | 하류 |
| 상류 쪽 노드 0 | 60분 | 6 | 51.39분 | 하류 |
| 상류 쪽 노드 0 | 120분 | 14 | 114.59분 | 하류 |
| 중간 노드 12 | 30분 | 2 | 19.80분 | 상류 |
| 중간 노드 12 | 60분 | 6 | 51.39분 | 상류 |
| 중간 노드 12 | 120분 | 12 | 98.79분 | 상류 |

- 출입구가 6곳뿐인 최초 가정에서는 상류 출발 30분 코스가 없었습니다. 검증이 처음 실패한 이유이며, 현재 검사에는 이 조건의 정상 결과를 `추천 없음`으로 남겼습니다.
- 구간 5가 폐쇄됐거나 접근성 정보가 없으면 노드 4의 출구에서 끝났습니다. 중간 구간을 삭제하고 반대편을 잇지 않습니다.
- 출구가 없거나 진입만으로 예산을 넘으면 추천하지 않습니다. 같은 입력은 같은 결과를 냅니다.
- 경로상의 10%·35%·70% 지점 누적 거리를 0.1m 이내 계산 오차로 복원했습니다. 이는 계산 정합성이며 현장 위치 정확도가 아닙니다.
- 현재 실험은 분기 없는 선형 경로만 다룹니다. 갈림길, 왕복, 혼잡, 시간대별 폐쇄가 필요하면 연결 관계를 나타내는 그래프[^3]로 확장해야 합니다.

기존 `RouteOrderPlanner`는 관심사·거리 기반 장소 순서와 약 10km 이동 제한을 처리합니다. 행사 내부의 시간 예산·출입구 조건은 별도 계산으로 추가하고, 기존 추천 기능을 유지하는 편이 적합합니다. 기존 TMap 도보 조회는 행사 외부 접근 경로의 후보이며, 임시 행사 동선·접근성을 보증하지 않습니다.

## 검증 범위와 재현

- 공간 실험: 로컬 PostgreSQL 16.4 / PostGIS 3.4.3, 합성 데이터만 사용. 모든 테이블은 TEMP이고 마지막에 ROLLBACK[^4]했습니다.
- 실행시간: 각 SQL은 예열 5회 후 30회, 단일 연결, JIT 비활성으로 측정했습니다. 실행 계획과 원시 요약은 아래 JSON에 있습니다. API·네트워크·동시접속 성능을 뜻하지 않습니다.
- 투어 계산: Node.js 22.23.1, 예열 100회 후 1,000회. 외부 API·DB·AI 호출을 포함하지 않습니다. PDF의 API p95[^5] 100ms 목표는 이번 결과만으로 통과 판정할 수 없습니다.
- 기존 코드: 행사 신청 검증, 행사 기간 가드, 기존 경로 정렬 테스트 56건 통과. 전체 통합 테스트·권한 경합·실서비스 데이터·현장 보행은 이번에 실행하지 않았습니다.
- 로컬 Docker가 꺼져 있어 OrbStack을 시작했습니다. 처음 `postgres` DB에는 PostGIS 함수가 없어 기존 `fillmap` DB에서 TEMP 실험으로 진행했습니다. 애플리케이션 테이블과 시드는 건드리지 않았습니다.
- 경계 수정 실험은 버퍼를 영상마다 다시 만들지 않도록 경계를 한 번 계산한 임시 결과로 재사용합니다. 실행시간 표는 데이터 생성·좌표 변환 시간을 제외한 조회 시간입니다.

## 추가 도입 순서 제안

1. **운영자가 검수한 행사 경계부터 연결합니다.** 기존 행사 위치와 별도 정밀 경계를 연결하고, 전체 셀을 계산합니다. 경계 수정과 셀 목록 갱신은 같은 버전으로 반영해야 합니다.
2. **정확한 위치가 있는 영상부터 경계 조회를 제공합니다.** 행사 영상의 대표 좌표는 실제 촬영 좌표로 취급하지 않습니다. 신규 좌표 입력·보존 정책은 PRD에서 정합니다.
3. **검수된 구간과 출입구로 시간별 코스를 추가합니다.** 첫 대상은 분기 없는 한 행사장으로 한정합니다. 접근성 정보를 확인할 수 없는 구간은 해당 조건의 추천에서 제외합니다.
4. **실측 후 집계를 최적화합니다.** 먼저 기존 공개 조건을 적용한 SQL 집계를 사용하고, 동시접속 측정에서 병목이 확인되면 캐시를 추가합니다.

제품 구현 전에 정할 항목은 81칸 제한을 다룰 방법, 실제 좌표 저장 여부, 경계선 위 포함 정책, 투어 제공 기간, 출입구·접근성 데이터의 검수 주체와 갱신 절차입니다. 임의로 제한을 늘리거나 기존 업로드·행사 종료 정책을 변경하지 않았습니다.
