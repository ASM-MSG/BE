# MSG-164: [스파이크] 좌표→행정동 판별 — 폴리곤 ST_Covers vs 컬럼 레이블 성능 비교

**Owner**: A (`com.msg.fillmap.region.*`) · 스파이크(연구·포트폴리오 산출물, 배포 코드 변경 없음)
**전제**: MSG-93(역지오코딩 `ST_Covers`·`RegionQueryService`) · MSG-66(`videos.region_code` 사전 레이블 컬럼) · MSG-154(regions 3,558 시딩)

## 왜 이 스파이크인가

멘토 피드백: "감으로 하지 말고, 폴리곤 geospatial 처리와 컬럼 레이블 처리를 둘 다 구성해 성능으로 비교하라."
MSG-93 §D2가 이 비교를 별도 스파이크로 분리했고, 이 문서가 그 계량이다.

- **(a) 폴리곤 실시간 판별** — MSG-93 `findContainingRegion`: `ST_Covers(boundary_geom, 좌표)` + GEOGRAPHY GIST(`idx_regions_boundary`). 임의 좌표를 3,558개 행정동 폴리곤에 point-in-polygon.
- **(b) 사전 레이블 컬럼** — MSG-66 `videos.region_code`: 업로드 시 1회 판정해 저장해 둔 값을 **일반 컬럼으로 읽기**.

핵심 질문: **역지오코딩 쿼리가 실데이터 3,558 폴리곤에서 GIST Index Scan을 실제로 타는가**, 그리고 두 방식의 단건 레이턴시 차이가 얼마인가. (CI에 못 넣은 이유가 소량 픽스처에서 플래너 비결정성이라, 실데이터 1회 계량이 이 스파이크의 존재 이유다.)

## 측정 환경

| 항목 | 값 |
|---|---|
| DB | PostgreSQL **16.4** (x86_64, Alpine musl) + PostGIS **3.4** (GEOS/PROJ/STATS) |
| 컨테이너 | `postgis/postgis:16-3.4-alpine`, `fillmap-postgres` (로컬 공유), macOS Docker Desktop |
| regions | **3,558 실데이터** 행정동 폴리곤, `GEOGRAPHY(MULTIPOLYGON,4326)`, `idx_regions_boundary` GIST |
| arm(b) 데이터 | 격리 합성 5,000 `videos`(`region_code`=실코드 200종 순환, 서해 공해상 좌표) — 측정 후 전량 회수 |
| 좌표 샘플 | 전국 육지 25 + 경계 근처 3 = 28점(강남/부산/광주/제주/강릉…) |

> ⚠️ **보정 노트**: x86_64 이미지를 macOS(에뮬레이션)에서 돌린 개발 노트북 수치다. **절대값은 환경 종속**이고, 이 스파이크가 주장하는 결론은 **인덱스 사용 여부**와 **(a)/(b) 상대비**다 — 그 둘은 환경에 무관하게 성립한다.

## 방법론

1. **EXPLAIN (ANALYZE, BUFFERS)** — 실데이터에서 실제 실행계획·버퍼·시간. 콜드(첫 실행) 기준이라 planning/execution에 1회성 오버헤드가 섞임.
2. **정상상태 p50/p95** — plpgsql `clock_timestamp()` 하네스. warmup(플랜캐시·버퍼 프라이밍) 후 `iters=300 × 28점 = 8,400` 반복, `percentile_cont`. plpgsql 정적쿼리는 5회 뒤 generic plan을 캐시 → **앱의 서버-준비(prepared) statement와 동일 조건**. 측정은 `SELECT`만(집계 INSERT는 타이밍 밖) = **서버측 순수 statement 레이턴시**(네트워크 제외).
   - *샘플링 방식 교정*: arm(b)는 `videos.id` 범위 난수가 아니라 **실제 삽입된 bench id 배열에서** 뽑는다. `id` 시퀀스는 비트랜잭셔널·전역 공유라 동시 삽입/롤백이 범위에 구멍(없는 id)을 낼 수 있고, 없는 id 조회는 heap 접근이 생략돼 (b)를 빠르게 편향시키기 때문(기존 수치는 조용한 DB에서 측정돼 유효).
3. **pgbench 교차검증** — `-M prepared -c 1 -T 8`, `-l` 로그의 트랜잭션 레이턴시로 percentile. libpq 왕복을 포함한 **클라이언트 체감** 값.
4. **k6 부하** — **미실행**. 서버 기동(bootRun)+인증 흐름이 필요해 SQL-레벨 비교(이 스파이크의 본질)에 비해 비용 과다. 아래 §후속 제안 참조.

재현 스크립트: [`scripts/bench-msg164.sql`](../scripts/bench-msg164.sql) (단일 트랜잭션으로 셋업→EXPLAIN→하네스→`ROLLBACK` 원복→원상복구검증까지 1파일, 실행법 주석 포함).

## 측정 1 — EXPLAIN: 인덱스 사용 실측 (핵심 산출물)

### (a) 폴리곤 ST_Covers — GIST Index Scan **확인**

```
-- 강남역 (37.4979, 127.0276)
 Limit  (actual time=2.042..2.095 rows=1 loops=1)
   Buffers: shared hit=32
   ->  Index Scan using idx_regions_boundary on regions  (actual time=1.985..1.985 rows=1 loops=1)
         Index Cond: (boundary_geom && '...'::geography)          -- GIST bbox 겹침으로 후보 축소
         Filter: st_covers(boundary_geom, '...'::geography)       -- 후보에만 정밀 PIP 재검
         Rows Removed by Filter: 2                                -- 정밀검사 대상 단 2~3건
         Buffers: shared hit=32
 Planning Time: 16.586 ms      -- 콜드: PostGIS 함수비용 산정 1회성(prepared로 상각)
 Execution Time: 2.881 ms
```

- **`Index Scan using idx_regions_boundary`** — 역지오코딩이 GIST 인덱스를 실제로 탄다(스파이크 핵심 질문 = YES).
- 패턴은 `boundary_geom && 좌표`(GIST bounding-box 필터)로 후보 2~3건 추림 → 그 후보에만 `st_covers` 정밀 재검. 버퍼 25~32페이지.
- 바다/미스매치(동해상 130.5,37.5)도 동일 인덱스로 후보 0건 확인(`rows=0`, 버퍼 28). 제주(126.53,33.50)도 `idx_regions_boundary` 사용.

### (a) 인덱스 미사용 대조군 — 강제 seqscan

```
 Limit  (actual time=8.194..208.226 rows=1 loops=1)
   ->  Gather (Workers Launched: 1)
         ->  Parallel Seq Scan on regions  (actual time=91.185..91.186 rows=0 loops=2)
               Filter: st_covers(boundary_geom, '...'::geography)
               Rows Removed by Filter: 1778                       -- 워커당 1,778 × 2 = 3,556 폴리곤 전수 PIP
               Buffers: shared hit=1336 read=1335
 Execution Time: 208.909 ms
```

- 인덱스를 끄면 3,558 폴리곤에 **전수 `ST_Covers`** → **208.9 ms**, 버퍼 2,671페이지. GIST가 **동일 쿼리를 ~수천 배** 줄인다(208.9ms → warm 0.05ms).
- (재현 스크립트 교정 후 1회 재검증: 동일 `Parallel Seq Scan`, warm 실행 **192.2 ms**·버퍼 2,671 전량 hit. 절대 ms는 캐시 온도로 ~190–210ms 흔들리나 플랜·전수 PIP·수천배 비율은 불변.)

### (b) 사전 레이블 컬럼 — PK 단건 읽기

```
-- 대상 id 는 측정 밖에서 미리 선택(\gset) → EXPLAIN 은 순수 PK 조회만 (탐색/정렬 비용 불혼입)
 Index Scan using videos_pkey on videos  (cost=0.27..8.29 rows=1 width=11) (actual time=0.025..0.026 rows=1 loops=1)
   Index Cond: (id = 23328)
   Buffers: shared hit=6
 Planning Time: 0.034 ms
 Execution Time: 0.035 ms
```

## 측정 2 — 단건 레이턴시 p50/p95 (정상상태)

**서버측 순수 statement 레이턴시** (plpgsql 하네스, 각 8,400 샘플)

| 방식 | p50 | p95 | p99 | avg | max |
|---|---|---|---|---|---|
| **(a) 폴리곤 `ST_Covers`** | 0.053 ms | 0.132 ms | 0.218 ms | 0.066 ms | 2.99 ms |
| **(b) `region_code` 컬럼 읽기** | 0.006 ms | 0.006 ms | 0.010 ms | 0.006 ms | 0.13 ms |

**클라이언트 체감 레이턴시** (pgbench, prepared, 1 client, 8s — libpq 왕복 포함)

| 방식 | p50 | p95 | p99 | max | tps | 처리량(8s) |
|---|---|---|---|---|---|---|
| **(a) 폴리곤 `ST_Covers`** | 0.101 ms | 0.182 ms | 0.268 ms | 32.2 ms | 8,588 | 68,606 tx |
| **(b) `region_code` 컬럼 읽기** | 0.050 ms | 0.055 ms | 0.061 ms | 13.5 ms | 19,208 | 153,471 tx |

- 두 측정이 정합: pgbench−하네스 차 ≈ **0.045 ms**(양쪽 arm 공통) = libpq 왕복 바닥값. arm(b)에서 서버측 0.006 → 클라 0.050 이 그 왕복을 그대로 드러낸다.
- **순수 연산비**(왕복 바닥 제거)는 (a) ≈ 0.05ms vs (b) ≈ 0.006ms — **ST_Covers 계산 자체가 레이블 읽기의 ~8–9배**. 단, **둘 다 p95가 0.2ms 미만**으로 절대값은 아주 작다(GIST 덕).

## (a) vs (b) 결론 · 판정

**판정: 현재 아키텍처 유지 (조정 불요).**

1. **결과는 동일, 연산량만 다르다.** 두 방식 모두 같은 행정동을 돌려준다. (a)는 호출마다 GIST 하강+정밀 PIP를 하고, (b)는 미리 계산해 둔 값을 읽을 뿐이다. (b)가 per-op ~2배(클라 체감)~9배(순수 연산) 싸지만, **(b)의 그 값은 이미 누군가 (a)를 1회 실행해 채워둔 것**이다 — 비용이 사라진 게 아니라 **쓰기 시점으로 상각**됐다.
2. **현재 설계가 이미 (b) 우위 구조다.** MSG-66/93 아키텍처 = 업로드 시 `ST_Covers` **1회**(쓰기, ~0.05–0.1ms)로 `videos.region_code`를 채우고, 이후 **모든 조회 경로는 레이블 읽기**(~0.006ms). 즉 고빈도 읽기는 (b)로 상각되고, 쓰기만 단발 sub-ms를 낸다. 이 스파이크는 그 설계를 **정량으로 검증**한다.
3. **(a)가 불가피한 곳은 딱 하나** — *레이블이 없는 임의 좌표*를 판정할 때(MSG-93 역지오코딩의 사용자 탭 좌표, 또는 업로드 라벨링 그 자체). 이 경로는 **저빈도·사용자 트리거·단건**이라 GIST가 sub-ms로 묶어주며, MSG-93 §D1(ADR 예외 허용)의 근거와 정확히 일치한다.

> 요약 한 줄: **폴리곤 방식은 "느려서" 문제가 아니라(GIST로 sub-ms) 조회마다 반복하면 낭비라서, 쓰기 1회 판정+읽기 레이블(현행)이 정답이다 — 스파이크가 이를 확인.**

## 후속 제안

- **k6 부하는 후속으로.** SQL-레벨에서 두 arm 모두 p95<0.2ms·단일클라 8.5k~19k tps로 병목 아님이 확인돼 우선순위 낮다. 실행한다면 MSG-93 `GET /api/regions/reverse-geocode`를 대상으로 MSG-134 러너 방법론 재사용(대상: (a) 경로. (b)는 별도 read 엔드포인트가 생길 때).
- **역지오코딩이 예상 밖 고빈도화되면**(예: 지도 이동마다 호출) MSG-93 §D1 튜닝 노브대로 **클라 디바운스 또는 좌표-스냅 캐시**. 현재 트래픽 근거로는 불요(YAGNI).
- **배포 코드 변경 없음.** 이 스파이크는 계량·검증만. `region`/`video` 런타임 무변경.

## 검증 (DB 원상복구)

재현 스크립트는 전체를 **단일 트랜잭션**에 담고 끝에서 `ROLLBACK` 한다 → 합성 행·임시테이블·함수·플래너 통계 무엇도 커밋되지 않아 원복이 구조적으로 보장된다(중간 실패 시에도 세션 종료로 자동 롤백 — 실측 확인). `regions` 변경·`TRUNCATE` 없음. 최종 카운트:

| 항목 | 기대 | 실측 |
|---|---|---|
| regions | 3558 (불가침) | **3558** |
| videos | 0 | **0** |
| users | 4 | **4** |
| grids | 0 | **0** |
| user_grids | 0 | **0** |
| bench_msg164_pts(임시) | 없음 | **0** |
| videos `pg_class.reltuples` | 0 (낡은 통계 잔류 없음) | **0** |

> 통계 주의: `ANALYZE` 의 `reltuples` 는 **inplace 갱신**이라 `ROLLBACK` 으로도 안 지워진다(본 스파이크서 실측: 롤백 후 100 잔류). 그래서 스크립트는 ANALYZE 를 아예 하지 않고 — (b)는 PK 단건 조회라 통계가 플랜에 영향 없음 — 통계 잔류를 원천 차단한다.

> 시퀀스 주의: users/videos id 시퀀스는 run당 ~5,001 전진한 채 남는다 — `nextval` 은 비트랜잭셔널이라 ROLLBACK 대상이 아니다. surrogate key 갭이라 기능 영향 0(어떤 롤백된 INSERT 든 동일하게 소비)이며, "원상복구"의 범위는 행·통계·객체까지고 시퀀스 위치는 포함하지 않는다(Codex 5차 리뷰 반영 명시).

+ 스파이크 중 생성된 빈 볼륨 `be-msg164_postgres_data`·컨테이너 `/tmp` pgbench 로그 제거. 공유 DB는 벤치 이전 상태로 복구됨.
