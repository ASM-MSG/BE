# MSG-278: 미션 스탬프 판정의 촬영 시각 위조 방어 — 미래 recordedAt 거부

**Owner**: B (`com.msg.fillmap.video.*` — infrastructure.md 실측, video 패키지는 Owner B)

> 요구사항 정본: `docs/prd/MSG-278-prd.md` (상태: 검토됨, §8 성민 확정 2건 — 갤러리 포함 인정
> 유지 · 허용 오차 5분). 이 스펙은 PRD FR-1~5·비기능에 "어떻게"만 붙인다.

## 개요

업로드 확정(POST)·교체(PUT)의 `recordedAt`이 **서버 현재 시각(UTC) + 5분을 초과**하면
`ApiException(RECORDED_AT_IN_FUTURE, 3424)` 400으로 거부한다. 5분 이내 미래·모든 과거는 통과.
판정 쿼리(`findCompleted`)·스탬프 발급 로직·DB는 무수정 — 방어는 입력 경계 한 곳이다.

## 배경 · 목표

- `recordedAt`은 클라 신고값인데 검증이 `@NotNull`뿐이라(실측: `VideoUploadRequestDto` L38-39),
  미래·기간-안 시각을 조작하면 축제가 끝난 뒤에도 스탬프를 딸 수 있다. dev에 기간형 미션
  416건이 실적재된 상태(MSG-290)라 라이브 노출 중.
- 목표: 트리비얼 위조(미래 시각) 차단. "기간 안 과거 시각" 위조는 PRD 비목표 — 잔존 위험으로
  수용·문서화(§도메인 로직 끝).

## 도메인 로직

### D1. 시간대 기준 — `recordedAt`은 UTC 순간, 비교 now도 UTC (실측 확정)

`recordedAt`은 시간대 무표기 `LocalDateTime`이지만 **UTC 순간**으로 해석한다. 근거(실측):

- 저장된 `videos.recorded_at`은 `MissionRepository.findCompleted`(L65-66)에서
  `m.start_at/end_at`과 직접 비교되고, missions 기간은 UTC 순간이다(MSG-223 §D3).
- 활성 술어는 `statement_timestamp() AT TIME ZONE 'UTC'`(`findAwardCandidateIds` L44-45) —
  "저장값이 UTC 순간이라 세션 타임존(KST) 비교는 9시간 스큐" 주석이 그 자리에 있다.

따라서 비교용 서버 now는 `LocalDateTime.now(clock)` + **`Clock.systemUTC()`** 여야 한다.
`Clock.systemDefaultZone()`이면 KST JVM에서 now가 +9h 앞서 — 반대로 이 검증에서는 클라의
정상 UTC 값이 전부 "9시간 과거"가 되어 통과야 맞지만, 클라가 KST 벽시계를 보내는 버그를
은폐하고, 테스트·환경별로 판정이 갈린다. MSG-222 전례(활성 판정 +539분 스큐 실측 →
`Clock.systemUTC()` 교체)를 그대로 따른다.

### D2. 검증 지점 — 서비스 검증 (bean validation 아님)

`VideoServiceImpl`에 공유 private 메서드 하나. 두 경로가 모두 이 메서드를 지난다:

```java
private static final Duration RECORDED_AT_TOLERANCE = Duration.ofMinutes(5);

private void validateRecordedAt(LocalDateTime recordedAt) {
	if (recordedAt.isAfter(LocalDateTime.now(clock).plus(RECORDED_AT_TOLERANCE))) {
		throw new ApiException(VideoErrorCode.RECORDED_AT_IN_FUTURE);
	}
}
```

- **호출 위치 (실측)**:
  - `saveVideo`: visibility 파싱·`validateCoordinate`(L112-117)와 나란히, `confirmUpload`(L118)
    **전** — 잘못된 값이 S3 부수효과(advisory lock·headObject·복사) 없이 거부되게 (MSG-204
    FR-3 선례: "confirmUpload 전에 확정한다" 주석 L110).
  - `replaceVideo`: `findOwnedVideo`·`isDeleted` 검증(L164-167) 뒤, `confirmUpload`(L170) **전**.
    소유권·존재가 먼저인 게 기존 에러 우선순위와 일관.
- **bean validation(@Valid) 배제 근거 (실측)**:
  - `MethodArgumentNotValidException`은 `GlobalExceptionHandler`가 공통 `BAD_REQUEST`로
    변환한다 — FR-4의 도메인 3xxx 구분 코드를 낼 수 없다.
  - `@Future`류는 5분 허용 오차를 표현 못 하고, 커스텀 validator에 Clock 주입은 어색하다.
  - 선례: 값 검증을 서비스에서 하는 `parseVisibility`(MSG-204, 3420) — null 아닌 형식 위반은
    서비스가 도메인 코드로 거른다.
- **경계 의미**: `recordedAt == now + 5분` 정확히는 **통과**(isAfter — 초과만 거부).
  5분은 단말 시계 스큐 커버(PRD §8), 상수 `RECORDED_AT_TOLERANCE`로 고정 — 설정화하지 않는다.

### D3. Clock 주입 — 이중 생성자 선례, 기존 테스트 무수정 유지

`MissionQueryServiceImpl`(L64-84)·`HotScoreCommandServiceImpl`(L51-55)·시더들의 선례:
`@Autowired` 기본 생성자가 `Clock.systemUTC()`로 위임, 전체 생성자는 테스트 고정 클럭용.

`VideoServiceImpl`은 `@RequiredArgsConstructor` + final 12개다. 다음으로 최소 반영:

- `private final Clock clock;` 필드를 **마지막에** 추가 — Lombok 생성자가 13-인자 전체
  생성자(테스트 고정 클럭용)가 된다.
- 기존 12-인자 시그니처의 `@Autowired` 생성자를 수기 추가, `this(…, Clock.systemUTC())` 위임.
  → 기존 유닛 테스트 5곳(VideoGlobalCoverServiceTest·VideoEncodingTriggerTest·VideoS3CleanupTest
  ·VideoGridQueryServiceTest·VideoPresignTest)의 `new VideoServiceImpl(12개)` 호출이 **무수정**
  컴파일·동작한다.

### D5. 기존 테스트 픽스처 UTC 정규화 — 이 티켓의 실제 블래스트 반경 (실측)

(JVM 기본존 — 로컬·CI KST)를 넣는다. UTC 기준 검증이 들어가면 이 값들은 **UTC now보다
+9h 미래**라 전부 3424로 오거부된다 — MSG-222 스큐 함정의 테스트판. `LocalDateTime.now(
ZoneOffset.UTC)`로 교체한다 (`VideoMissionIntegrationTest` L134가 이미 이 형태 — MSG-223에서
같은 함정을 밟고 고친 선례).

  픽스처 정규화가 같은 이유)
