# MSG-350: AI 추천 하이라이트 구간을 영상 조회 응답에 포함

**Owner**: B

> 요구사항 정본: `docs/prd/MSG-350-prd.md` (검토됨, 2026-08-10 성민 승인). 이 스펙은 PRD의
> FR 5건에 "어떻게"만 붙인다. PRD와 어긋나는 서술이 보이면 PRD가 이긴다.

## 개요

AI가 뽑아 `videos.highlights` jsonb[^1] 컬럼에 저장까지 된 하이라이트 구간을, 단건 영상 조회
API(`GET /api/videos/{videoId}`) 응답의 `highlights` 필드로 노출한다. 새 쿼리 없이 이미 읽고
있는 엔티티의 컬럼 하나를 응답 DTO에 실어 주는 작업이다. 상위 스토리 MSG-141의 완료 조건
중 미구현으로 남아 있던 "응답에 포함" 절반을 닫는다.

## 배경 · 목표

하이라이트 파이프라인은 AI 산출(MSG-159)과 저장(MSG-145, MSG-150)까지 끝나 있는데 꺼내 주는
API가 없어서, 프론트 추천 화면(MSG-303)이 mock 데이터로만 동작한다. 이 티켓으로 FE가
실데이터를 받아갈 수 있게 한다.

목표는 두 가지다. 단건 조회 응답으로 하이라이트 구간을 받을 수 있게 하고, 없는 경우의 표현과
배열 순서의 의미를 Swagger[^2] 계약으로 명시한다.

**범위 밖** (PRD 비목표, 재확인): 격자 영상 목록과 전역 목록 등 목록성 응답에는 넣지 않는다.
구간별 추천 사유 라벨은 AI 계약에 없어 만들지 않는다. 구간 품질 보정과 업로드 확정 전 선분석
API는 MSG-351이다. 영상 길이별 카드 노출 티어는 FE 정책이라 서버는 항상 저장된 전체(최대
3구간)를 내려준다.

## 성공 기준

1. 하이라이트가 저장된 READY 영상을 단건 조회하면 응답 `highlights`에 저장 형식 그대로
   `[[시작초, 끝초], ...]` 배열이 실린다 (FR-1).
2. 저장 값이 null이거나 빈 배열인 영상은 응답 `highlights`가 null이다 (FR-2, null 통일).
3. Swagger 스키마에 nullable과 "배열 순서 = 추천 우선순위(첫 요소가 최우선)"가 명시된다
   (FR-2, FR-5).
4. 접근 제어, 조회수 증가, 기존 응답 필드 등 단건 조회의 나머지 동작은 바이트 하나 변하지
   않는다 (FR-3). 기존 단건 조회 테스트가 전부 green이면 검증된 것으로 본다.
5. 하이라이트 유무 각각을 검증하는 테스트가 기존 관례(한국어 메서드명)로 추가된다 (FR-4).

## API 명세

기존 API의 응답 필드 추가만 있다. 신규 endpoint, 신규 에러 케이스, developCode 추가는 없다.

- **Endpoint**: `GET /api/videos/{videoId}` (기존, MSG-206)
- **응답**: `SuccessResponse<VideoPlaybackResponseDto>` (기존 그대로, 필드 1개 추가)

추가 필드:

| 필드 | 타입 | 설명 |
|------|------|------|
| `highlights` | `List<List<Double>>`, nullable | AI 추천 하이라이트 구간 `[[시작초, 끝초], ...]`. 최대 3구간, 초는 소수점 둘째 자리. **배열 순서가 추천 우선순위다(첫 요소가 최우선 추천)**. 하이라이트가 없으면(READY 이전, FAILED, AI 비활성 시절 처리분, AI가 0구간 반환) null |

Swagger 스키마 문안(DTO `@Schema` description에 그대로 반영):

```text
AI 추천 하이라이트 구간 [[시작초, 끝초], ...]. 최대 3구간, 초는 소수점 둘째 자리.
배열 순서가 추천 우선순위(첫 요소가 최우선 추천). 없으면 null (READY 이전·FAILED·0구간 포함,
빈 배열은 내려가지 않는다)
예시: [[0.0, 4.25], [12.0, 18.5], [20.0, 27.5]]
```

`nullable = true`를 명시하고, 기존 nullable 필드들(playbackUrl, zoneName 등)과 같은 관례로
record 클래스의 `requiredProperties` 목록에는 추가한다 (필드 자체는 항상 존재, 값이 null일
수 있음).

에러 케이스: 변화 없음. 404(VIDEO_NOT_FOUND), 403(VIDEO_FORBIDDEN), 401은 기존 판정
그대로이며, 접근이 거부된 요청에는 highlights가 노출될 경로 자체가 없다 (응답 DTO가
만들어지기 전에 던져진다).

## 도메인 로직

새 도메인 규칙은 없다. 판정 로직 추가 없이 저장 값의 노출과 정규화만 있다.

- **접근 제어 불변**: `getVideoPlayback`의 first-match[^3] 판정(존재/DELETED → BLINDED →
  visibility → processing_status)을 통과한 요청만 응답을 받으므로, highlights도 자동으로 같은
  제어 아래 놓인다. 별도 분기를 만들지 않는다.
- **값 보장 범위**: 계약상 값이 보장되는 것은 AI 처리를 거쳐 READY가 된 영상뿐이다. "AI가 안
  돈 영상"과 "AI가 돌았지만 0구간인 영상"은 저장 계약(MSG-145)상 컬럼 값만으로 구분되지
  않으므로(null과 빈 배열 혼재), 응답 계약도 이 구분을 약속하지 않는다 (PRD 비기능 데이터
  정합 항목).

### 설계 결정 D-1: 정규화 위치는 `of()` 팩토리

PRD가 열어 둔 유일한 재량이다 (변경 파일 목록에서 VideoServiceImpl은 "정규화를 서비스에서
하기로 결정되는 경우만" 수정). **DTO의 `of()` 정적 팩토리에서 정규화한다.**

```java
List<List<Double>> highlights = video.getHighlights();
// 저장 혼재(null 또는 [])를 응답 null 하나로 정규화 (MSG-350 FR-2)
if (highlights != null && highlights.isEmpty()) {
	highlights = null;
}
```

근거: 이 정규화는 비즈니스 판정이 아니라 표현 계층의 계약 정리다(무엇이 옳은 값인지가 아니라
어떻게 보여줄지). `of()`는 이미 엔티티에서 응답으로의 매핑을 전담하고 있어 자리가 맞고,
`VideoServiceImpl.getVideoPlayback`을 한 줄도 건드리지 않는 가장 작은 diff가 된다. 서비스에
두는 대안은 이후 다른 응답(예: 목록)이 highlights를 실을 때 정규화를 각자 반복하게 만드는데,
지금은 그 소비자가 없으므로(비목표) 팩토리 한 곳이면 충분하다.

### 변경 지점 (전체)

| 파일 | 변경 |

| `src/main/java/com/msg/fillmap/video/dto/VideoPlaybackResponseDto.java` | record 컴포넌트 `highlights` 추가(`List<List<Double>>`), `@Schema` 위 문안 반영, `requiredProperties`에 추가, `of()`에서 D-1 정규화 후 전달 |

컨트롤러, 서비스, 엔티티, 폴러, AiClient, VideoStatusWriter는 건드리지 않는다. highlights를
쓰는 기존 코드(저장 경로)와 이 티켓(노출 경로)은 `Video.getHighlights()` 하나로만 만난다.

## 데이터 모델

변경 없음. `videos.highlights` jsonb 컬럼은 MSG-145에서 이미 존재하고, 엔티티 매핑
(`Video.highlights`, `List<List<Double>>`, `@JdbcTypeCode(SqlTypes.JSON)`)도 이미 있다.
**Flyway 마이그레이션 없음.**

## 계약 변경

없음. `GridQueryService`, `HotZoneService`, `UserGridQueryService`, `UserOidcCommandService`
등 Owner 간 계약 인터페이스는 건드리지 않는다. `VideoPlaybackResponseDto`는 Owner B 내부의
응답 DTO이고, 변경도 필드 추가라 기존 FE 소비자에 하위 호환이다.

기존 관례(JUnit 5, AssertJ, 한국어 백틱 메서드명)를 따른다. 메서드명 후보:

**VideoPlaybackControllerTest** (기존 파일):

```java

void 단건_조회_응답에_highlights_배열이_실린다() throws Exception {
	// Then: jsonPath("$.data.highlights[0][0]") 등으로 직렬화 형태 검증
```

컨트롤러 테스트는 기존 `단건_조회는_200과_재생메타를_반환한다`에 jsonPath 단언만 얹는 확장도
허용한다. JSON 직렬화 결과가 `[[0.0, 4.25], ...]` 중첩 배열임을 한 번은 통합 레벨에서 봐야
하므로(record[^4] 필드 추가가 Jackson 직렬화까지 이어지는지), 서비스 테스트만으로 끝내지
않는다.

기존 테스트 23건(서비스 19, 컨트롤러 4)은 수정 없이 전부 통과해야 한다. `of()` 시그니처가
바뀌지 않으므로(엔티티에서 직접 읽음) 컴파일 파급도 없다.

## 미해결 질문

없음. PRD의 미해결 질문 3건은 2026-08-10 성민 확인으로 모두 해소됐고(null 통일, 라벨 제외,
품질 보정 MSG-351 분리), 스펙 단계에서 새로 생긴 질문도 없다.

[^1]: jsonb: PostgreSQL의 JSON 컬럼 타입. 하이라이트 구간은 별도 테이블 없이 `videos.highlights` 한 컬럼에 배열 그대로 저장돼 있다.
[^2]: Swagger: API 요청과 응답 형식을 자동 문서화하는 도구. 이 프로젝트는 springdoc으로 생성하며, `@Schema` 어노테이션의 description과 nullable이 그대로 FE가 보는 계약 문서가 된다.
[^3]: first-match: 여러 거부 조건을 정해진 순서로 검사해 처음 걸리는 것 하나로 판정하는 방식. 단건 조회는 존재 여부, 블라인드, 공개범위, 처리상태 순서로 검사한다 (MSG-206 확정).
[^4]: record: Java의 불변 데이터 클래스 문법. 필드(컴포넌트)를 추가하면 생성자 시그니처가 함께 바뀌지만, 이 DTO는 모든 생성을 `of()` 팩토리로만 하므로 호출부 파급이 팩토리 내부 한 곳에 갇힌다.
