# MSG-330: 핫구역 신호 폐기 로그가 업로드 응답을 붙잡는 문제

**Owner**: A (`com.msg.fillmap.hotzone.*`)

**PRD 면제**: 버그 수정 — 기존 요구사항(MSG-233 §D6 "응답 경로 분리")의 복구다. 무엇이 옳은
동작인지는 이미 정의돼 있고 요구사항이 바뀌지 않는다.

## 문제

`HotScoreCommandServiceImpl.recordUpload()` 의 catch 가 큐 포화(`RejectedExecutionException`)마다
예외 스택을 통째로 WARN 에 남겼다. 이 catch 는 업로드 트랜잭션 afterCommit 콜백에서 돌고,
그 콜백은 요청 스레드에서 실행된다. 큐가 넘치는 순간 업로드 응답이 로그 쓰는 시간만큼 늦어졌다.

신호 적재를 별도 스레드로 뺀 이유가 "Redis 가 느려도 업로드 응답은 안 늦어지게"(§D6)인데,
정작 큐가 넘치는 상황에서 그 보호가 로그 때문에 깨졌다. 큐 포화는 사고가 아니라 설계가 예상하고
허용한 흐름(§D4 신호 유실 허용)이라 스택 추적을 남길 이유도 없다.

발견: MSG-321 부하 측정 (`docs/MSG-321-hotzone-load-test.html` 5절).

## 변경

폐기 경로를 `RejectedExecutionException` 전용 catch 로 분리하고, 스택 추적 대신 건수만 세서
주기(60초) 요약 한 줄로 내보낸다. 포화가 아닌 실패(Redis 장애 등)는 기존대로 스택 추적을 남긴다.

요약은 폐기 경로와 정상 경로 양쪽에서 확인한다. 폐기 때만 확인하면 스파이크가 끝난 뒤 마지막
구간의 건수가 영영 안 나가고, 정상 때만 확인하면 포화가 이어지는 동안 아무 로그도 안 나간다.
정상 경로가 추가로 치르는 비용은 대개 `AtomicLong.get()` 하나다. 종료 시점에도 한 번 남긴다.

### 남는 한계 (Codex 리뷰 P2 지적)

업로드가 완전히 끊긴 채 요약 주기가 지나면 밀린 건수는 다음 업로드나 애플리케이션 종료 때까지
안 나간다. 이 빈에 시간 기반 트리거를 둘 수 없어서다. 이 프로젝트의 `@EnableScheduling` 은
`AiConfig`(`ai.enabled`)와 `NotificationConfig`(`fillmap.notification.enabled`) 안에 있고 둘 다
`@ConditionalOnProperty` 라, 로컬·CI·현재 prod 처럼 두 기능이 꺼진 환경에서는 스케줄링 자체가
안 뜬다. 여기에 `@EnableScheduling` 을 새로 붙이면 꺼져 있던 다른 도메인의 `@Scheduled` 가 전부
같이 켜지므로 이 티켓에서 할 일이 아니다.

실질 영향은 작다. "포화가 일어났다"는 사실은 첫 폐기에서 이미 한 줄 나가고, 늦어지는 건 정확한
건수뿐이다. 큐 10,000칸을 채울 만큼 업로드가 몰린 직후 60초간 업로드가 한 건도 없는 상황이라야
드러난다. 정상 배포·재기동 경로는 `@PreDestroy` 가 드레인 뒤에 잔여분을 남겨 대부분 덮는다.
다만 그 기록과 프로세스 종료 사이의 짧은 창에 들어온 폐기는 여전히 안 남는다.

| `hotzone/service/HotScoreCommandServiceImpl.java` | 폐기 catch 분리, `reportDiscardsIfDue()` 신설, 카운터 필드 2개 |

## 작업 로그 — 런타임 동작

**데이터 저장 위치**: Redis 키·스키마 변경 없음. 기록 대상은 그대로 `hotzone:{bucketId}`
Sorted Set (member = gridId, TTL 54h)다. 이번에 생긴 상태는 JVM 힙에만 있는 `AtomicLong` 2개
(`discardedSinceLastLog`, `nextDiscardLogAtEpochSecond`)이고 어디에도 영속되지 않는다.

**실행 쿼리**: 변경 없음. 적재는 기존 Lua 스크립트 그대로
`ZINCRBY hotzone:{bucketId} 1 {gridId}` + `EXPIRE hotzone:{bucketId} 194400` 원자 실행이다.
폐기 경로는 Redis 를 아예 건드리지 않는다.

**예외 흐름**:
- `executor.execute()` 가 던지는 `RejectedExecutionException` → 새 catch 가 흡수. 예외 객체는
  버리고 카운터만 올린다. 호출자에게 전파되지 않으므로 업로드 트랜잭션에 영향이 없다.
- 그 밖의 `Exception` → 기존 catch 유지. `gridId` 와 스택 추적을 WARN 으로 남긴다.
- 워커 스레드의 `increment()` catch(78행)는 손대지 않았다. Redis 장애 시 건별 스택 추적을 남기지만
  요청 스레드가 아니라 응답 경로에 영향이 없다.
- 어느 경로도 `ApiException` 을 던지지 않는다. 핫스코어 실패가 업로드 성공을 막지 않는다는
  §D4·FR-6 가 그대로다.

**빈 동작**: `@Service` 싱글턴이라 카운터 2개는 애플리케이션 수명 동안 유지된다. `@PreDestroy
shutdown()` 이 드레인을 마친 **뒤** 잔여 폐기 건수를 한 줄 남긴다. 순서가 중요하다 —
`executorService.shutdown()` 이후에 들어온 `recordUpload()` 도 거부돼 카운터를 올리므로, 드레인
앞에서 남기면 그만큼이 빠진다(PR #129 리뷰 지적). 그래도 이 마지막 기록과 프로세스가 실제로
죽는 시점 사이의 짧은 창은 못 덮고, 강제 종료(SIGKILL)면 통째로 사라진다. 둘 다 유실 허용
대상이라 의도된 동작이다.

`nextDiscardLogAtEpochSecond`
초기값이 0이라 기동 후 첫 폐기는 주기를 기다리지 않고 즉시 한 줄 나간다. 요약 주기 판정은
`Clock` 을 읽는데 이 빈의 기본 Clock 은 `systemUTC()` 이고, 테스트는 밀 수 있는 Clock 을 주입해
주기 경과를 결정적으로 재현한다. 드레인 로직(`awaitTermination` 타임아웃·인터럽트 처리) 자체는
변경 없고 위치만 앞으로 옮겼다.

**동시성**: 카운터 갱신은 락 없이 CAS 다. 여러 요청 스레드가 동시에 주기 경계를 넘으면 한 스레드만
CAS 에 성공해 요약을 찍고 나머지는 조용히 넘어간다. 실패한 쪽의 건수는 카운터에 남아 다음 요약에
합산된다. `getAndSet(0)` 과 `incrementAndGet()` 사이의 미세한 경합으로 몇 건이 다음 주기로
넘어갈 수 있는데, 폐기 건수는 로깅용 근사값이라 허용한다.
