# MSG-260: [BE] prod 필수 env 기동 검증 일반화 — 맨 플레이스홀더 리터럴 통과 결함

**Owner**: B (`global.config` — MSG-244 선례대로 auth-developer 담당)

> 출처: MSG-244 Codex 교차 리뷰 파생 (2026-07-30). 결함 수정 티켓 — PRD 없음.
> 선행: MSG-244 (`ProdRedisPasswordValidator` — 일반화의 출발 패턴), MSG-135 (JwtProperties),
> MSG-132/149 (AwsProperties @Pattern 선례).
> 위키 대조: 워크트리 격리 지시로 생략 — MSG-244 파생 결함 수정이라 스펙 상충 위험 낮음.

---

## 개요

`application-prod.yml`의 기본값 없는 맨 플레이스홀더(`${JWT_REFRESH_SECRET}` 등)는 env 미주입 시
기동 실패하지 않는다 — Spring Boot 바인더(`PropertySourcesPlaceholdersResolver`)가 미해석
플레이스홀더를 리터럴 문자열로 통과시키고, `@NotBlank`는 리터럴 `"${JWT_REFRESH_SECRET}"`가
공백이 아니라 통과시킨다 (MSG-244에서 `ProdRedisPasswordValidatorTest`로 확증한 메커니즘).
결과: prod에서 시크릿 미주입 시 앱은 뜨고 토큰 재발급·로그인 시점에야 터진다.

MSG-244의 `ProdRedisPasswordValidator`(prod 전용, 공백/미해석 리터럴 완전 일치 시 기동 실패)를
**prod 필수 env 일괄 검증기 `ProdRequiredEnvValidator`로 일반화**하고, Redis 검증기는 흡수·삭제한다.

## 배경 · 목표

- MSG-244는 REDIS_PASSWORD 한 건만 잡았다 — 같은 결함이 JWT·DB·카카오 등 잔여 대상에 그대로 남아 있다.
- 목표: prod 필수 env가 하나라도 빠지면 기동 시점에 누락 변수명을 명시하며 실패한다(fail-fast).
  런타임(토큰 발급·로그인)까지 결함이 잠복하지 않는다.

## 성공 기준

1. prod 프로파일에서 필수 env 중 하나라도 미주입(공백 또는 미해석 리터럴) 시 기동 실패하고,
   예외 메시지에 **누락 변수명이 전부** 나열된다. 값은 메시지에 찍지 않는다 (시크릿).
2. 전부 주입 시 정상 기동 — 검증기 무개입.
3. prod 외 프로파일(dev/local/테스트)에서 검증기 미로딩 — 기존 전체 스위트 green 유지.
4. `ProdRedisPasswordValidator`의 기존 보장(공백/리터럴 완전 일치 거부, `abc${def` 정상값 통과 —
   Codex 2R P2)이 신규 검증기에서 회귀 없이 유지된다.

**티켓 원문 정정 — `${JWT_SECRET}`**: prod yml에 `jwt.secret` 라인은 **없다** (relaxed binding으로
`JWT_SECRET` env가 직접 바인딩). 미주입 시 null → `@NotBlank`가 이미 기동 실패시킨다.
단, 향후 prod yml에 라인이 추가되면 같은 리터럴 결함이 재현되므로 검증기 목록에는 포함한다 (방어).

## 설계 결정

- **D1 — 단일 검증기 일반화 채택** (`ProdRequiredEnvValidator`, 프로퍼티 클래스별 `@Pattern` 기각).
  - `spring.datasource.*`·`spring.data.redis.*`는 **Boot 소유 프로퍼티 클래스**라 애너테이션을 붙일 수
    없다 — `@Pattern` 방식으로는 어차피 커스텀 검증기가 따로 필요해 두 방식이 공존하게 된다.
  - 시크릿은 값 형식이 없어 `@Pattern` 정규식을 쓸 수 없다 — blank/리터럴 검사가 유일한 일반 규칙.
  - "prod 필수 env" 목록이 한 파일에 모인다 — env 추가 시 한 곳만 고친다.
  - `AwsProperties`의 `@Pattern`은 **존치** — 명명 규칙 형식 검증이라 blank 검사의 상위 호환이고,
    이미 기동 실패를 보장하므로 검증기에 중복 등재하지 않는다.
- **D2 — Redis 검증기 흡수·삭제.** `ProdRedisPasswordValidator`(+테스트)를 삭제하고
  `ProdRequiredEnvValidator`(+`ProdRequiredEnvValidatorTest`)가 대체한다. 기존 테스트 5건은 전부
  이전한다: 바인더 리터럴 통과 증거 1건(그대로), 리터럴/공백/정상/`abc${def` 4건(새 검증기 대상으로).
  기존 javadoc의 메커니즘 설명(바인더 리터럴 통과·Lettuce 지연 인증)도 신규 클래스로 승계.
- **D3 — 검사 규칙 = MSG-244 그대로.** `!StringUtils.hasText(value) || ("${" + envVar + "}").equals(value)`
  → 위반. **완전 일치만** 거부한다 — 정상 값에 `${` 시퀀스가 있을 수 있다 (Codex 2R P2 회귀 방지).
  위반을 **전부 모아** `IllegalStateException` 1회로 던지고 메시지에 누락 변수명만 나열한다
  (운영자가 한 번에 전체 누락을 파악, 값 미출력).
- **D4 — 실행 시점은 InitializingBean 유지 (MSG-244 패턴), 순서 한계 수용.** DB 3종은 Flyway
  초기화가 검증기보다 먼저 돌면 드라이버 에러로 선행 실패할 수 있다 — 어느 쪽이든 **기동 실패
  자체는 보장**되므로 수용하고, 메시지 명확화는 검증기가 먼저 도는 경우의 이득으로 둔다.
  `EnvironmentPostProcessor` 승격은 바인딩 전 원시 값 접근 등 복잡도 대비 이득이 없어 기각.

## 수정 내용

### 1. `ProdRequiredEnvValidator` (신규, `com.msg.fillmap.global.config`)

```java
@Component
@Profile("prod")
@RequiredArgsConstructor
public class ProdRequiredEnvValidator implements InitializingBean {

	private final DataSourceProperties dataSourceProperties;   // org.springframework.boot.jdbc.autoconfigure (Boot 4)
	private final DataRedisProperties redisProperties;
	private final JwtProperties jwtProperties;
	private final KakaoOidcProperties kakaoOidcProperties;

	@Override
	public void afterPropertiesSet() {
		List<String> missing = new ArrayList<>();
		check(missing, "DB_URL", dataSourceProperties.getUrl());
		check(missing, "DB_USERNAME", dataSourceProperties.getUsername());
		check(missing, "DB_PASSWORD", dataSourceProperties.getPassword());
		check(missing, "REDIS_HOST", redisProperties.getHost());
		check(missing, "REDIS_PASSWORD", redisProperties.getPassword());
		check(missing, "KAKAO_CLIENT_ID", kakaoOidcProperties.clientId());
		check(missing, "JWT_SECRET", jwtProperties.secret());
		check(missing, "JWT_REFRESH_SECRET", jwtProperties.refreshSecret());
		if (!missing.isEmpty()) {
			throw new IllegalStateException(
				"prod 필수 환경변수 미설정: " + String.join(", ", missing)
					+ " — 값이 비었거나 미해석 플레이스홀더 리터럴 (MSG-260)");
		}
	}

	private void check(List<String> missing, String envVar, String value) {
		// 미해석 리터럴 완전 일치로만 거부 — 정상 값에 "${" 시퀀스가 있을 수 있다 (MSG-244 Codex 2R P2)
		if (!StringUtils.hasText(value) || ("${" + envVar + "}").equals(value)) {
			missing.add(envVar);
		}
	}
}
```

## 테스트 시나리오

`ProdRequiredEnvValidatorTest` — 기존 테스트 스타일 유지(프로퍼티 객체 직접 구성 + AssertJ).
전부-정상 픽스처 헬퍼를 만들고 테스트마다 한 항목씩 오염시키는 방식.

1. `바인더는_미해석_플레이스홀더를_리터럴로_통과시킨다` — MockEnvironment + Binder 증거 테스트
   (MSG-244 이전, 결함 메커니즘의 러너블 문서).
2. `필수_env가_리터럴_플레이스홀더면_기동_실패하고_메시지에_변수명이_있다` — 8종 각각
   (`@ParameterizedTest` 권장). `hasMessageContaining(변수명)`.
3. `공백_값도_기동_실패시킨다`.
4. `복수_누락_시_메시지에_전부_나열된다` — 예: JWT 2종 동시 리터럴 → 메시지에 둘 다.
5. `실패_메시지에_정상_주입된_시크릿_값은_없다` — 일부 정상·일부 누락 구성에서
   `hasMessageNotContaining(정상 값)`.
6. `전부_정상이면_통과한다`.
7. `플레이스홀더_시퀀스를_포함한_정상_값은_통과한다` — `abc${def` (Codex 2R 회귀, 기존 이전).
8. **dev/local 미로딩** — `@Profile("prod")` 애너테이션으로 보장. 별도 테스트 없이 간접 검증:
   기존 `@SpringBootTest` 스위트가 prod env 없이 green인 것 자체가 미로딩 증거
   (로딩됐다면 전부 기동 실패). 리뷰어는 애너테이션 존재를 확인.

수동 스모크(선택, EC2/로컬): prod 최소 컨텍스트에서 env 하나씩 제외 부팅 → 기동 실패 +
메시지에 해당 변수명 / 전부 주입 → 정상 기동.
