# MSG-237: 격자 전역 영상 목록 API — `GET /api/grids/{gridId}/videos` (READY+PUBLIC 필터, 인기순 페이지)

**Owner**: B (`com.msg.fillmap.video.*`) — videos 테이블 = Owner B 도메인. grid/region 패키지 무수정.

> 에픽: 지도 탐색 / 공개 노출. **MSG-162 §도메인 3이 예약한 티켓**이다 — 162가 visibility 전환으로
> 공개 영상 생성을 열고, MSG-87이 그 격자의 전역 대표 1건을 냈다면, 본 티켓은 같은 격자의 **전역 목록 N건**
> (타인 영상 포함)을 낸다. 162 §범위밖 "전역 영상 목록 API — 별도 티켓 · READY 필터 MUST"와
> status.md video "없는 것: 전역 영상 목록 API(READY 필터 MUST — MSG-162 §도메인 3)"가 지목한 바로 그것.
> **경로는 이미 예약돼 있다**: MSG-127이 `GET /api/grids/{gridId}/videos`를 `.../my-videos`로 옮긴 이유가
> "컨플루언스 Grid 확장 API가 `/videos`를 **전역 영상 목록**(남의 격자 포함)용으로 선점" — 그 자리를 본 티켓이 채운다.
> **순수 Owner B**다 — 계약 인터페이스 시그니처 변경 없음(§계약 변경) → 상대 팀 확인 불필요.
>
> **형제 경계**: MSG-87(전역 대표 **1건** — 본 티켓은 같은 필터·같은 인덱스의 **목록 N건**, cover DTO 미오염) /
> MSG-127(격자별 **내** 영상 — 개인 축·PRIVATE 포함, 본 티켓은 **전역 축**·PUBLIC만) /

> MSG-206(단건 재생 — 목록 항목 탭 시 진입점, `viewCount`·접근 제어 축 정합) /
> MSG-90(viewport keyset 커서 — **커서 패턴 계승**, §D2에서 keyset opaque 커서 채택 · 사용자 확정 2026-07-23) /
> **MSG-240**(`videos.title` 신설 — 본 티켓은 title 컬럼 부재로 **title 제외**, 240 후속 additive, §D3·Open Q1).

## 개요

디자인 ver 5 "격자 상세 보기" 시트의 **"이 격자의 영상" 리스트**(전역 축 — 타인 영상 포함, 썸네일·조회수·시간)를
채우는 read 경로 1종을 만든다. 격자 썸네일 뷰(탐색)에서 격자를 탭하면 이 목록으로 진입하고, 항목을 탭하면
큰 플레이어(MSG-206 재생)로 이어진다.

```
[MSG-87]  grid_id → 전역 대표 영상 1건        (ACTIVE·PUBLIC·READY, view_count DESC LIMIT 1)
[MSG-237] grid_id → 전역 영상 목록 N건(페이지) (같은 필터, view_count DESC 페이지 순회)  ← 본 티켓
[MSG-127] grid_id → 내 영상 리스트            (user_id=나, ACTIVE, PRIVATE 포함 — 다른 축)
```

**전역 선정(본인 포함)**. 필터·정렬은 MSG-87 대표 1건을 그대로 **LIMIT 1 → 페이지 윈도우**로 넓힌 것이라
`idx_videos_grid_popular` 부분 인덱스(`V1__init.sql:110`)를 그대로 탄다. 후보가 없으면 200 + 빈 페이지
(격자는 항상 존재하는 논리 개념 — glossary, MSG-73/87/127과 일관).

## 배경 · 목표

- **사용자/제품 관점**: MVP UI는 영상이 올라온 격자만 지도에 드러낸다(미점령 미표시 — glossary). 그 격자를 탭하면
  대표 썸네일(MSG-87) 하나만이 아니라 **그 격자에 쌓인 공개 영상 전부를 인기순으로 훑어보고**, 하나를 골라
  재생(MSG-206)한다. 지금은 대표 1건만 있어 "더 보기"가 불가능하다.
- **목표**: `gridId` 하나로 그 격자의 **전역 공개·READY 영상 목록**을 인기순(조회수→최신) 페이지로 조회하는 read
  API 1종을 Owner B(video)에 제공한다. 필터·정렬은 MSG-162 §도메인3 MUST와 `idx_videos_grid_popular`를
  단일 진실 원천으로 삼고, 신규 마이그레이션 없이(에러코드는 `INVALID_CURSOR` 1건만) 목록 쿼리 + 페이지 래퍼 1건만 추가한다.

## 성공 기준 (관찰 가능)

1. `GET /api/grids/{gridId}/videos`가 그 격자의 **전역 공개·READY 영상**을 필터
   `status=ACTIVE AND visibility=PUBLIC AND processing_status=READY`, 정렬 `view_count DESC, created_at DESC, id DESC`로
   한 페이지(최대 `size`개) + `hasNext`/`nextCursor`로 반환한다.
2. 각 항목은 `videoId`·`thumbnailUrl`(presigned GET URL)·`durationSec`·`viewCount`·`recordedAt`를 담는다.
   **`processingStatus`·작성자 정보·title 미포함**(§D3).
3. **READY MUST(MSG-162 §도메인3)**: 인코딩·블러 미완(processing_status≠READY) 영상은 목록에 **절대 포함되지 않는다**.
4. **visibility 게이트**: PRIVATE 영상은 **본인 것이라도** 전역 목록에 포함되지 않는다(§D1 — 내 PRIVATE는 MSG-127 축).
5. **전역 선정**: 다른 사용자의 공개·READY 영상도 목록에 포함된다(본인 포함). 삭제(DELETED)·블라인드(BLINDED)는 제외.
6. **인기순**: `view_count` 큰 순, 동률이면 최신(`created_at DESC`), 그마저 같으면 `id DESC`로 **결정적**. MVP에
   `view_count`가 0에 몰리면 자연히 최신순 폴백(MSG-87 §도메인3과 동일).
7. **페이지 순회**: 커서 없이 첫 요청 → 첫 페이지. `hasNext=true`면 응답의 `nextCursor`(opaque)를 다음 요청 `cursor`로
   넘겨 이어지고, 마지막 페이지는 `hasNext=false`·`nextCursor=null`. 무효 커서(파싱 실패·형식 위반)는 400(INVALID_CURSOR).
   no-LIMIT 아님(전역 축 페이로드 증폭 방지 — §D2).
8. **빈 페이지**: 공개·READY 영상이 없거나(비공개만·인코딩만·미점령·타인 없음) 존재하지 않는 gridId면
   **404가 아니라 200 + `{videos:[], hasNext:false, nextCursor:null}`**.
9. `size`가 범위(1..상한) 밖이면 **클램프**(에러 아님, §D5). 응답은 `SuccessResponse.of(...)`로 HTTP 200 + developCode 200.
   인증 없이 호출하면 401. **Flyway 마이그레이션 없이**, 신규 에러코드는 `INVALID_CURSOR` 1건만으로 전체 테스트 green.

## 결정 (Decisions)

### D1 — 필터 = **`status=ACTIVE AND visibility=PUBLIC AND processing_status=READY`**(전역·PUBLIC만, 내 PRIVATE 미포함)

- **결정**: 목록 WHERE를 `idx_videos_grid_popular` 부분 인덱스 조건과 **바이트 단위로 일치**시킨다 —
  `grid_id=:gridId AND status='ACTIVE' AND visibility='PUBLIC' AND processing_status='READY'`. **소유자 분기 없음**
  (`OR user_id=:me` 같은 조건을 붙이지 않는다) → **내 PRIVATE 영상도 전역 목록엔 나오지 않는다.**
- **근거**:
  1. **MSG-162 §도메인3 MUST 정본화**: "모든 공개 노출 쿼리는 `processing_status='READY'`를 반드시 포함" — 인코딩·블러
     전 영상 노출 금지. visibility 게이트(`PUBLIC`)도 함께. 이 규칙의 단일 진실 원천이 **read 필터 + 부분 인덱스**다.
  2. **MSG-87 전역 축의 자연 확장**: 대표 1건이 `ACTIVE·PUBLIC·READY`를 `LIMIT 1`로 뽑았고, 목록은 같은 후보 집합을
     `LIMIT N`으로 넓힌 것뿐이다(전역, 본인 포함). 같은 필터·같은 인덱스라 정책이 어긋날 여지가 없다.
  3. **축 구분(127과 대비)**: 내 PRIVATE·인코딩 중 영상은 **개인 축(MSG-127 my-videos, visibility 무필터)**에서 이미
     보인다. 전역 목록에 소유자 조건부 행을 섞으면 (a) 항목마다 owner 분기가 필요해지고 (b) `idx_videos_grid_popular`
     (PUBLIC+READY+ACTIVE 전용 부분 인덱스)를 **못 타** 정렬·페이징이 풀스캔이 되며 (c) MSG-206 접근 제어 first-match가
     세운 "전역 노출 vs 개인 열람" 경계가 흐려진다. → 전역 목록은 **순수 PUBLIC**으로 둔다.
- **기각 — 내 PRIVATE 포함(`... OR (user_id=:me AND visibility='PRIVATE')`)**: 부분 인덱스 이탈 + 축 혼선. 내 영상은
  이미 127에서 전부 보이므로 이중 노출일 뿐이다. 만약 "격자 상세에서 내 비공개도 같이"라는 UX 요구가 확정되면,
  그건 이 전역 목록이 아니라 FE가 127(my-videos)을 **함께 호출해 합성**할 문제다(축 분리 유지).

### D2 — 정렬·페이지네이션 = **인기순 `view_count DESC, created_at DESC, id DESC` + keyset opaque 커서**(사용자 확정 2026-07-23)

- **결정**:
  - **정렬**: `view_count DESC, created_at DESC, id DESC`. 앞 두 키는 `idx_videos_grid_popular`가 그대로 제공하고,
    `id DESC`는 (view_count, created_at)까지 동률인 행의 **페이지 간 결정성 타이브레이크**(같은 초 업로드 셔플 방지 —
    MSG-167이 `id DESC` 타이브레이크를 넣은 것과 동일 논리). id는 인덱스에 없으나 동률 그룹이 작아 국소 정렬로 무해.
  - **페이지네이션**: **keyset opaque 커서**(MSG-90 `GridCursor` 패턴의 video 축 등가물). 첫 요청은 커서 없음.
    커서 = Base64URL로 인코딩한 마지막 항목의 경계값 `(viewCount, createdAt, id)` — **와이어 포맷 명시**:
    페이로드는 `"{viewCount}:{createdAtEpochMicros}:{id}"` 3필드 콜론 구분(시각은 ISO 문자열이 아니라 **epoch
    마이크로초 정수** — 콜론 없는 표현이라 split 모호성이 없고 `created_at` 마이크로초 정밀도 보존).
    `created_at`은 `LocalDateTime`(존 없음)이라 epoch 변환은 **UTC 고정**으로 명시한다 — encode/decode가 같은 존이면
    대칭이라 절대 시각 의미는 불필요하고, 환경(JVM 기본 존)에 따라 값이 갈리는 것만 막으면 된다. 커서의 시각 성분은
    정렬키 `created_at`이며 응답 DTO의 `recordedAt`(표시용)과 **다른 컬럼**이다(§D3 표시값≠정렬키). 조회는 row-value 비교
    `(view_count, created_at, id) < (:cv, :cc, :ci)`(DESC 등가) + `LIMIT size+1` **lookahead** → `hasNext`,
    `nextCursor = hasNext ? encode(마지막 항목) : null`.
  - **무효 커서**: 파싱 실패·형식 위반(필드 수/타입 불일치) = `VideoErrorCode.INVALID_CURSOR(3423, 400)` —
    기존 3400~3422 다음 번호. MSG-90 `GridErrorCode.INVALID_CURSOR(4403)` 관례의 video 도메인 등가물
    (**신규 에러코드 1건**, §D5 갱신). 서명(HMAC) 없음 — 형식이 유효한 임의 경계값은 그냥 조회된다(공개 목록이라
    무해, GridCursor와 동일 수준). "변조 감지"를 주장하지 않는다.
- **근거**: **사용자 확정(2026-07-23) — 커서식 채택.** FE 무한스크롤 관례(opaque nextCursor 전달)와 MSG-90 페이지네이션
  패턴 통일, 깊은 페이지도 부분 인덱스 range scan으로 처음부터 안 훑는다(비용은 동률 그룹 크기 비례 — §도메인2).
  스펙 초안은 offset을 제안했으나 결정으로 종결.
- **기각 — offset 페이지(스펙 초안)**: 랭킹을 요청마다 재평가해 가변키에 정직하다는 논거였으나 사용자 결정으로 기각.
  (논거 기록 보존 — 랭크드 피드에서 offset의 페이지별 스냅샷은 keyset의 경계 고정보다 랭크 변동 흡수에 유리하다.)
- **불안정성 ceiling(정직)**: 정렬키 `view_count`는 MSG-206 재생마다 +1로 **가변**이다. 커서가 경계값을 동결하므로,
  페이지 사이에 영상의 조회수가 경계를 넘나들면 **항목 skip/dup drift**가 날 수 있다 — MVP 수용(랭크드 피드의 통상
  동작, 단일 격자 소량 규모라 cosmetic).
  `ponytail: 랭크 churn 이 실사용에서 문제되면 사전계산 랭킹(주기 스냅샷) 또는 정렬 축 재검토. MVP 규모엔 keyset+lookahead 로 충분.`
- **size 상한**: 기본 20, 상한 **50** 제안(리뷰 확정). 무한스크롤 한 화면 + 프리페치에 충분, presign N회도 로컬 서명이라 저비용.

## 도메인 로직

### 1. 전역 목록 조회 (인덱스가 정본 — Owner B, `VideoServiceImpl`)

`@Transactional(readOnly=true)`. userId 없음(전역).

1. `size` 보정: `size ← clamp(size, 1, 50)`(§D5). `cursor` 있으면 디코드 → `(cv, cc, ci)` 경계값(파싱 실패 = `INVALID_CURSOR` 400).
2. `videos`에서 `grid_id=:gridId AND status='ACTIVE' AND visibility='PUBLIC' AND processing_status='READY'` 필터
   (+커서 있으면 row-value 비교 `(view_count, created_at, id) < (:cv, :cc, :ci)`),
   `ORDER BY view_count DESC, created_at DESC, id DESC`, `LIMIT size+1` **lookahead**.
3. 반환 행이 `size+1`개면 `hasNext=true`, 앞 `size`개만 응답. 이하면 `hasNext=false`, 전부 응답.
4. 각 항목 썸네일 key → `ThumbnailUrlPresigner.presign(key)`(READY라 non-null 기대, null이면 null 통과 — 미강제 관례 §API 명세) → `GridGlobalVideoResponseDto`.
5. `GridVideoPageResponseDto.of(items, hasNext)` 반환(`nextCursor` = hasNext면 마지막 항목 경계값 인코딩, 아니면 null).

`user_id` 조건 **없음** — 전역 선정(본인 PUBLIC 포함). MSG-127 개인 격리(`user_id=:userId`)와 정반대 축이다.

### 2. 리포지토리 (부분 인덱스 일치 native + 페이지 윈도우)

`findGlobalCover`(MSG-87, `LIMIT 1`)를 페이지로 넓힌다. 필터·정렬을 `idx_videos_grid_popular`와 일치시켜 플래너가
인덱스 range scan으로 페이지를 만족하게 한다.
```sql
SELECT * FROM videos
WHERE grid_id = :gridId
  AND status = 'ACTIVE' AND visibility = 'PUBLIC' AND processing_status = 'READY'
  AND (:cv IS NULL OR (view_count, created_at, id) < (:cv, :cc, :ci))   -- keyset (§D2, 첫 페이지는 커서 없음)
ORDER BY view_count DESC, created_at DESC, id DESC
LIMIT :limit                         -- limit = size + 1 (lookahead)
```
- **정렬 일치(정직한 범위)**: `view_count DESC, created_at DESC`는 부분 인덱스가 그대로 제공. `id`는 **인덱스에 없다**
  — `id DESC` 타이브레이크와 커서 3열 경계의 id 성분은 동률 그룹 국소 처리라 단일 격자 소량 규모에 무해(§D2와 동일
  ceiling). `SELECT *`라 index-only scan도 아니다 — 주장 범위는 "부분 인덱스 range scan으로 깊은 페이지도 처음부터
  안 훑는다"까지이고, 비용은 **동률 그룹 크기에 비례해 늘 수 있다**(id가 인덱스에 없어 그룹 내 추가 필터·정렬 발생).
  동률 대량 격자가 실측에서 문제되면 인덱스에 `id DESC` 추가를 그때 재검토(현재는 마이그레이션 없음 유지).
- **구현 형태**: native `@Query` + 커서 경계값 3파라미터(`cv, cc, ci`) — 커서 유무로 메서드 2개(첫 페이지/이후 페이지)로
  나누거나 위처럼 null 가드 단일 쿼리, 리뷰 재량. lookahead(`LIMIT size+1`)·`hasNext` 판정은 서비스 수동(§도메인1).
  row-value 비교는 DESC 등가로 `<` 방향 — PostgreSQL row-value 비교가 인덱스 range scan을 탄다.

### 3. 노출 게이트 정합 (MSG-162 §도메인3 MUST)

- 목록은 `processing_status='READY' AND visibility='PUBLIC'`을 read 필터로 강제하고, `idx_videos_grid_popular` 부분
  인덱스가 이를 물리적으로 뒷받침한다 — MSG-162가 명문화한 "모든 공개 노출 쿼리는 READY 강제"의 준수 지점이다.
- **정렬/필터 변경 금지 원칙**(MSG-87 컨플루언스 경고 계승): 인기순 외 정렬 옵션이나 필터를 추가하려면 쿼리만
  고치지 말고 **부분 인덱스부터 재설계**한다(안 그러면 인덱스를 못 타 풀스캔).
