# MSG-349: 구역 밖 격자도 이름이 나오도록 지도 응답 3종에 행정동 이름 추가

**Owner**: A (단독)

> 요구사항 정본: `docs/prd/MSG-349-prd.md` (검토됨, 2026-08-09 승인). 이 스펙은 PRD의 FR-1~FR-9와
> 비기능 요구에 "어떻게"만 붙인다. 변경 파일이 전부 grid, hotzone, zone 패키지이고, 조달에 쓰는
> region 패키지도 A 소유(MSG-251 §D1)라 크로스오너 접점이 없다.

## 개요

MSG-341이 "폴백 재료 미제공"으로 확정했던 지도 응답 3종(뷰포트 격자 조회, 단일 격자 조회, 핫구역)에
행정동 이름 `regionName`(String, nullable) 필드를 가산한다. 기존 필드와 응답 구조는 그대로 두고 필드만
늘린다(FR-8). DB 마이그레이션은 없다. 값은 `regions.region_name` 전체 문자열("부산광역시 영도구
영선1동") 그대로이며, 시 이름 축약과 문자열 조립은 FE 몫이다(PRD 5절).

이 변경으로 FE의 이름 조립 규칙이 응답 종류와 무관하게 한 줄로 통일된다:
`zoneName이 있으면 "zoneName + 공백 + zoneCell", 없으면 regionName`.

## 배경, 목표

구역(zone) 밖 격자가 다수인데(전국 등재 구역 48개, dev 시드 109칸 중 90칸이 구역 밖) 지도 응답 3종에는
구역 밖에서 쓸 행정동 이름이 없어, FE가 이름 하나를 얻으려고 탐험률 API를 추가 호출하거나 칸마다 단건
조회를 돌려야 했다. 이름 때문에 추가로 나가는 API 호출을 0으로 만들고, 같은 격자가 어느 화면에서든 같은
이름을 갖게 하는 것이 목표다. 상세 배경과 기각 대안(대응표 응답 모양, `displayName` 조립본)은 PRD
1절과 5절 참조.

## 성공 기준

1. 3종 응답의 격자 항목마다 `regionName`이 실린다. 구역 안 격자에도 실린다(FR-9, 위치줄의 시/구 출처).
2. 미점령 격자를 단일 조회해도 `regionName`이 나온다(FR-3). 무귀속(해상) 격자만 null이다(FR-5).
3. 뷰포트 조회는 지금과 같은 쿼리 1회를 유지하고, 핫구역은 일괄 조회 1회만 추가된다(비기능 성능).
4. 기존 클라이언트가 깨지지 않는다: 기존 필드 불변, 새 에러 코드 없음, 기존 성공/실패 케이스의 HTTP
   상태와 developCode 불변(FR-8).
5. 같은 격자의 `regionName`이 3종 응답과 기존 6종(도감 목록, 업로드 확정, 재생 등)에서 같다(FR-6).
6. `ResponseSchemaNullabilityTest`(MSG-319) green: 새 필드가 `requiredProperties`에 들어가고
   `nullable = true`가 병기된다(FR-7).

## API 명세

세 엔드포인트 모두 요청은 불변이고 응답 항목에 `regionName` 하나가 늘어난다. 에러 케이스도 전부
불변이다(신규 에러 코드 없음).

### 1. 뷰포트 격자 조회: `GET /api/grids` (내 격자), `GET /api/friends/{userId}/grids` (친구 격자 공용)

`OccupiedGridResponseDto` 항목 예시 (구역 밖 격자):

```json
{
	"gridId": "16712_11413",
	"gridY": 16712,
	"gridX": 11413,
	"zoneName": null,
	"zoneCell": null,
	"regionName": "부산광역시 영도구 영선1동"
}
```

구역 안 격자면 세 필드가 모두 실린다: `"zoneName": "서면", "zoneCell": "I-6", "regionName":
"부산광역시 부산진구 부전1동"`. 친구 격자 조회는 `FriendServiceImpl.getFriendGrids`가
`gridQueryService.getOccupiedInViewport`에 위임하므로 friend 쪽 파일 변경 없이 그대로 반영된다(FR-1).

### 2. 단일 격자 조회: `GET /api/grids/{gridId}`

`GridCellResponseDto`. 미점령 격자(빈 칸 클릭)도 이름이 나온다(FR-3):

```json
{
	"gridId": "16781_11406",
	"occupied": false,
	"videoCount": 0,
	"zoneName": null,
	"zoneCell": null,
	"regionName": "부산광역시 영도구 영선1동"
}
```

기존 에러 불변: gridId 형식 불량은 지금처럼 `INVALID_GRID_ID`다. 형식이 유효한데 서비스 범위(한국)
밖인 gridId는 지금처럼 200으로 응답하며 `regionName`만 null이다(아래 도메인 로직의 6400 흡수 참조).

### 3. 핫구역: `GET /api/hotzones`

`HotZoneResponseDto` 항목에 `regionName` 가산. 기존 필드(gridId, gridY, gridX, score, zoneName,
zoneCell) 불변.

### 스키마 표기 (FR-7)

세 DTO 모두 `regionName`을 클래스 레벨 `@Schema(requiredProperties = {...})`에 추가하고 필드에
`nullable = true`를 붙인다. 이 레포의 required는 "키가 존재한다"는 뜻이고 nullable은 "값이 null일 수
있다"는 뜻이라 둘을 함께 쓴다(`ResponseSchemaNullabilityTest` 주석의 확정 규칙, `UserProfileResponseDto.email`
선례). 필드 설명에는 null 조건을 적는다: "격자 중심점이 속한 행정동 전체 이름. 어느 행정동에도 속하지
않으면(해상 등) null. zoneName이 null이면 이 값이 표시 이름 폴백이다."

## 도메인 로직

행정동 이름의 출처는 두 가지인데 판정 술어가 동일해서 결과가 어긋나지 않는다. 신규 격자 저장
(`VideoRepository.upsertGrid`)의 라벨 판정과 역지오코딩(`RegionQueryService.resolveByPoint`)이 같은
조건(`ST_Covers(boundary_geom, 격자 중심점) ORDER BY region_code LIMIT 1`)[^stcovers]을 쓴다는 것이
upsertGrid 주석에 명문화되어 있다(MSG-167 §D1). 그래서 응답별로 싼 쪽을 고른다(PRD 5절 표).

### 뷰포트: 저장 라벨을 같은 쿼리에서 조인으로 읽는다

`GridRepository`의 실경로 쿼리 3종(`findOccupiedInRange`, `findOccupiedPage`, `findOccupiedPageAfter`)이
이미 `JOIN grids g`를 하므로, 각각에 조인 하나와 SELECT 컬럼 하나를 더한다. `findOccupiedPage` 기준:

```sql
SELECT g.grid_id AS "gridId", g.grid_y AS "gridY", g.grid_x AS "gridX",
	r.region_name AS "regionName"
FROM user_grids ug
JOIN grids g ON g.grid_id = ug.grid_id
LEFT JOIN regions r ON r.region_code = g.region_code
WHERE ug.user_id = :userId
	AND g.grid_y BETWEEN :minY AND :maxY
	AND g.grid_x BETWEEN :minX AND :maxX
ORDER BY g.grid_y, g.grid_x
LIMIT :limit
```

- **LEFT JOIN**[^leftjoin]인 이유: 무귀속 격자는 `grids.region_code`가 NULL이라 INNER JOIN이면 격자 행
  자체가 응답에서 사라진다. 색칠된 격자가 지도에서 증발하는 것은 FR-5 위반이다(FR-5는 "이름이 빈 것"이
  정상이지 "칸이 빠지는 것"이 아니다).
- 조인 키가 정렬 키와 무관하므로 keyset 커서 페이지네이션[^keyset]의 순서와 lookahead 판정은 불변이다.
- `OccupiedGridProjection`[^projection]에 `getRegionName()`을 추가하고,
  `GridQueryServiceImpl.toViews`가 `OccupiedGridView`로 전달한다.
- 접근 B(`findOccupiedByIntersects`)는 실경로 미사용(벤치마크 이력 보존 전용, MSG-90 Open Q1=b)이라
  조인을 추가하지 않는다. 프로젝션에 `regionName` 별칭이 없으면 `getRegionName()`이 null일 뿐이고,
  유일한 소비처인 벤치마크는 이 게터를 읽지 않는다.

### 단일 격자: 중심점 재판정 (저장 라벨을 읽을 수 없는 유일한 경로)

미점령 격자는 grids 행이 없을 수 있어(행 존재는 lazy insert[^lazy]된 격자뿐, 전국 약 1,010만 칸 중
극소수) 저장 라벨을 읽을 수 없다. 그래서 이 경로만 중심점 재판정을 쓴다.

`GridQueryServiceImpl.getCell`에 `RegionQueryService`를 주입하고:

1. 기존 `validateGridId`(형식 불량이면 `INVALID_GRID_ID`, 불변)를 통과한 gridId에서
   `GridEncoder.center(gridId)`로 중심 좌표를 얻는다.
2. **6400 흡수 가드**: `KoreaCoordinates.isOutOfService(lat, lon)`이면 `resolveByPoint`를 호출하지
   않고 `regionName = null`로 둔다. `resolveByPoint`는 서비스 범위 밖 좌표에
   `INVALID_COORDINATE`(6400)를 던지는 계약인데, getCell은 형식이 유효한 gridId면 지금 200을 주는
   API라서 이번 변경으로 새 에러가 생기면 FR-8 위반이다. `RegionStatsQueryServiceImpl.findStatByGrid`가
   같은 이유로 같은 가드를 쓴다(MSG-153 §D6 선례).
3. 범위 안이면 `resolveByPoint(lat, lon)` 결과의 `RegionView.regionName`을 쓰고,
   `Optional.empty`(무귀속)면 null이다.

`region_code` 저장 없이 이름만 계산해서 응답한다(격자 행을 만들거나 갱신하지 않는다, 조회는 읽기
전용). getCell의 쿼리 수는 기존 1회(`findVideoCount`)에서 2회가 되지만 단건 API의 상수 증가이고, 지금도
같은 화면이 병행 호출하던 by-grid 탐험률 API와 같은 비용이다(PRD 5절). 이번 변경 후 FE는 이름 목적의
by-grid 호출을 없앨 수 있다.

`GridQueryService` 인터페이스의 getCell javadoc에 regionName 서술을 추가한다(시그니처 불변, 아래 계약
변경 참조).

### 핫구역: 상위 격자 id로 일괄 조회 1회

`HotZoneServiceImpl.getHotZones`의 흐름을 두 단계로 나눈다. 먼저 기존 필터(상위 K, 최소 임계, 뷰포트)를
통과한 항목의 gridId 목록을 모으고, 그 목록으로 `GridRepository`에 신설하는 일괄 조회를 1회 실행해
"gridId → regionName" 맵을 만든 뒤 `HotZoneView`를 조립한다. 항목마다 단건 조회를 돌리는 N+1[^nplus1]은
금지다(비기능 성능). 통과 항목이 0건이면 조회를 생략한다(빈 IN 목록의 SQL 문법 오류 방지를 겸한다).

신설 쿼리(GridRepository, 네이티브):

```sql
SELECT g.grid_id AS "gridId", r.region_name AS "regionName"
FROM grids g
JOIN regions r ON r.region_code = g.region_code
WHERE g.grid_id IN (:gridIds)
```

- 여기는 **INNER JOIN**이다. 뷰포트와 달리 격자 행을 잃어도 되는 자리가 아니라, 결과가 항목이 아니고
  이름 사전이기 때문이다. 무귀속 격자는 결과에 안 나타나고 맵 miss로 null이 되는데, 이 편이 LEFT
  JOIN으로 null 값을 받는 것보다 낫다. `Collectors.toMap`은 null 값에서 NPE를 던지므로 null 행을
  아예 안 받는 쪽이 조립 코드를 단순하게 만든다.
- 핫구역 격자는 업로드 확정 시 `upsertGrid`로 lazy insert되므로 grids 행이 항상 있다. 만에 하나
  없어도(Redis와 DB의 순간 불일치) 맵 miss로 null이라 안전하게 무귀속과 같은 처리가 된다.
- 목록 크기 상한은 topK = 50이라 IN 목록도 최대 50이다.
- `HotZoneServiceImpl`이 `GridRepository`를 주입받는다. hotzone과 grid는 둘 다 Owner A라 크로스오너
  접점이 아니다(`HotZoneService`가 grid.dto의 `ViewportBounds`를 재사용할 때와 같은 판정, status.md
  계약 표 명문).

### 문서 정정 (코드 로직 불변, 이번에 사실과 어긋나게 되는 잔재)

- `HotZoneResponseDto.zoneName`의 `@Schema` 설명 중 "마커를 누르면 단일 격자 조회가 라벨을 준다"는
  regionName 동봉으로 더는 필요한 안내가 아니므로 regionName 폴백 안내로 교체한다.
  `OccupiedGridResponseDto.zoneName`의 "행정동 폴백 재료를 싣지 않는다"와
  `GridCellResponseDto.zoneName`의 "by-grid 응답의 regionName으로 폴백한다"도 같은 이유로 정정한다.
- `GridController`(두 엔드포인트)와 `HotZoneController`의 `@Operation` 설명에 폴백 규칙을 명시한다:
  "zoneName이 null이면 regionName이 표시 이름이다(폴백에는 칸 번호를 붙이지 않는다)".
- `ZoneController`의 `@Tag`와 `@Operation`에 남은 "FE가 캐시해 로컬 명명" 문구는 MSG-341(표시명 서버
  계산 전환) 이전의 잔재라 정정한다. 이 API의 현재 용도는 검색바 구역 이동(MSG-234 §D6)과 구역 범위
  오버레이뿐이다. 클래스 javadoc의 "§D3, FE-local 계산"도 같이 고친다. 코드 로직은 불변이다.
- `OccupiedGridView`, `GridCellView`, `HotZoneView` javadoc에 regionName 서술을 추가한다.

## 계약 변경

크로스오너 메서드 시그니처 변경은 없다. 다만 아래 확장이 계약 반환 타입에 닿으므로 리뷰 시 상대 팀원
확인 지점으로 남긴다.

- **`GridQueryService` (A 제공, B 소비)**: 메서드 시그니처 불변. 반환 뷰 record 2종
  (`GridCellView`, `OccupiedGridView`)에 `regionName` 필드가 가산된다. B 소비처
  (`FriendServiceImpl.getFriendGrids`)는 뷰를 읽어 통과시키기만 하고 생성하지 않으므로 비파괴다.
  `CollectionGridView`에 regionName을 가산했던 MSG-167과 같은 유형의 확장이다.
- **`RegionQueryService` (A 소유, 기존 계약)**: 시그니처 불변. 소비처에 `GridQueryServiceImpl`이
  추가될 뿐이다(둘 다 A라 크로스오너 아님).
- `HotZoneService`와 `HotZoneView`: 유일한 소비처가 `HotZoneController`(A)라 계약 경계 밖이다.

## 미해결 질문

없다. PRD 8절과 동일하며, 유일한 열린 선택(응답 모양)은 PRD 5절 실측으로 닫혔다.

[^stcovers]: ST_Covers. PostGIS의 포함 판정 함수로, 한 도형(행정동 경계)이 다른 도형(격자 중심점)을 완전히 덮는지 검사한다. 경계선 위의 점도 포함으로 판정해 ST_Contains와 달리 가장자리에서 결과가 비지 않는다.
[^leftjoin]: LEFT JOIN. 조인 상대(행정동)가 없어도 왼쪽 테이블(격자)의 행을 버리지 않고 상대 컬럼을 NULL로 채워 반환하는 조인이다. 무귀속 격자를 응답에서 잃지 않기 위해 쓴다.
[^keyset]: keyset 커서 페이지네이션. 페이지 번호 대신 마지막 항목의 정렬 키(grid_y, grid_x)를 커서로 받아 그 다음부터 읽는 방식이다. OFFSET과 달리 앞 페이지를 다시 세지 않아 깊은 페이지에서도 비용이 일정하다.
[^projection]: 프로젝션. 쿼리 결과에서 필요한 컬럼만 게터 인터페이스로 노출하는 Spring Data 방식이다. 네이티브 쿼리의 컬럼 별칭과 게터 이름을 맞춰 매핑한다.
[^lazy]: lazy insert. 격자를 미리 전부 저장하지 않고 첫 영상이 올라오는 순간에만 grids 테이블에 등록하는 전략이다(용어집 백엔드 전용 개념). 그래서 grids 행 존재는 "누군가 영상을 올린 격자"와 같은 뜻이다.
[^nplus1]: N+1. 목록 하나를 얻는 쿼리 1회 뒤에 항목마다 추가 쿼리 N회가 따라붙는 성능 결함 패턴이다. 핫구역 50칸이면 51회가 되므로 일괄 조회 1회로 대체한다.
