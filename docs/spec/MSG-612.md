# MSG-612: 사용자 격자 영상과 행사 영상 목록이 전체를 훑지 않도록 인덱스 두 개를 추가한다

**Owner**: B (`com.msg.fillmap.video.*`, `com.msg.fillmap.event.*` 안의 리포지토리와 엔티티 변경. Flyway 마이그레이션 두 개는 공동 자산이라 상대 팀원 확인 대상)

> PRD 면제: 요구사항 불변. 2026-10-03 감사 실측 근거(docs/audit/2026-10-03-backend-audit-plan-tx.md §3.1 #9, #12).
> 인덱스 추가와 컬럼 1개 비정규화[^1]는 응답 계약, 정렬 순서, 커서 형식 어느 것도 바꾸지 않고, 기존
> 요구(FR-COLLECT-04, FR-COLLECT-11, FR-FRIEND-07, FR-EVENT-09의 "최신 업로드순")를 같은 의미로 더 싸게 맞춘다.
> 성능 목표를 새로 세우지 않는다. 완료 조건의 수치(1ms, 30ms, Sort 노드 없음)는 지라 티켓이 정한 검증 기준이지
> 서비스 NFR 이 아니다.
>
> 요구사항 정본은 지라 MSG-612 본문이다. 이 스펙은 그 본문의 "무엇, 왜, 완료 조건"에 "어떻게"만 붙인다.

## 개요

영상 테이블에 "사용자 + 격자" 순서의 인덱스 하나를, 행사 영상 연결 테이블에 "위치 + 올린 시각" 순서의 인덱스
하나를 추가한다. 두 번째 인덱스는 정렬 키가 다른 테이블(`videos.created_at`)에 있어서 그 값을
`event_videos.created_at` 에 한 칸 복사해 두는 비정규화가 같이 간다. 코드 변경은 (1) `EventVideo` 엔티티에
필드 하나, (2) 피드 JPQL 두 개의 ORDER BY 와 keyset[^2] 조건을 복사본 컬럼으로 바꾸는 것, (3) 테스트 픽스처의
native INSERT 두 곳에 컬럼 하나를 더하는 것이 전부다. 응답 값은 바뀌지 않는다(복사본은 원본과 같은 값이다).

## 배경 · 목표

- 격자 8.5만 개를 점령한 사용자의 격자 1건 영상 조회가 14.3ms(버퍼 2,581)다. `idx_videos_user_created` 로
  사용자 전 행 85,083건을 Bitmap[^3] 으로 긁은 뒤 `grid_id` 를 힙에서 걸러 85,082행을 버린다. 친구 도감 30칸은
  같은 서브쿼리를 LATERAL[^4] 로 30번 돌아 482ms 다. 영상 삭제 뒤 대표 영상 재선정(`reselectCover`)도 같은
  술어라 같은 비용이다.
- 행사 영상 피드는 필터 키(`event_videos.event_location_id`)와 정렬 키(`videos.created_at`)가 다른 테이블에
  있어 "이 위치의 최신순 상위 21건"을 바로 꺼낼 인덱스가 없다. 영상 2만 건 위치의 첫 페이지가 361ms(버퍼
  20,101)이고, 매 페이지 그 위치의 영상 전부를 조인한 뒤 top-N 정렬한다. 다음 페이지도 같은 구조다.
- 첫 번째 인덱스는 MSG-127 이 "한 격자당 소량이라 YAGNI, 필요 시 후속 마이그레이션"으로 미뤄 둔 것이다
  (`docs/spec/MSG-127.md:172`). 유예 조건이 실측으로 도래했다.
- 목표: 다섯 경로(격자 1건, 친구 도감 30칸, 행사 피드 첫 페이지, 행사 피드 다음 페이지, 대표 영상 재선정)가
  사용자 보유량이나 위치 영상 수에 비례하지 않게 인덱스 한 번으로 끝나게 한다. 응답 계약은 그대로다.

## 성공 기준

- AC-612-01: 격자 8.5만 사용자(로컬 시드, 아래 §검증)에서 격자 1건 내 영상 조회
  (`findByUserIdAndGridIdAndStatusOrderByCreatedAtDesc`)의 `EXPLAIN (ANALYZE, BUFFERS)` 실행 시간이 1ms 안쪽이고,
  플랜이 `idx_videos_user_grid` Index Scan 이며 `Rows Removed by Filter` 가 85,082 에서 0 이 된다.
- AC-612-02: 같은 사용자의 친구 도감 30칸(`getCollectionGridsForFriend`)이 30ms 안쪽이고, LATERAL 서브플랜 30회가
  전부 `idx_videos_user_grid` 를 탄다.
- AC-612-03: 영상 2만 건 위치의 행사 피드 첫 페이지(`findVisibleByLocationId`)와 다음 페이지
  (`findVisibleByLocationIdAfter`) 플랜에 Sort 노드가 없고, `idx_event_videos_location_recent` Index Scan 아래
  LIMIT 으로 끝난다.
- AC-612-04: 대표 영상 재선정(`reselectCover`)의 서브쿼리가 `idx_videos_user_grid` 를 타고 1ms 안쪽이다.
- AC-612-05: 행사 영상 업로드(`EventVideoServiceImpl.upload`) 뒤 저장된 `event_videos.created_at` 이 같은 영상의
  `videos.created_at` 과 같다(통합 테스트로 판정).
- AC-612-06: V58 적용 후 기존 `event_videos` 행 전부가 `created_at NOT NULL` 이고
  `SELECT count(*) FROM event_videos ev JOIN videos v ON v.id = ev.video_id WHERE ev.created_at <> v.created_at`
  이 0 이다(로컬 시드 2만 행에서 확인).
- AC-612-07: 기존 테스트 전부 통과. 특히 행사 피드 정렬과 커서 테스트(`EventVideoQueryServiceTest`,
  `EventVideoCursorTest`)와 친구 도감, 격자 영상 테스트가 무수정 통과한다(응답 순서 불변의 가드).

## 도메인 로직

### 1. `videos (user_id, grid_id, created_at DESC)`

혜택 경로 4개 (줄 번호는 2026-10-03 `feature/MSG-612-video-indexes` 기준으로 재확인한 값):

| 경로 | 위치 | 현재 술어와 정렬 | 인덱스와의 대응 |
|---|---|---|---|
| 격자별 내 영상 | `VideoRepository.java:27` 파생 쿼리 | `user_id = ? AND grid_id = ? AND status = 'ACTIVE' ORDER BY created_at DESC` | 선두 2열 등치, 셋째 열이 정렬 방향과 같아 Sort 없음. `status` 는 남는 행 1~수십 건에 Filter |
| 친구 격자 영상 | `VideoRepository.java:34-43` | `userId = ? AND gridId = ? AND status/processingStatus/visibility … ORDER BY createdAt DESC, id DESC` | 같은 선두 2열. `id DESC` 타이브레이커는 인덱스에 없지만 격자당 소량이라 Sort 비용이 없다시피 하다(인덱스에 넣지 않는 이유: 4열 인덱스 대비 이득이 없다) |
| 친구 도감 LATERAL | `UserGridRepository.java:160-171` | `v.grid_id = ug.grid_id AND v.user_id = ug.user_id … ORDER BY (v.id = cover) DESC, created_at DESC, id DESC LIMIT 1` | 칸마다 선두 2열 등치로 그 격자의 행만 읽는다. ORDER BY 의 CASE 식은 인덱스 순서를 못 쓰지만 입력이 격자당 소량이라 무관 |
| 대표 영상 재선정 | `VideoRepository.java:471-486` | `user_id = ? AND grid_id = ? AND status = 'ACTIVE' ORDER BY created_at, id LIMIT 1` | 선두 2열 등치, 오름차순은 역방향 스캔 |

기존 `idx_videos_user_created (user_id, created_at DESC)` 는 그대로 둔다. 사용자 단위 조회(업로드 이력, 뱃지
count, 탈퇴 CASCADE)가 계속 쓴다.

### 2. `event_videos.created_at` 복사와 `(event_location_id, created_at DESC, video_id DESC)`

**정합 규칙**: `event_videos.created_at` 은 언제나 같은 행의 `videos.created_at` 과 같은 값이다.

- 쓰기 경로는 한 곳이다. `EventVideoServiceImpl.upload:151` 이 `new EventVideo(confirmed.video(), location,
  occurrenceId)` 를 save 한다. **`EventVideo` 생성자가 `video.getCreatedAt()` 을 복사한다.** 생성자 시그니처는
  그대로라 테스트 13곳의 `new EventVideo(video, location, occId)` 호출은 손대지 않아도 된다.
- 엔티티 생성 시각(`LocalDateTime.now(clock)`)을 따로 찍는 안은 기각한다. `Video` 는 `confirmAtGrid` 안에서
  `saveAndFlush` 된 뒤 넘어오므로 두 시각은 ms 단위로 어긋나고, 커서는 응답의 `createdAt`(프로젝션의
  `v.createdAt`)으로 발급되는데 keyset 비교는 `ev.created_at` 으로 하게 되므로 경계가 어긋난다. 복사해야 둘이
  글자 단위로 같다. `Video.createdAt` 은 생성 시 µs 로 절단된 값(`Video.java:136`)이라 복사본도 같은 정밀도다.
- **어긋날 수 있는 경로 확인**: `Video.createdAt` 은 `@Column(updatable = false)` (`Video.java:120`) 이고,
  파일 교체 `replaceFile` (`Video.java:221-233`)은 `originalS3Key`, `durationSec`, `recordedAt` 과 파생 결과만
  갈아끼우며 `createdAt` 을 건드리지 않는다. `markDeleted`, `applyBlurResult`, 상태 전이 메서드도 마찬가지다.
  native UPDATE 중 `videos.created_at` 을 쓰는 문장은 없다(`VideoRepository` 전수, `view_count` 와 상태와 키만 갱신).
  따라서 업로드 이후 원본이 바뀌는 경로가 없고 복사본 갱신 로직은 필요 없다.
- **DEFAULT 를 두지 않는다.** V41 선례(`event_video_comments.created_at`)의 DEFAULT 는 "지금"이 맞는 컬럼의
  안전망이다. 이 컬럼은 "지금"이 아니라 `videos` 의 복사본이라, 컬럼을 빠뜨린 INSERT 가 틀린 값으로 조용히
  채워지는 것보다 NOT NULL 위반으로 실패하는 편이 낫다. 그래서 native INSERT 두 곳(아래 §테스트)은 반드시 같이
  고친다.
- **피드 JPQL 변경** (`EventVideoRepository.java:63`, `:85-86`): ORDER BY 를 `v.createdAt DESC, v.id DESC` 에서
  `ev.createdAt DESC, ev.videoId DESC` 로, 다음 페이지의 keyset 조건을 `(ev.createdAt < :cursorCreatedAt OR
  (ev.createdAt = :cursorCreatedAt AND ev.videoId < :cursorId))` 로 바꾼다. 프로젝션(`v.createdAt`)과
  `EventVideoCursor` 는 그대로다. `ev.videoId = v.id` 이고 `ev.createdAt = v.createdAt` 이므로 결과 집합, 순서,
  커서 값이 전부 동일하다. 술어(ACTIVE, PUBLIC, READY, 차단 NOT EXISTS)는 손대지 않는다.
- 기대 플랜: `idx_event_videos_location_recent` 를 위치 등치 + 정렬 순서로 Index Scan → `videos_pkey` 로 행마다
  노출 게이트 3종 판정 → LIMIT 21 에서 멈춘다. 비노출 행이 섞인 만큼만 더 읽는다. Sort 노드가 사라지는 것이
  판정 기준이다.
- `countVisibleByLocationIds` (`:29-39`)와 `existsByLocationId` (`:18`)는 변경하지 않는다. 새 인덱스의 선두 열이
  `event_location_id` 라 V39 의 `idx_event_videos_location` 을 그대로 대체하므로 **V39 인덱스는 V58 에서 DROP** 한다.
  같은 선두 열의 인덱스 둘을 유지하면 쓰기마다 두 번 갱신할 뿐 이득이 없다.

### 3. Flyway 와 CONCURRENTLY

Flyway 는 마이그레이션을 트랜잭션 안에서 돌려 `CREATE INDEX CONCURRENTLY`[^5] 를 쓸 수 없다. 일반 `CREATE INDEX`
는 생성 동안 그 테이블의 쓰기를 막는다. dev 와 prod 의 `videos`, `event_videos` 는 소규모라(로컬 시드 74만 행에서도
인덱스 생성은 수 초) 허용한다. 수백만 행이 되면 그때 Flyway 밖 수동 CONCURRENTLY 를 검토한다.

-- Flyway 가 트랜잭션 안에서 돌려 CONCURRENTLY 를 못 쓴다. dev 와 prod 는 소규모라 잠금 시간이 짧다.

### `V58__event_videos_created_at.sql`

```sql
-- MSG-612: 행사 피드 "위치의 최신순 상위 N" 인덱스. 정렬 키(videos.created_at)가 필터 키
-- (event_videos.event_location_id)와 다른 테이블에 있어 어떤 인덱스도 top-N 을 못 줬다
-- (2026-10-03 감사 §3.1 #12: 영상 2만 건 위치의 첫 페이지 361ms, 매 페이지 전 영상 정렬).
-- videos.created_at 을 event_videos 에 한 칸 복사한다. 원본은 updatable=false 라 어긋날 경로가 없다.
-- DEFAULT 를 두지 않는다: 이 값은 "지금"이 아니라 videos 의 복사본이라, 빠뜨린 INSERT 는 틀린 값으로
-- 조용히 채워지는 것보다 NOT NULL 로 실패하는 편이 낫다.
ALTER TABLE event_videos ADD COLUMN created_at TIMESTAMP;

UPDATE event_videos ev
SET created_at = v.created_at
FROM videos v
WHERE v.id = ev.video_id;

ALTER TABLE event_videos ALTER COLUMN created_at SET NOT NULL;
COMMENT ON COLUMN event_videos.created_at IS
	'videos.created_at 복사본(피드 정렬과 keyset 인덱스용). 업로드 시 EventVideo 생성자가 채운다. MSG-612';

CREATE INDEX idx_event_videos_location_recent
	ON event_videos (event_location_id, created_at DESC, video_id DESC);

-- V39 의 단일 열 인덱스는 새 인덱스의 선두 열이 같아 전부 대체된다(위치별 count, exists, 피드).
DROP INDEX idx_event_videos_location;
```

백필 UPDATE 는 `event_videos` 전 행(FK 로 `videos` 행이 반드시 있다)을 한 문장으로 채우므로 NOT NULL 승격에서
실패할 행이 없다. `videos` 삭제는 소프트 삭제라 고아 행도 없다.

### 엔티티 `EventVideo` (`src/main/java/com/msg/fillmap/event/entity/EventVideo.java`)

```java
/**
 * videos.created_at 의 복사본 (MSG-612). 피드 정렬과 keyset 이 event_videos 쪽 인덱스
 * (idx_event_videos_location_recent)만으로 끝나게 하려고 둔다. 원본이 updatable=false 라 갱신 경로가 없다.
 */
@Column(name = "created_at", nullable = false, updatable = false)
private LocalDateTime createdAt;

public EventVideo(Video video, EventLocation location, Long eventOccurrenceId) {
	this.video = video;
	this.location = location;
	this.eventOccurrenceId = eventOccurrenceId;
	this.createdAt = video.getCreatedAt();
}
```

`spring.jpa.hibernate.ddl-auto: validate` 가 컬럼 존재를 기동 시 확인한다.

## 검증 (실측 절차)

구현 에이전트가 그대로 따른다. 결과는 아래 §작업 로그의 전후 표에 옮긴다.

### 시드

### 예외 흐름

- 새 예외 없음. `created_at` 을 빠뜨린 native INSERT 는 PostgreSQL NOT NULL 위반

  실측 메시지(로컬, 컬럼 없는 INSERT 를 롤백 트랜잭션에서 실행): `ERROR: null value in column "created_at" of
  relation "event_videos" violates not-null constraint — DETAIL: Failing row contains (900003602, 3324, 2223, null)`.
- **AC-612-07 예외**: `EventVideoQueryServiceTest` 의 시각 고정 헬퍼 `업로드시각` 이 복사본 `event_videos.created_at`
  도 같이 갱신하도록 고쳤다. 이 헬퍼는 `videos.created_at` 을 native UPDATE 로 고정하는 테스트 전용 경로라 복사본이
  어긋나 정렬·커서 테스트 2건(`커서로_다음_페이지가_끊김_없이_이어진다`, 차단 `빠진_행사_영상은_페이지_크기를_
  소비하지_않고…`)이 깨졌다. 운영에는 `created_at` 을 고치는 경로가 없어(`updatable = false`) 정합 규칙 자체는 그대로다.

정했다. 상대 팀원(Owner A)이 확인할 것은 마이그레이션 두 파일뿐이다.

[^1]: 비정규화: 조인으로 구할 수 있는 값을 다른 테이블에 복사해 두는 것. 여기서는 `videos.created_at` 을
    `event_videos` 에 복사해, 필터 열과 정렬 열이 한 테이블, 한 인덱스에 놓이게 한다. 대가는 두 값을 같게 유지할
    책임인데, 원본이 생성 후 바뀌지 않는 컬럼이라 그 책임이 업로드 시점 복사 한 번으로 끝난다.
[^2]: keyset 커서: 페이지 번호 대신 "마지막으로 본 항목의 정렬 키 값"(여기서는 `created_at`, `video_id` 쌍)을
    경계로 넘겨 그 뒤부터 읽는 페이지네이션. 정렬 키와 같은 열로 인덱스가 있으면 경계 위치로 바로 점프한다.
[^3]: Bitmap Heap Scan 과 Rows Removed by Filter: 인덱스로 후보 행의 위치 비트맵을 만든 뒤 테이블(힙)을 읽는
    방식. `Rows Removed by Filter` 는 힙까지 읽고 나서 WHERE 로 버린 행 수다. 85,082 는 인덱스가 `grid_id` 를
    몰라 사용자 전 행을 읽은 뒤 버렸다는 뜻이고, 이 수치가 0 이 되는 것이 인덱스 효과의 직접 증거다.
[^4]: LATERAL 조인: 바깥 행마다 서브쿼리를 한 번씩 실행하는 조인. 친구 도감은 격자 30칸마다 썸네일 1건을 고르는
    서브쿼리를 돌리므로 서브쿼리 비용 × 30 이 전체 비용이 된다.
[^5]: `CREATE INDEX CONCURRENTLY`: 테이블 쓰기를 막지 않고 인덱스를 만드는 PostgreSQL 옵션. 트랜잭션 블록 안에서는
    쓸 수 없어서 Flyway 의 기본 트랜잭션 마이그레이션과 양립하지 않는다.
[^6]: `VACUUM ANALYZE`: 죽은 행을 정리하고 플래너 통계를 다시 모은다. 대량 시드나 백필 직후에는 통계가 낡아
    플래너가 엉뚱한 플랜을 고를 수 있으므로, 전후 측정 모두 이 명령 뒤에 한다.
