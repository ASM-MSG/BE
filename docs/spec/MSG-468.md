# MSG-468: AI 경로추천의 화면 밖 지역 안내 신호

**Owner**: 공동 (주 구현 Owner B, Owner A 확인 지점은 계약 변경 절의 RegionQueryService 1건)

> 요구사항 정본: `docs/prd/MSG-468-prd.md` (상태 검토됨, 2026-08-25 성민 승인). 이 스펙은 그
> PRD의 FR과 비기능에 "어떻게"만 붙인다. 내용이 어긋나면 PRD가 이긴다.
> route 도메인 로직의 정본은 `docs/spec/MSG-457.md`다. 후보 수집과 순서 배열과 응답 조립
> 구조는 그대로 두고, 판정 하나와 응답 필드 하나만 얹는다.
> SRS 참조: FR-ROUTE-14 (`docs/srs.md` 등재 완료, 상태 계획), FR-ROUTE-06 (불변 확인).

## 개요

AI 경로추천은 뷰포트[^1] 안에서만 후보를 찾는다. 서울 지도를 보며 "부산 축제랑 팝업스토어
보고 싶어"를 보내면 서울 결과 여덟 개가 아무 안내 없이 정상 응답으로 나간다(2026-08-24 dev
실측). 이 티켓은 자연어 해석[^2]이 이미 돌려주는 지역 이름(`ParsedIntent.region`)을 서버가
보유한 행정구역(regions)과 구역 통칭(zones) 데이터에 대조해, 언급 지역과 뷰포트가 어긋나면
응답에 신호 하나(지역 이름, 중심 좌표, 외접 사각형, 종류)를 싣는다. 추천 자체는 계속 뷰포트
기준이고(FR-ROUTE-06 불변), 지도를 옮기고 다시 요청하는 것은 FE와 사용자의 몫이다.

## 배경 · 목표

지역을 먼저 말하는 문장("부산 여행 가는데 코스 짜 줘")은 이 기능의 가장 자연스러운 말투라서,
조용한 오답이 첫 사용에서 바로 나온다. 빈 결과보다 나쁜 상태다. 목표는 사용자가 화면 밖
지역을 말했다는 사실을 응답이 알려주는 것, 그리고 화면이 언급 지역의 일부만 담게 뚜렷이
좁을 때 더 넓게 볼지 알려주는 것이다(2026-08-25 편입, FR-6).

## API 명세

### `POST /api/routes/recommend` (기존 엔드포인트, 응답 필드 추가만)

요청은 무변경이다. 응답 `RouteRecommendResponseDto`에 `mentionedArea` 하나가 는다.

```json
{
	"points": [ { "order": 1, "...": "기존 그대로" } ],
	"notice": null,
	"mentionedArea": {
		"name": "부산광역시",
		"centerLat": 35.1985,
		"centerLng": 129.0538,
		"minLat": 35.0512,
		"minLng": 128.7602,
		"maxLat": 35.3891,
		"maxLng": 129.2723,
		"kind": "MOVE"
	}
}
```

| 필드 | 타입 | 규칙 |
|---|---|---|
| `mentionedArea` | 객체, nullable | 언급 지역 신호. **무신호가 기본값(null)이다.** 스키마 선언은 `notice`와 같은 방식(requiredProperties에 포함, nullable=true)으로 해 응답 스키마 전역 가드를 통과시킨다 |
| `mentionedArea.name` | String | 서버 데이터의 정식 표기다. 행정구역이면 매칭된 단위의 토큰("부산광역시", "해운대구", "부전2동"), 통칭이면 `zones.name`("서면"). AI가 준 문자열("부산")이 아니다 |
| `mentionedArea.centerLat/centerLng` | double | 언급 지역의 중심(WGS84). 행정구역은 경계 도형의 무게중심[^4], 구역은 외접 사각형 중점이다 |
| `mentionedArea.minLat/minLng/maxLat/maxLng` | double | 언급 지역의 외접 사각형(남서, 북동 두 좌표, WGS84). **kind와 무관하게 항상 실린다.** 행정구역은 경계 도형의 외접 사각형(`ST_Extent`), 구역은 격자 사각형의 위경도 환산이다 |
| `mentionedArea.kind` | String | `MOVE`(언급 지역이 뷰포트와 안 겹침, 이동 제안)와 `ZOOM_OUT`(겹치지만 뷰포트가 뚜렷이 좁음, 축소 제안) 두 값 |

외접 사각형을 kind와 무관하게 항상 싣는 이유는 FR-4의 "그 지역이 보이게 넓힌다"에 축척
재료가 필요해서다(Codex 3라운드 반영). 구역은 남북 약 2.6km 캡이 있고 시도는 수십 km라 필요한
축척이 전혀 다른데, 중심 좌표만으로는 FE가 얼마나 넓힐지 정할 수 없다. MOVE에서도 지역이
보이게 옮기는 데 같은 값을 쓴다. FE 주의 한 가지: 사각형대로 넓혀도 뷰포트 상한(한 변 0.5도)
때문에 지역 전체를 못 담을 수 있다(경기도, 섬이 사각형을 늘리는 인천과 경북 등). FE는
상한까지만 넓히고, 재요청은 그 화면 기준이다. 축소를 제안해도 추천은 상한 안의 화면 범위라는
PRD 비목표 그대로다. 신호 구성에 사각형을 더한 것은 필드 추가뿐인 비파괴 확장[^5]이라 PRD
문면(이름과 중심 좌표가 실린다)과 상충하지 않는다. 시각 필드가 없어 시각 컨벤션(MSG-376)
검사 대상이 아니다. 에러 코드 변화 없음.

## 도메인 로직

### 0. 판정 위치: 해석 캐시 뒤, 두 반환 경로 앞

판정은 `doRecommend`에서 **parse(해석 캐시[^6] 경유) 직후** 실행한다. 캐시 앞이 아니라 뒤에
두는 이유: 판정 입력이 (해석된 region 문자열, 요청 뷰포트)인데 캐시 키가 (text, 뷰포트
4좌표)라서, 캐시 창 안의 재요청은 같은 region 문자열을 받아 같은 판정이 재현된다. regions와
zones는 시딩 때만 변하는 데이터라 재계산 결과가 흔들릴 일이 없고, 조회 비용이 ms 수준이라
판정 결과를 따로 캐시하지 않는다.

계산 결과는 **빈 후보 조기 반환(FR-ROUTE-07 분기)과 정상 assemble 두 경로 모두에 싣는다.**
서울 뷰포트에 서울 후보조차 없는 응답이야말로 "부산으로 옮길까요" 신호가 가장 필요한
지점이라, 조기 반환 경로 누락이 이 기능의 가장 쉬운 구현 실수다. explain 입력(facts)에는
아무 영향이 없다.

### 1. 이름 대조 (매칭 규칙)

`intent.region`이 null이거나 공백이면 무신호로 끝낸다(FR-2). 값이 있으면 trim 후 통칭 먼저,
다음 행정구역 세 단위 순서로 대조한다.

- **구역 통칭**: `zones.name` 완전 일치. 기존 `ZoneQueryService.getZones()`(전량 48행)를
  요청 시 한 번 불러 메모리에서 거른다. 계약 변경이 없다(계약 변경 절).
- **시도**: `region_name`의 첫 토큰이 입력과 같거나, 입력에 행정 접미 다섯 가지(특별시,
  광역시, 특별자치시, 도, 특별자치도)를 붙인 값과 같으면 매칭이다. "부산"과 "부산광역시"가
  둘 다 부산광역시에 닿는다. 접미 붙이기는 문법 규칙이지 별칭 사전이 아니다. "충북" 같은
  축약형은 사전 없이는 못 잡으므로 대조 실패로 흘린다(FR-3, PRD 비목표).
- **시군구**: 둘째 토큰 완전 일치("해운대구"). 축약형("해운대")은 시도와 달리 접미를 떼면
  통칭이나 다른 지명과 충돌하기 쉬워 받지 않는다.
- **동**: 셋째 토큰 완전 일치("부전2동").

토큰 번호와 코드 접두 길이의 정본은 `RegionUnit`(동 10/3, 시군구 5/2, 시도 2/1)이다. 매칭
그룹은 단위별 코드 접두로 묶는다. 부산의 행정동 200여 행은 시도 그룹 하나다.

**판정은 2단이고, 통칭 일치가 행정구역 동명을 이긴다(2026-08-25 성민 확정으로 PRD FR-1에
반영됨, 정본은 PRD).**

1. zones 이름 대조에서 **유일** 일치가 나오면 그것을 채택하고, 행정구역 쪽 동명 그룹은 세지
   않는다. zone끼리 동명이면(zones.name은 비유일) 무신호다.
2. zone 일치가 없을 때만 행정구역 매칭 그룹의 유일성을 본다. 그룹이 0이면 대조 실패(FR-3),
   2 이상이면 동명 다수(FR-2)로 무신호다. 전부 화면 밖이어도, 하나가 화면 안이어도 동명
   다수는 무신호라는 PRD 확정을 그대로 따른다.

통칭 우선을 두는 이유. 첫째, 평면 유일성 판정이면 이 기능의 대표 사례가 구조적으로 죽는다.
regions의 셋째 토큰에는 읍·면이 포함되므로 "서면"은 춘천시 서면, 홍천군 서면, 양양군 서면 등
면 단위 그룹이 여럿 잡히고, 거기에 zone 서면(부산 상권)까지 더해 그룹 수가 항상 2 이상이다.
zones 대조를 편입한 바로 그 사례("서면")가 늘 무신호가 된다. 둘째, 표시명 체계의 기존 선례와
같은 방향이다. zone 안 격자는 zoneName이 행정동 폴백을 이긴다(MSG-341, 조립 규칙
`zoneName ? zoneName+" "+zoneCell : regionName`). 셋째, zones 등재 기준이 "유명하거나 특별한
통칭"이라 사용자가 그 이름을 말했을 때 의도가 등재된 통칭일 확률이 압도적이다. 강원의 면을
의도한 사용자가 부산 통칭 신호를 받는 오답은 수용한다. 신호는 무시 가능하고 추천 결과는
불변이다. PRD FR-2의 동명 다수 무신호는 행정구역끼리의 동명("중구")에 적용되는 규칙이고,
통칭과 행정구역이 같은 이름일 때 통칭을 짚는 규칙은 2026-08-25 성민 확정으로 PRD FR-1
문면에 올라갔다(스펙 Codex 리뷰가 적발한 후속 결정, 정본은 PRD).

### 2. 신호 종류 판정 (겹침과 축소 임계)

유일 매칭 하나에 대해 뷰포트와의 관계를 본다.

- **겹침 없음이면 MOVE.** 행정구역의 겹침은 외접 사각형이 아니라 **실제 경계 도형**으로
  판정한다(`ST_Intersects`, 조회 1문장에 동봉). 외접 사각형으로 하면 김해 뷰포트가 부산
  사각형 안에 들어 "부산을 더 넓게 볼까요"라는 틀린 종류가 나간다. 구역은 격자 사각형이 곧
  실체라 WGS84 외접 사각형 교차로 충분하다(EPSG:5179[^7] 기울어짐 때문에 외접 사각형이
  실제보다 수십 m 크지만 판정 목적에 무해).
- **겹침이 있으면 담김 비율을 본다.** 담김 비율 = (뷰포트 ∩ 지역 외접 사각형)의 넓이 / 지역
  외접 사각형의 넓이. 도 단위 평면 산술로 계산한다. 두 사각형이 같은 위도대에 있어 경도
  축척이 분자와 분모에서 상쇄되므로 비율 판정에는 충분하다.
  **비율이 0.25 미만이면 ZOOM_OUT, 이상이면 무신호다.** 상수
  `ZOOM_OUT_COVERAGE_RATIO = 0.25`.

신호를 만들면 판정에 쓴 외접 사각형 그대로를 응답에 싣는다(API 명세 절). 판정용과 응답용이
같은 값이라 별도 계산이 없다.

### 3. 임계값 25%의 근거 (PRD 미해결 질문 1의 해소)

갈라야 하는 두 군집이 실데이터에서 멀리 떨어져 있다.

- 신호가 떠야 하는 쪽(FR-6의 동기 사례): 도착 직후 도보 화면은 한 변 1~3km(0.01~0.03도)다.
  부산광역시 외접 사각형은 약 0.34도 × 0.51도라 담김 비율이 0.5%를 넘지 못한다.
- 신호가 뜨면 안 되는 쪽(PRD가 경고한 무뎌짐 사례): 서울 외접 사각형은 약 0.27도 ×
  0.46도로 뷰포트 상한(한 변 0.5도) 안에 들어온다. 서울을 얼추 다 담은 화면에서 "서울
  맛집"을 물으면 담김 비율이 80%를 넘는다.

임계는 그 사이 중간 지대를 가르는 값이다. 구 하나를 보며 시를 말하면 비율 5~10%라 신호가
뜨고, 시의 절반을 보면 50%라 안 뜬다. 0.25를 고른 이유는 선형 절반 기준의 넓이 표현이라서다.
가로세로 모두 지역의 절반을 못 담으면 0.5의 제곱인 0.25 아래로 떨어진다. "화면이 지역을
절반도 못 담는다"가 "뚜렷이 좁다"의 산술 번역이다. 가장 작은 단위에서도 상식과 맞는지
확인했다. 구역은 남북 26행(약 2.6km) 캡이 있는데, 서면(약 1.7km × 1.1km)을 1km 화면으로
보면 절반쯤 담겨 무신호이고 500m 화면이면 13%라 신호가 뜬다. 지역 자기 크기 대비 비율이라
시군구 크기의 10배 편차(강남구 약 0.05도, 홍천군 약 0.8도)에 자동 적응한다. PRD가 후보로
적은 "행정 단위별 고정 임계" 방식을 쓰지 않은 이유가 이 편차다. 25%는 실측 없이 고른
설계값이므로 아래 지표 로그로 발화 빈도를 재고, 무뎌지거나 안 뜨면 상수 하나만 조정한다.

### 4. 실패 비전파

판정 도중의 예외(DB 오류 등)는 warn 로그만 남기고 무신호로 삼킨다. 신호는 부가 정보라
판정이 안 된다고 추천이 실패로 바뀌면 안 된다는 FR-3의 정신을 예외까지 확장한 것이고, 장소
검색 5502를 후보 0으로 삼키는 기존 확정(MSG-457, 2026-08-24)과 같은 원칙이다.

### 5. 지표 로그

기존 한 줄에 `signal=none|move|zoom_out` 키를 추가한다. 임계 25%가 설계값이라 발화 빈도
실측이 튜닝 재료다. 지역 이름 자체는 로그에 남기지 않는다(문장 원문 비기록 규칙과 같은 결).

## 계약 변경

- **RegionQueryService(Owner A)에 이름 대조 조회 1건을 신설한다. 이 스펙의 유일한 크로스오너
  확인 지점이다.**

  ```java
  /** 언급 지명 대조: 시도(접미 보정), 시군구, 동 세 단위 완전 일치 그룹. 매칭 없으면 빈 리스트. */
  List<MentionedRegionMatch> matchMentionedRegions(String name, ViewportBounds viewport);

  record MentionedRegionMatch(String name, double centerLat, double centerLng,
  	double minLat, double minLng, double maxLat, double maxLng, boolean overlapsViewport) {
  }
  ```

  구현(Owner A)은 `RegionRepository`에 native 한 문장을 신설한다. UNION ALL 3분기(시도,
  시군구, 동)로 토큰을 대조하되 split_part 위치는 리터럴로 박고(MSG-356 실측 선례,
  `findDistricts` 주석), 단위별 코드 접두로 GROUP BY 해 그룹마다 이름(MIN 단일화),
  `ST_Centroid(ST_Collect(boundary_geom::geometry))` 중심,
  `ST_Extent(boundary_geom::geometry)` 외접 사각형,
  `BOOL_OR(ST_Intersects(boundary_geom, 뷰포트 envelope::geography))` 겹침을 낸다.
  외접 사각형은 담김 비율 판정과 응답 신호의 범위 재료를 겸한다(API 명세 절).
  무게중심을 외접 사각형 중점 대신 쓰는 이유: 인천(백령도 포함)이나 경북(울릉도 포함)처럼
  섬이 사각형을 끌어 늘리는 시도에서 중점이 바다에 떨어진다. 무게중심은 면적 가중이라 본토
  근처에 남는다.
- **ZoneQueryService는 무변경이다.** PRD 변경 파일 목록에는 통칭 조회 추가가 있었지만 기존
  `getZones()`(전량 48행)로 충분해 "부족하면 비파괴 추가" 조건이 불발동한다
  (MissionQueryService를 무변경으로 판정한 MSG-457 선례). 구역의 WGS84 외접 사각형은 route
  쪽에서 네 모서리 셀의 `GridEncoder.bbox` 점들을 모아 만든다. 기울어진 사각형이라 남서와
  북동 두 점으로 복원할 수 없다는 격자 계산 규칙 그대로다. 이 환산값이 겹침과 담김 판정,
  그리고 응답 신호의 범위 재료로 그대로 쓰인다.
- 판정 합성(통칭 우선 2단 판정, 종류 결정, 담김 비율 산술)은 route 패키지 안에서 한다.
  행정구역과 통칭 두 출처에 같은 규칙을 한 곳에서 적용하기 위해서다. PRD 변경 파일 목록이
  RegionQueryServiceImpl에 적어 둔 "뷰포트 겹침 판정" 중 경계 도형 겹침은 위 계약의
  `overlapsViewport`로 Owner A가 내고, 순수 사각형 산술은 route(Owner B)가 갖는다.
- `RouteRecommendResponseDto`에 nested record `MentionedAreaDto` 추가(Owner B, API 명세 절).
- `GridQueryService`, `HotZoneService`, `UserGridQueryService`, `UserOidcCommandService`
  변경 없음.

## 테스트 시나리오

테스트 메서드명 후보와 검증 요구(`// 검증: FR-ROUTE-14` 주석 규칙, FR-n은 PRD 번호):

- `화면_밖_지역을_말하면_이동_신호가_실린다`: 서울 뷰포트에 "부산" 언급, name이
  "부산광역시"(AI 반환 문자열 아님) (FR-1, 데이터 정합)
- `축약형_시도_이름도_정식_명칭으로_대조된다`: "부산"과 "부산광역시" 모두 같은 신호 (FR-1)
- `동명_읍면이_있어도_통칭이_우선한다`: 서울 뷰포트에 "서면" 언급이면 강원의 면 그룹들이
  아니라 zone 서면(부산 상권) 기준 MOVE (FR-1, 통칭 우선 결정)
- `신호에는_외접_사각형이_항상_실린다`: MOVE(행정구역, ST_Extent 출처)와 ZOOM_OUT(구역, 격자
  사각형 환산 출처) 각각에서 남서와 북동 두 좌표 검증 (FR-4 재료)
- `지역을_말하지_않으면_신호가_없다`: region null과 공백 각각 (FR-2)
- `동명_행정구역이_여럿이면_신호가_없다`: "중구"류, 하나가 화면 안에 겹치는 배치도 무신호
  (FR-2)
- `동명_통칭이_여럿이면_신호가_없다`: 같은 name의 zone 두 건 시드 (FR-2, 2단 판정 1)
- `모르는_지역_이름은_신호_없이_정상_추천된다`: 오타, 해외 지명, 미등재 통칭 (FR-3)
- `좁은_화면에서_넓은_지역을_말하면_축소_신호가_실린다`: 부산역 도보 화면에 "부산", kind가
  ZOOM_OUT (FR-6)
- `화면이_언급_지역을_충분히_담으면_신호가_없다`: 담김 비율 25% 경계 양쪽 케이스 (FR-6)
- `실제_경계와_겹치지_않으면_외접_사각형이_겹쳐도_이동_신호다`: 김해 뷰포트에 "부산" (FR-1,
  FR-6 종류 구분)
- `후보가_없어도_신호는_실린다`: 빈 points 조기 반환 경로에 mentionedArea 동봉 (FR-1, FR-5)
- `신호가_있어도_추천_결과는_그대로다`: points와 notice가 신호 유무와 무관하게 동일 (FR-5)
- `판정_조회가_실패해도_추천은_성공한다`: region 조회 예외 스텁, 무신호 성공 응답 (FR-3 확장)
- `캐시_창_안_재요청은_같은_신호를_받는다`: 해석 캐시 히트 경로에서 판정 재현 (판정 위치 절)
