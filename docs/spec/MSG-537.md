# MSG-537: 행사 운영자 첫 로그인 비밀번호 설정 API

**Owner**: B (콘텐츠·인증 도메인, `com.msg.fillmap.auth.*`)

> 요구사항 정본: `docs/prd/MSG-537-prd.md` (검토됨, 2026-09-01 사용자 승인)
> SRS: FR-AUTH-17 (계획 → 이 티켓이 구현) · 디자인: 웹 시안 1-3a (피그마 `15836:357`,
> 캡처 `docs/design-captures/org-1-3a-first-login-password.png`)

## 개요

행사 운영자[^1]의 첫 로그인 화면(시안 1-3a)이 부를 API가 없다. 화면은 새 비밀번호 두 칸만 받는데,
기존 변경 API(`POST /api/auth/password/change`)는 현재 비밀번호가 필수라 이 화면에서 호출할 수 없다.
초기 비밀번호 상태(강제 변경 플래그[^2]가 켜진 계정)에서만 통하는 설정 전용 엔드포인트
`POST /api/auth/password/initial`을 추가한다. 기존 변경·재설정 2종의 계약은 건드리지 않는다.

## 배경 · 목표

- 관리자가 발급한 계정은 첫 로그인에서 비밀번호 변경이 강제다(FR-AUTH-15). 그 첫 설정을 현재
  비밀번호 입력 없이 새 비밀번호만으로 마칠 수 있게 한다(FR-AUTH-17). 현재 비밀번호 생략은
  "초기 비밀번호로 이미 로그인에 성공한 사용자"라는 전제에서 수용된 결정이다(2026-09-01 사용자 확정).
- 설정을 마친 계정은 이 경로를 다시 쓸 수 없고, 그 요청은 화면이 재변경 화면(1-3b)으로 안내할 수
  있는 전용 오류로 거절된다.

## 성공 기준

아래 조건이 전부 테스트로 관찰되면 완료다. 검증 테스트에는 `// 검증: FR-AUTH-17` 마커를 단다
(2441 메시지 교체분은 FR-AUTH-15 게이트 테스트의 기대 문자열 갱신).

1. 강제 변경 플래그가 켜진 LOCAL 계정이 새 비밀번호 하나로 200을 받고, 직후 `/api/org/**` 접근
   차단이 풀리며 현재 로그인 세션은 유지된다 (PRD FR-1·FR-2).
2. 성공 시 남아 있던 재설정 링크[^3]가 폐기된다 (PRD FR-2).
3. 플래그가 꺼진 계정의 요청은 전용 코드 2446으로 거절된다 (PRD FR-3).
4. 새 비밀번호가 저장된 해시와 같으면 2444로 거절된다 (PRD FR-4).
5. 비밀번호 없는 소셜 계정은 2445로 거절된다 (PRD FR-5).
6. 새 비밀번호는 기존 정책(영문과 숫자 각 1자 이상, 8~64자) 위반 시 400 검증 실패다 (PRD FR-6).
7. 2441 게이트 응답 메시지가 "초기 비밀번호를 설정해야 이용할 수 있습니다"로 나온다 (코드값 불변).

## API 명세

### POST /api/auth/password/initial

- 인가: 로그인 필수 (액세스 토큰). `SecurityConfig`에서 `/api/auth/password/status`·`/change`와
  같은 줄의 `authenticated` 명시에 합류한다. catch-all이 역할 제한이라 명시하지 않으면 주 사용자인
  ORG가 403이 된다 (기존 주석의 이유 그대로). 첫 로그인 게이트 차단 경로(`/api/org/**`) 밖이라
  초기 비밀번호 상태에서도 호출된다 (`PasswordChangeGateInterceptor` 변경 없음).
- Request: `PasswordInitialRequestDto` (신규, record)
  - `newPassword: String`. `PasswordChangeRequestDto.newPassword`와 동일한 어노테이션을 재사용한다
    (`@NotBlank`, `@Size(8~64)`, `@Pattern` 영문·숫자 각 1자 이상)
- Response: `SuccessResponse<Void>` (200, data null)
- 에러 케이스 (서비스 검사 순서대로):

| 조건 | developCode | HTTP | 비고 |
|---|---|---|---|
| 사용자 행 없음 | 1404 USER_NOT_FOUND | 404 | change와 동일 |
| 소셜 계정 (provider != LOCAL 또는 해시 null) | 2445 PASSWORD_NOT_SET | 400 | PRD FR-5. 플래그 검사보다 **먼저** 둔다. 소셜 계정은 플래그가 항상 꺼져 있어 순서를 바꾸면 2446으로 새고, 화면이 재변경 화면으로 잘못 안내한다 |
| 강제 변경 플래그 꺼짐 | **2446 신설** | 409 | PRD FR-3. 화면 분기 신호 |
| 새 비밀번호 = 저장된 해시 | 2444 NEW_PASSWORD_SAME_AS_CURRENT | 400 | PRD FR-4 |
| 정책 위반 | 400 BAD_REQUEST (공통) | 400 | `@Valid` 검증, 핸들러가 필드 메시지 조합 |

### AuthErrorCode 변경 2건

```java
// 신설. 2446은 행사 운영자 계정 보안 대역(2441~2445)의 다음 값이다
INITIAL_PASSWORD_ALREADY_SET(2446, HttpStatus.CONFLICT, "이미 비밀번호 설정을 마친 계정입니다"),

// 메시지 교체 (코드값·상수명 불변). 시안 1-3a 뱃지 문구 정렬, PRD 미해결 질문 1 확정
PASSWORD_CHANGE_REQUIRED(2441, HttpStatus.FORBIDDEN, "초기 비밀번호를 설정해야 이용할 수 있습니다"),
```

2446의 HTTP를 409로 두는 이유: 요청 자체는 올바른데 계정 상태가 전제와 어긋난 경우라서다.
입력 문제(400 대역인 2442·2444·2445)와 갈라 두면 화면이 상태 충돌만 골라 1-3b로 안내할 수 있다.

## 도메인 로직

`PasswordService.setInitialPassword(Long userId, PasswordInitialRequestDto request)` 신설.
`changePassword`의 잠금·후처리 계약을 그대로 따르고, 현재 비밀번호 대조 한 단계만 플래그 확인으로
바뀐다 (PRD 변경 파일 표의 문구 그대로).

1. `transactionTemplate.executeWithoutResult` 경계 안에서 `userRepository.findWithLockById(userId)`
   행 잠금[^4] 조회. 초기 비밀번호 재발송(MSG-499)·변경·재설정 확정이 같은 행을 같은 잠금으로 쓰는
   계약이라, 잠그지 않으면 낡은 스냅숏이 최신 커밋을 되덮는다(lost update 실측, PRD 비기능).
2. 소셜 계정 검사 → 2445 (`changePassword`와 동일 조건식).
3. 플래그 검사: `user.isPasswordMustChange()`가 false면 2446. 잠금 뒤 검사이므로 동시 요청 두 건이
   와도 두 번째는 첫 번째 커밋이 푼 플래그를 보고 2446으로 수렴한다 (멱등하지 않은 대신 안전).
4. 동일 해시 검사: `passwordEncoder.matches(newPassword, 저장 해시)`면 2444. 발급자가 아는 값을
   그대로 쓰면 강제 변경의 목적이 무산되기 때문이다 (PRD FR-4).
5. `user.changePassword(encode(newPassword))`. 더티 체킹으로 해시 교체와 플래그 해제가 함께 간다
   (기존 엔티티 메서드 재사용, 신규 메서드 없음).
6. 커밋 전 `passwordResetTokenStore.revoke(userId)`. 커밋 뒤로 미루면 Redis 장애가 "비밀번호는
   바뀌었는데 옛 링크가 산다"를 만든다. 여기서 던지면 롤백돼 fail-closed[^5]다 (`changePassword`
   주석의 원칙 그대로).
7. 세션·토큰 무효화 없음. 자발적 설정이라 복구 시나리오가 아니고, 게이트 직후 재로그인을 강제하면
   흐름이 끊긴다 (`changePassword`와 동일 결정, PRD FR-2 "세션 유지").

`reset`처럼 `invalidateUser`·`deleteAll`을 부르지 않는 것이 의도다. change와 reset 중 이 API의
계약 원본은 change다.

## 테스트 시나리오

`PasswordControllerTest`에 추가. 전부 `// 검증: FR-AUTH-17` 마커를 단다 (10번은 FR-AUTH-15).

1. `강제_변경_상태의_행사_운영자가_새_비밀번호만으로_설정에_성공한다`: 200, 이후 로그인은 새
   비밀번호로만 성공
2. `설정에_성공하면_강제_변경_상태가_풀려_콘솔_접근이_열린다`: 설정 후 `/api/org/**` 호출이
   2441 없이 통과
3. `설정에_성공해도_현재_로그인_세션은_유지된다`: 설정 전 발급 액세스 토큰이 계속 유효
4. `설정에_성공하면_남아_있던_재설정_링크가_폐기된다`: 선발급 토큰으로 `/reset` 호출 시 2443
5. `설정을_마친_계정의_재요청은_전용_코드로_거절된다`: 2446, HTTP 409
6. `새_비밀번호가_초기_비밀번호와_같으면_거절된다`: 2444
7. `비밀번호가_없는_소셜_계정의_요청은_거절된다`: 2445 (2446이 아님을 함께 단언)
8. `정책에_어긋나는_새_비밀번호는_검증에서_거절된다`: 7자·숫자 없음 각 400
9. `비로그인_요청은_거부된다`: 401 (2403)
10. `게이트_차단_메시지가_설정_문구로_나온다`: `/api/org/**` 차단 응답 message가
    "초기 비밀번호를 설정해야 이용할 수 있습니다"

## 미해결 질문

없음. PRD 미해결 질문 2건은 모두 2026-09-01에 닫혔다 (2441 메시지 교체 포함, 강도 문구는 디자인 몫).

[^1]: 행사 운영자: 행사를 등재하는 외부 주체(지자체·팝업 운영사 등). 관리자가 발급한 이메일과 초기 비밀번호로 로그인하는 `role=ORG`, `provider=LOCAL` 계정이다. 필맵 내부 인력을 가리키는 맨 "운영자"와 다르다.
[^2]: 강제 변경 플래그: `users.password_must_change` 컬럼. 관리자 발급·재발급이 켜고, 비밀번호 변경·재설정·이번 설정이 끈다. 켜져 있는 동안 `PasswordChangeGateInterceptor`가 콘솔 경로(`/api/org/**`)를 2441로 막는다.
[^3]: 재설정 링크: "비밀번호를 잊었을 때" 공식 이메일로 받는 30분 유효 1회용 토큰(MSG-497). Redis에 저장되며, 비밀번호가 다른 경로로 바뀌면 폐기해야 옛 링크로 새 비밀번호를 덮는 일을 막는다.
[^4]: 행 잠금: `findWithLockById`의 비관적 잠금(SELECT ... FOR UPDATE). 같은 사용자 행을 쓰는 트랜잭션들을 줄 세워, 나중 트랜잭션이 낡은 값을 읽고 최신 커밋을 되덮는 lost update를 막는다.
[^5]: fail-closed: 부분 실패 시 아무것도 바뀌지 않은 상태로 되돌아가는 설계. 여기서는 링크 폐기가 실패하면 트랜잭션이 롤백돼 비밀번호도 링크도 그대로이고, 사용자는 재시도만 하면 된다.
