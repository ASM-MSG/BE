# MSG-432: 알림 딥링크 (서버 몫: 이동 대상 저장과 페이로드·응답 노출)

**Owner**: B (notification 도메인과 알림을 기록하는 Owner B 발생 지점 7곳, 마이그레이션 V56. 도메인 간
계약 인터페이스는 무변경)

> 요구사항 정본: `docs/prd/MSG-432-prd.md` (검토됨, 2026-09-24 성민 확정) · SRS FR-NOTI-12
> 이 문서는 PRD의 FR 1~5, FR-10과 비기능 요구에 "어떻게"만 붙인다. FR 6~9는 앱 몫이라 FE 레포에서
> 별도 스펙으로 다룬다.

## 개요

알림 한 건이 가리키는 화면을 앱이 찾아갈 수 있게, 서버가 알림을 기록하는 시점에 이동 대상을 함께
저장한다. 대상은 종류(`targetType`)와 식별자(`targetId`) 두 값이다. 저장된 대상은 두 경로로 앱에
닿는다. 푸시 발송 시 FCM `data`에 실리고, 알림함 목록 응답 항목에 실린다. 발송 파이프라인(outbox[^1]
릴레이, Kafka 소비, FCM 전송 흐름)은 그대로다. 컬럼 두 개와 페이로드 키 세 개, 응답 필드 두 개를
더할 뿐이다.

## 배경 · 목표

푸시 `data`에는 `notificationId` 하나만 있어 알림을 눌러도 첫 화면이 열린다. 앱 알림함(FE MSG-602)이
생기면서 행을 눌러도 갈 곳이 없는 진입점이 하나 더 늘었다. 서버는 영상 id, 격자 id, 뱃지 id, 회차
id를 이미 `event_key`에 넣어 두지만 그 키는 중복 방지용 내부 값이라 형식이 카테고리마다 다르고 응답에
싣지 않는 것이 계약이다(MSG-434 비기능 보안). 그래서 대상을 별도 컬럼으로 정규화해 저장하고, 화면
매핑은 앱이 대상 종류로 정한다.

## 성공 기준

- AC-432-01: 대상과 함께 기록한 알림은 `notifications.target_type`, `target_id`에 그 값이 저장되고,
  대상 없이 기록한 알림(기존 5인자 `record`, REMIND, WEEKLY)은 두 컬럼이 모두 NULL이다 (FR-1).
- AC-432-02: 종류만 있고 식별자가 없는 행, 식별자만 있는 행, 5종 밖의 종류 값은 DB CHECK가 거부한다
  (비기능 데이터).
- AC-432-03: 회차 시작 알림(`recordEventStart`)으로 기록된 모든 구독자 행은
  `EVENT_OCCURRENCE:{occurrenceId}` 대상을 갖는다 (FR-5).
- AC-432-04: FCM 메시지 `data`는 대상이 있으면 `notificationId`, `category`, `targetType`, `targetId`
  네 키를, 대상이 없으면 `notificationId`, `category` 두 키만 싣는다. `notification`(제목, 본문)과
  웹푸시 설정은 종전과 같다 (FR-2, 비기능 호환).
- AC-432-05: 컨슈머는 outbox 행의 카테고리와 대상을 그대로 발송기에 넘긴다. 기존 행(대상 NULL)도
  예외 없이 발송된다 (FR-2, FR-10).
- AC-432-06: 알림함 목록 항목에 `targetType`, `targetId`가 실리고, 대상이 없는 행은 두 필드가 null이다.
  `event_key`와 발송 내부 상태는 여전히 실리지 않는다 (FR-3, 비기능 보안).
- AC-432-07: 발생 지점 7곳이 카테고리별 규칙대로 대상을 기록한다. VIDEO 완료·실패와 MODERATION
  가림·해제는 `VIDEO:{videoId}`, HOTZONE은 `GRID:{gridId}`, BADGE 획득·임박은 `BADGE:{badgeId}`,
  FRIEND 요청 도착은 `USER:{요청자 userId}`, FRIEND 수락은 `USER:{수락자 userId}`, EVENT 일정 변경은
  `EVENT_OCCURRENCE:{occurrenceId}` (FR-5).

## 핵심 설계 결정

### D-1. 저장 = notifications 테이블에 컬럼 2개 추가 (V56)

PRD 비기능 데이터 요구를 그대로 따른다. `target_type VARCHAR(20)`, `target_id VARCHAR(64)`, 둘 다
NULL 허용이고 기존 행은 NULL로 남는다(FR-10). 별도 테이블은 검토하지 않았다. 대상은 알림과 수명이
같고 조회가 항상 알림 행 단위라 분리할 이유가 없다.

CHECK 두 개를 건다. 첫째, 종류와 식별자는 함께 있거나 함께 없다
(`(target_type IS NULL) = (target_id IS NULL)`). 한쪽만 있는 행은 앱이 해석할 수 없는데, 애플리케이션
코드는 값 객체(D-2)가 막지만 native INSERT 문장이 둘이라 DB가 최종 방어선이다. 둘째, 종류는
5종 안에서만(`chk_notifications_target_type`). 카테고리 CHECK(V21 이래)와 같은 방식이고, 새 종류는
SRS 개정과 마이그레이션이 같이 간다(FR-4).

`target_id`가 문자열인 이유는 격자 id가 문자열(`GRID:{gridId}`)이기 때문이다. 나머지 네 종류는
숫자 id를 십진 문자열로 넣는다. 인덱스는 만들지 않는다. 대상으로 알림을 찾는 조회가 없다.

### D-2. 값 객체 `NotificationTarget`(record)과 종류 enum `NotificationTargetType`

PRD 6절 클래스 다이어그램 그대로다. `record NotificationTarget(NotificationTargetType type, String id)`에
정적 팩토리 5개(`video(long)`, `grid(String)`, `badge(long)`, `eventOccurrence(long)`, `user(long)`)를
둔다. 생성자에서 두 값의 null을 거부해 "종류만 있는 대상"이 코드에서 만들어지지 않게 한다.
발생 지점은 `NotificationTarget.video(video.getId())`처럼 팩토리만 부르므로 종류와 식별자 짝이
어긋날 자리가 없다.

`Notification` 엔티티에는 `targetType`(`@Enumerated(STRING)`), `targetId` 두 필드를 조회 매핑으로
더한다. 쓰기는 전부 native INSERT라 도메인 메서드는 없다(엔티티 주석의 기존 원칙). 엔티티에서 값
객체로 되돌리는 `target()` 접근자를 하나 두어 컨슈머와 DTO가 같은 조립 규칙을 쓴다(둘 다 NULL이면
null).

### D-3. 기록 API = `record` 오버로드 하나, `recordEventStart`는 시그니처 무변경

`NotificationCommandService.record(userId, category, eventKey, title, body, NotificationTarget target)`를
더하고 기존 5인자는 `target = null`로 위임한다. REMIND(`StreakRemindScheduler`)와
WEEKLY(`WeeklySummaryScheduler`)는 5인자 그대로 두어 무변경이다.

`recordEventStart(occurrenceId, startsAt, eventKey, title, body)`는 이미 회차 id를 받으므로 인자를
늘리지 않고 구현 안에서 `EVENT_OCCURRENCE`와 그 id를 INSERT ... SELECT 문장의 상수 열로 넣는다.
호출자(`EventNotificationScheduler`)와 그 테스트는 손대지 않는다.

### D-4. 발송기 시그니처에 카테고리와 대상 추가, `data`는 있는 키만

`NotificationSender.send(notificationId, tokens, title, body, category, target)`로 바꾼다(PRD 6절).
`FcmNotificationSender.buildMessage`는 `category`를 항상 넣고, `target`이 null이 아닐 때만
`targetType`, `targetId`를 넣는다. 대상이 없을 때 빈 문자열이나 `"null"`을 넣지 않는 이유는 앱 쪽
판정이 "키가 있는가"가 아니라 "값이 5종 중 하나인가"로 가더라도, 키 자체를 안 보내는 쪽이 기존 앱
버전(모르는 키 무시)과 새 앱 버전 어느 쪽에도 해석 여지를 남기지 않기 때문이다. `notification`
필드와 `WebpushConfig`는 그대로다(비기능 호환: `data` 전용으로 바꾸지 않는다).

`category`를 함께 싣는 것은 PRD FR-2의 요구다. 앱이 REMIND 같은 대상 없는 알림을 카테고리로
구분할 여지를 남기되, 이번 결정(Q2)에서는 쓰지 않는다.

### D-5. 알림함 응답 = 항목에 nullable 필드 2개

`NotificationItemResponseDto`에 `NotificationTargetType targetType`, `String targetId`를 더한다.
둘 다 `@Schema(nullable = true)`다. 조립은 `from(Notification)`이 엔티티 필드를 그대로 옮긴다.
`event_key`는 여전히 싣지 않는다. 컨트롤러와 서비스, 리포지토리 조회 쿼리는 무변경이다(엔티티
매핑이 늘어난 것을 `SELECT n`이 그대로 읽는다).

### D-6. 발생 지점 배선 = 팩토리 한 인자 추가, 문구와 키는 무변경

| 발생 지점 | 카테고리 | 대상 | 식별자 출처 |
|---|---|---|---|
| `VideoStatusWriter.recordOutcomeNotification` (완료, 실패 2줄) | VIDEO | `video(video.getId())` | 전이 대상 엔티티 |
| `VideoModerationServiceImpl.blind`, `unblind` | MODERATION | `video(videoId)` | 메서드 인자 |
| `HotZoneEntryDetector.notifyOccupants` | HOTZONE | `grid(gridId)` | 메서드 인자 |
| `BadgeAwardServiceImpl.award` (획득), `recordNearMiss` (임박) | BADGE | `badge(candidate.getBadgeId())`, `badge(nearMiss.getBadgeId())` | 후보 프로젝션 |
| `FriendServiceImpl` 요청 도착 | FRIEND | `user(userId)` (요청자) | 요청 보낸 사용자 |
| `FriendServiceImpl.recordAcceptedNotification` | FRIEND | `user(accepterId)` (수락자) | 메서드 인자 |
| `EventSeeder.notifyScheduleChanged` | EVENT | `eventOccurrence(occurrence.getId())` | 갱신 대상 회차 |
| `EventNotificationScheduler.recordStart` | EVENT | (D-3, 구현 내부) | `recordEventStart` 인자 |
| `StreakRemindScheduler`, `WeeklySummaryScheduler` | REMIND, WEEKLY | 없음 | 무변경 |

`event_key` 형식, 제목, 본문, dedupe 규칙은 어느 지점도 바꾸지 않는다.

## API 명세

새 엔드포인트는 없다. 기존 `GET /api/notifications`(MSG-434) 응답 항목이 늘어난다.

```json
{
  "notificationId": 123,
  "category": "VIDEO",
  "title": "영상이 준비됐어요",
  "body": "올린 영상 처리가 끝났어요. 지금 확인해 보세요",
  "createdAt": "2026-09-24T02:11:00Z",
  "read": false,
  "targetType": "VIDEO",
  "targetId": "9876"
}
```

- `targetType`: `VIDEO`, `GRID`, `BADGE`, `EVENT_OCCURRENCE`, `USER` 또는 null.
- `targetId`: 문자열 또는 null. `targetType`이 null이면 반드시 null이다(D-1 CHECK).
- 이 요구 이전에 기록된 알림은 두 필드가 null이다. 앱은 null이면 지도 홈으로 보낸다(PRD FR-6, FR-10).
- 에러 케이스 변화 없음.

FCM 메시지(앱 수신 계약, 새 엔드포인트가 아니라 페이로드 계약):

```text
notification: { title, body }                       (종전과 동일)
data: {
  notificationId: "123",                             (종전과 동일)
  category: "VIDEO",                                 (신규, 항상)
  targetType: "VIDEO",                               (신규, 대상 있을 때만)
  targetId: "9876"                                   (신규, 대상 있을 때만)
}
```

## 도메인 로직

- 대상은 알림 기록과 같은 INSERT 문장에 들어간다. 별도 UPDATE가 없으므로 "대상 저장 실패가 알림
  기록을 막는" 경로는 존재하지 않는다(비기능 운영). 기록 트랜잭션 참여 규칙(호출자 트랜잭션 REQUIRED,
  FR-3 원자성)은 MSG-179 그대로다.
- 컨슈머는 행을 읽어 `notification.getCategory()`와 `notification.target()`을 발송기에 넘긴다.
  설정 필터, 전송률 제한, 토큰 조회, 상태 전이 순서와 조건은 무변경이다.
- 대상의 존재 여부는 발송 여부에 영향을 주지 않는다. 삭제된 영상이나 종료된 회차를 가리키는 대상도
  그대로 실린다. 목적지 화면의 기존 오류 처리에 맡긴다(PRD FR-9).
- 알림함 조회의 노출 조건(30일, PREF_OFF 숨김), 커서, 읽음 처리는 무변경이다.

## 데이터 모델

- **마이그레이션 V56** (`V56__notification_target.sql`. 착수 시점(2026-09-24) 원격 브랜치 전수에서
  V56 이상이 없음을 확인했다):

```sql
-- 알림 딥링크 이동 대상 (MSG-432 D-1). 기존 행은 NULL = 대상 없음(앱은 지도 홈).
ALTER TABLE notifications
	ADD COLUMN target_type VARCHAR(20),
	ADD COLUMN target_id   VARCHAR(64),
	ADD CONSTRAINT chk_notifications_target_pair
		CHECK ((target_type IS NULL) = (target_id IS NULL)),
	ADD CONSTRAINT chk_notifications_target_type
		CHECK (target_type IN ('VIDEO', 'GRID', 'BADGE', 'EVENT_OCCURRENCE', 'USER'));
```

- 인덱스 없음(D-1). `uq_notifications_user_event`, dedupe 규칙 무변경.
- **엔티티** `Notification`: `targetType`(`@Enumerated(EnumType.STRING) @Column(name = "target_type",
  length = 20)`), `targetId`(`@Column(name = "target_id", length = 64)`) 조회 매핑, `target()` 조립
  접근자.
- **신규 타입** `notification/entity/NotificationTargetType.java`(enum 5종),
  `notification/entity/NotificationTarget.java`(record, 팩토리 5개).
- **리포지토리** `insert`에 `target_type`, `target_id` 열과 파라미터 2개 추가. `insertEventStart`는
  SELECT 열에 `'EVENT_OCCURRENCE'`, `CAST(:occurrenceId AS VARCHAR)` 상수 2개 추가.

## 계약 변경

없음. `GridQueryService`, `UserGridQueryService`, `HotZoneService`, `UserOidcCommandService` 무변경.
`NotificationCommandService`는 Owner B 안에서만 소비되는 인터페이스라 계약 인터페이스가 아니고,
변경도 오버로드 추가라 기존 호출이 그대로 컴파일된다. `NotificationSender`는 notification 패키지
내부 인터페이스다.
