# MSG-597: 미션 목록 카드의 영상 수를 서버가 내려준다

**Owner**: B (`com.msg.fillmap.mission.*`, `com.msg.fillmap.video.*` 둘 다 콘텐츠 도메인)

> 요구사항 정본: `docs/prd/mission-map-explore.md` (상태: 검토됨, 2026-08-13 성민 승인) FR-3
> "그 미션 영역에 영상이 하나도 없어도 카드는 온전히 표시된다. 영상 수는 있을 때만 덧붙는다"
> 이 스펙은 FR-3에 "어떻게"만 붙인다.

## 개요

지도 홈의 미션 목록 카드가 표시하는 "영상 N"을 서버가 내려주게 한다. 지금 그 숫자는 서버에서
오지 않는다. 화면이 미션 id를 해시[^djb2]에 넣고 13으로 나눈 나머지를 그리고 있어서, 카드에는
"영상 9"가 뜨는데 같은 미션의 상세를 열면 "올라온 영상 0개"가 나온다. 서버 버그가 아니라 서버가
주지 않는 값을 화면이 지어내고 있는 것이다.

2026-09-13 프로덕션 번들(`fillmap.kr/assets/index-Dk1hV75i.js`) 실측이 근거다.

```js
LG = e => { let t = 5381; for (let n=0; n<e.length; n+=1) t = (t*33 + e.charCodeAt(n)) % 2147483647; return t }
RG = e => LG(`mission:${e}`) % 13   // 목록 카드 "영상 N"
// 카드 렌더: c = RG(e.missionId); ... c > 0 && <span>영상 {c}</span>
```

`c > 0` 조건부 렌더가 FR-3의 "있을 때만 덧붙는다"를 그대로 구현한 모양이다. 즉 화면은 이미
FR-3대로 만들어져 있고 빠진 것은 값 하나다. 상세 화면은 `${n.items.length}개`로 실제 응답을 세므로
0개가 옳은 값이다.

이 티켓은 `GET /api/missions/active` 응답 항목(`MissionResponseDto`)에 `videoCount` 하나를 더한다.
새 엔드포인트도 새 쿼리도 새 테이블도 만들지 않는다.

## 배경 · 목표

**왜 필요한가.** 지금 화면에 뜬 숫자는 틀린 값이 아니라 아예 데이터가 아니다. 사용자는 "영상 9"를
보고 카드를 눌렀다가 빈 상세를 만난다. 목록과 상세가 같은 대상을 두고 다른 말을 하는 상태라
숫자에 대한 신뢰가 통째로 깎인다. 이 티켓의 목적은 값을 예쁘게 만드는 것이 아니라 화면에서
거짓말을 걷어내는 것이다.

**스펙에 남기는 사실 하나.** 2026-08-13 dev 실측으로 미션이 덮은 격자 21,529칸 중 영상이 하나라도
있는 칸은 24칸, 0.1%다. 그래서 이 값을 서버가 내려주면 대부분의 카드에서 `videoCount`가 0이 되고
화면에서는 숫자가 사라진다. "서버가 내려주기 시작했는데 왜 값이 늘 0이냐"는 질문은 결함이 아니라
데이터의 현재 상태다. 그럼에도 구현하는 이유는 지금 그 자리에 있는 숫자가 가짜이기 때문이고,
0을 정직하게 내려 숫자를 지우는 것이 9를 지어내는 것보다 낫기 때문이다.

**목표**

- 목록 카드의 영상 수가 미션 상세의 영상 수와 같은 값이 된다.
- 영상이 없는 미션도 카드가 온전히 나가고, 영상 수만 0으로 실린다 (FR-3).
- 목록 응답이 여전히 모든 사용자에게 같다 (SRS FR-MISSION-02, 전역 스냅숏 캐시[^snapshot]의 전제).
- 미션 영상 수의 술어를 한 벌로 유지한다 (D2). 다만 차단 축의 기존 비대칭은 이 티켓으로 닫히지
  않는다 (D6).

## 성공 기준

- AC-597-01: `GET /api/missions/active` 응답의 각 항목에 `videoCount` 필드가 실리고, 그 값이 같은
  미션의 상세(`GET /api/missions/{missionId}`) `videoCount`와 같다.
- AC-597-02: 영상이 하나도 없는 미션도 항목이 그대로 실리고 `videoCount`는 `0`이다 (키 누락도
  null도 아니다).
- AC-597-03: **차단 관계가 없는 요청자 기준으로** 목록 `videoCount`, 상세 `videoCount`, 미션 영상
  목록(`GET /api/missions/{missionId}/videos`)의 후보 전체 건수 셋이 같다. 차단 관계가 있는
  요청자에게는 카드 수가 그 사람이 실제로 보는 목록 행 수보다 클 수 있고, 이는 이 티켓 이전부터
  있던 계약이다 (D6).
- AC-597-04: 비로그인 요청의 목록 응답이 로그인 요청과 완전히 같다. 컨트롤러는 이번에도
  `AuthPrincipal`을 받지 않는다.
- AC-597-05: 뷰포트[^viewport] 안에 그 종류 미션이 없으면 응답은 빈 배열이고, 영상 수 집계 쿼리는
  아예 실행되지 않는다.
- AC-597-06: `VideoRepository`에 새 native 쿼리가 추가되지 않는다. 집계는 기존
  `countVideosByMissionIds` 재사용으로만 이뤄진다.
- AC-597-07: 미션 기간 밖 촬영분, PRIVATE와 FRIENDS 공개범위, 인코딩 중, 삭제된 영상, 행사 영상은
  `videoCount`에서 빠진다.
- AC-597-08: 한 종류 실측 상한인 169건이 걸리는 뷰포트에서도 목록 조회에 추가되는 DB 왕복은
  1회다 (미션 수만큼 늘지 않는다).
- AC-597-09: `videoCount`가 응답 스키마의 `requiredProperties`에 들어가
  `ResponseSchemaNullabilityTest`가 통과한다. 이 테스트는 required(키 존재)만 검사하므로 `long`
  0 채움이라는 결정 자체는 D3의 계약과 아래 응답 계약 테스트가 고정한다.
- AC-597-10: Flyway 마이그레이션이 추가되지 않는다 (스키마 변경 없음).
- AC-597-11: 경로 추천 경로에 영상 수 집계가 붙지 않는다. 판정은 두 자리로 나뉜다. ①
  `RouteCandidateCollector`는 기존 `getMissionsInViewport`만 부르고 목록 카드용 메서드는 부르지
  않는다(인터페이스 수준). ② 그 기존 메서드는 실제 구현에서 `countVideosByMissionIds`를 한 번도
  실행하지 않는다(구현 수준).
- AC-597-12: 상세 응답의 중첩 `mission.videoCount`가 최상위 `videoCount`와 같은 값이다 (D5).

## 도메인 로직

**영상 수의 정의는 이미 레포에 있다.** 새로 정하지 않는다. "이 미션의 영상"은 그 미션의 대상 격자
(`mission_grids`)에서 미션 기간 안에 촬영되고, 전역 공개 게이트 세 가지(status ACTIVE, visibility
PUBLIC, processing_status READY)를 통과하며, 행사 영상이 아닌 영상이다. 마지막 조건은 행사 영상
안티 조인[^antijoin]이고 미션 계열 쿼리의 계약이다 (MSG-450, SRS FR-EVENT-12).

이 값이 세는 것은 glossary의 **방문**(영상 하나가 방문 이벤트 하나)이지 **점령**이 아니다. 도감
점령이나 사용자별 진행도와는 다른 값이고, 미션 카드의 "내 진행 0/1칸"은 지금처럼 별개 조회
(`GET /api/missions/progress`)에서 온다. 두 값을 한 필드로 합치지 않는다.

무기간 미션(코스처럼 `start_at`, `end_at`이 비어 있는 미션)은 기간 조건이 `IS NULL OR` 형태라 코드
분기 없이 전체 기간을 인정한다. 노출 중지된 미션(`missions.hidden_at`)은 스냅숏과 집계 양쪽에서
같이 빠지므로 어긋나지 않는다.

**차단 관계는 이 숫자에 반영되지 않는다.** 집계 쿼리 두 개(`countVideosByMissionIds`,
`countMissionVideosByGrid`)에는 `user_blocks` 절이 없고, 목록 쿼리 두 개(`findMissionVideos`,
`findMissionVideosAfter`)에는 있다. 그 결과 누군가를 차단한 사용자에게는 카드 숫자가 실제로 보이는
목록 행 수보다 크게 나온다. 이 비대칭은 이번 티켓이 만드는 것이 아니라 MSG-569가 이미 만들어 둔
상태이고, 이 티켓은 목록 카드를 그 count 축에 잇는다. 판단은 D6에 적었다.

## 계약 변경

**서비스 경계 계약(Owner A와 B가 인터페이스로만 만나는 지점)은 변경 없다.** `GridQueryService`,
`HotZoneService`, `UserGridQueryService`, `UserOidcCommandService` 중 어느 것도 건드리지 않는다.

**API 와이어 계약은 additive 변경이다.** 두 응답이 함께 바뀐다.

| 응답 | 변경 |
|------|------|
| `GET /api/missions/active` 항목 | `videoCount` 필드 추가 |
| `GET /api/missions/{missionId}` 의 `mission` 객체 | 같은 필드가 중첩으로 함께 추가 (D5) |

기존 필드의 이름, 타입, 의미는 바뀌지 않으므로 소비자가 깨지지 않는다. 상세 쪽이 함께 바뀌는 것은
의도가 아니라 구조의 결과다. `MissionDetailResponseDto`가 `MissionResponseDto`를 통째로 중첩하고
있어서다.

**Owner B 내부 계약은 하나 는다.** `MissionQueryService`에 목록 카드용 조회 메서드가 하나 추가된다
(D1의 소비자 분리). 기존 `getMissionsInViewport`의 시그니처와 동작은 그대로 두므로 route 도메인의
호출부는 손대지 않는다.

## 결정

### D1. 캐시 배치: 요청 시점 집계를 택하고, 소비자를 가른다

**결론: (b) 캐시는 그대로 두고, 뷰포트로 걸러진 미션 id 목록에 대해 요청 시점에 배치 집계[^batch]
한 번. 단 그 집계는 지도 목록 경로에만 붙이고 AI 경로 추천 경로에는 붙이지 않는다.**

#### (a) 스냅숏 동봉을 기각한 이유

지금 목록은 `MissionQueryServiceImpl`의 전역 단일 홀더 캐시에서 나간다. TTL이 1시간이고
(`CACHE_TTL`, `:83`), `getMissionsInViewport`(`:196`)가 `CachedMission::dto`를 그대로 반환하므로 응답
DTO가 캐시 안에 미리 조립돼 있다. 그래서 videoCount를 스냅숏 재계산 때 함께 세는 안 (a)이 가능하고,
요청마다 쿼리가 붙지 않는다는 것이 그 안의 장점이다.

그럼에도 (b)를 택한 이유는 셋이다.

첫째, 이 티켓이 고치려는 결함 자체가 "목록 숫자와 상세 숫자가 다르다"이다. 상세는 요청마다
`countMissionVideosByGrid`를 불러 조회 시점 실측을 내려주는데(`:316`), 목록만 스냅숏에 얼려 두면
같은 미션의 두 숫자가 최대 1시간 동안 다시 갈린다. 값의 출처가 해시에서 지난 스냅숏으로 바뀔 뿐
사용자가 겪는 증상의 모양은 같다. 고치러 온 자리에 같은 모양의 불일치를 다시 심지 않는다.

둘째, 이 레포에서 같은 성격의 수는 전부 조회 시점 실측이다. 도움돼요 수는 집계를 저장하지 않고
조회할 때 센다(glossary). 미션 진행도는 PRD 4절이 "별도 집계 값을 두고 어긋나게 하지 않는다"로
못 박았다. 격자 역조회의 videoCount도 캐시를 읽지 않는다(MSG-459).

셋째, 스냅숏에 넣으면 신선도를 되찾을 방법이 업로드 시점 무효화뿐인데, 지금 스냅숏 무효화 훅은
`MissionRegistrationService`의 `register`(승인 미션 신규 등재)와 `hide`(노출 중지) 두 곳에만 걸려
있다(`invalidateSnapshotAfterCommit`, MSG-500 D-12. 재개 API는 없다). 업로드마다 전국 활성 미션
스냅숏을 통째로 날리는 것은 훨씬 큰 변경이고, 업로드 경로에 미션 캐시 의존을 새로 만든다.

**선례와의 차이는 인정하고 간다.** `getMissionsByGrid`(`:331`, MSG-459)가 같은 배치 집계를 캐시 없이
부르고 근거를 주석에 남겼지만("방금 시작하거나 방금 끝난 미션이 누락되면 안 되기 때문"), 그쪽은
격자 하나의 대표 미션 역조회라 대상이 보통 한두 건이다. 목록은 뷰포트 한 종류 실측 최대 169건이고
지도를 움직일 때마다 불리는 고빈도 경로다. 그래서 근거를 그대로 베끼지 않고 위 세 가지로 따로
세웠고, 비용은 D4의 측정 항목으로 넘긴다.

#### 소비자 분리: AI 경로 추천을 집계에 태우지 않는다

`getMissionsInViewport`의 소비자는 컨트롤러 하나가 아니다. `RouteCandidateCollector`(`:117`)가 미션
종류 셋(EVENT, POPUP, COURSE)을 루프로 돌며 같은 메서드를 부른다. 이 메서드 안에서 집계하면 경로
추천 요청 하나에 집계 쿼리가 최대 3회 붙는데, **경로 추천은 이 DTO에서 `videoCount`를 읽지 않고
응답에 싣지도 않는다.**

`docs/prd/MSG-457-prd.md:74`가 이 구간에 성능 기준을 걸어 두었다. "후보 검색과 순서 배열은 서버
안에서 끝나며 외부 왕복을 추가하지 않는다. 이 구간은 기존 미션 조회 수준(뷰포트 목록 웜 p95
4.0ms 실측, MSG-398)을 유지한다." 쓰지도 않을 값을 위해 그 구간에 DB 왕복 셋을 얹는 것은 이 기준과
정면으로 부딪힌다.

**그래서 소비자를 가른다.** `MissionQueryService`에 목록 카드용 메서드를 하나 더 두고
(`getMissionCardsInViewport(bounds, type)` 정도, 이름은 구현 단계에서 다듬어도 된다) 그 안에서
기존 `getMissionsInViewport` 결과에 배치 집계를 얹는다. 컨트롤러는 새 메서드를, 경로 추천은 기존
메서드를 부른다. 추가되는 코드는 서너 줄이고 route 도메인은 한 글자도 고치지 않는다.

기각한 대안 둘. 공유 메서드에 그대로 얹는 안은 위 성능 기준을 깬다. 기존 메서드에 boolean 플래그를
더하는 안은 호출부에서 `true`, `false`가 무슨 뜻인지 읽히지 않아 메서드를 나누는 것보다 나쁘다.

**부작용 하나를 계약으로 적는다.** 경로 추천이 받는 DTO는 스냅숏 원본이라 `videoCount`가 0으로
남는다. 그 값이 경로 추천 응답에 실리지 않으므로 밖으로 새지 않지만, 앞으로 route 쪽에서 이 필드를
읽으면 조용히 0을 읽게 된다. D5의 스냅숏 주석과 같은 자리에 이 사실을 남긴다.

#### 사용자 무관 계약은 깨지지 않는다

`countVideosByMissionIds`에는 사용자 파라미터가 없고 차단 절도 없다. 나가는 값이 전역 공개 영상의
수라 누가 물어도 같으므로, 컨트롤러가 principal을 받지 않는 지금 모양(SRS FR-MISSION-02의 코드
수준 방어)을 그대로 유지한다. 전역 캐시 전제도 그대로다. 목록 응답에 개인화 값이 들어가는 것이
아니라, 캐시된 전역 스냅숏 위에 또 다른 전역 값을 얹는 것이기 때문이다. 이 성질의 대가가 차단
비대칭이고 D6에서 다룬다.

**올라갈 사다리(지금 만들지 않음).** D4 측정이 예산을 넘으면 다음 후보는 videoCount 맵만 짧은
TTL로 따로 캐시하는 안이다. 뷰포트와 무관하게 활성 미션 전체를 한 벌로 들고 있으면 되고 사용자와
무관하니 캐시 분열도 없다. 측정 전에는 만들지 않는다.

### D2. 쿼리 재사용: 새 쿼리를 만들지 않는다

**결론: `VideoRepository.countVideosByMissionIds`(MSG-459)를 그대로 재사용한다.**

미션 영상 수를 세는 술어는 네 곳이 한 벌로 관리된다. `findMissionVideos`와
`findMissionVideosAfter`(MSG-390, 목록), `countMissionVideosByGrid`(MSG-399, 상세의 격자별 개수),
`countVideosByMissionIds`(MSG-459, 미션별 배치 개수)다. 이 넷은 술어 동등[^predicate] 계약이고,
행사 영상 안티 조인도 그 계약의 일부다. 새 쿼리를 하나 더 만들면 목록과 상세와 역조회의 숫자가
갈릴 수 있는 다섯 번째 자리가 생긴다. 이번 티켓의 목적이 바로 그 갈림을 없애는 것이라
자기모순이다. (차단 절 하나에서 이미 count 축과 list 축이 갈려 있다는 점은 D6에 적었다. 그것이
이 재사용 결정을 바꾸지는 않는다. 오히려 새 쿼리를 만들면 갈림이 하나 더 는다.)

`countVideosByMissionIds`는 `GROUP BY m.id`라 미션 id 목록을 그대로 받는다. 이번 경로가 필요한
모양과 정확히 같아 수정 없이 쓴다.

구현상 지킬 것 둘.

- **빈 목록 가드.** 뷰포트 필터 결과가 비면 집계를 부르지 않고 빈 배열을 반환한다. `IN (:missionIds)`에
  빈 컬렉션을 넘기면 SQL이 깨지고, `getMissionsByGrid`도 같은 이유로 `isEmpty()` 가드를 두고 있다.
- **새 id 상한을 두지 않는다.** `MAX_PROGRESS_IDS`(300)는 클라이언트가 보내는 id 목록이라 방어가
  필요했던 값이다. 여기 id는 서버가 자기 뷰포트 필터로 만든 것이고 활성 미션 수(현재 404건)가
  자연 상한이라 새 상한은 방어할 대상이 없다.

**이 결정을 지키는 수단은 실행 테스트가 아니라 구현 diff 확인이다.** 새 쿼리를 만들어도 그 쿼리로
짠 테스트가 함께 통과하기 때문이다. 검증 항목은 아래 테스트 절 마지막 소절에 두었다(AC-597-06).

### D3. 필드 계약: `long` 0 채움

**결론: 필드명 `videoCount`, 타입 `long`, `requiredProperties`에 포함, nullable 아님, 영상이 없는
미션은 `0`.**

`GridMissionResponseDto.videoCount`(MSG-459)와 `MissionDetailResponseDto.videoCount`(MSG-399)가 이미
`long` 0 채움이라 그대로 맞춘다. 세 응답의 같은 이름 필드가 타입까지 같아야 FE가 한 가지로 다룬다.

null을 쓰지 않는 이유는 둘이다. 화면이 `c > 0`으로 렌더를 가르고 있어 0이 곧 "표시하지 않음"이고,
이 레포에서 required는 "값이 non-null"이 아니라 "키가 존재한다"는 뜻이라(`MissionResponseDto`
클래스 주석, MSG-319) 0 채움과 required가 자연스럽게 맞물린다.

**기계가 지켜 주는 범위를 오해하지 않는다.** `ResponseSchemaNullabilityTest`는 응답 DTO의 모든
필드가 `requiredProperties`에 있는지만 본다. 그 클래스 주석이 "nullable은 이 테스트가 강제하지
않는다"고 명시한다. 어떤 필드가 null을 낼 수 있는지는 사람만 판단할 수 있기 때문이다. 따라서
`requiredProperties`에 `videoCount`를 넣는 것만 자동으로 걸리고, `long` 0 채움이라는 결정은 아래
테스트 시나리오의 0 채움 케이스가 지킨다.

### D4. 성능: 우려는 적되 단정하지 않는다

**확정된 사실.**

- 뷰포트 한 변 상한은 0.5도다 (MSG-398 D6, 초과는 12401 거절).
- 엔드포인트는 `type`이 필수라 한 요청이 한 종류만 받는다. **그 한 종류의 실측 최대는 POPUP
  169건이다** (PRD 4절, 0.5도 강남역 중심). PRD 8절의 192건은 같은 뷰포트의 **전 종류 합계**라 이
  엔드포인트 한 번에 실리는 수가 아니다. 아래에서 192를 쓸 때는 실제 상한이 아니라 보수적 합성
  부하로만 쓴다.
- 활성 미션 전체는 404건이다 (2026-08-14 재측정).
- 추가되는 DB 왕복은 요청당 1회 고정이다. 미션 수가 늘어도 왕복 수는 늘지 않는다.
- 경로 추천 경로에는 왕복이 늘지 않는다 (D1 소비자 분리).

**MSG-437 맥락과의 관계.** 지금 목록과 집계는 요청 경로에서 DB를 타지 않는다. 스냅숏 위 메모리
산술만 하기 때문이다. 기준선 수치는 둘이 있다. MSG-398 실측이 뷰포트 목록 웜 p95 4.0ms이고
(`docs/prd/MSG-457-prd.md:74`가 인용), MSG-437 작업 당시 dev 실측은 콜드 첫 요청 1.51초 대 웜
12ms였다(콜드 비용은 역지오코딩이라 부트 웜업으로 옮겼다). 이번 변경이 그 설계와 충돌하지는
않는다. 스냅숏 재계산 비용도 웜업의 목적도 그대로다. 다만 "웜 상태에서는 DB를 안 탄다"는 성질은
지도 목록 경로에서 사라지고, 웜 응답 위에 집계 왕복 하나가 얹힌다.

**추정은 추정이라고 적는다.** 축제 미션의 판정 격자가 9x9(81칸)이므로 169건이면 격자 프로브가
대략 1만 회 수준이 될 것으로 보이지만, 이것은 계산이지 측정이 아니다. 대부분의 프로브가
`idx_videos_grid_popular`에서 0행을 돌려받고 끝날 것이라는 예상도 마찬가지다. 실측 없이 느리다고도
빠르다고도 단정하지 않는다.

**구현 단계 측정 항목.**

1. dev에서 실제 169건 id 목록으로 `countVideosByMissionIds`를 `EXPLAIN (ANALYZE, BUFFERS)` 1회
   실행하고, 실행 시간과 인덱스 사용을 기록한다. 보수적 상한을 함께 보고 싶으면 192건으로 한 번
   더 돌리되 그 값이 합성 부하임을 적는다.
2. `GET /api/missions/active`를 강남역 0.5도 POPUP으로 워밍 후 p50과 p95를 재고, 변경 전 기준선
   (MSG-398 웜 p95 4.0ms)과 나란히 적는다.
3. 경로 추천은 측정 대상이 아니다. 대신 집계가 그 경로에 붙지 않았음을 테스트로 고정한다
   (AC-597-11). 측정보다 회귀 고정이 이 경로에 맞는 도구다.

**판정선.** PRD 4절의 300ms(칩 전환과 지도 이동에서 목록 갱신) 안에 들어야 한다. 그 안이라도 p95가
눈에 띄게 올라가면(기준선 대비 100ms 초과 제안) D1의 사다리로 올린다. 두 수치를 스펙 작업 로그에
남긴다.

### D5. 상세 응답의 중복 필드 처리

상세 응답은 `MissionResponseDto`를 통째로 중첩하므로(`MissionDetailResponseDto.mission`) 필드를
더하는 순간 영상 수가 두 자리에 생긴다. `detail.videoCount`와 `detail.mission.videoCount`다.

**결론: 두 자리에 같은 값을 채운다. 값은 상세가 이미 계산해 둔 합계를 재사용하고 쿼리를 더하지
않는다.** `getMissionDetail`은 `countMissionVideosByGrid` 결과의 합으로 `videoCount`를 이미 만들고
있으므로(`:319`), 그 변수를 중첩 DTO에도 넣으면 두 값이 같은 계산에서 나와 구조적으로 어긋날 수
없다.

기각한 대안. 중첩 쪽을 0으로 두는 안은 그 자리에 거짓 값을 남긴다. null로 두는 안은 타입을 `Long`으로
낮춰 목록 계약(D3)까지 흔든다. 중복 자체를 없애려고 `detail.videoCount`를 빼는 안은 기존 응답
계약을 깨는 변경이라 이번 범위 밖이다.

**구현 형태와 함정 하나.** `MissionResponseDto.of(mission, shape)`는 그대로 두고(videoCount는 0으로
생성) `withVideoCount(long)` 복사 메서드를 더해 목록 카드 경로와 상세 양쪽에서 채운다. 그러면 캐시
스냅숏 안의 DTO는 `videoCount = 0`이 박힌 상태로 남고, 경로 추천은 그 원본을 그대로 받는다
(D1 소비자 분리). 지금 설계에서 그 0이 응답으로 나가는 경로는 없다. **이 사실을 스냅숏 필드
주석에 남긴다.** 나중에 누군가 목록 카드 경로에서 `cached.dto()`를 그대로 반환하거나 route 쪽에서
이 필드를 읽으면 전 카드가 조용히 0이 되는 회귀가 나기 때문이다.

**지금 이 결정을 고정하는 테스트가 없다.** 현재 상세 테스트는 최상위 값만 본다
(`MissionDetailServiceTest:172`, `MissionControllerTest:285`). 중첩 쪽이 스냅숏 기본값 0으로 남아도
전부 통과하므로 위 함정이 그대로 테스트를 지나간다. 그래서 두 값의 동등을 직접 단언하는 시나리오를
테스트 절에 명시 항목으로 넣었다(AC-597-12).

### D6. 차단 축의 비대칭: 이 티켓에서 닫지 않고 계약으로 적는다

> **2026-09-13 정민 확정**: 이 비대칭을 영구 계약으로 수용한다. 후속 티켓을 내지 않는다.

**사실.** `findMissionVideos`와 `findMissionVideosAfter`에는 차단 절이 있다 (MSG-569 D-4).

```sql
AND (CAST(:viewerId AS bigint) IS NULL OR NOT EXISTS (
  SELECT 1 FROM user_blocks b
  WHERE (b.blocker_id = :viewerId AND b.blocked_id = v.user_id)
     OR (b.blocker_id = v.user_id AND b.blocked_id = :viewerId)))
```

`countVideosByMissionIds`와 `countMissionVideosByGrid`에는 없다. 그래서 누군가를 차단한 사용자에게는
카드와 상세의 영상 수가 실제로 열리는 목록보다 크게 나온다. 이 티켓이 고치려는 결함(목록 숫자와
실제 목록의 불일치)과 모양이 같은 상태가 차단 사용자에게 남는다.

**결론: 이 티켓에서 해결하지 않고, 의도된 것으로 수용해 계약에 적는다.**

**막는 것은 구조가 아니라 제품 계약이다.** 기술적으로는 가능하다. D1이 택한 구조가 이미 "전역
스냅숏은 그대로 두고 요청 시점 값을 뒤에 합성"이므로, `viewerId`를 받는 집계도 같은 자리에서 캐시
밖 후처리로 얹을 수 있다. 캐시를 사용자별로 뜰 필요가 없고, 비로그인도 `findMissionVideos`가 이미
하는 것처럼 `viewerId IS NULL` 단락으로 양립한다. 그러니 "구조상 불가능"은 사실이 아니다.

실제 제약은 SRS FR-MISSION-02다. 목록 응답은 모든 사용자에게 같아야 하고, 컨트롤러가 principal을
받지 않는 것이 그 계약의 코드 수준 방어다(MSG-398 D10). 차단을 반영하려면 목록 조회가 요청자를
알아야 하므로 그 방어를 걷어내고 응답을 사용자별 값으로 만들어야 한다. 비로그인 열람(MSG-454)도
같은 전제 위에 서 있다. 두 요구를 견주면 목록의 전역성이 상위 요구라고 판단했고, 카드 숫자의
차단 정확도를 위해 그것을 뒤집을 만하지 않다고 보았다.

MSG-569가 이 비대칭을 이미 명시적으로 허용했다는 점도 근거다(`findGlobalVideos` 주석의 같은
허용과 나란히 적혀 있다). 이 티켓은 그 허용 범위를 넓히지 않고, 이미 그렇게 도는 count 축에 목록
카드를 하나 더 잇는다.

**남기는 계약.** 차단 관계가 있는 요청자에게 카드의 영상 수는 그가 실제로 보는 목록 행 수보다 클
수 있다(작아지지는 않는다). 화면이 "영상 3"을 보고 들어가 2건만 보는 상황이 성립한다.

**후속 티켓 후보로 올린다.** 아래 미해결 질문 참조. 값어치를 따져 볼 선택지는 상세 화면에서만
차단 반영 개수를 따로 세는 안(상세는 사용자별 조회라 전역성 계약이 걸리지 않는다) 정도이고,
목록 카드는 어느 안으로도 전역 값으로 남는다.

- **영상 수 표시 규칙(0일 때 감추기).** 화면 몫이고 이미 구현돼 있다. 서버는 0을 그대로 내려준다.

    사용자에게 같은 응답이라야 성립하므로, 응답에 사용자별 값이 하나라도 끼면 캐시를 사람 수만큼
    떠야 한다.

[^predicate]: 술어 동등: 여러 쿼리가 대상 행을 고르는 조건을 같은 집합으로 유지한다는 계약이다.
    문자열까지 똑같을 필요는 없고 조건 집합이 같으면 된다. 이 계약이 깨지면 같은 대상을 두고 화면
    사이 숫자가 갈린다.

[^antijoin]: 안티 조인: 다른 테이블에 짝이 있는 행을 빼는 조인이다. 여기서는 `event_videos`에 행이
    붙은 영상, 즉 행사 영상을 미션 집계에서 제외하는 데 쓴다. 행사 영상은 현장에 없어도 올릴 수
    있어 미션 방문의 증거가 아니기 때문이다.

[^batch]: 배치 집계: 대상 id를 한 번에 넘겨 그룹별 개수를 한 쿼리로 받아 오는 방식이다. 항목마다
    세면 항목 수만큼 쿼리가 나가는 N+1이 되므로, 미션이 몇 건이든 왕복이 1회로 고정된다.

[^viewport]: 뷰포트: 지도에서 지금 화면에 보이는 경위도 범위다. 전국을 다 내려보내는 대신 이
    범위로 잘라 응답 크기를 줄이며, 한 변 상한은 0.5도다.
