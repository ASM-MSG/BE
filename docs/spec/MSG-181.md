# MSG-181: 알림 트리거 연동 — 뱃지 발급 · 핫구역 진입 · 스트릭 리마인드

**Owner**: B

> PRD(정본): `docs/prd/MSG-178-prd.md` (상태: 검토됨) — 알림 묶음 4티켓 공유 PRD. 이 스펙은
> **FR-9(뱃지 발급 알림) · FR-10(핫구역 신규 진입 알림) · FR-11(스트릭 리마인드 배치)** 만 다룬다.
> 지라 티켓 제목("친구 활동·핫구역·리텐션")의 **친구 활동은 PRD §8(2026-08-03 성민 확정)이 명시
> 제외** — friend 도메인 후속 티켓. PRD가 정본이므로 이 스펙에 친구 트리거는 없다.
> 선행 완료: MSG-179(발송 파이프라인)·MSG-180(설정 API) 머지됨. **181의 몫은 트리거 지점 배선뿐**
> — 설정 필터·전송률 제한·멱등·재시도·발송은 컨슈머가 전부 처리한다(docs/spec/MSG-179.md 도메인 로직).

## 개요

구현된 이벤트 소스 3종을 MSG-179 outbox 진입점 `NotificationCommandService.record(userId,
category, eventKey, title, body)`에 배선한다. 181이 만드는 것: **record 호출부 3종 + 핫구역 진입
검출 스케줄러 + 리마인드 배치 + 알림 문구**. title/body는 기록 시점 확정 저장(179 D3) — 문구
조립은 전부 이 티켓 몫이다.

Owner 판정: 배선 대상이 badge·streak·usergrid·notification — 전부 B. hotzone 접점은 **기존 계약
`HotZoneService.getHotZones(ViewportBounds)` 소비뿐(시그니처 무변경, D4)** 이라 **B 단독**.
Owner A 코드 변경 0.

## 배경 · 목표

- 파이프라인(179)과 설정(180)은 완성됐지만 outbox에 기록하는 쪽이 아직 없다 — 리텐션 루프
  (뱃지·핫구역·스트릭)가 여전히 앱 밖 사용자를 부르지 못한다.
- 목표: 3종 이벤트가 커밋되는 순간 알림 기록이 원자적으로 남고(FR-3 규약 준수), 이후는 기존
  파이프라인이 알아서 발송한다.

## 성공 기준

1. **뱃지** (FR-9): 뱃지 발급이 커밋되면 같은 커밋에 BADGE 알림 기록이 존재한다(뱃지당 1건,
   발급 트랜잭션 롤백 시 함께 소멸). 이미 보유한 뱃지 재판정은 기록 0건.
2. **핫구역** (FR-10): 격자가 핫구역에 신규 진입하면 검출 주기(10분) 안에 그 격자를 점령한
   사용자 전원에게 HOTZONE 기록이 생성된다. 핫구역 **유지 중** 재통지 없음(진입 전이만),
   같은 날(KST) 재진입은 중복 기록 없음.
3. **리마인드** (FR-11): 매일 20시(KST) 이후 "어제(KST) 기록 있음 + 오늘 미업로드" 사용자
   전원에게 REMIND 기록이 생성되고, 부분 실패는 자정 전(21·22·23시 재발화)에 회복된다.
   같은 날 재실행은 중복 기록 없음(멱등).
4. **문구**: title/body가 기록 시점에 확정 저장되고, glossary UI 규칙을 지킨다
   ("점령" 미사용 — "수집"·"핫구역"·"스트릭"만).
5. **게이트 경계**: `fillmap.notification.enabled=false`(로컬·CI)에서 검출·리마인드 스케줄러 빈이
   없고, record 배선(뱃지)은 상시 활성이어도 무해하다(DB insert뿐 — 179 D6).

## 결정

### D1. 뱃지 트리거 — `BadgeAwardServiceImpl.award()` 단일 지점 배선

**실측 (발급 경로 전수)**: 발급 INSERT(`userBadgeRepository.insertIgnoreConflict`)는
`BadgeAwardServiceImpl.award(userId, type, metric)` 안 **한 곳뿐**이다. 호출 경로 전부가 이
메서드로 수렴한다:

| 축 | 경로 | 트랜잭션 |
|---|---|---|
| UPLOAD_COUNT | `VideoServiceImpl.saveVideo` → `awardUploadBadges` → award | 업로드 확정 |
| TOTAL_GRIDS · REGION_PERCENT | 〃 → `awardCollectionBadges` → award ×2 | 업로드 확정 |
| STREAK_DAYS | 〃 → `StreakCommandServiceImpl.recordUpload` → award | 업로드 확정 |
| MISSION_COUNT | 〃 → `MissionAwardServiceImpl.awardOnUpload` → award | 업로드 확정 |

**확정**: record 배선은 award() 내부, `insertIgnoreConflict == 1`(실제 발급 성공) 직후 1줄.
호출자별 배선(4곳+미래 축마다 추가)이 아니라 단일 지점 — 새 축이 생겨도 배선이 자동 커버된다.
award()는 `@Transactional`(REQUIRED)이라 record가 발급과 **같은 커밋**(179 D6 규약, FR-3).
경합 패자(ON CONFLICT 0행)는 record도 안 탄다 — "이 요청으로 획득한" 뱃지만 알림.

- **한 요청 다중 발급 = 뱃지당 1건씩.** 근거: FR-12가 BADGE를 무제한으로 확정(사용자 액득
  직결·희소), event_key가 뱃지 단위, FE 획득 연출도 뱃지별. 다중 발급 자체가 드문 경로다
  (동시 티어 통과).
- `BadgeAwardServiceImpl`에 `NotificationCommandService` 의존 추가 — B 내부 service 접점,
  notification은 badge를 참조하지 않아 순환 없음.

### D2. 뱃지 event_key·문구 — `BADGE:{badgeId}`

- **event_key `BADGE:{badgeId}` 확정** (179 D3 관례 제안 채택). 날짜 불요 — 뱃지는 사용자당
  생애 1회(user_badges PK (user_id, badge_id))라 UNIQUE(user_id, event_key)와 성질이 정확히
  일치한다. 재지급이 불가능하므로 dedupe가 곧 정합성 방어.
- **문구 재료 실측**: `EligibleBadgeProjection`(→ `EarnedBadgeResponseDto`)에 `name`(표시명,
  예 "첫 발자국")·`description`이 있다 — award() 루프의 candidate에서 바로 꺼낸다.
- 문구: title `새 뱃지 획득` · body `'{name}' 뱃지를 획득했어요` (description은 body 255 제한과
  중복 정보라 미사용).

### D3. 핫구역 진입 검출 = 주기 스케줄러 스냅숏 비교 (대안 기각 근거 포함)

**실측**: 핫스코어는 Redis 6h 버킷(`hotzone:{bucketId}`) 합산의 **조회 시점 계산**(MSG-183/184)
— "진입 순간" 이벤트가 없다. 핫구역 판정 = 상위 K(50) ∩ 최소 임계(3), `hotzone:top` 캐시
TTL 30s.

**① 업로드 이벤트 시점 판정 — 기각** (실측 근거 3):
- 핫스코어 증분은 `afterCommit` + 비동기 단일 데몬 스레드(`HotScoreCommandServiceImpl`) —
  업로드 트랜잭션 시점엔 **이번 신호가 아직 Redis에 없어** 판정이 항상 1건 뒤처진다.
- 진입은 업로드 없이도 발생한다 — 타 격자의 버킷 만료로 상위 K에 밀려들어오는 경우는 업로드
  훅으로 영원히 미검출.
- 업로드 hot path에 Redis 왕복 추가.

**② 주기 스케줄러 스냅숏 비교 — 확정**: `HotZoneEntryDetector`(notification/relay — 179가
스케줄 잡 홈으로 확립한 패키지, StaleTokenCleaner 선례)가 10분 주기로:

1. 현재 핫구역 집합 조회 (D4)
2. 직전 스냅숏(D5)과 비교 → **진입분**(현재 − 직전) 산출
3. 진입 격자마다 점령 사용자 역조회(D6) → 사용자별 `record(HOTZONE, ...)` — 비즈니스 상태
   변경이 없는 트리거라 record 자체 트랜잭션으로 충분(179 D6 "없으면 자체 트랜잭션" — FR-3의
   원자성 짝인 비즈니스 커밋이 애초에 없다)
4. 스냅숏을 현재 집합으로 덮어쓰기 — **record 이후에** 갱신한다. 3~4 사이 크래시는 다음
   사이클 재검출 → event_key dedupe가 흡수(at-least-once). 역순이면 유실.

- **주기 10분 상수**(`fixedDelay = 600_000`). 근거: 연성 실시간(수 분 허용, PRD 비기능) +
  사용자당 HOTZONE 1건/일 제한(FR-12)이라 더 촘촘해도 발송이 안 늘고, `hotzone:top` TTL 30s라
  매 사이클 신선한 집계를 읽는다. 릴레이와 달리 테스트가 `detect()` 직접 호출이라 프로퍼티
  불요(179 상수 선례 — AiConfig 타임아웃).
- 사이클 전체 try-catch + warn — 폴러는 죽지 않는다(AiBlurPoller·릴레이 선례).
- 본인 업로드로 진입해도 본인에게 통지된다 — 신호 기여자 추적이 없고(핫스코어 근사 철학)
  "내 격자가 인기"는 본인에게도 유효한 정보라 수용.

### D4. 전국 핫구역 조회 — 기존 계약 `getHotZones` + 한국 전역 bbox (신설 계약 없음)

**실측**: `HotZoneService`의 유일 메서드 `getHotZones(ViewportBounds)` — 뷰포트 필터형이고
"전국 목록" 메서드는 없다. 신설 계약(예: `getHotGridIds()`)을 검토했으나 **기각**:

- MVP는 한국 대상(glossary 격자 계산 규칙 절) — **한국 전역 bbox 상수**(sw 33.0/124.0, ne
  39.5/132.0 — 마라도~독도 커버)를 넘기면 뷰포트 필터가 사실상 no-op이 되어 전국 상위 K가
  그대로 나온다. 메서드 의미("viewport 안 핫구역")대로의 정당한 사용이다.
- 계약 무변경 → Owner A 구현·공동 리뷰 불요, 181이 B 단독으로 닫힌다.
- `HotZoneView`에 gridId가 있어 추가 정보 불요. 검출기의 호출이 `hotzone:top` 캐시(30s)를
  공유하므로 부하 추가도 없다.

### D5. 스냅숏 저장 — Redis SET `notification:hotzone:last`

"신규 진입" = 전이 검출이므로 직전 상태 기억이 필요하다. 대안 비교:

- **인메모리 필드 — 기각**: 재기동(배포)마다 스냅숏이 비어 지속-핫 격자가 "진입"으로 오판 →
  날이 바뀌었으면 재통지된다. 배포가 잦아 실사용 결함.
- **notifications 테이블 역산 — 기각**: "어제 event_key 존재 = 어제도 핫"은 어제 **기록이
  생성됐을 때만** 참이다. 지속-핫 격자는 둘째 날부터 기록이 없어(중복 방지) 셋째 날 "진입"으로
  오판 — 일 단위 마커를 계속 써야 해 배보다 배꼽.
- **Redis SET — 확정**: 재기동에도 유지되고, notification 도메인 자기 네임스페이스 키라 경계
  침범 없음(hotzone의 `hotzone:*` 키는 A 내부 — 직접 읽지 않는다). Redis 유실 시 1회 스냅숏
  공백 → 지속-핫 격자 재통지 가능성이 있으나 같은 날은 dedupe, 아니어도 1건/일 상한이 캡 —
  핫스코어 자체가 근사값·유실 허용(glossary)이라 정합 수준이 일치한다.

갱신은 DEL 후 SADD(현재 집합 空이면 DEL만). 둘 사이 크래시는 빈 스냅숏 → 다음 사이클 전량
재검출 → dedupe 흡수라 원자화(Lua) 불요. TTL 없음.

최초 가동(스냅숏 자체가 없음) 1회는 현재 핫구역 전부가 "진입"으로 기록된다 — 기능 첫 배포의
1회성 웨이브로 수용(1건/일 상한이 캡).

### D6. 점령 사용자 역조회 — `UserGridQueryService` 메서드 추가 + V24 인덱스

**실측**: user_grids PK는 `(user_id, grid_id)` — 선두가 user_id라 `WHERE grid_id = ?` 역조회를
못 받친다. grid_id 단독 인덱스 없음(V1~V23 전수), FK는 인덱스 자동 생성 안 됨(V1
idx_push_tokens_user 선례 문언). 기존 쿼리는 전부 user_id 축이라 이번이 **최초의 grid 축 접근
경로**다. 규모: 핫구역 격자 = 48h 내 업로드 3건 이상인 격자 — 점령 사용자 수십 수준(MVP),
진입 이벤트당 1회 실행.

- **V24__user_grids_grid_index.sql** 신설(D12) — 검출 주기마다 도는 설계된 접근 경로라
  seq scan 방치 대신 명시 인덱스(idx_notifications_user와 같은 논리).
- 조회는 3-Layer 원칙(타 도메인 접점은 Service까지 — BadgeAwardService javadoc 실측)대로
  `UserGridQueryService`에 메서드 추가, `UserGridRepository`에 native 쿼리(이 리포지토리가
  grids·regions를 native로 조인하는 선례 다수 — MSG-167 §D4):

```java
/**
 * 격자를 점령한 사용자 전원 + 격자 행정동 이름 (MSG-181 핫구역 진입 통지용, B-내부 read —
 * notification 만 소비, Owner A 미소비라 non-breaking). 행정동 없는 격자(해상 등)는 regionName null.
 */
List<GridOccupantView> getGridOccupants(String gridId);
```

```sql
SELECT ug.user_id AS "userId", r.region_name AS "regionName"
FROM user_grids ug
LEFT JOIN grids g ON g.grid_id = ug.grid_id
LEFT JOIN regions r ON r.region_code = g.region_code
WHERE ug.grid_id = :gridId
```

`GridOccupantView(long userId, String regionName)` — usergrid/service의 View record 선례
(CollectionGridView 등). region_name이 행마다 중복되지만 1왕복이 우선.

### D7. 핫구역 event_key·문구 — `HOTZONE:{KST일자}:{gridId}`

- **event_key `HOTZONE:{KST일자}:{gridId}` 확정** (179 관례 채택, 일자는 ISO `yyyy-MM-dd`).
  같은 날 이탈→재진입은 같은 키 → ON CONFLICT 흡수(당일 1회), 다른 날 재진입은 새 키 → 정당한
  새 이벤트. VARCHAR(100)에 여유(~32자).
- **문구의 위치명 = 행정동 이름**(D6 쿼리의 region_name). "{zone명} A-14" 표시명은 FE-local
  산술이 정본(glossary 표시명 — 서버는 문자열을 만들지 않는다)이라 서버 문구에 못 쓰고,
  행정동 이름 폴백은 서버 저장 데이터(regions.region_name)라 정당하다.
- 문구: title `내 격자가 핫구역에 들어왔어요` · body `{region_name}에서 수집한 격자가 지금
  인기예요. 지도에서 확인해 보세요` / region_name 없으면(해상 등) `내가 수집한 격자가 지금
  인기예요. 지도에서 확인해 보세요`.
- 여러 격자가 같은 날 동시 진입하면 기록은 격자별로 남고 발송은 컨슈머의 HOTZONE 1건/일
  상한이 캡(FR-12 — 나머지 SKIPPED RATE_LIMITED). 의도된 피로 방지라 트리거에서 중복 억제를
  또 하지 않는다.

### D8. 스트릭 리마인드 대상 판정 — `last_recorded_date = KST 어제` 한 조건

**실측**: streaks는 1 user = 1 row(user_id PK · current_count · max_count ·
last_recorded_date(KST date) · updated_at), 갱신은 `upsertOnUpload` 3분기 CASE(같은 날 no-op /
어제 +1 / 그 외 1 리셋). row가 있으면 current_count ≥ 1이 불변식(첫 기록이 1).

"당일 미업로드 + 스트릭 진행 중" = **`last_recorded_date = (KST 오늘 − 1)`** 하나로 끝난다:

- `= 오늘` → 이미 업로드함(리마인드 불요)
- `= 어제` → 오늘 올리면 +1, 안 올리면 끊김 — **정확히 리마인드 대상**
- `< 어제` → 이미 끊김(오늘 올려도 1 리셋) — 지킬 스트릭이 없어 제외. "다시 시작하세요" 류
  재획득 넛지는 별개 기획이라 비목표.

`StreakRepository` 신규 파생 native(어제 날짜는 앱이 KST 계산해 바인딩 — MSG-222 세션 TZ 스큐
재발 방지, 179 D8과 동일 규칙):

```sql
SELECT user_id AS "userId", current_count AS "currentCount"
FROM streaks WHERE last_recorded_date = :yesterday
```

인덱스 없이 풀스캔 — 사용자당 1행 테이블의 일 1회 스캔이라 수용.

### D9. 리마인드 배치 — `StreakRemindScheduler`(streak/service), 20시 첫 시도 + 자정 전 시간별 재시도

- **위치 streak/service**: 대상 판정("지킬 스트릭이 있는 마지막 날")은 스트릭 도메인 지식 —
  자기 리포지토리 + `NotificationCommandService`(계약) 소비로 신규 인터페이스 0. 스케줄러가
  service 디렉터리에 사는 선례: video/service/AiBlurPoller.
- **`@Scheduled(cron = "0 0 20-23 * * *", zone = "Asia/Seoul")`** — 20·21·22·23시 4회 발화
  (Codex 1R P2 반영 — 초안의 20시 단발은 부분·전역 실패 시 당일 재실행 주체가 없어 시간 민감
  알림이 영구 유실, PRD "발송 보장 우선" 위배). **시간별 재발화가 곧 당일 재시도 메커니즘**:
  이미 기록된 대상은 REMIND:{일자} ON CONFLICT 0행 흡수 + 컨슈머 전송률 1건/일 상한이 2차
  방어라 별도 재시도 코드 없이 멱등 설계가 재실행을 공짜로 만든다. 비용은 streaks 풀스캔
  3회 추가(1 user = 1 row — 무시 가능). **20시 시작 근거**: ① 끊김 경계(KST 자정)까지 4시간 —
  받고 행동할 여유 ② 저녁 여가 시간대라 푸시 확인 기대가 높음 ③ 기존 배치(04시 스테일
  토큰)와 분산. 23시가 마지막인 것도 자정 직전 발화는 행동 여유가 없어서다.
- 대상 루프를 돌며 사용자별 `record(...)` — 호출마다 자체 트랜잭션(D3과 같은 논리) +
  **per-recipient 예외 격리**(Codex 1R P2 반영 — 한 사용자의 record 실패가 나머지를 막지
  않게 루프 안 try-catch, 실패 건수만 warn). 배치 전체 단일 트랜잭션을 안 묶는 이유: 중간
  크래시 시 재실행이 event_key dedupe로 이어붙는(멱등) 쪽이 전량 롤백-재시작보다 단순·안전하다.

### D10. 리마인드 event_key·문구 — `REMIND:{KST일자}`

- **event_key `REMIND:{KST일자}` 확정** (179 관례 채택). **재실행 멱등의 구조**: 같은 날 재실행

  상한(FR-12)이 2차 방어.
- 문구: title `스트릭이 오늘 자정에 끊겨요` · body `{current_count}일 연속 기록 중이에요. 영상
  하나만 올리면 스트릭이 이어져요` (current_count는 D8 프로젝션에서).

- **예외 흐름**: 신규 REST 없음 — 실패는 로그로. 검출기는 사이클 전체 try-catch warn(폴러 생존,
  다음 10분 사이클이 스냅숏 기준 재검출). 리마인드는 per-recipient try-catch — 실패 건수만
  warn(사용자 ID 미노출, 마지막 예외 체이닝), 21~23시 재발화가 당일 재시도하고 dedupe가 기기록
  흡수. 뱃지 record 실패는 발급 트랜잭션과 함께 롤백(같은 커밋 — 의도된 원자성)

  (최초 가동은 스냅숏 부재로 현재 핫구역 전부가 진입 처리 — 1회성 웨이브, 1건/일 상한 캡).
