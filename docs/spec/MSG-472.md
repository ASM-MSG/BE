# MSG-472: 코스 라인의 원문 JSON 타입을 명세에 제대로 발행하기

**Owner**: B (`com.msg.fillmap.mission.*`가 CLAUDE.md "협업 원칙"의 Owner B 목록에 있고, 이 티켓이
고치는 파일은 그 패키지의 DTO 하나다. 회귀 테스트만 `com.msg.fillmap.global.config` 아래에 두는데,
그 자리는 명세 발행 가드들이 이미 모여 있는 테스트 전용 위치라 Owner A 코드와 겹치지 않는다.
Owner A 코드는 읽지도 고치지도 않는다)

> **PRD 면제 티켓이다.** 근거는 코스 미션 응답의 라인 필드가 GeoJSON 원문 객체를 그대로 싣는다는
> 계약이 MSG-222 §설계 D7에서 이미 정해져 있고 와이어에 나가는 바이트도 그대로라는 것이다. 이 티켓이
> 바꾸는 것은 그 계약을 API 문서가 잘못 적어 내보내던 표기 하나뿐이라, 제품 요구사항을 새로 만들지도
> 바꾸지도 않는다. CLAUDE.md "개발 파이프라인" 면제 기준의 "버그 수정(기존 요구사항의 복구)"에
> 해당한다. 게이트 판정은 호출 측이 이미 통과시켰고 이 스펙은 그 판정을 다시 하지 않는다.
>
> SRS 대응: FR-MISSION-01(코스의 렌더 형상이 "경로와 스팟"이라는 요구). 상태는 `구현됨` 그대로다.
> 요구 문장이 그대로 유효하고 구현도 그대로이며, 달라지는 것은 그 구현을 설명하는 문서 표기다.
> 아래 D4가 SRS를 손대지 않는 근거를 적었다.
>
> 선행 정본: `docs/spec/MSG-222.md` §설계 D7(라인 필드를 원문 passthrough로 내보내기로 한 결정).
> 이 스펙은 그 결정을 바꾸지 않는다.
>
> **구현과 검증이 이미 끝난 뒤에 쓰는 기록 문서다.** 아래 값은 전부 로컬에서 직접 확인한 실측이다.

## 개요

코스 미션 응답의 `PathShape.line`은 `missions.path`에 든 GeoJSON LineString[^2] 원문을 파싱 없이 그대로
싣는 자리다. 자바 타입은 `String`이지만 `@JsonRawValue`[^1] 덕에 와이어에는 따옴표 없는 JSON 객체가
나간다. 그래서 애노테이션에 `type = "object"`를 지정해 두었는데도, 같이 붙어 있던 `nullable = true`
때문에 springdoc[^4]이 타입을 자바 타입 기준으로 다시 계산해 지정값을 덮어썼다. 발행된 명세에는
`"type": ["string","null"]`이 실려 나갔다.

**소스만 읽으면 맞아 보이고 발행값만 틀린 결함이다.** 애노테이션은 옳게 적혀 있었고, 서버가 보내는
바이트도 처음부터 객체였다. 틀린 것은 그 사이에서 만들어지는 문서 한 줄뿐이었다.

실제 피해는 프런트엔드에서 났다. FE(`apps/web/src/features/map-home/model/course.ts`)의
`parseLineString`이 명세대로 생성된 타입(`line: string | null`)을 믿고 `JSON.parse(line)`을 했는데,
와이어에는 객체가 오므로 문자열로 강제 변환되며 `"[object Object]"`가 되어 예외가 났다. 그 예외를
catch가 빈 배열로 삼켜서 `coursePath`가 비었고, 화면은 포토스팟을 번호순으로 이은 직선 폴백을 탔다.
지도에는 실제 산책로 대신 스팟을 곧게 이은 선이 그려졌고 그 선이 바다를 가로질렀다.

dev 실측이 그 차이를 그대로 보여 준다. 남파랑길 3코스는 114점 14.3km짜리 트랙 대신 6점 7.4km짜리
직선으로 그려졌다. 행정동 경계와 대조했을 때 직선은 표본의 11.5%가 육지에서 100m 넘게 떨어져 있었고,
트랙에서 그렇게 떨어진 점은 3개뿐이었다. **코스 미션 148건은 전부 `missions.path`가 채워져 있었다.**
데이터가 빈 것이 아니라 명세가 틀린 것이었다.

수정은 널 허용을 타입 목록 안에 함께 적는 방식(`types = {"object", "null"}`)으로 바꾸는 한 줄이고,
발행된 문서를 실제로 받아 확인하는 회귀 가드[^6] 하나를 함께 둔다. **신규 엔드포인트도 와이어 스키마
변경도 새 에러 코드도 없고, DDL과 마이그레이션도 없다.**

## 배경과 목표

FE는 서버가 배포한 명세를 그대로 받아 타입을 기계로 생성해 쓴다(`apps/web/openapi/api-docs.json`을
`https://api.fillmap.kr/v3/api-docs`에서 내려받아 코드 생성기[^5]에 넣는다). 그래서 명세에 실린 타입은
설명문이 아니라 FE 코드가 컴파일 단계에서 믿는 값이다. 명세가 틀리면 FE는 틀린 쪽으로 정확하게
구현하고, 그 결과가 이번처럼 조용히 폴백으로 흡수되면 아무 데서도 빨간불이 뜨지 않는다.

목표는 셋이다.

1. 발행된 명세에서 `PathShape.line`의 타입이 객체이고 문자열이 아니다.
2. 그 명세로 생성한 FE 타입이 `JSON.parse`를 허용하지 않는다. 즉 같은 오해가 FE에서 타입 검사에
   걸려 되풀이되지 않는다.
3. 같은 회귀가 springdoc이나 애노테이션 라이브러리 버전을 올리다 다시 나면 서버 테스트에서 잡힌다.

## 성공 기준

완료 판정은 아래 조건이고, "테스트 시나리오"가 그 검증 수단이다.

1. `/v3/api-docs`의 `PathShape.line` 타입이 `["object","null"]`이다. 문자열이 들어 있지 않고, 널 허용은
   그대로 유지된다.
2. 그 명세로 생성한 FE 타입이 문자열이 아니다. 실측으로 `line: { [key: string]: unknown } | null`이
   나온다.
3. 발행 결과를 실제로 받아 확인하는 회귀 가드가 있고, 애노테이션을 원래대로 되돌리면 그 가드가
   실패한다. 되돌린 상태에서 통과하는 가드는 아무것도 지키지 못한다.
4. 와이어 응답이 그대로다. 서버가 보내는 바이트는 이 티켓 전후로 한 글자도 달라지지 않는다.
5. `@JsonRawValue`가 붙은 다른 필드가 남아 있지 않다. 같은 부류의 자리는 전부 닫혔다는 뜻이다.
6. `com.msg.fillmap.global.config` 패키지의 테스트가 green이다. 전체 스위트는 CI에서 확인한다
   (아래 "잔여와 후속"에 사유를 적었다).

## 비목표

- **라인 필드를 원문 passthrough로 내보내는 설계 자체의 재검토.** MSG-222 §D7 그대로다. 서버가
  GeoJSON을 파싱해 구조화된 DTO로 바꾸는 방향은 이 티켓에서 다루지 않는다.
- **다른 널 허용 필드의 표기 일괄 교체.** `nullable = true`가 문제를 일으키는 것은 지정 타입이 자바
  타입과 다를 때뿐이다. `Spot.seq`나 `RegionShape.regionCode`처럼 지정 타입이 없는 자리는 그대로 둔다.
- **FE 레포 수정.** 저장소가 다르고 이 티켓 범위 밖이다. 의존 관계는 아래에 명시했다.
- **`missions.path` 데이터 점검.** 148건 전부 채워져 있음을 이미 확인했고 데이터 결함이 아니었다.
- **SRS 요구 문장 수정.** D4에서 판정했다.

## API 명세

**와이어 계약은 변경 없다.** 엔드포인트도 요청도 응답 바이트도 그대로이고 새 에러 코드도 없다.
달라지는 것은 그 응답을 설명하는 발행 스키마 한 자리다.

| 대상 | 이전 발행값 | 이후 발행값 |
|------|------------|------------|
| `components.schemas.PathShape.properties.line.type` | `["string","null"]` | `["object","null"]` |
| 같은 명세로 생성한 FE 타입 | `line: string \| null` | `line: { [key: string]: unknown } \| null` |

영향받는 응답은 코스(COURSE) 유형 미션을 담는 경로 전부다. 미션 목록(`GET /api/missions`)과 미션
상세가 여기 해당하고, 응답 본문의 실제 내용은 아래처럼 이전에도 이후에도 같다.

```json
"shape": {
  "line": { "type": "LineString", "coordinates": [[129.04, 35.10], [129.05, 35.11]] },
  "spots": [ { "gridId": "19443_9582", "lat": 35.10, "lng": 129.04, "seq": 1 } ]
}
```

## 도메인 로직

용어는 glossary 기준이고 도메인 규칙은 하나도 바뀌지 않는다. 코스 미션의 렌더 형상이 "경로와 스팟"
이라는 FR-MISSION-01의 정의도, 그 경로가 `missions.path` 원문이라는 MSG-222의 정의도 그대로다.
아래는 표기 방식과 가드 배치에 대한 결정이다.

### D1. 널 허용을 별도 속성이 아니라 타입 목록에 적는다

**결정: `@Schema(type = "object", nullable = true)`를 `@Schema(types = {"object", "null"})`로 바꾼다.**

바꾸는 자리는 `src/main/java/com/msg/fillmap/mission/dto/MissionShape.java`의 `PathShape.line` 한 줄이다.
아래 블록에서 `description = ...`은 원문 그대로 두는 설명문이라 줄여 적었다.

```java
// 이전
@Schema(description = ..., type = "object", nullable = true)
@JsonRawValue String line,

// 이후
@Schema(description = ..., types = {"object", "null"})
@JsonRawValue String line,
```

근거는 두 속성이 명세로 옮겨지는 경로가 다르다는 데 있다. `nullable = true`는 OpenAPI 3.1[^3]에 그대로
옮길 자리가 없는 옛 표기라 springdoc이 이를 타입 배열로 번역하는데, 그 번역이 배열을 만들면서 타입을
자바 타입에서 다시 뽑는다. 그 순간 손으로 지정한 `object`가 `String`으로 덮인다. 반면 `types`는 발행할
타입 배열을 통째로 받는 속성이라 번역 단계가 없고 지정값이 그대로 나간다. 이 결함이 노리는 것은 널
허용 자체가 아니라 **널 허용을 적는 방식이 타입 지정을 지운다는 점**이므로, 널 허용을 유지한 채 표기만
옮기는 것이 최소 수정이다.

`types` 속성은 `swagger-annotations-jakarta` 2.2.47에 있고 2.2.7에는 없다. 지금 레포가 2.2.47을 쓰고
있어 의존성 추가나 버전 올림 없이 그대로 쓸 수 있다.

### D2. 회귀 가드는 발행된 명세를 실제로 받아 본다

**결정: `@SpringBootTest`와 `@AutoConfigureMockMvc`로 컨텍스트를 띄워 `/v3/api-docs`를 받고, 그
산출물에서 타입을 확인한다.**

애노테이션을 읽는 리플렉션 가드로는 이 결함을 잡을 수 없다. 기존
`ResponseSchemaNullabilityTest`(MSG-319)가 그런 가드인데, 그 테스트가 보는 것은 소스에 무엇이 적혀
있는가다. 이번 결함은 **적힌 것은 옳고 발행된 것만 틀린** 경우라 애노테이션을 아무리 정확히 읽어도
아무 위반이 없다. 잡으려면 명세가 만들어진 뒤의 값을 봐야 하고, 그러려면 실제로 발행해서 받아 보는
수밖에 없다.

가드가 견뎌야 할 표현 차이가 둘 있어 그것도 함께 처리한다. 하나는 `allOf` 가지다. sealed 인터페이스
구현체는 상속 표현 때문에 프로퍼티가 `allOf` 아래로 들어갈 수 있어, 직접 `properties`에서 못 찾으면
가지를 훑는다. 다른 하나는 타입 표현이다. OpenAPI 3.1은 널 허용을 타입 배열로 적으므로 단일 문자열과
배열을 모두 받아 비교한다.

검사 문장은 "`object`를 포함하고 `string`을 포함하지 않는다"로 적는다. `["object","null"]`과 정확히
같은지 보지 않는 이유는 널 허용 표기 방식이 바뀌어도(예를 들어 `anyOf`로 갈리더라도) 이 가드가 지키려는
성질은 "자바 타입을 주장하지 않는다" 하나이기 때문이다. 그 성질만 좁게 고정하면 무관한 표기 변화에
붉어지지 않는다.

### D3. 가드는 MSG-460의 가드와 합치지 않고 별도 파일로 둔다

**결정: `src/test/java/com/msg/fillmap/global/config/RawJsonSchemaPublicationTest.java`를 새로 만든다.
기존 `OpenApiNullableDataTest`에 넣지 않는다.**

두 파일이 비슷해 보이는 것은 사실이다. 둘 다 `/v3/api-docs`를 받아 `components.schemas`를 훑고, 선행
사고인 MSG-460도 같은 부류였다. 그때는 널 허용 참조 속성이 형제 `type`을 달고 나가 FE 생성 타입이 널로만
좁혀졌고, 그 가드가 `OpenApiNullableDataTest`에 들어갔다.

그래도 가르는 이유는 **검사 축이 다르다**는 것이다. 그쪽이 보는 것은 널 허용 표기가 제대로 나갔는가이고
(응답의 `data` 속성, 참조 속성의 `anyOf` 분기), 이쪽이 보는 것은 원문 passthrough 필드가 자바 타입을
주장하지 않는가다. 널 허용은 이쪽 검사에서 곁가지라 배열이든 아니든 상관하지 않는다. 검사 대상 목록도
서로 다르게 자란다. 이쪽은 `@JsonRawValue`가 붙는 필드가 늘 때 자라고, 그쪽은 널 허용 속성이 늘 때
자란다.

두 번째 이유는 실패했을 때 읽는 사람에게 필요한 정보가 다르다는 것이다. 이쪽 실패 메시지는 "이 필드는
원문을 그대로 싣는 자리이고 자바 타입이 `String`인 것은 구현 사정이다"라는 맥락이 있어야 조치를 할 수
있는데, 그 맥락을 널 허용 가드의 클래스 주석에 섞으면 두 이야기가 엉킨다. `OpenApiNullableDataTest`는
이미 널 허용, enum 허용값, 참조 속성 표기 세 축이 섞여 있어서, 네 번째를 더하면 파일 이름이 내용을
설명하지 못하게 된다.

**파일을 하나 더 만드는 비용은 실질적으로 없다.** 두 테스트가 `@SpringBootTest`와
`@AutoConfigureMockMvc` 조합에 추가 설정이 없어 컨텍스트 캐시 키가 같고, 스프링이 같은 컨텍스트를
재사용한다. 파일이 갈렸다고 기동이 한 번 더 일어나지 않는다.

### D4. SRS는 손대지 않는다

**결정: FR-MISSION-01의 요구 문장과 상태(`구현됨`)를 그대로 둔다. 마무리 단계에서 근거 열에 이 티켓
번호를 덧붙이는 정도면 충분하다.**

그 요구가 정의하는 것은 코스 미션이 "경로와 스팟"이라는 렌더 형상 하나를 담아 나간다는 것이고, 이
티켓 전에도 서버는 그 형상을 정확히 보내고 있었다. 요구가 지켜지지 않은 적이 없으므로 상태를 내렸다
올릴 근거가 없다. 문서 표기 결함은 요구사항의 층이 아니라 그 요구를 설명하는 산출물의 층에서 났다.

## 검증 실측

전부 로컬에서 직접 확인한 값이다.

1. **발행 스키마 왕복.** 로컬 기동 후 `/v3/api-docs`를 받아 확인했다. `"type": ["string","null"]`이
   `"type": ["object","null"]`로 바뀌었다. 명세 버전은 OpenAPI 3.1.0이고 발행기는
   springdoc-openapi-starter-webmvc-ui 3.0.3, 애노테이션은 swagger-annotations-jakarta 2.2.47이다.
2. **FE 생성 타입.** 그 명세를 코드 생성기(hey-api openapi-ts 0.99.0)에 직접 넣어 확인했다.
   `line: string | null`이 `line: { [key: string]: unknown } | null`로 바뀐다. 이제 FE에서
   `JSON.parse(line)`을 쓰면 타입 검사에서 막힌다.
3. **가드 유효성.** 애노테이션을 이전 상태로 되돌리고 새 테스트를 돌려 FAILED를 확인했다. 이 확인이
   없으면 가드가 애초에 무엇이든 통과시키는 껍데기인지 구분할 수 없다.
4. **패키지 green.** `com.msg.fillmap.global.config` 전체가 develop 기준 워크트리에서 초록이다.
   기존 명세 가드 두 종(`OpenApiNullableDataTest`, `ResponseSchemaNullabilityTest`)이 수정 없이
   통과한다.
5. **같은 부류 전수 확인.** `@JsonRawValue`는 `src/main` 전체에서 이 필드 하나뿐이고,
   `@Schema(type = "...")`로 타입을 손지정한 자리도 이 자리 하나뿐이었다(grep 전수). 같은 조합으로
   생길 수 있는 자리는 전부 닫혔다.

## 테스트 시나리오

### 모듈 1. `RawJsonSchemaPublicationTest` (신규, 발행 결과 검사)

`@SpringBootTest`와 `@AutoConfigureMockMvc`로 컨텍스트를 띄우고 `/v3/api-docs`를 받는다. 데이터에
의존하지 않아 공유 로컬 DB의 시드 상태와 무관하게 결정적이다.

- `원문_passthrough_필드는_object_로_발행된다`
  - Given: `@JsonRawValue` 필드 목록(현재 `PathShape.line` 한 건)을 상수로 선언한다.
  - When: `/v3/api-docs`를 받아 `components.schemas`에서 각 필드의 스키마를 찾는다. 직접
    `properties`에서 못 찾으면 `allOf` 가지를 훑는다.
  - Then: 선언된 타입이 `object`를 포함하고 `string`을 포함하지 않는다. 위반은 필드 이름과 실제
    타입을 함께 모아 한 번에 보고한다.
  - 명세에서 필드를 아예 못 찾는 경우도 위반으로 센다. 필드가 개명되거나 스키마 이름이 바뀌면 검사가
    조용히 0건이 되어 통과하는 상태를 막는다.

- **음성 확인**(테스트가 아니라 착수 시 절차): 애노테이션을 이전 상태로 되돌린 뒤 이 테스트를 돌려
  실패를 눈으로 본다. 위 "검증 실측" 3번이 그 기록이다.

### 모듈 2. 기존 가드 회귀 (수정 없이 초록)

## 잔여와 후속

- **FE 수정이 함께 있어야 화면이 낫는다.** `parseLineString`이 이미 파싱된 객체도 받도록 고쳐야
  한다. 서버 수정만으로는 지도에 그려지는 선이 달라지지 않는다. 웹과 모바일 양쪽에 같은 함수가 있고
  `apps/web/src/features/map-home/model/course.test.ts`와 `apps/mobile/.../course.parity.test.ts`가 두
  구현의 일치를 검증하므로 한쪽만 고치면 그 검증이 깨진다. **FE 레포는 이 티켓 범위 밖이다.**
- **이 수정이 배포돼야 FE 생성 타입이 바뀐다.** FE는 명세 스냅숏(`apps/web/openapi/api-docs.json`)을

  갱신되지 않는다.
- **전체 테스트 스위트는 로컬에서 확인하지 못했다.** 로컬 Postgres가 `max_connections=100`인데

  CI에서 한다. 위 실측 4번의 범위는 `com.msg.fillmap.global.config` 패키지까지다.
- **발견 경위 기록.** 이 결함은 MSG-470 작업 중 워킹트리에서 발견돼 무관한 관심사로 분리됐다
  (2026-08-25).

## 각주

[^1]: **@JsonRawValue**: Jackson이 그 필드의 문자열을 문자열로 감싸지 않고 JSON 조각 그대로 출력하게
    하는 표시다. 이미 JSON인 값을 파싱했다가 다시 직렬화하는 왕복을 없애려고 쓴다. 자바 타입은
    `String`인데 와이어에 나가는 것은 객체라, 타입을 자동으로 뽑는 도구들과 어긋나기 쉬운 자리다.

[^2]: **GeoJSON LineString**: 좌표 배열 하나로 선을 표현하는 GeoJSON 표준 형식이다.
    `{"type": "LineString", "coordinates": [[경도, 위도], ...]}` 모양이고, 지도 라이브러리가 그대로
    받아 그릴 수 있다. FillMap에서는 코스 미션의 실제 산책로 트랙이 이 형식으로 `missions.path`에
    들어 있다.

[^3]: **OpenAPI 3.1의 타입 배열**: 3.0까지는 널 허용을 `nullable: true`라는 별도 속성으로 적었지만,
    3.1은 JSON Schema와 정렬되면서 그 속성을 없애고 타입 목록에 `"null"`을 함께 넣는 방식으로 바꿨다.
    `"type": ["object","null"]`이 그 표기다. 옛 표기를 쓰면 도구가 새 표기로 번역해 주는데, 이번
    결함은 그 번역 과정이 손으로 지정한 타입을 덮으면서 났다.

[^4]: **springdoc**: 스프링 컨트롤러와 DTO를 훑어 OpenAPI 명세를 만들어 `/v3/api-docs`로 내보내는
    라이브러리다. 애노테이션에 적힌 것과 자바 타입에서 뽑은 것을 합쳐 스키마를 만들기 때문에, 둘이
    어긋나면 어느 쪽이 이기는지가 이번처럼 결과를 가른다.

[^5]: **코드 생성기**: OpenAPI 명세를 입력으로 클라이언트 타입과 호출 함수를 자동 생성하는 도구다.
    FE는 hey-api openapi-ts를 쓴다. 명세가 곧 FE 코드의 타입이 되므로, 명세의 오류는 설명문의 오류가
    아니라 FE 컴파일러가 믿는 값의 오류가 된다.

[^6]: **회귀 가드**: 한 번 고친 결함이 같은 모양으로 되돌아오는지 지키는 테스트다. 이 티켓의 가드는
    소스가 아니라 발행된 산출물을 검사한다는 점이 핵심이다. 라이브러리 버전을 올리다 발행 규칙이
    다시 바뀌면 소스는 그대로여도 결과가 틀어지는데, 그 경우를 잡을 수 있는 것은 결과를 보는 검사뿐이다.
