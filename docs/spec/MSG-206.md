# MSG-206: 영상 재생 조회 API (GET /api/videos/{videoId} — 재생 URL 발급)

**Owner**: B (`com.msg.fillmap.video.*`) — videos 테이블 = Owner B 도메인. grid/region 패키지 무수정.

> 에픽: 지도 탐색 / 영상 재생. **video 패키지의 마지막 미구현 read API**다. 단건 영상 상세 메타 +
> 재생 URL(presigned GET)을 발급한다. 위키 `03-specs/Video 재생 조회 API 예정.md`와 대조 완료:
> 접근 제어는 `status`·`visibility`·`processing_status` 3축이 결정하고, 재생 소스는 **presigned GET으로 확정**
> (버킷 Block Public Access 유지, MSG-127 썸네일 presign과 일관). "공개 범위 변경 API 부재"는 MSG-162로 해소됨.
> **순수 Owner B**다 — 계약 인터페이스 시그니처 변경 없음(§계약 변경) → 상대 팀 확인 불필요.

---

## 개요

영상 하나의 상세 메타데이터와 **재생용 presigned GET URL**을 발급하는 read API 1종(`GET /api/videos/{videoId}`)을
만든다. 격자 상세(MSG-127 리스트) / 전역 대표(MSG-87 커버)에서 썸네일을 보고 개별 영상으로 진입할 때,
그 영상을 실제로 재생할 수 있는 서명 URL을 이 API가 내려준다.

```
[현재] 목록·대표 조회는 있으나(thumbnail presign) 단건 재생 진입점 없음 → 영상을 재생할 수단이 없다
[MSG-206] GET /api/videos/{videoId} → 접근 제어 판정 → READY면 재생본 presigned GET 발급 → FE가 재생
```

버킷이 Block Public Access라 영구 URL이 없다. `encoded_url`·`blurred_s3_key`·`thumbnail_url` 컬럼은
**URL이 아니라 S3 key**이며(`Video.java` 필드 주석), 재생 시점에 TTL 있는 presigned GET을 발급한다 —
MSG-127 썸네일(`ThumbnailUrlPresigner`)과 정확히 같은 결이다.

---

## 배경 · 목표

- **사용자/제품 관점**: 지도에서 격자를 탭 → 썸네일 목록/대표를 본다(MSG-127/87). 여기서 영상 하나를
  골라 재생하려면 그 영상의 재생 URL과 표시용 메타(길이·촬영시각·조회수 등)가 필요하다. 이 API가
  그 "재생 진입" 계약을 채운다.
- **목표**: video 도메인 안에서 완결되는 단건 재생 조회 API를 제공한다. 소유권/공개범위/처리상태를
  하나의 판정 순서로 게이트해, **누가 무엇을 볼 수 있는지**를 정보 노출 관점에서 정확히 정한다.
  presign은 기존 `ThumbnailUrlPresigner`(GET presign)를 재사용하고, 신규 마이그레이션 없이(view_count·
  status·visibility·processing_status 컬럼 모두 V1에 존재) read 경로 + 조회수 증가 1건만 추가한다.

## 성공 기준

1. `GET /api/videos/{videoId}`가 단건 영상의 메타 + 재생 URL을 `VideoPlaybackResponseDto`로 반환한다.
2. **접근 제어 판정 순서**(§도메인 2)를 정확히 따른다: 존재/DELETED → BLINDED → visibility → processing_status.
   순서가 곧 정보 노출 정책이다.
3. **DELETED**: 소유자·타인 모두 `VIDEO_NOT_FOUND(3404)` — 존재 자체를 숨긴다.
4. **BLINDED**: 타인 `VIDEO_NOT_FOUND(3404)`(존재 미노출), 소유자 200 메타 + `playbackUrl=null` + `status=BLINDED`(§도메인 3).
5. **PRIVATE**: 타인 `VIDEO_FORBIDDEN(3403)`, 소유자 정상 조회.
6. **재생 소스**(§도메인 4): `blurred_s3_key != null`이면 그 key, 아니면 `encoded_url` key를 presigned GET으로 발급.
   `processing_status != READY`면 `playbackUrl=null`(상태만 반환).
7. **조회수**(§도메인 5): `playbackUrl`을 실제로 발급(non-null)한 조회일 때만 `view_count`를 **원자적 UPDATE**로 +1.
   단 **소유자 본인 조회는 제외**. 중복 방지 없음(Phase 2 후속).
8. `expiresInSec`는 `playbackUrl` 발급 시 presign TTL(초)과 정합, `playbackUrl=null`이면 null.
9. 인증 필수 — 미인증은 SecurityConfig가 401. 응답은 `SuccessResponse.of(...)`로 감싸 HTTP 200 + `developCode 200`.
   **Flyway 마이그레이션 없이** 전체 테스트 green.

## 설계 결정 (근거 포함)

| # | 포인트 | 결정 | 한 줄 근거 |
|---|---|---|---|
| M1 | 엔드포인트·메서드 | **`GET /api/videos/{videoId}`** | 단건 리소스 조회 = GET의 정직한 동사. `VideoController`에 GET 전례가 없을 뿐 `/{videoId}`는 PUT(교체)·DELETE와 같은 리소스라 자연스럽다. `GridVideoController`의 GET들은 `/api/grids/**`라 경로 충돌 없음(확인). |
| M2 | 소유권 조회 | **`findById`로 먼저 가져와 caller(owner/타인)를 판정** — `findOwnedVideo`(주인 아니면 곧장 403)를 쓰지 **않는다** | 본 API는 타인도 PUBLIC 영상을 재생할 수 있어야 하므로 "주인만" 게이트인 `findOwnedVideo`는 부적합하다. row를 먼저 얻고 status/visibility/owner 조합으로 노출을 판정한다. owner 판정은 `video.getUserId() == userId`(기존 `findOwnedVideo`의 `!=` 비교와 동일 관용). |
| M3 | 재생/썸네일 URL 발급 | **기존 `ThumbnailUrlPresigner.presign(key)` 재사용** — 재생본 key와 썸네일 key 둘 다 이걸로 GET presign. TTL은 그 상수(10분=600s)를 `expiresInSec`로 노출 | 이 컴포넌트는 이미 "S3 key → TTL 있는 presigned GET URL, null-safe"라는 범용 연산이고 MSG-153에서 공유용으로 추출됐다(video·usergrid 소비). 재생도 완전히 같은 연산이라 새 클래스는 슬롭이다(ponytail 재사용). `expiresInSec`를 채우려면 서비스가 TTL 값을 알아야 하므로 **TTL을 public 상수/`long ttlSeconds()`로 노출**하는 최소 additive 변경만 한다(기존 호출부 영향 0). *대안(리뷰 교체 가능): 이름이 Thumbnail이라 의미가 어긋난다면 `S3GetUrlPresigner`로 리네임(호출부 2곳 + 테스트 기계적 수정). 동작 무차이 — 팀 취향.* |
| M4 | 응답 DTO | **신규 `VideoPlaybackResponseDto` + `of(Video, playbackUrl, thumbnailUrl, expiresInSec)` 팩터리** | presign은 엔티티에 없어 서비스가 발급해 넘긴다 — `GridCoverVideoResponseDto.of(video, thumbnailUrl)` 패턴과 동일. 필드는 §API 명세 참조. |
| M5 | 응답에 `status` 필드 포함 | **`VideoPlaybackResponseDto`에 `status`(ACTIVE/BLINDED) 포함** | BLINDED 영상을 소유자가 조회할 때 `playbackUrl=null`만으로는 "블라인드됨"과 "아직 READY 아님"을 구분할 수 없다(둘 다 null). status를 내보내야 소유자가 사유를 안다(성공기준 4). 타인·정상 응답에서는 항상 `ACTIVE`라 무해하고, DELETED는 404라 이 응답에 도달하지 않는다. *리뷰 노트: 모더레이션(status=BLINDED 세팅)은 MVP 미구현이라 BLINDED는 현재 도달 불가 상태다. "BLINDED-소유자에게 메타 노출"이 불필요하다고 판단되면 BLINDED도 전원 404로 단순화하고 `status` 필드를 뺄 수 있다 — §미해결 질문 1.* |
| M6 | 조회수 증가 방식 | **원자적 native `@Modifying` UPDATE `view_count = view_count + 1 WHERE id=:id`** | read-modify-write(엔티티 dirty check)면 동시 재생에 lost update가 난다. `decrementVideoCount`(MSG-72)가 이미 쓰는 "SQL 안에서 원자 연산" 관용을 그대로 따른다. `@Transactional`(read-write) 안에서 조건부로 1회 호출. |
| M7 | 조회수 노출값 | **응답 `viewCount`는 이번 조회 증가 전 스냅샷**(`video.getViewCount()`) | native UPDATE 후 엔티티 값은 stale하다. 정확한 표시를 위해 재조회하는 대신 증가 전 값을 내보낸다 — 조회수는 결과적 일관성으로 충분하고 자기 조회를 즉시 반영할 요구가 없다. 표시에 +1이 꼭 필요하면 DTO 매핑에서 더한다(minor, 리뷰 교체 가능). |

**중복 방지·익명 재생은 범위 밖**: MVP는 "재생 URL 발급 = 1 view"(소유자 제외, 중복 방지 없음). 세션/IP 단위
중복 방지, 미인증 공개 재생은 Phase 2 후속 티켓(§범위 밖).

## 접근 제어 매트릭스

판정은 §도메인 2 순서대로 위→아래 first-match. `caller` = 소유자(`video.userId == principal.userId`) / 타인.

| caller | status | visibility | processing_status | 응답 | playbackUrl | view_count |
|---|---|---|---|---|---|---|
| any | (row 없음) | — | — | **404** `VIDEO_NOT_FOUND` | — | — |
| any | DELETED | — | — | **404** `VIDEO_NOT_FOUND` | — | — |
| 타인 | BLINDED | — | — | **404** `VIDEO_NOT_FOUND` | — | — |
| 소유자 | BLINDED | — | — | **200** 메타 | null | 증가 X |
| 타인 | ACTIVE | PRIVATE | — | **403** `VIDEO_FORBIDDEN` | — | — |
| 소유자 | ACTIVE | PRIVATE | READY | **200** 메타 | 발급 | 증가 X(소유자) |
| 소유자 | ACTIVE | PRIVATE | ≠READY | **200** 메타 | null | 증가 X |
| 소유자 | ACTIVE | PUBLIC | READY | **200** 메타 | 발급 | 증가 X(소유자) |
| 소유자 | ACTIVE | PUBLIC | ≠READY | **200** 메타 | null | 증가 X |
| 타인 | ACTIVE | PUBLIC | READY | **200** 메타 | 발급 | **+1** |
| 타인 | ACTIVE | PUBLIC | ≠READY | **200** 메타 | null | 증가 X |

핵심 규칙 요약:
- **404 = 존재 은닉**(DELETED 전원 · BLINDED 타인). **403 = 존재 노출 + 접근 거부**(PRIVATE 타인).
- `playbackUrl != null` ⟺ `status==ACTIVE AND processing_status==READY AND (visibility==PUBLIC OR 소유자)`.
- `view_count +1` ⟺ `playbackUrl != null AND 타인`. (= ACTIVE·PUBLIC·READY를 타인이 재생) — MSG-87 대표
  선정(`view_count DESC`)이 참조하는 바로 그 카운트다.

## 도메인 로직

### 1. 조회 흐름 (read)

`@Transactional`(readOnly=false — 조회수 증가 UPDATE 때문). 순서:

1. `videoRepository.findById(videoId)` → 없으면 `VIDEO_NOT_FOUND`.
2. `boolean owner = video.getUserId() == userId`.
3. 접근 제어 판정(§2) — 거부면 예외, 허용이면 아래로.
4. 재생 소스 결정(§4)·presign, 조회수 증가(§5).
5. `VideoPlaybackResponseDto.of(video, playbackUrl, thumbnailUrl, expiresInSec)` 반환.

grid/region 파생 없음 — 도감·점령·수집률과 무관(재생 조회는 노출 축이지 점령 축이 아니다).

### 2. 접근 제어 판정 순서 (순서가 정보 노출을 결정)

first-match로 위에서부터 판정한다. **순서를 바꾸면 노출 정책이 깨진다**(예: visibility를 BLINDED보다
먼저 보면 블라인드된 PUBLIC 영상이 403 대신 200으로 존재를 드러낸다).

1. **존재/DELETED**: row 없음 또는 `status==DELETED` → `VIDEO_NOT_FOUND`(소유자 포함 전원). 지운/없는 영상은
   존재 자체를 숨긴다. `deleteVideo`/`replaceVideo`가 DELETED를 `VIDEO_NOT_FOUND`로 막는 선례와 일관.
2. **BLINDED**: `status==BLINDED` → 타인이면 `VIDEO_NOT_FOUND`(신고 처리된 영상의 존재 은닉), 소유자면
   통과하되 재생 불가로 처리(§3).
3. **visibility**: `status==ACTIVE AND visibility==PRIVATE AND 타인` → `VIDEO_FORBIDDEN`. 소유자·PUBLIC은 통과.
   *주의: PRIVATE는 404가 아니라 403이다 — 존재는 노출하되 접근만 막는다(티켓 확정). DELETED/BLINDED의 은닉과
   의도적으로 다르다.*
4. **processing_status**: 통과한 영상에 대해 `READY`면 재생 URL 발급, 아니면 `playbackUrl=null`(상태만 반환, §4).

### 3. BLINDED 소유자 조회 (재생 불가 메타)

- 소유자가 자기 BLINDED 영상을 조회하면 200 + 메타를 주되 `playbackUrl=null`, `status=BLINDED`로 반환한다.
  소유자는 "내 영상이 블라인드됐다"를 응답의 `status`로 인지한다(processing_status가 READY여도 status가 구분).
- 조회수 증가 없음(재생 URL 미발급).
- **모더레이션(status=BLINDED 세팅)은 MVP 미구현** — BLINDED는 현재 도달 불가 상태다. 본 API는 그 상태가
  들어와도 안전하도록 방어적으로만 처리한다(§미해결 질문 1에서 단순화 여지 명시).

### 4. 재생 소스 선택 & presign

- `processing_status != READY`면 `playbackUrl=null`, `expiresInSec=null`. 그 외 메타는 그대로 반환한다
  (FE가 `processingStatus`로 "인코딩 중/실패" 플레이스홀더를 그린다).
- `READY`면 재생 key = **`blurred_s3_key != null ? blurred_s3_key : encoded_url`**. 블러본이 있으면 우선.
  - AI 블러 흐름을 거친 READY 영상은 `blurred_s3_key`·`encoded_url` 둘 다 채워져 있고(MSG-150) 블러본을 재생한다.
  - AI 없이 인코딩만 거친 READY 영상은 `blurred_s3_key`가 null이라 `encoded_url`을 재생한다. `markReady`가
    `encoded_url`을 세팅하므로 **READY ⇒ `encoded_url` non-null**이 보장된다(재생 key null 불가).
- `playbackUrl = thumbnailUrlPresigner.presign(재생key)`, `thumbnailUrl = thumbnailUrlPresigner.presign(thumbnail key)`.
  presign은 로컬 서명 연산(S3 호출 아님)이라 두 번 호출해도 비용 무시 가능.
- `expiresInSec = ThumbnailUrlPresigner` TTL(600초). presign URL과 같은 TTL이라야 FE가 만료를 정확히 안다.
  *ponytail: TTL은 재생·썸네일 공통 600초. 30초 영상 재생 시작엔 충분. 재생 중 재버퍼링(>10분)이 문제되면
  재생 전용 TTL 상수로 분리 — 지금은 YAGNI.*

### 5. 조회수 증가 (원자적, 소유자 제외, 중복 방지 없음)

- `playbackUrl`을 실제로 발급한 조회(= ACTIVE·READY·재생 허용)이고 **타인**일 때만 1회 증가.
- 증가는 `videoRepository.incrementViewCount(videoId)` — native `@Modifying` `UPDATE videos SET view_count =
  view_count + 1 WHERE id = :id`. 읽고 계산해 쓰지 않으므로 동시 재생에도 lost update가 없다
  (`decrementVideoCount` 관용과 동일). `chk_videos_view_count CHECK (view_count >= 0)`는 증가라 항상 만족.
- **소유자 본인 조회는 제외** — 자기 영상 여닫기로 조회수가 부풀지 않게. `owner==false`일 때만 호출.
- **중복 방지 없음**: 같은 사용자가 반복 재생하면 매번 +1. 세션/IP 단위 dedup은 Phase 2 후속 티켓(§범위 밖).

1. **BLINDED 소유자 응답을 유지할지 vs 전원 404로 단순화할지.**

   지금 붙이는 건 YAGNI"라 판단하면 **BLINDED도 전원 404로 단순화하고 `VideoPlaybackResponseDto.status`
   필드를 제거**할 수 있다. 두 안 모두 정상 흐름(ACTIVE)엔 영향 없다 — 리뷰에서 택1. 기본값은 방어 버전.
