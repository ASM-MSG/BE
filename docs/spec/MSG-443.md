# MSG-443: 행사방 열람 인원 집계 (heartbeat와 캐시 TTL)

**Owner**: B (`com.msg.fillmap.event.*` 신설. 콘텐츠 도메인이라 video, mission, notification과 같은 축이다. 이 패키지는 CLAUDE.md 협업 원칙 Owner B 목록에 아직 없으므로, 구현 첫 커밋에서 목록 행 추가를 함께 넣는다. zone 패키지의 2026-08-07 누락 보완 선례를 따른다)

> PRD 정본: `docs/prd/event-room-location-videos.md` §4.4 현재 열람 인원, US-008, FR-17~19
> SRS: FR-EVENT-11 (계획)
> 제약: MSG-438(행사 도메인 모델)과 독립 구현이다. occurrenceId는 경로 변수로만 받고 행사 엔티티나 테이블에 의존하지 않는다. 존재 검증은 MSG-438 이후 후속 연결.

## 개요

행사방을 지금 보고 있는 사람 수를 근실시간으로 세는 서버 몫이다. 클라이언트가 행사방을 보는 동안 30초 주기로 heartbeat[^1]를 보내고, 서버는 마지막 신호가 90초 이내인 고유 세션만 센다. 저장은 Redis Sorted Set[^2] 하나에 TTL[^3]을 걸어 하고 DB 테이블은 만들지 않는다. 유실을 허용하는 근사값이라는 점에서 핫구역(MSG-233)과 같은 철학이다. 산출물은 heartbeat 수신과 열람 인원 조회, 엔드포인트 둘이며 두 경로 모두 비로그인 열람을 허용한다(D4, 2026-08-20 확정).

## 배경 · 목표

행사방 헤더에 "120명 보는 중"을 띄우려면(PRD §4.4) 지금 보고 있는 세션의 목록이 어딘가에 있어야 하는데, 이 수치는 정확할 필요도 없고 잃어버려도 다시 쌓이는 값이다. 그래서 DB가 아니라 TTL 캐시에 두고, 캐시가 죽으면 수치만 숨기고 행사방의 나머지 기능은 그대로 돌게 한다(FR-19). 행사 도메인 테이블(MSG-438)이 아직 없어도 성립하는 구조라 병렬 착수가 가능하다.

## 성공 기준

- heartbeat를 보내는 세션만 열람 인원에 들어가고, 마지막 신호가 90초를 넘긴 세션은 집계에서 빠진다 (FR-17, FR-18)
- 같은 사용자가 탭 두 개로 heartbeat를 보내도 1명으로 세고, 비로그인 세션도 헤더 식별자로 집계된다 (FR-17, PRD §4.4 중복 제거·US-008)
- 열람 집계 연산이 실패하면 열람 인원 조회는 오류가 아니라 "값 없음"으로 응답하고, heartbeat 실패는 삼켜진다. 열람 집계 코드는 다른 API 경로에 존재하지 않으므로 영상 조회와 업로드는 영향을 받지 않는다. 격리 범위의 한정(공유 Redis 전면 장애는 별개)은 D3 참조 (FR-19)
- 회차(occurrenceId)가 다르면 열람 인원이 섞이지 않는다 (PRD US-010의 회차 분리 원칙)
- 아래 "테스트 시나리오"가 전부 green이다

## API 명세

### POST /api/event-occurrences/{occurrenceId}/heartbeat (신설)

열람 세션 갱신. 비로그인 허용(SecurityConfig permitAll 등록, D4). 요청 본문 없음.

| 항목 | 내용 |
|---|---|
| 경로 변수 | `occurrenceId` (Long). 존재 검증 없음, MSG-438 이후 후속 연결 |
| 세션 식별자 | 로그인이면 principal[^5]의 `userId`로 `u:{userId}`, 비로그인이면 `X-Viewer-Session` 헤더 값으로 `s:{sessionId}` (D4). 비로그인인데 헤더도 없으면 식별 불가라 공통 400(`BAD_REQUEST`, 도메인 에러코드 신설 없음) |
| 성공 응답 | `SuccessResponse<Void>` (data null, PushTokenController.register 선례) |
| 캐시 예외 | 삼키고 warn 로그, 200 응답 (D3). 클라이언트가 할 수 있는 일이 없고 30초 뒤 재전송이 내장돼 있다 |

없는 occurrenceId로 보내도 200이다. 캐시에 키 하나가 생겼다가 120초 뒤 TTL로 사라질 뿐이라 오염이 남지 않는다. 누구나 임의 Long ID로 키를 만들 수 있는 표면이 남지만, 살아 있는 키 수는 요청률 × TTL(120초)로 유계이고, MSG-438 후속의 회차 존재 검증이 이 표면을 닫는다(미해결 질문 참조). 경로 변수가 숫자가 아니면 스프링 타입 변환 실패로 공통 400(`BAD_REQUEST`)이며 도메인 에러코드를 신설하지 않는다.

### GET /api/event-occurrences/{occurrenceId}/viewer-count (신설)

현재 열람 인원 조회. 비로그인 허용(SecurityConfig permitAll 등록, D4). 응답이 사용자 무관이므로 principal을 받지 않는다.

**성공 응답**: `SuccessResponse<EventViewerCountResponseDto>`

```java
// event/dto/EventViewerCountResponseDto.java
public record EventViewerCountResponseDto(
	Integer viewerCount   // 현재 열람 인원. 0 = 아무도 없음(표시), null = 캐시 장애(숨김)
) { }
```

0과 null을 가른다. 0은 정상 집계 결과라 FE가 그대로 표시할 수 있고, null은 "지금은 모른다"라서 FE가 문구 자체를 숨긴다(PRD US-008 "캐시 장애 시 숫자를 숨기고"). 캐시 예외를 오류 응답으로 바꾸지 않는 이유는 D3 참조.

**에러 케이스**: 없음. 이 티켓은 도메인 에러코드를 하나도 만들지 않으므로 event 도메인의 developCode 대역 배정(response-pattern 표 갱신)은 에러코드가 처음 필요해지는 티켓(MSG-438 계열)으로 미룬다.

## 도메인 로직

### 저장 구조 (Redis, DB 없음)

| 항목 | 값 |
|---|---|
| 키 | `eventviewer:{occurrenceId}` (Sorted Set) |
| member | 세션 식별자 문자열. 로그인 `u:{userId}`, 비로그인 `s:{sessionId}` (D4) |
| score | 마지막 heartbeat의 epoch 초 (주입된 `Clock` 기준, UTC) |
| 키 TTL | 120초. 활성 판정(90초 경계)은 ZCOUNT의 score 경계만 담당하고, 키 TTL은 조용해진 방의 메모리 회수만 담당한다. 활성 창과 같은 90초로 두면 마지막 heartbeat 후 정확히 90초에 키째 만료돼, 포함돼야 할 경계 멤버가 세어지기 전에 사라진다 |

### D-결정

**D1. 저장은 회차당 Sorted Set 하나다.**

member가 세션 식별자(로그인 사용자는 `u:{userId}`)라 같은 사용자의 중복 탭은 ZADD가 score만 덮어써 자동으로 1명이 되고, score가 시각이라 "90초 이내" 판정이 범위 연산(ZCOUNT) 하나다. 중복 제거와 시간 창을 자료구조 하나가 다 처리한다.

기각한 대안과 이유:
- **세션당 String 키(`eventviewer:{occurrenceId}:{식별자}`, TTL 90초)**: 만료는 공짜지만 세는 쪽이 문제다. 키 개수 집계는 SCAN 순회라 조회마다 O(전체 키공간) 비용이고, 별도 카운터를 두면 만료와 감산의 정합 문제가 새로 생긴다.
- **HyperLogLog**: 추가만 되고 만료(제거)가 안 된다. 90초 창은 오래된 멤버를 빼는 것이 본질이라 부적합하다.

**D2. heartbeat는 Lua 스크립트[^4] 하나로 원자 실행한다.**

```text
ZREMRANGEBYSCORE key -inf (now-90)   -- 만료 멤버 청소
ZADD key GT now viewerKey            -- 갱신 (중복 탭은 덮어쓰기)
EXPIRE key 120                       -- 키 TTL 재설정 (메모리 회수 전용, 활성 판정 아님)
```

분리 명령이면 ZADD 후 단절 시 TTL 없는 키가 잔존한다(핫구역 `INCREMENT_SCRIPT`와 같은 이유). GT 플래그는 기존보다 큰 score만 갱신하고 신규 멤버 추가는 그대로 허용해서, 네트워크에서 지연된 옛 heartbeat가 나중에 도착해 최신 score를 과거로 되돌리는 역순 실행을 막는다. 청소(ZREMRANGEBYSCORE)를 쓰기 경로에 넣는 것은 멤버가 키 TTL로만 지워지는 구멍을 막기 위해서다. heartbeat가 계속 오는 인기 행사방은 키가 안 죽어서, 쓰기마다 청소하지 않으면 하루 동안 다녀간 모든 사용자가 멤버로 쌓인다.

조회는 `ZCOUNT key now-90 +inf`다. 90초 경계는 포함이다("90초 이내"). 경계 문법이 두 식에서 다른 것은 의도다. 청소식의 `(now-90)`은 배타 경계라 딱 90초 경과한 멤버를 지우지 않고 남기며, 조회식은 포함 경계라 그 멤버를 세므로 두 식이 같은 "90초 이내" 판정을 이룬다. 청소를 이미 쓰기가 하므로 조회는 세기만 한다.

**D3. 장애 격리는 "구조적 분리 + 예외 삼킴" 두 겹이고, 격리 대상은 열람 집계 연산의 실패다 (FR-19).**

- 구조: 열람 집계는 이 티켓의 서비스 안에만 있고 영상 조회, 업로드, 다른 행사방 API 코드 경로 어디에도 끼어들지 않는다. 핫구역이 업로드 트랜잭션에 집계를 끼울 때 겪은 결합 문제가 여기엔 애초에 없다.
- 예외: 서비스 구현이 Redis 호출을 try-catch로 감싸 heartbeat는 삼키고(warn 로그) 조회는 `viewerCount = null`을 돌려준다. 예외를 컨트롤러 밖으로 던지지 않으므로 GlobalExceptionHandler의 500 변환에 닿지 않는다. 유실 허용은 설계다. 근사값이고 30초마다 다시 쌓인다(핫구역 D6 철학).

**격리 범위의 한정**: FR-19가 격리하는 장애 도메인은 집계 호출 자체가 던지는 예외(타임아웃, 커맨드 오류, 집계용 연결 실패 등)다. 공유 Redis가 전면 장애면 인증 필터의 토큰 블랙리스트 조회(`JwtTokenProvider.validateToken` → `RedisInvalidatedTokenStore.isInvalidated`, try-catch 없음)가 먼저 실패해, 토큰을 실은 요청은 D3의 try-catch에 도달하기 전에 인증 단계에서 실패한다(토큰 없는 비로그인 요청은 그 조회를 거치지 않아 D3이 그대로 받는다). 이때는 영상 조회와 업로드를 포함한 전 인증 API가 함께 실패하며, 이는 이 티켓 밖의 기존 플랫폼 특성이다. 블랙리스트 조회를 fail-open으로 바꾸는 것(폐기 토큰 재허용, 보안 후퇴)도 열람 집계용 Redis 인스턴스 분리(인프라 범위 밖)도 채택하지 않는다. 아래 장애 격리 테스트 2건의 목(Redis 호출 예외)이 검증하는 것도 이 한정된 범위다.

**D4. 비로그인 열람을 허용한다 (2026-08-20 정민 확정 — 구 제안안 "로그인 필수" 대체).**

웹 정책상 열람 계열(홈 칩: 핫구역, 지역축제, 팝업스토어, 경로추천, 지역)은 비로그인 가능이고 업로드, 도감, 프로필만 로그인 강제다. 행사방 열람 인원도 열람 계열이므로 heartbeat와 viewer-count 두 경로를 SecurityConfig permitAll 목록에 추가한다.

**permitAll 배선 경계**: 두 경로는 **SecurityConfig permitAll에만** 추가하고 **`JwtAuthenticationFilter.PUBLIC_AUTH_PATHS`(shouldNotFilter)에는 넣지 않는다.** 그 필드 주석("SecurityConfig 의 permitAll 인증 경로와 반드시 함께 갱신한다")을 여기에 따르면 Bearer 파싱이 통째로 건너뛰어져 로그인 사용자의 principal이 null이 되고, 헤더 없는 로그인 요청이 400이 되거나 `s:`로 잘못 집계된다. 이 경로들은 "인증 불요"이지 "토큰 무시"가 아니다. 유효 토큰이 실려 오면 필터가 평소처럼 principal을 세운다. 만료·위조 토큰이 실린 요청은 기존 필터 의미론대로 401이며, 익명으로 보내고 싶으면 토큰을 빼면 된다.

세션 식별자 규칙:
- **로그인**: principal의 userId로 `u:{userId}`. 헤더가 함께 와도 무시한다. principal 우선이어야 같은 사용자의 중복 탭이 항상 1명으로 수렴한다(탭마다 헤더 세션 ID가 다를 수 있다).
- **비로그인**: 클라이언트 생성 세션 ID를 `X-Viewer-Session` 헤더로 받아 `s:{sessionId}`. 값 형식은 유계로 강제한다. **공백이 아니고 최대 64자**(UUID 권장이나 형식 강제는 문자수뿐). 헤더 부재, 빈 값, 64자 초과 전부 식별 불가와 같은 공통 400이다. 빈 값이 통과하면 모든 익명이 member `s:` 하나로 뭉개져 집계가 무너지고, 길이 무제한은 member 크기 증폭이라 막는다.
- 접두사(`u:` / `s:`)로 네임스페이스를 갈라 userId 숫자와 익명 ID 문자열이 우연히 충돌하는 것을 막는다.

수용하는 한계: 익명 세션 ID는 클라이언트가 만드는 값이라 새 ID를 연타하면 열람 인원을 부풀릴 수 있다. 열람 인원은 보호 자산이 아니라 공개 근사값이므로 이를 수용하며, rate limit 같은 방어는 요구사항 신설이라 이 티켓에서 하지 않는다.

후속 참고: 현행 SecurityConfig는 핫구역 등 다른 칩 조회도 인증 필수라, 열람 계열 전면 비로그인 개방은 별도 후속 티켓 몫이고 이 티켓은 행사방 2개 경로만 연다. NFR-SEC-01(예외 명시 목록)의 SRS 갱신도 후속이다.

**D5. 시각은 주입된 `Clock`에서만 얻는다.** epoch 초로 다뤄 시간대 문제가 없고, 인자 없는 `now()` 금지 컨벤션을 지키며, 90초 경계 테스트를 고정 Clock으로 결정적으로 만든다(핫구역 양쪽 구현 선례). 기본 생성자는 `Clock.systemUTC()`, 테스트 생성자는 Clock 주입.

**D6. heartbeat 처리는 요청 스레드 동기다.** 핫구역 집계가 별도 스레드로 뺀 것은 업로드 응답에 Redis 지연이 전가되는 문제 때문이었는데, heartbeat는 그 자체가 독립 요청이라 지연이 전가될 본체가 없다. Redis 클라이언트의 기본 타임아웃이 최악 지연의 상한이고, 그 실패는 D3이 삼킨다.

### 신설 구성 요소

```text
com.msg.fillmap.event
├─ controller/EventViewerController.java        # 엔드포인트 2개, principal/헤더 → viewerKey 해석 (D4)
├─ service/EventViewerService.java              # 인터페이스: recordHeartbeat(occurrenceId, viewerKey) / getViewerCount(occurrenceId)
├─ service/EventViewerServiceImpl.java          # StringRedisTemplate + Lua, Clock 주입
└─ dto/EventViewerCountResponseDto.java
```

`getViewerCount`의 반환은 `Integer`(장애 시 null)다. 30초 주기 상수는 FE 계약 값이라 서버 코드에 두지 않고, 서버 상수는 활성 창 90초와 키 TTL 120초 둘이다.

## 데이터 모델

## 미해결 질문

- **occurrenceId 존재 검증**: MSG-438의 행사 회차 테이블이 생긴 뒤 heartbeat와 viewer-count에 존재 검증을 붙일지, 붙인다면 404(EVENT_NOT_FOUND)로 할지는 MSG-438 이후 후속 티켓 몫이다. 현재는 없는 id도 무해하게 흡수된다(키 TTL 120초 뒤 자연 소멸).

[^1]: heartbeat: 클라이언트가 "아직 보고 있음"을 알리려 주기적으로 보내는 신호. 명시적 퇴장 이벤트에 의존하지 않아 앱 강제 종료나 네트워크 단절에도 신호가 끊기는 것만으로 집계에서 빠진다.
[^2]: Sorted Set: Redis의 정렬 집합. 멤버마다 점수(score) 하나를 붙여 저장하고, 점수 범위로 세거나 지우는 연산이 로그 시간에 된다. 여기서는 점수를 마지막 신호 시각으로 써서 "90초 이내"를 범위 연산 하나로 판정한다.
[^3]: TTL(Time To Live): 키에 걸어 두는 자동 만료 시간. 만료가 지나면 Redis가 키를 스스로 지우므로, 별도 청소 작업 없이도 조용해진 행사방의 데이터가 사라진다.
[^4]: Lua 스크립트: Redis가 여러 명령을 하나의 원자 단위로 실행하게 하는 방법. 명령 사이에 연결이 끊기거나 다른 클라이언트가 끼어드는 일이 없어, "갱신했는데 TTL을 못 걸었다" 같은 반쪽 상태를 막는다.
[^5]: principal: 인증 필터가 토큰을 검증해 요청에 붙여 주는 사용자 신원 객체. 이 프로젝트에서는 `AuthPrincipal(userId, role)`이고, 로그인 사용자의 식별은 항상 여기서만 얻는다(NFR-SEC-02).
