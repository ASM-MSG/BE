# MSG-469: 비로그인 지도의 나머지 조회 개방 (구역 목록, 장소 검색, 인기 검색어, 격자 영상 2종, 시간대 차트)

**Owner**: A

Owner 판정 근거: 자바 코드가 바뀌는 파일이 `com.msg.fillmap.search`(장소 검색과 검색어 집계)와
`com.msg.fillmap.zone`(주석 갱신), 그리고 공용 인프라인 `global/config/SecurityConfig` 셋이다.
CLAUDE.md 협업 원칙에서 search와 zone은 Owner A(지도 인프라)다. 개방 대상 여섯 중 격자 대표 영상과
격자 전역 영상 목록과 격자 시간대 분포는 Owner B의 `com.msg.fillmap.video`(GridVideoController)가
서비스하지만, 이 티켓에서 그 패키지의 파일은 한 줄도 바뀌지 않는다. 매처[^1] 등록 세 줄이 전부이고
요청과 응답 계약도 그대로다. 그래서 구현 배정은 A로 두되, 개방 사실 자체는 B가 알아야 하므로 아래
"계약 변경" 절에 경계면 항목으로 적어 리뷰에서 확인받는다. 선행 스펙 MSG-454가 B, MSG-467이 A였던
것과 같은 기준(티켓의 축이 어느 패키지의 코드를 실제로 고치는가)을 따랐다.

**선행 정본**: `docs/prd/mission-map-explore.md` 8절 "2026-08-25 추가 (사용자 확정, MSG-469)".
개방 대상 여섯, 단일 격자 조회와 AI 경로 추천의 로그인 유지, 비로그인 검색의 인기 검색어 집계 편입과
그 집계에 방문자 식별값을 쓰는 결정, 호출량 제한 미도입과 관찰 조건이 모두 그 절에 등재돼 있다.
이 스펙은 거기에 "어떻게"만 붙인다.

## 개요

MSG-454(핫구역과 미션)와 MSG-467(행정동)로 비로그인 지도를 열어 왔는데, 지도가 실제로 부르는 조회
여섯이 아직 401이라 화면이 반쪽으로 동작한다. 검색바에서 "서면"처럼 구역 이름을 쳐서 그 자리로
지도를 옮기는 기능이 구역 목록 401로 막히고, 격자를 눌러도 대표 영상과 영상 목록과 시간대 차트가
비며, 장소 검색과 인기 검색어도 쓰지 못한다. 이 티켓은 그 여섯을 GET 한정으로 열고, 그중 유일하게
코드가 필요한 장소 검색에서 익명 검색이 인기 검색어 집계에 들어가도록 검색자 식별값을 사용자 id
하나에서 "로그인 사용자 또는 익명 방문자"로 넓힌다. 여섯 모두 응답 본문은 로그인 때와 완전히 같다.

격자 표시명("서면 A-14")은 이 개방과 무관하게 이미 나온다. 표시명 계산은 2026-08-07(MSG-341)에
서버로 옮겨져 격자를 담는 응답이 `zoneName`과 `zoneCell`을, 구역 밖이면 `regionName`을 직접
싣는다(glossary "표시명" 항목이 정본). 구역 목록의 잔존 용도는 검색바 구역 이동(MSG-234 §D6)과
구역 범위 오버레이 둘이고, FR-ZONE-11의 문안이 그대로 그 용도를 가리킨다.

다섯(구역 목록, 인기 검색어, 격자 대표 영상, 격자 전역 영상 목록, 격자 시간대 분포)은 컨트롤러가
principal[^2]을 아예 받지 않아 `SecurityConfig` 매처 등록만으로 끝난다. 장소 검색만
`principal.userId()`를 서비스에 넘기고 있어 매처만 열면 익명 요청이 401이 아니라 NPE 500이 된다.
그래서 search 패키지 안의 검색자 식별 표현을 `long userId`에서 문자열 검색자 키로 바꾸고, 익명은
화면이 보내는 방문자 세션 값을 그 키로 삼는다.

## 배경 · 목표

기획의도는 상단 칩과 지도가 로그인 없이 보이고 로그인은 업로드부터라는 것이다(MSG-439에서 확정,
MSG-454와 MSG-467이 이행). 그 개방이 화면 단위가 아니라 엔드포인트 단위로 진행되다 보니 매번 잔여
401이 남았고, 이번이 QA 결함 대조에서 확인된 마지막 잔여분이다. 목표는 셋이다. 첫째, 비로그인
지도에서 구역 이동과 영상과 검색이 로그인 때와 같이 동작하게 만든다. 둘째, 사용자별 값이 실린
조회는 그대로 닫아 둔다. 셋째, 비로그인 검색을 인기 검색어 표본에 넣되 "한 사람이 하루에 같은 말을
여러 번 쳐도 한 번만 센다"는 기존 규칙을 익명에도 지킨다.

세 번째가 이 티켓에서 유일하게 설계가 필요한 지점이다. 지금 그 규칙은 로그인 사용자 id를 기준으로
걸려 있고, 기준이 없으면 아예 세지 않는 것이 MSG-258의 결정이다(코드 주석에 "Redis 실패면 카운트도
진행하지 않는다. 중복 제거[^3] 없이 세면 도배 방어가 뚫린다"로 박혀 있다). 익명을 기준 없이 세는
설계는 그 결정 위반이므로 택하지 않는다.

## 성공 기준

1. 비로그인(무토큰) GET 요청이 다음 여섯 경로에서 200으로 성공한다.
   `/api/zones`, `/api/search/places`(q 필수), `/api/search/trending`,
   `/api/grids/{gridId}/cover`, `/api/grids/{gridId}/videos`,
   `/api/grids/{gridId}/hourly-uploads`.
2. 여섯 경로의 응답 본문이 로그인 조회와 완전히 같다. 새 필드도 없고 빠지는 필드도 없다.
3. 비로그인 GET이 `/api/grids/{gridId}`(단일 격자), `/api/grids`(뷰포트 도감),
   `/api/grids/aggregation`(도감 집계), `/api/grids/{gridId}/my-videos`(내 영상)에서 여전히 401이다.
   비로그인 POST `/api/routes/recommend`(AI 경로 추천)도 401이다.
4. 방문자 식별값을 실은 익명 장소 검색이 200이고, 그 검색어가 인기 검색어 집계에 1회 접수된다.
   같은 식별값으로 같은 날 같은 검색어를 다시 치면 추가로 세지 않는다.
5. 방문자 식별값이 없거나 비었거나 상한을 넘거나 콜론을 포함하는 익명 장소 검색도 200이고 결과는
   동일하며, 집계에만 접수되지 않는다. 이 경우에도 400을 내지 않는다.
6. 익명 집계의 어떤 값도 데이터베이스에 저장되지 않는다. `search_keyword_daily_counts`에는 날짜와
   검색어와 개수만 남고 방문자 식별값은 Redis 중복 제거 키에만 존재한다.
7. 여섯 경로의 비GET 요청은 여전히 401이다.
8. 개방된 GET에 무효 토큰이 실려 오면 기존과 같이 401 + developCode 2401이다.

### 장소 검색의 요청 헤더 (신규, 선택)

| 이름 | 필수 | 규칙 | 용도 |
|---|---|---|---|
| `X-Viewer-Session` | 아니오 | 공백이 아닌 문자열, 최대 64자, 콜론(`:`) 불가 | 비로그인 검색의 인기 검색어 집계 중복 제거 기준 |

- 로그인 요청에서는 이 헤더를 무시한다. 검색자 식별은 항상 principal이 우선이다.
- 값이 없거나 비었거나 64자를 넘거나 콜론을 포함하면 집계만 건너뛰고 검색은 정상 200이다. 400을
  내지 않는다. MSG-443의 열람 인원이 같은 조건에서 400을 내는 것과 다른데, 그쪽은 식별값이 없으면
  기능 자체가 성립하지 않는 반면 여기서는 검색이 주 기능이고 집계가 부수 경로이기 때문이다. 화면이
  헤더를 붙이기 전에도 검색이 막히지 않아야 한다는 PRD 확정이 이 차이의 근거다.
- 콜론을 막는 이유는 아래 D4에 적었다. 중복 제거 키가 콜론으로 이어 붙는 구조라 값 안의 콜론이
  구분자와 섞이면 서로 다른 검색이 같은 키가 된다. UUID를 권장하는 MSG-443의 안내와도 어긋나지
  않는다.
- 이름은 MSG-443이 이미 쓰는 헤더를 그대로 재사용한다. 브라우저 하나가 익명으로 들고 있는 방문자
  세션 값은 하나면 충분하고, 새 이름을 만들면 화면이 같은 성격의 값을 둘 관리하게 된다.

### 에러 케이스 (전부 기존 동작 그대로)

- 장소 검색의 q 파라미터 누락은 400이다. 익명이어도 같다.
- 트림 후 빈 q는 200 + 빈 배열이고 외부 호출도 집계 접수도 없다.
- 카카오 로컬 장애와 타임아웃은 502 + developCode 5502다. 이때도 검색어는 집계에 접수된다
  (FR-SEARCH-05, 익명도 동일).
- 격자 전역 영상 목록의 무효 커서는 400(INVALID_CURSOR)이고 size는 1에서 50으로 클램프된다.
- 격자 시간대 분포는 공개 영상이 없는 격자와 존재하지 않는 gridId에도 전 구간 0인 200이다.
- 익명이 닫힌 경로로 오면 401 (`CustomAuthenticationEntryPoint`, 공통 UNAUTHORIZED).
- 개방 GET + 무효 토큰은 401 + developCode 2401 (`JwtAuthenticationFilter`가 기존대로 검증).
- 새 developCode는 없다.

## 도메인 로직

### D1. SecurityConfig 매처 등록 (다섯은 이것으로 끝난다)

MSG-467 블록 아래에 GET 한정 항목 하나를 더한다. 경로는 정확히 여섯만 열거한다.

```java
// 비로그인 지도의 나머지 조회(MSG-469): 위 행정동 개방(MSG-467)과 같은 "상단 칩은 비로그인,
// 업로드는 로그인" 원칙의 마지막 잔여분이다(정본 docs/prd/mission-map-explore.md 8절 2026-08-25).
// 구역 목록은 검색바에서 구역 이름("서면")으로 지도를 옮기는 기능의 재료이고(MSG-234 §D6,
// FR-ZONE-11), 격자 커버와 전역 영상 목록과 시간대 분포는 격자를 눌렀을 때 화면을 채우는
// 값이다(셋의 노출 자리가 같아 하나만 빠지면 그 자리만 빈다). 여섯 다 사용자 무관 값이라 응답
// 계약은 불변이다(FR-ZONE-11, FR-SEARCH-01·07, FR-VIDEO-17·18, FR-MAP-09).
// GET 한정과 경로 열거가 계약의 일부다. /api/grids/** 로 넓히면 단일 격자와 뷰포트 도감과 도감
// 집계와 내 영상 목록까지 함께 풀리는데, 그 넷은 principal.userId() 를 null 가드 없이 부르므로
// 익명 유입이 401 이 아니라 NPE 500 이 된다(GridController 72·102·146행, GridVideoController 48행).
// /api/search/** 로 넓히는 것도 같은 이유로 금지다. 지금 search 하위가 둘뿐이라 안전해 보여도
// 다음에 붙는 경로가 기본 공개가 되는 fail-open 이 된다.
.requestMatchers(HttpMethod.GET,
	"/api/zones",
	"/api/search/places",
	"/api/search/trending",
	"/api/grids/*/cover",
	"/api/grids/*/videos",
	"/api/grids/*/hourly-uploads").permitAll()
```

- `*`는 한 세그먼트만 매치하므로 `/api/grids/*/videos`는 `/api/grids/{id}/my-videos`를 잡지 않는다
  (세그먼트 문자열 자체가 다르다). 회귀 방지는 아래 테스트 2번이 맡는다.
- `/api/grids/aggregation`도 안 잡힌다. 위 세 패턴은 grids 뒤에 세그먼트가 둘 있어야 매치된다.
- MSG-454가 쓴 숫자 제약 변수(`{missionId:[0-9]+}`) 같은 장치는 필요 없다. 여기 여섯은 마지막
  세그먼트가 리터럴이거나(cover, videos, hourly-uploads, trending, places) 경로 변수가 없는
  리터럴이다(zones).
- HEAD는 열지 않는다. 여섯 중 명시 HEAD 매핑이 있는 경로가 없고 화면 요구도 아니다.

### D2. JwtAuthenticationFilter는 건드리지 않는다

`PUBLIC_AUTH_PATHS`에 새 경로를 넣지 않는다. MSG-443 D4 원칙 그대로다. permitAll[^4]은 인증
불요이지 토큰 무시가 아니다. 무효 토큰은 기존대로 401 + 2401이고, 유효 토큰이 실려 오면 필터가
평소처럼 principal을 세운다. 장소 검색은 이 성질에 실제로 기대고 있다. 로그인 사용자가 개방된
경로로 검색해도 principal이 서 있어야 집계가 사용자 기준으로 잡힌다.

### D3. 검색자 식별값의 표현 (장소 검색의 유일한 코드 변경)

`PlaceSearchService.searchPlaces(long userId, String q)`와
`SearchKeywordCommandService.recordSearch(long userId, String rawQuery)`의 첫 인자를 문자열
검색자 키로 바꾼다. 값은 로그인이면 사용자 id의 문자열 표현이고, 익명이면 `s:` 접두를 붙인
방문자 세션 값이며, 집계 대상이 아니면 null이다.

```java
// PlaceSearchService
List<PlaceSearchResponseDto> searchPlaces(String searcherKey, String q);   // searcherKey null 이면 집계 생략
List<PlaceSearchResponseDto> searchPlaces(String q);                        // MSG-457 오버로드, 무변경
```

세 안 중 이것을 택한 이유는 이렇다.

- **nullable `Long userId`로만 바꾸는 안**은 익명을 표현하지 못한다. 익명도 중복 제거 기준이
  있어야 하므로 사용자 id 자리에 담을 값이 필요한데, 그 값은 숫자가 아니다.
- **오버로드를 하나 더 추가하는 안**(`searchPlaces(long, String)`을 남기고
  `searchPlaces(String, String)`을 신설)은 같은 뜻의 경로가 둘이 되고, 집계 규칙이 바뀔 때마다 두
  곳을 고쳐야 한다. MSG-457이 오버로드를 추가한 것은 뜻이 실제로 다른 경우였다(기계가 조립한
  검색어라 집계에 접수하지 않는다). 이번은 같은 뜻의 값이 넓어지는 것이라 교체가 맞다.
- **채택안(교체)**은 컴파일 오류로 모든 호출부를 드러내 준다는 이점이 있다. 실제 호출부는
  컨트롤러 한 곳뿐이고(route가 쓰는 1인자 오버로드는 무변경), 나머지는 테스트다.

컨트롤러는 MSG-443의 `EventViewerController.resolveViewerKey`와 같은 모양으로 키를 만든다. 다른
점은 식별값이 없을 때 예외 대신 null을 돌려준다는 것과, 길이 검사 옆에 콜론 검사가 하나 더 붙는다는
것 둘이다(콜론 검사의 근거는 D4).

```java
private static final String VIEWER_SESSION_HEADER = "X-Viewer-Session";
/** 익명 세션 값 길이 상한. MSG-443 EventViewerController 와 같은 값이고 이유도 같다(키 크기 증폭 방지). */
private static final int MAX_SESSION_ID_LENGTH = 64;

/** null 은 "집계 대상 아님"이다. 검색 자체는 그대로 수행된다(PRD 8절 2026-08-25 확정). */
private String resolveSearcherKey(AuthPrincipal principal, String viewerSession) {
	if (principal != null) {
		return String.valueOf(principal.userId());
	}
	// 콜론은 중복 제거 키의 구분자라 값에 들어오면 세션과 검색어의 경계가 모호해진다 (D4)
	if (viewerSession == null || viewerSession.isBlank()
		|| viewerSession.length() > MAX_SESSION_ID_LENGTH || viewerSession.indexOf(':') >= 0) {
		return null;
	}
	return "s:" + viewerSession;
}
```

`VIEWER_SESSION_HEADER` 상수는 `EventViewerController`의 것과 값이 같지만 공용 상수로 뽑지 않는다.
뽑으려면 Owner B의 event 패키지를 고쳐야 하고, 얻는 것은 20자짜리 리터럴 하나의 중복 제거뿐이다.
대신 양쪽 주석에 같은 헤더임을 적는다. 소비자가 셋째로 늘면 그때 공용 상수로 승격한다.

### D4. 익명 중복 제거 키 (MSG-258 결정을 지키는 방식)

집계 구현은 지금 구조를 그대로 쓴다. Redis SET `searchdedupe:{yyyyMMdd}`(KST 날짜)에 member를
넣고, SADD가 1을 반환한 경우에만 `upsertIncrement(date, keyword)`로 DB 카운트를 올린다. TTL[^5]
26시간도 그대로다. 바뀌는 것은 member의 앞부분 하나다.

| 검색자 | member | 예시 |
|---|---|---|
| 로그인 | `{userId}:{정규화 검색어}` (기존 그대로) | `42:부산대` |
| 익명 | `s:{세션값}:{정규화 검색어}` | `s:9f3c...:부산대` |

- **왜 로그인 쪽에 `u:` 접두를 붙이지 않는가**: 붙이면 배포 순간부터 member 포맷이 바뀌어, 그날
  이미 검색한 로그인 사용자가 같은 검색어를 다시 칠 때 한 번 더 세어진다. "하루에 한 번"이라는
  규칙(FR-SEARCH-06)을 배포 당일에 스스로 어기는 셈인데, 얻는 것은 두 포맷의 대칭성뿐이다.
  MSG-443이 `u:`와 `s:`를 함께 쓴 것은 그 키 공간이 신설이라 이행 비용이 0이었기 때문이다.
- **로그인 member는 애초에 모호하지 않다**: 사용자 id가 십진수라 콜론이 없고, 그래서 첫 콜론까지가
  검색자이고 나머지가 검색어라는 해석이 유일하다.
- **익명 member는 세션 값에 콜론을 금지해 같은 성질을 얻는다** (Codex 리뷰 P2 반영). 금지하지
  않으면 서로 다른 조합이 같은 member가 된다. 세션 `a`에 검색어 `b:c`, 세션 `a:b`에 검색어 `c`가
  둘 다 `s:a:b:c`가 되어 뒤에 온 검색이 중복으로 취급돼 집계에서 통째로 빠진다.
  `normalize()`는 트림과 공백 압축과 소문자화만 하므로 검색어 쪽 콜론은 그대로 남는다. 검색어를
  건드리는 대신 세션 값을 좁히는 쪽을 택한 이유는 검색어가 사용자 입력이자 순위 재료라 변형하면
  안 되는 값인 반면, 세션 값은 화면이 만드는 불투명한 식별자라 형식을 정할 수 있기 때문이다.
  길이 프리픽스 인코딩처럼 임의 값을 모호하지 않게 잇는 방식도 있지만, 지금 필요한 성질을 검사
  한 줄로 얻을 수 있어 채택하지 않는다.
- **충돌하지 않는 근거**: 로그인 member는 항상 숫자로 시작하고 익명 member는 항상 `s`로 시작한다.
  사용자 id의 십진 표현이 `s:`로 시작할 수 없으므로 두 공간은 구조적으로 겹치지 않는다. 이 불변은
  테스트 12번이 고정한다.
- **Redis 실패 시 동작은 불변**이다. 익명이라고 중복 제거를 건너뛰고 세는 경로는 만들지 않는다.
  MSG-258 §D4의 결정("중복 제거 없이 세면 도배 방어가 뚫린다")이 익명에도 그대로 적용된다.
- **운영 메모**: 익명이 늘면 일별 SET의 원소 수가 방문자와 검색어 조합만큼 늘어난다. 원소 하나가
  수십 바이트이고 키가 통째로 만료되므로(만료 시점의 정확한 계산은 D5) 지금 규모에서는 문제가
  아니지만, 인기 검색어 순위가 부자연스럽게 흔들리는지와 함께 배포 뒤 관찰 대상이다(PRD 8절이
  관찰을 조건으로 뒀다).

### D5. 방문자 식별값은 저장하지 않는다

`search_keyword_daily_counts`(V23)에는 사용자 컬럼이 없고 DDL 주석이 "사용자 식별자와 카카오 응답
필드 없음(약관 경계, FR-7)"으로 그 경계를 명시한다. 익명 식별값도 같은 경계 안에 둔다. 그 값은
Redis 중복 제거 member의 일부로만 존재하고 어떤 테이블에도 저장되지 않는다. DB 마이그레이션이 없는
이유이기도 하다.

**보존 기간은 "member가 들어간 뒤 26시간"이 아니다.** 중복 제거 스크립트가 이렇게 생겼다.

```lua
local added = redis.call('SADD', KEYS[1], ARGV[1]) redis.call('EXPIRE', KEYS[1], ARGV[2]) return added
```

`EXPIRE`가 `added` 값과 무관하게 매 호출마다 실행되고 키는 날짜 단위라, **그 날짜로 접수되는 검색이
하나 들어올 때마다 집합 전체의 TTL이 26시간으로 다시 설정된다.** 중복이라 카운트되지 않은 검색도
갱신을 일으킨다. 그래서 정확한 서술은 "그 날짜 키의 마지막 접수로부터 26시간"이고, 그날 이른
시각에 들어온 식별값은 최대 약 50시간까지 남을 수 있다(그날 마지막 검색이 자정 직전이면 26시간이
거기서 다시 시작하므로).

이 동작은 이번 티켓이 만든 것이 아니라 MSG-258 때부터 있던 기존 동작이고, 로그인 사용자 id에도
똑같이 적용된다. 익명이라서 더 오래 남는 것이 아니다.

**스크립트는 고치지 않는다.** SADD와 EXPIRE를 한 스크립트로 묶은 이유가 코드 주석에 있고(분리하면
SADD 성공 후 단절 시 TTL 없는 키가 잔존한다), EXPIRE를 `added == 1`일 때만 걸도록 바꾸는 것은
로그인 경로의 기존 동작까지 바꾸는 별개 변경이라 이 티켓 범위가 아니다. 지금 필요한 것은 기간을
정확히 기록하는 것이고, 보존 기간 단축이 요구가 되면 그때 별도 티켓에서 다룬다.

로그도 같은 경계로 다룬다. 집계 실패 warn 로그는 지금 `userId`를 남기는데, 익명 세션 값은 클라이언트
입력이므로 그대로 찍지 않는다(MSG-342 D-2의 "입력값을 로그에 에코하지 않는다"). 로그인 검색자 키는
서버가 발급한 값이라 그대로 남기고, 익명은 접두만 남긴다.

```java
/** 로그인 키는 서버 발급값이라 그대로, 익명 세션 값은 클라이언트 입력이라 접두만 남긴다(MSG-342 D-2). */
private static String logKey(String searcherKey) {
	return searcherKey.startsWith("s:") ? "s:(masked)" : searcherKey;
}
```

### D6. 집계 생략의 배선

`PlaceSearchServiceImpl`의 2인자 오버로드는 지금 흐름을 유지하고 접수 앞에 null 검사만 더한다.
트림 후 빈 검색어를 먼저 자르는 순서도 그대로다(빈 검색어는 집계도 외부 호출도 하지 않는다).

```java
@Override
public List<PlaceSearchResponseDto> searchPlaces(String searcherKey, String q) {
	String query = q.trim();
	if (query.isEmpty()) {
		return List.of();
	}
	if (searcherKey != null) {   // 식별값 없는 익명. 검색은 하고 집계만 건너뛴다 (PRD 8절)
		searchKeywordCommandService.recordSearch(searcherKey, query);
	}
	return searchPlaces(query);
}
```

접수가 실패해도 검색 응답에 영향이 없다는 성질(FR-SEARCH-05, fire-and-forget[^6])은 그대로다.

### D7. 낡은 주석 정리

세 컨트롤러의 클래스 주석이 이 티켓으로 낡는다. 다음 취지로 고친다.

- `ZoneController`: 마지막 줄의 "지도 화면 뒤 조회라 로그인 필요(SecurityConfig anyRequest)"만
  비로그인 열람 허용(MSG-469)으로 바꾼다. **그 앞 문단은 지금 것이 정확하니 그대로 둔다.** 표시명
  계산은 서버 몫이고(MSG-341) 격자를 담는 응답이 `zoneName`과 `zoneCell`을 직접 실으므로, 이 API의
  용도가 검색바 구역 이동(MSG-234 §D6)과 구역 범위 오버레이 둘이라는 현행 서술이 정본과 맞는다.
  비로그인 개방의 근거로도 그 용도를 적는다. "격자 이름의 재료라 이것이 막히면 이름이 안 나온다"는
  취지의 문장을 새로 넣지 않는다. 사실이 아니고, 정확한 기존 설명을 틀린 의존성으로 덮어쓰게 된다.
- `TrendingKeywordController`: "인증은 SecurityConfig anyRequest 로 강제된다(미인증 401)" 문구를
  비로그인 열람 허용으로 바꾼다.
- `PlaceSearchController`: 같은 문구 교체에 더해, 검색자 식별이 principal 우선이고 익명은 방문자
  세션 헤더이며 값이 없거나 형식을 벗어나면 집계만 건너뛴다는 규칙을 적는다.

`GridVideoController`는 인증을 언급하는 주석이 없어 손대지 않는다. Owner B 코드 무수정 원칙과도
맞는다.

변경 없음. 엔티티 변경도 Flyway 마이그레이션도 필요 없다. 익명 식별값은 Redis 중복 제거 키

## 계약 변경

**있음. `PlaceSearchService`가 바뀐다.** 이 파일은 레포가 관리하는 Owner A와 B 사이의 계약
인터페이스다. `.claude/docs/status.md`(257행) 계약 인터페이스 표에 Owner A 소유로 등재돼 있고,
MSG-457부터 B(route)가 집계 없는 오버로드 `searchPlaces(String)`을 소비해 경계면에 편입됐다.
CLAUDE.md 협업 원칙의 route Owner 판정도 "A 접점은 PlaceSearchService 오버로드 1건"으로 같은
사실을 적는다. 이 절을 "없음"으로 두지 않는 이유는 이 절이 상대 팀원의 리뷰를 부르는 장치이기
때문이다. 공유 파일이 바뀌는데 없음이라고 적으면 그 검토가 통째로 건너뛰어진다.

아래 둘이 리뷰에서 Owner B의 확인이 필요한 항목이다.

1. **`PlaceSearchService` 시그니처 변경 (B 쪽 실질 영향 없음)**. 바뀌는 것은 2인자 메서드
   하나다. `searchPlaces(long userId, String q)`가 `searchPlaces(String searcherKey, String q)`가
   된다(D3). B가 소비하는 1인자 오버로드 `searchPlaces(String q)`는 시그니처도 동작도 그대로이고,
   실제 호출부는 `RouteCandidateCollector`의 `placeSearchService.searchPlaces(query)` 한 곳이라
   재컴파일만 된다(grep 확인). status.md가 함께 적어 둔 계약 성질도 불변이다. 반환은 여전히
   비null(`List.of()`)이고 실패는 `ApiException(5502)` 전파이며, route가 그것을 삼켜 장소 후보를
   0으로 취급하는 처리도 그대로 성립한다. 같이 바뀌는 `SearchKeywordCommandService`는 search
   패키지 안에서만 소비되는 3-layer 경계라 B의 확인 대상이 아니다.
2. **Owner B 도메인 엔드포인트 3종의 인증 정책 변경**. 격자 대표 영상과 격자 전역 영상 목록과 격자
   시간대 분포가 익명에 열린다. video 패키지의 파일은 바뀌지 않고 응답도 동일하지만, 그 도메인의
   노출 범위가 바뀌는 결정이라 B가 인지해야 한다. 근거는 PRD 8절 2026-08-25 확정이고, 셋 다 이미
   전역 노출 경로라 PUBLIC이며 READY인 영상만 실린다(FR-VIDEO-17, FR-MAP-09). 익명에게 새로 보이는
   값은 없다.

그 밖에 CLAUDE.md가 지목한 계약 인터페이스 넷(`GridQueryService`, `HotZoneService`,
`UserGridQueryService`, `UserOidcCommandService`)과 `ZoneNameQueryService`는 전부 무변경이다.

API 수준의 변경은 위 "API 명세" 절이 정본이고 FE 공유 대상이다.

### A. 신규 `src/test/java/com/msg/fillmap/global/config/AnonymousReadAccessHttpTest.java`

검증 대상이 `SecurityConfig` 한 곳인데 개방 경로가 zone과 search와 video 셋에 걸쳐 있어 어느 도메인

`MSG-467`의 `RegionPublicAccessHttpTest` 패턴을 그대로 쓴다. `@SpringBootTest` +
`@AutoConfigureMockMvc`로 MockMvc[^7]가 시큐리티 필터 체인을 실제로 타고, 서비스는 전부

---

[^1]: 매처(request matcher): SecurityConfig에서 어떤 경로와 메서드에 어떤 접근 규칙을 적용할지
    정하는 단위다. 등록 순서대로 검사해 먼저 맞은 규칙 하나만 적용되고, 아무 매처에도 안 잡힌
    요청은 마지막 `anyRequest()` 기본 규칙(이 프로젝트는 인증 필수)으로 떨어진다.
[^2]: principal: 인증 필터가 요청마다 세우는 "지금 호출한 사용자" 객체다. 이 프로젝트에서는
    사용자 id를 가진 `AuthPrincipal`이고 비로그인 요청에서는 null이다. principal을 받지 않는
    엔드포인트는 익명 개방에 코드 수정이 필요 없다.
[^3]: 중복 제거(dedupe): 같은 신호를 여러 번 받아도 한 번만 집계하는 처리다. 인기 검색어에서는
    "한 사람이 하루에 같은 검색어를 여러 번 쳐도 1회"가 그 규칙이고, 판정 재료가 검색자 식별값과
    날짜와 정규화한 검색어 셋이다.
[^4]: permitAll: Spring Security에서 특정 경로를 인증 없이 통과시키는 접근 규칙이다. 인증을
    요구하지 않는다는 뜻이지 실려 온 토큰을 무시한다는 뜻이 아니다. 무효 토큰은 평소처럼 401로
    거절된다.
[^5]: TTL(time to live): 저장한 키가 스스로 사라지기까지의 시간이다. 여기서는 중복 제거 SET에
    26시간을 거는데 그 시계가 접수마다 다시 시작하므로, 실제 만료는 그 날짜 키의 마지막 접수를
    기준으로 계산된다(D5). 하루 1회 판정 자체는 TTL이 아니라 키 이름에 든 날짜가 담당한다.
[^6]: fire-and-forget: 호출해 놓고 결과를 기다리지 않는 방식이다. 검색어 집계가 이 방식이라
    Redis나 DB가 느리거나 죽어도 검색 응답이 그만큼 늦어지거나 실패하지 않고, 대신 집계 신호는
    유실될 수 있다(순위는 근사 지표라 허용된다).
[^7]: MockMvc: 서버를 띄우지 않고 스프링 MVC 요청과 응답을 통째로 실행하는 테스트 도구다.
    시큐리티 필터 체인과 JSON 직렬화까지 타므로 인증 정책 검증에 적합하다.

- 신규 `AnonymousReadAccessHttpTest` 5건 + 기존 테스트 확장 8건, 개방으로 무효해진 익명 401 기대 **6건** 삭제(zone·trending·places·cover·videos·hourly-uploads). `my-videos`의 401 기대는 유지된다.
- 리뷰 권고 3건 반영. 그중 `logKey`의 null 역전이 실질 결함이었다. 예외를 삼키는 catch 블록 안에서 불리는 메서드라 null이 오면 NPE가 나 fire-and-forget 계약이 뒤집힌다. `searcherKey != null &&` 가드와 인터페이스 javadoc의 null 금지 명시로 닫았다.

**데이터 저장 위치**: 새 테이블·컬럼·마이그레이션 없음. 익명 방문자 식별값은 **DB에 저장되지 않고** Redis 중복 제거 집합의 member로만 존재한다. 키는 `searchdedupe:{yyyyMMdd}`(KST 날짜), member는 로그인이면 `{userId}:{키워드}`, 익명이면 `s:{세션값}:{키워드}`다. `search_keyword_daily_counts`에는 여전히 날짜·정규화 검색어·횟수만 쌓여 약관 경계(사용자 식별자 미저장)가 유지된다.

**보존 기간**: `DEDUPE_TTL_SECONDS`는 26시간이지만 Lua가 `SADD` 결과와 무관하게 매 호출 `EXPIRE`를 실행하고 키가 날짜 단위라, 실제 만료는 **그 날짜 키의 마지막 접수로부터 26시간**이다. 이른 시각에 들어온 값은 최대 약 50시간까지 남을 수 있다. 중복이라 카운트되지 않은 검색도 갱신을 일으킨다. MSG-258부터 있던 기존 동작이고 로그인 사용자 id에도 똑같이 적용되므로 익명이라서 더 오래 남는 것이 아니다.

**실행 쿼리**: 집계 경로는 Redis Lua `SADD`+`EXPIRE` 한 번과, 신규 member일 때만 `SearchKeywordDailyCountRepository.upsertIncrement`(native `ON CONFLICT (keyword_date, keyword) DO UPDATE SET search_count = search_count + 1`) 한 번이다. 중복이면 UPSERT를 실행하지 않는다. 개방된 조회 6종의 쿼리는 이번 변경으로 바뀌지 않았다.

**예외 흐름**: 개방 6경로에 무효 토큰이 실려 오면 매처와 무관하게 `JwtAuthenticationFilter`가 검증 실패를 HandlerExceptionResolver로 넘겨 401 + developCode 2401이 나간다(permitAll은 인증 불요이지 토큰 무시가 아니다). 매처에 안 잡히는 경로의 익명 요청은 `anyRequest().authenticated()`에서 `CustomAuthenticationEntryPoint`로 떨어져 401 + 2403이다. 집계 실패는 사용자에게 전파되지 않는다. `recordSearch`가 전 예외를 warn으로 삼키고 검색 응답은 독립적으로 200이며, 로그의 익명 키는 `s:(masked)`로 마스킹된다.

**빈 동작**: 신설·변경 빈 없음. 집계 워커(단일 데몬 스레드, 유계 큐 10,000)와 그 `@PreDestroy` 종료 흐름은 MSG-258 그대로다.
