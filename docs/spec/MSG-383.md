# MSG-383: 미션 설명과 장소, 운영시간, 대표 이미지를 저장하고 응답에 싣기

**Owner**: B (`com.msg.fillmap.mission.*` 전부 Owner B, CLAUDE.md 협업 원칙. Owner A 코드는 건드리지 않고
`GridEncoder`는 읽기만 한다)

> 요구사항 정본: `docs/prd/mission-map-explore.md` (상태: 검토됨, 2026-08-13 성민 승인).
> 이 스펙은 그 PRD의 FR-11, FR-12, FR-13, FR-14와 비기능 "데이터 정합", "운영" 항목을 다룬다.
> SRS 대응: FR-MISSION-16, NFR-DATA-07.
> 선행: V6 미션 스키마(MSG-166), 축제 시더(MSG-224), 코스 시더(MSG-225), 팝업 시더(MSG-235),
> 활성 조회(MSG-222).
> 후행: 축제 소스 TourAPI 전환과 이미지 수집(MSG-384), 뷰포트 목록과 상세 조회(MSG-368 계열).

## 개요

`missions` 테이블에 화면이 읽을 메타데이터 컬럼 8개를 더하고(V31), 시더 3종이 원본에서 그 값을
읽어 적재하며, 기존 미션 조회 응답(`MissionResponseDto`)이 그 값을 그대로 내려준다.

수집 원본에는 축제 설명과 장소, 팝업 운영시간과 주소, 코스 거리와 소요시간과 난이도가 이미 들어
있는데 지금은 하나도 저장하지 않는다. 미션이 판정 대상이기만 하던 시절의 결정이라(MSG-224,
MSG-225, MSG-235가 나란히 "missions에 컬럼이 없어 미적재") 이름과 좌표와 기간만 적재한다.
보여주는 화면이 생기면서 그 전제가 끝났다.

이 티켓의 범위는 저장과 노출까지다. **대표 이미지는 컬럼과 적재 경로만 준비하고 값은 채우지
않는다.** 지금 세 원본 중 어디에도 이미지 주소가 없기 때문이고, 실제 수집은 축제가 MSG-384의
TourAPI 전환에서, 팝업 포스터가 같은 티켓의 상세 페이지 수집에서 들어온다(D7).

신규 API 엔드포인트 없음, 신규 에러 코드 없음, 계약 인터페이스 변경 없음. DDL은 V31 한 건이다.

## 배경 · 목표

지도 홈에서 축제나 팝업 영역을 눌러도 사용자는 그게 무슨 축제인지, 어디인지, 몇 시에 여는지 알
수 없다. PRD가 지적하는 대로 미션이 "가야 할 곳"으로 읽히려면 카드와 상세에 채울 텍스트가 있어야
하는데, 그 텍스트는 이미 수집해 둔 파일 안에 있고 DB로 넘어오지 않았을 뿐이다.

목표는 세 가지다.

1. 세 종류 미션 모두 카드에 쓸 위치 한 줄과 상세에 쓸 소개문을 갖는다 (FR-11).
2. 코스는 거리와 소요시간과 난이도를, 팝업은 운영시간과 주소를 갖는다 (FR-12, FR-13).
3. 대표 이미지 자리가 스키마와 응답에 준비돼 있어서, 수집이 끝나는 대로 화면 수정 없이 채워진다
   (FR-14).

이미 적재된 미션을 지우지 않고 채우는 것이 제약이다. dev 실적재는 542건이다(축제 237, 팝업 157, 코스 148). 스탬프가
걸린 미션을 지우면 비회수 원칙(FR-MISSION-04)이 깨진다.

## 성공 기준

아래 "테스트 시나리오"가 이 기준을 검증한다.

1. V31 적용 후 `missions`에 메타데이터 컬럼 8개가 있고, 코스 전용 3개는 `type='COURSE'`가 아닌
   행에서 CHECK가 거부한다. 기존 행은 전부 NULL이고 스탬프와 격자는 그대로다.
2. 시더 3종이 각 원본에서 해당 필드를 읽어 신규 컬럼에 적재한다. 유형별로 채워지는 컬럼이 D3의
   매핑표와 일치한다.
3. **이미 적재된 미션 위에서 시더를 재실행하면 메타데이터만 채워진다.** 제목과 기간과
   `mission_grids`와 `source_key`는 한 글자도 바뀌지 않고, `user_missions` 행 수도 그대로다
   (PRD 운영 요구, FR-MISSION-04).
4. 코스 소개문의 `<br>` 태그가 개행으로 바뀐 상태로 저장된다. 저장값에 태그 문자열이 남지 않는다.
5. 팝업 운영시간 배열이 여러 줄일 때 줄 순서를 유지한 한 문자열로 저장된다.
6. `GET /api/missions/active` 응답의 각 항목에 신규 필드 8개가 실린다. 값이 없는 필드는 null이고
   기존 필드는 이름도 타입도 그대로다.
7. `image_url`은 이 티켓 범위에서 항상 null이다. 외부 도메인 주소가 저장되는 경로가 없다 (D7).
8. `./gradlew test` green.

## API 명세

**신규 엔드포인트 없음.** 기존 `GET /api/missions/active`(MSG-222) 응답에 필드가 추가되는
additive[^1] 변경 하나뿐이다. 기존 필드의 이름, 타입, 의미는 그대로이므로 FE는 배포 순서에 상관없이
안전하다.

`MissionResponseDto`에 추가되는 필드:

| 필드 | 타입 | 설명 | 비는 경우 |
|------|------|------|-----------|
| `description` | String | 소개문 원문. 출처 표기 없이 그대로 노출한다 (PRD 확정 사항) | 팝업은 현재 스냅샷에 없어 null |
| `placeName` | String | 사람이 읽는 위치 한 줄. 축제는 행사장, 팝업은 주소, 코스는 시군 | 원본 결측 시 null |
| `sourceUrl` | String | 원문 링크. 축제 홈페이지, 팝업 상세 페이지 | 코스는 null, 축제는 34%가 null |
| `operationTime` | String | 운영시간 안내 문구. 여러 줄이면 개행으로 이어 붙인다 | 축제와 코스는 null |
| `imageUrl` | String | 대표 이미지 주소. 우리 스토리지 URL만 들어간다 (D7) | 이 티켓 범위에서는 항상 null |
| `distanceMeters` | Integer | 코스 총 거리(미터) | 코스가 아니면 null |
| `durationMinutes` | Integer | 코스 소요시간(분) | 코스가 아니면 null |
| `difficulty` | Integer | 코스 난이도. 두루누비 등급 1(쉬움), 2(보통), 3(어려움) | 코스가 아니면 null |

여덟 개 모두 `@Schema(requiredProperties = ...)`에 넣고 각 필드에 `nullable = true`를 함께 단다.
이 레포에서 `required`는 "값이 non-null"이 아니라 **"키가 존재한다"**는 뜻이라 nullable과 직교한다
(`ResponseSchemaNullabilityTest` 계약, `UserProfileResponseDto.email` 선례). 초판에서 이 둘을
배타로 다뤘다가 잡힌 이력이 그 가드 테스트에 적혀 있다. FR-14의 "이미지가 없으면 빈 자리로 두되
레이아웃이 무너지지 않는다"는 화면 몫이고, 서버는 필드를 빼지 않고 null로 내려 FE 분기를 하나로
유지한다.

`operationTime`은 이름과 달리 시각 값이 아니라 "매일 11:00 ~ 22:00" 같은 안내 문구다. 그래서
시각 타입이 아니라 String이 맞고, 시각 처리 컨벤션의 "String에 시각을 담는 우회 금지"에도 걸리지
않는다. 이 문구는 특정 순간을 가리키지 않으므로 시간대 변환 대상이 아니다.

**신규 에러 코드 없음.** 적재는 운영자가 플래그를 켜고 1회 기동하는 경로뿐이라 실패는 예외와
기동 로그로 드러난다(RegionSeeder 선례).

## 도메인 로직

용어는 glossary 기준이다. 여기서 다루는 것은 **미션 정의**이고, `grids` 테이블의 전역 격자 등록이나
사용자 점령과는 무관하다. `mission_grids.grid_id`는 grids FK가 없는 논리 식별자다(V6 §D2).

### D1. 앞선 세 스펙의 "컬럼이 없어 미적재" 결정을 대체하는 근거

MSG-224, MSG-225, MSG-235는 각각 원본의 나머지 필드를 미적재로 두면서 이유를 "missions에 컬럼
없음, 신규 DDL 금지"로 적었다. 다만 세 스펙 모두 조건을 함께 달아 두었다. MSG-235는 "카드 UI가
필요해지면 요구사항 신설 = PRD부터"라고 썼다.

그 조건이 그대로 충족됐다. PRD `mission-map-explore.md`가 검토됨 상태로 승인되면서 FR-11부터
FR-14까지가 카드와 상세에 이 값들을 요구하고, SRS FR-MISSION-16이 "MSG-224와 MSG-235의 컬럼이
없어 미적재 결정을 대체"한다고 명시한다. 그러니 이건 결정 번복이 아니라 그 결정들이 스스로
예고한 경로를 밟는 것이다. 앞선 스펙 3종의 해당 표 행은 이 스펙이 대체하며, 그 문서를 소급 수정하지
않는다(결정 시점의 기록으로 남긴다).

바뀌지 않는 것도 분명히 해 둔다. 미션의 **판정 규칙은 이 티켓에서 손대지 않는다.** 격자 전개
방식, `target_count`, 기간 판정, 스탬프 발급은 전부 그대로다. 팝업 판정 범위를 반경 40m로 좁히는
PRD 확정 사항은 별도 티켓이다.

### D2. 컬럼 8개와 타입

| 컬럼 | 타입 | 의미 |
|------|------|------|
| `description` | TEXT | 소개문 원문 |
| `place_name` | VARCHAR(200) | 사람이 읽는 위치 한 줄 |
| `source_url` | TEXT | 원문 링크 |
| `operation_time` | TEXT | 운영시간 안내 문구 |
| `image_url` | TEXT | 대표 이미지 주소 (우리 스토리지 URL) |
| `distance_meters` | INTEGER | 코스 총 거리(미터) |
| `duration_minutes` | INTEGER | 코스 소요시간(분) |
| `difficulty` | SMALLINT | 코스 난이도 등급 |

길이 근거는 실측이다. 축제 설명은 채움률 100%에 길이 중앙값 24자, 최대 214자다. 코스 소개문
(`crsContents`)은 148건 중 400자를 넘는 것이 8건이고 1,000자를 넘는 것은 없다. 그래도 상한을
문자 수로 못 박지 않고 TEXT를 쓰는 이유는, 소스가 바뀌었을 때(MSG-384 TourAPI 전환) 길이 초과가
적재 실패로 나타나면 운영자가 원인을 찾기 어렵기 때문이다. PostgreSQL에서 TEXT와 VARCHAR(n)은
저장 비용이 같다.

`place_name`만 VARCHAR(200)인 것은 `missions.title`과 같은 방어선을 공유하기 위해서다. 시더는
title과 같은 방식으로 200자에서 절단한다.

URL 두 개를 TEXT로 두는 것은 `users.profile_image_url text` 선례를 따른다. 외부 URL은 길이 상한을
믿을 수 없다.

`difficulty`를 정수로 저장하고 "쉬움" 같은 라벨로 바꾸지 않는 이유는, 라벨을 서버가 만들면 등급
체계가 서버 문자열 상수로 굳어 다국어와 표기 변경이 전부 서버 배포가 되기 때문이다. 실측으로 값은
1, 2, 3 세 가지뿐이고(148코스 전수, 4 이상 0건) API 문서에 그 의미를 적어 FE가 표기를 정한다.

거리를 킬로미터가 아니라 미터로 저장하는 것은 원본이 `"14"` 같은 문자열 정수여서다. 지금은 소수점이
없지만 재수집에서 `"13.4"`가 들어오면 정수 컬럼이 조용히 잘라낸다. 미터로 환산해 담으면 그 값이
13,400으로 보존된다. 표기 단위 변환은 화면 몫이다.

**코스 전용 3개에 CHECK를 건다.** `chk_missions_course_metrics`는 `type = 'COURSE'`가 아닌 행에서
세 값이 전부 NULL이기를 요구한다. 기존 `chk_missions_path`(path는 COURSE만)와 같은 형태이고, 축제
행에 거리가 붙어 화면에 "거리 22km인 축제"가 뜨는 사고를 스키마가 막는다. 반대로 값 범위 CHECK
(난이도 1~3, 거리 양수)는 걸지 않는다. 등급이 하나 늘면 마이그레이션이 필요해지는데, 그 검증은
시더의 reader가 이미 하는 일이다.

### D3. 유형별 원본 매핑

**축제 (`festivals.jsonl`, source='FESTIVAL')**. 실측 1,059행 기준.

| 원본 필드 | 대상 | 비고 |
|-----------|------|------|
| `description` | `description` | 채움률 100%, 중앙값 24자 |
| `place` | `place_name` | 빈 값 0건. 200자 절단 |
| `homepage` | `source_url` | 채움률 66%, 빈 문자열이면 null |
| 없음 | `operation_time`, 코스 3종 | 축제에는 해당 개념이 없다 |
| 없음 | `image_url` | 현 소스에 이미지가 없다. MSG-384가 채운다 |

`roadAddress`와 `lotAddress`는 계속 미적재다. 카드와 상세가 요구하는 것은 위치 한 줄인데 `place`가
100% 채워져 있어 주소 컬럼을 따로 두면 화면이 쓰지 않는 값이 하나 더 생긴다. `referenceDate`와
`sourceOrg`도 미적재이고, 이 판단은 축제 소스가 TourAPI로 바뀌는 MSG-384에서 다시 검토된다.

**팝업 (`popups.jsonl`, source='POPGA')**. 실측 2,593행 기준.

| 원본 필드 | 대상 | 비고 |
|-----------|------|------|
| `roadAddress` (+ `addressDetail`) | `place_name` | roadAddress 빈 값 0건. addressDetail이 있으면 공백으로 이어 붙인다(빈 값 144건). 200자 절단 |
| `sourceUrl` | `source_url` | 팝가 상세 페이지 |
| `operationTime` | `operation_time` | 문자열 배열. 원소를 순서대로 개행으로 이어 붙인다. 빈 배열 0건이지만 비면 null |
| 없음 | `description` | **현 스냅샷에 소개문 필드가 없다.** 미해결 질문 참조 |
| 없음 | `image_url`, 코스 3종 | 포스터는 MSG-384가 채운다 |

`address`는 `roadAddress`가 비었을 때만 쓰는 예비 값으로 둔다. 실측 결측이 0건이라 실행되지 않는
분기지만, 크롤 산출물의 결측은 시점에 따라 달라지고 위치 한 줄이 비면 카드가 무너진다.
`periodType`은 MSG-235 D6 그대로 계속 미사용이다.

**코스 (`courses-seed.json`, source='DURUNUBI')**. 원본은 `courses.json` 148코스.

| 원본 필드 | 대상 | 비고 |
|-----------|------|------|
| `crsContents` | `description` | 빈 값 0건. `<br>` 정규화 대상(D5) |
| `sigun` | `place_name` | "부산 영도구" 형태 |
| `crsDstnc` | `distance_meters` | 킬로미터 문자열을 1,000배해 반올림 |
| `crsTotlRqrmHour` | `duration_minutes` | 이름과 달리 단위가 분이다. `"330"`이 5시간 30분 |
| `crsLevel` | `difficulty` | `"1"`~`"3"` |
| 없음 | `source_url`, `operation_time`, `image_url` | 코스 대표 이미지는 스팟 사진에서 오므로 MSG-384 |

`crsSummary`(요약 불릿)와 `crsCycle`(순환 여부)과 `travelerinfo`(시종점 교통편)는 미적재다. 상세
화면이 소개문 하나를 요구하는데 `crsContents`가 전건 채워져 있어 폴백이 필요 없고, 나머지 둘은
PRD가 요구하지 않는다.

### D4. 코스 산출물 계약 확장

코스 시더가 읽는 것은 원본 `courses.json`이 아니라 레포 밖 파이프라인
(`~/fillmap-data/durunubi/spot_pipeline.py`)이 만든 `courses-seed.json`이다(MSG-225 D2). 따라서 새
필드가 흐르려면 그 산출물에 필드가 실려야 하고, 파이프라인 수정은 이 티켓의 레포 밖 선행 작업이다.
스펙이 정하는 것은 산출물 계약이다. 코스 객체에 `contents`, `sigun`, `distanceKm`, `durationMinutes`,
`level` 다섯 키를 더한다.

**결측은 허용하고 형식 위반은 거부한다.** `CourseSeedReader`는 지금 전량 거부[^2] 계약을 따르는데,
그 계약을 신규 필드에 그대로 적용하면 기존 산출물 파일로 재실행하는 순간 148코스가 통째로 거부돼
운영자가 손댈 수 없게 된다. 판정에 쓰이는 값(경로, 스팟, 격자 식별자)과 화면에 쓰이는 값의 무게가
다르다. 그래서 키가 없으면 null로 적재하고 시더 로그에 "메타데이터 결측 N건"을 집계한다. 반대로
키가 있는데 숫자가 아니거나 난이도가 정수가 아니면 기존 계약대로 예외를 던진다. 형식 위반은 결측이
아니라 결함이다.

### D5. 소개문의 `<br>` 정규화

코스 원본에는 `<br>` 태그가 451회 등장한다(대부분 `crsSummary`, 일부 `crsContents`). 다른 HTML
태그는 전수 확인 결과 없다.

시더는 `<br>`, `<br/>`, `<br />`를 대소문자 구분 없이 개행 문자 하나로 바꾼 뒤 저장한다. 다른 태그
제거나 HTML 이스케이프는 하지 않는다. 지금 없는 입력을 상대로 새니타이저를 만드는 셈이고, 값을
문자열로 렌더하는 클라이언트가 이미 이스케이프하기 때문이다. 나중에 다른 태그가 섞인 소스가
들어오면(TourAPI 소개문이 후보다) 그때 같은 자리에서 규칙을 넓힌다.

PRD가 "외부 소개문은 원문 그대로 노출"이라고 확정했으므로 요약이나 재작성은 하지 않는다. 태그를
개행으로 바꾸는 것은 내용 변경이 아니라 원본이 의도한 줄바꿈을 저장 형식으로 옮기는 일이다.

### D6. 재실행이 곧 백필

세 시더 모두 dedupe 통과분만 INSERT하는 구조라, 지금 그대로 두면 이미 적재된 미션(dev 542건)은 새 컬럼이
영원히 NULL이다. 새 파일로 갈아엎는 방법은 쓸 수 없다. 스탬프가 걸린 미션은 FK가 삭제를 막고
(V6 `user_missions.mission_id` NO ACTION), PRD 운영 요구가 "지우지 않고 채우는 방향"을 명시한다.

**결정: 시더의 skip 경로를 "아무것도 하지 않음"에서 "메타데이터만 갱신"으로 넓힌다.** 재실행이
그대로 백필[^3]이 되므로 마이그레이션에 백필 SQL을 넣지 않아도 된다.

- 갱신 대상은 이번에 추가한 8개 컬럼뿐이다. `title`, `start_at`, `end_at`, `target_count`,
  `source`, `source_key`, `path`, `mission_grids`는 건드리지 않는다.
- 따라서 **멱등 키[^4]는 그대로다.** 축제는 좌표와 기간, 팝업은 `source_key`, 코스는 제목이 계속
  키이고 키를 이루는 값은 갱신 대상이 아니다. 재실행 결과가 여전히 같은 상태로 수렴한다
  (NFR-DATA-03).
- 스탬프는 영향을 받지 않는다. `user_missions`는 `mission_id`만 참조하고 그 id가 바뀌지 않는다.
- 갱신은 JPA 더티 체킹[^5]으로 한다. 세 시더 모두 대조 단계에서 기존 미션을 엔티티로 이미
  읽으므로, 그 인스턴스에 값을 넣으면 트랜잭션 커밋에서 UPDATE가 나간다. native UPDATE를 따로
  쓰지 않는다.

구현상 필요한 변경 한 가지가 있다. 축제 시더의 `existingFestivalKeys()`는 지금 `Set<DedupeKey>`를
돌려줘서 skip할 때 어느 미션인지 모른다. `Map<DedupeKey, Mission>`으로 바꿔 skip 경로에서 그
미션을 갱신한다. 팝업은 `source_key` 기준, 코스는 제목 기준으로 같은 형태의 맵을 쓴다.

MSG-235 D3의 "INSERT-only, 기존 행 UPDATE 없음"은 이 범위에서만 완화된다. 그 결정이 지키려던 것은
날짜와 이름이 소스에서 흔들려도 기존 미션이 흔들리지 않는 것이었고(연장 팝업의 노출 공백을
정리-선행 순서로 흡수하는 D4 로직이 그 위에 서 있다), 메타데이터 갱신은 그 전제를 건드리지 않는다.

세 시더 모두 로그에 갱신 건수를 더한다. `SeedResult`에 `updated` 필드를 추가하고 기존
`loaded`, `deduped` 집계는 유지한다. 운영자가 "적재 0건"만 보고 아무 일도 없었다고 오해하지 않게
하는 장치다.

### D7. 이미지 컬럼의 의미와 NFR-DATA-07의 이 티켓 내 범위

**결정: 이 티켓은 컬럼과 그 의미를 정하는 데까지만 하고, 이미지 수집과 미러링은 MSG-384가 한다.**

수집 대상이 지금 0건이기 때문이다. 축제 표준데이터에도 팝가 스냅샷에도 이미지 주소 필드가 없고,
코스 대표 이미지는 TourAPI 스팟 사진에서 오는데 그 API 연동 자체가 MSG-384다. 여기서 미러링
파이프라인을 짜면 호출자가 없는 코드와 가짜 입력으로만 도는 테스트가 남는다. NFR-DATA-07이 요구하는
형식 통일(실측으로 팝업은 WebP, 축제 이미지 일부는 BMP)도 다운로드 시점의 변환이라 수집 코드에
붙는 것이 자연스럽다.

대신 컬럼 계약을 지금 못 박아 둔다. 그래야 나중 티켓이 외부 주소를 그대로 넣는 손쉬운 길로 새지
않는다.

- `missions.image_url`에는 **우리 스토리지(S3) URL만 저장한다.** 외부 도메인 주소를 넣지 않는다.
  `users.profile_image_url`과 같은 규칙이다.
- 이유는 NFR-DATA-07 그대로다. 팝업은 기간이 끝나면 원본 페이지가 사라지므로 외부 주소를 저장하면
  화면이 깨진다. 핫링크[^6]는 남의 서버에 트래픽을 떠넘기는 문제도 있다.
- 이 티켓에서 값은 항상 null이다. 세 시더 어디에도 이 컬럼에 값을 쓰는 경로가 없다.
- MSG-384가 받는 것은 컬럼 하나와 위 규칙, 그리고 응답 필드 하나다. 그쪽에서 다운로드, 형식 통일,
  S3 업로드, URL 기록을 한다.

PRD 엣지 케이스의 "대표 이미지 원본이 사라졌거나 형식을 읽을 수 없으면 이미지 없는 미션과 같게
처리한다"는 이 티켓에서 자동으로 성립한다. 값이 null이면 이미지 없는 미션이다.

### D8. 응답에 8개를 전부 싣는 판단

PRD의 클래스 다이어그램이 `MissionResponseDto`에 `description`, `placeName`, `imageUrl` 추가를
명시한다. 여기에 코스 3종과 운영시간과 원문 링크까지 같은 DTO에 싣는 이유는 상세 전용 DTO
(`MissionDetailResponseDto`)가 아직 없기 때문이다. 지금 필드를 목록과 상세로 나눠 두면 상세 티켓이
들어올 때 소비처가 두 번 바뀐다.

응답 크기가 늘어나는 것은 사실이다. 활성 미션(dev 기준 503건, 종료분 39건 제외)에 소개문이 붙고, 그중 코스 148건의 소개문이
가장 길다(400자 초과 8건, 1,000자 초과 0건). 감당 가능하다고 보는 근거는 두 가지다. 조회 경로에
1시간 전역 캐시가 있어 DB 부하는 늘지 않고, 뷰포트 제한(PRD 성능 요구, MSG-368)이 들어오면 실제
전송량은 화면에 보이는 범위로 줄어든다. 그전까지 이 응답은 이미 전국 전량을 내려주고 있었다.

조회 서비스(`MissionQueryServiceImpl`)는 **한 줄도 바뀌지 않는다.** `MissionResponseDto.of`가
엔티티에서 값을 더 읽을 뿐이고 메서드 시그니처도 그대로다. 캐시 구조와 shape 합성도 그대로다.

## 데이터 모델

### 마이그레이션: `V31__mission_metadata.sql`

현재 최신은 V30(`V30__videos_visibility_default_public.sql`)이고 다음 번호는 V31이다. 기존 V1부터
V30까지는 수정하지 않는다(체크섬 고정, MSG-130).

```sql
ALTER TABLE missions
	ADD COLUMN description      TEXT,
	ADD COLUMN place_name       VARCHAR(200),
	ADD COLUMN source_url       TEXT,
	ADD COLUMN operation_time   TEXT,
	ADD COLUMN image_url        TEXT,
	ADD COLUMN distance_meters  INTEGER,
	ADD COLUMN duration_minutes INTEGER,
	ADD COLUMN difficulty       SMALLINT;

ALTER TABLE missions ADD CONSTRAINT chk_missions_course_metrics CHECK (
	type = 'COURSE'
	OR (distance_meters IS NULL AND duration_minutes IS NULL AND difficulty IS NULL)
);
```

전 컬럼 nullable에 DEFAULT 없음이라 기존 행은 값이 NULL로 남고 재작성이 없다(PostgreSQL은
DEFAULT 없는 컬럼 추가를 카탈로그 변경만으로 끝낸다). 백필 SQL을 넣지 않는 이유는 D6이다. 시더
재실행이 백필이며, 그래야 값의 출처가 원본 파일 한 곳으로 유지된다.

인덱스는 만들지 않는다. 이 컬럼들로 검색하거나 정렬하는 요구가 PRD에 없다.

### 엔티티: `Mission` (부분 매핑[^7] 유지)

필드 8개를 평면으로 추가한다. 연관관계는 만들지 않는다(project-conventions.md 영속 계층 절).

값 묶음을 다루는 자리가 두 곳(생성과 갱신)이므로 순수 값 record 하나를 둔다.

```java
public record MissionMetadata(
	String description, String placeName, String sourceUrl, String operationTime, String imageUrl,
	Integer distanceMeters, Integer durationMinutes, Integer difficulty) {
}
```

`@Embeddable`로 만들지 않는다. 전 필드가 null인 embedded는 Hibernate가 null 객체로 돌려주는
경우가 있어 조회 경로에 NPE 함정이 생기는데, 이 티켓의 미션 대부분이 정확히 그 상태(전 필드 null)다.

- `Mission.builder()`에 `metadata(MissionMetadata)` 파라미터 하나를 더한다. 생성자가 8개 필드로
  펼친다. String 파라미터를 8개 나열하면 순서를 바꿔도 컴파일이 통과하는 자리라 record로 묶는다.
- 갱신용 `applyMetadata(MissionMetadata)` 메서드를 더한다. 상태 전이 메서드이므로 setter를 열지
  않는다(`Video.markBlinded()` 선례). 이 메서드는 시각을 만들지 않으므로 `Clock`이 필요 없다.

`created_at`은 지금처럼 `insertable = false`로 DB DEFAULT에 맡긴다. 메타데이터 갱신은 `updated_at`
같은 컬럼을 새로 만들지 않는다. 시더 실행 로그가 언제 무엇이 갱신됐는지를 이미 남긴다.

### 시각 처리

새 컬럼에 시각 타입이 없어 대부분 해당 사항이 없다. 지켜야 할 것은 세 가지다. 시더 3종의 기존
`Clock` 주입 구조를 그대로 두고 인자 없는 `LocalDateTime.now()`를 새로 쓰지 않는다. `operation_time`은
안내 문구이지 시각이 아니므로 시각 타입으로 바꾸지 않는다. DTO에 추가되는 필드에 시각 타입이 없어
`DtoTimeTypeGuardTest`는 그대로 통과한다.

## 미해결 질문

- **팝업 소개문의 출처.** PRD 확정 사항이 "팝업 소개문"을 원문 그대로 노출한다고 적었는데 현
  `popups.jsonl` 스냅샷에는 소개문 필드가 없다. 팝가 상세 페이지에는 있을 것으로 보이고, 그렇다면
  포스터(og:image)를 가지러 상세 페이지를 여는 MSG-384가 같이 수집하는 것이 크롤 1회로 끝나 자연
  스럽다. 이 티켓은 컬럼을 준비해 두고 팝업 `description`을 null로 남긴다. MSG-384 착수 시 확인이
  필요하다.
- **외부 데이터 이용약관의 출처 표기 조건.** PRD 미해결 질문 그대로다. 화면에는 표기하지 않기로
  확정됐고(FR-MISSION-16), 조건이 있으면 서비스 약관 페이지에 일괄 표기한다. 저장 스키마에는 영향이
  없다. `source_url`을 적재해 두므로 나중에 표기가 필요해져도 재수집이 필요 없다.

[^1]: additive 변경: 기존 필드를 그대로 둔 채 새 필드만 더하는 응답 변경. 옛 클라이언트가 모르는
    필드를 무시하기만 하면 되므로 서버와 클라이언트의 배포 순서를 맞출 필요가 없다.
[^2]: 전량 거부: 입력 파일에 결함이 하나라도 있으면 일부만 적재하지 않고 전체를 거부하는 계약.
    코스처럼 완성 산출물을 받는 경로에 쓴다. 결함 하나는 재생성 신호이지 부분 적재 신호가 아니라는
    판단이다.
[^3]: 백필: 나중에 생긴 컬럼을 이미 저장된 행에 채워 넣는 작업. 보통 일회성 SQL을 쓰지만, 여기서는
    시더 재실행이 그 역할을 겸한다.
[^4]: 멱등 키: 같은 입력을 여러 번 실행해도 행이 한 번만 만들어지도록 대조에 쓰는 값. 축제는
    중심 격자와 기간, 팝업은 팝가 id, 코스는 제목이다.
[^5]: 더티 체킹: JPA가 트랜잭션 안에서 읽어 둔 엔티티의 필드 변경을 감지해 커밋 시점에 UPDATE를
    자동으로 내보내는 동작. UPDATE 문을 직접 쓰지 않아도 된다.
[^6]: 핫링크: 남의 서버에 있는 이미지를 우리 화면에서 주소로 직접 불러 쓰는 것. 원본이 내려가면
    화면이 깨지고 상대 서버에 트래픽을 떠넘기게 된다.
[^7]: 부분 매핑: 엔티티가 테이블의 모든 컬럼이 아니라 실제로 쓰는 컬럼만 필드로 갖는 방식.
    이 레포의 관례이며 `Grid.geom`처럼 매핑하지 않는 컬럼이 이미 있다.

## 작업 로그 (2026-08-13 구현)

### 알려진 한계: 종료된 미션은 백필되지 않는다

`FestivalJsonlReader`와 `PopupJsonlReader`가 종료된 원본 행을 파싱 단계에서 걸러내므로, 스탬프가
있어 정리에서 살아남은 종료 미션은 D6 재실행 백필의 대상이 되지 않는다. 그 미션의 메타데이터는
계속 NULL이다.

지금 보이는 자리가 없어 이번 범위에서 닫지 않았다. 미션 목록은 활성만 담고(FR-MISSION-02),
스탬프북 화면은 아직 없다(FR-MISSION-12, MSG-219). 스탬프북이 들어올 때 "내가 깬 미션" 카드에
설명과 사진이 필요해지면 그때 리더를 "적재는 막되 갱신 대상으로는 통과"시키는 형태로 고친다.

### 저장 위치

- `missions` 테이블 8컬럼(`description`, `place_name`, `source_url`, `operation_time`,
  `image_url`, `distance_meters`, `duration_minutes`, `difficulty`). 모두 nullable, DEFAULT 없음
- `image_url`은 이 티켓에서 항상 NULL이다. 값을 쓰는 경로가 세 시더 어디에도 없다
- 별도 캐시나 파일 저장 없음. 조회 경로의 1시간 전역 캐시는 기존 그대로다

### 실행 쿼리

- **대조**: `MissionRepository.findBySource(source)` + `ORDER BY m.id`. 세 시더가 이 하나를 지난다.
  결과를 `Map`으로 색인하며 동키 충돌은 `(first, duplicate) -> first`로 최소 id를 고정한다
- **갱신**: native UPDATE를 쓰지 않는다. `Mission.applyMetadata`가 필드를 바꾸고 트랜잭션 커밋에서
  더티 체킹이 UPDATE를 낸다. 변경이 없으면 UPDATE 자체가 나가지 않아 재실행이 같은 상태로 수렴한다
- **신규**: 기존 INSERT 경로 그대로이고 컬럼만 늘었다

### 예외 흐름

`CourseSeedReader`가 형식 위반을 `IllegalStateException`으로 던지고 시더 트랜잭션이 롤백된다.
부분 적재가 남지 않는다. 던지는 조건은 넷이다.

- 숫자가 아닌 문자열
- 유한하지 않은 값(`NaN`, `Infinity`). 문자열 경로에도 검사가 걸린다
- INTEGER 범위 초과 (거리는 미터 환산 뒤 판정)
- 난이도가 1~3 밖, 거리·소요시간이 0 이하

**키가 아예 없는 것은 예외가 아니라 null이다.** 판정에 쓰는 값(경로·스팟·격자)과 화면에 쓰는 값의
무게가 다르기 때문이다(D4).

### 빈 동작

- 세 시더 모두 `@ConditionalOnProperty` 플래그 게이트 뒤에 있고 기본은 꺼져 있다. 플래그를 켜고
  1회 기동하는 것이 운영 절차다(NFR-OPS-06)
- `@Transactional`은 프로덕션 진입점 `run()`에 있다. 그 안에서 읽은 엔티티가 관리 상태라 더티
  체킹이 성립한다
- `SeedResult`에 `updated`(갱신 건수)와 코스의 `missingMetadata`(화면용 5종이 전부 없는 코스 수)가
  더해졌다. "적재 0건"만 보고 아무 일도 없었다고 오해하지 않게 하는 장치다

### 레포 밖 선행 작업

코스 시더가 읽는 `courses-seed.json`에 다섯 키(`distanceKm`, `durationMinutes`, `level`, `summary`,
`sigun`)를 산출 파이프라인(`~/fillmap-data/durunubi/spot_pipeline.py`)이 추가해야 값이 채워진다.
그전까지 재실행하면 `missingMetadata`가 코스 수만큼 찍힌다.

**결측은 키 생략이나 null로 표현하고 빈 문자열은 쓰지 않는다.** `""`는 결측이 아니라 형식 위반이라
전량 거부로 이어진다.
