# MSG-135: 리프레시 토큰 발급 (Redis · 로테이션 · 블랙리스트)

**Owner**: B (`com.msg.fillmap.auth.*`) — 순수 Owner B(KangJeong). 부모 MSG-36(회원가입/로그인).

> **A↔B 계약 인터페이스(`GridQueryService`·`HotZoneService`·`UserGridQueryService`·`UserOidcCommandService`)는 변경 없음.** (§계약 변경 참조)
> 이 티켓은 auth 도메인 내부(`auth/jwt`, `auth/service`, `auth/controller`, `auth/dto`, `auth/exception`)와 전역 설정(`global/config/SecurityConfig`, `application-*.yml`, `build.gradle`)만 건드린다.
>
> **선행 작업**: 로그인(`AuthService`)·OIDC 소셜 로그인(`OidcLoginService`)·JWT 액세스 토큰(`JwtTokenProvider`)·인메모리 블랙리스트(`InMemoryInvalidatedTokenStore`)가 develop에 이미 존재한다. MSG-135는 이 흐름에 **리프레시 토큰**을 추가하고, 블랙리스트 저장소를 **Redis로 이관**한다(신규 도메인 아님, 기존 인증 흐름 확장).
>
> **용어 주의**: glossary.md는 격자/도감 도메인 용어의 단일 진실 원천이며, 본 티켓의 auth 토큰 용어(액세스/리프레시 토큰·재발급·로테이션·블랙리스트·디바이스)는 glossary 관할 밖이라 용어 충돌이 없다. "점령/방문/수집" 등 격자 용어는 이 문서에 등장하지 않는다.

## 개요

로그인 시 발급하는 JWT 액세스 토큰(TTL `PT1H`)만으로는 만료 후 매번 재로그인해야 한다. MSG-135는 **2주 TTL 리프레시 토큰**을 Redis에 발급·저장해, 액세스 토큰이 만료돼도 재로그인 없이 `POST /auth/reissue`로 새 액세스 토큰을 받을 수 있게 한다.

토큰 탈취 위험을 줄이기 위해 **로테이션(재발급마다 새 리프레시 발급 + 직전 것 즉시 무효화)** 과 **재사용 감지(이미 회전된 리프레시가 다시 들어오면 탈취로 간주, 해당 디바이스 토큰 체인 폐기)** 를 함께 구현한다. 로그아웃 시 액세스 토큰을 **Redis 블랙리스트**에 올려 잔여 만료까지 차단한다(기존 인메모리 블랙리스트를 Redis 기반으로 이관).

```
[현재]  로그인 → access(PT1H)                                    만료 시 재로그인
[MSG-135] 로그인 → access(PT1H) + refresh(2주, Redis)
          access 만료 → POST /auth/reissue(refresh) → 새 access + 회전된 refresh
          로그아웃 → refresh 삭제 + access 블랙리스트
```

## 배경 · 목표

- **사용자/제품 관점**: 웹·앱에서 한 번 로그인하면 세션이 자연스럽게 이어져야 한다. 액세스 토큰이 1시간마다 만료돼 재로그인을 강요하면 이탈이 생긴다. 동시에, 토큰이 유출돼도 탈취를 감지하고 세션을 끊을 수 있어야 한다.
- **목표**:
  1. 로그인/소셜 로그인 시 **리프레시 토큰(2주)** 을 함께 발급하고 Redis에 저장한다.
  2. **디바이스별 독립 세션** — 유저가 웹+앱을 동시에 로그인해도 서로 영향 없이 각자 재발급/로그아웃된다.
  3. **로테이션 + 재사용 감지** 로 리프레시 토큰 탈취에 대응한다.
  4. **하이브리드 전송** — 웹은 `HttpOnly` 쿠키, 앱은 응답 body로 리프레시 토큰을 내려 각 클라이언트의 보안 특성에 맞춘다.
  5. 로그아웃 시 액세스 토큰을 **Redis 블랙리스트**로 즉시 무효화한다.

## 성공 기준 (검증 가능)

1. `POST /auth/login`·`POST /auth/oauth/{provider}` 성공 시, 액세스 토큰과 함께 리프레시 토큰이 발급되고 Redis `refresh:{userId}:{deviceId}`에 저장된다(TTL 2주).
2. 웹(`X-Client-Type: web`)은 리프레시 토큰이 `Set-Cookie`(`HttpOnly; Secure; SameSite=None; Path=/auth/reissue`)로, 앱(`X-Client-Type: app`)은 응답 `body.refreshToken`으로 내려간다. 웹 응답 body의 `refreshToken`은 `null`.
3. `X-Device-Id` 헤더가 없으면 서버가 UUID를 생성하고, 응답 헤더 `X-Device-Id`로 그 값을 돌려준다.
4. `POST /auth/reissue`에 유효한 리프레시 토큰(웹=쿠키/앱=body)을 넣으면 **새 액세스 + 회전된 새 리프레시**가 발급되고, 직전 리프레시는 즉시 무효화된다.
5. **재사용 감지**: 이미 회전돼 무효인 리프레시 토큰으로 재발급을 시도하면 `REFRESH_TOKEN_REUSE_DETECTED`(2433)로 거절되고, 해당 `(userId, deviceId)` 체인이 Redis에서 삭제된다(이후 그 디바이스의 어떤 리프레시도 재발급 불가 → 재로그인 필요).
6. 만료·존재하지 않는 리프레시 → `EXPIRED_REFRESH_TOKEN`(2432), 위조·형식오류·타입불일치 → `INVALID_REFRESH_TOKEN`(2431).
7. `POST /auth/logout` 시 액세스 토큰이 Redis 블랙리스트에 등록되어(TTL=잔여 만료) 이후 `parseAccessToken`에서 `INVALID_TOKEN`으로 거절되고, 해당 `(userId, deviceId)` 리프레시가 삭제된다.
8. **디바이스 격리**: 같은 유저의 서로 다른 deviceId 세션은 한쪽 재발급/로그아웃이 다른 쪽에 영향을 주지 않는다.
9. 블랙리스트 저장소가 Redis 기반으로 동작한다(멀티 인스턴스에서 공유 — 인메모리 한계 해소).
10. DB 스키마 변경 없음(Flyway 마이그레이션 불필요). 응답은 전부 `SuccessResponse.of(...)` / 실패는 `ApiException(AuthErrorCode.*)`. 전체 테스트 green.

**하는 것**
- `POST /auth/reissue` 신설(로테이션 + 재사용 감지).

## API 명세

전송 분기 헤더:
- `X-Client-Type`: `web` | `app` (기본 `web`). 리프레시 토큰을 쿠키로 줄지 body로 줄지 결정.
- `X-Device-Id`: 디바이스 식별자(클라이언트 보관). 없으면 서버가 UUID 생성 → 응답 헤더 `X-Device-Id`로 반환.

### 1) `POST /auth/login` (변경)

- 요청: `LoginRequestDto{email, password}` (불변) + 헤더 `X-Client-Type`, `X-Device-Id`(선택).
- 처리: 기존 인증 → 액세스 발급 + 리프레시 발급/저장.
- 응답 200 `body` = `LoginResponseDto{accessToken, refreshToken}`:
  - `X-Client-Type: app` → `refreshToken` 채움, 쿠키 없음.
  - `X-Client-Type: web` → `refreshToken=null`, `Set-Cookie: refreshToken=...; HttpOnly; Secure; SameSite=None; Path=/auth/reissue; Max-Age=1209600`.
  - 응답 헤더 `X-Device-Id`(요청 값 에코 또는 서버 생성 UUID).

### 2) `POST /auth/oauth/{provider}` (변경)

- login과 동일 패턴. 요청 body `OidcLoginRequestDto{idToken}`(불변) + 동일 헤더/쿠키/body 처리.

### 3) `POST /auth/reissue` (신설)

- **permitAll** (액세스 토큰이 만료된 상태에서 호출되므로 인증 불필요; 리프레시 토큰 자체가 자격 증명).
- 요청:
  - 헤더 `X-Client-Type`(전송 분기).
  - 리프레시 토큰 출처: **쿠키(`refreshToken`)에 있으면 쿠키에서, 없으면 body에서** 읽는다.
  - body(앱): `ReissueRequestDto{refreshToken}` (`refreshToken`은 선택 — 웹은 쿠키로 오므로 비어 있을 수 있음).
- 처리: 로테이션 + 재사용 감지(아래 §도메인 로직).
- 응답 200 `body` = `ReissueResponseDto{accessToken, refreshToken}`:
  - `web` → `refreshToken=null` + 회전된 리프레시를 `Set-Cookie`(위와 동일 속성)로 재설정.
  - `app` → `refreshToken`에 회전된 리프레시.
- 에러:

| 조건 | 코드 |
|---|---|
| 쿠키로 리프레시가 왔는데 `X-Client-Type` 헤더 없음 | `MISSING_CLIENT_TYPE_HEADER` (2434, 400) — MSG-389에서 추가. 아래 CSRF 노트의 방어가 이 검증에 걸려 있다 |
| 쿠키·body 모두 리프레시 없음 | `INVALID_REFRESH_TOKEN` (2431) |
| 서명 위조·형식 오류·타입(`typ`) 불일치 | `INVALID_REFRESH_TOKEN` (2431) |
| JWT `exp` 만료 · Redis에 해당 키 없음(로그아웃/TTL만료/체인폐기) | `EXPIRED_REFRESH_TOKEN` (2432) |
| Redis 저장 jti ≠ 제시된 jti(회전된 옛 토큰 재사용) | `REFRESH_TOKEN_REUSE_DETECTED` (2433) → 체인 삭제 |

**성공 응답 예시(app)**
```json
{
  "developCode": 200,
  "httpStatus": "OK",
  "message": "성공",
  "body": { "accessToken": "eyJhbGciOiJIUzI1NiJ9...", "refreshToken": "eyJhbGciOiJIUzI1NiJ9..." }
}
```

### 4) `POST /auth/logout` (변경)

- 인증 필요(유효 액세스 토큰). 헤더 `Authorization: Bearer {access}`, `X-Device-Id`(웹 쿠키는 `Path=/auth/reissue`라 이 요청엔 실려오지 않으므로 헤더로 디바이스 식별).
- 처리:
  1. 액세스 토큰 블랙리스트 등록(TTL=잔여 만료) — 기존 `invalidateAccessToken`.
  2. `userId`(SecurityContext의 `AuthPrincipal`) + `X-Device-Id` → `refresh:{userId}:{deviceId}` 삭제.
     - `X-Device-Id` 없으면 폴백: 해당 유저의 모든 리프레시 삭제(로그아웃-올) — §Open Q.
  3. 웹: 리프레시 쿠키 만료 `Set-Cookie: refreshToken=; Max-Age=0; Path=/auth/reissue`.
- 응답: `SuccessResponse<Void>` (기존 형식).

### CSRF / 크로스오리진 노트

- 리프레시 쿠키는 `SameSite=None`이라 크로스오리진 전송이 가능해야 한다(웹 FE ↔ API 도메인 분리). 이때 단순 폼 기반 CSRF는 **커스텀 헤더 `X-Client-Type` 요구**로 방어한다 — 브라우저가 커스텀 헤더가 붙은 크로스오리진 요청에 CORS preflight를 강제하므로, 서버 CORS 정책을 통과한 오리진만 요청 가능.
- prod는 HTTPS 필수(`Secure`), FE는 `withCredentials`(fetch `credentials:'include'`) 필요. `CorsConfig`가 이미 `allowCredentials(true)`. **로컬(http) 주의**: `SameSite=None; Secure`는 https에서만 브라우저가 저장/전송한다 → 로컬 웹 개발은 앱 모드(body) 사용 또는 로컬 https 필요(§Open Q).

## 도메인 로직

### 리프레시 토큰 형식 (결정 · 제안)

리프레시 토큰은 **HS256 서명 JWT**로 발급한다(액세스 토큰과 동일 JWT 인프라 재사용). 로테이션/재사용 감지가 성립하려면 재발급 시점(액세스 만료 상태)에 토큰만으로 `(userId, deviceId)`를 복원할 수 있어야 하므로 자가 기술(self-contained) JWT가 자연스럽다.

| claim | 값 |
|---|---|
| `sub` | userId |
| `did` | deviceId |
| `jti` | 발급마다 새 UUID (로테이션 식별자) |
| `typ` | `"refresh"` (액세스 토큰과 혼용 방지) |
| `iat` / `exp` | 발급시각 / +`refreshTokenTtl`(2주) |

- 서명 키: 액세스와 **분리된 `jwt.refresh-secret`** 권장(§Open Q). 분리하지 않더라도 `typ` claim 검증으로 액세스↔리프레시 상호 오용을 차단한다.
- **Redis 저장 값 = 현재 유효한 `jti`** (토큰 원문/비밀재료를 저장하지 않음, 크기 작음). 재사용 감지는 "저장 jti ≠ 제시 jti"로 판정.

### Redis 키 설계

| 용도 | 키 | 값 | TTL | 연산 |
|---|---|---|---|---|
| 리프레시 세션 | `refresh:{userId}:{deviceId}` | 현재 리프레시의 `jti`(UUID) | `refreshTokenTtl`(2주) | 로그인/재발급 시 `SET`, 로그아웃/재사용감지 시 `DEL` |
| 액세스 블랙리스트 | `blacklist:{sha256hex(accessToken)}` | `"1"` | 액세스 잔여 만료(`exp - now`) | 로그아웃 시 `SET`, `parseAccessToken`에서 `EXISTS` |

- 블랙리스트 키를 토큰 해시로 잡는 이유: 현재 액세스 토큰에 `jti`가 없고(실측), 원문 토큰을 키에 그대로 넣으면 길이·노출 문제 → SHA-256 해시로 고정 길이화. `InvalidatedTokenStore` 인터페이스(`invalidate(token, expiresAt)`/`isInvalidated(token)`)는 **그대로 유지**하고 Redis 구현체 내부에서 해싱한다.
- 로그아웃-올 폴백을 위해 유저의 디바이스 키를 열거해야 하면 `SCAN refresh:{userId}:*` 사용(KEYS 금지). 규모가 커지면 `refresh:index:{userId}` Set으로 역인덱스 관리 검토(§Open Q).

### 로테이션 + 재사용 감지 시퀀스 (`POST /auth/reissue`)

1. **리프레시 토큰 확보**: 쿠키(`refreshToken`) 있으면 쿠키, 없으면 body. 둘 다 없음 → `INVALID_REFRESH_TOKEN`(2431).
2. **JWT 검증**: 서명·형식·`typ="refresh"` 확인. 실패 → `INVALID_REFRESH_TOKEN`(2431). `exp` 만료 → `EXPIRED_REFRESH_TOKEN`(2432).
3. **claim 추출**: `userId(sub)`, `deviceId(did)`, `jti`.
4. **Redis 조회**: `GET refresh:{userId}:{deviceId}` → `storedJti`.
   - `null` → `EXPIRED_REFRESH_TOKEN`(2432) (로그아웃됨/TTL만료/체인폐기 → 재로그인).
   - `storedJti != jti` → **재사용 감지**: `DEL refresh:{userId}:{deviceId}`(체인 폐기) 후 `REFRESH_TOKEN_REUSE_DETECTED`(2433).
   - `storedJti == jti` → 정상, 다음 단계.
5. **유저 확인 + 액세스 발급**: `userRepository.findById(userId)`로 유저 존재/역할 확인(탈퇴/삭제된 유저는 재발급 불가). 존재하지 않으면 `INVALID_REFRESH_TOKEN`(2431). `tokenProvider.issueAccessToken(userId, role)`.
6. **로테이션**: 새 `jti'`·새 리프레시 JWT 발급 → `SET refresh:{userId}:{deviceId} = jti'` (TTL 2주로 재설정 = 슬라이딩 세션, §Open Q). 응답에 새 액세스 + 새 리프레시(웹=쿠키/앱=body), 헤더 `X-Device-Id` 에코.

> **동시성 주의**: 같은 리프레시로 짧은 시간에 두 번 재발급이 들어오면(네트워크 재시도 등) 4→6 사이 경합으로 정상 요청이 재사용으로 오판될 수 있다. 4~6을 원자적으로 처리(예: Lua 스크립트로 "compare jti and set new" `GETSET`/`CAS`)하는 것을 권장. 최소 구현은 단일 `GET`→`SET`이되, 재시도 오판 리스크를 §Open Q에 남긴다.

### 로그인/OIDC 발급 흐름

1. 기존 인증(비밀번호 검증 / ID Token 검증).
2. deviceId 결정: `X-Device-Id` 헤더, 없으면 `UUID.randomUUID()`.
3. 액세스 발급(기존) + 새 `jti`·리프레시 JWT 발급, `SET refresh:{userId}:{deviceId}=jti` (TTL 2주).
4. 전송 분기(`X-Client-Type`) + `X-Device-Id` 에코.

### 컴포넌트 배치 (3-layer 준수)

- `auth/jwt/RefreshTokenProvider`(interface) + `JwtRefreshTokenProvider`(impl): 리프레시 JWT 발급/검증(claim 파싱).
- `auth/jwt/RefreshTokenStore`(interface) + `RedisRefreshTokenStore`(impl): `save/findJti/delete`(userId, deviceId).
- `auth/jwt/RedisInvalidatedTokenStore`: 기존 `InvalidatedTokenStore` 구현(Redis).
- `auth/service/RefreshTokenService`: 로테이션·재사용 감지 오케스트레이션. `AuthService.login/logout`·`OidcLoginService.login`·`AuthController.reissue`가 호출.
- 쿠키 조립/해제는 컨트롤러(또는 `auth/support`의 소형 헬퍼)에서. 컨트롤러는 얇게(파싱·서비스 호출·응답/쿠키 변환만).

## 확정 결정 (구현 전 잠금 — 2026-07-18)

> 아래 8건은 착수 전 사용자와 확정했다. Fable 구현은 이 결정을 그대로 따르며 재논의하지 않는다.

1. **로컬 Redis** — 로컬 `docker-compose.yml`에 redis 서비스(`local-cache-server` → `fillmap-local-redis`, redis:7-alpine, 6379)가 **이미 추가·구동 중**(이 스펙 커밋에 포함). Fable은 compose를 추가로 건드리지 않는다. 앱은 `application-local.yml`의 `spring.data.redis {host: localhost, port: 6379}`로 접속(이미 추가됨). `application-dev.yml`은 `${REDIS_HOST:localhost}/${REDIS_PORT:6379}`, prod는 기존 활성 설정 사용.
2. **`InMemoryInvalidatedTokenStore` 처리** — **(a) `@Profile("test")`로 격리**, 리프레시 스토어도 동일하게 인메모리 페이크 제공 → 슬라이스/서비스 테스트를 Redis-free로 유지. Redis 구현체가 기본(non-test) 빈.
3. **리프레시 서명 키** — **액세스와 분리된 `jwt.refresh-secret`.** 값은 **64바이트(512bit) 무작위 문자열**(로컬: `application-local.yml`에 생성해 주입 완료, 운영: `JWT_REFRESH_SECRET` env). `typ=refresh` claim 검증도 병행.
4. **재발급 TTL** — **슬라이딩**(로테이션마다 TTL 2주 재설정). 절대 상한 미도입.
5. **로그아웃 `X-Device-Id`** — 있으면 해당 `(userId, deviceId)`만 삭제, **없으면 로그아웃-올 폴백**(`SCAN refresh:{userId}:*`, KEYS 금지).
6. **재발급 동시성** — **MVP는 단순 `GET`→`SET`.** 원자화(Lua/CAS)는 후속 하드닝(짧은 연속 재시도의 재사용 오판 리스크는 감수, 여기 명시).
7. **reissue DTO** — **별도 `ReissueRequestDto`/`ReissueResponseDto`** (의미 구분, `LoginResponseDto` 재사용 안 함).
8. **로컬 웹 쿠키** — `SameSite=None; Secure`는 https 전용이므로 **로컬 웹 개발은 앱 모드(body)로 진행**. 로컬 https는 도입하지 않음.

**남은 외부 의존(구현 차단 아님)**: FE 대면 계약(login 응답 refreshToken·`/auth/reissue`·`X-Client-Type`/`X-Device-Id`·쿠키 규약)은 프론트와 별도 합의 필요.
