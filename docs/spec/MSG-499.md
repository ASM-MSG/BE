# MSG-499: 행사 운영자 계정 발급 (공개 접수, 관리자 검토 발급, 직접 발급)

**Owner**: B (user와 auth 도메인. 계약 인터페이스 4종 어느 것도 건드리지 않는 단독 작업이고,
SecurityConfig 변경은 MSG-496이 만든 구조 위에 permitAll 한 줄을 더하는 것이라 공동 판정이 아니다)

> 요구사항 정본: `docs/prd/event-submission.md` (상태 검토됨, 2026-08-28 승인). 이 스펙은 그중
> FR-1(관리자 계정 발급), FR-2(초기 비밀번호 서버 발송과 재발송, 평문 비노출), FR-6(비로그인
> 공개 폼 접수와 관리자 요청 큐)의 "어떻게"만 다룬다. 선행 스펙 두 개를 전제한다.
> `docs/spec/MSG-496.md`(role ORG, catch-all이 USER와 ADMIN 한정이라 신규 공개 경로는
> SecurityConfig 명시 등록 필수)와 `docs/spec/MSG-497.md`(메일 발송 유틸 `global/mail`,
> mustChange 게이트. 둘 다 develop 머지 완료를 워크트리에서 실측했다).

## 개요

계정이 없는 행사 운영자가 비로그인 공개 폼으로 발급을 신청하면, 관리자가 요청 큐에서 검토해
계정을 만들고 초기 비밀번호를 공식 이메일로 보낸다. 공문으로 먼저 확인된 기관은 요청 없이
관리자가 직접 발급한다. MSG-497이 만든 메일 유틸과 mustChange 플래그를 소비하는 쪽이며,
`password_must_change`를 true로 세우는 첫 코드 경로가 이 티켓이다.

## 배경 · 목표

- 행사 등재 셀프서비스(PRD 목적)의 입구가 계정인데, 회원가입 기반 자체 가입은 비목표로 확정돼
  있다(MSG-484). 그래서 "신청 받고 관리자가 발급"하는 통로가 있어야 행사 운영자가 콘솔에
  진입할 수 있다.
- 목표: 계정이 없는 행사 운영자가 폼 하나로 발급을 신청하고, 관리자가 큐에서 검토해 몇 번의
  클릭으로 계정 발급과 초기 비밀번호 발송까지 끝내는 상태. 초기 비밀번호 평문이 메일 밖
  어디에도(응답, 로그, DB) 존재하지 않는 상태.

## 성공 기준

1. 토큰 없이 `POST /api/org-account-requests`를 부르면 요청이 대기 상태로 저장된다. 같은
   이메일의 대기 요청이 이미 있으면 행이 늘지 않고 내용이 갱신되며 응답은 같은 성공이다.
2. 관리자가 큐에서 대기, 발급됨, 반려 건수와 목록을 보고 상세를 열 수 있다.
3. 승인하면 `provider=LOCAL, role=ORG, password_must_change=true`인 계정이 생기고 초기
   비밀번호가 공식 이메일로 발송된다. 응답에는 발송 성공 여부만 실리고 평문은 어디에도 없다.
4. 메일 발송이 실패해도 계정 생성과 상태 전이는 유지되고, 응답의 발송 실패 표시를 본 관리자가
   재발송 API로 복구할 수 있다.
5. 반려는 사유가 필수이고 메일이 발송되지 않는다(수기 통보, 피그마 댓글 #108).
6. 직접 발급은 요청 행 없이 3번과 같은 결과를 만든다.
7. 관리자 계정 목록에서 각 ORG 계정이 사용 중인지 초기 로그인 전인지(mustChange 파생)
   구분된다.
8. 아래 테스트 시나리오가 전부 green이다.

## API 명세

전부 공통 응답 포맷(`SuccessResponse` / `ApiException`)을 따른다. 공개 접수 1개는 비로그인,
나머지 7개는 `/api/admin/**` matcher(MSG-195부터 존재)가 ADMIN으로 인가한다.

### 1. `POST /api/org-account-requests` (permitAll[^1], 비로그인)

[운영자 1-1] 공개 폼의 접수다(FR-6).

- 요청 `OrgAccountRequestCreateRequestDto`:

  | 필드 | 검증 |
  |------|------|
  | `orgName` (기관명) | `@NotBlank`, 최대 100자 |
  | `contactName` (담당자명) | `@NotBlank`, 2~20자. 승인 시 `users.nickname`에 그대로 들어가므로 MSG-497 프로필의 담당자 이름 제약과 같게 맞춘다 |
  | `contactPhone` (연락처) | `@NotBlank` + `@Pattern("^[0-9][0-9-]{7,18}[0-9]$")` (MSG-497 `OrgProfileUpdateRequestDto`와 동일 패턴) |
  | `email` (공식 이메일) | `@NotBlank` + `@Email`, 최대 255자 |
  | `eventName` (예정 행사명) | `@NotBlank`, 최대 200자 |
  | `content` (요청 내용) | `@NotBlank`, 최대 2000자 |

- 처리: native UPSERT 한 문장이다(PostgreSQL 전용 ON CONFLICT라 컨벤션의 native 허용 대상.
  MSG-497 `org_email_change_requests`의 선례를 형태 그대로 따른다). 같은 이메일의 PENDING
  행이 있으면 내용 필드와 마지막 접수 시각(updated_at)을 갱신하고, 없으면 새 행을 만든다
  (최초 접수 시각 created_at은 보존). 마지막 접수가 유효하다는 규칙이라 더블클릭 재제출과
  오타 정정 재접수가 한 행으로 수렴한다. 발급됨이나 반려 상태의 이메일은 부분 유니크
  인덱스[^2] 밖이라 새 대기 행을 만들 수 있다(반려 후 재신청 경로).

  ```sql
  INSERT INTO org_account_requests
      (org_name, contact_name, contact_phone, email, event_name, content, status,
       created_at, updated_at)
  VALUES (:orgName, :contactName, :contactPhone, :email, :eventName, :content, 'PENDING',
       :now, :now)
  ON CONFLICT (email) WHERE status = 'PENDING'
  DO UPDATE SET org_name = EXCLUDED.org_name, contact_name = EXCLUDED.contact_name,
      contact_phone = EXCLUDED.contact_phone, event_name = EXCLUDED.event_name,
      content = EXCLUDED.content, updated_at = EXCLUDED.updated_at
  ```

  - `:now`는 서비스가 주입받은 Clock의 UTC 시각이다(MSG-497 §6과 같은 방식).
  - `updated_at`은 관리자 심사의 낙관적 검증 토큰이기도 하다(API 4의 에코 대조).
- **신뢰 경계**: 접수 데이터는 검증되지 않은 자기 신고 값이다. 익명 호출자가 이메일만 알면
  타인의 PENDING 요청을 이 UPSERT로 덮어쓸 수 있는데, 이메일 검증이 없는 공개 폼에서는 어떤
  저장 규칙을 골라도 변조 벡터가 남는다. **신뢰 경계는 관리자 심사다.** 승인 전에 공문과 공식
  채널로 기관의 실재와 신청 사실을 확인하는 것이 전제이고, 접수 폼 값은 심사의 참고 재료이지
  발급 근거가 아니다. 기각한 대안 둘:
  - ON CONFLICT DO NOTHING(첫 접수 보존): 공격자가 선점한 쓰레기 행이 피해자의 진짜 신청을
    조용히 삼킨다. 응답이 동일 성공이라 피해자는 자기 신청이 저장되지 않은 것을 모른다.
    덮어쓰기와 마찬가지로 변조 벡터인데 본인 오타 정정 UX까지 잃는다.
  - 이메일 검증 링크(접수 시 확인 메일): 공개 엔드포인트에 발송 트리거를 여는 것이라 임의
    주소로의 메일 폭탄(SES 비용, 평판 훼손) 스팸 벡터가 새로 생긴다. 이번 범위에서 미도입.
- 응답: `SuccessResponse<Void>`. 신청 번호를 주지 않는다. 행사 신청(FR-10)과 달리 계정 발급
  요청에는 번호 요구가 없고, [운영자 1-2] 완료 화면은 접수 사실 안내뿐이다.
- 에러: 검증 위반 공통 400뿐. 새 실패 케이스가 없다.
- 스팸 방어의 범위: 필드 검증과 이메일당 대기 1행 수렴까지다. 이 API는 메일을 보내지 않아
  비용 지점(SES 발송)이 없고, 저장 결과는 관리자 큐 열람 전용이라 대량 기계 접수의 피해가
  DB 행 누적에 그친다. IP 쿨다운은 관측 후 필요해지면 붙인다(MSG-497 쿨다운 선례 재사용 가능).

### SecurityConfig 등록

```java
// 행사 운영자 계정 발급 요청(MSG-499): 계정이 없는 신청자의 폼이라 permitAll. POST 하나만 연다.
.requestMatchers(HttpMethod.POST, "/api/org-account-requests").permitAll()
```

- 삽입 위치는 기존 permitAll 열거 영역(`/api/auth/password/*` 옆, `/api/admin/**` 블록 앞)이다.
  permitAll이 catch-all보다 먼저 평가되는 기존 순서 규칙을 따른다.
- **`JwtAuthenticationFilter.PUBLIC_AUTH_PATHS`(필터 skip 목록)에는 넣지 않는다**(MSG-443
  교훈). 신청자는 계정이 없어 토큰 없이 호출하고, 토큰이 없으면 필터가 그냥 통과시키므로
  (doFilterInternal 실측: token null이면 체인 진행) skip 없이도 접수가 된다. 무효 토큰을
  동봉한 비정상 요청이 401이 되는 부작용은 정상 사용자에게 발생하지 않아 수용한다.
- 관리자 7종은 기존 `/api/admin/**` hasRole(ADMIN) matcher가 덮어 추가 등록이 없다.

### 2. `GET /api/admin/org-account-requests` (ADMIN)

발급 요청 큐다([관리자 1-1]). AdminReportController의 목록 형태(상태 필터, page, size)를
따르되 탭 건수를 함께 싣는다.

- 쿼리: `status`(PENDING, ISSUED, REJECTED, 대소문자 무관, 기본 PENDING), `page`(기본 0),
  `size`(기본 20, 1~100)
- 응답 `AdminOrgAccountRequestListResponseDto`:

  ```json
  {
    "pendingCount": 3, "issuedCount": 12, "rejectedCount": 2,
    "totalElements": 3, "page": 0, "size": 20,
    "requests": [
      { "id": 7, "orgName": "부산진구청", "contactName": "김담당", "email": "e@busanjin.go.kr",
        "eventName": "서면 겨울 축제", "status": "PENDING",
        "createdAt": "...", "updatedAt": "..." }
    ]
  }
  ```

  건수 3종은 status 무관 전체 집계다(탭 뱃지 재료). 정렬은 마지막 접수 최신순(updated_at DESC).
- 에러: 지원하지 않는 status는 400(1424), page 음수나 size 범위 밖은 400(1425).

### 3. `GET /api/admin/org-account-requests/{id}` (ADMIN)

- 응답 `AdminOrgAccountRequestDetailResponseDto`: 접수 필드 전체(orgName, contactName,
  contactPhone, email, eventName, content)에 status, rejectReason(반려 시), issuedUserId(발급
  시), createdAt, **updatedAt**(마지막 접수 시각, 승인과 반려 요청이 에코해야 하는 검토 기준
  시각), processedAt을 더한 것.
- 에러: 없는 요청은 404(1421). 관리자 전용 API라 존재 은닉이 필요 없다.

### 4. `POST /api/admin/org-account-requests/{id}/approve` (ADMIN)

계정 생성과 초기 비밀번호 발송이다(FR-6, FR-1, FR-2).

- 요청 `OrgAccountRequestApproveRequestDto`: `{ "updatedAt": "..." }` (`@NotNull`. 상세
  조회(API 3)가 내려준 updatedAt을 그대로 에코한다)
- 처리 순서가 계약이다:
  1. 요청을 비관적 락[^3]으로 조회(`@Lock(PESSIMISTIC_WRITE)` 파생 쿼리). 없으면 1421,
     상태가 PENDING이 아니면 1422. 동시 승인의 늦은 쪽이 여기서 1422로 수렴한다
     (AdminReportService의 이미 처리 409 선례와 같은 규칙).
  2. **낙관적 검증(검토 시점 대조)**: 락 획득 후 행의 updated_at이 에코된 updatedAt과 다르면
     1426(요청이 변경됨, 409)으로 끝낸다. 익명 UPSERT가 공개로 열려 있어서, 관리자가 상세에서
     검토한 내용과 승인 클릭 시점의 행이 다를 수 있다(조회와 승인 사이의 재접수 또는 변조).
     불일치면 발급하지 않고 재검토를 요구한다. 비교는 값 완전 일치다(서버가 내려준 값을
     그대로 되돌려 받으므로 반올림 여지가 없다).
  3. 이메일 중복 선확인(`existsByEmail`), 중복이면 1409(기존 `EMAIL_ALREADY_EXISTS` 재사용).
     선확인과 삽입 사이의 경합은 `saveAndFlush` + `DataIntegrityViolationException` catch로
     같은 1409에 수렴시킨다(AuthService.signup 선례 그대로).
  4. 초기 비밀번호 생성(아래 도메인 로직) 후 계정 생성: `User.createOrgUser(email, 해시,
     contactName, contactPhone, orgName)` (신설 팩토리, role ORG, provider LOCAL,
     passwordMustChange true). 요청 행은 ISSUED로 전이하고 issuedUserId와 processedAt을 채운다.
  5. 여기까지 한 트랜잭션으로 커밋. **메일 발송은 커밋 후다.** 발송을 트랜잭션 안에 두면 SES
     왕복이 DB 커넥션을 점유하고, 발송 성공 후 커밋이 실패하면 비밀번호는 나갔는데 계정이
     없는 역방향 구멍이 생긴다. 커밋 후 발송의 실패는 아래 6번이 흡수한다.
  6. `MailSender.send`를 try-catch로 감싼다(유틸은 실패를 예외로 올린다는 MSG-497 계약).
     성공이면 `emailSent: true`, 실패면 ERROR 로그 후 `emailSent: false`. 어느 쪽이든 HTTP는
     성공 응답이다. 계정은 이미 발급됐고 복구 수단이 재발송 API(아래 7번)로 따로 있으므로,
     발송 실패가 발급 자체를 실패로 뒤집을 이유가 없다.
- **크래시 창(수용, 문서화)**: 커밋과 발송 사이에 프로세스가 죽으면 요청은 ISSUED인데 메일은
  나가지 않았고 `emailSent` 신호도 남지 않는다. 발송 대기 행을 두는 아웃박스 워커는 도입하지
  않는다(관리자 소수 저빈도 흐름에 과설계이고, 복구 수단이 이미 재발송 API로 있다). 대신
  관리자 복구 수칙 한 줄이 계약이다: **approve 응답을 받지 못했으면 요청 상세를 재조회하고,
  ISSUED인데 발송 확신이 없으면 재발송 API를 쓴다. 재발송은 mustChange 계정에 항상
  안전하다(새 비밀번호로 교체 발송).**
- 응답 `OrgAccountIssueResponseDto`: `{ "userId": 42, "emailSent": true }`. 평문은 없다.
- 에러: 1421(없는 요청, 404), 1422(이미 처리, 409), 1426(검토 후 요청 변경, 409),
  1409(이미 계정이 있는 이메일, 409).
- **"발송 성공"의 의미는 SES[^4] 접수까지다** (2026-08-29 성민 코멘트 3의 확정 요구).
  `emailSent: true`는 SES가 MessageId를 돌려줬다는 뜻이고 배달 확인이 아니다. 오타 주소도 이
  시점엔 true이며 하드바운스[^5]는 몇 분 뒤에 온다. 배달 확인까지 동기로 기다리는 설계는 SES가
  제공하지 않아 불가능하고, 이 구멍의 복구 장치가 재발송 API와 재신청 경로다(아래 도메인 로직
  "오타 주소" 절).

### 5. `POST /api/admin/org-account-requests/{id}/reject` (ADMIN)

- 요청 `OrgAccountRequestRejectRequestDto`: `{ "reason": "...", "updatedAt": "..." }`
  (reason은 `@NotBlank` 최대 500자, 사유 필수는 FR-6과 시안 [관리자 1-1] 명문. updatedAt은
  `@NotNull`, approve와 같은 낙관적 검증 에코)
- 처리: 비관적 락 조회 후 PENDING 검증(아니면 1422), updated_at 에코 대조(다르면 1426,
  approve의 2단계와 동일. 검토한 신청과 다른 내용을 그 사유로 반려하는 어긋남을 막는다),
  REJECTED 전이, rejectReason과 processedAt 저장. **메일을 보내지 않는다.** 반려 통보는
  당분간 수기다(피그마 댓글 #108, PRD FR-6). 상세 조회의 rejectReason은 관리자의 수기 통보
  재료다.
- 응답: `SuccessResponse<Void>`.
- 에러: 1421, 1422, 1426, 검증 위반 공통 400.

### 6. `POST /api/admin/organizations` (ADMIN)

공문으로 먼저 확인된 기관의 직접 발급이다([관리자 1] 화면, FR-1).

- 요청 `OrgAccountCreateRequestDto`: `orgName`(필수, 최대 100자), `contactName`(필수, 2~20자),
  `email`(필수, `@Email`, 최대 255자), `contactPhone`(선택, 값이 있으면 접수 폼과 같은 패턴.

- 처리: approve의 4~6단계와 동일하다(요청 행 관련 단계만 없다). 같은 발급 코어를 공유한다.
- **크래시 복구 수칙(직접 발급 전용)**: approve의 복구 수칙은 요청 행 재조회가 전제라 요청
  행이 없는 직접 발급에는 적용되지 않는다. 대신 이렇게 복구한다: **직접 발급 응답을 못
  받았으면 같은 요청을 재시도한다. 1409(이미 존재)가 오면 그 이메일로 계정이 존재한다는
  뜻일 뿐, ORG 발급이 성공했다는 증거가 아니다**(기존 카카오 USER 계정과의 충돌일 수 있고,
  그 경우 재발송도 재설정 안내도 무의미하다). 판정은 API 8의 email 검색 한 번이다(목록
  필터가 ORG·LOCAL을 보장하므로 관리자가 필드를 눈으로 대조할 필요가 없다):
  - **검색 결과가 있으면 발급 성공**(크래시 전에 커밋된 것)이다. 재발송 API를 쓰거나
    MSG-497의 이메일 재설정 흐름을 해당 기관에 안내한다(공식 이메일이 유효하므로 재설정
    링크가 도달하고, ORG 계정은 reset-request의 발송 대상이다).
  - **검색 결과가 없으면 발급 실패**(카카오 등 다른 계정이 1409를 낸 경우 포함)다. 애초 발급
    자체가 이메일 충돌로 불가능했던 것이므로 기관에 다른 공식 이메일을 요청한다.
- 응답: `OrgAccountIssueResponseDto` (approve와 동일).
- 에러: 1409(이미 계정이 있는 이메일, 409), 검증 위반 공통 400.

### 7. `POST /api/admin/organizations/{userId}/resend-password` (ADMIN)

FR-2의 "재발송"이다. 형태 확정(범위 명시 사항): **재발송은 재발급이다.** 평문을 저장하지
않으므로(FR-2) 보냈던 비밀번호를 다시 보낼 수 없고, 새 초기 비밀번호를 생성해 해시를 교체한
뒤 발송한다. 이전 초기 비밀번호는 그 즉시 무효가 된다. 이 무효화는 초기 비밀번호가 유출된
시나리오에서 의미가 있는 보안 계약이라, 아래 직렬화가 깨지면 수용이 아니라 결함이다.

- 요청 본문 없음.
- 대상 조건: 사용자가 존재하고(아니면 1404), `role=ORG`이고 `provider=LOCAL`이고
  `password_must_change=true`인 계정만(아니면 1423). mustChange가 false인 계정은 본인이 이미
  비밀번호를 바꾼 사용 중 계정이라, 관리자가 재발급하면 발급자가 다시 비밀번호를 아는 상태가
  되어 FR-21(행위자 특정)의 목적이 무너진다. 사용 중 계정의 분실 복구는 MSG-497의 이메일
  재설정 흐름이 이미 담당한다.
- 처리: **재발송 트랜잭션은 사용자 행을 비관적 락으로 잡는다**(`@Lock(PESSIMISTIC_WRITE)`
  파생 쿼리 또는 SELECT FOR UPDATE). 그리고 **락 안에서 mustChange를 재검사한다.** 락 없이
  선검사 후 교체하면, 사용자의 첫 비밀번호 변경(MSG-497 change)이 먼저 커밋한 뒤 늦게 커밋한
  재발송이 방금 정한 비밀번호를 무효화하고 mustChange를 true로 되돌리는 상태 훼손이 생긴다.
  락 안 재검사면 본인 변경이 먼저 커밋했을 때 재검사가 false를 보고 1423으로 끝난다(발송
  없음). 재검사 통과 후 해시 교체(mustChange는 true 유지), 커밋 후 발송, 실패 격리는
  approve와 동일.
- **직렬화는 그 행을 쓰는 모든 경로가 락을 잡아야 성립한다.** 실코드 확인 결과
  `PasswordService.changePassword`와 `PasswordService.resetPassword`(MSG-497 둘 다)는 락 없는
  findById로 읽고 커밋하므로, 재발송 쪽만 락을 잡으면 두 경로 각각에서 재발송이 중간에
  커밋해도 낡은 엔티티가 마지막에 덮어쓴다(lost update[^7]). 그래서 **이 티켓이 비밀번호를
  쓰는 세 경로 전부(재발송, 본인 변경 change, 재설정 reset)를 같은 PESSIMISTIC_WRITE 락 조회
  리포지토리 메서드로 통일한다**(changePassword와 resetPassword의 사용자 조회 교체).
  - change는 락 획득 후 현재 비밀번호 검증부터 수행하므로, 재발송이 먼저 커밋했으면 사용자의
    변경 요청은 이전 초기 비밀번호가 더 이상 맞지 않아 CURRENT_PASSWORD_MISMATCH(2442)로
    안전하게 실패한다(새 메일의 비밀번호로 다시 로그인해 변경하면 된다).
  - reset은 토큰 소비가 선행돼 재발송과의 인터리빙에서도 늦게 읽은 쪽이 락 대기 후 최신
    상태를 보고 판정된다. 어느 순서든 마지막 커밋의 해시와 mustChange 값이 단일 진실이 되고,
    중간 상태를 낡은 스냅숏이 덮는 경우가 없다.
  - MSG-497 코드 수정 최소화 원칙과의 관계: 이 경합은 499가 신설하는 재발송이 만드는 것이라
    대응 락도 499 몫이다.
- 응답: `{ "emailSent": true }` (`OrgAccountResendResponseDto`).
- 에러: 1404(없는 사용자, 404), 1423(재발송 대상 아님, 409).
- 동시 재발송끼리도 위 행 락으로 직렬화된다: 두 번 눌리면 순차 실행돼 마지막 발송분의
  비밀번호만 유효하다. 수신자가 여러 통 중 어느 것이 유효한지는 메일 본문의 발급 시각으로
  가린다(아래 발급 메일 절).

### 8. `GET /api/admin/organizations` (ADMIN)

[관리자 1] "최근 발급 목록"과 재발송 버튼의 대상 식별 재료다. PRD 서버 재료 목록에 없던
추가분이었는데 **2026-08-29 사용자 승인으로 확정됐다**(근거는 셋: FR-2의 재발송은 대상을 고를
목록 없이는 화면이 성립하지 않고, [관리자 1] 시안에 최근 발급 목록이 실측되며, 직접 발급의
크래시 복구(API 6)가 이메일로 계정을 확인하는 수단을 요구한다. `GET /api/org/events`를
스펙에서 더한 MSG-501 선례와 같은 유형). PRD 서버 재료 목록에 23번째로 반영 완료(이 브랜치,
미해결 질문 1의 결정 기록 참조).

- **목록 대상은 `role=ORG AND provider=LOCAL` 필터다.** 재발송 대상 식별과 직접 발급 복구
  확인이 목적이라 이 티켓의 발급 경로가 만드는 계정 형태로 좁힌다. role이 ORG인데 provider가
  LOCAL이 아닌 계정이 존재하더라도 이 목록과 복구 판정에서 제외된다(그런 계정은 이 티켓의
  발급과 재발송 대상이 아니므로 fail-safe하게 안 보이는 쪽이 맞다).
- 쿼리: `page`(기본 0), `size`(기본 20, 1~100), `email`(선택, 완전 일치 필터. 직접 발급
  크래시 복구의 확인 수단으로, 결과 유무가 곧 발급 성공 여부다)
- 응답 `AdminOrgAccountListResponseDto`: 발급 최신순(created_at DESC)으로
  `{ "totalElements", "page", "size", "accounts": [ { "userId", "orgName", "contactName",
  "email", "contactPhone", "provider", "mustChange", "createdAt" } ] }`
  - `provider`는 목록 필터가 LOCAL을 보장한다는 사실을 응답에서도 확인할 수 있게 싣는다
    (복구 판정 계약의 재료).
  - 화면의 "사용 중 / 초기 로그인 전" 라벨은 `mustChange` boolean의 파생이다(false가 사용 중).
    범위 명시 사항의 판단 결과: **전용 상태 컬럼은 만들지 않는다.** 계정 상태는 mustChange
    하나로 완전히 갈리고(true로 세우는 곳은 발급뿐, false로 내리는 곳은 본인 변경뿐), 파생
    가능한 값을 컬럼으로 복제하면 두 저장 축의 정합 관리만 늘어난다.
- 에러: 1425(페이지 범위, 400).

## 도메인 로직

### 초기 비밀번호 생성

- `SecureRandom`으로 16자를 만든다. 알파벳은 영문 대문자, 소문자, 숫자에서 헷갈리는 글자
  (`0/O/1/l/I`)를 뺀 집합이고, 영문과 숫자가 각 1자 이상 포함되게 생성한다(로그인에는 정책
  검증이 없지만, 사용자가 보는 첫 비밀번호가 서비스 비밀번호 정책과 어긋난 모양이면 혼란만
  준다). `User.friendCode`의 SecureRandom 선례를 따른다.
- 평문의 생애: 생성 직후 bcrypt 해시로 저장하고, 커밋 후 메일 본문에 한 번 실은 뒤 버린다.
  응답, 서버 로그, DB 어디에도 남기지 않는다(FR-2, MSG-497의 토큰 원문 로그 금지와 같은
  원칙). 발송 실패의 ERROR 로그에도 수신 주소와 예외만 남기고 평문을 섞지 않는다. 로컬과
  dev의 LoggingMailSender가 본문을 로그로 찍는 것은 MSG-497이 확정한 유일한 예외이고
  prod에서는 그 빈이 뜰 수 없다. 이 예외를 마스킹으로 좁히지 않는 이유: 실발송 없는 환경에서
  수동 E2E(로그의 비밀번호로 로그인)를 성립시키는 장치라서, 마스킹하면 검증 수단 자체가
  없어진다(MSG-497 선례 그대로).
- **로그 비노출은 테스트로 잡는다**: 응답 단언만으로는 서버 로그 경로가 검증되지 않으므로,
  approve 서비스 테스트에서 스텁 MailSender로 발송을 대체하고 로그 캡처(ListAppender 류)로
  생성된 평문이 서비스 계층 로그 어디에도 없음을 단언한다. 발송 실패 경로의 ERROR 로그도 같은
  캡처로 평문 미포함을 단언한다(아래 테스트 시나리오).

### 발급 메일

- 발신은 `fillmap.mail.from`(contact@fillmap.kr, MSG-497 프로퍼티 재사용), 제목과 본문은
  한국어 평문이다. 본문에 로그인 주소(fillmap.kr), 아이디(공식 이메일), 초기 비밀번호,
  발급 시각, 그리고 "24시간 안에 비밀번호를 변경해 주세요" 안내를 싣는다.
- **발급 시각은 락 안에서 찍는 트랜잭션 시각이다**(발급 코어가 해시를 교체하는 그 트랜잭션
  안에서 주입 Clock으로 확정). 발급과 재발송이 전부 users 행 락으로 직렬화되므로(API 7)
  시각 순서가 곧 커밋 순서다. 메일 도착 순서는 역전될 수 있으나 본문의 발급 시각이 가장 늦은
  메일의 비밀번호가 유효하다. 세대 번호 컬럼은 도입하지 않는다(직렬화 후에는 시각으로 충분).
- **24시간은 안내이지 강제가 아니다.** 티켓 범위 명문("발송 후 24시간 내 변경 안내, 첫 로그인
  강제 변경은 mustChange가 담당")대로, 시간과 무관하게 변경 전 콘솔을 막는 것은 MSG-497
  게이트가 이미 하고 있다. 초기 비밀번호에 만료 시각을 붙이는 설계(발급 시각 저장, 로그인 시
  비교, 만료 시 재발송 유도)는 게이트가 이미 막는 위험을 이중으로 막는 비용이라 두지 않는다.

### 발급 코어의 공유

approve(4번)와 직접 발급(6번)과 재발송(7번)이 "비밀번호 생성, 해시 저장, 커밋 후 발송, 실패
격리"를 공유한다. 한 서비스 메서드로 모으고 호출부는 요청 행 전이 여부만 다르다. 커밋 후
발송의 구현(트랜잭션 메서드 분리)은 구현 몫이되, "발송이 트랜잭션 밖"이라는 경계 자체는 이
스펙의 계약이다.

### 오타 주소: 계정은 생겼는데 비밀번호를 아무도 모르는 상태

성민 코멘트 3이 지적한 구멍이다. 신청자가 이메일을 잘못 적었으면 `emailSent: true`여도 메일이
하드바운스로 사라지고, 평문 비노출 설계라 그 비밀번호는 아무도 모른다. 복구는 두 갈래다.

1. 주소가 맞는데 발송이 유실된 경우(SES 일시 장애, 메일함 실수 삭제): 재발송 API가 복구한다.
2. 주소 자체가 오타인 경우: 재발송해도 같은 오타로 간다. 신청자는 메일이 안 오면 올바른
   이메일로 다시 신청하고(발급됨 상태는 부분 유니크 밖이라 새 대기 행이 생긴다), 관리자가 새
   요청을 승인하면 새 계정이 발급된다. 오타 이메일로 남은 유령 계정의 정리 수단(삭제 또는
   이메일 정정)은 이 티켓에 없다. 미해결 질문 2(후속 티켓 이월 확정).

### SES 실발송 전환: 코드 변경 없음, 런북이다 (성민 코멘트 1)

MSG-497 유틸은 이미 실발송 코드(SesMailSender)를 갖고 있고 `fillmap.mail.enabled` 프로퍼티로
로그 모드와 갈린다. 프로덕션 액세스가 승인됐으므로(2026-08-29, 인프라 내역 MSG-504) 전환은
설정 작업이고, 이 스펙은 런북으로 다룬다(스펙에서 판단하라는 지시 사항의 판단 결과).

**성민 코멘트의 "SMTP 자격증명(IAM 사용자 생성, SES SMTP 비밀번호)"은 불필요하다.** 검증
가능한 사실은 코드가 이긴다: 유틸은 SMTP가 아니라 SES v2 SDK(`SesV2Client`)이고 자격 증명은
DefaultCredentialsProvider 체인(dev와 prod는 EC2 인스턴스 role)이다(MSG-497 스펙 메일 유틸 절,
코드 실측 일치). SMTP 자격증명은 spring-boot-starter-mail 경로였다면 필요했을 물건인데 그
안은 MSG-497에서 기각됐다. 이 어긋남은 성민에게 회신할 사항이다.

전환 런북(dev부터, 완료 후 prod):

1. EC2 인스턴스 role에 `ses:SendEmail` 권한 추가 (MSG-497 스펙의 운영 선행 작업 목록 그대로)
2. 환경변수 `fillmap.mail.enabled=true` 주입 (prod는 `fillmap.mail.reset-link-base-url`도 함께,
   미주입 시 기동 실패는 MSG-497의 의도된 fail-fast)
3. SES 계정 수준 억제 목록[^6]이 BOUNCE와 COMPLAINT 양쪽에 활성인지 확인
   (`aws sesv2 get-account`, 신규 계정 기본 활성이지만 실측으로 못 박는다)
4. dev에서 발급 흐름 수동 E2E: 접수, 승인, 실메일 수신, 초기 비밀번호 로그인, mustChange
   게이트 403, 변경 후 콘솔 통과 (MSG-496과 497 런북의 연장)

### 반송과 불만 처리(SNS 연동): 이 티켓 범위 밖, 별도 티켓 (성민 코멘트 2)

프로덕션 신청서에 약속한 조건이라 선택이 아니라는 점은 그대로 인정하고, **이 티켓이 아니라
별도 티켓으로 가른다.** 근거 셋:

1. **약속의 강제 장치는 플랫폼에 이미 있다.** SES 계정 수준 억제 목록이 하드바운스와 불만
   주소를 자동 등재해 이후 발송을 계정 전체에서 차단한다(위 런북 3이 활성을 확인한다). "즉시
   억제, 발송 중단"의 실행부는 서버 코드 없이 성립한다.
2. SNS 수신은 구독 확인, 서명 검증, 억제 사유 저장까지 붙는 독립 수신 인프라라 발급 흐름과
   관심사가 다르고, 이 티켓에 싣으면 커밋 단위가 섞인다.
3. SNS 연동이 이 티켓에 더하는 실익은 "관리자가 반송을 알아채는 관측"인데, 당장의 발송량이
   관리자 발급 소수 통이라 큐 화면에서 신청자 무응답으로도 드러난다.

별도 티켓의 범위 예고: SNS 토픽 구독 수신 엔드포인트, Bounce와 Complaint 이벤트 기록, 발급
메일 반송 시 관리자에게 드러내는 표식. 이월은 2026-08-29 확정됐고 MSG-511로 발행됐다
(미해결 질문 3의 결정 기록 참조).

### 엔티티

- 신설 `user/entity/OrgAccountRequest` (+ enum `OrgAccountRequestStatus`: PENDING, ISSUED,
  REJECTED). 연관관계 없이 issuedUserId를 Long으로 보관한다. 쓰기가 native UPSERT와 상태
  전이뿐이고 조인 조회가 없어 `@ManyToOne`을 달 근거(크기 상한, 조회 수요)가 아직 없다

  LocalDateTime processedAt)`, `reject(String reason, LocalDateTime processedAt)` 두 개를
  두고 더티 체킹으로 UPDATE한다.
- `User`에 팩토리 `createOrgUser(String email, String encodedPassword, String contactName,
  String contactPhone, String orgName)` 신설: provider LOCAL, role ORG, passwordMustChange
  true, nickname에 담당자명(MSG-497이 세운 "ORG의 nickname이 곧 담당자 이름" 전제),
  contactPhone과 orgName 반영. 재발급용 상태 전이
  `resetInitialPassword(String newPasswordHash)`(해시 교체, mustChange true 유지)도 더한다.
  기존 `changePassword`는 mustChange를 내리므로 재발송에 못 쓴다.

## 데이터 모델

Flyway 1건. **번호는 V47이다.** 워크트리 실측 최신이 `V46__org_account_security.sql`(MSG-497
머지분)이라 그다음을 배정했다. PRD 변경 파일 표의 "V46 = 신청 테이블"은 표 작성 시점 실측일
뿐이고 PRD 스스로 구현 시점 재실측을 단서로 달아 뒀다. 구현 시점에 develop에 새 번호가 먼저
붙었으면 같은 규칙으로 민다.

`V47__org_account_requests.sql`:

```sql
-- 행사 운영자 계정 발급 (MSG-499).
-- 1) 기관명. 발급 계정(role ORG)에만 값이 있고 그 외 역할은 항상 NULL 이다 (contact_phone 과 같은 방식).
ALTER TABLE users ADD COLUMN org_name VARCHAR(100);

-- 2) 계정 발급 요청 큐 (FR-6). 비로그인 공개 폼이 쓰고 관리자가 검토한다.
--    created_at 은 최초 접수 시각(보존), updated_at 은 마지막 접수 시각이며 관리자 심사의
--    낙관적 검증 토큰이다 (approve/reject 가 에코 대조).
CREATE TABLE org_account_requests (
    id BIGSERIAL PRIMARY KEY,
    org_name VARCHAR(100) NOT NULL,
    contact_name VARCHAR(20) NOT NULL,
    contact_phone VARCHAR(20) NOT NULL,
    email VARCHAR(255) NOT NULL,
    event_name VARCHAR(200) NOT NULL,
    content TEXT NOT NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'PENDING',
    reject_reason VARCHAR(500),
    issued_user_id BIGINT REFERENCES users (id),
    created_at TIMESTAMP NOT NULL,
    updated_at TIMESTAMP NOT NULL,
    processed_at TIMESTAMP,
    CONSTRAINT chk_org_account_requests_status
        CHECK (status IN ('PENDING', 'ISSUED', 'REJECTED'))
);
-- 이메일당 대기 요청은 한 건. 재접수는 그 행의 갱신이다 (접수 UPSERT 의 ON CONFLICT 대상).
CREATE UNIQUE INDEX uq_org_account_requests_pending
    ON org_account_requests (email) WHERE status = 'PENDING';
-- 큐 목록(상태 필터 + 마지막 접수 최신순)용.
CREATE INDEX idx_org_account_requests_status_updated
    ON org_account_requests (status, updated_at DESC);
```

- `issued_user_id`의 ON DELETE를 지정하지 않는 이유: 사용자 삭제 흐름이 이 테이블을 참조할 일이
  생기면 그때 정하면 되고, 지금 사용자 하드 삭제 경로 자체가 없다.
- 기관명을 users 컬럼으로 두는 이유(별도 organizations 테이블 대신): 기관 하나에 계정 여러
  개를 다는 요구가 없고(FR-1은 계정 단위 발급), 시안의 표시 재료도 계정당 기관명 하나다.
  다계정 요구가 생기면 그때 테이블로 승격한다.

### 런타임 동작

**데이터 저장 위치** (`V48__org_account_requests.sql`)

- `org_account_requests` — `id BIGSERIAL PK`, `org_name(100)`, `contact_name(20)`, `contact_phone(20)`,
  `email(255)`, `event_name(200)`, `content TEXT`, `status(20) DEFAULT 'PENDING'` +
  `chk_org_account_requests_status CHECK (status IN ('PENDING','ISSUED','REJECTED'))`, `reject_reason(500)`,
  `issued_user_id BIGINT REFERENCES users(id)`(ON DELETE 미지정), `created_at`·`updated_at` NOT NULL, `processed_at`.
  인덱스 둘: `uq_org_account_requests_pending (email) WHERE status = 'PENDING'`(부분 유니크 — 접수 UPSERT의
  ON CONFLICT 대상이자 "이메일당 대기 1행"의 강제자), `idx_org_account_requests_status_updated (status, updated_at DESC)`(큐 목록).
- `users` — 컬럼 하나 추가: `org_name VARCHAR(100)`(ORG 계정만 값이 있고 그 외 역할은 항상 NULL).
  기존 `password_must_change`(V46)를 **true로 세우는 첫 코드 경로**가 이 티켓의 `User.createOrgUser`다.
- 비밀번호 평문은 어디에도 저장하지 않는다. bcrypt 해시가 `users.password_hash`에 들어가고, 평문은 메일 본문에
  한 번 실린 뒤 버려진다(운반체 `IssuedInitialPassword`는 `toString`을 덮어 평문을 지운다).

**실행 쿼리** (Hibernate `show-sql` 실측, 2026-08-29)

- 접수 UPSERT (`OrgAccountRequestRepository.upsertPending`, native 원문):

  ```sql
  INSERT INTO org_account_requests
      (org_name, contact_name, contact_phone, email, event_name, content, status, created_at, updated_at)
  VALUES (:orgName, :contactName, :contactPhone, :email, :eventName, :content, 'PENDING', :now, :now)
  ON CONFLICT (email) WHERE status = 'PENDING'
  DO UPDATE SET org_name = EXCLUDED.org_name, contact_name = EXCLUDED.contact_name,
      contact_phone = EXCLUDED.contact_phone, event_name = EXCLUDED.event_name,
      content = EXCLUDED.content, updated_at = EXCLUDED.updated_at
  ```

  `created_at`이 갱신 목록에 없는 것이 "최초 접수 시각 보존"의 구현이고, 충돌 대상이 부분 인덱스라 추론 절에
  같은 WHERE를 적는다. 발급됨·반려 행은 인덱스 밖이라 같은 이메일로 새 대기 행이 생긴다(재신청 경로).
- 심사 잠금 조회 (`OrgAccountRequestRepository.findWithLockById`) — **생성 SQL 실측**:
  `select ... from org_account_requests oar1_0 where oar1_0.id=? for no key update of oar1_0`.
  Hibernate 6 PostgreSQL 방언이 `PESSIMISTIC_WRITE`를 `FOR UPDATE`가 아니라 **`FOR NO KEY UPDATE`**로 낸다.
  두 `FOR NO KEY UPDATE`는 서로 충돌하므로 동시 승인 직렬화는 그대로 성립하고, 기존 `findIdForKeyShare`
  (`FOR KEY SHARE`, MSG-417)와는 충돌하지 않아 그 경로를 새로 막지 않는다.
- 비밀번호 세 경로 공용 잠금 (`UserRepository.findWithLockById`) — 실측
  `select ... from users u1_0 where u1_0.id=? for no key update of u1_0`. 재발송·`changePassword`·`resetPassword`가
  전부 이 한 문장을 거친다.
- 큐 목록 (`findAllByStatusOrderByUpdatedAtDesc`) — 실측
  `select ... from org_account_requests oar1_0 where oar1_0.status=? order by oar1_0.updated_at desc fetch first ? rows only`
  (`idx_org_account_requests_status_updated`가 받는 형태). 탭 건수는
  `select count(oar1_0.id) from org_account_requests oar1_0 where oar1_0.status=?` 세 번(상태별, 관리자 저빈도 흐름).
- 계정 목록 (`findAllByRoleAndProviderOrderByCreatedAtDesc` / `...AndEmail...`) — 실측
  `select ... from users u1_0 where u1_0.role=? and u1_0.provider=? [and u1_0.email=?] order by u1_0.created_at desc fetch first ? rows only`.
- 이메일 중복 선확인 (`existsByEmail`) — 실측 `select u1_0.id from users u1_0 where u1_0.email=? fetch first ? rows only`.

- **커밋 후 발송 실패는 핸들러에 닿지 않는다.** `MailSender.send`의 예외를 `sendInitialPassword`의 try-catch가
  삼키고 ERROR 로그(메시지 + userId + 수신 주소 + **예외 타입 문자열**, 예외 객체는 넘기지 않음)를 남긴 뒤
  `emailSent:false`를 돌려준다. HTTP는 200이고 계정과 요청 상태는 커밋된 그대로다.

**빈 동작**

- `OrgAccountRequestService`·`OrgAccountIssueService` 둘 다 `TransactionTemplate`을 주입받아 **트랜잭션 경계를
  코드로 연다**(`@Transactional` 프록시 아님). 발송을 커밋 뒤로 밀려면 경계의 끝이 눈에 보여야 하고, 같은 빈 안의
  `@Transactional` 메서드 자기 호출은 프록시를 안 타 경계가 서지 않기 때문이다(`PasswordService` 선례).
  승인은 `transactionTemplate.execute { 잠금 → 대조 → 계정 생성 → 상태 전이 }` 반환 뒤에 `sendInitialPassword`를
  부르는 형태라, 발송 시점에 트랜잭션이 없다는 것이 테스트에서 직접 단언된다.
- 조회 전용 메서드(`getRequests`·`getRequest`·`getAccounts`)와 접수(`create`)만 `@Transactional`을 쓴다.
- 잠금 대기 지점은 둘이다: 심사의 `org_account_requests` 행(동시 승인·반려), 재발송·변경·재설정의 `users` 행.
  둘 다 `FOR NO KEY UPDATE`라 늦은 트랜잭션이 앞선 커밋까지 대기한 뒤 **바뀐 상태를 읽고** 판정한다
  (동시 승인의 늦은 쪽 1422, 본인 변경이 앞선 재발송 1423).
- 두 서비스 모두 프로덕션 생성자에서 `Clock.systemUTC()`를 고정 주입한다(인자 없는 `now()` 금지 컨벤션).
  발급 시각은 잠금 안에서 이 Clock으로 찍히고, 메일 본문에서만 KST로 표기된다(마이크로초까지).
