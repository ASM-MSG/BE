# MSG-178: FCM 푸시 토큰 등록/해제 API

**Owner**: B

> PRD(정본): `docs/prd/MSG-178-prd.md` — 알림 묶음 4티켓 공유 PRD, 이 스펙은 **FR-1(등록 UPSERT)·FR-2(해제 멱등)** 만 다룬다.
> 발송 파이프라인(outbox·Kafka·FCM 호출·무효 토큰 정리)은 MSG-179, 수신 설정은 MSG-180, 트리거는 MSG-181.
> **firebase-admin 의존성 이 티켓에서 추가하지 않는다** — 178은 DB CRUD뿐이라 불필요.

## 개요

디바이스별 FCM 푸시 토큰의 등록/갱신/해제 API. V1 `push_tokens` 테이블(스키마 무변경)을 처음 소비하는
코드로, `com.msg.fillmap.notification` 패키지를 신설한다. Owner 판정: user FK 종속 데이터·콘텐츠/인증 축 —
PRD 변경 파일 목록과 동일하게 **B**.

## 배경 · 목표

- 알림 파이프라인(MSG-179~181)이 발송하려면 "이 사용자의 디바이스 토큰"이 DB에 있어야 한다. 그 수집 창구가 이 API다.
- 목표: 재로그인·계정 전환·로그아웃이 반복돼도 토큰 행이 항상 "현재 이 디바이스를 쓰는 계정"을 가리키게 한다.

## 성공 기준

1. 같은 fcm_token 재등록이 **충돌 없이** user_id·platform·app_version·last_used_at을 갱신한다 (FR-1).
   특히 같은 브라우저에서 다른 계정으로 재로그인하면 행의 user_id가 새 계정으로 넘어간다.
2. 없는 토큰 해제도 200 성공 — 멱등 (FR-2). 재호출·중복 호출 전부 동일 결과.
3. 계정 삭제 시 토큰 정리는 코드 0줄 — `user_id FK ON DELETE CASCADE`(V1 실측)가 처리.
4. 비로그인 호출은 401 (developCode 2403 — `CustomAuthenticationEntryPoint` 실측).

## API 명세

### 1. 토큰 등록/갱신 — `POST /api/notifications/tokens`

인증 필수 (SecurityConfig `anyRequest().authenticated()` — 신규 permitAll 없음, SecurityConfig 무변경).
userId는 `@AuthenticationPrincipal AuthPrincipal principal` → `principal.userId()` (BadgeController 실측 패턴,
`@Parameter(hidden = true)` 포함).

**Request** — `PushTokenRequestDto` (record):

| 필드 | 타입 | 검증 | 비고 |
|---|---|---|---|
| `fcmToken` | String | `@NotBlank` `@Size(max = 512)` | push_tokens PK (VARCHAR(512)) |
| `platform` | String | `@NotBlank` | 서비스에서 대소문자 무시 파싱 → `PushPlatform` (IOS/ANDROID/WEB) |
| `appVersion` | String | `@Size(max = 20)` | 선택 (nullable) |

platform을 enum 타입이 아니라 String으로 받는 이유: 잘못된 값을 Jackson 파싱 400(무의미한 메시지)이 아니라
도메인 코드 10400으로 주기 위해 — `VideoErrorCode.INVALID_VISIBILITY`(3420)·`AuthService.parseProvider`
(`valueOf(toUpperCase())` + catch → ApiException) 실측 선례와 동일 패턴.

**Response**: `SuccessResponse<Void>` — `new SuccessResponse<>(null)` (AuthController.logout · VideoController L130 실측 선례).
등록/갱신 구분 없이 항상 200 — 클라가 구분할 이유가 없다.

**에러**:

| 케이스 | HTTP | developCode |
|---|---|---|
| fcmToken 공백/512자 초과, appVersion 20자 초과 | 400 | 400 (`@Valid` → global 핸들러, 필드별 메시지) |
| platform이 IOS/ANDROID/WEB 외 | 400 | **10400** `INVALID_PLATFORM` |
| 본문 누락/JSON 깨짐 | 400 | 400 (HttpMessageNotReadable 핸들러 실측) |
| 미인증 | 401 | 2403 |

### 2. 토큰 해제 — `DELETE /api/notifications/tokens?fcmToken={token}`

인증 필수. **멱등** — 행이 있으면 삭제, 없으면 그냥 200. 10404류 에러 코드를 만들지 않는다 (위키 계약 확정 — 위키 원문은 8404, 대역 이동에 따라 정정).

- `fcmToken`: `@RequestParam` 필수 — 누락 시 400 (MissingServletRequestParameter 핸들러 실측).
- **소유 검증(user_id 대조) 있음** — `WHERE fcm_token = ? AND user_id = ?`. 이관 경합(토큰이 다른 계정으로
  넘어간 직후 지연 도착한 이전 사용자의 DELETE)이 새 사용자 행을 오삭제하는 것을 차단한다. 불일치는 0행
  삭제 = 그냥 200이라 멱등 유지. *(초안은 검증 없음이었으나 Codex 1R P2 → 2026-08-03 성민 결정으로 번복 —
  "잔류 행을 현재 사용자가 못 지운다"는 기각 근거는 로그인 직후 POST 규약 하에선 성립하지 않는다)*
- **Response**: `SuccessResponse<Void>` body null.

### /auth/logout 통합 — 확정: 선택 필드로 통합한다 (Codex 1R P1 → 2026-08-03 성민 결정, 초안 번복)

초안의 "비통합 + 179 보험" 논리는 깨졌다: FCM 토큰은 앱 로그아웃으로 무효화되지 않아 UNREGISTERED가
영영 오지 않고, DELETE는 로그아웃 후 401이라 사후 정리도 막힌다 — 공유 기기에서 이전 사용자의 알림이
무한 잔존하는 프라이버시 구멍(P1).

- logout 요청에 **선택 body** `LogoutRequestDto { fcmToken }` 추가 — `@RequestBody(required = false)`,
  body 없는 기존 클라 호출은 기존 동작 그대로(하위 호환).
- fcmToken이 오면 세션 삭제와 같은 처리 안에서 `PushTokenService.unregister(userId, fcmToken)` 호출
  (auth → notification 단방향 주입, userId는 logout이 파싱한 토큰에서). 순서 문제(logout 후 401) 소멸.
- 별도 DELETE API는 유지 — 토큰 로테이션 등 로그아웃 외 정리 용도.
- 잔여 보험(클라가 fcmToken을 안 실은 경우): 스테일 배치(last_used_at N일 무갱신 삭제)는 **MSG-179에
  편입** — 성민 결정.

클라 규약(FE 전달 사항): 로그인 직후 POST, 로그아웃은 `/api/auth/logout` body에 fcmToken을 실어 한 번에
(별도 DELETE 불필요). 추가 권장: 로그아웃 시 FCM SDK `deleteToken()`도 호출하면 토큰 자체가 무효화된다.

## 도메인 로직

- **등록 = UPSERT 단일 문장** (FR-1). fcm_token이 PK라 INSERT로 짜면 재로그인 시 PK 충돌 — `ON CONFLICT
  (fcm_token) DO UPDATE`로 user_id 포함 전 필드를 EXCLUDED로 갱신한다. 같은 디바이스 토큰이 항상 마지막
  등록 계정 소유가 되는 게 의도된 시맨틱(계정 전환 이관).
- **중복 정책** (Jira 위임 사항 확정): fcm_token PK + UPSERT가 원천 흡수 — 중복 행 자체가 불가능.
  같은 사용자의 다중 디바이스 = 토큰별 행 N개 (`idx_push_tokens_user`가 179의 사용자별 조회를 받친다).
- **만료 정책** (Jira 위임 사항 확정): 178은 능동 만료 없음. 무효 토큰 감지·삭제는 FCM 응답이 유일하게
  신뢰 가능한 신호라 MSG-179 FR-5 소관이다. `last_used_at`은 등록/갱신 시 `now()`로만 갱신해 두고, 스테일
  판단 재료로 남긴다(스테일 배치 삭제는 비범위 — 필요해지면 후속 티켓).
- 서비스 메서드는 `@Transactional` (modifying native query 요건). 조회 없음 — 178의 읽기 경로는 0.
- platform 파싱은 `toUpperCase(Locale.ROOT)` — 기본 로케일 의존 금지(터키어 로케일에서 `ios` → `İOS` 오거부,
  Codex 1R P2). 기존 visibility 파서 선례와 동일.
- `unregister(userId, fcmToken)` — 소유 검증 반영으로 userId 파라미터 포함 (컨트롤러가 principal 전달).

## 데이터 모델

**마이그레이션 없음** — V1 `push_tokens` 그대로 (실측: fcm_token VARCHAR(512) PK · user_id FK CASCADE ·
platform CHECK IOS/ANDROID/WEB · app_version VARCHAR(20) · last_used_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
`idx_push_tokens_user`).

신설 파일 (`com.msg.fillmap.notification.*`):

| 파일 | 내용 |
|---|---|
| `entity/PushToken` | `@Id @Column(name = "fcm_token", length = 512) String fcmToken` (String 자연키 PK — Grid 엔티티 실측 선례) + userId·platform(`@Enumerated(EnumType.STRING)`)·appVersion·lastUsedAt. `@NoArgsConstructor(access = PROTECTED)` — 쓰기는 전부 native라 리포지토리 앵커 겸 조회 매핑 |
| `entity/PushPlatform` | enum `IOS, ANDROID, WEB` (DB CHECK와 일치) |
| `repository/PushTokenRepository` | `JpaRepository<PushToken, String>` + 아래 native 2종 |
| `service/PushTokenService` / `PushTokenServiceImpl` | register(userId, dto) · unregister(userId, fcmToken) — 인터페이스+Impl 분리 (컨벤션) |
| `controller/PushTokenController` | `@RequestMapping("/api/notifications/tokens")`, 얇게 — principal + 서비스 호출 + SuccessResponse |
| `dto/PushTokenRequestDto` | record + `@Schema` (badge DTO 실측 패턴) |
| `exception/NotificationErrorCode` | `ErrorCodeIfs` 구현, 아래 대역 |

**리포지토리 native 쿼리** (ZoneRepository.upsert 실측 스타일 — `@Modifying @Query nativeQuery = true`, text block):

```sql
-- 등록/갱신
INSERT INTO push_tokens (fcm_token, user_id, platform, app_version, last_used_at)
VALUES (:fcmToken, :userId, :platform, :appVersion, now())
ON CONFLICT (fcm_token) DO UPDATE SET
	user_id      = EXCLUDED.user_id,
	platform     = EXCLUDED.platform,
	app_version  = EXCLUDED.app_version,
	last_used_at = EXCLUDED.last_used_at
```

```sql
-- 해제 (affected 0이어도 성공 — 반환 int는 무시. 소유 불일치도 0행 = 멱등 200)
DELETE FROM push_tokens WHERE fcm_token = :fcmToken AND user_id = :userId
```

**developCode 대역 — 10xxx** *(경위: 9xxx 확정(위키의 8xxx 제안 기각) → 병렬 레인 MSG-185(friend)가
같은 시기 9400~9424를 점유해 develop에서 9400 충돌 → 2026-08-03 성민 결정으로 notification이
10xxx로 이동, MSG-179 실측 발견. 대역 정본은 response-pattern.md 표)*. 최초 전수 실측: user 1xxx · auth 2xxx · video 3xxx ·
grid 4xxx · search 5xxx · region 6xxx · badge 7xxx · **hotzone 8xxx(8400 사용 중)** — 8xxx는 이미 점유라
충돌. streak/mission/zone/usergrid는 에러 enum 없음. notification = **10xxx**, 이번 티켓 상수는 하나:

```java
INVALID_PLATFORM(10400, HttpStatus.BAD_REQUEST, "platform 은 IOS, ANDROID, WEB 중 하나여야 합니다"),
```
