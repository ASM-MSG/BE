# MSG-496: 행사 등재 v2, 행사 운영자 계정과 권한 기반

**Owner**: B (auth와 user 도메인, CLAUDE.md 협업 원칙 기준. SecurityConfig 변경은 MSG-195 ADMIN matcher와 같은 방식의 한 줄 추가라 공동 판정이 아니다)

> 요구사항 정본: `docs/prd/event-submission.md` (상태 검토됨, 2026-08-28 승인). 이 스펙은 그중
> FR-1부터 FR-5까지의 서버 기반 재료만 다룬다.

## 개요

행사 운영자[^1]가 콘솔에 로그인할 수 있으려면 서버에 세 가지 기반이 필요하다. 역할값 ORG가
DB와 코드에 존재해야 하고, 화면이 역할에 따라 경로를 가를 수 있게 로그인 응답과 내 프로필
응답에 role이 실려야 하며, ORG 전용 API 경로에 역할 인가가 걸려야 한다. 이 티켓은 그 세 가지와
개발용 ORG 계정 생성 수단까지를 만든다. 후속 티켓(MSG-497 비밀번호 흐름, MSG-498 신청 API,
MSG-499와 MSG-500 관리자 심사와 콘솔)이 전부 이 위에 올라간다.

## 배경 · 목표

- 행사 등재 v2(PRD 1절)는 관리자가 발급한 자체 계정으로 행사 운영자가 로그인해 콘솔을 쓰는
  구조다. 지금 코드에는 역할이 USER와 ADMIN 둘뿐이라 ORG라는 값 자체가 없다.
- 진입 구조는 공용 로그인 모달 하나로 확정됐다(PRD FR 표 아래 결정문). 로그인 결과의 role로
  화면 경로가 갈리므로, 서버가 role을 응답에 실어야 흐름이 성립한다. 이메일 문자열로 역할을
  추정하는 방식은 금지다(PRD 명문).
- 목표: ORG 역할이 저장, 발급(JWT), 응답 노출, 인가까지 한 바퀴 도는 상태.

## 성공 기준

1. `role = 'ORG'`인 users 행이 DB 제약을 통과해 저장된다(기존 USER, ADMIN 행은 무변경).
2. ORG 계정으로 `POST /api/auth/login` 하면 응답에 `role: "ORG"`가 실리고, 액세스 토큰의 role
   클레임[^2]도 ORG다.
3. `GET /api/users/me` 응답에 role 필드가 실린다(세 역할 모두).
4. ORG 전용 경로 프리픽스에 대해 비로그인은 401, USER 토큰은 403, ORG 토큰은 인가를 통과한다
   (경로 실체는 MSG-498부터 생기므로 이 티켓에서는 인가 판정까지만 검증한다).
5. ORG 토큰은 콘솔 밖 일반 사용자 API(영상 업로드, 친구 등)에서 403이다. 예외는 명시 허용한
   공용 경로(`GET /api/users/me`, `POST /api/auth/logout`)와 비로그인 공개 조회뿐이다(FR-5).
6. USER와 ADMIN의 기존 경로 동작, permitAll 공개 조회 경로는 전부 무변경이다.
7. 아래 테스트 시나리오가 전부 green이다.

## API 명세

새 엔드포인트는 없다. 기존 응답 2종에 필드를 추가한다.

### 1. `POST /api/auth/login` 응답에 role 추가

`LoginResponseDto`(record)에 `String role` 필드를 추가한다. 값은 `user.getRole().name()`
(USER, ORG, ADMIN 중 하나)이고 항상 실린다(required). 이에 맞춰 클래스의
`@Schema(requiredProperties = {"accessToken", "refreshToken"})`에 `"role"`을 추가한다
(LoginResponseDto.java 5행 실측, 갱신하지 않으면 스웨거 문서가 role을 선택 필드로 그린다).

실측한 생성 지점 4곳이 전부 함께 바뀐다(record라 컴파일러가 누락을 잡는다):

| 위치 | 처리 |
|------|------|
| `AuthService.login` (LOCAL 로그인, 62행) | `user.getRole().name()` 전달 |
| `OidcLoginService` (카카오, 65행) | 동일. 소셜 가입자는 항상 USER지만 분기 없이 실값 전달 |
| `AuthController.applyTransport` (285행) | 웹 전송에서 refreshToken을 null로 비우며 DTO를 재조립하는 지점. `issued.role()`을 그대로 통과시켜야 웹 응답에서 role이 사라지지 않는다 |
| DevAuthController 경유 경로 | OidcLoginService를 재사용하므로 별도 변경 없음 확인만 |

토큰 재발급(`ReissueResponseDto`)에는 role을 넣지 않는다. 재발급된 액세스 토큰 안에 role
클레임이 이미 있고(RefreshTokenService 62행이 DB에서 role을 다시 읽어 발급, 역할 변경도 재발급
시점에 반영됨), 화면 라우팅 재료는 로그인 응답과 /me로 충분하다.

- 성공: 기존과 동일, developCode 200에 role 필드만 추가.
- 에러: 기존 흐름 무변경(INVALID_CREDENTIALS 등). 새 에러 케이스 없음.

### 2. `GET /api/users/me` 응답에 role 추가

`UserProfileResponseDto`에 `String role` 필드를 추가하고 `from(User)`에서
`user.getRole().name()`으로 채운다. `@Schema`의 requiredProperties에 `"role"`을 추가한다.
이 DTO는 조회, 닉네임 수정, 프로필 이미지 변경, 위치정보 동의 변경이 공유하므로(클래스 주석
명문) 네 응답 모두에 role이 함께 실린다. 이는 형태 공유 설계의 자연스러운 결과라 별도 분기를
두지 않는다.

### 3. SecurityConfig 인가 체인 개정: ORG matcher[^3] 추가와 catch-all 역할 제한

FR-5 첫 문장("행사 운영자 권한은 등재 콘솔 기능에만 미친다")의 해석이 확정됐다(2026-08-28
사용자 확정, 미해결 질문의 결정 기록 2 참조). ORG 토큰은 `/api/org/**` 밖의 일반 사용자
API에서 **차단**한다. matcher 한 줄 추가만으로는 ORG가 `anyRequest().authenticated()`(현재
174행)를 통과해 영상 업로드, 친구 같은 일반 API를 그대로 쓸 수 있으므로, catch-all 자체를
역할 제한으로 바꾼다.

실측 기준 변경 지시 (SecurityConfig.java 170~174행):

```java
// 기존 (173~174행)
.requestMatchers("/api/admin/**").hasRole("ADMIN")
.anyRequest().authenticated()

// 변경 후
.requestMatchers("/api/admin/**").hasRole("ADMIN")   // 기존 유지 (MSG-195)
.requestMatchers("/api/org/**").hasRole("ORG")       // 신규 (MSG-496)
// ORG 도 쓰는 공용 경로 2개: 아래 catch-all 이 역할 제한이라 여기서 명시 허용해야 한다.
// GET 한정: /me 의 형제 쓰기 경로(닉네임·프로필 이미지 등)는 ORG 에 열지 않는다.
.requestMatchers(HttpMethod.GET, "/api/users/me").authenticated()   // 신규 (FR-4 role 조회)
.requestMatchers("/api/auth/logout").authenticated()                // 신규 (콘솔 로그아웃)
.anyRequest().hasAnyRole("USER", "ADMIN")            // 변경: authenticated() 를 대체 (FR-5)
```

실측 근거와 파급:

- **login과 reissue는 무변경이다.** `/api/auth/signup`, `/api/auth/login`, `/api/auth/oauth/**`,
  `/api/auth/reissue`, `/api/auth/dev/**`는 이미 permitAll(71, 73, 75행)이고 permitAll matcher는
  catch-all보다 먼저 평가되므로 이번 변경의 영향을 받지 않는다.
- **logout은 명시 허용이 필요하다.** `POST /api/auth/logout`(AuthController 217행)은 permitAll
  목록에 없어 지금은 anyRequest로 인가된다. catch-all을 역할 제한으로 바꾸면 ORG의 로그아웃이
  403이 되므로 위처럼 authenticated로 등록한다.
- **`GET /api/users/me`도 같은 이유로 명시 허용한다**(FR-4, ORG 화면의 역할 조회 재료).
  GET 한정 등록이 계약의 일부다. 형제 쓰기 경로(`PUT /api/users/me/nickname` 등)는 경로
  세그먼트가 달라 이 matcher에 안 잡히고 catch-all로 떨어져 ORG에게 403이다.
- **비로그인 동작은 그대로다.** permitAll 공개 조회(행사, 핫구역, 미션, 재생 등 열거 목록,
  71~169행)는 catch-all 앞에서 먼저 매치되어 무변경이고, 비공개 경로의 익명 접근은
  `hasAnyRole`에서도 익명 판정이 entry point로 넘어가 지금과 같은 401이다(403 아님).
- **USER와 ADMIN은 그대로다.** `JwtAuthenticationFilter`가 `ROLE_{role.name()}` 권한을
  심으므로(65행 실측) 두 역할 모두 `hasAnyRole("USER", "ADMIN")`을 통과한다. ORG만
  `CustomAccessDeniedHandler` 경유 403으로 갈린다.
- ADMIN에게 `/api/org/**`를 열어주지 않는다. 관리자는 자기 심사 API(`/api/admin/**`)를 쓰면
  되고, 소유권 검사(FR-14)가 걸릴 콘솔 API에 관리자가 들어올 이유가 없다. ADMIN 경로에 ORG
  토큰이 접근하면 기존 matcher가 이미 403으로 막는다.
- 비로그인 계정 발급 요청 경로(MSG-498 이후의 `POST /api/org-account-requests`)는
  `/api/org/**` 패턴에 잡히지 않는다(`org-account-requests`는 다른 세그먼트다). 후속 티켓이
  permitAll을 추가할 때 이 matcher와 충돌하지 않음을 여기 적어둔다.
- MSG-497의 비밀번호 API(`auth/` 하위 status·change 등)가 ORG에게 열려야 하면 그 티켓이
  같은 방식(명시 authenticated 또는 permitAll)으로 등록한다. 기본이 차단 쪽이라 누락은 403으로
  드러난다(fail-open이 아니라 fail-closed).

**경로 프리픽스는 `/api/org/**` 통일로 확정됐다**(2026-08-28 사용자 명시 확정, 미해결 질문의
결정 기록 1 참조). 이 확정이 MSG-497부터 MSG-500까지의 URL을 고정한다.

## 도메인 로직

- `UserRole` enum에 `ORG` 상수를 추가한다(USER와 ADMIN 사이). glossary.md 기준으로 ORG는
  행사 운영자를 가리키는 서버 역할값이고 지자체 중립이다.
- JWT 발급, 파싱, 필터의 권한 매핑은 전부 `UserRole`을 값으로만 다루므로(issueAccessToken이
  `role.name()`을 클레임에 넣고, parseAccessToken이 `UserRole.valueOf`로 복원) enum 상수 추가
  외에 인증 코드 변경이 없다.
- 로그인 자체는 기존 `POST /api/auth/login`(provider LOCAL) 재사용이다(FR-3). AuthService.login이
  이메일로 사용자를 찾아 비밀번호 해시를 대조하는 흐름은 역할과 무관해 무변경이다.
- 첫 로그인 비밀번호 변경 강제(FR-21)와 mustChange 게이트는 MSG-497 몫이라 이 티켓의 ORG
  계정은 게이트 없이 로그인된다. MSG-497 병합 전까지의 의도된 상태다.

### 개발과 테스트용 ORG 계정: 수동 런북으로 확정

dev 시드가 아니라 **런북 2단계**로 만든다:

```text
1. POST /api/auth/signup  {"email": "...", "password": "...", "nickname": "..."}   (permitAll, 전 프로파일 동작)
2. UPDATE users SET role = 'ORG' WHERE email = '...';
```

근거(실측):

- 기존 시더 선례(ZoneSeeder, EventSeeder, 미션 시더 3종)는 전부 도메인 데이터의 자연키 멱등
  UPSERT이고, 사용자 계정 시더는 선례가 없다. 계정을 시드 JSON에 넣으려면 비밀번호 해시를
  파일에 두거나 시더가 passwordEncoder를 물어야 해서 새 코드가 생긴다.
- ADMIN 계정도 지금 같은 방식으로 만들고 있다. `src/main`에 `UserRole.ADMIN`을 쓰는 생성
  경로가 0건이다(grep 실측, V1의 CHECK 제약 한 건뿐). ORG만 다른 방식을 발명할 이유가 없다.
- signup이 해시 생성을 이미 해주므로 런북에 코드가 한 줄도 안 든다.

런북은 이 스펙의 이 절이 정본이고, 별도 스크립트 파일을 만들지 않는다. 관리자 발급 API
(`POST /api/admin/organizations`)가 MSG-499에서 생기면 dev에서도 그 API를 쓰면 된다.

## 데이터 모델

Flyway 마이그레이션 1건. **번호는 V45다.** 워크트리 실측으로 최신이
`V44__video_encoding_jobs.sql`이라 그다음 번호를 배정했다. PRD 변경 파일 표의 초안 배정(V44)은
이 실측과 충돌해 같은 날 PRD를 V45(role)·V46(신청 테이블, MSG-498 몫)으로 정렬했고, PRD에
"번호는 각 티켓 구현 시점에 재실측" 단서를 붙였다. 구현 시점에 develop에 새 마이그레이션이
먼저 붙었으면 이 번호도 같은 규칙으로 다시 민다.

`V45__users_role_org.sql`:

```sql
-- 행사 등재 v2 (MSG-496): users.role 에 ORG(행사 운영자) 추가.
-- V1 의 chk_users_role 이 USER, ADMIN 만 허용하고 있어 제약을 재정의한다.
-- 기존 행은 값 변경이 없어 새 CHECK 을 그대로 통과한다.
ALTER TABLE users DROP CONSTRAINT chk_users_role;
ALTER TABLE users ADD CONSTRAINT chk_users_role CHECK (role IN ('USER', 'ORG', 'ADMIN'));
```

- `role VARCHAR(10)`은 'ORG'(3자)를 그대로 수용하므로 컬럼 변경 없음.
- 엔티티 변경은 `UserRole`에 상수 추가뿐(User 엔티티의 매핑은 `@Enumerated(STRING)`이라 무변경).
- 신청 테이블(`event_submissions`)은 MSG-498 몫이라 이 티켓에 없다.

## SRS 정합: FR-AUTH-11 재정의

`docs/srs.md` FR-AUTH-11("이메일과 비밀번호 가입과 로그인은 로컬 테스트 용도로만 유지한다",
MSG-310)과 정면 충돌한다. 이 티켓부터 LOCAL 로그인은 행사 운영자와 관리자의 **프로덕션
경로로 승격**된다. SRS 자신도 이 충돌을 예고해 뒀다(FR-AUTH-11 비고: "행사 등재 콘솔 계획이
확정되면 이메일 로그인이 행사 운영자의 운영 경로가 되므로 재정의 대상").

재정의 방향(구현 마무리 시 srs-writer로 SRS 갱신, 이 스펙은 방향만 확정):

- 이메일 **로그인**은 역할 무관 프로덕션 경로다. "로컬 테스트 용도로만" 조건 절을 삭제한다.
- 이메일 **가입**(signup)의 운영 차단 여부(MSG-360)는 별도 판단으로 남는다. 계정이 관리자
  발급으로 확정된 이상(FR-1) 자체 가입은 여전히 막을 대상일 수 있으나, 이 티켓의 런북이
  signup을 쓰므로 지금은 건드리지 않는다. MSG-360의 "전면 차단" 방향은 로그인을 남기고
  signup만 다루는 쪽으로 좁혀야 한다.

SRS 갱신과 rtm 재생성은 후속 절차다(finalize 2-1, 검증 테스트와 같은 브랜치에 커밋).

## 작업 로그

### 2026-08-28 구현 (M1~M5)

**마이그레이션 실행 결과.** Flyway 번호는 착수 시점 재실측에서도 최신이 `V44__video_encoding_jobs.sql`
이라 스펙대로 `V45__users_role_org.sql`로 확정했다. 로컬 DB 적용 실측:

```text
version | description    | success
45      | users role org | t

-- pg_get_constraintdef(chk_users_role)
CHECK (((role)::text = ANY ((ARRAY['USER','ORG','ADMIN'])::text[])))
```

**데이터 저장 위치.** 역할값은 `users.role VARCHAR(10)` 한 곳뿐이다. 새 테이블·Redis 키·S3 경로가
없고, 토큰의 role 클레임은 발급 시점 스냅숏이라 저장이 아니다(액세스 토큰 1시간, 재발급 때
`RefreshTokenService`가 DB에서 다시 읽어 심는다 — 역할 변경은 재발급 시점에 반영된다).

**실행 쿼리.** 새 쿼리가 없다. 로그인은 기존 `select ... from users where email = ?`
(`UserRepository.findByEmail`), 내 프로필은 기존 `findById` 그대로이고, 두 응답 DTO가 이미 읽어 둔
`User.role`을 문자열로 옮겨 담을 뿐이라 조회가 한 번도 늘지 않는다. 개발용 계정 발급은 아래 런북의
`UPDATE users SET role = 'ORG' WHERE email = ?` 한 문장이다.

**예외 흐름 (인가 거부).** 두 갈래가 컨트롤러에 닿기 전에 필터 체인에서 갈린다.

| 상황 | 처리 주체 | 응답 |
|------|-----------|------|
| 토큰 없음 (익명) | `CustomAuthenticationEntryPoint` → `AuthErrorCode.UNAUTHENTICATED` | 401, developCode 2403 |
| 역할 불일치 (USER→`/api/org/**`, ORG→일반 API·`/api/admin/**`) | `CustomAccessDeniedHandler` → 공통 `ErrorCode.FORBIDDEN` | 403, developCode 403, "접근 권한이 없습니다" |

catch-all을 `hasAnyRole`로 바꿔도 익명은 403이 아니라 401이다 — 스프링 시큐리티가 익명 인증
객체의 접근 거부를 entry point로 넘기기 때문이고, `비로그인으로_비공개_경로_접근은_여전히_401이다`가
이 성질을 잡아 둔다.

**빈 동작.** 새 빈이 없다. `SecurityFilterChain` 하나에 matcher 4줄이 늘었고, 등록 순서가 곧 평가
순서라 permitAll 열거(71~169행) → `/api/admin/**` → `/api/org/**` → 공용 2종 → catch-all로 떨어진다.
`GET /api/users/me`가 GET 한정인 것이 계약이라 형제 쓰기 경로(`PUT /me/nickname` 등)는 catch-all로
떨어져 ORG에게 403이다.

**개발용 ORG 계정 런북 (실행 형태).** 위 "개발과 테스트용 ORG 계정" 절의 2단계를 그대로 옮긴 것이다.

```bash
# 1) 계정 생성 — signup 이 비밀번호 해시까지 만들어 준다 (permitAll, 전 프로파일)
curl -X POST http://localhost:8080/api/auth/signup \
  -H 'Content-Type: application/json' \
  -d '{"email":"organizer@fillmap.dev","password":"fillmap1234","nickname":"행사운영자"}'

# 2) 역할 승격 — 로컬은 컨테이너로 붙는다 (psql 미설치 환경)
docker exec fillmap-postgres psql -U user -d fillmap \
  -c "UPDATE users SET role = 'ORG' WHERE email = 'organizer@fillmap.dev';"

# 3) 확인 — 응답의 role 이 ORG 면 끝
curl -X POST http://localhost:8080/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"organizer@fillmap.dev","password":"fillmap1234"}'
```

MSG-499의 관리자 발급 API(`POST /api/admin/organizations`)가 생기면 dev에서도 그 API를 쓴다.

**SRS 정합.** 테스트 `// 검증:` 마커는 SRS ID로 달았다 — 역할값 저장·역할 조회·인가 경계는
FR-AUTH-14, ORG 계정이 기존 로그인 경로를 그대로 쓰는 축은 FR-AUTH-13이다. 두 요구의 상태 갱신과
rtm 재생성은 finalize 2-1 절차로 남는다(FR-AUTH-13은 계정 발급 API가 MSG-499 몫이라 이 티켓만으로는
`진행 중`이다).

[^3]: matcher: 스프링 시큐리티에서 URL 패턴별로 접근 규칙을 거는 단위

    fail-open(새 경로가 실수로 공개되는 것)을 막아 왔고, 역할 인가는 프리픽스 하나에 한 줄이
    원칙이다(MSG-195의 `/api/admin/**` 선례).
