# MSG-399: 미션 하나를 여는 상세 조회 신설

**Owner**: B

> 요구사항 정본: `docs/prd/mission-map-explore.md` (상태 검토됨, 2026-08-13 성민 승인).
> 적용 요구사항: PRD FR-5, FR-6, FR-7, FR-11, FR-12, FR-13, FR-16과 SRS
> FR-MISSION-16, FR-MISSION-17, FR-MISSION-18.
> MSG-398이 추가하는 미션 진행도 조회와 12xxx 에러 대역을 선행 계약으로 재사용한다.

## 개요

인증 사용자가 미션 ID 하나로 상세를 조회하는 `GET /api/missions/{missionId}`를 추가한다. 응답은
기존 미션 정보와 렌더 형상, 내 진행도와 스탬프 보유 여부, 미션 영상 개수, 코스 포토스팟별 방문
여부와 영상 개수를 담는다.

미션 정보는 기존 `MissionResponseDto`를 중첩해 재사용한다. 상세에서만 필요한 값은
`MissionDetailResponseDto`에 덧붙인다. 같은 메타데이터와 shape를 상세 전용 타입에 다시 복사하지
않는다. `MissionResponseDto`의 OpenAPI 설명만 "활성 미션"에서 "미션"으로 중립화해 기간이 끝난
미션에도 쓸 수 있게 한다.

상세는 사용자마다 값이 다르므로 전역 캐시[^4]에 넣지 않는다. MSG-398의
`MissionRepository.findProgress`와 `MissionProgressResponseDto`를 그대로 써서 목록과 상세의 진행도
뜻을 한 곳에 둔다.

## 배경과 목표

MSG-383과 MSG-394가 상세 화면에 필요한 미션 메타데이터를 이미 적재했다. MSG-390도 미션 영상 목록을
추가했지만 총 개수를 응답에서 뺐다. 현재 API만으로는 팝업 운영시간과 축제 기간 같은 기본 정보는
조합할 수 있어도 아래 사용자별 값과 집계값은 만들 수 없다.

- 내 진행 `0/1칸`, `2/3곳`과 완료 여부
- 코스 포토스팟별 방문 여부
- 상세 상단과 영상 목록 헤더에 표시할 전체 영상 개수
- 코스 포토스팟별 영상 개수

피그마 최신 정본의 상세 화면 세 개를 노드 단위로 확인했다.

| 유형 | 노드 | 서버가 채울 값 |
|------|------|----------------|
| 팝업 | `14599:9718` | 내 진행, 운영시간, 올라온 영상 개수 |
| 지역축제 | `14599:9998` | 내 진행, 축제 기간, 올라온 영상 개수 |
| 코스 | `14599:10258` | 내 진행, 거리, 소요시간, 포토스팟별 방문 여부와 영상 개수 |

목표는 상세 화면이 미션 정보와 사용자 상태를 한 번에 받고 화면의 영상 개수가 MSG-390 목록의 실제
후보 수와 항상 같게 만드는 것이다.

## 성공 기준

- 미션 ID 하나로 상세를 조회한다.
- 응답의 `mission`은 기존 미션 필드와 shape를 빠짐없이 담는다. 소개문은 저장된 원문을 그대로 낸다.
- 응답의 `progress`는 MSG-398 목록 진행도와 같은 계산을 쓴다. 채운 칸 수는 `targetCount`를 넘지 않고,
  `completed`는 비회수 스탬프 보유 여부라 진행도와 독립적이다.
- 코스의 `spotStats`는 `shape.spots`와 같은 순서로 오며 각 항목에 `gridId`, 방문 여부, 영상 개수가
  담긴다. 영상이 없으면 `videoCount`는 0이다.
- 코스가 아닌 미션의 `spotStats`는 빈 배열이다.
- 미션 전체 `videoCount`는 `spotStats.videoCount`의 합과 같다. 이 등식은 모든 대상 격자가
  포토스팟인 코스에 적용한다.
- 전체 영상 개수와 스팟별 영상 개수는 MSG-390 후보 술어와 술어 동등[^2]하다.
- 영상이 하나도 없는 미션은 200으로 응답하고 `videoCount`는 0이다.
- 존재하지 않는 미션 ID는 404 `MISSION_NOT_FOUND`다.
- 기간이 끝난 미션도 행이 남아 있으면 상세를 조회할 수 있다. 활성 기간 조건은 목록 노출에만 쓴다.
- 미션 격자 수와 무관하게 쿼리 횟수가 고정된다. 스팟마다 DB를 다시 읽지 않는다.

## 선행 및 인접 티켓

### MSG-398 선행

MSG-398이 아래 두 기반을 먼저 만든다. MSG-399 구현 브랜치는 MSG-398 병합 뒤 시작하거나 리베이스한다.

- `MissionProgressResponseDto`
- `MissionRepository.findProgress(userId, missionIds)`
- `MissionErrorCode`와 developCode 12xxx 대역

상세는 `findProgress(userId, List.of(missionId))`를 호출한다. 같은 교집합 계산을 상세용 SQL로 복제하지
않는다.

### MSG-390 정합

MSG-390은 `GET /api/missions/{missionId}/videos`와 영상 후보 술어의 정본이다. 이 스펙은 목록 쿼리를
호출해 전체 페이지를 세지 않는다. 같은 후보 술어로 격자별 COUNT를 한 번 실행하고 합계를 낸다.

### MSG-397 비스코프

포토스팟 장소 이름의 저장과 노출은 MSG-397 몫이다. MSG-399의 `spotStats`는 이름을 중복 보관하지 않고
`gridId`로 `mission.shape.spots`에 대응한다. MSG-397이 `MissionShape.Spot`에 이름을 더해도
`spotStats` 계약은 바뀌지 않는다.

## API 명세

### GET /api/missions/{missionId}

- **인증**: 토큰 필수. `@AuthenticationPrincipal AuthPrincipal`의 `userId`로 진행도와 방문 여부를
  계산한다.
- **경로 변수**: `missionId` (`long`)
- **기간 판정**: 하지 않는다. `MissionRepository.findById`로 현재 저장된 행을 찾는다.
- **성공**: HTTP 200, `SuccessResponse<MissionDetailResponseDto>`

`MissionController`에 메서드 하나를 추가한다. `/api/missions/active`와 `/api/missions/progress`는 리터럴
경로라 `{missionId}`와 충돌하지 않는다.

### 응답 DTO

```java
public record MissionDetailResponseDto(
	MissionResponseDto mission,
	MissionProgressResponseDto progress,
	long videoCount,
	List<SpotStats> spotStats
) {
	public record SpotStats(String gridId, boolean visited, long videoCount) {
	}
}
```

- `mission`: 기존 공통 필드, 메타데이터 8종, 유형별 shape. 값이 없는 nullable 필드도 키는 항상 보낸다.
- `progress`: MSG-398 응답 타입을 재사용한다. `filledCount`는 `LEAST(미션 기간 안에 촬영한 내 영상이
  있는 격자 수, targetCount)`다(MSG-398 D8, 2026-08-15 개정판 — 판정 술어).
- `videoCount`: MSG-390 후보 술어를 통과한 전체 영상 수다.
- `spotStats`: COURSE만 값이 있다. 정렬은 `seq ASC NULLS LAST, gridId ASC`이고 영상이 없는 스팟도
  빠뜨리지 않는다.

`MissionDetailResponseDto`의 `requiredProperties`에는 네 필드를 모두 넣는다. `spotStats`는 COURSE가
아니어도 `null` 대신 빈 배열을 보낸다.

### 에러 케이스

| 상황 | 응답 |
|------|------|
| 존재하지 않는 미션 ID | 404, `MissionErrorCode.MISSION_NOT_FOUND` (12404) |
| 미인증 | 공통 401 |

`MISSION_NOT_FOUND`의 메시지는 `"미션을 찾을 수 없습니다"`로 한다. MSG-390 영상 목록은 없는 미션을
빈 목록으로 다루지만 상세는 단일 리소스를 요청하므로 404로 구분한다.

## 도메인 로직

### 상세 조립 순서

1. `missionRepository.findById(missionId)`로 미션을 찾고 없으면 `MISSION_NOT_FOUND`를 던진다.
2. `missionGridRepository.findByMissionIds(List.of(missionId))`로 shape와 포토스팟 순서에 쓸 격자를
   한 번 읽는다.
3. `missionRepository.findProgress(userId, List.of(missionId))`로 진행도와 스탬프 보유 여부를 읽는다.
4. `missionGridRepository.findVisitedGridIds(missionId, userId)`로 기간 안에 촬영한 내 영상이 있는
   대상 격자 ID를 읽는다(진행도와 같은 술어).
5. `videoRepository.countMissionVideosByGrid(missionId)`로 격자별 영상 개수를 읽고 합계를 낸다.
6. 기존 `buildShape`로 `MissionResponseDto`를 만든 뒤 COURSE면 `spotStats`를 같은 스팟 순서로 조립한다.

DB 조회는 최대 다섯 번이고 미션 격자 수가 늘어도 횟수는 고정이다. 미션 하나가 덮는 현재 상한은 축제
81칸이고 코스는 포토스팟 5곳에서 8곳이라 이 범위에서 추가 캐시나 집계 테이블을 두지 않는다.

### 진행도와 방문 여부

진행도와 스팟 방문 여부는 **스탬프 판정과 같은 술어**를 기준으로 한다. 미션 기간 안에 촬영한 내
영상(`status <> 'DELETED'`, 블라인드 포함)이 있는 격자가 채운 칸이고 방문한 스팟이다. MSG-398 D8의
2026-08-15 개정판과 같은 정의이고, 도감 점령(`user_grids`) 기준이던 초안 정의는 그 개정으로 폐기됐다.

이 스펙의 직전 판은 방문 여부를 `user_grids`로 정의했다. 무기간 코스에서는 두 술어의 결과가 지금
같지만(기간 조건이 자연 통과되고, 점령 롤백 규칙상 점령 행 존재가 곧 삭제 안 된 영상 존재다) 그것은
구성상 보장이 아니라 우연의 일치다. 같은 카드에 그려지는 `filledCount`와 `spotStats.visited`가 다른
술어에서 나오면 기간 있는 코스가 등장하는 순간 조용히 갈라지므로 술어를 한 곳으로 통일한다.

영상을 지우면 이 술어에서도 그 격자가 빠지므로, 마지막 영상을 지운 스팟은 다음 조회에서 방문하지
않은 것으로 바뀐다. 미션 기간 조건은 `IS NULL OR` 형태라 무기간 코스는 과거 영상도 인정한다
(FR-MISSION-03).

`completed`는 `user_missions` 스탬프 보유 여부다. 스탬프는 비회수라 영상을 지운 뒤
`filledCount < targetCount`여도 `completed = true`일 수 있다. 화면은 `completed`를 진행도에서 다시
계산하지 않는다.

### 영상 개수

"이 미션의 영상"은 MSG-390의 아래 조건을 모두 만족하는 영상이다. 목록과 개수의 행 집합이 같아야
한다. 이 조건 묶음이 전역 공개 게이트[^1]다.

```sql
JOIN mission_grids mg ON mg.grid_id = v.grid_id
JOIN missions m ON m.id = mg.mission_id
WHERE mg.mission_id = :missionId
  AND v.status = 'ACTIVE'
  AND v.visibility = 'PUBLIC'
  AND v.processing_status = 'READY'
  AND (m.start_at IS NULL OR v.recorded_at >= m.start_at)
  AND (m.end_at IS NULL OR v.recorded_at <= m.end_at)
```

`VideoRepository.countMissionVideosByGrid`는 이 술어에 `GROUP BY v.grid_id`만 붙인다.

```sql
SELECT v.grid_id AS "gridId", COUNT(*) AS "videoCount"
FROM videos v
JOIN mission_grids mg ON mg.grid_id = v.grid_id
JOIN missions m ON m.id = mg.mission_id
WHERE mg.mission_id = :missionId
  AND v.status = 'ACTIVE'
  AND v.visibility = 'PUBLIC'
  AND v.processing_status = 'READY'
  AND (m.start_at IS NULL OR v.recorded_at >= m.start_at)
  AND (m.end_at IS NULL OR v.recorded_at <= m.end_at)
GROUP BY v.grid_id
```

영상이 없는 격자는 결과 행이 없다. 서비스가 해당 `gridId`를 0으로 채운다. 전체 `videoCount`는
프로젝션[^3]의 `videoCount` 합으로 계산하므로 별도 COUNT 쿼리를 한 벌 더 만들지 않는다.

기간이 끝난 미션도 상세와 영상 집계를 열어 둔다. 영상 후보 기간은 그대로 적용하므로 그 미션이
활성일 때 촬영된 영상만 센다.

## 데이터 모델

스키마 변경과 Flyway 마이그레이션은 없다.

새 저장 위치도 없다. 아래 기존 테이블만 읽는다.

- `missions`: 미션 정보와 메타데이터
- `mission_grids`: 대상 격자와 코스 순서
- `user_missions`: 비회수 완료 스탬프
- `videos`: 진행도·방문 여부(판정 술어)와, 전역 공개 게이트를 통과한 영상 개수

`MissionGridRepository.findVisitedGridIds`는 다음 native 쿼리를 쓴다.

```sql
SELECT DISTINCT mg.grid_id
FROM mission_grids mg
JOIN missions m ON m.id = mg.mission_id
JOIN videos v ON v.grid_id = mg.grid_id
	AND v.user_id = :userId
	AND v.status <> 'DELETED'
	AND (m.start_at IS NULL OR v.recorded_at >= m.start_at)
	AND (m.end_at IS NULL OR v.recorded_at <= m.end_at)
WHERE mg.mission_id = :missionId
```

`videos` 조인 조건은 `MissionRepository.findProgress`(MSG-398 D8)와 글자 단위로 같다. 같은 격자에
재방문 영상이 여러 개일 수 있어 `DISTINCT`가 필수다. 받치는 인덱스는 `findProgress`와 같은
`idx_videos_user_created`의 `user_id` 선두부라 별도 인덱스는 추가하지 않는다. 구현 후
`EXPLAIN (ANALYZE, BUFFERS)`로 실제 계획을 확인하고 작업 로그에 남긴다.

**런타임 동작 기록**

- **데이터 저장 위치**: 신설 없음. 읽기 전용 API로 `missions`·`mission_grids`·`user_missions`·`videos`만 읽는다. 스키마·마이그레이션 무변경.
- **실행 쿼리** (`EXPLAIN (ANALYZE, BUFFERS)` 실측, 로컬 DB 롤백 트랜잭션 합성 videos 58,060행·ANALYZE 후):
  - `findVisitedGridIds`: `Bitmap Index Scan on idx_videos_user_created`(user_id 조건)로 내 영상 15,060행 프로브 → `mission_grids_pkey` Index Only Scan(81행)과 Hash Join → Sort+Unique. shared hit 284 buffers, 실행 5.1ms. 스펙 예상(user_id 선두부, 신규 인덱스 불요)과 일치.
  - `countMissionVideosByGrid`: `idx_videos_grid_popular` 부분 인덱스(전역 공개 게이트 3종이 인덱스 술어라 잔여 필터 없음) Index Scan과 `mission_grids_pkey`의 Merge Join → GroupAggregate. shared hit 28,830, 실행 6.7ms.
  - 측정 주의: 미션 격자에 영상 57%를 몰아넣은 비현실 분포에서는 플래너가 Seq Scan(17.5ms)을 택했다. 실분포(미션 격자 영상이 소수)로 재측정한 위 수치가 유효값이다.
- **예외 흐름**: 없는 미션 ID는 `MissionQueryServiceImpl.getMissionDetail`이 `ApiException(MissionErrorCode.MISSION_NOT_FOUND)`을 던지고 `GlobalExceptionHandler`가 HTTP 404 + developCode 12404 "미션을 찾을 수 없습니다"로 변환한다. 미인증은 컨트롤러 도달 전 시큐리티 체인의 공통 401.
- **빈 동작**: `getMissionDetail`만 메서드 레벨 `@Transactional(readOnly = true, isolation = REPEATABLE_READ)` 오버라이드로 다섯 읽기가 첫 문장 스냅숏을 공유한다(클래스 레벨은 `readOnly=true` 그대로, 읽기 전용이라 직렬화 실패 부작용 없음). 부수 효과로 findById 성공 직후 시더 정리가 커밋되는 극소 경합의 `findProgress` 빈 결과 500도 봉쇄된다. 단 `@Transactional` 테스트는 기존 테스트 트랜잭션에 참여(REQUIRED)해 격리 속성이 적용되지 않는다 — 운영 경로(컨트롤러 진입 새 트랜잭션)에서만 발효. 전역 스냅숏 캐시는 상세에 쓰지 않는다(사용자별 값).
