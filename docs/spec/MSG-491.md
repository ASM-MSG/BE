# MSG-491 — 비로그인 조회 개방 마무리 (동 격자 카드 목록·영상 재생·전체 지역 목록)

- **상위 정본**: `docs/prd/mission-map-explore.md` 8절 2026-08-26 확정
- **선행**: MSG-454(상단 칩) · MSG-467(행정동) · MSG-469(구역 목록·격자 클릭)
- **대기 중인 후속**: MSG-474(FE, 비로그인 지도 홈 개방)
- **Owner**: B (video 패키지) · SecurityConfig 공통

## 1. 배경

앞선 세 티켓이 배포된 뒤에도 비로그인 지도가 반쪽으로 남았다. 2026-08-26 재실측(`https://api.fillmap.kr`,
Authorization 헤더 없음)으로 익명 401이 남은 경로를 전수 확인한 결과는 여섯이다.

| 경로 | 판정 |
|---|---|
| `GET /api/regions/{regionCode}/grids` | **연다**. 동 격자 카드 목록이고 principal 미사용 |
| `GET /api/videos/{videoId}` | **연다**. 재생이고 PUBLIC만 통과 |
| `GET /api/regions/explore` | **연다**. 전체 지역 목록이고 개인화 절 없음 |
| `GET /api/grids/{gridId}` | 로그인 유지 (2026-08-25 PRD 확정. 사용자 무관 값이 없다) |
| `GET /api/grids/{gridId}/my-videos` | 로그인 유지 (사용자별) |
| `GET /api/regions/stats/**` | 로그인 유지 (사용자별) |

MSG-474의 요구 다섯 가운데 넷(행정동 확정·장소 불러오기 갱신·칩 최근접 이동·격자 클릭)은 앞선
티켓들로 이미 열려 있고, 남은 하나("비로그인 좌측 패널에 그 동의 전체 공개 영상 목록")가 동 격자
카드 목록 조회에 걸려 있었다. 재생은 그 카드를 눌렀을 때 바로 이어지는 동작이라 같이 연다.

라이브 `/v3/api-docs`는 레포 스냅숏과 바이트 단위로 같았다. 인가 설정은 명세에 나타나지 않으므로
이번 변경에도 명세 재생성은 필요 없다.

## 2. 결정

**D-1. 개방은 GET 한정이고 경로를 하나씩 열거한다.** `/api/regions/**`로 넓히면 수집률 stats 계열이,
`/api/videos/**`로 넓히면 업로드 확정·교체·공개범위 변경·삭제·신고가 함께 풀린다. 특히 재생은
교체(PUT)·공개범위 변경(PATCH)·삭제(DELETE)와 **URL이 같아서**, GET 한정이 그 셋을 막는 유일한
수단이다. stats 계열은 `principal.userId()`를 null 가드 없이 부르므로 익명 유입이 401이 아니라
NPE 500이 된다.

**D-2. 재생의 명시 HEAD 매핑도 함께 연다.** `VideoController`의 HEAD 매핑(MSG-206에서 조회수 증가를
막으려 둔 심)은 GET 한정 매처에 안 잡혀 익명 HEAD가 401이 된다. 행사 영상 상세와 같은 처리다.
HEAD 응답은 전 id 동일이라 존재 오라클이 아니다.

**D-3. 익명은 `null` userId로 서비스에 들어간다.** 레포에 이미 있는 형태를 그대로 쓴다
(`MissionController` · `EventVideoController` · `EventOccurrenceController`의
`principal == null ? null : principal.userId()`). 0 같은 센티넬 값을 새로 만들지 않는다. 판정이
"존재하지 않는 사용자 id"라는 우연에 기대게 되고, 뒤에 오는 사람이 그 우연을 읽어낼 방법이 없다.

**D-4. 비로그인 재생은 PUBLIC만 통과한다.** 나머지 공개범위는 **기존 분기에서** 거절된다. 익명은
소유자일 수 없고(`owner = userId != null && userId.equals(...)`) 친구일 수도 없으므로(`case FRIENDS -> userId != null && ...`),
판정이 자연히 PRIVATE 비소유자와 같은 자리로 수렴한다. 응답은 `VIDEO_FORBIDDEN`("비공개 영상입니다")
그대로이고 신규 에러코드가 없다. 거절 응답이 갈리면 그 차이가 영상의 존재와 공개범위를 알려주는
신호가 된다는 MSG-285 §D1의 근거가 그대로 적용된다.

`case FRIENDS`의 `userId != null &&` 단축 평가는 성능도 겸한다. 익명에게 친구가 있을 수 없으므로
친구 판정 쿼리를 아예 돌리지 않는다(소유자 경로가 쿼리 0회인 것과 같은 이유).

**D-5. 익명 재생도 조회수에 센다.** 지금 규칙이 "재생 URL을 실제로 발급했고 소유자가 아닐 때"인데
익명은 언제나 소유자가 아니므로 규칙을 그대로 적용하면 세는 쪽이다(코드 변경 없음). 세지 않으면
지도를 비로그인에 열어 둔 상태에서 인기순 표본이 로그인 쪽으로 기운다. 2026-08-25에 비로그인
검색을 인기 검색어 집계에 넣기로 한 결정과 같은 계열이고, 부풀리기 가능성을 수용하는 것도 같다.

**D-6. 전체 지역 목록은 쿼리를 새로 만들지 않는다.** 개인화가 `personal_regions` CTE
(`WHERE ug.user_id = :userId`) 하나뿐이라, 파라미터 타입을 `Long`으로 열고 null을 넘기면 CTE가
0행이 되어 LEFT JOIN이 전부 null이 되고 정렬이 `grid_count DESC, region_code ASC`로 자연히 떨어진다.
익명 전용 쿼리를 따로 두면 두 벌이 갈라져 앞으로 한쪽만 고쳐지는 일이 생긴다.

**D-7. 커서의 userId 자리를 비운다.** `RegionExploreCursor`가 userId를 실어 발급 주체를 대조하는데
익명에는 그 값이 없다. 레코드 성분을 `Long`으로 열고 토큰 첫 자리를 빈 문자열로 직렬화한다
(`:{ts}:{cnt}:{code}`). 대조는 `Objects.equals`라 익명 커서를 로그인 사용자가 쓰거나 그 반대도 여전히
`INVALID_CURSOR`다. 0을 쓰지 않은 이유는 D-3과 같고, 레코드 생성자 가드(`userId <= 0` 거부)도 그대로
살아 있다(`userId != null && userId <= 0`).

**D-8. 응답 계약과 성능은 그대로다.** 세 조회 모두 필드가 늘거나 줄지 않는다. 전체 지역 목록은
개인화에 쓰이던 값(`personalLastUploadedAt`)이 익명에서 비어 나갈 뿐이고 페이지 계약(20개·커서)도
불변이다. 비용 대부분인 `content_regions` 집계는 사용자와 무관하므로(MSG-461 실측 266ms 가운데
257ms) 익명 응답이 더 느려질 자리가 없다.

### 핵심 diff

```java
// VideoServiceImpl.getVideoPlayback
// equals 로 비교한다. 양쪽 다 Long 이라 == 는 값이 아니라 참조를 본다.
boolean owner = userId != null && userId.equals(video.getUserId());
...
case FRIENDS -> userId != null && friendshipQueryService.isFriend(video.getUserId(), userId);
```

```java
// SecurityConfig
.requestMatchers(HttpMethod.GET,
    "/api/regions/*/grids",
    "/api/regions/explore",
    "/api/videos/{videoId:[0-9]+}").permitAll()
.requestMatchers(HttpMethod.HEAD, "/api/videos/{videoId:[0-9]+}").permitAll()
```

재생 경로의 videoId 자리는 숫자로 못박는다. `/api/videos/*`로 두면 앞으로 이 하위에 붙는 한 세그먼트
GET(`drafts`·`my` 류)이 열거를 거치지 않고 기본 공개가 되는 fail-open이다. 미션 상세가 같은 이유로
`{missionId:[0-9]+}`를 쓴다(MSG-454). 지금 이 하위의 한 세그먼트 GET은 재생 하나뿐이라 동작은 그대로이고,
경로가 늘어날 때 기본이 401 쪽으로 닫힌다.

## 5. 작업 로그 (런타임 동작)

**데이터 저장 위치**. 이번 변경으로 새로 쓰는 저장소가 없다. 익명 재생이 건드리는 유일한 쓰기는
`videos.view_count` 증가 한 번이다.

**실행 쿼리**. 전체 지역 목록의 SQL 본문은 글자 하나 안 바뀌었고 바인딩 값만 null이 된다.
익명 요청에서 `personal_regions` CTE는 `ug.user_id = NULL` 비교라 Postgres에서 결과가 NULL로 평가돼
0행이고, 뒤따르는 `LEFT JOIN personal_regions p`가 전부 null을 채운다. 그래서 `ORDER BY`의 첫 두 절
(`(p.last_uploaded_at IS NOT NULL) DESC`, `p.last_uploaded_at DESC NULLS LAST`)이 전 행 동률이 되고
`c.grid_count DESC, c.region_code ASC`만 순서를 정한다.

익명 재생의 쿼리 수는 로그인 타인 조회보다 하나 적다. PUBLIC이면 친구 판정이 애초에 안 돌고,
FRIENDS면 `userId != null` 단축 평가로 `isFriend`가 생략된다.

**예외 흐름**. 비로그인이 PRIVATE·FRIENDS 영상을 요청하면 `VideoServiceImpl`의 visibility 분기에서
`ApiException(VideoErrorCode.VIDEO_FORBIDDEN, "비공개 영상입니다")`가 던져지고 `GlobalExceptionHandler`가
403 + developCode 3403으로 변환한다. 로그인 비소유자와 완전히 같은 경로다. 삭제·블라인드 타인 조회는
종전대로 `VIDEO_NOT_FOUND`(404)다. 열린 경로에 무효 토큰을 실으면 `JwtAuthenticationFilter`가 먼저
잡아 2401이다(개방은 인증 불요이지 토큰 무시가 아니다. MSG-443 D4).

**빈 동작**. `SecurityConfig`의 필터체인 빈만 정의가 바뀐다. `JwtAuthenticationFilter`와
`PUBLIC_AUTH_PATHS`는 손대지 않았고, 스케줄러·트랜잭션 경계 변화도 없다. `@Transactional` 경계는
`getVideoPlayback`(쓰기 포함)과 `getExploreRegions`(읽기) 모두 종전 그대로다.
