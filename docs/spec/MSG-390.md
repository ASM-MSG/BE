# MSG-390: 미션 상세의 영상 목록 조회 API

**Owner**: B

> 요구사항 정본: `docs/prd/MSG-390-prd.md` (상태 검토됨, 2026-08-14 성민 승인).
> 상위 PRD는 `docs/prd/mission-map-explore.md`의 FR-8과 FR-9이고, SRS 등재 ID는 FR-MISSION-17이다.
> 이 스펙은 그 PRD의 FR-1부터 FR-15까지에 "어떻게"만 붙인다.

## 개요

미션 하나를 지정하면 그 미션의 대상 격자에서 그 미션 기간에 촬영된 공개 영상을 촬영 시각
최신순으로 돌려주는 조회 API를 추가한다. 팝업 상세와 축제 상세 하단의 "이 미션의 영상" 목록이
이 응답을 그대로 그린다.

`videos`에는 `mission_id`가 없고 미션과 영상을 잇는 것은 격자뿐이므로, 스탬프 판정 쿼리
(`MissionRepository.findCompleted`)가 이미 쓰고 있는 조인(미션 격자와 영상을 `grid_id`로 잇고
미션 기간 조건을 붙이는 형태)을 그대로 물려받는다. 스키마 변경과 마이그레이션은 없다.

`videos` 테이블만 읽고 쓰는 코드라 Owner는 B다. 경로 접두사가 `/api/missions`여도 videos를 다루는
코드는 video 패키지에 두는 선례(`GridVideoController`, MSG-127)를 따르고, mission 패키지는
무수정이다(PRD §7).

## 배경 · 목표

지금 있는 영상 조회는 격자 하나 단위라, 81칸을 덮는 축제 미션의 목록을 그리려면 화면이 81번
호출해 직접 합쳐야 한다. 합쳐도 결과가 다르다. 그 조회는 인기순이고 미션 기간 밖 영상까지 섞이며,
기간을 아는 쪽은 서버인데 판단이 클라이언트로 넘어간다.

목표는 두 가지다. 미션 상세가 한 번의 호출로 그 미션의 영상을 받는 것, 그리고 "이 미션의 영상"의
정의를 서버 한 곳에 두어 화면과 스탬프 판정이 서로 다른 뜻을 갖지 않게 하는 것이다.

## 성공 기준

- 미션 하나를 지정한 조회 한 번으로 그 미션의 영상 페이지가 온다. 화면이 격자마다 호출하지 않는다.
- 대상 격자 밖에서 촬영된 영상, 미션 기간 밖에 촬영된 영상, PUBLIC이 아닌 영상, 삭제되거나
  블라인드된 영상, 인코딩이 끝나지 않은 영상은 목록에 없다.
- 기간이 없는 미션(코스와 지속형)은 기간 조건을 타지 않아 과거 영상도 들어온다.
- 정렬은 `videos.recorded_at` 내림차순이고, 촬영 시각이 같으면 `videos.id` 내림차순으로 갈린다.
  **정렬 키와 후보 집합 멤버십이 페이지 사이에 둘 다 그대로일 때** 이어 받은 페이지에 중복도 누락도
  없다. 촬영 시각이 바뀌거나(영상 교체) 후보 집합에 새로 들어오고 빠지는 항목이 생기면(공개범위
  변경, 인코딩 완료, 삭제나 블라인드, 미션 격자 변경) 그 항목은 두 번 나오거나 건너뛰어질 수 있고,
  이는 수용한다(아래 정렬 문단).
- 조건에 맞는 영상이 없거나 존재하지 않는 미션 ID여도 실패가 아니라 빈 페이지다.
- 무효 커서는 400이다. 형식이 깨진 토큰뿐 아니라 시각 성분이 저장 가능 범위를 벗어난 토큰도 400이며,
  DB까지 흘러가 500이 되지 않는다. 반대로 **서버가 발급한 커서는 어떤 값이든 다시 받아들여진다.**
- 응답 항목 여섯 개(videoId, thumbnailUrl, durationSec, viewCount, recordedAt, nickname)가 시안의
  영상 카드 한 장을 그대로 채운다.
- 아래 "후보 술어" 블록과 미션 상세 조회의 영상 개수 집계가 **술어 동등**하다. 표기(별칭, 줄바꿈,
  조건 순서)는 달라도 되지만 두 쿼리를 통과하는 행 집합이 같아야 한다. 상세가 "영상 3개"라고 쓰면
  이 목록에도 세 개가 온다.
- 격자가 가장 많은 축제 미션(81칸)의 첫 페이지 응답이 p95[^7] 300ms 안에 온다(PRD 비기능 요구
  첫 줄, 상위 PRD의 화면 갱신 예산과 같은 값). 측정 절차는 테스트 시나리오의 "성능 측정"에 있다.

## API 명세

### GET /api/missions/{missionId}/videos

미션 영상 목록 조회. 신규 컨트롤러 `video/controller/MissionVideoController`에 둔다. 기존
`GridVideoController`에 얹지 않는 이유는 그 클래스가 "격자 하위 리소스"로 선언된 자리라 미션 경로가
섞이면 태그와 문서가 어긋나기 때문이다. 클래스 하나에 메서드 하나이고, 배치 근거는 MSG-127과 같다.

- **인증**: 토큰 필수(`SecurityConfig`의 `anyRequest().authenticated()`). 응답이 호출자와 무관하므로
  `AuthPrincipal` 파라미터는 받지 않는다(`/api/grids/{gridId}/cover`, `/videos` 선례).
- **경로 변수**: `missionId` (`long`)
- **쿼리 파라미터**
  - `cursor` (선택, opaque): 직전 응답의 `nextCursor`. 생략하면 첫 페이지다.
  - `size` (선택, 기본 20): 1 미만이면 20으로, 50 초과면 50으로 클램프한다. 격자 전역 목록과 같은
    상수(`GLOBAL_PAGE_DEFAULT_SIZE`, `GLOBAL_PAGE_MAX_SIZE`)를 그대로 쓴다. 코스처럼 무기간 미션의
    후보가 길어질 수 있어 상한이 필요하다는 PRD 엣지 케이스를 이 상한이 받는다.

**성공 응답** (`SuccessResponse`, developCode 200):

```json
{
	"developCode": 200,
	"message": "성공",
	"data": {
		"videos": [
			{
				"videoId": 1042,
				"thumbnailUrl": "https://.../thumb.jpg?X-Amz-Signature=...",
				"durationSec": 27,
				"viewCount": 1200,
				"recordedAt": "2026-07-20T18:03:11Z",
				"nickname": "busan.vlog"
			}
		],
		"hasNext": true,
		"nextCursor": "MTI6MTc4NDQ1NTgwMDAwMDAwMDoxMDM5"
	}
}
```

- 총 개수는 담지 않는다. 총계 없는 페이지(Slice 의미, MSG-90과 MSG-237 선례)를 유지하고, 화면 상단
  지표의 "올라온 영상 N개"와 목록 헤더의 "이 미션의 영상 N개"는 미션 상세 조회
  (`MissionDetailResponseDto`, 상위 PRD 배정)가 준다.
- 시안의 카드 요소와 응답 필드는 이렇게 대응한다. 썸네일과 중앙 재생 버튼은 `thumbnailUrl`과
  `videoId`, 우하단 길이 표기(`0:47` 형태)는 `durationSec`, 아래 한 줄의 작성자와 상대 시각과 조회수는
  `nickname`, `recordedAt`, `viewCount`다. `0:47` 같은 분초 표기와 "어제", "3시간 전" 같은 상대 시각
  문구는 클라이언트가 만든다. 목록 헤더 우측의 "최신순" 라벨도 고정 문구라 서버 재료가 없다.
- 빈 상태(축제 빈 상태 시안 `14460:1621`)는 `videos: []`, `hasNext: false`, `nextCursor: null`로 온다.
  존재하지 않는 미션 ID도 같은 응답이다(FR-11, FR-12).

**에러 케이스**

| 상황 | 응답 |
|------|------|
| 무효 커서(형식 위반, 성분 수 불일치, 정수 아님) | 400 `VideoErrorCode.INVALID_CURSOR` (3423) |
| 시각 성분이 저장 가능 범위 밖인 커서 | 400 `VideoErrorCode.INVALID_CURSOR` (3423) |
| 다른 미션에서 발급된 커서 | 400 `VideoErrorCode.INVALID_CURSOR` (3423) |
| 미인증 | 공통 401 |

에러 코드는 신설하지 않는다. mission 도메인은 developCode 대역이 미배정인데, 이 API에는 미션 존재
여부로 갈리는 실패가 없어(FR-12가 빈 목록으로 규정) 새 대역을 열 이유가 없다. 커서 오류는 video
대역의 기존 3423을 재사용한다. 무효 커서를 조용히 첫 페이지로 되돌리지 않는 것은 클라이언트 버그가
무한 첫 페이지 루프로 은폐되는 것을 막기 위해서다(MSG-237 §D5). 다른 미션의 커서도 같은 400인
이유는 경계값이 이 미션의 keyset[^2]에 오적용되어 결과가 조용히 잘리기 때문이고, 격자 목록이 다른
격자 커서를 거부하는 규칙과 같다.

**DTO**: 신규 없음. 항목은 `GridGlobalVideoResponseDto`, 페이지는 `GridVideoPageResponseDto`를
그대로 쓴다. 시안의 카드가 요구하는 값 여섯 개가 이 record의 필드와 정확히 일치하고, 팩토리
`of(video, thumbnailUrl, nickname)`도 그대로 맞는다.

재사용 결론은 유지하되 근거는 다시 따졌다. 두 DTO에는 격자 전용 문구가 필드 설명 두 곳 말고도 더
남아 있고, springdoc은 타입 하나의 스키마를 두 엔드포인트 문서에 함께 싣는다. 그대로 두면 미션 경로
문서가 "인기순"과 격자 4성분 커서 예시를 광고한다. 그래서 **공유 스키마에서는 엔드포인트마다 달라지는
사실(정렬 축, 커서 성분 형식과 예시)을 전부 걷어내고, 그 사실은 각 `@Operation` 설명에 둔다.** 이
방향이 맞는 근거는 격자 쪽이 이미 그렇게 하고 있다는 것이다. `GridVideoController`의 `@Operation`은
"조회수(viewCount) 최신(createdAt) 순으로 페이지 조회한다"와 커서 사용법, size 클램프 규칙을 이미
문장으로 담고 있다. 정렬 축이 DTO 설명에도 중복돼 있던 쪽이 예외였다.

중립화 대상 전수는 다음 여덟 곳이다. `@Schema`는 OpenAPI 문서에 실려 FE가 읽는 **계약**이고,
javadoc은 문서에 실리지 않아 **코드를 읽는 사람**만 본다. 그래도 사실이 아닌 서술을 남기지 않는다.

| 파일 | 위치 | 종류 | 지금 문구 | 조치 |
|------|------|------|----------|------|
| `GridGlobalVideoResponseDto` | 클래스 `@Schema` | 계약 | "격자 전역 영상 목록 항목" | "전역 공개 영상 목록 항목"으로 중립화 |
| `GridGlobalVideoResponseDto` | 클래스 javadoc | 가독성 | "그 격자에 쌓인 공개, READY 영상 하나를 브라우징 피드 행으로 표현한다" | 격자 전용 서술을 걷고 두 목록(격자와 미션)이 공유하는 항목이라고 적는다 |
| `GridGlobalVideoResponseDto` | `viewCount` | 계약 | "조회수, 인기순 정렬 근거" | 정렬 근거 문구 삭제, "조회수"만 남긴다 |
| `GridGlobalVideoResponseDto` | `recordedAt` | 계약 | "촬영 시각 (표시용). 정렬 tie-break 키는 createdAt 이다" | "촬영 시각"만 남기고 정렬 관련 서술 삭제 |
| `GridVideoPageResponseDto` | 클래스 `@Schema` | 계약 | "격자 전역 영상 목록 페이지 응답 (keyset 커서 페이지네이션)" | "전역 공개 영상 목록 페이지 응답 (keyset 커서 페이지네이션)" |
| `GridVideoPageResponseDto` | 클래스 javadoc | 가독성 | "videos 는 인기순(viewCount, createdAt, id DESC) 한 페이지" | 정렬 축은 엔드포인트가 정한다고 고쳐 적는다 |
| `GridVideoPageResponseDto` | `videos` | 계약 | "이 페이지의 전역 공개, READY 영상 (인기순). 없으면 빈 배열" | "(인기순)" 삭제 |
| `GridVideoPageResponseDto` | `nextCursor` | 계약 | `example`이 격자 4성분 커서 값 | `example` 속성 삭제. 값이 opaque라 예시의 쓸모가 작고, 성분 형식은 엔드포인트마다 다르다 |

두 엔드포인트의 `@Operation`은 각자 정렬 축과 커서 규칙을 문장으로 갖는다. 미션 쪽은 "촬영 시각
최신순"과 "커서는 이 미션 전용이며 다른 미션 커서는 400"을 적는다. 격자 쪽은 이미 있는 문장을 그대로
둔다.

DTO를 나누지 않은 이유는 그대로다. 필드 집합과 팩토리가 같아 복제하면 두 화면의 카드 모양이 나중에
조용히 어긋난다. 위 여덟 곳을 중립화하면 공유 스키마에 남는 것은 필드 여섯 개의 뜻뿐이고 그것은 두
화면에서 같은 사실이다. 항목 필드가 갈리는 날(예: 미션 목록에만 격자 표시명이 필요해지는 때)이 오면
그때 나눈다.

## 도메인 로직

**후보 술어(이 문서가 정본).** "이 미션의 영상"은 아래 조건을 전부 만족하는 `videos` 행이다.
미션 상세 조회의 영상 개수 집계도 같은 술어를 쓴다. 요구는 문자열 일치가 아니라 **술어 동등**이다.
별칭 유무(`v.status`와 `status`), 줄바꿈, 조건 순서는 달라도 되고 통과하는 행 집합이 같으면 된다.
문자열을 요건으로 걸지 않는 이유는 레포에 이미 두 표기가 공존하기 때문이다. `VideoRepository`의
격자 조회 3종은 별칭 없이 쓰고 탐색 쿼리는 `v.` 별칭을 붙인다. 표기로 판정하면 별칭 하나 차이에
리뷰가 오탐을 내고, 그런 규칙은 실제로 지켜지지 않는다. 리뷰에서는 조건을 항목별로 대조하고,
어긋남 자체는 아래 정합 테스트(같은 데이터에서 개수와 목록 길이가 같은지)가 잡는다.

```sql
JOIN mission_grids mg ON mg.grid_id = v.grid_id
JOIN missions m ON m.id = mg.mission_id
WHERE mg.mission_id = :missionId
  AND v.status = 'ACTIVE' AND v.visibility = 'PUBLIC' AND v.processing_status = 'READY'
  AND (m.start_at IS NULL OR v.recorded_at >= m.start_at)
  AND (m.end_at IS NULL OR v.recorded_at <= m.end_at)
```

- **영역 조건은 격자 조인 하나다.** `mission_grids`의 PK가 `(mission_id, grid_id)`라 한 미션 안에서
  격자가 한 번씩만 나오고, 영상은 `grid_id`를 하나만 가지므로 조인 팬아웃[^1]이 없다. `DISTINCT`가
  필요 없고, 같은 영상이 두 번 실리지도 않는다. 반대로 격자가 겹치는 두 미션의 목록에 같은 영상이
  각각 들어오는 것은 정상이며 중복 제거 대상이 아니다(PRD 엣지 케이스).
- **기간 조건은 `IS NULL OR` 형태 그대로.** 무기간 미션(코스와 지속형)은 조건이 자연히 생략되어
  코드 분기가 없다(FR-4). 경계는 양끝 포함이고 판정 쿼리와 같다. 비교 대상이 둘 다 저장 시각
  (UTC 벽시계)이라 존 변환이 필요 없다. 판정 쿼리가 `statement_timestamp() AT TIME ZONE 'UTC'`를
  쓰는 곳은 활성 미션을 고르는 단계이지 이 기간 비교가 아니다.
- **활성 여부는 보지 않는다.** 기간이 끝난 미션도 목록은 조회된다(FR-13). 완료한 미션을 나중에 다시
  열어 볼 수 있어야 해서다. 판정 경로의 후보 역조회(`findAwardCandidateIds`)에 있는 활성 조건은
  여기 오지 않는다.
- **전역 공개 게이트[^3]는 세 개를 함께 건다.** `status = 'ACTIVE'`, `visibility = 'PUBLIC'`,
  `processing_status = 'READY'`이며 소유자 분기가 없다. 내 PRIVATE 영상과 FRIENDS 영상은 나에게도
  나오지 않는다(비기능 요구 "응답은 누가 부르든 같다"). 이 세 조건은 `findGlobalCover`,
  `findGlobalVideos`, `countHourlyUploadsByGrid`의 게이트와 **술어 동등**이어야 한다. 그 셋은 별칭
  없이 쓰여 있고 이 쿼리는 조인이 있어 `v.` 별칭을 붙이므로 문자열은 애초에 다르다. 판정은 조건
  집합으로 한다.
- **판정과 목록의 차이는 의도된 것이다.** 스탬프 판정(`findCompleted`)은 `v.user_id = :userId`로
  내 영상만 보고 `v.status <> 'DELETED'`만 걸어 블라인드 영상도 촬영 사실로 인정한다. 목록은
  사용자 조건을 빼고 상태를 `= 'ACTIVE'`로 좁히며 공개범위와 처리 상태를 더 건다. 그래서 화면에
  보이는 영상 수가 판정 근거보다 작을 수 있다. 버그가 아니다.
- **팝업 판정 범위 축소의 여파도 정상 동작이다.** 반경 40m 전환으로 대상 격자가 줄면 목록에서
  빠지는 영상이 생긴다. 이미 발급된 스탬프는 회수하지 않으므로(SRS FR-MISSION-04) 스탬프는 남았는데
  목록이 빈 상태가 나올 수 있다. 목록은 항상 현재 `mission_grids` 기준으로 다시 계산되며, 미션의
  대상 격자가 바뀌면 다음 조회부터 반영된다(FR-14). 별도 집계 테이블이 없어 백필도 없다.

**정렬은 `recorded_at DESC, id DESC`다.** 미션 기간 판정이 촬영 시각을 쓰고 카드에 보이는 시각도
촬영 시각이라 세 곳을 한 축으로 맞춘 것이다(PRD §8). tie-break를 `id`로 잡은 이유는 PK라 값이 항상
유일해 두 키로 전순서가 완성되기 때문이다. `created_at`을 중간에 끼우면 키가 하나 늘 뿐 결정성은
그대로다. 촬영 시각은 클라이언트가 신고하는 값이라 확정 시점에 검사하는데, 그 검사는
`VideoServiceImpl.validateRecordedAt`이 서버 시각에 허용 오차 5분(`RECORDED_AT_TOLERANCE`)을 더한
값을 넘을 때만 `RECORDED_AT_IN_FUTURE`(3424)를 던지는 형태다. 그래서 미래 시각으로 목록 맨 위를
차지하는 것은 최대 5분 폭 안에서 제한적으로 가능하다. 그 오차는 단말 시계 스큐를 덮으려고 둔
것이고(MSG-278), 5분이면 목록 순서가 실질적으로 뒤집히지 않는다. 갤러리에서 오래된 영상을 올리면
목록 위가 아니라 중간에 꽂히는 것은 받아들인 손해다.

**정렬 키도 후보 집합도 불변이 아니고, 그로 인한 페이지 흔들림은 수용한다.** 영상
교체(`Video.replaceFile`)가 `recorded_at`을 새 파일의 값으로 갈아끼운다. 교체 중에는 처리 상태가
UPLOADED로 되돌아 READY 게이트에서 빠졌다가 재인코딩 후 다시 들어오는데, 그때 촬영 시각이 달라져
있을 수 있다. 1페이지에 나왔던 영상이 더 과거 시각으로 바뀌면 `(recorded_at, id) <` 조건에 다시 걸려
2페이지에 또 나오고, 더 최신으로 바뀌면 건너뛰어진다. 정렬 키가 그대로여도 같은 일이 생긴다. 공개범위
변경(PRIVATE에서 PUBLIC), 인코딩 완료, 삭제나 블라인드, 미션 격자 변경은 정렬값은 그대로 둔 채 후보
집합의 멤버십만 바꾸는데, 커서가 이미 지나친 지점에 새로 들어온 항목은 그 페이징에서 영영 보이지
않는다. 두 경우 모두 keyset 페이징이 살아 있는 데이터 위에서 도는 한 생기는 알려진 성질이지 이 설계의
결함이 아니다. 격자 전역 목록은 `view_count`가 재생마다 변해 같은 흔들림을 안고 있고 MSG-237이 이를
수용으로 문서화했다. 이 목록은 그보다 변화가 훨씬 드물다. 스냅숏 정렬이나 정렬 키 동결 같은 대안은
이 규모에서 과하다.

**페이지 조립은 격자 전역 목록과 같은 순서로 한다**(`VideoServiceImpl.getGridGlobalVideos` 패턴).

1. `size`를 클램프한다.
2. `size + 1`로 lookahead[^5] 조회한다.
3. 행 수가 `size`를 넘으면 `hasNext = true`로 두고 마지막 한 행을 잘라낸다.
4. 남은 행의 작성자 id를 중복 제거해 닉네임을 한 번에 조회한다(`findAuthorNicknames`). 페이지가
   커져도 DB 왕복은 두 번으로 고정된다.
5. 배치 결과에 작성자가 없는 항목은 응답에서 뺀다. 두 조회 사이에 탈퇴로 연쇄 삭제된 영상이라,
   닉네임이 빈 카드를 그리지 않기 위해서다(FR-15).
6. 썸네일은 항목마다 사전 서명 URL[^6]로 발급한다.
7. `nextCursor`는 5번에서 걸러내기 **전** 페이지의 마지막 행 기준으로 발급한다. 걸러낸 뒤 기준으로
   잡으면 숨긴 항목이 페이지 끝일 때 커서가 제자리에 멈춰 같은 페이지를 무한히 다시 읽는다.

이 패턴을 그대로 쓰는 근거는 두 목록이 커서 페이지, 배치 닉네임, presign까지 구조가 같기 때문이다.
다른 것은 정렬 축과 후보 술어뿐이고 그 둘은 리포지토리 쿼리에 있다.

**커서는 신규 record `MissionVideoCursor`를 video/support에 둔다.** 현행 `VideoCursor`는
`(gridId, viewCount, createdAt, id)` 네 성분이라 성분 수와 의미가 둘 다 다르다. 여기 성분을 더하거나
뜻을 바꾸면 이미 발급된 격자 목록 커서가 깨지고 기존 경로를 함께 손봐야 한다. `VideoCursor`는
무수정으로 두고, 형식과 규칙만 그대로 물려받은 record를 하나 더 만든다.

- 원문 `"{missionId}:{recordedAtEpochMicros}:{id}"`를 Base64URL(패딩 없음)로 감싼 opaque 토큰이다.
- 시각은 ISO 문자열이 아니라 epoch 마이크로초 정수로 싣는다(`recorded_at`의 마이크로초 정밀도 보존).
  존 없는 `LocalDateTime`이라 변환은 UTC 고정이며, encode와 decode가 같은 존이면 대칭이라 JVM 기본
  존에 따라 값이 갈리는 것만 막으면 된다.
- **시각 성분의 허용 범위를 디코드 단계에서 명시적으로 검증한다. 판정선은 PostgreSQL `timestamp`가
  저장할 수 있는 범위다.** 복원된 시각이 기원전 4713년(ISO 연도 -4712)부터 서기 294276년 사이 밖이면
  무효 커서로 떨어뜨린다. 이 검증이 없으면 구멍이 생긴다. `LocalDateTime`이 받아들이는 연도 범위는
  대략 ±999999999라 `Long.MIN_VALUE` 마이크로초(연도 약 -290308) 같은 값이 예외 없이 통과하는데, 그
  값을 쿼리에 바인딩하면 실행 단계에서 깨진다. 그 시점은 디코드 try-catch 밖이라 400으로 변환되지
  못하고 공통 500이 된다. **이 검증의 목적은 DB까지 흘러가 500이 나는 입력을 400으로 바꾸는 것이지
  정상 값을 거르는 것이 아니다.**
- **실제로 검사할 값은 하한 하나뿐이다.** 상한은 `long`으로 표현할 수 없다. PostgreSQL 상한
  (`294276-12-31 23:59:59.999999`)을 epoch 마이크로초로 환산하면 `9224318015999999999`인데 이 값이
  `Long.MAX_VALUE`(`9223372036854775807`)보다 크다. 토큰의 시각 성분은 `long`이라 상한을 넘는 값이
  애초에 실릴 수 없고, `Long.MAX_VALUE` 마이크로초는 서기 294247년이라 저장 가능 범위 **안**이다.
  그래서 상한 검사는 도달 불가능한 죽은 코드이고 그것을 겨냥한 테스트도 만들 수 없다.
- **하한은 숫자 리터럴이 아니라 뜻으로 적는다.** 경계는 ISO `-4712-01-01T00:00:00`(곧 기원전 4713년
  1월 1일)이고 마이크로초로는 `-210863520000000000`이다. 코드에는 상수 대신
  `LocalDateTime.of(-4712, 1, 1, 0, 0)` 비교를 두고 숫자는 주석에만 병기한다. 이 자리에 손으로 계산한
  숫자를 넣으면 하루가 어긋나도 알아채기 어렵고, 하루만 넓어져도 가드가 막으려던 구간이 그대로
  열린다(초안이 실제로 `-210863606400000000`을 적었는데 그 값은 ISO `-4713-12-31T00:00`이다).
  실측 확인(pgjdbc 42.7.11 + PostgreSQL 16): ISO `-4712-01-01T00:00`은 `4713-01-01 00:00:00 BC`로
  정상 저장되고, 그보다 이른 값은 `setObject(LocalDateTime)` 경로에서 **예외 없이 `-infinity`로
  조용히 바뀌거나** `setTimestamp` 경로에서 `PSQLException: timestamp out of range`가 된다.
  조용한 `-infinity`가 특히 위험하다. 경계값이 엉뚱하게 적용돼 빈 페이지가 나가면서 실패로 보이지도
  않는다. `Long.MIN_VALUE` 마이크로초(ISO 연도 -290308)가 그 경로다.
- **원칙: 커서 수용 범위는 항상 발급 가능 범위 이상이어야 한다.** 좁히면 정상 페이징이 막힌다.
  초안은 판정선을 네 자리 연도 창으로 잡았는데 그것이 이 원칙을 어겼다. 업로드 경로의
  `validateRecordedAt`은 미래만 막고 과거 하한이 없어서 연도 0 이하인 `recorded_at`도 저장될 수 있고,
  그런 행이 첫 페이지 경계가 되면 서버가 그 값으로 `nextCursor`를 발급한 뒤 다음 요청에서 자기가
  발급한 토큰을 거부하게 된다. 그 미션의 2페이지 이후가 통째로 막히는 결함이다. 판정선을 저장 가능
  범위에 맞추면 발급 가능한 모든 값이 수용 범위 안에 들어와 이 구간이 사라진다.
- `missionId` 성분은 발급 미션 바인딩이다. 서비스가 요청 `missionId`와 대조해 다르면 400으로 거부한다.
- 디코드 실패는 `IllegalArgumentException`, 위 범위 위반도 같은 예외로, 시각 복원 자체가 실패하는
  극단값은 `DateTimeException`으로 표면화한다. 셋 다 `RuntimeException`이라 서비스가 한 번에 잡아
  `INVALID_CURSOR`로 바꾼다. 결과적으로 커서 관련 실패는 어떤 입력이든 400 하나로 수렴한다.

## 데이터 모델

**변경 없음. 마이그레이션 없음. 되돌리기는 엔드포인트를 걷어내는 것으로 끝난다.**

`VideoRepository`에 native 쿼리 두 개를 추가한다. 커서 유무로 메서드를 나누는 것은 null 파라미터의
타입 추론 문제를 피하는 기존 관례다(`findGlobalVideos`와 `findGlobalVideosAfter`, MSG-90 선례).

```sql
-- 첫 페이지
SELECT v.* FROM videos v
JOIN mission_grids mg ON mg.grid_id = v.grid_id
JOIN missions m ON m.id = mg.mission_id
WHERE mg.mission_id = :missionId
  AND v.status = 'ACTIVE' AND v.visibility = 'PUBLIC' AND v.processing_status = 'READY'
  AND (m.start_at IS NULL OR v.recorded_at >= m.start_at)
  AND (m.end_at IS NULL OR v.recorded_at <= m.end_at)
ORDER BY v.recorded_at DESC, v.id DESC
LIMIT :limit
```

```sql
-- 커서 이후 페이지 (위 쿼리에 경계 조건 한 줄 추가)
  AND (v.recorded_at, v.id) < (:cursorRecordedAt, :cursorId)
```

경계 비교는 PostgreSQL의 row-value 비교다. 정렬이 둘 다 DESC라 "정렬상 뒤"가 `<` 하나로 표현되고,
격자 전역 목록이 세 성분으로 쓰는 것과 같은 형태다.

**인덱스는 신설하지 않는다.** 예상 실행 계획은 이렇다. `mission_grids`의 PK `(mission_id, grid_id)`가
선두 컬럼 등치로 그 미션의 격자만 훑고(축제 81칸, 코스 5칸에서 8칸, 팝업 1칸에서 4칸), 격자마다
`idx_videos_grid_popular`를 `grid_id` 선두로 프로브한다. 이 부분 인덱스[^4]가 쓰이는 근거는 쿼리와
인덱스의 WHERE 문자열이 같아서가 아니라, 쿼리 조건이 인덱스 술어를 **함의**하기 때문이다.
PostgreSQL은 부분 인덱스를 술어 함의로 매칭하므로 별칭 표기나 조건 순서가 달라도 조건이 같은 뜻이면
인덱스를 쓴다. 반대로 말하면 문자열 대조는 인덱스 사용 여부를 증명하지 못한다. 확인 수단은
`EXPLAIN (ANALYZE, BUFFERS)` 실행 계획이며, 결과는 구현 후 작업 로그에 남긴다. 인덱스의 나머지 정렬
컬럼은 조회수 축이라 촬영 시각 정렬을 만족시키지 못하므로 뒤에 정렬 단계가 붙지만, 대상 행이 적어
비용이 무시할 수준이다. 근거는 실측이다. 미션 격자는 전체 32,903행인데 영상이 하나라도 있는 칸은
24칸(0.1%)이라 대부분의 조회는 격자 프로브 몇십 번과 빈 결과로 끝난다.

한계도 같이 적는다. 커서 조건이 인덱스 지원을 받지 못해 페이지를 깊이 넘길수록 후보 행을 다시 훑는다.
지금 규모에서는 후보 자체가 수십 행이라 문제가 아니다. 미션 하나의 후보 행이 수천 단위로 커지거나
성공 기준의 그 값(첫 페이지 p95 300ms)을 넘기면 그때
`CREATE INDEX ... ON videos (grid_id, recorded_at DESC) WHERE 게이트 세 조건`을 추가한다. 지금 만들면
쓰이지 않는 인덱스가 모든 업로드의 쓰기 비용만 늘린다.

성능 측정 (재현 가능하게, 결과는 작업 로그)

1. **대상 선정.** 유효 영상(후보 술어를 통과하는 영상)이 가장 많은 축제 미션을 고른다. 나온
   `mission_id`와 `valid_videos`를 작업 로그에 적어 다음 측정이 같은 대상을 쓰게 한다.

   ```sql
   SELECT mg.mission_id, COUNT(v.id) AS valid_videos
   FROM mission_grids mg
   JOIN missions m ON m.id = mg.mission_id
   JOIN videos v ON v.grid_id = mg.grid_id
     AND v.status = 'ACTIVE' AND v.visibility = 'PUBLIC' AND v.processing_status = 'READY'
     AND (m.start_at IS NULL OR v.recorded_at >= m.start_at)
     AND (m.end_at IS NULL OR v.recorded_at <= m.end_at)
   WHERE m.source = 'FESTIVAL'
   GROUP BY mg.mission_id
   ORDER BY valid_videos DESC, mg.mission_id
   LIMIT 1
   ```

   `source` 필터가 필요한 이유는 팝업 시더가 아직 9×9 고정이라(반경 40m 전환은 상위 PRD의 미구현
   항목) 팝업 미션도 81칸이고, 필터 없이는 축제라 적어 놓고 팝업을 뽑을 수 있어서다. `'FESTIVAL'`은
   `FestivalMissionSeeder.SOURCE_FESTIVAL` 값이다. tie-break로 `mission_id` 오름차순을 붙인 것은
   동률일 때 실행마다 다른 미션이 뽑혀 재현성이 깨지기 때문이다. 재현성이 이 절을 둔 이유다.
2. **측정 전 확인(생략 불가).** 위 `valid_videos`가 `size + 1`(기본 규격에서 21) 이상인지 본다.
   미달이면 그 대상 미션의 격자에 합성 영상을 시드해 21건을 채운 뒤 측정한다(합성 영상도 후보 술어를
   통과하도록 상태, 공개범위, 처리 상태, 촬영 시각을 맞춘다). **이 확인을 통과하지 못한 측정 결과는
   p95 판정 근거로 쓰지 않는다.** 이 단계를 넣는 이유는 실측 분포 때문이다. 미션 격자 32,903행 중
   영상이 있는 칸이 24칸(0.1%)이라 그냥 재면 빈 페이지를 재게 되고, presign 스무 번과 커서 쿼리
   비용을 한 번도 재지 않은 채 p95가 통과한다. 검증 절차가 검증을 안 하게 된다.
3. **첫 페이지 측정.** `size=20`, `cursor` 없음으로 워밍업 10회 후 **100회** 호출해 응답 시간의
   95번째 백분위를 낸다. `EXPLAIN`은 백분위를 재지 못하므로 실행 계획 확인과 별개로 이 호출 측정을
   한다. 판정은 성공 기준의 p95 300ms다.
4. **두 번째 페이지 측정.** 첫 페이지가 가득 차 `hasNext`가 true여야 성립한다(2단계가 이 전제를
   보장한다). 받은 `nextCursor`로 한 번 재어 커서 페이지의 열화 정도를 기록해 둔다. 인덱스 추가
   트리거를 나중에 판단할 재료다.

`load-test/`의 기존 스크립트 관례(단일 셸 스크립트, 결과는 사람이 읽는 요약)를 따르고 새 하네스는
만들지 않는다. 대상 규모가 작아 그 이상이 필요 없다.

티켓 경계를 넘는 인계가 셋 있다.

- 미션 상세 조회의 영상 개수 집계는 상위 PRD가 배정한 별도 작업인데, 그 쿼리는 이 문서 "후보 술어"
  블록과 술어 동등이어야 한다. 그 티켓의 리뷰에서 조건을 항목별로 대조하고, 위 정합 테스트(목록 길이와
  개수 일치)를 완료 조건으로 삼는다.
- 기존 `VideoCursor`(격자 목록)에도 시각 성분 범위 구멍이 같은 형태로 있다. 그 javadoc은 "epoch 범위
  밖 시각 성분은 DateTimeException 으로 표면화한다"고 적고 있으나, `LocalDateTime`은 받아들이는데
  PostgreSQL은 못 담는 중간 구간에서는 그 서술이 정확하지 않다. MSG-237 영역이라 이 티켓에서 손대지
  않는다. 후속 판단 재료로만 남긴다.
- 업로드 확정의 `validateRecordedAt`에는 **과거 하한이 없다.** 미래만 막으므로 연도 0 이하 같은 값도
  저장될 수 있고, 그런 데이터는 목록 맨 아래에 영구히 남는다. 이 티켓은 커서 수용 범위를 저장 가능
  범위에 맞추는 것으로 페이징 문제만 닫았고, 입력 검증 자체는 video 업로드 경로의 별도 판단거리로
  남긴다.

**무수정 확인.** `mission/**` · `grid/**` · `SecurityConfig` · `VideoCursor` · `GridVideoController`. 마이그레이션 0, 신규 developCode 0(`VideoErrorCode.INVALID_CURSOR` 3423 재사용), 엔티티 변경 0이라 연관관계 매핑 신설도 없다.

**구현 중 뒤집힌 결정 하나.** 스펙이 커서 하한을 숫자 리터럴 `-210863606400000000`으로 적었는데 그 값은 ISO `-4713-12-31T00:00`이라 의도한 경계보다 하루 이르다. 하루 넓어진 만큼 PostgreSQL이 저장하지 못하는 구간이 열려 가드가 무력해진다. 코드는 리터럴 대신 `LocalDateTime.of(-4712, 1, 1, 0, 0)` 비교로 뜻을 담았고, 스펙 문구도 그에 맞춰 고쳤다. 손계산한 epoch 상수를 스펙에 박는 방식 자체가 실패 지점이었다.

**리뷰 결과.** convention-reviewer가 후보 술어 항목별 대조 · 정렬과 커서 · DTO 중립화 8곳 · 경계 · 시각 컨벤션 · 가짜 완료를 전수 확인해 블로킹 위반 0으로 통과시켰다. Codex 교차 리뷰(working-tree 스코프)도 1라운드에서 지적 0건. 리뷰어가 구현 **전에** 스펙 결함 하나를 잡아낸 것이 이번 실행의 가장 큰 소득이다(`Long.MAX_VALUE` 400 기대 케이스가 스펙 자신의 판정선과 모순이라 통과시키려면 금지된 회귀를 저질러야 했다).

#### 런타임 동작

**데이터 저장 위치.** 새로 쓰는 곳이 없다. 읽기 전용으로 `videos` · `mission_grids` · `missions` · `users`(닉네임 배치)를 본다. 마이그레이션이 없어 스키마도 그대로다.

**실행 쿼리.** 요청당 DB 왕복 2회로 고정된다. 목록 native 1회 + 닉네임 JPQL `IN` 1회이고, 빈 페이지면 닉네임 조회를 건너뛰어 1회다. 썸네일 사전 서명은 로컬 서명이라 왕복이 없다. 첫 페이지 원문은 아래이고, 이어받기 쿼리는 여기에 `AND (v.recorded_at, v.id) < (:cursorRecordedAt, :cursorId)` 한 줄만 더한다.

```sql
SELECT v.* FROM videos v
JOIN mission_grids mg ON mg.grid_id = v.grid_id
JOIN missions m ON m.id = mg.mission_id
WHERE mg.mission_id = :missionId
  AND v.status = 'ACTIVE' AND v.visibility = 'PUBLIC' AND v.processing_status = 'READY'
  AND (m.start_at IS NULL OR v.recorded_at >= m.start_at)
  AND (m.end_at IS NULL OR v.recorded_at <= m.end_at)
ORDER BY v.recorded_at DESC, v.id DESC
LIMIT :limit
```

관측된 실행 계획은 스펙이 예상한 "격자별 프로브"와 형태가 다르다. 합성 5만 행에서 `mission_grids_pkey` Index Only Scan과 `idx_videos_grid_popular` Index Scan의 **merge join**이 선택됐다(첫 페이지 20.8ms, 커서 페이지 20.2ms). 구속력 있는 조건 두 개는 지켜졌다. 신규 인덱스 0개이고 두 인덱스가 실제로 쓰인다. merge join은 플래너의 비용 선택이라 위반이 아니다. 다만 합성 분포가 한 사용자에 5,000칸 균등이라 실제 분포(미션 격자 32,903칸 중 영상 있는 칸 24칸, 0.1%)와 통계가 달라 이 계획이 운영 계획을 예측하지는 못한다.

**예외 흐름.** `MissionVideoCursor.decode`가 던지는 `IllegalArgumentException`(Base64 불량 · 성분 수 불일치 · 정수 아님 · 시각 하한 미만)과 `DateTimeException`을 `VideoServiceImpl.decodeMissionCursor`가 잡아 `ApiException(VideoErrorCode.INVALID_CURSOR)`로 바꾼다. 요청 `missionId`와 커서의 미션이 다른 경우는 `queryMissionPage`가 같은 예외를 직접 던지며, 이 자리는 `catch (RuntimeException)` 밖이라 이중 래핑되지 않는다. 셋 다 `GlobalExceptionHandler`가 400 + developCode 3423으로 변환한다. 미인증은 컨트롤러에 닿기 전 시큐리티 필터의 공통 401이다.

**빈 동작.** `MissionVideoController`(싱글턴)에서 `VideoServiceImpl.getMissionVideos`로 들어가는 지점이 `@Transactional(readOnly = true)` 프록시 경계다. 목록 조회와 닉네임 조회가 한 트랜잭션(READ COMMITTED) 안에 있어, 두 문장 사이에 작성자가 탈퇴하면 그 항목만 응답에서 빠지고 `nextCursor`는 **숨긴 행을 포함한 트림 전 마지막 행** 기준으로 발급된다(같은 페이지를 무한히 다시 읽는 것을 막는 기존 규칙). 스케줄러 · 자체 executor · 생명주기 훅은 없고, 시각을 새로 만들지 않아 `Clock` 주입도 없다.

#### 미완료로 남긴 것

**첫 페이지 p95 300ms를 측정하지 못했다.** 로컬 DB에 `videos` 0행 · `grids` 0행이라(미션 시드만 적재: `missions` 715, `mission_grids` 46,873) 스펙 성능 측정 절차의 1단계 대상 선정 쿼리가 0행을 반환한다. 2단계 "유효 영상 `size + 1`건 확보"는 커밋된 합성 데이터와 앱 기동이 필요해 공유 dev DB를 오염시킨다. 스펙이 "확인을 통과하지 못한 측정은 p95 판정 근거로 쓰지 않는다"고 정해 두었으므로, 위 합성 20.8ms는 p95가 아니고 판정 근거도 아니다. **시드가 있는 dev 환경에서 측정하는 항목으로 남긴다.**
