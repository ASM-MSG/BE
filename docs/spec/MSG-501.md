# MSG-501: 행사 운영자가 참여할 승인 이벤트를 시·도로 골라잡는다 (승인 이벤트 목록 조회)

**Owner**: B (event 도메인은 Owner B다. CLAUDE.md 협업 원칙의 `com.msg.fillmap.event.*` 배정 기준이고,
Owner A 계약 인터페이스는 하나도 건드리지 않는다)

> 요구사항 정본: `docs/prd/event-submission.md` (상태 검토됨, 2026-08-28 승인). 이 스펙은 그중
> 등록 유형 "이벤트"(v2.1 재편, 구 세 번째 유형)의 선택 모달이 쓰는 조회 재료를 다룬다.
> 전역 요구사항 ID는 **SRS FR-EVENT-16**(진행 중, MSG-501)이고 PRD FR-26이 같은 요구다.
> 유형 표 개정은 MSG-498 몫이고, 이 브랜치는 모달 조회 FR과 API 표면만 최소 개정했다.
> 용어는 지라 코멘트 10812가 최종이다: **이벤트 = 지역축제와 팝업스토어를 제외한 큰 행사
> 카테고리**이고, 모달이 나열하는 상위가 곧 승인 이벤트다.

## 개요

행사 운영자[^1]가 콘솔에서 등록 유형 "이벤트" 카드를 누르면 모달이 열린다. 시·도 칩을 골라
그 지역의 승인 이벤트 목록을 보고, 이름으로 검색하고, 하나를 골라 참여 신청(MSG-502, 비범위)으로
넘어간다. 이 티켓은 그 모달의 재료인 **승인 이벤트 목록 조회 API 하나**를 만든다. 조회 전용이고
쓰기가 없다.

## 배경 · 목표

- v2.1 재편으로 세 번째 등록 유형은 독립 행사 신설이 아니라, 이미 승인된 큰 이벤트를 골라 그
  아래에 하위 위치를 추가하는 참여형 구조가 됐다(PRD 미해결 질문 1의 2026-08-28 작성자 설명).
  고를 부모 목록을 주는 API가 아직 없다. [관리자 4] 서버 재료 프레임은 이 API가 없는 구판이라
  계약은 이 스펙이 신설한다.
- 목표: ORG 토큰 하나로 모달 화면(시·도 칩, 건수, 검색, 목록 항목)이 조립되는 응답을 한 번의
  호출로 준다.

## 성공 기준

1. ORG 토큰으로 호출하면 종료 전 이벤트만 실린 목록이 온다. 아카이브됐거나 업로드 유예 중인
   (이미 종료된) 회차는 실리지 않는다.
2. 시·도 필터와 이름 검색이 동작하고, 시·도별 건수는 검색어와 무관한 전체 기준으로 실린다
   (칩은 내비게이션이라 검색 중에도 건수가 흔들리지 않는다).
3. 항목마다 이벤트 이름, 기간, 장소 라벨, 시·도가 실린다(시안 실측 항목).
4. 비로그인은 401, USER와 ADMIN 토큰은 403이다(MSG-496 matcher 실경로).
5. 아래 테스트 시나리오가 전부 green이다.

## 스펙 확정 3건

### ① "승인 이벤트"는 회차(EventOccurrence)다

모달 항목이 요구하는 값이 전부 회차[^2]에 있다. 기간(`starts_at`, `ends_at`)과 시·도(`city_name`)는
`event_occurrences` 컬럼이고, 장소 라벨의 재료인 위치(`event_locations`)도 회차를 FK로 참조한다.
시리즈(`event_series`)는 자연키와 이름뿐이라 목록 항목을 만들 수 없다. 참여 신청(MSG-502)이
붙일 하위 위치도 `event_locations.event_occurrence_id` 구조상 부모가 회차여야 하고, 회차 미혼합
원칙(FR-EVENT-07)과도 같은 방향이다. 응답의 식별자는 `occurrenceId`이고 MSG-502가 이 값을
부모 참조로 받는다.

"승인된 이벤트만 노출"의 현재 해석: 지금 `event_occurrences`의 모든 행은 팀이 직접 고른
시드분 회차 4건(biff-busan-2026, busan-fireworks-2026, seoul-fireworks-2026,
lol-national-team-busan-2026)이라 전부 노출 대상이다. 별도 승인 플래그는
만들지 않는다. MSG-500 승인이 만드는 회차는 같은 테이블에 들어와 자연 합류하고, 관리자 노출
중지(FR-20)가 구현되면 그 티켓이 이 조회에 제외 조건을 더한다(접점 명시, 이 티켓 비범위).

### ② 시·도 분류는 `event_occurrences.city_name`에서 얻는다

회차가 이미 시·도 문자열을 갖고 있고(`city_name VARCHAR(30) NOT NULL`), 기존 지도 홈 칩
API(MSG-439)도 FE가 이 값으로 시 칩을 묶는 계약이다(`EventOccurrenceChipResponseDto` 주석 명문).
같은 값을 그대로 쓴다. 대표 격자에서 `region_code`를 거슬러 행정구역 테이블로 조인하는 안은
기각한다: 조회마다 조인이 늘어나는데 회차에 이미 답이 저장돼 있다.

주의 사항 하나. 시드 저장값은 "부산", "서울" 축약형인데 시안 칩 문구는 "부산광역시"다. 응답은
저장값을 그대로 실어(기존 칩 API와 동일 계약), 정식 명칭 라벨이 필요하면 FE 표기 몫이거나 시드
데이터 개정 몫이다. 시드를 고치면 기존 칩 API 응답값도 함께 바뀌므로 이 티켓에서 건드리지 않는다.

### ③ 부모는 이벤트 카테고리만이다 (결정 D-3, 사용자 확정 2026-08-28)

모달 목록에는 **이벤트 카테고리(지역축제와 팝업스토어를 제외한 큰 행사)의 승인분만** 나온다.
지금 `event_occurrences`의 전 행이 이 카테고리라 쿼리에 구분 조건이 없고, 유형 컬럼도 배지
필드도 만들지 않는다(전 항목이 이벤트라 배지가 상수다). 시안 목록의 지역축제, 팝업스토어
배지는 **구판 잔재로 정리됐다**.

기각된 대안(B안, 세 유형 전부 부모): `event_series`에 `category VARCHAR(20)` 컬럼을 신설해
시드 행을 EVENT로 백필하고, 응답에 `category` 배지 필드를 실으며, MSG-500 approve가 승인
유형을 기록하는 접점을 만드는 안이었다. 기각 이유는 지역축제 승인분 아래에 또 참여 위치가
붙는 구조가 되어 "이벤트 참여형" 유형 정의와 충돌하기 때문이다. 지역축제와 팝업 승인분이
언젠가 `event_occurrences`에 들어오는 시점(MSG-500 노출 방식 확정, PRD 미해결 질문 1)에는
구분 컬럼이 필요해지는데, 그때 그 티켓이 추가한다(이 조회의 필터 조건 추가 접점 포함).

## API 명세

### `GET /api/org/events` : 승인 이벤트 목록 조회

경로 근거: `/api/org/**` 프리픽스는 확정 계약이다(MSG-496 결정 기록 1, PRD 7절). 이 프리픽스
아래는 ORG 콘솔 전용이라 "승인됨"이 전제이므로 `approved-events` 같은 수식이 불필요하고,
MSG-502의 참여 신청이 `/api/org/events/{occurrenceId}` 하위로 자연 확장된다.

**SecurityConfig는 무변경이다.** MSG-496이 넣은 `requestMatchers("/api/org/**").hasRole("ORG")`
matcher가 이 경로를 이미 덮는다(실측 SecurityConfig 176행). 비로그인 401, USER 403이 보장되고,
ADMIN도 403이다(관리자에게 열지 않는 결정은 MSG-496 주석 명문). catch-all[^3]이 역할 제한이라
신규 경로의 별도 등록은 프리픽스 밖일 때만 필요한데 이 경로는 프리픽스 안이다.

쿼리 파라미터 (둘 다 선택):

| 파라미터 | 타입 | 의미 |
|---|---|---|
| `city` | String | 시·도 필터. `city_name` 저장값과 정확 일치. 생략하면 전체 보기. 없는 값이면 빈 목록(에러 아님) |
| `name` | String | 이벤트 이름 검색. `title` 부분 일치, 대소문자 무시. 생략하면 전체 |

응답 `OrgEventListResponseDto`:

```json
{
	"totalCount": 4,
	"cityCounts": [
		{ "cityName": "부산", "count": 3 },
		{ "cityName": "서울", "count": 1 }
	],
	"events": [
		{
			"occurrenceId": 1,
			"name": "부산국제영화제",
			"cityName": "부산",
			"startsAt": "2026-10-06T01:00:00Z",
			"endsAt": "2026-10-15T13:00:00Z",
			"placeLabel": "영화의전당"
		}
	]
}
```

- `totalCount`와 `cityCounts`는 **필터와 검색을 적용하지 않은 전체 기준**이다. 시안의
  "부산광역시 · 승인 이벤트 3건" 칩과 "전체 보기" 칩의 재료이고, 검색 중에도 칩 건수가 변하지
  않아야 내비게이션 구실을 한다. `cityCounts` 정렬은 건수 내림차순, 동수는 이름 오름차순이다.
- `events`에만 `city`와 `name`이 적용된다. 정렬은 `startsAt` 오름차순(가까운 이벤트 먼저)이고,
  시작 시각이 같으면 `occurrenceId` 오름차순이다(동일 시각 회차의 순서 비결정 방지).
  페이지네이션은 두지 않는다(콘솔은 내부 소수 사용자 대상이고 PRD 비기능 성능 절이 별도 목표를
  두지 않는다. 승인 이벤트는 시드 4건에 승인분이 더해지는 수십 건 규모다).
- `name` 필드의 원천은 `event_occurrences.title`이다(칩 API 선례와 동일. 시리즈 이름이 아니라
  회차 제목이 사용자 대면 이름이다). 검색 대상도 같은 컬럼이라 보이는 이름과 찾는 이름이
  어긋나지 않는다.
- `placeLabel`(장소 라벨)은 그 회차의 `event_locations` 중 **`display_order` 최소, 같으면 `id`
  오름차순인 첫 위치**의 `name`이다. DDL이 `display_order INTEGER NOT NULL DEFAULT 0`이고
  유니크 제약이 없어 한 회차 안 동순위가 성립하므로(기본값 0이라 오히려 흔하다) 2차 키로
  `id`를 확정한다(MSG-439 위치 목록 정렬 계약과 같은 2차 키). 위치가 없는 회차면 null이다
  (시드와 승인 흐름상 항상 1개 이상이지만 DDL이 강제하지 않으므로 계약에 명시한다).
  **FE 계약상 이 값은 장소명일 수도, 지역 라벨일 수도 있는 표시 문자열이다.** 시안 예
  "벡스코 제1전시장"은 위치 이름이 저장된 시드분 기준이고, 승인 흐름산 회차는 사정이 다르다.
  신청자는 위치에 이름을 붙이지 않으므로(FR-8, 순번과 지역 라벨로만 식별)
  `event_locations.name`(NOT NULL)에 넣을 신청자 입력 재료가 없고, 채움 규칙이 아직 미정의다.
  **MSG-500 approve가 name 채움 규칙(예: 대표 격자의 지역 라벨 저장, 또는 순번 라벨)을 정의해야
  이 계약이 승인분에서도 성립한다.** 노출 중지(FR-20)와 같은 성격의 MSG-500 접점으로 명시해
  두며, 부모 범위 결정(D-3)과는 별개 항목이다.
- `startsAt`, `endsAt`은 `LocalDateTime`으로 UTC `Z` 코덱을 탄다(시각 컨벤션, 칩 API와 동일).
  기간의 날짜 라벨 변환은 FE 몫이다.
- 유형 배지 필드는 싣지 않는다. 전 항목이 이벤트 카테고리라 배지가 상수다(결정 D-3).

에러 케이스: 신규 없음. 인증 실패 401과 역할 불일치 403은 공통 경로(ErrorCode)이고, 파라미터는
자유 문자열이라 형식 위반이 성립하지 않는다(없는 city는 빈 목록).

## 도메인 로직

### 노출 조건: 종료 전 회차만 (결정 D-1)

`ends_at > now`인 회차만 싣는다. 파생 상태[^4]로 말하면 UPCOMING과 LIVE다. UPLOAD_GRACE는
이미 종료된 행사라 지금 참여를 신청해도 심사를 거치면 열 자리가 없고, ARCHIVED는 읽기 전용
기록이다. 판정은 기존 `EventOccurrence.statusAt`을 재사용하지 않고 저장 컬럼 조건
(`endsAt > :now`)으로 DB에서 거른다. 파생 상태 네 값 중 두 값의 경계가 정확히 `ends_at`
하나라서 조건 한 줄과 등가이고, 전량을 읽어 메모리에서 상태 계산할 이유가 없다.
`now`는 주입받은 `Clock`에서 얻는다(인자 없는 `now()` 금지 컨벤션).

### 노출 시작 전 예정 회차도 콘솔에는 보인다 (결정 D-2)

일반 유저 조회의 노출 판정(`isVisibleAt`, 시작 2주 전부터)은 이 API에 적용하지 않는다. 그
술어는 유저 지도에서 미공개 행사의 존재를 은닉하는 장치인데, 행사 운영자는 심사로 걸러진 소수
파트너이고 참여 신청과 재심사에 시간이 걸리므로 노출 시작 전에 미리 골라 신청할 수 있어야
흐름이 성립한다. 시작 2주 전까지 부모를 고를 수 없다면 참여분 위치가 행사 시작에 못 맞는다.

### 조회 조립

1. `EventOccurrenceRepository`에 파생 쿼리 하나를 더한다: `findByEndsAtAfter(LocalDateTime now)`.
   시리즈 조인은 필요 없다(응답이 시리즈 값을 쓰지 않는다).
2. 시·도 필터, 이름 검색(소문자 변환 contains), 시·도별 집계, 정렬은 애플리케이션에서 한다.
   후보 집합이 수십 건 규모라 쿼리를 세 갈래로 나눌 이유가 없고, DB 기능 최소화라는 멘토 권고
   방향과도 맞는다. 전체 기준 집계와 필터 적용 목록이 같은 후보 집합 한 번의 조회에서 나온다.
3. 장소 라벨은 회차 id 컬렉션으로 `EventLocationRepository`에서 위치를 일괄 조회한 뒤 회차별
   `display_order` 오름차순, 동순위면 `id` 오름차순 첫 행의 `name`을 취한다(루프 안 지연 로딩
   금지, 쿼리 총 2회로 고정).
4. 배치는 기존 event 패키지다: `event/controller/OrgEventController` 신규,
   `EventQueryService`에 조회 메서드 1개 추가(기존 인터페이스와 Impl 확장. 콘솔 조회지만
   승인 이벤트라는 기존 엔티티의 읽기라 신규 서비스 분리는 과하다), DTO 3종 신규
   (`OrgEventListResponseDto`, `OrgEventCityCountResponseDto`, `OrgEventItemResponseDto`).

## 테스트 시나리오

JUnit 5와 AssertJ, 한국어 백틱 메서드명. 구현 시 `// 검증: FR-EVENT-16` 주석으로 전역 요구사항

ORG_토큰이면_200과_목록_필드가_온다()                     // totalCount·cityCounts·events 존재 검증

// 노출 조건 (결정 D-1, D-2 / 검증: FR-EVENT-16)

종료_후_유예_중인_이벤트는_실리지_않는다()                // ends_at 경과, UPLOAD_GRACE 제외
아카이브된_이벤트는_실리지_않는다()
노출_시작_전_예정_이벤트도_콘솔_목록에는_실린다()         // visible_from 미적용 (D-2)

// 필터와 검색 (검증: FR-EVENT-16)
시도_필터를_주면_그_시도_이벤트만_온다()

// 항목 조립
장소_라벨은_첫_위치의_name_저장값_그대로다()              // display_order 최소 행. 시드분은 장소명이고,

display_order가_같으면_id가_작은_위치의_이름이다()        // DEFAULT 0 동순위, 2차 키 id

[^1]: 행사 운영자: 행사를 등록하는 외부 주체(지자체, 팝업 운영사, 축제 대행사). 서버 역할값
    ORG다. "행사"를 떼고 운영자라고만 쓰면 필맵 쪽 사람을 가리키므로 붙여 쓴다(glossary.md).

[^3]: catch-all: SecurityConfig에서 앞의 어떤 matcher에도 안 걸린 나머지 요청 전부를 받는 마지막

    차단이고 `/api/org/**` 안은 ORG 전용이다.
[^4]: 파생 상태: 저장 컬럼이 아니라 회차의 시작과 종료 시각에 서버 시각을 대어 계산하는 상태
