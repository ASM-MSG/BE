# MSG-418: 근접 미션 알림 (축제·팝업 촬영 유도)

**Owner**: B

> 요구사항 정본: `docs/prd/MSG-418-prd.md` (검토됨, 2026-08-18 성민 승인) · SRS `FR-NOTI-16`
> 변경 패키지는 `notification`과 `mission` 둘 다 Owner B라 계약 경계를 넘지 않는다.

## 개요

사용자가 활성 축제나 팝업 미션의 근접 반경에 들어오면 촬영을 유도하는 알림을 받는다. 근접
판정과 알림 생성은 전부 기기의 지오펜싱[^1]이 하고, 서버는 사용자 위치를 받아 판정하거나
수집·저장하지 않는다(PRD FR-2, 2026-08-18 문언 정정).
서버 몫은 두 가지다. 첫째, 이 알림을 끄는 설정을 기기 간 동기화하기 위해 알림 설정에 전용
카테고리 `MISSION_NEARBY`를 신설한다(PRD FR-6). 둘째, 기기가 지오펜스 등록에 쓰는 미션 조회는
기존 뷰포트 미션 조회를 그대로 재사용하므로(PRD FR-7, FE 합의) 신규 API 없이 FE 혼동의
원인이던 스키마 설명 한 줄만 고친다.

## 배경 · 목표

축제 222건, 팝업 227건이 활성으로 깔려 있는데 사용자가 지도를 열어 보지 않으면 존재를 알
방법이 없다. 방문 기록 서비스의 핵심 순간, 즉 사용자가 그 장소에 실제로 있는 순간에 촬영을
유도해 미션 완료율과 영상 업로드를 늘리는 것이 목표다. 구현의 무게중심은 앱이고, 이 스펙은
서버 레포가 감당하는 좁은 범위만 다룬다.

## 성공 기준

1. `GET /api/notifications/preferences` 응답에 `MISSION_NEARBY`가 포함되어 설정 대상이
   7종이 된다. 설정을 만진 적 없는 사용자는 기본 켜짐이다(옵트아웃[^2] 모델 그대로).
2. `PATCH /api/notifications/preferences/MISSION_NEARBY`로 끄고 켤 수 있고, 끄면
   `notification_opt_outs`에 행이 저장되며 DB CHECK 제약[^3]을 통과한다. 같은 값 재전환은
   멱등이고, 목록 외 값과 `MODERATION`은 지금처럼 10420이다.
3. `./gradlew build`가 green이다. 특히 `NotificationConsumer`의 카테고리 전수 분기[^4]에
   case가 추가되어 enum 확장 후에도 컴파일이 성립한다.
4. 뷰포트 미션 조회(`GET /api/missions/active`)의 와이어 계약은 바이트 하나 안 바뀐다.
   바뀌는 것은 springdoc 스키마 설명 문구뿐이다.

기기 쪽 동작(지오펜스 등록, 발화 조건, 반경 상수, 하루 상한)은 앱 몫이라 이 스펙의 검증
범위가 아니다. 서버는 설정 API가 위 계약대로 응답하는 것까지 책임진다.

## API 명세

신규 endpoint는 없다. 기존 2종의 계약이 넓어지고, 1종은 문서만 바뀌고, 1종은 무변경
재사용이다.

### GET /api/notifications/preferences (변경)

- 응답 `preferences` 목록이 6종에서 7종이 된다. 순서는 enum 선언 순 고정이므로
  `BADGE, HOTZONE, REMIND, VIDEO, WEEKLY, FRIEND, MISSION_NEARBY`다.
- 저장 행이 없는 카테고리는 `true` 합성이라 기존 사용자도 `MISSION_NEARBY: true`로 받는다.
  FE는 부재 처리가 필요 없다(기존 계약 유지).
- `MODERATION`은 여전히 목록에 없다(수신 거부 불가, MSG-417 FR-7).

### PATCH /api/notifications/preferences/{category} (변경)

- 허용값에 `MISSION_NEARBY`가 추가된다(대소문자 무시, 기존 파싱 로직 그대로).
- 목록 외 값은 400 + developCode 10420(`INVALID_CATEGORY`). 에러 메시지의 허용값 나열에
  `MISSION_NEARBY`를 추가한다.
- 기기는 발화 전에 이 설정을 조회해 따른다(PRD FR-6). off는 서버 발송을 막는 게 아니라
  기기가 로컬 발화를 스스로 삼가는 근거 데이터다. 이 의미 차이는 스웨거 설명과 컨트롤러
  javadoc에도 한 줄로 밝힌다(구현 리뷰 권고 반영. 기존 "off는 발송만 막는다" 서술이 서버
  발송형 전제라 이 카테고리에는 맞지 않아서다). FE 문서 계약은 "카테고리 7종 토글"로 동일하다.

### GET /api/missions/active (문서만)

- `MissionShape.BoxShape`의 스키마 설명이 "이벤트(EVENT)"라서 팝업이 BOX 형상임을 FE가
  놓쳤다. 설명을 "축제·팝업(EVENT·POPUP)"으로 고친다. 응답 JSON은 불변이다.
- `type` 파라미터는 요청당 하나만 받는다(단일 enum 파싱). 축제와 팝업 지오펜스를 둘 다
  등록하려는 기기는 `type=EVENT`와 `type=POPUP`으로 두 번 조회해 id 목록을 합친 뒤 아래
  progress 필터로 넘어간다.
- 기기는 이 조회로 받은 BOX `polygon` 앞 4점 평균으로 중심점을 계산해 지오펜스를 등록한다
  (PRD FR-7, FE 합의). 서버가 중심점을 따로 내려주지 않는다.

### GET /api/missions/progress (재사용, 무변경)

- 위 active 응답은 사용자 무관 전역 캐시라 스탬프 상태가 없다. PRD FR-3(스탬프 보유분
  제외)을 기기가 지키려면 두 번째 조회가 필요하다. active 두 번 조회로 합친 미션 id 목록을
  이 API에 넘겨(콤마 구분 또는 반복 파라미터) `completed`(스탬프 보유 여부)를 받고,
  `completed=true`인 미션을 지오펜스 등록에서 뺀다.
- 배치 상한은 300개이고 초과는 400 + developCode 12403이다. 지오펜스 후보는 OS 한도
  (최대 100개) 안이라 한 번 호출로 끝나지만, active 응답 전체를 넘길 때는 이 상한을
  의식해야 한다.
- 서버 코드 변경은 없다. 기존 계약의 재사용 서술이다.

## 도메인 로직

서버는 이 카테고리의 알림을 만들지도 보내지도 않는다. 로직 변경은 설정 표면의 값 편입이 전부다.

1. **`NotificationCategory`에 `MISSION_NEARBY` 추가** (enum 마지막, `MODERATION` 뒤).
   V35 선례처럼 끝에 붙인다. 설정 응답 순서가 enum 선언 순이므로 기존 6종의 순서는 흔들리지
   않고 새 값이 `FRIEND` 다음에 온다(`MODERATION`은 응답에서 걸러지므로). 주석에 두 가지를
   명시한다. 서버 발송 경로가 없는 최초의 카테고리라는 점, 그리고 `notifications` CHECK가
   아니라 `notification_opt_outs` CHECK에만 실린다는 점(아래 데이터 모델 참조. 기존 주석의
   "notifications CHECK와 일치" 문구도 이에 맞게 갱신한다).

2. **`NotificationPreferenceServiceImpl`은 코드 변경이 없다.** 조회 합성이
   `NotificationCategory.values()` 순회 + `MODERATION` 필터라서 enum에 값을 추가하면 자동
   편입된다. 토글 파싱도 `valueOf` 기반이라 그대로다. 이 무변경이 설계의 결과임을 리뷰에서
   확인한다(값 나열 하드코딩이 어디에도 없어야 한다).

3. **`NotificationConsumer.rateLimited` 전수 분기에 `case MISSION_NEARBY -> null;` 추가.**
   컴파일 요건이다. 알림이 기기 로컬 생성이라 서버 발송 경로가 없고, 하루 5건 상한(PRD FR-4)도
   앱 상수라 서버가 세지 않는다. 이 case에 런타임이 도달하면 그 자체가 결함이다(아웃박스[^5]에
   이 카테고리 행이 생겼다는 뜻). 주석에 이 근거를 남긴다.

4. **설정 표면 문구 7종화.** 카테고리 나열이 하드코딩된 표면은 다섯 곳이다.
   `NotificationPreferenceController`의 Operation 설명 2곳(조회·토글)과 PATCH 경로 변수의
   `@Parameter` description 1곳, `NotificationPreferenceService.getPreferences`의
   javadoc("설정 대상 카테고리 6종"), `NotificationPreferenceResponseDto`의 설명과
   `allowableValues`, `NotificationErrorCode.INVALID_CATEGORY` 메시지. 전부에
   `MISSION_NEARBY`를 추가한다.

5. **`MissionShape.BoxShape` 설명에 POPUP 명시.** javadoc 첫 줄과 `@Schema` description 두
   곳이다. 렌더 로직(`case EVENT, POPUP -> boxShape(grids)`)은 이미 팝업을 처리하고 있어
   코드 변경이 아니라 문서 정정이다.

기기 몫이라 서버가 구현하지 않는 것: 근접 반경(팝업 200m, 축제 500m), 미션당 생애 1회
발화, 하루 5건 상한, 스탬프 보유분 제외, 권한 회수 시 조용한 미동작. 전부 PRD FR-1, FR-3,
FR-4, FR-6의 앱 구현 사항이다. 기기 구현에 걸리는 주의 두 가지를 남긴다.

- **생애 1회의 실제 의미**: 발화 이력이 기기에만 남으므로 재설치, 기기 변경, 앱 데이터
  삭제 시 같은 미션이 다시 발화할 수 있다. PRD가 기기 판정형을 확정하며 "발화 이력이
  서버에 안 남는 것까지 감수"한 결정의 귀결이라 결함이 아니다.
- **경계 기준 반경의 등록 방식**: PRD FR-1의 반경은 미션 경계 기준인데 FR-7의 등록은
  중심점(polygon 앞 4점 평균) 원형이다. 고정 반경 원을 중심점에 걸면 큰 축제 박스에서
  경계 기준 500m 안인 사용자가 원 밖일 수 있다. 기기는 polygon 전체를 이미 받으므로 유효
  등록 반경을 "반경 상수 + 중심에서 경계까지 최대 거리"로 계산하면 경계 기준이 지켜진다.
  다만 이 원은 놓침만 막는 깨우기용 상한이다. 길쭉한 박스에서는 경계에서 반경 상수보다
  훨씬 먼 사용자도 원 안에 들어오므로(한 변 900m 정사각형이면 500m 규칙이 약 1,136m 원이
  된다), 진입 이벤트 후 발화 전에 기기가 polygon까지의 실거리가 반경 상수 이하인지 정밀
  판정해 과발화를 막는다. FE 계약 논의에서 짚을 항목이다.

## 데이터 모델

Flyway 마이그레이션 1건과 엔티티 컬럼 속성 정합 1건이 필요하다.

**컬럼 폭이 선행 문제다 (Codex 교차 리뷰 P1).** `V22__notification_opt_outs.sql`이
`category VARCHAR(10)`으로 만들었고 V25·V26·V35는 CHECK만 교체해 폭이 그대로다.
`MISSION_NEARBY`는 14자라 CHECK 평가 전에 INSERT가 길이에서 실패한다. V36은 CHECK 재정의에
앞서 컬럼 폭부터 넓혀야 성공 기준 2가 성립한다.

**`V36__notification_opt_outs_category_mission_nearby.sql`**

```sql
-- MISSION_NEARBY(MSG-418) 설정 카테고리 확장. 기존 행 무변경, CHECK 상위집합 재정의 (V35 형상).
-- 폭 확장 선행: V22 의 VARCHAR(10) 은 14자 MISSION_NEARBY 를 CHECK 평가 전에 길이로 거부한다.
ALTER TABLE notification_opt_outs ALTER COLUMN category TYPE VARCHAR(20);
-- notifications CHECK 는 손대지 않는다. 이 카테고리는 서버 발송 경로가 없어(알림은 기기 로컬 생성)
-- outbox 행이 생기면 결함이고, CHECK 가 그것을 막는 마지막 방어선이다. MODERATION 의 거울상이다
-- (그쪽은 발송만 있고 설정이 없어 opt_outs 에서 의도적 제외됐다, V35 주석).
-- 같은 이유로 notifications.category(V21, VARCHAR(10)) 폭 확장도 불요하다. 이 값은 그 테이블에 실리지 않는다.
ALTER TABLE notification_opt_outs DROP CONSTRAINT chk_notification_opt_outs_category;
ALTER TABLE notification_opt_outs ADD CONSTRAINT chk_notification_opt_outs_category
	CHECK (category IN ('BADGE', 'HOTZONE', 'REMIND', 'VIDEO', 'WEEKLY', 'FRIEND', 'MISSION_NEARBY'));
```

**엔티티 정합**: `NotificationOptOutId.category`의 `@Column(nullable = false, length = 10)`을
`length = 20`으로 올린다. DB 폭과 매핑 선언이 어긋난 채 두지 않는다. 엔티티 변경은 이 속성
하나이고 필드 추가나 타입 변경은 없다.

폭 20 선택 근거: 14자 + 여유. `grids.grid_id VARCHAR(20)`과 같은 폭이라 낯설지 않다.

PRD 7절의 "카테고리 CHECK 상위집합 재정의"를 `notification_opt_outs` 한 곳으로 구체화한
결정이다. 대안이었던 "양쪽 CHECK 모두 추가"(enum과 notifications CHECK의 일치 불변식 유지)는
기각했다. 그 불변식은 주석 한 줄의 계약일 뿐이고, 발송 경로가 없는 값을 notifications가
받아들이게 열어 두면 잘못 만들어진 outbox 행을 DB가 못 잡는다. 일치 불변식 쪽 주석을 "두
테이블 CHECK의 합집합과 일치"로 고치는 편이 싸다. 리뷰에서 이 결정에 이견이 있으면 V36만
고치면 되는 지점이다.

## 테스트 시나리오

FRIEND 편입(MSG-416) 때의 테스트 선례를 그대로 따른다. 신규는 서비스 통합 테스트 1건이고
나머지는 기존 단언의 7종화 갱신이다. 검증 주석은 `// 검증: FR-NOTI-16`.

**`NotificationPreferenceServiceIntegrationTest` (갱신 + 신규)**

기존 단언 중 enum 확장에 깨지는 곳이 세 곳이다. 셋 다 갱신한다.

- 갱신 1: `조회는_카테고리_6종_전부를_반환한다`를 7종으로. 단언 튜플에
  `tuple(NotificationCategory.MISSION_NEARBY, true)` 추가, DisplayName의 "6종"도 갱신.
- 갱신 2: `카테고리를_off하면_isEnabled가_false다`의 `containsExactly` 6튜플 나열에도
  `tuple(NotificationCategory.MISSION_NEARBY, true)`를 추가한다. 조회 테스트와 별개로
  update 반환 경로를 단언하는 곳이라 따로 잡아야 한다.
- 갱신 3: `알림_설정_응답에_MODERATION이_없다`의 `hasSize(6)`을 `hasSize(7)`로. 놓치면
  enum 확장 직후 이 테스트가 깨진다. MODERATION 부재 단언(`doesNotContain`)은 그대로 둔다.
- 신규: `MISSION_NEARBY_카테고리를_끄고_켤_수_있다`. FRIEND 동형 시나리오다.
  - Given 설정을 만진 적 없는 사용자 / When `isEnabled` 조회 / Then true (기본 켜짐)
  - When `update(me, "MISSION_NEARBY", false)` / Then `isEnabled` false이고 조회 응답의
    해당 항목이 false다. 통합 테스트라 이 저장이 V36의 폭 확장과 CHECK를 실제로 통과하는
    것까지 확인된다(14자 값이라 폭 확장 누락 시 이 테스트가 INSERT에서 깨진다).
  - When 다시 on / Then 행이 삭제되고 `isEnabled` true로 복귀.
- 기존 유지 확인: `잘못된_카테고리는_10420이다`(프로브 문자열이 enum에 영원히 없는 값이라
  무변경), `MODERATION_토글_요청은_INVALID_CATEGORY다`(무변경).

**`NotificationPreferenceControllerTest` (무변경 green 확인)**

## 참고

- 알림이 서버 파이프라인(아웃박스, Kafka, FCM)을 타지 않으므로 발화 이력이 서버에 남지
  않는다. PRD가 감수하기로 확정한 사항이다(2026-08-18, 기기 판정형). 그 귀결로 미션당
  생애 1회(FR-4)는 기기가 기억하는 1회라서, 재설치나 기기 변경 후에는 같은 미션이 다시
  발화할 수 있다(위 도메인 로직의 기기 주의 참조).
- 백그라운드 갱신의 뷰포트 bbox는 기기 위치에서 파생된 값이다. 스펙 리뷰가 이 점과 FR-2의
  원래 문언("사용자 위치는 기기 밖으로 나가지 않는다") 사이 간극을 지적했고, PRD 문언을
  "서버가 위치를 받아 판정·수집·저장하지 않는다"로 정정하는 것으로 해소했다(2026-08-18 성민
  확정. 원래 문언대로면 기존 지도 화면의 조회부터 위반이었다). 기기가 bbox를 격자 단위로
  스냅해 정밀도를 낮추는 완화는 필수가 아니라 FE 계약 논의 항목이다.
- 마무리 단계에서 SRS 갱신 대상: FR-NOTI-16 상태(서버 몫 구현 완료 시점에도 앱 구현 전이면
  `진행 중`), FR-NOTI-06의 설정 카테고리 목록 7종화. 단, FR-NOTI-06 현행 본문의 "끈
  카테고리는 이벤트 기록은 남되 발송 단계에서 걸러진다"는 서버 발송형 전제라
  MISSION_NEARBY에는 맞지 않는다(이벤트 기록이 아예 없고 기기가 발화 전에 설정을 조회해
  로컬 억제한다). 갱신 시 단순 7종화가 아니라 서버 발송형 6종과 기기 로컬형 1종을 구분해
  서술해야 한다.

[^1]: 지오펜싱: OS에 "이 좌표 반경 안에 들어오면 앱을 깨워 달라"고 등록해 두는 기능. 앱이 GPS를 계속 켜지 않아도 OS가 저전력으로 진입을 감지한다. 이 기능 덕에 서버가 사용자 위치를 받을 필요가 없다.
[^2]: 옵트아웃(opt-out): 기본값이 "받는다"이고 사용자가 명시적으로 꺼야 안 받는 모델. FillMap 알림 설정은 끈 카테고리만 `notification_opt_outs`에 행으로 남기고, 행이 없으면 켜진 것으로 합성한다.
[^3]: CHECK 제약: 컬럼에 들어올 수 있는 값을 DB가 직접 검증하는 제약. 애플리케이션 코드가 잘못된 값을 넣으려 해도 DB가 거부하므로, enum 확장 시 이 제약도 함께 넓혀야 저장이 성립한다.
[^4]: 전수 분기(exhaustive switch): Java의 switch 식이 enum의 모든 값을 다루도록 컴파일러가 강제하는 것. enum에 값이 추가되면 case를 안 쓴 switch는 컴파일이 깨지므로, 새 카테고리를 다루는 걸 잊는 실수를 빌드 단계에서 잡는다.
[^5]: 아웃박스(outbox): 비즈니스 변경과 알림 요청 기록을 같은 DB 트랜잭션으로 남기고, 별도 소비자가 그 기록을 읽어 발송하는 패턴. FillMap의 `notifications` 테이블이 이 역할이라, 서버 발송이 없는 카테고리의 행이 여기 생기면 잘못된 경로다.
