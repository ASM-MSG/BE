# MSG-247: 업로드·교체 확정 트랜잭션 롤백 시 S3 original 복사본 고아 방지

**Owner**: B (`com.msg.fillmap.video.*` 내부 — 계약 인터페이스 무관)

> 출처: Codex 교차 리뷰 (2026-07-24 — P2). 결함 수정 티켓 — PRD 없음.

## 개요

`VideoServiceImpl`의 업로드 확정(`saveVideo`)·교체(`replaceVideo`)는 트랜잭션 안에서
`videos/pending/` → `videos/original/` S3 복사를 수행한다. 복사 **이후** 트랜잭션이 실패하면
(점령 upsert·뱃지·수집률 refresh·스트릭·커밋 flush 등) DB는 롤백되지만 S3 복사본은 남는다.
pending 전용 라이프사이클(1일 만료, MSG-133)은 `videos/original/` 경로를 못 지우므로 **영구 고아**다.
롤백 시 복사 키를 지우는 보상을 `TransactionSynchronization.afterCompletion(STATUS_ROLLED_BACK)`으로
등록한다 — MSG-133의 "삭제·교체는 커밋 후 객체 제거"(afterCommit) 패턴의 **롤백 대칭**.

## 배경 · 목표

- S3 고아는 데이터 정합에는 무해하지만 비용·위생 문제이고, original 경로 고아는 어떤 정리
  장치도 못 잡는다(라이프사이클은 pending 전용, 삭제·교체 정리는 DB row 기준).
- 목표: 확정 도중 어느 지점에서 실패해도 original 복사본이 함께 정리된다. 보상 자체의 실패는
  로그만 남긴다(베스트 에포트 — `deleteQuietly` 기존 정책과 동일).

## 성공 기준

1. 확정 트랜잭션이 롤백되면 그 트랜잭션에서 복사한 original 키가 S3에서 삭제된다 (업로드·교체 공통).
2. 커밋이 성공하면 보상 삭제가 실행되지 않는다 — 방금 확정한 원본이 지워지는 일이 없어야 한다.
3. 교체 롤백 시 삭제 대상은 **새 original 키뿐**이다 — 옛 original·블러본은 건드리지 않는다
   (영상 row가 롤백으로 옛 파일을 그대로 가리키므로. 옛 키 삭제는 기존 afterCommit 소관이고
   afterCommit은 롤백 시 실행되지 않아 겹침·충돌 없음).
4. 보상 삭제가 실패해도 예외가 전파되지 않고 ERROR 로그만 남는다.
5. 트랜잭션 밖 호출(동기화 비활성 — 기존 단위 테스트 경로)에서는 보상이 등록·실행되지 않는다.

## 수정 방식 — 복사 직후 롤백 보상 등록

`copyToOriginal` 안에서 S3 복사 성공 직후 보상을 등록한다. 복사 자체가 실패하면 대상 객체가
없으니 보상 불요(예외 전파 → 롤백 → pending은 라이프사이클이 정리 — 기존 동작 유지).

```java
private void copyToOriginal(String pendingKey, String originalKey) {
	s3Client.copyObject(...);   // 기존 그대로
	deleteOnRollback(originalKey);
}

/** MSG-133 afterCommit 의 롤백 대칭 (MSG-247). 트랜잭션 밖이면 롤백 개념이 없으니 아무것도 안 한다. */
private void deleteOnRollback(String originalKey) {
	if (!TransactionSynchronizationManager.isSynchronizationActive()) {
		return;
	}
	TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
		@Override
		public void afterCompletion(int status) {
			if (status == TransactionSynchronization.STATUS_ROLLED_BACK) {
				deleteQuietly(originalKey);
			}
		}
	});
}
```

### 설계 결정

- **D1 — 등록 위치는 `copyToOriginal` 내부, 복사 직후.** 두 호출부(`saveVideo:119`,
  `replaceVideo:159`)가 공유하는 지점이라 한 곳 수정으로 양쪽이 커버되고, 이후 어느 지점에서
  터져도 보상이 걸린다. 호출부 코드는 무변경 — MSG-241/243이 얹은 변경과 충돌 없음.
- **D2 — `STATUS_ROLLED_BACK`에만 삭제.** `STATUS_COMMITTED`는 당연히 제외하고,
  `STATUS_UNKNOWN`(커밋 결과 불명)도 삭제하지 않는다 — 커밋됐을 수도 있는 영상의 원본을 지우면
  데이터 유실(재생 불가)이고, 고아는 비용 문제일 뿐이다. 불명확하면 남기는 쪽이 안전.
- **D3 — 트랜잭션 밖(동기화 비활성)이면 no-op.** 기존 `afterCommit` 헬퍼는 이 경우 즉시
  실행하지만, 롤백 보상은 반대다 — 트랜잭션이 없으면 롤백도 없으므로 등록 자체를 건너뛴다.
  가드 없이 등록을 시도하면 `registerSynchronization`이 `IllegalStateException`을 던져
  무트랜잭션 경로(`VideoS3CleanupTest` 등)가 통째로 깨진다.
- **D4 — 삭제는 `deleteQuietly` 재사용.** 베스트 에포트(SdkException 삼킴 + ERROR 로그,
  배치 응답 errors 검사)가 이미 구현돼 있다. 보상 실패는 로그만 — 롤백 응답(사용자에게는 이미
  실패한 요청)을 보상 실패로 다시 오염시키지 않는다. 덧붙여 Spring 자체도
  `afterCompletion`의 예외를 전파하지 않고 로그 후 삼킨다(이중 안전망).
- **D5 — pending 키는 보상 대상이 아니다.** 기존 정책 유지(MSG-133) — 라이프사이클이 만료시킨다.
- **D6 — 교체 경로의 옛 키와 겹침 없음 확인.** 롤백 보상 대상은 새 original 키뿐이고, 옛 키
  삭제(`:163`)는 `afterCommit`이라 롤백 시 실행되지 않는다. 새 키 ≠ 옛 키는 구조적으로 보장 —
  새 키는 새 presign UUID에서 파생되고 `confirmUpload:500`의 `existsByOriginalS3Key` 중복
  검사가 DB에 있는 키(=옛 키)의 재사용을 거부한다.

## 설계 수정 (Codex 1R P1, 2026-07-30)

**P1 결함**: 같은 pending 키를 두 확정(업로드·교체)이 동시 제출하면 둘 다 `existsByOriginalS3Key`를
통과하고(미커밋 row 불가시 — read committed) 같은 original 키로 복사한다. 유니크 제약
(`uq_videos_original_s3_key`, V2)이 커밋 flush 에서 한쪽만 살리는데, **패자의 롤백 보상(D1~D4)이
승자가 참조하는 같은 키의 S3 객체를 지운다** — 고아 방지 보상이 데이터 유실(재생 불가)을 만드는 역전.

**대응 — 클레임 선행 직렬화** (사용자 확정):

- `original_s3_key` DB 클레임을 S3 복사보다 먼저 flush 한다. `saveVideo`는 `saveAndFlush`
  (IDENTITY 라 기존 `save`도 즉시 INSERT — ID 전략이 바뀌어도 순서가 유지되게 명시),
  `replaceVideo`는 `replaceFile` 직후 `videoRepository.flush()` (더티체킹 UPDATE 를 그 시점에 강제).
- 유니크 인덱스가 동시 클레임을 자연 직렬화한다: 패자는 클레임 flush 에서 승자 커밋까지 블록됐다가
  위반으로 롤백되고, **복사 자체를 안 하므로** 보상 삭제가 남의 키를 지울 수 없다.
- **불변식**: "롤백된 트랜잭션의 original 키를 참조하는 타 커밋은 존재 불가" — 보상 등록
  (`deleteOnRollback`, 복사 직후)은 그대로 유지되고, 이 불변식 아래에서 보상이 지우는 객체는 항상
  자기 트랜잭션만 참조하던 것이다 (`deleteOnRollback` javadoc 에 명시).
- 복사 실패 시: 예외 → 롤백 → 클레임도 함께 롤백, 고아 없음(복사가 안 됐으니 보상 대상도 없음).
- 기존 의미 무변: `existsByOriginalS3Key`는 비동시 중복의 4xx 선별로 유지(유니크가 최종 방어선 —
  confirmUpload 기존 주석 그대로), 교체 옛 키 정리는 afterCommit 소관 불변, 테스트 시나리오 1~4 green 유지.
  패자 요청의 응답이 유니크 위반(5xx)으로 끝나는 것은 이 레이스의 기존 동작 그대로다.

## 설계 수정 2 (Codex 2R P1, 2026-07-30)

**P1 잔여 결함**: 1R 의 불변식("롤백된 트랜잭션의 키를 참조하는 타 커밋은 존재 불가")은 락 해제
시점을 놓쳤다 — 롤백이 유니크 락을 **먼저** 풀고 `afterCompletion` 보상은 그 **뒤**에 돈다. 그 갭에
후속 클레이머(같은 pending 재시도)가 같은 결정 파생 키를 클레임·복사·커밋할 수 있고, 앞 시도의 보상
삭제와 후속의 복사·커밋은 각각 S3 호출 1회라 순서 미보장 — 보상이 커밋된 영상의 원본을 지울 수 있다.
1R 의 "실질 불가능" 평가(잔여 창 수용)는 낙관이었고 **이번 설계로 소멸됐다**.

**대응 — 시도별 유니크 키** (사용자 확정):
