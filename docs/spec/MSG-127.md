# MSG-127: 격자 상세 조회 — 격자별 내 영상 리스트 (MSG-73에서 분리)

**Owner**: B (`com.msg.fillmap.video.*`) — videos 테이블 = Owner B 도메인. grid 패키지 무수정.

> 부모: **MSG-73**(격자 색칠 응답 API)에서 분리. MSG-73은 색칠(점령 여부·격자 인덱스)만 담당하고 `videos`를 전혀 건드리지 않기로 확정 → 그 격자의 **내 영상 리스트 조회**를 본 티켓으로 분리.
> 형제 경계: MSG-73(색칠 read·완료) / MSG-90(viewport 커서·완료) / **MSG-87 대표 영상 랭킹 선정(KangJeong 담당, 스코프 밖)** / 영상 재생(presigned GET playback, 별도 미구현 티켓).
> 이 티켓은 **순수 Owner B**다. 계약 인터페이스(`GridQueryService`/`UserGridQueryService` 등) 시그니처 변경 없음 → 상대 팀 확인 불필요(§계약 변경 참조).

---

## 개요

사용자가 지도에서 **격자를 탭했을 때**, 그 격자에 내가 올린 영상들의 리스트(썸네일·상태·업로드 시각)를 내려주는 read 경로를 만든다.
MSG-73이 "이 격자가 내 색으로 칠해졌는가(점령 여부)"만 답한다면, 본 티켓은 "그 칠해진 격자를 열었을 때 **안에 뭐가 들었는가**"에 답한다.

```
[MSG-73]  grid_id  →  occupied + videoCount          (색칠 상태, videos 미접근)
[MSG-127] grid_id  →  그 격자의 내 영상 리스트         (videos 접근 · 썸네일 presigned GET)
```

**로그인 사용자 본인의 영상만** 반환한다(glossary "MVP는 개인 도감만"). `createdAt DESC`(최근 업로드 먼저) 정렬.
썸네일은 S3 key로 저장돼 있고 버킷이 private(Block Public Access)이라 **presigned GET URL을 발급**해 내려준다(§도메인 로직).

---

## 배경 · 목표

- **사용자/제품 관점**: 격자는 100×100m라 사용자는 한 격자를 여러 번 재방문(glossary "재방문")할 수 있다. 격자를 탭하면 "여기서 내가 찍은 영상들"을 시간순으로 보고, 개별 영상으로 진입(재생·교체·삭제)할 수 있어야 한다. MSG-73은 색칠까지만 만들었고 이 상세 화면의 데이터가 비어 있다.
- **목표**: `(userId, gridId)`로 내 영상 목록을 조회하는 조회 API 1종을 Owner B(video) 도메인에 제공한다. 썸네일은 재생 가능한 presigned URL로, 아직 인코딩 중이면 상태(`processingStatus`)로 FE가 플레이스홀더를 그릴 수 있게 한다.

## 선행 상태 (현재 코드 — `status.md` · 실코드 확인 결과)

video 도메인은 write·삭제·교체·presigned **PUT**까지 있으나 **조회(read) API가 하나도 없다.** 본 티켓이 첫 read 경로다.

| 있음 | 없음 (본 티켓이 생성/추가) |
|---|---|
| `video/entity/Video` (`thumbnailUrl`=S3 key, `processingStatus`, `status`, `createdAt`, `durationSec` 매핑 완료) | 격자별 내 영상 조회 쿼리 (`VideoRepository`에 메서드 추가) |
| `video/repository/VideoRepository` (native UPSERT·롤백·소유권 조회) | 조회 서비스 메서드 (`VideoService`에 추가) |
| `video/service/VideoServiceImpl` (`S3Presigner`·`S3Client`·`AwsProperties` 주입 완료) | **presigned GET 발급 로직** (코드베이스 최초 — 지금은 `presignPutObject`만 존재) |
| `video/controller/VideoController` (`@AuthenticationPrincipal AuthPrincipal` 패턴) | 조회 컨트롤러 엔드포인트 + 응답 DTO |
| `auth/jwt/AuthPrincipal` (`userId()`), `response/SuccessResponse` | (신규 에러코드 불필요 — §도메인 로직 3) |

- **`Video.thumbnailUrl`은 URL이 아니라 S3 key다**(엔티티 주석 명시). `markReady(encodedKey, thumbnailKey)`로 READY 시점에만 채워지고, `UPLOADED`/`ENCODING`/`FAILED` 상태에선 `null`이다.
- 코드베이스에 **presigned GET(재생/썸네일 열람)이 아직 없다.** `S3Client.getObject`(인코딩 워커의 다운로드)만 있고, `S3Presigner`는 PUT 업로드에만 쓰인다. 본 티켓이 첫 GET presign을 도입한다.

## 성공 기준

1. `GET /api/grids/{gridId}/my-videos`가 로그인 사용자가 그 격자에 올린 **본인 영상 목록**을 `createdAt DESC`로 반환한다.
2. 각 항목은 `videoId`, `thumbnailUrl`(presigned GET URL·READY 아니면 `null`), `processingStatus`, `durationSec`, `createdAt`를 담는다.
3. 삭제된 영상(`status=DELETED`)은 목록에 포함되지 않는다.
4. 다른 사용자의 영상은 절대 포함되지 않는다(개인 도감 격리).
5. 영상이 없거나(미점령·타인만 점령한 격자 포함) 존재하지 않는 `gridId`여도 **404가 아니라 200 + 빈 배열**로 응답한다(격자는 항상 존재하는 논리 개념 — glossary, MSG-73과 일관).
6. 응답은 `SuccessResponse.of(...)`로 감싸 HTTP 200 + `developCode 200`.
7. 인증 없이 호출하면 SecurityConfig의 기존 정책대로 401.
8. Flyway 마이그레이션 없이(v6 `V1__init.sql`) 전체 테스트 green.

## API 명세

인증: 로그인 필수. `userId`는 `@AuthenticationPrincipal AuthPrincipal principal` → `principal.userId()`로 획득(video 도메인 기존 방식 재사용 — `VideoController` 동일).

### `GET /api/grids/{gridId}/my-videos` — 격자별 내 영상 리스트

> **URL 네임스페이스 주의(리뷰 확인 포인트)**: 경로 접두사는 `/api/grids/...`지만, 이 컨트롤러는 **video 패키지에 두는 Owner B 코드**다. Spring은 경로 접두사에 소유권을 강제하지 않으므로 grid 패키지(`GridController`)를 전혀 수정하지 않고 서브리소스로 매핑할 수 있다. "격자 상세 = 격자의 하위 리소스(영상)"라는 REST 의미가 FE 멘탈모델("격자 탭 → 그 안의 영상")과 일치해 이 경로를 택한다.
> 대안 `GET /api/videos?gridId=...`(VideoController에 추가)도 가능하나, 상세 조회 성격상 서브리소스 경로가 더 명확하다. **최종 경로는 리뷰에서 확정**(둘 다 grid 패키지 무수정·Owner B).

- Path: `gridId` (예: `"41642_110458"`)
- 성공 200 `body` = `List<GridVideoResponseDto>` (없으면 `[]`)

**`GridVideoResponseDto` 항목**

| 필드 | 타입 | 의미 |
|---|---|---|
| `videoId` | Long | 영상(방문 이벤트) id. 개별 재생/교체/삭제 진입 키 |
| `thumbnailUrl` | String \| null | 썸네일 **presigned GET URL**. `processingStatus != READY`(썸네일 key 없음)이면 `null` |
| `processingStatus` | String | `UPLOADED`/`ENCODING`/`BLURRING`/`READY`/`FAILED` (FE가 플레이스홀더·스피너 판단) |
| `durationSec` | Short | 영상 길이(초, 최대 30) |
| `createdAt` | LocalDateTime | 업로드(방문) 시각 — 정렬 키 |

**정렬**: `createdAt DESC`(최근 업로드 먼저 — Jira 명세).

**응답 예시**
```json
{
  "developCode": 200,
  "httpStatus": "OK",
  "message": "성공",
  "body": [
    {
      "videoId": 1042,
      "thumbnailUrl": "https://bucket.s3.ap-northeast-2.amazonaws.com/videos/thumb/1042.jpg?X-Amz-...",
      "processingStatus": "READY",
      "durationSec": 12,
      "createdAt": "2026-07-20T18:03:11"
    },
    {
      "videoId": 1041,
      "thumbnailUrl": null,
      "processingStatus": "ENCODING",
      "durationSec": 8,
      "createdAt": "2026-07-20T17:55:02"
    }
  ]
}
```

**에러**: 없음(별도 도메인 에러코드 추가 없음 — §도메인 로직 3). 인증 실패는 SecurityConfig가 401 처리.

## 도메인 로직

### 1. 조회 (개인 도감 격리)

1. `principal.userId()`로 로그인 사용자 확정.
2. `videos`에서 `user_id = :userId AND grid_id = :gridId AND status = 'ACTIVE'` 조회, `ORDER BY created_at DESC`.
   - `status='ACTIVE'`로 삭제(`DELETED`)·블라인드(`BLINDED`) 제외. `visibility`·`processing_status`는 **필터하지 않는다** — 내 도감이므로 PRIVATE·인코딩 중 영상도 내겐 보여야 한다(MSG-87 공개 대표영상 인덱스 `idx_videos_grid_popular`의 필터 조건과는 목적이 다르다).
3. 결과를 DTO로 매핑. 각 항목의 썸네일 key → presigned GET URL(§2).

핵심 쿼리는 항상 `user_id = :userId`로 제한한다(전역 아님 — glossary "MVP는 개인 도감만"). 타인 영상·미점령 격자는 결과에 담지 않는다.

### 2. 썸네일 presigned GET (코드베이스 최초 도입)

- 버킷이 private(Block Public Access)이라 `thumbnail_url`에 담긴 **S3 key는 그대로는 열람 불가** → 요청 시점에 `S3Presigner.presignGetObject`로 **TTL 있는 GET URL을 발급**해 내려준다(Jira 지침: "버킷이 private이면 presigned가 필수").
- `thumbnailUrl` key가 `null`인 영상(READY 이전)은 발급 대상이 없으므로 응답 `thumbnailUrl = null`. FE는 `processingStatus`로 스피너/플레이스홀더를 그린다.
- presigning은 **로컬 서명 연산**(S3 네트워크 호출 아님)이라 목록 항목마다 발급해도 비용이 낮다 — N+1 우려 없음.
- TTL: 새 상수(예: `THUMBNAIL_PRESIGN_TTL`, 제안 10분 — 기존 `PRESIGN_TTL`과 동일값). 목록 열람 세션 내 유효하면 충분.
- 배치 위치: `S3Presigner`·`S3Client`·`AwsProperties`가 이미 주입된 `VideoServiceImpl`에 헬퍼로 추가. `VideoServiceImpl` 상단 ponytail 주석("S3 관심사가 2개째면 `PresignedUrlService`로 분리")대로, presign이 PUT·GET 2종이 되므로 **`PresignedUrlService`(또는 `VideoQueryService`) 분리를 검토**할 수 있다 — 다만 MVP 최소 구현은 헬퍼 1개 추가로 충분. 분리 여부는 구현자/리뷰 재량.

### 3. gridId 검증·에러 정책

- **포맷 검증을 하지 않는다.** 잘못된/존재하지 않는 `gridId`는 `videos`에 매치되는 행이 없어 자연히 빈 배열이 되고, 이는 "미점령 격자 = 빈 상세"와 동일한 안전한 응답이다(성공 기준 5, MSG-73의 "격자는 항상 존재하는 논리 개념"과 일관).
- 따라서 **신규 에러코드가 필요 없다.** `GridErrorCode.INVALID_GRID_ID`(Owner A enum) 재사용도 하지 않는다 — Owner B가 Owner A 예외에 의존하지 않게 경계를 지킨다.

### 4. 페이지네이션 미채택 (근거)

- **한 `(user, grid)`의 영상 수는 상한이 있는 소량이다.** 격자는 100×100m이고 한 사용자가 같은 격자를 재방문한 영상은 현실적으로 수 개~수십 개다. MSG-90이 cursor 페이지네이션을 도입한 이유는 **viewport 하나에 격자가 수만 개**에 달할 수 있어서였는데(그 압력), 격자 상세에는 그 압력이 없다.
- coding-principles §2(과설계 금지)에 따라 **전체 리스트를 한 번에** 반환한다. 향후 한 격자당 영상이 비정상적으로 커지면 MSG-90의 `GridCursor`/lookahead 패턴을 그대로 이식해 후속 티켓에서 추가한다(YAGNI).

## 데이터 모델

**Flyway 마이그레이션 불필요.** v6 `V1__init.sql`이 필요한 컬럼을 모두 보유한다(스키마 변경 없음).
- `videos`: `user_id`, `grid_id`(FK), `thumbnail_url`, `processing_status`, `status`, `duration_sec`, `created_at` — 전부 존재·`Video` 엔티티 매핑 완료.
- 인덱스: 기존 `idx_videos_user_created (user_id, created_at DESC)`가 있어 `user_id` 프리픽스로 좁힐 수 있다. 한 격자당 소량이라(§도메인 4) `(user_id, grid_id, created_at DESC)` 전용 인덱스는 **추가하지 않는다**(YAGNI — 필요 시 후속 마이그레이션).

**신규 엔티티 없음.** `Video` 엔티티를 그대로 조회한다.

**리포지토리 메서드(제안)** — derived query로 충분(네이티브 불필요):
```
List<Video> findByUserIdAndGridIdAndStatusOrderByCreatedAtDesc(Long userId, String gridId, VideoStatus status);
// 호출: findBy...(userId, gridId, VideoStatus.ACTIVE)
```
`Video`는 연관관계가 없어 LazyInitialization 우려가 없다. 매핑(썸네일 presign 포함)은 서비스에서 수행한다.
