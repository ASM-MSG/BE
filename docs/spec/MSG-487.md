# MSG-487: 경로 추천이 출발지와 지역 이동을 묻지 않고 자동으로 처리한다

**Owner**: 공동 (주 구현 B)

> 요구사항 정본: `docs/prd/MSG-487-prd.md` (상태 검토됨, 2026-08-26 성민 승인). 이 스펙은 그
> PRD의 FR과 비기능에 "어떻게"만 붙인다. 내용이 어긋나면 PRD가 이긴다.
> route 도메인 로직의 정본은 `docs/spec/MSG-457.md`, 언급 지역 신호의 정본은
> `docs/spec/MSG-468.md`다. 두 스펙의 구조는 그대로 두고 서버는 두 곳만 바꾼다.
> SRS 참조: FR-ROUTE-11, FR-ROUTE-12, FR-ROUTE-14, FR-ROUTE-15 (2026-08-26 개정 완료).

## 개요

AI 경로 추천의 사용 흐름에서 사용자가 정하거나 확인하던 단계 세 개를 자동화한다. 출발
토글은 없어지고 현재 위치가 화면 안인지로 origin 전송이 자동 판정되며(FR-1~3), 언급 지역
이동 신호[^1]는 확인 없이 즉시 지도를 옮기고 재추천까지 이어지고(FR-4, FR-5), 동선 짜기
실행 시점에 화면 축척이 목표 축척(짧은 변 약 2km)으로 정규화된다(FR-6). 세 변경 모두 화면
동작이라 이 레포(서버)의 코드 변경은 정확히 두 가지다. 결과 부족 notice[^2] 문구
교체(FR-7)와 반복 요청 제한의 자동 이동 직후 재요청 1회 예외(FR-9)다. API 요청과 응답
구조는 바꾸지 않는다(PRD 비목표).

## 배경 · 목표

부산 코스를 짜 달라고 적은 사용자가 부산 이동을 거절할 일은 없는데, 지금 흐름은 토글과
확인과 축척 판단을 사용자에게 미룬다(PRD 문제 상황, 경쟁 서비스 실측). 목표는 문장 입력과
동선 짜기 실행 외에 아무 조작 없이 출발지와 언급 지역이 반영된 추천이 나오는 것이다. 자동
재추천이 반복 요청 제한(10초)과 충돌하는 문제는 첫 응답이 실측 4~7초라 거의 항상
발생하므로, 예외 식별을 서버가 어떻게 하는지가 이 스펙의 핵심 설계 결정이다.

## 스펙이 정하는 결정 3건 (PRD 8절의 위임)

### 결정 1. 축소 신호(ZOOM_OUT)는 화면이 무시한다

**FE는 ZOOM_OUT 신호를 소비하지 않는다(안내 없음). 서버의 신호 생성 코드는 불변이다.**

- 근거: 정규화(FR-6) 뒤에도 시도나 시군구급 언급이면 서버는 ZOOM_OUT을 계속 만든다(1~2km
  화면은 그 지역 외접 사각형의 25%를 담을 수 없다). "더 넓게 볼까요" 안내는 넓혀도 다음
  실행에서 도로 1~2km가 되니 자기모순이라 폐기한다(PRD FR-7과 같은 이유).
- 서버 생성을 끄지 않는 이유: 판정 비용이 ms 수준이고, 지표 로그의 `signal=zoom_out` 발화
  빈도 실측(MSG-468 튜닝 재료)이 계속 필요하며, 무시는 소비 정책이고 생성 중단은 계약
  변경이라 되돌리기가 비싸다. 서버 변경 0이 가장 싸다.
- 자동 이동 후 재요청의 응답에도 ZOOM_OUT이 실릴 수 있는데(부산 중심 1~2km 뷰포트[^3]는
  부산의 25% 미만), 무시 결정이라 FR-5의 재이동 금지와 자연스럽게 정합한다.
- **후속 이행 완료**: SRS FR-ROUTE-14의 "처리 미정" 문구가 이 결정으로 정정 완료됐다("좁아도
  별도 안내는 없다. 축소 신호는 화면이 소비하지 않는다", srs-changelog 2026-08-26 행).

### 결정 2. 결과 부족 문구 확정값

FR-7에 따라 화면을 넓히거나 옮기라는 제안을 문구에서 뺀다. 배너는 서버 notice 값을 그대로
표시하는 FE 계약이라(LLM-WIKI 지도 홈 API 연동 가이드 명문) 재문구는 서버 몫이다.

| 케이스 | 현행 상수 | 교체값 (제안) |
|---|---|---|
| 0곳 (EMPTY_NOTICE) | "조건에 맞는 추천 지점을 찾지 못했어요. 지도 범위를 옮기거나 문장을 바꿔보세요." | "조건에 맞는 곳을 찾지 못했어요. 문장을 바꾸거나 다른 지역에서 다시 짜 보세요." |
| 1~2곳 (INSUFFICIENT_NOTICE) | "조건에 맞는 지점이 충분하지 않아 찾은 만큼만 보여드려요." | "조건에 맞는 곳을 {N}곳만 찾았어요. 문장을 바꾸거나 다른 지역에서 다시 짜 보세요." (N = points 개수) |

- 1~2곳 문구는 개수 삽입 포맷으로 바꾼다. 피그마 시안(제안 5)의 배너 실측 문구 "조건에 맞는
  곳을 2곳만 찾았어요. 문장을 바꾸거나 다른 지역에서 다시 짜 보세요"와 2곳 케이스가 글자
  단위로 일치하고, 1곳은 같은 포맷의 자연 확장("1곳만")이라 별도 확정이 필요 없다고 본다.
  응답 구조는 불변이다(notice는 여전히 String 하나).
- **0곳 문구는 디자인 확정 대기다.** 시안이 1~2곳 케이스만 그렸으므로, 위 값은 시안
  방향(문장을 바꾸거나 다른 지역에서)에 맞춘 제안이다. 확정되면 상수만 바꾼다.

### 결정 3. 축척 정규화의 정의

**동선 짜기 실행 시점에 항상 목표 축척으로 정규화한다. 목표는 뷰포트 짧은 변의 지상 길이 약
2km(시안 주석 값)다.**

- "1~2km"는 맞추는 규칙이 아니라 결과의 허용 범위다. 지도 라이브러리의 줌 단계가 이산이라
  목표 2km에 정확히 맞출 수 없고, 목표에 가장 가까운 줌 단계를 고르면 실제 짧은 변이 이
  범위 언저리에 떨어진다.
- **대역 안이어도 목표로 맞춘다.** "대역을 벗어날 때만 보정"이면 1.1km 화면과 1.9km 화면이
  서로 다른 후보 범위를 쓰게 되어 "화면을 얼마나 확대해 뒀든 같은 범위 기준"(FR-6,
  FR-ROUTE-15)이 깨진다(Codex 3라운드 적발). 항상 목표로 맞추면 같은 자리에서 같은 문장일
  때 같은 목표에 대한 같은 최근접 줌 단계가 선택되어 같은 뷰포트가 나가고, 좁히기와 넓히기
  양방향 보정도 이 규칙에 자연히 포함된다.
- 짧은 변 기준인 이유: 뷰포트 종횡비는 기기마다 다른데(웹 1440×900, 앱 390×844), 짧은 변을
  목표로 잡으면 어느 기기든 보이는 최소 폭이 같아진다.
- 실행 규칙: 지도 중심을 고정한 채 짧은 변이 약 2km가 되는 최근접 줌 단계로 맞춘 뒤
  요청한다. 자동 이동 뒤의 재요청도 같은 목표다(FR-6).
- 서버 검증과의 정합: 짧은 변 2km는 위도로 약 0.018도다. 종횡비를 감안한 긴 변도 0.05도
  안쪽이라 뷰포트 상한(한 변 0.5도, 14401)과 넓이 0 검증(14400)에 닿을 일이 없다. 서버
  검증 코드는 불변이다.
- SRS FR-ROUTE-15는 같은 날 이 정의로 정정 완료됐다(srs-changelog 2026-08-26 행).

## API 명세

`POST /api/routes/recommend`의 요청과 응답 구조, 에러 코드 목록은 모두 불변이다. 바뀌는
것은 관찰 가능한 동작 두 가지다.

| 항목 | 현행 | 변경 후 |
|---|---|---|
| notice 값 (0곳) | 지도 범위 이동을 제안하는 문구 | 결정 2의 0곳 문구 |
| notice 값 (1~2곳) | 개수 없는 고정 문구 | 결정 2의 개수 포맷 문구 |
| 14429 (요청 제한) | 직전 시도로부터 10초 안의 모든 요청 거부 | 직전 응답에 MOVE 신호가 실렸으면 바로 다음 요청 1회는 통과. 그 외는 현행과 동일 |

## 도메인 로직 (서버 몫)

### 1. notice 문구 교체

`RouteRecommendServiceImpl`의 상수 두 개를 결정 2의 값으로 바꾼다. EMPTY_NOTICE는 상수
교체이고, INSUFFICIENT_NOTICE는 개수가 들어가므로 `assemble`에서 points 개수를 넣는 포맷
문자열이 된다. 임계(NOTICE_THRESHOLD 3), 분기 조건, 빈 후보 조기 반환 구조는 전부 불변이다.

### 2. 자동 이동 재요청 예외 (FR-9, 핵심 설계)

**채택안: 직전 응답에 MOVE 신호가 실렸으면 그 사용자의 바로 다음 요청 1회를 서버가 기억해
통과시킨다.** 요청과 응답에 아무것도 더하지 않는다.

기각한 후보 두 가지. 응답에 1회용 토큰을 동봉하는 안과 요청에 "자동 재요청" 필드를 더하는
안은 클라이언트가 위조할 수 없다는 장점이 있지만 둘 다 PRD 비목표(요청과 응답 구조 불변)를
깬다. 위조 내성도 실익이 없다. 서버 기억 방식의 최대 노출이 "MOVE 응답을 받은 사용자가
자동 재요청 대신 수동 요청을 한 번 빨리 보낼 수 있다"인데, 이는 비용 상한(한 번의 실행에
recommend 요청 최대 두 번, 아래 연쇄 차단 참조) 안이라 막을 이유가 없다. 구조를 지키는 안이
더 단순하기까지 하므로 트레이드오프 없이 채택한다.

메커니즘. **기존 요청 제한 맵의 값 타입을 교체하는 구조 변경이다.**
`ConcurrentHashMap<Long, Long>`(시도 시각)을 사용자당 상태 하나를 드는
`ConcurrentHashMap<Long, 상태>`로 바꾸고, 상태는 (lastAttemptMillis, moveExempt) 두 값의
record다. 예외 보유를 별도 자료구조로 두면 소거와 창 선점이 별개 원자 연산이 되어 그 사이
인터리빙으로 아래 "직후 한정"이 깨진다(Codex 1라운드 적발. 10초 경계 직전에 들어온 요청이
예외만 집어 들고 멈춘 사이, 경계 직후 요청이 창 만료로 정상 통과해 새 창을 열면, 먼저 온
요청이 그 새 창에 대고 예외로 통과하는 반례). 판정과 기록을 상태 하나에 대한 원자
선점[^4](compute) 한 번으로 묶어 이 갭을 없앤다.

1. **청구.** `claimRateLimitWindow`의 compute 한 번이 세 전이를 원자로 판정한다.
   - 창 통과(첫 요청이거나 직전 시도로부터 10초 경과): 통과하고 새 상태 (지금 시각, 예외
     없음)를 기록한다. 남아 있던 예외는 이 전이가 함께 지운다.
   - 창 위반이고 예외 보유: 예외를 소비하며 통과하고 새 상태 (지금 시각, 예외 없음)를
     기록한다.
   - 창 위반이고 예외 없음: 14429. compute 안에서 던지므로 상태는 직전 그대로다(거부된
     시도가 창을 늘리지 않는 기존 규칙 불변).

   소비 여부와 이번에 기록한 시도 시각은 청구가 함께 돌려준다(아래 부여의 입력).
2. **부여는 원 청구에 바인딩된 조건부다.** 응답의 mentionedArea.kind가 MOVE이고 이번 요청이
   예외 소비로 통과한 것이 아니면, 같은 맵의 compute로 그 사용자 상태의 moveExempt를 켜되,
   **상태의 lastAttemptMillis가 이 요청의 청구가 기록한 값 그대로일 때만** 켠다(시도 시각
   불변). 값이 다르면 처리 중에 다른 요청이 창을 새로 선점한 것이므로 부여를 버린다. 추천
   처리는 외부 호출을 여럿 지나며(해석과 설명이 별개 호출, 각자 타임아웃) 10초를 넘을 수
   있어, 뒤늦게 완성된 MOVE 응답이 남의 창에 예외를 다는 것을 이 조건이 막는다(Codex
   2라운드 적발). 통과한 청구의 기록 시각끼리는 같은 밀리초일 수 없으므로(정상 통과는 직전
   시도와 10초 이상 벌어지고, 예외 통과는 부여 이후라 항상 뒤 시각이다) 시도 시각이 곧 시도
   식별자로 충분하다. 빈 후보 조기 반환 응답에도 MOVE가 실리므로 부여는 두 반환 경로가
   합류한 뒤(응답 확보 시점) 한 곳에서 한다. ZOOM_OUT과 무신호는 부여하지 않는다(자동
   이동이 없으니 자동 재요청도 없다).

남용 가드 세 겹이 이 구조에 내장된다.

- **연쇄 차단**: 부여 조건 2의 "예외 소비 통과가 아니면" 때문에, 예외로 통과한 요청의
  응답에 MOVE가 또 실려도 예외가 재부여되지 않는다. 이것이 없으면 MOVE를 유발하는 문장을
  반복 전송해 제한을 무한히 뚫는다. 있으면 한 창에 recommend 통과가 최대 두 번이다. 비용
  상한은 이렇게 읽는다. recommend 요청 하나가 외부 호출을 최대 세 번(해석 parse, 설명
  explain, 장소 검색 카카오 최대 1회) 동반하므로, 이 가드가 실제로 강제하는 상한은 **한
  번의 실행에 recommend 요청 최대 두 번(요청마다 동반 외부 호출 포함)**이다. PRD FR-9와
  SRS FR-ROUTE-12는 같은 날 이 기준으로 정정 완료됐다(srs-changelog 2026-08-26 행).
- **직후 한정은 원자 상태 전이와 조건부 부여가 보장한다(별도 TTL 불요)**: 한 사용자의
  판정과 기록이 같은 상태 항목에 대한 compute 하나라 청구들이 직렬화된다. 예외 플래그는
  조건부 부여만 켜는데, 부여 조건이 "상태의 시도 시각 = 부여 요청 자신의 청구가 기록한
  값"이라 플래그가 켜진 창은 언제나 부여 요청이 직접 연 창이다(낡은 MOVE 응답이 다른
  요청의 창에 예외를 달 수 없다). 그리고 그 뒤의 어떤 청구든 통과하는 순간 플래그를 끈다.
  따라서 예외를 소비하는 청구는 부여 요청의 창 안에서 통과하는 첫 청구뿐이고, 소비에는 창
  위반이 필요하므로 언제나 부여 요청의 시도 시각으로부터 10초 안이다. 판정과 기록 사이에
  다른 청구가 끼어들 틈이 없어, 이 성질은 동시 요청과 처리 지연에서도 성립한다.
- **비용 안 나가는 거부는 예외를 안 태운다**: 뷰포트 검증(14400, 14401)과 플래그
  거부(14503)는 청구 호출 전이라 상태 맵을 아예 건드리지 않는다. 창을 소모하지 않는 거부는
  예외도 소모하지 않는다는 기존 배치 원칙(MSG-457, 2026-08-24 확정) 그대로다.

경합과 실패 처리는 기존 원칙을 따른다. 동시 재요청 두 개가 예외 하나를 다투면 compute
직렬화로 하나만 소비 전이를 타고 나머지는 14429다. 예외로 통과한 요청이 이후 단계에서
실패해도(14502 등) 예외를 되돌리지 않는다. 외부 비용이 이미 나갔기 때문이며, 시도 시각
미롤백과 같은 원칙이다. 예외 통과도 시도 시각을 기록하므로 그다음 요청부터는 새 10초 창이
정상 적용된다.

단일 인스턴스 전제의 메모리 구조라는 한계도 기존 요청 제한 맵과 동일하다(다중 인스턴스
전환 시 Redis로 함께 옮긴다. MSG-457 ponytail 주석의 단순화 계급 그대로).

지표 로그에 `exempt={true|false}` 키 하나를 더한다. 예외 발동 빈도가 비용 조항의 실측
재료다. 문장 원문 비기록 규칙은 그대로다.

### 3. 자동 재요청이 예외를 필요로 하는 이유 (배경 기록)

자동 이동 후 재요청은 뷰포트가 달라져 해석 캐시[^5] 키가 어긋난다. 캐시 미스라 외부 parse
호출이 나가고, 첫 응답이 4~7초라 재요청은 거의 항상 10초 창 안에 도착해 현행 제한에
걸린다. 화면이 10초를 채우고 재요청하는 안(서버 무변경)은 체감 대기 15초 안팎이라 PRD가
기각했다.

## 화면 동작 계약 (FE 몫, 이 레포 구현 없음)

프런트 레포가 구현할 동작을 서버 계약 소비 방식으로 정의한다. 서버 테스트 대상이 아니다.

1. **실행 시점 처리 순서**: 동선 짜기 버튼을 누르면 축척 정규화(결정 3) 후 현재 위치가
   정규화된 뷰포트 안인지 판정하고 요청을 보낸다(PRD 시퀀스 다이어그램 순서).
2. **origin 자동 판정 (FR-1~3)**: 현재 위치가 뷰포트 안이면 요청의 origin[^6](기존 선택
   필드)에 현위치 좌표를 넣고, 밖이거나 알 수 없으면(권한 거부, 측위 실패) 필드를 아예
   보내지 않는다. origin이 실릴 때만 입력 카드에 "현재 위치에서 출발" 상태줄이 붙고, 이
   표시는 누를 수 없다. 출발 토글을 비롯한 출발지 조작 UI는 없다. 측위 실패가 추천 실패로
   번지지 않는다.
3. **MOVE 소비 (FR-4, FR-5)**: 응답에 kind MOVE 신호가 있으면 확인 없이 지도를
   `mentionedArea` 중심 좌표로 즉시 옮기고 축척은 결정 3의 목표로 맞춘 뒤, 토스트
   "{mentionedArea.name}으로 이동했어요" 하나로만 알린다(name은 서버 정식 표기 그대로).
   원래 화면 기준 결과는 표시하지 않고 버린 뒤 새 뷰포트로 재요청한다. 재요청 시 origin은
   2의 규칙으로 다시 판정한다(이동으로 현위치가 화면 밖이 되면 생략, 피그마 제안 2).
   재요청 응답에 신호가 또 실려도 다시 옮기지 않고 결과를 그대로 표시한다.
4. **ZOOM_OUT 무시 (결정 1)**: 어떤 안내도 만들지 않는다.
5. **무신호 (FR-8)**: 지금과 같다. 요청 한 번으로 끝난다.
6. **결과 부족 배너**: 서버 notice 값을 그대로 표시한다(기존 계약 불변, 문구만 서버에서
   바뀐다).
7. **다시 짜기 버튼**: 10초 비활성 처리(위키 FE 가이드 주의 지점 3)는 수동 재요청에만
   해당한다. 자동 재요청은 예외로 통과하므로 버튼 상태와 무관하게 즉시 보낸다.

관찰 하나를 남긴다. 결정 1(ZOOM_OUT 무시)과 이동 후 축척을 목표로 맞추는 규칙이
합쳐지면, MSG-468이 축척 재료로 동봉한 외접 사각형(min/max 좌표 4개)의 화면 소비처가
사라진다. 응답 구조 불변이 비목표라 필드는 그대로 두고, 계약 축소는 이 티켓 범위가 아니다.

- **데이터 저장 위치**: 새 영속 저장소 없음. 예외 상태는 `RouteRecommendServiceImpl`의

- **예외 흐름**: 14429는 `claimRateLimitWindow`의 compute 리매핑 함수 안에서

- **빈 동작**: 생명주기 특이점 없음. 상태 맵은 빈 필드라 `@PostConstruct`도 스케줄러도
