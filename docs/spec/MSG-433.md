# MSG-433: 회원가입 약관 동의 저장과 게이트 판별

**Owner**: B (user 도메인 단독. `com.msg.fillmap.user.*`만 변경하고 auth 패키지는 건드리지 않는다)

> 요구사항 정본: `docs/prd/MSG-433-prd.md` (상태: 검토됨) · 상위 요구사항 ID: SRS FR-USER-15
> 이 스펙은 PRD의 FR 1~10에 "어떻게"만 붙인다. 요구사항 해석이 갈리면 PRD가 이긴다.

## 개요

회원가입 동의 5항목(만 14세 이상 확인, 서비스 이용약관, 개인정보 수집·이용, 위치기반서비스
이용약관, 마케팅 정보 수신)을 `users` 컬럼으로 저장하고(철회 없는 필수 4항목은 동의 시각을
영구 보존, 철회 가능한 것은 마케팅뿐이라 그 항목만 현재 상태와 마지막 변경 시각), 클라이언트 동의
게이트[^1]가 판별에 쓸 전용 동의 상태 조회 API를 신설한다. 위치기반서비스 항목은 기존
`users.location_consent`(MSG-402)와 한 값으로 관리해 이중 저장을 만들지 않는다. 로그인 API와
프로필 응답은 무수정이다 (2026-08-19 정민 확정, MSG-402 스펙 D-2와 같은 방향).

## 배경과 목표

카카오 로그인 동의 화면은 "카카오가 필맵에 정보를 제공해도 되는가"까지만 다루므로, 사업자 약관
동의 5항목은 필맵이 직접 받아 증빙(언제 무엇에 동의했나)을 보관해야 한다. 지금 서버에는 위치
동의 한 칸만 있어 모바일 게이트(MSG-422, 웹 선례 MSG-407)가 전제하는 "로그인 직후 서버가
미동의로 응답하면 동의 화면을 띄우고, 제출하면 저장된다"는 흐름이 성립하지 않는다. 이 티켓으로
저장과 판별 재료를 완성한다. 미동의 사용자의 다른 API를 서버가 차단하지는 않는다 (FR-9, 차단은
클라이언트 게이트 몫이라는 FR-USER-14 원칙 그대로).

## 성공 기준

- 로그인 직후 동의 상태 조회 한 번으로 필수 동의 완료 여부와 항목별 여부를 알 수 있다 (FR-1).
- 동의 제출 한 번으로 5항목이 저장된다. 필수 3항목(만 14세, 서비스약관, 개인정보)은 동의 시각이
  영구 보존되고(철회 API가 없어 덮일 경로 자체가 없다), 위치도 철회 불가 전환(D-11)으로 같은
  성질을 갖는다. 철회 가능한 것은 마케팅뿐이라 그 항목만 현재 상태와 마지막 변경 시각이 남는다
  (FR-2, FR-4 정밀화 반영).
- 필수 4항목 중 하나라도 동의가 아닌 제출은 400으로 거절되고 아무 항목도 저장되지 않는다 (FR-3).
- 제출 후 기존 `location_consent`가 켜져 있고, 프로필 화면의 위치 동의와 값이 하나다 (FR-5).
- 위치 동의 철회 요청은 400(1400)으로 거절되고, 필수 동의를 마친 사용자의 완료 상태가 사후에
  풀리지 않는다 (D-11).
- 마케팅 수신 동의는 동의 상태 조회에 동봉되고, 전용 API로 켜고 끌 수 있으며 실제로 값이 바뀔
  때만 변경 시각이 갱신된다 (FR-6).
- V37 적용만으로 기존 사용자 전원이 필수 동의 미완료로 시작한다. 백필 없음 (FR-7).
- 같은 내용 재제출이 성공한다 (FR-8 멱등[^2]). 필수 3항목은 최초 동의 시각이 그대로고, 위치와
  마케팅은 같은 값 재제출이면 마지막 변경 시각이 유지된다 (`IS DISTINCT FROM` 경로).
- 계정 삭제 시 users 행 삭제로 동의 기록도 함께 제거된다 (비기능 "데이터 정합", 컬럼이라 별도
  정리 불요).

## API 명세

세 엔드포인트 모두 인증 필수이고 항상 본인 계정만 대상이다 (경로에 대상 식별자 없음, 비기능
"보안/인가"). 인증·부재 에러는 공통이다:

| 상황 | HTTP | developCode | 비고 |
|------|------|-------------|------|
| 토큰 없음 | 401 | 2403 | AuthErrorCode UNAUTHENTICATED |
| 무효 토큰 | 401 | 2401 | AuthErrorCode INVALID_TOKEN |
| 만료 토큰 | 401 | 2402 | AuthErrorCode EXPIRED_TOKEN |
| 사용자 부재 | 404 | 1404 | USER_NOT_FOUND (탈퇴 직후 재호출 등) |

기존 위치 동의 API의 철회 거부 하나가 신규 상수다 (D-11):

| 상황 | HTTP | developCode | 비고 |
|------|------|-------------|------|
| 위치 동의 철회 시도 | 400 | 1400 | UserErrorCode LOCATION_CONSENT_IRREVOCABLE — `PUT /me/location-consent`에 `consented=false` (1409는 이메일 중복이 선점해 1400 배정) |

### 1. 동의 상태 조회 (신규): `GET /api/users/me/consents`

로그인 직후 게이트 판별용 (FR-1). 마케팅 상태 조회(FR-6)도 이 응답에 동봉된다.

**Response**: `SuccessResponse<ConsentStatusResponseDto>` (신규 DTO)

| 필드 | 타입 | 설명 |
|------|------|------|
| `ageOver14` | `Boolean` (required) | 만 14세 이상 확인 여부. `age_over14_consented_at IS NOT NULL` |
| `serviceTerms` | `Boolean` (required) | 서비스 이용약관 동의 여부. `service_terms_consented_at IS NOT NULL` |
| `privacyPolicy` | `Boolean` (required) | 개인정보 수집·이용 동의 여부. `privacy_consented_at IS NOT NULL` |
| `locationTerms` | `Boolean` (required) | 위치기반서비스 이용약관 동의 여부. 기존 `location_consent` 그대로 (D-3) |
| `marketing` | `Boolean` (required) | 마케팅 정보 수신 동의 여부 (선택 항목) |
| `requiredCompleted` | `Boolean` (required) | 필수 4항목 전부 동의면 true (D-8). false면 FE가 동의 게이트를 띄운다 |

`@Schema`의 `requiredProperties`에 6개 필드를 전부 넣는다. 빠뜨리면
`ResponseSchemaNullabilityTest`가 깨진다 (MSG-402 선례).

성공 예시 (기존 사용자 첫 조회, FR-7):

```json
{
  "developCode": 200,
  "message": "성공",
  "data": {
    "ageOver14": false,
    "serviceTerms": false,
    "privacyPolicy": false,
    "locationTerms": false,
    "marketing": false,
    "requiredCompleted": false
  }
}
```

### 2. 동의 제출 (신규): `PUT /api/users/me/consents`

가입 게이트의 "동의하고 시작하기" 제출 (FR-2). 재제출 멱등 (FR-8, D-9).

**Request**: `ConsentSubmitRequestDto` (신규)

| 필드 | 타입 | 검증 | 설명 |
|------|------|------|------|
| `ageOver14` | `Boolean` | `@NotNull` `@AssertTrue` | 만 14세 이상 자기 확인 (필수) |
| `serviceTerms` | `Boolean` | `@NotNull` `@AssertTrue` | 서비스 이용약관 (필수) |
| `privacyPolicy` | `Boolean` | `@NotNull` `@AssertTrue` | 개인정보 수집·이용 (필수) |
| `locationTerms` | `Boolean` | `@NotNull` `@AssertTrue` | 위치기반서비스 이용약관 (필수) |
| `marketing` | `Boolean` | `@NotNull` | 마케팅 정보 수신. true·false 모두 유효 (선택 항목) |

`@AssertTrue`는 null을 통과시키므로 `@NotNull`을 반드시 병기한다. 필수 필드가 false거나
누락이면 `@Valid` 실패로 400이고 서비스에 닿지 않는다 (FR-3, D-6). 원시 boolean이 아니라
Boolean인 이유는 누락이 false로 둔갑하지 않게 하기 위해서다 (`LocationConsentUpdateRequestDto`
주석 동일).

**Response**: `SuccessResponse<ConsentStatusResponseDto>` (제출 후 상태. FE가 재조회 없이 게이트
통과를 확정한다. `requiredCompleted`는 이 경로에서 항상 true)

**에러 케이스** (전부 기존 코드, D-6): 필수 항목 false 또는 누락은 400, 나머지는 공통 표.

### 3. 마케팅 수신 동의 변경 (신규): `PUT /api/users/me/marketing-consent`

가입 후 설정 화면의 켜고 끄기 (FR-6). `PUT /api/users/me/location-consent` 미러다 (D-4).

**Request**: `MarketingConsentUpdateRequestDto` (신규)

| 필드 | 타입 | 검증 | 설명 |
|------|------|------|------|
| `consented` | `Boolean` | `@NotNull` | true면 동의, false면 철회 |

**Response**: `SuccessResponse<ConsentStatusResponseDto>` (변경 후 상태)

같은 값 재저장은 성공하되 변경 시각이 그대로다 (멱등, location-consent와 동일 규칙).

### 기존 API와의 관계 (FR-5)

- `PUT /api/users/me/location-consent` (MSG-402): **켜기 전용으로 축소** (D-11). 제출과 이 API가
  같은 `location_consent` 한 값을 쓴다. 켜기(`true`)는 무수정으로 유효하고 멱등이며, 철회
  (`false`)는 1400으로 거절된다. 값이 true에서 되돌아갈 경로가 없어 동의를 마친 사용자의
  `requiredCompleted`가 사후에 false가 되지 않는다. FE 공유 필요 사항이다.
- `GET /api/users/me` 프로필과 로그인 API: 무수정 (D-1).
- 필수 4항목(만 14세·서비스약관·개인정보·위치기반서비스) 전부 철회 API가 없다. 이 동의들의
  철회는 계정 삭제(`DELETE /api/users/me`)다 (D-2, D-11).

## 도메인 로직

`UserServiceImpl`에 메서드 3개 추가. 갱신 2개는 메서드 단위 `@Transactional` 필수다
(`@Modifying` 쿼리는 트랜잭션 없이 실행이 거부된다. 기존 관례 동일).

### 동의 상태 조회: `getConsentStatus(Long userId)`

`findUser(userId)`로 조회해 (부재 시 1404) 엔티티 필드를 `ConsentStatusResponseDto.from(user)`로
변환한다. 필수 3항목은 시각의 NULL 여부, 위치와 마케팅은 boolean, `requiredCompleted`는 4항목
AND를 DTO 팩토리에서 계산한다 (D-8).

### 동의 제출: `submitConsents(Long userId, ConsentSubmitRequestDto request)`

1. 주입된 `Clock`으로 `now`를 만든다 (UTC, MICROS 절단, D-10).
2. `userRepository.submitConsents(userId, request.marketing(), now)` 원자 UPDATE 한 문장 (D-5).
   영향 행 0이면 1404.
3. 재조회해 `ConsentStatusResponseDto.from(user)` 반환. `@Modifying(clearAutomatically = true)`로
   갱신 전 스냅숏을 비우고 읽는다 (MSG-402 선례).

리포지토리 쿼리 (native). 필수 4항목은 검증을 통과했으면 전부 동의 확정이라 파라미터는
`marketing` 값과 시각뿐이다:

```sql
UPDATE users
SET age_over14_consented_at = COALESCE(age_over14_consented_at, :now),
    service_terms_consented_at = COALESCE(service_terms_consented_at, :now),
    privacy_consented_at = COALESCE(privacy_consented_at, :now),
    location_consent = TRUE,
    location_consent_changed_at = CASE
        WHEN location_consent IS DISTINCT FROM TRUE THEN :now
        ELSE location_consent_changed_at
    END,
    marketing_consent = :marketing,
    marketing_consent_changed_at = CASE
        WHEN marketing_consent IS DISTINCT FROM :marketing THEN :now
        ELSE marketing_consent_changed_at
    END
WHERE id = :userId
```

- `COALESCE`가 필수 3항목의 최초 동의 시각을 영구 보존하므로 재제출이 증빙 시각을 덮지 않는다
  (FR-4, FR-8).
- 위치는 MSG-402 온보딩으로 이미 켠 사용자라면 CASE가 기존 변경 시각을 유지한다 (FR-5 정합).
- 마케팅은 재제출에서 값이 달라지면 시각이 갱신되고, 같으면 그대로다.
- 철회 가능한 항목은 마케팅뿐이며(위치는 D-11로 철회 불가), 철회 뒤 원 동의 시각이 남지 않고
  마지막 변경 시각만 보관된다. 정밀화된 FR-4가 이 항목의 증빙을 현재 상태와 마지막 변경 시각으로
  정의한다 (D-4).
- 위치의 `IS DISTINCT FROM` CASE는 철회 불가 전환 이후에도 남는다 — 선행 동의자(MSG-402 온보딩
  경유)의 최초 동의 시각을 제출이 덮지 않게 하는 것이 그 역할이다.
- 시각 샘플이 잠금 선행이라 동시 요청에서 저장 시각이 실제 순서와 어긋날 수 있는 수용 경합은
  MSG-402 작업 로그의 판정(동의 여부 자체는 항상 마지막 값으로 정확)을 그대로 승계한다.

### 마케팅 변경: `updateMarketingConsent(Long userId, boolean consented)`

`updateLocationConsent`의 갱신 부분과 동형이다. 원자 UPDATE(`IS DISTINCT FROM` CASE) 한 문장,
영향 행 0이면 1404, 재조회 후 `ConsentStatusResponseDto` 반환. 마케팅은 철회가 가능하므로
`false` 거부 가드가 없다 (위치와 다른 유일한 지점, D-11).

### 위치 철회 거부: `updateLocationConsent(Long userId, boolean consented)` (기존 메서드 수정)

메서드 진입부에서 `consented`가 false면 `ApiException(LOCATION_CONSENT_IRREVOCABLE)`을 던진다
(D-11). 거부가 UPDATE 앞에서 끝나므로 저장 값도 동의 시각도 건드리지 않는다. 이미 켜진
사용자든 아직 미동의인 사용자든 false 요청은 같은 1400이다 — 이 API의 계약이 "켜기"로
바뀐 것이지 상태에 따라 갈리는 규칙이 아니다.

미동의 상태를 읽고 분기하는 서비스는 어디에도 없다 (FR-9). glossary의 방문·점령 흐름에 변화가
없다.

## 미해결 질문

서버 구현을 막는 미해결 질문은 없다. 저장 모델(users 컬럼 확장)과 게이트 판별(전용 조회)은
2026-08-19 정민 확정을 그대로 따랐다.

[^1]: 게이트: 조건을 채우기 전에는 다음 화면으로 못 가게 막는 클라이언트 관문. 미동의 차단을 서버가 아니라 클라이언트가 맡는 원칙은 FR-USER-14에서 확정됐고 이 티켓도 같다.
[^2]: 멱등(idempotent): 같은 요청을 여러 번 보내도 한 번 보낸 것과 결과가 같은 성질. 게이트 화면 재진입이나 네트워크 재시도로 제출이 중복될 수 있어 필요하다.
[^3]: 원자 UPDATE: 읽기와 판정과 쓰기를 UPDATE문 하나에 담아 DB가 한 번에 실행하게 하는 방식. 문장 실행 중 행 잠금이 걸려 동시 요청이 직렬화되고, 부분 저장 상태가 생길 수 없다.
[^4]: COALESCE: 인자 중 첫 번째 NULL 아닌 값을 고르는 SQL 함수. 여기서는 "이미 시각이 있으면 유지, 없으면 지금 시각"이 되어 최초 동의 시각 보존을 한 표현식으로 만든다.
[^5]: IS DISTINCT FROM: NULL을 보통 값처럼 취급하는 PostgreSQL의 불일치 비교. `=`는 NULL 비교가 unknown이 되어 CASE 분기가 새는데, 이 연산자는 NULL과 값의 비교도 참·거짓으로 떨어진다.
[^6]: Clock: 자바 표준 시계 추상화(`java.time.Clock`). 프로덕션은 `Clock.systemUTC()` 고정, 테스트는 고정 시각 주입으로 "지금"이 들어간 로직을 결정적으로 검증한다. 인자 없는 `now()` 금지 컨벤션의 실행 수단이다.

### 2026-08-19 정책 전환 — 위치 동의 철회 불가 (D-11 반영)

- 팀 합의로 SRS FR-USER-14가 개정돼 위치기반서비스 동의가 철회 불가가 됐다. 기존 `PUT /api/users/me/location-consent`는 켜기 전용이 되고 `consented=false`는 신규 `UserErrorCode.LOCATION_CONSENT_IRREVOCABLE`(1400, 400)로 거절한다. 켜기와 그 멱등성은 그대로다 — 웹 온보딩(MSG-407)이 쓰는 경로라 유지가 조건이었다.
- 거부 위치는 `UserServiceImpl.updateLocationConsent` 진입부다. `false`는 형식상 유효값이라 Bean Validation으로 표현할 수 없고, 진입부에서 던지므로 UPDATE·시각 산출 전에 끝나 저장 값과 동의 시각을 건드리지 않는다.
- **예외 흐름 추가**: 위치 철회 요청 → 서비스가 `ApiException(LOCATION_CONSENT_IRREVOCABLE)` → GlobalExceptionHandler → HTTP 400 · developCode 1400 · "위치기반서비스 이용 동의는 철회할 수 없습니다". 1409는 `EMAIL_ALREADY_EXISTS`가 선점해 1400을 배정했다 (user 1xxx 대역, response-pattern.md 표에 이미 등재된 도메인이라 표 갱신 불요).
- **소멸한 동작**: D-3이 수용했던 "철회하면 `requiredCompleted`가 false로 복귀해 게이트가 다시 뜬다"가 사라졌다. 저장 값이 true에서 되돌아갈 경로가 없어 동의를 마친 사용자의 완료 상태가 사후에 풀리지 않는다. `requiredCompleted`는 위치 포함 4항목 AND 그대로다 (D-8 불변).
- 쿼리는 그대로다. `submitConsents`의 위치 `IS DISTINCT FROM` CASE는 선행 동의자(MSG-402 온보딩 경유)의 최초 동의 시각을 제출이 덮지 않게 하는 역할로 남는다.
- **테스트 정정**: 철회 성공을 기대하던 MSG-402 테스트 3건을 거절 기대로 바꾸거나 지웠다 — `동의를_끄면...`→`동의를_끄는_요청은_1400으로_거절된다`, `철회하면_변경_시각이...`→`거절된_철회_시도는_동의_시각도_건드리지_않는다`, `false를 false로 재저장`·`철회 후 재저장` 2건은 철회가 불가능해져 삭제하고 `미동의_사용자의_false_요청도_1400이다`(상태 무관 거절)와 `웹_온보딩의_켜기_재호출은_세_번을_보내도_성공한다`(MSG-407 회귀 방지)로 대체. 생명주기 통합 시나리오 ③은 "철회 거절 후 완료 유지"로, ④는 "재제출 멱등, 시각 무갱신"으로 다시 썼다. 컨트롤러 와이어 계약은 `UserProfileControllerTest`가 400·1400으로 확인한다.
