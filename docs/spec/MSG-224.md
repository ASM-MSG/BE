## 개요

전국문화축제표준데이터 정제본(`festivals.jsonl`)의 진행 중·예정 축제를 `missions`(EVENT) +
`mission_grids`(중심 좌표 기준 9×9 격자 81행, target_count=1)로 적재한다(FR-1·2). 러너는
플래그 게이트 ApplicationRunner **1개**(region GeoJSON 시더/MSG-154 패턴)로, 초기 시드와 격주
수동 갱신을 같은 코드 경로로 처리한다 — 시드는 "빈 DB에서의 갱신"의 특수 경우다. dedupe는
**좌표(중심 격자)+기간**으로 멱등(FR-3), 갱신은 종료 축제 정리+신규 추가를 단일 트랜잭션으로
수행해 실패 시 기존 데이터가 그대로 남는다(FR-4·5). **상시 스케줄러 금지**(2026-07-30 성민 확정).
신규 API 없음. DDL은 **V13 1건**(`missions.source` 적재 출처 컬럼 — Codex 리뷰 파생, 아래 D7).

## 배경 · 목표

미션 인프라(V6 스키마·조회·판정)는 완성됐지만 **미션 데이터가 0건**이라 지도에 아무것도 보이지
않는다. 이 티켓이 발견 → 참여 → 보상 루프의 첫 고리(발견할 실데이터)를 채운다. 규모 실측:
부산 지역 17건, 특정 시점 지도 노출 면 0~2개 — 인플레이션 없음 검증됨(티켓 확정사항).

## 성공 기준

아래 "테스트 시나리오"가 이 기준의 검증 수단이다.

1. 플래그 off(기본) 기동·통합 테스트에서 러너가 아무것도 하지 않는다 — 평시 기동 무영향
   (PRD 비기능·운영)
2. 시드 실행 시 진행 중·예정 축제만 EVENT 미션으로 적재된다 — 미션당 mission_grids 81행
   (중심±4, seq NULL)·target_count=1·region_code NULL·path NULL·**source='FESTIVAL'** (FR-1·2, D7)
3. 같은 파일로 재실행하면 신규 적재 0건 — 중심 격자+기간 dedupe 멱등 (FR-3)
4. 갱신 실행 시 종료 축제(end_at < 현재 UTC)가 삭제되고 mission_grids가 CASCADE로 함께
   정리된다. 단, 스탬프 걸린 미션은 잔존하고 **source가 'FESTIVAL'이 아닌 미션(팝업 등 타 소스·
   NULL 수동 데이터)은 불가침** (FR-4, D7)
5. 파일 부재·유효 0건 파싱·중간 예외 시 전체 롤백 — 기존 미션 데이터 무변경 (FR-5)
6. KST 날짜 → UTC 순간 변환이 MSG-223 §D3 계약과 일치한다: "7/1~7/5" →
   `start_at='2026-06-30 15:00:00'`, `end_at='2026-07-05 14:59:59'`
7. `./gradlew test` green

### D2. 9×9 격자 전개와 grid_id 생성

중심 격자 = `GridEncoder.encode(latitude, longitude)` → `GridEncoder.decode`로 `(gridY, gridX)` 복원
→ `dy, dx ∈ [-4, 4]` 이중 루프로 `"{gridY+dy}_{gridX+dx}"` 81개 생성.

- 인덱스 → id 문자열 조립은 시더의 private 헬퍼 1줄로 한다(`gridY + "_" + gridX`). 포맷은
  glossary 확정 논리 식별자 `"{grid_y}_{grid_x}"`라 드리프트 위험이 없고, 좌표에
  `dy*GRID_LAT_STEP`를 더해 `encode(double,double)`를 재호출하는 방식은 셀 경계 부동소수점
  오프바이원 위험이 있어 배제한다. (원하면 `GridEncoder`에 `encode(long,long)` 오버로드 추가가
  정석이나 Owner A 파일 접촉이라 이번 범위에서 제외 — 리뷰에서 A가 원하면 전환)
- 81행은 `mission_grids` PK(mission_id, grid_id)로 자연 중복 방지 — 미션 신규일 때만 삽입하므로
  충돌 경로 없음.

### D3. dedupe — 중심 격자 + 기간 (FR-3)

**dedupe 키 = (중심 grid_id, start_at, end_at).** 이름을 쓰지 않는다 — 같은 축제가 기관별 파일에
이름 변형("제8회 ~"·연도 접두)으로 중복 등장하는 원본 특성 때문(티켓 확정). 좌표는 격자
양자화(≈100m 허용 오차)로 비교한다.

- **소스 내 dedupe**: 같은 키의 행은 첫 행만 적재.
- **DB 대조(재실행 멱등)**: 기존 **`source='FESTIVAL'`** 미션 전체를 기간과 함께 로드하고, 각
  미션의 중심 격자를 `mission_grids` 81행에서 `min(gridY)+4, min(gridX)+4`로 복원한다 — 축제
  러너 산출물만 조회하므로 9×9 블록(중심±4)이 보장돼 결정적. `findByType(EVENT)` 조회는
  금지 — EVENT는 팝업(MSG-235, 1격자)과 공유 타입이라 1격자 미션의 min+4가 가짜 중심 키를
  만들어 실축제를 오스킵한다(Codex 리뷰 파생, D7). 축제 미션은 수백 건 규모·수동 실행이라
  메모리 대조로 충분(조회는 기존 `MissionGridRepository.findByMissionIds` 재사용).
- 중심 격자를 **정확 일치**로 비교한다 — "후보 블록에 포함" 판정은 동일 기간 인접(≤400m) 축제를
  오흡수한다. 같은 중심 격자+같은 기간의 서로 다른 두 행사는 1건으로 흡수되는데, 이것이 FR-3의
  의도된 의미다(같은 곳·같은 기간 = 같은 축제).
- 수용 한계: 축제 기간이 원본에서 연장·변경되면 키가 달라져 신 미션이 추가되고 구 미션은 종료
  후 갱신(D4)이 정리한다 — 종료 전까지 한시적 중복 노출 수용. 내년 회차는 기간이 달라 새 미션 —
  올바른 동작.

### D4. 갱신 러너 — 러너 1개, 단일 트랜잭션 (FR-4·5)

시드와 갱신은 **같은 러너**다: ① 파일 파싱·필터(D1) → ② dedupe 통과분 INSERT(D2·D3) →
③ 종료 축제 정리. 빈 DB에서 돌리면 ③이 0건인 시드가 되고, 이후 격주 실행이 갱신이 된다.

**③ 종료 정리 SQL** — MSG-223 §D2가 명시한 **`AT TIME ZONE 'UTC'` 규칙 준수 필수**
(`timestamp` vs `timestamptz` 비교는 세션 타임존으로 캐스트돼 KST 세션에서 9시간 스큐 —
리뷰 실측, `findAwardCandidateIds`·StreakRepository 동일 패턴):

```sql
DELETE FROM missions m
WHERE m.source = 'FESTIVAL'
  AND m.end_at IS NOT NULL
  AND m.end_at < statement_timestamp() AT TIME ZONE 'UTC'
  AND NOT EXISTS (SELECT 1 FROM user_missions um WHERE um.mission_id = m.id)
```

- `mission_grids`는 `ON DELETE CASCADE`(V6)로 함께 정리 — 별도 DELETE 불요.
- **스탬프 걸린 미션은 건너뛴다**(`NOT EXISTS`) — V6 FK `user_missions.mission_id NO ACTION`이
  하드삭제를 차단하므로(비회수 보호) 시도 자체가 실패한다. 잔존 행은 `findActive`가 이미
  숨긴다 — 정리는 위생이지 노출 제어가 아니다.
- **`source = 'FESTIVAL'` 한정** — 타 소스·수동 데이터 불가침. 당초 `type='EVENT'` 한정이었으나
  EVENT는 팝업(MSG-235)과 공유 타입이라 종료 팝업을 축제 갱신이 오삭제하는 결함(Codex 리뷰
  파생) → source 컬럼 도입으로 교체(D7, 2026-07-31 성민 확정). `source IS NULL`(수동/기타)은
  어떤 러너도 건드리지 않는 안전 기본값이다.
- 소스에서 사라졌지만 아직 안 끝난 축제는 **삭제하지 않는다** — 정리 대상은 "종료"뿐(FR-4 문언).
  취소 공지 대응 같은 확장은 근거 티켓 없이 하지 않는다.

**원자성(FR-5)**: 러너의 실행 메서드에 `@Transactional` — INSERT·DELETE가 한 트랜잭션이라 어느
단계가 실패해도 전체 롤백되고 기존 미션 데이터가 그대로 남는다(부분 삭제로 노출 공백 금지).
파일 부재·유효 0건 파싱은 RegionSeeder 선례대로 **명확한 예외로 조기 실패** — 잘못된 파일이
조용히 no-op으로 넘어가지 않게.

**플래그 게이트**: `@Value("${fillmap.mission.festival.seed.enabled:false}")` — off면 early return.
파일 경로 `@Value("${fillmap.mission.festival.seed.path:data/mission/festivals.jsonl}")`.
yml 무수정(기본값이 곧 설정 — region 시더와 동일, 켤 때만 env/인자로 override). `@Order(30)`
(RegionSeeder 10 · ZoneSeeder 20 이후 — 의존은 없지만 결정적 순서. 당초 20이었으나 ZoneSeeder
점유 실측으로 30 조정, 2026-07-31 리뷰 사전 점검).

### D5. 시간 변환 — KST 날짜 → UTC 순간 (MSG-223 §D3 계약 이행)

원본 날짜는 KST 달력 날짜, DB TIMESTAMP는 UTC 순간이다(glossary). MSG-223 §D3이 "변환은
시더(MSG-224) 몫"으로 지정한 계약을 그대로 이행한다:

- `start_at` = `startDate` KST 00:00:00 → UTC (예: `2026-07-01` → `2026-06-30 15:00:00`)
- `end_at` = `endDate` KST 23:59:59 → UTC (예: `2026-07-05` → `2026-07-05 14:59:59`) —
  판정이 양끝 포함(`v.recorded_at <= end_at`)이므로 종료일 자정 직전까지 인정된다

Java: `date.atStartOfDay(KST)` / `date.atTime(23, 59, 59).atZone(KST)` →
`.withZoneSameInstant(UTC).toLocalDateTime()`. Zone 상수는 `Asia/Seoul`·`ZoneOffset.UTC`.
D1의 "오늘(KST)" 판정도 `LocalDate.now(clock)` + KST 존 — 양변이 KST 달력 날짜라 TZ 함정 없음.
클럭은 생성자 주입 가능하게(테스트용, `MissionQueryServiceImpl` 클럭 주입 선례 — 기본
`Clock.system(KST)`).

### D7. 적재 출처 컬럼 — `missions.source` (V13, Codex 리뷰 파생)

축제와 팝업(MSG-235)이 같은 `EVENT` 타입을 공유한다(MSG-222 §유형→shape: "EVENT | 축제·팝업",
팝업=1격자 BOX). 타입만으로는 축제 러너가 "자기 산출물"을 식별할 수 없어 ① 종료 정리가 팝업을
오삭제하고 ② dedupe 중심 복원(min+4)이 1격자 팝업에서 가짜 키를 만든다 — 2026-07-31 Codex 리뷰
지적 2건(P2), source 컬럼 도입으로 해소(성민 확정).

- **V13**: `ALTER TABLE missions ADD COLUMN source VARCHAR(30)` — NULL 허용, CHECK 없음.
  NULL = 수동/미상 적재 → 모든 러너의 정리·dedupe 대상에서 제외(안전 기본값). CHECK를 두지
  않는 이유: 소스 추가(MSG-225 코스·MSG-235 팝업)마다 마이그레이션을 강제하지 않기 위해.
  기존 행 backfill 없음 — 러너 도입 전 데이터는 전부 수동이므로 NULL이 맞다.
- **엔티티**: `Mission.source`는 **String** 필드 + 시더의 `static final String SOURCE_FESTIVAL =
  "FESTIVAL"` 상수로 기록. enum으로 두면 후속 소스(POPUP 등)가 상수 추가를 잊었을 때 기존 조회
  경로 전체가 역직렬화로 터진다 — 공유 엔티티라 String이 안전. 오타 위험은 상수 1곳으로 수렴.
- **조회·판정 무영향**: `findActive`(MSG-222)·판정 엔진(MSG-223)은 source를 보지 않는다 —
  소스 구분은 적재 러너들의 소유권 문제일 뿐 노출·판정 의미가 없다.
