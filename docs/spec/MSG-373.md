# MSG-373: 프로필 이미지 변경과 가입일 노출

**Owner**: B

> 요구사항 정본: `docs/prd/MSG-373-prd.md` (상태 검토됨, 2026-08-11 정민 승인).
> 전역 요구사항은 `docs/srs.md` FR-USER-12(등록, 변경, 제거, 한도)와 FR-USER-13(조회 노출, 친구 축 반영).
> 이 스펙은 PRD의 요구사항에 "어떻게"만 붙인다.

## 개요

프로필 이미지의 "쓰는 쪽"을 만든다. `users.profile_image_url` 컬럼과 엔티티 매핑은 초기
스키마(V1)부터 있고 친구 축 응답 3종(친구 목록, 친구 프로필, 받은 친구 요청)은 이미 이 값을
내려주는데, 값을 채울 API가 없어 항상 null이다. 이번 티켓에서 presigned URL[^1] 직접 업로드로
이미지를 등록하고 변경하고 제거하는 API 3개를 추가하고, 내 프로필 조회 응답에
프로필 이미지 URL과 가입 시각을 싣는다.

## 배경 · 목표

웹 디자인 ver 11의 프로필 편집 모달에 이미지 "변경" 버튼이 있고 프로필 화면에 가입일 표기가
있는데(2026-08-10 실측), 서버가 둘 다 지원하지 않는다. 목표는 세 가지다.

- 사용자가 프로필 이미지를 등록하고 변경하고 제거할 수 있다.
- 내 프로필 조회에 프로필 이미지 URL(미설정이면 null)과 가입 시각이 담긴다.
- 친구 축 응답 3종의 `profileImageUrl`이 실제 값으로 채워진다. 이 축은 코드 변경이 없어야
  한다(PRD 7절). 프로젝션이 이미 `u.profileImageUrl` 컬럼 원문을 그대로 DTO에 싣고 있으므로,
  저장 값이 그 자체로 쓸 수 있는 URL이면 자동으로 반영된다.

## 성공 기준

- presign 발급, S3 직접 업로드, 확정 요청의 왕복으로 이미지가 등록되고, 등록 직후의
  내 프로필 조회와 친구 축 조회 3종에 같은 URL이 보인다.
- 허용 형식은 jpg, png, webp 세 가지이고 크기 상한은 5MB다. 아이폰 사진(heic)은 클라이언트
  변환으로 지원하고 원본 heic는 거부한다(2026-08-11 재확정 — D-4). 형식이나 한도를 벗어난
  요청은 아래 API 명세의 에러 코드로 명확하게 거부된다.
- 이미지를 교체하면 이전 객체가 저장소에 남지 않고, 계정을 삭제하면 프로필 이미지 객체가
  기존 영상 객체와 함께 정리 대상에 들어간다.
- 제거하면 기본 상태(null)로 돌아가고, 이미 기본 상태에서의 제거도 성공으로 응답한다.

## API 명세

세 엔드포인트 모두 인증 필수이고 항상 본인 계정만 대상이다(경로에 대상 식별자가 없다).
기존 `UserController`에 추가한다.

### 1. presign 발급: `POST /api/users/me/profile-image/presigned-url`

영상 presign(MSG-64)과 같은 방식이다. 발급 시점에 형식과 크기를 검증하고, 서명에
Content-Type과 크기를 포함시켜 클라이언트가 선언과 다르게 올리면 S3가 403을 내게 한다.

**Request** `ProfileImagePresignRequestDto` (신규, `user/dto/`)

| 필드 | 타입 | 제약 | 설명 |
|---|---|---|---|
| `extension` | String | `@NotBlank` | 확장자, 점 없이. 허용: jpg, jpeg, png, webp (소문자 정규화 후 비교. heic·heif는 1415 거부 — D-4 재확정) |
| `contentType` | String | `@NotBlank` | MIME 타입. 확장자와 쌍으로 검증한다 (MSG-64 D2 방식) |
| `contentLength` | Long | `@NotNull @Positive` | 업로드할 파일 크기(바이트) |

허용 쌍: jpg와 jpeg는 `image/jpeg`, png는 `image/png`, webp는 `image/webp`. 형식은 PRD의
3종(FR-5, 2026-08-11 재확정)이고 jpeg는 같은 형식의 확장자 표기 차이라 함께 받는다.

**Response** `ProfileImagePresignResponseDto` (신규, `user/dto/`)

| 필드 | 타입 | 설명 |
|---|---|---|
| `uploadUrl` | String | S3에 직접 PUT 업로드할 presigned URL, 유효 10분 (영상 선례와 동일 TTL) |
| `s3Key` | String | `profiles/pending/{userId}/{uuid}.{ext}`. 확정 요청에 그대로 전달한다 |
| `expiresInSec` | long | 600 |

**실패**

| 케이스 | developCode | HTTP |
|---|---|---|
| 허용 밖 확장자, 또는 확장자와 Content-Type 쌍 불일치 | `1415 UNSUPPORTED_IMAGE_EXTENSION` | 400 |
| 선언 크기가 5MB 초과 | `1413 IMAGE_TOO_LARGE` | 400 |
| 필드 누락 등 `@Valid` 실패 | 공통 `BAD_REQUEST` | 400 |

### 2. 변경 확정: `PUT /api/users/me/profile-image`

**Request** `ProfileImageUpdateRequestDto` (신규): `s3Key` (String, `@NotBlank`) 하나.

**동작** (검증 순서는 S3 부수효과가 없는 것부터, MSG-132 선례의 재사용 범위는 도메인 로직 D-3 참조)

1. 키가 `profiles/pending/{내 userId}/`로 시작하고 허용 확장자(jpg, jpeg, png, webp)를
   가졌는지 확인한다. 아니면 `1401`. 확장자 재검증은 공개 읽기 프리픽스로 들어가는 마지막
   관문이다 (구현 중 보강, 리뷰 승인 — presign이 발급하지 않은 형식의 키는 전부 위조 키 성격).
2. HeadObject[^2]로 실존을 확인한다. 없으면 `1402`.
3. HeadObject 응답의 실측 크기가 5MB를 넘으면 `1413` (선언값만 믿지 않는다, MSG-132 P1-1 선례).
4. 확정 키 `profiles/original/{userId}/{uuid}.{ext}`를 새 UUID로 발급하고 pending에서 서버측
   복사한다. 새 UUID인 이유는 확정마다 URL이 바뀌어 브라우저 캐시가 자연히 무효화되기 때문이다.
5. `users.profile_image_url`에 완성된 공개 URL(D-1)을 더티 체킹[^3]으로 저장한다.
6. 커밋 후에 이전 이미지 객체를 best-effort 삭제한다(D-5). pending 원본은 지우지 않는다,
   라이프사이클 규칙[^4]이 쓸어간다 (영상 선례 그대로).

**Response**: 갱신된 `UserProfileResponseDto` (4번 참조). PRD 시퀀스의 "갱신된 프로필 응답"이며
닉네임 수정이 같은 형태를 반환하는 기존 관례(MSG-203 D2)와 일치한다.

**실패**

| 케이스 | developCode | HTTP |
|---|---|---|
| 내 pending 경로가 아닌 키, 확장자가 없거나 허용 밖인 키(heic 포함) | `1401 INVALID_IMAGE_KEY` | 400 |
| S3에 실제로 없는 키 | `1402 IMAGE_UPLOAD_NOT_FOUND` | 400 |
| 실측 크기 5MB 초과 | `1413 IMAGE_TOO_LARGE` | 400 |
| 유저 부재 | `1404 USER_NOT_FOUND` | 404 |

### 3. 제거: `DELETE /api/users/me/profile-image`

`profile_image_url`을 null로 되돌리고, 기존 객체가 있었으면 커밋 후 best-effort 삭제한다.
이미 null이면 아무것도 지우지 않고 그대로 성공한다(멱등). 응답은 2번과 같은
`UserProfileResponseDto`다.

### 4. 조회 확장: `GET /api/users/me` 응답 필드 추가

`UserProfileResponseDto`에 두 필드를 추가한다. 조회와 닉네임 수정(PUT /me/nickname)이 이
DTO를 공유하므로 두 응답이 함께 확장된다. 기존 필드는 그대로라 FE 하위 호환 문제가 없다.

| 필드 | 타입 | 설명 |
|---|---|---|
| `profileImageUrl` | String | 설정한 이미지의 공개 URL. 미설정이면 null (required + nullable, email 필드 선례) |
| `createdAt` | LocalDateTime | 가입 시각. DB 저장값(UTC) 그대로 노출하고 "2026.01.12" 표기는 FE 몫 (친구 요청 `requestedAt` 선례) |

## 도메인 로직

### D-1. 저장 값은 S3 키가 아니라 완성된 공개 URL이다

`profile_image_url`에는 `https://{bucket}.s3.{region}.amazonaws.com/profiles/original/{userId}/{uuid}.{ext}`
형태의 완성 URL을 저장한다. 근거는 강제에 가깝다.

- 친구 축 3종 프로젝션은 컬럼 원문을 그대로 DTO에 싣는다. PRD 7절이 이 축의 코드 변경 없음을
  전제하므로 저장 값이 그 자체로 브라우저에서 열리는 URL이어야 한다.
- presigned GET은 TTL이 있어 저장할 수 없고(썸네일이 요청 시점마다 서명하는 이유),
  요청 시점 서명으로 바꾸면 친구 축 3곳을 고쳐야 해서 PRD와 어긋난다.

따라서 `profiles/original/` 프리픽스만 공개 읽기로 연다. 버킷 정책[^5]을 이 프리픽스로
한정하고 pending 경로와 영상 경로는 지금처럼 비공개로 남긴다. 이 공개 방식은 2026-08-11
정민이 승인했다(미해결 질문 1번 해소). CloudFront를 기각한 것이 아니라 현행 인프라에 없어서 지금 도입하지 않는 것이며,
도입 시 URL 조립 지점(UserServiceImpl 한 곳) 교체로 끝난다.

URL 조립과 역산(URL에서 키 추출, 삭제용)은 `UserServiceImpl`의 private 메서드로 둔다.
사용처가 이 클래스 안 두 곳(확정 조립, 정리 역산)뿐이라 별도 컴포넌트를 만들지 않는다.

### D-2. 키 경로는 영상 선례를 미러링한다

pending은 `profiles/pending/{userId}/{uuid}.{ext}`, 확정본은
`profiles/original/{userId}/{uuid}.{ext}`. `videos/pending/`, `videos/original/`과 같은 구조라
라이프사이클 만료(pending 전용)와 고아 관리 방식을 그대로 이해할 수 있다. `profiles/pending/`
만료 규칙 추가는 인프라 작업이다(미해결 질문 1번에 묶음, 방식 승인 완료).

### D-3. presign과 확정 검증은 패턴 재사용, 이중 확정 장치는 뺀다

영상 쪽에서 가져오는 것: 확장자와 Content-Type 쌍 검증(MSG-64 D2), 서명에 크기와 타입
고정(MSG-64 D3), prefix 소유권 검사와 HeadObject 실존 확인과 실측 크기 재검증(MSG-132).
소유권 검사는 보안 경계라 생략하지 않는다. prefix에 내 userId가 박혀 있어도 공격자는 자기
id를 아니까 실존 확인(HeadObject)까지 있어야 지어낸 키가 막힌다(영상 confirmUpload 주석의 논리).

가져오지 않는 것: advisory lock[^6]과 키 이중 사용 차단. 영상에서 그 장치는 "영상 한 개로
좌표만 바꿔 무한 점령"이라는 도메인 불변식 훼손을 막기 위한 것이었다. 프로필 이미지는 같은
키를 두 번 확정해도 결과가 같은 URL 저장이고, 동시 확정이 겹쳐도 최악의 결과는 진 쪽 객체
하나가 고아로 남는 것뿐이다(5MB 이하, 비용 문제). 복사 후 롤백 보상(MSG-247)도 같은 이유로
걸지 않는다.

코드 재사용이 아니라 패턴 재사용인 이유: 영상 presign은 `VideoServiceImpl` 내부 private이고
DTO 설명도 영상 전용이다. user 도메인에서 `S3Presigner`, `S3Client`, `AwsProperties`를 직접
주입받아 같은 모양으로 작성한다(둘 다 Owner B라 경계 문제는 없지만, 30줄 수준의 로직에 공용
컴포넌트 추출은 세 번째 사용처가 생기면 그때 한다. 영상 쪽 ponytail 주석과 같은 판단).

### D-4. heic 표시 호환 변환은 클라이언트 몫이다

heic는 Chrome 등 대부분 브라우저가 표시하지 못한다. 변환 위치를 클라이언트로 확정한다.

- 주 유입 경로가 이미 변환돼 들어온다. iOS Safari의 사진 선택기는 heic 원본을 선택해도
  플랫폼 수준에서 JPEG로 변환해 전달하고, 이후의 네이티브 앱도 내보내기 API 한 번으로 JPEG를
  얻는다. 서버 변환기가 실제로 처리할 파일이 거의 없다.
- 서버 변환은 확정 요청의 동기 경로에 S3 다운로드, 변환 실행, 재업로드를 넣는 일이고, 배포된
  ffmpeg의 heic 디코드 지원이 빌드 구성에 의존해 검증 비용이 따로 든다. 영상 인코딩
  파이프라인(비동기 상태 관리, 실패 전이, 폴러)을 이미지 한 장에 이식하는 것은 더 과하다.
- 잔여 구멍이던 "변환 없이 올라온 원본 heic"는 2026-08-11 재확정으로 닫혔다: 서버가 heic와
  heif를 허용 목록에서 빼고 1415로 거부한다(초안의 "거부하지 않는다"를 대체 — 저장해도
  브라우저에 표시되지 않는 모순을 짚은 Codex 교차 리뷰가 계기, 정민 결정). FE 계약은 두 겹이다:
  파일 선택 accept 목록에서 heic를 빼 iOS가 플랫폼 수준에서 JPEG로 변환하게 만들고, 그래도
  새어 들어오는 원본 heic는 서버 거부 응답을 안내 문구로 처리한다.

이 구성으로 저장되는 이미지는 항상 모든 브라우저에서 표시된다. 서버 변환 승격 조건(heic 거부
실측이 유의미하게 쌓이면 확정 시 서버 변환 도입, FfmpegRunner 재사용 검토)은 유효하다.

### D-5. 안 쓰는 객체 정리는 커밋 후 best-effort 삭제다

- 교체와 제거: 트랜잭션 안에서 이전 URL을 잡아두고, 커밋 후에 역산한 키를 조용히
  삭제한다(영상 deleteQuietly, 계정 삭제 afterCommit과 같은 구조). 실패는 로그만 남긴다.
  커밋된 변경이 정리 실패 때문에 500으로 보이는 역전을 막는 기존 논리 그대로다.
- 확정되지 않은 업로드: `profiles/pending/` 라이프사이클 만료가 쓸어간다.
- 계정 삭제(MSG-205): `deleteAccount`의 키 수집을 확장한다. 지금 `collectS3Keys`는 videos의
  4컬럼만 모으므로, `deleteUser` 호출 전에 `users.profile_image_url`을 읽어 키로 역산해
  수집 목록에 추가한다. 이후 흐름(커밋 후 1000키 청크 일괄 삭제)은 그대로다.

### D-6. 5MB 상한은 상수로 둔다

`UserServiceImpl`에 `MAX_PROFILE_IMAGE_BYTES = 5 * 1024 * 1024` 상수. 영상 상한은 환경별
튜닝 대상이라 설정(`aws.s3.maxUploadBytes`)이지만, 이 값은 PRD가 고정한 제품 요구사항이라
설정화할 이유가 없다. 값을 바꾸는 일 자체가 요구사항 변경(PRD 개정)이다.

## 데이터 모델

- **Flyway 마이그레이션 없음.** `users.profile_image_url`(V1, text)과 `created_at` 컬럼,
  엔티티 매핑이 이미 있다 (PRD 비기능 확인 사항).
- `User` 엔티티에 상태 변경 메서드 `changeProfileImage(String url)` 하나를 추가한다.
  null 전달이 제거다. `updateNickname` 선례처럼 검증은 서비스 몫이고 엔티티는 전달값을
  더티 체킹으로 반영만 한다.

[^1]: presigned URL: 서버가 서명해 발급하는 한시적 업로드/다운로드 주소. 클라이언트가 서버를 거치지 않고 S3에 직접 파일을 올릴 수 있게 한다. 영상 업로드(MSG-64, MSG-133)가 같은 방식이다.
[^2]: HeadObject: S3 객체의 본문 없이 메타데이터(존재 여부, 실제 크기 등)만 조회하는 S3 API. 확정 시점에 "정말 올라간 파일인지"와 실측 크기를 추가 다운로드 비용 없이 확인하는 데 쓴다.
[^3]: 더티 체킹(dirty checking): JPA가 트랜잭션 안에서 엔티티 필드 변경을 감지해 커밋 시점에 UPDATE문을 자동 실행하는 방식. 별도 UPDATE 쿼리 없이 `user.changeProfileImage(url)` 호출만으로 저장이 성립한다.
[^4]: 라이프사이클 규칙(lifecycle rule): 지정 프리픽스의 객체를 일정 기간 후 자동 삭제하는 S3 설정. 확정되지 않은 pending 업로드를 코드 없이 청소하는 장치로, 영상의 `videos/pending/`이 같은 방식을 쓴다.
[^5]: 버킷 정책(bucket policy): S3 버킷에 붙이는 접근 제어 규칙. 특정 프리픽스에만 익명 읽기(GetObject)를 허용하는 식의 경로 단위 공개가 가능하다. 적용하려면 계정의 Block Public Access(공개 설정 일괄 차단 장치) 중 공개 정책 차단을 버킷 수준에서 풀어야 한다.
[^6]: advisory lock: PostgreSQL이 제공하는 애플리케이션 정의 잠금. 영상 확정은 같은 pending 키의 동시 확정을 직렬화하는 데 썼지만, 프로필 이미지는 동시 확정의 최악 결과가 고아 객체 하나라 잠금 없이 둔다.
