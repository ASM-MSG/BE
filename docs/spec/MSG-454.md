# MSG-454: 비로그인에서 상단 칩 조회 허용 (핫구역·미션 목록/집계/상세/영상)

**Owner**: B

**선행 정본**: `docs/prd/mission-map-explore.md` 8절 2026-08-22 확정 (정민, 2026-08-14
"비로그인 미션 열람 폐기" 결정의 번복). 이 작업은 요구사항 변경이며, 번복 결정(비로그인 미션
열람 재허용, 상단 칩 비대칭 제거, progress 로그인 유지, 스크래핑 우려 정리)이 그 PRD에
등재돼 있다. 핫구역은 그 PRD의 원래 범위(미션 지도) 밖이지만, 같은 8절 2026-08-22 확정 항목이
"미션 조회와 핫구역 조회를 익명 허용으로 맞춘다"로 핫구역을 명시적으로 포함한다
(같은 상단 칩 원칙, MSG-439). 즉 핫구역 개방도 등재된 결정의 이행이지 이 스펙의 재량이 아니다.

## 개요

fillmap.kr 지도 홈 상단 칩(핫구역·지역축제·팝업스토어·경로추천)이 로그인 없이는 보이지 않는다.
원인은 `SecurityConfig`의 `anyRequest().authenticated()`다. 행사방(MSG-439·440)만 GET
permitAll[^1]로 열려 있고 핫구역·미션 조회 경로가 빠졌다. 이 티켓은 핫구역 조회 1종과 미션 조회
4종(목록·집계·상세·영상 목록)을 비로그인에 열고, 사용자별 값인 미션 진행도 조회는 로그인
필수로 지킨다.

## 배경 · 목표

비로그인 미션 열람은 2026-08-14에 스크래핑 우려로 한 차례 폐기됐다가(정본 PRD 8절),
행사방(MSG-439)이 "상단 칩은 비로그인, 업로드는 로그인" 원칙으로 행사 조회를 익명에 열면서
같은 칩 줄의 핫구역·미션만 로그인 벽 뒤에 남는 비대칭이 생겨 2026-08-22에 번복됐다.
목표는 그 비대칭 제거다. 열람 계열 조회를 익명에 허용하되, 개인화 값(진행도·스탬프)은
로그인 사용자에게만 내린다. 폐기 근거였던 스크래핑 우려는 완화가 아니라 **수용**으로
정리됐다: 공개 조회의 조합으로 미션 데이터 열거가 가능함을 인정하되, 공공 출처의 비민감
데이터이고 행사 조회 선례와 상단 칩 제품 요구가 우선한다는 판단이다. 상세 논리는 PRD 8절
정본을 참조한다.

## 성공 기준

1. 비로그인(무토큰) GET 요청이 다음 5개 경로에서 200으로 성공한다. 단, 각 API의 유효 파라미터를
   포함한 요청 기준이다. 파라미터가 빠지면 인가와 무관하게 400이 나가므로(핫구역은 bbox 4개
   필수, 목록은 type과 bbox 필수, 집계는 type·unit·bbox 필수) 파라미터 없는 요청으로는 이
   기준을 검증할 수 없다:
   `/api/hotzones`(swLat·swLng·neLat·neLng), `/api/missions/active`(type·bbox),
   `/api/missions/aggregation`(type·unit·bbox), `/api/missions/{missionId}`,
   `/api/missions/{missionId}/videos`.
2. 비로그인 GET `/api/missions/progress`는 여전히 401이다.
3. 비로그인 미션 상세 응답은 `progress` 키가 있되 값이 null이고, `spotStats[].visited`가 전부
   false다. 로그인 상세 응답은 기존과 동일하게 진행도·스탬프·방문 여부를 담는다.
4. 공개 GET에 무효 토큰이 실려 오면 기존과 같이 401 + developCode 2401이다
   (permitAll은 인증 불요이지 토큰 무시가 아니다).
5. 위 경로들의 비GET 요청(예: POST)은 여전히 401이다.

## API 명세

새 endpoint는 없다. 기존 5개 GET의 인증 정책과 미션 상세 응답 1종의 계약만 바뀐다.

| Method | Path | 변경 전 | 변경 후 |
|---|---|---|---|
| GET | `/api/hotzones` | 로그인 필수 | 익명 허용 (응답 변화 없음: principal[^2] 미사용, 개인화 없음) |
| GET | `/api/missions/active` | 로그인 필수 | 익명 허용 (응답 변화 없음: 전역 데이터) |
| GET | `/api/missions/aggregation` | 로그인 필수 | 익명 허용 (응답 변화 없음: 전역 데이터) |
| GET | `/api/missions/{missionId}` | 로그인 필수 | 익명 허용, 익명이면 개인화 필드가 null 값으로 나간다(아래) |
| GET | `/api/missions/{missionId}/videos` | 로그인 필수 | 익명 허용 (응답 변화 없음: 누가 부르든 같은 응답 명문) |
| GET | `/api/missions/progress` | 로그인 필수 | **로그인 필수 유지** (사용자별 값, 열지 않는다) |

### 미션 상세의 익명 계약 (`MissionDetailResponseDto`)

- `progress`: 익명이면 **값이 null**이다. 내 진행도와 스탬프 보유 여부(completed)가 모두 이 객체
  안에 있으므로 null 하나로 개인화 항목 배제가 완결된다. 이 프로젝트는 Jackson 기본 직렬화라
  (`@JsonInclude` 전역 설정 없음) 값이 null이어도 **키는 항상 나간다**. 따라서 `@Schema`의
  `requiredProperties`에서 `"progress"`를 빼지 않는다: 이 프로젝트에서 required는 "키 존재"
  의미이고, `ResponseSchemaNullabilityTest`(MSG-319)가 응답 DTO 전 필드의 requiredProperties
  등재를 강제한다. 대신 progress 필드에 **`@Schema(nullable = true)`를 추가**하고 설명에
  "비로그인 조회면 null"을 명시한다. `UserProfileResponseDto.email`의 required + nullable
  선례(MSG-310·311)와 같은 형태다.
- `spotStats[].visited`: 익명이면 항상 **false**. 타입은 `boolean` 그대로 둔다. `Boolean`
  nullable로 바꾸면 로그인 사용자를 포함한 모든 소비자의 와이어 타입이 바뀌는데, 익명 화면은
  개인 방문 표시를 그리지 않으므로 얻는 것이 없다. `@Schema` 설명에 "비로그인이면 항상 false"를
  적는다. (사용자 확정은 "진행도·스탬프 생략(null)"까지였고, 스팟 방문 여부는 그 결정의 연장으로
  여기서 false 고정을 택했다. 방향이 다르면 미해결 질문으로 올릴 것)
- `mission`, `videoCount`, `spotStats`(배열 자체와 `gridId`·`videoCount`)는 전역 값이라 익명과
  로그인이 같다.
- 존재하지 않는 missionId는 익명이든 로그인이든 404 + developCode 12404로 동일하다.
- Swagger `@Operation` description에 익명 동작(progress null, visited false)을 추가한다.

### 에러 케이스

- 익명 `/api/missions/progress`: 401 (CustomAuthenticationEntryPoint, 공통 UNAUTHORIZED).
- 공개 GET + 무효 토큰: 401 + developCode 2401 (JwtAuthenticationFilter가 기존대로 검증).
- 새 developCode 없음.

## 도메인 로직

### 1. SecurityConfig 매처[^3] 구성 (핵심 결정)

상세 경로 `/api/missions/{missionId}`는 `/api/missions/active`·`progress`와 같은 깊이다.
제약 없는 와일드카드 `/api/missions/*`는 리터럴 형제(`active`, `aggregation`, `progress`)까지
전부 잡으므로 쓰지 않고, **제약 변수 매처 `{missionId:[0-9]+}`로 숫자 상세만 연다.**
Spring Security 6의 기본 PathPattern 매처가 `{name:regex}` 제약 변수를 지원한다(구현 참고).

```java
// 핫구역·미션 조회(MSG-454): 비로그인 허용. MSG-439 "상단 칩은 비로그인, 업로드는 로그인"의
// 적용이다(정본 docs/prd/mission-map-explore.md 8절 2026-08-22). GET 한정이 계약의 일부다
// (행사 경로 주석과 같은 이유). 상세·영상 두 줄만 {missionId:[0-9]+} 제약 변수를 쓴다:
// 제약 없는 /api/missions/* 는 progress 같은 리터럴 형제와 미래의 한 세그먼트 GET 경로까지
// 기본 공개로 만드는 fail-open 이라서다. 숫자 제약이면 문자 경로는 이 매처에 안 잡혀
// anyRequest().authenticated() 로 떨어진다 (기본이 인증 쪽, NFR-SEC-01).
.requestMatchers(HttpMethod.GET,
	"/api/hotzones",
	"/api/missions/active",
	"/api/missions/aggregation",
	"/api/missions/{missionId:[0-9]+}",
	"/api/missions/{missionId:[0-9]+}/videos").permitAll()
```

- **왜 제약 변수인가 (fail-closed)**: 앞선 검토안이었던 "`/api/missions/*` permitAll +
  `progress` authenticated 선등록"은 fail-open이다. 미래에 `/api/missions/summary` 같은
  인증 필요 한 세그먼트 GET이 추가되면 작성자가 선등록 규칙을 기억해야만 보호되는데, 이는
  SRS NFR-SEC-01의 "기본이 인증 필수" 원칙과 반대 방향이다. 제약 변수 매처는 숫자 상세만
  열어 기본값이 인증 쪽으로 남는다(fail-closed). 그 안의 정규식 매처 기각 근거였던 "파일이
  경로 패턴 관례"는 이 결정으로 대체한다: 제약 변수는 경로 패턴 문법 안의 기능이라 관례
  충돌이 없고, 설령 있더라도 fail-closed가 파일 관례보다 우선한다.
- `progress`를 위한 별도 `authenticated()` 선등록은 불필요하다. 문자 경로라 숫자 제약에 안
  잡혀 기본 규칙으로 떨어진다. 다만 "progress 익명 401" 테스트(테스트 시나리오 2)는 매처가
  느슨해지는 회귀를 잡는 가드로 유지한다.
- 등록 위치는 기존 행사 permitAll 블록 근처로 하고, MSG-439·440 주석과 같은 톤으로 이유를
  단다(제약 변수를 쓰는 이유 포함, 위 주석 지시 참조).
- `/api/missions/{missionId:[0-9]+}/videos`는 컨트롤러가 video 패키지
  (`MissionVideoController`)에 있지만 경로 깊이가 달라 별도 항목이 필요하다.
- 존재하지 않는 숫자 id는 매처를 통과한 뒤 컨트롤러에서 404(12404)가 되고, 비숫자 경로
  (`/api/missions/abc`)는 익명이면 401이다. 의도된 차이다.
- HEAD는 다루지 않는다. 행사 영상(MSG-440)의 HEAD 항목은 그 경로에 명시 HEAD 매핑이 있어서
  필요했던 것이고, 핫구역·미션에는 명시 HEAD 매핑이 없으며 칩 요구사항도 아니다
  (MSG-439의 조회 4종도 HEAD를 열지 않았다. 동일 정책).

### 2. 미션 상세 익명 분기 (MSG-439 선례 재사용)

`EventOccurrenceController`가 이미 같은 문제를 풀었다: 익명이면 `@AuthenticationPrincipal`이
null이고, `userId(principal)` private 헬퍼가 null을 그대로 서비스에 넘긴다. 같은 패턴을 쓴다.

- `MissionController.getMissionDetail`: `principal.userId()` 직접 호출을
  `userId(principal)` 헬퍼(null이면 null 반환)로 바꾼다.
- `MissionQueryService.getMissionDetail(long missionId, long userId)`의 두 번째 파라미터를
  `Long userId`(nullable)로 바꾸고, javadoc에 "null은 비로그인 조회, 개인화 필드는 null 값"을
  적는다.
- `MissionQueryServiceImpl.getMissionDetail`: `userId == null`이면 `findProgress`와
  `findVisitedGridIds` 두 조회를 건너뛴다. progress는 null, visitedGridIds는 빈 집합이 되어
  spotStats.visited가 전부 false로 조립된다. DB 조회는 5회에서 3회가 된다(미션·격자·영상 수).
  REPEATABLE_READ 트랜잭션 등 나머지 구조는 그대로다.
- `/api/hotzones`, `/api/missions/active`, `/api/missions/aggregation`,
  `/api/missions/{missionId}/videos`는 principal을 아예 받지 않으므로 **코드 무수정**이다.
  핫구역(hotzone) 패키지는 이 티켓에서 한 줄도 바뀌지 않는다.

### 3. JwtAuthenticationFilter는 건드리지 않는다

`PUBLIC_AUTH_PATHS`에 새 경로를 넣지 않는다. MSG-443 교훈 그대로다: permitAll은 인증 불요이지
토큰 무시가 아니다. 토큰이 실려 오면 필터가 평소처럼 principal을 세워야 로그인 사용자가
상세에서 자기 진행도를 받는다. SecurityConfig의 MSG-443 주석(현행 81~83행)과 같은 규칙이다.

### 4. MissionController 클래스 주석 갱신

현행 주석의 "인증은 필수다(SecurityConfig anyRequest().authenticated())" 문구가 이 티켓으로
낡는다. 다음 취지로 고쳐 쓴다: 목록·집계·상세는 비로그인 열람이다(MSG-454, 상단 칩은 비로그인).
목록·집계 응답이 호출자와 무관해야 전역 캐시가 성립한다는 계약(FR-MISSION-02)과 그 코드 수준
방어(principal 미수신, D10)는 그대로 유지된다. 진행도는 사용자별 값이라 로그인 필수다.

## 테스트 시나리오

시큐리티 계약 테스트는 MSG-439의 `EventPublicAccessHttpTest` 패턴(@SpringBootTest +
@AutoConfigureMockMvc, 서비스는 @MockitoBean 목이라 변수는 SecurityConfig 등록뿐)을 그대로 쓴다.
신규 클래스 `src/test/java/com/msg/fillmap/mission/controller/MissionPublicAccessHttpTest.java` 하나에
핫구역까지 함께 담는다(검증 대상이 SecurityConfig 한 파일이므로 쪼개지 않는다).

1. `무인증으로_핫구역과_미션_조회_5종이_200으로_성공한다`: 성공 기준 1의 5개 경로 전부.
   파라미터 누락 400이 익명 200 검증을 가리지 않도록 각 요청에 유효 파라미터를 싣는다
   (EventPublicAccessHttpTest가 뷰포트 조회에 bbox를 실은 것과 같은 이유):
   - `/api/hotzones?swLat=37.50&swLng=127.00&neLat=37.55&neLng=127.05`
   - `/api/missions/active?type=POPUP&swLat=37.50&swLng=127.00&neLat=37.55&neLng=127.05`
   - `/api/missions/aggregation?type=POPUP&unit=SIGUNGU&swLat=35.10&swLng=128.90&neLat=35.30&neLng=129.20`
   - `/api/missions/{missionId}` · `/api/missions/{missionId}/videos` (경로 변수 외 필수 없음)
2. `무인증_미션_진행도_조회는_401로_거절된다`: progress가 어떤 permitAll 매처에도 잡히지 않고
   기본 인증으로 남는지 고정하는 회귀 가드. 누가 상세 매처를 제약 없는 `/api/missions/*`로
   넓히면 이 테스트가 깨진다.
3. `무인증_비GET_미션_경로는_401로_거절된다`: POST `/api/missions/{missionId}/videos` 등이
   401인지. GET 한정 계약의 회귀 방지(EventPublicAccessHttpTest의 같은 이름 시나리오와 동형).
4. `공개_GET에서도_무효_토큰은_2401로_거절된다`: 결정 3(필터 무수정)의 성질 보존.
5. `무인증_미션_상세는_progress_키가_있고_값이_null이다`: **MockMvc[^4] JSON 단언 필수**
   (EventPublicAccessHttpTest 동형 패턴). 응답 본문에서 `data.progress` 키가 존재하고 값이
   JSON null임을 직접 단언하고, `data.spotStats[*].visited`가 전부 false인지 함께 본다.
   서비스 레벨 테스트로 대체할 수 없다: 서비스 테스트는 DTO 필드 값만 보므로 와이어 계약
   (키 존재 + null 값)을 검증하지 못하고, 나중에 전역 NON_NULL 직렬화가 끼어들어 키가
   사라져도 통과해 버린다.
6. 서비스 레벨은 기존 `MissionDetailServiceTest`에 보조로 추가한다.
   `익명_상세는_진행도가_null이고_스팟_방문이_전부_false다`: `getMissionDetail(id, null)`이
   progress null, 모든 spotStats.visited false, videoCount와 mission은 로그인 조회와 동일.
7. `익명_상세는_진행도와_방문_조회를_실행하지_않는다`: `findProgress`·`findVisitedGridIds`
   미호출 검증(목 verify).
8. 기존 로그인 상세 테스트(`MissionDetailServiceTest`·`MissionDetailConsistencyTest`·
   `MissionControllerTest`)는 시그니처 변경(`Long`)만 반영하고 기대값 무변경으로 green이어야
   한다. 로그인 시 진행도 포함 계약이 그대로임을 이 테스트들이 증명한다.
