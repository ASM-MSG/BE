# MSG-343: 영상 처리와 알림 발송 목표를 Metric으로 측정할 수 있게 한다

**Owner**: B (콘텐츠, 인증 도메인)

계측 대상이 전부 `com.msg.fillmap.video.*`와 `com.msg.fillmap.notification.*`이다. 두 패키지 모두
CLAUDE.md 협업 원칙에서 Owner B다. 계약 인터페이스 4종의 시그니처 변경은 없다.

**PRD**: 면제. 처리 결과와 API 계약이 불변인 관측 추가이고, 측정하는 30초 목표도 기존 목표의
측정이지 신설이 아니다. 티켓 설명(MSG-343)이 요구사항 정본이다.

## 개요

영상 처리와 알림 발송의 상태를 기존 Micrometer[^1] 기반으로 계측해 `/actuator/prometheus`에
노출한다. 새 라이브러리는 추가하지 않는다. 이미 `spring-boot-starter-actuator`와
`micrometer-registry-prometheus`가 들어 있고(build.gradle 32~33행), MSG-344/377 관측 스택이
이 엔드포인트를 scrape 중이다. 이 티켓은 앱이 내보내는 Metric 자체만 다룬다.

## 배경과 목표

현재 앱에는 HTTP, JVM, Hikari 자동 Metric만 있고 비즈니스 처리를 세는 Counter, Timer, Gauge가
하나도 없다(`src/main`에서 MeterRegistry 사용 0건 확인). 영상 로그의 duration은 영상 자체 길이라
업로드부터 재생 가능까지 걸린 시간이 아니다. 이 상태로는 "업로드 후 30초 안에 준비되는 비율"과
실패, 재시도의 성공률을 숫자로 말할 수 없고, 알림도 DB를 직접 조회해야 DEAD 누적을 안다.

목표: 대시보드 쿼리만으로 영상 처리 p95[^2], 30초 이내 완료 비율, READY/FAILED 비율, 인코딩 큐
거부, AI 처리 결과, 알림 전이와 백로그를 읽을 수 있게 한다.

## 성공 기준

1. `/actuator/prometheus`에서 아래 Metric 명세 표의 이름과 태그가 전부 조회된다.
2. 아래 PromQL[^3] 예시가 그대로 동작한다(p95, 30초 이내 비율, READY/FAILED 비율).
3. 인코딩 큐 거부와 AI 결과가 원인별 고정 태그로 구분된다.
4. 알림 SENT, SKIPPED, DEAD 전이 건수와 현재 PENDING/PUBLISHED 백로그가 보인다.
5. 성공, 실패, 재시도 테스트에서 상태 전이당 Metric이 정확히 한 번 증가한다(재전달 재소비는 0회).
6. 사용자 ID, videoId, jobId, S3 키, 검색어, 예외 메시지가 어떤 태그에도 실리지 않는다.
7. 구현 완료 시 실측 노출명과 계산식을 이 문서 작업 로그에 기록한다(정본은 아래 표).

## Metric 명세 (확정)

구현은 이 표를 그대로 따른다. 태그 값은 표의 고정 집합만 허용한다.

| Micrometer 이름 (Prometheus 노출명) | 유형 | 단위 | 태그와 허용값 |
|---|---|---|---|
| `video.processing.outcome` (`video_processing_outcome_total`) | Counter | 건 | `outcome` = `ready`, `failed` / `path` = `encoding`, `ai` |
| `video.processing.duration` (`video_processing_duration_seconds`) | Timer | 초 | `outcome`, `path` 위와 동일 |
| `video.encoding.task` (`video_encoding_task_total`) | Counter | 건 | `result` = `completed`, `failed_over_duration`, `failed_error`, `rejected` |
| `video.ai.job` (`video_ai_job_total`) | Counter | 건 | `event` = `submitted`, `done`, `failed`, `precheck_rejected`, `timeout`, `job_lost` |
| `notification.outcome` (`notification_outcome_total`) | Counter | 건 | `result` = `sent`, `skipped`, `dead` / `reason` = `none`, `pref_off`, `rate_limited`, `no_token` (skipped 외에는 `none`) |
| `notification.backlog` (`notification_backlog`) | Gauge | 건 | `status` = `pending`, `published` |

인코딩 큐 적체는 새 Metric을 만들지 않는다. Spring Boot가 `ThreadPoolTaskExecutor` 빈을 자동
바인딩해 노출하는 `executor_queued_tasks{name="encodingExecutor"}` 계열을 재사용한다(결정 D4).
노출명은 구현 단계 실측으로 확정했다. 설계 때 적었던 `executor_queued`는 Micrometer가 단위
접미사를 붙이기 전 이름이라 실제 스크레이프에는 나오지 않는다.

### 히스토그램 버킷 (application.yml)

`video.processing.duration`에만 SLO 버킷[^4]을 명시한다. MSG-321이 정한 기존 철학 그대로
`percentiles-histogram`은 쓰지 않고 관측에 필요한 경계만 준다. 30초 경계가 "30초 이내 완료
비율"의 판정선이라 필수다.

```yaml
management:
  metrics:
    distribution:
      slo:
        "[video.processing.duration]": 5s, 10s, 15s, 30s, 60s, 120s, 300s
```

비용: 태그 조합 4개 × (버킷 7 + Inf + count + sum + max) 수준으로 시계열 약 44개. 기존
http.server.requests 버킷 비용보다 작다.

### 대시보드 계산식 예시 (PromQL)

```promql
# 영상 처리 p95
histogram_quantile(0.95, sum by (le) (rate(video_processing_duration_seconds_bucket[5m])))

# 30초 이내 완료 비율
sum(rate(video_processing_duration_seconds_bucket{le="30.0"}[5m]))
  / sum(rate(video_processing_duration_seconds_count[5m]))

# READY 비율 (FAILED 비율은 outcome="failed"로 동일 형태)
sum(rate(video_processing_outcome_total{outcome="ready"}[5m]))
  / sum(rate(video_processing_outcome_total[5m]))

# 인코딩 큐 거부율과 큐 깊이
rate(video_encoding_task_total{result="rejected"}[5m])
executor_queued_tasks{name="encodingExecutor"}

# AI 원인별 결과
sum by (event) (increase(video_ai_job_total[1h]))

# 알림 발송 성공률과 하루 DEAD 누적
sum(rate(notification_outcome_total{result="sent"}[5m]))
  / sum(rate(notification_outcome_total[5m]))
increase(notification_outcome_total{result="dead"}[1d])

# 알림 백로그
notification_backlog
```

## 결정 사항

### D1. 카디널리티[^5] 규칙: 가변값 태그 금지

태그 값은 위 표의 고정 집합만 쓴다. 건마다 달라지는 값(videoId, userId, jobId, S3 키, 검색어,
예외 메시지, AI 프리체크 사유 원문)은 태그에 넣지 않는다. Prometheus는 태그 조합마다 시계열을
하나씩 만들므로 가변값 태그는 메모리와 scrape 비용을 무한히 키운다. 프리체크 사유 원문은
`precheck_rejected` 하나로 뭉친다. 건별 사유가 필요하면 이미 `videos.fail_reason` 컬럼에 있다.
새 태그 값이 필요해지면 이 표를 갱신하는 커밋을 선행한다(developCode 대역 표와 같은 규칙).

### D2. 처리 시간 시작점: 저장 시각은 재사용할 수 없다, 인메모리 시작점을 쓴다

티켓 지시대로 시작점은 업로드 확정 트랜잭션 커밋 시각으로 통일한다. 재사용 후보를 실코드로
확인한 결과는 다음과 같다.

- `videos.created_at`: 첫 업로드에서는 확정 트랜잭션의 INSERT 시각이라 근사 가능하지만, 교체
  (`Video.replaceFile`)는 행을 유지하므로 created_at이 원 업로드 시각으로 남는다. 교체 후
  재처리 시간이 며칠로 부풀 수 있어 부적합.
- `videos.blurring_started_at`: AI 단계 시작 시각(markEncoded가 찍음)이라 시작점이 아니다.
- `videos.recorded_at`: 촬영 시각(클라이언트 신고)이라 무관.

결론: 재사용 가능한 저장 시각이 없다. 컬럼 신설 대신 인메모리 시작점으로 간다. 신규 컴포넌트
`VideoProcessingMetrics`(video 패키지)가 `ConcurrentHashMap<Long, Long>`(videoId, nanoTime)을
들고, `VideoServiceImpl.submitEncoding` 진입 시 등록한다. 이 지점은 saveVideo와 replaceVideo
양쪽이 공유하는 afterCommit 실행부라 "확정 커밋 직후" 정의와 정확히 일치하고, 교체는 같은 키를
덮어써 옛 시도 시각이 섞이지 않는다. 단일 앱 인스턴스 전제는 AiBlurPoller, NotificationRelay가
이미 깔고 있는 전제와 동일하다.

허용 오차 두 가지를 명시한다. 첫째, 앱 재시작으로 시작점이 유실된 영상은 종결 시 Timer 표본만
결손되고 Counter(`video.processing.outcome`)는 정확히 증가한다. READY/FAILED 비율은 Counter로
계산하므로 영향이 없다. 둘째, 삭제된 영상의 시작점은 `deleteVideo`에서 제거하고, 탈퇴 CASCADE
등 그 밖의 경로로 남는 엔트리는 극소량이라 허용한다(엔트리 하나가 수십 바이트).

### D3. 백로그 Gauge: 60초 주기 DB 폴링, count 2문

scrape 시점마다 DB를 조회하는 방식은 수집 주기와 DB 부하가 결합되고 scrape가 멎으면 값도 멎어
기각한다. 신규 컴포넌트 `NotificationBacklogMetrics`(notification 패키지,
`@ConditionalOnProperty(prefix = "fillmap.notification", name = "enabled")`, 스케줄링은
NotificationConfig의 기존 `@EnableScheduling` 재사용)가 `@Scheduled(fixedDelay = 60000)`으로
AtomicLong 두 개를 갱신하고, 그 값을 Gauge로 등록한다.

- 주기 60초 근거: 백로그는 분 단위 추세 지표다. 릴레이 폴링(5초)보다 촘촘할 이유가 없다.
- 쿼리와 비용: `SELECT count(*) FROM notifications WHERE status = 'PENDING'`과 같은 형태의
  단문 2개. 둘 다 partial index(`idx_notifications_pending`, `idx_notifications_published`,
  V21)가 받쳐 테이블 크기와 무관하게 저비용이다. 분당 2문은 릴레이가 5초마다 도는 기존 쿼리
  비용보다 훨씬 작다.
- 알림 비활성 환경(로컬, CI)에서는 빈이 뜨지 않아 이 Gauge가 노출되지 않는다. 릴레이,
  컨슈머와 같은 게이트 동작이라 의도된 것이다.

### D4. encodingExecutor 큐는 자동 노출 Metric을 재사용한다

Spring Boot의 TaskExecutorMetricsAutoConfiguration이 `ThreadPoolTaskExecutor` 빈을
ExecutorServiceMetrics로 바인딩해 `executor.queued`, `executor.active`, `executor.pool.size`
등을 `name="encodingExecutor"` 태그로 노출한다. 구현 첫 단계에서 `/actuator/prometheus` 실측으로
확인하고, 현재 Boot 형상에서 노출되지 않으면 그때만 `ExecutorServiceMetrics.monitor` 수동 바인딩
한 줄을 추가한다. 자체 큐 깊이 Gauge는 만들지 않는다.

### D5. 영상 종결 계측은 VideoStatusWriter 한 곳, 전이 적용 지점에서만

종결 전이(READY, FAILED)는 인코딩 경로와 AI 경로가 모두 VideoStatusWriter를 지나므로 여기 한
곳에서 계측해 중복 증가를 막는다. 증가는 스테일 가드를 통과해 전이가 실제 적용되는 분기에서만
한다. 가드가 skip한 옛 시도의 종결은 계측하지 않는다(그 영상의 새 시도가 따로 종결된다).
REQUIRES_NEW 전이 트랜잭션이 커밋 직전에 실패하면 Counter가 한 번 과대 계상될 수 있는 창이
남는데, 핫스코어의 근사 허용과 같은 결로 수용한다. 알림 쪽은 전이 UPDATE가
`tx.executeWithoutResult` 반환 후에 증가시키므로 이 창이 없다.

## 도메인 로직 (계측 지점)

| Metric | 증가 지점 (실코드 기준) |
|---|---|
| `video.processing.outcome`, `video.processing.duration` | VideoStatusWriter의 종결 4메서드. markReady는 ready/encoding, markBlurReady(applied=true)는 ready/ai, markFailed는 failed/encoding, markBlurFailed는 failed/ai. Counter는 무조건 +1, Timer는 시작점이 있을 때만 기록 후 제거 |
| 처리 시간 시작점 등록 | VideoServiceImpl.submitEncoding 진입부(확정 커밋 직후, 업로드와 교체 공용). deleteVideo에서 제거 |
| `video.encoding.task{result=completed}` | VideoEncodingServiceImpl.encode의 성공 로그 지점(markReady 또는 markEncoded 호출 후, aiEnabled 무관) |
| `video.encoding.task{result=failed_over_duration}` | 실측 길이 초과 분기 |
| `video.encoding.task{result=failed_error}` | encode의 catch 블록(다운로드, ffmpeg, 업로드 실패) |
| `video.encoding.task{result=rejected}` | VideoServiceImpl.submitEncoding의 TaskRejectedException catch. 이 경로는 encode 본문이 돌지 않아 completed/failed와 겹치지 않고, 이어지는 markFailed가 종결 Counter를 따로 올린다(의도된 이중 관점: 태스크 결과와 처리 종결) |
| `video.ai.job{event=submitted}` | AiBlurPoller.submit 성공 지점. 404 유실 후 재제출도 여기로 다시 잡힌다 |
| `video.ai.job{event=done}` | complete에서 markBlurReady가 true를 반환한 지점 |
| `video.ai.job{event=failed}` | AiJobStatus.FAILED 분기 |
| `video.ai.job{event=precheck_rejected}` | 프리체크 탈락 분기(사유 원문은 태그 금지, D1) |
| `video.ai.job{event=timeout}` | failIfTimedOut이 true를 반환하는 내부 한 곳(미제출, poll 불가, DONE 소비 실패, UNKNOWN 경로 전부가 이 메서드를 지난다) |
| `video.ai.job{event=job_lost}` | 404 분기의 clearAiJob 호출 지점 |
| `notification.outcome{result=sent}` | NotificationConsumer.consume의 markSent 트랜잭션 반환 후 |
| `notification.outcome{result=skipped}` | consume의 skip 헬퍼(사유를 소문자 고정값으로 매핑: PREF_OFF는 pref_off, RATE_LIMITED는 rate_limited, NO_TOKEN은 no_token) |
| `notification.outcome{result=dead}` | NotificationConfig.notificationDeadRecoverer의 markDead 트랜잭션 성공 후. NumberFormatException 폐기 경로는 전이가 없으므로 계측하지 않는다 |
| `notification.backlog` | NotificationBacklogMetrics 60초 폴링 (D3) |

전이당 정확히 1회 보장의 근거: 영상 쪽은 스테일 가드가, 알림 쪽은 consume 초입의 종결 상태
가드(이미 SENT, SKIPPED, DEAD면 즉시 반환)가 재소비를 걸러낸다. Kafka 재전달로 같은 메시지가
다시 와도 두 번째 소비는 어떤 Counter도 올리지 않는다.

신규 클래스는 `VideoProcessingMetrics`와 `NotificationBacklogMetrics` 둘이고, 나머지는 기존
클래스에 MeterRegistry(또는 위 컴포넌트) 주입과 증가 호출 한 줄씩이다. 계측 실패가 본 처리를
깨뜨리지 않게 계측 호출은 상태 전이 로직의 제어 흐름에 끼어들지 않는 단순 증가로만 둔다.

## 테스트 시나리오

전 모듈 공통: SimpleMeterRegistry를 주입해 상태 전이 전후의 Counter, Timer 값을 단언한다
(티켓 지시). 모듈 구분은 spec-driven-dev 작업 보드 단위다.

### 모듈 1: 영상 처리 종결 계측 (VideoProcessingMetrics + VideoStatusWriter)

- `시작점_등록_후_READY_전이는_카운터와_타이머를_각_한_번_기록한다`
- `FAILED_전이는_outcome_failed로_기록된다` (encoding, ai 두 path 각각)
- `시작점_없이_종결되면_카운터만_증가하고_타이머는_기록되지_않는다` (재시작 유실 시나리오)
- `스테일_전이_skip은_어떤_Metric도_증가시키지_않는다`
- `교체_재등록이_시작점을_덮어써_옛_시도_시각이_쓰이지_않는다`
- `삭제_시_시작점이_제거된다`

## 작업 로그

2026-08-12 구현 완료. 신규 클래스는 `VideoProcessingMetrics`와 `NotificationBacklogMetrics`
둘이고 나머지는 기존 클래스의 증가 호출이다. 아래는 실행 시점 사실 기록이다.

### 데이터 저장 위치

계측값은 DB나 Redis에 남지 않는다. 전부 앱 프로세스 메모리의 Micrometer 레지스트리에 있고
`/actuator/prometheus` 응답으로만 나간다(prod는 관리 포트 8081, MSG-344). 보존은 수집 서버
Prometheus의 30일 TSDB가 담당한다. Flyway 마이그레이션은 없다.

프로세스 메모리를 쓰는 상태가 둘 있다. `VideoProcessingMetrics.startNanos`는
`ConcurrentHashMap<Long, Long>`으로 videoId별 처리 시작 nanoTime을 들고 있다가 종결 시
제거한다(D2). `NotificationBacklogMetrics`의 `AtomicLong` 두 개는 폴링이 채우는 최신 백로그
값이고 Gauge가 그 참조를 읽는다.

### 실측 노출명

| Prometheus 노출명 | 태그 조합 |
|---|---|
| `video_processing_outcome_total` | `outcome`(ready·failed) × `path`(encoding·ai) 4조합 |
| `video_processing_duration_seconds_{bucket,count,sum,max}` | 위와 같은 4조합. 버킷 경계 5·10·15·30·60·120·300초와 `+Inf` |
| `video_encoding_task_total` | `result` 4종 |
| `video_ai_job_total` | `event` 6종 |
| `notification_outcome_total` | `result`+`reason` 5조합 |
| `notification_backlog` | `status`(pending·published) |

전 조합을 빈 생성 시점에 선등록해 증가가 0회여도 노출된다. 대시보드에서 계열이 사라지지
않게 하려는 것이고, 동시에 가변값 태그를 만들 자리가 없어 D1이 구조로 강제된다.

인코딩 큐 적체는 실측에서 `executor_queued_tasks{name="encodingExecutor"}`로 확인됐다
(`executor_active_threads`·`executor_pool_size_threads`·`executor_queue_remaining_tasks` 동반).
Boot 자동 바인딩이라 수동 바인딩 코드는 넣지 않았다. 설계 때 적은 `executor_queued`는
Micrometer가 단위 접미사를 붙이기 전 이름이라 실제로는 나오지 않는다.

### 실행 쿼리

백로그 Gauge가 60초마다 아래 두 문장을 던진다. `status`를 바인드 파라미터가 아니라 리터럴로
박은 이유는 generic plan이 partial index 조건 일치를 증명하지 못해 인덱스를 놓치기 때문이다.

```sql
SELECT count(*) FROM notifications WHERE status = 'PENDING';    -- idx_notifications_pending (V21)
SELECT count(*) FROM notifications WHERE status = 'PUBLISHED';  -- idx_notifications_published (V21)
```

새 인덱스는 만들지 않았다. 알림 종결 카운터는 `markSent`·`markSkipped`·`markDead`의 반환 행
수가 1일 때만 올라간다(Codex 2라운드).

그 세 UPDATE에는 `AND status IN ('PENDING', 'PUBLISHED')` 술어를 넣어 DB 수준의
compare-and-set으로 만들었다(Codex 4라운드, 2026-08-12 성민 승인). ID로만 갱신하면 두 소비자가
동시에 같은 행을 처리할 때 양쪽 다 1행을 받아 계상이 겹친다. 허용 원본을 이 둘로 잡은 근거는
`consume` 초입 가드가 통과시키는 상태 집합과 같아야 의미론이 일관되기 때문이다.
`notifications.status`의 CHECK가 5값으로 닫혀 있어 이 술어는 "비종결이면 종결시킨다"와 동치이고,
0행이 되는 경우는 이미 종결된 행뿐이라 갇히는 행은 생기지 않는다.

이 술어는 계측 범위를 넘어 알림 파이프라인의 동작 두 가지를 함께 고친다. 발송 성공 뒤 재시도
복구기가 DEAD로 덮어쓰던 것이 이제 SENT로 남고(푸시가 실제로 나갔으므로 SENT가 사실이다),
DEAD 행이 재전달될 때 오류 메시지를 다시 쓰던 것도 멈춘다.

### 예외 흐름

계측은 예외를 새로 던지지 않는다. 미등록 태그 값 증가 요청은 조용히 무시하고(맵 조회 결과가
null이면 아무 일도 안 한다), `ApiException` 변환이나 developCode 추가도 없다. 사용자에게
보이는 응답은 전부 불변이다.

예외와 계측의 순서는 세 곳에서 의도적으로 정해져 있다.

- 인코딩 실패 두 경로(길이 초과·일반 오류) 모두 `countEncodingTask`를 `statusWriter.markFailed`
  **앞에** 둔다. 인코더는 재시도가 없어서(MSG-65 D8) 상태 기록이 DB 장애로 던지면 그 태스크가
  어떤 result 시계열에도 남지 않기 때문이다. `resultCounted` 플래그가 길이 초과 계상 후
  catch로 떨어지는 경우의 이중 계상을 막는다.
- AI 제출은 `aiClient.submit` 성공 직후에 센다. `recordAiJob`(DB) 실패로 재제출되면 원격 잡이
  실제로 둘 생기므로 2회 계상이 사실에 맞다.
- 알림은 반대로 전이 트랜잭션이 **끝난 뒤** 반환 행 수를 보고 센다. 여기는 재시도 경로가 있어
  과대 계상 쪽이 위험하다.

`notification.outcome{result=sent}`가 세는 것은 **상태 전이 횟수이지 실제 푸시 발송 횟수가
아니다.** 중복 소비 창에서 FCM 푸시가 두 번 나가도 전이는 하나뿐이라 카운터는 1이다. 완료
조건 5가 "상태 전이당 정확히 한 번"이라 이 쪽이 규정에 맞지만, 대시보드에서 발송량으로 읽으면
어긋나므로 여기 적어 둔다.

`markFailed`가 던진 예외는 `encode()` 밖으로 나가는데 이는 MSG-343 이전부터의 동작이다
(`@Async`라 executor의 uncaught 핸들러가 받는다). 이번 변경이 만든 전파가 아니다.

### 빈 동작

- `VideoProcessingMetrics`는 싱글턴 `@Component`다. 태그 조합 선등록이 생성자에서 끝나고,
  테스트용으로 시각원(`LongSupplier`)을 받는 패키지 전용 생성자가 하나 더 있다.
- `NotificationBacklogMetrics`는 `@ConditionalOnProperty(fillmap.notification.enabled)` 게이트를
  달고 있어 알림 비활성 환경(로컬·CI)에서는 빈 자체가 뜨지 않고 Gauge도 노출되지 않는다.
  릴레이·컨슈머와 같은 게이트라 의도된 동작이다. `@Scheduled(fixedDelay = 60_000)`는
  `NotificationConfig`의 기존 `@EnableScheduling`을 재사용하며, fixedDelay라 앞 폴링이 끝나야
  다음 60초가 시작된다(DB가 느려도 폴링이 겹치지 않는다).
- 처리 시간 시작점 등록·제거는 둘 다 트랜잭션 커밋 이후 콜백에서 일어난다. 교체는
  `triggerEncodingAfterCommit`을 옛 파일 S3 삭제보다 먼저 등록해 시작점이 삭제 I/O만큼
  늦게 찍히지 않게 했고, 삭제는 `removeStart`를 `afterCommit`으로 옮겨 롤백 시 시작점만
  사라지는 창을 없앴다(Codex 1라운드).
- 앱 재시작은 `startNanos`를 비운다. 그 시점에 처리 중이던 영상은 종결 시 Counter만 오르고
  Timer 표본이 빠진다. 2026-08-11 성민 확정으로 허용한 오차이고, 비율 지표는 Counter로
  계산하므로 영향받지 않는다.
