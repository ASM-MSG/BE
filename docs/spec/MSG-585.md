# MSG-585: 격자 리포지토리의 네이티브 조회를 연관관계 기반 JPQL로 옮기는 파일럿

**Owner**: A (지도 인프라, `com.msg.fillmap.grid.*`)

> 요구사항 변경 없음 — 리팩터링이라 PRD 면제 (CLAUDE.md 면제 기준 "요구사항 불변"). 발단은
> `docs/audit/2026-09-08-backend-audit.md` §3.1 NQ1(native 108건 중 42건이 PostgreSQL 전용이 아님)과
> 2026-09-07 박원형 멘토링의 "native 최소화·JPQL 우선" 권고. 지라: MSG-585.

## 개요

`GridRepository`의 native 8건 가운데 PostgreSQL 전용 구문이 없는 5건을 JPQL로 옮긴다. 그러기 위해
`Grid → Region`, `UserGrid → Grid` 읽기 전용 연관관계를 붙인다(경로 조인 `ug.grid`, `g.region`). 나머지
3건(`aggregateOccupiedInRange`·`findOccupiedPageAfter`·`findOccupiedByIntersects`)은 `split_part`·`ST_Y`·
행 값 비교·GIST 공간 연산이라 native로 남긴다. API 계약·응답·저장 쓰기는 하나도 바뀌지 않는다.

이 티켓은 파일럿이다. 실행 SQL과 실행 계획을 전후 비교해 같으면, 나머지 41건(감사 §3.1 분류표 (b) 열)에
같은 방식을 쓸지 팀이 정한다.

## 결정 기록

| ID | 결정 | 근거·기각 대안 |
|---|---|---|
| D-1 | 연관관계는 **읽기 전용**(`insertable = false, updatable = false`)으로만 붙이고 기존 id 필드(`Grid.regionCode`, `UserGridId.gridId`)는 그대로 둔다 | `grids`·`user_grids` 쓰기는 native upsert(`VideoServiceImpl.upsertGrid/upsertUserGrid`)라 연관을 쓰기 경로에 태울 이유가 없다. `@MapsId`로 복합키를 연관에 넘기는 안은 `UserGrid` 빌더·`UserGridId` 사용처 전부를 건드려 기각 |
| D-2 | `findOccupiedPageAfter`(커서 이후 페이지)는 native 유지 | `(grid_y, grid_x) > (:y, :x)` 행 값 비교가 `uq_grids_yx` 단일 범위 스캔 계약(`docs/spec/MSG-90.md` §정렬 키·keyset)이다. JPQL은 `y > :y OR (y = :y AND x > :x)`로 풀어야 하고 플래너가 같은 스캔을 고른다는 보장이 없다 — 별도 실측 후 판단 |
| D-3 | 첫 페이지의 LIMIT은 Spring Data `Limit` 파라미터로 건다 | JPQL에 LIMIT 문법이 없다. `Pageable`은 OFFSET·정렬을 같이 들고 와 keyset 계약(OFFSET 금지)과 어긋나 기각. 호출부 2곳(서비스 1·테스트 2)이 `Limit.of(n)`으로 바뀐다 |
| D-4 | `summarizeOccupiedByRegion`의 `COUNT(*)::int`는 `CAST(COUNT(ug) AS Integer)`로, `COALESCE(SUM, 0)`은 `0L`로 옮겨 프로젝션 게터 타입(`Integer`/`Long`)을 유지한다 | 프로젝션·`CurrentRegionView` 시그니처 무변경. Hibernate 생성 SQL은 `cast(count(*) as integer)`로 원문과 같다 |
| D-5 | `BETWEEN` 파라미터는 종전 `long` 그대로 둔다(컬럼은 `Integer`) | Hibernate 7이 정수 확장 비교를 허용하는 것을 테스트로 확인. 시그니처를 바꾸면 `GridRange`(long) 호출부까지 캐스트가 번진다 |
| D-7 | `Grid.regionCode` 문자열 필드를 `region` 연관과 **함께 남긴다** (같은 컬럼 2중 매핑 허용) | 아래 실측 참조 |
| D-6 | `findRegionCodeNames`(MSG-466, 이미 JPQL·연관 없는 `ON` 조인)는 손대지 않는다 | 결과가 `g.region` 경로 조인과 같고, 이 티켓은 native 전환이 범위다. 주석만 사실에 맞게 정정 |

### 2026-09-08 구현 (강정민 · Claude)

**데이터 저장 위치**: 변경 없음. 연관관계는 기존 컬럼(`grids.region_code`, `user_grids.grid_id`)을 읽기 전용으로

**실행 쿼리 (실측, Hibernate 7 생성 SQL — DB 로그 `log_min_duration_statement=0` 캡처)**:

```sql
-- findVideoCount
select ug1_0.video_count from user_grids ug1_0 where ug1_0.user_id=$1 and ug1_0.grid_id=$2
-- findOccupiedInRange
select g1_0.grid_id,g1_0.grid_y,g1_0.grid_x,r1_0.region_name from user_grids ug1_0
  join grids g1_0 on g1_0.grid_id=ug1_0.grid_id left join regions r1_0 on r1_0.region_code=g1_0.region_code

-- findOccupiedPage (동일 + 정렬·상한)
  ... order by g1_0.grid_y,g1_0.grid_x fetch first $6 rows only
-- summarizeOccupiedByRegion
select cast(count(*) as integer),coalesce(sum(ug1_0.video_count),0) from user_grids ug1_0

-- findRegionNames
select g1_0.grid_id,r1_0.region_name from grids g1_0 join regions r1_0 on r1_0.region_code=g1_0.region_code
```

원문 native와 조인·술어·정렬이 글자 수준으로 대응한다(별칭만 다름). `FETCH FIRST n ROWS ONLY`는 PostgreSQL이

**실행 계획 전후 (격자 40,000 · 점령 10,000 · 뷰포트 100×100 셀, 로컬 콜드)**:

| 쿼리 | 구 native | 신 JPQL | 판정 |
|---|---|---|---|
| findOccupiedInRange | Hash Join(grids Seq Scan 10,000행 필터 + user_grids Hash) → regions Memoize Index Scan, cost 2412, 6.5ms | 동일 노드·동일 cost 2412, 5.3ms | 같음 |
| findOccupiedPage LIMIT 501 | `Index Scan using uq_grids_yx` → `idx_user_grids_grid` Nested Loop → Limit, cost 1635, 2.2ms | 동일, 2.2ms | 같음 — keyset 인덱스 정렬 유지 |

### 2026-09-08 추가 실측 — "JPQL 없이 연관관계 탐색만으로 하면 안 되나"

사용자 지적: N+1이 난다고 단정하지 말고 실제로 얼마나 심각한지 재고 결정한다. 테스트 소스에만 실험용
리포지토리(`grid/benchmark/UserGridFetchExperimentRepository`)와 벤치마크(`GridViewportFetchBenchmark`,
`GRID_BENCHMARK=true` 게이트)를 두고 프로덕션 코드는 건드리지 않았다. 세 방식이 같은 격자·같은 행정동
이름 목록을 내는지 단언으로 확인하고, 방식당 5회 반복 중앙값을 쓴다. 문장 수는 Hibernate 통계
(`generate_statistics`)의 `prepareStatementCount`.

- A. 현행 JPQL 인터페이스 프로젝션(컬럼 4개)
- B. 파생 쿼리 `findByIdUserIdAndGridGridYBetween…` + `ug.getGrid().getRegion()` 탐색, `@EntityGraph` 없음
  (`default_batch_fetch_size=100` 적용)
- C. B + `@EntityGraph(attributePaths = {"grid", "grid.region"})`

격자 10,000 · 점령 2,500(1/4) · 라벨 절반, 로컬:

| 뷰포트 | 행 | A JPQL 프로젝션 | B 파생 + 지연 로딩 | C 파생 + EntityGraph |
|---|---|---|---|---|
| 10×10 | 25 | 1문장 · 1.9ms | 3문장 · 51엔티티 · 5.4ms | 1문장 · 51엔티티 · 3.3ms |
| 50×50 | 625 | 1문장 · 6.3ms | 9문장 · 1,251엔티티 · 14.2ms | 1문장 · 1,251엔티티 · 9.5ms |
| 100×100 | 2,500 | 1문장 · 20.4ms | 27문장 · 5,001엔티티 · 42.5ms | 1문장 · 5,001엔티티 · 26.3ms |

읽기: B의 "N+1"은 배치 크기 100 때문에 `1 + ceil(N/100)(grid) + 1(region)` 문장으로 묶인다 — 2,500칸에서
27문장·약 2배 시간이라 장애급은 아니다. C는 문장 1개로 돌아오지만 엔티티 5,001개를 영속성 컨텍스트에
올려 A보다 약 30% 느리다. 어느 크기에서도 B·C가 A를 이기는 구간은 없었다. 결론은 사용자 판단
(JPQL 문자열을 없애는 값 vs 1.3~2배 비용).

같은 벤치마크를 `GRID_BENCH_BLOCK=300`(격자 90,000 · 점령 22,500)으로 다시 돌린 결과. 뷰포트 행 수가 같으면 표
전체 크기는 결과에 거의 영향이 없고, 뷰포트 200×200(10,000행)에서 B는 102문장이다:

| 뷰포트 | 행 | A JPQL 프로젝션 | B 파생 + 지연 로딩 | C 파생 + EntityGraph |
|---|---|---|---|---|
| 10×10 | 25 | 1문장 · 2.0ms | 3문장 · 5.0ms | 1문장 · 3.2ms |
| 50×50 | 625 | 1문장 · 7.6ms | 9문장 · 16.1ms | 1문장 · 10.7ms |
| 100×100 | 2,500 | 1문장 · 22.0ms | 27문장 · 47.4ms | 1문장 · 27.9ms |
| 200×200 | 10,000 | 1문장 · 65.9ms | 102문장 · 20,001엔티티 · 116.0ms | 1문장 · 20,001엔티티 · 90.1ms |

DB 로그(`log_min_duration_statement=0`)로 잡은 세 방식의 **실제 실행문** (원본 `/tmp/backend-audit/msg585-bench.log`):

```sql
-- A. 현행 JPQL 프로젝션 — 요청당 1문장, 컬럼 4개
select g1_0.grid_id,g1_0.grid_y,g1_0.grid_x,r1_0.region_name
from user_grids ug1_0 join grids g1_0 on g1_0.grid_id=ug1_0.grid_id
  left join regions r1_0 on r1_0.region_code=g1_0.region_code
where ug1_0.user_id=$1 and g1_0.grid_y between $2 and $3 and g1_0.grid_x between $4 and $5

-- B. 파생 쿼리 + 지연 로딩 — 요청당 1 + ceil(N/100) + 1 문장
select ug1_0.grid_id,ug1_0.user_id,ug1_0.cover_video_id,ug1_0.first_collected_at,ug1_0.last_uploaded_at,ug1_0.video_count
from user_grids ug1_0 left join grids g1_0 on g1_0.grid_id=ug1_0.grid_id
where ug1_0.user_id=$1 and g1_0.grid_y between $2 and $3 and g1_0.grid_x between $4 and $5
select g1_0.grid_id,g1_0.grid_x,g1_0.grid_y,g1_0.region_code from grids g1_0 where g1_0.grid_id = any ($1)   -- 100개씩 반복
select r1_0.region_code,r1_0.parent_code,r1_0.region_name,r1_0.total_grid_count from regions r1_0 where r1_0.region_code=$1

-- C. 파생 쿼리 + @EntityGraph — 요청당 1문장이지만 grids 를 두 번 조인한다 (g1_0 조건용, g2_0 fetch 용)
select ug1_0.*, g2_0.grid_id,g2_0.grid_x,g2_0.grid_y,g2_0.region_code, r1_0.region_code,r1_0.parent_code,r1_0.region_name,r1_0.total_grid_count
from user_grids ug1_0 left join grids g1_0 on g1_0.grid_id=ug1_0.grid_id
  left join grids g2_0 on g2_0.grid_id=ug1_0.grid_id
  left join regions r1_0 on r1_0.region_code=g2_0.region_code
where ug1_0.user_id=$1 and g1_0.grid_y between $2 and $3 and g1_0.grid_x between $4 and $5
```

C의 이중 조인은 Spring Data가 파생 쿼리의 조건 경로(`grid.gridY`)와 `@EntityGraph`의 fetch 경로를 별개 별칭으로
만들기 때문이다. 같은 행을 두 번 조인하는 비용이 C가 A보다 느린 이유의 일부다.

### 2026-09-08 부하 실측 — 실제 엔드포인트 · 실제 SQL · 서버 지표

### 2026-09-09 인덱스 검증 — `long` 파라미터(int8) vs `integer` 컬럼, 복합 인덱스 `uq_grids_yx`

D-5의 "Hibernate 7이 Long 파라미터를 허용한다"는 컴파일·결과 정합만 본 것이라, 실제 int8 바인딩이 `grid_y`/`grid_x`(int4)의

`/tmp/backend-audit/msg585-index.out`).

| 조건 | 계획 | 비고 |
|---|---|---|
| 범위 조회 50×50 (격자의 2.8%) | `Index Scan using uq_grids_yx` — `Index Cond: grid_y >= '999100'::bigint AND … AND grid_x <= …::bigint` | int8 파라미터가 인덱스 조건으로 들어간다 (PostgreSQL `integer_ops` opfamily의 int4/int8 교차 연산자) |
| 범위 조회 100×100 (11%) | `Bitmap Index Scan on uq_grids_yx` → Bitmap Heap | 선택도가 커지면 비트맵으로 전환. 이전 감사 EXPLAIN의 Seq Scan은 뷰포트가 시드의 25%였기 때문 |
| 첫 페이지 50×50 / 100×100 | 같은 인덱스 조건 + 메모리 quicksort(68KB/272KB) + Limit | 벤치 사용자가 점령의 100%를 갖는 시드라 조인 방향이 hash 쪽으로 바뀌어 정렬이 붙었다. 격자 4만·점령 1만 시드에서는 인덱스 순서 그대로 Nested Loop(정렬 없음) |

동작한다(두 조건 모두 `Index Cond` 에 보이지만 스캔 경계는 선행 컬럼 y). 2차원 범위의 대안(GiST 접근 B)은 MSG-90에서
A 채택으로 이미 판정됐다. `user_grids` 쪽 `Seq Scan … Filter user_id` 는 이 시드에서 한 사용자가 전부를 갖기 때문이고,
실데이터에서는 PK `(user_id, grid_id)` 선행 컬럼으로 잡힌다 — dev 실측 권장.

### 2026-09-09 Z-order 곡선(모턴 코드) 검토 — 기각

사용자 제안. 앞선 후보 목록에 공간 채움 곡선이 빠져 있었다(누락이지 기각이 아니었다). `(grid_y, grid_x)`를 비트 인터리브로
1차원 모턴 코드로 접고 `(user_id, morton)` 인덱스에 단일 구간 `BETWEEN morton(minY,minX) AND morton(maxY,maxX)` + 사각형
재검(오탐 제거)으로 조회하는 방식이다. 실제·독립 실험 테이블(사용자 200명 성글게 + 헤비 1명, 50,008행)로 비교했다.

| 쿼리 | `(user_id, grid_y, grid_x)` 복합 | Z 단일 구간 + 재검 |
|---|---|---|
| 헤비 · 100×100 (정답 553행) | 0.113ms · 16버퍼 · **553행 읽음** | 0.154ms · 18버퍼 · 1,646행 읽음 |
| 헤비 · 100×100 첫 페이지(LIMIT 101) | **0.035ms · 6버퍼** | 0.234ms · 18버퍼 |
| 헤비 · 20×20 (정답 22행) | 0.019ms · 6버퍼 · **22행 읽음** | 0.033ms · 7버퍼 · **356행 읽음** |
| 일반 · 100×100 (정답 25행) | 0.016ms · 4버퍼 · 25행 | 0.016ms · 4버퍼 · 74행 |

**기각 사유 셋.**

1. **복합 btree 가 이미 정확히 필요한 행만 읽는다.** 오버리드를 예상했는데 실측은 정답 행 수와 같았다(553/553, 22/22).
   선행 컬럼 `user_id` 등치가 큰 가지치기를 하고 나면 나머지 두 범위는 인덱스 스캔 키로 처리된다. Z-order 의 존재 이유
   (두 차원을 동시에 가지치기)가 여기서는 이미 충족돼 있다.
2. **단일 Z 구간의 오탐이 크다.** 100×100 에서 3배(1,646/553), 20×20 에서 **16배**(356/22). 작은 정사각형이 Z 곡선의
   상위 비트 경계를 걸치면 구간이 통째로 넓어진다. BIGMIN/LITMAX 로 구간을 여러 개로 쪼개면 줄어들지만(미실측), 복합
   btree 가 이미 정답 행만 읽으므로 **최선이어야 무승부**다.
3. **정렬 순서를 잃는다.** 모턴 순서 ≠ `(grid_y, grid_x)` 행 우선 순서라 첫 페이지에 명시 정렬이 붙고 LIMIT 조기 종료가
   깨진다 — 0.035 → 0.234ms(6.7배). 커서 계약(MSG-90)이 `(grid_y, grid_x)` 순서라 이건 우회가 안 된다.

Z-order 가 유리한 조건은 **선행 등치 키가 없는 전역 2차원 범위 조회**다. 이 API 는 언제나 `user_id` 로 시작하므로 해당하지
않는다. 전역 조회(핫구역·미션 클러스터링)에서 같은 문제가 나오면 그때 다시 볼 후보다.

### 2026-09-09 `Grid.regionCode` 를 지울 수 있나 (D-7 근거)

지적: `region` 연관이 생겼으니 같은 컬럼을 읽는 `regionCode` 문자열 필드는 중복 아닌가. 실제로 `Grid.getRegionCode()`
자바 호출부는 0건이고 JPQL 두 곳에서만 쓴다. 세 가지 대안을 코드로 바꿔 생성 SQL 을 대조했다.

| 대안 | 결과 |
|---|---|
| ① `g.region.regionCode` + `LEFT JOIN g.region r` (연관 조인) | **동작 변경.** SELECT·WHERE 가 `r1_0.region_code`(조인된 쪽)로 바인딩돼 LEFT JOIN 이 사실상 INNER 가 된다 — 라벨은 있는데 regions 행이 없는 격자가 결과에서 빠진다(MSG-466 javadoc 이 막으려던 경우). 기존 테스트 194건이 못 잡았다 |
| ② `fk(g.region)` | SELECT 절에서 Hibernate 예외(`ColumnReference cannot be cast to DomainResultProducer`). WHERE 에서는 동작 |
| ③ `g.region.regionCode` + `LEFT JOIN Region r ON r.regionCode = g.region.regionCode` (연관을 조인하지 않고 Region 을 별도 조인) | **성공.** 생성 SQL 이 원본과 글자 단위로 같고 테스트 green. 필드 제거 가능 |

**그럼에도 남긴다.** ③이 성립하는 이유는 "연관을 명시 조인하지 않으면 경로가 FK 컬럼으로 풀린다"는 Hibernate 해석 규칙인데,
나중에 누군가 자연스러운 형태(`LEFT JOIN g.region r`)로 고치는 순간 ①의 함정으로 되돌아간다. 그때 붙잡을 안전한 필드가
없어진다. 필드 하나를 줄이는 값보다 "FK 원값을 애매함 없이 읽는 통로"를 남기는 값이 크다고 판단했다. 판단 근거는
`Grid.java` javadoc 에도 적었다.

**부수 발견**: "라벨은 있는데 regions 행이 없는 격자" 회귀 테스트가 없다(①이 194건을 통과한 이유). 별도 티켓 후보.
