# MSG-149 · MSG-150: 인코딩 완료 → AI 처리 트리거 · 결과 반영 · READY 전이

**Owner**: B (`com.msg.fillmap.video.*`) — video 도메인 단독. grid/region 무수정, 계약 인터페이스 무변경.

> 두 티켓을 한 파이프라인으로 묶는다. MSG-149 = 인코딩 완료 후 AI 제출·폴링·타임아웃,
> MSG-150 = 결과 수신·DB 반영·`BLURRING→READY|FAILED` 전이. 나누면 절반짜리 상태 머신이 커밋된다.
> 선행: MSG-145(develop 머지) — `videos.blurred_s3_key`·`highlights`·`ai_job_id` 컬럼 + `Video.applyBlurResult`.
> AI 계약 정본: `FillMap-AI/README.md` "### API (BE ↔ AI 계약)". 실행 방식 정본: MSG-143 ADR(상시 FastAPI, 직접 HTTP).
> MSG-147 잔여 "블러본 S3 업로드"는 이 티켓에서 해소된다(§계약, §범위 안).

---

## 개요

인코딩(MSG-65) 워커가 READY 로 끝내던 흐름을, AI 활성 시 `ENCODING → BLURRING → READY` 로 확장한다.
인코딩본을 AI 서버(`POST /jobs`)에 제출하고, `@Scheduled` 폴러가 결과를 받아 블러본을 S3 에 올린 뒤
`blurred_s3_key`·`highlights` 를 채우고 READY 로 전이한다. AI 실패·타임아웃·유실은 FAILED 로 수렴한다.

## 배경 · 목표

- FillMap 은 업로드 영상의 얼굴·번호판을 AI 로 블러 처리하고 하이라이트 구간을 뽑아 재생본으로 쓴다(에픽).
  MSG-145 가 저장 자리를 만들었고, 이 티켓이 그 자리를 채우는 **호출·폴링·상태전이 오케스트레이션**이다.
- **목표**: 인코딩 완료가 AI 처리를 자동 트리거하고(149), 결과가 DB 에 반영되며 상태가 READY/FAILED 로
  전이한다(150). AI 서버가 없거나 죽은 환경에서도 영상이 영구 BLURRING 에 갇히지 않는다.

## 계약 (AI 서버 — 정본 `FillMap-AI/README.md`)

비동기. 1080p 30초 ≈ 3~4분(실측), 큐 순차 처리(≈17건/시). **AI 가 다운스케일을 자체 수행** → BE 는
인코딩본(720p)을 그대로 보낸다.

| 메서드 | 경로 | 응답 | BE 처리 |
|---|---|---|---|
| `POST` | `/jobs` | `202 {job_id, status}` — multipart `file` | job_id 를 `ai_job_id` 에 기록 |
| `GET` | `/jobs/{id}` | `{job_id, status, highlights, error}` | 폴링. status 매핑 아래 |
| `GET` | `/jobs/{id}/video` | 블러본 mp4(h264, 오디오 유지). 완료 전 `409` | DONE 시 받아 S3 업로드 |
| `GET` | `/health` | 헬스체크 | (사용 안 함) |

- status 전이: `QUEUED → PROCESSING → DONE | FAILED`. 매핑: `PROCESSING` 은 BE `BLURRING` 유지,
  `DONE` → READY, `FAILED`/404(잡 유실)/타임아웃 → `FAILED`.
- `highlights`: 완료 시 `[[시작초, 끝초], …]` **최대 3구간, 소수점 2자리**(`List<List<Double>>`, MSG-145). 0구간 가능.
- `highlights` 값 세팅은 `Video.applyBlurResult`(MSG-145, 필드만 채우고 전이 안 함)를 재사용한다.

## 성공 기준

1. AI 활성 시 인코딩 완료가 `ENCODING → BLURRING` 전이 + `POST /jobs` 제출 + `ai_job_id` 기록으로 이어진다.
2. 폴러가 `DONE` 결과의 블러본을 S3 에 올리고 `blurred_s3_key`·`highlights` 를 채운 뒤 `BLURRING → READY` 로 전이한다.
3. AI `FAILED`·잡 유실(404)·타임아웃 상한 초과 시 `markFailed`(FAILED) 로 수렴한다 — 영구 BLURRING 없음.
4. **AI 비활성(플래그 off)이면 오늘 흐름 그대로** `ENCODING → READY` 로 끝난다(기존 동작·기존 테스트 보존).
5. 서버 재시작 후에도 BLURRING 영상이 폴러에 잡혀 이어 처리된다(`WHERE processing_status='BLURRING'`, MSG-145 D3).
6. FAILED·BLURRING 영상은 전역 대표 조회(`findGlobalCover`, READY 강제)에 노출되지 않는다 — 미블러본이 남에게 공개되지 않는다.
7. 신규 HTTP 의존성 없이 Spring `RestClient`(webmvc 내장)로만 통신한다. 전체 테스트 green.

## 설계 결정 (근거 포함)

| # | 포인트 | 결정 | 한 줄 근거 |
|---|---|---|---|
| D1 | 상태 머신 | **`markReady` 재정의 없음 + 전이 메서드 2개 신설**. 활성: 워커가 `markEncoded(encoded,thumb)`→BLURRING, 결과 후 `applyBlurResult`+`markReadyFromBlurring`→READY. 비활성: 오늘처럼 `markReady`→READY | `markReady` 를 건드리면 MVP 경로·`VideoStatusTransitionTest`가 깨진다. `applyBlurResult`는 MSG-145 가 "전이 안 함"으로 못박음 → 전이만 별 메서드로 얹는 게 계약 정합 |
| D2 | AI 제출 파일 소스 | **폴러가 S3 `encoded_url` 키에서 재다운로드해 제출** | 인코딩 tmp 는 `encode()` finally 에서 삭제 → 로컬 수명이 `encode()` 안에 갇힘. 로컬 재사용은 워커를 AI 가용성에 결합하고 제출 경로를 둘로 쪼갬. 같은 리전 수 MB GET 은 무시 가능 |
| D3 | 폴링 구조 | **`@Scheduled(fixedDelay)` 단일 폴러가 BLURRING 일괄 조회** (`@EnableScheduling` 추가). `ai_job_id` null=미제출→제출, non-null=제출됨→`GET /jobs/{id}` 폴링. 기본 주기 30s(프로퍼티) | BLURRING 을 상태로 두면 재시작 복구가 공짜(MSG-145 D3). 잡별 in-memory async 루프는 재시작 시 소실. `fixedDelay` 로 폴 중첩 방지 |
| D4 | 재시도 · 타임아웃 | **명시적 backoff 없음(YAGNI)**. 제출된 잡은 **먼저 poll** — `QUEUED`/`PROCESSING`(살아있음)이면 타임아웃 검사 skip. 타임아웃 상한은 **미제출 행과 poll 불가(연결 실패) 행에만** `blurring_started_at` 기준(경과 > PT30M → FAILED, null 이면 `created_at` 폴백) | 폴러 조정이 곧 재시도. **타임아웃 기준을 `blurring_started_at`(V4)로 승격**: 교체 후 재인코딩은 `created_at` 이 옛 시각이라 **100% 결정적 오탐**이라 상시 재현 → 지금 반영. **살아있는 잡 제외**: 큐 적체로 `PROCESSING` 중인 잡을 타임아웃이 죽이던 오탐 제거. **불변 원칙(R7): 모든 폴 사이클 결말은 ①성공 ②가드거부 ③failIfTimedOut 셋 중 하나** — 외부 응답 실패(연결·파싱·완료본 미가용)가 비예외 형태로 타임아웃을 우회하지 못하게 한다. `ponytail`: `PROCESSING` 행업은 무한 대기 — AI 재시작(→404)·AI FAILED 가 정리, 잦으면 PROCESSING 상한 추가 |
| D5 | 블러본 S3 키 | **`videos/blurred/{userId}/{videoId}.mp4`** | `videos/encoded/{userId}/{videoId}.mp4` 와 동형·videoId 기반 → 교체 시 같은 키 덮어쓰기 정합, MSG-145 `replaceFile`/`deleteQuietly` 정리 로직·기존 테스트 예시(`videos/blurred/1/7.mp4`)와 일관 |
| D6 | 실패 · BLURRING 중 표시 | **기존 `markFailed`(FAILED) 재사용, 신규 UI 처리 없음.** AI 활성 신규 업로드는 **READY 전까지 썸네일 객체가 없다**(P1 — 인코딩이 미블러 썸네일을 올리지 않음) | 전역 대표는 `processing_status='READY'` 강제 → FAILED·BLURRING 자동 제외(미블러본 비공개). 내 도감 리스트는 `status=ACTIVE` 만 필터 → FAILED·BLURRING 이 내 리스트엔 남고, my-videos 가 `processingStatus` 를 주므로 **FE 가 BLURRING 을 플레이스홀더로 렌더**(썸네일 부재는 인코딩 중 FAILED 와 동일 처리) |
| D7 | 게이트 · 범위 | **`ai.enabled` 기본 off**(RegionSeeder `fillmap.region.seed.enabled` 관례). MSG-147 잔여 블러본 업로드=이 티켓에서 해소(범위 안) | AI 서버 없는 로컬/CI 에서 워커가 오늘 흐름(READY) 유지. 블러본 S3 업로드는 `GET /jobs/{id}/video`→S3 로 여기서 완결 |
| D8 | 썸네일 = AI 완료 시 생성 · 키 기록 | **미블러 썸네일은 아예 안 만든다** — AI 활성 인코딩은 썸네일을 추출·업로드하지 않고 `thumbnailUrl` 도 기록하지 않는다(P1/R5). 폴러가 **완료 시 블러본에서 뽑아** 결정적 키(인코더와 동일 포맷 `videos/thumb/{userId}/{videoId}.jpg`)에 올린 **직후**, `markBlurReady`(=`markReadyFromBlurring`)에서 `thumbnailUrl` 을 기록한다. 인코딩 워커와 같은 `FfmpegRunner`·`encodingExecutor` 로 직렬화(P2-a). 순서: 블러본·썸네일 업로드 → `markBlurReady`. ffmpeg 실패면 사이클 skip. 엔티티/스키마 무변경 | 인코딩 썸네일은 **블러 전 원본 프레임**이라 교체 시 재인코딩이 살아있는 공개 키(presigned)에 덮어써 노출 창 → 업로드 시점을 AI 완료 시로 이동해 미블러 바이트가 S3 에 안 닿게 근본 차단. **"thumbnailUrl non-null ⇔ S3 객체 실존" 불변식 복원**(R5): BLURRING 동안 null → my-videos 가 계약대로 null 반환(FE 플레이스홀더), 객체 업로드 완료 후에만 키 기록. 가드 거부 시 재추출 썸네일도 블러본과 함께 정리(P2-c). t3.small 동시 ffmpeg = OOM 이라 폴러 추출도 인코딩 풀로 직렬화(P2-a) |

## 구현 스케치 (신규/변경)

- **`AiProperties`** (record + `@ConfigurationProperties(prefix="ai")`, `AwsProperties` 관례): `base-url`,
  `enabled`(기본 false), `timeout`(Duration, 기본 PT30M), `poll-interval-ms`(기본 30000).
- **`AiClient`** — `RestClient.builder().baseUrl(...)` 어댑터. `submit(Path/bytes) → String jobId`,
  `poll(jobId) → AiJobResult{status, highlights, notFound}`, `downloadBlurred(jobId) → byte[]/InputStream`.
- **`Video`**: `markEncoded(encodedKey, thumbnailKey)`(ENCODING→BLURRING, 키 저장), `markReadyFromBlurring()`
  (BLURRING→READY), `recordAiJob(jobId)`(ai_job_id 세팅). `applyBlurResult`·`markReady`·`markFailed` 재사용.
- **`VideoStatusWriter`** (REQUIRES_NEW): `markEncoded`, `recordAiJob`, `markBlurReady`(applyBlurResult+markReadyFromBlurring), `markFailed` 재사용.
- **`VideoEncodingServiceImpl`**: 완료 지점 1-라인 분기 — `ai.enabled` 면 `markEncoded`(BLURRING), 아니면 `markReady`(오늘 그대로).
- **`AiBlurPoller`** (`@Scheduled(fixedDelayString="${ai.poll-interval-ms:30000}")`): BLURRING 조회 → 잡별 reconcile(제출/폴링/완료/실패/타임아웃).
- **`VideoRepository`**: `findByProcessingStatus(ProcessingStatus.BLURRING)`.
- **`AsyncConfig` 또는 신규 config**: `@EnableScheduling`.

## 리뷰 반영 이력 (Codex 교차 리뷰)

구현 후 Codex 교차 리뷰 8라운드를 오케스트레이터가 사실 확인해 반영했다.

**라운드 1**
- P1 — 완료·실패 쓰기에 잡 정체성 가드: `markBlurReady`·신규 `markBlurFailed(videoId, expectedJobId)` 가 fresh 조회 후 `ACTIVE·BLURRING·같은 ai_job_id` 일 때만 적용. 무가드 `markFailed(Long)` 은 인코딩 경로용으로 보존.
- P2 — 폴러 조회를 `findByStatusAndProcessingStatus(ACTIVE, BLURRING)` 로 한정(삭제본 제외) + 쓰기 가드에 ACTIVE 확인.
- P3 (수용) — 크래시 창 중복 제출 1건 가능: 제출 지점 `ponytail` 주석만.

**라운드 2**
- P1-a — **`blurring_started_at`(V4) 승격**: 타임아웃을 시도 시작 기준으로. 교체 후 재인코딩 시 `created_at` 기반 100% 오탐이 근거(D4).
- P1-b — `recordAiJob(videoId, jobId, expectedBlurringStartedAt)`: 시도 넌스(blurringStartedAt) 로 제출 가드. 교체된 옛 파일의 잡ID 를 새 시도에 붙이지 않음.
- P1-c — 가드 조회를 `findWithLockById`(PESSIMISTIC_WRITE) 로 원자화 — replace/delete 트랜잭션과 행 잠금 직렬화.
- P2-d — `markBlurReady` 가 적용 여부 boolean 반환 → 폴러가 거부 시 방금 올린 블러본을 deleteQuietly.

**라운드 3**
