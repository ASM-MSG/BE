# MSG-391: 친구 코드 미리보기에 관계 상태 동봉

**Owner**: B (friend 도메인, `com.msg.fillmap.friend.*`)

> 요구사항 정본: `docs/prd/MSG-391-prd.md` (검토됨, 2026-08-25 성민 승인), SRS FR-FRIEND-14 (계획)
> 선행 결정: MSG-185 "미리보기는 advisory[^1] 전용" 중 "자기 코드나 이미 친구도 단순 조회로 성공"
> 부분을 "성공하되 관계 상태를 함께 알려준다"로 일부 뒤집는다 (PRD §2).
> 작업 브랜치: `feature/MSG-391-friend-preview-relation` (생성 완료)

## 개요

GET /api/friends/preview 응답에 조회자와 코드 주인의 관계 상태 필드 `relation`을 추가한다.
값은 SELF(본인), NONE(관계 없음), OUTGOING_PENDING(내가 보낸 요청 대기),
INCOMING_PENDING(상대가 보낸 요청 대기), FRIENDS(이미 친구)의 다섯 가지다.
기존 `nickname` 필드와 9404 실패 계약은 그대로 두는 additive 계약 변경[^2]이며,
DB 마이그레이션은 없다.

## 배경 · 목표

미리보기가 닉네임만 주기 때문에, 사용자는 요청 버튼을 누르고 나서야 자기 코드였다는 것(9400),
이미 친구였다는 것(9409), 이미 보낸 요청이 있다는 것(9410)을 안다. 가장 나쁜 경우는 상대가
먼저 요청을 보내 둔 상태다. 이때 요청 버튼을 누르면 기존 요청이 수락으로 승격되어(자동 수락[^3])
사용자가 모르는 채 친구가 된다. 미리보기 단계에서 관계를 알려주면 화면이 버튼의 활성 여부와
문구를 미리 정할 수 있다 (피그마 친구 에러 상태 보드 14614:631이 이 전제로 그려져 있다).

목표: 미리보기 응답에 관계 상태 다섯 값 중 하나가 실리고, 같은 관계 상태에서 미리보기와
요청 API가 서로 다른 답을 내지 않는다 (PRD FR-1~FR-10).

## 성공 기준

- 다섯 관계 상태 각각에서 미리보기가 PRD FR-2~FR-6이 정한 값을 돌려준다.
- 존재하지 않는 코드는 기존과 동일한 9404 실패다. 응답 형태와 코드 불변 (FR-7).
- `nickname` 필드가 그대로 유지되어 새 필드를 모르는 기존 클라이언트도 이전과 같이 동작한다 (FR-8).
- 요청 API의 검증, 에러, 자동 수락 동작이 변하지 않는다. 기존 request 테스트 전부 green (FR-9).
- 같은 관계 상태에서 미리보기와 요청 API의 답이 대응한다. 예: FRIENDS를 받은 직후 관계 변동
  없이 요청하면 9409 (FR-10). 아래 "테스트 시나리오"가 이 기준의 검증 수단이다.
- 미리보기 조회가 관계 행을 잠그지 않는다 (비기능·성능): 신설 조회에 `@Lock` 부재.

## API 명세

### GET /api/friends/preview (기존 API의 응답 필드 추가)

- 인증: 필수. SecurityConfig가 `anyRequest().authenticated()`라 로그인은 이미 강제되고 있었고,
  이번에 메서드에 인증 주체를 주입만 한다. 보안 수준 변화 없음.
- 요청: `?code={8자 친구 코드}` (기존 그대로)

**성공 200**

```json
{
  "developCode": 200,
  "message": "성공",
  "data": {
    "nickname": "채우미",
    "relation": "NONE"
  }
}
```

- `relation`: `SELF` | `NONE` | `OUTGOING_PENDING` | `INCOMING_PENDING` | `FRIENDS` (문자열 직렬화)
- `nickname`: 기존 그대로. SELF일 때는 내 닉네임이 실린다.

**실패** (기존 그대로, 추가 없음)

| developCode | HTTP | 조건 |
|---|---|---|
| 9404 | 404 | 존재하지 않는 친구 코드 (`FRIEND_CODE_NOT_FOUND`) |

9400, 9409, 9410은 여전히 요청 API에서만 난다. 미리보기는 관계가 무엇이든 200이다.

## 구현 결정

### D-1. 무잠금 방향 포함 쌍 조회 신설: `findPair` 재사용 불가

티켓 컨텍스트는 `findPair` 재사용을 예상했지만 `findPair`는 비관적 쓰기 잠금[^4]이 걸린
조회라서 읽기 전용 트랜잭션[^5]인 preview에서 PostgreSQL이 거부한다 (MSG-186 실측,
리포지토리 javadoc과 위키 Friend API 문서에 명시). 기존 무잠금 조회 `existsAcceptedPair`는
ACCEPTED 존재만 boolean으로 주므로 대기 상태의 방향을 가르지 못한다. 따라서
`FriendshipRepository`에 무잠금 쌍 조회를 신설한다.

```java
/**
 * 방향 무관 쌍 조회, 무잠금 (MSG-391). findPair 와 JPQL 동일, @Lock 만 없다.
 * readOnly 트랜잭션(preview)용. findPair 는 PESSIMISTIC_WRITE 라 여기서 못 쓴다 (MSG-186 실측).
 */
@Query("""
	SELECT f FROM Friendship f
	WHERE (f.id.requesterId = :a AND f.id.addresseeId = :b)
		OR (f.id.requesterId = :b AND f.id.addresseeId = :a)
	""")
Optional<Friendship> findPairWithoutLock(@Param("a") Long a, @Param("b") Long b);
```

행이 오면 `getRequesterId()`로 방향을, `getStatus()`로 상태를 가른다. 별도 프로젝션 없이
엔티티를 그대로 쓴다 (readOnly 트랜잭션이라 변경 위험 없음). 두 방향 모두 복합 기본 키
(requester_id, addressee_id) 또는 V1 `idx_friendships_addressee` 인덱스를 타는 단건 수준
조회 1회다 (PRD 비기능·성능).

### D-2. 관계 판정을 한 곳으로 모은다: `FriendRelation.of`

상태 판정 분기를 enum의 정적 팩토리 하나에 두고 preview와 request가 같이 소비한다.
두 곳이 각자 분기를 들고 있으면 FR-10(두 API가 다른 답을 내지 않는다)이 관례로만 지켜지는데,
판정 코드가 하나면 구조로 보장된다 (티켓 제안 채택).

```java
/** 쌍 행(무잠금·잠금 무관)과 조회자 id 로 관계를 판정한다. SELF 는 호출 전에 가른다 (D-4). */
public static FriendRelation of(Long viewerId, Friendship pairOrNull) {
	if (pairOrNull == null) {
		return NONE;
	}
	if (pairOrNull.getStatus() == FriendshipStatus.ACCEPTED) {
		return FRIENDS;
	}
	return pairOrNull.getRequesterId().equals(viewerId) ? OUTGOING_PENDING : INCOMING_PENDING;
}
```

`request`는 기존 분기(ACCEPTED → 9409, 내가 requester → 9410, 역방향 → 승격)를 이 판정의
switch 소비로 바꾼다. 동작 불변 리팩터링이다: 판정 순서, 에러 코드, 자동 수락 전부 그대로이고
(FR-9), 기존 request 테스트가 회귀 가드다. KEY SHARE 선취와 findPair 잠금 등 request의
트랜잭션 구조는 건드리지 않는다.

```java
// request 내부 (KEY SHARE 선취와 findPair 잠금 이후)
switch (FriendRelation.of(userId, pair.orElse(null))) {
	case NONE -> { /* 기존 PENDING 생성 + 알림 */ }
	case FRIENDS -> throw new ApiException(FriendErrorCode.ALREADY_FRIENDS);
	case OUTGOING_PENDING -> throw new ApiException(FriendErrorCode.FRIEND_REQUEST_ALREADY_PENDING);
	case INCOMING_PENDING -> { /* 기존 승격 + 수락 알림 */ }
	case SELF -> throw new IllegalStateException("unreachable"); // self 는 앞에서 9400
}
```

### D-3. enum 이름과 위치: `friend/dto/FriendRelation.java`

PRD 클래스 다이어그램의 "이름은 스펙에서 확정"을 `FriendRelation`으로 확정한다. 위치는 PRD
변경 파일 목록대로 `friend/dto`다. 응답 계약에 실리는 값 집합이고, 영속 상태 enum
`FriendshipStatus`(entity)와 관심사가 다르다 (저장 상태 2값 대 응답 관점 5값).

### D-4. SELF는 쌍 조회 전에 가른다

`findByCode` 결과의 id가 조회자와 같으면 쌍 조회 없이 SELF를 돌려준다. 자기 쌍 행은 존재할
수 없어 조회가 무의미하고, request의 기존 순서(9404 → 9400 → 쌍 판정)와도 같은 순서가 된다
(PRD 시퀀스 다이어그램 그대로).

## 도메인 로직

preview의 판정 흐름 (request와 같은 순서, glossary 용어 기준):

1. 코드로 사용자 조회 (`findByFriendCode`). 없으면 9404 (기존 그대로).
2. 코드 주인이 나면 `SELF` (D-4). 쌍 조회 생략.
3. `findPairWithoutLock`으로 쌍 행 조회 (D-1) 후 `FriendRelation.of`로 판정 (D-2):
   행 없음 → `NONE`, ACCEPTED → `FRIENDS`, PENDING이고 내가 requester → `OUTGOING_PENDING`,
   PENDING이고 상대가 requester → `INCOMING_PENDING`.
4. `FriendPreviewResponseDto(nickname, relation)` 반환.

판정은 조회 시점 실시간이다 (FR-10). 캐시나 비정규화 없음: 친구 삭제 즉시 다음 미리보기는
NONE이다. 미리보기는 힌트이고 최종 판정은 요청 API가 그 시점 기준으로 다시 한다 (FR-9,
미리보기와 요청 사이에 관계가 바뀔 수 있다).

## 테스트 시나리오

새 테스트에는 `// 검증: FR-FRIEND-14` 주석을 단다. 통합 테스트는 기존
`FriendIntegrationTest`(실 DB, `@Transactional` 롤백 격리) 패턴에 추가한다.

관계 판정 5종 (FR-1~FR-6):

- `내_코드_미리보기는_SELF를_준다`: Given 나. When 내 코드 preview. Then relation SELF, nickname은 내 닉네임.
- `관계_없는_상대의_미리보기는_NONE을_준다`
- `내가_요청을_보낸_상대의_미리보기는_OUTGOING_PENDING을_준다`: Given 나 → 상대 PENDING.
- `상대가_요청을_보낸_코드의_미리보기는_INCOMING_PENDING을_준다`: Given 상대 → 나 PENDING.
- `이미_친구인_상대의_미리보기는_FRIENDS를_준다`: Given ACCEPTED 쌍 (방향 무관: 양방향 각 1건씩 검증하면 더 좋다).

계약 유지 (FR-7~FR-9):

- `없는_코드_미리보기는_9404를_반환한다`: 기존 테스트를 새 시그니처로 갱신만 한다 (검증 주석은 FR-FRIEND-02 유지 + FR-FRIEND-14 병기).
- `코드로_상대_닉네임을_미리본다`: 기존 테스트 시그니처 갱신, nickname 유지 확인 (FR-8).
- 기존 request 테스트 전부 green (FR-9 회귀 가드, `FriendRelation.of` 소비 리팩터링의 안전망).

정합 (FR-10):

- `FRIENDS_미리보기_직후_관계_변동_없이_요청하면_9409다`: Given ACCEPTED 쌍. When preview 후 request. Then preview는 FRIENDS, request는 9409.

직렬화 (컨트롤러 계층):

- 기존 `FriendControllerTest` 방식으로 `relation`이 문자열(예: `"NONE"`)로 실리는 것 1건.

무잠금 성질에 관한 주의: `@Transactional` 테스트는 서비스 트랜잭션이 테스트 트랜잭션에
참여해 readOnly가 실효되지 않으므로, "readOnly에서 FOR UPDATE 거부" 자체는 테스트로 재현되지
않는다. 무잠금 보장의 가드는 신설 쿼리에 `@Lock`이 없다는 코드 사실이고, 리뷰에서 확인한다.

[^1]: advisory 조회: 화면을 미리 맞추기 위한 참고용 조회. 최종 판정 권한이 없고, 실제 검증은 요청 API가 그 시점 기준으로 다시 수행한다 (MSG-185 결정, 이번에 "관계 상태 동봉"으로 일부 확장).
[^2]: additive 계약 변경: 기존 필드를 그대로 두고 새 필드만 더하는 응답 변경. 새 필드를 모르는 기존 클라이언트는 그 필드를 무시하므로 하위 호환이 유지된다.
[^3]: 자동 수락: 상대가 나에게 보낸 요청이 대기 중일 때 내가 요청을 보내면 새 행을 만들지 않고 기존 행을 ACCEPTED로 승격시키는 규칙 (FR-FRIEND-03). "동일 쌍 최대 1행" 불변식을 지키는 장치다.
[^4]: 비관적 쓰기 잠금(PESSIMISTIC_WRITE): 조회한 행을 트랜잭션이 끝날 때까지 다른 쓰기가 못 건드리게 잠그는 방식. SQL로는 SELECT FOR UPDATE로 나간다.
[^5]: 읽기 전용 트랜잭션(readOnly): 조회만 한다고 선언한 트랜잭션. PostgreSQL은 이 안에서 FOR UPDATE 계열 잠금 자체를 거부하므로 잠금 조회를 재사용할 수 없다 (MSG-186 실측).
