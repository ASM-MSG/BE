# MSG-417: 운영 조치로 영상이 가려지면 주인에게 알림 보내기

**Owner**: B (video, moderation, notification 전부 Owner B 패키지. 계약 인터페이스 무변경)

> 요구사항 정본: `docs/prd/MSG-417-prd.md` (상태 검토됨, 2026-08-18 성민 승인) · SRS FR-NOTI-15
>
> **선행 전제: MSG-416 머지.** 이 티켓의 DB 변경은 MSG-416의
> `V35__notification_category_friend_moderation.sql`이 이미 동봉했다(notifications CHECK 7종에
> MODERATION 포함, opt_outs CHECK 6종에서 MODERATION 의도적 제외). 따라서 이 티켓에는
> 마이그레이션이 없고, MSG-416이 develop에 먼저 머지된 뒤에만 구현을 시작한다.

## 개요

영상이 블라인드[^1]되면 소유자에게 아무 통지가 없어, 영상이 사라진 이유를 서비스 오류로
오해하기 쉽다. 블라인드 전환과 해제 시점에 소유자에게 푸시 알림을 남긴다. 알림은 신설
MODERATION 카테고리로 분류되고 수신 거부가 불가능하다(설정 화면 비노출, PRD FR-7 확정).
신고자에 대한 통지는 이번에도 만들지 않는다(FR-MOD-14 유지).

## 배경 · 목표

- 제재를 통지 없이 적용하는 것은 신뢰 문제다. 조치 사실을 소유자가 즉시 알게 해서 몰래
  사라지는 경험을 없앤다(PRD 1절).
- 기록 지점은 `VideoModerationServiceImpl` 한 곳이다. 신고 승인(`AdminReportServiceImpl`)과
  운영 직접 조치가 모두 이 서비스의 `blind()`를 지나므로 두 트리거가 자동으로 같은 알림이
  된다(PRD FR-1).

### PRD 미해결이었던 2건의 확정 (2026-08-18 성민)

- **해제 복구 알림은 포함한다.** FR-3는 PRD에서 Must로 승격됐다(2026-08-18 성민 확정, PRD와
  SRS FR-NOTI-15 문안 갱신 완료). 기록 지점(`unblind()`)과 파이프라인은 블라인드 알림과
  완전히 공유된다.
- **문의 채널 안내는 문구에 넣지 않는다(비목표, 같은 날 확정).** 안내할 기능(문의 채널) 자체가
  제품에 없다. 채널이 생기면 문구 상수 교체로 끝나는 후속이다.

## 성공 기준

1. 영상이 블라인드로 전환되면 소유자의 notifications에 MODERATION 카테고리 행이 1건 남고,
   기존 파이프라인(릴레이, Kafka, FCM)을 타고 발송된다.
2. 블라인드가 해제되면 복구 알림이 같은 경로로 1건 남는다.
3. 알림 문구 어디에도 신고 사유, 신고자 정보, 신고 존재 여부가 없다.
4. 전이가 실패(3404, 3409)하면 알림 행도 남지 않는다.
5. 해제 후 재블라인드는 새 알림 행이 된다(event_key가 다르다).
6. 알림 설정 조회 응답에 MODERATION이 나타나지 않고, MODERATION 토글 요청은 10420으로
   거부되며, springdoc 생성 스키마의 카테고리 허용값에도 MODERATION이 없다.
7. 신고자에게는 어떤 기록도 발송도 없다.

## API 명세

신규 API 없음. 기존 알림 설정 API 2종의 표면만 달라진다.

| API | 변경 |
|-----|------|
| `GET /api/notifications/preferences` | 응답 preferences 목록에 MODERATION 미포함. 목록은 FRIEND까지 6종이다(MSG-416이 5종에서 6종으로 확장 중이므로 이 티켓의 기준 표면은 6종) |
| `PATCH /api/notifications/preferences/{category}` | `category=MODERATION`(대소문자 무시)은 존재하지 않는 값과 동일하게 10420 INVALID_CATEGORY. 에러 메시지의 카테고리 나열도 6종 기준(MODERATION 미포함) |

Swagger 문구(컨트롤러 `@Operation` 2곳, `NotificationPreferenceResponseDto`의 `@Schema`)의
"5종" 나열을 6종으로 고치는 것은 MSG-416 몫이다. 이 티켓은 그 위에 "MODERATION은 설정
대상이 아니라 목록에 없다"는 한 문장만 얹는다. 충돌 방지를 위해 MSG-416 머지 후 그 문구를
기준으로 작업한다.

## 도메인 로직

### 1. 기록 지점: `VideoModerationServiceImpl`

`blind()`와 `unblind()` 각각의 끝(상태 전이와 파생 정리가 끝난 뒤)에서
`NotificationCommandService.record()`를 호출한다.

- **원자성(FR-4)**: `record`는 전파 REQUIRED[^2]라 `@Transactional`인 전이 트랜잭션에
  참여한다. 전이가 롤백되면 알림도 남지 않는다. `VideoStatusWriter`의 MSG-313 선례와 같은
  구조다.
- **소유자 식별**: `blind()`가 이미 video 행을 잠금 로드하므로 `video.getUserId()`로 확보돼
  있다. 추가 조회 없음.
- **가드 뒤 호출이라 실패 경로에 알림이 없다**: 삭제된 영상(3404)과 이미 목표 상태인
  영상(3409)은 record 앞의 기존 가드에서 예외로 나간다.
- **신고자 무통지(FR-6)**: record 호출의 수신자 인자는 `video.getUserId()` 하나뿐이다.
  신고자(Report.reporterId)는 이 서비스에 아예 들어오지 않는다.

### 2. 잠금 순서: 소유자 users KEY SHARE를 videos 잠금보다 먼저 (데드락 방지)

`notifications.user_id`는 `users(id)` FK(ON DELETE CASCADE, V21)라 record의 INSERT가 users
행 KEY SHARE 잠금[^3]을 요구한다. 전이 트랜잭션이 videos 행 잠금을 잡은 채 record에
도달하면 잠금 순서가 videos → users가 되는데, 소유자 계정 삭제 트랜잭션은 users 배타 잠금을
잡고 videos CASCADE 삭제를 대기하므로(users → videos) 교차 대기 사이클이 되어 PostgreSQL이
한쪽을 abort시킨다. 선례가 정확히 이 경로용으로 존재한다:
`VideoStatusWriter.lockUploaderFirst`(MSG-313 Codex 2R) + `UserRepository.findIdForKeyShare`.

잠금 순서는 메서드가 아니라 트랜잭션 단위이므로 적용 지점이 2곳이다.

- **`blind()`/`unblind()` 서두**: 선례 그대로 무잠금 선독(`VideoRepository.findUserIdById`,
  user_id는 불변 컬럼)으로 userId를 얻고 `findIdForKeyShare`로 users를 먼저 잡은 뒤에 기존
  `findWithLockById`를 호출한다. 선취 실패(영상 행 부재, 또는 유저 부재 = 탈퇴 진행)는 배경
  태스크인 선례의 조용한 스킵과 달리 관리자 API이므로 기존 3404(VIDEO_NOT_FOUND)로 던진다.
  "삭제는 없음으로 취급"하는 기존 D3 가드와 같은 결이다.
- **`AdminReportServiceImpl.approve()`** (신고 승인, 62행): 이 메서드는 `blind()` 호출(78행)
  전에 자기 트랜잭션에서 `findWithLockById`(70행)로 videos 잠금을 먼저 잡는다. `blind()` 내부
  선취만으로는 이 경로의 순서가 여전히 videos → users이므로, 같은 선취를 그 잠금 앞에 둔다.
  `unblindVideo()`는 선행 잠금 없이 `unblind()`에 위임만 하므로 내부 선취로 충분하다.

신규 리포지토리 메서드는 없다. `findUserIdById`와 `findIdForKeyShare` 둘 다 MSG-313이 만들어
둔 것을 재사용한다.

### 3. event_key 설계 (FR-5)

```text
블라인드: MODERATION:BLIND:{videoId}:{uuid}
해제:     MODERATION:UNBLIND:{videoId}:{uuid}
```

`uuid`는 record 직전에 만드는 무작위 UUID(`UUID.randomUUID()`) 36자다. `VideoStatusWriter`가
event_key 꼬리에 시도 식별자(attemptUuid)를 붙이는 선례와 같은 형태다. 폭 검산: 접두
`MODERATION:UNBLIND:` 19자 + videoId 최대 19자 + `:` 1자 + UUID 36자 = 최대 75자로
`event_key VARCHAR(100)` 안이다.

- **왜 videoId만으로는 안 되나**: dedupe[^4] 수단이 `(user_id, event_key)` UNIQUE + DO
  NOTHING이라, 키가 `MODERATION:BLIND:{videoId}` 고정이면 해제 후 재블라인드가 기존 행에
  먹혀 새 알림이 안 간다(FR-5 전반부 위반). 전이 인스턴스를 구분하는 꼬리가 필요하다.
- **왜 전이 시각(epochMilli)이 아닌가**: 시각 꼬리는 고정 Clock 테스트에서 블라인드, 해제,
  재블라인드가 같은 밀리초에 떨어지는 순간 두 번째 블라인드의 record가 DO NOTHING에 삼켜져
  FR-5 위반이 결정론적으로 재현된다(Codex 재리뷰 적발). 무작위 UUID는 시계와 무관해 이
  함정이 없고, 시각 제어 없이도 테스트가 그대로 성립한다.
- **꼬리가 무작위라 키가 매번 달라도 같은 전이가 중복 기록되지 않는 근거**: (a) 전이
  트랜잭션이 롤백되면 record도 함께 롤백된다(원자성). (b) 커밋된 뒤의 같은 요청 재시도는
  3409 가드가 record 앞에서 끊는다. (c) 발송 단계의 Kafka 재전달은 컨슈머의 종결 상태
  가드(기존 MSG-179 FR-6 2차)가 막는다. 즉 같은 전이가 record를 두 번 타는 경로 자체가
  없고, UNIQUE는 최후 보험이다.

이 티켓에는 시각 사용처가 없으므로 Clock 주입도 없다. 엔티티 전이 메서드(`markBlinded()` 등)
내부의 시각 기록은 기존 코드 그대로다(`LocalDateTime.now(ZoneOffset.UTC)`, MSG-376 컨벤션).

### 4. 문구 (FR-2)

| 전이 | title | body |
|------|-------|------|
| 블라인드 | 영상이 가려졌어요 | 올린 영상이 운영 정책에 따라 가려졌어요. 지금은 다른 사람에게 보이지 않아요 |
| 해제 | 영상 숨김이 풀렸어요 | 가려졌던 영상이 원래 상태로 돌아왔어요 |

- 신고 사유, 신고자 정보, 신고 존재 여부를 싣지 않는다. "운영 정책에 따라"는 신고의 존재를
  암시하지 않는다. 영상 처리 실패 알림이 탈락 사유를 싣지 않는 것과 같은 결이다(FR-NOTI-10).
- **해제 문구에 "공개"라는 말을 쓰지 않는다.** `unblind()`는 status만 ACTIVE로 되돌리고
  `videos.visibility`(PUBLIC·FRIENDS·PRIVATE)는 보존하므로, PRIVATE 영상은 해제돼도 남에게
  보이지 않는다. "다시 공개됐어요"는 이 경우 거짓 안내가 된다(Codex 재리뷰 적발). "원래
  상태로 돌아왔어요"는 원래 공개범위 그대로라는 뜻이라 세 값 모두에서 참이다.
- 어떤 영상인지의 특정(딥링크, 썸네일)은 이번 범위 밖이다. `record` 시그니처가 title과 body
  문자열만 받고, 같은 제약의 VIDEO 카테고리(처리 결과 통지)도 "올린 영상"으로만 가리키는
  기존 표면과 동일하다.

### 5. 수신 거부 불가 가드 (FR-7)

DB 1차 가드는 MSG-416 V35가 이미 세웠다. opt_outs CHECK에 MODERATION이 없어 옵트아웃[^5]
행 자체가 생길 수 없다. 이 티켓은 애플리케이션 2차 가드를 만든다.

| 지점 | 변경 | 이유 |
|------|------|------|
| `NotificationCategory` | MODERATION 추가, 주석의 CHECK 목록을 7종으로 갱신 | enum에 넣는 순간 아래 세 표면이 자동으로 오염되므로 가드가 같은 커밋에 함께 가야 한다 |
| `NotificationPreferenceServiceImpl.currentPreferences()` | `values()` 순회에서 MODERATION을 제외(filter 한 줄) | 61행의 전 카테고리 순회 때문에 enum 추가만으로 getPreferences 응답에 자동 노출된다 |
| `NotificationPreferenceServiceImpl.parseCategory()` | 파싱 결과가 MODERATION이면 `INVALID_CATEGORY` throw | 열거형 파싱이라 PATCH가 MODERATION을 받아버린다. 존재하지 않는 값과 동일 취급이 설정 표면에서 카테고리의 존재 자체를 숨긴다 |
| `NotificationErrorCode.INVALID_CATEGORY` | 메시지 나열을 6종 기준으로(MODERATION 미포함) | 에러 메시지가 곧 허용 값 문서다 |
| `NotificationPreferenceResponseDto.CategoryPreferenceDto.category` | 필드 `@Schema`에 `allowableValues` 6종 명시 | 필드 타입이 `NotificationCategory` enum 그대로라(24행) 런타임 필터와 무관하게 springdoc 생성 스키마의 허용값 목록에 MODERATION이 노출된다. 이 DTO는 이미 필드 단위 `@Schema`로 문서를 다는 스타일이라 어노테이션 한 줄이 최소 변경이다. 설정 전용 enum 분리는 값 목록 하나를 위한 타입 신설이라 과하다. 구현 시 `/v3/api-docs` 생성 결과에서 허용값 6종을 실측 확인한다(enum이 공유 컴포넌트 스키마로 빠지면 제약이 안 먹을 수 있는 springdoc 특성 대비) |
| `NotificationConsumer.rateLimited()` | `case MODERATION -> null` 추가(무제한) | switch가 default 없는 전수 분기라 enum 추가 시 컴파일이 깨진다. 무제한 근거: 제재 통지는 희소하고 사용자 행동에 직결된다. FR-NOTI-07의 뱃지 획득과 같은 결 |

`NotificationPreferenceService.isEnabled()`는 무변경이다. opt_outs에 MODERATION 행이 생길
경로가 없으므로(CHECK + PATCH 가드) 항상 true가 나온다. "끌 수 없음"이 별도 분기 없이
성립한다.

## 데이터 모델

- 엔티티 변경 없음, Flyway 마이그레이션 없음.
- notifications CHECK 7종(MODERATION 포함)과 opt_outs CHECK 6종(MODERATION 제외)은 MSG-416의
  `V35__notification_category_friend_moderation.sql`이 동봉했다. **MSG-416 선행 머지가 이

- `category VARCHAR(10)`에 'MODERATION'은 정확히 10자라 통과한다(MSG-416 스펙에서 검산 완료).

## 운영 고려: 코드 롤백 게이트

이 티켓은 MODERATION enum 값과 기록 코드(writer)를 함께 배포한다. 배포 후 MODERATION 알림
행이 쌓인 상태에서 코드만 MSG-416 시점으로 롤백하면, 구 enum(6종)이 그 행의 category를
하이드레이션하지 못해 릴레이와 컨슈머가 잔여 행을 읽을 때마다 반복 실패한다. DB의 V35
CHECK는 7종이라 행 자체는 합법이고, 문제는 코드 쪽 enum 폭이다.

- **롤백 게이트 (필수)**: MSG-417 코드를 롤백하기 전에 MODERATION 카테고리의 PENDING·
  PUBLISHED 행이 전부 소진(drain)됐는지 확인한다. 잔여가 있으면 SENT 종결을 기다리거나
  수동으로 종결 처리한 뒤에만 롤백한다.
- **reader 선행 편입(MSG-416에 enum 값만 먼저 넣는 대안)은 기각**: 두 티켓이 같은 브랜치
  흐름에서 연속 구현·배포되어 노출 창이 극소이고, 편입하면 MSG-416이 자기 범위 밖 가드
  (rateLimited 분기, 설정 표면 제외)까지 떠안게 된다.

[^1]: 블라인드: 운영 조치로 영상을 타인에게 숨기는 상태. 삭제와 달리 점령과 영상 수에는 영향이 없고 해제로 되돌릴 수 있다. 상태 전이는 `VideoModerationServiceImpl`(MSG-193)이 전담한다.
[^2]: 전파 REQUIRED: 스프링 트랜잭션 전파 방식 중 하나로, 이미 열린 트랜잭션이 있으면 새로 만들지 않고 거기 합류한다. 합류한 작업은 바깥 트랜잭션과 함께 커밋되거나 함께 롤백되므로 원자성이 구조로 보장된다.
[^3]: KEY SHARE: PostgreSQL 행 잠금 중 가장 약한 공유 잠금. FK 검사가 참조되는 부모 행에 자동으로 거는 종류로, 부모 행의 삭제와 키 변경만 막고 다른 읽기와는 공존한다. 탈퇴 트랜잭션의 배타 잠금과는 충돌하므로 획득 순서가 어긋나면 데드락 재료가 된다.
[^4]: dedupe(중복 제거): 같은 이벤트가 여러 번 기록 요청돼도 알림 행은 하나만 남게 하는 장치. 이 프로젝트는 notifications의 `(user_id, event_key)` UNIQUE 제약과 INSERT 시 DO NOTHING(충돌 시 조용히 무시)으로 구현한다.
[^5]: 옵트아웃(opt-out): 기본은 수신이고 사용자가 끈 것만 행으로 저장하는 방식. 행이 없으면 켜짐으로 합성되므로, MODERATION처럼 행이 생길 수 없는 카테고리는 자동으로 항상 켜짐이 된다.
