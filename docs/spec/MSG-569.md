# MSG-569: 사용자 차단 (차단, 해제, 목록과 콘텐츠 상호 비노출)

**Owner**: B (콘텐츠와 인증 도메인. 신규 코드는 `com.msg.fillmap.user.*`, 변경은 `friend`, `video`, `event` 패키지)

> 요구사항 정본: `docs/prd/MSG-569-prd.md` (검토됨, 2026-09-08 사용자 승인, 미해결 질문 0) FR-1~13과 비기능
> SRS: FR-MOD-15, FR-MOD-16, FR-MOD-17, FR-MOD-18, FR-MOD-20 (FR-MOD-19 는 폐기, `docs/srs.md` MOD 절)
> 모바일 화면은 MSG-570, 에픽 MSG-174

## 개요

로그인 사용자가 다른 사용자를 차단하고 해제하고 자기가 차단한 목록을 보는 API 3종을 만들고, 차단 관계에
있는 두 사용자가 요청자를 아는 조회 경로 6종(격자 전역 영상 목록, 미션 영상 목록, 영상 재생, 행사 위치
영상 목록, 행사 영상 상세, 행사 영상 댓글 목록)에서 서로의 영상과 댓글을 보지 못하게 한다. 앱이 차단
대상을 지정할 수 있도록 영상 응답 4종에 작성자 사용자 식별자를 추가한다. 저장은 `friendships`의 BLOCKED
상태가 아니라 신규 테이블 `user_blocks`다.

범위 밖(PRD 비목표): 요청자를 받지 않는 전역 경로의 필터(격자 대표 영상, `/api/regions/explore`, 핫구역,
격자와 행사 위치의 영상 개수), 관리자 블랙리스트, 차단 사유, 차단 알림, 화면, 차단 관계에서의 친구 요청
거부. 신고는 차단과 무관하게 계속 된다.

## 배경 · 목표

- 애플 앱스토어 심사 지침 1.2 와 구글 플레이 사용자 생성 콘텐츠 정책이 신고와 함께 차단 수단을 요구한다.
  지금 서버에는 신고(MSG-192, 195)만 있고 차단은 MSG-194 에서 "MVP 범위 제외"로 닫혀 있었다. 스토어
  출시 요건이라 그 결정을 번복한다(SRS FR-FRIEND-13 단서).
- 영상 응답이 작성자를 닉네임으로만 내려주고 있어(MSG-371) 앱이 "이 영상의 작성자를 차단"이라는 요청을
  보낼 식별자가 없다. 식별자를 함께 싣는다.
- 목표는 MSG-570(앱 화면)이 이 API만으로 차단 흐름 3곳(메뉴, 확인, 목록과 해제)을 붙일 수 있는 것이다.

## 성공 기준

아래가 전부 테스트로 관찰되면 완료다. 검증 테스트 마커는 `// 검증: FR-MOD-NN, AC-569-NN`이다.

- AC-569-01: `POST /api/users/{userId}/block`에서 경로의 userId 가 요청자 본인이면 400 에 developCode 1430 이고, 존재하지 않는 사용자면 404 에 1404 이며, 정상이면 200 에 `user_blocks` 행이 한 건 생긴다.
- AC-569-02: 이미 차단한 사용자를 다시 차단해도 200 이고 행은 한 건이며 `created_at`은 처음 값 그대로다. 같은 두 사용자의 차단 요청이 서로 다른 트랜잭션으로 동시에 들어와도(스레드 2개) 둘 다 200 이고 행은 한 건이다.
- AC-569-03: `DELETE /api/users/{userId}/block`은 차단 행이 있으면 지우고 200, 없으면(차단한 적 없음이든 존재하지 않는 userId 든) 아무것도 지우지 않고 200 이다.
- AC-569-04: `GET /api/users/me/blocks`는 내가 걸은 차단 전부를 `blockedAt` 내림차순으로 페이지 없이 주고, 항목은 `userId`, `nickname`, `profileImageUrl`(없으면 null), `blockedAt`이다. 나를 차단한 사람은 목록에 없다. 차단이 없으면 빈 배열이다.
- AC-569-05: A 가 B 를 차단하면 같은 트랜잭션에서 A 와 B 사이의 `friendships` 행이 상태(ACCEPTED, PENDING)와 방향에 무관하게 삭제된다. 해제해도 행은 되살아나지 않는다.
- AC-569-06: A 가 B 를 차단한 뒤 A 로 격자 전역 영상 목록(`GET /api/grids/{gridId}/videos`)과 미션 영상 목록(`GET /api/missions/{missionId}/videos`)을 조회하면 B 의 영상이 빠지고, B 로 조회하면 A 의 영상이 빠진다. 빠진 행은 페이지 크기를 소비하지 않는다(size 만큼의 다른 영상이 채워진다).
- AC-569-07: 비로그인(viewer null) 조회는 차단 행이 있어도 지금과 같은 결과다.
- AC-569-08: 차단 관계에 있는 사용자의 영상을 `GET /api/videos/{videoId}`로 요청하면 404 에 developCode 3404 이고 응답 본문이 삭제된 영상의 404 와 같다. 재생 URL 발급과 조회수 증가가 일어나지 않는다. 판정은 방향 무관이다.
- AC-569-09: 차단 관계에 있는 사용자의 행사 영상은 행사 위치 영상 목록에서 빠지고, `GET /api/event-videos/{videoId}`는 404 에 13406 이며 조회수가 늘지 않는다. 판정은 방향 무관이다.
- AC-569-10: 차단 관계에 있는 사용자의 댓글은 `GET /api/event-videos/{videoId}/comments`와 상세 응답에 품긴 댓글 첫 페이지에서 빠진다. 빠진 댓글은 페이지 크기를 소비하지 않는다.
- AC-569-11: 차단한 사용자의 영상을 신고하는 요청은 차단 전과 같은 응답이다(차단이 신고를 막지 않는다).
- AC-569-12: 격자 전역 영상 목록 항목과 재생 응답에 `userId`, 행사 위치 영상 목록 항목과 행사 영상 상세에 `uploaderId`가 실리고 값은 `videos.user_id`다. 기존 `nickname`, `uploaderNickname` 필드는 그대로다. 댓글 응답은 변경이 없다.
- AC-569-13: 역방향 차단 행이 없을 때 차단을 해제하면 다음 요청부터 6종 경로 전부에서 상대 콘텐츠가 다시 보인다(캐시 없음).
- AC-569-14: 사용자를 삭제하면 그 사용자가 걸었거나 당한 `user_blocks` 행이 함께 사라진다(DB CASCADE, 애플리케이션 코드 없음).
- AC-569-15: 차단, 해제, 목록 3경로는 토큰 없이 부르면 401 이고 요청자 식별은 토큰에서만 온다. 경로나 본문으로 요청자를 바꿀 수 없다.
- AC-569-16: 차단 절이 붙은 4개 native 목록 쿼리의 실행 계획에서 `videos` 접근 경로가 기존(idx_videos_grid_popular, mission_grids PK 선두)과 같고 `user_blocks`는 인덱스로만 접근된다(작업 로그에 EXPLAIN 실측을 남긴다).
- AC-569-17: 차단 관계(어느 방향이든)에 있는 작성자의 행사 영상에 대해 댓글 목록 조회, 댓글 작성, 수정, 삭제, 도움돼요 추가, 취소는 전부 상세와 같은 404 에 13406 이다.
- AC-569-18: A→B 와 B→A 차단이 둘 다 있을 때 A 가 해제해도 B→A 행이 남아 A 와 B 는 6종 경로 전부에서 서로의 콘텐츠를 계속 보지 못한다.

## API 명세

### 신규 3종 (`UserBlockController`, `@RequestMapping("/api/users")`)

경로 변수는 `{userId:[0-9]+}`로 숫자를 못박는다. `/api/users/me/...` 형제 경로가 있어 제약이 없으면
`me`가 userId 자리에 잡혀 형 변환 400 으로 떨어진다(의미 없는 실패 모양을 미리 막는다).

| method | path | 요청 | 응답 | 실패 |
|---|---|---|---|---|
| POST | `/api/users/{userId}/block` | 본문 없음. 요청자는 `@AuthenticationPrincipal AuthPrincipal` | `SuccessResponse<Void>` (data null) | 본인 1430, 없는 사용자 1404, 미인증 401 |
| DELETE | `/api/users/{userId}/block` | 본문 없음 | `SuccessResponse<Void>` | 미인증 401 (그 외 실패 없음, 멱등) |
| GET | `/api/users/me/blocks` | 없음 | `SuccessResponse<List<BlockedUserResponseDto>>` | 미인증 401 |

```java
@Schema(description = "내가 차단한 사용자 목록 항목",
	requiredProperties = {"userId", "nickname", "profileImageUrl", "blockedAt"})  // 가드 ResponseSchemaNullabilityTest: 응답 DTO 필드는 전부 required, null 은 nullable=true 로
public record BlockedUserResponseDto(
	@Schema(description = "차단한 사용자 ID. 해제(DELETE /api/users/{userId}/block)의 경로 값", example = "42")
	Long userId,
	@Schema(description = "닉네임 원문(조회 시점 값, 사본 아님)", example = "busan.vlog")
	String nickname,
	@Schema(description = "프로필 이미지 URL. 없으면 null", nullable = true)
	String profileImageUrl,
	@Schema(description = "차단 시각(최초 차단 시각, 재차단해도 바뀌지 않는다)", example = "2026-09-08T03:10:00Z")
	LocalDateTime blockedAt
) {
}
```

`UserErrorCode`에 한 상수를 더한다. 새 패키지를 만들지 않고 `user` 아래 두므로 `response-pattern.md`
대역 표 갱신은 없다(1xxx 그대로).

```java
// 사용자 차단 (MSG-569 FR-1). 없는 사용자는 1404 를 그대로 쓴다(식별자가 영상 응답에 노출되므로 은닉 대상이 아니다).
SELF_BLOCK(1430, HttpStatus.BAD_REQUEST, "자기 자신은 차단할 수 없습니다"),
```

`authenticated()` 매처는 세그먼트 하나만 매치해 `/api/users/me/blocks`를 덮지 않는다. ORG 계정이
403 이 되는 것은 MSG-496 FR-5(행사 운영자 권한은 콘솔에만)와 같은 결과라 의도된 동작이다.

## 도메인 로직

용어는 `glossary.md`를 따른다. "차단"은 이 문서에서 `user_blocks` 행이 있는 상태를 뜻하고, 사용자 대면
문구도 "차단"이다(친구 도메인의 "삭제"와 구분).

### D-1. 저장 위치와 패키지: `user` 패키지, `user_blocks` 테이블

- `friendships.status = BLOCKED`를 쓰지 않는다. V19 유니크 인덱스 `uq_friendships_pair`가 방향 무관
  쌍을 1행으로 묶어 "친구이면서 차단"을 담을 수 없고, 차단은 방향이 있는 관계(A→B 와 B→A 가 별개
  행)라 대칭 쌍 모델과 맞지 않는다(PRD 데이터 정합).
- 새 코드는 `com.msg.fillmap.user` 아래 둔다. 경로가 `/api/users` 아래고 에러 코드가 1xxx 대역을 그대로
  써서 `response-pattern.md` 대역 표에 행을 먼저 넣는 선행 커밋이 필요 없다. `block` 패키지를 따로 파면
  대역 배정 커밋과 status.md 패키지 행이 늘 뿐 얻는 게 없다.
- 엔티티는 컨벤션 "영속 계층" 절이 신규 코드에 요구하는 LAZY 단방향 연관으로 짠다(id 보관은 기존
  엔티티에만 허용된 잔존이라 `Friendship`을 신규 코드의 근거로 쓰지 않는다. Codex 2R 반영):
  `@EmbeddedId UserBlockId(blockerId, blockedId)` +
  `@MapsId("blockerId") @ManyToOne(fetch = FetchType.LAZY) User blocker` +
  `@MapsId("blockedId") @ManyToOne(fetch = FetchType.LAZY) User blocked` + `createdAt`.
  `User`는 타 도메인 엔티티라 읽기 전용 참조다. equals, hashCode, toString 은 `id`(UserBlockId)만 쓰고
  연관 필드 둘을 제외한다(프록시 초기화와 순환 참조 방지). JPQL 에서 `b.blocker.id`는 FK 컬럼 직접
  참조라 조인이 생기지 않으며 D-4 의 `b.id.blockerId`와 같은 컬럼이다.

### D-2. 멱등[^1] 저장: `ON CONFLICT DO NOTHING` native 한 문장

두 안을 비교했다.

| | ON CONFLICT DO NOTHING (채택) | 유니크 제약 + 예외 흡수 |
|---|---|---|
| 문장 수 | INSERT 1 | INSERT 1 + 실패 시 예외 처리 |
| 같은 트랜잭션의 후속 작업 | 영향 없음 | 제약 위반이 나면 PostgreSQL 이 그 트랜잭션을 abort 상태로 만들어 이어지는 친구 관계 삭제(D-3)가 실패한다. 살리려면 `REQUIRES_NEW` 로 저장을 떼어내야 한다 |
| 동시 요청 | 늦은 쪽이 0행으로 성공 | 늦은 쪽이 예외, 흡수 코드 필요 |
| 선례 | `VideoRepository.upsertGrid`, `upsertUserGrid` | 없음 |

차단과 친구 삭제가 한 트랜잭션이어야 한다(FR-MOD-16)는 요구 때문에 예외 흡수 안은 트랜잭션 분리를
부르고, 그 순간 "차단만 남고 친구가 남는 중간 상태 없음"이 깨진다. `ON CONFLICT`는 PostgreSQL 전용
기능이라 컨벤션이 native 를 허용하는 범주다.

```sql
INSERT INTO user_blocks (blocker_id, blocked_id, created_at)
VALUES (:blockerId, :blockedId, :createdAt)
ON CONFLICT (blocker_id, blocked_id) DO NOTHING
```

`created_at`은 서비스가 주입받은 `Clock`으로 만든 `LocalDateTime.now(clock)`을 넘긴다(UTC 관례,
MSG-376. `statement_timestamp() AT TIME ZONE 'UTC'` 선례도 있지만 Clock 쪽이 테스트에서 시각을
고정할 수 있다). 재차단은 DO NOTHING 이라 최초 차단 시각이 유지된다(AC-02).

### D-3. 차단 흐름 (`UserBlockService.block`, `@Transactional`)

1. `userId.equals(targetId)` 이면 1430.
2. `userRepository.findIdForKeyShare(targetId)`가 비면 1404. 존재 확인과 잠금을 한 문장으로 한다.
   `existsById` 뒤 INSERT 사이에 탈퇴가 끼면 FK 위반 500 이 되는데, KEY SHARE[^2]를 잡아 두면 탈퇴

   사용자에게 보이는 결함이 아니고, 친구 요청 경로(`FriendServiceImpl.request` 122행
   `findIdForKeyShare(target.getId())`)도 대상만 잠그고 요청자 본인은 잠그지 않는 같은 선례다.
3. D-2 의 upsert.
4. `friendService.deleteRelationsBetween(userId, targetId)`: 아래 JPQL 벌크 삭제 한 문장. 상태를 보지
   않으므로 ACCEPTED 와 PENDING(어느 방향이든)이 함께 지워진다. 0행이어도 성공이다.

잠금 순서는 기존 경로와 같다: users(KEY SHARE) → friendships. 친구 요청(`FriendServiceImpl.request`)도
users KEY SHARE 다음 friendships FOR UPDATE 이고, 탈퇴 CASCADE 는 users 배타 다음 자식이라 교착이 생길
조합이 없다. 친구 요청과 차단이 겹쳐 차단의 벌크 삭제 뒤에 PENDING 이 새로 들어오는 경우는 허용한다
(차단 관계에서의 요청 거부는 범위 밖, FR-MOD-19 폐기).

같은 이유로 **재친구 우회도 허용한다**(Codex 1R P2, 미채택). 차단 뒤 B 가 A 의 친구 코드로 다시 요청하고

남아 있어도 콘텐츠가 보인다. 그대로 두는 근거는 둘이다. 재친구는 차단한 쪽(A)이 상대 요청을 직접 수락해야만
성립하므로 차단자 의사 없이는 생기지 않고, 사용자가 2026-09-08 "친구 축은 이번에 건드리지 않는다"고
확정해 FR-MOD-19 를 폐기했다. 후속은 미해결 질문 2 다.

`FriendService`에 메서드를 더하는 이유는 `friendships`의 소유 도메인이 friend 이고 "타 도메인 상태

### D-4. 목록 필터 방식: 쿼리 안 `NOT EXISTS` 안티 조인[^3] (채택) 대 차단 id 목록 파라미터

| | NOT EXISTS 서브쿼리 (채택) | 차단 id 목록을 먼저 읽어 `NOT IN (:ids)` |
|---|---|---|
| 왕복 | 목록 1회 (기존과 같음) | 목록 1회 + 차단 id 1회 (양방향 합집합은 앱에서) |
| 비로그인 처리 | 파라미터 null 이면 절이 참으로 단락 | 빈 목록 바인딩 불가(native `IN ()` 문법 오류)라 감시값이 필요 |
| 파라미터 크기 | 1개 | 수십 개(가정) 이상이면 계획 캐시가 갈라진다 |
| 페이지 정합 | keyset 커서[^4] 와 lookahead 가 그대로 성립 | 같음 |
| 실행 계획 | 후보 행마다 `user_blocks` 인덱스 프로브 2회(양방향), 페이지당 최대 (size+1)×2 | `NOT IN` 은 NULL 의미론 때문에 플래너가 안티 조인으로 못 바꾸는 경우가 있어 `NOT EXISTS` 로 써야 한다 |

어느 쪽도 성능 차이는 페이지당 수십 회의 인덱스 프로브 수준이라 결정 근거는 성능이 아니라 형태다.
채택안은 술어가 쿼리 한 곳에 남고, 비로그인이 자연스럽게 단락되며, 왕복이 늘지 않는다.
응답 뒤 애플리케이션에서 걸러내는 방식은 아예 후보가 아니다: 차단한 작성자가 한 페이지를 통째로
차지하면 빈 페이지에 `hasNext=true`가 반복되어 커서 계약(MSG-237 §D2)이 깨진다. 기존 닉네임 누락
필터는 탈퇴 경합이라는 희귀 경우에만 한 항목이 빠지는 것이라 성격이 다르다.

native 4종(`findGlobalVideos`, `findGlobalVideosAfter`, `findMissionVideos`, `findMissionVideosAfter`)에
붙는 절. 격자 쿼리는 별칭이 없어 `videos.user_id`로 쓰고, 미션 쿼리는 `v.user_id`다. 게이트 줄
(`status = 'ACTIVE' AND visibility = 'PUBLIC' AND processing_status = 'READY'`)은 글자 하나 바꾸지
않는다: `countHourlyUploadsByGrid`와의 문자열 동일 계약, `idx_videos_grid_popular` 부분 인덱스 매칭이
그 줄에 걸려 있다. 차단 절은 그 줄 다음에 한 절로 더한다.

```sql
  AND (CAST(:viewerId AS bigint) IS NULL OR NOT EXISTS (
	SELECT 1 FROM user_blocks b
	WHERE (b.blocker_id = :viewerId AND b.blocked_id = videos.user_id)
	   OR (b.blocker_id = videos.user_id AND b.blocked_id = :viewerId)))
```

`CAST(:viewerId AS bigint)`는 null 파라미터의 native 타입 추론 문제(MSG-90 이 메서드를 커서 유무로
나눈 이유)를 `getRegionExplorePage`의 `CAST(:limit AS bigint)` 선례대로 푼 것이다. 메서드를 viewer
유무로 또 나누면 목록 쿼리가 4개에서 8개가 된다.

JPQL 4종(`EventVideoRepository.findVisibleByLocationId`, `findVisibleByLocationIdAfter`,
`EventVideoCommentRepository.findPageByVideoId`, `findPageByVideoIdAfter`)에 붙는 절. 영상은 `v.userId`,
댓글은 `c.userId`가 비교 대상이다.

```jpql
  AND (:viewerId IS NULL OR NOT EXISTS (
	SELECT 1 FROM UserBlock b
	WHERE (b.id.blockerId = :viewerId AND b.id.blockedId = v.userId)
	   OR (b.id.blockerId = v.userId AND b.id.blockedId = :viewerId)))
```

Hibernate 6 은 같은 이름 파라미터가 `b.id.blockerId = :viewerId`에도 쓰여 타입을 Long 으로 잡는다.
리포지토리 테스트에서 null 바인딩이 실제로 통과하는지 첫 케이스로 확인하고, 만약 바인딩 예외가 나면
JPQL 도 native 와 같이 `CAST(:viewerId AS Long)`으로 맞춘다(구현 중 판정, 설계 변경 아님).

행사 위치 영상 수(`countVisibleByLocationIds`)와 격자 영상 개수, 미션 영상 개수 쿼리에는 이 절을 붙이지
않는다(PRD 비목표). 그래서 MSG-440 이 "카운트와 피드는 술어 동등"으로 묶어 둔 계약은 이번부터
"노출 게이트 3종은 동등, 차단 절은 요청자를 아는 목록에만"으로 바뀐다. 카드 숫자가 목록 행 수보다 클 수
있고 그 차이를 허용한다(MSG-390 이 BLINDED 에서 허용한 것과 같은 취급). 리포지토리 주석의 "동등 계약"
문구를 이 문장으로 고친다.

### D-8. 시각과 트랜잭션

- 새 시각 생성은 `UserBlockService`의 `LocalDateTime.now(clock)` 한 곳이다. 엔티티에는 상태 전이 메서드가
  없어 `ZoneOffset.UTC` 직접 호출도 없다. DTO 시각 타입은 `LocalDateTime`(코덱이 `Z` 표기).
- **`Clock` 빈은 없다**(Codex 2R P1). `@RequiredArgsConstructor`만 두면 기동에 실패하므로 선례대로
  생성자를 둘 둔다: `@Autowired` 프로덕션 생성자가 `Clock.systemUTC()`를 고정해 Lombok 전체 생성자로
  위임하고, 테스트는 전체 생성자로 고정 Clock 을 주입한다(`VideoServiceImpl` 152~168행,
  `BadgeAwardServiceImpl` 64~72행, `AiBlurPoller` 86~96행). `systemUTC`인 이유는 `created_at`이 UTC 저장
  관례(MSG-376)라서다. 기본존 JVM(KST)이면 +9h 로 저장된다.
- `block`은 쓰기 `@Transactional` 하나, `unblock`도 하나, 목록과 판정은 `readOnly`.

## 데이터 모델

Flyway `V53__user_blocks.sql` 신규 1건. 다른 테이블은 바꾸지 않고 백필도 없다. 롤백은 `DROP TABLE`.

```sql
-- 사용자 차단 (MSG-569). friendships 의 BLOCKED 상태를 쓰지 않는 이유: V19 대칭 쌍 유니크가
-- "친구이면서 차단"을 한 행에 담을 수 없고, 차단은 방향이 있는 관계(A→B 와 B→A 가 별개 행)다.
CREATE TABLE user_blocks (
	blocker_id BIGINT    NOT NULL REFERENCES users(id) ON DELETE CASCADE,
	blocked_id BIGINT    NOT NULL REFERENCES users(id) ON DELETE CASCADE,
	created_at TIMESTAMP NOT NULL,
	PRIMARY KEY (blocker_id, blocked_id),
	CONSTRAINT chk_user_blocks_self CHECK (blocker_id <> blocked_id)
);

-- 피차단자 기준 역조회 (상호 비노출의 "상대가 나를 차단" 방향, 탈퇴 CASCADE 의 blocked_id FK 검사).
CREATE INDEX idx_user_blocks_blocked ON user_blocks (blocked_id, blocker_id);
```

- 복합 PK 가 "같은 방향 차단은 한 행"(PRD 데이터 정합)과 `ON CONFLICT (blocker_id, blocked_id)`의 충돌
  대상을 동시에 맡는다.
- `created_at`은 `blockedAt` 응답값이자 목록 정렬 키다. 정렬 타이브레이크는 `blocked_id`(PK 두 번째
  컬럼)라 같은 시각에도 순서가 결정적이다.
- `CHECK (blocker_id <> blocked_id)`는 서비스 1430 검증의 DB 백스톱이다(`chk_friendships_self` 선례).
- 탈퇴 정리(FR-13)는 양쪽 FK 의 `ON DELETE CASCADE`가 맡는다. `UserServiceImpl` 탈퇴 코드 변경 없음.

엔티티 `user/entity/UserBlock`(`@Table(name = "user_blocks")`, `@EmbeddedId UserBlockId` 에 `@MapsId` 로
매핑된 LAZY `@ManyToOne User blocker`, `blocked` 둘, `createdAt` `updatable = false`. 상세는 D-1). JPA
`ddl-auto`는 `validate`라 컬럼 이름과 타입이 위 DDL 과 맞아야 기동한다.

[^2]: KEY SHARE 잠금: PostgreSQL 의 `SELECT ... FOR KEY SHARE`. 그 행의 키가 삭제되거나 바뀌는 것만 막는 가장 약한 행 잠금이라, 외래키 검사가 잡는 잠금과 같은 종류다. 대상 사용자 행에 먼저 걸어 두면 탈퇴 CASCADE 가 이 트랜잭션이 끝날 때까지 기다린다.
[^3]: 안티 조인(NOT EXISTS): "저쪽 테이블에 짝이 없는 행만"을 고르는 조인. 플래너가 후보 행마다 `user_blocks` 인덱스를 찍어 보거나, 차단 행이 적으면 해시로 바꿔 처리한다. `NOT IN`과 달리 NULL 이 섞여도 의미가 흔들리지 않는다.
[^4]: keyset 커서: 페이지 번호 대신 직전 페이지 마지막 행의 정렬 키 값을 커서로 주고 "그 값보다 뒤"만 읽는 페이지 방식. 필터가 쿼리 안에 있어야 한 페이지가 항상 size 건으로 채워지고 커서가 앞으로 나아간다.
[^5]: 순환 참조: 빈 A 가 B 를 주입받고 B 가 다시 A 를 주입받는 구조. 스프링이 기동에서 `BeanCurrentlyInCreationException`으로 거부한다. 지연 조회로 우회하면 기동 검출이 꺼져 다음 순환은 런타임에야 드러나므로(MSG-312 교훈) 판정을 다른 빈을 참조하지 않는 leaf 로 분리해 푼다.
