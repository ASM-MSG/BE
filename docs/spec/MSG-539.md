# MSG-539: 경로 추천 응답에 동선 전체의 종합 이유를 담는다

**Owner**: 공동 (주 구현 B, MSG-457 §Owner 판정 선례. 변경 파일은 전부 route 패키지와 그
테스트라 A 몫 구현은 없고, FillMap-AI 쪽 개정은 별도 레포의 분리 티켓 MSG-540이다. MSG-513과
같은 구성)

> 요구사항 정본: `docs/prd/MSG-539-prd.md` (검토됨, 2026-09-01 성민 승인). SRS `FR-ROUTE-20` (계획).

## 개요

이유 문장화[^1] 호출 하나에 얹어, 지점이 실리는 추천 응답에 동선 전체의 종합 추천 이유
(`summary`)를 함께 싣는다. 지금은 지점마다 한 줄 이유(FR-ROUTE-05)만 있어서, 사용자가 적은
문장과 이번 동선 구성이 어떻게 이어졌는지는 사용자가 지점 이유들을 읽고 스스로 재구성해야
한다. 추가 AI 호출은 없고(PRD 확정), 지점별 이유와 추천 결과 자체는 그대로다. 빈 목록
응답에는 종합 이유가 없고 기존 안내(notice)가 그 자리를 맡는다.

## 배경 · 목표

추천 결과 상단에서 "이 동선이 내 요청을 이해한 결과"라는 신뢰를 주는 것이 목적이다(PRD 1절).
종합 이유는 사용자가 적은 문장을 근거로 이번 지점들이 왜 골라졌는지 설명하고, 문장에 조건이
하나도 없는 빈 해석[^2]이어도 화면 범위 기준으로 골랐다는 설명이 온다(FR-ROUTE-06 유지).
결과에 없는 장소나 서버가 확인하지 않은 사실은 담기지 않고(FR-ROUTE-03과 같은 원칙), 형태를
벗어난 종합 이유는 채택하지 않는다(FR-ROUTE-08, NFR-SEC-08과 같은 원칙).

## 성공 기준

항목마다 붙은 번호가 테스트 검증 마커(`// 검증: FR-ROUTE-20, AC-539-XX`)와 이어진다.
실서비스에서 summary가 실제로 실리기 시작하는 것은 승격 커밋(결정 3의 3단계) 이후지만,
서버 동작 자체는 전부 AI 스텁으로 지금 판정 가능하다.

- AC-539-01: 지점이 1개 이상 실린 추천 응답(정상 3개 이상, 부족 안내가 붙는 1~2개 포함)에
  summary가 문자열로 실린다. 값은 explain 응답의 summary가 형태 검증을 통과한 그대로다.
- AC-539-02: 승격 커밋 이후의 explain 요청 본문에는 parse에 보낸 것과 동일한 트림 본문
  `text`가 동봉된다. 뷰포트 좌표와 사용자 식별 정보는 동봉되지 않는다(NFR-SEC-09 유지).
- AC-539-03: summary가 문자열이 아니거나, 빈 문자열이거나, 240자를 넘거나, 개행을 담으면
  기존 규칙대로 14502다. 부분 채택이나 지어낸 대체 문장은 없다(FR-ROUTE-08 유지).
- AC-539-04: 한시 수용 기간에는 summary가 없는 explain 응답이 거부되지 않고 응답의
  summary가 null이다. reasons 처리와 나머지 조립은 정상이다(MSG-540 배포 확인 후 부재도
  14502로 승격, 결정 3의 3단계. MSG-513 AC-513-05와 같은 개정 예정 구조).
- AC-539-05: 빈 목록 응답 세 갈래(후보 없음 FR-ROUTE-07, 무관 문장 FR-ROUTE-19, 도보 절단
  소진 FR-ROUTE-13)는 explain을 부르지 않고 summary가 null이다. notice가 그 자리를 맡는다.
- AC-539-06: 빈 해석(related=true, 전 필드 빈)이어도 지점이 실리면 summary 경로가 정상
  추천과 같다. text가 동봉되고 summary가 실린다.
- AC-539-07: 지점별 reason의 개수, 순서, 값과 검증 규칙(개행 없는 1~120자)이 이번 변경
  전과 같다(PRD 비목표: 지점별 이유 불변).
- AC-539-08: 한시 수용 기간의 explain 요청 본문은 구계약과 글자 그대로 같다(text 미동봉).
  구계약 AI의 정의 밖 요청 필드 거부(`extra="forbid"`[^3])에 걸리지 않는다.
- AC-539-09: 해석 캐시[^4] 창 안의 재요청도 explain이 새로 나가고 summary가 새로 실린다.
  parse는 재호출되지 않는다(summary는 캐시되지 않는다, 결정 5).

## 결정 (PRD 미해결 질문의 해소)

### 결정 1. 문장 맥락은 사용자 문장 원문 `text` 하나다. 뷰포트는 동봉하지 않는다

explain 요청에 필드 `text`를 더한다. 값은 parse에 보낸 것과 동일한 트림 본문이다
(`RouteRecommendRequestDto` 컴팩트 생성자가 정규화를 보장하고, 요청 검증이 1~500자를
보장하므로 조립 시점 추가 절단이 없다. parse와 같은 규칙, 같은 문자열).

- 원문을 보내는 이유(PRD 유력안 채택): 해석 결과(지역, 관심사, 기간, 순서 희망)만 보내면
  AI는 구조화된 값의 재번역으로 설명을 만들게 되고, 그것은 "사용자가 적은 문장에 대한"
  설명이 아니라 "서버 해석에 대한" 설명이 된다. 원문은 이미 parse로 같은 AI 서버에 나가는
  값이라 이 동봉으로 외부 모델에 새로 나가는 정보가 없다(PRD 비기능 보안, NFR-SEC-08 전제
  유지). 필드명은 parse 요청과 같은 `text`(snake_case 한 단어)다.
- 뷰포트를 동봉하지 않는 이유: 후보 수집 기준은 언제나 화면 범위라(FR-ROUTE-06,
  FR-ROUTE-14의 "추천 기준 자체는 계속 화면 범위") 좌표 값이 문장화 재료가 아니다. 좌표를
  주면 모델이 좌표에서 지역 이름을 만들어 내는 위험 재료만 된다(FR-3의 "서버가 확인하지
  않은 사실" 위반 경로). parse가 뷰포트를 받는 이유는 상대 표현 해석 재료(MSG-458 D-3)인데
  explain은 해석을 하지 않는다. 빈 해석일 때 "화면 범위 기준" 취지의 문구를 쓰라는 지침은
  MSG-540 프롬프트 몫이다(문장에 조건이 없다는 사실이 곧 그 재료다).
- 기각 대안: 해석 결과 동봉(위 재번역 문제), 원문과 해석 결과 병행 동봉(원문에 이미 다
  있어 필드만 는다), 빈 해석 여부 플래그 동봉(문구 뉘앙스 하나를 위해 계약 필드를 늘린다.
  실측에서 빈 해석 요청의 summary가 조건을 지어내면 그때 확장을 논의한다).

### 결정 2. summary 형태는 개행 없는 1~240자다. 위반은 14502다

- 길이 상한 240자: 지점별 한 줄(1~120자)의 두 배로, 문장 두어 개 분량이다. 동선 전체
  서술이라 한 줄보다 여유를 두되(PRD 미해결 3), 상한이 없으면 모델 폭주 출력이 그대로
  화면에 실리고 형태 검증(FR-5) 자체가 성립하지 않는다.
- 개행 금지, 빈 문자열 위반: 지점별 reasons와 같은 원칙이다. 한 덩어리 텍스트를 보내고
  줄 구성은 화면 몫이다.
- 비문자열, 빈 문자열, 길이 초과, 개행 포함 전부 기존 단일 수렴[^5](14502)이다. 문장 속
  숨긴 지시가 summary를 뒤틀어도 지점 목록과 reasons는 별개 검증을 통과해야 하므로 영향
  반경은 "요청 전체가 14502로 실패"까지다(NFR-SEC-08 유지).

### 결정 3. AI가 요청 쪽을, 서버가 응답 쪽을 각각 조건부로 연다. 세 단계다

related 선례(MSG-513 결정 2)는 "서버 선배포 후 한시 수용"이었지만 이번엔 그대로 못 쓴다.
방향이 반대라서다. 실측 두 건이 설계를 결정한다.

- 구계약 AI의 explain 요청 모델은 정의 밖 필드를 거부한다(`ExplainRequest`의
  `extra="forbid"`, FillMap-AI `route_ai.py` 195행 실측, MSG-458 D-4의 요청 검증). 서버가
  `text`를 먼저 보내는 순간 지점이 실리는 추천 전부가 422로 튕겨 14502 전면 장애가 된다.
  새 값을 서버가 먼저 보내는 MSG-513 방향이 여기서 막힌다.
- 반대로 현행 서버의 explain 응답 검증(`toReasons`)은 `reasons`만 읽고 정의 밖 필드를
  거부하지 않는다(parse 검증과 다른 기존 동작, MSG-457 검증 목록 그대로). AI가 summary를
  먼저 실어도 구서버는 무시하고 아무 일도 없다.

이 비대칭에 맞춰 세 단계로 간다.

1. **이번 티켓(서버 1차)**: 응답 쪽만 연다. explain 응답의 `summary`를 있으면 형태
   검증(결정 2, 위반 14502) 후 채택하고, 없으면 null로 한시 수용한다. 요청 본문은 구계약과
   글자 그대로 같다(`text` 미동봉). `explain` 시그니처는 text를 미리 받되 본문에 싣지
   않고, 이것이 승격 대기의 한시 상태임을 코드 주석으로 남긴다(MSG-513 1단계의 관대 수용
   주석 선례).
2. **MSG-540(AI)**: 아래 계약 변경 절대로 개정해 배포한다. explain 요청에 `text` 선택
   필드를 수용하고, **text가 있으면 summary를 만들어 싣고 없으면 구계약 응답 그대로
   (summary 부재)** 다. text 동봉 여부가 곧 신구 서버 판별자라 별도 버전 협상이 없고,
   전환 구간의 구서버(text 안 보냄)는 구계약 응답을 받아 아무것도 변하지 않는다.
3. **승격(MSG-540 완료 조건에 편입)**: AI 배포 확인 후 BE 한 커밋으로 두 가지를 함께
   바꾼다. explain 요청 본문에 text를 동봉하기 시작하고, summary 부재를 14502로 승격한다.
   한 커밋으로 묶는 이유: 신계약은 "text가 있으면 summary 필수"라, text를 보내기 시작하는
   시점이 곧 부재를 위반으로 볼 수 있는 시점이다. 나눠 배포하면 의미 없는 중간 창만 생긴다.

부속 결정 두 건.

- AI 쪽 `text`는 필수로 승격하지 않고 선택으로 유지한다. 서버가 1차 코드로 롤백하면 text
  없는 요청이 다시 나가는데, AI가 text를 필수로 올려 두면 그 롤백이 전면 422 장애가 된다.
  선택 유지가 서버 롤백의 자연 완충이다.
- 승격 후 AI가 구계약으로 롤백하면 text 실린 요청이 422로 튕겨 전면 14502가 된다. parse
  필수 키와 같은 성질이라 새 결정이 아니다(MSG-513 결정 2의 같은 조항).

기각 대안: 동시 배포(레포가 둘이라 원자적 동시 배포가 불성립, MSG-513과 같은 이유), 서버에
text 송신 플래그 신설(승격 커밋이 할 일을 설정 노브로 한 번 더 만드는 중복이고, 끄고 켜는
주체와 시점 관리가 커밋 하나보다 어렵다).

### 결정 4. 응답 필드명은 `summary`, 마지막 성분, 빈 목록과 한시 수용 기간은 null이다

`RouteRecommendResponseDto`에 `String summary`를 마지막 성분으로 더한다. PRD 시퀀스
다이어그램의 이름 그대로다. 마지막에 두는 이유는 프로덕션 생성자 호출 4곳(무관 조기 반환 1,
빈 후보 반환 2, assemble 1)의 기존 인자 순서를 보존해 성분 추가의 파급을 인자 하나 덧붙임
으로 닫기 위해서다.

- null 규약: 빈 목록 세 갈래는 explain 자체를 타지 않으므로 summary가 null이다(FR-4).
  한시 수용 기간(결정 3의 1단계와 3단계 사이)에도 null이다. 승격 후 지점이 실린 응답은
  항상 문자열이다(부재가 14502로 실패하므로 null인 성공 응답이 없다).
- Swagger: `@Schema(description = "동선 전체의 종합 추천 이유(FR-ROUTE-20). 사용자 문장을
  근거로 이번 지점 구성을 설명한다. 빈 목록 응답(후보 없음, 무관 문장, 도보 절단)은 null이고
  notice가 그 자리를 맡는다", nullable = true)`. `requiredProperties`에 `summary`를 더한다.
  nullable이어도 키 자체는 항상 실린다는 기존 notice, mentionedArea 표기 선례 그대로다.
- `RouteIntentClient.explain`의 반환형은 `List<String>`에서 중첩 record
  `ExplainResult(List<String> reasons, String summary)`로 바꾼다. reasons 검증은 불변이고
  summary 검증이 옆에 붙는다. 호출처는 `RouteRecommendServiceImpl` 한 곳뿐이다.

### 결정 5. 해석 캐시와 무관하다. 지표 키는 추가하지 않는다

- parse 캐시는 ParsedIntent만 저장하고 explain에는 캐시가 없다. 캐시 창 안의 재요청은
  parse 없이 같은 해석을 재사용하지만 explain은 매번 새로 나가므로 summary도 요청마다 새로
  생성된다. 문장 표현이 회차마다 완전 동일하지 않을 수 있는 것은 기존 reasons와 같은
  성질이고(FR-ROUTE-10의 재현 보장은 해석, 후보, 순서까지다. temperature 0은 흔들림 완화),
  새 결정이 아니다.
- 지표 로그에 summary 관련 키를 더하지 않는다. 부재는 승격 후 14502라 기존 ai_error
  버킷에 이미 잡히고, 성공 응답에서의 존재는 상수라 정보량이 없다. 한시 수용 기간의 부재
  빈도도 관측 대상이 아니다. 그 기간엔 서버가 text를 안 보내므로 부재가 100%인 것이 계약상
  정상이라서다. summary 원문은 AI 응답 원문 로그 금지 규칙 그대로 로그에 남기지 않는다.

## API 명세

`POST /api/routes/recommend`의 endpoint, method, 에러 코드(14xxx) 전부 그대로다.
RouteErrorCode에 신규 상수가 없고, 바뀌는 것은 응답 필드 하나다.

| 케이스 | HTTP | developCode | summary |
|---|---|---|---|
| 정상 추천 (지점 3개 이상) | 200 | 200 | 문자열 (notice는 null) |
| 부족 안내 (지점 1~2개) | 200 | 200 | 문자열 (부족 notice와 공존) |
| 빈 목록 세 갈래 (후보 없음, 무관, 절단 소진) | 200 | 200 | null (notice가 그 자리) |
| summary 형태 위반 (비문자열, 빈 문자열, 241자, 개행) | 502 | 14502 | 응답 자체가 실패 |
| 한시 수용 기간의 summary 부재 | 200 | 200 | null (승격 후에는 14502) |

## 도메인 로직

처리 순서는 기존 그대로다: 입력 검증 → 플래그 게이트 → 요청 제한 원자 선점 → parse(캐시) →
무관 조기 반환 → 언급 지역 판정 → 후보 수집 → 순서 배열 → 도보 예산 절단 → explain → 응답
조립. 새 분기가 없고, explain 왕복에 값 하나가 늘고 조립에 그 값이 이어질 뿐이다.

1. **형태 검증 (RouteIntentClient)**: `toReasons` 옆에 summary 검증이 붙는다. 있으면 결정
   2의 규칙(개행 없는 1~240자 문자열)으로 검사해 위반은 `contractViolation`(14502)이고,
   없으면 null이다(한시, 결정 3의 1단계. 승격 커밋이 부재를 위반으로 바꾼다). explain
   응답의 정의 밖 필드를 거부하지 않는 기존 동작은 이번에 바꾸지 않는다. MSG-457 검증
   목록이 정의한 범위 그대로이고, 그 관용이 바로 이번 전환(2단계에서 구서버가 신 AI 응답을
   받는 구간)을 성립시키는 성질이다.
2. **조립 (RouteRecommendServiceImpl)**: `doRecommend`가 이미 들고 있는 트림 본문 `text`를
   explain 호출에 넘기고(본문 동봉은 승격 커밋 몫), `ExplainResult`의 summary를
   `assemble`로 이어 응답에 싣는다. 빈 목록 세 갈래의 조기 반환 3곳은 summary 자리에
   null을 넣는다. 그 밖의 로직(요청 제한, 신호 부여, facts 조립, 절단)은 무변경이다.
3. **지표 (recommend)**: 변경 없음(결정 5). outcome 판정과 spans, counts 관례 그대로다.

### BE ↔ AI: `POST /route/explain` 개정 (MSG-458 계약 개정)

요청에 필드가 하나, 응답에 필드가 하나 는다. parse 계약과 explain의 points, reasons 규칙은
불변이다.

| 방향 | 필드 | 타입 | 규칙 |
|---|---|---|---|
| 요청 | `text` | string, **선택** | 사용자 문장 원문(트림 본문), 1~500자(parse와 동일). 부재는 구계약 요청과 동일하게 처리한다. 선택 유지는 영구다(서버 롤백 완충, 결정 3 부속) |
| 응답 | `summary` | string | 동선 전체의 종합 이유. **요청에 text가 있을 때만, 그리고 그때는 반드시** 실린다. 개행 없는 1~240자. 사용자 문장과 points의 facts에서 확인되는 내용만 담는다(FR-ROUTE-03과 같은 원칙) |

FillMap-AI 쪽 개정 제안 4곳:

1. **요청 모델 (`ExplainRequest`)**: `text` 선택 필드 추가(1~500자, 부재 허용).
   `extra="forbid"`는 그대로 둔다.
2. **프롬프트와 모델 출력 스키마**: summary 생성 지침을 붙인다. 주어진 text와 facts만으로
   쓰고(사실의 문장화이지 생산이 아니라는 D-4 원칙 그대로), 문장에서 지역이나 관심사 같은
   조건이 확인되지 않으면 지금 보고 있는 화면 범위 기준으로 골랐다는 취지로 설명한다
   (FR-2의 빈 해석 케이스). text 없는 요청을 구 스키마로 부를지, 모델 출력의 summary를
   버릴지는 MSG-540 구현 몫이다(json_schema strict는 선택 속성이 불성립하므로 어느 쪽이든
   내부 처리가 필요하다).
3. **검증 (`ExplainResult` 상당)**: summary 개행 없는 1~240자, text 있는 요청에서 부재면
   502(형태 위반). BE와 같은 규칙의 이중 방어다.
4. **문서와 스모크**: `docs/MSG-458.md` 계약 표와 README 계약 절에 두 필드 반영. 스모크에
   text 있는 요청의 summary 형태 검증, text 없는 요청의 summary 부재 확인, summary 형태
   위반(개행, 241자, 빈 문자열) 거부 케이스를 더하는 것을 MSG-540 완료 조건으로 제안한다.

서버 쪽 대응 개정은 결정 3의 1단계(summary 한시 수용, text 미동봉)와 3단계(text 동봉과
summary 필수 승격 한 커밋)다. 승격 커밋은 MSG-540 완료 조건에 편입한다.
