# MSG-204: 업로드 시 공개범위 지정 (PUBLIC/PRIVATE, 기본 공개)

**Owner**: B (video 도메인 단독 — `com.msg.fillmap.video.*`)

> 요구사항 정본: `docs/prd/MSG-204-prd.md` (상태: 검토됨, 2026-08-01 사용자 승인).
> 이 스펙은 PRD FR-1~7에 "어떻게"만 붙인다.
> 선행: `docs/spec/MSG-162.md` §설계 M3가 "업로드 시 선택은 확정 후 별도 티켓"으로 미뤄둔 자리.
> **M3의 "기본 PRIVATE 안전값" 결정은 이 PRD가 "기본 PUBLIC"으로 대체한다** (2026-08-01 확정).
> FRIENDS 3값 확장은 MSG-285(백로그) — 이번엔 `Visibility` enum·DB CHECK 무변경.

## 개요

업로드 확정 요청(`POST /api/videos`)에 선택 필드 `visibility`를 추가한다. 지정하면 그 값으로,
생략(null)하면 **PUBLIC**으로 저장한다. 현재는 엔티티 생성자가 PRIVATE를 하드코딩해 업로드 후
전환 API(MSG-162)를 한 번 더 불러야만 공개된다 — "올리면 지도에 게시된다"는 제품 기본 동작을 완성한다.

## 배경 · 목표

- 지도에 게시하는 서비스인데 기본이 비공개라, 전환을 잊으면 대표 영상·전역 목록 등 공개
  노출면에 아무것도 잡히지 않는다 (PRD §1).
- 목표: 업로드 확정 한 번으로 공개/비공개를 정하고, 미지정은 PUBLIC (PRD FR-1·FR-2).
- 비목표: FRIENDS(MSG-285) · 설정 화면 기본값 저장(폐기) · 기존 영상 소급 전환 (PRD §2).
- 서비스 미출시 확정(2026-08-01)이라 FE 칩 UI 없이 BE 선행 — 과도기 이슈 없음 (PRD §8 해소).

## 성공 기준

1. `POST /api/videos`에 `"visibility": "PRIVATE"`를 넣으면 PRIVATE로, `"PUBLIC"`이면 PUBLIC으로 저장된다.
2. `visibility` 필드를 생략(또는 null)한 요청은 PUBLIC으로 저장된다 — 구버전 클라이언트 요청 동일 (FR-2).
3. `PUBLIC`/`PRIVATE` 외 값(FRIENDS·빈 문자열 포함)은 400 + `INVALID_VISIBILITY(3420)`로 거부되고
   영상은 저장되지 않는다 — S3 원본 클레임(`confirmUpload`)·복사도 일어나지 않는다 (FR-3).
4. 업로드 직후 PUBLIC이어도 `processing_status`가 READY가 되기 전에는 공개 노출면에 나타나지 않는다 (FR-4).
   근거는 기존 read 게이트 — 전역 노출 SQL 9곳(`VideoRepository` findGlobalCover:57 ·
   findGlobalVideos:74 · findGlobalVideosAfter:89 · 탐색 집계 4곳(270·276·307·313) · 요약 2곳(338·361))이
   전부 `visibility='PUBLIC' AND processing_status='READY'` 등식이다 (2026-08-01 실측, MSG-162 §M4 원칙 유지).
5. 교체(`PUT /api/videos/{videoId}`)는 공개범위를 유지한다 — `Video.replaceFile` 무접촉 (FR-6).
6. 전환 API(`PATCH /api/videos/{videoId}/visibility`)는 무변경으로 그대로 동작한다 — 회귀 확인만 (FR-7).
7. Flyway 마이그레이션 없이 전체 테스트 green. 기존 영상 데이터 무변경 (FR-5).

## API 명세

신규 엔드포인트 없음 — 기존 `POST /api/videos` (업로드 확정, `VideoController.upload`) 요청 계약에
필드 하나 추가. 인증·응답(`SuccessResponse<VideoUploadResponseDto>`)·컨트롤러 코드는 무변경.

### Request — `VideoUploadRequestDto` (record, 필드 추가)

| 필드 | 타입 | 제약 | 설명 |
|---|---|---|---|
| s3Key | String | @NotBlank | (기존) |
| lat / lng | Double | @NotNull | (기존) |
| durationSec | Short | @NotNull @Min(1) @Max(30) | (기존) |
| recordedAt | LocalDateTime | @NotNull | (기존) |
| **visibility** | **String** | **없음 (null 허용)** | **신규.** `PUBLIC` \| `PRIVATE`, 대소문자 무관. 생략·null 시 PUBLIC. `@Schema(description = "공개범위. PUBLIC 또는 PRIVATE, 생략 시 PUBLIC", example = "PUBLIC")` |

- record 마지막 필드(recordedAt 뒤)로 추가 — canonical constructor가 바뀌므로 테스트의
  위치 인자 생성 호출부가 전부 깨진다 (아래 변경 파일 참조). 프로덕션 코드에서 DTO를 직접
  생성하는 곳은 없다 (@RequestBody 역직렬화만 — 2026-08-01 grep 실측).
- **enum이 아니라 String으로 받는 이유**: `VideoVisibilityRequestDto`(MSG-162 §M2) 선례 그대로 —
  `GlobalExceptionHandler`에 `HttpMessageNotReadableException` 핸들러가 없어 enum 역직렬화 실패가
  500이 된다. 문자열 수신 후 서비스 파싱(`AuthController.parseProvider` 패턴)으로 4xx를 보장.
- 전환 DTO와 달리 `@NotBlank`를 **붙이지 않는다** — null이 유효값(기본 PUBLIC)이기 때문.
  단, 빈 문자열 `""`·공백은 "지정한 잘못된 값"이라 3420으로 거부된다(`valueOf` 실패 자연 동작).

### 에러 케이스

| 케이스 | 응답 |
|---|---|
| visibility가 PUBLIC/PRIVATE 외 값 (FRIENDS, "", "public!" 등) | 400 · `INVALID_VISIBILITY(3420)` "visibility 는 PUBLIC 또는 PRIVATE 여야 합니다" — **기존 코드 재사용, 신규 에러 코드 없음** |
| 기존 검증 (s3Key·좌표·durationSec 등) | 무변경 |

## 도메인 로직

용어(glossary): 업로드 확정 = **방문** 이벤트 1건 저장. 첫 방문이면 **점령**(user_grids 생성) —
이 흐름은 전부 무변경이고, 이번 변경은 저장되는 **영상**의 공개범위 결정 한 지점뿐이다.

1. **파싱 위치**: `VideoServiceImpl.saveVideo`(현재 105-150행) **초입**, `confirmUpload`(S3 검증·
   원본 키 클레임) **호출 전**에 visibility를 확정한다 — 잘못된 값이 S3 부수효과 없이 거부되게 (FR-3).
   - `request.visibility() == null` → `Visibility.PUBLIC`
   - 값이 있으면 기존 private 메서드 `parseVisibility`(197-204행) **재사용** — `toUpperCase(Locale.ROOT)`
     후 `valueOf`, 실패 시 `ApiException(INVALID_VISIBILITY)`. 신규 파싱 코드 없음.
2. **엔티티**: `Video.create(...)`(128-131행) 시그니처에 `Visibility visibility` 파라미터를 마지막에
   추가하고, private 생성자(114-126행)의 `this.visibility = Visibility.PRIVATE;` 하드코딩(123행)을
   파라미터 대입으로 바꾼다. 기본값 결정은 서비스 몫 — 엔티티는 받은 값을 저장만 한다
   (null 기본값 분기를 엔티티에 두면 "기본 PUBLIC"이라는 제품 결정이 엔티티에 숨는다).
   - **null 가드는 넣지 않는다** (2026-08-01 리뷰 판단 기록, Codex 2R 정정 반영): 근거 세 가지 —
     ① `requireNonNull`은 src/main 전체 0건(grep 실측)으로, 이 레포는 엔티티·팩토리에서 null을
     검증하지 않고 **검증을 서비스 경계에 둔다**(`parseProvider`/`parseVisibility` 패턴). visibility만
     가드하면 새 패턴 도입이다. ② visibility 컬럼은 NOT NULL이고 `Video`에 `@DynamicInsert`가 없어
     INSERT가 이 컬럼을 항상 포함한다 — null이 새면 같은 트랜잭션 flush에서 NOT NULL 위반으로
     즉시 롤백돼 오염 없이 실패한다 (nullable이라 null이 조용히 저장되는 `original_s3_key`와 다른 축 —
     "전 파라미터 NOT NULL"이라던 초판 근거는 오기라 정정). ③ 유일 호출부(saveVideo)는 분기상
     non-null 보장.
3. **무접촉 유지**: `Video.replaceFile`(교체) · 전환 API(`VideoServiceImpl.setVisibility` →
   엔티티 `Video.changeVisibility`) · 재생 판정 · 전역 노출 쿼리 9곳 · `deleteVideo` 전부 무변경.

## 데이터 모델

**변경 없음 — Flyway 마이그레이션 없음.**

- `videos.visibility` 컬럼 · `chk_videos_visibility CHECK (IN ('PUBLIC','PRIVATE'))` ·
  컬럼 DEFAULT `'PRIVATE'` 전부 무변경.
- **DEFAULT를 PUBLIC으로 바꾸지 않는 근거** (2026-08-01 판단, 기록): 앱 경로는 엔티티가 visibility를
  항상 명시하므로 DB DEFAULT에 의존하지 않는다. DEFAULT가 발동하는 유일한 경로는 컬럼을 누락한
  수동 INSERT인데, 그때 PRIVATE로 떨어지는 것은 **과소 노출 방향이라 안전**하다 (실수로 공개되는
  사고보다 낫다). 기존 영상 소급 변경 없음(FR-5)과도 정합.
