# MSG-466: 핫구역 줌아웃 행정 단위 집계 조회 신설

**Owner**: A (`com.msg.fillmap.hotzone`, `com.msg.fillmap.grid` 내부 수정. SecurityConfig 한 줄은 전역 설정이라 Owner 무관)

> PRD 정본: `docs/prd/MSG-466-prd.md` (검토됨, 2026-08-24 사용자 승인)
> SRS: FR-HOTZONE-13 (2026-08-24 등재, 계획)
> 선례 정합 대상: 도감 집계 `docs/spec/MSG-356.md`, 미션 집계 `docs/spec/MSG-437.md`

## 개요

축소 화면에서 핫구역을 도감, 미션과 같은 행정 단위(동, 구, 시) 이름 마커로 보여줄 집계 조회를 신설한다. 산출물은 엔드포인트 `GET /api/hotzones/aggregation` 하나이고, 집계 대상은 개별 조회(`GET /api/hotzones`)와 완전히 같은 핫 판정 집합이다(FR-2). 계산은 기존 개별 조회 파이프라인(`hotzone:top` 캐시[^1], 임계, 뷰포트 필터)을 그대로 지나온 통과 격자를 `grids.region_code`[^2] 접두로 묶는 메모리 산술이다. 개별 격자 조회의 계약 변경은 없고(PRD 비목표), FE 렌더링은 별도 레인이다.

## 배경 · 목표

지도를 부산 전체나 전국으로 축소하면 최대 50개의 핫 격자 마커가 점으로 뭉쳐 읽을 수 없다. 같은 화면의 도감(MSG-356)과 미션(MSG-437)은 이미 행정 단위 이름 마커로 이 문제를 풀었고, 핫구역만 낱개 격자로 남아 한 화면에서 마커 문법이 갈린다. 세 레이어가 같은 축척 사다리(동, 구, 시)와 글자 단위로 같은 이름 규칙을 쓰게 하는 것이 목표다.

## 성공 기준

- 시, 전국 축척의 넓은 bbox에서 핫구역의 행정 단위 묶음이 200으로 조회된다 (FR-1, FR-12)
- 같은 시각의 개별 조회와 집계가 같은 핫 판정 집합을 본다. 개별과 집계를 갈아타도 세는 대상이 달라지지 않는다 (FR-2)
- 묶음 항목마다 지역 이름, 핫 격자 수, 대표 좌표, 줌인 후 좁힘 재료(gridIds)가 온다 (FR-3, FR-5)
- 코드 접두 길이와 이름 토큰 규칙이 도감, 미션 집계와 동일해 세 레이어 마커가 지역 이름에서 갈리지 않는다 (FR-4)
- 응답이 호출 사용자와 무관하고 비로그인으로도 조회된다 (FR-7, FR-8)
- 아래 "테스트 시나리오"가 전부 green이다

## API 명세

### GET /api/hotzones/aggregation (신설)

넓은 축척용 핫구역 행정 단위 집계. 비로그인 허용(GET permitAll, 아래 보안 절)이고 principal을 받지 않는다. 응답이 사용자 무관이어야 전역 캐시가 성립하고, principal을 안 받는 것이 그 계약의 코드 수준 방어다(기존 `getHotZones`, 미션 집계와 동일 패턴).

**Query 파라미터** (전부 필수. `required = false`로 받아 컨트롤러가 도메인 에러코드로 검증한다. 아래 D5):

| 이름 | 타입 | 의미 |
|---|---|---|
| `unit` | String | 집계 단위. DONG, SIGUNGU, SIDO. 대소문자 무관 (`RegionUnit` 재사용) |
| `swLat` `swLng` `neLat` `neLng` | Double | 남서, 북동 모서리 좌표 |

**검증 우선순위** (복합 오류 시 앞선 검사의 코드가 나간다. 미션 집계와 같은 순서에서 type 단계만 없다):

1. bbox 파라미터 누락 → 8400
2. unit 누락, 미지원 → 8405
3. 좌표가 WGS84 정의역 밖이거나 NaN → 8400
4. 뒤집힌 bbox (sw가 ne보다 북쪽이나 동쪽) → 8400
5. bbox 한 변이 단위별 span 상한 초과 → 8401

**성공 응답**: `SuccessResponse<List<HotZoneRegionAggregateResponseDto>>`. 항목은 regionCode 오름차순, 무귀속(null) 항목이 있으면 마지막이다(MSG-356 `ORDER BY 1 NULLS LAST`, 미션 집계와 동일). 범위 안에 핫 격자가 없으면 빈 배열이다(오류 아님, FR-9). Redis가 유실돼도 같은 빈 배열이다(FR-11).

**에러 케이스**:

| 상황 | HTTP | developCode |
|---|---|---|
| bbox 파라미터 누락, WGS84 정의역 밖, NaN, 뒤집힌 bbox | 400 | 8400 `INVALID_VIEWPORT` (기존) |
| bbox 한 변이 단위별 상한 초과 (DONG 1도, SIGUNGU 4도, SIDO 10도. `RegionUnit.maxSpanDeg` 재사용, 정확히 상한값은 허용) | 400 | 8401 `VIEWPORT_TOO_LARGE` (신설) |
| unit 누락, 미지원 값 | 400 | 8405 `INVALID_AGGREGATION_UNIT` (신설) |

8401과 8405는 미션의 12401, 12405와 상수명과 끝자리를 나란히 맞춘다(grid 4405, mission 12405와 같은 정렬 방침). 8xxx 대역은 이미 hotzone에 배정돼 있어 response-pattern 표 갱신은 없다. `HotZoneErrorCode` 클래스 javadoc의 "면적 상한 없음, MVP 상수는 하나다" 문구는 이번에 낡으므로 함께 고친다.

### 응답 DTO (신설)

```java
// hotzone/dto/HotZoneRegionAggregateResponseDto.java
public record HotZoneRegionAggregateResponseDto(
	String regionCode,     // 묶음 키. 행정동 코드를 단위 길이로 자른 접두 (동 10, 구 5, 시 2자리). 무귀속만 null
	String name,           // 단위 표시 이름 (동 "부전2동", 구 "부산진구", 시 "부산광역시"). 무귀속만 null
	double lat,            // 마커 대표 좌표 위도. 묶음에 속한 핫 격자 셀 중심의 평균 (D3)
	double lng,
	int count,             // 그 단위 안 핫 격자 수
	List<String> gridIds   // 그 묶음의 핫 격자 id, 사전순 오름차순. 크기는 count와 같다 (D4)
) { }
```

count는 핫 격자 수이고 핫스코어[^3] 합산은 싣지 않는다(2026-08-24 사용자 확정, FR-3). `grid/dto/RegionAggregateResponseDto`를 재사용하지 않는 이유는 미션 집계(MSG-437 D4)와 같다. count의 뜻이 다르고(점령 격자 수 대 핫 격자 수) gridIds 필드가 핫구역 전용이라 hotzone 패키지 신설이 경계에 맞다. 기존 개별 조회의 겉면(`HotZoneListResponseDto` 래핑)도 가져오지 않는다. 미션과 도감 집계가 둘 다 배열 직접 응답이라 집계 3종의 겉면을 맞추는 쪽이 FE에 일관된다.

## 도메인 로직

### D-결정

**D1. 집계 대상은 개별 조회 파이프라인의 통과 집합 그대로다 (FR-2, 이 스펙의 핵심 결정).**

`HotZoneServiceImpl.getHotZones`의 판정 경로(`ensureTopCache`로 `hotzone:top` 30초 캐시 보장 → 상위 K(50) 조회 → 최소 임계(3) 필터 → `GridEncoder.viewportRange` 정수 인덱스 뷰포트 필터)를 private 공통 메서드로 추출해 개별 조회와 집계가 같은 판정을 공유한다. 같은 코드가 같은 캐시를 읽으므로 같은 시각의 개별과 집계가 다른 집합을 볼 구조가 없다(MSG-356이 "같은 FROM 절, 같은 술어"로 정합을 보장한 것과 같은 수법의 메모리판).

기각한 대안: 집계 전용 Redis 연산이나 DB 집계 신설. 데이터 원천이 미션(DB 스냅숏)과 달리 Redis Sorted Set이고 재료가 최대 50건이라, 판정을 두 벌로 가르면 정합 근거만 잃고 얻는 것이 없다. 근사값 성질(삭제 미차감, 유실 허용, FR-11)도 파이프라인을 공유하면 자동 승계된다.

**D2. 행정 귀속은 `grids.region_code` 벌크 조회 1회다. 조회는 JPQL 엔티티 조인으로 쓴다. 컬럼 신설도 Flyway 마이그레이션도 없다.**

핫 격자는 업로드가 만든 격자라 grids row가 항상 있고(전역 격자 등록, lazy insert), region_code는 MSG-349가 이름 동봉에 이미 쓰는 저장 라벨이다. 통과 격자 id(최대 50건)로 코드와 전체 경로 이름을 일괄 조회한다. 기존 `GridRepository.findRegionNames`는 이름만 반환하므로 접두 그룹핑에 필요한 코드 원값(10자리)을 함께 싣는 프로젝션[^4] 조회를 추가한다(Owner A 내부 수정).

신규 조회는 native가 아니라 JPQL이다 (Codex 리뷰 2라운드 반영). 영속 컨벤션(project-conventions.md "영속 계층" 4항, 2026-08-19 개정)상 native는 PostgreSQL 전용 기능(ON CONFLICT, PostGIS, advisory lock)과 대량 배치에 한정인데, 이 쿼리는 최대 50개 id의 단순 동등 조인이라 예외 요건이 없다. 기존 `findRegionNames`가 native인 것은 개정 전 코드의 잔존이라 신규 코드의 근거가 못 되고(소급 리팩터링은 안 하되 신규는 JPQL 우선), Region은 타 도메인 엔티티지만 읽기 전용 소비만이라 컨벤션과 충돌이 없다. Grid에 `@ManyToOne` 연관을 새로 달지 않고 Hibernate 6 엔티티 조인(ON 절)으로 잇는다.

전제 수정 두 가지가 grid 패키지에 필요하다. `region/entity/Region`은 이미 regionCode와 regionName을 매핑하고 있지만, `grid/entity/Grid`에는 region_code 매핑이 없어(gridId, gridY, gridX뿐) 읽기 전용 `@Column(name = "region_code")` 필드를 추가한다(연관관계 매핑 아님, 쓰기는 기존 경로 그대로).

```java
// grid/entity/Grid.java: 읽기 전용 @Column(name = "region_code") 필드 추가
// grid/repository/GridRegionCodeNameProjection.java (신설): gridId, regionCode, regionName 세 값
// GridRepository 신설 메서드 스케치 (JPQL 엔티티 조인, 별칭이 프로젝션 게터와 대응):
SELECT g.gridId AS gridId, g.regionCode AS regionCode, r.regionName AS regionName
FROM Grid g LEFT JOIN Region r ON r.regionCode = g.regionCode
WHERE g.gridId IN :gridIds AND g.regionCode IS NOT NULL
```

`region_code IS NULL`인 격자(해상 등)는 결과에 안 나타나고, 조회 결과에 없는 통과 격자가 곧 무귀속이다. 무귀속은 regionCode와 name이 null인 이름 없는 묶음 하나로 마지막에 실린다(FR-6, MSG-356 NULLS LAST와 동일). Region을 LEFT JOIN으로 두는 이유는 orphan region_code(격자에 라벨은 있으나 regions 행 부재, MSG-356 작업 로그의 데이터 엣지)를 코드 있는 묶음으로 유지하기 위해서다. 그 경우 regionCode는 있고 name만 null인 항목이 나올 수 있으며 도감 집계와 같은 동작이다. 빈 통과 집합이면 조회를 생략한다(0건이면 물을 것이 없고, 빈 IN 목록의 방언 차이도 피한다).

**D3. 그룹핑, 이름, 대표 좌표는 전부 메모리 산술이다.**

regionCode를 `RegionUnit.codePrefixLength`로 자른 접두가 묶음 키다(동 10, 구 5, 시 2자리). 이름은 전체 경로 이름("부산광역시 부산진구 부전2동")의 `nameTokenIndex`번째 공백 토큰(동 3, 구 2, 시 1)이고, MSG-356 `split_part`와 미션 집계 D2의 토큰 추출과 글자 단위로 같아야 한다(FR-4). 미션 구현의 토큰 추출과 동작을 맞추되 공용 유틸 승격 여부는 구현 몫이다. 토큰이 모자라는 이름의 동작도 두 선례와 같게 맞추고 검증 테스트는 3토큰 표준형만 고정한다.

대표 좌표는 묶음에 속한 핫 격자 셀 중심(`GridEncoder.center(gridId)`)의 평균이다. 마커가 실제 데이터 위에 서는 규칙(MSG-356의 격자 중심 평균, MSG-437의 귀속점 평균)과 같은 의미이고, `grids.center_geom`을 안 읽는 이유는 격자 id에서 산술로 같은 값이 나오기 때문이다(V28이 center_geom을 GridEncoder와 같은 규칙으로 재계산했고, 개별 조회도 이미 decode 산술로 필터한다). DB 왕복은 D2의 코드·이름 조회 1회로 끝난다.

**D4. 묶음 선택 시 좁힘 재료는 gridIds 동봉이고, 좁힘의 제품 계약은 "줌인 후 교집합"이다 (FR-5, 미션 집계 D5와 같은 계약).**

묶음 마커 선택은 다음 세부 축척으로의 줌인이고, 좁힘은 개별 조회가 성립하는 축척에서 개별 조회 결과와 선택했던 묶음의 gridIds의 교집합으로 완결된다. gridIds만으로 카드를 그리는 화면은 계약 밖이다. 크기는 전 항목 합계가 최대 50(상위 K)이라 미션(관찰값 449)보다도 작아 페이징 논의 자체가 불요하다. 시점 어긋남도 안전하다. `hotzone:top`이 30초 캐시라 집계와 이후 개별 조회의 세대가 다를 수 있지만, 교집합 방식이라 사라진 id는 자연 탈락하고 유령 마커가 생기지 않는다(미션의 1시간 스냅숏보다 창이 훨씬 짧다).

**D5. 파라미터는 `required = false`로 받아 컨트롤러가 도메인 코드로 검증한다 (미션, 도감 집계의 `toBounds`, `toUnit` 패턴).**

기존 핫구역 개별 조회는 `@RequestParam` 필수 기본으로 전역 400 핸들러에 맡기지만, 집계는 unit 누락과 미지원 값을 같은 8405 하나로 수렴시켜야 해서(MSG-356이 4405를 직접 검증으로 만든 이유 그대로) 직접 검증한다. bbox도 같은 엔드포인트에서 검증 방식이 갈리면 안 되므로 함께 직접 검증한다. 기존 개별 조회의 처리 방식은 바꾸지 않는다(계약 불변, PRD 비목표). span 상한 검사는 기존 `validateBounds`에 단위 상한 인자를 받는 형태로 확장하되 개별 조회 경로는 종전 그대로 상한 없이 지나간다(결과가 K로 이미 상한, FR-HOTZONE-09 불변).

**D6. 개별과 집계의 전환 축척은 서버가 정하지 않는다.** 클라이언트가 축척에 맞춰 unit만 바꿔 부르고 서버 방어선은 unit별 `maxSpanDeg`다(MSG-356, MSG-437 D6과 동일, 2026-08-24 사용자 확정).

### 보안 설정

`SecurityConfig`의 MSG-454 GET permitAll 블록에 `"/api/hotzones/aggregation"` 한 줄을 추가한다(핫구역 칩의 비로그인 개방과 동일 원칙, FR-8). GET 한정 matcher 계약도 그대로다. `JwtAuthenticationFilter`의 PUBLIC_AUTH_PATHS에는 넣지 않는다. permitAll은 인증 불요이지 토큰 무시가 아니다(MSG-443 교훈, SecurityConfig 주석 명문).

### 성능

요청당 비용은 Redis 1~2회(캐시 보장 스크립트 + 상위 K 조회)와 DB 벌크 조회 1회(최대 50 id, PK IN)로 기존 개별 조회와 같은 차수다. 개별 조회의 캐시 특성(30초 `hotzone:top`, 만료 순간에도 원자 스크립트로 실패 없음)을 파이프라인 공유로 그대로 승계한다(NFR-PERF-04). 신규 성능 목표는 없다.

## 데이터 모델

## 계약 변경

**`HotZoneService`(계약 인터페이스 4종에 포함, A 제공)에 메서드가 늘어난다. 리뷰 시 상대 팀원 확인 필수.** 기존 `getHotZones`는 불변이다.

```java
// com.msg.fillmap.hotzone.service.HotZoneService 신규 메서드
/**
 * viewport 안 핫 격자를 행정 단위(동, 시군구, 시도)로 묶어 센 집계 목록 (MSG-466).
 * 집계 대상은 getHotZones 와 같은 핫 판정 집합이다 (상위 K, 최소 임계, 뷰포트 필터 공유).
 * region_code 미판정 격자는 키와 이름이 null 인 항목 하나로 마지막에 실린다.
 * bbox 상한은 단위별 차등(RegionUnit.maxSpanDeg), 초과 시 VIEWPORT_TOO_LARGE.
 * 사용자 무관 응답이라 userId 를 받지 않는다. 비로그인 조회 허용 (GET permitAll).
 */
List<HotZoneRegionAggregateResponseDto> getHotZoneAggregates(ViewportBounds bounds, RegionUnit unit);
```

이 인터페이스의 소비처는 둘이다 (Codex 리뷰 3라운드 정정). hotzone 컨트롤러와, Owner B의 `notification/relay/HotZoneEntryDetector`가 10분 주기 전국 bbox로 `getHotZones(KOREA_BOUNDS)`를 불러 핫구역 진입 알림을 검출한다(MSG-181). 신설 메서드는 추가일 뿐 기존 시그니처가 불변이라 B 코드 변경은 여전히 0이지만, D1이 `getHotZones`의 필터 파이프라인을 공통 메서드로 추출하는 리팩터링을 포함하므로 그 경로의 동작 불변이 B 소비처(전국 bbox 상위 K 의미론)에도 걸린다. 아래 테스트 시나리오의 기존 경로 회귀 검증이 이를 고정한다. 그 외 계약 인터페이스(`GridQueryService`, `UserGridQueryService`, `UserOidcCommandService`)는 전부 불변이고, `RegionUnit`(grid.dto)과 `ViewportBounds`는 문서된 용법 안의 소비다. `GridRepository`의 프로젝션 조회와 `Grid` 엔티티 필드 추가(D2)는 Owner A 내부 수정이라 계약 밖이다.
