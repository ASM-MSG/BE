# MSG-596: 도감 요약의 방문 행정동 수를 영상이 아니라 행정동별 집계에서 센다

**Owner**: B (`com.msg.fillmap.usergrid.*` 내부 native 쿼리 수정, Owner A 접점 없음)

> PRD 면제: 성능 개선이고 요구사항(응답 계약 `CollectionSummaryResponseDto`·지표 의미)은 불변이다
> (CLAUDE.md 면제 기준). 성능 목표를 새로 세우지 않았다 — 티켓의 완료 기준은 "규모별 실측표가 남고
> MSG-246 의미 테스트가 그대로 통과한다"이고, 이 스펙은 그 기록이다. 지표 의미의 정본은
> `docs/spec/MSG-246.md`(by-grid 귀속·DELETED 제외·BLINDED 포함)이며 그대로 재사용한다.
>
> 개발은 담당자(강정민)가 직접 했고 AI는 실측 하네스·힌트·리뷰만 맡았다(티켓 본문 명시).

## 개요

도감 요약 `GET /api/collections/summary`는 `UserGridRepository.getCollectionSummary` 한 문장에 지표 6개를
스칼라 서브쿼리[^1]로 담는다. 그중 `visitedRegionCount`(방문한 서로 다른 행정동 수)만 `videos`를
영상 1건당 1행으로 훑고 `grids`를 조인한 뒤 `COUNT(DISTINCT region_code)`를 셌다. 영상이 많은 사용자일수록
느려지는 유일한 지표였고, 실측 기록이 없었다(MSG-152·246·362 스펙 전부).

이번 수정은 그 서브쿼리 하나를 **이미 운영 중인 행정동별 집계 테이블 `region_stats`**를 읽는 것으로
바꾼다. 응답 계약, 메서드 시그니처, 프로젝션, 나머지 지표 5개, DB 스키마, 인덱스, 마이그레이션 어느 것도
바뀌지 않는다. 새 빈도 없다.

## 배경 · 목표

- 로컬 실측(격자 61만·영상 135만)에서 격자 40만 사용자의 도감 요약 응답이 1.1~1.4초였고, 그 사용자 요청을
  5%만 섞은 부하에서 **50 rps부터** 커넥션 풀 10개가 전부 그 쿼리에 잡혀 응답 중앙값이 34초로 무너졌다.
- 목표는 이 지표의 비용을 사용자 영상 수·격자 수에 비례하지 않게 만드는 것. 지표 의미는 그대로.

## 성공 기준

1. MSG-246 의미 테스트 9건(DELETED 제외·BLINDED 포함·무라벨 격자 제외·같은 동 중복 1회 등)이 무수정 통과.
2. 등가성: 개선 전 서브쿼리와 개선 후 서브쿼리가 벤치 사용자 전원(204명)에서 같은 값(mismatch 0).
3. 헤비 5% 혼합 부하에서 50 rps에 무너지던 것이 1,000 rps 계단까지 dropped 0·500 0·풀 대기 0.

## 도메인 로직

### 진짜 원인

답은 "행정동 몇 개"인데 세는 대상이 영상 전부였다. 격자 하나에 영상이 열 개여도 행정동은 하나이므로
영상을 하나씩 볼 이유가 없고, 격자를 하나씩 볼 이유도 없다. 실행 계획으로는 보통 사용자(격자 384·영상 2,000)도
`videos` 2,000행 → `grids` PK 1,920회 → 정렬 → DISTINCT에 병렬 워커 기동까지 얹혀 27ms였고(그중 20ms가
병렬 오버헤드), 헤비 사용자(격자 38만)는 병렬 해시 조인 + 정렬 디스크 spill로 700ms~1.4초였다.

### 해결

`region_stats(user_id, region_code) → collected_count`는 탐험률 화면을 위해 이미 존재하는 테이블이고,
첫 점령과 점령 롤백 시점에 업로드·삭제 트랜잭션 안에서 `RegionStatsCommandService.refresh`가
`user_grids ⨝ grids` 기준으로 재계산해 둔다. 방문 행정동 수는 그 행 중 `collected_count > 0`인 것의 수다.

```sql
-- before (MSG-246)
(SELECT COUNT(DISTINCT g.region_code)::int
	FROM videos v
	JOIN grids g ON g.grid_id = v.grid_id
	WHERE v.user_id = :userId AND v.status <> 'DELETED') AS "visitedRegionCount",
-- after (MSG-596)
(SELECT COUNT(*)::int
	FROM region_stats WHERE user_id = :userId AND collected_count > 0) AS "visitedRegionCount",
```

사용자당 최대 행 수는 행정동 수(3,558)이고 PK `(user_id, region_code)` 범위 스캔 한 번이다.

### 결과 집합이 같은 이유

- **점령 롤백 규칙**: 격자의 내 영상이 전부 삭제되면 `user_grids` 행이 지워지고 그 순간 `refresh`가 돌아
  해당 행정동의 `collected_count`가 다시 계산된다. 따라서 "삭제되지 않은 영상이 있는 격자"의 집합과
  `user_grids` 행 집합이 같고, 그 격자들의 행정동 집합이 `collected_count > 0`인 행정동 집합이다.
- **BLINDED**: 블라인드 전환은 롤백 경로를 타지 않아 `user_grids`에 남는다. 종전 쿼리도 `status <> 'DELETED'`라
  BLINDED를 포함했다. 양쪽 동일.
- **무라벨 격자**(`grids.region_code IS NULL`, 바다 등): `refresh`가 행을 만들지 않는다. 종전 `COUNT(DISTINCT)`도
  NULL을 세지 않았다. 양쪽 동일.
- **롤백으로 0이 된 행**: `refresh`는 행을 지우지 않고 0으로 둔다. 그래서 `collected_count > 0` 필터가 필요하다.
- 실측 등가성: 벤치 사용자 204명 전원에서 before/after 값 비교 mismatch 0 (`scripts/bench-msg596-region-stats-backfill.sql` 마지막 SQL).

## 기각한 대안

1. **`user_grids` 축으로만 교체 (1단계)**: 보통 사용자는 충분하지만 헤비 사용자가 격자 38만 행을 병렬 해시 조인으로
   읽는 구조가 남아 300 rps에서 무너진다. 요청마다 병렬 워커를 띄우는 것 자체가 동시성 위험이다.
2. **커버링 인덱스** `grids(grid_id) INCLUDE (region_code)`·`user_grids(user_id) INCLUDE (video_count)` (2단계):
   보통 사용자 블록 −25%뿐이고 헤비 경로에는 플래너가 쓰지 않는다. 최종 쿼리가 `region_stats`라 이 API에 더는
   쓰이지 않으므로 마이그레이션에 넣지 않았다(로컬 DB에만 만들었다 DROP).
3. **`COUNT(DISTINCT)` → GROUP BY 서브쿼리** (3단계): 정렬 spill은 없앴지만 조인 행 수는 그대로라 절반 개선.
4. **Redis 카운터 신설**(참고 글의 해법): 이미 운영 중인 쓰기 시점 집계가 있어 새 저장소·새 갱신 코드가 필요 없다.
   티켓 범위 밖 조건("인덱스·재작성으로 부족하다는 실측 뒤에만")은 충족했지만 기존 테이블로 끝났다.

## 남는 한계와 승격 조건

- **진실이 읽기 시점에서 쓰기 시점으로 옮겨갔다.** `user_grids`를 직접 쓰는 모든 경로(시드·백필·배치·테스트
  픽스처)가 `region_stats`를 함께 챙겨야 한다. 리포지토리 테스트 8건이 이 우회를 즉시 잡는다(아래 테스트 절).
- **[Codex P2, 미해결 — 담당자 판단 대기]** `RegionSeeder.run`이 기동 시 `backfillGridRegionCodes()`로 무라벨 격자에
  라벨을 채우지만(regions 후착 환경, MSG-167) `region_stats`는 다시 세지 않는다. 종전 쿼리는 라벨을 실시간으로
  읽어 백필 직후 바로 반영됐고, 이 쿼리는 그 사용자가 그 행정동에서 다음 업로드·삭제를 하기 전까지 0으로 남는다.
  탐험률(MSG-167)은 처음부터 같은 구멍이 있었고 이번에 방문 행정동 수까지 같은 구멍에 얹힌다. 닫는 법은 백필이
  1건 이상 라벨을 바꿨을 때 `user_grids ⨝ grids ⨝ regions`로 전 사용자 재계산 UPSERT를 한 문장 더 도는 것
  (`scripts/bench-msg596-region-stats-backfill.sql`의 INSERT에서 사용자 조건을 뺀 형태, 기동 1회·멱등).
- `grids.region_code`를 재라벨링(백필)하면 `region_stats`는 옛 값으로 남는다. 그때는 재계산이 필요하며 SQL은
  `scripts/bench-msg596-region-stats-backfill.sql`의 INSERT 부분을 대상 사용자 조건만 바꿔 쓰면 된다.
- `refresh`가 재계산 방식인데 업로드 advisory lock이 pending S3 키 단위(사용자 단위 아님)라, 같은 사용자의
  같은 행정동·다른 격자 동시 업로드에서 READ COMMITTED lost update로 `collected_count`가 1 적게 남을 수 있다.
  다음 refresh에서 복구되고 방문 행정동 수(> 0 판정)에는 영향이 없다. 별도 안건.
- 헤비 사용자의 남은 30ms(`totalGridCount`·`SUM(video_count)`)는 `SUM(collected_count) FROM region_stats`로 같은
  방식이 가능하다. 다음 과제.
- 관측 교훈: Tomcat 200 스레드가 다 막히자 actuator도 응답을 못 해 Prometheus가 앱 지표를 잃었다.
  `management.server.port` 분리는 별도 안건.
