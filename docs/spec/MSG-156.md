# MSG-156: 내 행정동별 수집률 조회 API (`GET /api/regions/stats`)

**Owner**: A
— region 패키지의 **read 경로만**이다. 엔드포인트는 MSG-93이 만든 `RegionController`에 추가, 읽기 서비스·리포지토리 쿼리·DTO 전부 `com.msg.fillmap.region.*`. Owner B 접점 없음(155와 달리 트리거 배선 불필요). 크로스오너 계약 4종 불변 → §계약 변경 "없음".

> `region_stats`(수집률 캐시)를 **읽기만** 한다. 이 캐시를 **채우는 주체는 MSG-155**(`RegionStatsCommandService.refresh`, 점령/롤백 시 동기 recompute UPSERT). 본 티켓은 그 캐시를 `regions`와 조인해 **행정동별 수집률 리스트**로 내보내는 순수 SELECT다.
>
> **구현 선행조건(필수)**: **MSG-155 merge**. 이 워크트리(`BE-msg156`, develop 기준)에는 155 코드(`RegionStatsCommandService`·recompute UPSERT·트리거 배선)가 **아직 없다**. 155 없이도 이 API는 동작하지만(빈 테이블 → 빈 배열) 의미 있는 데이터는 155가 채워야 나온다. 테스트는 155 write 경로에 의존하지 않고 **`region_stats` 합성 row를 직접 시드**한다(§테스트).
>
> **PO 확정(2026-07-21)**: 기본 노출 = **행정동별 수집률**. 시/도 상위 집계("서울 34%")는 **MVP 이후 별도 티켓**(§범위 제외). `regions.parent_code` 체인 재료는 이미 준비돼 있음만 언급한다.
>
> **형제 경계**: MSG-93(`RegionQueryService`·`RegionController`·`RegionErrorCode` — 재사용) / MSG-152(`visitedRegionCount` = 영상 좌표축, 본 티켓 수집률 = 격자 중심축, 의미 분리 — §Open Q) / MSG-154(`regions.total_grid_count` = 분모 정본) / MSG-155(`region_stats` 쓰기 — 선행) / **MSG-156(본 티켓, 읽기)**.

## 개요

로그인 사용자의 `region_stats(user_id, region_code)`를 `regions`와 조인해 **행정동별 수집률 리스트**로 반환한다. `parentCode`(시군구)로 필터하고, `collectedOnly`로 "수집한 행정동만" vs "손댄 행정동 전부(롤백 0행 포함)"를 고른다. **geospatial 연산 0** — `region_stats` SELECT + `regions` equi-join뿐이라 조회 경로 ADR(핫패스 geospatial 금지)을 자연 준수한다(§도메인 로직).

```
GET /api/regions/stats?parentCode&collectedOnly  (인증 필수, userId = AuthPrincipal)
        │
        ▼  RegionStatsQueryService.findStats(userId, parentCode, collectedOnly)  (Owner A, readOnly)
   [parentCode 존재 검증]  parentCode != null 이고 regions.parent_code 에 없으면 → 6404
   region_stats rs JOIN regions r ON r.region_code = rs.region_code
        WHERE rs.user_id = :userId
          AND (:parentCode IS NULL OR r.parent_code = :parentCode)
          AND (:collectedOnly = FALSE OR rs.collected_count > 0)
        → List<RegionStatResponseDto> (빈 결과 = 빈 배열, 에러 아님)
```

**스키마 변경·마이그레이션·엔티티 신설 없다.** 산출물 = 엔드포인트 1개 + read 서비스(`RegionStatsQueryService`) + `RegionRepository` read 쿼리 1개 + 프로젝션 + 응답 DTO + `RegionErrorCode.REGION_NOT_FOUND(6404)`.

## 배경 · 목표

- **사용자/제품 관점**: 도감 화면에서 "내가 어느 행정동을 얼마나 채웠나"를 리스트로 보여줘야 한다("강남구 역삼1동 25%"). 155가 `region_stats`를 정확히 채워도 **읽는 API가 없으면** FE가 렌더할 값이 없다.
- **목표**:
  1. `region_stats`를 사용자별로 읽어 `regions`(이름·상위코드)와 합쳐 **행정동별 수집률 리스트**를 낸다.
  2. `parentCode`(시군구) 필터와 `collectedOnly` 토글을 제공한다.
  3. 조회 경로를 **순수 SELECT**로 유지(geospatial 0) — 155가 쓰기 시 물질화한 `total_count`·`progress_rate` 덕에 조회는 계산이 없다.
  4. 155의 0-row 유지 정책(D5)이 만든 "수집했다 0이 된 행"과 "아예 없는 행"의 구분을 `collectedOnly` 의미로 확정한다(§D1).

## 성공 기준 (관찰 가능)

1. 인증 사용자가 `GET /api/regions/stats` 호출 → 자기 `region_stats` 행이 `regions` 조인으로 `regionName`·`parentCode`까지 채워진 리스트로 반환된다.
2. `parentCode=X` → `regions.parent_code = X`인 행정동 stats만 반환.
3. `collectedOnly=true`(기본) → `collected_count > 0` 행만. `collectedOnly=false` → 롤백으로 0이 된 행 포함(그 사용자가 **손댄** 행정동 전부).
4. 수집한 행정동이 없거나 필터 결과가 없으면 → **빈 배열 + 200**(에러 아님, DoD).
5. `parentCode`가 제공됐지만 **실존하지 않는 시군구 코드**(어떤 `regions.parent_code`에도 없음)면 → **6404 REGION_NOT_FOUND**(§D3).
6. `progressRate`는 **100.00으로 clamp**되어 나온다(§D4). `updatedAt` = 해당 `region_stats.updated_at`(캐시 기준 시각).
7. 다른 사용자의 stats가 섞이지 않는다(`user_id` 스코프).
8. 조회 경로에 **geospatial 연산 0**(ST_Covers 등 없음) — region_stats SELECT + regions equi-join만(§도메인 로직).
9. 스키마 변경·마이그레이션 없음. 크로스오너 계약 4종 불변. 공유 로컬 DB 미오염, 전체 테스트 green.

## 결정 (Decisions)

### D1 — `collectedOnly` 기본값 = **true**, false = **손댄 행정동 전부(0-row 포함)** (전체 regions outer-join 아님)

- **결정**: `collectedOnly`(optional boolean) **기본값 `true`**. `true` → `collected_count > 0` 행만(도감 = 수집한 곳 리스트). `false` → 그 사용자의 `region_stats` 행 **전부**(155 D5로 남은 `collected_count = 0` 롤백행 포함). **전체 3,558 `regions` outer-join(미점령 행정동 0%까지 나열)은 하지 않는다** — 그건 별도 티켓(§범위 제외).
- **근거**:
  1. **도감 UX 기본 = 수집한 곳 리스트** → 기본값 `true`가 화면 요구와 일치. 미수집 행정동을 0%로 나열하면 강남구만 필터해도 수백 dong이 쏟아져 리스트가 무의미.
  2. **0-row vs no-row(155 D5)**: 155는 롤백 0을 DELETE 않고 UPSERT로 남긴다. 그 이력이 의미 있는 화면(예: "한 번 채웠다 비워진 곳")을 위해 `collectedOnly=false`가 **손댄 행 전부**를 노출한다. `true`가 그 0행을 걸러 순수 도감을 준다.
  3. **DoD 정합(핵심)**: "빈 결과 = 빈 배열". 전체 regions outer-join이면 리스트가 절대 비지 않아 DoD와 모순. 그래서 `false`도 **sparse한 region_stats만** 읽는다(전체 regions 아님) → 수집 이력 없는 사용자는 `false`여도 빈 배열.
- **155 D5와의 관계(명시)**: 155 D5 근거는 "156이 no-row도 0%로 폴백하면 0-row≡no-row"였다. 156은 **그 전체 폴백을 MVP에서 안 한다**. 따라서 `collectedOnly=false`에서 **0-row는 보이고 no-row는 안 보인다**(관측상 비동치) — 이는 롤백 이력 노출이라는 의도된 동작이며, 155의 DELETE 회피(단일 UPSERT 경로) 정당성은 그대로 유효하다. 전체 폴백이 필요해지면 별도 티켓에서 outer-join으로 추가한다.

### D2 — 페이지네이션 = **없음**(MVP), 인위적 LIMIT 도 없음 (2026-07-22 정정)

- **결정**: cursor·offset 페이지네이션 도입하지 않는다. 단순 `List` 반환, **LIMIT 없음**.
- **근거**:
  1. **결과가 구조적으로 유한**: 사용자당 region_stats 행은 최대 regions 행 수(**3,558**)를 넘을 수 없다. `parentCode` 필터 시 시군구당 행정동 수십 개.
  2. **MSG-90(cursor)은 뷰포트 격자 수천~수만 건**이라 정당했다. 여기는 상한 3,558의 유한 집합이라 cursor 복잡도(인코딩·정렬키·재조회)를 정당화하지 못한다.
- **정정 이력**: 최초안은 `LIMIT 1000` 안전 상한을 뒀으나 Codex 리뷰 지적으로 제거 — 전국 1,000개 초과 수집 사용자의 유효 데이터를 **아무 신호 없이 절단**해 "parentCode 없으면 전체" 계약을 위반하는 반면, 실제 응답 폭주는 구조적 상한(3,558)이 이미 막고 있어 지키는 것이 없었다. `ponytail: 무커서 무LIMIT List, 전 행정동 규모(3,558행) 응답이 실측 문제 되면 그때 MSG-90식 cursor 도입.`

### D3 — `REGION_NOT_FOUND(6404)` = **parentCode가 실존하지 않는 시군구일 때만**. "데이터 없음"은 6404 아님(빈 배열)

- **결정**: `RegionErrorCode.REGION_NOT_FOUND(6404, NOT_FOUND, "존재하지 않는 행정 구역 코드입니다")` 추가. **`parentCode`가 제공됐고 어떤 `regions.parent_code`에도 없으면**(= 실존하지 않는 시군구) 6404. 유효한 `parentCode`인데 사용자 수집이 없으면 → **빈 배열 + 200**. `parentCode` 미제공(전국)은 6404 불가.
- **근거**: DoD가 "빈 결과 = 빈 배열(에러 아님)"이라 6404는 **데이터 유무**가 아니라 **클라이언트 입력 오류**(오타·없는 코드)를 가른다. 실존 시군구인데 안 채웠으면 그건 정상적 빈 리스트(0% 상태), 없는 코드로 필터하면 그건 잘못된 요청이라 404. 존재 검증은 `SELECT EXISTS(SELECT 1 FROM regions WHERE parent_code = :parentCode)` 1건(`idx_regions_parent` 사용, geospatial 아님).
- **대안 반려**: "형식만 검사(숫자 5자리)하고 없는 코드는 빈 배열"은 6404를 사실상 미사용으로 만들고 오타 UX가 나빠 반려. "빈 결과도 6404"는 DoD 위반이라 반려.
- 서비스가 검증·throw(`ApiException(REGION_NOT_FOUND)`), 컨트롤러는 얇게 유지.

### D4 — `progress_rate` = **표시 시 100.00 clamp**(`LEAST(progress_rate, 100.00)`), 저장값(raw)은 155 그대로

- **결정**: 응답 `progressRate`는 조회 SELECT에서 `LEAST(rs.progress_rate, 100.00)`로 **100 상한 clamp**. `region_stats`에 저장된 raw 값은 155가 쓴 그대로(무변경).
- **근거**: 155 D4/Open Q1대로 `total_grid_count`가 면적 근사(MSG-154 D1)라 `progress_rate`가 100 초과 가능. 사용자에게 "103%"는 혼란 → **표시단(156)에서 clamp**, 무결성/디버깅용 raw는 캐시에 보존(155 = raw 저장, 156 = 표시 clamp로 역할 분리 확정 — 155 Open Q1 종결).

### D5 — 서비스 배치 = **`RegionStatsQueryService` 신설**(RegionQueryService에 안 얹음), 155 Command와 대칭

- **결정**: stats read를 위한 `region/service/RegionStatsQueryService`(+impl) 신설. MSG-93 `RegionQueryService.resolveByPoint`에 **추가하지 않는다**.
- **근거**:
  1. **책임 분리**: `RegionQueryService`는 **geospatial 역지오코딩**(ST_Covers)이다. stats read는 **순수 SELECT**(geospatial 0). 한 서비스에 섞으면 "조회 경로 geospatial 0"이라는 성질이 흐려진다.
  2. **대칭성**: 155가 `RegionStatsCommandService`(write)를 세웠다. read는 `RegionStatsQueryService`(read) — 프로젝트의 Query/Command 분리 컨벤션(`GridQueryService` 등)과 정합. 신규 발명 아님.
  3. **오너 경계**: 둘 다 region 패키지 내부(Owner A 자기완결). `RegionStatsQueryService`는 `RegionController`(Owner A)만 소비 → **크로스오너 계약 아님**(§계약 변경). 155 command와 달리 grid-dev/auth-dev 상호 확인 불필요.

## API 명세

### `GET /api/regions/stats` — 내 행정동별 수집률 조회 (인증 필수)

- **인증**: 필수. `userId` = `@AuthenticationPrincipal AuthPrincipal principal → principal.userId()`. 미인증은 SecurityConfig(anyRequest authenticated) → 401.
- **Query params**:

| 이름 | 타입 | 필수 | 기본값 | 의미 |
|---|---|---|---|---|
| `parentCode` | String | 아니오 | (없음=전국) | 상위 시군구 코드. 지정 시 그 시군구 산하 행정동만. **실존하지 않으면 6404**(§D3) |
| `collectedOnly` | boolean | 아니오 | **true** | `true`=수집한(`collected_count>0`) 행정동만, `false`=손댄 행정동 전부(0-row 포함)(§D1) |

- **성공 응답**: `SuccessResponse<List<RegionStatResponseDto>>` (HTTP 200, developCode 200). **빈 배열 허용**(수집 없음·필터 결과 없음 = `[]`).

`RegionStatResponseDto` (record, `RegionResponseDto` 패턴 복제):

|---|---|---|---|
| `regionCode` | String | `region_stats.region_code` | |

## 도메인 로직

### `RegionStatsQueryService.findStats(userId, parentCode, collectedOnly)` (Owner A, readOnly)

1. `parentCode != null`이면 존재 검증: `regionRepository.existsByParentCode(parentCode)` 거짓 → `throw new ApiException(RegionErrorCode.REGION_NOT_FOUND)`(§D3).
2. `regionRepository.findStats(userId, parentCode, collectedOnly)` → `List<RegionStatProjection>` → `List<RegionStatView>` 매핑(컨트롤러가 DTO로).

**read 쿼리** — `RegionRepository`(native, region_stats 대상):
```sql
SELECT
    rs.region_code    AS "regionCode",
    r.region_name     AS "regionName",
    r.parent_code     AS "parentCode",
    rs.collected_count AS "collectedCount",
    rs.total_count    AS "totalCount",
    LEAST(rs.progress_rate, 100.00) AS "progressRate",   -- §D4 clamp
    rs.updated_at     AS "updatedAt"
FROM region_stats rs
JOIN regions r ON r.region_code = rs.region_code
WHERE rs.user_id = :userId
  AND (:parentCode IS NULL OR r.parent_code = :parentCode)
  AND (:collectedOnly = FALSE OR rs.collected_count > 0)
ORDER BY r.parent_code, r.region_name
```
- **geospatial 0**(성공 기준 8): `ST_Covers`/`ST_MakePoint` 등 없음 — PK equi-join뿐. 조회 경로 geospatial 금지 ADR 준수. (분모·rate는 155가 쓰기 시 물질화해 조회 시 재계산 불필요.)
- `parent_code` 필터·`ORDER BY r.parent_code`는 `idx_regions_parent` 활용. `user_id`는 region_stats PK 선두라 인덱스 태움.
- boolean 파라미터 바인딩 형태(`:collectedOnly`)는 구현자가 native boolean 캐스트로 확정.

존재 검증:
```sql
SELECT EXISTS(SELECT 1 FROM regions WHERE parent_code = :parentCode)
```

### 조회 경로 ADR 정합 (명시)
- 본 API는 **순수 SELECT + PK equi-join** — 조회/실시간 핫패스 geospatial 금지 규칙과 무관. 155가 쓰기 시점 recompute로 넣은 값을 그대로 읽는다.
- v6 ADR(region-grid 비연결) 무관 — 여기선 격자를 만지지 않고 이미 집계된 `region_stats`만 읽는다.

## 데이터 모델

- **Flyway 마이그레이션 없음. 스키마 변경 전무.** `region_stats`(`V1__init.sql` L130–139)·`regions`(L53–61) 이미 존재.
- **`RegionStats` 엔티티 안 만든다**(YAGNI): 조회는 join 프로젝션이라 root 엔티티 매핑이 불필요. 155의 write native와 대칭으로 read native + 인터페이스 프로젝션(`RegionStatProjection`, `regionCode`/`regionName`/`parentCode`/`collectedCount`/`totalCount`/`progressRate`/`updatedAt` 별칭)을 쓴다 — `RegionProjection`(MSG-93) 선례와 동일.
- **read 쿼리 위치 = `RegionRepository`**: 155 write UPSERT도 여기 얹혔으므로 read도 여기 두는 게 일관. `RegionRepository extends JpaRepository<Region, String>`에 `@Query(nativeQuery=true)` 메서드 2개(`findStats`, `existsByParentCode`) 추가.
  - **ceiling**: 이제 `region_stats` 접근이 155(write)+156(read) 둘이라 155 ponytail 노트의 분리 트리거에 근접. 단, native 2~3개는 아직 `RegionRepository`로 충분. `ponytail: region_stats 접근/쿼리가 더 늘면 RegionStatsRepository로 분리, 지금은 얹는다.`

## 테스트 시나리오 (JUnit5 + AssertJ · 한국어 백틱 메서드명 · 모듈 단위)

> **테스트 격리(MEMORY 'shared local DB' · MSG-93/154/155 §격리 원칙)**: DB 테스트는 **합성 fixture**만 쓴다 —
> 자기 유저 신규 생성 + 합성 `region_code`(`RegionTestFixtures.syntheticCode`, 실존하지 않는 999 sido 대역) + `region_stats` **합성 row 직접 시드**(155 write 경로에 의존하지 않음 — 이 워크트리에 155 미merge) + `@Transactional` 롤백.
> `regions`·`region_stats`를 **truncate하지 않는다**(공유 DB FK — NonUniqueResult). 실데이터 `regions`(3,558행)는 불가침. 합성 region은 `RegionRepository.upsert`(MSG-154, `ON CONFLICT DO NOTHING`류)로 시드.
> `parentCode`는 합성 region의 `parent_code`(999 대역 앞 5자리)를 쓴다 — 실데이터 시군구 코드와 충돌하지 않음.

### 모듈 1 — read 쿼리 (`RegionRepository.findStats` native, DB 통합 · 합성 fixture)
- `내_region_stats를_regions와_조인해_regionName과_parentCode가_채워진다`

## 미해결 질문 (Open Questions)

1. **`visitedRegionCount`(영상 축) vs 수집률 `collectedCount`(격자 중심축) 노출 문구** — `visitedRegionCount`(MSG-152, `/api/collections/summary`)는 **방문 = 영상 좌표(`videos.region_code`)** 기준 서로 다른 행정동 수이고, 본 API `collectedCount`는 **수집 = 격자 중심점 귀속**(155 D2) 기준이다. 의미상 자연 분리지만 두 지표가 한 화면에 보일 때 "방문 행정동 5개인데 수집률 리스트엔 3개"처럼 어긋나 보일 수 있다 — **노출 문구/라벨 정리는 FE·기획 확인 필요**. (155 Open Q2에서 156으로 이관된 항목, 여기서도 코드 결정 없이 문구 이슈로 유지.)

> **결정으로 종결된 155 이관 항목**:
> - `progress_rate > 100%` 표시 → **§D4에서 100 clamp 확정**(155 Open Q1 종결).
> - 미점령 행정동 0% 폴백 → **§D1/범위 제외로 확정**(MVP는 손댄 행만, 전체 regions outer-join은 별도 티켓).
