# MSG-492: 코스 미션 포토스팟 표시 이름

> 선행 정본: `docs/prd/MSG-492-prd.md` (상태 검토됨, 2026-08-26 승인)
> 작성일: 2026-08-26 · Owner B (mission 패키지) · **Owner A 계약 1건에 메서드 추가**(§계약 변경)

## 개요

코스 미션 상세와 목록의 포토스팟 항목에 표시 이름을 싣는다. 원본 산출물이 가진 명소 이름을
적재해 그대로 내보내고, 명소가 없는 지점은 그 자리의 격자 표시명을 적재 시점에 계산해 채운다.

산출물 파일과 수집 파이프라인은 건드리지 않는다. 이미 파일에 들어 있는데 적재 단계에서
버리고 있던 필드를 읽기 시작하는 작업이다.

## 배경 · 목표

지금 스팟 항목은 `gridId`·`lat`·`lng`·`seq` 넷뿐이라 응답에 이름이 없다. 그래서 **화면은
스팟마다 `GET /api/regions/reverse-geocode`를 따로 부르고 있다**(라이브 실측 2026-08-27 —
`35.0512,128.9663` → `"부산광역시 사하구 다대1동"`). 코스 하나를 열면 스팟 수만큼 왕복이 생기고,
그 응답이 `data: null`인 지점이 "이름 없는 경유 지점"으로 뜬다.

**더 큰 손실은 따로 있다.** `courses-seed.json`의 스팟 989개는 전부 `name`을 갖고 있는데 파서가
그걸 버려서, 광안리해수욕장 같은 명소 417곳이 전부 동 이름으로 뭉개져 나간다. 이름이 이미 파일에
있는데 아무도 안 읽고 있는 상태다.

격자 쪽으로 이름을 얻는 길은 막혀 있다. 코스 스팟 972칸 중 951칸(98%)은 `grids` 테이블에 행
자체가 없다 — 격자 행은 업로드 확정 때 lazy insert 되므로 아무도 안 다녀간 경유 지점은 조회할
대상이 존재하지 않는다. `reverse-geocode`가 동을 돌려주는 것은 그쪽이 `grids`가 아니라 `regions`
공간 조회라서다.

`courses-seed.json`의 스팟 989개는 전부 `name`을 갖고 있다. `CourseRecord` 클래스 주석이
"spots[].name/method 도 미적재(운영 검수용, MSG-222 계약에 없음)"라고 명시한 대로 파서가
`seq`와 `gridId`만 꺼낸다.

**dev 실측 (2026-08-26)**

| 항목 | 값 |
|---|---|
| 코스 · 스팟 · 고유 격자 | 148개 · 989개 · 972칸 |
| `method` 분포 | `tourapi` 417 / `geometric-fallback` 572 |
| `grids` 행 없는 스팟 격자 | 951 / 972 (98%) |
| 스팟 좌표 역지오코딩 성공 | 910 / 972 (94%) |
| 실패 62칸의 경계 거리 | 300m 내 55칸, 밖 7칸 (최대 2,189m) |

목표는 PRD FR-1~FR-11이다. 요약하면 972칸 전부가 빈 이름 없이 표시되고, 명소는 원본 이름
그대로, 나머지는 구역 안이면 `구역명 + " " + 칸번호`(예 `"서면 A-14"`)·밖이면 행정동 이름으로
대신하며, 목록과 상세가 같은 이름을 낸다.

## 성공 기준

1. 코스 미션 상세와 목록의 스팟 항목에 `name`이 실린다. 기존 필드 4종은 그대로다
2. `method=tourapi` 스팟은 산출물 이름이 글자 그대로 나간다
3. `method=geometric-fallback` 스팟은 격자 표시명이 나간다. `"경유점 3"` 같은 자리표시는
   응답 어디에도 나타나지 않는다
4. 행정동에도 구역에도 안 걸리는 스팟은 가장 가까운 행정동 이름을 받는다
5. 조회 경로에 쿼리가 한 건도 늘지 않는다. 이름은 저장된 값을 그대로 통과시킨다.
   화면이 이름을 얻으려고 스팟마다 돌던 `reverse-geocode` 왕복도 없어진다
6. 이미 등재된 코스 148개가 시더 재실행으로 채워진다. 삭제·재적재가 필요 없다
7. 판정·진행도·스탬프·뱃지 동작이 변하지 않는다

## API 명세

변경은 응답 한 곳이다. `MissionShape.Spot`에 필드 하나가 붙는다.

**영향 받는 조회**

- `GET /api/missions/active` — `type=COURSE`의 `shape.spots[]`
- `GET /api/missions/{missionId}` — 코스 미션의 `mission.shape.spots[]`

```jsonc
{
  "gridId": "16752_11357",
  "lat": 35.0512,
  "lng": 128.9663,
  "seq": 5,
  "name": "다대2동"     // 신규. nullable
}
```

`name`은 nullable로 선언한다. 이 레포의 `required`는 키 존재를 뜻하므로 `required` + `nullable`
병기다(MSG-383 선례). 값이 null인 경우는 아래 둘뿐이다.

- 코스가 아닌 유형의 스팟. `PathShape`는 코스 전용이라 실제로는 도달하지 않는다
- 시더 갱신 전이라 이름 재료가 없고 격자 표시명도 못 구한 지점

화면은 기존 안내 문구를 폴백으로 남겨 둔다. null은 오류가 아니다.

`MissionDetailResponseDto.SpotStats`는 변경하지 않는다. 이름은 `shape.spots`에만 실린다.

## 도메인 로직

### 1. 이름 결정 규칙

스팟 하나의 표시 이름은 아래 순서로 처음 값이 나오는 자리에서 멈춘다. **판정은 전부 적재
시점에 끝나고, 결과 문자열 하나가 `mission_grids.name`에 저장된다(D-2).**

```text
① 산출물 name (method=tourapi)                     → 그대로                       ("광안리해수욕장")
② ZoneNameResolver.name(y, x) 가 NONE 이 아니면    → zoneName + " " + zoneCell   ("서면 A-14")
③ RegionQueryService.resolveByPoint(중심 좌표)     → regionName 의 마지막 토큰   ("다대2동")
④ RegionQueryService.resolveNearestByPoint(중심)   → regionName 의 마지막 토큰   ("다대2동")
⑤ null
```

`ZoneNameResolver.name`은 문자열이 아니라 `ZoneCellName(zoneName, zoneCell)` 레코드를 돌려주고,
구역 밖은 null이 아니라 `ZoneCellName.NONE`(두 필드 null)이다. 그래서 ②의 판정은
`zoneName != null`이고, 문자열 조립은 이 스펙이 서버에서 한다.

**이 조립은 기존 규칙에서 의도적으로 벗어난다(D-7).** 지금까지 서버는 `zoneName`·`zoneCell`·
`regionName` 재료만 내려주고 조립은 클라이언트 몫이었다(`ZoneCellName` 클래스 주석 명문). 코스
스팟은 응답 필드가 문자열 `name` 하나라 재료 셋을 실을 자리가 없다. 근거와 대안은 D-7에 적었다.

⑤에 도달하는 경우는 실측상 없다. 972칸 전부가 ①~④ 안에서 이름을 얻는다. 그래도 null을 계약에
남기는 것은 시더 갱신 전 상태(FR-7)와 훗날 데이터가 늘 경우를 위해서다.

### 2. 적재 — 최종 표시 이름을 굳힌다

`CourseSeedReader.toSpots`가 `name`과 `method`를 함께 읽고, **`method`가 `tourapi`일 때만**
`CourseRecord.Spot.name`에 담는다. `geometric-fallback`이면 null이다. `"경유점 3"`은 지명이
아니라 자리표시라 여기서 버린다(D-1).

시더가 그 다음에 ②~④를 돌려 빈 자리를 채우고, **완성된 문자열을 `mission_grids.name`에
저장한다.** 리졸버는 시더 실행당 1회 만들고, 행정동 판정은 이름이 빈 스팟에 대해서만 돈다.

`method` 자체는 저장하지 않는다(D-3).

검증은 기존 전량 거부 계약을 따른다. `method`가 `tourapi`·`geometric-fallback` 밖이면 던진다.
`name`은 `requireText`로 문자열임을 확인하되 **`method=tourapi`인데 공백만 있으면 함께 던진다** —
`requireText`(`CourseSeedReader.java:266`)는 `isTextual`만 보므로 빈 문자열이 통과하고, 빈 이름이
저장되면 ①에서 걸려 폴백이 돌지 않은 채 빈 제목이 화면에 나간다(FR-1 위반). 산출물 한 줄이
깨졌는데 조용히 넘어가면 그 코스만 이름 없이 남는다.

### 3. 적재 — 이미 등재된 코스 갱신

`CourseMissionSeeder`는 지금 이미 있는 코스를 만나면 메타데이터만 갱신하고 `continue`한다.
`mission_grids`는 최초 INSERT 이후 다시 쓰이지 않는다. 그대로 두면 dev·prod의 148개 코스가
영원히 이름 없이 남는다.

skip 분기에 이름 갱신을 얹는다. MSG-383이 메타데이터에 만든 "재실행이 곧 백필"과 같은 형태다.

```text
이미 등재된 코스
  → applyMetadata (기존)
  → 스팟 이름 갱신 (신규)
      같은 (mission_id, grid_id)의 name 만 UPDATE
      seq·격자 집합·target_count·path 는 건드리지 않는다
```

**격자 집합은 절대 바꾸지 않는다.** 스팟 격자가 바뀌면 이미 발급된 스탬프의 근거가 흔들리고
진행도가 요동친다. 이 갱신이 바꾸는 값은 `name` 하나다.

정확히는 더티 체킹이 내는 UPDATE 문에 `seq` 도 실린다 — 하이버네이트 기본 동작이 엔티티의 가변
컬럼 전부를 쓰기 때문이다. 다만 실리는 값은 방금 읽어온 그 값이라 결과가 달라지지 않는다.
`@DynamicUpdate` 로 문장을 좁히지 않는 이유는, 얻는 것이 SQL 모양뿐인데 캐시된 문장을 매번
새로 만드는 대가를 치르기 때문이다. 격자 집합·`target_count`·`path` 는 이 경로가 아예 손대지 않는다.

산출물에 없는 `(mission_id, grid_id)`는 건너뛴다. **명소였다가 `geometric-fallback`으로 바뀐
스팟은 null로 되돌리지 않고 폴백 계산 결과로 덮는다.** 적재 시점 계산(D-2)에서는 저장값이 언제나
최종 표시 문자열이라 코스 스팟에 null이 남는 상태 자체가 없다. 막아야 하는 것은 명소가 억제
목록에 올라 빠졌는데 옛 이름이 그대로 남는 것뿐이다.

### 4. 조회 — 통과만 한다

`MissionQueryServiceImpl.pathShape`가 `grid.getName()`을 그대로 `Spot.name`에 옮긴다. **조회
경로에 쿼리가 늘지 않고 새 의존도 생기지 않는다.**

목록과 상세가 같은 컬럼을 읽으므로 **정상 운영 중에는** 두 화면의 이름이 갈리지 않는다. 다만
목록은 조립된 DTO를 1시간 스냅숏으로 들고 있어(`CACHE_TTL`), **시더가 이름을 갱신한 직후 최대
1시간 동안 목록이 옛 이름을 보일 수 있다.** 이것은 이름만의 성질이 아니라 미션 제목·기간·이미지
등 스냅숏이 담는 모든 값이 이미 갖고 있는 창이고(MSG-383 메타데이터 백필도 같다), 시더 실행
시점은 운영자가 고른다. 이 티켓에서 캐시 무효화를 새로 만들지는 않는다.

메모도 TTL도 리졸버 호이스팅도 없다. 초안은 조회 시 계산이었는데, 그것을 지키려다 메모와 TTL이
붙고 그 둘이 다시 목록·상세 세대 불일치를 만들었다. 판정을 적재로 옮기면 셋 다 사라진다(D-2).

zones·regions가 바뀌면 시더를 다시 돌려 이름을 갱신한다. 그 재실행은 어차피 운영 절차에 이미
있다(§3).

### 5. 최근접 행정동

`ST_Covers`가 비면 `boundary_geom <-> 점`으로 가장 가까운 행정동을 찾는다. `regions.boundary_geom`은
`GEOGRAPHY(MULTIPOLYGON, 4326)`이고 GIST 인덱스(`idx_regions_boundary`, V1)가 있어 KNN이 인덱스를
탄다.

**거리 상한을 두지 않는다.** 상한은 계산 비용을 막으려고 두는 장치인데 이 경로는 격자당 생애
1회라 비용이 문제되지 않고, 대상 집합이 실측된 972칸이라 최댓값이 2,189m로 이미 확인됐다.
상한을 두면 그 7칸만 이름 없이 남아 FR-1을 스스로 깨뜨린다.

**동률은 `region_code`로 가르되, 정렬 키로 덧붙이지 않는다.** 경계선에서 거리가 같은 행정동이 둘이면
KNN 순서만으로는 결과가 비결정적이라 재실행 때 이름이 바뀐다. 그런데 `ORDER BY 거리, region_code`로
쓰면 **인덱스를 통째로 잃는다** — PostgreSQL 은 `ORDER BY`가 KNN 연산자 하나뿐일 때만 GIST 순서
스캔을 쓰고, 키가 하나라도 더 붙으면 전량을 읽어 정렬한다.

dev 실측(2026-08-27, 행정동 3,558건)이 이렇다.

| 쿼리 | 실행 계획 | 실행 시간 |
|---|---|---|
| `ORDER BY 거리, region_code LIMIT 1` | Seq Scan on regions | 1,666 ms |
| `ORDER BY 거리 LIMIT 1` | Index Scan using idx_regions_boundary | 13 ms |
| **2단 (안쪽 거리만 LIMIT 8 → 바깥 동률 정렬)** | **Index Scan + Incremental Sort** | **20.7 ms** |

그래서 2단으로 쓴다. 안쪽이 거리만으로 최근접 8건을 인덱스로 뽑고, 바깥이 그 8건 안에서만
`region_code`로 가른다. 후보 8은 "한 점에서 동시에 최단거리인 행정동"의 현실적 상한이다 —
행정동 경계는 변을 공유하므로 실제 동률은 2~3개이고, 실측에서 `LIMIT 8`을 걸어도 인덱스가 읽은
행은 2건이었다.

이 조회는 **`RegionQueryService`에 새 메서드로 낸다**(§계약 변경). Owner B가
`RegionRepository`를 직접 부르면 "두 도메인의 접점은 인터페이스로만"이 깨진다. 기존
`resolveByPoint`의 의미(포함 판정, 없으면 `Optional.empty`)를 바꾸지 않는 것도 중요하다 —
그 계약은 지금 다른 소비처가 "없음"을 신호로 쓰고 있다.

호출은 **시더에서만** 일어난다. 조회 경로는 이 메서드를 부르지 않는다.

이 조회는 **코스 스팟 전용 경로에서만** 쓴다. `grids.region_code` 라벨링(`upsertGrid`,
`backfillGridRegionCodes`)은 건드리지 않는다. 그쪽은 영상이 올라온 격자의 귀속을 정하는 값이라
"가까우니 그 동으로 친다"를 넣으면 동별 집계와 수집률 분모가 흔들린다.

### V43__mission_grid_spot_name.sql

```sql
ALTER TABLE mission_grids ADD COLUMN name VARCHAR(100);
```

- **저장값은 최종 표시 문자열이다.** 명소 이름이든 구역 표시명이든 행정동 이름이든 완성된 형태로 들어간다

  이지만(V31) 그쪽은 외부 원문을 그대로 받는 자리라 폭이 다르다
- **인덱스 없음.** 이 컬럼으로 검색하거나 정렬하지 않는다
- 백필 없음. 값은 시더가 채운다

`MissionGrid`에 `name` 필드를 더하고, 코스 시드용 생성자를 `(missionId, gridId, seq, name)`으로
넓힌다. 기존 2인자·3인자 생성자는 그대로 둔다(축제·팝업 시더가 쓴다).

이름 갱신은 더티 체킹으로 처리한다. `applyName(String)`이 값이 실제로 달라질 때만 대입하고
바뀌었는지를 boolean으로 돌려준다(`Mission.applyMetadata`와 같은 형태).

집계는 **`SeedResult`에 필드를 하나 더한다.** 기존 `updated`는 "메타데이터가 바뀐 미션 수"라
단위가 미션이고(`CourseMissionSeeder.java:114`), 이름 갱신은 단위가 스팟이라 같은 칸에 더하면
로그가 뜻을 잃는다. `spotNamesUpdated`로 따로 센다.

## 결정 사항

### D-1. 자리표시 이름은 저장하지 않는다

산출물의 `"경유점 3"`은 파이프라인이 이름 자리를 비워 두지 않으려고 넣은 값이지 지명이 아니다.
저장하면 이름 결정 규칙 ①에서 걸려 폴백이 영영 안 돈다. `method=tourapi`일 때만 담는다.

기각한 대안은 "저장하되 조회 때 `경유점 ` 접두로 판별"이다. 문자열 패턴으로 데이터 의미를
되찾는 구조라, 파이프라인이 문구를 바꾸면 조용히 깨진다.

### D-2. 대체 이름을 적재 시점에 계산해 저장한다 (초안 번복)

초안은 "저장하지 않고 조회 때 계산"이었다. 근거는 두 가지였다. 구역 데이터가 바뀌어도 이름이
따라가고, 훗날 출처 필드가 필요할 때 서버가 어느 분기를 탔는지 알고 있어 공짜로 더할 수 있다.

**둘 다 값이 작았고 대가가 컸다.** Codex 교차 리뷰 2라운드에서 드러난 연쇄가 이렇다.

```text
조회 때 계산
  → 스팟마다 행정동 판정 왕복        → PRD 비기능("상세 5회 고정") 위반
  → 막으려고 gridId 메모 도입        → 영구 메모면 갱신이 재기동까지 안 붙음
  → 막으려고 메모 TTL 도입           → 스냅숏 TTL과 세대가 어긋나
                                       목록·상세 이름 불일치 (PRD FR-6 위반)
```

장치를 하나 넣을 때마다 다음 구멍이 열렸다. 판정을 적재로 옮기면 넷이 한꺼번에 없어진다.
조회는 컬럼 통과라 쿼리가 0이고, 목록과 상세가 같은 값을 읽는다. 시더가 이름을 갱신한 직후
목록 스냅숏이 만료되기 전까지 최대 1시간은 예외이며, 그 창은 §도메인 로직 4와 PRD FR-6에
명시했다.

포기하는 것도 적어 둔다. 구역·행정동 데이터가 바뀌면 **시더를 다시 돌려야** 이름이 따라온다.
그 재실행은 이미 운영 절차에 들어 있고(§도메인 로직 3), zones는 손으로 그리는 48건이라 자주
바뀌지 않는다. 출처 필드가 필요해지면 그때 `method` 컬럼을 더한다. 컬럼 하나 값이지
설계를 뒤집을 값이 아니다.

### D-3. 이름 출처를 응답에 담지 않는다

PRD 비목표에 확정으로 올라 있다(2026-08-26). 대체 이름이 `"다대2동"` 형태라 이름만으로
명소가 아님이 드러나고, 화면이 둘을 시각적으로 가를지는 디자인이 정하지 않았다.

이 결정으로 SRS FR-MISSION-19의 뒷 문장("정식 명소가 아님을 구분한다")은 부분 충족으로 남는다.
요구 상태를 올릴 때 이 차이를 함께 적는다.

`method`를 DB에 저장하지 않는 것도 같은 판단이다. 지금 아무도 안 읽는 값이라 두지 않고,
필요해지면 그때 컬럼 하나를 더한다(D-2).

### D-4. 대체 이름에 순번을 붙이지 않는다

화면이 항목 부제로 이미 "3번째 스팟"을 찍는다. `"다대2동 경유점 3"`으로 만들면 한 줄 안에서
순번이 두 번 나온다. 한 코스가 같은 동을 여러 번 지나 이름이 겹쳐도 부제가 가른다(PRD FR-11).

### D-5. 최근접 행정동에 거리 상한을 두지 않는다

§도메인 로직 5에 근거를 적었다. 대상이 실측된 고정 집합이고 최댓값이 2.2km라 상한이 막을
것이 없으며, 두면 7칸이 이름 없이 남는다.

### D-6. 시더 skip 분기에 이름 갱신을 얹는다

MSG-383이 메타데이터에 만든 "재실행이 곧 백필" 형태를 그대로 쓴다. 마이그레이션으로 백필하지
않는 이유는 이름의 출처가 DB 밖 산출물 파일이라 SQL이 읽을 수 없어서다.

갱신은 `name` 한 컬럼만 만진다. 격자 집합·seq·target_count·path는 불변이라 스탬프와 진행도가
영향을 받지 않는다(성공 기준 7).

### D-7. 표시명 문자열 조립을 서버가 한다 (기존 관행에서 벗어남)

이 레포는 지금까지 격자 이름을 **재료로만** 내려줬다. `ZoneCellName` 클래스 주석이 그 원칙을
명문으로 적고 있다("행정동 폴백 문자열 조립은 서버가 하지 않는다"). 다만 재료 구성은 응답마다
다르다 — 셋을 다 싣는 응답도 있고, `regionName`만 있는 것도, 장소 검색처럼 `address`를 쓰는
것도 있다. 공통점은 "조립을 서버가 안 한다"이지 "필드 셋이 늘 같다"가 아니다.

코스 스팟은 그 방식을 못 쓴다. 응답 항목이 문자열 `name` 하나이고, 재료 셋을 싣자고 스팟
항목에 필드 세 개를 더하면 화면이 쓰지도 않을 분기를 계약에 박게 된다. 이름 하나가 필요한
자리라 이름 하나를 준다.

**행정동은 마지막 토큰만 쓴다.** `region_name`은 `"부산광역시 사하구 다대2동"` 형태의 전체
경로라 목록 한 줄에 그대로 넣으면 줄이 넘친다. 이 잘라내기도 기존 규칙에는 없던 것이다.

대가를 명확히 적어 둔다. 같은 격자를 지도 응답으로 보면 재료가 오고 코스 스팟으로 보면 조립된
문자열이 온다. **기존 조립을 이 함수로 단일화하지는 않는다** — 지금 조립은 클라이언트와 화면
문맥에 흩어져 있어 서버 함수 하나로 모을 대상이 아니다. 이 티켓이 만드는 것은 코스 전용 조립
한 자리이고, 훗날 다른 화면도 조립본을 원하면 그때 그 함수를 공유한다.

이 결정은 glossary "표시명" 항목과 어긋나므로 **구현 시 glossary에 코스 스팟 예외를 한 줄
등재한다.** 같은 항목의 "행정동도 없으면(해상 등) 표시명 없음"도 이 티켓의 최근접 폴백(D-5)과
어긋나 함께 손봐야 한다.

### D-8. `mission_grids`에 행정동 코드를 같이 저장하지 않는다

검토한 대안은 `region_code` 컬럼을 함께 두고 응답에 `regionName`을 실어, 화면이
`reverse-geocode`를 아예 끊게 하는 것이었다. 동기는 두 가지였다 — 왕복 제거, 그리고 스팟 격자의
행정동을 서버가 알고 있게 해서 탐험률과 엮는 것.

**두 번째 동기가 성립하지 않는다.** 탐험률·도감 표시명·업로드 확정 응답의 `regionName`은 전부
`grids.region_code` 하나를 읽는다. 그 값은 업로드 확정 때 `upsertGrid`
(`VideoRepository.java:294`)의 `ST_Covers` 서브쿼리가 붙인다. `mission_grids`에 무엇을 저장하든
그 경로는 쳐다보지 않으므로 탐험률은 1도 바뀌지 않는다.

**넣으면 오히려 어긋남을 새로 만든다.** `upsertGrid`에는 최근접 폴백이 없어서, 이 스펙이 최근접으로
이름을 채워주는 62칸은 실제로 영상이 올라가면 `region_code`가 NULL이 된다.

| | 스팟 카드 (`mission_grids`) | 업로드 후 (`grids`) |
|---|---|---|
| 정상 910칸 | 다대2동 | 다대2동 |
| 최근접 폴백 62칸 | 다대2동 | **NULL — 무귀속** |

카드에는 동이 떠 있는데 거기 올린 영상은 어느 동의 탐험률에도 안 잡히는 상태가 된다. 지금은 양쪽
다 이름이 없어 최소한 일관된다.

**진짜 고칠 자리는 `upsertGrid`의 `ST_Covers`다.** 거기에 최근접 폴백이 들어가면 탐험률·도감·업로드
응답이 한 번에 정리되고 이 컬럼이 필요 없어진다. 다만 `grids.region_code`는 동별 수집률의 분모를
정하는 값이라 폴백을 넣으면 기존 모든 동의 숫자가 움직이고, 바다 격자를 육지 동에 귀속시키는 것이
옳은지가 기획 판단이다. 표시 이름 티켓이 감당할 파급이 아니라 **별도 티켓으로 낸다.**

왕복 제거만 남는데, 그것만으로는 컬럼을 더할 이유가 못 된다. 화면이 동을 계속 쓰려면 지금 쓰는
`reverse-geocode`를 그대로 두면 되고, 그건 성능이지 기능 결손이 아니다.

## 작업 로그

### 저장 위치

`mission_grids.name VARCHAR(100)` 한 곳이다 (V43). Redis·S3·별도 캐시를 쓰지 않는다.

값은 **완성된 표시 문자열**이고 무엇이 채웠는지(명소·구역·행정동)는 저장하지 않는다. 코스가 아닌
유형(EVENT·POPUP·THEME·CONTINUOUS)의 스팟 행은 `name`이 NULL인 채로 남는다 — 그쪽 시더는
2·3인자 생성자를 쓰고 그 생성자가 `name`에 null을 넣는다.

목록 응답은 기존 1시간 스냅숏(`MissionQueryServiceImpl.CACHE_TTL`)에 조립된 DTO째로 담기므로,
시더가 이름을 갱신한 직후 최대 1시간은 목록이 옛 값을 보인다. 상세는 스냅숏을 안 타서 즉시 반영된다.

### 실행 쿼리 (실측 — 하이버네이트 SQL 로깅, 2026-08-27)

**신규 코스 적재** — 스팟당 INSERT 1회. `saveAll`이지만 배치로 묶이지 않는다.

```sql
insert into mission_grids (name, seq, grid_id, mission_id) values (?, ?, ?, ?)
```

**이미 등재된 코스 갱신** — 코스당 SELECT 1회 + 이름이 실제로 바뀐 스팟마다 UPDATE 1회.

```sql
select mg1_0.grid_id, mg1_0.mission_id, mg1_0.name, mg1_0.seq
from mission_grids mg1_0
where (mg1_0.grid_id, mg1_0.mission_id) in ((?, ?))

update mission_grids set name=?, seq=? where grid_id=? and mission_id=?
```

`seq`가 UPDATE에 실리는 것은 `@DynamicUpdate`가 없어서다(§도메인 3). **실측으로 확인했고 의도한
상태다** — 실리는 값은 같은 트랜잭션에서 방금 읽어온 그 값이다.

**최근접 행정동** — 이름이 빈 스팟에서 `ST_Covers`가 비었을 때만 1회.

```sql
SELECT "regionCode", "regionName", "parentCode"
FROM (
    SELECT region_code AS "regionCode", region_name AS "regionName", parent_code AS "parentCode",
        boundary_geom <-> ST_SetSRID(ST_MakePoint(?, ?), 4326)::geography AS distance
    FROM regions
    ORDER BY boundary_geom <-> ST_SetSRID(ST_MakePoint(?, ?), 4326)::geography
    LIMIT 8
) nearest
ORDER BY distance, "regionCode"
LIMIT 1
```

dev 실행 계획 실측 (2026-08-27, 행정동 3,558건):

```text
Limit  (actual time=20.542..20.543 rows=1)
  ->  Incremental Sort  (actual time=20.540..20.541 rows=1)
        Sort Key: (boundary_geom <-> ...), region_code
        Presorted Key: (boundary_geom <-> ...)
        ->  Limit  (actual time=20.255..20.444 rows=2)
              ->  Index Scan using idx_regions_boundary on regions
                    Order By: (boundary_geom <-> ...)
Execution Time: 20.700 ms
```

**초안의 한 문장 `ORDER BY 거리, region_code`는 인덱스를 안 탔다** — 같은 조건에서 Seq Scan
1,666ms(128배)였다. 구현 중 실측으로 발견해 2단으로 바꿨다(§도메인 5).

**조회 경로** — 쿼리가 늘지 않았다. `pathShape`가 이미 로드한 `MissionGrid`의 컬럼을 읽을 뿐이라
스팟 수와 무관하게 문장 수가 같다(`CourseSeedContractTest.상세_조회_문장수가_스팟_수와_무관하다`).

### 예외 흐름

전부 **시더 경로**에서만 발생하고, 사용자 요청 경로에는 이 티켓이 만든 예외가 없다.

| 어디서 | 무엇이 | 결과 |
|---|---|---|
| `CourseSeedReader.toSpotName` | `name` 누락·비문자열 | `IllegalStateException` → 파싱 단계라 **전량 거부**, DB 무변경 |
| `CourseSeedReader.toSpotName` | `method=tourapi`인데 이름이 공백 | 같음 |
| `CourseSeedReader.toSpotName` | `method`가 두 값 밖 | 같음 |
| `RegionQueryServiceImpl.resolveNearestByPoint` | 서비스범위 밖 좌표 | `ApiException(6400)` — **도달하지 않는다.** `CourseSpotNameResolver`가 부르기 전에 막고 null을 돌린다 |

파싱이 저장보다 먼저 전부 끝나므로 부분 적재가 없다. 저장 단계에서 예외가 나면 `run`의
`@Transactional`이 전체를 롤백한다.

`GlobalExceptionHandler`는 이 경로에 관여하지 않는다 — 시더는 HTTP 요청 밖 `ApplicationRunner`다.

### 빈 동작 · 생명주기

`CourseMissionSeeder`는 `@Order(40)` `ApplicationRunner`이고 `fillmap.mission.course.seed.enabled=true`
일 때만 돈다. Region(10) · Zone(20) 시더 뒤라 **`regions`·`zones`가 이미 채워진 상태에서 이름을
계산한다** — 이 순서가 뒤집히면 모든 스팟이 최근접 폴백조차 못 찾아 null이 된다.

`CourseSpotNameResolver`는 **빈이 아니다.** `seed(Path)` 안에서 `new`로 만들고 그 실행이 끝나면
버린다. `ZoneNameResolver`가 `zones` 전량을 들고 있어 스팟마다 만들면 989회 전량 로드가 되므로
실행당 1회만 만든다.

`run`의 `@Transactional`은 프록시 경계라 **`seed(Path)`를 직접 부르는 테스트에는 안 걸린다** —
테스트는 자기 `@Transactional`로 감싸 롤백 격리한다.
