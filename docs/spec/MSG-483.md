# MSG-483: AI 경로 추천 보행 경로 표시

**Owner**: B

> 요구사항 정본: `docs/prd/MSG-483-prd.md` (검토됨, 2026-08-26 성민 승인).
> 이 스펙은 PRD의 FR 1~10과 비기능 요구에 "어떻게"만 붙인다.
> SRS 연결: FR-ROUTE-16, FR-ROUTE-17, NFR-SEC-10, NFR-OPS-09, FR-ROUTE-05 개정 (2026-08-26 등재).

## 개요

AI 경로 추천(MSG-457) 결과에서 지점을 잇는 선을 직선에서 실제 보행로 모양으로 바꾸고, 카드의
거리 안내를 실제 걷는 거리로 바꾼다. 서버는 신규 엔드포인트 `POST /api/routes/walk-paths` 하나를
연다. 클라이언트가 추천 응답의 이웃 좌표쌍(출발지 구간 포함, 최대 8개 세그먼트[^1])을 보내면
서버가 TMap 보행자 경로안내 API를 대신 호출해 세그먼트별 보행 좌표열과 실거리를 돌려준다.
추천 API `POST /api/routes/recommend`의 요청과 응답 계약은 바꾸지 않는다.

함께, 추천 이유 사실 문장 조립에서 직전 지점까지의 직선거리 항목을 뺀다(FR-10, FR-ROUTE-05 개정).
카드의 실거리와 이유 문장 속 하버사인[^2] 직선거리가 나란히 어긋나 보이는 상황을 없애기 위해서다.

**Owner 판정**: route 패키지는 협업 원칙에서 공동 라벨(주 구현 B, MSG-457 §Owner 판정)이지만,
이번 범위는 route 패키지 안에서 완결되고 계약 인터페이스 변경과 Owner A 접점 신설이 없다.
spec-driven-dev 배정은 **B(auth-developer) 단독**으로 한다.

## 배경 · 목표

직선 연결은 건물과 길 없는 곳을 가로질러 동선의 신뢰를 깎는다. 걷기 코스(두루누비)는 실측 GPX가
있어 표시만 바꾸면 됐지만, AI 추천은 지점 조합이 요청마다 달라 두 지점 사이 걷는 길을 그때그때
계산해야 한다. MSG-457 스펙이 비목표로 남긴 "도보 경로 계산"을 이 티켓이 뒤집는다(요구사항 변경,
PRD 게이트 통과). 국내 도보 길찾기 공개 API는 SK TMap이 사실상 유일하고, 무료 한도(일 1,000건,
보행자는 "경로안내" 그룹 한 행이라 그룹 합산으로 보수 계획)로 지금 규모를 감당한다.

목표는 세 가지다. 추천 결과의 선이 실제 보행로를 따르고, 카드 거리가 실거리로 나오고, 길찾기가
실패하거나 한도가 소진되면 지금의 직선으로 조용히 폴백[^3]해 추천 기능 자체는 죽지 않는 것이다.

## 성공 기준

- 추천 결과의 이웃 좌표쌍으로 `POST /api/routes/walk-paths`를 호출하면 세그먼트별 보행 좌표열과
  실거리(미터)가 요청과 같은 개수, 같은 순서로 온다 (FR-ROUTE-16).
- 같은 좌표쌍을 다시 조회하면 외부 호출 없이 응답하고, 캐시 키의 TTL 24시간이 받은 데이터의
  보관과 사용을 함께 24시간 안에 묶는다 (NFR-OPS-09, TMap 약관 준수사항).
- TMap 호출이 실패한 세그먼트는 실패 표시로 오고, 나머지 세그먼트와 추천 기능은 영향이 없다
  (FR-ROUTE-17).
- 하루 외부 호출이 설정 한도에 닿으면 그날의 미스 세그먼트는 외부 호출 없이 실패로 떨어진다.
  캐시에 있는 세그먼트는 계속 성공한다 (FR-ROUTE-17, NFR-OPS-09).
- TMap 인증 키는 서버 설정에만 있고, 조회는 로그인 필수다 (NFR-SEC-10).
- 추천 이유 문장 조립 입력에 "이전 지점에서 X.Xkm" 항목이 더는 없다 (FR-ROUTE-05 개정).
- 기존 추천 API 테스트가 계약 변경 없이 green이다 (FR-ROUTE-16의 계약 불변 조항).

## API 명세

### POST /api/routes/walk-paths (신규)

세그먼트 보행 경로 조회. 인증은 recommend와 동일하게 SecurityConfig anyRequest로 강제된다
(비로그인 개방 6종에 포함되지 않음, MSG-469 확정. 미인증은 401). 좌표쌍 목록은 요청 본문으로
받는다. 시각 필드가 없어 시각 컨벤션(MSG-376) 검사 대상이 아니다.

**RouteWalkPathRequestDto**

```json
{
	"segments": [
		{ "startLat": 35.1587, "startLng": 129.1604, "endLat": 35.1631, "endLng": 129.1635 }
	]
}
```

| 필드 | 타입 | 규칙 |
|---|---|---|
| `segments` | 배열 | 1~8개 (지점 상한 8이라 세그먼트 최대 7개에 출발지 구간 1개, FR-ROUTE-13 파생). null 원소 불허 |
| `startLat` `startLng` `endLat` `endLng` | double | 한국 서비스 범위 (위도 33~39, 경도 124~132, SRS 2.4 전역 제약). 범위 비교가 NaN과 무한대까지 함께 걸러낸다. 구현 타입은 박싱 `Double` — Jackson 3는 record 원시 double의 필드 누락에 역직렬화 실패(공통 400)를 던져 14402 수렴이 깨지므로, 누락과 null도 범위 검증으로 흘려 14402에 수렴시킨다 (2026-08-26 TDD 실측) |

검증은 서비스에서 한 코드로 수렴한다: `segments`가 null이거나 비었거나 9개 이상, **원소가
null이거나**(JSON `[null]`이 목록 크기 검증만 통과해 null 역참조 500으로 새는 것을 막는다, Codex
교차 리뷰 4라운드 적발), 좌표가 한국 서비스 범위 밖이면 전부 400 + **14402
`INVALID_WALK_SEGMENTS`** 다(뷰포트 검증 14400이 시행하는 SRS 2.4 제약을 같은 방식으로 적용, FE
분기 단일화). WGS84 정의역만 보면 해외 좌표 세그먼트로 일 한도를 소진시키는 경로가 열린다(Codex
교차 리뷰 1라운드 적발). 출발과 도착이 같은 좌표인 세그먼트는 거부하지 않고 TMap 결과에
맡긴다(실패하면 실패 표시).

**RouteWalkPathResponseDto** (요청과 같은 개수, 같은 순서)

```json
{
	"segments": [
		{
			"resolved": true,
			"path": [ { "lat": 35.1587, "lng": 129.1604 }, { "lat": 35.1589, "lng": 129.1611 } ],
			"distanceMeters": 742
		},
		{ "resolved": false, "path": null, "distanceMeters": null }
	]
}
```

| 필드 | 타입 | 의미 |
|---|---|---|
| `resolved` | boolean | 보행 경로 확보 여부. false면 클라이언트는 그 세그먼트를 직선과 직선거리 안내로 유지한다 (FR-5) |
| `path` | 배열, nullable | 보행로를 따르는 좌표열 (위도, 경도 순의 객체). 실패 시 null |
| `distanceMeters` | Integer, nullable | 실제 걷는 거리 (TMap totalDistance, 미터). 실패 시 null |

**실패 케이스**

| 상황 | 응답 |
|---|---|
| 미인증 | 401 (공통) |
| 세그먼트 목록 형식 위반 | 400 + `14402 INVALID_WALK_SEGMENTS` "유효하지 않은 구간 목록입니다" |
| 기능 플래그 꺼짐 (`route.walk.enabled=false`) | 503 + `14504 ROUTE_WALK_DISABLED` "보행 경로 표시가 꺼져 있습니다" (14503 선례와 같은 명시적 비활성. 404를 주면 FE가 기능 없음과 기능 꺼짐을 구분하지 못한다) |
| TMap 호출 실패, 형태 위반, 일 한도 소진 | **에러가 아니라 200** 에 해당 세그먼트 `resolved: false` (부분 실패 허용, FR-ROUTE-17). 별도 사용자 안내 없음 (2026-08-26 성민 확정) |

한도 소진을 에러 응답으로 갈라 주지 않는 이유: 클라이언트의 폴백 동작이 "실패 세그먼트는 직선
유지" 하나뿐이라(FR-9, 별도 안내 없음), 부분 실패와 전체 실패를 한 형태로 수렴하면 FE 분기가
하나가 된다. 캐시 히트 세그먼트는 한도 소진 중에도 성공으로 준다(외부 호출이 아니다).

`RouteErrorCode`에 상수 2개를 추가한다(14xxx 대역은 MSG-457 배정 그대로, 대역 표 갱신 불요):
`INVALID_WALK_SEGMENTS(14402, BAD_REQUEST)`, `ROUTE_WALK_DISABLED(14504, SERVICE_UNAVAILABLE)`.

### TMap 보행자 경로안내 호출 (서버 내부)

`TmapWalkClient`가 전담한다 (KakaoLocalClient, RouteIntentClient 선례의 어댑터).

| 항목 | 값 |
|---|---|
| 엔드포인트 | `POST {base-url}/tmap/routes/pedestrian?version=1` |
| 인증 | `appKey`[^4] 요청 헤더 (서버 설정 주입, NFR-SEC-10) |
| 본문 | `startX`(출발 경도), `startY`(출발 위도), `endX`, `endY`, `startName`(고정 "출발"), `endName`(고정 "도착"), `reqCoordType`, `resCoordType` 모두 `WGS84GEO` |
| 타임아웃 | 연결 1초, 교환 전체 3초 (카카오 NFR-PERF-07 선례. JdkClientHttpRequestFactory로 교환 전체 시한, RouteIntentClient 선례) |

응답은 GeoJSON[^5] FeatureCollection이다. 첫 Point feature의 `properties.totalDistance`(미터)를
실거리로, LineString feature들의 `coordinates`를 순서대로 이어붙여 좌표열로 삼는다. GeoJSON
좌표는 경도가 먼저라 응답 DTO로 옮길 때 위도, 경도 순서로 뒤집는다. 형태 검증은 신뢰 경계
원칙(NFR-SEC-08의 BE 몫)대로 한다: totalDistance가 없거나 음수, **LineString feature가 없거나
이어붙인 좌표열의 총 점이 2개 미만**(거리만 있고 선을 그릴 수 없는 응답이 `resolved: true`로
나가는 것을 막는다, Codex 교차 리뷰 1라운드 적발), LineString 좌표가 정의역 밖, 좌표열 총 점수
5,000점 초과는 형태 위반으로 그 세그먼트를 실패 처리한다. 필드명과 형태는 TMap 공식 문서
기준으로 적었으므로 구현 첫 단계에서 실호출 1건으로 대조한다.

로그에는 TMap 응답 본문과 좌표 값을 남기지 않는다(클래스명과 상태 코드만, KakaoLocalClient
선례). appKey는 어떤 로그와 응답에도 싣지 않는다.

## 도메인 로직

처리 순서: 세그먼트 검증(14402) → 플래그 게이트(14504) → 세그먼트를 순서대로 하나씩, 캐시 조회 →
미스면 일 한도 선점 → TMap 호출 → 형태 검증 → 캐시 저장. 전 구간 읽기 전용이고 저장 의존이
없다(FR-ROUTE-09와 같은 구조).

빈 구조는 MSG-457 선례 그대로다. `RouteWalkPathService`와 구현체는 상시 빈, `TmapWalkClient`만
`@ConditionalOnProperty(prefix = "route.walk", name = "enabled")` 조건부 빈이라 서비스는
`ObjectProvider`로 받고 부재 시 14504를 던진다.

**1. 좌표쌍 캐시 (FR-8, NFR-OPS-09)**

- 저장소는 **Redis, 키당 TTL[^6] 24시간**이다. 키는
  `route:walk:seg:{startLat}:{startLng}:{endLat}:{endLng}`(Double.toString 정규형. Java와 JSON의
  double 왕복이 값을 보존해 같은 세그먼트는 같은 키가 된다), 값은 좌표열과 거리의 JSON 직렬화다.
  저장은 `SET ... EX 86400` 단일 명령이라 값과 TTL이 원자로 함께 걸린다(한도 카운터와 달리 Lua가
  필요 없다). TTL 만료는 Redis의 능동 삭제라 FR-8의 문면("받은 데이터의 **보관**과 사용은
  24시간을 넘기지 않는다")을 저장소가 스스로 지킨다.
- 프로세스 메모리 LRU[^7](parse 해석 캐시 선례)를 쓰지 않는 이유 두 가지(Codex 교차 리뷰 3라운드
  적발): 조회 시점 TTL 검사는 재사용 방지일 뿐 삭제가 아니라서 접근이 다시 없는 항목의 TMap
  데이터가 24시간 넘게 힙에 남아 FR-8 보관 문면을 위반하고, 엔트리 수 상한만으로는 좌표열 상한
  5,000점 기준 최악 수백 MB 힙 압박이 열린다. Redis로 가면 둘 다 해소되고, 일 한도 카운터가 이미
  Redis라(§도메인 로직 2) 저장소도 하나로 모이며, 단일 인스턴스 전제도 사라진다. 메모리 규모는
  TTL이 자연 상한이다: 하루 신규 키가 일 한도(기본 900) 이하이고 키당 수 KB 수준이라 수 MB다.
- **캐시의 Redis 오류는 미스로 취급해 TMap 호출을 진행한다**(저장 실패도 무시하고 응답은 정상
  진행). 한도 카운터의 차단 폴백과 방향이 다른 이유: 한도는 열어두면 방어 자체가 사라지는
  안전장치지만 캐시는 없어도 안전한 절감 장치라, 닫으면 잃는 것(멀쩡한 세그먼트의 실패)이 열어서
  생기는 비용(계수되는 호출 1건)보다 크다. 그 호출 1건도 여전히 한도 카운터가 지키고, Redis 전면
  장애라면 카운터의 차단 폴백이 어차피 호출을 막으므로 두 폴백은 모순 없이 맞물린다.
- **성공 응답만 캐시한다.** 실패의 대부분은 일시(타임아웃, 서버 오류)라서 캐시하면 직선 폴백이
  24시간 고착된다. 미스 경합의 중복 호출은 수용한다(드물게 한도 2건 소모). 한 요청 안의 중복
  좌표쌍은 순차 처리라 첫 호출의 저장을 다음 세그먼트가 히트한다.

**2. 일 한도 방어 (FR-9, NFR-OPS-09)**

- **Redis 카운터**다. KST 날짜를 키에 넣고(`route:walk:daily:{yyyyMMdd}`) **INCR와 EXPIRE(48시간)를
  Lua 스크립트 하나로 원자 실행**해 선점한다. 분리 2명령이면 INCR 직후 크래시나 연결 유실 때
  TTL 없는 키가 영구 잔존해 명시한 48시간 수명과 모순이다(Codex 교차 리뷰 2라운드 적발). 같은
  이유로 이미 원자 스크립트를 쓰는 선례가 둘 있다: 핫존 집계의 ZINCRBY+EXPIRE
  (`HotScoreCommandServiceImpl.INCREMENT_SCRIPT`, 주석의 근거도 동일)와 검색 dedupe의 Lua
  (MSG-469, `SearchKeywordCommandServiceImpl.DEDUPE_SCRIPT`). 자정 리셋은 날짜 키 전환으로
  성립하고 지난 키는 TTL로 소멸한다. 프로세스 메모리 카운터를 쓰지 않는 이유: 재기동마다 0으로
  리셋돼 배포나 크래시가 있는 날 한도의 두 배 가까이 나갈 수 있어 NFR-OPS-09("무료 한도 안에
  머물도록 서버가 방어")의 문면을 지키지 못한다(Codex 교차 리뷰 1라운드 적발). Redis는 핫존
  집계와 검색 dedupe로 이미 인프라에 있어 신규 의존이 아니다.
- 날짜 판정은 주입된 `Clock`을 KST로 변환해 한다(인자 없는 `now()` 금지 컨벤션). TMap 무료
  한도의 리셋 주기가 일 단위이고 SK 국내 서비스라 KST 날짜 기준이다.
- **한도 카운터의 Redis 오류는 호출을 막는다**(그 세그먼트 실패 처리, 직선 폴백). 핫존은 Redis
  유실을 허용하지만 여기는 한도 방어가 목적이라, 계수 불능 상태에서 호출을 열어두면 방어 자체가
  사라진다. 보수 방향이 맞고, 실패의 사용자 영향도 "그 세그먼트 직선 유지"로 그친다. 캐시의
  미스 취급 폴백과 방향이 다른 근거는 §도메인 로직 1 참조.
- 한도 값은 설정 `route.walk.daily-limit`, **기본 900**이다. 요금표에서 보행자가 "경로안내" 그룹
  한 행에 묶여 있어 그룹 합산으로 보수 계획한 여유다(2026-08-26 성민 실측).
- 선점은 TMap 호출 직전이고(스크립트가 돌려준 카운트가 한도를 넘으면 호출하지 않는다) 호출이
  실패해도 되돌리지 않는다. 시도가 나갔으면 외부 한도는 이미 소모됐다는 보수 계상이다(요청
  제한의 시도 시각 기록과 같은 논리).
- 한도에 닿으면 그 요청의 남은 미스 세그먼트는 호출도 카운터 증가도 없이 실패 처리한다. 초과 시
  TMap이 차단하는 구조라 과금 사고는 없지만, 서버 방어가 먼저 서서 한도 초과 에러 호출 자체를
  만들지 않는다.

**3. 요청 내 단락 (지연 상한)**

한 요청 안에서 TMap 호출이 **연결 실패나 타임아웃**(응답 자체가 없는 실패)으로 죽으면 남은 미스
세그먼트는 호출 없이 실패 처리한다. TMap이 죽은 상태에서 8세그먼트를 순차로 다 두드리면 최악
지연이 타임아웃의 8배가 되는 것을 1회로 묶는 장치다. 상태 코드가 있는 실패(4xx, 5xx 응답과 형태
위반)는 그 세그먼트만 실패하고 다음 세그먼트를 계속 진행한다(경로 없음 같은 세그먼트 고유
실패까지 단락하면 멀쩡한 세그먼트를 버린다).

**4. 이 API에 사용자별 요청 제한을 두지 않는다**

recommend의 10초 제한(FR-ROUTE-12) 같은 장치를 추가하지 않는다. 근거: 보행 경로 조회는 추천 1회당
1회로 자연 결합되고, 반복 조회는 캐시가 흡수하며, 전역 일 한도가 최종 방어선이고, 로그인 필수라
익명 남용이 없다. 악용의 피해 상한도 "그날 보행 경로 미표시"로 제한적이다(추천 기능 무영향).
세그먼트 직선거리 상한 검증도 두지 않는다. TMap 실패가 곧 폴백이라 방어가 이미 있고, 임의 컷
값은 근거 없이 실경로 표시만 깎을 수 있다.

**5. 추천 이유에서 직전 거리 제거 (FR-10, FR-ROUTE-05 개정)**

`RouteRecommendServiceImpl.facts()`의 previous 분기(현행 272~276행, "이전 지점에서 %.1fkm")를
제거하고 `explainPoints()`의 previous 인자 전달도 함께 걷어낸다. facts는 출처(상시 1건), 기간,
관심사 일치의 최대 3건이 된다(AI 계약 하한 1, 상한 5 안쪽 그대로). `RouteOrderPlanner.
distanceMeters()` 하버사인은 순서 결정용으로 불변이다(순서까지 보행 거리로 정하면 지점 쌍 전부의
조회가 필요해 한도가 감당하지 못한다, PRD 비목표). 기존 테스트 `RouteRecommendServiceTest` 197행
부근의 직전 거리 단언을 새 조립 규칙으로 갱신한다.

**6. 지표 로그 (NFR-OPS-09 운영 감시)**

요청당 한 줄: `[route-walk] segments={} hits={} calls={} failed={} daily_used={}`. 좌표와 TMap
응답 원문은 남기지 않는다. `daily_used`가 한도 소진 시점의 실측 재료다.

## 설정

```yaml
# AI 경로 추천 보행 경로 (MSG-483). route.ai 와 독립 게이트다. 추천만 켜고 보행 경로는 끌 수 있다.
route:
  walk:
    enabled: ${ROUTE_WALK_ENABLED:false}    # 기본 꺼짐 (NFR-OPS-06 관례). 꺼지면 호출은 14504
    base-url: ${ROUTE_WALK_BASE_URL:https://apis.openapi.sk.com}
    app-key: ${TMAP_APP_KEY:}               # NFR-SEC-10, 서버에만 둔다. dev/prod env 주입
    daily-limit: ${ROUTE_WALK_DAILY_LIMIT:900}
    timeout: ${ROUTE_WALK_TIMEOUT:PT3S}     # 교환 전체 시한 (카카오 선례와 같은 급)
```

`RouteWalkProperties` record 바인딩(`RouteAiProperties` 선례)에 검증 하나를 얹는다:
**compact 생성자에서 `enabled`인데 `app-key`가 빈 값이면 예외를 던져 기동을 실패시킨다**(바인딩
시점 검증, 전 프로파일). 플래그가 켜졌는데 키가 비면 기동은 통과하고 모든 요청이 TMap 인증
실패로 조용히 직선 폴백돼, 폴백 설계가 설정 장애를 감춘다(Codex 교차 리뷰 4라운드 적발). prod
한정 검증(`ProdRequiredEnvValidator`, NFR-OPS-04) 대신 바인딩 검증을 고른 이유: 이 실수는 플래그를
먼저 켜 보는 dev에서 먼저 나고, 조건부 필수(켜졌을 때만)라 prod 전용 검증기에 넣으면 꺼진 환경의
기동을 막지 않기 위한 분기가 따로 붙는다. record 생성자의 if 하나가 가장 짧고 전 환경을 덮는다.

신규 파일은 config의 `RouteWalkProperties`, service의 `TmapWalkClient`와
`RouteWalkPathService(Impl)`, `RouteWalkSegmentCache`, `RouteWalkDailyLimiter`(폴백 방향이 반대인
두 관심사를 분리하고 실 Redis 테스트를 서비스 없이 격리하기 위해 구현 중 분리 신설, 2026-08-26
리뷰 수용 — 상시 빈, 계약 무변경), dto의 `RouteWalkPathRequestDto`와 `RouteWalkPathResponseDto`이고,
수정은 `RouteController`(엔드포인트 추가), `RouteErrorCode`(상수 2개),
`RouteRecommendServiceImpl`(facts), application yml이다. 일 한도 카운터와 좌표쌍 캐시 모두 기존
Redis 연결(핫존 인프라)을 쓰므로 접속 설정 추가가 없다.

## 미해결 질문

서버 몫은 없다. PRD의 스펙 유보 5건(캐시 저장소, 일 한도 카운터 방식, TMap 호출 파라미터, 에러
코드, 엔드포인트와 DTO 형태)은 이 문서에서 전부 확정했다. PRD의 디자인 미확인 1건(실경로 선
스타일과 직선 폴백 세그먼트의 시각 구분)은 FE와 디자인 몫으로 계승되며 서버 구현을 막지 않는다.

[^1]: 세그먼트: 추천 동선에서 이웃한 두 지점 사이 구간. 지점 상한이 8개라 세그먼트는 최대
    7개이고, 출발지 반영 추천이면 출발지에서 첫 지점까지 구간이 하나 더 붙는다.
[^2]: 하버사인 거리: 두 좌표를 지구 곡면 위 직선으로 잰 거리. 지점 방문 순서 결정이 이 값을
    쓰고, 이번 변경 후에도 순서 결정 용도는 그대로 남는다.
[^3]: 폴백: 주 방식이 실패했을 때 대신 쓰는 예비 동작. 여기서는 보행 경로를 못 받은 세그먼트를
    지금의 직선 연결과 직선거리 안내로 되돌리는 것.
[^4]: appKey: TMap Open API의 인증 키. 요청 헤더에 실어 보내며, 노출되면 제3자가 우리 한도로
    호출할 수 있어 서버 설정에만 둔다.
[^5]: GeoJSON: 지리 데이터를 JSON으로 적는 표준 형식. 좌표를 경도, 위도 순서로 적는 점이 이
    프로젝트의 응답 관례(위도 먼저)와 반대라 변환 지점이 된다.
[^6]: TTL(Time To Live): 저장된 항목의 수명. Redis는 TTL이 다한 키를 스스로 지우므로 좌표쌍
    캐시에서는 TMap 약관의 24시간 보관 상한을 지키는 삭제 장치이고, 한도 카운터에서는 지난 날짜
    키를 치우는 청소 장치다.
[^7]: LRU(Least Recently Used): 캐시가 가득 찼을 때 가장 오래 안 쓰인 항목부터 버리는 정책.
    parse 해석 캐시가 이 방식인데, 버리는 기준이 접근 순서라 안 쓰인 항목의 보관 시간 자체는
    보장하지 못한다. 좌표쌍 캐시가 이 방식을 기각한 이유가 그 성질이다.

**런타임 동작 기록**

- **데이터 저장 위치**: DB 테이블·Flyway 없음. Redis 키 2종 — `route:walk:seg:{startLat}:{startLng}:{endLat}:{endLng}`(Double.toString 정규형, 값은 좌표열+거리 JSON, `SET ... EX 86400` 단일 명령 = TTL 24시간), `route:walk:daily:{yyyyMMdd}`(KST, 주입 Clock 변환, Lua로 INCR+EXPIRE 172800초 원자 실행, TTL 48시간). 기존 Redis 연결(핫존 인프라) 재사용, 접속 설정 추가 없음.
- **실행 쿼리**: JPA·SQL 무접점. 외부 호출은 `POST {base-url}/tmap/routes/pedestrian?version=1`(appKey 헤더, 본문 8필드, 연결 1초·교환 전체 3초) 하나.
- **예외 흐름**: 14402(`INVALID_WALK_SEGMENTS`)·14504(`ROUTE_WALK_DISABLED`)는 `RouteWalkPathServiceImpl`에서 `ApiException`으로 던져져 `GlobalExceptionHandler`가 400/503으로 변환. `TmapUnreachableException`은 핸들러에 닿지 않는다 — 서비스 세그먼트 루프의 catch가 삼켜 단락 플래그로 접고 200 유지(전파되면 `Exception.class` 폴백이 500을 만들므로 삼킴이 규범). TMap 4xx·5xx·형태 위반은 클라이언트가 null 반환 — 그 세그먼트만 `resolved:false`. 기동 시점 예외 1종: enabled+빈 appKey면 `RouteWalkProperties` compact 생성자의 `IllegalStateException`으로 컨텍스트 기동 실패.
- **빈 동작**: `TmapWalkClient`만 `@ConditionalOnProperty(route.walk.enabled)` 조건부, 나머지(서비스·캐시·리미터)는 상시 빈 — 플래그 off에서 서비스는 `ObjectProvider.getIfAvailable()` null로 14504. 스케줄러·executor·트랜잭션 없음(전 경로 무트랜잭션 — DB 무접점). 지표 로그 1줄 `[route-walk] segments= hits= calls= failed= daily_used=`(INFO, 좌표·TMap 원문·appKey 미기록).
