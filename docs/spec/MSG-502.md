# MSG-502: 행사 운영자가 승인 이벤트를 골라 참여를 신청한다 (이벤트 참여형 신청)

**Owner**: B (event 도메인은 Owner B다. CLAUDE.md 협업 원칙의 `com.msg.fillmap.event.*` 배정
기준이고, Owner A 계약 인터페이스는 MSG-498이 이미 쓰는 표시명 재료 계약을 시그니처 변경 없이
소비만 한다)

> 요구사항 정본: `docs/prd/event-submission.md` (상태 검토됨, 2026-08-29 v2.2 개정 동반. 이
> 브랜치가 미해결 질문 1의 해소를 v2.2로 싣는다). 이 스펙은 FR-7의 세 번째 등록 유형(이벤트
> 참여형)의 신청 제출 서버 몫을 다룬다. 부모를 고르는 모달 조회(FR-26)는 MSG-501이 완료했고,
> 이 티켓은 그 응답의 `occurrenceId`를 신청 payload로 받는 쪽이다. 참여로 생기는 실체는 별도
> 명칭 없이 부모 이벤트 아래 **행사 위치**다(v2.2 확정 1).

## 개요

행사 운영자[^1]가 콘솔에서 등록 유형 "이벤트"를 골라, MSG-501 모달에서 고른 승인 이벤트
회차[^2] 아래 참여를 신청할 수 있게 한다. 신규 엔드포인트는 없다. MSG-498이 만든 신청 API
5개(presign, 제출, 내 목록, 상세, 재제출)가 `EVENT` 유형을 받도록 확장하고, 제출 후
흐름(심사 중, 반려, 재제출)은 기존 코드를 그대로 탄다. 새로 생기는 것은 부모 이벤트 검증
2건(에러 코드 13440, 13441), 유형별 항목 분기, Flyway 1건(V50)이다.

## 배경 · 목표

- v2.1 재편으로 세 번째 등록 유형은 독립 행사 신설이 아니라 승인 이벤트 아래 참여를 붙이는
  구조가 됐다. 목록(MSG-501)은 있는데 그 선택을 받아 저장하는 쪽이 없다.
- 목표: ORG 토큰으로 이벤트 참여 신청을 제출부터 반려 후 재제출까지 완주할 수 있는 상태.
  승인 시 부모 회차 아래 행사 위치로 반영하는 쪽은 MSG-500이다.

## 성공 기준

1. `type=EVENT` 신청을 제출하면 부모 회차 참조와 참여 방식이 저장되고, 기존과 같은 심사 중
   상태와 `FM-2026-XXXX`꼴 신청 번호가 온다(FR-10 재사용).
2. 부모 검증이 동작한다. 없는 회차는 13440, 종료된(유예, 아카이브 포함) 회차는 13441이다.
3. EVENT 신청의 위치는 정확히 1곳(대표 위치)이고, 사각형 영역과 81칸 상한, 대표 격자[^3]
   서버 계산은 기존 규칙 그대로다(FR-8의 v2.2 예외, FR-9, FR-24 재사용).
4. 유형별 항목 분기가 동작한다. `participationMethod`와 `parentOccurrenceId`는 EVENT 전용
   필수이고, 반대 유형 필드가 실려 오면 13439다(기존 분기 규칙의 확장).
5. 반려 재제출에서 유형과 부모는 불변이고, 재제출 시점에 부모가 종료돼 있으면 13441이다.
6. 기존 FESTIVAL, POPUP 신청 흐름이 회귀 없이 그대로 동작한다.
7. 아래 테스트 시나리오가 전부 green이다.

## API 명세

신규 엔드포인트 없음. SecurityConfig 무변경(`/api/org/**` matcher가 기존 경로를 이미 덮는다,
MSG-496). 아래는 MSG-498 계약에 대한 **증분**만 적고, 적지 않은 것은 전부 MSG-498 스펙
그대로다.

### 1. `POST /api/org/event-submissions/image/presigned-url` : 변경 없음

커버 이미지도 대표 이미지와 같은 규격(jpg, jpeg, png, 10MB)이라 그대로 재사용한다. 시안의
"16:9 권장"은 권장 문구라 서버 검증을 두지 않는다(비율 검증은 이미지 디코딩이 필요한데 얻는
것이 안내 문구 하나다. FE 안내 몫).

### 2. `POST /api/org/event-submissions` : EVENT 유형 추가

`EventSubmissionCreateRequestDto`에 필드 2개가 늘어난다.

```json
{
	"type": "EVENT",
	"parentOccurrenceId": 1,
	"title": "필맵 스탬프 투어",
	"organizerName": "필맵 파트너스",
	"startsOn": "2026-10-06",
	"endsOn": "2026-10-15",
	"participationMethod": "부스 방문 후 현장에서 인증 영상을 촬영해 업로드하면 참여가 완료됩니다",
	"description": "부산국제영화제 기간에 영화의전당 일대에서 진행하는 스탬프 투어입니다",
	"imageS3Key": "event-submissions/pending/12/3f2b….jpg",
	"locations": [
		{
			"areaRects": [
				{ "minGridY": 16859, "maxGridY": 16861, "minGridX": 11509, "maxGridX": 11515 }
			]
		}
	]
}
```

- `type`: `EVENT` 값이 추가된다(기존 FESTIVAL, POPUP 유지).
- `parentOccurrenceId`: **EVENT 전용 필수.** MSG-501 목록 응답의 `occurrenceId`를 그대로
  넣는다. 제출은 이 본문 값으로 부모의 존재(13440)와 종료(13441)를 검증한다. FESTIVAL,
  POPUP에 실려 오면 13439다(반대 유형 필드 거부 규칙 그대로).
- 유형별 항목 매핑(ver 14 [4C] 실측): `title`은 이름, `organizerName`은 운영 주체,
  `startsOn`과 `endsOn`은 공개 기간, `description`은 소개, `imageS3Key`는 커버 이미지다.
  시안의 구 라벨 "행사방 이름"은 쓰지 않는다("행사방"은 MSG-503으로 폐기된 용어. 화면 라벨은
  "이름"이고 저장은 기존 `title` 컬럼 재사용이라 코드 심볼 변경도 없다).
- `participationMethod`(참여 방식): **EVENT 전용 필수.** 주요 프로그램과 같은 서술 항목이라
  String `@Size(min = 10, max = 2000)`이다(피그마 #100 규칙과 D-11 상한 준용). FESTIVAL,
  POPUP에 실려 오면 13439.
- `programDescription`, `operatingHours`가 EVENT에 실려 오면 13439(자기 유형이 아닌 필드).
- `locations`: **EVENT는 정확히 1개다**(결정 D-2, PRD FR-8의 v2.2 예외). 0개는 기존 공통
  규칙대로 13431, 2개 이상은 13439(유형별 구조 위반)다. 위치 내부(사각형 배열, 81칸 합집합,
  인덱스 범위, 대표 격자 계산)는 기존 규칙을 전부 재사용한다.
- 응답은 기존 `EventSubmissionSubmitResponseDto` 그대로다.

### 3. `GET /api/org/event-submissions/my` : 변경 없음

EVENT 신청도 같은 목록에 실린다. 항목의 `type`이 `EVENT`로 오는 것 외에 필드 추가가 없다
(부모 이름은 상세 몫. 목록 카드는 신청 `title`로 충분하다).

### 4. `GET /api/org/event-submissions/{id}` : 필드 2개 동봉

EVENT 신청의 상세에 다음이 실린다(다른 유형에서는 null).

```json
{
	"type": "EVENT",
	"participationMethod": "부스 방문 후 현장에서 …",
	"parentEvent": { "occurrenceId": 1, "name": "부산국제영화제" },
	"operatingHours": null,
	"programDescription": null
}
```

- `parentEvent.name`의 원천은 `event_occurrences.title`이다. MSG-501 목록의 `name`과 같은
  원천이라 모달에서 고른 이름과 상세에 보이는 이름이 어긋나지 않는다. 조회는 저장된
  `parentEventOccurrenceId`로 회차 1건을 읽어 채운다.
- 존재 은닉(13430), 이력, 반려 사유, 위치 표시명 재료 동봉은 전부 기존 그대로다.

### 5. `PATCH /api/org/event-submissions/{id}` : EVENT 재제출

- `EventSubmissionUpdateRequestDto`에 `participationMethod`가 추가된다.
  **`parentOccurrenceId`는 추가하지 않는다.** 유형과 마찬가지로 부모는 재제출에서 바꿀 수
  없고(결정 D-3), 저장된 부모가 그대로 유지된다. 본문에 `parentOccurrenceId`를 실어 보내도
  DTO에 필드가 없어 역직렬화에서 버려진다.
- **부모 검증의 호출 계약**: 제출(POST)은 요청 본문의 `parentOccurrenceId`로 존재(13440)와
  종료(13441)를 검증한다. 재제출(PATCH)은 본문에 부모를 받지 않으므로, 소유 조회로 로드한
  신청의 저장 부모를 **같은 검증 메서드에 별도 인자로 넘겨 종료(13441)만 재검증한다**(저장
  부모는 FK로 보장되는 값이라 존재 검증이 성립하지 않는다). 부모 필수 검증을 공통
  `EventSubmissionForm`에 넣지 않는 이유도 이것이다: 재제출 DTO에는 부모 필드 자체가 없다.
- 반려와 수정 사이에 부모 회차가 종료됐으면 13441이다(참여할 자리가 사라진 신청은 재제출로
  살릴 수 없다. 새 부모로 새로 제출한다).
- 그 외 검증은 제출과 동일하게 전부 다시 탄다. 조건부 UPDATE 원자 전이, 존재 은닉, 이미지
  유지 계약(null이면 유지)은 MSG-498 그대로다.

## 도메인 로직

### 부모 이벤트 검증 (신규)

제출과 재제출에서 EVENT 유형이면 다음 순서로 검사한다.

1. `parentOccurrenceId`로 `EventOccurrenceRepository.findById` 조회. 없으면 **13440**(404).
   존재 은닉을 하지 않는 이유: 승인 이벤트 목록(MSG-501)이 ORG 전원에게 같은 전체를
   보여주므로 회차의 존재는 비밀이 아니다. 은닉 대상은 남의 신청(13430)이지 공개된 부모가
   아니다.
2. **`endsAt <= now`이면 13441**(409). `now`는 주입받은 `Clock`에서 얻는다. 이 판정은
   MSG-501 목록 노출 조건(D-1, `endsAt > now`)의 **정확한 여집합**이라, 종료 정각을 포함한
   어떤 시각에도 모달에 보이는 회차와 신청이 되는 회차가 항상 일치한다(정각에 목록에서
   빠지는 회차는 신청도 13441이다). 파생 상태[^4]로 말하면 UPCOMING과 LIVE만 부모가 될 수
   있다. 재제출은 저장 부모로 이 종료 검증만 반복한다(호출 계약은 API 명세 5절).
3. **카테고리 검증은 만들지 않는다.** v2.2 확정 2로 지역축제와 팝업 승인분은 미션으로
   편입되지 `event_occurrences`에 들어오지 않으므로, 이 테이블의 전 행이 이벤트 카테고리다
   (MSG-501 결정 D-3과 같은 전제이고, 그 결정이 남겼던 "승인분 유입 시 카테고리 컬럼" 접점은
   확정 2로 소멸했다). "이벤트 카테고리 아닌 시리즈" 케이스는 데이터상 성립하지 않는다.
4. 관리자 노출 중지(FR-20)는 미구현이다. 중지 상태를 만드는 티켓이 이 검증에도 제외 조건을
   더한다(MSG-501 조회와 같은 접점).

### 위치: 대표 위치 1곳, 형태는 기존 행사 위치와 동일 (결정 D-2)

위치 단계 화면 "다음: 대표 위치 등록"의 확정이다. EVENT 신청의 위치는 **정확히 1곳**이고,
그 1곳은 기존 위치와 똑같이 areaRects[^5] 사각형 여러 개로 영역을 그린다. 대표 격자 하나만
점으로 받는 안은 기각한다. 승인 결과가 부모 회차 아래 `event_locations` 1행 + 격자
전개(`event_location_grids`)인데(확정 1), 점 하나로는 승인 시점에 영역을 지어낼 수 없다.
81칸 상한(FR-24), 인덱스 범위, 합집합 판정, `RepresentativeGridResolver` 계산은 기존 검증
경로를 분기 없이 그대로 통과한다.

### 기간 검증

기존 D-6 규칙(시작 ≤ 종료, 종료일은 KST 오늘 이상)만 적용한다. **공개 기간이 부모 회차 기간
안에 들어야 한다는 교차 검증은 두지 않는다**(결정 D-4). 부모 기간은 UTC 시각이고 신청 기간은
KST 날짜 라벨이라 서버 단정이 경계일에서 애매하고, 시안과 PRD 어디에도 이 제약이 없으며,
기간의 타당성은 어차피 관리자 심사가 본다(반려 코드 PERIOD가 그 자리다).

### 유형별 필수 분기 (13439 확장)

기존 2유형 분기 표가 3유형이 된다.

| 필드 | FESTIVAL | POPUP | EVENT |
|---|---|---|---|
| `programDescription` | 필수 | 거부 | 거부 |
| `operatingHours` | 거부 | 필수 | 거부 |
| `participationMethod` | 거부 | 거부 | 필수 |
| `parentOccurrenceId` | 거부 | 거부 | 필수 (제출 본문 한정, 재제출 DTO에는 필드 없음) |
| `locations` 개수 | 1~20 | 1~20 | 정확히 1 (2개 이상 13439) |

위반은 전부 기존 13439 하나로 낸다(메시지가 "등록 유형에 필요한 항목이 올바르지 않습니다"라
세 유형 모두를 덮는다). 검증 구현은 `EventSubmissionForm` 경유의 기존 분기 지점에 값 추가다.

### 이미지, 신청 번호, 상태와 이력

전부 MSG-498 그대로다. 커버 이미지는 대표 이미지와 같은 pending 검증, original 복사, 롤백
보상 경로를 타고, 신청 번호는 같은 시퀀스에서 나오며, 상태 전이와 이력 기록도 분기가 없다.

## 데이터 모델

Flyway 1건, **`V50__event_submission_participation.sql`**. develop 실측 최신이 V49
(`V49__event_submissions.sql`, MSG-498 머지분)라 V50이다(PRD 7절의 재실측 규칙. 병렬 레인이
먼저 붙이면 구현 시점에 다시 실측한다).

```sql
-- 이벤트 참여형 (MSG-502): 승인 이벤트 회차 아래 참여를 신청한다.
-- 승인 시 부모 회차의 event_locations 로 반영하는 쪽은 MSG-500 (PRD v2.2 확정 1).
ALTER TABLE event_submissions
	ADD COLUMN parent_event_occurrence_id BIGINT REFERENCES event_occurrences(id),
	ADD COLUMN participation_method TEXT;

COMMENT ON COLUMN event_submissions.parent_event_occurrence_id
	IS '참여 대상 승인 이벤트 회차. EVENT 유형 전용 (MSG-502)';
COMMENT ON COLUMN event_submissions.participation_method
	IS '참여 방식 서술. EVENT 유형 전용, 최소 10자 (#100 준용)';

ALTER TABLE event_submissions DROP CONSTRAINT chk_event_sub_type;
ALTER TABLE event_submissions ADD CONSTRAINT chk_event_sub_type
	CHECK (type IN ('FESTIVAL', 'POPUP', 'EVENT'));

-- EVENT 행에는 부모가 반드시 있고 다른 유형 행에는 없다. MSG-500 approve 가 이 불변식 위에서
-- 부모를 역참조하므로 DB 가 강제한다 (유형별 텍스트 필수는 V49 선례대로 앱 검증 13439).
ALTER TABLE event_submissions ADD CONSTRAINT chk_event_sub_parent
	CHECK ((type = 'EVENT') = (parent_event_occurrence_id IS NOT NULL));
```

- 부모 컬럼에 인덱스는 두지 않는다. 이 티켓의 어떤 조회도 부모로 걸지 않고(상세는 id 1건
  조회), 회차는 삭제 경로가 없어 FK 역방향 스캔 우려도 없다. 부모 기준 목록이 필요해지는
  티켓이 그때 추가한다.
- `EventSubmissionType`에 `EVENT` 상수를 추가한다. **주석 필수**: 이 값은 glossary의 이벤트
  카테고리(지역축제, 팝업 제외 큰 행사)이고, `MissionType.EVENT`(축제 미션)와 이름이 같지만
  반대편을 가리킨다(glossary "이벤트" 항목 명문. v2.2 확정 2로 승인된 지역축제가
  `MissionType.EVENT` 미션이 되는 교차까지 생기므로 주석 없이는 반드시 헷갈린다).
- `EventSubmission` 엔티티에 `Long parentEventOccurrenceId`, `String participationMethod`
  추가. 부모는 연관 없이 id 보관이다. 이 티켓이 부모에서 읽는 값은 상세의 `title` 하나라
  리포지토리 1건 조회로 충분하고, `userId` 필드의 기존 근거와 같다(MSG-500이 연관이 필요하면
  그쪽에서 읽기 전용으로 단다).
- 기존 행 마이그레이션은 없다(신규 컬럼 둘 다 NULL 허용이고 기존 행은 전부 FESTIVAL, POPUP
  이라 CHECK를 그대로 통과한다).

## 에러 코드

**event 13xxx의 13440대 블록을 이 티켓이 처음 소비한다.** MSG-501 스펙의 대역 예약대로이고,
그 스펙이 요구한 재확인도 마쳤다: develop 머지된 `EventErrorCode` 실코드의 신청 블록 점유는
13430~13439까지다(2026-08-29 실측). 기존 대역 잔여 사용이라 `response-pattern.md` 표 갱신
커밋은 필요 없다.

| developCode | 상수 | HTTP | 메시지 | 발생 |
|---|---|---|---|---|
| 13440 | `PARENT_EVENT_NOT_FOUND` | 404 | 참여할 이벤트를 찾을 수 없습니다 | 없는 `parentOccurrenceId` (제출 한정) |
| 13441 | `PARENT_EVENT_CLOSED` | 409 | 종료된 이벤트에는 참여를 신청할 수 없습니다 | `endsAt <= now` 회차(정각 포함, 유예와 아카이브 포함)에 제출 또는 재제출. 상태 충돌 409(13434 선례) |

그 외 실패는 전부 기존 코드 재사용이다: 13439(유형별 항목 분기, 위 표), 13431/13432(영역),
13433(기간), 13435~13438(이미지), 13430(존재 은닉), 13434(반려 아닌 상태 수정), Bean
Validation 공통 400(10자 미만, 2000자 초과 등).

## 결정 기록

- **D-1 신규 엔드포인트 없이 기존 신청 API에 유형 편입**: 제출 후 흐름(목록, 상세, 반려,
  재제출, 심사 큐)이 FR-10~14로 세 유형 공통이고, MSG-498 결정 D-9가 정확히 이 확장(type
  CHECK 재정의 + 부모 컬럼 추가)을 위해 자리를 열어 뒀다. MSG-501 스펙이 언급했던
  `/api/org/events/{occurrenceId}` 하위 신설안은 기각한다. 신청이 URL 두 체계로 갈라지면
  목록, 상세, 재제출, 관리자 심사(MSG-500)까지 전부 두 벌이 된다.
- **D-2 위치는 대표 위치 1곳, 형태는 기존 위치 규칙 그대로**: 시안 [4C]의 버튼("다음: 대표
  위치 등록")과 하단 안내("대표 위치가 일반 유저 지도에 표시됩니다")가 모두 단수이고, 승인
  결과가 부모 회차 아래 행사 위치 1행이다(v2.2 확정 1). 전용 프레임이 없어 열려 있던 "영역도
  받는지"는 **받는 쪽으로 확정**한다. `event_locations`가 영역(격자 전개)과 대표 격자를 둘 다
  가지므로 점 하나만 받으면 승인 시 영역 재료가 없다. 검증과 계산은 기존 경로 재사용이라
  구현 증분은 개수 검사 하나다. 이 1곳 예외는 FR-8(위치 여러 개 허용)과 충돌하지 않도록
  **PRD v2.2가 FR-8에 예외 문장으로 명문화했다**(상호참조).
- **D-3 재제출에서 유형과 부모는 불변**: MSG-498 D-8(유형 불변)과 같은 근거다. 부모를 바꾸면
  참여 대상이 달라져 사실상 새 신청이다. 부모를 바꾸려면 새로 제출한다. 재제출의 부모 검증은
  저장 부모로 종료만 재검증한다(호출 계약은 API 명세 5절).
- **D-4 공개 기간과 부모 기간의 교차 검증 없음**: 근거는 도메인 로직 기간 절. 타당성 판단은
  관리자 심사(PERIOD 반려)가 게이트다.
- **D-5 참여 방식은 서술 항목**: String 최소 10자, 최대 2000자, DDL TEXT.
  `programDescription`과 같은 성격이라 같은 규칙(#100, D-11)을 준용한다.
- **D-6 부모 검증은 은닉 없는 404와 상태 충돌 409, 종료 판정은 `endsAt <= now`**: 은닉과
  409의 근거는 도메인 로직 부모 검증 절. 종료 판정을 MSG-501 노출 조건의 정확한 여집합으로
  두어 목록과 신청의 경계가 정각에서도 갈리지 않는다. 신청의 존재 은닉(13430)과 다른
  성격이라 코드를 섞지 않는다.
- **D-7 격자 겹침 검사는 제출 시점에 하지 않는다**: 참여 영역이 부모 회차의 기존 위치
  격자와 겹치는지(회차 내 격자 단일 귀속, V39 제약)는 제출 시점에 확인해도 승인 시점까지
  다른 승인으로 상태가 바뀔 수 있어 승인 처리(MSG-500)가 어차피 다시 판정해야 한다. 두 번
  구현하지 않고 승인 쪽 한 곳에 둔다(위반 시 AREA 반려 안내 정의도 MSG-500 몫).
- **D-8 구 라벨 "행사방 이름"은 "이름"으로**: MSG-503 용어 확정의 반영이고 저장은 기존
  `title` 컬럼이다. 승인 시 이 값이 `event_locations.name`(NOT NULL)의 재료가 된다.
  MSG-501이 "승인 흐름산 위치의 name 채움 규칙 미정의"로 남긴 접점의 참여분 답이 이것이고,
  규칙 확정 자체는 MSG-500 approve 스펙 몫이다.

## 비범위

- 관리자 심사와 승인 반영: MSG-500. EVENT 승인 시 부모 회차 아래 행사 위치 생성(격자 전개,
  `location_key` 채번, `name` 채움, 겹침 위반 처리)과 지역축제·팝업 승인분의 미션 칩 편입
  (v2.2 확정 2), SRS FR-EVENT-01 등재 기준 서술 갱신까지 전부 그쪽이다.
- **참여 속성의 승인 반영 계약: MSG-500 스펙 몫.** 이 티켓은 속성을 신청 행에 저장하는
  데까지다. 지금 `event_locations`(V39)에는 이름 컬럼뿐이라, 신청 행에 저장된 속성이 승인
  후 사용자에게 노출되려면 위치 쪽 확장이 필요하다. MSG-500이 정의할 것 세 가지: ①
  `event_locations` 확장 컬럼(별도 마이그레이션. 후보는 운영 주체 `organizer_name`, 소개
  `description`, 공개 기간 `starts_on`과 `ends_on`, 참여 방식 `participation_method`, 커버
  이미지 키 `image_key`), ② 승인 시 신청 행에서 위치 행으로의 복사 매핑, ③ 그 속성을 사용자
  조회 어느 API에 실을지의 노출 계약. 이 셋이 없으면 v2.2 확정 1("속성은 위치에 붙는 부가
  정보")이 승인 시점에 유실된다(PRD 미해결 질문 1의 결정 기록에 같은 문구로 박아 뒀다).
- 승인 이벤트 목록 조회: MSG-501 완료.
- 지역축제, 팝업스토어 신청: MSG-498 완료. 이 티켓은 그 코드의 확장점만 만진다.
- glossary "이벤트" 항목의 하위 실체 미정 표기 갱신: v2.2 확정 1의 회부 몫(별도 진행).
- 관리자 노출 중지(FR-20)의 부모 검증 제외 조건: 중지 상태를 만드는 티켓 몫.

## 테스트 시나리오

JUnit 5와 AssertJ, 한국어 백틱 메서드명. 구현 시 `// 검증: FR-…` 주석으로 PRD 요구사항 ID를
달고, 전역 SRS ID는 구현 마무리에서 srs-writer로 등재를 확인한다(FR-EVENT 영역, MSG-501의
FR-EVENT-16 선례).

```text
// 부모 이벤트 검증 (검증: FR-7)
없는_회차로_참여_신청하면_거부한다()                       // 13440
종료된_회차로_참여_신청하면_거부한다()                     // 13441, 고정 Clock, endsAt 경과
종료_정각의_회차는_참여_신청이_거부된다()                  // 13441, endsAt == now 경계, 고정 Clock
                                                          // (MSG-501 노출 조건의 여집합 확인)
유예_중인_회차도_참여_신청이_거부된다()                    // 13441, UPLOAD_GRACE 는 종료
종료_직전_회차는_참여_신청이_된다()                        // endsAt > now 경계, MSG-501 노출과 동일 판정

// 유형별 항목 분기 (검증: FR-7)
이벤트_신청에_부모_회차가_없으면_거부한다()                // 13439
축제_신청에_부모_회차가_실려_오면_거부한다()               // 13439, 반대 유형 필드
이벤트_신청에_참여_방식이_없으면_거부한다()                // 13439
이벤트_신청에_주요_프로그램이_실려_오면_거부한다()         // 13439
참여_방식이_10자_미만이면_400이다()                        // Bean Validation 공통 경로
참여_방식이_2000자를_넘으면_400이다()                      // D-5 경계

// 위치 (검증: FR-8 v2.2 예외, FR-9, FR-24 / D-2)
이벤트_신청의_위치는_1곳이면_통과한다()                    // 사각형 여러 개 영역 + 대표 격자 계산
이벤트_신청에_위치가_2곳이면_거부한다()                    // 13439
이벤트_신청에_위치가_없으면_거부한다()                     // 13431, 공통 규칙 재사용
이벤트_위치도_81칸_상한이_적용된다()                       // 13432, 기존 경로 무분기 확인

// 제출과 저장 (검증: FR-10)
이벤트_신청이_부모_참조와_참여_방식을_저장한다()           // parent_event_occurrence_id 실측
이벤트_신청도_심사_중_상태와_FM꼴_신청_번호를_받는다()     // 기존 흐름 합류

// 상세 (검증: FR-12)
이벤트_신청_상세에_부모_이벤트_이름이_실린다()             // event_occurrences.title 원천
축제_신청_상세의_참여형_필드는_null이다()                  // participationMethod·parentEvent

// 재제출 (검증: FR-13 / D-3)
이벤트_반려본을_수정하면_심사_중으로_돌아간다()            // 부모 불변 확인 포함
재제출_시점에_저장_부모가_종료됐으면_거부한다()            // 13441, 저장 부모 재검증 (API 5절 계약)
재제출_본문의_부모_변경_시도는_무시되고_부모가_불변이다()  // PATCH 본문에 parentOccurrenceId 를
                                                          // 실어도 DTO 에 필드가 없어 버려진다

// 회귀 (기존 유형 무영향)
축제_신청_흐름은_그대로_동작한다()                         // FESTIVAL 기존 시나리오 대표 1건 재확인
```

통합 테스트의 부모 회차는 MSG-501 선례대로 `msg502-*` 자연키와 합성 데이터로 격리해 공유
로컬 DB의 시드에 의존하지 않는다. S3와 직렬화 수단도 MSG-498 선례 그대로다.
