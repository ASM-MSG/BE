# MSG-495: 운영 영상 전송망과 전용 도메인 구성

**Owner**: B

> PRD 면제: 재생 권한, API 필드와 사용자 동작을 바꾸지 않고 MSG-67에서 검증한 전송 구조를
> 운영 AWS 자원에 적용하는 인프라 작업이다. 요구사항 입력은 Jira MSG-495와 `docs/spec/MSG-67.md`다.

## 개요

운영 영상용 S3 버킷과 CloudFront 배포를 만들고 `media.fillmap.kr`을 연결한다. 재생과 썸네일은
MSG-67과 같은 10분짜리 CloudFront 서명 URL[^1]을 사용한다. dev 배포와 기본 도메인은 바꾸지 않는다.

## 배경과 목표

MSG-67은 dev에서 MP4 반복 재생의 전체 GET TTFB를 105.9ms에서 51.8ms로, 1MiB Range TTFB를
94.4ms에서 48.6ms로 줄였다. 운영 환경에는 영상 버킷과 영상용 CloudFront 배포가 없고,
`media.fillmap.kr`을 포함하는 인증서도 없다. 운영 자원을 dev와 분리하고 사용자에게는 AWS 기본
도메인 대신 서비스 소유 주소를 노출한다.

현재 운영 백엔드 서비스와 전용 EC2는 없다. 이 티켓은 전송 자원과 배포 설정값을 준비하되 운영
애플리케이션을 기동하지 않는다.

## 성공 기준

1. `fillmap-video-prod` 버킷은 ap-northeast-2에 있고 모든 공개 접근을 차단한다.
2. 버킷은 SSE-S3 기본 암호화, 버킷 소유자 강제 객체 소유권, `videos/pending/` 1일 만료 규칙과
   운영 웹 출처의 PUT CORS를 가진다.
3. `FillMapVideoUploadProd` IAM 정책은 운영 영상 경로의 PutObject, GetObject, DeleteObject만 허용한다.
   prod EC2 역할이 생기기 전에는 어떤 역할에도 연결하지 않는다.
4. 운영 CloudFront 배포는 `PriceClass_200`, HTTPS 강제, GET과 HEAD 허용, IPv6 사용으로 구성한다.
5. OAC[^2] 버킷 정책은 운영 배포가 `videos/encoded/*`, `videos/blurred/*`, `videos/thumb/*`만 읽게 한다.
   원본과 pending 객체는 CloudFront에서 읽지 못한다.
6. `media.fillmap.kr`은 Route 53 별칭 레코드[^3]로 운영 배포를 가리키며 유효한 HTTPS 인증서를 쓴다.
7. 서명 없는 URL과 만료된 URL은 403이다. 유효한 전체 GET은 200, Range GET은 206과 올바른
   `Content-Range`를 반환한다.
8. 같은 객체의 반복 요청은 CloudFront 캐시를 적중한다.
9. dev 배포 `E3CZ3XF3CKTFQM`과 `d3teyj4rrssh77.cloudfront.net`의 설정과 동작은 바뀌지 않는다.
10. 운영 백엔드가 사용할 환경변수와 되돌리기 절차를 `.claude/docs/deploy.md`에 기록한다.

## 설계 결정

### D1. 운영 자원은 dev와 분리한다

운영 버킷, OAC, 공개 키와 신뢰 키 그룹, CloudFront 배포를 새로 만든다. dev 개인 키로 운영 URL을
서명할 수 없게 RSA 2048 운영 키 쌍도 분리한다. 개인 키는 레포와 환경변수에 넣지 않고 현재 운영
준비 호스트의 `/home/ubuntu/fillmap-prod-cloudfront-private-key.pem`에 권한 600으로 둔다.

캐시 정책은 환경별 상태를 갖지 않으므로 MSG-67의 TTL 0/600/600초 정책을 재사용한다. 서명 쿼리
문자열, 쿠키와 요청 헤더가 캐시 키에서 빠져 사용자별 서명 URL도 같은 객체 캐시를 공유한다.

### D2. 운영 버킷은 영상 경로만 준비한다

버킷은 브라우저의 S3 직접 업로드를 위해 `https://fillmap.kr`과 `https://www.fillmap.kr`의 PUT만
CORS로 허용한다. 미완료 영상은 하루 뒤 만료한다. 프로필 이미지와 미션 이미지의 공개 정책은 이
티켓에서 열지 않는다. 운영 애플리케이션을 배포하기 전에 해당 기능의 별도 운영 준비가 필요하다.

### D3. 인증서는 media.fillmap.kr 전용으로 발급한다

기존 us-east-1 ACM 인증서[^4]는 `fillmap.kr`만 포함하므로 재사용할 수 없다. CloudFront가 요구하는
us-east-1에서 `media.fillmap.kr` 인증서를 새로 발급하고 Route 53 DNS 검증을 쓴다. 배포에는
`media.fillmap.kr` 하나만 별칭으로 연결한다.

### D4. HLS와 추가 엣지 기능은 넣지 않는다

재생 산출물은 MSG-67과 같은 `+faststart` MP4다. HLS, WAF, Origin Shield, CloudFront Functions,
Lambda@Edge와 실시간 로그는 추가하지 않는다. 30초 MP4의 반복 재생에 필요한 캐시와 Range 응답만
구성한다.

## API 명세

신규 API와 필드는 없다. 운영 백엔드가 아래 값을 주입받으면 기존 `ThumbnailUrlPresigner`가
`https://media.fillmap.kr/{s3Key}`를 600초 동안 유효한 canned policy[^5]로 서명한다.

```text
CLOUDFRONT_ENABLED=true
CLOUDFRONT_DOMAIN=media.fillmap.kr
CLOUDFRONT_KEY_PAIR_ID={운영 공개 키 ID}
CLOUDFRONT_PRIVATE_KEY_PATH=/home/ubuntu/fillmap-prod-cloudfront-private-key.pem
```

## 설정과 인프라

### AWS 자원

- S3 버킷 `fillmap-video-prod`, ap-northeast-2
- 관리형 IAM 정책 `FillMapVideoUploadProd`, 아직 역할 연결 없음
- 운영 OAC 1개
- RSA 2048 공개 키 1개와 운영 신뢰 키 그룹 1개
- MSG-67 캐시 정책 `1993b24f-5cde-4352-a428-dd9b2892c41a` 재사용
- `media.fillmap.kr` ACM 인증서 1개, us-east-1
- 표준 CloudFront 배포 1개와 Route 53 A, AAAA 별칭 레코드

자원에는 `Project=FillMap`, `Environment=prod`, `Ticket=MSG-495` 태그를 붙인다. CloudFront 배포와
버킷 정책을 먼저 검증한 뒤 운영 애플리케이션에서 CDN 플래그를 켠다.

### 적용 순서

1. 운영 S3 버킷과 보안 설정을 만든다.
2. 운영 영상 경로용 IAM 정책을 만들되 dev 역할에는 연결하지 않는다.
3. 운영 키 쌍, CloudFront 공개 키와 신뢰 키 그룹을 만든다.
4. OAC와 ACM 인증서를 만들고 인증서의 DNS 검증을 마친다.
5. 운영 CloudFront 배포를 만든다.
6. 배포 ARN으로 버킷의 OAC 읽기 정책을 제한한다.
7. 배포가 `Deployed`가 된 뒤 Route 53 A와 AAAA 별칭 레코드를 만든다.
8. 임시 MP4로 서명, Range, 캐시와 접근 거부를 검증한 뒤 검증 객체를 삭제한다.

### 되돌리기

운영 애플리케이션을 배포한 뒤 문제가 생기면 `CLOUDFRONT_ENABLED=false`로 기존 S3 사전서명 URL을
사용한다. 도메인 문제가 있으면 Route 53 A와 AAAA 별칭을 제거한다. CloudFront 배포는 비활성화 후
삭제하며 운영 버킷과 객체는 자동으로 삭제하지 않는다.

## 도메인 로직

MSG-67에서 구현한 서명과 폴백 로직을 그대로 사용한다. 새 Java 코드, 스케줄러와 실행기는 없다.
운영 설정이 켜졌는데 도메인, 공개 키 ID나 개인 키 파일이 없으면 애플리케이션은 기동에 실패한다.

## 데이터 모델

엔티티, SQL과 Flyway 마이그레이션은 없다. DB에는 계속 S3 키만 저장하고 URL 호스트는 요청 시점에
붙인다.

- `fillmap-video-prod` 버킷을 ap-northeast-2에 만들었다. 모든 공개 접근 차단, SSE-S3, 버킷 소유자

- 관리형 정책 `FillMapVideoUploadProd`는 `arn:aws:s3:::fillmap-video-prod/videos/*`의 PutObject,
  GetObject, DeleteObject만 허용한다. 연결된 역할, 사용자와 그룹은 모두 0개다.
- 운영 OAC `E34R2FIFKBI670`, 공개 키 `K16XTNUYLRC55E`, 신뢰 키 그룹
  `7b522040-a71c-4b53-95a2-a89e1ffecba3`을 만들었다. 개인 키는
  `/home/ubuntu/fillmap-prod-cloudfront-private-key.pem`에 권한 600으로 저장했다.
- CloudFront 배포 `E3RTGBXCIBKF2M`은 `media.fillmap.kr` 인증서와 A, AAAA 별칭을 사용한다.
  배포 상태는 `Deployed`이며 OAC 버킷 정책은 encoded, blurred, thumb 경로만 허용한다.
- FFmpeg testsrc로 만든 10,439바이트 MP4를 임시로 올려 검증했다. 유효한 전체 GET은 200이고 원본과
  응답의 SHA-256이 같았다. `Range: bytes=0-1023`은 206, `Content-Range: bytes 0-1023/10439`,
  응답 본문 1,024바이트였다. 반복 요청은 `Hit from cloudfront`, age 15초를 반환했다.
- 미서명, 만료된 서명, original과 pending 경로는 모두 403이었다. dev 배포의 기존 객체도 Range 206,
  `Content-Range: bytes 0-1023/234338`을 유지했다.
- 검증용 운영 객체 3개는 확인 직후 삭제했다. DB 쓰기, SQL, 예외 변환, 생명주기 콜백과 자체 실행기는
  없다. 운영 애플리케이션과 prod EC2가 없어 환경변수 주입과 IAM 역할 연결은 배포 시점에 남는다.
- 사용자 커밋 `1af9f482` 뒤 전체 `./gradlew build`가 2분 28초에 통과했다. AWS 재조회에서도 배포는
  `Deployed`, 인증서는 `ISSUED`, A와 AAAA 별칭은 운영 배포를 가리켰고 버킷 공개 상태는 false였다.
  추가 리뷰 도구는 커밋 뒤 남은 무관한 부하테스트 파일만 검토해 MSG-495 반영 사항은 수동 대조했다.

[^1]: CloudFront 서명 URL은 백엔드가 객체 경로와 만료 시각을 개인 키로 서명한 주소다. CloudFront는 운영 신뢰 키 그룹의 공개 키로 서명을 확인한다.
[^2]: Origin Access Control은 CloudFront가 S3 원본에 보내는 요청을 AWS 서명으로 인증한다. 버킷을 공개하지 않고 지정한 배포에 필요한 읽기 권한만 줄 수 있다.
[^3]: Route 53 별칭 레코드는 도메인 이름을 CloudFront 같은 AWS 자원에 연결하는 DNS 레코드다. CloudFront 배포의 주소가 바뀌어도 레코드 대상은 AWS가 관리한다.
[^4]: ACM 인증서는 AWS 서비스가 HTTPS에 사용할 인증서를 발급하고 갱신한다. CloudFront용 인증서는 us-east-1에 있어야 한다.
[^5]: canned policy는 객체 하나와 만료 시각만 담는 CloudFront의 짧은 서명 정책이다. 현재 재생 계약에는 시작 시각이나 접속 IP 제한이 없어 이 방식이면 충분하다.
