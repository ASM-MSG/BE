# MSG-583: 행사 시작 알림의 반복 저장 비용 줄이기

**Owner**: B(콘텐츠와 인증). `event`와 `notification`의 내부 구현을 다룬다. `event` 배정은 AGENTS.md가 안내하는 `.claude/CLAUDE.md` 협업 원칙과 MSG-438을 따른다.

## 개요

이벤트 회차의 시작 알림을 구독자마다 저장하는 경로를 회차별 `INSERT SELECT` 한 문장으로 바꾼다. 구독자 엔티티 전량 조회와 사용자별 반복 호출을 없애고 기존 알림 기록 서비스 경계는 유지한다.

PRD 면제 근거: 기존 FR-EVENT-06과 MSG-442의 수신 대상, 문구, 중복 방지, 발송 창, 트랜잭션 범위를 유지하는 성능 개선이다. 제품 요구사항과 성능 목표를 새로 만들지 않는다. 사용자 승인 범위는 스펙 작성, 구현, 같은 규모 재측정이다. 감사 후속 번호 MSG-583을 사용하며 Jira 변경은 범위 밖이다.

참조 정본은 [기존 스펙](MSG-442.md), [확정 PRD](../prd/event-room-location-videos.md)의 US-007과 FR-16, `docs/srs.md` FR-EVENT-06이다. PRD 헤더의 첫 상태 토큰 `확정`을 확인했다. 위키 `03-specs`와 `04-decisions`의 행사 관련 항목도 조회했다. `ADR 행사 중심 임시 커뮤니티 행사방.md`는 2026-08-19 갱신된 초안이므로 2026-08-20 확정 PRD와 후속 MSG-442 구현 계약을 우선한다.

## 배경과 목표

[대량 실측 보고서](../audit/2026-09-08-backend-audit-tx-load.md)에서 구독자 5만 명의 시작 알림 기록은 400.387초, 같은 행사 잠금의 경쟁 요청은 334.367초가 걸렸다. 준비된 SQL 문장 수는 50,005회였고, 실행 스택에서 구독자별 native INSERT 전 반복 flush[^1]를 확인했다. 각 원인의 시간 비중을 분리한 결과는 아니다.

구독자 수에 비례하는 애플리케이션 SQL 호출과 엔티티 관리를 제거한다. 개선 여부는 기존과 같은 데이터 규모 및 계측 조건으로 비교한다. 초 단위 상한, 개선율, 운영 SLO를 완료 조건으로 신설하지 않는다.

## 성공 기준

- AC-583-01: 기존 회차 후보 조건과 `created_at <= starts_at`에 맞는 현재 구독자에게만 기존 내용의 시작 알림을 기록한다. 시작 정각 포함, 종료 정각 및 24시간 정각 제외를 유지한다.
- AC-583-02: 동일 사용자와 event key의 재실행은 한 건으로 수렴하며 기존 행의 내용과 상태를 덮지 않는다. 시작 일정이 바뀌면 기존 규칙대로 새 키를 사용한다.
- AC-583-03: 모든 후보 회차 기록은 기존 전역 잠금 아래 한 발송 트랜잭션으로 처리한다. 중간 실패는 앞선 회차 기록까지 롤백하며 종료 정리는 독립적으로 실행된다. 원인 제거 후 발송 창 안의 다음 틱에서 복구한다.
- AC-583-04: 구독 취소 및 사용자 탈퇴 경합에서 외래 키와 조회 시점 계약을 유지한다. 존재하지 않는 사용자의 알림을 남기거나 DB 오류를 부분 성공으로 삼키지 않는다.
- AC-583-05: 시작 알림의 구독자 엔티티 전량 조회와 사용자별 INSERT가 사라지고 후보 회차당 한 번의 알림 DML[^2]만 실행된다. 1천, 1만, 5만 명의 신규 기록 및 기존 측정에 대응하는 중복 실행을 재측정해 행 수, 중복, 처리 시간, SQL 횟수, 연결 점유, 잠금 경합을 보고한다.

## API 명세

외부 endpoint, HTTP method, RequestDto, ResponseDto, 성공 응답 및 에러 코드는 변경하지 않는다. 기존 구독 토글과 알림함 조회도 그대로다. 이번 작업은 스케줄러 내부 기록 경로만 바꾼다.

## 도메인 로직

### 기존 실행 경계 유지

1. `EventNotificationScheduler.tick()`에서 주입 Clock으로 UTC `now`를 한 번 구한다. 기존 `notificationEnabled` 조건을 통과한 경우 시작 알림 단계를 실행한다.
2. 기존 `TransactionTemplate` 안에서 `EventSeriesRepository.acquireEventWriteLock()`으로 `event_seed` 전역 트랜잭션 advisory lock[^3]을 먼저 얻는다.
3. 기존 `findStartNotificationCandidates(now, now.minusHours(24))`를 그대로 호출한다. 조건은 `starts_at <= now AND ends_at > now AND starts_at > now - 24시간`이다.
4. 후보 회차마다 기존 코드로 키와 문구를 만들고 새 알림 서비스 메서드를 한 번 호출한다. 구독자 목록은 애플리케이션으로 가져오지 않는다.
5. 발송 실패는 발송 트랜잭션 밖의 기존 catch에서 경고를 남긴다. 이후 종료 구독 정리는 별도 `TransactionTemplate`에서 같은 잠금을 얻고 기존 DELETE를 실행한다. 발송 비활성일 때도 정리는 실행한다.

`fixedDelay`와 `initialDelay`의 기본 300000ms, `!encoding-worker` 프로필, 전체 후보 회차를 묶는 커밋 경계는 그대로다. 회차나 사용자 단위 커밋, 비동기 호출, 새 executor, 잠금 축소, 전역 flush 모드 변경은 하지 않는다.

### 회차별 일괄 기록

`NotificationCommandService`에 아래 내부 메서드를 추가하고 구현체에서 기존과 같은 `@Transactional` REQUIRED 전파로 repository에 위임한다. 알림 DB 쓰기는 `notification`이 소유한다. 반환 건수를 소비하지 않으므로 서비스 반환형은 `void`다.

```java
void recordEventStart(long occurrenceId, LocalDateTime startsAt,
    String eventKey, String title, String body);
```

`NotificationRepository`에 `@Modifying` native 쿼리 메서드 `int insertEventStart(...)`를 추가한다. 입력은 위와 동일하고 SQL은 다음과 같다.

```sql
INSERT INTO notifications (user_id, category, event_key, title, body, created_at)
SELECT s.user_id, 'EVENT', :eventKey, :title, :body,
       statement_timestamp() AT TIME ZONE 'UTC'
FROM event_notification_subscriptions s
WHERE s.event_occurrence_id = :occurrenceId
  AND s.created_at <= :startsAt
ON CONFLICT (user_id, event_key) DO NOTHING
```

| 항목 | 유지할 값 |
|---|---|
| category | `EVENT` |
| event key | `EVENT_START:{occurrenceKey}:{startsAt의 UTC epoch초}` |
| title | 회차의 title 그대로 |
| body | `행사가 시작됐어요. 현장 영상을 올려보세요` |
| created_at | 기존 INSERT와 같은 `statement_timestamp() AT TIME ZONE 'UTC'` |
| 초기 상태 | 기존 DDL DEFAULT에 따른 `PENDING`, `retry_count = 0`; 나머지 기본값도 기존과 동일 |

같은 문장으로 기록한 회차의 알림은 같은 created_at을 가진다. 기존 개별 INSERT의 사용자별 기록 시각 간격은 보장된 계약이 아니며, 시각의 의미는 계속 DB 기록 시점의 UTC다. 수신 거부와 푸시 토큰은 기존 소비 단계가 판단한다. 여기서 새 필터를 붙이지 않는다. outbox[^4]에 기록만 하며 Kafka나 FCM을 직접 호출하지 않는다.

기존 `record(...)`와 `NotificationRepository.insert(...)`는 그대로 둔다. 그 호출자는 뱃지, 친구, 핫구역 진입, 스트릭 리마인드, 주간 요약, 영상 상태 및 검수, `EventSeeder` 일정 변경 알림이다. `findAllByIdEventOccurrenceId(...)` 역시 일정 변경 알림이 사용하므로 삭제하지 않는다.

### 경합과 실패

구독 토글은 현재 `event_seed` 잠금을 얻지 않는다. 기존 구현도 회차별 구독자 SELECT가 본 스냅샷[^5]을 대상으로 기록하며 취소 API와 직렬화되지 않는다. 개선 후에는 같은 대상 술어를 INSERT SELECT의 문장 스냅샷에서 평가한다. 이전 SELECT와 새 INSERT SELECT 사이에 취소가 커밋되는 실행 순서라면 수신자 결과가 달라질 수 있다. 조회와 기록 사이 간격을 없애는 변화이며, 취소 완료 후 이미 진행 중인 기록을 반드시 철회한다는 새 보장은 만들지 않는다.

INSERT SELECT 시작 전에 커밋된 취소는 제외한다. 그 문장이 이미 본 구독이 이후 취소되면 해당 틱에 알림이 기록될 수 있다. ON을 시작 후에 눌렀다면 `created_at > startsAt` 조건으로 제외한다. 시작 정각에 저장된 구독은 포함한다. 일정 변경과 종료 정리는 기존 전역 잠금 순서로 직렬화한다.

사용자 탈퇴는 구독과 알림의 기존 `ON DELETE CASCADE`를 유지한다. 탈퇴가 먼저 커밋돼 구독이 사라지면 대상이 아니다. 문장 스냅샷에 구독이 남았지만 알림 INSERT의 외래 키 검사 전에 사용자가 삭제됐다면 DB 오류가 발송 트랜잭션 전체를 롤백할 수 있다. 기록이 먼저 완료되면 탈퇴가 연쇄 삭제한다. 오류를 사용자별로 무시하거나 users JOIN만으로 경합이 해결됐다고 간주하지 않는다.

### 대안 판단

구독자 projection은 엔티티 관리만 줄이고 사용자별 SQL 왕복을 남긴다. JDBC 배치는 별도 목록과 배치 처리를 요구한다. 현재 목적에는 기존 repository에 INSERT SELECT 하나를 추가하는 방법이 더 작다. 회차 목록까지 한 SQL로 합치면 event key 생성과 후보 판정을 SQL로 옮겨야 하므로 기존 회차 루프를 유지한다.

## 데이터 모델

엔티티, 컬럼, 인덱스, 제약 변경과 Flyway 마이그레이션은 없다. 기존 `idx_event_noti_sub_occurrence(event_occurrence_id)`와 `uq_notifications_user_event(user_id, event_key)`를 사용한다. 실제 인덱스 사용 여부는 재측정 실행 계획으로 확인하며 계획을 미리 단정하지 않는다. Redis 키, TTL, S3 경로는 추가하지 않는다.

## 계약 변경

Owner A/B 접점인 `GridQueryService`, `HotZoneService`, `UserGridQueryService`, `UserOidcCommandService` 변경은 없다. Owner B 내부 `NotificationCommandService`에 `recordEventStart(...)`만 추가한다. 새 추상 메서드로 함수형 인터페이스가 아니게 되므로 기존 `EventNotificationSchedulerTest`, `StreakRemindSchedulerTest`, `WeeklySummarySchedulerTest`의 실패 주입 lambda는 Mockito mock 등 기존 테스트 도구로 교체한다. 단건 `record(...)`를 쓰는 기존 호출자의 시그니처와 동작은 유지한다.

## 같은 규모 재측정

기존 `load-test/tx-workload/EventFanoutBenchmark.java`와 초기화 설정을 재사용한다. 별도 합성 DB에서 자동 예약 작업을 취소하고 실제 repository, command service, transaction manager를 주입한 tick을 실행한다. fixture 준비와 정합성 조회는 시간 및 SQL 횟수에서 제외한다.

- 1천 명과 1만 명: 준비 실행 1회 제외 후 신규 기록 3회의 중앙값과 범위, 중복 재실행 1회. 기존 5만 명 수치는 단발이므로 같은 규모 단발 신규 기록을 비교하고 추가 반복은 별도로 표시한다.
- JDK, 힙 2GiB, Hikari 2개, PostgreSQL 설정, JaCoCo, 데이터 분포를 기존 조건과 맞춘다. 기존 5만 명은 JFR과 잠금 관찰이 포함된 진단값이므로 계측 차이를 숨기지 않는다.
- 처리 시간, 첫 발송 TX 시간, prepare 횟수, 실제 업무 SQL execute, 연결 반환 횟수와 점유 합계, 동일 `event_seed` 경쟁 잠금의 차단 여부 및 획득 시간을 기록한다. 빨라져 자연 경합을 놓치면 대기 0초로 단정하지 않고 미관측으로 표시하며, 제어된 경합 검증은 순수 시간 측정과 분리한다.
- 사용자별 알림 N건, 중복 0건, 구독 N건, 발송과 정리의 두 트랜잭션 커밋을 확인한다. 중복 실행에서는 신규 알림 0건과 기존 행 보존을 확인한다.
- 결과는 기존 실측 수치와 나란히 기록하고 완료 샘플과 전체 실행 성공을 구분한다. 운영 처리량이나 HTTP 동시 사용자 수로 외삽하지 않는다. 원문, 실행 명령, 종료 후 합성 데이터 정리 결과를 남긴다.

### 2026-09-08 구현 및 실측

- `EventNotificationScheduler`의 구독자 로딩·개별 기록을 `recordEventStart` 호출로 교체했다. 기존 단건 메서드와 EventSeeder 경로는 유지했다. 서비스 반환형은 void, repository는 기존 DB 제약으로 중복을 흡수한다.

- 실제 SQL: 발송은 `SELECT pg_advisory_xact_lock(hashtextextended('event_seed', 0))` → 후보 회차 SELECT → 위 명세의 INSERT SELECT였다. 종료 정리는 별도 TX에서 같은 잠금 → 종료 회차 구독 DELETE로 실행됐다. 1천 명 DB 로그에서 각각 업무 execute 3회·2회, 전체 prepare 5회를 확인했다. 원문은 [검증 기록](../../load-test/tx-workload/event-performance-results.txt)에 보존했다.
- 예외: 두 번째 회차에 title=null을 전달해 DB NOT NULL 오류를 발생시켰다. repository 예외가 REQUIRED 서비스와 발송 TransactionTemplate을 빠져나가 첫 회차까지 롤백됐고, `notifyStarted`의 기존 catch에서 경고 후 독립 정리 TX가 성공했다. 다음 틱은 두 회차를 복구했다. HTTP 핸들러 밖이므로 새 developCode는 없다.
- 빈·TX: 새 빈과 executor는 없다. 기존 주기·초기 지연 5분, encoding-worker 제외, Clock 주입을 유지했다. 서비스 프록시의 REQUIRED가 발송 TX에 참여하며 전체 후보 기록 뒤 커밋한다. 종료 정리는 다음 TX다.

## 미해결 질문

제품 정책 질문은 없다. 동시 탈퇴의 모든 실행 순서와 운영 처리량은 측정하지 않았다. 기존 외래 키·전체 롤백 계약을 유지하며 그 범위를 넘어선 보장은 하지 않는다.

[^1]: flush는 영속성 컨텍스트가 관리하는 엔티티의 변경을 확인하고 DB에 반영하는 과정이다. 기존 경로는 전량 조회한 구독자가 남은 상태에서 native INSERT를 반복해 검사 비용도 반복됐다.
[^2]: DML은 INSERT, UPDATE, DELETE처럼 데이터를 바꾸는 SQL 문장이다. 한 문장으로 많은 행을 기록해도 DB의 행별 제약 검사 비용까지 사라지는 것은 아니다.
[^3]: 트랜잭션 advisory lock은 정해진 키를 직접 잠그는 PostgreSQL 기능이다. 이 경로의 `event_seed` 잠금은 일정 갱신과 알림 기록 및 종료 정리를 커밋 또는 롤백까지 직렬화한다.
[^4]: outbox는 외부 발송 요청을 먼저 DB에 저장하는 방식이다. 이번 작업은 notifications 기록까지이며 실제 전달과 재시도는 기존 릴레이 및 소비자가 담당한다.
[^5]: 문장 스냅샷은 SQL이 읽을 때 보이는 데이터 상태다. 현재 구독 토글은 행사 전역 잠금에 참여하지 않으므로 기록 도중 취소가 커밋돼도 이미 선택된 수신자가 즉시 철회된다는 뜻은 아니다.
