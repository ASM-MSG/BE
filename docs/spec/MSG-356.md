# MSG-356: 지도 축소 시 격자 집계 조회 (줌아웃 클러스터링)

**Owner**: 공동 (grid 패키지는 A, friend 패키지는 B, `GridQueryService` 계약 변경 포함)

> 요구사항 정본: `docs/prd/MSG-356-prd.md` (검토됨, 2026-08-10 정민 승인).
> FE 계약 예고: LLM-WIKI `03-specs/지도 홈 API 연동 가이드 FE.md` §1.5. 필드명은 이 스펙이
> 확정하며, 구현 마무리 때 가이드의 가안을 확정 필드명으로 갱신한다.

## 개요

지도를 축소한 시야에서 개별 100m 격자 대신, 뷰포트[^1] 안 점령 격자를 행정 단위(동, 구, 시)로
묶어 센 집계 목록을 내려주는 조회를 신설한다. 내 도감과 친구 도감 레이어가 같은 집계를 쓴다.
서버는 1차 압축(행정 3단 집계)만 담당하고, 화면에서 마커가 겹칠 때의 병합은 네이버 지도 SDK
마커 클러스터링(FE)이 담당하는 2단 구조다. 격자 시프트(500m 묶음) 같은 중간 집계 단위는
이번에 만들지 않는다(PRD 비목표, 실측 후 확장 지점).

## 배경 · 목표

축소 상태에서 100m 격자 전량 전송은 전송량만 크고 화면이 밀도를 읽지 못한다(2026-08-08 김민수
멘토링 확정 방향). 서버가 축척[^2]에 맞는 집계 표현을 내려주면 FE가 마커 병합으로 마무리한다.
전환 시점은 서버가 모른다. FE가 축척 구간(250m~500m는 동, 1km~8km는 구, 16km~전체는 시)에
따라 단위 파라미터만 바꿔 부르고, 서버는 받은 단위로 묶어 셀 뿐이다.

## 성공 기준

1. 축소 뷰포트에서 단위별 집계 목록을 페이지 없이 한 번에 받는다 (FR-1, FR-5).
2. 어느 단위로 묶어 세어도, FE가 항목을 더 묶어 합산해도, 같은 뷰포트 개별 격자 조회의 총
   개수와 값이 일치한다 (FR-3, FR-7). 행정동 미판정 격자도 누락되지 않는다.
3. 확대해서 개별 조회로 돌아갈 때 경계가 자연스럽게 이어진다. 집계와 개별 조회가 같은 뷰포트
   환산(`GridEncoder.viewportRange`)과 같은 필터 술어를 쓰는 것으로 구조적으로 보장한다.
4. 친구 도감 레이어가 같은 집계를 받고, 친구 관계 검증은 기존 친구 뷰포트 조회와 동일하게
   요청 시점 실시간이다 (FR-4).
5. 구현 후 FE와 함께 전환 기준(화면당 약 100객체)을 실측해 이 문서 작업 로그에 기록한다
   (Jira 완료 조건).

## API 명세

### 1. 내 도감 집계 조회

`GET /api/grids/aggregation`

| 파라미터 | 타입 | 필수 | 설명 |
|---|---|---|---|
| `swLat` | Double | O | 남서 모서리 위도 (기존 뷰포트 조회와 동일) |
| `swLng` | Double | O | 남서 모서리 경도 |
| `neLat` | Double | O | 북동 모서리 위도 |
| `neLng` | Double | O | 북동 모서리 경도 |
| `unit` | String | O | 집계 단위. `DONG`(동), `SIGUNGU`(구), `SIDO`(시). 대소문자 무관 (auth `parseProvider` 선례) |

FE 전환 표의 "구"는 정확히는 시군구, "시"는 시도 수준이라 파라미터 이름은 행정 표준 용어인
`SIGUNGU`, `SIDO`로 쓴다. 페이지 파라미터는 없다. 커서와 size를 받지 않는다.

라우팅 주의: 기존 `GET /api/grids/{gridId}`와 같은 컨트롤러에 얹지만, Spring MVC는 리터럴
세그먼트(`aggregation`)를 경로 변수보다 우선 매칭하므로 충돌하지 않는다.

성공 응답 (200, `ApiResponseDto` 래핑):

```json
{
	"developCode": 200,
	"message": "성공",
	"data": [
		{ "regionCode": "2623058000", "name": "부전2동", "lat": 35.162, "lng": 129.065, "count": 31 },
		{ "regionCode": "2623059000", "name": "전포동", "lat": 35.155, "lng": 129.071, "count": 12 },
		{ "regionCode": null, "name": null, "lat": 35.101, "lng": 129.032, "count": 2 }
	]
}
```

| 필드 | 의미 |
|---|---|
| `regionCode` | 묶음 키. 동은 행정동 코드[^3] 10자리, 구는 앞 5자리, 시는 앞 2자리. 미판정 항목만 null |
| `name` | 단위 표시 이름 (동 "부전2동", 구 "부산진구", 시 "부산광역시"). 미판정 항목만 null |
| `lat`, `lng` | 마커 대표 좌표 (WGS84) |
| `count` | 그 단위 안 점령 격자 수 |

`name`, `lat`, `lng`, `count`는 FE 가이드 §1.5 가안을 그대로 확정한 것이고, `regionCode`는
마커 식별 키로 추가한다. 동 이름은 전국에서 중복될 수 있어(여러 도시의 "중앙동") 이름만으로는
항목 식별이 안 되고, 팬 이동 간 마커 재사용에도 안정 키가 필요하다. "부산광역시 214"를
"부산 214"로 줄이는 표기 축약은 FE 몫이다.

정렬은 `regionCode` 오름차순, 미판정 항목(null)은 마지막이다. 점령 격자가 0개인 단위는
항목이 없고(FR-5), 뷰포트 안에 점령 격자가 하나도 없으면 200에 빈 배열이다.

에러 케이스:

| developCode | 조건 |
|---|---|
| `4401 INVALID_VIEWPORT` | bbox 파라미터 누락, 뒤집힌 bbox (기존과 동일) |
| `4402 VIEWPORT_TOO_LARGE` | 단위별 bbox 상한 초과 (아래 도메인 로직, 기존 코드 재사용) |
| `4405 INVALID_AGGREGATION_UNIT` (신규) | `unit` 누락 또는 미지원 값 |

`unit`은 기존 bbox 파라미터처럼 `required = false`로 받아 컨트롤러가 직접 검증한다. Spring의
필수 파라미터 예외는 전역 핸들러에서 500으로 새기 때문에 기존 `toBounds` 패턴을 따른다.

### 2. 친구 도감 집계 조회

`GET /api/friends/{userId}/grids/aggregation`

파라미터, 응답, 에러가 1번과 완전히 같고 다음이 추가된다.

- 친구 판정 실패(비친구, 본인 ID, 대기 중 상대, 미존재 userId)는 기존 친구 뷰포트 조회와 같은
  `9424 FRIENDSHIP_NOT_FOUND` 단일 실패다 (관계와 계정 존재 은닉).
- 검증 순서는 MSG-187 D3-1을 따른다. bbox와 unit 파싱(컨트롤러)이 친구 판정(서비스)보다
  앞서도 관계 정보를 누설하지 않으므로 은닉이 깨지지 않는다. `toBounds`와 unit 파싱 헬퍼는
  기존 관례대로 FriendController에 동형 사본을 둔다.

## 도메인 로직

### 묶음 키: 행정동 코드 접두

격자의 저장 라벨 `grids.region_code`(10자리, MSG-167)를 단위별 길이로 잘라 묶는다. 동은
10자리 전체, 구는 앞 5자리(시군구), 시는 앞 2자리(시도)다. 앞자리가 상위 단위를 가리키는
행정동 코드 체계 덕에 별도 매핑 테이블이 필요 없다 (`RegionGeoJsonReader.PARENT_CODE_LENGTH = 5`
선례).

### 단위 이름: region_name 토큰 분해

`regions.region_name`은 "부산광역시 부산진구 부전2동" 전체 경로 형식이고, 원천 데이터
(HangJeongDong GeoJSON `adm_nm`) 전수에서 공백 구분 3토큰이 성립한다. 세종처럼 시군구가
없는 지역도 "세종특별자치시 세종시 조치원읍"으로 3토큰이다 (2026-08-10 `data/region/` 실측).
따라서 이름은 `split_part(region_name, ' ', n)`으로 도출한다. 동은 3번째, 구는 2번째, 시는
1번째 토큰이다.

한계 하나를 데이터 원형 그대로 수용한다. 경기도 등 일반시의 시군구 토큰은 원천 데이터가
"수원시장안구"처럼 붙여 쓴다. 서버는 원형을 내려주고, 표기 정형화가 필요해지면 FE 표기나
데이터 후속 티켓의 몫이다.

같은 묶음 안 이름은 접두가 같아 항상 한 값이지만, 집계 함수 자리라 `MIN()`으로 결정적으로
단일화한다 (데이터 불일치 시에도 응답이 흔들리지 않는 보험).

### 대표 좌표: 그룹 점령 격자 중심의 평균 (PRD 미해결 ② 확정)

마커 좌표는 그 그룹에 속한 점령 격자들의 중심점(`grids.center_geom`) 평균으로 한다.
행정 경계 도형(`regions.boundary_geom`)의 무게중심은 쓰지 않는다. 근거는 세 가지다.

1. 마커가 실제 데이터 위에 선다. 부산 전체에서 해운대만 점령한 사용자의 시 마커가 도시
   기하 중심(바다일 수 있음)이 아니라 점령 지점 근처에 찍힌다. 네이버 SDK 클러스터 마커가
   구성원 평균 위치에 서는 것과도 의미가 맞는다.
2. 규칙 하나로 전 그룹이 성립한다. 미판정 격자 묶음은 행정 경계가 아예 없어 경계 무게중심
   방식으로는 좌표를 만들 수 없다.
3. 비용이 없다. 구와 시는 저장된 경계 도형이 없어(행 단위는 동뿐) 경계 방식이면 요청마다
   MULTIPOLYGON 합성이 필요하지만, 평균은 이미 스캔하는 행의 산술이다.

위경도 단순 평균은 한국 스팬에서 왜곡이 무시 가능하다. `center_geom`이 GEOGRAPHY[^4] 타입이라
SQL에서는 `::geometry` 캐스트 후 `ST_X`, `ST_Y`로 꺼낸다.

### 행정동 미판정 격자 (PRD 미해결 ① 확정)

`region_code IS NULL`인 격자(해상 등)는 단위와 무관하게 **이름 없는 항목 하나**로 묶어
응답에 포함한다. `regionCode`와 `name`이 null이고 좌표와 count 규칙은 동일하다. 제외가
아니라 항목화이므로 집계 총합에서 누락되지 않는다(FR-7). 구현은 특례 코드가 없다.
PostgreSQL `GROUP BY`가 NULL 키를 한 그룹으로 묶는 표준 동작이 그대로 이 버킷이 된다.
이름 없는 마커의 표기(개수만 표시 등)는 FE 몫이며 가이드 갱신 때 안내한다.

### bbox 차등 상한 (FR-6 확정 수치)

| 조회 | 한 변 상한 (위도, 경도 각각) |
|---|---|
| 개별 격자 조회 (기존) | 0.5도 불변 |
| 집계 `DONG` | 1.0도 |
| 집계 `SIGUNGU` | 4.0도 |
| 집계 `SIDO` | 상한 없음 (전국 시야 허용, 뒤집힘 검증만) |

수치 근거: 각 단위의 축척 구간에서 나올 수 있는 최대 시야보다 넉넉히 크게 잡아 정상 사용이
절대 걸리지 않게 하되, 단위에 안 맞는 과대 요청(동 단위로 전국 등)만 거른다. 스캔량 자체는
`user_id` 필터가 먼저라 사용자의 점령 격자 수로 유계이므로, 시 단위 무상한도 안전하다.
초과 시 기존 `4402 VIEWPORT_TOO_LARGE`를 재사용한다(새 코드 불요). 상한 값은 단위 enum
(`RegionUnit`)이 접두 길이, 이름 토큰 위치와 함께 보유하는 것을 제안한다.

### 정합 근거 (FR-3)

집계 쿼리는 기존 개별 조회(접근 A)와 같은 FROM 절, 같은 WHERE 술어(`user_id`, `grid_y/grid_x`
BETWEEN), 같은 뷰포트 환산(`GridEncoder.viewportRange`, 꼭짓점 4점 min/max)을 쓴다. 세는
행 집합이 동일하므로 합이 어긋날 구조가 없다. 단위 그룹은 행 집합의 서로소 분할이라 FE가
항목을 어떻게 재조합해도 이중 계산이나 누락이 없다. 개별 조회는 keyset 페이지라 비교 시
전 페이지 합계 기준이다.

### 집계 쿼리 스케치 (GridRepository 신규)

```sql
SELECT
	substring(g.region_code FROM 1 FOR :codeLen)     AS "regionCode",
	MIN(split_part(r.region_name, ' ', :nameToken))  AS "name",
	AVG(ST_Y(g.center_geom::geometry))               AS "lat",
	AVG(ST_X(g.center_geom::geometry))               AS "lng",
	COUNT(*)                                         AS "count"
FROM user_grids ug
JOIN grids g ON g.grid_id = ug.grid_id
LEFT JOIN regions r ON r.region_code = g.region_code
WHERE ug.user_id = :userId
	AND g.grid_y BETWEEN :minY AND :maxY
	AND g.grid_x BETWEEN :minX AND :maxX
GROUP BY substring(g.region_code FROM 1 FOR :codeLen)
ORDER BY "regionCode" NULLS LAST
```

- `:codeLen`과 `:nameToken`은 단위 enum에서 온다. 동 (10, 3), 구 (5, 2), 시 (2, 1).
- `regions`는 기존 관례대로 LEFT JOIN이다(MSG-349). 미판정 격자를 INNER로 떨구면 FR-7이
  깨진다. NULL 키 행은 `substring(NULL)`이 NULL이라 자동으로 한 그룹이 된다.
- 접근 경로는 기존 `findOccupiedInRange`와 동일하고(신규 인덱스 불요), 출력만 단위 수로
  준다. videos 미접근이라는 `GridQueryService` 계약 주석도 그대로 성립한다.

### 성능

시 단위 전국 시야가 최다 스캔 경로지만, 스캔 행은 그 사용자의 전체 점령 격자 수로 유계라
기존 뷰포트 SLO(p95[^5] 300ms)를 준용한다(PRD 비기능, 신규 목표 없음). 집계 결과 행 수는
뷰포트가 아무리 커도 단위 개수(동 약 3,500 이하)로 유계다. 실측은 구현 후 작업 로그에 남긴다.

## 데이터 모델

**변경 없음. Flyway 마이그레이션 불요.** 재료가 전부 기존 스키마다.

- `grids.region_code` (V5, MSG-167) + `idx_grids_region_code` (V7). 이번 조회는 저장 라벨을
  행에서 읽고 regions와 PK 조인만 하므로 이 인덱스에 새로 의존하지도 않는다.
- `grids.center_geom` GEOGRAPHY(POINT, 4326) NOT NULL (V1, V28에서 재계산 완료).
- `regions.region_name` (RegionSeeder 시딩, 전체 경로 형식).

마이그레이션이 필요해지는 상황이 구현 중 발견되면 최신이 V28이므로 V29부터 쓰되, 현재
판단으로는 없다.

## 계약 변경

**`GridQueryService`(A 제공, B 소비) 시그니처가 늘어난다. 리뷰 시 상대 팀원 확인 필수.**
기존 3메서드(`getCell`, `getOccupiedInViewport` 2형)는 불변이다 (PRD 비목표, MSG-73/90 계약
유지).

```java
// com.msg.fillmap.grid.service.GridQueryService 신규 메서드
/**
 * viewport 안 점령 격자를 행정 단위(동, 시군구, 시도)로 묶어 센 집계 목록 (MSG-356).
 * 항목은 묶음 키(regionCode 접두), 표시 이름, 대표 좌표(그룹 점령 격자 중심 평균), 격자 수.
 * region_code 미판정 격자는 키와 이름이 null 인 항목 하나로 포함된다(제외 불가, FR-7).
 * bbox 상한은 단위별 차등(RegionUnit 보유), 초과 시 VIEWPORT_TOO_LARGE.
 */
List<RegionAggregateView> getOccupiedAggregatesInViewport(long userId, ViewportBounds bounds, RegionUnit unit);
```

동반 신규 타입 (모두 A 소유, B가 import):

```java
// com.msg.fillmap.grid.dto.RegionUnit: ViewportBounds 와 같은 자리 (B 공유 값객체 선례)
public enum RegionUnit {
	DONG(10, 3, 1.0),
	SIGUNGU(5, 2, 4.0),
	SIDO(2, 1, null);
	// (codePrefixLength, nameTokenIndex, maxSpanDeg. null 은 무상한)
}

// com.msg.fillmap.grid.service.RegionAggregateView: OccupiedGridView 선례의 내부 뷰
public record RegionAggregateView(String regionCode, String name, double lat, double lng, int count) {
}
```

HTTP 응답 변환은 컨트롤러 책임 관례대로 `com.msg.fillmap.grid.dto.RegionAggregateResponseDto`
(record, `from(view)`)가 담당한다.

B 내부 변경(계약 인터페이스 4종 밖이지만 병기): `FriendService`에
`List<RegionAggregateView> getFriendGridAggregates(Long userId, Long targetUserId, ViewportBounds bounds, RegionUnit unit)`
를 추가한다. 구현은 기존 `getFriendGrids`와 동일하게 `requireFriend` 판정 후
`gridQueryService.getOccupiedAggregatesInViewport(targetUserId, ...)` 위임 한 줄이다.
friend 쪽 검증 코드 0줄 원칙(MSG-187 D2, D3)이 그대로 유지된다.
