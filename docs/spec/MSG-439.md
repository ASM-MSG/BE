# MSG-439: 행사 조회 API (뷰포트 칩 목록 · 행사방 상세 · 위치 목록 · 격자 역조회)

**Owner**: B (제안). `com.msg.fillmap.event.*`는 신규 패키지라 CLAUDE.md 협업 원칙 목록에 아직
없다. 위치별 영상, 댓글, 알림으로 이어지는 콘텐츠 도메인이므로 Owner B로 판정하며, 목록 갱신
커밋은 스키마를 확정하는 MSG-438에 편승한다. grid 도메인 코드는 건드리지 않는다(격자 역조회는
URL만 `grids` 하위이고 구현은 event 패키지). **단 예외 1건**: regionName 조달을 위한
`GridQueryService` 계약 확장(§계약 변경)은 Owner A 코드 수정을 포함한다.

> 요구사항 정본: `docs/prd/event-room-location-videos.md` (확정, 2026-08-20 정민 승인) ·
> `docs/srs.md` FR-EVENT-01·02·07·08. 이 스펙은 그중 읽기 경로의 "어떻게"만 정한다.

## 개요

행사방의 읽기 경로 네 갈래를 만든다. 지도 홈 칩의 재료가 되는 뷰포트[^1] 기준 행사 목록,
행사방 진입 화면의 회차 상세 헤더, 회차의 위치 목록, 그리고 지도에서 누른 격자를 행사 위치로
해석하는 역조회다. 사용자가 `지역 → 행사 → 행사 위치` 순서로 내려가는 조회이며, 위치별 영상
피드 자체(MSG-440) 직전까지가 범위다.

## 배경 · 목표

영상은 행사 위치의 대표 격자[^2] 하나에만 저장되므로(FR-EVENT-08), 사용자가 행사 영역의 아무
격자나 눌렀을 때 그 위치의 피드로 들어가려면 격자를 위치로 해석하는 역조회가 유일한 진입
경로다. 또 지도 홈 칩은 "지도를 부산으로 옮기면 부산 행사가 뜨는" 뷰포트 연동이
요구사항이므로(FR-EVENT-01), 행사 목록도 기존 지도 조회 계약(bbox 파라미터)과 같은 형태로
만든다.

## 선행 의존: MSG-438이 스키마 정본

엔티티, 테이블, 컬럼의 확정 권한은 MSG-438(데이터 모델·시드·대표 격자)에 있다. 이 스펙은
PRD §3(데이터 관계)과 §8(필드 제안)의 이름을 그대로 쓴다: `EventSeries` · `EventOccurrence` ·
`EventLocation` · `EventLocationGrid` · `EventVideo`. **어긋나면 MSG-438 스펙을 따른다.**

PRD §8에 없지만 이 티켓의 조회가 요구하는 필드 2종은 438이 제공을 채택했다(아래 체크리스트):

- `EventOccurrence`의 **노출 영역**: 격자 정수 사각형 `min/max_grid_y/x` (zones 테이블 선례).
  뷰포트 겹침 판정의 재료다 (FR-EVENT-01 "행사마다 노출 영역").
- `EventOccurrence`의 **대상 지역 시 이름**(`cityName`, 예 "부산")과 **노출 시작
  시각**(`visibleFrom`): 시 칩 묶음 기준과 "시작 전 노출 기간 이내" 판정 재료.
  노출 정책은 **시작 2주 전**으로 확정됐다(2026-08-20 사용자). 시드 기본값
  `visibleFrom = startsAt - 14일`의 반영은 MSG-438(시드) 몫이고, 이 티켓의 노출·존재 은닉
  판정 로직은 `visibleFrom` 값 기준이라 정책값과 무관하게 불변이다.

이 티켓은 조회 전용이라 **Flyway 마이그레이션을 만들지 않는다** (V39는 438이 사용).

**구현 착수 전 하드 게이트**: 아래 각 항목의 판정은 **438 스펙 초안 기준이며, 438 엔티티
커밋 시 재대조한다.** 어긋나면 이 문서의 해당 절을 먼저 고친 뒤 개발한다.

- [x] 노출 영역(`min/max_grid_y/x`) · `cityName` · `visibleFrom` 제공: **채택** (438 회신 ①)
- [x] `EventVideo`의 삭제·노출 표현: **videos 1:1 확장 테이블**(처리 상태·공개범위·soft
      delete 재료는 `videos` 행에 있다). 노출 술어는 기존 전역 게이트(ACTIVE+PUBLIC+READY)와
      동일 (438 회신 ②, API 3 참조)
- [x] 한 격자의 회차 내 단일 위치 귀속: **UNIQUE(event_occurrence_id, grid_id) + 복합 FK**로
      보장 (438 회신 ③)
- [x] `EventLocation` 표시 순서 필드: **`display_order` 있음**, 위치 목록 정렬 1차 키로 사용
      (438 회신 ④, API 3 정렬 계약)
- [x] SRS FR-EVENT-02 문구 보정의 438 문서 커밋 편승: **확인** (438 회신 ⑤)
- [ ] 13xxx 대역 표 행(response-pattern.md)의 438 커밋 선점: 커밋 확인 대기

## 성공 기준

- 행사 영역의 서로 다른 두 격자를 역조회하면 같은 `eventLocationId`가 나온다 (PRD 테스트 4).
- 한 뷰포트에 여러 시, 시마다 여러 행사가 잡혀도 목록 하나로 성립하고, 겹치는 행사가 없으면
  실패가 아니라 빈 목록이다.
- 같은 시리즈의 새 회차를 만들어도 이전 회차의 위치·영상 수가 현재 회차 응답에 섞이지 않는다.
- 위치 목록의 영상 수는 별도 집계 테이블 없이 조회 시점 실측이다 (FR-EVENT-02).

아래 "테스트 시나리오"가 이 기준의 검증 수단이다.

## API 명세

네 API 모두 `GET`이다. **인증: 조회 4종 전부 비로그인 허용** (2026-08-20 사용자 확정,
"상단 칩은 비로그인, 업로드는 로그인". PRD §4.4의 익명 세션 heartbeat도 비로그인 행사방
열람을 전제한다, MSG-443). `SecurityConfig` 등록은 **`requestMatchers(HttpMethod.GET,
{정확한 네 경로 패턴})` 형태로 GET 한정**한다. 현행 SecurityConfig의 matcher는 메서드
무제한 문자열 패턴이라, 문자열만 추가하면 향후 같은 경로의 쓰기 API(440·441·442)까지
광역으로 풀리는 실수를 테스트가 못 잡는다. 이 global 설정 1곳 수정은 **이 티켓의 구현
범위다**. 로그인은 쓰기(업로드 MSG-440 · 댓글 MSG-441 · 알림 변경 MSG-442)부터 요구된다.
앱의 로그인 강제는 클라이언트 게이트라 서버 계약은 웹과 동일하다. 존재 은닉 규칙(아래)은
인증 여부와 무관하게 동일 적용된다.

컨트롤러는 `SuccessResponse.of(data)`만 반환하고 실패는 `ApiException(EventErrorCode)`
throw 하나로 처리한다(response-pattern.md 공통 규칙). 시각 필드는 전부 `LocalDateTime`
(UTC `Z` 코덱, MSG-376 체계)이고 D-day 계산은 FE 몫이다(재료는 `startsAt`).

**미노출 예정 회차의 존재 은닉(공통)**: 미노출 예정 회차(파생 status가 UPCOMING이면서
`visibleFrom > now`)는 네 API 모두에서 노출 전이다. 목록·역조회는 결과에서 제외하고,
id 직접 조회(API 2·3)는 **없는 회차와 동일하게 `13404 EVENT_NOT_FOUND`** 로 처리한다.
다른 코드를 쓰면 "있긴 있다"가 드러나 순차 occurrenceId 대입만으로 노출 전 행사명·일정·
위치·격자가 새기 때문이다.

**위치 표시명 재료(공통)**: 위치를 담는 응답(API 3·4)은 위치 단위로 **대표 격자 기준**
`zoneName` · `zoneCell` · `regionName`을 동봉한다 (2026-08-20 사용자 확정. 격자를 담는
조회 응답 9종 선례 MSG-341·349의 필드명 그대로, 조립 규칙도 동일:
`zoneName ? zoneName+" "+zoneCell : regionName`, 무귀속이면 null). `gridIds` 배열의 격자
각각에는 동봉하지 않는다. 영역 채색에는 불필요하고 응답만 비대해지기 때문이다. 구현
재료는 §계약 변경 참조.

### 1. 뷰포트 행사 목록: `GET /api/event-occurrences`

지도 홈 칩 재료. 쿼리 파라미터는 기존 뷰포트 조회 3종(grid·hotzone·mission)과 동일하게
`swLat` `swLng` `neLat` `neLng`이며, `required = false`로 받아 컨트롤러 `toBounds()`에서
직접 검증한다. 스프링의 필수 파라미터 예외는 도메인 developCode[^3]를 못 싣기 때문이다
(`MissionController.toBounds` 동일 패턴, `ViewportBounds` 레코드 재사용).

- 담기는 회차: 상태가 예정(단 `visibleFrom <= now`)이거나 진행 중이고, 노출 영역 사각형이
  뷰포트와 겹치는 것. 업로드 유예·아카이브 회차는 칩에 안 담긴다(상세·역조회로만 접근).
- 겹침 판정: `GridEncoder.viewportRange(bounds)`로 뷰포트를 격자 인덱스 사각형으로 바꾼다.
  꼭짓점 네 점을 전부 EPSG:5179[^4]로 투영해 min/max를 잡는 방식이며, 남서·북동 2점만
  쓰면 중앙자오선(경도 127.5도)을 품는 뷰포트에서 남쪽 한 행이 빠진다(실측 최대 이탈
  29.6m). 여기에 mission과 동일하게 **사방 1칸 보정**(`PROJECTION_PAD_CELLS = 1` 선례,
  `MissionQueryServiceImpl` MSG-398 D3 주석 참조)을 더한 사각형과 노출 영역을 정수
  부등식으로 겹침 판정한다.
- 검증: 뒤집힌 bbox와 WGS84 정의역 밖은 `13400 INVALID_VIEWPORT`, 변당 0.5도 초과는
  `13401 VIEWPORT_TOO_LARGE` (mission의 상한·판정과 동일, 정확히 0.5도는 허용).
  검증 순서(좌표 유효성 → 뒤집힘 → 크기)와 상수를 mission과 동일하게 유지한다.
  이 검증은 이제 세 번째 소비자라 공통 validator 승격 후보지만 **의도적으로 유예한다**:
  2026-09-07 멘토 라이브 코드 리뷰 전 구조 변경 금지 합의 때문이며, 동일 순서·동일 상수
  유지가 유예의 조건이다.
- 행사 행은 도시별 한두 개 수동 시드뿐이므로(FR-EVENT-01) 노출 후보 전량을 조회해
  자바에서 거른다. 인덱스나 공간 쿼리를 만들지 않는다.
- 정렬: `cityName` 오름차순 → `startsAt` 오름차순 → `occurrenceId` 오름차순(타이브레이커,
  SPOT_ORDER 선례의 결정적 정렬). FE가 시 칩 뒤에 그 시의 행사 칩을 나열하는 그룹핑의
  안정 재료다.

응답 `data`: `EventOccurrenceChipResponseDto` 배열

| 필드 | 타입 | 설명 |
|---|---|---|
| `occurrenceId` | Long | 행사 회차 id |
| `title` | String | 행사명 (칩 라벨 재료) |
| `cityName` | String | 대상 지역 시 이름 ("부산"), 시 칩 묶음 기준 |
| `startsAt` / `endsAt` | LocalDateTime | 기간. D-day는 FE가 `startsAt`으로 KST 계산 |
| `status` | String | `UPCOMING` 또는 `LIVE` (이 목록엔 두 값만 가능) |

### 2. 행사 회차 상세: `GET /api/event-occurrences/{occurrenceId}`

행사방 헤더. 없는 id는 `13404 EVENT_NOT_FOUND` (404). **미노출 예정 회차도 동일하게
13404다**(공통 존재 은닉 규칙, API 명세 서두 참조). 행사 이미지는 이번 범위에 없다
(2026-08-20 사용자 확정. 스키마 필드도 응답 필드도 없고, 헤더는 이미지 없이 렌더).

응답 `data`: `EventOccurrenceDetailResponseDto`

| 필드 | 타입 | 설명 |
|---|---|---|
| `occurrenceId` | Long | |
| `seriesId` | Long | 시리즈 식별 (이전 회차 묶음 기준) |
| `title` | String | |
| `startsAt` / `endsAt` | LocalDateTime | |
| `uploadClosesAt` | LocalDateTime | `endsAt + 30일` 파생값 (저장 컬럼 아님, 438 정의) |
| `status` | String | `UPCOMING / LIVE / UPLOAD_GRACE / ARCHIVED` |
| `notificationOn` | Boolean | 알림 구독 여부 (읽기만, 아래 참고) |
| `previousOccurrences` | 배열 | 같은 시리즈의 지난 회차 (`occurrenceId`·`title`·`startsAt`·`endsAt`) |

- `status`는 **주입받은 `Clock`의 서버 시각으로 파생 계산**한다 (FR-22 "서버 시각 판정"의
  이행). 저장 status 컬럼은 없고 **`statusAt(now)` 파생만 존재한다**(438 엔티티 정의
  정본, 초안 기준). 경계는 전부 **반개구간**이다: `now < startsAt` = UPCOMING,
  `startsAt <= now < endsAt` = LIVE, `endsAt <= now < uploadClosesAt` = UPLOAD_GRACE,
  `uploadClosesAt <= now` = ARCHIVED. `now == endsAt` 정각이 LIVE면 PRD §4.2 "종료 시
  즉시 차단"과 어긋나므로 정각은 다음 상태에 속한다.
- `previousOccurrences`의 술어: `같은 seriesId AND startsAt < 조회 회차의 startsAt`.
  여기에도 공통 노출 판정을 적용해 미노출 회차는 제외한다(술어상 startsAt이 과거인
  회차만 담겨 실제로 걸릴 일은 없지만, 판정을 명시해 일관성을 확보한다).
  정렬은 `startsAt` 내림차순 → `occurrenceId` 내림차순(타이브레이커). 미래 회차(예정
  재개최)는 "지난 회차"가 아니므로 담기지 않는다. 상세에 동봉하고 별도 API를 만들지
  않는다. 회차 수는 시리즈당 몇 개 수준이라 페이지네이션이 필요 없고, 이전 회차의
  위치·영상은 그 회차 id로 이 스펙의 API 3(영상은 MSG-440)을 다시 부르면 되므로 회차 간
  데이터가 섞일 경로 자체가 없다.
- `notificationOn`: 이 티켓이 확정하는 것은 **응답 필드 계약**과 principal 전달
  시그니처다. principal은 인증돼 있으면 사용자 id를 서비스에 전달하고 비로그인이면
  null이다(조회 4종 비로그인 허용에 따른 조정). **비로그인 요청은 `false` 고정**이고,
  로그인 사용자도 구독 저장소(MSG-442)가 생기기 전까지는 `false` 고정이다. 구독 조회
  호출 연결은 442 몫이다.
- 열람 인원(viewer-count)은 MSG-443이라 이 응답에 싣지 않는다.

### 3. 위치 목록: `GET /api/event-occurrences/{occurrenceId}/locations`

없는 회차 id는 `13404 EVENT_NOT_FOUND`. **미노출 예정 회차도 동일하게 13404다**(공통 존재
은닉 규칙, 위치·격자 영역은 API 2보다 더 구체적인 노출 전 정보다). 위치가 없으면 빈 배열.

응답 `data`: `EventLocationResponseDto` 배열

| 필드 | 타입 | 설명 |
|---|---|---|
| `locationId` | Long | |
| `name` | String | "부산역 팝업" |
| `type` | String | 위치 유형 (enum 값은 438 정본) |
| `operatingHours` | String | 운영 시간 표시 문자열 |
| `gridIds` | List\<String\> | 영역을 구성하는 격자 전체 (`"{gridY}_{gridX}"` 포맷), FE 영역 채색 재료 |
| `representativeGridId` | String | 대표 격자 |
| `zoneName` / `zoneCell` / `regionName` | String | 대표 격자 기준 표시명 재료 (공통 규칙 참조, 무귀속 null) |
| `videoCount` | Long | 이 위치의 영상 수 (조회 시점 실측) |

- 정렬 계약: `display_order` 오름차순 → `locationId` 오름차순(동률 타이브레이커).
  438 확정(초안)으로 `display_order`가 있어 1차 키로 쓴다(엔티티 커밋 시 재대조).
  결정적 정렬이다(SPOT_ORDER 선례).
- `videoCount` 쿼리 계약: `EventVideo`는 `videos`의 1:1 확장 테이블(438 회신 ②)이라 노출
  술어 재료가 `videos` 행에 있다. 회차의 위치 id 집합을 먼저 얻은 뒤
  `SELECT ev.event_location_id, COUNT(*) FROM event_videos ev JOIN videos v ON v.id =
  ev.video_id WHERE ev.event_location_id IN (:locationIds) AND {전역 노출 게이트} GROUP BY
  ev.event_location_id` **한 번**으로 전 위치 분을 얻고, 집계에 없는 위치는 0으로
  조립한다. 위치 루프 안 개별 count는 금지다(N+1[^5] 예방).
- `videoCount`의 후보 집합은 **MSG-440 피드의 노출 술어와 동등해야 한다(정의 하나를
  공유)**. 노출 술어는 **기존 전역 게이트(ACTIVE+PUBLIC+READY)와 동일로 확정**됐다
  (PRD §10 공통 영상 정책 재사용 + 438 회신 ②). 삭제·비공개·블라인드·처리 미완료 영상이
  카운트에는 잡히고 피드에는 안 나오면 숫자 불일치에 존재 노출까지 되므로, 술어 정의는
  한 곳에 두고 이 카운트와 440 피드가 같이 소비한다.
- 조회 키가 회차의 위치 id 집합이므로 다른 회차의 영상이 세어질 수 없다 (FR-EVENT-07).
  영상의 회차 id와 위치의 회차 id가 일치한다는 무결성 자체는 438 DDL과 440 쓰기 경로의
  소유이며, 일치가 깨진 데이터의 방어는 이 조회의 범위 밖이다.

### 4. 격자 역조회: `GET /api/grids/{gridId}/event-locations`

선택한 격자가 속한 행사 위치를 해석한다. 영상은 대표 격자에만 저장되므로 이 역조회가 위치별
피드 진입의 유일 경로다 (FR-EVENT-08). URL은 `grids` 하위지만 컨트롤러는 event 패키지의
`EventLocationController`에 둔다. grid 도메인 코드는 불변이다(단 §계약 변경의
`GridQueryService` 확장 1건은 예외).

- `EventLocationGrid`에서 `gridId` 일치 행을 찾아, 연결된 위치와 그 회차를 함께 돌려준다.
  한 격자가 여러 회차의 위치에 속할 수 있으므로(같은 장소 재개최) 배열이다.
- 노출 조건: **미노출 예정 회차는 응답에서 아예 제외한다**(배열에도 담지 않는다. 판정은
  공통 존재 은닉 규칙과 동일: UPCOMING이면서 `visibleFrom > now`). 노출 전 회차는 존재
  자체가 비공개 정보라 역조회로 새면 안 된다. 유예·아카이브 회차는 칩과 달리 역조회에는
  담긴다(지난 기록 접근 경로).
- 정렬은 서버 계약이다: **첫 항목이 진입 기본값**(FR-EVENT-07 "기본 화면은 현재 회차")이
  되도록 파생 status 우선순위 `LIVE > UPCOMING > UPLOAD_GRACE > ARCHIVED` 먼저다.
  동순위 보조 정렬은 상태별로 방향이 다르다: UPCOMING끼리는 `startsAt` 오름차순(가장
  임박한 회차가 "다음 행사"), LIVE·UPLOAD_GRACE·ARCHIVED끼리는 `startsAt` 내림차순
  (지난 것은 최근 기록이 우선). 이어서 `occurrenceId` 내림차순 → `locationId`
  오름차순. `locationId`는 최종 타이브레이커로, 같은 회차의 두 위치가 한 격자에 연결되는
  비정상 데이터에서도 정렬이 결정적이게 한다(정상 데이터에선 회차당 한 위치라 도달하지
  않는 키. 438 회신 ③의 UNIQUE 제약이 정상 데이터를 보장한다).
- 우선순위 근거 두 가지. `startsAt` 내림차순만으로는 미래 재개최 회차(UPCOMING)가 진행 중
  회차를 앞질러 기본 화면 요구와 충돌한다. 그리고 UPCOMING을 UPLOAD_GRACE보다 앞에 둔
  것은 이전 회차 유예 중 + 새 회차 예정(노출 중) 공존 시 새 회차가 "현재"이기 때문이다
  (PRD US-010: 기본 화면은 현재 회차, 지난 회차는 "지난 행사 영상"에서 명시적 선택).
  유예 회차는 배열 후순위와 `previousOccurrences`로 여전히 접근할 수 있다. 이 우선순위는
  사용자 결정으로 뒤집을 수 있는 지점이라 근거를 남긴다.
- 어떤 위치에도 속하지 않는 격자, 그리고 격자 포맷이 아닌 임의 문자열도 **빈 배열**이다.
  일치 조회라 포맷 검증이 판정을 바꾸지 못하므로 검증 코드를 두지 않는다.

응답 `data`: `GridEventLocationResponseDto` 배열

| 필드 | 타입 | 설명 |
|---|---|---|
| `occurrenceId` | Long | 소속 회차 |
| `occurrenceTitle` | String | 행사명 |
| `occurrenceStatus` | String | 파생 status (API 2와 같은 계산) |
| `locationId` | Long | 해석된 위치, 피드 진입 키 |
| `locationName` | String | |
| `representativeGridId` | String | 피드(MSG-440)가 영상을 붙일 격자 |
| `zoneName` / `zoneCell` / `regionName` | String | 대표 격자 기준 표시명 재료 (공통 규칙 참조, 무귀속 null) |

### 에러 코드: `EventErrorCode` (13xxx)

event 도메인은 `13xxx` 대역을 쓴다. **대역 표(response-pattern.md) 갱신 커밋은 MSG-438
몫이다**(438 세션이 선점 커밋 예정). 이 티켓은 표를 수정하지 않고 값만 그 대역에서 쓴다.

| developCode | 상수 | HTTP | 메시지 |
|---|---|---|---|
| 13400 | `INVALID_VIEWPORT` | 400 | 유효하지 않은 지도 범위입니다 |
| 13401 | `VIEWPORT_TOO_LARGE` | 400 | 조회 범위가 너무 넓습니다 |
| 13404 | `EVENT_NOT_FOUND` | 404 | 행사를 찾을 수 없습니다 |

PRD §7의 `EVENT_LOCATION_NOT_FOUND` 등 나머지 코드는 그 코드를 실제로 던지는 티켓
(MSG-440 이후)이 추가한다. 이 티켓의 API에는 `locationId` 경로 파라미터가 없다.

## 조회 구현 방식

영속 계층 컨벤션의 2026-08-19 개정(연관관계 허용, 메인 체크아웃 기준. 이 워크트리의
project-conventions.md 사본은 개정 전이라 참조하지 않는다)을 따른다: **파생 쿼리와
JPQL(fetch join·생성자 프로젝션) 우선, native 불요**. 이 티켓의 조회에는 PostgreSQL 전용
기능이 없다(videoCount의 join + group by count도 JPQL 생성자 프로젝션으로 충분). 신규
엔티티의 연관관계 설계 자체는 438 몫이고, 이 티켓은 438이 만든 매핑을 소비만 한다.

## 도메인 로직

- **행사 회차**(EventOccurrence)가 조회의 중심이다. 시리즈는 이전 회차 묶음 기준으로만
  쓰이고 직접 조회 API가 없다.
- **격자**는 glossary의 논리 식별자(`"{gridY}_{gridX}"`, EPSG:5179 계산 규칙)를 그대로 쓴다.
  event 도메인은 `grids` 테이블 존재 여부와 무관하다. 소속 판정은 `EventLocationGrid`
  일치 조회뿐이고, 뷰포트 판정은 `GridEncoder` 산술 소비뿐이다.
- **상태는 파생값**: 조회 3곳(목록·상세·역조회)이 `EventOccurrence.statusAt(LocalDateTime
  now)` 하나를 공유한다. 저장 status 컬럼은 없다(438 엔티티 정의 정본). 경계 반개구간
  정의는 API 2 참조.
- **미노출 예정 회차의 존재 은닉**도 네 API가 판정 하나를 공유한다(API 명세 서두).

## 계약 변경

**계약 변경 1건 있음** (상대 팀 확인 필수 지점).

1. **`GridQueryService` 확장 (Owner A 계약, 변경)**: 위치 표시명의 `regionName` 조달을
   위해 벌크 조회 메서드를 추가한다. 시그니처 제안: `Map<String, String>
   findRegionNames(Collection<String> gridIds)` 류(확정 표기는 구현 시).
   **계약 성질: `grids` 행 존재와 무관하게 격자 중심점 기준 행정동 판정을 보장한다.**
   `grids`는 lazy insert(누군가 업로드한 격자만 행 존재)라 행사 대표 격자에 행이 없을 수
   있는데, 저장 라벨(`GridRepository.findRegionNames`, MSG-349)에만 의존하면 실제 행정동
   안 격자도 null이 돼 표시명 계약("행정동도 없는 진짜 무귀속만 null", glossary 정본)을
   위반한다. 구현 선택은 Owner A 몫이다: 행이 있으면 저장 라벨 + 없으면 중심점 재판정,
   또는 전량 중심점 판정(단건 선례는 `GridQueryServiceImpl.getCell`의 중심점 판정).
   **Owner A 인터페이스·구현체·계약 테스트 수정이 이 티켓 범위에 포함되며, 계약 테스트에
   "grids 행이 없는 내륙 대표 격자도 regionName이 나온다"를 포함한다.** 이 확장이
   Owner·API 4 절의 "grid 도메인 코드 불변" 선언의 유일한 예외다.
2. **기존 인터페이스 소비 추가 (시그니처 변경 없음)**: `ZoneNameQueryService`(MSG-341,
   Owner A)를 event 도메인이 새로 소비한다. 실측 시그니처: `ZoneNameResolver resolver()`를
   요청당 1회 불러 불변 리졸버를 얻고, 대표 격자마다 `resolver.name(gridY, gridX)`로
   `ZoneCellName`을 얻는다(무매칭이면 `ZoneCellName.NONE`, null 아님. DTO 조립에서 null
   필드로 변환).

그 외 `HotZoneService` · `UserGridQueryService` · `UserOidcCommandService`의 시그니처는
바뀌지 않는다. 신규 서비스 인터페이스(`EventQueryService` 제안)는 event 도메인 내부용이고
타 도메인이 소비하지 않는다.

## 작업 로그

### 2026-08-21 — 구현 완료 (조회 4종 + 계약 메서드)

- **완료 모듈**: M1 `GridQueryService.resolveRegionNames` 벌크 계약(Owner A, grid-dev) → M2 서비스 계층(EventErrorCode·리포지토리 조회·EventQueryService, Owner B, auth-dev) → M3 컨트롤러 계층(DTO 4종·컨트롤러 2종·SecurityConfig permitAll·통합 테스트). 신규 테스트 53건(서비스 36·컨트롤러 10·공개 정책 4·grid 계약 3), 전체 스위트 2,039건 green.
- **구현 결정**: ① 계약 메서드명을 `findRegionNames`가 아니라 `resolveRegionNames`로 — 기존 `GridRepository.findRegionNames`는 grids INNER JOIN이라 행 없는 격자가 누락돼 표시명 재료로 부적합(중심점 재판정 성질을 이름에 노출, javadoc에 분리 사유). ② 무귀속 격자는 맵에서 키 부재(null 값 없음) — 조립부 `getOrDefault`/`get` null 그대로 DTO. ③ 역조회 리포지토리는 `EventLocationGrid`가 아니라 `EventLocation` 반환 — `EventLocationGrid.location`이 `insertable=false` 읽기 전용 매핑이라 같은 트랜잭션 생성 인스턴스에서 null(테스트 실측 NPE)이던 함정 제거. ④ 역조회는 일치 조회 우선 → 0행이면 표시명 판정 전 빈 배열 — 원시 경로 파라미터가 `GridEncoder.decode`에 도달하지 않아 불량 문자열 500 경로 차단.
- **리뷰 이력**: convention-reviewer 3회 전부 통과(위반 0 — R1에서 기존 findRegionNames 위임 함정·이기대 시드 무귀속을 사전 적발해 회피). Codex 교차 리뷰(sol+medium) 1라운드 수렴 — 신규 지적 0. 실서버 스모크(합성 4상태 회차) — 칩·상세·위치·역조회·존재 은닉·인증 경계 전 구간 실측 통과.
- **수용 잔여(주의)**: ① 칩 경로만 노출 판정을 `findByVisibleFromLessThanEqual` SQL로 별도 표현 — 나머지 3 API의 `isVisible` 자바 판정과 결과 동치는 `visible_from = starts_at - 14일` DDL CHECK에서 추론된다. 노출 정책에 조건이 추가되면 칩 쿼리도 같이 고쳐야 한다. ② "요청당 1회 쿼리" 성질은 구조로 보장되고 테스트로는 단언되지 않는다(쿼리 카운팅 선례 없음 — 인프라 신설 기각).
- **데이터 저장 위치**: 없음(조회 전용, Flyway 없음). 읽는 테이블 = `event_series`·`event_occurrences`·`event_locations`·`event_location_grids`·`event_videos`(count)·`videos`(노출 게이트)·`regions`(중심점 판정)·`zones`(표시명).
- **실행 쿼리(실측, 스모크 서버 Hibernate 로그)**:
  - 칩 후보: `select ... from event_occurrences eo1_0 where eo1_0.visible_from<=?` → 자바에서 statusAt·뷰포트 겹침 필터.
  - 위치 목록: `select ... from event_locations el1_0 where el1_0.event_occurrence_id=? order by el1_0.display_order, el1_0.id`.
  - 영역 격자 벌크: `select ... from event_location_grids elg1_0 where elg1_0.event_location_id in (?, ?) order by elg1_0.grid_id`.
  - 영상 수: `select ev1_0.event_location_id, count(ev1_0.video_id) from event_videos ev1_0 join videos v1_0 on v1_0.id=ev1_0.video_id where ev1_0.event_location_id in (?, ?) and v1_0.status='ACTIVE' and v1_0.visibility='PUBLIC' and v1_0.processing_status='READY' group by ev1_0.event_location_id`.
  - 역조회: `event_location_grids` → `event_locations` → `event_occurrences` fetch join 한 방(원문은 로그 참조), 격자당 표시명은 `resolveByPoint`(ST_Covers) 대표 격자 1회.
- **예외 흐름**: 뷰포트 위반은 컨트롤러 `toBounds()`에서 `ApiException(INVALID_VIEWPORT 13400 / VIEWPORT_TOO_LARGE 13401)` → `GlobalExceptionHandler`가 400 변환. 없는 회차·미노출 회차는 서비스에서 `ApiException(EVENT_NOT_FOUND 13404)` → 404(존재 은닉 — 두 경우 응답 구분 불가). 공개 GET에 무효 Bearer는 핸들러 밖 `JwtAuthenticationFilter`가 2401 401로 응답(무토큰 익명 200과 별개 — 선택적 인증).
- **빈 동작**: `EventQueryServiceImpl`은 `@Transactional(readOnly = true)` 단일 트랜잭션, 프로덕션 생성자 `Clock.systemUTC()` 주입(스케줄러·자체 스레드 없음). `SecurityConfig`는 GET 4패턴만 permitAll — 나머지 경로 인증 불변.
- **커밋 제안**: ① `MSG-439 feat: grids 행 없는 격자도 행정동 이름을 얻는 벌크 조회 추가`(M1 3파일) ② `MSG-439 feat: 행사 조회 서비스와 에러 코드 추가`(M2) ③ `MSG-439 feat: 행사 조회 API를 비로그인 GET으로 공개`(M3) ④ `MSG-439 docs: 요구 상태 승격과 작업 로그, 구현 현황 반영`(SRS·rtm·changelog·status.md·spec·FR 주석).
