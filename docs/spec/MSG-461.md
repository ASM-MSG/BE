# MSG-461: 전체 지역 목록의 전국 집계 비용을 조인 순서로 낮춘다

**Owner**: B (`com.msg.fillmap.video.*` 내부 native 쿼리 수정, Owner A 접점 없음)

> 요구사항 정본: `docs/prd/MSG-460-prd.md` §4 비기능 요구사항 "성능" 행, **2026-08-25 정정본**
> (상태: 검토됨, 정정과 성능 목표 모두 정민 승인). 이 행이 MSG-461을 지목해 범위를 담고 있고,
> MSG-461 전용 PRD는 없다. 커서 구조와 정렬 규칙, 응답 계약은 `docs/spec/MSG-460.md`를
> **그대로 재사용**한다.
>
> 이 스펙은 PRD 면제로 서 있지 않다. 아래 성공 기준의 **500 ms 미만이라는 성능 목표는 이 티켓이
> 스스로 만든 값이 아니라 PRD 정정본이 승인한 요구사항**이다. CLAUDE.md가 "성능 목표 자체를 새로
> 세우면 요구사항 신설"로 규정하므로 목표를 PRD에 올려 승인받은 뒤 스펙이 그것을 참조한다.
> 승격 조건(격자 50만 초과 또는 p95 1초 초과 시 머티리얼라이즈드 뷰)도 PRD 정정본에 함께 실려 있다.

## 개요

검색 화면의 `전체 지역` 목록(`GET /api/regions/explore`)이 페이지를 넘길 때마다 약 3.7초 걸린다.
MSG-460이 커서 페이지로 응답 크기는 20개로 묶었지만 집계 비용은 그대로 남았고, PRD §4가 그 미충족을
명시적으로 기록하며 이 티켓으로 분리했다.

이번 수정은 쿼리 하나의 **조인 순서와 그룹 키만** 바꾼다. 정렬 규칙, 화면, 응답 계약
(`items`/`hasNext`/`nextCursor`), 메서드 시그니처, 프로젝션 인터페이스, DB 스키마 어느 것도
바뀌지 않는다. 새 인덱스도 마이그레이션도 새 빈도 없다.

## 배경 · 목표

검색창을 누르면 처음 뜨는 기본 목록이 3.7초 걸리는 상태로 배포됐다(2026-08-22 정민 판단, 다음
스프린트 해소를 조건으로 함). 사용자가 검색을 시작하기도 전에 기다리는 구간이라 체감 비용이 크다.

목표는 PRD §4가 요구한 "한 번 조회 비용을 고정한다", 다시 말해 **페이지 깊이에 따라 비용이 늘지
않고 절대 시간도 사람이 기다린다고 느끼지 않는 수준으로 내려오는 것**이다.

## 성공 기준

1. dev 실데이터에서 첫 페이지와 깊은 페이지 모두 `EXPLAIN (ANALYZE)` 실행 시간이 500 ms 미만이고,
   두 구간의 차이가 유의하지 않다(깊이에 비례하지 않는다). **PRD 정정본이 승인한 목표값이다.**
2. 실행 계획에서 `Memoize`[^1] 노드가 사라지고 정렬이 디스크로 새지 않는다
   (`Sort Method: external merge`[^2]가 `quicksort Memory`로 바뀐다).
3. 결과 집합이 수정 전과 완전히 같다. 기존 통합 테스트
   `src/test/java/com/msg/fillmap/video/repository/RegionExploreQueryTest.java`의 **기존 케이스는
   한 건도 고치지 않고 전부 통과**하고, 같은 파일에 **경계 케이스 1건을 새로 추가한다**
   (`region_code`가 NULL인 격자, 아래 테스트 시나리오 5번). 기존 케이스 무수정과 신규 1건 추가는
   서로 모순되지 않는다. 앞은 결과 집합이 안 바뀌었다는 회귀 확인이고, 뒤는 이번 변경이 새로
   건드린 조인 위치를 겨냥한 경계 확인이다.
4. 메서드 시그니처, 파라미터, `RegionExplorePageProjection`, 컨트롤러, DTO, `RegionExploreCursor`가
   한 줄도 바뀌지 않는다.
5. Flyway 마이그레이션, 새 인덱스, 새 빈이 추가되지 않는다.

다섯 항목 모두 충족했다. 실측값은 아래 작업 로그에 있다.

## 도메인 로직

### 진짜 원인

티켓은 원인을 "요청마다 전국을 다시 센다"로 보고 미리 계산(카운트 칼럼, 머티리얼라이즈드 뷰)을
제안했는데, **dev 실측에서 그 진단이 부분적으로 틀린 것이 확인됐다.** 전국 격자 144,542개를 훑어
세는 것 자체는 비싸지 않다. 비싼 것은 그 옆에 붙은 두 가지다.

첫째, `regions` 조인이 집계보다 앞에 있다. 현재 CTE[^3]가
`FROM grids g JOIN regions r ON r.region_code = g.region_code ... GROUP BY g.region_code, r.region_name`
이라 행정동 이름을 얻는 조회가 격자 수만큼 돈다. 실행 계획에 `Memoize (loops=144536)`와
`Index Scan using regions_pkey (loops=3963)`이 찍힌다.

둘째, `GROUP BY (region_code, region_name)`으로 그룹 키가 넓다. 144,542행을 varchar 두 개로
정렬하느라 작업 메모리를 넘겨 디스크로 샜다(`Sort Method: external merge  Disk: 2312kB`).

분해 실측(dev, 2026-08-25)이 이 판단의 근거다.

| 측정 | Execution Time |
|---|---|
| `regions` 조인 없이 `GROUP BY region_code`만, EXISTS 게이트 없음 | 25 ms |
| `regions` 조인 없이 `GROUP BY region_code` + EXISTS[^4] 게이트 | 257 ms |
| 현행 쿼리(조인 먼저 + 넓은 그룹 키) | 6,810 ms |

6.8초 중 실제로 세는 데 쓴 시간은 257 ms이고, 나머지 6.5초가 조인과 디스크 정렬이다.

### 해결

`content_regions` CTE를 `region_code`로만 묶어 1,339행을 먼저 만들고, `regions` 조인을 **그 뒤에**
둔다. 조인 대상이 144,536행에서 1,339행으로 줄고 그룹 키가 좁아져 정렬이 메모리에서 끝난다
(`quicksort Memory: 110kB`, `Memoize` 노드 소멸).

```sql
WITH content_regions AS (
    SELECT g.region_code, COUNT(*)::int AS grid_count
    FROM grids g
    WHERE g.region_code IS NOT NULL
      AND EXISTS (SELECT 1 FROM videos v WHERE v.grid_id = g.grid_id
        AND v.status='ACTIVE' AND v.visibility='PUBLIC' AND v.processing_status='READY')
    GROUP BY g.region_code
), personal_regions AS ( ... 현행 그대로 ... )
SELECT c.region_code AS "regionCode", r.region_name AS "regionName",
       c.grid_count AS "gridCount", p.last_uploaded_at AS "personalLastUploadedAt"
FROM content_regions c
JOIN regions r ON r.region_code = c.region_code
LEFT JOIN personal_regions p ON p.region_code = c.region_code
WHERE ... 현행 커서 술어 그대로 ...
ORDER BY ... 현행 정렬 그대로 ...
LIMIT CAST(:limit AS bigint)
```

CTE의 `region_code IS NOT NULL`은 Codex 교차 리뷰 4라운드에서 보강한 것이다. 바깥 INNER 조인이
어차피 버릴 무라벨 격자(해안 등)를 세기 전에 걷어낸다. 없으면 NULL 한 무더기를 만들어 놓고
바깥에서 버린다. dev 실측 무라벨 7,470개(전체 144,542의 5.2%)로, CTE만 떼어 재면 343ms가 257ms가
되지만 전체 쿼리는 266ms로 붙이기 전(267ms)과 오차 범위다. 버릴 것을 안 세는 게 옳아서 넣은
것이지 응답이 빨라져서가 아니며, 결과 집합은 어느 쪽이든 같다.

건드리지 않는 것을 못박아 둔다. `personal_regions` CTE는 현행 그대로이고, 커서 술어
(`hasCursor`/`cursorPersonal` 분기 전부), `ORDER BY` 네 단계, `LIMIT` 표현식도 현행 그대로다.
바뀌는 것은 `content_regions`의 SELECT 목록과 WHERE와 GROUP BY, 그리고 `regions` 조인의 위치뿐이다.

### 결과 집합이 같은 이유

`JOIN regions`(INNER)는 현행과 같은 의미를 유지한다. 현행도 INNER 조인이라 `regions`에 없는
`region_code`를 가진 격자는 지금도 목록에서 빠진다. 조인을 뒤로 미뤄도 걸러지는 집합이 같다.
차이는 걸러내는 시점뿐이고, `grid_count`는 조인 전 격자 수를 세므로 조인 위치에 영향받지 않는다.

전역 노출 게이트(ACTIVE, PUBLIC, READY)와 `gridCount` 정의는 MSG-238부터 이어진 기준 그대로다.
glossary의 격자와 점령 정의도 그대로다. 이 티켓은 어떤 격자를 세는지에 손대지 않는다.

## 실측 결과

dev, 2026-08-25, 각 2회 반복.

| 구간 | 현행 | 수정 후 |
|---|---|---|
| 첫 페이지 (`hasCursor=false`) | 6,810 ms | 272 ms, 315 ms |
| 깊은 페이지 (비개인 커서) | 3,675 ms (티켓 2026-08-22 측정) | 277 ms, 345 ms |

첫 페이지와 깊은 페이지가 비슷한 것이 정상이자 요구 충족이다. PRD가 요구한 것은 "페이지 깊이에
따라 비용이 늘지 않는다"이고, 깊이와 무관하게 272~345 ms로 평탄하다.

재현 환경은 `ssh fillmap` 뒤 `docker exec -i fillmap-postgres-dev psql -U dev -d fillmap`이고
`EXPLAIN (ANALYZE, BUFFERS)`로 쟀다. 측정 사용자는 `user_id=499`(개인 지역 337개, `user_grids`
512행)다. 데이터 규모는 격자 144,542개, 영상 240,198건(공개이면서 READY이고 ACTIVE인 것 240,184건),
`regions` 3,558행, 콘텐츠 있는 행정동 1,339개다. prod 컨테이너는 건드리지 않았다.

## 기각한 대안

티켓이 제안했던 방향이 여기 들어 있으므로 왜 채택하지 않았는지를 근거와 함께 남긴다.

**1. 머티리얼라이즈드 뷰[^5] + 주기 갱신.** dev 실측으로 첫 페이지 237 ms, 깊은 페이지 6 ms,
`REFRESH ... CONCURRENTLY` 3.76초였다. 깊은 페이지는 훨씬 빠르지만 첫 페이지는 272 ms와 사실상
동률이다. 첫 페이지의 남은 비용은 집계가 아니라 개인 구간 `user_grids` 조회이기 때문이다.
마이그레이션, 스케줄러, 다중 인스턴스 갱신 경합이 새로 붙고 값이 갱신 주기만큼 낡는 대가를
치르는데 얻는 것이 첫 페이지 35 ms라 지금은 수지가 맞지 않는다.

**2. `regions`에 카운트 칼럼을 두고 업로드와 삭제 때 증감.** 낡음은 없지만 격자가 공개 영상
0에서 1로, 1에서 0으로 넘어가는 순간만 증감해야 해서 업로드, 삭제, 블라인드, 공개범위 변경,
인코딩 상태 전이라는 다섯 경로에 유지 로직이 붙는다. 얻는 성능이 1번보다 크지 않은데 쓰기 경로
결함 위험은 가장 크다.

**3. 정렬 규칙을 인덱스 탈 수 있는 키로 변경**(꼬리 구간을 `region_code ASC`로). 스트레스 실측
결과 **단독 기각**으로 판정이 굳었다. 절차상 이유(정렬 규칙 변경은 티켓의 제외 범위이자 PRD §4가
확정한 규칙이라 제품 결정이 필요하다)보다 기술적 이유가 더 결정적이다.

첫째, `gridCount`는 정렬에서 빠져도 **응답에는 남는다.** 21개 행마다 그 행정동의 격자를 세야
하는데 행정동 크기가 제각각이라 페이지마다 비용이 튄다. 작은 동 21개짜리 페이지는 14 ms인데
격자 834개짜리 큰 읍이나 면 21개짜리 페이지는 약 390 ms다
(`Nested Loop Semi Join rows=834 loops=21`). 지역 코드순이면 같은 군의 큰 읍과 면이 붙어 나오므로
이런 페이지가 실제로 생긴다. 확정안은 어떤 페이지든 272 ms로 평탄하다.

둘째, 콘텐츠 없는 행정동을 건너뛰느라 **비용이 페이지 깊이에 비례해 는다.** 첫 페이지 14 ms,
중간 63 ms, 끝자락 98 ms다. 콘텐츠 분포가 불균등해서 그렇다(충남은 208개 중 0개, 경남은 305개 중
2개, 세종은 24개 중 0개 행정동에만 콘텐츠가 있다).

그래서 PRD의 "깊이 무관" 요구를 확정안은 만족하고 이 대안은 만족하지 못한다. 절대값은 작지만
성질이 반대다. 이 대안은 단독으로 완결되지 않고 미리 계산(기각 대안 1번)과 묶이거나 페이징 제거에
흡수되어야 한다. 파생 티켓 **MSG-479**로 분리했다.

**4. 영상 쪽 부분 인덱스(`idx_videos_grid_popular`)로 집계 방향 뒤집기.**
`SELECT DISTINCT grid_id FROM videos ...`를 먼저 만들어 격자에 조인하는 방향이다. 6,810 ms에서
6,123 ms로 사실상 효과가 없었다. 원인이 집계 방향이 아니라 조인 위치였기 때문이다.

**5. 최근 업로드로 후보를 좁히거나 전역 최신순으로 정렬.** dev 실측(2026-08-25)으로 전역 최신순
313 ms, 최근 30일 창을 씌운 최신순 864 ms였다(그중 568 ms는 기준 시각 `MAX(created_at)` 계산이라
실제 코드에서는 빠진다). 확정안 272 ms보다 빠르지 않다. 이유가 둘이다. 첫째, 후보가 줄지 않는다.
최근 30일 안에 업로드가 있는 행정동이 1,318개로 콘텐츠 있는 행정동 1,339개의 98퍼센트다. 둘째,
지역별 최근 업로드 시각은 `MAX(created_at)`이라 `gridCount`와 같은 계산값이다. 계산값으로
정렬하는 한 상위 21개를 고르려면 1,339개를 전부 구해야 하므로 `LIMIT`이 일찍 멈출 수 없다.
`LIMIT`이 일찍 멈추려면 정렬 키가 테이블에 저장된 컬럼이어야 하고, 그것이 기각 대안 3번
(정렬 규칙 변경)이다.

## 남는 한계와 승격 조건

수정 후에도 집계는 요청마다 돌고 격자 전체를 훑는다(그 부분이 257 ms). 페이지 깊이에는 비례하지
않지만 **격자 수에는 비례한다.** 지금 격자 144,542개에서 257 ms이므로 격자가 대략 10배(약 145만)로
늘면 2.5초대로 돌아온다.

**승격 조건: 격자 수가 50만을 넘거나 이 엔드포인트의 p95[^6]가 1초를 넘으면 기각 대안 1번
(머티리얼라이즈드 뷰)으로 올린다.** 그 시점에는 깊은 페이지 6 ms라는 이득이 갱신 주기와 낡음
비용을 이긴다. 이 조건은 PRD 정정본에도 같은 값으로 실려 있다.

## 테스트 시나리오

성능은 단위 테스트로 잡히지 않으므로 검증은 세 축이다. 기존 케이스로 회귀 동등성을 확인하고,
경계 케이스 1건을 새로 추가하며, 배포 전 실행 계획을 다시 잰다.

1. **기존 케이스는 한 건도 고치지 않는다.**
   `src/test/java/com/msg/fillmap/video/repository/RegionExploreQueryTest.java`가 정렬, 커서 경계,
   중복과 누락을 이미 검증한다. 이번 변경은 결과 집합이 동일해야 하므로 기존 케이스를 손대지 않고
   전부 green이어야 한다. 기존 케이스를 고쳐야 green이 된다면 그것은 결과 집합이 달라졌다는
   신호이므로 테스트가 아니라 쿼리를 다시 본다.
2. **쿼리 텍스트 검사 단언을 함께 확인한다.**
   `전체_지역_쿼리에_ST__geospatial_연산이_없다`가 `getRegionExplorePage`의 `@Query` 문자열을
   리플렉션으로 읽어 `ST_`와 `geom` 부재를 단언한다. 새 쿼리도 공간 연산을 쓰지 않아 그대로
   통과할 것으로 보지만, 단언이 새 쿼리와 어긋나면 그 테스트를 함께 갱신해야 한다.
3. `개인_지역_우선_정렬이_수정_전과_같다` (기존 케이스로 커버, 추가 없음)
4. `개인에서_비개인으로_넘어가는_커서_경계가_수정_전과_같다` (기존 케이스로 커버, 추가 없음)
5. **신규 필수 1건: `region_code가_NULL인_격자는_전체_지역_목록에_영향을_주지_않는다`.**
   이번 변경이 새로 추가하는 유일한 테스트이고, 조건부가 아니라 반드시 넣는다. 조인을 집계 뒤로
   옮겨도 INNER 조인 의미가 보존되는지 확인하는 자리이며 **이 성질을 잡을 수 있는 유일한 입력**이다.
   원래 확인하고 싶은 형태인 "`regions`에 없는 `region_code`를 가진 격자"는 만들 수 없다.
   `grids.region_code`에 `REFERENCES regions(region_code)` 외래키가 걸려 있어서
   (`src/main/resources/db/migration/V5__grids_region_code.sql:10`), 존재하지 않는 코드를 넣으면
   테스트 준비 단계의 INSERT가 FK 위반으로 먼저 실패하고 쿼리 동작에 도달하지 못한다. 같은 컬럼이
   nullable이므로 실제로 만들 수 있는 경우는 `region_code IS NULL`인 격자(해안 등 무귀속)이고,
   이 격자도 `JOIN regions`(INNER)에서 똑같이 빠지므로 확인하려던 성질(집계와 조인 순서를 바꿔도
   결과 집합이 같다)은 그대로 검증된다. 나중에 orphan `region_code` 케이스를 다시 넣자는 제안이
   나오면 이 FK 근거로 재검토를 닫는다.

   기존 파일에 비슷한 이름의 케이스가 있지만 그것으로는 대체되지 않는다.
   `무라벨_격자는_어떤_행정동_탐색에도_포함되지_않는다`는 모듈 2의 행정동 카드 쿼리
   (`findExploreGridsPopular`)를 대상으로 하고, 이번에 손대는 모듈 3 전체 지역
   (`getRegionExplorePage`)에는 무라벨 격자 케이스가 없었다.

   단언은 둘이다. 무라벨 격자가 **행으로 나오지 않는다**는 것과, 라벨된 격자가 속한 행정동의
   **`gridCount`를 올리지 않는다**(1이지 2가 아니다)는 것이다.

[^1]: Memoize: PostgreSQL이 반복되는 조인 조회의 결과를 실행 중에 캐시하는 실행 계획 노드다. 이 노드가 `loops=144536`으로 찍혔다는 것은 그만큼 조회가 반복됐다는 뜻이라, 캐시가 붙어 있어도 애초에 반복 자체를 없애는 편이 낫다는 신호로 읽었다.
[^2]: external merge: 정렬 대상이 작업 메모리(`work_mem`)를 넘어 임시 파일로 흘러 디스크에서 병합 정렬하는 방식이다. 같은 정렬이 메모리에서 끝나면 계획에 `quicksort Memory`로 찍히고 훨씬 빠르다.
[^3]: CTE(Common Table Expression): `WITH` 절로 이름 붙인 임시 결과 집합이다. 쿼리를 읽기 좋게 나누는 용도이고, 여기서는 그 안의 조인 위치와 그룹 키가 성능을 좌우했다.
[^4]: EXISTS 게이트: 조건을 만족하는 행이 하나라도 있는지만 확인하고 멈추는 준조인이다. 격자마다 공개 영상 존재 여부만 보면 되므로 영상을 전부 세는 것보다 싸다.
[^5]: 머티리얼라이즈드 뷰: 쿼리 결과를 실제 테이블처럼 저장해 두고 명시적으로 갱신하는 객체다. 조회는 빠르지만 값이 마지막 갱신 시점의 스냅숏이라 그 사이 변경이 반영되지 않는다.
[^6]: p95: 응답 시간을 느린 순으로 줄 세웠을 때 상위 5퍼센트 경계값이다. 평균이 가리는 느린 요청을 드러내므로 사용자 체감 지연의 기준으로 쓴다.
