# MSG-586: 지도 이벤트 칩에 업로드 유예 회차 노출

**Owner**: B (콘텐츠·인증 도메인, `com.msg.fillmap.event.*`)

> 요구사항 정본: `docs/prd/event-room-location-videos.md` (확정, 2026-09-09 개정) §4.2 행사 상태 표
> "지도 칩 노출" 열과 2026-09-09 확정 문단, §6 FR-23·FR-24·FR-25, US-001 수용 기준
> SRS: FR-EVENT-01 (2026-09-09 개정, 진행 중) · 선행 스펙: `docs/spec/MSG-439.md` §API 1

## 개요

지도 뷰포트 이벤트 칩 조회 `GET /api/event-occurrences`가 업로드 유예[^1] 회차도 담도록 바꾼다.
지금은 종료 정각에 칩에서 빠지는데, 업로드와 댓글과 도움돼요는 30일 더 열려 있어서 들어갈 입구만
없는 상태가 된다(서울세계불꽃축제 2026-09-05 21:30 종료 뒤 실측). 원인은
`EventQueryServiceImpl.CHIP_STATUSES = Set.of(UPCOMING, LIVE)` 한 줄이고, 고치는 것도 그 한 줄이다.
아카이브[^2] 회차는 계속 제외한다.

범위 밖: 칩에 "종료" 배지를 붙이는 화면 처리(FE와 디자인 몫, 별도 티켓), 상태 우선순위 정렬,
쿼리 변경, `.claude/docs/status.md` MSG-439 항목 갱신(구현 마무리 단계에서 한다).

## 배경 · 목표

- 2026-08-21에 댓글과 도움돼요 잠금을 종료 정각에서 아카이브 전환으로 옮긴 근거가 그대로다. 유예
  기간을 둔 목적이 "행사 다녀와서 나중에 올리기"인데 들어갈 경로가 없으면 유예의 목적과 결과가 서로
  깎인다(PRD §4.2 2026-09-09 확정 문단).
- 목표는 유예 기간 동안 칩이 빠지는 순간이 없게 하는 것이다. 종료 정각에 상태만 LIVE에서 UPLOAD_GRACE로
  바뀌고 칩은 그대로 남았다가, 종료 30일 정각에 아카이브로 넘어가면서 빠진다.

## 성공 기준

검증 테스트 마커는 `// 검증: FR-EVENT-01, AC-586-NN`이다. 경계 시각은 전부 `EventOccurrence.statusAt`의
반개구간[^4] 기준이다.

- AC-586-01: 종료 뒤 30일이 지나지 않은 회차(유예)가 뷰포트에 걸치면 칩 목록에 담기고 `status`가 `"UPLOAD_GRACE"`다.
- AC-586-02: 종료 30일 정각 이후의 회차(아카이브)는 뷰포트에 걸쳐도 칩 목록에 담기지 않는다.
- AC-586-03: 종료 정각에 조회하면 그 회차는 `status`가 `"UPLOAD_GRACE"`인 채로 칩 목록에 담긴다(LIVE에서 넘어가는 순간에 빠지지 않는다).
- AC-586-04: 종료 30일 정각에 조회하면 그 회차는 칩 목록에서 빠진다.
- AC-586-05: 같은 시 안에 유예 회차와 진행 중 회차가 섞여 있어도 정렬은 cityName → startsAt → id 그대로라, 시작일이 빠른 유예 회차가 진행 중 회차 앞에 온다.
- AC-586-06: 노출 시작 전 예정 회차(`visibleFrom > now`)는 여전히 칩 목록에서 빠진다(존재 은닉 불변).
- AC-586-07: AI 경로 추천 후보 수집은 유예 회차를 받아도 후보에 넣지 않는다. 진행 중 회차는 종전대로 후보가 된다.

## API 명세

`GET /api/event-occurrences` (MSG-439 §API 1). 파라미터, 검증, 에러코드(13400·13401), 응답 필드 전부 불변.
바뀌는 것은 담기는 회차의 범위 하나다.

- 담기는 회차: 파생 상태[^5]가 예정(단 `visibleFrom <= now`), 진행 중, 업로드 유예 중 하나이고 노출 영역이
  뷰포트와 겹치는 것. 아카이브 회차는 안 담긴다.
- `status` 값 집합: `UPCOMING`, `LIVE`, `UPLOAD_GRACE` (Swagger `allowableValues`도 이 세 값으로 맞춘다).
- 정렬: cityName → startsAt → id 오름차순, 불변.

## 도메인 로직

`statusAt(now)`가 `UPLOAD_GRACE`를 돌려주는 구간 `[endsAt, endsAt + 30일)`이 칩 노출 구간에 새로 들어간다.
상태 판정 자체(`EventOccurrence.statusAt`, `isVisibleAt`, `uploadClosesAt`)는 건드리지 않는다.

## 테스트 시나리오

`EventQueryServiceTest` 뷰포트 목록 절에 고정 클럭 `NOW` 기준으로 둔다.

- `업로드_유예_상태의_행사는_칩_목록에_담기고_아카이브만_빠진다`: 유예(종료 1일 전), 아카이브(종료 90일 전),
  진행 중 세 회차 중 유예와 진행 중만 담긴다. 유예 칩의 `status`는 `"UPLOAD_GRACE"`. (AC-01, AC-02)
- `종료_정각에도_칩에_담기고_상태만_유예로_바뀐다`: `endsAt == NOW`인 회차가 담기고 `status`가
  `"UPLOAD_GRACE"`. (AC-03)
- `종료_30일_정각부터_칩에서_빠진다`: `endsAt == NOW.minusDays(30)`인 회차는 안 담긴다. (AC-04)
- `유예_회차가_섞여도_정렬은_시_이름_시작일_id_순서_그대로다`: 같은 시에 유예(시작일 빠름)와 진행 중(시작일
  늦음)을 두면 유예가 앞이다. 이것이 의도된 동작이다(D-2). (AC-05)
- `노출_시작_전인_예정_행사는_뷰포트_목록에_담기지_않는다`: 기존 테스트 유지, 통과 확인. (AC-06)
- `업로드_유예_회차는_경로_후보에서_빠진다` (`RouteCandidateCollectorTest`): 칩 조회 mock이 LIVE 1건과 UPLOAD_GRACE 1건을
  주면(둘 다 기간 필터 통과) 후보에 LIVE만 남는다. (AC-07)
- `목록의_상태는_파생_계산을_공유한다`: DisplayName만 세 값으로 갱신하고 단언에 유예 회차 하나를 더해
  `"UPLOAD_GRACE"`까지 세 값이 나오는지 본다.

[^1]: 업로드 유예(UPLOAD_GRACE): 행사 종료 정각부터 종료 30일 정각 직전까지의 파생 상태. 이 구간에는 영상 업로드, 댓글, 도움돼요가 전부 열려 있다(PRD §4.2).

[^4]: 반개구간: 시작점은 포함하고 끝점은 제외하는 구간 `[a, b)`. `statusAt`이 `isBefore`로 판정하므로 정각은 항상 다음 상태에 속하고, 두 상태가 같은 순간을 나눠 갖거나 비는 일이 없다.
[^5]: 파생 상태: DB에 저장하지 않고 조회 시각(서버 Clock)과 `starts_at`, `ends_at`으로 매번 계산하는 회차 상태. 저장하지 않으므로 이번 변경에도 데이터 보정이 필요 없다.
