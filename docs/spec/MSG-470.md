# MSG-470: 영상 길이를 클라이언트 신고값 대신 서버 실측값으로 저장한다

**Owner**: B (콘텐츠/인증 도메인, `com.msg.fillmap.video.*`)

**선행 정본**: `docs/prd/MSG-470-prd.md` (2026-08-25 승인, 상태 검토됨).
처음에는 버그 수정으로 보아 PRD를 면제했으나, Codex 스펙 리뷰가 "저장·표시되는 길이를 정의한
요구사항이 SRS에 없다"고 지적해 면제를 철회하고 PRD를 작성했다.

**요구사항**: FR-MEDIA-19 (저장·표시 길이는 서버 실측을 따른다. 이 티켓이 신설했다).
기존 FR-VIDEO-01 (업로드 확정은 신고 정수 초로 판정, 여유 허용)과 FR-MEDIA-03 (실측 31초 초과는
실패, 30~31초 구간은 자르지 않음)은 불변이다. 이 티켓은 "판정"이 아니라 "저장"을 고친다.

## 개요

업로드 확정(`VideoServiceImpl`)과 교체(`Video.replaceFile`)는 클라이언트가 신고한 정수 초를
그대로 `videos.duration_sec`에 저장한다. 인코딩 워커는 ffprobe[^1]로 실제 길이를 재지만
그 값을 30초 초과 판정과 썸네일 시킹에만 쓰고 버린다. 결과적으로 길이를 표시하는 모든 DTO가
신고값을 내보내, 클라이언트가 잘못 보내면 화면 길이가 실제와 어긋난다 (QA 결함 리스트
컨플루언스 41091074의 "실제 영상 시간이랑 화면에 떠있는 시간이랑 안 맞음" 항목의 서버 몫).

수정: 인코딩 성공 전이 시점에 ffprobe 실측값을 `duration_sec`에 덮어쓴다.

## 배경 · 목표

사용자 화면(내 영상 목록, 전역 목록, 재생 등)에 뜨는 영상 길이가 실제 재생 길이와 일치해야
한다. 신고값은 업로드 확정의 사전 판정 재료로만 쓰고, 저장되는 최종 길이는 서버가 파일에서
실측한 값으로 확정하는 것이 목표다.

## 성공 기준

- 인코딩이 성공한(READY 또는 BLURRING 도달) 영상의 `duration_sec`은 클라이언트 신고값과
  무관하게 실측 반올림값이다 (신고 30초, 실측 12.7초면 13이 저장된다).
- 교체 후 재인코딩된 영상도 같은 규칙으로 실측값이 저장된다.
- 실측 30~31초 여유 구간(MSG-370) 영상은 30으로 저장된다 (스키마 CHECK 위반 없음).
- 실측 전 영상(UPLOADED, ENCODING, 그리고 인코딩 단계에서 실패한 FAILED)의 `duration_sec`은
  종전대로 신고값이다. 반면 블러 켜짐 경로에서 BLURRING 도달 후 AI 실패로 FAILED가 된 영상은
  이미 반영된 실측값을 유지한다 (되돌리지 않는다. FR-3).
- API 응답의 `durationSec` 필드 형태와 이름은 그대로다.

## API 명세

**변경 없음.** 길이를 표시하는 기존 DTO들(내 영상 목록, 전역 목록, 격자 대표 영상, 재생 등)은
`videos.duration_sec`을 그대로 읽으므로, 저장값이 실측으로 바뀌면 별도 수정 없이 실측 길이를
내보낸다. 정수 초 계약 불변.

## 도메인 로직

### 1. 덮어쓰는 시점 = 인코딩 성공 전이 (두 경로)

인코딩 워커(`VideoEncodingServiceImpl.encode`)가 `ffmpegRunner.probeDurationSec(original)`로
얻는 실측값을 성공 전이에 실어 보낸다. 전이는 `VideoStatusWriter`의 두 메서드다:

- **블러 꺼짐 경로**: `markReady(videoId, expectedOriginalKey, encodedKey, thumbnailKey, measuredDurationSec)`
  에서 ENCODING → READY 전이와 함께 덮어쓴다.
- **블러 켜짐 경로**: `markEncoded(videoId, expectedOriginalKey, encodedKey, measuredDurationSec)`
  에서 ENCODING → BLURRING 전이와 함께 덮어쓴다. 이후의 `markBlurReady`(BLURRING → READY)는
  손대지 않는다. 실측값은 이미 BLURRING 전이 때 확정됐고, 블러본은 원본과 길이가 같다.
  이후 AI가 실패해 `markBlurFailed`로 FAILED가 되어도 실측값은 그대로 둔다. 되돌리려면 신고값을
  따로 보관해야 하는데, 실측값이 파일의 실제 길이라는 사실은 블러 성공 여부와 무관하므로
  되돌릴 이유가 없다 (FR-3, Codex 2R 지적 반영).

두 전이 모두 `findWithLockById` 행 잠금[^2]과 `isCurrentEncodingAttempt` 스테일 가드[^3]를 이미
갖추고 있어, 교체·삭제와의 경합은 기존 가드가 그대로 처리한다. 가드에 걸려 전이가 skip되면
길이 덮어쓰기도 함께 skip된다 (옛 파일의 실측값이 새 파일에 붙지 않는다).

엔티티 쓰기는 `Video.markReady`와 `Video.markEncoded`에 `short durationSec` 파라미터를 추가해
상태 전이와 같은 더티 체킹[^4]으로 반영한다. 별도 UPDATE 쿼리 없음.

### 2. 값 계산 (반올림 + 스키마 범위 클램프[^5])

```java
short measured = (short) Math.max(1, Math.min(30, Math.round(duration)));
```

- **반올림**: 실측 12.7초 → 13. 정수 초 계약 유지.
- **상한 30 클램프**: 스키마 CHECK `duration_sec > 0 AND duration_sec <= 30` 준수.
  MSG-370이 허용한 실측 30~31초 여유 구간이 반올림으로 31이 되어도 30으로 저장한다.
- **하한 1 클램프**: 실측 0.5초 미만은 반올림하면 0이라 같은 CHECK의 하한(`> 0`)을 위반한다.
  확정 시점 신고값 검증(1~30)은 파일 실제 길이를 보장하지 않으므로 이 경계가 실재한다.
  상한과 같은 근거(CHECK 준수)로 1로 클램프한다. 승인된 수정 방향의 식에 하한만 더한
  상세화이며, 방향 자체(실측 저장, 30 클램프)는 그대로다.

계산은 probe 직후 `VideoEncodingServiceImpl`에서 한 번 수행해 두 경로(markReady, markEncoded)에
같은 값을 넘긴다. 31초 초과 실패 판정(`MAX_DURATION_SEC = 31.0`)은 종전대로 double 원값으로 한다.

### 3. 교체·확정 경로는 불변

`VideoServiceImpl`의 확정(`Video.create`)과 교체(`replaceFile`)는 종전대로 신고값을 저장한다.
신고값은 인코딩 전 구간(UPLOADED, ENCODING)의 잠정 표시값이 되고, 교체 재인코딩도 같은 성공
전이를 타므로 별도 처리 없이 실측값으로 갱신된다.

**데이터 저장 위치**: `videos.duration_sec` (SMALLINT) 한 곳. 새 테이블·Redis 키·S3 경로 없음.

**실행 쿼리**: 별도 UPDATE문을 만들지 않았다. 전이 트랜잭션이 커밋될 때 더티 체킹이 기존
상태 UPDATE에 컬럼 하나를 얹는다.
`update videos set ..., duration_sec=?, encoded_url=?, processing_status=?, thumbnail_url=? where id=?`.
행은 이미 `SELECT ... FOR UPDATE`(`findWithLockById`)로 잠긴 상태다.

**예외 흐름**: 새 예외·새 developCode 없음. 실측 31초 초과는 종전대로 `markFailed` → FAILED이고,
클램프는 그 판정 **뒤에** 계산하므로 초과 영상이 30으로 뭉개져 통과하지 않는다
(`길이_초과_판정은_클램프_전_원값으로_한다`가 이 순서를 고정한다).

**빈 동작**: `VideoStatusWriter`는 그대로 `REQUIRES_NEW` 프록시 경계다. 스테일 가드
(`isCurrentEncodingAttempt`)에 걸려 전이가 skip되면 길이 덮어쓰기도 함께 skip된다.
옛 파일의 실측값이 교체된 새 파일에 붙지 않는다. `markBlurReady`·`markReadyFromBlurring`은
손대지 않아, BLURRING 도달 후 AI가 실패해도 이미 반영된 실측값이 유지된다(FR-3).

**미구현**: 통합 테스트(교체 후 재인코딩)는 스펙에서 선택 항목이라 넣지 않았다. 교체 경로는
확정과 같은 성공 전이를 타고, 그 전이의 길이 갱신은 위 라이터·인코더 테스트가 덮는다.

[^1]: ffprobe: ffmpeg에 딸린 미디어 분석 도구. 영상 파일의 컨테이너 메타데이터에서 재생 길이 등을 읽어낸다. 이 프로젝트에서는 `FfmpegRunner.probeDurationSec`이 감싸고 있다.
[^2]: 행 잠금: `SELECT ... FOR UPDATE`로 해당 videos 행을 트랜잭션 동안 배타 점유하는 것. 교체나 삭제 트랜잭션이 같은 행을 동시에 고치지 못하게 막는다. `VideoRepository.findWithLockById`가 담당한다.
[^3]: 스테일 가드: 비동기 워커가 일을 마치고 돌아왔을 때, 그 사이 교체나 삭제로 "이미 다른 시도가 된" 영상에 옛 결과를 쓰지 않도록 원본 S3 키와 상태를 재확인하는 검사. `VideoStatusWriter.isCurrentEncodingAttempt`가 담당한다 (MSG-241).
[^4]: 더티 체킹: JPA가 트랜잭션 안에서 엔티티 필드 변경을 감지해 커밋 시점에 UPDATE문을 자동 생성하는 동작. 상태 전이 메서드가 UPDATE 쿼리 없이 성립하는 이유다.
[^5]: 클램프: 값이 허용 범위를 벗어나면 범위 경계값으로 눌러 맞추는 것. 여기서는 반올림 결과를 스키마 CHECK가 허용하는 1 이상 30 이하로 맞춘다.
