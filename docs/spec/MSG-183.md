# MSG-183: 핫스코어 집계 — 업로드 확정 시 Redis 버킷 증분

**Owner**: 공동 (hotzone 패키지 신설 = A, VideoServiceImpl 훅 배선·video 테스트 = B, 계약 인터페이스 신설 1건)

> PRD: `docs/prd/MSG-233-hotzone-prd.md` (검토됨, 2026-07-31 성민 확정) — 이 티켓 범위는
> **"핫스코어 집계 (MSG-183)" FR-4~FR-6**.
> 설계 정본: `docs/spec/MSG-233.md` **D1~D6** — 산식·버킷·키 스키마·TTL·계약 시그니처·배선 지점은
> 전부 거기서 확정됐다. 이 스펙은 D-결정을 재창작하지 않고 **구현 세부(클래스 배치·훅 위치·

## 범위 경계 — MSG-184(조회)는 이 티켓이 아니다

이 티켓은 **집계(write 경로)만**: hotzone 패키지 신설 + `HotScoreCommandService` 인터페이스/impl
+ Redis 증분 + VideoServiceImpl 훅 배선. 아래는 전부 **제외** (MSG-184 몫):

- `HotZoneService` 조회 계약 · `HotZoneView` · `ViewportBounds` 재사용
- `ZUNIONSTORE` 8버킷 합산 · `hotzone:top` 캐시
- `GET /api/hotzones` · 컨트롤러 · DTO
- `HotZoneErrorCode`(8xxx) — 집계는 에러를 전파하지 않으므로(FR-6) 에러 코드 자체가 불요
- `fillmap.hotzone.top-k` · `min-score` yml 프로퍼티(D3) — 조회 판정 값이라 MSG-184에서 추가

## 개요

업로드가 확정되면 그 격자의 핫스코어를 Redis 시간버킷에 +1 증분한다(FR-4). 배치 재계산 없이
이벤트 시점 증분이며, 48시간 윈도우 밖 신호는 버킷 구조(조회 룩백)와 TTL로 자동 소멸한다(FR-5).
집계 실패는 업로드를 실패시키지 않는다(FR-6).

## 배경 · 목표

- MSG-233 설계 확정으로 착수 가능해진 첫 구현 티켓. 핫구역 칩(MSG-184)이 읽을 신호 원장을 쌓는다.
- 목표: 업로드 확정 경로에 O(1) Redis 연산 하나를 커밋 후 비동기로 얹고, 업로드 응답 계약은
  바이트 하나 바꾸지 않는다.

## 성공 기준

- 아래 테스트 시나리오 전부 green
- 업로드 API(`saveVideo`) 응답·에러 계약 무변 — Redis가 죽어 있어도 업로드는 성공(FR-6)
- Redis 키가 D4 스키마와 일치: `hotzone:{bucketId}` Sorted Set, member=gridId, TTL 54h
- 교체(`replaceVideo`)·삭제(`deleteVideo`) 경로에 hotzone 코드가 등장하지 않음 (D6)

`VideoUploadResponseDto`에 핫스코어 관련 필드를 싣지 않는다(D6 — 응답에 실을 결과가 없어 비동기).

## 도메인 로직 — D-결정 참조 요약

정본은 `docs/spec/MSG-233.md`. 구현이 따를 확정치만 요약:

| 항목 | 확정 (출처) |
|---|---|
| 신호 | 업로드(방문 이벤트) 1건 = +1. **재방문 포함 전부 인정, 도배 방어 없음** (D1) |
| 버킷 | UTC 6h 고정, `bucketId = epochSeconds / 21600` 정수 나눗셈 — KST 변환 불요 (D2) |
| 증분 | `ZINCRBY hotzone:{bucketId} 1 {gridId}` + `EXPIRE 54h` 재설정(멱등) (D2·D4) |
| TTL 역할 | **청소 전용** — 48h 윈도우 판정은 조회 룩백(MSG-184) 몫. 54h = 48h + 버킷폭 6h 여유 (D4) |
| 실패 비전파 | impl 내부 try-catch(Exception) + warn 로그. 호출자에게 예외 전파 금지 (D6, FR-6) |
| 배선 지점 | `saveVideo` 훅 체인(badge→streak→mission) 뒤 `afterCommit` 1줄 (D6) |
| 미배선 | 교체 — 새 방문이 아니라 파일 교체(스트릭 동일 판단). 삭제 — 차감 없음, 윈도우 만료로 자연 소멸 (D4·D6) |

glossary 대조: 신호는 **"방문"(업로드 이벤트, N회 반복)**이다 — "점령"(첫 업로드 상태)이 아니다.
재방문도 전부 신호이므로 코드·테스트명에 점령 계열 표현(`occupied` 등)을 쓰지 않는다.

### 클래스 배치 — Owner A

```text

├── HotScoreCommandService.java        # 인터페이스 (위 계약 전문)
└── HotScoreCommandServiceImpl.java    # @Service
```

- 평면 `service` 패키지. (근거 정정 — 리뷰어 실측: `service/impl` 하위가 다수다.
  grid·region·search·mission·usergrid·zone 6개 도메인이 impl 하위, badge·streak·video 3개가 평면.
  다만 이 모듈은 인터페이스+Impl 2파일뿐이고 MSG-184가 합류해도 4파일 수준이라 하위 계층 없이
  평면을 유지한다 — badge·streak 신설 선례와 동일 규모 판단.)
- `@Service` + `@Slf4j`, **`StringRedisTemplate` 주입** — `RedisRefreshTokenStore` 선례
  (auth, `refresh:*` 키)와 동일 템플릿.
- **프로파일 분리·인메모리 대역 없음** (auth의 `@Profile("!test")`+`InMemory*` 이중화를 따르지
  않는다). 실측 근거: ① 전 테스트가 기본 `local` 프로파일로 돌고(`@ActiveProfiles("test")` 사용
  0건) 실 Redis(localhost:6379 — 로컬 `fillmap-local-redis`, CI redis 서비스 컨테이너)가 살아있다.
  ② 이 빈은 실패를 삼키므로(FR-6) Redis 부재 환경에서도 컨텍스트 로드·호출이 죽지 않는다 —
  인메모리 대역이 보호할 것이 없다.
- **`Clock` 주입** — `MissionQueryServiceImpl` 선례: `@Autowired` 기본 생성자는 `Clock.systemUTC()`,
  테스트 생성자로 고정 Clock 주입. 버킷 경계(6h) 플레이크 없는 결정적 테스트를 위해서다.

구현 스케치:

```java
@Override
public void recordUpload(String gridId) {
	try {
		String key = "hotzone:" + clock.instant().getEpochSecond() / 21600L;
		redisTemplate.opsForZSet().incrementScore(key, gridId, 1);
		redisTemplate.expire(key, Duration.ofHours(54));
	} catch (Exception e) {
		log.warn("핫스코어 증분 실패 — 신호 1건 유실 허용: gridId={}", gridId, e);   // FR-6
	}
}
```
