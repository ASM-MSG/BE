# MSG-195: 관리자 신고 처리 API

**Owner**: B

> 요구사항 정본: `docs/prd/MSG-195-prd.md` (상태 검토됨, 2026-08-06 승인. 미해결 질문 0건).
> 이 스펙은 PRD의 FR-1~10과 비기능 요구사항에 "어떻게"만 붙인다.

## 개요

신고 접수(MSG-192)로 쌓이는 PENDING 신고를 관리자가 열람하고 승인 또는 기각으로 종결하는
API를 연다. 승인하면 대상 영상이 블라인드되고, 오판이면 해제로 복구한다. 블라인드 전환과
해제는 MSG-193이 만들어 둔 `VideoModerationService`를 호출만 하고 video 쪽 코드는 건드리지
않는다. 관리자라는 행위자는 이미 완비된 role 배관(JWT role 클레임, `ROLE_ADMIN` 권한)을
소비하는 URL 인가[^1] 하나로 분리한다. 이 프로젝트 최초의 인가 지점이다.

## 배경 · 목표

신고 접수만 있고 처리가 없어 모더레이션 루프가 반쪽이다. 지금은 신고 열람도 영상 내리기도
DB 직접 조작뿐이다. 이 티켓으로 접수부터 조치까지 한 바퀴가 API로 돈다.

- 관리자가 신고 목록을 상태별로 조회하고, 판단에 필요한 정보를 한 번에 받는다
- 승인은 신고 종결(RESOLVED)과 영상 블라인드를 한 트랜잭션으로 묶고, 기각(REJECTED)은
  영상에 손대지 않는다. 두 경우 모두 처리자와 처리 시각이 남는다
- 블라인드 해제로 영상을 복구할 수 있다 (신고 상태는 되돌리지 않는다)
- ADMIN이 아닌 사용자는 관리자 API에 접근할 수 없고, 실패 응답도 공통 형식을 유지한다

비목표는 PRD 2절 그대로다. 관리자 계정 생성 수단, REVIEWING 상태, 대시보드 화면, 일괄
처리, 신고자 알림, 사용자 정지는 전부 만들지 않는다.

## 성공 기준

1. ADMIN 토큰으로 `GET /api/admin/reports`를 호출하면 PENDING 신고가 최신 접수 순으로,
   신고자 닉네임과 영상 소유자 닉네임을 포함해 페이지 단위로 온다 (FR-1, FR-2)
2. 승인 호출 한 번으로 신고가 RESOLVED가 되고 영상이 BLINDED가 되며, `reviewed_by`와
   `reviewed_at`이 채워진다. 롤백 시 두 변경이 함께 사라진다 (FR-4)
3. 대상 영상이 이미 BLINDED이거나 DELETED인 신고를 승인하면 영상 전이 없이 신고만
   종결된다 (FR-5)
4. 기각 후 영상 상태와 대표 영상, 조회수 등 영상 축 데이터가 전이 전과 동일하다 (FR-6)
5. 이미 처리된 신고의 승인과 기각, 그리고 같은 신고에 대한 동시 처리 중 늦은 쪽은 409를
   받는다 (FR-7, FR-10)
6. 해제 호출로 BLINDED 영상이 ACTIVE로 돌아오고, 그 신고의 RESOLVED는 그대로다 (FR-8)
7. 관리자 단건 확인은 PRIVATE와 BLINDED 영상에도 재생 URL을 발급하며, 조회수를 올리지
   않는다 (FR-3)
8. USER 토큰의 관리자 API 호출은 403 공통 응답(`ApiResponseDto`)으로, 무토큰 호출은 기존
   401(2403)로 거부된다 (FR-9)

## API 명세

다섯 엔드포인트 전부 `/api/admin` 아래이고 ADMIN role 필수다. 컨트롤러는
`AdminReportController` 하나로 묶는다 (PRD 6절 클래스 다이어그램 그대로. 신고 축 3개와
영상 축 2개뿐이라 분리 이득이 없다).

### 1. 신고 목록 조회

```text
GET /api/admin/reports?status=PENDING&page=0&size=20
```

| 파라미터 | 기본값 | 규칙 |
|---|---|---|
| `status` | `PENDING` | `ReportStatus` 4값 중 하나 (대소문자 무관). 그 외 값은 400 (11420) |
| `page` | `0` | 0 이상. 위반 시 400 (11421) |
| `size` | `20` | 1 이상 100 이하. 위반 시 400 (11421) |

일반 오프셋 페이징[^2]이다. 레포의 사용자향 목록은 전부 keyset 커서지만, 관리자 전용
소량 데이터라 커서의 이점이 없어 이 API만 예외로 둔다 (2026-08-06 확정, PRD 비기능 성능
행). 정렬은 `created_at DESC, id DESC` 고정이다 (같은 시각 접수의 순서 안정화 타이브레이크).

REVIEWING은 유효한 필터 값으로 받되, 만드는 경로가 없으므로 항상 빈 목록이다.

**200 응답** `AdminReportListResponseDto`:

```json
{
	"items": [
		{
			"reportId": 7,
			"status": "PENDING",
			"reason": "INAPPROPRIATE",
			"detail": null,
			"createdAt": "2026-08-06T10:15:00",
			"reporterId": 3,
			"reporterNickname": "정민",
			"videoId": 1042,
			"videoStatus": "ACTIVE",
			"videoOwnerNickname": "성민",
			"reviewedBy": null,
			"reviewedAt": null
		}
	],
	"page": 0,
	"size": 20,
	"totalElements": 1,
	"totalPages": 1
}
```

항목 필드는 FR-2 목록에 신고 상태와 처리자, 처리 시각을 더한 것이다. RESOLVED와 REJECTED
필터 조회(FR-1)가 처리 이력 없이는 반쪽이라서다. `reviewedBy`는 처리한 관리자의 사용자 id,
미처리면 null이다.

### 2. 신고 승인

```text
POST /api/admin/reports/{reportId}/approve
```

**200 응답** `AdminReportProcessResponseDto`:

```json
{
	"reportId": 7,
	"status": "RESOLVED",
	"videoId": 1042,
	"videoStatus": "BLINDED",
	"reviewedAt": "2026-08-06T11:00:00"
}
```

`videoStatus`는 처리 후 영상 상태다. FR-5의 전이 생략 케이스(이미 BLINDED, 또는 DELETED)를
관리자가 응답만으로 구분할 수 있다.

### 3. 신고 기각

```text
POST /api/admin/reports/{reportId}/reject
```

**200 응답**: 승인과 같은 `AdminReportProcessResponseDto`. `status`는 `REJECTED`,
`videoStatus`는 손대지 않은 현재 상태다.

### 4. 블라인드 해제

```text
POST /api/admin/videos/{videoId}/unblind
```

**200 응답** `AdminVideoUnblindResponseDto`:

```json
{
	"videoId": 1042,
	"status": "ACTIVE"
}
```

신고 상태는 건드리지 않는다 (FR-8, 2026-08-06 확정). 해제 축의 실패는
`VideoModerationService`의 기존 가드가 그대로 올라온다: 없는 영상과 DELETED는 3404,
이미 ACTIVE면 3409.

### 5. 관리자 단건 영상 확인

```text
GET /api/admin/videos/{videoId}
```

목록과 분리된 확인 요청 시점에 재생 URL을 발급한다 (2026-08-06 확정. 목록에 실으면 발급과
시청 사이에 presigned URL[^3]이 만료되고, 사용자 재생 경로에 관리자 예외를 넣으면 조회수
증가와 은닉 로직이 오염된다는 근거는 PRD FR-3에 있다).

**200 응답** `AdminVideoReviewResponseDto`:

```json
{
	"videoId": 1042,
	"status": "BLINDED",
	"processingStatus": "READY",
	"visibility": "PRIVATE",
	"durationSec": 12,
	"recordedAt": "2026-07-20T18:03:11",
	"playbackUrl": "https://...presigned...",
	"thumbnailUrl": "https://...presigned...",
	"expiresInSec": 600
}
```

- `visibility`와 `status`(BLINDED 포함)를 무시하고 발급한다. 단 DELETED는 3404다: 삭제
  경로(MSG-133)가 커밋 후 S3 객체를 지우므로 발급해도 재생할 파일이 없다
- 재생 소스 선택은 MSG-206 `getVideoPlayback`과 같은 규칙이다. `processingStatus`가
  READY일 때만 블러본 키가 있으면 블러본, 없으면 인코딩본을 `ThumbnailUrlPresigner`로
  서명한다. READY가 아니면 `playbackUrl`과 `expiresInSec`은 null이다
- 사용자 경로와 달리 조회수를 올리지 않고, 소유자 판정과 친구 판정이 없다

### 에러 응답 정리

| developCode | HTTP | 상수 | 발생 지점 |
|---|---|---|---|
| 11420 | 400 | `INVALID_STATUS_FILTER` (신규) | 목록의 미지원 status 값 |
| 11421 | 400 | `INVALID_PAGE_REQUEST` (신규) | page 음수, size 범위 밖 |
| 11404 | 404 | `REPORT_NOT_FOUND` (신규) | 없는 신고의 승인과 기각 |
| 11410 | 409 | `ALREADY_PROCESSED_REPORT` (신규) | 처리된 신고의 재처리, 동시 처리의 패자 |
| 3404 | 404 | `VIDEO_NOT_FOUND` (기존) | 해제와 단건 확인의 없는 영상, DELETED 영상 |
| 3409 | 409 | `ALREADY_IN_TARGET_STATUS` (기존) | 이미 ACTIVE인 영상 해제 |
| 403 | 403 | 공통 `FORBIDDEN` | ADMIN 아닌 인증 사용자의 관리자 API 호출 |
| 2403 | 401 | `UNAUTHENTICATED` (기존) | 무토큰 호출 (기존 EntryPoint 그대로) |

신규 4개는 `ReportErrorCode`(11xxx 대역, MSG-192 신설)에 추가한다. 뒷자리는 HTTP 에코가
기본이되 겹치면 의미 구분이라는 기존 규칙을 따랐다. 11420과 11421은 "잘못된 열거형 파라미터
= x420" 선례(3420, 9420)의 연장이고, 11409는 DUPLICATE_REPORT가 선점해 11410으로 비켰다
(9409와 9410 선례). 신고는 관리자만 보는 자원이라 존재 은닉[^4]이 필요 없어, 영상 축의
3404 재사용 관례 대신 11404를 신설한다.

## 도메인 로직

### 인가: 이 프로젝트 최초의 role 검사 지점

역할 배관은 전부 있고 검사만 없다는 것을 코드로 확인했다. `JwtAuthenticationFilter`가
`ROLE_ADMIN` 권한을 SecurityContext에 심지만(`JwtAuthenticationFilter` 49행), 소비 지점은
0곳이다 (`@PreAuthorize`, `@EnableMethodSecurity`, role matcher 전무).

`SecurityConfig.filterChain`의 `authorizeHttpRequests`에 한 줄을 추가한다. permitAll
목록 다음, `anyRequest().authenticated()` 앞이다:

```java
.requestMatchers("/api/admin/**").hasRole("ADMIN")
```

메서드 보안(`@EnableMethodSecurity`)은 도입하지 않는다. 관리자 API가 URL 프리픽스 하나로
전부 묶이므로 matcher 한 줄이 최소 구현이다.

**403 응답 형식 실측 결과 (PRD 미해결 질문 3의 확정 이행)**: 현재 `exceptionHandling`에는
`authenticationEntryPoint`만 등록돼 있고 `accessDeniedHandler`가 없다. 이 상태에서 인가
실패가 나면 스프링 시큐리티 기본 `AccessDeniedHandlerImpl`이 `sendError(403)`으로 `/error`에
포워드하고, Spring Boot 기본 에러 JSON(timestamp, status, error, path)이 나간다.
`ApiResponseDto` 형식이 아니므로 **`CustomAccessDeniedHandler`를 신설한다** (2026-08-06
확정 조건 충족). 기존 `CustomAuthenticationEntryPoint`(`auth/jwt`)를 미러링해 같은 패키지에
두고, 공통 `ErrorCode.FORBIDDEN`(403)을 `ApiResponseDto`로 직렬화해 쓴다. 등록은
`exceptionHandling(ex -> ex.authenticationEntryPoint(...).accessDeniedHandler(...))`.

무토큰 요청은 새 코드가 필요 없다. 익명 상태에서 matcher에 걸리면
`ExceptionTranslationFilter`가 인증 문제로 분류해 기존 EntryPoint(2403, 401)로 보낸다.
이 동작은 테스트로 검증한다.

### 관리자 계정 승격: 운영 절차 문서만

계정 생성 코드와 시드는 만들지 않는다 (2026-08-06 확정). `.claude/docs/deploy.md`에
"관리자 계정 승격" 절을 신설해 다음을 담는다 (PRD가 위치 결정을 스펙에 위임한 항목):

- 승격 SQL: `UPDATE users SET role = 'ADMIN' WHERE id = {대상 id};`
- role은 로그인 시 액세스 토큰 클레임에 실리므로, 승격 후 **재로그인(토큰 재발급)해야
  ROLE_ADMIN이 반영**된다
- 강등의 역방향 주의: `role = 'USER'`로 되돌려도 이미 발급된 액세스 토큰은 만료까지
  ADMIN으로 동작한다. 즉시 차단이 필요하면 토큰 만료를 기다리거나 리프레시를 무효화한다

### 승인 흐름: 잠금 순서와 FR-5

`AdminReportServiceImpl.approve(adminId, reportId)`는 한 트랜잭션이다 (FR-4):

1. `reportRepository.findWithLockById(reportId)`로 신고 행을 비관적 잠금[^5] 조회한다.
   없으면 11404. `FriendshipRepository.findWithLockById` 선례의 파생 쿼리 + `@Lock` 방식
2. 상태가 PENDING이 아니면 11410. 동시 승인 경쟁(FR-10)은 이 행 잠금이 직렬화한다:
   늦은 트랜잭션은 잠금 대기 후 RESOLVED를 읽고 여기서 걸린다
3. `videoRepository.findWithLockById(report.getVideoId())`로 영상 행을 잠근다.
   moderation이 `VideoRepository`를 직접 주입하는 것은 MSG-192 §D4 선례다 (둘 다 Owner B라
   계약 인터페이스가 필요한 경계가 아니다)
4. 영상 상태로 분기한다 (FR-5):
   - ACTIVE면 `videoModerationService.blind(videoId)` 호출. blind 내부의
     `findWithLockById`는 같은 트랜잭션이 이미 보유한 잠금의 재획득이라 대기가 없다
   - BLINDED거나 DELETED면 전이를 생략하고 신고만 종결한다. blind를 호출해 3409와 3404
     예외를 잡는 방식은 쓰지 않는다: 예외 코드 비교로 제어 흐름을 짜면 blind의 가드 변경에
     조용히 깨진다. 상태 사전 확인이 명시적이고, 3번의 잠금 덕에 확인과 전이 사이 경합도 없다
5. `report.resolve(adminId)`로 RESOLVED 전이와 `reviewedBy`, `reviewedAt` 기록
   (더티 체킹 UPDATE)

잠금 순서는 "reports 행 먼저, videos 행 다음" 하나뿐이다. 기존 경로(신고 접수, 삭제,
블라인드)는 videos 행만 잠그고 reports 행을 잠그지 않으므로 역순 획득이 없어 데드락이
불가능하다.

단계 3에서 영상 행이 없는 경우는 FK(`reports.video_id REFERENCES videos ON DELETE
CASCADE`) 때문에 이론상 불가하다 (영상 행이 지워지면 신고 행도 함께 사라진다). 방어적으로
3404를 던진다.

### 기각 흐름

승인의 1번과 2번만 수행하고 `report.reject(adminId)`로 끝낸다. 영상 축은 조회조차 하지
않는다 (FR-6). 응답의 `videoStatus`는 잠금 없는 일반 조회로 채운다.

### 해제와 단건 확인

- **해제**: `videoModerationService.unblind(videoId)` 위임 한 줄이다. MSG-193이 가드(3404,
  3409)와 잠금을 이미 갖췄고, 대표 원복 없음과 파생 갱신 없음도 그쪽 결정(D6) 그대로다.
  MSG-193이 "호출 주체와 감사 이력은 MSG-195 몫"이라 남긴 감사 축은, 해제의 경우 신고
  행을 되돌리지 않으므로 별도 기록 없이 접근 로그로 갈음한다 (아래 설계 결정 D4)
- **단건 확인**: `AdminReportServiceImpl`이 `VideoRepository`로 직접 조회하고
  `ThumbnailUrlPresigner`로 서명한다. 사용자 경로(`VideoServiceImpl.getVideoPlayback`)를
  호출하거나 수정하지 않는다. 그쪽의 소유자 분기, 친구 판정, 조회수 증가, BLINDED 은닉이
  전부 관리자 맥락에 부적합해서다

### 목록 조회

`ReportRepository`에 생성자 프로젝션[^6] 쿼리를 추가한다. `FriendshipRepository`의
"User를 FK 매핑 없이 Long 조인" 선례를 따라 Report, 신고자 User, Video, 소유자 User를
세타 조인 한 방으로 낸다:

```java
@Query(value = """
	SELECT new com.msg.fillmap.moderation.dto.AdminReportItemResponseDto(
		r.id, r.status, r.reason, r.detail, r.createdAt,
		r.reporterId, ru.nickname,
		r.videoId, v.status, vu.nickname,
		r.reviewedBy, r.reviewedAt)
	FROM Report r, User ru, Video v, User vu
	WHERE ru.id = r.reporterId AND v.id = r.videoId AND vu.id = v.userId
		AND r.status = :status
	ORDER BY r.createdAt DESC, r.id DESC
	""",
	countQuery = "SELECT count(r) FROM Report r WHERE r.status = :status")
Page<AdminReportItemResponseDto> findPageByStatus(@Param("status") ReportStatus status, Pageable pageable);
```

페이징 구현은 Spring Data의 `PageRequest`를 그대로 쓴다. 코드베이스 첫 사용이지만 이미
클래스패스에 있는 표준 기능이라 손으로 LIMIT OFFSET을 만들 이유가 없다. `page`와 `size`
범위는 `PageRequest.of` 호출 전에 서비스가 검사해 11421을 던진다 (검사 없이 넘기면
`IllegalArgumentException`이 catch-all 핸들러에서 500이 된다). `status` 문자열 파싱은
`ReportServiceImpl.parseReason` 선례대로 서비스에서 `valueOf` + `Locale.ROOT` 대문자
변환으로 하고 실패 시 11420이다.

조인 결측 걱정은 없다. 신고자는 FK(RESTRICT)로, 영상과 소유자는 위 CASCADE 논리로 행
존재가 보장된다 (사용자 하드 삭제 경로도 코드에 없다).

[^1]: 인가(authorization): 인증(누구인지 확인)과 구분되는 개념으로, 확인된 사용자가 이
    행동을 해도 되는지 판단하는 것. 이 티켓 전까지 코드에는 인증만 있고 role 기반 인가
    검사가 한 곳도 없었다.
[^2]: 오프셋 페이징(offset paging): "앞에서 N건 건너뛰고 M건"으로 페이지를 끊는 방식.
    페이지 번호 이동이 자유로운 대신 깊은 페이지일수록 건너뛰기 비용이 커서, 이 레포의
    사용자향 목록은 마지막 항목 기준으로 이어 읽는 keyset 커서를 쓴다. 관리자 소량
    데이터는 그 비용이 무의미해 오프셋을 예외 허용한다.
[^3]: presigned URL: private S3 버킷의 객체를 제한 시간 동안만 열 수 있게 서명한 URL.
    발급 후 TTL(이 레포는 10분)이 지나면 무효라서, 발급 시점과 시청 시점을 붙여야 한다.
[^4]: 존재 은닉: 권한 없는 요청에 403 대신 404를 돌려줘 리소스의 존재 자체를 숨기는 응답
    방식. 사용자향 영상 경로가 쓰는 규칙이며, 관리자 전용 신고 자원에는 숨길 상대가 없어
    적용하지 않는다.
[^5]: 비관적 잠금(pessimistic lock): 행을 읽는 시점에 DB 잠금(SELECT FOR UPDATE)을 걸어
    다른 트랜잭션의 접근을 커밋까지 세워두는 방식. 같은 신고를 두 관리자가 동시에 처리하는
    경쟁을 행 하나 기준으로 직렬화한다.
[^6]: 생성자 프로젝션(constructor projection): JPQL의 SELECT NEW 구문으로 조회 결과를
    엔티티가 아닌 DTO 생성자에 바로 담는 기법. 엔티티 간 FK 매핑 없이도 필요한 컬럼만
    조인해 가져올 수 있다.

**런타임 동작 기록**

- 데이터 저장 위치: 마이그레이션 0건 확정(V27 유지) — 이번 티켓의 쓰기는 전부 기존 컬럼이다.
  `reports.reviewed_by`(BIGINT NULL, users FK)·`reports.reviewed_at`(TIMESTAMP NULL)은 V1부터
  있던 컬럼에 엔티티 매핑만 보탰고(MSG-192 §D6 예약분), `reports.status` 전이(RESOLVED/REJECTED)와
  `videos.status` 전이(BLINDED↔ACTIVE)도 기존 컬럼 UPDATE다. Redis·S3 접점 없음 — 해제가
  가능해야 하므로 블라인드는 S3 객체를 건드리지 않는다(MSG-193 결정 소비).
- 실행 쿼리 (AdminReportIntegrationTest SQL 로그 실측, Hibernate 생성):
  - 목록 `findPageByStatus`: `select r1_0.id, r1_0.status, …, u1_0.nickname, …, v1_0.status,
    u2_0.nickname, … from reports r1_0, users u1_0, videos v1_0, users u2_0 where
    u1_0.id=r1_0.reporter_id and v1_0.id=r1_0.video_id and u2_0.id=v1_0.user_id and r1_0.status=?
    order by r1_0.created_at desc, r1_0.id desc fetch first ? rows only`. JPQL 세타 조인이 INNER
    JOIN 구문으로 재작성되지 않고 FROM 콤마 나열 + WHERE 등가 조건 그대로 나간다(의미상 내부
    조인 동일). 페이징은 page 0이면 `fetch first ? rows only`, page>0이면 `offset ? rows fetch
    first ? rows only`. count 쿼리는 조인 없이 `select count(r1_0.id) from reports r1_0 where
    r1_0.status=?`.
  - 신고 행 잠금 `ReportRepository.findWithLockById`(파생 쿼리 + @Lock): `select r1_0.* from
    reports r1_0 where r1_0.id=? for no key update of r1_0`. PESSIMISTIC_WRITE 가 PostgreSQL
    방언에서 FOR UPDATE 가 아니라 **FOR NO KEY UPDATE** 로 나간다(MSG-192 실측과 동일) —
    동시 승인·기각 직렬화에는 충분하고, FK 참조 검사(KEY SHARE)와는 충돌하지 않는다.
  - 승인 흐름의 영상 잠금 `VideoRepository.findWithLockById`: `select v1_0.* from videos v1_0
    where v1_0.id=? for no key update of v1_0` — 역시 FOR NO KEY UPDATE. blind 내부의 같은
    메서드 호출은 동일 트랜잭션의 잠금 재획득이라 두 번째 SELECT 가 대기 없이 돈다. 이후
    `update videos set status=? where id=?`(markBlinded 더티 체킹), 대표 재선정 native UPDATE
    (user_grids cover_video_id 서브쿼리), `update reports set …, reviewed_at=?, reviewed_by=?,
    status=? where id=?`(resolve 더티 체킹) 순으로 커밋된다.
- 예외 흐름: 도메인 실패는 전부 서비스에서 `ApiException`으로 던지고 `GlobalExceptionHandler`가
  변환한다 — 11404(없는 신고)·11410(처리된 신고 재처리·동시 처리 패자)은
  `AdminReportServiceImpl.lockPendingReport`에서, 11420(미지원 status)·11421(page·size 범위 밖,
  오프셋 int 오버플로 포함)은 `getReports`에서 각각 404/409/400/400으로. 영상 축은
  moderation 이 던지는 3404(단건 확인의 없는 영상·DELETED, 승인의 방어적 영상 결측)와

  핸들러 밖 시큐리티 필터 체인 처리다: 무토큰은 `CustomAuthenticationEntryPoint`가
  `AuthErrorCode.UNAUTHENTICATED`(2403, HTTP 401)로, ADMIN 아닌 인증 사용자는
  `CustomAccessDeniedHandler`(M1 신설)가 공통 `ErrorCode.FORBIDDEN`(403)으로 직접
  `ApiResponseDto` JSON 을 써서 응답한다 — 컨트롤러에 도달하지 않는다.
- 빈 동작: `AdminReportServiceImpl.approve`는 단일 `@Transactional`이고
  `VideoModerationServiceImpl.blind`의 `@Transactional`은 REQUIRED 전파로 **기존 트랜잭션에
  합류**한다 — 새 트랜잭션이 아니므로 신고 종결과 영상 블라인드가 원자적으로 함께
