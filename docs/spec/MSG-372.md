# MSG-372: 격자 활발한 시간대 차트 재료 API

**Owner**: B

> 요구사항 정본: `docs/prd/MSG-372-prd.md` (상태 검토됨, 2026-08-13 사용자 승인).
> 이 스펙은 그 PRD의 FR-1 ~ FR-7(SRS 등재 ID: FR-MAP-09)에 "어떻게"만 붙인다.

## 개요

격자 하나를 지정하면 그 격자의 전역 공개 영상이 어느 시간대(KST 0시부터 23시)에 업로드됐는지를
24개 구간 개수로 돌려주는 조회 API를 추가한다. 지도 홈에서 칩(핫구역, 지역축제 등)이 활성일 때
격자 선택 패널의 "활발한 시간대" 차트가 이 응답을 그대로 그린다. 서버는 구간별 개수만 주고,
차트의 시각 형태와 칩 활성 판정은 클라이언트 몫이다(FR-7).

video 도메인 단독 변경이라 Owner B다. grid 패키지는 건드리지 않는다. 경로 접두사가
`/api/grids`여도 videos 테이블을 다루는 코드는 video 패키지에 두는 선례(GridVideoController,
MSG-127)를 그대로 따른다.

## 배경 · 목표

칩이 보여주는 콘텐츠는 전역(모든 사용자) 영상인데, 그 장소가 언제 활발한지를 보여줄 재료 API가
서버에 없다. 같은 패널의 전역 영상 카드와 숫자가 어긋나지 않는 시간대 분포 하나를 조회 한 번으로
제공하는 것이 목표다(PRD FR-2). 집계 윈도우는 전체 누적이다. 서비스 초기 데이터 희소성 때문이며,
최근 N일 윈도우는 별도 요구로 미룬다(FR-4).

## 성공 기준

- 격자 하나를 지정한 조회 한 번으로 24구간 분포가 온다. 어떤 격자든(공개 영상 0건, 존재하지 않는
  gridId 포함) 항상 0시부터 23시까지 24개 구간이 전부 있고 빈 구간은 0이다.
- 세는 기준이 격자 전역 영상 목록(`findGlobalVideos`)의 게이트[^1]와 글자 단위로 같다. 카드에
  보이는 영상은 차트에도 세어지고, 안 보이는 영상은 차트에도 없다.
- 시간대는 업로드 시각(`videos.created_at`, UTC 저장)을 KST로 변환해 뽑은 시(0~23)다.
- 삭제, 블라인드, 비공개 전환된 영상은 다음 조회부터 빠진다. 별도 캐시 없이 조회 시점 실시간
  판정이므로 자동 성립한다(FR-6).

## API 명세

### GET /api/grids/{gridId}/hourly-uploads

격자 전역 시간대 분포 조회. 기존 격자 상세 3종과 같은 `GridVideoController`에 동거한다.

- **인증**: 토큰 필수. 기존 격자 조회 관례 그대로 시큐리티 필터가 막고, 응답이 사용자별로 다르지
  않으므로 `AuthPrincipal` 파라미터는 받지 않는다(`/cover`, `/videos` 선례).
- **경로 변수**: `gridId` (예: `19422_9582`)
- **쿼리 파라미터**: 없음. 칩 상태를 파라미터로 받지 않는다(FR-7).

**성공 응답** (`SuccessResponse`, developCode 200):

```json
{
	"developCode": 200,
	"message": "성공",
	"data": {
		"gridId": "19422_9582",
		"hours": [
			{ "hour": 0, "count": 0 },
			{ "hour": 1, "count": 2 },
			{ "hour": 23, "count": 5 }
		]
	}
}
```

- `hours`는 항상 24개, `hour` 오름차순(0부터 23) 고정이다. 업로드가 없는 구간은 `count: 0`.
- 공개 영상이 하나도 없는 격자와 존재하지 않는 gridId는 실패가 아니라 전 구간 0인 정상
  응답이다(FR-5, 전역 영상 목록의 빈 페이지 정책과 동일).

**에러 케이스**: 신설 없음. 인증 실패는 공통 401뿐이다. VideoErrorCode에 상수를 추가하지 않는다.

**DTO** (video/dto, record + `@Schema`, `GridVideoPageResponseDto` 선례):

- `GridHourlyUploadResponseDto` 신규: `String gridId`, `List<HourlyUploadCountResponseDto> hours`
- `HourlyUploadCountResponseDto` 신규(별도 파일, 리스트 항목 분리 선례): `int hour`, `long count`
- 시각 타입 필드가 없어 `DtoTimeTypeGuardTest` 대상 필드는 없다. `*Dto` 네이밍은 지킨다.

## 도메인 로직

- **세는 대상 = 전역 공개 게이트 통과 영상 전부**. 상태가 ACTIVE이고 공개범위가 PUBLIC이며 처리
  상태가 READY인 영상만 센다. 소유자 분기가 없어 내 영상도 남의 영상과 똑같이 게이트로만
  판정된다(내 PRIVATE 영상은 나에게도 안 세어진다. 전역 영상 목록 MSG-237 §D1과 동일).
- **시간대 축 = 업로드 시각의 KST 시**. `created_at`은 타임존 없는 벽시계 저장[^2]이라 저장
  존(UTC, 호출자 바인딩)으로 해석한 뒤 KST로 변환해 시를 뽑는다. 잔디 재료
  `getUploadHistory`(MSG-362)와 같은 이중 `AT TIME ZONE` 패턴이다. 촬영 시각(recordedAt)은
  클라이언트 신고값이라 쓰지 않는다(PRD 각주 4).
  - **알려진 dev 한정 스큐**: dev의 psql 직접 시딩분은 KST 벽시계로 저장돼 있어(MSG-376 잔재)
    보정 티켓 MSG-379 완료 전까지 dev 차트에서 그 행만 9시간 밀려 보인다. prod·dev의 앱 경로
    저장은 UTC 실측 확인(MSG-376)이라 이 티켓에서 감사·백필은 하지 않는다.
- **24구간 채움은 서비스 몫**. 리포지토리는 업로드가 있는 시간대만 돌려주고(GROUP BY 결과),
  서비스가 `long[24]` 배열에 얹어 0시부터 23시까지 전 구간을 조립한다. SQL에서
  `generate_series`로 채우는 것보다 단순하고, 쿼리는 게이트 프래그먼트 비교가 쉬운 최소형으로
  남는다.
- 시각을 새로 만들지 않으므로 `Clock` 주입이 필요 없다.

## 데이터 모델

**변경 없음. 마이그레이션 없음.**

집계 쿼리(리포지토리 `VideoRepository`에 native로 추가, 프로젝션[^3] 인터페이스
`HourlyUploadProjection` 신규):

```sql
SELECT EXTRACT(HOUR FROM ((created_at AT TIME ZONE :storedZone) AT TIME ZONE 'Asia/Seoul'))::int AS "hour",
       COUNT(*) AS "count"
FROM videos
WHERE grid_id = :gridId
  AND status = 'ACTIVE' AND visibility = 'PUBLIC' AND processing_status = 'READY'
GROUP BY 1
ORDER BY 1
```

- WHERE의 게이트 줄은 `findGlobalCover`, `findGlobalVideos`와 **글자 단위로 같은 문자열**이어야
  한다(PRD 데이터 정합 요구). 리뷰에서 대조한다.
- `:storedZone`은 호출자가 `"UTC"`를 바인딩한다(`getUploadHistory` 선례, MSG-376 관례).
- **인덱스**: 기존 부분 인덱스[^4] `idx_videos_grid_popular` (grid_id, view_count DESC,
  created_at DESC, WHERE 절이 게이트와 동일)가 이 쿼리의 필터와 정확히 일치한다. `grid_id` 선두
  컬럼으로 그 격자의 게이트 통과 행만 몰아 읽으므로 신규 인덱스는 없다. 단일 격자의 행 수는
  소량이라 집계 비용도 무시할 수준이고, 지도 화면 계열 SLO(p95[^5] 300ms 미만, SRS
  NFR-PERF-01의 응답 목표를 이 조회까지 넓혀 적용하며 측정은 NFR-PERF-02 기준)를 만족한다.
  실행계획 실측은 구현 후 작업 로그에 남긴다(PRD 운영 요구).

```java

 * 영상을 업로드 시각(created_at)의 KST 시(0~23)로 접어 24구간 개수를 돌려준다. 집계 윈도우는

 */
GridHourlyUploadResponseDto getGridHourlyUploads(String gridId);
```

## 테스트 시나리오

한국어 테스트 메서드명 후보. 통합 테스트는 공유 로컬 DB를 쓰므로 시드 정리를 선행한다.

- `공개_영상의_업로드_시각이_KST_시간대로_접혀_집계된다`
- `응답은_항상_0시부터_23시까지_24구간이고_빈_구간은_0이다`
- `비공개_영상은_집계에서_빠진다` (PRIVATE, FRIENDS 모두)
- `삭제되거나_블라인드된_영상은_집계에서_빠진다`
- `인코딩_미완_영상은_집계에서_빠진다`
- `다른_사용자의_공개_영상도_함께_센다` (전역 기준 확인)
- `내_비공개_영상은_나에게도_세어지지_않는다` (소유자 분기 부재 확인)
- `UTC_저장_시각이_KST로_변환되어_경계_시간대에_바르게_접힌다`
  (예: created_at 15:30 UTC는 KST 0시 구간이다. 9시간 스큐 검출용)
- `공개_영상이_없는_격자는_전_구간_0인_정상_응답이다`
- `존재하지_않는_gridId도_전_구간_0인_정상_응답이다`
- `게이트_프래그먼트가_전역_영상_목록과_글자_단위로_같다`
  (선택. 쿼리 문자열 상수 비교가 과하면 리뷰 체크리스트로 대체)

## 미해결 질문

없음. PRD의 미해결 항목(셀 선택 패널 차트 형태의 디자인 재확인)은 서버 재료(24구간 개수)에
영향이 없어 이 스펙에서 결정할 것이 없다.

---

[^1]: 전역 공개 게이트: 전역 노출 경로가 공유하는 영상 필터. 살아 있고(ACTIVE) 전체 공개(PUBLIC)이며 처리 완료(READY)인 영상만 통과한다. 이 조건이 화면마다 달라지면 같은 격자의 카드 개수와 차트 합이 어긋나므로, 모든 전역 조회에서 글자 단위로 같은 SQL 조각을 쓴다.
[^2]: 벽시계 저장: 타임존 정보 없이 날짜와 시각 숫자만 저장하는 방식(PostgreSQL TIMESTAMP WITHOUT TIME ZONE). 이 프로젝트는 "저장된 숫자는 UTC 시각"이라는 관례(MSG-376)로 해석하므로, 읽을 때 UTC로 해석한 뒤 원하는 시간대로 변환한다.
[^3]: 프로젝션: JPA에서 엔티티 전체가 아니라 필요한 컬럼 몇 개만 담아 받는 조회 결과 인터페이스. 쿼리의 컬럼 별칭과 getter 이름을 맞추면 스프링이 자동으로 매핑한다.
[^4]: 부분 인덱스: WHERE 조건을 붙여 그 조건을 만족하는 행만 담는 인덱스. 게이트 통과 영상만 담고 있어 게이트 조건이 같은 조회에서 테이블 전체를 읽지 않고 답할 수 있다.
[^5]: p95: 요청 100건 중 느린 쪽 5건을 제외한 나머지가 이 시간 안에 끝난다는 백분위 응답 시간 지표. 평균과 달리 느린 꼬리를 잡아낸다.
