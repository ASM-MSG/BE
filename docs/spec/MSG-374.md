# MSG-374: 지도 홈 줌아웃 집계에 영상 수와 현재 행정동 더하기

**Owner**: 공동 (grid, region 변경은 A가 주도하고, friend 쪽은 API 설명 문구 정정 한 건만 B 몫이다.
`GridQueryService` 계약이 늘어나므로 리뷰 때 상대 팀원 확인이 필요하다)

> 요구사항 정본: `docs/prd/MSG-374-prd.md` (상태 검토됨, 2026-08-11 사용자 승인).
> 기존 집계 설계 정본: `docs/spec/MSG-356.md`. 무귀속 버킷, 이름 토큰 분해, 대표 좌표 평균,
> 검증 순서는 그 문서의 결정을 그대로 이어받고 다시 논의하지 않는다.

## 개요

지도를 축소했을 때 쓰는 기존 집계 조회(`GET /api/grids/aggregation`, MSG-356)에 두 가지를 더한다.
묶음마다 내 영상 수를 함께 세어 사이드 패널 헤더의 "이 지역 격자 5개, 영상 355개" 뒤쪽 숫자를
만들 수 있게 하고, 동 단위 조회에 한해 뷰포트[^1] 중심이 속한 현재 행정동을 응답에 함께 담는다.

이 티켓은 기존 개인 기준 집계를 넓히는 작업이다. 2026-08-11 오전에 지도 홈을 전역 기준으로
바꾸려던 방향은 같은 날 번복됐고(SRS FR-MAP-05 폐기, FR-MAP-01 복원), 지도 홈은 내 격자가
디폴트다. 전역 데이터는 상단 칩을 켰을 때만 나온다(SRS FR-MAP-07). 전역 기준 집계는 만들지 않는다.

## 배경 · 목표

사이드 패널 헤더는 격자 수와 영상 수를 나란히 보여주는데 지금 집계는 격자 수만 센다. 그리고
네이버 지도를 참조한 화면 결정(SRS FR-MAP-06)으로 동 단위 시야에서는 화면 라벨과 "이 동네 보기"
버튼이 지도 이동을 따라 갱신돼야 하는데, 그 이름을 얻으려면 조회마다 역지오코딩[^2]을 따로
호출해야 한다.

목표는 두 재료를 기존 조회 한 번으로 끝내는 것이다. 영상 수는 이미 격자마다 저장돼 있는 값을
합하고, 현재 행정동은 이미 있는 점 판정을 재사용한다. 새 테이블도 새 판정 규칙도 만들지 않는다.

## 성공 기준

1. 동, 구, 시 어느 단위로 조회해도 묶음마다 격자 수와 영상 수가 함께 온다 (FR-1).
2. 뷰포트의 격자별 영상 수를 더한 값과 집계의 영상 수 합이 일치하고, 단위를 바꿔 묶어도 그 합이
   달라지지 않는다 (FR-4).
3. 같은 격자를 도감 화면에서 볼 때와 이 집계에 반영될 때 세는 규칙이 같다. 삭제로만 줄고 블라인드로는
   줄지 않으며 비공개와 인코딩 중 영상도 포함한다 (FR-5, SRS FR-MOD-08).
4. 동 단위 응답에만 현재 행정동이 실리고, 구와 시 단위 응답에는 실리지 않는다 (FR-2).
5. 뷰포트 중심이 바다이거나 서비스 좌표 범위 밖이어도 조회는 200이고 현재 행정동만 빈 값이다 (FR-3).
6. 친구 집계 응답(`GET /api/friends/{userId}/grids/aggregation`)의 JSON이 필드 하나까지 지금과
   같다 (FR-6).
7. 영상 수가 int 범위를 넘어도 잘리지 않는다 (FR-5a).

## API 명세

### 내 도감 집계 조회 (응답 형태 변경)

`GET /api/grids/aggregation`

요청 파라미터는 지금과 같다(`swLat`, `swLng`, `neLat`, `neLng`, `unit`). 단위별 bbox 상한
(DONG 1도, SIGUNGU 4도, SIDO 10도)과 대소문자 무관 `unit` 파싱도 그대로다.

**응답이 배열에서 객체로 바뀐다. FE 계약 변경이므로 배포 전에 FE와 맞춘다.**

```json
{
	"developCode": 200,
	"message": "성공",
	"data": {
		"currentRegion": { "regionCode": "2611051500", "name": "동구 초량1동" },
		"items": [
			{ "regionCode": "2623058000", "name": "부전2동", "lat": 35.162, "lng": 129.065, "count": 31, "videoCount": 94 },
			{ "regionCode": "2623059000", "name": "전포동", "lat": 35.155, "lng": 129.071, "count": 12, "videoCount": 20 },
			{ "regionCode": null, "name": null, "lat": 35.101, "lng": 129.032, "count": 2, "videoCount": 3 }
		]
	}
}
```

| 필드 | 타입 | 의미 |
|---|---|---|
| `currentRegion` | 객체 또는 null | 뷰포트 중심이 속한 행정동. `unit=DONG`일 때만 값이 들어오고 구와 시 단위에서는 항상 null이다 |
| `currentRegion.regionCode` | String | 행정동 코드[^3] 10자리 |
| `currentRegion.name` | String | 서버가 조립한 한 줄 이름 ("동구 초량1동"). 화면은 그대로 표시만 한다 |
| `items` | 배열 | 묶음 목록. 정렬은 지금처럼 `regionCode` 오름차순이고 미판정 항목이 마지막이다 |
| `items[].videoCount` | long | 그 묶음 안 내 격자에 내가 올린 영상 수 (신규) |

`items[]`의 나머지 필드(`regionCode`, `name`, `lat`, `lng`, `count`)는 의미도 값도 지금과 같다.
점령 격자가 없으면 `items`는 빈 배열이고, 이때도 `currentRegion`은 판정해서 담는다 (FR-7).

`videoCount`가 long인 이유는 이 값이 격자 하나의 수가 아니라 여러 격자를 합한 수이기 때문이다
(FR-5a). 도감 요약의 영상 총합(`CollectionSummaryView.totalVideoCount`)이 이미 long이고,
DB에서도 `SUM(integer)`는 bigint[^4]로 나온다. 프로젝션에서 DTO까지 어느 계층에서도 int로 좁히지
않는다. 격자 하나의 값인 `CollectionGridResponseDto.videoCount`가 Integer인 것은 이번 값과 다른
자리라서 기준으로 삼지 않는다.

계층별 타입을 못 박아 둔다. `RegionAggregateProjection`에 `Long getVideoCount()`를 더한다
(JPA 인터페이스 프로젝션이라 원시형이 아닌 래퍼로 받는다. 기존 `Long getCount()`와 같은 방식이다).
서비스가 뷰로 옮길 때 `long`으로 풀고, DTO도 `long`으로 받는다. 널 방어는 두지 않는다. 그룹마다
행이 최소 하나이고 `user_grids.video_count`가 NOT NULL이라 `SUM`이 널이 되는 경로가 없기 때문이며,
같은 이유로 기존 `COUNT(*)`도 널 방어 없이 풀고 있다. 반대로 기존 `count`를 long으로 넓히는 변경은
하지 않는다. 이번 범위가 아니고 응답 계약이 바뀐다.

에러 케이스는 지금 그대로이고 신규 코드는 0건이다.

| developCode | 조건 |
|---|---|
| `4401 INVALID_VIEWPORT` | bbox 파라미터 누락, 뒤집힌 bbox, WGS84 범위 밖 좌표(NaN과 무한대 포함) |
| `4402 VIEWPORT_TOO_LARGE` | 단위별 bbox 상한 초과 |
| `4405 INVALID_AGGREGATION_UNIT` | `unit` 누락 또는 미지원 값 |

현재 행정동 판정이 던질 수 있는 `6400 INVALID_COORDINATE`는 응답으로 나가지 않는다 (아래 도메인 로직).

### 친구 도감 집계 조회 (동작 불변)

`GET /api/friends/{userId}/grids/aggregation`의 파라미터, 응답, 에러는 전부 그대로다. 응답은
여전히 배열이고 항목에 `videoCount`가 없다 (FR-6).

다만 이 조회의 `@Operation` 설명이 "파라미터, 응답, 에러가 내 집계 조회와 완전히 같다"고 적고
있는데, 내 집계 응답이 겉면을 얻고 항목에 영상 수가 붙으면 그 문장이 거짓이 된다. 문장을
"묶음 항목의 공통 필드는 내 집계 조회와 같고, 응답 겉면과 영상 수는 이 조회에 없다"는 취지로
정정한다. 코드 동작과 응답 스키마는 건드리지 않는다. 이 한 건이 Owner B 몫이다.

## 도메인 로직

### 영상 수: user_grids.video_count 합산

집계 쿼리가 이미 `user_grids`를 조인하고 있고 그 행이 격자별 영상 수를 들고 있다. 따라서
`SUM(ug.video_count)` 한 줄을 출력에 더하면 끝이다. `videos` 테이블은 조인하지 않는다.
`GridQueryService`가 videos에 접근하지 않는다는 기존 계약 주석도 그대로 성립한다.

이 방식을 고른 이유는 정합이 자동으로 맞기 때문이다. 도감 요약의 영상 총합도 같은 컬럼의 SUM이고
격자 목록의 영상 수도 같은 컬럼이라, 같은 격자를 어느 화면에서 보든 같은 값이 나온다. 블라인드가
영상 수를 줄이지 않는다는 계약(SRS FR-MOD-08)과 삭제 시에만 줄어드는 규칙도 이 컬럼의 증감 규칙이
그대로 물려받는다. 여기에 상태별 필터링(예: ACTIVE만 세기)을 새로 넣으면 두 화면의 숫자가 갈라지므로
넣지 않는다.

정합의 뜻을 한 번 못 박아 둔다. 도감 요약의 총합과 이 집계의 총합이 같은 값이 되는 것이 아니다.
도감 요약은 내 전체를 세고 이 집계는 화면 범위만 센다. 같아야 하는 것은 세는 규칙과 격자 하나에
매겨진 영상 수이며, 그래서 검증도 "같은 뷰포트의 격자별 값을 더한 것과 집계 값이 같다"로 한다.

행 중복 걱정은 없다. `grids`는 PK 조인이고 `regions`는 LEFT JOIN이지만 역시 PK 조인이라 점령 격자
한 행이 결과에서 한 번만 세어진다. 그룹마다 최소 한 행이 있고 `video_count`가 NOT NULL이라 SUM이
NULL이 되는 경로도 없어 COALESCE를 두지 않는다.

### 현재 행정동: 뷰포트 중심의 점 판정 재사용

중심 좌표는 `((swLat + neLat) / 2, (swLng + neLng) / 2)`다. 판정은 `RegionQueryService.resolveByPoint`를
그대로 호출한다. 새 판정 로직을 만들지 않는다. 저장 라벨(`grids.region_code`)을 쓸 수 없는 이유는
중심점이 격자에 걸린 임의의 점이라 저장된 값이 없기 때문이며, 이것이 실시간 조회 경로에서 공간
연산을 하지 않는다는 원칙(SRS FR-REGION-12)의 유일한 예외다. 비용은 동 단위 요청당 점 하나이고
`idx_regions_boundary`(GIST[^5]) 위 단건 조회다.

이름 조립은 서버가 한다. `regions.region_name`이 "부산광역시 동구 초량1동" 전체 경로 형식이므로
공백으로 나눈 마지막 두 토큰을 붙여 "동구 초량1동"을 만든다. MSG-356에서 확인한 대로 원천 데이터
전수가 3토큰이며, 혹시 토큰이 3개 미만인 행이 들어오면 전체 이름을 그대로 내려 응답이 깨지지 않게
한다. 조립 위치는 grid 서비스의 private 헬퍼로 둔다. 소비처가 하나뿐이라 region 도메인에 공용 API를
새로 파지 않고, 두 번째 소비처가 생기면 그때 옮긴다.

동 단위가 아니면 판정 자체를 호출하지 않는다. 구와 시 시야에서는 화면이 이 값을 쓰지 않으므로
불필요한 공간 연산을 돌릴 이유가 없다.

### 6400 흡수 지점

`resolveByPoint`는 서비스 좌표 범위(한국) 밖 좌표에 `RegionErrorCode.INVALID_COORDINATE`(6400)를
던진다. 이 집계 조회는 화면 중심이 바다이거나 한국 밖이어도 실패하면 안 되므로(FR-3), 호출 앞에
`KoreaCoordinates.isOutOfService(lat, lon)` 가드를 두고 밖이면 호출하지 않고 현재 행정동을 null로
둔다. 흡수 지점은 `GridQueryServiceImpl`의 현재 행정동 헬퍼 한 곳이다.

이 가드가 완전한 이유는 6400을 던지는 술어가 바로 그 `isOutOfService`이기 때문이다. 같은 판정을
앞에서 하면 예외 경로 자체가 열리지 않는다. 같은 파일의 `resolveRegionName`(MSG-349)과
`RegionStatsQueryServiceImpl.findStatByGrid`가 이미 쓰고 있는 선례를 그대로 따른다. try/catch로
`ApiException`을 삼키는 방식은 쓰지 않는다. 관계없는 실패까지 조용히 먹어 장애를 가리기 때문이다.

포함 행정동이 없는 경우(바다)는 원래부터 예외가 아니라 빈 결과라 그대로 null이 된다.

### 검증 순서와 세는 범위

파라미터 검증은 지금 순서 그대로다. bbox 파싱과 `unit` 파싱이 먼저이고, 좌표 유효성과 뒤집힘과
상한 검사가 그 다음이며, 현재 행정동 판정은 맨 뒤다. 잘못된 요청은 현재 행정동 판정에 도달하기
전에 4401이나 4402나 4405로 거절된다. 중심 좌표를 계산하는 시점에는 네 좌표가 이미 유한하고
WGS84 범위 안임이 보장된다.

세는 범위는 손대지 않는다. `GridEncoder.viewportRange`가 화면을 덮는 보수적 범위라 가장자리에서
화면 밖 셀이 소량 포함되는데, MSG-347이 무해로 판정했고 개별 조회와 같은 범위를 써야 총합이
어긋나지 않는다(MSG-356 FR-3). 정밀 포함 판정을 새로 넣지 않는다.

### 집계 쿼리 변경분

기존 native 쿼리에 출력 한 줄만 추가한다.

```sql
SELECT
	substring(g.region_code FROM 1 FOR :codeLen)     AS "regionCode",
	MIN(split_part(r.region_name, ' ', :nameToken))  AS "name",
	AVG(ST_Y(g.center_geom::geometry))               AS "lat",
	AVG(ST_X(g.center_geom::geometry))               AS "lng",
	COUNT(*)                                         AS "count",
	SUM(ug.video_count)                              AS "videoCount"   -- 신규
FROM user_grids ug
JOIN grids g ON g.grid_id = ug.grid_id
LEFT JOIN regions r ON r.region_code = g.region_code
WHERE ug.user_id = :userId
	AND g.grid_y BETWEEN :minY AND :maxY
	AND g.grid_x BETWEEN :minX AND :maxX
GROUP BY 1
ORDER BY 1 NULLS LAST
```

`GROUP BY 1`과 `ORDER BY 1`의 출력 서수 표기는 그대로 둔다. 같은 substring 식을 두 자리에 쓰면
`:codeLen` 바인딩이 서로 다른 파라미터 자리가 되어 PostgreSQL이 두 식을 같은 것으로 보지 못하고
거절한다는 실측 이유가 리포지토리 주석에 남아 있다(MSG-356 구현 결정). 그 결정을 다시 논의하지 않는다.

### 성능

스캔 대상이 늘지 않는다. `SUM`은 이미 읽고 있는 `user_grids` 행의 컬럼 하나를 같은 그룹에서 더할
뿐이라 새 테이블도 새 인덱스도 관여하지 않고, 실행계획[^6]의 노드 구성도 그대로다(HashAggregate
아래 Hash Left Join과 Hash Join). MSG-356 실측이 사용자 1인 1만 행 시드의 전국 시도 집계에서
Execution 10.872ms였고 SLO(p95 300ms) 대비 27배 여유였으므로, 집계 함수 하나 추가로 그 여유가
사라질 여지가 없다.

그래도 PRD 비기능이 요구한 대로 채택 전에 확인한다. 다만 무엇을 확인하는 것인지 성격을 분명히
해 둔다. 기존 `GridAggregationExplainBenchmark`(`GRID_BENCHMARK=true` 게이트)로 도는 EXPLAIN은
**퇴행 점검**이지 SLO 판정이 아니다. 로컬에서 한 번 잰 실행 시간은 부하도 동시성도 네트워크도
없는 값이라 그것들을 더해 p95를 말할 수 없다. 새 하네스는 만들지 않는다.

EXPLAIN으로 확인할 것은 시간이 아니라 성질 세 가지다.

| 확인 대상 | 통과 조건 |
|---|---|
| 집계 SQL (SIDO와 DONG 각각) | 계획에 `videos` 등 새 테이블 접근이 없고, 읽는 관계와 행 수가 `SUM` 추가 전과 같다 |
| 중심점 판정 SQL | `regions`를 순차 스캔하지 않는다(공간 인덱스를 타는 계획이면 형태는 무엇이든 통과) |
| 두 SQL 모두 | Execution이 같은 시드의 변경 전 실측 대비 자릿수가 바뀌지 않는다 |

계획의 노드 구성을 특정 형태로 못 박지 않는다. 데이터가 늘면 플래너가 더 나은 계획을 고르는 것이
정상이고, 형태를 기준으로 삼으면 더 빠른 계획이 실패로 판정된다. 실측값은 작업 로그에 남긴다.

SLO(p95 300ms) 자체를 다시 판정해야 한다면 그것은 엔드포인트 부하 측정의 일이고 `load-test/`
하네스가 담당한다. 이번 변경은 그 재측정을 요구할 만한 성격이 아니라고 본다. 읽는 행이 그대로이고
집계 함수 하나와 요청당 점 판정 하나가 붙을 뿐이며, 그 점 판정은 이미 단독 API로 서비스 중인
쿼리와 같기 때문이다. 위 퇴행 점검에서 읽는 행이 늘거나 자릿수가 바뀌는 것이 나오면 그때는 전제가
틀린 것이므로 구현을 진행하지 말고 사용자에게 올려 부하 측정 여부를 정한다.

## 데이터 모델

## 계약 변경

**`GridQueryService`(A 제공, B 소비) 계약이 늘어난다. 리뷰 시 상대 팀원 확인 필수.**

1. 기존 메서드 `getOccupiedAggregatesInViewport(long, ViewportBounds, RegionUnit)`는 시그니처
   그대로 남는다. 친구 집계(`FriendServiceImpl`)가 계속 이 메서드를 쓴다.
2. 지도 홈 전용 메서드를 하나 더한다.

```java
/**
 * 뷰포트 집계에 현재 행정동을 더해 돌려준다 (MSG-374). 지도 홈 전용이라 친구 집계는 위 메서드를 계속 쓴다.
 * currentRegion 은 unit 이 DONG 일 때만 판정하며, 뷰포트 중심이 바다이거나 서비스 범위 밖이면 null 이다
 * (판정의 INVALID_COORDINATE 를 밖으로 내보내지 않는다).
 */
GridAggregationView getOccupiedAggregatesWithCurrentRegion(long userId, ViewportBounds bounds, RegionUnit unit);
```

3. 반환 뷰 `RegionAggregateView`에 `long videoCount`가 추가된다. 두 조회가 같은 리포지토리 쿼리
   하나를 공유하므로 내부 뷰는 나누지 않고, 친구 응답에서 값이 새지 않는 것은 응답 DTO 층에서
   보장한다. `RegionAggregateResponseDto`가 지금처럼 이 필드를 매핑하지 않으면 친구 JSON은 불변이다
   (FR-6). `FriendServiceImpl`은 뷰를 그대로 통과시키므로 코드 변경이 없다.

동반 신규 타입 (모두 A 소유):

```java
// com.msg.fillmap.grid.service
public record GridAggregationView(CurrentRegionView currentRegion, List<RegionAggregateView> items) {
}

public record CurrentRegionView(String regionCode, String name) {
}
```

HTTP 응답 DTO는 컨트롤러 책임 관례대로 `com.msg.fillmap.grid.dto`에 둔다. 겉면
`GridAggregationResponseDto(CurrentRegionResponseDto currentRegion, List<GridAggregationItemResponseDto> items)`,
항목 `GridAggregationItemResponseDto(String regionCode, String name, double lat, double lng, int count, long videoCount)`,
현재 행정동 `CurrentRegionResponseDto(String regionCode, String name)` 세 개가 신규다. 기존
`RegionAggregateResponseDto`는 친구 조회 전용으로 남으며 필드가 바뀌지 않는다.

## 미해결 질문

없다. PRD의 열린 항목(성능 실측 미달 시 대응)은 위 성능 절의 근거와 벤치 재실행 계획으로 닫는다.
사이드 패널 영상 카드 3장의 출처는 PRD가 이 티켓 밖으로 명시한 별도 논의라 여기서 다루지 않는다.

[^1]: 뷰포트: 지도 화면에 지금 보이는 사각형 범위. 남서와 북동 두 모서리 좌표 네 값으로 서버에 전달한다.
[^2]: 역지오코딩: 좌표를 사람이 읽는 주소나 행정 구역 이름으로 되돌리는 조회. 여기서는 점 하나가
    어느 행정동 경계 안에 있는지를 판정하는 것이다.
[^3]: 행정동 코드: 행정안전부의 10자리 행정동 식별 코드. 앞 2자리가 시도, 앞 5자리가 시군구를 가리켜
    코드를 자르는 것만으로 상위 단위 묶음이 된다.
[^4]: bigint: PostgreSQL의 64비트 정수 타입. int(32비트) 컬럼을 SUM 하면 결과가 자동으로 이 타입이
    되며, Java에서는 long으로 받는다.
[^5]: GIST: PostGIS가 도형 검색에 쓰는 인덱스 종류. 점이 어느 도형 안에 있는지를 전수 비교 없이
    좁혀 준다.
[^6]: 실행계획: 데이터베이스가 쿼리를 어떤 순서와 방법으로 처리할지 정한 계획. EXPLAIN으로 출력해
    스캔 방식과 소요 시간을 확인한다.
