# MSG-374: 지도 홈 집계 응답에 현재 동네 싣기

**Owner**: 공동 (grid, region 변경은 A가 주도하고, friend 쪽은 API 설명 문구 정정 한 건만 B 몫이다.
`GridQueryService` 계약이 늘어나므로 리뷰 때 상대 팀원 확인이 필요하다)

> 요구사항 정본: `docs/prd/MSG-374-prd.md` (상태 검토됨, 2026-08-12 동 전체 기준 반영본).
> 기존 집계 설계 정본: `docs/spec/MSG-356.md`. 무귀속 버킷, 이름 토큰 분해, 대표 좌표 평균,
> 검증 순서는 그 문서의 결정을 그대로 이어받고 다시 논의하지 않는다.

## 개요

지도 홈 사이드 패널이 쓰는 재료 세 가지, 곧 지역명("부전동")과 "이 지역 격자 5개 · 영상 355개"의
두 숫자를 기존 집계 조회(`GET /api/grids/aggregation`, MSG-356)가 함께 내려 주게 한다. 패널은
네이버 지도처럼 **뷰포트[^1] 중심이 속한 동 하나**를 기준으로 서므로, 세 값 모두 그 동을 가리킨다.
두 숫자는 화면에 걸친 범위가 아니라 **그 동 전체**를 센다.

묶음 목록(마커)은 손대지 않는다. 마커는 지역명과 격자 수만 표시하므로 묶음마다 영상 수를 붙일
자리가 없다(FR-6). 기존 집계 쿼리도 그대로 두고, 새 재료는 조회 두 번을 옆에 붙여 만든다.

이 티켓은 기존 개인 기준 집계를 넓히는 작업이다. 2026-08-11 오전에 지도 홈을 전역 기준으로
바꾸려던 방향은 같은 날 번복됐고(SRS FR-MAP-05 폐기, FR-MAP-01 복원), 지도 홈은 내 격자가
디폴트다. 전역 데이터는 상단 칩을 켰을 때만 나온다(SRS FR-MAP-07). 전역 기준 집계는 만들지 않는다.

## 배경 · 목표

패널 지역명과 두 숫자를 주는 조회가 지금 없다. 좌표를 동 이름으로 바꾸려면 역지오코딩[^2]을 따로
불러야 하고, 그 동에서 내가 점령한 격자 수와 올린 영상 수는 어느 API도 주지 않는다. 패널 하단의
"부전동 장소 불러오기" 버튼(피그마 지도 홈 default 노드 `14357:18822`, `fab-load-places`)도 같은
이름을 쓴다.

세는 범위를 동 전체로 잡은 것이 이 티켓의 중심 결정이다(2026-08-12 확정, SRS FR-MAP-06). 화면
범위로 세면 지도를 조금만 밀어도 숫자가 흔들리는데, 패널은 "이 동네가 어떤 곳인가"를 말하는 자리라
같은 동 안에서는 값이 고정되는 편이 맞다. 이 결정 하나로 뷰포트와 무관한 카운트가 필요해졌고, 대신
기존 집계 쿼리는 건드릴 일이 없어졌다.

목표는 재료를 기존 조회 한 번으로 끝내는 것이다. 동 판정은 이미 있는 점 판정을 재사용하고, 두
숫자는 격자에 저장된 행정동 라벨로 거른다. 새 테이블도 새 판정 규칙도 만들지 않는다.

## 성공 기준

1. 동, 구, 시 어느 단위로 조회해도 응답에 현재 동네가 실린다. 축척도 가리지 않는다 (FR-1, FR-4).
2. 현재 동네의 격자 수와 영상 수는 그 동 전체를 센다. 화면 밖의 내 격자도 그 동이면 포함되고,
   화면에 걸쳤어도 다른 동이면 빠진다. 같은 동 안에서 지도를 움직여도 값이 변하지 않는다 (FR-2).
3. 이름은 동 이름 한 토큰이다. 패널 지역명과 버튼 라벨에 그대로 들어가는 값이다 ("부전동", FR-1).
4. 같은 격자를 도감 화면에서 볼 때와 이 숫자에 반영될 때 세는 규칙이 같다. 삭제로만 줄고
   블라인드로는 줄지 않으며 비공개와 인코딩 중 영상도 포함한다 (FR-5, SRS FR-MOD-08).
5. 뷰포트 중심이 바다이거나 서비스 좌표 범위 밖이어도 조회는 200이고 현재 동네만 빈 값이다 (FR-3).
6. 그 동에 점령 격자가 하나도 없어도 오류가 아니다. 이름과 함께 0이 온다 (FR-8).
7. 묶음 목록의 항목은 필드도 값도 지금과 같다 (FR-6).
8. 친구 집계 응답(`GET /api/friends/{userId}/grids/aggregation`)의 JSON이 필드 하나까지 지금과
   같다 (FR-7).
9. 영상 수가 int 범위를 넘어도 잘리지 않는다 (FR-5a).

## API 명세

### 내 도감 집계 조회 (응답 겉면 변경)

`GET /api/grids/aggregation`

요청 파라미터는 지금과 같다(`swLat`, `swLng`, `neLat`, `neLng`, `unit`). 단위별 bbox 상한
(DONG 1도, SIGUNGU 4도, SIDO 10도)과 대소문자 무관 `unit` 파싱도 그대로다.

**응답이 배열에서 객체로 바뀐다. FE 계약 변경이므로 배포 전에 FE와 맞춘다.**

```json
{
	"developCode": 200,
	"message": "성공",
	"data": {
		"currentRegion": {
			"regionCode": "2623058000",
			"name": "부전2동",
			"gridCount": 5,
			"videoCount": 355
		},
		"items": [
			{ "regionCode": "2623058000", "name": "부전2동", "lat": 35.162, "lng": 129.065, "count": 31 },
			{ "regionCode": "2623059000", "name": "전포동", "lat": 35.155, "lng": 129.071, "count": 12 },
			{ "regionCode": null, "name": null, "lat": 35.101, "lng": 129.032, "count": 2 }
		]
	}
}
```

| 필드 | 타입 | 의미 |
|---|---|---|
| `currentRegion` | 객체 또는 null | 뷰포트 중심이 속한 행정동. 축척과 `unit`에 관계없이 판정한다. 중심이 바다이거나 서비스 범위 밖일 때만 null |
| `currentRegion.regionCode` | String | 행정동 코드[^3] 10자리 |
| `currentRegion.name` | String | 동 이름 한 토큰 ("부전2동"). 화면이 패널 지역명과 "부전2동 장소 불러오기" 버튼 라벨에 그대로 넣는다 |
| `currentRegion.gridCount` | int | **그 동 전체**에서 내가 점령한 격자 수. 뷰포트와 무관하다 |
| `currentRegion.videoCount` | long | **그 동 전체**에서 내 격자에 내가 올린 영상 수. 뷰포트와 무관하다 |
| `items` | 배열 | 묶음 목록. 항목 필드와 정렬(`regionCode` 오름차순, 미판정 마지막)이 지금과 같다 |

`items[]`는 통째로 불변이다(FR-6). 마커에 영상 수를 붙이지 않는 이유는 마커가 지역명과 격자 수만
표시하기 때문이고, 패널이 쓰던 영상 수는 이제 `currentRegion`이 준다.

뷰포트에 점령 격자가 없으면 `items`는 빈 배열이고, 이때도 중심이 한국 안이면 `currentRegion`은
판정해서 담는다. 중심 동에 내 격자가 없으면 두 숫자가 0이다 (FR-8).

두 자리는 서로 독립이다. 중심 동에 내 격자가 0개여도 같은 화면의 이웃 동에 내 격자가 있으면
`items`는 비어 있지 않고, 반대로 `items`가 비어 있어도 `currentRegion`은 이름을 담는다.
세는 범위가 다르기 때문이며(뷰포트 대 동 전체), 한쪽이 비었다고 다른 쪽을 비우지 않는다.

`videoCount`가 long인 이유는 이 값이 격자 하나의 수가 아니라 동 하나를 합한 수이기 때문이다
(FR-5a). 도감 요약의 영상 총합(`CollectionSummaryView.totalVideoCount`)이 이미 long이고,
DB에서도 `SUM(integer)`는 bigint[^4]로 나온다. 프로젝션에서 DTO까지 어느 계층에서도 int로 좁히지
않는다. `gridCount`가 int인 것은 한 행정동의 격자 수라 상한이 행정동 면적으로 묶여 있어서다
(전국 최대 행정동도 100m 격자로 int를 넘지 않는다).

에러 케이스는 지금 그대로이고 신규 코드는 0건이다.

| developCode | 조건 |
|---|---|
| `4401 INVALID_VIEWPORT` | bbox 파라미터 누락, 뒤집힌 bbox, WGS84 범위 밖 좌표(NaN과 무한대 포함) |
| `4402 VIEWPORT_TOO_LARGE` | 단위별 bbox 상한 초과 |
| `4405 INVALID_AGGREGATION_UNIT` | `unit` 누락 또는 미지원 값 |

현재 동네 판정이 던질 수 있는 `6400 INVALID_COORDINATE`는 응답으로 나가지 않는다 (아래 도메인 로직).

### 친구 도감 집계 조회 (동작 불변)

`GET /api/friends/{userId}/grids/aggregation`의 파라미터, 응답, 에러는 전부 그대로다. 응답은
여전히 배열이고 겉면이 없다 (FR-7). 친구 도감이 현재 동네를 요구한 적이 없고, 이번에 묶음 항목도
바뀌지 않아 이 조회는 코드 변경 없이 불변이다.

다만 이 조회의 `@Operation` 설명이 "파라미터, 응답, 에러가 내 집계 조회와 완전히 같다"고 적고
있는데, 내 집계 응답이 겉면을 얻으면 그 문장이 거짓이 된다. 문장을 "묶음 항목은 내 집계 조회와
같고, 응답 겉면(현재 동네)은 이 조회에 없다"는 취지로 정정한다. 코드 동작과 응답 스키마는
건드리지 않는다. 이 한 건이 Owner B 몫이다.

## 도메인 로직

### 현재 동네 판정: 뷰포트 중심의 점 판정 재사용

중심 좌표는 `((swLat + neLat) / 2, (swLng + neLng) / 2)`다. 판정은 `RegionQueryService.resolveByPoint`를
그대로 호출한다. 새 판정 로직을 만들지 않는다. 저장 라벨(`grids.region_code`)을 쓸 수 없는 이유는
중심점이 격자에 걸린 임의의 점이라 저장된 값이 없기 때문이며, 이것이 실시간 조회 경로에서 공간
연산을 하지 않는다는 원칙(SRS FR-REGION-12)의 예외다. 비용은 요청당 점 하나이고
`idx_regions_boundary`(GIST[^5]) 위 단건 조회다. 같은 파일의 `resolveRegionName`(MSG-349)이
이미 같은 예외를 쓰고 있다.

이름은 서버가 잘라 준다. `regions.region_name`이 "부산광역시 부산진구 부전2동" 전체 경로 형식이므로
공백으로 나눈 **마지막 한 토큰**을 쓴다. 패널 지역명과 버튼 라벨이 "부전2동"이라 앞에 시나 구가
붙으면 화면과 어긋난다. 토큰이 하나뿐인 행이 들어오면 전체 이름을 그대로 내려 응답이 깨지지 않게
한다. 자르는 위치는 grid 서비스의 private 헬퍼로 둔다. 소비처가 하나뿐이라 region 도메인에 공용
API를 새로 파지 않고, 두 번째 소비처가 생기면 그때 옮긴다.

동명이인 걱정은 이 자리에 없다. "중앙동"처럼 여러 시군구에 같은 이름이 있어도 이 값은 지금 보고
있는 화면의 라벨이라 사용자가 어느 동네를 보는지 이미 알고 있고, 식별이 필요한 쪽은 `regionCode`가
따로 실린다.

### 축척과 단위를 가리지 않는 이유

현재 동네는 `unit`이 무엇이든, 뷰포트가 얼마나 넓든 항상 판정한다(FR-4). 패널은 마커가 뜨는
줌아웃 시야에서도 그대로 떠 있고 기준이 여전히 중심 동 하나이기 때문이다. 초기 설계에는 1km 이하
시야에서만 판정하는 상한이 있었는데, 그때는 이 값의 유일한 소비처가 "장소 불러오기" 버튼이라고
봤기 때문이다. 패널 지역명과 두 숫자가 같은 값을 쓰게 되면서 상한이 사라졌다. 1km는 버튼 노출을
가르는 화면 규칙으로 남고 클라이언트가 판정한다(SRS FR-MAP-08). 서버에는 그 상수를 두지 않는다.

### 동 전체 카운트: 저장된 행정동 라벨로 거른다

뷰포트와 무관한 카운트라 기존 집계 쿼리에 얹을 수 없다. 리포지토리에 조회 하나를 새로 더한다.

```sql
SELECT
	COUNT(*)::int                    AS "gridCount",
	COALESCE(SUM(ug.video_count), 0) AS "videoCount"
FROM user_grids ug
JOIN grids g ON g.grid_id = ug.grid_id
WHERE ug.user_id = :userId
	AND g.region_code = :regionCode
```

**`COALESCE`가 필요하다.** 기존 집계 쿼리는 `GROUP BY`가 있어 그룹마다 최소 한 행이 보장되지만,
이 쿼리는 그룹이 없는 집계라 매칭 행이 0건이어도 한 행을 돌려주고 그때 `SUM`이 NULL이다. 그 동에
내 격자가 하나도 없는 경우가 흔하므로(FR-8) 여기서만 널 방어를 둔다. `COUNT(*)`는 0건에서도
0이라 방어가 필요 없다.

`user_grids`를 기준으로 잡고 `grids`를 PK 조인하므로 행 중복이 없다. 인덱스는 두 방향 다 있다.
사용자로 먼저 좁히면 `user_grids`의 복합 PK `(user_id, grid_id)`(V1)를 타고, 행정동으로 먼저
좁히면 `grids`의 `idx_grids_region_code`(V7)로 격자를 모은 뒤 `idx_user_grids_grid`(V24)로
되짚는다. 어느 쪽을 드라이버로 잡든 플래너가 인덱스로 좁히므로 계획 형태를 못 박지 않는다.

영상 수를 `user_grids.video_count`에서 가져오는 이유는 정합이 자동으로 맞기 때문이다. 도감 요약의
영상 총합도 같은 컬럼의 SUM이고 격자 목록의 영상 수도 같은 컬럼이라, 같은 격자를 어느 화면에서
보든 같은 값이 나온다. 블라인드가 영상 수를 줄이지 않는다는 계약(SRS FR-MOD-08)과 삭제 시에만
줄어드는 규칙도 이 컬럼의 증감 규칙이 그대로 물려받는다. 여기에 상태별 필터링(예: ACTIVE만 세기)을
새로 넣으면 두 화면의 숫자가 갈라지므로 넣지 않는다. `videos` 테이블은 조인하지 않으므로
`GridQueryService`가 videos에 접근하지 않는다는 기존 계약 주석도 그대로 성립한다.

격자 수도 같은 축이다. 도감 수집률(SRS FR-REGION-12)이 `grids.region_code`로 격자를 행정동에
귀속시키므로, "부전동 격자 5개"가 패널과 수집률 화면에서 같은 값이 된다.

여기서 세는 격자와 마커가 세는 격자는 범위가 다르다는 점을 못 박아 둔다. 마커의 `count`는 뷰포트
안 격자를 묶은 수이고 `currentRegion.gridCount`는 동 전체 수라, 중심 동의 마커 숫자와 패널 숫자가
서로 다른 것이 정상이다. 화면이 두 값을 나란히 놓지 않으므로 사용자에게 모순으로 보이지 않는다.

한 응답이 서로 다른 범위의 "격자 수"를 두 개 담는 것은 소비자가 헷갈릴 자리다. 필드명으로는
구분이 안 되므로(`count`와 `gridCount` 둘 다 격자 수로 읽힌다) **두 DTO의 해당 필드에
`@Schema` 설명으로 범위를 명시한다.** 항목 쪽은 "뷰포트 안에서 이 묶음에 속한 내 격자 수",
현재 동네 쪽은 "이 행정동 전체에서 내 격자 수(뷰포트 무관)"다. 필드명을 범위까지 담게 바꾸는
안(`regionWideGridCount` 등)은 쓰지 않는다. 겉면 객체 이름이 이미 범위를 가리키고 있고, 화면이
쓰는 이름이 길어질 뿐이다. Swagger 설명과 FE 가이드 갱신(후속 1번)이 이 구분을 맡는다.

### 6400 흡수 지점

`resolveByPoint`는 서비스 좌표 범위(한국) 밖 좌표에 `RegionErrorCode.INVALID_COORDINATE`(6400)를
던진다. 이 집계 조회는 화면 중심이 바다이거나 한국 밖이어도 실패하면 안 되므로(FR-3), 호출 앞에
`KoreaCoordinates.isOutOfService(lat, lon)` 가드를 두고 밖이면 호출하지 않고 현재 동네를 null로
둔다. 흡수 지점은 `GridQueryServiceImpl`의 현재 동네 헬퍼 한 곳이다.

이 가드가 완전한 이유는 6400을 던지는 술어가 바로 그 `isOutOfService`이기 때문이다. 같은 판정을
앞에서 하면 예외 경로 자체가 열리지 않는다. 같은 파일의 `resolveRegionName`(MSG-349)과
`RegionStatsQueryServiceImpl.findStatByGrid`가 이미 쓰고 있는 선례를 그대로 따른다. try/catch로
`ApiException`을 삼키는 방식은 쓰지 않는다. 관계없는 실패까지 조용히 먹어 장애를 가리기 때문이다.

포함 행정동이 없는 경우(바다)는 원래부터 예외가 아니라 빈 결과라 그대로 null이 된다. 이때는
카운트 쿼리도 호출하지 않는다. 거를 `regionCode`가 없기 때문이다.

### 검증 순서

파라미터 검증은 지금 순서 그대로다. bbox 파싱과 `unit` 파싱이 먼저이고, 좌표 유효성과 뒤집힘과
상한 검사가 그 다음이며, 현재 동네 판정은 맨 뒤다. 잘못된 요청은 판정에 도달하기 전에 4401이나
4402나 4405로 거절된다. 중심 좌표를 계산하는 시점에는 네 좌표가 이미 유한하고 WGS84 범위 안임이
보장된다.

묶음 목록이 세는 범위는 손대지 않는다. `GridEncoder.viewportRange`가 화면을 덮는 보수적 범위라
가장자리에서 화면 밖 셀이 소량 포함되는데, MSG-347이 무해로 판정했고 개별 조회와 같은 범위를 써야
총합이 어긋나지 않는다(MSG-356 FR-3). 정밀 포함 판정을 새로 넣지 않는다.

### 성능

기존 집계 쿼리가 불변이라 그쪽 실행계획[^6]은 논의 대상이 아니다. 요청당 늘어나는 것은 조회 두
개다. 중심점 판정 하나와 동 단위 카운트 하나이며, 둘 다 인덱스 단건 접근이다. 중심점 판정은 이미
단독 API로 서비스 중인 쿼리와 같은 것이고, 카운트는 V7이 깔아 둔 `idx_grids_region_code`가 노리던
바로 그 형태의 조회다.

MSG-356 실측이 사용자 1인 1만 행 시드의 전국 시도 집계에서 Execution 10.872ms였고 SLO(p95 300ms)
대비 27배 여유였으므로, 인덱스 단건 조회 두 개로 그 여유가 사라질 여지는 없다고 본다. 그래도 PRD
비기능이 요구한 대로 채택 전에 확인한다. 다만 무엇을 확인하는 것인지 성격을 분명히 해 둔다. 기존
`GridAggregationExplainBenchmark`(`GRID_BENCHMARK=true` 게이트)로 도는 EXPLAIN은 **퇴행 점검**이지
SLO 판정이 아니다. 로컬에서 한 번 잰 실행 시간은 부하도 동시성도 네트워크도 없는 값이라 그것들을
더해 p95를 말할 수 없다. 새 하네스는 만들지 않고 기존 벤치에 새 SQL 두 개를 얹는다.

EXPLAIN으로 확인할 것은 시간이 아니라 성질이다.

| 확인 대상 | 통과 조건 |
|---|---|
| 동 단위 카운트 SQL | `grids`와 `user_grids` 어느 쪽도 순차 스캔하지 않는다 (인덱스를 타는 계획이면 형태는 무엇이든 통과) |
| 중심점 판정 SQL | `regions`를 순차 스캔하지 않는다 |
| 기존 집계 SQL | 변경 전과 계획도 소요도 같다 (쿼리를 안 건드렸으니 같아야 정상이고, 다르면 시드가 달라진 것이다) |
| 세 SQL 합 | Execution 합이 같은 시드의 변경 전 집계 단독 실측 대비 자릿수가 바뀌지 않는다 |

계획의 노드 구성을 특정 형태로 못 박지 않는다. 데이터가 늘면 플래너가 더 나은 계획을 고르는 것이
정상이고, 형태를 기준으로 삼으면 더 빠른 계획이 실패로 판정된다. 실측값은 작업 로그에 남긴다.

SLO 자체를 다시 판정해야 한다면 그것은 엔드포인트 부하 측정의 일이고 `load-test/` 하네스가
담당한다. 이번 변경은 그 재측정을 요구할 만한 성격이 아니라고 본다. 위 퇴행 점검에서 순차 스캔이
나오거나 자릿수가 바뀌면 그때는 전제가 틀린 것이므로 구현을 진행하지 말고 사용자에게 올려 부하
측정 여부를 정한다.

## 계약 변경

**`GridQueryService`(A 제공, B 소비) 계약이 늘어난다. 리뷰 시 상대 팀원 확인 필수.**

1. 기존 메서드 `getOccupiedAggregatesInViewport(long, ViewportBounds, RegionUnit)`는 시그니처도
   반환 타입도 그대로 남는다. 친구 집계(`FriendServiceImpl`)가 계속 이 메서드를 쓴다.
2. 지도 홈 전용 메서드를 하나 더한다.

```java
/**
 * 뷰포트 집계에 현재 동네를 더해 돌려준다 (MSG-374). 지도 홈 전용이라 친구 집계는 위 메서드를 계속 쓴다.
 * currentRegion 은 뷰포트 중심점이 속한 행정동이고 unit·축척과 무관하게 항상 판정한다 — 사이드 패널이
 * 마커 시야에서도 중심 동 하나를 기준으로 서기 때문이다. gridCount·videoCount 는 뷰포트가 아니라
 * 그 행정동 전체에서 센다(items 의 count 와 세는 범위가 다르다). 중심이 바다이거나 서비스 범위 밖이면
 * null 이다 (판정의 INVALID_COORDINATE 를 밖으로 내보내지 않는다). name 은 동 이름 한 토큰이다.
 */
GridAggregationView getOccupiedAggregatesWithCurrentRegion(long userId, ViewportBounds bounds, RegionUnit unit);
```

3. `RegionAggregateView`는 바뀌지 않는다. 두 조회가 같은 리포지토리 쿼리 하나를 그대로 공유하고,
   친구 응답 DTO(`RegionAggregateResponseDto`)도 손대지 않으므로 친구 JSON은 자동으로 불변이다
   (FR-7). `FriendServiceImpl`은 코드 변경이 없다.

동반 신규 타입 (모두 A 소유):

```java
// com.msg.fillmap.grid.service
public record GridAggregationView(CurrentRegionView currentRegion, List<RegionAggregateView> items) {
}

public record CurrentRegionView(String regionCode, String name, int gridCount, long videoCount) {
}
```

HTTP 응답 DTO는 컨트롤러 책임 관례대로 `com.msg.fillmap.grid.dto`에 둔다. 겉면
`GridAggregationResponseDto(CurrentRegionResponseDto currentRegion, List<RegionAggregateResponseDto> items)`와
현재 동네 `CurrentRegionResponseDto(String regionCode, String name, int gridCount, long videoCount)`
두 개가 신규다. **묶음 항목은 기존 `RegionAggregateResponseDto`를 그대로 재사용한다.** 항목이
불변이라 타입을 나눌 이유가 없고, 나누면 친구 조회와 지도 홈이 같은 모양의 DTO 두 개를 들고 있게 된다.

리포지토리에는 `RegionGridSummaryProjection`(`Integer getGridCount()`, `Long getVideoCount()`)을
더한다. JPA 인터페이스 프로젝션이라 원시형이 아닌 래퍼로 받는다(기존 `Long getCount()`와 같은 방식).
서비스가 뷰로 옮길 때 `int`와 `long`으로 푼다. SQL이 `COALESCE`로 널을 막았으므로 서비스 쪽에
추가 널 방어는 두지 않는다.

없다. PRD의 열린 항목(성능 실측 미달 시 대응)은 위 성능 절의 근거와 벤치 재실행 계획으로 닫는다.
사이드 패널 영상 카드 3장의 출처는 PRD가 이 티켓 밖으로 명시한 별도 논의라 여기서 다루지 않는다.

카드가 정해지지 않은 채로 이 티켓이 나가면 한동안 패널 안에서 기준이 섞인다. 지역명과 두 숫자는
내 격자를 동 전체로 세는데, 바로 아래 카드 3장은 `GET /api/regions/{regionCode}/grids`가 주는 전역
공개 콘텐츠를 같은 동에서 뽑는다. 범위는 같고 주인이 다른 상태다. 알고 남기는 것이고 카드 티켓이 닫는다.

[^1]: 뷰포트: 지도 화면에 지금 보이는 사각형 범위. 남서와 북동 두 모서리 좌표 네 값으로 서버에 전달한다.
[^2]: 역지오코딩: 좌표를 사람이 읽는 주소나 행정 구역 이름으로 되돌리는 조회. 여기서는 점 하나가
    어느 행정동 경계 안에 있는지를 판정하는 것이다.
[^3]: 행정동 코드: 행정안전부의 10자리 행정동 식별 코드. 앞 2자리가 시도, 앞 5자리가 시군구를 가리켜
    코드를 자르는 것만으로 상위 단위 묶음이 된다.
[^4]: bigint: PostgreSQL의 64비트 정수 타입. int(32비트) 컬럼을 SUM 하면 결과가 자동으로 이 타입이
    되며, Java에서는 long으로 받는다.
[^5]: GIST: PostGIS가 도형 검색에 쓰는 인덱스 종류. 점이 어느 도형 안에 있는지를 전수 비교 없이
    좁혀 준다.
[^6]: 실행계획: 데이터베이스가 쿼리를 어떤 순서와 방법으로 처리할지 정한 계획. EXPLAIN으로 출력해
    스캔 방식과 소요 시간을 확인한다.
