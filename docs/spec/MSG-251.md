## 개요

검색바에 "부산대"·"광안리" 같은 장소명을 치면, 백엔드가 카카오 장소 검색을 대신 호출해 장소 이름·주소·좌표에
**그 좌표의 격자 ID를 얹어** 돌려준다. 프론트는 결과 선택 즉시 지도 이동 + 격자 하이라이트를 한 번에 처리한다.

```
[FE 검색바] --q (디바운스 300ms)--> GET /api/search/places?q=부산대
                                        │  (BE 프록시 — 실시간 패스스루, 저장 0)
                                        ▼
                          카카오 GET /v2/local/search/keyword.json?query=&size=15
                          (Authorization: KakaoAK {REST키} — 서버 보관)
                                        │
                                        ▼
              [{name, address, lat, lng, gridId}]   gridId = GridEncoder.encode(lat, lng) 즉석 계산
                                        │
                                        ▼
                     FE: 지도 이동(lat/lng) + 격자 하이라이트(gridId)
```

DB·Redis 접점 **0** — 조회도 저장도 없다(약관 제약이 곧 설계 제약).

## 배경 · 목표

사용자는 행정동 이름("장전2동")으로 검색하지 않고 장소명("부산대")으로 검색하는데, 우리 DB(행정동 3,558개)로는
그걸 못 찾는다 — 외부 POI 검색이 필요하다.

- **사용자/제품 관점**: 검색 → 선택 → 그 자리 격자로 바로 이동이 지도 탐색의 기본 진입로다. 카카오 좌표는 스모크
  실측(2026-07-28, 로컬 PostGIS 실데이터 4곳)에서 변환 없이 우리 격자·행정동에 정확 매핑됐다 —
  부산대→`39147_112245`(장전2동) / 서면역→`39064_112225`(부전2동) / 홍대입구역→`41729_110368`(서교동) /
  광안리→`39059_112277`(광안2동), 전건 적중.
- **목표**:
  1. `GET /api/search/places?q=` 프록시 API 1종 — 카카오 keyword.json 실시간 패스스루 + `gridId` 합성.
  2. 약관 준수를 코드 구조로 강제 — 저장·캐시 경로 자체가 없음(DB·Redis import 0).
  3. 캐시 유/무 로컬 벤치 실측 수치를 본 문서에 기록(사용자 지시 — 도입 아님, §D6).

## 성공 기준 (관찰 가능)

이 조건들이 전부 관찰되면 완료다 — 아래 테스트 시나리오가 검증 수단이다.

1. `GET /api/search/places?q=부산대`가 카카오 검색 결과를 `[{name, address, lat, lng, gridId}]`(≤15건)로 반환하고,
   각 `gridId`는 그 항목 좌표의 `GridEncoder.encode` 값과 일치한다 — 스모크 실측 4곳 좌표를 fixture로 고정(부산대
   `39147_112245` 등).
2. **약관 준수가 구조로 관찰된다**: search 패키지에 Repository·Entity·캐시 빈 import 0, `@Transactional` 0,
   마이그레이션 0 — 요청마다 카카오 실시간 호출 1회뿐.
3. `q` 공백/trim 후 빈 값 → **카카오 호출 0회** + 200 `[]`(234 trim 가드 계승). `q` 누락 → 400(global).
   무매치 → 200 `[]`. 미인증 → 401.
4. 카카오 5xx·타임아웃·4xx(키/쿼터)·응답 파싱 실패 → **502 + developCode 5502** 단일 수렴(§D3), 원인은 로그로 구분.
5. 크로스오너 계약 4종 시그니처 불변 · SecurityConfig 무변경 · 신규 외부 의존성 0(webmvc 내장 RestClient) ·
   신규 env 0(§D5) · 전체 테스트 green.
6. 캐시 유/무 로컬 벤치 p50/p95·외부 호출 수 비교 수치가 본 문서 작업 로그에 기록된다(도입 아님 — §D6).

## 결정 (Decisions)

### D1 — Owner = **A**, 패키지 = **`com.msg.fillmap.search.*` 신설** (티켓 위임)

이 기능을 누가 만들고 어디에 두느냐 — 지도 탐색 기능이므로 지도 인프라 오너(A)가 새 패키지에 만든다.

- **결정**: 신설 `search` 패키지에 전부 배치, Owner A(grid-developer) 단독. spec-driven-dev 팀 배정 기준.
- **근거**:
  1. **기능의 정체가 지도 인프라 축**: "장소명 → 격자로 이동"은 격자 탐색 진입로다. 전신인 MSG-234 서버 검색(제거·이관)도
     A(zone 패키지) 소유였다 — 이관받은 티켓이 오너까지 승계하는 게 자연스럽다.
  2. **소비 자산이 전부 A**: `GridEncoder`(A 순수 유틸) 하나뿐(§D2에서 region 소비 기각). A 호스팅이면 크로스오너
     소비·계약 논점이 0이다.
  3. **B 선례(AiClient)는 코드가 아니라 패턴**: AiConfig의 Builder 빈은 conditional 게이트라 재사용 불가(선행 상태 표)
     — B 호스팅으로 얻을 실재 재사용이 없다.
- **기각**:
  - **video 패키지 편입**: 검색은 영상 도메인과 무관 — "AiClient가 거기 있다"는 배치 사유가 못 된다(응집 위반).
  - **grid/region 패키지 편입**: grid는 격자 산술·색칠 조회 축, region은 행정동 축 — 외부 HTTP 어댑터를 넣으면 두 패키지의
    "geospatial/산술 순수" 성격이 오염된다. 외부 의존 실패 모드(타임아웃·쿼터)는 격리된 패키지가 낫다.

### D2 — `regionName` 합성 = **안 함** (티켓 위임)

검색 결과에 행정동 이름을 얹을지 — 얹지 않는다. 카카오 주소가 이미 표시용으로 충분하고, 얹으려면 결과당 geospatial 1회가 든다.

- **결정**: 응답은 `name·address·lat·lng·gridId`만. `RegionQueryService.resolveByPoint` 미소비.
- **근거**:
  1. **표시 정보 중복**: 카카오가 `road_address_name`/`address_name`(사람이 읽는 주소)을 이미 준다 — 행정동 라벨은
     검색 리스트에서 더해줄 정보가 없다.
  2. **geospatial 예산**: 결과당 `resolveByPoint` 1회 = 요청당 최대 15회 `ST_Covers`. 디바운스 300ms 자동완성 경로에
     타이핑마다 실리는 비용으로 부적절하다(238이 "조회 경로 geospatial 0"을 지킨 축과 같은 감각).
  3. **소비처 부재**: 선택 후 동선은 지도 이동+격자 하이라이트 — `gridId`로 완결. 격자 진입 후 행정동 라벨이 필요하면
     기존 `reverse-geocode`(93)·`by-grid`(153)가 이미 있다.
  4. 부수 효과: `resolveByPoint`는 서비스 범위 밖 좌표에 6400을 던지는데, 미소비라 그 실패 경로도 안 생긴다.
     `GridEncoder.encode`는 어떤 좌표든 실패 없이 인코딩(순수 floor 산술) — 좌표 검증 코드 0줄.
- **주소 표시 규칙(부속)**: `address` = `road_address_name`이 비어있지 않으면 도로명, 아니면 `address_name`(지번) —
  FE 분기 제거용 1필드. 디자인이 병기를 요구하면 필드 추가만(Open Q1).

### D3 — 에러 = **search 5xxx 대역 신설, 카카오 실패는 `SEARCH_UPSTREAM_ERROR(5502)` 단일 수렴** (티켓 위임)

카카오가 죽거나 느리거나 쿼터가 막히면 전부 502 하나로 낸다 — FE의 대응(잠시 후 재시도 안내)이 어차피 같기 때문이다.

- **결정**:
  - `search/exception/SearchErrorCode` 신설 — 대역 **5xxx**(선행 상태 표: 1·2·3·4·64xx 사용 중, 5xxx 공백).
  - 상수 1개: `SEARCH_UPSTREAM_ERROR(5502, HttpStatus.BAD_GATEWAY, "장소 검색이 일시적으로 어렵습니다. 잠시 후 다시 시도해주세요")`.
  - 수렴 범위: 카카오 5xx · connect/read 타임아웃(`ResourceAccessException`) · 4xx(401/403 키 문제, 429 쿼터) ·
    응답 파싱 실패 — 전부 `ApiException(SEARCH_UPSTREAM_ERROR, cause)`. 원인 구분은 warn 로그로(운영 진단용).
  - `q` 처리(234 §D6 trim 가드 계승): 누락 = **400**(global `MissingServletRequestParameter`) / trim 후 빈 =
    **200 + `[]` + 카카오 호출 0**(빈 쿼리를 카카오에 흘리면 카카오가 400을 내고 쿼터만 소모) / 무매치 = **200 + `[]`**.
- **근거**: 도메인 실패가 아니라 **업스트림 실패**다 — 사용자 입력 잘못(400 계열)도 우리 서버 결함(500)도 아니므로
  502가 의미론상 정확하고, 세분화(5429 등)는 FE 행동이 갈릴 때만 가치가 있다. MVP 쿼터(일 10만)에서 429는 사실상
  이론 케이스다. `ponytail: 쿼터 초과가 실측되면 5429 분리(FE 백오프 신호) — 상수 1개 추가로 끝.`
- **기각**: 429/타임아웃/5xx 개별 코드 — 지금은 소비처 없는 세분화(YAGNI). 공통 `ErrorCode` 재사용 — response-pattern
  규칙("새 실패 케이스는 도메인 XxxErrorCode에") 위반.

### D4 — `size`/`page` 파라미터 = **미노출** (티켓 위임)

파라미터는 `q` 하나만 받는다. 카카오 1페이지(15건)를 그대로 넘긴다.

- **결정**: 카카오 호출 고정 `size=15`(최대)·`page=1`. FE가 덜 보여주고 싶으면 잘라 쓴다.
- **근거**: 자동완성 UI는 상위 몇 건만 소비하고 디자인(ver6)에 검색 결과 페이지네이션이 없다 — 파라미터를 노출하면
  검증(클램프/400)·테스트 표면만 는다. 15건 JSON은 수 KB라 전달 비용도 무의미.
- `ponytail: FE가 2페이지 이상·건수 제어를 실제로 요구하면 size(1~15 클램프)·page 노출 — 파라미터 2개 추가로 끝, 계약 확장만.`

### D5 — RestClient/키 = **search 자체 `RestClient` 빈 + `oauth.kakao.client-id` 프로퍼티 재사용, 신규 env 0** (티켓 위임)

HTTP 클라이언트는 AiClient의 것을 못 쓰므로 직접 만들고, 카카오 REST 키는 OAuth 로그인이 이미 쓰는 값을 그대로 참조한다.

- **결정**:
  - `search/config/SearchConfig`가 **완성된 `RestClient` 빈**(`kakaoLocalRestClient`)을 직접 구성:
    `SimpleClientHttpRequestFactory` + **connect 1s / read 3s 상수** + `baseUrl` + `defaultHeader("Authorization", "KakaoAK " + restApiKey)`.
    `KakaoLocalClient`는 그 빈을 주입받아 호출·파싱만 한다.
  - **`RestClient.Builder` 빈은 만들지 않는다** — `AiClient`가 Builder를 **by-type 무한정 주입**받고 있어(AiConfig 활성
    환경에서) 두 번째 Builder 빈은 기동 모호성 폭탄이다. 완성 RestClient 빈은 현재 0개라 by-type 유일.
  - `search/config/KakaoLocalProperties` record(`@ConfigurationProperties("search.kakao")`, 스캔 자동 등록):
    ```yaml
    search:
      kakao:
        base-url: https://dapi.kakao.com
        rest-api-key: ${oauth.kakao.client-id:}   # 카카오는 OIDC client_id == REST API 키 (같은 "필맵" 앱)
    ```
  - 타임아웃은 상수(AiConfig 선례 — env 튜닝 수요 없음, 필요 시 프로퍼티 승격). 근거: 동기 사용자 경로(자동완성) —
    카카오 정상 응답 수백 ms, read 3s면 hang 시 사용자 대기 상한 3s 후 5502.
- **근거(키 재사용)**: 티켓 확정 "필맵 카카오 앱(OAuth용 재사용)에 로컬 API 활성화 완료" — OIDC `client-id`와 로컬 API
  `KakaoAK` 키가 **같은 앱의 같은 REST 키**다. 프로퍼티 placeholder 참조라 로컬(application-local.yml)·운영(`KAKAO_CLIENT_ID`
  env) 어느 주입 경로든 자동 승계 — 배포 변경·신규 시크릿 0. auth 패키지 Java import도 0(프로퍼티 레벨 참조라 코드 결합 없음).
- **기각**: `KakaoOidcProperties` 직접 주입(auth 클래스 교차 import — 의미 결합) / 신규 `KAKAO_REST_API_KEY` env(같은
  값의 이중 관리 — 로테이션 실수 표면). 앱 분리로 키가 갈라지면 그때 env 승격(1줄).

### D6 — 캐싱 = **프로덕션 도입 금지(약관 하드), 로컬 벤치 실측 수치만 기록** (사용자 지시)

캐시를 붙이면 얼마나 빨라졌을지를 숫자로 남긴다 — 도입하기 위해서가 아니라, 약관이 바뀌거나 제휴가 생겼을 때의
의사결정 입력으로(성능 변경은 구/신 실측 비교로 채택 결정 — MSG-164 원칙).

- **결정**: 구현 완료 후 로컬 1회성 실측 — 절차:
  1. **pass-through(현 구현)**: 실 카카오 대상 동일 `q` 반복 N=100, p50/p95(ms) + 카카오 호출 수(=100).
  2. **캐시 히트**: 로컬 임시 브랜치에서 서비스에 인메모리 맵 몇 줄(커밋 금지) 얹고 동일 N, p50/p95 + 카카오 호출 수(=1).

- 쿼터 영향: ~200회 = 일 10만의 0.2% — 무시 가능. **캐시 코드가 develop에 남으면 약관 위반** — 브랜치 폐기가 DoD.

## API 명세

엔드포인트는 하나다. 인증 필수(SecurityConfig `anyRequest()` — 무변경), 성공은 `SuccessResponse.of(...)`(HTTP 200 · developCode 200).

### `GET /api/search/places` — 장소 검색 (신설)

| 파라미터 | 타입 | 필수 | 의미 |
|---|---|---|---|
| `q` | String | ✅ | 검색어(자유 텍스트). 누락 400 / trim 후 빈 값 200 `[]`(카카오 호출 0 — §D3) |

성공 200 `body` = `List<PlaceSearchResponseDto>` (카카오 정확도순 그대로, ≤15건 — §D4. 무매치 `[]`):

| 필드 | 타입 | 의미 |
|---|---|---|
| `name` | String | 장소명 (카카오 `place_name`) |
| `address` | String | 표시용 주소 — 도로명(`road_address_name`) 우선, 없으면 지번(`address_name`) (§D2) |
| `lat` | double | 위도 (카카오 `y` — WGS84 직결, 변환 없음) |
| `lng` | double | 경도 (카카오 `x`) — 필드명은 티켓 스케치·`ViewportBounds`(swLng) 선례 |
| `gridId` | String | 그 좌표의 격자 ID — `GridEncoder.encode(lat, lng)` **즉석 계산, 저장 아님**. FE 격자 하이라이트 키 |

**요청/응답 예시**
```
GET /api/search/places?q=부산대
```
```json
{ "developCode": 200, "message": "성공", "body": [
  { "name": "부산대학교", "address": "부산 금정구 부산대학로63번길 2",
    "lat": 35.2335, "lng": 129.0790, "gridId": "39147_112245" },
  { "name": "부산대학교병원", "address": "부산 서구 구덕로 179",
    "lat": 35.1046, "lng": 129.0175, "gridId": "39004_112188" }
] }
```

**에러**

| 상황 | 응답 |
|---|---|
| `q` 누락 | **400** (global `MissingServletRequestParameter`) |
| `q` 공백/무매치 | 에러 아님 — **200 + `[]`** |
| 미인증 | **401** (global) |
| 카카오 5xx·타임아웃·4xx(키/쿼터)·파싱 실패 | **502** + `developCode 5502 SEARCH_UPSTREAM_ERROR` (§D3) |

신규 에러코드: `SEARCH_UPSTREAM_ERROR(5502)` 1개 — search 5xxx 대역 신설.

## 도메인 로직

흐름은 3단이다: trim 가드 → 카카오 호출·파싱 → gridId 합성. DB가 없으므로 `@Transactional`도 없다.

### 1. `KakaoLocalClient` (search/service — AiClient 어댑터 선례)

```
GET {base-url}/v2/local/search/keyword.json?query={q}&size=15
Authorization: KakaoAK {rest-api-key}     ← RestClient 빈의 defaultHeader (§D5)
```
- 응답 `documents[]` → `KakaoPlace(placeName, addressName, roadAddressName, lat, lng)` record 리스트.
  `x`/`y`는 카카오가 **문자열**로 주므로 클라이언트가 double 파싱(WGS84 직결 — ADR 확정, 변환 없음).
  `road_address_name` null/누락은 `""` 정규화.
- 실패 수렴: `RestClientException`(5xx·4xx·타임아웃)·파싱 실패 → `throw new ApiException(SearchErrorCode.SEARCH_UPSTREAM_ERROR, e)`
  (+ warn 로그에 원인). 부분 성공 없음 — 전건 실패로 단순화.

### 2. `PlaceSearchServiceImpl` (`@Transactional` 없음 — DB 무접점)

```java
public List<PlaceSearchResponseDto> searchPlaces(String q) {
	String query = q.trim();
	if (query.isEmpty()) {
		return List.of();                       // 234 §D6 trim 가드 계승 — 카카오 호출 0 (§D3)
	}
	return kakaoLocalClient.search(query).stream()
		.map(place -> new PlaceSearchResponseDto(
			place.placeName(),
			place.roadAddressName().isEmpty() ? place.addressName() : place.roadAddressName(),  // §D2 주소 규칙
			place.lat(), place.lng(),
			GridEncoder.encode(place.lat(), place.lng())))   // 즉석 계산 — 저장 아님
		.toList();
}
```
