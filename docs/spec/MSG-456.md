# MSG-456: 블러 처리 일시 비활성화, 블러 전용 플래그 분리

**Owner**: B

> 요구사항 정본: `docs/prd/MSG-456-prd.md` (검토됨, 2026-08-22 성민 승인) · SRS FR-MEDIA-18
> 변경 패키지: `com.msg.fillmap.video.*` 전부. 계약 인터페이스 변경 없음.

## 개요

기능 플래그 `ai.enabled` 하나가 AI 연동 전체(블러 파이프라인, 하이라이트 선분석)를 묶고 있어
블러만 끌 수 없다. 블러 전용 플래그 `ai.blur-enabled`(기본 꺼짐)를 신설해 블러 파이프라인만
게이트하고, 블러가 꺼진 동안에도 재생용 하이라이트는 인코딩 완료 시점에
`AiClient.analyzeHighlights`로 계산해 저장한다. 코드 제거는 없다(일시 비활성화).

## 배경 · 목표

AI 레포에서 블러 제거 작업이 진행 중인데 dev 서버는 `AI_ENABLED=true`로 라이브 중이라, 블러 잡
API(`/jobs`)가 먼저 사라지면 신규 업로드 전부가 BLURRING에 갇혔다가 30분 타임아웃 뒤 실패
알림까지 나간다. 이 배포로 블러 요청이 나가지 않게 만들되, 선분석(FR-1)과 재생 하이라이트(FR-8)는
살린다. 기본값이 꺼짐이라 배포만으로 dev의 블러가 꺼진다(FR-4, env 변경 없음).

## 성공 기준

- `AI_ENABLED=true`만 켜진 환경(배포 후 dev)에서: 업로드 확정 영상이 인코딩 완료 즉시 READY가
  되고, AI 서버로 `/jobs` 계열 요청이 한 건도 나가지 않으며, 재생 응답에 하이라이트가 실린다.
- 같은 환경에서 선분석 API(`POST /api/videos/highlight-preview`)가 기존과 동일하게 동작한다.
- `AI_ENABLED=false` 환경(로컬, CI)은 블러 플래그 값과 무관하게 지금과 완전히 동일하다.
  기존 테스트가 전부 green이면 이 기준의 검증이다.
- 아래 "테스트 시나리오"의 케이스가 전부 green이다.

## 설정 명세 (플래그 확정)

| 항목 | 값 |
|------|-----|
| 프로퍼티 키 | `ai.blur-enabled` |
| 환경변수 | `AI_BLUR_ENABLED` (yml에서 `${AI_BLUR_ENABLED:false}`로 바인딩) |
| 기본값 | `false` (FR-4 확정) |
| 바인딩 방식 | `AiProperties` record에 `@DefaultValue("false") boolean blurEnabled` 필드를 `enabled` 바로 뒤에 추가 |

`@Value` 산발 주입 대신 record 필드를 택한 이유: `AiProperties`는
`@ConfigurationPropertiesScan`으로 조건 없이 항상 등록되는 빈이라 어느 환경에서도 주입이
안전하고, 플래그가 2개가 된 시점부터는 한 타입에 모아 읽는 쪽이 조합 실수를 줄인다.
`blur-enabled`와 `blurEnabled`, `AI_BLUR_ENABLED`는 스프링 완화 바인딩[^1]으로 같은 키다.
record 컴포넌트 추가는 정준 생성자 인자 수를 바꾸므로 직접 생성하는 기존 테스트 2곳의 갱신이
따라온다(테스트 시나리오의 "기존 테스트 파급" 참조).

**실효 블러 활성** = `ai.enabled && ai.blur-enabled`. 블러 파이프라인은 AiClient와
RestClient.Builder(둘 다 `ai.enabled` 게이트 유지, PRD 7절)에 의존하므로 단독 플래그로는
켤 수 없다. `ai.enabled=false`면 블러 플래그와 무관하게 지금과 동일하다(FR-5).

## API 명세

신규, 변경 엔드포인트 없음. RequestDto와 ResponseDto 변경 없음. 에러 코드 신설 없음.

관찰 가능한 변화는 하나다: 블러가 꺼진 기간에 준비 완료된 영상도 재생 응답(MSG-350)의
`highlights` 필드가 채워진다. 계산 실패나 워커 큐 포화 시에만 null이다(FR-8). 계산이 READY
전이의 후행 단계이므로(도메인 로직 3, D-1) READY 직후 수 초 동안은 재생이 null을 볼 수 있다.
PRD FR-8 개정(2026-08-22)이 이 일시 null을 명시 허용한다("READY를 막거나 늦추지 않는다, 준비
완료 직후 잠깐 null 가능, 정상 수 초").

## 도메인 로직

### 1. 빈 게이트 재배선

| 대상 | 현재 조건 | 변경 후 |
|------|----------|---------|
| `AiConfig` (RestClient.Builder, `@EnableScheduling`) | `ai.enabled` | 불변 |
| `AiClient` | `ai.enabled` | 불변 |
| `AiBlurPoller` | `ai.enabled` | `@ConditionalOnProperty(prefix = "ai", name = {"enabled", "blur-enabled"})` |

`@ConditionalOnProperty`[^2]의 `name` 배열은 나열한 키가 전부 true여야 매치되므로, 폴러는 실효
블러 활성일 때만 뜬다. 폴러가 없으면 블러 잡 제출, 폴링, 다운로드가 일절 나가지 않는다(FR-3).

**전역 스케줄링 영향 없음 확인**: `@EnableScheduling`은 멱등[^3]이고, 레포에는 무조건 켜는
`EventSchedulingConfig`가 따로 있다(이벤트, 주간 요약, 스트릭, 핫구역 스케줄러가 여기 의존).
따라서 AiConfig의 `@EnableScheduling`이 `ai.enabled`에 남아도, 폴러가 새 조건으로 옮겨가도
다른 `@Scheduled` 빈의 동작은 변하지 않는다. `ai.enabled=true`에 블러만 꺼진 환경에서
스케줄링 인프라는 뜨지만 폴러 빈이 없어 블러 관련 스케줄 작업은 존재하지 않는다.

### 2. 인코딩 완료 분기 교체 (`VideoEncodingServiceImpl`)

`@Value("${ai.enabled:false}") boolean aiEnabled` 필드를 제거하고 `AiProperties`를 생성자
주입한다. 기존 `aiEnabled` 분기 두 곳(썸네일 추출 생략, markEncoded 대 markReady)을 실효 블러
활성(`aiProperties.enabled() && aiProperties.blurEnabled()`)으로 교체한다.

- **블러 켜짐** (실효 활성): 기존 그대로. 썸네일을 만들지 않고 `markEncoded`로 BLURRING 전이,
  폴러가 이어받는다. 미블러 썸네일 차단 불변식(P1/R5)도 그대로다.
- **블러 꺼짐**: 기존 `ai.enabled=false` 경로 그대로 원본에서 썸네일을 추출해 올리고 READY로
  직행한다. 미블러 썸네일이 공개 키에 올라가는 것은 이 기간의 의도된 동작이다. 영상 본편이
  미블러로 나가는 것과 같은 결이며 SRS 프라이버시 제약 유예(FR-MEDIA-18)에 포함된다.

### 3. 블러 꺼짐 경로의 하이라이트 계산 (FR-8): 전용 워커의 후행 계산

`VideoEncodingServiceImpl`에 `ObjectProvider<AiClient>`[^4]를 주입한다
(`HighlightPreviewServiceImpl` 선례. `AiClient`는 `ai.enabled=false` 환경에 빈이 없어 직접
주입하면 기동이 깨진다).

**D-1 (설계 결정): READY 전이를 먼저 끝내고, 하이라이트는 전용 단일 스레드 워커가 S3의
인코딩본으로 후행 계산한다.**

계산을 markReady 앞에 두면 AI 호출(정상 p50 수 초, AI 서버 hang이면
`HIGHLIGHT_READ_TIMEOUT` 120초)이 그대로 준비 완료 시간에 더해진다. 인코딩 실측이
22.6~27.7초라 정상 지연만으로도 NFR-PERF-08(30초) p50 경계를 넘는다. 그래서 후행이 먼저
확정됐고(PRD FR-8 개정과 5절 시퀀스 다이어그램 갱신, 2026-08-22 정본화), 실행 위치는 인코딩
스레드 인라인이 아니라 **전용 워커**다. 인라인이면 현재 영상의 READY는 지켜지지만 유일한
인코딩 워커(corePool 1)가 AI 호출에 잡혀, 대기 중인 다음 업로드의 인코딩 시작이 밀린다
(헤드오브라인 블로킹[^6]. hang 시 다음 영상의 확정에서 READY까지가 최대 120초 더해진
142.6~147.7초). 전용 워커로 빼면 인코딩 경로와 완전히 격리된다.

인코딩 완료 지점은 제출까지만 한다:

```java
// 블러 꺼짐 경로. READY 전이와 완료 계측을 먼저 끝내고, 하이라이트는 전용 워커에 넘긴다 (D-1)
upload(thumbnailKey, "image/jpeg", thumbnail);
statusWriter.markReady(videoId, originalKey, encodedKey, thumbnailKey);
videoProcessingMetrics.countEncodingTask(VideoProcessingMetrics.TASK_COMPLETED);
resultCounted = true;
submitHighlightJob(videoId, originalKey, encodedKey);
```

```java
/** 워커 제출 (FR-8, D-1). 큐 포화 거부는 폐기가 정책이다. 그 영상은 하이라이트 null 로 남는다. */
private void submitHighlightJob(Long videoId, String originalKey, String encodedKey) {
	if (aiClientProvider.getIfAvailable() == null) {
		return;   // ai.enabled=false. 지금과 동일 (FR-5)
	}
	try {
		highlightExecutor.execute(() -> computeAndRecordHighlights(videoId, originalKey, encodedKey));
	} catch (RejectedExecutionException e) {
		log.warn("하이라이트 큐 포화로 폐기. 하이라이트 없이 둔다: videoId={}", videoId);
	}
}

/** 워커 본문. S3 의 인코딩본을 파일로 받아 분석한다. 어떤 실패도 하이라이트 부재로만 남는다. */
private void computeAndRecordHighlights(Long videoId, String originalKey, String encodedKey) {
	Path workDir = null;
	try {
		workDir = Files.createTempDirectory("highlight-" + videoId + "-");
		Path encoded = workDir.resolve("encoded.mp4");
		download(encodedKey, encoded);   // 기존 download 헬퍼 재사용
		List<List<Double>> highlights = aiClientProvider.getObject().analyzeHighlights(encoded);
		statusWriter.recordHighlights(videoId, originalKey, highlights);
	} catch (Exception e) {
		log.warn("재생 하이라이트 계산 실패. 하이라이트 없이 둔다: videoId={}", videoId, e);
	} finally {
		deleteQuietly(workDir);   // 기존 헬퍼 재사용
	}
}
```

설계 근거와 결정:

- **입력은 S3의 인코딩본이다**: markReady 시점에 encoded 객체는 결정적 키로 S3에 이미 올라가
  있으므로, AiBlurPoller의 제출 경로가 encoded를 재다운로드하는 것과 같은 결로 받아 쓴다.
  인라인 설계의 근거였던 "tmp 수명이 태스크 경계를 넘는 소유권 문제"가 이것으로 소멸한다
  (인코딩 tmp는 encode()의 finally가 지금처럼 지우고, 워커는 자기 임시 파일을 스스로 만들고
  지운다). 다운로드 대상은 최대 31초 720p 인코딩본(수십 MB)이라 2GiB 선분석 원본과 달리
  다운로드가 수 초고, 파일 경유(`FileSystemResource`)라 힙 부담도 없다.
- **전용 단일 스레드 워커, 유계 큐, 포화 시 폐기**: `AsyncConfig`에 encodingExecutor 관례로
  `highlightExecutor` 빈(ThreadPoolTaskExecutor, corePool 1, maxPool 1, queueCapacity 50,
  AbortPolicy)을 추가하고 구체 타입으로 주입한다(AiBlurPoller의 encodingExecutor 주입 선례).
  큐 50은 상류인 인코딩 큐(50)가 쏟아낼 수 있는 최대 백로그와 맞춘 값이다. 정상 운전에선
  폐기가 없고, AI 장기 hang에서만 거부가 나며 그 결말은 하이라이트 null이다(FR-8의 실패 null과
  같은 결). 거부는 제출부가 catch해 warn 로그만 남긴다.
- **t3.small 메모리 전제와 충돌하지 않는다**: 동시 ffmpeg 회피 관례(단일 인코딩 풀)는 ffmpeg
  프로세스의 메모리 점유에 관한 것인데, 이 워커는 ffmpeg를 돌리지 않고 HTTP 응답 대기만 한다.
- **NFR-PERF-08 정합**: 준비 완료 시간은 인코딩 실측 22.6~27.7초 그대로다. AI 지연은 워커
  스레드에서만 발생해 현재 영상에도 다음 업로드에도 닿지 않고, 관찰 가능한 대가는 READY 직후
  수 초의 하이라이트 null 창뿐이다(API 명세 절의 수용 근거 참조).
- **워커 실행 시점의 스테일은 기존 가드가 닫는다**: 워커가 돌 때쯤 영상이 교체·삭제됐을 수
  있다. 삭제로 S3 객체가 사라졌으면 다운로드 실패가 곧 실패 경로(null 유지)고, 교체로 encoded
  객체가 새 인코딩본으로 덮였어도 originalKey 불일치로 `recordHighlights` 가드가 저장을
  skip한다(4절). 어느 창에서도 잘못된 저장은 없다.
- **완료 계측을 markReady 직후로 당긴다**: `TASK_COMPLETED` 계상과 `resultCounted` 세팅을
  워커 제출 앞에 둔다(over_duration 경로의 "계상 먼저" 원칙과 같은 결). 워커 본문의 실패는
  인코딩 태스크 계측과 무관하다.
- **예외 구분 없음**: `HighlightSourceRejectedException`과 `HighlightUpstreamException`을
  가르지 않는다. 어느 쪽이든 대응이 "하이라이트 없이 둔다"로 같다. 워커 본문의 catch는 스레드
  풀이 예외를 조용히 삼키는 것을 막고 실패를 로그로 남기기 위한 것이기도 하다.

### 4. 하이라이트 저장 (`VideoStatusWriter.recordHighlights` 신설)

`markReady` 시그니처는 바꾸지 않는다. 후행 저장 전용 메서드를 신설한다:

```java
/**
 * 블러 꺼짐 경로의 후행 하이라이트 저장 (MSG-456 D-1). READY 전이 후에 불리므로 가드도 READY 국면을
 * 요구한다. 시도 식별 키는 originalS3Key 다. encoded 키는 결정적(videos/encoded/{userId}/{videoId}.mp4)
 * 이라 교체 후 새 시도의 READY 와 구분되지 않지만, 원본 키는 교체마다 새 attemptUuid 키라 시도를 유일하게
 * 식별한다 (isCurrentEncodingAttempt 와 같은 축). 불일치(교체로 UPLOADED 복귀, 삭제로 ACTIVE 이탈,
 * 새 시도의 READY)면 logStaleSkip 후 버린다. lockUploaderFirst 는 타지 않는다. 알림도 users FK 쓰기도
 * 없어 videos 행 잠금만으로 충분하다(잠금 순서 사이클 없음).
 */
@Transactional(propagation = Propagation.REQUIRES_NEW)
public void recordHighlights(Long videoId, String expectedOriginalKey, List<List<Double>> highlights) {
	videoRepository.findWithLockById(videoId).ifPresent(video -> {
		if (video.getStatus() != VideoStatus.ACTIVE
			|| video.getProcessingStatus() != ProcessingStatus.READY
			|| !Objects.equals(video.getOriginalS3Key(), expectedOriginalKey)) {
			logStaleSkip("하이라이트 저장", videoId, expectedOriginalKey, video);
			return;
		}
		video.recordHighlights(highlights);
	});
}
```

엔티티에는 `Video.recordHighlights(List<List<Double>> highlights)`를 신설한다
(`this.highlights` 세팅만. `applyBlurResult`는 블러본 키를 함께 세팅하므로 재사용하지 않는다).

행 잠금과 시도 정체성 가드[^5]를 지키므로, 교체나 삭제로 스테일이 된 태스크의 하이라이트가 새
시도에 붙지 않는다(PRD의 "저장도 같은 가드 안에서" 요구를 후행 구조에 맞게 이행한 것).
계산 실패 시에는 이 메서드가 호출되지 않는다(`analyzeHighlights`는 실패를 전부 예외로
올리므로 반환값은 항상 non-null이고, 저장할 것이 없는 실패는 호출 생략이 곧 null 유지다).

알림(FR-7)과 종결 계측은 변경 없다. `markReady`가 이미 `recordOutcomeNotification`(인코딩

### 배포 절차 (BLURRING 잔존 처리)

배포 전 확인만으로는 못 닫는 레이스가 있다: 확인 시점과 구 프로세스 종료 사이에 확정된
업로드가 BLURRING에 진입하면, 신 배포에는 폴러가 없어 그 행이 영구 대기(재생 불가)로 남는다.
그래서 배포 후 점검까지가 절차다. 앱 기동 시 자동 reconcile 코드는 dev 트래픽(시드 위주, 실사용
미미) 대비 과설계라 문서 절차로 닫는다.

1. **배포 전**: `SELECT count(*) FROM videos WHERE processing_status = 'BLURRING';`
   이 0건임을 확인한다 (dev 실측 0건, 2026-08-22).
2. 배포한다.
3. **배포 후**: 같은 조회를 다시 실행한다. 잔존이 있으면 아래 SQL로 READY 전환한다.
   블러본이 없으므로 재생은 인코딩본 폴백(FR-VIDEO-12)이고 하이라이트는 null이다.

```sql
UPDATE videos
SET processing_status = 'READY'
WHERE processing_status = 'BLURRING' AND status IN ('ACTIVE', 'BLINDED');
```

BLINDED를 포함하는 이유: BLURRING 중 신고 승인으로 블라인드된 행도 폴러 소멸로 영구 대기가
되는데, 블라인드 해제는 `status`만 ACTIVE로 되돌리므로 여기서 `processing_status`를 READY로
만들어 두지 않으면 해제 후에도 재생 불가로 남는다. DELETED만 제외한다.

전환의 한계 두 가지를 알고 수용한다(대상은 배포 창에 진입한 극소수뿐이다):

- 전환된 행은 `thumbnail_url`이 null이다(BLURRING 동안 미기록이 불변식이라). 목록에서 그
  영상의 썸네일이 비어 보인다. 사용자가 영상을 교체하면 정상 경로로 복구된다.
- 처리 완료 알림은 나가지 않는다(SQL 경로에는 outbox 기록이 없다).

`ai_job_id`와 `blurring_started_at`은 지우지 않는다. 폴러가 없어 무해하고, 재활성 후에도
BLURRING이 아닌 행은 폴러가 집지 않는다.

[^1]: 완화 바인딩(relaxed binding): 스프링 부트가 케밥 케이스 프로퍼티 키, 카멜 케이스 자바 필드, 대문자 스네이크 환경변수를 같은 키로 취급해 묶어 주는 규칙. `ai.blur-enabled`, `blurEnabled`, `AI_BLUR_ENABLED`가 전부 한 값이다.
[^2]: `@ConditionalOnProperty`: 설정값이 조건을 만족할 때만 빈을 컨테이너에 등록하는 스프링 부트 애너테이션. `name`에 여러 키를 주면 전부 true여야 등록된다. 등록 자체가 안 되므로 "꺼진 기능"의 코드는 메모리에도 스케줄에도 없다.
[^3]: 멱등(idempotent): 여러 번 적용해도 한 번 적용한 것과 결과가 같은 성질. `@EnableScheduling`은 여러 설정 클래스에 중복 선언돼도 스케줄링 인프라 빈을 한 번만 등록한다.
[^4]: `ObjectProvider`: 빈을 주입 시점이 아니라 사용 시점에 조회하는 스프링의 지연 조회 핸들. 대상 빈이 없어도 주입부가 깨지지 않고, `getIfAvailable()`이 null을 반환해 "빈이 없으면 건너뛰는" 분기를 만들 수 있다.
[^5]: 시도 정체성 가드: 비동기 태스크가 결과를 쓰기 직전, 행 잠금 후 "내가 처리한 원본이 아직 현재 시도인가"(상태와 원본 키 일치)를 재확인하고 아니면 조용히 버리는 패턴(MSG-241/382). 업로드 교체나 삭제와 늦게 끝난 태스크의 경합에서 옛 결과가 새 시도를 덮는 것을 막는다.
[^6]: 헤드오브라인 블로킹(head-of-line blocking): 줄 맨 앞의 느린 작업 하나가 뒤에 선 작업 전부를 막는 현상. 단일 워커 큐에서 첫 태스크가 120초짜리 HTTP 대기에 잡히면, 뒤 태스크는 자기 작업이 아무리 짧아도 그 120초를 같이 기다린다.
