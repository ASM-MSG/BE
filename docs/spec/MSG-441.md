## 개요

행사 영상 하나에 달리는 사용자 반응 두 종을 만든다. 댓글(작성, 수정, 삭제)과 도움돼요(추가, 취소)다.
둘 다 저장 원천 테이블이 이번에 처음 생기고, 그 집계가 위치별 영상 피드 카드의 하트 수·댓글 수와
영상 상세의 도움돼요 수·댓글 목록에 함께 실린다. MSG-440이 두 응답에 "자리 예약"이라고 주석으로
남겨 둔 필드가 이 티켓에서 채워진다.

세 번째 산출물은 잠금 배선이다. MSG-442가 만든 `EventLifecycleGuard.checkInteractionOpen`은
지금 호출자가 하나도 없다. 이 티켓의 변경 API 다섯 개가 그 유일한 소비처가 되어, 아카이브로 넘어간
행사에서 댓글과 도움돼요를 바꾸려는 요청이 서버에서 `EVENT_INTERACTION_LOCKED`(13422)로 거절되게 한다.

## 배경 · 목표

행사방에는 참여도 채팅도 없다. 사용자가 남길 수 있는 것은 영상과 그 영상에 붙는 반응뿐이라,
댓글과 도움돼요가 행사방의 유일한 대화 표면이다. 한편 행사가 끝나면 그 방은 기록이 되어야 한다.
영상도 대화도 종료 후 30일까지 열려 있다가 아카이브 전환에서 함께 닫힌다는 것이 §4.2 상태 표의
결정이고(2026-08-21 번복 — 아래 확정 사항 참조), "닫힌다"가 화면의 버튼 비활성화만 뜻하면 API를
직접 부르는 쪽에서 그대로 뚫린다. 그래서 PRD
비기능이 "댓글·도움돼요 잠금은 UI뿐 아니라 변경 API에서 반드시 검증한다"를 따로 적어 두었다.

목표는 셋이다. 첫째, 두 반응의 저장과 조회를 만든다. 둘째, 목록과 상세가 같은 원천에서 같은 수를
읽게 한다(US-006의 "목록의 하트 표기와 상세의 도움돼요 수는 동일한 반응 데이터"). 셋째, 모든
변경 경로에 잠금 가드를 걸되 조회 경로에는 걸지 않는다(FR-14의 "아카이브 후에도 집계는 조회 가능").

## 성공 기준

- 예정(UPCOMING)·진행 중(LIVE)·업로드 유예(UPLOAD_GRACE) 행사에서 댓글 작성·수정·삭제와 도움돼요
  추가·취소가 성공한다 (FR-EVENT-09). 유예 기간에 새로 올라온 영상에도 반응을 남길 수 있다.
- 아카이브 전환 정각부터(ARCHIVED) 같은 다섯 요청이 전부 409 + developCode 13422로 거절된다
  (FR-EVENT-10, PRD FR-13). 업로드 마감과 같은 정각이라 두 규칙이 함께 닫힌다.
- 아카이브 후에도 영상 상세의 댓글 목록·댓글 수·도움돼요 수와 피드 카드의 두 수가 그대로 조회된다
  (PRD FR-14). 조회 경로 어디에도 가드가 없다.
- 같은 영상에 대한 도움돼요 추가를 두 번 보내도 수가 1이고, 취소를 두 번 보내도 실패하지 않는다
  (사용자당 1회 + 멱등[^1]).
- 피드 카드의 하트 수·댓글 수와 상세의 도움돼요 수·댓글 수가 같은 영상에서 항상 일치한다
  (US-006, 원천 테이블 하나와 술어 하나).
- 댓글 수정·삭제는 작성자 본인만 성공하고 타인 요청은 403 + developCode 13403이다.
- 댓글 목록은 작성 시각을 담고 커서로 끊김 없이 이어진다(PRD FR-21).

아래 "테스트 시나리오"가 이 기준의 검증 수단이다. 테스트에는 `// 검증: FR-EVENT-09` 형식의
마커 주석을 단다. **마커에 PRD 로컬 번호(FR-13 등)를 쓰지 않는다.** `docs/srs.md`의 행사 요구는
FR-EVENT-01~11뿐이라 로컬 번호를 쓰면 `scripts/generate-rtm.sh`의 orphan 검사에 걸린다
(MSG-442 작업 로그가 같은 함정을 기록해 두었다). PRD 번호는 산문에만 남긴다.

## 확정 사항 (스펙 근거 기록)

- **잠금 시점은 종료가 아니라 아카이브 전환(종료 + 30일)이다 — 2026-08-21 번복.** 이 스펙의 초안과
  MSG-442는 "종료 정각부터 잠금"으로 적었고 근거는 "종료 = 기록 확정"이었다. 정민 확정으로 뒤집혔다.
  유예 기간은 "행사 다녀와서 나중에 올리기"를 위해 둔 구간인데, 그 영상이 처음부터 아무도 반응할 수
  없는 죽은 영상이 되면 유예를 둔 목적과 결과가 서로 깎인다는 것이 이유다. 기록 확정 시점은 아카이브
  전환으로 옮겨갔고, 업로드 창과 반응 창이 `시작 ~ 종료 + 30일`로 정렬돼 두 규칙이 한 정각에서 닫힌다.
  반영 지점은 `EventLifecycleGuard.checkInteractionOpen`(조건에서 `UPLOAD_GRACE` 제거) ·
  상세의 `interactionLocked` 파생 · 테스트 3종 · PRD §4.2 · SRS FR-EVENT-10 · glossary "도움돼요"다.
- **집계는 저장하지 않고 조회 시 센다.** 비정규화 카운터[^2] 컬럼(`event_videos.comment_count`
  같은 것)을 만들지 않는다. 근거는 두 가지다. 하나, 이 도메인은 같은 판단을 이미 한 번 했다.
  위치 목록의 영상 수가 `EventVideoRepository.countVisibleByLocationIds`의 group by 배치
  집계이고, SRS FR-EVENT-02가 "영상 수는 별도 집계 없이 조회 시점 실측"이라고 요구 자체에
  적어 두었다. 둘, 카운터를 두면 사용자 탈퇴의 FK 연쇄 삭제가 카운터를 지나쳐 드리프트를
  만든다(DB가 지운 행을 애플리케이션 카운터가 모른다). 피드 한 페이지는 최대 50행이고 집계는
  페이지의 영상 id 집합으로 도는 group by 두 번이라 왕복이 페이지 크기와 무관하게 상수다.
- **잠금 판정은 회차 상태의 파생이고 영상에 저장하지 않는다.** MSG-438이 `interactionLocked`
  저장 컬럼을 두지 않은 결정의 귀결이다. 가드는 (회차, 시각)의 순수 함수이므로 유예 기간에
  올라온 영상이 그 회차의 아카이브 전환에 맞춰 함께 잠기는 것(US-009)도 별도 로직이 아니다.
- **판정 시각은 서비스가 한 번 고정해 가드의 static 오버로드에 넘긴다.** MSG-440 업로드 경로가
  같은 형태다. 서비스가 주입받은 `Clock`으로 `now`를 한 번 만들고 그 값으로 상태 판정과 응답의
  파생 필드를 모두 계산한다. 가드가 자기 `Clock`을 다시 읽으면 한 요청 안에서 두 시각이 갈린다.
  **댓글의 `createdAt`도 같은 `now`를 쓴다**(아래 데이터 모델의 팩터리 참조).
- **비로그인은 조회만 한다.** MSG-439가 확정하고 MSG-440이 이어받은 "조회는 비로그인, 쓰기는
  로그인"을 그대로 따른다. 댓글 목록 GET은 permitAll, 댓글·도움돼요 변경 다섯 개는 인증 필수다.
  익명 세션 식별자(MSG-443의 heartbeat)는 열람 집계 전용이라 반응 주체로 쓰지 않는다.
  도움돼요가 사용자당 1회라는 요구 자체가 계정 단위 식별을 전제한다.
  **PRD §15의 "비로그인 사용자의 영상 업로드·댓글·도움돼요 허용 여부" 항목은 이 스펙과 같은
  커밋에서 종결 처리했다.** 새 결정이 아니라 이미 내린 결정의 기록 갱신이다. 정책은 MSG-439
  (조회 4종 GET 한정 permitAll)와 MSG-440(업로드 POST는 인증, 피드·상세 GET은 permitAll)에서
  사용자가 확정했는데 PRD에는 그 결과가 반영되지 않은 채 미해결로 남아 있었다. 441은 댓글·도움돼요
  변경에 같은 정책을 승계할 뿐이라 PRD 헤더의 `상태: 확정`은 그대로 둔다.
- **댓글 정렬은 오래된 순이다**(`id ASC`). **2026-08-21 사용자 확정**("최신에 올라온 댓글들이
  밑에 쌓이도록")으로, Figma 실측을 기다리지 않고 이 확정으로 종결한 항목이다. 행사방 댓글은
  시간순으로 읽는 기록에 가깝고, 상세 화면이 영상 아래에 댓글을 이어 붙이는 형태(PRD §9 "상세
  댓글에는 상대 작성 시간을 오른쪽에 표시")라 위에서 아래로 시간이 흐르는 배열이 자연스럽다.
  피드가 최신순인 것과 방향이 다른 것은 의도된 차이다(피드는 새 영상을 먼저 보여 주는 목록,
  댓글은 대화 흐름).
- **댓글 신고·블라인드는 이번 범위 밖이다**(비목표). 현행 moderation 도메인은 영상 전용이다
  (`reports.video_id NOT NULL`, `Report.create(reporterId, videoId, ...)`). 댓글을 신고 대상으로
  넓히면 신고 대상 타입 도입과 관리자 화면 확장이 따라오는 요구사항 신설이라 PRD 갱신이 선행이다.
- **댓글 수정 이력은 남기지 않는다.** `updated_at` 컬럼도 "수정됨" 표시 필드도 만들지 않는다.
  티켓·PRD가 요구하는 표시 재료는 작성자·내용·작성 시간 셋뿐이다. 필요해지면 컬럼 하나와 응답
  필드 하나를 뒤에 더하는 변경이라 지금 미리 넣을 이유가 없다.
- **용어집 등재 완료**: "도움돼요"는 새로 생기는 사용자 노출 용어라 `.claude/rules/glossary.md`의
  MVP 확정 용어 절에 등재했다(2026-08-21 사용자 승인). 일반 영상의 좋아요(`likes` 테이블, V1
  DDL만 있고 미구현)와 다른 개념이라는 구분도 그 항목과 "자주 헷갈리는 개념" 표에 함께 적었다.

## API 명세

**공통 규약**: 컨트롤러는 `SuccessResponse.of(data)`만 반환하고 실패는 `ApiException` throw
하나로 처리한다(response-pattern.md). 시각 필드는 `LocalDateTime`이며 전역 UTC `Z` 코덱이
직렬화한다(MSG-376). 서버 시각은 주입받은 `Clock`에서 얻는다.

**존재 은닉[^3] (전 API 공통)**: 대상 영상은 MSG-440 상세와 **같은 술어**로만 열린다. ①
`event_videos` 연결이 있고 ② 영상이 ACTIVE·PUBLIC·READY이며 ③ 소속 회차가 노출 상태여야 한다.
하나라도 어긋나면 404 + `13406 EVENT_VIDEO_NOT_FOUND`이며, 행사 영상이 아닌 영상 id도 같은
404다. 소유자 본인도 예외가 아니다(MSG-440 상세와 글자 그대로 같은 계약이라 "상세에서 보이는
영상에만 반응할 수 있다"가 성립한다).

**판정 순서 (변경 API 다섯 개 공통)**:

1. 영상 로드와 노출 판정 → 어긋나면 `13406`.
2. `EventLifecycleGuard.checkInteractionOpen(occurrence, now)` → 아카이브 전환(종료 + 30일) 이후면 `13422`.
3. (댓글 수정·삭제만) 댓글 로드와 소유자 검증 → 없거나 다른 영상의 댓글이면 `13407`,
   남의 댓글이면 `13403`.
4. 실행.

가드가 소유자 검증보다 **앞**이다. 아카이브된 행사에서는 자기 댓글이든 남의 댓글이든 결과가 같아야
하고, 순서가 반대면 그 행사에서 남의 댓글에 대한 응답(403)과 자기 댓글에 대한 응답(409)이
갈려 잠금이 아니라 권한 문제로 읽힌다.

### 1. 댓글 작성: `POST /api/event-videos/{videoId}/comments` (인증 필수)

요청 `EventVideoCommentRequestDto`:

| 필드 | 검증 | 설명 |
|---|---|---|
| `content` | `@NotBlank`, `@Size(max = 500)` | 댓글 본문. 짧은 반응 전제이며 컬럼 폭과 같은 값이다 |

응답 `EventVideoCommentResponseDto`: `commentId`, `authorId`, `authorNickname`, `content`,
`createdAt`. `authorId`는 화면이 "내 댓글에만 수정·삭제 버튼"을 그리는 재료다(서버가 `mine`
같은 파생 불리언을 따로 내리지 않는다. 목록에서 로그인 사용자 id와 비교하면 끝이라 필드를
늘릴 이유가 없다).

### 2. 댓글 수정: `PATCH /api/event-videos/{videoId}/comments/{commentId}` (인증 필수)

요청은 작성과 같은 `EventVideoCommentRequestDto`를 쓴다(필드와 검증이 동일하다). 응답도 작성과
같은 `EventVideoCommentResponseDto`이며 `createdAt`은 최초 작성 시각 그대로다. 본인만 성공한다.

### 3. 댓글 삭제: `DELETE /api/event-videos/{videoId}/comments/{commentId}` (인증 필수)

행을 실제로 지운다(소프트 삭제 아님. 영상 삭제가 소프트인 것과 다르며, 댓글은 신고·블라인드
대상이 아니라 지운 뒤 남겨 둘 이유가 없다). 응답 data는 없다(`SuccessResponse<Void>`). 본인만
성공하고, 이미 지운 댓글을 다시 지우려 하면 `13407`이다. 삭제를 멱등하게 만들지 않는 이유는
댓글 id가 사용자 화면에서 온 실재 참조라 "없는 댓글 삭제 성공"이 화면 상태 불일치를 감추기
때문이다(도움돼요와 성격이 다르다. 그쪽은 토글이라 멱등이 맞다).

### 4. 도움돼요 추가: `PUT /api/event-videos/{videoId}/helpful` (인증 필수)

요청 본문 없음. 응답 `EventVideoHelpfulResponseDto`: `helpfulCount`(처리 후 현재 수),
`helpfulByMe`(항상 true). 이미 누른 상태에서 다시 호출해도 성공하고 수는 늘지 않는다
(`INSERT ... ON CONFLICT DO NOTHING`). 메서드가 POST가 아니라 PUT인 것이 이 멱등성의 표현이고
PRD §7이 정한 형태다.

### 5. 도움돼요 취소: `DELETE /api/event-videos/{videoId}/helpful` (인증 필수)

요청 본문 없음. 응답은 4와 같은 DTO이며 `helpfulByMe`는 항상 false다. 누른 적 없는 상태에서
호출해도 삭제 0행으로 성공한다.

### 6. 댓글 목록: `GET /api/event-videos/{videoId}/comments?cursor=&size=` (비로그인 허용)

영상 상세가 첫 페이지를 이미 품고 있으므로(아래 7) 이 API는 **둘째 페이지부터**를 위한 것이다.
계약은 피드와 같다. `cursor`는 직전 응답의 `nextCursor`를 그대로 넣고(첫 페이지는 생략),
`size`는 1~50 범위 밖이면 잘라서 적용하며 생략하면 20이다. 형식이 깨졌거나 다른 영상의 목록에서
받은 커서면 400 + `13402 INVALID_CURSOR`다.

응답 `EventVideoCommentPageResponseDto`: `comments`(위 `EventVideoCommentResponseDto` 배열),
`hasNext`, `nextCursor`. `EventLocationVideoPageResponseDto`와 같은 형상이다.

**PRD 등재**: 이 엔드포인트는 FE가 소비하는 새 계약이라 **같은 커밋에서 PRD §7 "조회" 목록에
등재했고, §10 비기능의 커서 규칙에도 댓글 목록이 같은 규칙을 따른다는 문장을 덧붙였다.** 요구를
새로 만든 것이 아니라 승인된 범위(US-006·FR-21의 댓글 목록)를 전달하는 API를 기록에 남긴 것이라
PRD 헤더의 `상태: 확정`은 그대로 둔다.

**상세에 댓글을 통째로 싣지 않고 페이지를 나눈 이유**: 상한 없는 목록을 응답에 넣으면 댓글이
많은 영상에서 상세 응답이 그만큼 커진다. 위치별 영상 첫 페이지 p95 1.5초라는 비기능 목표가 있는
화면이라, 목록형 데이터는 전부 커서를 태운다는 레포 관례(피드·전역 영상 목록)를 그대로 따른다.

### 7. 영상 상세 확장: `GET /api/event-videos/{videoId}` (비로그인 허용, MSG-440 API)

`EventVideoDetailResponseDto`에 필드 넷을 더한다. 나머지 필드와 동작(재생 URL 발급, 조회수 증가,
존재 은닉)은 MSG-440 그대로다.

| 필드 | 타입 | 설명 |
|---|---|---|
| `helpfulCount` | `long` | 도움돼요 수 |
| `helpfulByMe` | `boolean` | 내가 눌렀는지. 비로그인은 항상 false |
| `commentCount` | `long` | 댓글 수 |
| `comments` | `EventVideoCommentPageResponseDto` | 댓글 첫 페이지(오래된 순 20건 + hasNext + nextCursor) |

기존 `interactionLocked` 필드는 그대로 두되 **판정을 가드와 같은 축으로 맞춘다**. MSG-440 구현은
`!now.isBefore(occurrence.getEndsAt())`라는 직접 비교로 계산하고 있는데, 이 티켓이 잠금의 실제
집행자가 되므로 표시와 집행이 갈리면 안 된다. `EventStatus`가 `ARCHIVED`인지 보는 형태로 바꾼다
(2026-08-21 번복 반영 — 유예 기간은 열려 있으므로 `UPLOAD_GRACE`는 false다). 경계 정각의 해석은
`statusAt`의 반개구간[^4] 규칙에 위임된다. **이 변경은 기존 테스트와 짝이다**:
`EventVideoQueryServiceTest`의 `종료_시각부터_interactionLocked가_참이다`(413~425행)가 종료 정각을
경계로 고정하고 있으므로, 새 테스트를 만들지 말고 그 테스트를 아카이브 전환 정각 기준으로 고쳐 쓴다
(이름도 함께 바꾼다. 아래 테스트 시나리오 참조).

### 8. 피드 카드 확장: `GET /api/event-occurrences/{occurrenceId}/locations/{locationId}/videos`

`EventLocationVideoResponseDto`에 `helpfulCount`와 `commentCount`(둘 다 `long`)를 더한다.
PRD US-004의 "카드 하단에는 하트 수, 댓글 수, 업로드 시간"이 이 두 필드로 채워진다. 카드에는
토글이 없으므로 `helpfulByMe`는 싣지 않는다(상세에만 있다). 반응이 하나도 없는 영상은 0이다.

### 에러 코드 (event 13xxx 대역)

`EventErrorCode`에 두 상수를 더한다. `response-pattern.md`의 대역 표에 event 행이 이미 있으므로
표 갱신은 불요하고, 그 행의 괄호 설명(현재 상수 현황)만 갱신 대상이다.

| 상수 | developCode | HttpStatus | 메시지 |
|---|---|---|---|
| `EVENT_COMMENT_FORBIDDEN` | 13403 | FORBIDDEN | 본인의 댓글만 수정하거나 삭제할 수 있습니다 |
| `EVENT_COMMENT_NOT_FOUND` | 13407 | NOT_FOUND | 댓글을 찾을 수 없습니다 |

번호는 기존 대역 규칙(13 + 의미상 HTTP status, 404 계열은 뒤로 이어 붙임)을 따른다. 13400~13402,
13404~13406, 13409, 13410, 13422는 이미 쓰이고 있어 비어 있는 13403과 13407을 잡았다.
잠금 거절은 새 코드를 만들지 않고 MSG-442가 만든 `EVENT_INTERACTION_LOCKED`(13422)를 그대로
쓴다. 무효 커서도 기존 `INVALID_CURSOR`(13402) 재사용이다. 다만 13422의 **표시 문자열**은 2026-08-21
잠금 시점 번복에 맞춰 `"행사 영상 댓글·도움돼요가 마감되었습니다"`로 바뀌었다(developCode·HttpStatus
불변 — 아래 작업 로그 참조).

권한 실패를 404로 뭉개지 않고 403으로 주는 이유: 남의 댓글은 목록에서 이미 공개된 존재라
숨길 것이 없다. 영상 존재 은닉과 성격이 다르며 `VIDEO_FORBIDDEN`(3403)과 같은 결이다.

### 인증 설정

`SecurityConfig`의 GET 한정 permitAll 블록에 `"/api/event-videos/*/comments"` 한 줄을 더한다.
기존 `"/api/event-videos/*"` 패턴은 세그먼트 하나만 매치하므로 댓글 하위 경로를 덮지 않는다.
**메서드 한정을 유지하는 것이 계약의 일부다.** 문자열 패턴으로만 열면 같은 경로의 댓글 작성
POST가 익명에 함께 풀린다(MSG-439·440이 같은 함정을 명시해 둔 자리다). 나머지 다섯 변경 API는
매처를 추가하지 않으므로 `anyRequest().authenticated()`가 적용된다.

## 도메인 로직

### 노출 판정과 로딩

변경 API 다섯과 댓글 목록이 모두 같은 재료를 필요로 한다. 노출 상태인 행사 영상과 그 소속 회차다.
판정을 서비스마다 손으로 반복하면 MSG-440 상세와 표현이 갈릴 위험이 있고, 갈리는 순간 한쪽
경로로만 삭제·비공개 영상의 존재가 새어 나간다. 그래서 술어를 **리포지토리 쿼리 한 곳**에 둔다.

`EventVideoRepository`에 조회 하나를 더한다. 기존 카운트·피드 쿼리 바로 옆에 붙여, 세 쿼리의
WHERE가 한눈에 대조되게 한다(그 파일이 이미 "노출 술어는 동등 계약"이라는 이유로 쿼리를 붙여
두고 있다).

```java
@Query("""
	SELECT ev FROM EventVideo ev
	JOIN FETCH ev.location l
	JOIN FETCH l.occurrence
	JOIN ev.video v
	WHERE ev.videoId = :videoId
	  AND v.status = com.msg.fillmap.video.entity.VideoStatus.ACTIVE
	  AND v.visibility = com.msg.fillmap.video.entity.Visibility.PUBLIC
	  AND v.processingStatus = com.msg.fillmap.video.entity.ProcessingStatus.READY
	""")
Optional<EventVideo> findVisibleWithOccurrence(@Param("videoId") Long videoId);
```

`JOIN FETCH`[^5]로 위치와 회차를 함께 읽는 것은 다음 줄에서 바로 가드에 회차를 넘기기 때문이다
(지연 로딩이면 왕복이 하나 더 생긴다). 회차의 노출 은닉 판정은 이 쿼리가 아니라
`EventOccurrence.isVisibleAt(now)`가 한다. MSG-442가 조회 네 경로와 공유하려고 엔티티에 올려 둔
술어이므로 여기서도 그것을 부른다.

### 잠금 가드 배선

변경 API 다섯 곳 전부가 영상을 로드한 직후 아래 한 줄을 부른다. 이 티켓의 핵심 계약이다.

```java
EventLifecycleGuard.checkInteractionOpen(link.getLocation().getOccurrence(), now);
```

`now`를 넘기는 static 오버로드를 쓴다(MSG-440 업로드 경로와 같은 형태). 조회 경로(상세, 댓글
목록, 피드)에는 이 호출이 **없다**. 가드에 조회용 메서드가 아예 없는 것이 MSG-442가 남긴
설계이며, FR-14가 요구하는 "아카이브 후에도 조회는 된다"의 구조적 보장이다.
가드 자체의 판정선은 2026-08-21 번복으로 `ARCHIVED` 하나가 됐다(위 확정 사항).

### 도움돼요의 사용자당 1회와 멱등

유일성은 애플리케이션 검사가 아니라 복합 기본키 `(video_id, user_id)`가 보장한다. 동시에 두 요청이
들어와도 DB가 하나만 남긴다. **쓰기 두 종은 모두 native 1문장이다.**

- 추가: `INSERT ... ON CONFLICT (video_id, user_id) DO NOTHING`, 반환은 삽입 행 수(0도 성공).
- 취소: `DELETE FROM event_video_helpfuls WHERE video_id = :videoId AND user_id = :userId`
  (`@Modifying @Query(nativeQuery = true)`), 반환은 삭제 행 수(0도 성공).
- 선례가 이 형태를 정해 두었다. `EventNotificationSubscriptionRepository`는 클래스 주석에
  "토글 쓰기는 native 2종(INSERT ON CONFLICT·DELETE)뿐"이라 적고 둘 다 1문장 멱등이라는 근거를
  달아 두었으며, OFF도 native DELETE(`deleteSubscription`)를 쓴다.
  `NotificationOptOutRepository.deleteOptOut`도 같은 형태다.
- **`deleteById`를 쓰지 않는 이유**는 그것이 SELECT 후 DELETE 두 문장이기 때문이다. 같은
  사용자의 동시 취소 두 건이 겹치면 양쪽이 조회에서 행을 보고, flush 시 진 쪽의 DELETE가 0행이
  되어 `StaleStateException`으로 공통 500이 된다. 추가는 `ON CONFLICT DO NOTHING`으로 이미 그
  창을 닫아 두었으므로 취소만 열어 두면 대칭이 깨진다. 두 쓰기가 같은 1문장 멱등이어야 동시
  요청에서 동작이 같다.
- `existsById`는 조회라 그대로 기본 메서드를 쓴다(복합 PK 단건 히트).
- 응답의 `helpfulCount`는 같은 트랜잭션에서 다시 센 값이다. 삽입·삭제 결과로 계산하지 않는
  이유는 동시에 다른 사용자가 누른 경우를 반영해야 하고, 어차피 카운터를 저장하지 않기 때문이다.

### 집계 조회

- 피드(한 페이지 최대 50건): 페이지에 담긴 `videoId` 집합으로 group by 배치 두 번
  (`countCommentsByVideoIds`, `countHelpfulsByVideoIds`). `countVisibleByLocationIds`와 같은
  형태이며 결과를 `Map<Long, Long>`으로 만들어 카드에 채우고, 값이 없는 영상은 0이다. 항목마다
  세면 N+1이라 금지다.
- 상세(단건): 댓글 수 `countByVideo_VideoId`, 도움돼요 수 `countById_VideoId`, 내가 눌렀는지
  `existsById` 각 한 번이다. 비로그인이면 `existsById`를 부르지 않고 false로 둔다(파생 쿼리
  이름의 근거는 아래 데이터 모델의 리포지토리 항목 참조).
- 두 경로가 같은 테이블을 아무 부가 술어 없이 센다. 이것이 US-006의 "목록과 상세가 같은 반응
  데이터"의 구현이다. **카운트 쿼리에 영상 상태 필터를 넣지 않는 근거는 삭제 종류에 따라
  다르다.**
  - **사용자 탈퇴는 하드 삭제**라 반응 행이 실제로 사라진다. 경로가 둘이다. 내가 올린 영상에
    달린 남의 반응은 `users` → `videos` → `event_videos` → 두 반응 테이블 체인으로 지워지고,
    남의 영상에 내가 단 반응은 두 테이블의 `user_id` FK CASCADE로 직접 지워진다
    (`UserRepository`의 탈퇴 CASCADE 경로 주석 참조).
  - **영상 삭제는 소프트 삭제**다. `VideoServiceImpl.deleteVideo`는 행 잠금 후 `markDeleted()`만
    부르므로 `videos` 행도 `event_videos` 행도 남고, 그 영상의 댓글·도움돼요 행도 테이블에
    남는다. 그래도 필터가 필요 없는 이유는 행이 없어서가 아니라 **그 영상을 향한 조회 자체가
    성립하지 않기 때문**이다. 노출 술어가 `VideoStatus.ACTIVE`를 요구하므로 소프트 삭제된
    영상은 상세·피드·댓글 목록 어디에도 잡히지 않고, 반응 변경 API도 같은 술어라 `13406`이다.
    남은 행이 응답에 반영되는 경로가 없으므로 반응 행만 따로 지우는 정리 트랜잭션은 두지
    않는다(소프트 삭제된 영상의 본체 행이 남는 것을 이미 수용한 레포 판단과 같은 결이다).

### 댓글 목록과 커서

정렬은 `id ASC` 하나다. `id`가 `BIGSERIAL` 단조 증가라 작성 순서와 같은 축이고, 유일 키라
타이브레이커가 필요 없다(피드가 `createdAt DESC, id DESC` 두 키를 쓴 것은 서로 다른 영상의
`created_at`이 같을 수 있어서다. 여기서는 정렬 키 자체가 유일하다).

커서는 `EventVideoCommentCursor`(`com.msg.fillmap.event.support`)다. `EventVideoCursor`의 형식과
규칙을 물려받되 성분이 `{videoId}:{commentId}` 둘뿐이라 별도 타입이다(Base64URL opaque 토큰,
디코드 실패는 `RuntimeException`으로 표면화해 서비스가 `INVALID_CURSOR`로 변환). `videoId` 성분은
**발급 영상 바인딩**이다. 다른 영상의 목록 요청에 재사용된 커서를 그대로 받으면 경계값이 남의
keyset[^6]에 오적용돼 결과가 조용히 잘리므로, 서비스가 경로의 `videoId`와 대조해 거부한다.

닉네임은 목록 쿼리에서 함께 읽는다. **세타 조인[^7] + 생성자 프로젝션**이다.

```java
SELECT new com.msg.fillmap.event.repository.EventVideoCommentRow(
	c.id, c.userId, u.nickname, c.content, c.createdAt)
FROM EventVideoComment c, User u
WHERE u.id = c.userId
  AND c.video.videoId = :videoId
ORDER BY c.id ASC
```

`JOIN User u ON ...`이 아니라 이 형태인 것은 컨벤션 조항 때문이다. project-conventions.md의
영속 계층 절이 "연관관계 없는 기존 엔티티에서 조인이 필요하면 종전대로 세타 조인 + 생성자
프로젝션을 쓴다"고 정하고 `FROM Report r, User ru WHERE ru.id = r.reporterId` 선례까지 적어
두었다. 이 댓글 엔티티는 `userId`를 연관으로 매핑하지 않기로 한 스펙 자신의 결정이 있으므로
정확히 그 경우다. 항목마다 닉네임을 따로 읽으면 N+1이고, 매 요청 `users`를 읽는 구조라 닉네임
변경이 다음 조회에 그대로 반영된다(비정규화 사본 없음, MSG-371 선례). 타 도메인 엔티티를
**읽기로만** 참조하는 것도 컨벤션이 허용하는 범위다. 다음 페이지 쿼리는 같은 문장에
`AND c.id > :cursorId`를 더한 형태다.

-- 시각 DEFAULT 는 V33·V40 선례를 따른다: CURRENT_TIMESTAMP 는 timestamptz 라 naive 컬럼
-- 대입 시 세션 타임존으로 변환돼 KST 세션에서 9시간 앞선 값이 저장된다.

	id         BIGSERIAL PRIMARY KEY,
	video_id   BIGINT       NOT NULL REFERENCES event_videos(video_id) ON DELETE CASCADE,
	user_id    BIGINT       NOT NULL REFERENCES users(id) ON DELETE CASCADE,

	-- (JPA save 는 created_at 을 INSERT 컬럼 목록에 포함하므로 DEFAULT 가 적용되지 않는다).
	created_at TIMESTAMP    NOT NULL DEFAULT (statement_timestamp() AT TIME ZONE 'utc')

-- 목록 keyset(video_id = ? ORDER BY id)과 댓글 수 집계가 같이 타는 인덱스
CREATE INDEX idx_event_video_comments_video ON event_video_comments (video_id, id);
-- 탈퇴 CASCADE 조회용. PostgreSQL 은 참조 측 FK 컬럼을 자동 인덱싱하지 않아, 없으면 사용자

CREATE TABLE event_video_helpfuls (
	video_id   BIGINT    NOT NULL REFERENCES event_videos(video_id) ON DELETE CASCADE,

	-- (댓글은 JPA save 경로라 팩터리가 채운다. 두 테이블의 차이가 여기서 갈린다).
	created_at TIMESTAMP NOT NULL DEFAULT (statement_timestamp() AT TIME ZONE 'utc'),

	-- 사용자당 1회를 DDL 이 보장한다. video_id 선두라 영상별 집계가 이 PK 인덱스를 탄다

엔티티와 리포지토리:

- `EventVideoComment`(`com.msg.fillmap.event.entity`): `@Id @GeneratedValue(IDENTITY) Long id`,
  `@ManyToOne(fetch = LAZY, optional = false) @JoinColumn(name = "video_id") EventVideo video`,
  `Long userId`, `String content`,
  `@Column(name = "created_at", nullable = false, updatable = false) LocalDateTime createdAt`.
  내용 수정은 `updateContent(String)` 도메인 메서드의 더티 체킹으로 한다. `userId`를 연관으로
  매핑하지 않는 것은 이 엔티티를 축으로 `User`를 타고 갈 일이 없어서다(닉네임은 목록 쿼리가
  세타 조인으로 읽는다).

  **`createdAt`은 정적 팩터리가 채운다.**
  `EventVideoComment.create(EventVideo video, long userId, String content, LocalDateTime now)`가
  `this.createdAt = now.truncatedTo(ChronoUnit.MICROS)`를 대입한다. 세 가지가 이 형태를 강제한다.
  ① JPA `save()`는 `created_at`을 INSERT 컬럼 목록에 포함하므로 필드가 null이면 DDL의 `DEFAULT`가
  적용되지 않고 `NOT NULL` 위반으로 **댓글 작성이 전량 실패**한다(형제 테이블
  `event_notification_subscriptions`가 DEFAULT에 기대는 것은 그쪽이 native upsert 경로여서다).
  ② `@CreationTimestamp`를 쓰지 않는 이유는 그것이 JVM 기본 존의 벽시계를 만들어 KST 개발
  머신에서 9시간 앞선 값을 저장하기 때문이다(`Report.createdAt` 주석이 같은 근거를 남겨 두었다).
  ③ 엔티티가 스스로 `now`를 읽지 않고 **서비스가 넘긴 `now`를 인자로 받는다.** 위 확정 사항의
  "판정 시각은 서비스가 한 번 고정한다"를 따르면 한 요청 안에서 가드 판정 시각과 댓글 시각이 같은
  축이 된다. 마이크로초 절단은 DB TIMESTAMP 정밀도에 맞추는 것으로, 리눅스 나노초 시계에서 저장
  후 재조회 값과 응답 값이 어긋나지 않게 한다(`Report` 선례와 같은 처리).
- `EventVideoHelpful` + `EventVideoHelpfulId`(`@EmbeddedId`, `videoId`·`userId`): `createdAt`.
  연관관계를 달지 않는다. 이 엔티티를 축으로 한 조인 조회가 없고(집계는 count, 판정은
  `existsById`) `EventNotificationSubscription`과 같은 형상이다. **`equals`/`hashCode`를 갖춘
  복합키 클래스**여야 `existsById`가 동작한다(MSG-442가 같은 계약을 테스트로 고정해 둔 선례가
  있다). 삽입이 native `ON CONFLICT` 경로라 `createdAt`은 DB DEFAULT가 채운다.
- `EventVideoCommentRepository`: 첫 페이지·다음 페이지 목록(세타 조인 + 생성자 프로젝션, 위 도메인
  로직 참조), 단건 댓글 수 `countByVideo_VideoId(Long videoId)`, group by 배치
  `countCommentsByVideoIds`, `findById`.
- `EventVideoHelpfulRepository`: native 쓰기 2종(`insertHelpful` upsert, `deleteHelpful` DELETE,
  위 도메인 로직 참조), `existsById`, 단건 도움돼요 수 `countById_VideoId(Long videoId)`,
  group by 배치 `countHelpfulsByVideoIds`.
- **파생 쿼리 이름은 프로퍼티 경로 표기를 그대로 따른다.** 두 엔티티 모두 식별자 프로퍼티 이름이
  관례와 다르기 때문이다. `EventVideo`의 식별자 필드는 `id`가 아니라 `videoId`라 댓글에서
  영상으로 가는 경로가 `video.videoId`(`countByVideo_VideoId`)이고, `EventVideoHelpful`은
  `@EmbeddedId id` 안에 값이 있어 경로가 `id.videoId`(`countById_VideoId`)다. 밑줄로 경로 경계를
  명시하지 않으면 스프링 데이터가 프로퍼티를 풀지 못해 **애플리케이션 기동 시 리포지토리 초기화가
  실패한다**(런타임에 조용히 틀리는 종류가 아니라 바로 깨진다). 도움돼요의 `existsById`는
  `CrudRepository`가 `@EmbeddedId` 값을 그대로 받는 기본 메서드라 이 규칙과 무관하다. group by
  배치 두 개는 `@Query` JPQL이라 이름 규칙 밖이고, 그래서 이름을 읽기 쉬운 형태로 지었다.
- 서비스는 새 클래스다. `EventVideoInteractionService`/`Impl`(`com.msg.fillmap.event.service`),
  컨트롤러도 새 클래스 `EventVideoInteractionController`. **`EventVideoServiceImpl`에 얹지 않는
  이유**는 그 클래스의 생성자를 MSG-440 테스트들이 직접 호출하고 있어, 리포지토리 두 개를 더하면
  기존 테스트가 전부 시그니처 수정 대상이 되기 때문이다. 관심사도 다르다(업로드·조회 대 반응).
  다만 상세 응답의 새 필드 네 개는 `EventVideoServiceImpl.getVideoDetail` 안에서 채워야 하므로,
  그 클래스는 `EventVideoInteractionService`를 **읽기 목적으로 주입받는다**(집계 조회와 댓글 첫
  페이지). 이때 생성자가 바뀌므로 440 테스트의 생성자 호출부 수정이 한 번 필요하다. 피드 쪽
  집계도 같은 서비스를 통한다.

[^1]: 멱등(idempotent): 같은 요청을 여러 번 보내도 한 번 보낸 것과 결과가 같은 성질. 도움돼요
    추가·취소가 이 성질을 가져야 네트워크 재시도가 수를 흔들지 않는다.
[^2]: 비정규화 카운터: 집계 값을 셀 때마다 세지 않고 별도 컬럼에 미리 적어 두는 방식. 읽기는
    빨라지지만 원천 행이 다른 경로로 지워질 때 값이 어긋난다(드리프트). 이 스펙은 채택하지 않았다.
[^3]: 존재 은닉: 볼 권한이 없는 리소스에 "권한 없음"이 아니라 "없음"으로 답해, 순차 id를 대입해
    보는 것만으로 리소스의 존재 여부를 알아내지 못하게 하는 응답 정책. 행사 도메인은 미노출
    회차와 비공개 영상에 이 정책을 쓴다.
[^4]: 반개구간: 시작점은 포함하고 끝점은 제외하는 구간 표기. 경계 정각이 정확히 한 상태에만
    속해 상태 판정에 빈틈과 겹침이 없다. 정의는 `EventOccurrence.statusAt` 한 곳이다.
[^5]: fetch join: 조회 한 번으로 연관 엔티티까지 함께 읽어 오는 JPQL 문법. 나중에 필요할 때
    다시 읽는 지연 로딩과 달리 왕복이 한 번이라, 조회 직후 반드시 쓰는 연관에 쓴다.
[^6]: keyset 페이지네이션: 몇 번째 행부터인지(offset)가 아니라 마지막으로 본 행의 키 값을
    기준으로 다음 페이지를 읽는 방식. 페이지를 넘기는 사이 행이 늘거나 줄어도 중복과 누락이
    생기지 않는다.
[^7]: 세타 조인: 엔티티끼리 매핑된 연관을 타지 않고, FROM 절에 두 엔티티를 나란히 둔 뒤 WHERE로
    조건을 걸어 잇는 조인. 연관관계를 만들지 않은 도메인 사이를 읽기로만 이을 때 쓴다.

**데이터 저장 위치**

- `event_video_comments` — `id BIGSERIAL PK` · `video_id BIGINT NOT NULL → event_videos(video_id) ON DELETE CASCADE` ·

  **DEFAULT는 운영 중 수동 INSERT용 안전망일 뿐 실제로 발동하지 않는다** — JPA `save()`가 `created_at`을
  INSERT 컬럼 목록에 넣기 때문이고(아래 실행 쿼리의 insert 문 참조), 실저장값은 정적 팩터리가 넣은

- `event_video_helpfuls` — `PRIMARY KEY (video_id, user_id)` · 두 컬럼 모두 위와 같은 FK CASCADE ·
  `created_at TIMESTAMP NOT NULL DEFAULT (statement_timestamp() AT TIME ZONE 'utc')`.
  이쪽은 native INSERT가 컬럼을 생략하므로 **DEFAULT가 실저장값**이다. 두 테이블의 차이가 여기서 갈린다.

  `idx_event_video_comments_user (user_id)`(탈퇴 CASCADE 조회) ·
  `event_video_helpfuls_pkey (video_id, user_id)`(**video_id 선두**라 영상별 집계가 PK를 탄다) ·
  `idx_event_video_helpfuls_user (user_id)`(PK 선두가 video_id라 user_id 단독 조회를 못 타서 따로 둔다).

**실행 쿼리** (Hibernate `show_sql` 실측, 2026-08-21. 파라미터는 `?`)

1. 노출 판정 `findVisibleWithOccurrence` — JOIN FETCH 둘이 실제로 한 문장으로 접히고 회차 컬럼까지 함께 실린다.
   ```sql
   select ev1_0.video_id, ev1_0.event_occurrence_id, ev1_0.event_location_id,
          l1_0.id, l1_0.display_order, l1_0.location_key, l1_0.name, l1_0.event_occurrence_id,
          o1_0.id, o1_0.city_name, o1_0.ends_at, o1_0.max_grid_x, o1_0.max_grid_y, o1_0.min_grid_x,
          o1_0.min_grid_y, o1_0.occurrence_key, o1_0.schedule_revision, o1_0.event_series_id,
          o1_0.starts_at, o1_0.title, o1_0.visible_from,
          l1_0.operating_hours, l1_0.representative_grid_id, l1_0.type
   from event_videos ev1_0
   join event_locations l1_0 on l1_0.id=ev1_0.event_location_id
   join event_occurrences o1_0 on o1_0.id=l1_0.event_occurrence_id
   join videos v1_0 on v1_0.id=ev1_0.video_id
   where ev1_0.video_id=? and v1_0.status='ACTIVE' and v1_0.visibility='PUBLIC'
     and v1_0.processing_status='READY'
   ```
   enum 셋이 바인드 파라미터가 아니라 **리터럴로 박혀 나간다**(JPQL에 상수로 적었기 때문). 회차 노출 은닉은
   이 SQL이 아니라 다음 줄의 `EventOccurrence.isVisibleAt(now)` 자바 판정이라 WHERE에 없다.
2. 댓글 목록(세타 조인 + 생성자 프로젝션) — `cross join`이 아니라 콤마 조인 그대로 나간다.
   ```sql
   -- 첫 페이지
   select evc1_0.id, evc1_0.user_id, u1_0.nickname, evc1_0.content, evc1_0.created_at
   from event_video_comments evc1_0, users u1_0
   where u1_0.id=evc1_0.user_id and evc1_0.video_id=?
   order by evc1_0.id fetch first ? rows only
   -- 다음 페이지 (keyset 경계 한 줄만 추가)
   ... and evc1_0.video_id=? and evc1_0.id>? order by evc1_0.id fetch first ? rows only
   ```
   `fetch first ? rows only`의 값은 서비스가 넘긴 **size+1**(lookahead)이다. `LIMIT`이 JPQL에 없고
   `PageRequest.of(0, pageSize + 1)`이 만든다.
3. 도움돼요 native 2종 (원문 그대로, `@Modifying @Query(nativeQuery = true)`)
   ```sql
   INSERT INTO event_video_helpfuls (video_id, user_id) VALUES (:videoId, :userId)
   ON CONFLICT (video_id, user_id) DO NOTHING;

   DELETE FROM event_video_helpfuls WHERE video_id = :videoId AND user_id = :userId;
   ```
   둘 다 1문장이라 반환 행 수 0도 성공이다. `deleteById`였다면 SELECT + DELETE 2문장이라 동시 취소에서
   진 쪽이 `StaleStateException` 500이 된다(회귀 가드: `EventVideoHelpfulConcurrencyTest`).
4. 피드 group by 배치 집계 — 페이지의 videoId 집합 하나로 각각 1회, 항목 수와 무관하게 왕복 2회다.
   ```sql
   select evc1_0.video_id, count(evc1_0.id) from event_video_comments evc1_0
   where evc1_0.video_id in (?,?) group by evc1_0.video_id

   select evh1_0.video_id, count(*) from event_video_helpfuls evh1_0
   where evh1_0.video_id in (?,?) group by evh1_0.video_id
   ```
5. 파생 쿼리 3종(밑줄 경로 표기가 실제로 만드는 SQL)
   ```sql
   -- countByVideo_VideoId(Long) : 경로 video.videoId 가 FK 컬럼 하나로 접혀 조인이 없다
   select count(evc1_0.id) from event_video_comments evc1_0 where evc1_0.video_id=?
   -- countById_VideoId(Long) : @EmbeddedId 안의 값도 컬럼 하나로 접힌다
   select count(*) from event_video_helpfuls evh1_0 where evh1_0.video_id=?
   -- existsById(EventVideoHelpfulId) : 복합키가 행 비교 튜플로 나간다 (컬럼 순서는 Hibernate 결정)
   select count(*) from event_video_helpfuls evh1_0 where (evh1_0.user_id,evh1_0.video_id)=(?,?)
   ```
6. 댓글 쓰기 3종
   ```sql
   insert into event_video_comments (content, created_at, user_id, video_id) values (?, ?, ?, ?)
   select evc1_0.id, evc1_0.content, evc1_0.created_at, evc1_0.user_id, evc1_0.video_id
     from event_video_comments evc1_0 where evc1_0.id=?     -- findById (수정·삭제 서두)
   delete from event_video_comments where id=?
   ```
   수정의 `update ... set content=?`는 **테스트 로그에 나타나지 않는다** — `@Transactional` 롤백이라
   flush가 없고, 같은 영속성 컨텍스트에서 `findById`가 1차 캐시로 히트해 자동 flush 트리거도 없기 때문이다.
   운영은 요청마다 트랜잭션이 새로 열려 커밋 시 더티 체킹 UPDATE가 나간다.

**빈 동작**

- `EventVideoInteractionServiceImpl` — `@Service` 싱글턴, 생성자 2개(`@Autowired` 프로덕션은
  `Clock.systemUTC()` 고정, 전체 생성자는 경계 정각 검증용 고정 클럭 주입. `EventVideoServiceImpl` 선례).
  트랜잭션 경계는 메서드 단위로, 쓰기 5개가 `@Transactional`, 읽기 3개(`getComments`·`getDetailReactions`·
  `countReactions`)가 `@Transactional(readOnly = true)`다. `LocalDateTime.now(clock)`은 **경로당 한 번만**
  호출해 가드 판정 시각과 댓글 `createdAt`이 같은 값이 되게 한다.
- `helpfulCount`는 native 쓰기 **직후 같은 트랜잭션에서 다시 센다**(`countById_VideoId`). native 문장이
  커넥션에 바로 나가 있으므로 뒤이은 JPQL count가 그 결과를 본다. 삽입·삭제 반환 행 수로 계산하지 않는
  이유는 그 사이 다른 사용자가 누른 것도 반영해야 하고 카운터를 저장하지 않기 때문이다.
- `EventVideoInteractionController` — `@RestController` + `@RequiredArgsConstructor` 싱글턴, 자체 트랜잭션 없음
  (컨트롤러는 파싱·위임·`SuccessResponse.of`만). 삭제 2종은 `SuccessResponse<Void>`로 data 없이 200이다.
- **호출 관계는 단방향이다.** `EventVideoServiceImpl`(상세·피드)이 `EventVideoInteractionService`를 주입받고,
  반응 서비스는 상세·피드 어느 것도 참조하지 않는다 — **순환 의존 없음**(스프링 기동 시 순환 감지에 걸리지
  않는 것으로 확인). 상세는 `getVideoDetail`(`@Transactional`, 조회수 UPDATE 때문에 readOnly 아님) 안에서
  반응 서비스의 readOnly 메서드를 호출하므로 **바깥 쓰기 트랜잭션에 참여**한다(`REQUIRED` 기본 전파 —
  안쪽 `readOnly = true`는 이미 열린 트랜잭션에서는 무시된다). 자기 호출 함정은 없다(빈 경계를 넘는 호출).
- 피드는 페이지 트림 뒤 `countReactions(videoIds)` **1회**만 부른다. 빈 페이지면 리포지토리를 아예 타지 않고
