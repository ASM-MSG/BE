# MSG-162: 영상 공개 범위 설정 API (visibility PUBLIC/PRIVATE 전환)

**Owner**: B (`com.msg.fillmap.video.*`) — videos 테이블 = Owner B 도메인. grid 패키지 무수정.

> 에픽: 지도 탐색 / 공개 노출. **MSG-87(격자 전역 대표 영상)의 치명적 선행 과제**를 해소하는 티켓이다.
> MSG-87 스펙 §선행 과제가 지목한 그대로: `videos.visibility` 기본값이 `PRIVATE`(`V1__init.sql:94`)이고
> 공개 전환 API가 없어 `findGlobalCover`(필터 `visibility='PUBLIC'`)가 **실데이터로는 항상 null**을 반환한다.
> 위키 `03-specs/FillMap API 설계 v2 draft.md` §선행 과제도 "MSG-162 미구현 — 전역 대표/목록이 항상 빈 결과"로 기록.
> 이 티켓은 **순수 Owner B**다. 계약 인터페이스 시그니처 변경 없음(§계약 변경) → 상대 팀 확인 불필요.

## 개요

영상 소유자가 자기 영상의 공개 범위(`visibility`)를 **PUBLIC ↔ PRIVATE**로 전환하는 write API 1종을 만든다.
전환 결과가 곧바로 MSG-87 대표 영상 쿼리의 노출 대상(`visibility='PUBLIC'`)을 채워, 지금은 죽어 있는
전역 노출 경로 전체(대표 영상 → 향후 전역 목록·좋아요)를 살아나게 하는 최소 잠금해제 티켓이다.

```
[현재]  업로드 → visibility=PRIVATE 고정 (Video.create, Video.java:119) → 공개 전환 수단 없음 → 전역 노출 0건
[MSG-162] PATCH .../visibility → PRIVATE↔PUBLIC 전환 → 공개 영상 생성 → MSG-87 대표 API 실데이터 작동
```

## 배경 · 목표

- **사용자/제품 관점**: 영상은 업로드 후 수정·삭제가 자유롭다(glossary "영상"). 공개 여부도 그런
  사후 조정 대상이어야 한다 — 내 도감에만 두던 영상을 나중에 공개로 돌리거나 다시 비공개로 내리는 흐름.
- **목표**: video 도메인 안에서 완결되는 소유자 전용 visibility 전환 API를 제공한다. 소유권 검증은
  기존 `findOwnedVideo` + `VIDEO_FORBIDDEN(3403)`을 재사용하고, 신규 마이그레이션 없이(컬럼·CHECK 존재)
  도메인 mutator 하나만 추가한다. 이 API가 배포돼야 MSG-87이 실사용자 화면에서 실제로 작동한다.

## 성공 기준

1. `PATCH /api/videos/{videoId}/visibility`가 body `{"visibility":"PUBLIC"}`(또는 `"PRIVATE"`)를 받아
   해당 영상의 `visibility`를 그 값으로 전환하고, 전환된 상태를 `VideoVisibilityResponseDto`로 반환한다.
2. **소유권 검증**: 타인 영상 전환 시 `VIDEO_FORBIDDEN(3403)`, 존재하지 않는 videoId면 `VIDEO_NOT_FOUND(3404)`.
   (둘 다 기존 `findOwnedVideo` 경로 재사용 — 신규 소유권 코드 없음.)
3. **미지 값 방어**: `PUBLIC`/`PRIVATE` 외 값·빈 값은 500이 아니라 **BAD_REQUEST**로 응답한다(§도메인 2).
4. **업로드 기본값 불변**: 업로드는 계속 PRIVATE로 생성된다(`Video.create` 무변경). 업로드 request에
   visibility 필드를 추가하지 않는다(§설계 M3).
5. **processing_status 무관하게 전환 허용**: UPLOADED/ENCODING/BLURRING/FAILED 영상도 PUBLIC으로 전환
   가능하다. 실제 노출은 read 경로(`findGlobalCover` 등)가 `processing_status='READY'`로 강제한다(§도메인 3).
6. **멱등**: 이미 PUBLIC인 영상을 다시 PUBLIC으로 전환하면 에러 없이 200 + 현재 상태(§도메인 5).
7. **삭제된 영상은 전환 불가**: DELETED 영상 전환 시 `VIDEO_NOT_FOUND`(replaceVideo 선례와 동일, §도메인 4).
8. 전환 후 그 격자에 `GET /api/grids/{gridId}/cover`(MSG-87)를 호출하면, PRIVATE만 있어 null이던 격자가
   READY·PUBLIC 조건을 만족하는 순간 대표 영상을 실데이터로 반환한다(티켓 완료 조건 검증).
9. 응답은 `SuccessResponse.of(...)`로 감싸 HTTP 200 + `developCode 200`. Flyway 마이그레이션 없이 전체 테스트 green.

## 설계 결정 (근거 포함)

| # | 포인트 | 결정 | 한 줄 근거 |
|---|---|---|---|
| M1 | 엔드포인트·메서드 | **`PATCH /api/videos/{videoId}/visibility`** | 필드 하나의 상태 전이 = 부분 수정이라 PATCH가 정직한 동사다. `PUT /{videoId}`는 이미 **파일 전체 교체** 의미로 점유돼 있어(MSG-71) 재사용하면 멘탈모델이 충돌한다. `/{videoId}/visibility` 서브패스가 "이 영상의 공개상태를 바꾼다"로 FE에 명료. PATCH 전례 부재는 제약이 아니라 "부분수정이 아직 없었을 뿐" — Spring `@PatchMapping` 네이티브 지원. *대안(동치): `PUT .../visibility`(멱등값으로 서브리소스 전체 치환) — 동작 무차이, 리뷰에서 교체 가능.* |
| M2 | 요청 형태·미지 값 | **body `{"visibility": "..."}`, 필드는 `String` + `@NotBlank`, 서비스에서 `Visibility.valueOf(toUpperCase())` try/catch → 신규 `VideoErrorCode.INVALID_VISIBILITY`(34xx, BAD_REQUEST)** | `GlobalExceptionHandler`에 `HttpMessageNotReadableException` 핸들러가 **없다**(검증함) → 필드를 `Visibility` enum으로 받으면 잘못된 값이 Jackson 역직렬화 실패 → generic `Exception` → **500**(입력 오류인데 5xx). `AuthController.parseProvider`(문자열→valueOf→`UNSUPPORTED_PROVIDER`, response-pattern.md 예시)가 코드베이스의 확립된 패턴이라 그대로 따라 깔끔한 4xx를 준다. *신규 코드 예: `INVALID_VISIBILITY(3420, HttpStatus.BAD_REQUEST, "visibility 는 PUBLIC 또는 PRIVATE 여야 합니다")` — 번호는 34xx 미사용값, 리뷰 확정.* |
| M3 | 업로드 시 선택 | **추가 안 함 — 전환 API만.** 업로드는 PRIVATE 기본값 유지 | PRD `03-specs/PRD FillMap MVP 화면별 기능·API.md` §4가 "도감 공개 범위(공개/비공개 2단?)"를 **MVP 미확정**으로 명시 — 업로드 화면(⑥)에 확정된 공개선택 UX가 없다. 확정 안 된 정책의 기본값을 지금 request에 박으면 나중에 PRD와 어긋난다(YAGNI). 기본 PRIVATE는 프라이버시 안전값(glossary Phase 2+ "누가 어디 갔는지 노출 방지"). 전환 API만으로 MSG-87 잠금해제에 충분. 업로드 토글이 PRD에서 확정되면 그때 필드 추가. |
| M4 | processing_status 관계 | **미READY 영상도 PUBLIC 전환 허용. 노출은 read 경로가 READY로 게이트** | visibility는 *의도*("공개하고 싶다"), processing_status는 *준비도*("볼 수 있나") — 코드가 이미 별 컬럼으로 분리하고 부분 인덱스가 둘을 AND로 묶는다. 전환에 READY 게이트를 걸면 read 경로가 이미 가진 규칙을 write에서 중복하는 것이고, 업로드 직후 공개하려는 사용자가 블러 완료(~3~4분)까지 못 켜거나 FAILED면 영영 못 켜는 나쁜 UX가 된다. "미블러 PUBLIC이 잠복 지뢰" 우려의 옳은 가드는 **read 경계**다 — `findGlobalCover`가 이미 `processing_status='READY'`로 증명한 패턴. 노출 쿼리마다 READY를 지게 하는 게 단일 진실 원천이고 부분 인덱스가 물리적으로 강제한다. write 게이트는 "공유 함수 대신 모든 호출부에 가드" 안티패턴. → §도메인 3에 "모든 공개 노출 쿼리는 `processing_status='READY'`를 강제한다" MUST 명문화. |
| M5 | 멱등성 | **같은 값 재전환 = 200 + 현재 상태(에러 아님)** | PATCH/PUT는 정의상 멱등. 현재값으로의 세팅은 성공적 no-op이고, JPA dirty-check가 값이 같으면 UPDATE도 생략한다. `deleteVideo`의 "중복 삭제는 멱등하게 성공"(MSG-72 D7)과 같은 태도. "이미 PUBLIC" 전용 에러코드 불필요. |
| M6 | 응답 DTO | **신규 `VideoVisibilityResponseDto(videoId, visibility)` + `from(Video)` 정적 팩터리** | FE가 토글 UI를 확정 상태로 갱신하려면 전환 결과를 돌려받아야 한다. 최소 2필드. `VideoReplaceResponseDto.from(video)` 네이밍·팩터리 패턴과 동일. visibility는 `video.getVisibility().name()`(String)으로 내보낸다. |

**티켓 제목("PUBLIC 전환") vs 완료 조건("PUBLIC/PRIVATE 전환") 불일치**: 완료 조건을 정본으로 삼아
**양방향 전환**을 구현한다(제목이 더 좁을 뿐, 상충 아님).

## API 명세

인증: 로그인 필수(`@AuthenticationPrincipal AuthPrincipal principal` → `principal.userId()`, 기존 컨트롤러와 동일). 미인증은 SecurityConfig가 401.

### `PATCH /api/videos/{videoId}/visibility` — 영상 공개 범위 전환

- Path: `videoId` (Long)
- Request: `VideoVisibilityRequestDto`

  | 필드 | 타입 | 제약 | 의미 |
  |---|---|---|---|
  | `visibility` | String | `@NotBlank` | `"PUBLIC"` 또는 `"PRIVATE"`. 대소문자는 `toUpperCase()`로 흡수 |

  ```json
  { "visibility": "PUBLIC" }
  ```

- 성공 200 `body` = `VideoVisibilityResponseDto`

  | 필드 | 타입 | 의미 |
  |---|---|---|
  | `videoId` | Long | 전환된 영상 id |
  | `visibility` | String | 전환 후 공개 범위 (`"PUBLIC"`/`"PRIVATE"`) |

  ```json
  { "developCode": 200, "httpStatus": "OK", "message": "성공",
    "body": { "videoId": 1042, "visibility": "PUBLIC" } }
  ```

**에러**

| 상황 | developCode | HTTP | 코드 |
|---|---|---|---|
| `visibility`가 PUBLIC/PRIVATE 아님·빈 값 | 3420(제안) / 400 | 400 | `INVALID_VISIBILITY`(신규) 또는 `@NotBlank` 검증 실패 시 `BAD_REQUEST(400)` |
| 타인 영상 | 3403 | 403 | `VIDEO_FORBIDDEN`(재사용) |
| 없는 videoId / 삭제된 영상 | 3404 | 404 | `VIDEO_NOT_FOUND`(재사용) |
| 미인증 | — | 401 | SecurityConfig |

## 도메인 로직

### 1. 전환 흐름 (write)

1. `findOwnedVideo(userId, videoId)`로 소유권 검증(없으면 `VIDEO_NOT_FOUND`, 주인 다르면 `VIDEO_FORBIDDEN`).
2. `video.isDeleted()`면 `VIDEO_NOT_FOUND`(§도메인 4).
3. 요청 문자열을 `Visibility`로 파싱 — 실패 시 `INVALID_VISIBILITY`(§도메인 2).
4. `video.changeVisibility(parsed)` 도메인 mutator로 필드 전환(JPA 변경감지로 UPDATE, 값 같으면 no-op).
5. `VideoVisibilityResponseDto.from(video)` 반환.

`@Transactional`(readOnly=false). grid/region 파생 없음 — 도감·점령·수집률과 무관(visibility는 노출 축이지 점령 축이 아니다).

### 2. 미지 값 = 4xx (500 방지)

- request 필드를 `Visibility` enum으로 직접 받으면 잘못된 값이 `HttpMessageNotReadableException` → (전용 핸들러 부재) → 500이 된다. 이를 피하려 **String으로 받아 서비스에서 파싱**한다.
- 파싱은 `AuthController.parseProvider`(`AuthProvider.valueOf(provider.toUpperCase())` catch → `UNSUPPORTED_PROVIDER`) 선례를 그대로 따라 `IllegalArgumentException`을 잡아 `new ApiException(VideoErrorCode.INVALID_VISIBILITY)`로 변환한다.
- *리뷰 노트(스코프 밖)*: `GlobalExceptionHandler`에 `HttpMessageNotReadableException` 핸들러를 추가하면 잘못된 JSON body가 전역적으로 400이 되어 이 잠재 500이 근본 해소되나, 공유 핸들러 변경은 다른 엔드포인트 동작에 영향을 주므로 본 티켓 스코프 밖. 여기선 도메인 로컬 패턴을 택한다.

### 3. 노출 게이트는 read 경계에만 (write는 자유)

- visibility 전환에는 `processing_status` 게이트를 걸지 않는다. 미READY 영상을 PUBLIC으로 둘 수 있다.
- **공개 노출은 전적으로 read 쿼리 책임**: `findGlobalCover`(MSG-87)가 `status='ACTIVE' AND visibility='PUBLIC' AND processing_status='READY'`로 이미 게이트하고, `idx_videos_grid_popular` 부분 인덱스가 이 조건을 물리적으로 강제한다.
- **MUST(후속 티켓 구속)**: 향후 전역 영상 목록·좋아요 등 **모든 공개 노출 쿼리는 `processing_status='READY'`를 반드시 포함**한다. 이 규칙을 빠뜨리면 미블러 영상이 노출되는 사고가 난다 — 게이트의 단일 진실 원천은 이 read 필터와 부분 인덱스다.

### 4. 삭제된 영상 가드 (선례 일치)

- `findOwnedVideo`는 status 무관하게 row를 돌려준다. `replaceVideo`가 삭제 영상을 `VIDEO_NOT_FOUND`로 막는 것(`VideoServiceImpl.java:119`)과 **똑같이** setVisibility도 `video.isDeleted()`면 `VIDEO_NOT_FOUND`. 지운 영상을 공개로 되살리는 경로를 열지 않는다.
- BLINDED(신고 블라인드)는 **스코프 밖** — 모더레이션 미구현(PRD: reports 테이블만). 본 티켓은 DELETED만 가드한다.

### 5. 멱등

- 현재값과 같은 값으로 전환하면 도메인 mutator가 같은 값을 세팅 → JPA가 UPDATE를 생략(또는 무해한 동일 UPDATE) → 200 + 현재 상태. 전용 에러 없음.
