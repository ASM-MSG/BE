# MSG-514: AI 경로 추천의 관심사 반영과 추천 이유 개선

**Owner**: 공동 (주 구현 B, MSG-457 §Owner 판정. 이번 변경 파일은 전부 route 패키지와 그 테스트라 A 몫 구현은 없다)

> 요구사항 정본: `docs/prd/MSG-514-prd.md` (검토됨, 2026-08-31 성민 승인)
> SRS: FR-ROUTE-18 신설(계획), FR-ROUTE-05 개정(진행 중). FR-ROUTE-03, FR-ROUTE-06, FR-ROUTE-07, FR-ROUTE-10은 유지 확인 대상이다.

## 개요

관심사[^1] 반영을 글자 겹침 판정에서 동의어 사전[^3] 기반 의미 판정으로 넓히고, 추천 이유의 재료인
사실 목록[^2]에 지점 고유 사실을 더한다. 관심사 일치 지점이 동선 앞쪽에 오도록 순서 규칙도 함께
고친다. 외부 호출 수(해석 1, 문장화 1, 장소 검색 최대 1)와 AI 계약, 응답 계약은 그대로다.

## 배경 · 목표

같은 화면에서 문장만 바꿔도 같은 여덟 지점이 같은 이유와 함께 돌아온다. 관심사 판정이
`contains` 하나라 "맛집" 두 글자가 제목이나 소개문에 없으면 반영이 안 되고, 사실 목록 세 칸 중
두 칸(출처, 기간)은 요청과 무관해 이유가 일반론이 된다. 사용자가 적은 문장이 지점 선정과 이유에
실제로 반영되게 하는 것이 목표다.

## 성공 기준

1. FR-4 고정 테스트가 통과한다: 같은 화면에서 관심사가 다른 두 문장은 다른 지점 구성이나
   순서를 돌려준다.
2. FR-5 사례 테스트가 통과한다: "맛집" 관심사가 음식과 무관한 해안 산책 코스에 일치로 붙지 않는다.
3. 지표 로그에 관심사 수와 일치 지점 수가 남고, 기준선 입력 세트 재실행에서 일치 비율이 개선 전
   실측(결정 5)보다 오른다.
4. 코스 지점의 이유에 거리와 시간과 난이도가, 축제와 팝업 지점의 이유에 장소나 소개가 재료로
   실린다. 응답 계약(points, notice, mentionedArea)과 행사 지점의 기존 구성은 변하지 않는다.

## 결정 (PRD 미해결 5건의 해소)

### 결정 1. 이어짐 판정은 동의어 사전으로 한다 (임베딩 기각)

서버 안에 두는 동의어 사전으로 판정한다. 관심사 원문 포함 판정(기존)을 유지하고, 그 위에 사전
경유 판정을 더한다.

- 근거: 외부 호출 수 불변(비기능 성능)과 결정성[^5](FR-ROUTE-10)을 코드 구조로 자동 충족한다.
  사전은 배포 아티팩트에 고정되고 판정은 순수 함수라 같은 해석과 같은 후보면 같은 결과다.
  후보 재료가 수십 건, 근거어[^4]가 수백 건 규모라 판정 비용은 메모리 문자열 검색 밀리초
  미만이고 응답 시간 예산(25초, MSG-457 상한 확정 절)에 보태는 시간이 없다.
- 기각: 임베딩. 외부 모델 호출이 늘어 호출 수 불변 요구와 정면 충돌하고, 모델 교체 때마다 판정이
  달라져 결정성 재검증이 따라온다. PRD 권고("사전 방식 부족의 실측이 나오기 전까지 꺼내지
  않는다")를 그대로 채택한다.

### 결정 2. 사전 데이터는 classpath 리소스 파일로 둔다 (DB, 코드 상수 기각)

`src/main/resources/route/interest-synonyms.json` 한 파일이 정본이다. 갱신 주체는 백엔드(주 구현
B)이고 갱신은 파일 수정과 배포다. 기동 시 1회 로드해 불변 구조로 보관하고, 로드 실패나 스키마
위반은 기동 실패로 처리한다(조용한 미적용이 커버리지 하락으로 잠복하는 것을 막는다).

- 근거: 항목 추가가 데이터 파일 diff 하나로 끝나 리뷰에서 규칙 변경과 데이터 추가가 파일 단위로
  갈린다. 수십 개 개념과 수백 개 근거어는 코드에 두면 클래스가 데이터 덤프가 된다.
  `seed/zones.json`과 같은 결의 선례다. 리소스 선택으로 Flyway 변경 없음이 확정된다.
- 기각: DB 테이블(마이그레이션과 관리 경로가 생기는데 갱신 주체가 개발자뿐이라 배포 대비 얻는
  것이 없다), 코드 상수(항목 수백 개 규모의 데이터가 코드에 묻힌다).
- 초기 커버리지: 개념 15개 내외로 시작한다. 후보 개념은 맛집, 카페, 야경, 바다, 산책, 등산,
  역사, 전시, 공연, 시장, 사진, 축제, 팝업, 데이트, 가족이다. 근거어는 상상으로 짓지 않고 dev
  시드(축제, 코스, 팝업)의 제목과 소개문과 장소명에 실제로 나오는 말에서 뽑는다. 개념당 근거어
  5건 이상을 하한으로 한다.

### 결정 3. 사실 목록 다섯 칸의 우선순위는 출처, 관심사, 지점 고유(최대 2건), 기간 순이다

지점 고유 사실을 2건으로 캡하면 총합이 정확히 5라 산술적으로 절단이 일어나지 않는다. 그래도
`limit(5)` 방어는 유지하고, 절단은 뒤에서부터 일어나므로 조립 순서가 곧 생존 우선순위다.

- 근거: PRD가 지적한 일반론의 원인이 출처와 기간이다. 요청마다 달라지는 재료(관심사, 고유
  사실)를 앞에 두고 가장 일반적인 재료(기간)를 마지막에 두면, 규칙이 더 늘어나는 미래에도
  일반론부터 잘린다. 출처가 첫째인 것은 사실 하한 1건 보장(AI 계약)의 상시 항목이라서다.
- 기각: 기간을 관심사보다 앞에 유지(현행 순서). 칸이 모자랄 때 이 티켓의 핵심 산출인 관심사
  표기(FR-7)가 먼저 잘리는 역전이 생긴다.

### 결정 4. preferred_order 힌트는 이번에 확장하지 않는다

순서 힌트 판정은 기존 상호 부분 문자열 그대로 둔다.

- 근거: 힌트는 특정 지점의 이름을 가리키는 값이고, 사전은 하고 싶은 일(개념)을 다룬다. 성질이
  달라 같은 사전을 대면 "맛집" 힌트 하나가 음식 근거어를 가진 모든 지점을 앞으로 끌어오는
  오배치가 생긴다. 이름 변형(정식 명칭보다 짧은 통칭)은 상호 부분 포함이 이미 잡는다.
- 기각: 함께 확장. PRD도 범위 증가를 병기했고, 확장이 고치는 실측 사례가 없다. 오매칭 실측이
  나오면 별도 티켓으로 다룬다.

### 결정 5. 지표 기준선은 개선 전 코드로 고정 입력 세트를 실측해 잡는다

구현 착수 전에 개선 전 코드로 기준선을 잰다. 방법: dev 시드 DB 위에서 고정 관심사 세트(10종
내외)와 대표 뷰포트(부산 시내, 해운대 등 3곳)로 `RouteCandidateCollector.collect()`를 직접 돌려
선별 지점 중 일치 지점 비율을 기록한다. AI 해석을 거치지 않고 `ParsedIntent`를 고정 입력으로
주므로 해석 비결정성이 배제되고, 개선 후 같은 세트를 재실행하면 순수하게 판정 확장의 효과만
비교된다. 입력 세트와 측정값은 이 문서 작업 로그에 남긴다.

기준선과 개선 후 측정 모두 **장소 검색은 빈 결과 스텁으로 고정하고 미션과 행사 후보만으로
잰다.** 장소 후보는 검색어가 곧 관심사라 matchedInterest가 판정 없이 즉시 붙는 값이어서 매처
효과 측정에는 잡음이다. 구 매처에서는 미션이 관심사를 못 채우면 장소 검색이 돌아 그 결과 최대
3건이 일치로 계상되는데, 신 매처가 미션을 채워 검색을 건너뛰면 개선인데도 matched/points가
내려갈 수 있다. 외부 검색 결과의 시점 변동성도 전후 비교의 격리를 깬다. 검색 경로를 측정에서
빼야 두 측정이 같은 조건이 된다.

- 기각: 배포 후 로그 소급 비교(개선 전 로그에는 일치 키 자체가 없고, dev 트래픽이 내부 개발
  수준이라 표본도 없다), 지표 키만 선배포(기준선 하나를 위해 배포를 한 번 더 가르는 비용 과다).

## API 명세

변경 없음. `POST /api/routes/recommend`의 요청과 응답 형태, 에러 코드(14xxx), 요청 제한, 언급
지역 신호 모두 MSG-457(과 후속 468, 483, 487)의 계약 그대로다. 달라지는 것은 응답 안의 값이다:
지점 구성과 순서가 관심사를 반영하고, `reason` 문장의 재료가 풍부해진다.

## 도메인 로직

### 1. 이어짐 판정 (InterestMatcher 신규)

`com.msg.fillmap.route.service.InterestMatcher` 컴포넌트가 판정 규칙과 사전 데이터를 한 곳에
모은다(PRD 클래스 다이어그램 확정 구조). `RouteCandidateCollector`의 기존 `matchedInterest()`
판정을 이 컴포넌트 위임으로 바꾼다.

판정 규칙: 관심사 배열 순서대로 아래 둘 중 하나가 성립하는 첫 관심사를 반환하고, 없으면 null이다.

1. 원문 포함(기존 유지, 한 글자 가드 신설): 후보 재료 문자열이 관심사 원문을 포함한다. 단
   트림 후 한 글자인 관심사는 이 판정을 건너뛰고 규칙 2의 한 글자 alias 정확 일치로만
   판정한다. 근거어 2자 규칙과 같은 논리를 원문 방향에도 적용하는 것이다: "회"를 원문 포함으로
   판정하면 무관 후보 "시민회관"이 걸려 일치로 표시되고 우선 선정까지 되어 FR-5가 깨진다.
   현행 코드는 한 글자도 원문 포함으로 통과시키므로 이 가드는 기존 동작의 의도적 변경이다
   (매칭 품질이 이 티켓의 범위). 사전에 없는 한 글자 관심사는 미충족으로 남아 종전 흐름대로
   장소 검색어 재료가 된다(FR-ROUTE-06, FR-ROUTE-07 유지).
2. 사전 경유(신설): 관심사가 걸린 개념들의 근거어 합집합 중 하나라도 후보 재료 문자열에
   포함되면 일치다. 관심사가 개념에 걸리는 조건은 표기(alias) 길이로 갈린다. 두 글자 이상
   alias는 관심사가 그것을 포함하면 걸리고("부산 맛집"이 "맛집"에 걸린다), 한 글자 alias는
   관심사가 트림 후 정확 일치일 때만 걸린다("밥"은 걸리고 "김밥천국"은 걸리지 않는다).
   한 글자 관심사는 AI 계약상 유효한 해석 출력이라(RouteIntentClientTest 실통과 사례) 포함
   판정만으로는 두 글자 alias를 영영 못 만나므로, 정확 일치 경로가 FR-1의 성립 조건이다.

사전에 걸리지 않는 관심사는 규칙 1로만 판정한다. 억지 매칭 금지(FR-5)는 별도 로직이 아니라
사전 편성 규율로 지킨다: 근거어는 그 개념의 실체를 직접 가리키는 말만 넣고("맛집" 개념에
음식점, 식당, 먹거리, 국밥 등), 장소 일반어(코스, 거리, 명소 등)를 넣지 않는다.

후보 재료(haystack) 구성:

| 후보 | 재료 | 변경 |
|------|------|------|
| 미션(축제, 팝업, 코스) | 제목 + 유형 라벨 + 소개문 + **장소명(placeName)** | 장소명 추가(PRD 변경 파일 명시) |
| 행사 | 제목 + " 행사" | 불변. 칩 DTO에 제목과 기간뿐이라 더할 재료가 없다 |
| 장소 검색 | 판정 없음 | 불변. 검색어가 곧 미충족 관심사라 일치가 자명해 종전대로 즉시 부여한다 |

미충족 관심사 판정(장소 검색 1회 유발 조건)과 선별 규칙(일치 우선, 거리순, gridId 사전순,
상한 8)은 바꾸지 않는다. 판정이 넓어지면 미션과 행사가 관심사를 더 자주 채워 장소 검색 호출은
같거나 줄어든다(호출 수 불변 요구에 유리한 방향).

### 2. 동의어 사전 데이터

`src/main/resources/route/interest-synonyms.json` 스키마:

```json
{
	"concepts": [
		{
			"key": "food",
			"aliases": ["맛집", "먹거리", "미식", "맛있는", "밥"],
			"evidence": ["맛집", "음식", "식당", "먹거리", "국밥", "야시장", "먹자골목"]
		}
	]
}
```

기동 시 검증(위반은 기동 실패):

- `key`는 개념 간 중복 금지.
- `evidence`의 전 항목은 트림 후 2자 이상. 후보 재료를 contains로 찾는 방향이라 한 글자가
  부분 문자열 오탐의 주범이다("회"가 "회관"과 "회의"에 걸린다).
- `aliases`의 전 항목은 트림 후 1자 이상(빈 문자열 금지). 한 글자를 허용하는 이유는 "밥" 같은
  한 글자 관심사가 유효 입력이라서다. 오탐 위험은 방향이 달라 규칙도 다르다: alias는 관심사가
  걸리는 쪽이고, 한 글자 alias의 정확 일치 판정(도메인 로직 1의 규칙 2)이 "김밥천국"류
  부분 포함 오탐을 막는다.
- 빈 배열 금지(근거어 없는 개념은 판정에 기여하지 못하는 죽은 항목이다).

한 관심사가 여러 개념의 표기에 걸리면 근거어 합집합으로 판정한다. 합집합은 순서 무관이라
결정성에 영향이 없다.

### 3. 순서 배열 개정 (RouteOrderPlanner)

최근접 이웃[^6] 선택의 비교 키를 (거리, gridId)에서 **(관심사 일치 여부, 거리, gridId)**로
바꾼다. 일치 지점이 남아 있는 동안은 그중 최근접이 먼저 뽑히므로 일치 지점 전부가 미일치
지점보다 동선 앞에 온다. preferred_order 힌트 배치는 종전대로 이 규칙보다 우선한다(사용자가
순서 자체를 지목한 것이라 관심사보다 강한 신호다). 시작 좌표 규칙(origin, 힌트 마지막, 뷰포트
중심)은 불변이다.

이 개정은 PRD 변경 파일 목록에 없던 추가인데, 없으면 FR-4가 성립하지 않는다: 관심사 일치는
현행 코드에서 선별(상한 8)에만 작용하므로, 화면 안 후보가 8개 이하면 관심사가 달라도 같은
지점이 같은 최근접 순서로 배열되어 지점 구성도 순서도 동일해진다. 구성 차이는 후보가 상한을
넘는 화면에서만 나는 것이라 순서 축이 반드시 필요하다.

- 수용하는 부작용: 일치 지점을 먼저 도는 동선은 순수 최근접보다 총거리가 늘 수 있다. 순서까지
  거리 최적화하지 않는 기존 태도(FR-ROUTE-16 근거 절)와 같은 결이고, 하루 8지점 도보 동선에서
  손실은 지점 간 수백 미터 수준이라 관심사 반영의 가치가 앞선다.
- 요구 문면의 전제(승인 대기): 이 스펙은 FR-4를 "서로 다른 후보 집합에 걸리는 두 관심사면 지점
  구성이나 순서가 달라진다"로 읽는다. 두 관심사가 같은 후보 집합에 걸리면(표기만 다르고 뜻이
  같은 말이면) 같은 동선이 옳은 결과이고, 그때 차이는 지점별 이유의 관심사 표기(FR-7)로
  나타난다. 현재 PRD FR-4와 SRS FR-ROUTE-18 문면은 이 구분 없이 "달라진다"라 이 읽기는 문면
  정정을 요구한다. 미해결 질문 절에 승인 대기 항목으로 올렸다. FR-4 고정 테스트의 픽스처를
  서로 다른 후보 집합에 걸리는 두 관심사로 짜는 것은 이 정정된 문면의 검증 조건이라서다.

### 4. 사실 목록 조립 확대 (RouteRecommendServiceImpl, RouteCandidate)

`RouteCandidate`에 `List<String> detailFacts`(지점 고유 사실, 최대 2건, 불변 리스트)를
추가한다. 조립은 수집 시점(`RouteCandidateCollector`, 원천 DTO가 손에 있는 곳)이고, 순서
편성과 상한과 100자 절단은 종전대로 발송 시점(`RouteRecommendServiceImpl.facts()`) 한 곳이다.

- 기각 대안: `RouteCandidate`에 유형별 원시 필드 6종(placeName, description, address,
  distanceMeters, durationMinutes, difficulty)을 늘어놓는 방식. record가 16개 컴포넌트로
  불어나고 생성 지점 세 곳이 전부 null 나열이 된다. 조립 문장 2건이 더 좁은 접면이다.

유형별 지점 고유 사실:

| 유형 | 1건째 | 2건째 |
|------|-------|-------|
| 코스(MISSION_COURSE) | 스펙 합성 문장 "총 14km, 약 5시간 30분, 난이도 보통" | 소개문(description) |
| 축제(MISSION_FESTIVAL), 팝업(MISSION_POPUP) | 장소명(placeName) | 소개문(description) |
| 행사(EVENT) | 없음 | 없음 |
| 장소(PLACE) | 주소(address) | 없음 |

- 코스 스펙 합성: 거리는 km 단위 소수 첫째 자리(끝이 .0이면 정수 표기), 시간은 "약 {시}시간
  {분}분"(60분 미만은 분만, 정시는 시간만), 난이도는 두루누비 등급 라벨(1 쉬움, 2 보통,
  3 어려움, 범위 밖 값은 항목 생략). null인 항목은 빼고 조립하고, 셋 다 null이면 문장 자체를
  만들지 않는다.
- 축제와 팝업에서 운영시간(operationTime)이 아니라 소개문을 고른 것은 PRD FR-6이 장소와 소개를
  지목했고 칸이 2건이라서다. 운영시간은 칸이 남는 미래 확장 후보로 미룬다.
- null 재료는 항목 생략이다. 고유 사실이 0건이어도 출처 상시 1건이 하한을 지킨다.
- `facts()` 최종 조립 순서는 결정 3을 따른다: 출처, 관심사 일치, detailFacts, 기간. 모든
  문자열은 발송 직전 `truncate`(100자)를 거친다. 사용자 원문은 종전대로 어떤 형태로도 explain에
  실리지 않는다(환각[^7] 방어 불변. 관심사 문자열이 "관심사 '{X}' 일치" 항목에 실리는 것은
  기존 동작 유지다).

### 5. 지표 로그

`logMetrics` 한 줄에 두 키를 더한다: `interests={해석의 비공백 관심사 수}`
`matched={선별 지점 중 matchedInterest 비non-null 수}`. 일치 비율은 집계 시 `matched/points`로
계산한다. 두 값은 `doRecommend` 안에서 확보해 밖으로 전달한다(`spans` 배열과 같은 관례).
실패 경로 라인은 0으로 남는데, 집계 대상이 outcome ok와 insufficient 라인뿐이라 무해하다.
관심사 원문은 종전 정책대로 로그에 남기지 않으므로, 커버리지가 빈 관심사가 무엇인지는 로그로
못 잡고 비율 추이로만 관측한다. 비율이 낮게 유지되면 사전 파일 갱신으로 대응한다.

[^1]: 관심사: 사용자 문장에서 AI 해석이 뽑아낸 하고 싶은 일의 목록. "맛집", "야경" 같은 짧은 말이 배열로 온다.
[^2]: 사실 목록(facts): 이유 문장화 요청에 지점마다 실어 보내는 사실 문장들. AI 계약상 지점당 1~5건, 각 100자이고 AI는 받은 목록만으로 이유를 쓴다.
[^3]: 동의어 사전: 관심사 표기(맛집, 먹거리 등)와 후보 텍스트에서 찾을 근거어를 개념 단위로 묶어 둔 데이터. 이 스펙에서는 서버 배포물에 포함되는 JSON 파일이다.
[^4]: 근거어: 후보의 제목이나 소개문이나 장소명에서 발견되면 그 개념과 이어졌다고 보는 증거 단어. 예를 들어 "국밥"은 맛집 개념의 근거어다.
[^5]: 결정성: 같은 입력에 항상 같은 출력이 나오는 성질. 짧은 간격의 재요청에서 결과가 흔들리면 안 된다는 요구(FR-ROUTE-10)가 걸려 있다.
[^6]: 최근접 이웃: 현재 위치에서 가장 가까운 다음 지점을 반복해 고르는 순서 결정 방식. 전체 최적은 아니지만 계산이 싸고 결정적이다.
[^7]: 환각: AI가 받은 재료에 없는 내용을 사실처럼 지어내는 현상. 이 기능은 "받은 사실만 쓴다"는 규칙으로 막고 있다.
