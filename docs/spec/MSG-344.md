# MSG-344: 운영 서버 상시 관측과 이상 알림

**Owner**: 공동(인프라)
**PRD**: 면제. 제품 동작과 API 계약을 바꾸지 않는 운영 안정성(관측, 알림) 개선이라 제품 요구사항을 새로 만들거나 바꾸지 않는다(티켓 명시 판정).

## 개요

운영(prod) 서버의 Actuator[^1] 메트릭을 대상 서버 밖에서 상시 수집하고, 이상 징후가 일정 시간
이어지면 운영자에게 알림이 가게 한다. MSG-128이 만든 부하테스트용 임시 스택(6시간 보관, 끝나면
내림)을 출발점으로 삼되 그것과는 별개의 상시 스택을 새로 구성한다. 같이 고치는 것 두 가지:
prod 배포 확인(CD)을 루트 경로 4xx 허용에서 `/actuator/health` 200 한정으로 바꾸고,
`/actuator/prometheus`를 수집 서버만 접근할 수 있게 제한한다.

## 배경 · 목표

지금 prod에는 상시 관측이 없다. 앱이 죽거나 느려져도 사용자가 겪기 전까지 아무도 모르고,
배포 확인조차 "401이면 떠 있는 것"이라는 간접 신호에 기대고 있다(cd-prod.yml의 4xx 허용).
MSG-128 스택은 D1 결정대로 부하테스트용 임시라서 이 구멍을 못 메운다. 이 티켓으로
기동 상태, HTTP 5xx 비율, 응답 지연 p95와 p99[^2], Hikari[^3] 커넥션 풀, JVM 메모리와 CPU,
수집 실패까지를 상시로 보고, 이상이 지속되면 사람이 알게 만든다.

| 자산 | 상태 |

| `.github/workflows/cd-prod.yml` | 헬스체크가 `http://localhost:8080/`에 curl, 2xx와 3xx와 4xx를 전부 통과 처리. "actuator 도입되면 /actuator/health로 교체" TODO가 남아 있고, "prod 앱은 아직 구성 전" 주석은 낡았다(prod는 api.fillmap.kr로 별도 서버에서 구동 중) |

| 인프라 | prod 앱 서버는 t3.small 단독(api.fillmap.kr). dev는 별도 EC2 1대(fillmap.kr)에 dev 앱과 postgres, redis, kafka가 함께 상주 |

## 성공 기준

티켓 완료 조건을 그대로 옮긴다. 아래 "구현 단계"의 검증 방법이 각 항목의 확인 수단이다.

1. 대상 애플리케이션과 다른 실행 환경에서 메트릭이 상시 수집된다.
2. 보관 기간[^5]이 정해져 있고 runbook에 기록돼 있다.
3. 앱 중단을 재현하면 정한 시간(제안: 5분) 안에 알림이 도착한다.
4. 5xx 비율, 응답 지연, Hikari 대기, 수집 실패에 알림 규칙이 있다.
5. prod CD는 `/actuator/health`가 HTTP 200일 때만 성공한다. DB 또는 Redis 장애로 health가
   DOWN이면(503) 배포 확인이 실패한다.
6. 외부에서 `/actuator/prometheus`에 접근할 수 없고, 수집 서버에서는 정상 조회된다.
7. 대시보드, 알림 기준, 장애 확인 절차가 runbook에 기록돼 있다.

## API 명세

제품 API 변경 없음. 운영 엔드포인트만 이동한다: prod 프로파일에서 Actuator 전체가 공개
포트를 떠나 관리 포트[^6]로 옮겨간다(아래 1단계). 공개 포트에서 `/actuator/**`는 404가 된다.
로컬과 dev 프로파일은 지금 그대로다(임시 스택 워크플로 불변).

## 설계

### 왜 관리 포트 분리인가

`/actuator/prometheus` 접근 제한 방법으로 세 가지를 비교했다.

- **관리 포트 분리 + 보안그룹 (채택)**: `application-prod.yml`에 `management.server.port`를
  두면 Actuator가 별도 포트에서만 열린다. 그 포트는 보안그룹에서 수집 서버만 인바운드
  허용한다. 앱 코드 변경이 없고(설정 1줄), 공개 경로에 리버스 프록시가 있든 없든 동작하며,
  permitAll을 건드리지 않아 로컬과 dev가 그대로 굴러간다.
- 앱 레벨 IP 검사 (기각): X-Forwarded-For는 위조 가능하고, 프록시 유무에 따라 원격 주소가
  달라져 취약하다.
- scrape 인증(bearer 토큰) (기각): 전역으로 꺼 둔 httpBasic을 Actuator에만 선별 활성화해야
  해서 SecurityConfig가 복잡해진다. 포트 분리면 같은 효과를 설정 1줄로 얻는다.

### 상시 스택 구성

임시 스택(`monitoring/`)과 물리적으로 분리해 `monitoring/prod/`를 신설한다. 임시 스택은
부하테스트 용도로 그대로 남긴다.

- 컨테이너 3개: Prometheus(보관 30일 제안), Alertmanager[^7], Grafana.
- scrape 간격 15초(임시 스택의 5초는 부하 구간용, 상시엔 과하다). 대상은 prod 앱
  사설IP:8081의 `/actuator/prometheus`와 Prometheus 자신.
- postgres-exporter는 넣지 않는다. 최소 관측 대상에 DB 메트릭이 없고, 커넥션 병목은
  Hikari 지표가 이미 보여준다. DB 내부까지 필요해지면 그때 추가한다.
- Grafana는 익명 접근을 끄고 admin 비밀번호를 환경변수로 주입한다(임시 스택의 익명 Viewer
  설정은 상시 노출엔 부적합). 대시보드는 상시용 1장을 새로 만든다: 기동 상태(up),
  5xx 비율, p95와 p99, Hikari(active, pending, max), JVM heap, CPU.

보관 30일 근거: 현재 시계열 규모(HTTP 버킷 18개 x uri 조합 + JVM, Hikari로 수천 개 수준)에
15초 간격이면 30일에 대략 1~2GB로, 최소 사양 디스크로도 충분하다. 확정값은 runbook에 기록한다.

### 알림 규칙

새 목표를 만드는 게 아니라 이미 확정된 값을 감시로 옮긴다. 다만 근거는 둘로 갈린다:
p95 < 300ms와 p99 < 800ms는 MSG-134 ADR의 뷰포트 SLO라 지연 규칙은 뷰포트 조회
(`uri="/api/grids"`)로 한정하고, 5xx < 1%는 서비스 전반 오류율의 운영 기본 임계다
(티켓 완료 조건의 5xx 비율 감시. 뷰포트로 좁히면 인증과 업로드 5xx를 놓친다).

| 알림 | 조건 (PromQL 요지) | 지속 | 심각도 |
|---|---|---|---|
| AppDown | `up{job="fillmap-prod"} == 0` | 1분 | critical |
| High5xxRate | 5xx 요청 비율 > 1% (`http_server_requests_seconds_count` rate 비) | 5분 | critical |
| HighLatencyP95 | `histogram_quantile(0.95, ...)` > 0.3s | 10분 | warning |
| HighLatencyP99 | `histogram_quantile(0.99, ...)` > 0.8s | 10분 | warning |
| HikariPending | `hikaricp_connections_pending > 0` | 2분 | critical |
| HikariSaturation | active / max > 0.9 | 5분 | warning |
| JvmHeapHigh | heap used / max > 0.9 | 10분 | warning |
| CpuHigh | `process_cpu_usage > 0.9` | 10분 | warning |

`up == 0`은 앱 중단과 수집 실패(네트워크, 보안그룹 문제)를 구분하지 못한다. 구분은 알림
규칙이 아니라 runbook 절차로 푼다: 알림을 받으면 수집 서버에서 관리 포트로 직접 curl해
앱 생존을 먼저 가른다.

알림 도착 목표는 재현 기준 5분이다. scrape 15초 + 지속 1분 + Alertmanager group_wait를
합쳐도 2분 안쪽이라 여유가 있다.

### prod CD 헬스체크 교체

`cd-prod.yml`의 Health check step에서 대상 URL을 `http://localhost:8081/actuator/health`로
바꾸고 **HTTP 200만** 통과시킨다(포트는 1단계의 관리 포트). 4xx 허용 case문과 "401이 곧
기동 성공" 주석, 낡은 "prod 미구성" 경고를 제거한다. Spring Boot 기본 구성에서 DataSource와
Redis HealthIndicator가 자동 등록되므로, DB나 Redis 장애면 health가 DOWN(503)이 되고 배포
확인이 실패한다. 재시도 루프는 유지하되 회수(30회 x 5초)가 아니라 경과 시간 150초
데드라인으로 센다(회수 방식은 curl 대기 최대 3초가 회마다 얹혀 최악 240초까지 늘어나
명시한 150초와 어긋난다).

```bash
code=$(curl -s -o /dev/null -w '%{http_code}' --max-time 3 http://localhost:8081/actuator/health || true)
[ "$code" = "200" ] && exit 0   # 200 외 전부 실패: 503(DOWN)도, 000(미기동)도 통과 못 한다
```

## 테스트 시나리오

코드 변경이 설정과 워크플로 파일뿐이라 JUnit 테스트는 없다. 검증은 위 표의 운영 시나리오로
한다. 핵심 3건을 Given/When/Then으로 다시 적는다.

- Given prod 앱 정상 구동, When 외부 네트워크에서 `/actuator/prometheus` 접근,
  Then 공개 포트에선 404, 관리 포트로는 연결 불가. 수집 서버에서 같은 요청은 200.
- Given 상시 스택 가동, When prod 앱을 중단(systemctl stop), Then 5분 안에 AppDown 알림
  도착, 재기동 후 resolved 알림 도착.
- Given CD 헬스체크 교체본, When health가 DOWN(구성요소 장애)인 상태로 배포 확인 실행,
  Then 150초 내 200을 못 받아 워크플로 실패, journalctl 로그가 출력된다.

## 미해결 질문

1번과 2번은 2026-08-11 성민 결정으로 해소됐다. 3번만 1단계 실측으로 확인한다.

1. **수집 서버 위치: fillmap-ai EC2 동거로 확정** (2026-08-11 성민, 실측 후 재결정).
   처음엔 "dev EC2 동거"로 골랐으나 실측에서 전제가 깨져 다시 결정했다. 실측 결과 앱 EC2는
   fillmap-dev(52.79.187.34, t3.small) 1대뿐이고 prod는 DB(5433)·Redis(6380) 컨테이너만
   준비된 채 앱 서비스가 아직 없다. 즉 dev 박스가 곧 미래 prod의 박스라 동거는 "대상 서버
   밖 수집" 요구와 충돌하고, 가용 메모리도 478MiB로 부족했다. fillmap-ai EC2
   (52.78.158.240, t3.small)는 가용 1070MiB로 여유가 있고 앱 서버와 분리된 박스라 요구를
   충족하며 추가 비용이 없다. 기각 대안: 새 EC2 t4g.micro(월 약 $9~10, 격리는 깨끗하나
   유료), dev EC2 동거(위 사유), Grafana Cloud 무료 티어(0원이나 scrape 에이전트 배치가
   따라오고 알림 구성이 레포 밖 웹 콘솔로 나간다).
2. **알림 채널: Slack incoming webhook 확정** (2026-08-11 성민). Alertmanager 기본 지원이라
   연동이 가장 단순하다. webhook URL은 성민이 Slack에서 발급해 수집 서버 환경변수로
   주입하고 레포에는 넣지 않는다. 기존 CloudWatch 알람이 쓰는 슬랙 채널 #dev-monitoring이
   후보다. 기각 대안: 디스코드 webhook(Slack 호환 접미 필요), 이메일(SMTP 설정 필요,
   즉시성 열세).
3. **해소 (2026-08-11 실측)**: fillmap-dev와 fillmap-ai는 같은 VPC(vpc-0079b780d6767bc1f),
   같은 서브넷이다. prod 관리 포트 8081 인바운드 소스는 수집 서버 보안그룹
   sg-05e4d5c7ddfa6c438(fillmap-ai-sg)로 지정한다.

**실측이 추가로 드러낸 것 (2026-08-11)**: prod 앱은 아직 어디에도 상시 구동돼 있지 않다
(fillmap-dev 박스에 fillmap-dev.service만 enabled, 현재 api.fillmap.kr 트래픽은 dev 앱이
받는다). 따라서 스택 가동 직후 prod 타깃은 DOWN이 정상이고, 수집 실패 알림이 계속 울리지
않도록 prod 가동 전까지의 조치(타깃 비활성 또는 silence)를 runbook에 명시한다. AppDown
알림의 실중단 재현 검증은 prod 앱이 뜨는 시점에 한다.

[^1]: Actuator: Spring Boot가 내장한 운영 엔드포인트 모음. 이 티켓에서는 앱의 건강 상태를 알려주는 `/actuator/health`와 메트릭을 내보내는 `/actuator/prometheus` 두 개를 쓴다.
[^2]: p95, p99: 응답 시간을 정렬했을 때 95번째, 99번째 백분위 값. 평균과 달리 느린 소수 요청을 드러내서, "대부분은 빠른데 일부가 느린" 상태를 잡아낸다.
[^3]: Hikari(HikariCP): Spring Boot 기본 DB 커넥션 풀. 풀이 가득 차면 요청이 대기(pending)하는데, 이 대기 수가 DB 병목의 가장 이른 신호다.
[^4]: scrape: Prometheus가 대상 서버의 메트릭 엔드포인트를 주기적으로 읽어 가는 수집 방식. 대상이 밀어 보내는 게 아니라 수집 서버가 당겨 간다.
[^5]: 보관 기간(retention): 수집한 메트릭을 디스크에 유지하는 기간. 지나면 자동 삭제된다. 임시 스택은 6시간이었고 상시 스택은 30일을 제안한다.
[^6]: 관리 포트: `management.server.port` 설정으로 Actuator를 서비스 포트와 다른 포트에 여는 것. 공개 트래픽과 운영 트래픽이 포트 수준에서 갈라져 방화벽(보안그룹)만으로 접근을 제한할 수 있다.
[^7]: Alertmanager: Prometheus의 알림 발송 컴포넌트. Prometheus가 규칙 위반을 감지해 넘기면 중복 제거와 그룹핑을 거쳐 webhook 등으로 사람에게 보낸다.
