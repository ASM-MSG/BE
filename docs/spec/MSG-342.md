# MSG-342: 예상하지 못한 500 오류를 ERROR 로그로 남기고 로그 설정을 정비

**Owner**: A

> PRD 게이트: 면제 (2026-08-11 확정). 이 작업은 제품 요구사항을 만들거나 바꾸지 않는 운영 로그
> 정비다. 클라이언트가 받는 500 응답의 형식, developCode[^1], 메시지는 전부 그대로다.
> Owner 판정: 도메인 접점은 search 패키지(Owner A) 하나이고, `com.msg.fillmap.global`과
> `src/main/resources` 설정은 공통 영역이라 별도 Owner가 없다. 계약 인터페이스 변경도 없어
> 공동이 아닌 A 단독이다.

## 개요

처리되지 않은 예외가 공통 catch-all 핸들러[^2]에 도달하면 요청 방법, 요청 경로, developCode,
전체 스택 추적[^3]을 담은 ERROR 로그를 정확히 한 번 남긴다. 함께 발견된 로그 설정 문제
세 가지를 같은 작업에서 정리한다. 애플리케이션 로그 레벨 경로를 실제 패키지인
`com.msg.fillmap`으로 고치고, 카카오 장소 검색과 검색어 집계의 실패 로그에서 검색어 원문을
제거하며, 요청 본문과 인증 헤더와 토큰이 오류 로그에 실리지 않음을 원칙으로 못박는다.

## 배경 · 목표

현재 `GlobalExceptionHandler.handleException()`(78행)은 예외를 500 응답으로 바꾼 뒤 아무
기록도 남기지 않는다. 사용자가 500을 받아도 서버 로그에는 원인이 없어서 무엇이 실패했는지
찾을 수 없다. 더 나쁘게, dev와 prod와 local 예제의 로그 레벨이 존재하지 않는 패키지
`com.fillmap`을 가리키고 있어 애플리케이션 로거는 전부 root 레벨(INFO)로만 동작해 왔다.
반대로 장소 검색 쪽은 기록이 과했다. 업스트림 장애가 나면 사용자가 입력한 검색어가 그대로
경고 로그에 남는다(`KakaoLocalClient` 77행의 `query={}`, `SearchKeywordCommandServiceImpl`
104행의 `keyword={}`).

목표는 두 방향이다. 부족한 쪽(500 원인 미기록)은 채우고, 과한 쪽(검색어 원문)은 걷어낸다.

**범위 밖** (티켓 재확인): 로그 수집 서버와 보관 정책 구축, 분산 추적과 APM 도입, 정상 요청
전체 접근 로그. 또한 `ApiException`과 400 계열 명시 핸들러 4종은 이미 의도된 처리 경로라
로그를 추가하지 않는다. 이 티켓의 대상은 "그 외 Exception" 폴백 경로뿐이다.

## 성공 기준

1. 처리되지 않은 예외가 catch-all 핸들러에 도달하면 ERROR 로그가 정확히 한 번 남는다.
2. 그 로그에 HTTP 방법, 요청 경로, developCode(500), 전체 스택 추적이 포함된다.
3. 기존 500 응답의 상태 코드, developCode(500), 메시지("서버 내부 오류")는 바이트 하나
   변하지 않는다. 기존 `ApiResponseContractTest`가 green이면 와이어 계약 쪽은 검증된 것으로
   본다.
4. 장소 검색과 검색어 집계의 실패 로그에 검색어 원문이 남지 않는다.
5. dev, prod, local 예제의 애플리케이션 로그 레벨 경로가 `com.msg.fillmap`을 가리킨다.
6. 로그 발생(1건, 구성 요소 포함)과 검색어 미포함을 테스트로 확인한다.

## API 명세

변경 없음. 신규 endpoint, 신규 에러 케이스, developCode 추가가 전부 없다. catch-all의 500
응답 body는 지금처럼 developCode 500, message "서버 내부 오류", data null이다
(`ErrorCode.INTERNAL_SERVER_ERROR` 상수를 그대로 사용).

## 도메인 로직

새 도메인 규칙은 없다. 전 항목이 로그와 설정의 정비다.

### D-1: catch-all 핸들러에 ERROR 로그 추가

`GlobalExceptionHandler`에 `@Slf4j`를 붙이고, `handleException`의 시그니처에
`HttpServletRequest`[^4]를 추가한다 (Spring이 `@ExceptionHandler` 메서드 인자로 주입해 주는
표준 방식이라 필터나 인터셉터 신설이 필요 없다).

```java
@ExceptionHandler(Exception.class)
public ResponseEntity<ApiResponseDto<Object>> handleException(Exception e, HttpServletRequest request) {
	log.error("처리되지 않은 예외: {} {} developCode={}",
			request.getMethod(), request.getRequestURI(),
			ErrorCode.INTERNAL_SERVER_ERROR.getErrorCode(), e);
	// 응답 조립은 기존 그대로
}
```

- **경로는 `getRequestURI()`만 쓴다. 쿼리 문자열[^5]은 로그에 넣지 않는다.** 검색 API는
  검색어를 쿼리 파라미터(`query=`)로 받으므로, 쿼리 문자열을 실으면 검색어 원문 제거(D-2)가
  이 로그로 다시 뚫린다. 같은 이유로 요청 본문과 헤더(Authorization 포함)도 읽지 않는다.
- **스택 추적은 SLF4J 마지막 인자 `e`로 전체를 남긴다.** 원인 체인 포함이며 별도 가공 없음.
- **정확히 한 번의 보장 구조**: 이 로그가 유일한 기록 지점이다. `@ExceptionHandler`가 예외를
  resolve하면 프레임워크(서블릿 컨테이너, DispatcherServlet)는 ERROR를 따로 남기지 않으므로
  호출 1회가 곧 로그 1건이다. search의 5502 경로는 `ApiException`이라 전용 핸들러로 빠져
  여기 도달하지 않고, 검색어 집계 워커의 예외는 자체 catch로 삼켜져 애초에 핸들러까지 오지
  않는다. 이중 기록 경로 없음.
- 메시지 문구는 예시다. 구현에서 다듬어도 되지만 방법, 경로, developCode, 스택 추적 네 요소
  포함이 계약이다.
- 알려진 소음원: 매핑 없는 경로의 `NoResourceFoundException`류도 지금 catch-all로 흘러 500이
  되고 있으므로 이 로그의 대상이다. 봇 스캔이 ERROR로 찍힐 수 있으나, 이를 404로 세분하는
  것은 응답 변경이라 이 티켓의 불변 조건과 충돌한다. 소음이 실측되면 후속 티켓으로 뺀다.

### D-2: 검색어 원문 제거 (2곳)

- `KakaoLocalClient.upstreamFailure()` 77행: warn 메시지에서 `query={}`를 제거하고, cause도
  통째로 싣지 않는다. 예외 클래스명과 HTTP 상태 코드만 남긴다(Codex 교차 리뷰 1라운드 반영).
  `cause.toString()`을 그대로 실으면 검색어가 두 경로로 되돌아온다.
  `RestClientResponseException` 메시지는 응답 본문을 포함하고(업스트림이 쿼리를 에코할 수 있음),
  `ResourceAccessException` 메시지는 `?query=`가 든 요청 URL 전체를 포함한다. 원인 구분(키,
  쿼터, 타임아웃, 파싱 실패. MSG-251 §D3)은 클래스명과 상태 코드로 충분하다.
- `SearchKeywordCommandServiceImpl`의 `aggregate()`와 `recordSearch()` catch 2곳:
  `keyword={}`를 `userId={}`로 교체하고, 마지막 인자로 넘기던 예외 `e`도 제거해
  `causeType={}`(예외 클래스명)으로 대체한다(Codex 교차 리뷰 2라운드 반영). 예외를 통째로
  넘기면 스택과 메시지가 찍히는데, 집계 경로의 예외 메시지에는 바인딩 값이 에코될 수 있다.
  대표 사례가 Postgres UNIQUE 위반의 DETAIL(`Key (keyword)=(...) already exists`)이다.
  같은 메서드 스코프에 userId가 있어 상관관계 추적 손잡이는 유지된다. 원래 스펙은 예외 `e`를
  남기는 것이었으나 이 유출 경로 때문에 뒤집었다.
- 나머지 로그는 무변경이다. 122행과 126행의 드레인 로그는 건수만 남긴다. auth 쪽 토큰 관련
  warn 2건(`KakaoAuthCodeExchanger`)도 토큰 값을 싣지 않음을 확인했다 (변경 대상 아님).

### D-3: 로그 레벨 경로 정정 (3곳)

`com.fillmap` → `com.msg.fillmap`. 대상은 `application-dev.yml` 37행,
`application-prod.yml` 57행, `application-local.yml.example` 27행이다. base `application.yml`과
테스트 리소스에는 해당 항목이 없음을 확인했다 (레포 전체에서 `com.fillmap`은 이 3곳뿐).

예상 효과를 명시해 둔다. 지금까지 이 항목은 유령 패키지를 가리켜 사실상 no-op이었으므로,
정정 후 dev와 local에서는 애플리케이션 패키지의 DEBUG 로그가 실제로 나오기 시작한다(로그량
증가는 의도된 변화). prod는 INFO라 root와 같아 체감 변화가 없다.

## 미해결 질문

없음. 카카오 실패 로그에서 검색어를 대체 없이 지우는 것(길이조차 남기지 않음)은 D-2에서
결정했다. 원인 구분에 필요한 정보가 cause에 전부 있고, 필요가 실측되기 전에는 추가하지
않는다.

[^1]: developCode: 이 프로젝트 공통 응답의 앱 내부 코드 필드. HTTP 상태와 별개로 실패 종류를 식별하며, 공통 500 오류는 `ErrorCode.INTERNAL_SERVER_ERROR`의 500이다.
[^2]: catch-all 핸들러: `@ExceptionHandler(Exception.class)`로 선언해, 더 구체적인 핸들러가 없는 모든 예외를 마지막으로 받아내는 메서드. 이 프로젝트에서는 `GlobalExceptionHandler.handleException`이며 도달한 예외는 전부 500이 된다.
[^3]: 스택 추적(stack trace): 예외가 발생한 지점부터 호출 경로를 거슬러 올라간 기록. SLF4J는 로그 인자 마지막에 예외 객체를 넘기면 원인 체인까지 통째로 출력한다.
[^4]: HttpServletRequest: 처리 중인 HTTP 요청 자체를 나타내는 서블릿 객체. Spring은 `@ExceptionHandler` 메서드가 인자로 선언하면 자동 주입해 주므로, 요청 방법과 경로를 얻으려고 별도 저장 장치를 만들 필요가 없다.
[^5]: 쿼리 문자열(query string): URL에서 `?` 뒤에 붙는 `key=value` 파라미터 부분. `getRequestURI()`는 이 부분을 제외한 경로만 반환하므로 검색어 같은 파라미터 값이 로그에 섞이지 않는다.
[^6]: ListAppender: Logback 테스트 도구로, 로거에 붙이면 로그 이벤트를 리스트에 쌓아 준다. 테스트가 로그의 레벨, 건수, 메시지 내용, 예외 첨부 여부를 단언할 수 있다.
