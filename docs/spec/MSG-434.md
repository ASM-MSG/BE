# MSG-434: 알림함 (받은 알림 목록 조회와 읽음 처리)

**Owner**: B (notification 도메인 코드와 그에 딸린 DB 마이그레이션(V37)만 변경, 도메인 간 계약
인터페이스는 무변경)

> 요구사항 정본: `docs/prd/MSG-434-prd.md` (검토됨, 2026-08-19 정민 승인) · SRS FR-NOTI-17
> 이 문서는 PRD의 FR 1~11과 비기능 요구에 "어떻게"만 붙인다.

## 개요

발송 기록으로만 쌓이던 notifications 테이블 위에 조회 계층을 얹는다. 사용자가 자기 알림을
최신순으로 훑어보고, 행 탭으로 하나씩 또는 버튼 하나로 전부 읽음 처리하고, 안읽은 개수를
가볍게 조회하는 API 4개를 만든다. 발송 동작(outbox[^1] 릴레이, Kafka 소비, FCM 전송)은
무변경이다. 단 D-2의 스킵 사유 상수 승격에 따라 NotificationConsumer의 skip 호출부가 리터럴
대신 그 상수를 참조하도록 바꾼다 (동작 동일, 문자열 값 불변).

## 배경 · 목표

푸시 권한을 거부한 사용자는 알림을 볼 방법이 없고, 받은 사용자도 지나간 알림을 되짚을 수 없다.
확정 디자인(2026-08-19)은 프로필 페이지의 알림함 카드, 프로필 카드의 "새 알림 N개" 문구,
지도 홈 프로필 이미지의 빨간 점 세 곳에서 이 API를 소비한다. 딥링크 페이로드는 비목표로,
MSG-432가 가져간다.

## 성공 기준

- 알림 목록이 최신순으로, 페이지 단위로 내려온다. 항목마다 카테고리, 제목, 본문, 생성 시각,
  읽음 여부가 실린다 (FR-1, FR-2).
- 목록과 안읽음 개수 모두에서 다음이 지켜진다: 최근 30일 이내 생성분만 (FR-10), 수신 거부로
  걸러진 알림(SKIPPED이면서 사유 PREF_OFF)은 제외, 전송률 상한으로 걸러진 알림(사유
  RATE_LIMITED)은 포함 (FR-11), PENDING과 DEAD 상태도 포함 (FR-3).
- 개별 읽음과 전체 읽음이 멱등[^2]으로 동작하고, 타인 알림 ID로는 존재하지 않는 알림과 같은
  실패 응답을 받는다 (FR-4, FR-5, FR-7).
- 안읽음 개수가 0이면 count 0이 내려온다. 알림이 없으면 빈 목록이다 (FR-6, FR-8).
- 읽음 처리가 outbox 상태 전이를 건드리지 않고, 상태 전이가 읽음을 덮어쓰지 않는다 (비기능
  데이터 정합).
- 목록과 개수 쿼리의 실행 시간 프록시 실측이 데이터 모델 절의 완료 조건을 통과한다 (비기능
  성능. 인덱스 무신설 결정의 검증이다).

## 핵심 설계 결정

### D-1. 읽음 상태 저장 = notifications 테이블에 read_at 컬럼 추가

별도 읽음 테이블(notification_reads)과 비교한 결과다.

| 기준 | read_at 컬럼 (채택) | 별도 테이블 (기각) |
|------|------|------|
| 목록과 개수 쿼리 | 단일 테이블, 조인 없음 | 매 조회에 LEFT JOIN |
| 마이그레이션 | ALTER 한 줄 | 테이블, FK, 인덱스 신설 |
| 탈퇴 정리 | 기존 FK CASCADE가 그대로 커버 (비기능 운영 요구) | CASCADE 경로 추가 관리 |
| outbox 상태와의 독립 | UPDATE 문장이 서로 다른 컬럼만 만져 충돌 없음 (아래 D-5) | 테이블 분리로 자연 독립 |
| 이득이 생기는 조건 | - | 읽음 기록이 알림과 다른 수명을 가질 때 (지금 없음) |

사용자당 수백 건 규모(비기능 성능 절)에서 분리 테이블의 이득은 없고 비용만 남는다.
`read_at TIMESTAMP NULL`로 두고 NULL이면 안읽음이다. 값은 UTC naive로, 이 테이블의 다른
시각 컬럼과 같은 관례를 따른다.

기존 행은 NULL(안읽음)로 시작한다. 사용자가 한 번도 본 적 없는 알림이므로 사실에 부합하고,
30일 창 밖 행은 어차피 보이지 않으며, 거슬리면 "모두 읽음" 한 번으로 해소된다.

### D-2. 수신 거부 스킵의 구분 = SKIPPED 상태의 last_error 사유 코드

FR-11의 "수신 거부 스킵은 숨기고 전송률 상한 스킵은 보여준다"에 필요한 구분 재료는 이미
저장돼 있다. `NotificationRepository.markSkipped`가 skip 사유를 `last_error`에 남기고
(PREF_OFF, RATE_LIMITED, NO_TOKEN 세 코드, MSG-179부터), SKIPPED는 종결 상태라 이후 어떤
전이도 이 값을 덮지 않는다 (모든 전이 UPDATE의 술어가 PENDING과 PUBLISHED만 통과시킨다).
따라서 마이그레이션 없이 다음 제외 조건 하나로 끝난다.

```
숨김 조건: status = 'SKIPPED' AND last_error = 'PREF_OFF'
```

RATE_LIMITED와 NO_TOKEN 스킵은 보인다. NO_TOKEN(푸시 토큰 없음)을 보여주는 것이 특히 옳다.
푸시 권한을 거부한 사용자가 알림을 확인하는 유일한 경로가 이 목록이기 때문이다 (FR-3).

이 결정으로 `markSkipped`의 사유 문자열이 조회 측 계약이 된다. 구현 시 사유 코드를
`NotificationRepository`에 상수로 올려 양쪽(NotificationConsumer의 skip 호출부, inbox 쿼리)이
같은 상수를 참조하게 하고(consumer는 리터럴을 상수 참조로 치환할 뿐 동작과 문자열 값은
불변이다), `markSkipped` javadoc에 "PREF_OFF는 알림함 숨김 판정에 쓰인다(MSG-434)"를 덧붙인다.

### D-3. 페이지네이션 = id 내림차순 keyset 커서[^3], 커서 값은 마지막 항목의 id

- **최신순은 id 할당순으로 정의한다.** BIGSERIAL id의 시퀀스 할당 순서는 동시 트랜잭션에서
  created_at 순서와 미세하게 어긋날 수 있다(시퀀스 할당 순서와 커밋 순서는 별개다). 그래도
  이 정의를 채택하는 근거: 같은 사용자에게 동시 트랜잭션이 알림을 만드는 경우가 드물고
  (사용자 행동 기반 이벤트는 직렬), 어긋나도 밀리초 수준 표시 순서 차이에 그친다. keyset
  무결성은 조회 시점에 가시(커밋)였던 데이터셋에 한정된다. 페이지를 넘기는 사이에 커밋된
  과거 id 행은 그 세션의 다음 페이지에서 누락될 수 있으나, 알림함은 재진입 시 첫 페이지부터
  다시 읽는 화면이라 다음 진입에서 보인다. (created_at, id) 복합 커서는 표시 순서의 미세
  역전을 없애는 대신 커서가 다성분이 되어 기각한다. id는 동점이 없어 keyset이 안정적이다.
- 커서는 직전 응답 마지막 항목의 `notificationId`(Long)를 그대로 되돌려 받는다. 다음 페이지
  조건은 `id < :cursor`. 첫 페이지는 cursor 생략이고 서비스가 `Long.MAX_VALUE`로 치환해
  쿼리 메서드를 하나로 유지한다.
- VideoCursor나 GridCursor 같은 Base64 토큰을 쓰지 않는 이유: 그 장치는 경계값이 여러
  성분일 때의 포장이다. 성분이 id 하나뿐이라 정수 하나가 곧 커서이고, 타입 불일치는 스프링
  바인딩이 400으로 거른다 (별도 INVALID_CURSOR 코드 불요).
- size 클램프 계약: **0 이하 또는 미지정이면 20, 51 이상이면 50** (VideoServiceImpl 선례와
  동일. size < 1은 기본값 20으로 치환하고, 50 초과만 50으로 자른다). size+1건을 조회해
  hasNext를 판정하고 초과 1건은 버린다.
- JPQL에는 LIMIT 문법이 없으므로 건수 제한은 Pageable 파라미터로 건다. 목록 repository
  메서드 시그니처:

```java
List<Notification> findInboxPage(@Param("userId") long userId,
	@Param("threshold") LocalDateTime threshold, @Param("cursor") long cursor, Pageable pageable);
```

  서비스가 `PageRequest.of(0, size + 1)`을 넘긴다 (정렬은 JPQL의 ORDER BY가 담당, Pageable은
  건수 제한만 진다).

### D-4. 30일 경계 = 서비스에서 Clock 주입으로 계산한 롤링 윈도우

`LocalDateTime.now(clock).minusDays(30)`을 threshold로 바인딩한다. 전역 Clock 빈은 없으므로
BadgeAwardServiceImpl과 같은 **이중 생성자 패턴**을 쓴다. 운영 생성자가 `Clock.systemUTC()`를
넣어 테스트용 생성자에 위임하고, 테스트는 고정 Clock을 주입한다 (인자 없는 now()는 컨벤션
금지). created_at이 UTC naive로 저장되므로 비교가 존 무관하게 성립한다. 저장 근거는 세 겹이다:
V21의 TIMESTAMP 컬럼 타입, V33의 기본값 UTC 교정, 현재 INSERT의 명시 UTC 기록(MSG-314).
KST 달력일 경계가 아니라 순수 720시간 롤링 윈도우다. PRD가 "30일 이내 생성"만 요구하므로
자정 정렬 장치를 더하지 않는다.

### D-5. 읽음 쓰기 = JPQL[^4] @Modifying 부분 UPDATE, 엔티티 더티 체킹 배제

읽음 처리를 엔티티 조회 후 save로 하면 전체 컬럼 UPDATE가 나가 컨슈머의 상태 전이와 경합 시
status를 과거 값으로 되돌릴 수 있다. read_at만 만지는 한 문장 UPDATE면 outbox 전이
UPDATE들(status, last_error, published_at, sent_at, retry_count만 SET)과 만지는 컬럼이 겹치지
않아 정합 요구가 구조적으로 성립한다. PostgreSQL 전용 기능이 필요 없으므로 native가 아니라
JPQL로 쓴다 (2026-08-19 영속 계층 개정 컨벤션).

개별 읽음은 다음 한 문장이다.

```
UPDATE Notification n SET n.readAt = coalesce(n.readAt, :now)
WHERE n.id = :notificationId AND n.userId = :userId
```

갱신 1행이면 성공(이미 읽었어도 coalesce가 최초 읽음 시각을 보존하며 1행 매칭이라 멱등 성공),
0행이면 "없거나 타인 소유"라 10404를 던진다. 존재 여부와 소유 여부를 응답으로 구분하지 않는
FR-7이 술어 하나로 충족된다.

전체 읽음은 `WHERE n.userId = :userId AND n.readAt IS NULL`이다. 30일 창이나 PREF_OFF 숨김
조건을 붙이지 않는다. 숨겨진 행이 읽음이 돼도 목록과 개수 어디에도 관찰되는 차이가 없고
(둘 다 자체 필터로 이미 제외), 술어가 단순할수록 정합을 따질 면이 준다.

쓰기 서비스는 대상 엔티티를 먼저 로드하지 않고 bulk update만 수행하며, 같은 트랜잭션에서
Notification 엔티티를 재사용하지 않는다 (영속성 컨텍스트 stale 방지, `clearAutomatically`
불요).

## API 명세

인증은 4개 전부 토큰 필수이고 대상 사용자는 `@AuthenticationPrincipal AuthPrincipal`에서
얻는다 (NotificationPreferenceController 선례). 컨트롤러 반환 타입은 전부
`SuccessResponse<T>`이므로 실제 응답은 developCode, message, data 3필드로 래핑된다 (공통 응답
규칙). 발송 내부 상태(status, retry_count, last_error)와 내부 키(event_key)는 어떤 응답에도
싣지 않는다 (비기능 보안 절).

### 1. 알림 목록 조회

```
GET /api/notifications?cursor={notificationId}&size={n}
```

| 파라미터 | 타입 | 설명 |
|---|---|---|
| cursor | Long, 선택 | 직전 응답 nextCursor. 생략하면 첫 페이지 |
| size | int, 기본 20 | 0 이하 또는 미지정이면 20, 51 이상이면 50 (D-3) |

응답 (`SuccessResponse<NotificationPageResponseDto>`, 래핑 포함 전체):

```json
{
	"developCode": 200,
	"message": "성공",
	"data": {
		"notifications": [
			{
				"notificationId": 123,
				"category": "BADGE",
				"title": "새 뱃지 획득",
				"body": "'첫 걸음' 뱃지를 획득했어요",
				"createdAt": "2026-08-19T02:11:00Z",
				"read": false
			}
		],
		"nextCursor": 123,
		"hasNext": true
	}
}
```

아래 2~4번 API 응답도 동일 래핑이며 data 안쪽만 적는다.

- 항목 타입은 `NotificationItemResponseDto`(중첩 record, 응답 DTO 네이밍 규칙 준수).
  createdAt은 `LocalDateTime`으로 선언하고 전역 코덱이 UTC Z 표기로 내린다 (DTO 시각 타입
  가드 대상이라 *Dto 네이밍 준수).
- hasNext가 false면 nextCursor는 null. 알림이 없으면 notifications 빈 배열 (FR-8).
- category는 enum 이름 문자열이다. MISSION_NEARBY는 등장하지 않는다 (FR-9, 별도 필터 없음).
  근거는 세 겹이다: 현행 notifications CHECK 제약[^5]은 V35가 정의한 7종이고, MISSION_NEARBY는
  V21 이래 어떤 CHECK 재정의(V25, V26, V35)에도 포함된 적이 없으며, V36은 opt_outs만 확장하고
  notifications CHECK는 의도적으로 불변으로 뒀다(서버 발송 경로가 없는 카테고리의 행 생성을
  막는 마지막 방어선, V36 주석). MODERATION은 발송 전용 카테고리지만 행이 존재하므로 목록에
  나온다.

에러: 없음 (도메인 에러 무발생 경로. cursor와 size 타입 불일치는 공통 400).

### 2. 안읽음 개수 조회

```
GET /api/notifications/unread-count
```

data는 `NotificationUnreadCountResponseDto`: `{ "count": 3 }` (long).
지도 홈 빨간 점은 count > 0 판정, 프로필 카드 문구는 count 값으로 FE가 조립한다 (FR-6).

### 3. 개별 읽음 처리

```
PATCH /api/notifications/{notificationId}/read
```

성공 시 data는 null이다. 이미 읽은 알림도 성공한다 (FR-4 멱등).

| 실패 | developCode | HTTP | 조건 |
|---|---|---|---|
| NOTIFICATION_NOT_FOUND | 10404 | 404 | 해당 id가 없거나 타인 소유 (FR-7, 응답 동일) |

### 4. 전체 읽음 처리

```
PATCH /api/notifications/read-all
```

성공 시 data는 null. 안읽은 알림이 0건이어도 성공한다 (FR-5 멱등). 경로 세그먼트 수가
3번 API와 달라 라우팅 충돌이 없다.

## 도메인 로직

목록과 안읽음 개수가 공유하는 노출 조건은 하나다 (glossary 용어로, 사용자가 "받은" 알림 중
설정으로 끄지 않은 최근 30일치):

```
user_id = 나
AND created_at >= now(clock) - 30일          -- FR-10, D-4
AND NOT (status = 'SKIPPED' AND last_error = 'PREF_OFF')   -- FR-11, D-2
```

- 목록: 위 조건 + `id < cursor`, `ORDER BY id DESC` + Pageable로 size+1건 제한 (D-3의
  findInboxPage 시그니처).
- 개수: 위 조건 + `read_at IS NULL`.
- 읽음 쓰기 2종은 D-5의 문장 그대로.

조회 서비스는 `@Transactional(readOnly = true)`, 쓰기 2종은 `@Transactional`이다.
목록 조회는 읽음 상태를 바꾸지 않는다 (읽음은 행 탭 시점에만, PRD 화면 확정).

## 데이터 모델

- **마이그레이션 V37** (`V37__notifications_read_at.sql`, 번호는 착수 시점 ls 재확인):

```sql
-- 알림함 읽음 상태 (MSG-434). NULL = 안읽음. 기존 행은 전부 안읽음으로 시작한다 (D-1).
ALTER TABLE notifications ADD COLUMN read_at TIMESTAMP;
```

- 새 인덱스는 만들지 않는다. 목록과 개수 쿼리 모두 `idx_notifications_user(user_id)`로
  사용자 행(수백 건)을 좁힌 뒤 처리한다. 이 결정의 검증은 실측이다. **완료 조건**: 대표
  시드(사용자당 500건, 30일 창 안팎 혼합)로 목록과 개수 쿼리의 EXPLAIN ANALYZE를 각 5회
  실행해 쿼리 실행 시간이 30ms 이내면 합격으로 본다 (p95 300ms 대비 10배 여유. 컨트롤러와
  직렬화 오버헤드를 감안한 프록시다). API 계층 p95 부하 측정은 하지 않으며, 이 프록시가
  부족해지는 규모가 되면 `(user_id, id DESC)` 복합 인덱스와 함께 재측정한다. 실행계획에
  Seq Scan이 나와도 시간 기준만 본다. 결과는 작업 로그에 기록한다.
- **엔티티**: `Notification`에 `readAt` 필드 추가 (`@Column(name = "read_at")`). 기존처럼
  조회 매핑 전용이고 상태를 바꾸는 도메인 메서드는 만들지 않는다 (쓰기는 전부 @Modifying,
  D-5).

[^1]: outbox 패턴: 알림 요청을 비즈니스 변경과 같은 DB 트랜잭션으로 테이블에 기록해 두고, 별도 프로세스가 읽어 발송하는 방식. FillMap의 notifications 테이블이 이 기록과 발송 결과 저장을 겸하며, 이번 기능은 그 위에 조회만 얹는다.
[^2]: 멱등(idempotent): 같은 요청을 여러 번 보내도 한 번 보낸 것과 결과가 같은 성질. 읽음 처리 재요청이 오류가 아니어야 행 탭과 버튼 연타가 안전하다.
[^3]: keyset 커서: 페이지 번호 대신 "직전 페이지 마지막 항목의 정렬 키"를 기준으로 그 다음부터 읽는 페이지네이션. OFFSET과 달리 새 알림이 끼어들어도 항목이 밀리거나 중복되지 않는다.
[^4]: JPQL(Java Persistence Query Language): 테이블이 아니라 엔티티를 대상으로 쓰는 JPA 표준 쿼리 언어. DB 방언에 묶이지 않아, PostgreSQL 전용 기능이 필요 없는 이 기능의 쿼리는 전부 JPQL로 쓴다.
[^5]: CHECK 제약: 컬럼이 가질 수 있는 값을 DB가 직접 검증하는 제약. notifications.category의 CHECK에 MISSION_NEARBY가 없어 그 카테고리 행은 애초에 저장될 수 없고, 덕분에 목록 필터가 필요 없다.
