# MSG-442: 행사 생명주기, 30일 유예 가드, 알림 구독

**Owner**: B. `com.msg.fillmap.event.*`(MSG-438이 Owner B로 확정, CLAUDE.md 목록 등재)와
`com.msg.fillmap.notification.*`(Owner B, MSG-178)만 건드린다. grid 도메인 코드는 무변경이다.

> 요구사항 정본: `docs/prd/event-room-location-videos.md` (확정, 2026-08-20 정민 승인) §4.2 행사
> 상태 표, US-007, US-009, FR-12~16, FR-22. `docs/srs.md` FR-EVENT-06(알림 구독),
> FR-EVENT-10(생명주기). 형제 티켓: MSG-438(데이터 모델, 머지 완료), MSG-439(조회 API, PR #197
> 진행 중), MSG-440(업로드, 미착수), MSG-441(댓글·도움돼요, 미착수), MSG-443(열람 인원, 머지
> 완료).

## 개요

행사 회차의 4단계 생명주기(예정, 진행 중, 업로드 유예, 아카이브)를 실제 동작으로 만든다. 저장
상태 컬럼은 만들지 않고 MSG-438이 구현해 둔 `EventOccurrence.statusAt(now)` 파생 계산을
재사용한다. 이 티켓의 산출물은 세 가지다. 첫째, 상태별 차단 규칙을 판정하는 공용 가드
컴포넌트(MSG-440 업로드와 MSG-441 댓글·도움돼요가 소비할 계약). 둘째, 행사 회차 단위 알림 구독
토글 API와 구독 저장 테이블. 셋째, 상태 경계의 부수효과(시작 알림 발송, 일정 변경 알림, 종료 시
구독 자동 해제)를 멱등[^1]하게 수행하는 스케줄러다.

## 배경 · 목표

행사방은 참여 절차가 없다. 사용자가 행사와 맺는 유일한 관계가 알림 구독이고(FR-EVENT-06),
행사의 시간 흐름이 곧 기능 차단 규칙이다(FR-EVENT-10). 종료 시점부터 댓글과 도움돼요 변경이
막히고, 종료 30일 후에는 업로드까지 막혀 읽기 전용 아카이브가 된다. 이 규칙을 소비할 쓰기
API(업로드는 440, 댓글·도움돼요는 441)가 아직 없으므로, 442는 규칙 자체를 한 곳에 구현해 단위
검증까지 끝내 두고 440·441은 호출 한 줄로 소비하게 만든다. 판정 규칙이 흩어지면 경계 정각의
해석이 API마다 갈라지기 때문이다.

## 확정 사항 (스펙 근거 기록)

- **예정 상태의 행사 경유 업로드 차단** (2026-08-21 사용자 확정, PRD §4.2에 반영됨). PRD
  §4.2가 "정책상 허용 시 가능"으로 열어 뒀던 미결의 해소이며 정본 PRD의 상태 표와 확정 기록
  불릿을 함께 갱신했다. 마감(`EVENT_UPLOAD_CLOSED`)과 구분되는 별도 에러코드
  `EVENT_UPLOAD_NOT_STARTED`를 쓴다(FE는 버튼 비활성화 근거로 구분이 필요하다). 따라서 행사
  연결 업로드 가능 구간은 시작부터 종료 30일 후까지다. 일반 격자 업로드는 이 티켓과 무관하게
  언제나 자유다(행사와 관계만 맺지 않는다).
- **알림 발송 대상은 행사 시작과 일정 변경 두 종뿐이다** (2026-08-21 오케스트레이터 판정).
  댓글 알림은 미도입이다. 댓글 도메인 자체가 MSG-441 미착수이고, 도입하려면 신규 요구 등재가
  선행이다. SRS 미해결 "행사방 알림 범위"는 이 판정으로 종결했다(FR-EVENT-06 비고 반영).
- **상태 판정 재사용**: `EventOccurrence.statusAt(now)`와 `uploadClosesAt()`이 정의의 정본이고
  경계는 전부 반개구간[^2]이다(정각은 다음 상태 소속, MSG-438·439 확정 그대로). 442는 이
  메서드를 호출만 하고 경계 정의를 어디에도 복제하지 않는다.
- **시각 처리**: 모든 판정 시각은 주입된 `Clock`에서 얻는다. 인자 없는 `now()` 금지, naive
  `LocalDateTime` = UTC 관례(project-conventions.md 시각 처리 절, MSG-376).
- **운영 기본값 확정** (2026-08-21 오케스트레이터 판정): 스케줄러 폴 주기 5분
  (`fillmap.event.lifecycle.poll-interval-ms` 기본 300000), 시작 알림 발송 창 24시간, 알림
  문구는 아래 발송 표 그대로. 셋 다 제품 요구가 아니라 프로퍼티나 상수로 덮을 수 있는 운영
  기본값이므로 스펙이 값을 확정한다.
- **종료 후 구독 의미론**: 구독 해제 시점은 정리 틱 타이밍이 아니라 **종료 경계(endsAt)
  통과** 하나로 결정된다. 종료 경계를 지난 회차의 구독은 어떤 재시드로도 되살아나지 않고,
  이미 해제됐거나 해제될 사용자에게는 그 회차의 알림도 더 나가지 않는다. 자동 해제(FR-16)가
  정당하게 발화한 결과이고, 집행 지점은 둘이다: 스케줄러 정리 틱, 그리고 종료 경계를 지난
  회차를 건드리는 시더 갱신 경로의 구독 선삭제(둘은 같은 advisory lock으로 직렬화된다.
  스케줄러 2단계와 시더 훅 참조, Codex 2R·4R·5R 반영).

## API 명세

### PUT /event-occurrences/{occurrenceId}/notification (인증 필수)

행사 회차 단위 알림 구독 ON/OFF (PRD §7, US-007). 참여 개념이 없으므로 구독이 곧 사용자와
행사의 관계 전부다.

- Request: `EventNotificationUpdateRequestDto` `{ "enabled": true }` (`@NotNull Boolean`)
- Response: `EventNotificationResponseDto` `{ "enabled": true }` (요청 처리 후의 현재 노출
  상태, 아래 파생 정의 기준)
- 멱등: 같은 값의 반복 요청은 같은 결과로 성공한다. ON 반복은 기존 행 유지(PostgreSQL
  `ON CONFLICT DO NOTHING`, `NotificationOptOutRepository.insertOptOut` 선례), OFF 반복은 삭제
  0행으로 성공.
- 에러:
  - 회차 없음 → `EVENT_NOT_FOUND` (MSG-439가 만드는 상수 재사용)
  - 종료된 행사(UPLOAD_GRACE, ARCHIVED)에 ON 요청 → `EVENT_INTERACTION_LOCKED`. PRD §4.2가
    유예부터 알림을 자동 OFF로 확정했으므로 종료 후 ON은 상태표와 모순이고, 시작 알림이 이미
    지난 구독은 받을 것이 없다. 종료 행사의 상호작용 잠금이라는 의미가 같아 새 코드를 만들지
    않는다. OFF 요청은 상태와 무관하게 항상 성공한다(구독 해제를 막을 이유가 없다).
- UPCOMING과 LIVE에서는 ON/OFF 모두 가능(PRD §4.2 "사용자 선택").

구현: `EventNotificationController` → `EventNotificationService`/`Impl`
(`com.msg.fillmap.event`). 439 헤더 응답의 알림 상태 필드가 소비할 조회는 같은 서비스의
`boolean isSubscribed(Long userId, Long occurrenceId)`로 노출한다.

**노출 상태는 파생값이다**: `isSubscribed` = 구독 행 존재 AND `statusAt(now)`가 UPCOMING 또는
LIVE. 행 존재만 보면 종료 시각부터 스케줄러의 다음 정리 틱까지(최대 폴 주기만큼, 발송이 꺼진
환경 논외로도) 헤더가 ON으로 보여 PRD §4.2 "유예부터 자동 OFF"와 모순되기 때문이다. 스케줄러의
행 삭제는 정리이지 상태 전환이 아니다. 상태 전환은 이 파생식 하나가 담당하고, PUT 응답의
`enabled`도 같은 식을 쓴다.

### 에러 코드 (event 13xxx 대역, response-pattern.md 표 등재 완료)

`EventErrorCode`는 MSG-439(PR #197)가 `EVENT_NOT_FOUND`와 함께 생성한다. 442는 그 enum에 세
상수를 추가한다(439 병합 후 번호 충돌 재확인, 아래 미해결 질문 1).

| 상수 | developCode 제안 | HttpStatus | 메시지 제안 | 소비처 |
|---|---|---|---|---|
| `EVENT_UPLOAD_NOT_STARTED` | 13420 | CONFLICT | 아직 시작 전인 행사입니다 | 가드(440 소비) |
| `EVENT_UPLOAD_CLOSED` | 13421 | CONFLICT | 업로드 기간이 마감된 행사입니다 | 가드(440 소비) |
| `EVENT_INTERACTION_LOCKED` | 13422 | CONFLICT | 종료된 행사에서는 변경할 수 없습니다 | 가드(441 소비), 구독 ON |

409 CONFLICT인 이유: 권한이 아니라 리소스(행사)의 현재 상태와 요청이 충돌하는
거절이다(`DUPLICATE_REPORT` 11409 선례).

## 도메인 로직

### 생명주기 가드 `EventLifecycleGuard` (공용 컴포넌트, 440·441 소비 계약)

`com.msg.fillmap.event.service`의 `@Component`. `Clock`을 주입받아(기본 `Clock.systemUTC()` +
테스트 생성자, `EventViewerServiceImpl` 선례) 판정 시각을 스스로 만든다. 소비자는 회차 엔티티만
넘기면 된다.

```java
public void checkUploadOpen(EventOccurrence occurrence);       // 440 업로드 경로가 호출
public void checkInteractionOpen(EventOccurrence occurrence);  // 441 댓글·도움돼요 경로가 호출
```

| statusAt(now) | checkUploadOpen | checkInteractionOpen |
|---|---|---|
| UPCOMING | throw `EVENT_UPLOAD_NOT_STARTED` | 통과 (PRD §4.2 예정 상태 댓글·도움돼요 가능) |
| LIVE | 통과 | 통과 |
| UPLOAD_GRACE | 통과 (종료 후 30일 유예, FR-12) | throw `EVENT_INTERACTION_LOCKED` (FR-13) |
| ARCHIVED | throw `EVENT_UPLOAD_CLOSED` (FR-15) | throw `EVENT_INTERACTION_LOCKED` |

- 조회는 어느 상태에서도 막지 않으므로 가드에 조회 메서드가 없다(FR-14, 조회 차단 없음).
- 경계 판정은 `statusAt` 하나에 위임하므로 가드에는 시각 비교식이 없다. 유예 기간에 올라간
  영상이 처음부터 댓글·도움돼요 불가인 것(US-009)도 별도 로직이 아니다. 잠금이 영상이 아니라
  회차 상태의 파생이기 때문이다(438이 `interactionLocked` 저장 컬럼을 두지 않은 결정의 귀결).
- 가드의 단위 검증은 이 티켓에서 끝낸다(4상태 × 2메서드 + 경계 정각). 440·441은 호출 존재만
  자기 테스트에서 확인하면 된다.

### 알림 구독과 발송

구독 모델은 회차 단위 opt-in[^3]이다. 행 존재 = 구독 ON. 여기에 기존 알림 설정의 카테고리
스위치(FR-EVENT-06 "카테고리로도 켜고 끌 수 있다")가 겹쳐진다. 실제 발송 여부는 두 층의 AND다:
회차 구독 행이 있고, `notification_opt_outs`에 EVENT off 행이 없어야 발송된다. 카테고리 층은
기존 경로가 대부분 처리한다. `NotificationConsumer`가 발송 직전
`isEnabled(userId, category)`를 검사해 off면 SKIPPED 처리하고(`NotificationConsumer:95`), 설정
표면(`NotificationPreferenceServiceImpl`의 목록·PATCH)은 enum 순회 기반이라 MODERATION 같은
제외 분기를 추가하지 않는 한 자동 편입된다(EVENT는 설정 가능 카테고리이므로 분기를 추가하지
않는다). PATCH의 카테고리 검증(`NotificationPreferenceServiceImpl:75`의 `valueOf` 파싱과 :79의
MODERATION 분기)도 enum 기반이라 EVENT를 자동 수용한다(`INVALID_CATEGORY` 경로 변경 불요).
다만 enum 추가만으로 끝나지는 않는다. notification 도메인에서 442가 고치는 지점은 다섯 곳이다:

1. `NotificationCategory`에 `EVENT` 추가(주석에 MSG-442, 양쪽 CHECK 소속 명기).
2. **`NotificationConsumer.rateLimited()`의 망라 switch에 `case EVENT -> null` 추가**
   (`NotificationConsumer:130`). default 없는 망라 switch라 case를 추가하지 않으면 컴파일이
   깨진다. 전송률은 무제한(null)이다. 시작 알림은 dedupe가 회차당 1건으로 이미 누르고 일정
   변경은 희소해 도배 벡터가 없다(BADGE·WEEKLY와 같은 결). 근거는 기존 case들처럼 그 자리
   주석으로 남긴다.
3. **알림함 목록 DTO의 공개 계약 표면**: `NotificationPageResponseDto:38`의 `@Schema
   allowableValues` 7종에 `EVENT` 추가. EVENT는 서버 발송형이라 outbox 행이 생겨 알림함
   목록에 실린다(MISSION_NEARBY만 발송 경로 부재로 의도 제외 유지, 그 자리 주석 그대로).
4. **알림 설정 DTO의 공개 계약 표면**: `NotificationPreferenceResponseDto:27`의 `@Schema
   allowableValues` 7종에 `EVENT` 추가. EVENT는 설정 가능 카테고리다(MODERATION 의도 제외는
   MSG-417 5절 결정 그대로 유지).
5. **카테고리 수를 세는 기존 테스트의 기대값 갱신**:
   `NotificationPreferenceServiceIntegrationTest`("카테고리 7종 전부" 전수 대조, :135)에
   EVENT를 추가하고, 같은 기대를 가진 인접 테스트(NotificationPreferenceControllerTest 등
   컨트롤러·DTO 스키마 검증 계열 포함)를 grep으로 전수 확인해 함께 갱신한다.

발송은 전부 기존 outbox[^4] 경로다. `NotificationCommandService.record()`가
`uq_notifications_user_event`(user_id + event_key UNIQUE)로 재기록을 흡수하므로, 발송 트리거를
몇 번 재실행해도 알림은 1회다. 스케줄러 멱등의 근거가 이 제약이다(WeeklySummaryScheduler의
`WEEKLY:{주차}` 선례).

발송하는 알림은 아래 두 종이 전부다. **댓글 알림은 미포함이다**(2026-08-21 판정, 확정 사항
참조. SRS 미해결 "행사방 알림 범위" 종결).

| 알림 | eventKey | title | body (확정) |
|---|---|---|---|
| 행사 시작 | `EVENT_START:{occurrenceKey}:{startsAt epoch초}` | 회차 title | 행사가 시작됐어요. 현장 영상을 올려보세요 |
| 일정 변경 | `EVENT_SCHEDULE:{occurrenceKey}:{scheduleRevision}` | 회차 title | 행사 일정이 변경됐어요. 새 일정을 확인해 보세요 |

- 길이 검산: event_key VARCHAR(100), occurrenceKey 최대 60자 기준 시작 키 최대
  12+60+1+10 = 83자, 일정 키 최대 15+60+1+10 = 86자로 안에 든다.
- 일정 변경 키는 시각값이 아니라 **단조 증가 개정 번호** `schedule_revision`(아래 데이터 모델)
  기반이다. 새 시각값을 키에 쓰면 A→B→A→B 왕복에서 두 번째 "B로 변경" 알림이 첫 번째와 같은
  키가 되어 dedupe에 억제되고, 사용자가 마지막 일정을 잘못 알게 된다(Codex 1R 적발). 개정
  번호는 변경마다 다르므로 매 변경이 정확히 1회씩 나간다.
- 시작 키에 startsAt을 넣는 이유: 일정 변경으로 시작이 미뤄지면 새 시각 도래 때 시작 알림이
  다시 나가야 한다. 일정 버전마다 키가 달라 dedupe가 버전 단위로 걸린다. 일정을 원래 시각으로
  되돌린 경우 시작 알림이 다시 나가지 않는 것은 억제가 아니라 올바른 동작이다(그 시각의 시작
  알림은 이미 받았고, 되돌림 자체는 일정 변경 알림이 알린다).
- title은 회차 title(최대 100자)을 그대로 쓴다. notifications.title도 VARCHAR(100)이라 잘림이
  없다. 문구는 위 표가 확정값이다(2026-08-21 판정, 확정 사항 참조).

### 스케줄링 설정 `EventSchedulingConfig` (무조건 활성)

`@EnableScheduling`은 레포에 두 곳뿐인데 둘 다 조건부다. `AiConfig`는 `ai.enabled`,
`NotificationConfig`는 `fillmap.notification.enabled` 게이트 안에 있어(Codex 4R 적발,
`HotScoreCommandServiceImpl:92` 주석이 같은 한계를 기록한 선례), 두 플래그가 모두 꺼진
환경(기본값)에서는 스케줄링 인프라 자체가 뜨지 않아 아래 스케줄러 빈을 무조건 띄워도
`@Scheduled`가 돌지 않는다. 따라서 event 도메인에 **조건 없는
`@Configuration @EnableScheduling` 하나**(`com.msg.fillmap.event.config.EventSchedulingConfig`)를
둔다. `@EnableScheduling`의 중복 선언은 무해하다(스프링이 인프라 빈을 한 번만 등록하는
멱등 애너테이션). 이 설정이 정리 단계(종료 구독 해제)의 실행 전제다.

### 스케줄러 `EventNotificationScheduler` (시작 알림 + 종료 시 구독 해제)

`com.msg.fillmap.event.service`. **빈은 조건 없이 항상 뜬다.**
`fillmap.notification.enabled`로 클래스를 게이트하면 안 된다(Codex 1R 적발). 그 속성의
기본값이 false라(application.yml:103, local·CI가 이 상태) 스케줄러가 통째로 죽으면 구독 API는
열려 있는데 종료 구독 해제(FR-16)가 영원히 돌지 않아 행이 무한 축적된다. 정리는 발송 게이트
밖이어야 한다. 구조는 한 클래스에 두 단계이고 발송 단계만 속성 검사로 스킵한다
(`@Value("${fillmap.notification.enabled:false}")` 주입).
`@Scheduled(fixedDelayString = "${fillmap.event.lifecycle.poll-interval-ms:300000}")`, 기본
5분(확정 기본값, 프로퍼티로 오버라이드). `Clock` 주입(기본 systemUTC + 테스트 생성자). 한 틱에
두 작업을 순서대로 한다.

1. **시작 알림 발송** (notification enabled일 때만): `startsAt <= now <
   min(endsAt, startsAt + 24시간)`인 회차를 조회하고, 각 회차의 구독자 중
   `created_at <= starts_at`인 사용자에게 `record()` 한다.
   - 발송 창 24시간(확정 기본값): dedupe만으로도 중복은 없지만, BIFF처럼 열흘짜리 LIVE 내내 매
     틱 전 구독자 무효 insert를 반복하지 않기 위한 스캔 상한이다. 서버가 24시간 연속으로 죽어
     창을 통째로 놓치면 시작 알림은 유실을 허용한다(넛지는 보장이 아니라 기회, MSG-314 D3
     승계).
   - `created_at <= starts_at` 조건: 시작 후에 구독한 사용자는 행사가 진행 중임을 이미 알고
     눌렀으므로 뒤늦은 "시작됐어요"를 보내지 않는다.
   - 사용자 단위 실패 격리(한 명의 record 실패가 나머지를 막지 않음, WeeklySummaryScheduler
     선례). 다음 틱 재실행이 재시도이고 dedupe가 중복을 흡수한다.
2. **종료 시 구독 자동 해제** (FR-16, PRD §4.2 유예부터 자동 OFF. 게이트 없이 항상 실행):
   `endsAt <= now`인 회차의 구독 행을 일괄 삭제한다. JPQL 벌크 delete 한 문장이다(`DELETE ...
   WHERE s.id.eventOccurrenceId IN (SELECT o.id FROM EventOccurrence o WHERE o.endsAt <=
   :now)`). DELETE는 본성상 멱등이라 재실행 안전 요건(PRD §10)이 그냥 충족된다. 이 삭제는
   저장소 정리다. 사용자에게 보이는 OFF 전환은 `isSubscribed` 파생식(위 API 명세)이 종료
   시각에 즉시 수행하므로 정리 지연이 노출 상태에 영향을 주지 않는다.
   - **재시드와의 경쟁은 advisory lock으로 직렬화한다** (Codex 2R 적발): 정리 트랜잭션이 구
     `endsAt` 스냅숏으로 도는 사이 시더가 일정 연장을 커밋하면, 되살아난 회차의 구독이
     전멸하고 그 일정 변경 알림도 수신자 0으로 유실된다. 정리 단계는 자체 트랜잭션 서두에서
     **438 시더와 같은 고정 키의 `pg_advisory_xact_lock`**(트랜잭션 종료 시 자동 해제)을
     선취한 뒤 DELETE를 실행한다. 시더 실행 중이면 대기하고, 락 획득 후의 DELETE는 연장이
     커밋된 `endsAt`을 읽으므로 연장된 회차는 자연히 no-op이다. 순서가 반대라면(정리가 먼저
     커밋) 확정 사항의 의미론대로 해제가 정당하게 남는다.

일정 변경 알림의 트리거는 스케줄러가 아니라 **시더**다. 일정은 재시드로만 바뀌므로(438 확정,
`EventOccurrence.update()`가 유일한 갱신 경로), `EventOccurrence.update()`가 기존
`startsAt` 또는 `endsAt`과 새 값이 다를 때만 `scheduleRevision`을 +1 하고(값이 같은 재시드는
불변이라 멱등 유지), `EventSeeder`의 회차 갱신 지점에서 개정 번호가 올랐으면 그 회차의 현재
구독자 전원에게 `record()` 한다. 시딩 트랜잭션 안이라 outbox의 원자성 설계(비즈니스 커밋과
같은 커밋)에 정확히 부합하고, 재실행돼도 같은 개정 번호는 같은 dedupe 키라 흡수된다. 시더끼리와
정리 단계와의 동시 실행은 위 advisory lock 하나가 직렬화한다(438이 시더끼리에 이미 쓰는 그
키다).

**종료 경계를 지난 회차를 건드리는 재시드는 구독을 먼저 지운다** (Codex 4R 적발, 5R에서 조건
단순화): 시더의 회차 갱신 경로(advisory lock 하)는 **구 `endsAt <= now`(락 획득 후 시각)이면
새 값과 무관하게 그 회차의 구독 행을 같은 트랜잭션에서 먼저 삭제한 뒤** 갱신을 적용한다. 종료
경계 통과 = 해제라는 규칙의 집행 지점이 정리 틱과 시더 터치 둘로 통일되는 것이고, 두 구멍을
한꺼번에 막는다. 부활 연장(새 `endsAt > now`)에서는 정리 틱의 no-op으로 살아남은 구독 행이
파생 `isSubscribed`를 다시 ON으로 만들고 일정 변경 알림까지 받는 문제(4R), 종료 유지
변경(새 `endsAt`도 과거)에서는 정리 틱 전 창의 구독 행이 일정 변경 알림을 받는 문제(5R)가
그 두 구멍이다. 어느 쪽이든 선삭제로 수신자가 없어져 논리적으로 이미 해제된 사용자에게 알림이
나가지 않고, 구독 해제 시점이 정리 틱 타이밍과 무관하게 종료 경계 통과 하나로 결정된다.

## 데이터 모델

Flyway `V40__event_notification.sql` 하나. V39가 최신임을 확인했고 V40을 이 티켓이 선점한다.

```sql
-- V40__event_notification.sql
-- MSG-442: 행사 알림 구독(FR-EVENT-06) + 알림 카테고리 EVENT 확장 + 일정 개정 번호.

-- 행 존재 = 해당 회차 알림 ON (opt-in. notification_opt_outs 의 거울상 방향).
-- 시각 DEFAULT 는 V33 선례를 따른다: CURRENT_TIMESTAMP 는 timestamptz 라 naive 컬럼 대입 시
-- 세션 타임존으로 변환돼 KST 세션에서 9시간 앞선 값이 저장된다. statement_timestamp() AT TIME
-- ZONE 'utc' 는 세션 타임존과 무관하게 항상 UTC 벽시계다 (created_at <= starts_at 판정 재료라
-- 어긋나면 시작 알림 대상 선별이 9시간 틀어진다).
CREATE TABLE event_notification_subscriptions (
	user_id             BIGINT    NOT NULL REFERENCES users(id) ON DELETE CASCADE,
	event_occurrence_id BIGINT    NOT NULL REFERENCES event_occurrences(id) ON DELETE CASCADE,
	created_at          TIMESTAMP NOT NULL DEFAULT (statement_timestamp() AT TIME ZONE 'utc'),

	PRIMARY KEY (user_id, event_occurrence_id)
);

-- 스케줄러 fanout·종료 일괄 해제의 조회 키 (PK 는 user_id 선두라 회차 조회를 못 탄다)
CREATE INDEX idx_event_noti_sub_occurrence ON event_notification_subscriptions (event_occurrence_id);

-- 일정 개정 번호: 시각 변경 시에만 +1 (엔티티 update() 소유). 일정 변경 알림 dedupe 키 재료.
-- 시각값 키는 일정 왕복(A→B→A→B)에서 두 번째 변경 알림이 억제되므로 단조 증가 번호로 대체한다.
ALTER TABLE event_occurrences ADD COLUMN schedule_revision INT NOT NULL DEFAULT 0;

-- EVENT 카테고리 확장. 기존 행 무변경, CHECK 상위집합 재정의 (V35·V36 형상).
-- 'EVENT'(5자)는 notifications VARCHAR(10)·opt_outs VARCHAR(20) 폭 확장이 불요하다.
ALTER TABLE notifications DROP CONSTRAINT chk_notifications_category;
ALTER TABLE notifications ADD CONSTRAINT chk_notifications_category
	CHECK (category IN ('BADGE', 'HOTZONE', 'REMIND', 'VIDEO', 'WEEKLY', 'FRIEND', 'MODERATION', 'EVENT'));

ALTER TABLE notification_opt_outs DROP CONSTRAINT chk_notification_opt_outs_category;
ALTER TABLE notification_opt_outs ADD CONSTRAINT chk_notification_opt_outs_category
	CHECK (category IN ('BADGE', 'HOTZONE', 'REMIND', 'VIDEO', 'WEEKLY', 'FRIEND', 'MISSION_NEARBY', 'EVENT'));
```

- 두 CHECK 모두에 EVENT가 실린다. 발송 경로가 있고(notifications) 설정 대상이기도
  하다(opt_outs). MODERATION(발송만)·MISSION_NEARBY(설정만)와 달리 양쪽 다인 일반형이다.
- 엔티티: `EventNotificationSubscription` (`com.msg.fillmap.event.entity`).
  `@EmbeddedId EventNotificationSubscriptionId(userId, eventOccurrenceId)` + `createdAt`.
  연관관계를 달지 않는다. 이 엔티티를 축으로 한 조인 조회가 없고(스케줄러는 회차 목록을 먼저
  뽑고 회차별 구독자를 파생 쿼리로 읽는 2단 조회, 해제는 서브쿼리 벌크 delete), 유일한 참조
  대상인 `EventOccurrence`는 타 조회에서 이미 손에 들려 있다. `NotificationOptOut`과 같은
  형상이다.
- `EventOccurrence`(438 엔티티)에 `scheduleRevision` 필드를 추가하고, `update()`가 시각 변경
  시에만 +1 한다(위 도메인 로직 참조).
- `EventSchedulingConfig` 신설(`com.msg.fillmap.event.config`, 조건 없는
  `@Configuration @EnableScheduling`). 근거는 위 스케줄링 설정 절 참조.
- notification 도메인 변경 5건(enum EVENT 추가, `NotificationConsumer.rateLimited()` case
  추가, 목록·설정 DTO의 `allowableValues` 2곳, 카테고리 수 기대 테스트 갱신)은 위 도메인 로직
  절 참조. PATCH 카테고리 검증은 enum 기반이라 변경 불요다.
- 리포지토리: `EventNotificationSubscriptionRepository`. ON CONFLICT insert(native, PG 전용
  허용 대상)와 삭제, `existsById`, `findAllByIdEventOccurrenceId`, 종료 회차 벌크
  delete(JPQL)와 종료 경계 지난 회차 터치 시의 회차 단위 벌크 delete. 회차 조회는 기존
  `EventOccurrenceRepository`에 파생 쿼리 추가. 정리 단계의 advisory lock 획득은 438 시더의
  native 선례를 따른다(PG 전용 허용 대상).

## 성공 기준

- 4상태 각각에서 가드 판정이 PRD §4.2 표와 일치하고, 경계 정각(startsAt, endsAt,
  uploadClosesAt)이 반개구간 규칙대로 다음 상태 판정을 받는다 (FR-EVENT-10, FR-12·13·15·22).
- 구독 토글이 멱등하고, 종료된 행사의 ON이 거절되며, 노출 상태가 종료 시각부터 즉시 OFF로
  파생된다(정리 틱을 기다리지 않는다, PRD §4.2) (FR-EVENT-06).
- 시작 알림이 구독자에게 1회만 발송되고, 스케줄러를 재실행해도 중복이 없으며, 시작 후
  구독자는 받지 않는다. 일정 변경 재시드가 구독자에게 변경 알림을 만들고, 같은 재시드 반복은
  추가 알림을 만들지 않으며, 일정을 되돌렸다 다시 바꾸는 왕복에서도 매 변경이 발송된다.
- 종료 시각이 지나면 스케줄러가 구독을 자동 해제하고 재실행에 안전하며, 알림 발송이 꺼진
  환경(스케줄링 인프라는 EventSchedulingConfig가 무조건 제공)에서도 해제는 돌고, 종료 경계를
  지난 회차는 어떤 재시드(부활 연장이든 종료 유지 변경이든)로도 해제 전 구독이 되살거나
  알림을 받지 않는다 (FR-16, PRD §10).
- EVENT 카테고리가 알림 설정 목록에 나타나고 off면 발송이 SKIPPED 된다 (FR-EVENT-06 카테고리
  스위치).

아래 테스트 시나리오가 이 기준의 검증 수단이다. 테스트에 `// 검증: FR-EVENT-10` 형식 주석을
단다(finalize 2-1. SRS FR-EVENT-06·10 상태 갱신과 rtm 재생성은 구현 마무리 몫. FR-EVENT-10
문안의 시작 전 차단 추가와 FR-EVENT-06 발송 대상 확정, 미해결 "행사방 알림 범위" 종결은
스펙 단계에서 이미 반영했다. `docs/srs-changelog.md` 2026-08-21 행 참조).

## 미해결 질문

남는 미해결은 아래 1건뿐이다(폴 주기·발송 창·문구는 확정 기본값으로 승격, 확정 사항 참조).

1. **MSG-439(PR #197) 병합 조율**: 이 워크트리(develop 4caf7ca)에는 `EventErrorCode`와 439
   스펙이 아직 없다. 442 구현 착수 시점에 439 병합 여부를 확인해, 병합됐으면 그 enum에 상수
   3개를 추가하고 developCode 번호 충돌을 재확인하며(위 표의 13420~13422는 제안값), 439 헤더
   응답의 알림 상태 필드가 스텁인지 확인해 `isSubscribed` 배선을 잇는다. 439보다 먼저 나가야
   하면 enum 생성 주체가 442로 넘어오므로 커밋 경합 정리가 필요하다.

[^1]: 멱등(idempotent): 같은 작업을 여러 번 실행해도 한 번 실행한 것과 결과가 같은 성질.
    스케줄러 재실행과 재시드가 안전하려면 부수효과가 이 성질을 가져야 한다.
[^2]: 반개구간: 시작점은 포함하고 끝점은 제외하는 구간 표기. 경계 정각이 정확히 한 상태에만
    속해 상태 판정에 빈틈과 겹침이 없다. 정의는 `EventOccurrence.statusAt` 한 곳이다.
[^3]: opt-in / opt-out: 명시적으로 켜야 동작하는 것이 opt-in, 명시적으로 꺼야 멈추는 것이
    opt-out이다. 행사 구독은 행 존재가 ON인 opt-in이고, 기존 알림 카테고리 설정은 행 존재가
    OFF인 opt-out이라 방향이 반대다.
[^4]: outbox: 알림 요청을 비즈니스 트랜잭션과 같은 커밋으로 DB에 먼저 기록하고, 별도
    릴레이가 나중에 실제 발송하는 패턴. 기록의 UNIQUE 제약(user_id + event_key)이 중복 발송
    방어를 겸한다.
