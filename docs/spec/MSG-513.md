# MSG-513: 여행 요청이 아닌 문장에 동선이 나오지 않게 막는다

**Owner**: 공동 (주 구현 B, MSG-457 §Owner 판정 선례. 변경 파일은 전부 route 패키지와 그
테스트라 A 몫 구현은 없고, FillMap-AI 쪽 개정은 별도 레포의 분리 티켓이다)

> 요구사항 정본: `docs/prd/MSG-513-prd.md` (검토됨, 2026-08-31 성민 승인). SRS `FR-ROUTE-19` (계획).

## 개요

AI 해석 계약에 관련성 판정 필드를 하나 넣고, 서버가 그 값을 소비해 무관 문장에는 동선 대신
전용 안내를 돌려준다. 지금은 "롤 정글 동선 짜 줘" 같은 문장도 빈 해석[^1]으로 돌아와 뷰포트
기준 추천이 그대로 나간다. 판정 위치는 AI이고 서버는 소비만 한다(PRD 확정, 서버 추정안 기각).
새 developCode는 없고, 무관 응답은 200에 빈 목록과 안내가 실리는 정상 응답이다.

## 배경 · 목표

빈 해석은 FR-ROUTE-06이 유효한 해석으로 규정한다. "이 근처 아무거나"를 살리는 그 규정 때문에,
해석에서 아무것도 못 읽은 무관 문장과 정보 없는 여행 문장이 서버에서 같은 모양이 된다. 이번
작업은 그 둘을 가르는 축(관련성)을 해석 계약에 별도로 신설한다. FR-ROUTE-06은 개정하지 않고,
관련성은 FR-ROUTE-19로 따로 등재됐다. 판정 기본값은 추천 시도다. 여행 요청을 잘못 거부하는
것이 무관 문장에 추천이 나가는 것보다 나쁘다(PRD FR-3).

## 성공 기준

항목마다 붙은 번호가 테스트 검증 마커(`// 검증: FR-ROUTE-19, AC-513-XX`)와 이어진다.

- AC-513-01: 무관 판정(related=false)이 실린 해석을 받으면 200 응답에 points가 빈 목록이고
  notice가 전용 안내 문구다. 후보 수집, 언급 지역 판정, explain[^2]을 부르지 않는다.
- AC-513-02: 전용 안내 문구는 후보 없음 안내(EMPTY_NOTICE)와 글자가 다르다.
- AC-513-03: related=true인 해석은 빈 해석이어도 기존 뷰포트 기준 추천 흐름을 그대로 탄다.
  지역만 적은 문장("부산"), 관심사만 적은 문장("맛집"), 정보가 없는 여행 문장("이 근처
  아무거나")이 이 경로다 (FR-ROUTE-06 유지).
- AC-513-04: related가 boolean이 아니거나(문자열 "false", 숫자 등) 정의 밖 필드가 있으면
  기존 규칙대로 14502다 (FR-ROUTE-08 유지).
- AC-513-05: related 필드가 없는 구버전 AI 응답은 true로 수용돼 기존 추천 흐름이 나온다
  (배포 순서 호환, 결정 2의 한시 규칙).
- AC-513-06: 무관 안내로 끝난 요청도 요청 제한 창[^3]을 소모한다. 직후 재요청은 14429다
  (FR-ROUTE-12 유지).
- AC-513-07: 해석 캐시[^4] 창 안의 같은 재요청은 parse 재호출 없이 같은 무관 안내를 재현한다
  (FR-ROUTE-10의 짧은 간격 재현 범위).
- AC-513-08: 무관 판정으로 끝난 요청이 지표 로그에 outcome=unrelated 한 줄로 남는다.
- AC-513-09: 무관 응답의 mentionedArea는 null이고, 자동 이동 재요청 예외(MSG-487)가 부여되지
  않는다.
- AC-513-10: 무관 판정 경로의 외부 AI 호출은 parse 한 번뿐이다 (PRD 운영 비기능 "호출 수는
  늘지 않는다").

## 결정 (스펙 몫 6건의 해소)

### 결정 1. 관련성 필드는 `related`, 타입은 boolean이다

의미는 "이 문장이 장소 방문 동선을 짜 달라는 요청과 관련 있는가"이고, 확실히 무관할 때만
false다. 애매하면 true라는 기본값 방향(PRD FR-3)이 긍정형 이름과 자연스럽게 맞는다.

- 기각 대안 1: 3값 열거(travel, uncertain, unrelated). 서버가 uncertain을 travel과 똑같이
  처리하므로(애매하면 추천 시도) 세 번째 상태가 아무 분기도 만들지 않는다. 상태를 늘릴 이유가
  생기면 그때 계약 개정으로 확장한다.
- 기각 대안 2: 부정형 이름(unrelated, off_topic). 프롬프트와 검증 코드에서 이중 부정("무관이
  아니면")이 반복돼 읽기 나쁘다.
- 표기: 해석 계약의 다른 키가 snake_case 한 단어(region)와 두 단어(preferred_order)를 쓰고
  있어 `related` 한 단어로 충분하다. 서버 record 필드는 `boolean related`다.

### 결정 2. 배포 순서는 서버가 먼저다. 부재는 true로 한시 수용하고, AI 배포 뒤 필수로 승격한다

서버 검증이 "정의 밖 필드 거부"라서 AI가 먼저 다섯 번째 필드를 내보내면 모든 parse 응답이
14502로 수렴해 전면 장애가 된다. 반대로 서버가 먼저 나가면 구버전 AI의 4필드 응답을 처리할
규칙이 필요하다. 세 단계로 간다.

1. **이번 티켓(서버)**: 허용 필드 집합을 5키로 넓힌다(`related` 추가). 필수 검사는 기존 4키
   그대로 두고, `related`는 있으면 boolean 검증(위반은 14502), 없으면 true로 채운다. 부재를
   true로 채우는 것은 구버전 AI의 현재 동작을 글자 그대로 재현하는 값이라 새 위험이 없다.
   이 관대 수용이 "필수 키 누락도 형태 위반"(MSG-457 검증 원칙)의 한시 예외임을 코드 주석으로
   남긴다.
2. **FillMap-AI 분리 티켓**: 아래 계약 변경 절대로 스키마, 프롬프트, pydantic을 개정해 배포한다.
3. **승격(분리 티켓 완료 조건에 편입)**: AI 배포 확인 후 서버 필수 검사에 `related`를 넣고
   부재 기본값을 지우는 BE 한 줄 커밋. 이후 부재는 다른 네 키와 같은 14502다. AI 롤백 시
   전면 14502가 되는 것은 기존 네 키와 같은 성질이라 새 결정이 아니다. 이 승격 커밋의
   재배포가 전환 창에 캐시된 관대 수용 판정도 함께 비운다(결정 5).

기각 대안: 동시 배포. 레포가 둘이라 원자적 동시 배포가 성립하지 않고, 어긋난 몇 분이 곧 전면
장애 창이 된다.

### 결정 3. 전용 안내 문구는 기능의 범위를 말한다

상수 `UNRELATED_NOTICE`를 신설한다.

```text
장소 방문 동선을 짜 드리는 기능이에요. 가고 싶은 지역이나 관심사를 문장에 담아 다시 요청해 보세요.
```

- EMPTY_NOTICE("조건에 맞는 곳을 찾지 못했어요. 문장을 바꾸거나 다른 지역에서 다시 짜
  보세요.")와 첫 문장부터 다르다. 후보 없음은 "찾았는데 없었다"이고 무관은 "이 기능이 답하는
  종류가 아니다"라서, 문구가 그 차이를 그대로 말한다(PRD 목적: 서비스가 무엇에 답하는지가
  응답에서 드러나게).
- 화면의 표시 위치는 FE 몫 미확정(PRD 미해결)이라, EMPTY_NOTICE 선례처럼 디자인 확정 대기의
  제안값이다. 화면이 두 상태를 기계로 구분해야 하면 응답에 구분 신호 추가가 필요하고 그때
  계약 논의로 올린다(PRD 미해결 2 그대로).

### 결정 4. 지표 outcome 값은 `unrelated`다

기존 버킷(ok, insufficient, rate_limited, ai_error, error)에 `unrelated`를 더한다. 무관
라인은 outcome=unrelated, points=0, signal=none, explain_ms=-1로 남고 나머지 키는 기존 관례
그대로다. 무관 응답 여부의 판정은 응답 notice가 `UNRELATED_NOTICE` 상수인지로 가른다. 빈
목록 응답 세 갈래(무관, 빈 후보, 절단 소진) 중 이 문구를 쓰는 것은 무관뿐이라 겹치지 않는다.
unrelated 라인 비율이 곧 무관 요청 빈도의 실측 재료다(PRD 운영 비기능).

### 결정 5. 판정은 ParsedIntent에 실려 해석 캐시에 함께 남는다

`related`는 ParsedIntent의 다섯 번째 성분이라 캐시 항목에 통째로 저장된다. 캐시 창(TTL 10분)
안의 같은 문장, 같은 뷰포트 재요청은 parse 재호출 없이 같은 판정과 같은 안내를 재현한다.
FR-ROUTE-10의 재현 보장이 무관 응답까지 자연 확장되는 것이고, 별도 구현이 없다.

이 재현에는 전환 창이 하나 있다. 서버 먼저 배포된 구간(결정 2의 1단계와 2단계 사이)에는
구버전 AI의 4필드 응답이 관대 수용값(related=true)으로 캐시에 저장되는데, AI 배포는 서버
프로세스 메모리의 캐시를 비우지 못한다. 따라서 AI 전환 직후 같은 문장과 뷰포트의 재요청은
최대 캐시 TTL 10분 동안 새 판정 대신 전환 전에 캐시된 관대 수용 판정을 재현할 수 있다.
이 창은 TTL 만료로 자연 소멸하므로 수용하고, 캐시 플러시 메커니즘은 추가하지 않는다. 영향
창이 TTL 상한으로 닫혀 있고, 결정 2의 3단계 승격 커밋 재배포가 어차피 서버 캐시를 비운다.

### 결정 6. 조기 반환은 parse 직후, 언급 지역 판정 앞이다. mentionedArea는 null이다

`doRecommend`에서 `cachedParse` 결과의 related가 false면 즉시
`RouteRecommendResponseDto(List.of(), UNRELATED_NOTICE, null)`을 돌려준다.
`mentionedAreaResolver.resolve`와 `candidateCollector.collect`에 도달하지 않는다.

- mentionedArea를 null로 두는 이유: 무관 문장에 지역 표기가 섞여 있어도("부산 사투리로 코드
  주석 써 줘") 그 지역으로 지도를 옮기면 "이 기능이 답하는 종류가 아니다"라는 안내와 화면
  행동이 모순된다. MOVE 신호가 없으니 자동 이동 재요청 예외(MSG-487)도 부여되지 않아,
  무관 요청이 요청 제한의 예외 창을 여는 부작용까지 함께 막힌다(`grantMoveExemption`은
  mentionedArea가 null이면 아무것도 하지 않는 기존 코드 그대로).
- resolve를 부르지 않는 이유: 결과를 버릴 값이면 regions와 zones 조회도 필요 없다. 판정
  하나로 뒤 단계 전부(지역 판정, 후보 수집, 순서, 절단, explain)가 생략된다.
- 요청 제한 정합: 선점(`claimRateLimitWindow`)은 doRecommend 진입 전이라 무관 경로도 창을
  이미 소모했고, 정상 응답이라 되돌리지도 않는다. FR-ROUTE-12와 PRD FR-5의 자연 충족이다.

## API 명세

`POST /api/routes/recommend`의 요청과 응답 DTO 구조, 에러 코드(14xxx) 전부 그대로다.
RouteErrorCode에 신규 상수가 없다(PRD 비목표 확정). 바뀌는 것은 값뿐이다.

| 케이스 | HTTP | developCode | 응답 |
|---|---|---|---|
| 무관 문장 (related=false) | 200 | 200 | `points: []`, `notice: UNRELATED_NOTICE`, `mentionedArea: null` |
| 여행 문장 (related=true, 빈 해석 포함) | 200 | 200 | 기존 그대로 (동선, 부족 안내, 신호) |
| related 비불리언, 정의 밖 필드, 필수 키 누락 | 502 | 14502 | 기존 형태 위반 수렴 그대로 |

`RouteRecommendResponseDto.notice`의 Swagger 설명은 "후보 부족 안내"에서 무관 안내까지 담는
문구로 고친다(구조 불변, 설명만).

## 도메인 로직

처리 순서는 MSG-457 플로우에서 분기 하나가 는다: 입력 검증 → 플래그 게이트 → 요청 제한 원자
선점 → parse(캐시) → **무관이면 조기 반환(전용 안내)** → 언급 지역 판정 → 후보 수집 → 순서
배열 → 도보 예산 절단 → explain → 응답 조립.

1. **형태 검증 (RouteIntentClient)**: 허용 필드 5키, 필수 4키(한시, 결정 2), `related`는
   boolean만 수용하고 부재는 true. 검증 위반은 기존 단일 수렴(14502) 그대로다. 문장 속 숨긴
   지시가 판정 값을 뒤집어도 후보는 서버 데이터로만 만들어지므로(FR-ROUTE-03) 영향 반경은
   "안내가 나가느냐 마느냐"까지다(NFR-SEC-08 유지, PRD 비기능 보안).
2. **조기 반환 (RouteRecommendServiceImpl.doRecommend)**: 결정 6. 반환 형태는 기존 빈 후보
   조기 반환과 같은 record이고 notice와 mentionedArea 값만 다르다.
3. **지표 (recommend)**: outcome 판정이 2분지(임계)에서 3분지가 된다(결정 4). spans와 counts
   배열 관례는 그대로다.

## 계약 변경

도메인 간 계약 인터페이스(`GridQueryService`, `UserGridQueryService`, `ZoneNameQueryService`
등)는 건드리지 않는다. 바뀌는 것은 BE와 FillMap-AI 사이의 해석 계약 하나이고, 이 절이
FillMap-AI 분리 티켓(번호 미정)의 입력이다.

### BE ↔ AI: `POST /route/parse` 응답에 `related` 추가 (MSG-458 계약 개정)

계약 표에 행이 하나 는다. 나머지 네 필드와 explain 계약은 불변이다.

| 필드 | 타입 | 규칙 |
|---|---|---|
| `related` | boolean | 문장이 장소 방문 동선 요청과 관련 있는가. 확실히 무관할 때만 false. 애매하면 true. null 없음 |

FillMap-AI 쪽 개정 4곳:

1. **구조화 출력 스키마[^5] (`RESPONSE_FORMAT_PARSE`)**: properties에
   `"related": {"type": "boolean"}`을 넣고 required 배열에 `"related"`를 더한다. strict
   모드는 모든 속성이 required에 있어야 하므로 선택 필드로 둘 수 없고, null 허용 타입도 쓰지
   않는다(서버가 boolean만 수용한다).
2. **프롬프트 (`PARSE_SYSTEM_TEMPLATE`)**: "출력 필드는 네 개뿐이다"를 다섯 개로 고치고 판정
   지침을 붙인다. 제안 문안: "related는 문장이 장소 방문 동선을 짜 달라는 요청인지의 판정이다.
   게임 속 동선, 코드 작성 요청, 일반 잡담처럼 확실히 무관할 때만 false다. 여행 요청인지
   애매하면 true다. 정보를 못 읽어 다른 필드가 전부 null과 빈 배열이어도 문장이 장소 방문
   이야기면 true다." 마지막 문장이 FR-ROUTE-06과의 축 분리(빈 해석과 무관은 다르다)를
   프롬프트에 고정한다.
3. **pydantic[^6] 검증 (`ParseResult`)**: `related: bool` 성분 추가. strict 설정이라 문자열
   "true"나 1을 boolean으로 받아 주지 않는 것이 그대로 두 번째 방어 층이 된다.
4. **문서와 스모크**: `docs/MSG-458.md` 계약 표와 README 계약 절에 행 반영. 스모크에 무관
   문장 판정 케이스와 related 누락 출력 거부 케이스를 더하는 것을 분리 티켓 완료 조건으로
   제안한다.

서버 쪽 대응 개정은 결정 2의 1단계(허용 5키, 한시 관대 수용)와 3단계(필수 승격 한 줄)다.
