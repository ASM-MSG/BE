# MSG-371: 전역 노출 영상 응답 3종에 작성자 닉네임 추가

**Owner**: B (video 패키지 단독)

> 요구사항 정본: `docs/prd/MSG-371-prd.md` (검토됨, 2026-08-11 정민 승인, 미해결 질문 3건 해소).
> 이 스펙은 PRD의 FR-1~FR-5와 비기능 요구에 "어떻게"만 붙인다. 전역 요구사항 명세는
> `docs/srs.md` FR-VIDEO-18, 정책 확정 이력은 glossary 2026-08-04 항목(작성자 닉네임 표시)이다.

## 개요

전역 노출 영상 응답 3종, 즉 격자 대표 영상(`GET /api/grids/{gridId}/cover`, MSG-87), 격자 전역
영상 목록(`GET /api/grids/{gridId}/videos`, MSG-237), 단건 재생(`GET /api/videos/{videoId}`,
MSG-206)에 작성자 닉네임 `nickname`(String) 필드를 가산한다. 기존 필드와 응답 구조는 그대로
두고 필드만 늘린다. DB 마이그레이션은 없다. 서버는 `users.nickname` 원문만 주고, `@` 접두 같은
화면 표기는 FE 몫이다(FR-4).

핵심 설계 결정 하나로 요약된다: **기존 native 조회 3종(findGlobalCover, findGlobalVideos,
findGlobalVideosAfter)은 한 글자도 바꾸지 않고, 닉네임은 같은 트랜잭션 안의 별도 조회 1회로
붙인다.** 목록은 작성자 id를 모아 IN 배치 1회로 가져오므로 항목 수만큼 조회가 반복되지 않고
(비기능 N+1 금지 충족), 부분 인덱스[^1] `idx_videos_grid_popular`와의 바이트 단위 일치
원칙(MSG-87/237)은 건드릴 일 자체가 없어진다.

## 배경, 목표

전역 영상 카드에 작성자 닉네임을 표시하기로 2026-08-04에 확정했는데(웹 디자인 ver 9 대조,
성민 확정) 일주일이 지나도록 응답 계약에 반영되지 않았고, DTO 두 곳의 주석은 "작성자 식별
정보는 프라이버시상 담지 않는다"라는 폐기된 방침을 아직 정본처럼 말하고 있다. 목표는 FE가
추가 호출 없이 카드와 재생 화면에 작성자를 그릴 수 있게 하는 것, 그리고 폐기 방침 주석을
현재 정책으로 정정하는 것이다. 상세 배경과 비목표(친구 축, 격자 카드, 프로필 이미지, 제목)는
PRD 1~2절 참조.

## 성공 기준

1. 3종 응답의 영상 항목마다 `nickname`이 실린다(FR-1, FR-2, FR-5).
2. 작성자가 닉네임을 바꾸면 다음 조회부터 바뀐 값이 나온다(FR-3). 응답이나 영상 행에 닉네임을
   복사해 두는 비정규화가 없다.
3. 목록 조회의 DB 왕복은 페이지 크기와 무관하게 2회로 고정된다(영상 페이지 1회, 닉네임 배치
   1회). 대표와 재생은 기존 대비 1회씩만 는다.
4. 기존 native 조회 3종의 SQL이 무변경이다. `idx_videos_grid_popular` 바이트 일치 원칙과
   실행 계획이 그대로 유지된다.
5. 기존 클라이언트가 깨지지 않는다: 기존 필드 불변, 신규 에러 코드 없음, 기존 성공/실패
   케이스의 HTTP 상태와 developCode 불변.
6. `ResponseSchemaNullabilityTest`(MSG-319) green: 새 필드가 `requiredProperties`에 등재된다.
7. 폐기 방침을 말하던 DTO 주석 2곳(GridCoverVideoResponseDto, GridGlobalVideoResponseDto)이
   현재 정책으로 정정된다.

## API 명세

세 엔드포인트 모두 요청은 불변이고 응답 항목에 `nickname` 하나가 늘어난다. 에러 케이스도 전부
불변이다(신규 에러 코드 없음, 인증·접근 제어 로직 무변경).

### 1. 격자 대표 영상: `GET /api/grids/{gridId}/cover`

`GridCoverVideoResponseDto`:

```json
{
	"videoId": 1042,
	"thumbnailUrl": "https://...(presigned)",
	"durationSec": 12,
	"viewCount": 37,
	"recordedAt": "2026-07-20T18:03:11",
	"nickname": "busan.vlog"
}
```

대표 없음(그 격자에 공개·READY 영상 0건)이면 지금처럼 `data` null이다. 이때 닉네임 조회는
아예 돌지 않는다.

### 2. 격자 전역 영상 목록: `GET /api/grids/{gridId}/videos`

`GridVideoPageResponseDto`의 각 항목(`GridGlobalVideoResponseDto`)에 `nickname` 추가. 페이지
구조(videos, hasNext, nextCursor)와 keyset 커서[^2] 규칙은 무변경이다. 커서에 닉네임은 들어가지
않는다(커서 경계값은 지금처럼 view_count, created_at, id 3키).

### 3. 단건 재생: `GET /api/videos/{videoId}`

`VideoPlaybackResponseDto`에 `nickname` 추가. 소유자 본인 조회에도 실린다(본인 닉네임).
접근 거부 경로(404, 403)는 무변경이며 거부된 요청에서는 닉네임 조회가 돌지 않는다.

### @Schema 표기

세 DTO 모두 동일하다: description은 "작성자 닉네임 원문. @ 등 화면 표기는 FE가 붙인다",
example은 `busan.vlog`, `requiredProperties`에 `nickname` 등재, `nullable` 미표기.
`users.nickname`이 NOT NULL(V1)이고 탈퇴 시 영상이 CASCADE 삭제라 작성자 없는 항목이
없기 때문이다(PRD 3절). 대표 DTO의 "항상 READY라 thumbnailUrl null 아님" 표기와 같은 결이다.

## 도메인 로직

### 닉네임 조달 방식 (핵심 결정)

두 대안 중 후자를 채택한다.

- **(기각) native 쿼리에 users JOIN을 넣고 프로젝션[^3]으로 전환**: 왕복은 1회지만, 엔티티
  반환을 프로젝션으로 바꾸는 순간 커서 인코딩, presign[^4] 재료 접근, DTO 팩토리까지 연쇄
  재작성이 필요하고, 엔티티 매핑 native 쿼리에 여분 컬럼을 섞는 위험도 진다. "부분 인덱스
  일치 원칙을 깨지 않는 설계 우선" 검토 지침에도 정면으로 닿는다.
- **(채택) 영상 조회 후 같은 트랜잭션에서 닉네임 별도 조회**: 기존 쿼리 3종 무변경. 목록은
  배치 IN 1회라 왕복이 상수(2회)로 고정된다. FR-3(조회 시점 현재 값)은 매 요청 users를 읽는
  구조 자체가 보장한다.

`VideoRepository`에 JPQL 2건을 추가한다. User 엔티티를 쿼리 수준에서 직접 읽는 것은 연관관계
매핑 금지 원칙(MSG-334)과 정합한다. 참조가 값 수준(JPQL의 엔티티 참조)이고 엔티티 필드에는
아무것도 늘지 않으며, Report 리포지토리가 User를 직조회하는 선례 그대로다. 쿼리를 user가 아닌
video 쪽 리포지토리에 두는 것도 "쿼리 소속은 용도 기준" 관례(UserRepository.findAllS3KeysByUserId
주석) 그대로다.

```java
/** 전역 노출 응답의 작성자 닉네임 (MSG-371). 단건 경로(대표·재생)용. */
@Query("SELECT u.nickname FROM User u WHERE u.id = :userId")
Optional<String> findAuthorNickname(@Param("userId") Long userId);

/** 전역 목록 페이지의 작성자 닉네임 배치 (MSG-371). 항목 수와 무관하게 1왕복, N+1 금지(PRD 비기능). */
@Query("SELECT u.id AS userId, u.nickname AS nickname FROM User u WHERE u.id IN :userIds")
List<AuthorNicknameProjection> findAuthorNicknames(@Param("userIds") Collection<Long> userIds);
```

`AuthorNicknameProjection`은 `userId`, `nickname` 접근자 2개짜리 인터페이스 프로젝션이다
(video/repository의 ExploreGridProjection 선례).

### 서비스 배선 (VideoServiceImpl)

- **getGridCover**: `findGlobalCover` 결과가 있을 때만 `findAuthorNickname(video.getUserId())`
  1회. 결과를 DTO 팩토리에 넘긴다.
- **getGridGlobalVideos**: lookahead 트림으로 `pageRows`가 확정된 뒤, 그 안의 중복 제거한
  userId 목록으로 `findAuthorNicknames` 1회를 호출해 `Map<Long, String>`을 만들고 항목 매핑에
  쓴다. 트림돼 버려지는 size+1번째 행의 작성자는 배치에 넣지 않는다.
- **getVideoPlayback**: 접근 제어 판정(404, 403)을 모두 통과한 뒤에만 `findAuthorNickname`
  1회. 격자 표시명 조달(MSG-341)과 같은 자리, 같은 결이다(응답을 실제로 내려주는 경로에서만
  돈다).

### 작성자 부재 처리

정상 경로에는 없다. 탈퇴하면 `videos.user_id` FK의 ON DELETE CASCADE(V1)로 영상이 함께
사라지므로 조회된 영상은 항상 살아 있는 작성자를 가진다(PRD 3절). 유일한 이론상 구멍은
READ COMMITTED[^5]에서 영상 조회 문장과 닉네임 조회 문장 사이(밀리초 창)에 탈퇴 커밋이 끼는
경우다. 이때 닉네임 조회가 빈손이라는 것은 그 영상이 방금 연쇄 삭제됐다는 뜻이므로, 응답에서
숨긴다(2026-08-11 정민 결정 — 초안의 "null로 싣고 방어 분기 없음"을 Codex 교차 리뷰 지적을
계기로 대체): 목록은 해당 항목 제외, 대표는 대표 없음 처리, 재생은 삭제 영상과 같은 404.
"탈퇴는 연쇄 삭제" 규칙이 조회 응답에서도 예외 없이 참이 되고, `nickname`의 non-null 계약이
창 없이 성립한다.

### DTO 변경

3종 record에 `nickname` 컴포넌트와 `of(...)` 파라미터를 추가한다. 아울러
GridCoverVideoResponseDto와 GridGlobalVideoResponseDto의 클래스 주석에서 "작성자 식별
정보(닉네임·색)는 프라이버시상 담지 않는다(glossary Phase 2+)" 문구를 삭제하고 현재 정책으로
바꾼다: 닉네임은 2026-08-04 확정으로 표시 대상이 됐고, 도감 색상은 여전히 담지 않는다
(PRD 비목표).

무변경 확인 대상: `FriendGridVideoResponseDto`(친구 축, 비목표), `GridVideoResponseDto`(내
영상, 작성자가 곧 본인), `ExploreGridResponseDto`(격자 카드, 작성자 표기 없음 확정),
`VideoCursor`, 컨트롤러 2종(GridVideoController, VideoController)의 시그니처.

## 미해결 질문

없음.

[^1]: 부분 인덱스(partial index): WHERE 조건을 만족하는 행만 담는 인덱스. `idx_videos_grid_popular`는 공개·READY·ACTIVE 영상만 담아, 쿼리의 조건·정렬이 인덱스 정의와 글자 단위로 같아야 플래너가 인덱스만으로 결과를 만든다.
[^2]: keyset 커서: 페이지 번호 대신 직전 페이지 마지막 항목의 정렬 키 값(여기서는 조회수, 시각, id)을 경계로 삼아 다음 페이지를 이어 읽는 방식. 행이 끼어들어도 중복·누락이 없다.
[^3]: 프로젝션(projection): 엔티티 전체 대신 필요한 컬럼 몇 개만 골라 담는 조회 결과 형태. Spring Data에서는 접근자만 선언한 인터페이스로 받는다.
[^4]: presign: S3 객체에 기한부 서명 URL을 발급하는 것. 응답의 썸네일·재생 URL은 저장된 S3 key가 아니라 서비스가 요청마다 발급한 서명 URL이다.
[^5]: READ COMMITTED: PostgreSQL 기본 격리 수준. 트랜잭션 안의 각 문장이 그 문장 시작 시점까지 커밋된 데이터를 본다. 그래서 한 트랜잭션의 두 문장 사이에 다른 커밋이 끼어들 수 있다.
