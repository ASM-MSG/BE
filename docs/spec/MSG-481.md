# MSG-481: 장소 검색 위치 기반 랭킹

**Owner**: A (`com.msg.fillmap.search.*` 단독 변경, CLAUDE.md 협업 원칙의 Owner A 목록)

**요구사항 정본**: `docs/prd/MSG-481-prd.md` (상태: 검토됨, 2026-08-26 정민 승인) ·
`docs/srs.md` FR-SEARCH-16, FR-SEARCH-17, 개정된 FR-SEARCH-02

## 개요

장소 검색이 지도 중심 좌표를 받아, 그 좌표에서 반경[^1] 20km 안의 장소를 카카오 로컬에 먼저 물어본다.
근처에 결과가 하나도 없으면 위치를 빼고 한 번 더 물어 전국 결과를 그대로 준다. 좌표를 보내지 않는 요청은
지금과 완전히 같게 동작한다.

지금 서버가 받는 파라미터는 검색어 하나뿐이라 위치를 반영할 방법 자체가 없다
(`PlaceSearchController.searchPlaces`의 `@RequestParam String q`). 카카오 로컬 키워드 검색은 정확도순[^2]으로
전국을 뒤지므로 부산 화면에서 "서면"을 검색해도 전라남도 순천시 서면이 15건 전부를 채운다.
받아온 15건을 서버에서 거리순으로 다시 세우는 방식은 답이 아니다. 15건이 전부 순천이면 재정렬해도 순천이라,
바꿔야 하는 것은 정렬이 아니라 카카오로 나가는 요청이다.

## 배경 · 목표

2026-08-25 전역 QA에서 `GET /api/search/places?q=서면`이 200으로 15건을 주는데 전부 순천시 서면의 자연휴양림,
계곡, 저수지였다. 검색은 지도를 옮기려고 쓰는 기능인데 화면과 무관한 결과만 나오면 그 수단이 동작하지 않는다.

목표는 세 가지다. 부산 화면에서 "서면"을 검색하면 부산 서면 인접 결과가 상위에 온다(FR-SEARCH-16).
근처에 해당 장소가 없는 검색(부산 화면에서 "제주공항")은 지금처럼 전국 결과를 준다. 좌표를 보내지 않는 기존
클라이언트는 고치지 않아도 그대로 동작한다.

## 성공 기준

1. `q=서면&lat=35.1578&lng=129.0594`(부산 서면) 호출이 200이고, 결과에 부산 서면 인접 장소가 들어온다.
2. `q=제주공항&lat=35.1578&lng=129.0594` 호출이 200이고 결과가 비어 있지 않다. 위치를 붙였다는 이유로
   결과가 사라지지 않는다. (2026-08-26 실측으로 충족은 확인했으나 내용은 제주가 아니었다. 아래 작업 로그의
   "수동 확인 결과" 참조.)
3. `q=서면` 단독 호출의 응답이 지금과 같다. 필드 구성과 최대 15건 상한이 그대로다.
4. `lat`만 있는 요청, 좌표가 대한민국 범위 밖인 요청, 좌표가 숫자가 아닌 요청이 400에 developCode 5400이다.
5. 비로그인 호출도 위 1번에서 4번까지 같다. 인증 요구가 새로 생기지 않는다.
6. 카카오 장애 시 좌표 유무와 관계없이 502에 developCode 5502 하나로 수렴한다.
7. 좌표는 DB에도 Redis에도 로그에도 남지 않는다.

아래 "테스트 시나리오"가 이 기준의 검증 수단이다.

## API 명세

### GET /api/search/places (수정)

기존 계약에 선택 파라미터 두 개가 늘어난다. 응답 형상은 바뀌지 않는다.

| 파라미터 | 위치 | 필수 | 타입 | 설명 |
|---|---|---|---|---|
| `q` | query | 예 | String | 검색어. 종전과 같다 |
| `lat` | query | 아니오 | 숫자 문자열 | 지도 중심 위도. 33.0 이상 39.0 이하 |
| `lng` | query | 아니오 | 숫자 문자열 | 지도 중심 경도. 124.0 이상 132.0 이하 |
| `X-Viewer-Session` | header | 아니오 | String | 비로그인 집계용. 종전과 같다 |

응답 `PlaceSearchResponseDto`는 필드 변경이 없다(`name`, `address`, `lat`, `lng`, `gridId`, `zoneName`,
`zoneCell`). 최대 15건도 그대로다.

**성공**

| 상황 | 응답 |
|---|---|
| 좌표 있음, 반경 20km 안에 결과 있음 | 200, 근처 결과 최대 15건 |
| 좌표 있음, 반경 20km 안에 0건 | 200, 위치 없이 재조회한 전국 결과 최대 15건 |
| 좌표 없음 | 200, 종전과 동일한 전국 결과 |
| trim 후 빈 `q` (좌표 유무 무관) | 200, 빈 배열. 카카오 호출 0회 |
| 무매치 (근처와 전국 모두 0건) | 200, 빈 배열 |

**에러**

| 상황 | HTTP | developCode | 비고 |
|---|---|---|---|
| `lat`과 `lng` 중 하나만 옴 | 400 | 5400 | 신규 상수 `INVALID_COORDINATE` |
| 좌표가 숫자가 아님 | 400 | 5400 | `NaN`, `Infinity`, 빈 문자열 포함 |
| 좌표가 대한민국 범위 밖 | 400 | 5400 | 경계값 33.0, 39.0, 124.0, 132.0은 허용 |
| `q` 누락 | 400 | 400 | 종전과 같다. 전역 핸들러 소관 |
| 카카오 실패 | 502 | 5502 | 종전과 같다 |

Swagger 설명에 좌표 파라미터 한 쌍을 함께 보내야 한다는 점, 반경 20km 안이 우선이고 0건이면 전국으로
되돌아간다는 점을 적는다. 이 문구가 FE 사전 고지의 실체다.

## 도메인 로직

### D1. 좌표 검증은 컨트롤러에서 한다

`PlaceSearchController`가 두 값을 받아 검증하고, 서비스에는 검증을 통과한 값만 넘긴다.
`MissionController.toBounds`와 `GridController.toBounds`가 이미 같은 자리에서 뷰포트를 검증하는 선례라
새 패턴을 만들지 않는다. 서비스가 검증을 겸하지 않는 이유는 좌표를 받는 오버로드[^3]의 유일한 호출자가
이 컨트롤러이고, 같은 검사를 두 겹으로 두면 어느 쪽이 계약인지 흐려지기 때문이다. 대신 인터페이스 javadoc에
"검증된 좌표만 받는다"를 계약으로 적는다.

### D2. 좌표는 문자열로 받아 서비스 계층 앞에서 직접 파싱한다

`@RequestParam Double lat`으로 받으면 숫자가 아닌 값은 스프링 바인딩 단계에서
`MethodArgumentTypeMismatchException`이 되고, 전역 핸들러가 developCode 400으로 변환한다. 그러면 FR-4가 요구한
5400이 나오지 않는다. 이 변환은 코드로 확인된 사실이다.
`src/main/java/com/msg/fillmap/global/GlobalExceptionHandler.java`의 `handleTypeMismatch`가 이 예외를
`ErrorCode.BAD_REQUEST`로 바꿔 응답한다. 따라서 `@RequestParam(required = false) String lat`으로 받고 컨트롤러가
`Double.parseDouble`로 바꾼다. 실패하면 `ApiException(SearchErrorCode.INVALID_COORDINATE)`이다.
문서 쪽 타입이 문자열로 보이지 않도록 `@Parameter(schema = @Schema(type = "number", format = "double"))`를 얹는다.

검증 순서는 세 단계다. 첫째, 둘 다 null이면 위치 없는 검색으로 진행한다. 둘째, 하나만 null이면 5400이다.
셋째, 파싱에 성공하면 `KoreaCoordinates.isOutOfService(lat, lng)`로 범위를 본다. 참이면 5400이다.

### D3. 유효 범위는 `KoreaCoordinates`를 그대로 쓴다

위도 33.0 이상 39.0 이하, 경도 124.0 이상 132.0 이하다. 영상 업로드 좌표 검증(MSG-66)과 역지오코딩(MSG-93)이
쓰는 공용 상수라 서비스 범위가 바뀌면 한 곳만 고치면 된다. `isOutOfService`가 `NaN`을 명시적으로 밖으로
처리하고 무한대는 범위 비교에서 걸리므로, `Double.parseDouble`이 통과시키는 `"NaN"`과 `"Infinity"`도 여기서
함께 막힌다. 좌표계 정의역(위도 90, 경도 180)이 아니라 서비스 범위를 쓰는 이유는, 이 좌표의 용도가 국내
장소 검색의 중심점이라 국외 좌표는 오작동이지 정상 입력이 아니기 때문이다.

### D4. 폴백[^4]은 `KakaoLocalClient` 안에서 한다

`search(String query, double lat, double lng)`가 반경 검색을 보내고, 2xx 응답의 `documents`가 빈 배열이면
같은 메서드 안에서 위치 없는 요청을 한 번 더 보낸다. 서비스로 올리지 않는 이유는 두 가지다. 카카오 요청
파라미터 조립은 어댑터의 관심사이고, 서비스로 올리면 "0건이면 재호출"이라는 판정이 서비스의 매핑 흐름과
섞여 두 오버로드 양쪽에 흩어진다. 서비스는 좌표를 그대로 전달할 뿐 재호출 여부를 모른다.

재호출은 한 번뿐이다. 폴백 결과가 0건이면 그대로 빈 리스트를 돌려주고 다시 부르지 않는다.

### D5. 근처 호출이 실패하면 폴백하지 않고 5502로 수렴한다

PRD FR-9가 실패의 수렴만 정하고 폴백 여부는 스펙에 맡겼으므로 여기서 정한다. 실패는 재호출하지 않는다.

근거는 셋이다. 첫째, 실패 원인(키 오류, 쿼터 초과, 카카오 장애, 타임아웃)은 대부분 두 번째 호출에서도
그대로 재현되므로 쿼터만 두 배로 태우고 결과는 같다. 둘째, 첫 호출이 읽기 타임아웃 3초를 다 쓰고 실패한
경우에 재호출을 붙이면 사용자는 실패를 확인하기까지 두 배를 기다린다. 셋째, 실패를 폴백으로 덮으면 근처
검색 경로가 망가져도 전국 결과가 정상으로 보여 증상이 드러나지 않는다. 폴백의 트리거는 "정상 응답에
결과가 0건"이라는 한 가지 조건뿐이다.

### D6. 카카오 요청 파라미터

`query`, `size=15`는 그대로 두고 좌표가 있을 때만 `x`, `y`, `radius`를 더한다. 카카오는 `x`가 경도이고
`y`가 위도이므로 `x=lng`, `y=lat`으로 싣는다. `radius=20000`은 카카오가 허용하는 최댓값이고 상수로 고정한다.

`sort`는 보내지 않아 기본값 정확도순을 유지한다. `distance`를 쓰지 않는 이유는, 반경 안에서까지 거리를
1순위로 삼으면 검색어와 정확히 맞는 장소가 조금 더 가까운 엉뚱한 장소에 밀리기 때문이다. 반경은 후보 집합을
좁히는 데만 쓰고 그 안의 순서는 공급자 정확도순을 그대로 따른다. 폴백 결과도 같은 정렬이라 두 경로의 결과
성격이 어긋나지 않는다. 개정된 FR-SEARCH-02("위치 신호가 없는 검색은 공급자 정확도순 유지")와도 일관된다.

카카오 로컬이 순수한 위치 가중치(먼 결과를 남기고 순위만 낮추는 옵션)를 제공하지 않아 반경 검색에 전국
재호출을 붙이는 조합이 됐다. 화면 사각형(`rect`)을 그대로 쓰는 안은 PRD 미해결 질문에서 반려됐다.
한 블록만 보이게 확대한 화면에서 0건이 되어 전국으로 되돌아가고, 그러면 이 티켓이 고치려는 증상이 그대로
재현되기 때문이다.

### D7. 집계 접수 순서와 위임 구조는 그대로 둔다

`PlaceSearchServiceImpl`의 흐름은 trim 가드, 집계 접수, 카카오 호출 순서를 유지한다(MSG-258, MSG-469).
좌표는 집계에 넘기지 않는다. `recordSearch(searcherKey, query)` 시그니처는 손대지 않는다.

중복을 막기 위해 기존 2인자 메서드는 신규 4인자 메서드에 `(null, null)`로 위임한다. 1인자 메서드는 종전대로
집계 없이 매핑 흐름을 직접 탄다. 카카오 호출과 DTO 매핑은 private 메서드 하나로 모으고, 좌표가 null이면
`kakaoLocalClient.search(query)`를, 아니면 `search(query, lat, lng)`를 부른다. `ZoneNameResolver`를 매핑 진입
전에 한 번만 얻는 규칙(MSG-341)도 그대로다.

### D8. 총 대기 상한은 산술로 보장한다

타임아웃 값(연결 1초, 읽기 3초)은 `SearchConfig` 그대로 두고 새 장치를 만들지 않는다. 호출 하나의 상한이
4초이고 호출은 최대 두 번이므로 총 대기는 8초를 넘지 않는다. `RestClient`에 재시도 설정이 없어 호출 횟수가
늘어날 경로도 없다. 폴백이 붙는 경우는 근처 결과가 0건인 검색뿐이고 그때도 첫 호출은 정상 응답이라 수백 ms에
끝나므로, 실제 두 배 대기는 카카오가 느려진 상황에서만 생긴다. 별도 상한 장치를 두지 않는 것이
이 판단의 결론이며, 폴백 호출이 늘어나거나 타임아웃을 올리는 변경이 생기면 이 산술을 다시 확인해야 한다.

### D9. 좌표는 저장하지도 로그로 남기지도 않는다

검색 경로에는 저장소가 없다(패스스루[^5], FR-SEARCH-03). 좌표는 사용자의 현재 위치에 준하는 값이라 검색어와
같은 취급이다. `KakaoLocalClient.upstreamFailure`가 예외 클래스명과 상태 코드만 남기는 현행 형태를 유지하고
좌표를 메시지에 넣지 않는다(MSG-342 로그 정책). 폴백이 일어났다는 사실을 남기는 로그도 추가하지 않는다.
좌표도 검색어도 못 싣는 상태에서는 진단 가치가 없기 때문이다.

### D10. 카카오가 다운되면

카카오 로컬이 응답하지 않는 동안 이 API가 어떻게 동작하는지를 못 박는다. 2026-08-26 사용자 지시로 넣는
절이며, 아래는 코드로 확인한 사실만 담았다.

**실패 수렴**. 좌표가 있든 없든 첫 호출이 실패하면 `KakaoLocalClient.upstreamFailure`가
`SearchErrorCode.SEARCH_UPSTREAM_ERROR`로 바꾸고 502에 developCode 5502로 나간다. 이번 변경이 새로 만드는
실패 경로는 없다. 반경 파라미터가 붙어도 실패 분기는 같은 자리 하나다.

**D5의 값이 여기서 드러난다**. 실패에도 폴백했다면 장애 중 카카오 호출이 요청당 두 배가 되고 사용자 대기
상한도 4초에서 8초로 늘었을 것이다. 지금 설계는 장애 상황의 호출 수와 대기 시간이 현행과 같다.

**사용자 대기**. 카카오가 연결을 거부하면 즉시 502이고, 응답을 물고 있으면 연결 1초와 읽기 3초를 합한
4초 뒤 502다.

**나머지 기능**. 검색어 집계는 카카오 호출 전에 접수되므로 장애 중에도 계속 쌓인다. FR-SEARCH-05가 의도한
동작이고 이번 변경으로 바뀌지 않는다. 지도, 격자, 도감, 미션 등 나머지 기능은 검색과 독립이라 영향이 없다
(SRS 이해관계자 표의 "검색은 단일 업스트림 오류로 수렴하고 나머지 기능은 영향 없다").

**하지 않는 것과 이유**. 결과를 캐시해 장애를 버티는 방법은 약관상 불가다(FR-SEARCH-03 무저장, 무캐시).
서킷 브레이커도 이번에 넣지 않는다. `SearchConfig`에는 재시도와 서킷 브레이커가 없고 타임아웃 연결 1초,
읽기 3초가 전부이며, 레포 의존성에도 resilience4j와 spring-retry가 없다(`build.gradle` grep 0건).
남는 한계는 장애가 길어지면 요청당 최대 4초의 스레드 점유가 계속된다는 점인데, 검색은 화면의 300ms 디바운스
뒤에 호출되고 아직 실측된 문제가 아니다. 이 한계를 여기 명시하고 후속 티켓 후보로 남긴다. 승격 조건은
카카오 장애가 실제로 관측되거나 검색 502가 지속 발생하는 것이다.

**변경 파일 9개** (`git diff --stat` 실측, `+714/-13`). main 5개는 `PlaceSearchController`(+46) ·

**데이터 저장 위치**: 없다. 좌표도 카카오 응답도 어디에도 쓰지 않는다. 이번 변경으로 새로 생긴 저장소가

`search_keyword_daily_counts` 테이블)는 검색어와 날짜만 담는 형태 그대로다. 좌표는 집계 호출
`recordSearch(searcherKey, query)` 에 인자로 들어가지 않는다.

**실행 쿼리**: DB 쿼리 변화가 없다. 대신 바뀐 것은 외부 HTTP 요청이고 실제 나가는 형태는 두 가지다.

```text
좌표 있음: GET /v2/local/search/keyword.json?query={q}&size=15&x={lng}&y={lat}&radius=20000
좌표 없음: GET /v2/local/search/keyword.json?query={q}&size=15
```

첫 요청의 응답 `documents` 가 빈 배열일 때만 두 번째 형태로 한 번 더 나간다. `sort` 는 어느 쪽에도 싣지
않아 카카오 기본 정확도순이 유지된다.

**예외 흐름**: 5400 은 컨트롤러 세 자리에서 던져진다. 짝 검사(`(lat == null) != (lng == null)`),
`parseCoordinate` 의 `NumberFormatException` 변환, `KoreaCoordinates.isOutOfService` 판정이다. 셋 다
`ApiException(SearchErrorCode.INVALID_COORDINATE)` 하나로 모이고
`GlobalExceptionHandler.handleApiException` 이 400 에 developCode 5400 으로 바꾼다.
5502 는 종전과 같이 `KakaoLocalClient.upstreamFailure` 가 만들어 같은 핸들러가 502 로 바꾼다.
근처 호출이 실패하면 예외가 폴백 삼항식(`nearby.isEmpty() ? ... : nearby`) 평가 **전에** 전파되므로
재호출 경로에 닿지 않는다(§D5). `handleApiException` 은 예외를 로깅하지 않아, 요청 URL 에 실린 좌표가
로그로 새는 경로도 없다(§D9, 리뷰 확인).

**빈 동작**: 새 빈이 없다. `KakaoLocalClient` 는 종전대로 `@Component` 싱글턴이고 상태를 갖지 않으며,

검색 경로에 `@Transactional` 이 없는 것도 그대로다. 저장이 없어 트랜잭션 경계가 필요 없다.
