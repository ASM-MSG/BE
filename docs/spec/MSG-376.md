# MSG-376: API 응답 날짜에 시간대 표기를 붙여 웹에서 9시간 밀려 보이는 문제 해결

**Owner**: 공동 (전역 직렬화 설정이 두 도메인의 응답 계약을 함께 바꾼다. 다만 계약 인터페이스 4종의
시그니처 변경은 없고, 실제 코드 변경은 전역 설정 1클래스와 예시 문자열 정리라 단일 개발 레인으로 충분하다)

> 요구사항 정본: `docs/prd/MSG-376-prd.md` (상태: 검토됨, 2026-08-11 승인, FE 합의 완료).
> 이 스펙은 PRD의 FR-1~7과 비기능 요구에 "어떻게"만 붙인다. 표기 방식(UTC `Z`), 표기 없는 입력의
> UTC 해석은 PRD §8에서 확정된 결정이며 여기서 다시 논하지 않는다.

## 개요

서버가 시각을 `"2026-08-11T05:55:21"`처럼 시간대 표기 없이 내려줘서, 한국 브라우저의 `new Date()`가
UTC 값을 KST로 잘못 해석해 모든 화면이 9시간 밀려 보인다. 시각을 담는 모든 API 응답 필드에 UTC `Z`
표기를 붙이고, 요청으로 받는 시각은 오프셋[^1]이 무엇이든 절대 시각으로 정확히 해석하도록 직렬화
계층 한 곳을 고친다. DB 저장(UTC naive[^2])과 서버 내부의 시각 판정 로직은 건드리지 않는다.

## 배경, 목표

- FE 연동 실측(2026-08-11)에서 전 화면 시각 9시간 밀림이 확인됐다. 원인은 응답 시각 문자열의
  시간대 표기 부재다 (PRD §1).
- 목표: 시각을 담는 모든 응답 필드가 `"2026-08-11T05:55:21Z"` 형태(UTC `Z` 통일)로 나가고,
  FE는 코드 수정 없이 정확한 시각을 표시한다. 왕복이 대칭이 된다 (웹은 이미 `Z`를 붙여 송신 중).

## 성공 기준

1. 시각을 담는 17종 응답 DTO의 모든 시각 필드가 `Z`로 끝나는 ISO 8601 문자열로 직렬화된다 (FR-1, FR-2).
2. 표기가 붙어도 절대 시각은 기존 값과 같다. 값 이동(이중 변환) 없음 (FR-3).
3. 요청 `recordedAt`은 `Z` 입력, `+09:00` 같은 임의 오프셋 입력, 표기 없는 입력을 모두 같은 규칙으로
   해석한다: 오프셋이 있으면 UTC로 환산, 없으면 UTC로 간주 (FR-4, FR-5).
4. 미래 `recordedAt` 거부(3424) 등 기존 검증과 null 시각 필드의 null 유지가 그대로다 (FR-6, FR-7).
5. Swagger의 시각 예시가 실제 응답 표기와 일치한다 (비기능 "문서").
6. 신규 DTO가 계약을 벗어난 시각 타입을 쓰면 테스트가 깨진다 (가드 테스트, 아래 시나리오 3).

## API 명세

신설 엔드포인트 없음. 전 API 공통의 와이어 표기만 바뀐다.

**응답 (모든 시각 필드 공통)**

| 구분 | 변경 전 | 변경 후 |
|---|---|---|
| 값 있음 | `"recordedAt": "2026-08-11T05:55:21"` | `"recordedAt": "2026-08-11T05:55:21Z"` |
| 밀리초 있음 | `"createdAt": "2026-08-11T05:55:21.724"` | `"createdAt": "2026-08-11T05:55:21.724Z"` |
| 값 없음 | `"notifiedAt": null` | `"notifiedAt": null` (불변, FR-7) |

초는 0이어도 항상 출력한다(`"…T05:55:00Z"`). 소수 초는 값에 있을 때만 붙는다. 둘 다
`new Date()`가 그대로 해석하는 형태다.

**요청 (`VideoUploadRequestDto`, `VideoReplaceRequestDto`의 `recordedAt`)**

| 입력 | 해석 | 비고 |
|---|---|---|
| `"2026-08-11T06:09:27.724Z"` | UTC 06:09:27.724 | 웹 현행 송신 형태. 지금도 동작하며 계약으로 굳힌다 (FR-4) |
| `"2026-08-11T14:55:21+09:00"` | UTC 05:55:21로 환산 | 현재는 파싱 실패이던 입력을 계약대로 수용 확장 (FR-4) |
| `"2026-08-11T05:55:21"` | UTC 05:55:21로 간주 | 방어 규칙 (FR-5). 현행 해석과 동일해 동작 변화 없음 |
| 형식 오류 문자열 | 파싱 실패 | 기존 말폼드 본문 처리 경로 그대로. 신규 에러 코드 없음 |

## 도메인 로직

### D-1. 구현 방식: (b) `LocalDateTime` 유지 + 전역 Jackson[^3] 설정 채택, (a) DTO 타입 전환 기각

PRD가 후보로 남긴 두 안을 다음 기준으로 판정했다.

| 기준 | (a) `Instant`/`OffsetDateTime` 전환 | (b) `LocalDateTime` 유지 + 전역 설정 |
|---|---|---|
| 고치는 곳 (PRD 원칙: 한 곳) | DTO 19곳 + 엔티티에서 DTO로 옮기는 매핑 지점 전부 + `validateRecordedAt`, 미션 기간 대조 등 서비스 연쇄 | 직렬화 컴포넌트 1클래스 |
| FR-3 (이중 변환 금지) 위험 | 매핑 지점 수만큼 변환 실수 여지 | 변환 로직이 한 곳이라 테스트 한 벌로 고정 |
| 신규 DTO의 자동 준수 | `Instant`를 쓰면 자동이지만, 습관대로 `LocalDateTime`을 쓰면 조용히 깨진다. 결국 가드 테스트 필요 | `LocalDateTime`을 쓰는 순간 자동 준수. 다른 시각 타입 이탈만 가드 테스트로 막으면 된다 |
| 역직렬화 관용성 (FR-5) | Jackson 기본 `Instant` 역직렬화[^4]는 오프셋 필수라 표기 없는 입력에 커스텀이 어차피 필요 | 커스텀 역직렬화 하나로 FR-4와 FR-5 동시 충족 |
| 내부 로직 (비기능 "데이터 정합") | 엔티티는 `LocalDateTime`이라 경계마다 변환 삽입 | 엔티티, 스트릭 KST 판정, `BadgeAwardServiceImpl`, `validateRecordedAt` 전부 무수정 |

(a)의 장점은 타입 자체가 절대 시각임을 표현한다는 것 하나인데, 그 계약 강제는 어느 안이든 가드
테스트가 담당하게 되므로 결정 축이 못 된다. **(b) 채택.** 두 안이 같은 결과를 낼 때 diff가 작고
실수 지점이 적은 쪽을 고른다.

### D-2. 직렬화 규칙

`LocalDateTime` 값을 UTC 순간으로 보고 `value.toInstant(ZoneOffset.UTC).toString()` 형태(ISO 8601
UTC `Z`)로 쓴다. 저장값이 이미 UTC이므로 변환 없이 표기만 부여되며 절대 시각이 이동하지 않는다 (FR-3).

### D-3. 역직렬화 규칙

`ISO_LOCAL_DATE_TIME` 뒤에 선택적 오프셋을 허용하는 포매터로 파싱한다. 오프셋이 있으면
`withOffsetSameInstant(UTC)`로 환산한 `LocalDateTime`을, 없으면 파싱값 그대로(UTC 간주)를 돌려준다.
`Z` 입력의 결과는 현행 동작(스프링 부트 기본 처리가 `Z`를 수용 중)과 값이 같아 회귀가 없다.
파싱 실패는 Jackson 표준 예외로 던져 기존 말폼드 본문 경로를 그대로 탄다.

### D-4. 등록 방식: `@JacksonComponent`[^5] 한 클래스

`com.msg.fillmap.global.config.UtcLocalDateTimeJsonCodec` (신규, `@JacksonComponent`) 안에 직렬화기와
역직렬화기를 내부 클래스로 둔다. 이 방식이 개별 필드 어노테이션 산발 적용(PRD가 금지)과 달리 한 곳
수정이고, 스프링 부트가 앱 매퍼에 자동 등록하며, `@WebMvcTest`와 `@JsonTest` 슬라이스가
`@JsonComponent`를 기본으로 집어 테스트에서도 실제 계약이 검증된다. 구현 참고 두 가지:

- 이 레포는 스프링 부트 4.1.0, Jackson 3(`tools.jackson`)이다. Jackson 3는 기반 클래스 이름이
  개명됐다(`JsonSerializer`가 `ValueSerializer`로, `JsonDeserializer`가 `ValueDeserializer`로).
  구현 때 시그니처를 컴파일러로 확인한다. (구현 실측 2026-08-11: 어노테이션도 부트 4.1에서
  `@JsonComponent`가 `@JacksonComponent`로 개명됐다. jar 실물 대조로 확인했고 취지는 동일하다.)
- 등록된 커스텀 처리기가 내장 java.time 기본 처리보다 우선함을 계약 테스트(시나리오 1)가 증명한다.
  만에 하나 우선하지 않으면 `SimpleModule` 빈 등록으로 대체한다. 판정은 테스트가 한다.

### 영향 범위 실측 (2026-08-11, 이 스펙 작성 시 코드 대조)

앱 매퍼가 주입되는 곳은 HTTP 계층 외에 시드 리더(mission, zone, region), 카카오 인가코드 교환기,
시큐리티 응답 핸들러다. 시드 파일의 시각은 표기 없는 입력이라 D-3 규칙상 현행과 동일하게 해석되고,
나머지는 시각 필드가 없다. 카프카 알림 파이프라인은 outbox id 문자열만 싣는 thin payload라
(`KafkaTemplate<String, String>`, `NotificationRelay` 실측) 시각 직렬화 자체가 없다. Redis도
문자열과 score만 쓴다. 따라서 이 변경의 관측 가능한 효과는 API 요청과 응답의 시각 표기뿐이다.

### D-5. Swagger 예시 갱신

`@Schema`의 시각 예시 문자열에 `Z`를 부여한다 (값은 유지, 예: `"2026-07-17T14:30:00"`을
`"2026-07-17T14:30:00Z"`로). 작성 시점 실측 23곳(응답 DTO 21곳 + 요청 DTO 2곳)이며, 구현 때
`example = "2\d{3}-\d{2}-\d{2}T` 패턴 grep으로 전수 재확인한다. springdoc이 만드는 스키마
`format: date-time`은 그대로라 별도 설정 변경은 없다.

1. **직렬화 계약 테스트** (신규 `@JsonTest`, `UtcLocalDateTimeJsonCodecTest`): 검증 대상은 손으로
   만든 매퍼가 아니라 스프링이 조립한 매퍼여야 한다. 기존 `ApiResponseContractTest`의
   `new ObjectMapper()` 패턴은 커스텀 등록을 못 보므로 따르지 않는다.
   - `시각_필드는_UTC_Z_표기로_직렬화된다`: `2026-08-11T05:55:21`이 `"2026-08-11T05:55:21Z"` 정확 일치
   - `초가_0인_시각도_초를_생략하지_않는다`: `"…T05:55:00Z"`
   - `밀리초가_있는_시각은_소수_초를_유지한다`: `"…T06:09:27.724Z"`
   - `Z_표기_입력은_값_그대로_UTC로_해석된다` (FR-4, 현행 동작 고정)
   - `임의_오프셋_입력은_UTC로_환산된다`: `"…T14:55:21+09:00"`이 `05:55:21` (FR-4)
   - `표기_없는_입력은_UTC로_간주된다` (FR-5)
   - `직렬화_후_역직렬화하면_원값이다` (왕복 대칭, FR-3)
   - `null_시각_필드는_null로_직렬화된다` (FR-7)
2. **MockMvc[^6] 관통 검증** (기존 슬라이스 테스트에 추가):

     `+09:00` 본문 전송 후 ArgumentCaptor로 서비스 수신값 단언 (컨트롤러 앞 역직렬화 관통)
   - 시각 필드를 응답하는 컨트롤러 슬라이스 테스트 한 곳에 응답 본문 시각이 `Z`로 끝나는지 jsonPath
     정규식 단언 1건 (직렬화 관통)
3. **신규 DTO 가드 테스트** (신규, 성공 기준 6): `com.msg.fillmap` 하위 클래스명 `*Dto`를 classpath
   스캔해, 필드와 record 컴포넌트의 시각 계열 타입(`java.time.*`, `java.util.Date`, `Calendar`)이
   `LocalDateTime`뿐임을 단언한다. 시각 타입이 `LocalDateTime`으로 수렴하는 한 D-4 한 곳이 계약을
   보장하므로, 이 테스트가 "신규 DTO 추가 시에도 깨지게" 요구를 충족한다. 스캔은 스프링 내장
   `ClassPathScanningCandidateComponentProvider`로 하고(추가 의존성 없음) record가 걸리도록 후보
   판정을 완화한다. 시각을 String에 담는 우회는 정적 검사로 못 막으므로 리뷰 몫으로 남긴다.
4. **기존 검증 회귀 확인** (FR-6): `VideoRecordedAtValidationTest`(3424 미래 거부)를 포함한 전체

## 미해결 질문

없음. PRD §9와 동일하게 2026-08-11 FE 확인으로 전부 해소됐고, 남은 불확실성(Jackson 3 기반 클래스
시그니처, 커스텀 처리기 우선순위)은 결정 사항이 아니라 구현 중 컴파일러와 계약 테스트가 판정할 항목이다.

[^1]: 오프셋: ISO 8601 시각 문자열 끝의 `Z`나 `+09:00` 부분. 그 시각이 UTC에서 얼마나 떨어진 기준인지 명시한다. 없으면 해석이 받는 쪽 환경에 좌우되어 이번 9시간 밀림이 생겼다.
[^2]: naive 시각: 시간대 정보가 없는 시각 값. 자바 `LocalDateTime`과 PostgreSQL `timestamp without time zone`이 여기 해당하며, 이 프로젝트는 naive 값을 UTC로 읽는 관례를 쓴다.
[^3]: Jackson: 스프링이 쓰는 JSON 변환 라이브러리. 이 레포는 3.x(`tools.jackson` 패키지)를 쓰며, 이 티켓의 수정 지점이 바로 이 계층이다.
[^4]: 역직렬화: JSON 문자열을 자바 객체로 되돌리는 일. 요청 본문의 `recordedAt` 문자열이 `LocalDateTime`이 되는 단계다.
[^5]: `@JacksonComponent`: 커스텀 직렬화기와 역직렬화기를 스프링 빈으로 등록하면 부트가 앱 전체 JSON 변환기에 자동으로 끼워 주는 어노테이션(부트 4.1에서 `@JsonComponent`를 개명). 테스트 슬라이스에서도 기본으로 포함된다.
[^6]: MockMvc: 서버 기동 없이 컨트롤러 계층에 실제 HTTP 요청과 응답을 흉내 내는 스프링 테스트 도구. 역직렬화와 직렬화가 실제 경로로 관통하는지 확인할 수 있다.
