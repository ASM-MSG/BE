# MSG-258: 인기 검색어 순위 — 검색어 일별 집계 + 오늘·어제 합산 TOP 10

**Owner**: A (search 패키지 — MSG-251 §D1로 Owner A 확정)

> 요구사항 정본: `docs/prd/MSG-258-prd.md` (상태: 검토됨, 2026-08-04 사용자 승인 — FR-1~10 ·
> 확정 결정 7건 · 카카오 약관 경계 2선). 이 스펙은 PRD에 "어떻게"만 붙인다.
> 선행 코드: MSG-251 장소 검색(`docs/spec/MSG-251.md`) — 훅을 꽂는 대상.

## 개요

장소 검색(MSG-251) 요청의 검색어를 일별로 집계해 DB에 영구 축적하고(배치 확장 재료),
`GET /api/search/trending`으로 오늘+어제 합산 TOP 10을 rank+keyword로 제공한다.
dedupe(사용자·검색어당 일 1회)는 Redis SET, 카운트는 PostgreSQL native UPSERT.
카카오 약관 경계: **저장은 사용자가 입력한 검색어 텍스트·날짜·횟수까지만** — 카카오 응답의
어떤 필드도 저장하지 않는다 (PRD 불변 원칙).

## 배경 · 목표

- 검색어라는 관심 신호가 현재 전부 버려진다 — "궁금해하는 곳"은 핫구역("채워지는 곳")과 다른 축.
- 목표: ① 유효 검색을 카카오 성공 여부와 무관하게 당일 집계 반영 ② 일별 이력 영구 축적
  ③ TOP 10 조회 API ④ 약관 경계 유지(카카오 응답 무저장).

## 성공 기준

1. 유효 검색(트림 후 비어있지 않음) 1회가 정규화 후 당일 (날짜, 검색어) 카운트에 반영된다 —
   카카오 호출 **전**에 집계가 접수되므로 카카오 실패와 무관 (FR-1, 결정 7).
2. 같은 사용자 · 같은 정규화 검색어 · 같은 날(KST)은 몇 번을 검색해도 +1이다 (FR-2).
3. `GET /api/search/trending`이 오늘+어제(KST) 합산 상위 10개를 rank+keyword만으로 반환하고,
   데이터가 없으면 200 빈 목록이다 (FR-4·5·8).
4. Redis·DB 어느 쪽이 죽어도 검색 응답(`/api/search/places`)은 기존과 동일하게 성공/실패한다 —
   집계는 비동기라 지연 전이도 없다 (FR-6).
5. 저장소 어디에도 카카오 응답 필드가 없고, 집계 테이블에 사용자 식별자가 없다 (FR-7, 비기능 보안).
6. 기존 검색 동작(카카오에 보내는 쿼리·응답 형태·에러 수렴) 무변경. SecurityConfig 무변경 ·
   신규 외부 의존성 0 (spring-data-redis · JPA 기존 보유).

## API 명세

### 1) `GET /api/search/places?q=` — 기존, 동작 확장 (요청/응답 형태 무변경)

- 변경: 컨트롤러가 `@Parameter(hidden = true) @AuthenticationPrincipal AuthPrincipal principal` 추가,
  서비스에 `principal.userId()` 전달. trim 가드 통과 직후 `searchKeywordCommandService.recordSearch(userId, query)`
  1줄 호출 후 기존 카카오 호출로 진행.
- 불변: 응답 DTO · trim 가드(빈 q → 집계·호출 0 + 200 `[]`, FR-9) · 5502 수렴 · q 누락 400(global).
- 집계는 fire-and-forget — 응답 성공/실패·지연에 영향 없음 (FR-6).

### 2) `GET /api/search/trending` — 신규

- 인증: 필수(SecurityConfig `anyRequest().authenticated()` — 무변경, 미인증 401). principal 미사용.
- 요청 파라미터: 없음.
- 응답: `SuccessResponse<List<TrendingKeywordResponseDto>>`

```json
{
	"developCode": 200,
	"message": "성공",
	"data": [
		{ "rank": 1, "keyword": "홍대 카페" },
		{ "rank": 2, "keyword": "부산대" }
	]
}
```

- `TrendingKeywordResponseDto(int rank, String keyword)` record. count·장소 정보 없음 (FR-4·8).
- 데이터 없으면 200 + `data: []` (FR-5). 10개 미만이면 있는 만큼만.
- 에러 케이스: 신규 없음 (D7).

## 도메인 로직

용어는 glossary 기준 — "검색어"는 사용자가 입력한 q 텍스트이며, 격자·점령·방문 어휘와 무관한
search 도메인 신호다. 일 경계는 **KST(Asia/Seoul) 자정** — 스트릭·알림 전송률 제한(MSG-179 D8)과
동일 관례.

### 집계 (`SearchKeywordCommandService.recordSearch(long userId, String rawQuery)`)

1. **요청 스레드**: 정규화(D3) → 255자 초과면 스킵 → KST `LocalDate` 확정(Clock) → 워커 큐 제출.
   큐 포화 등 제출 실패는 폐기+warn (hotzone 미러).
2. **워커 스레드**: Lua `SADD searchdedupe:{yyyyMMdd} {userId}:{keyword}` + `EXPIRE 26h` 원자 실행 —
   - 반환 1(오늘 이 사용자의 이 검색어 첫 등장) → `upsertIncrement(date, keyword)` UPSERT +1.
   - 반환 0 → 스킵 (FR-2).
   - Redis·DB 어느 단계 예외든 삼키고 warn (FR-6) — 신호 1건 유실 허용.
3. 동시성: SADD 원자성이 같은 사용자 동시 중복을 제거하고, ON CONFLICT 행 잠금이 서로 다른
   사용자의 동시 +1을 직렬화한다. Redis 유실(플러시·재기동) 시 같은 날 재카운트 가능 —
   "dedupe 판정과 카운트 증가 사이 중복 허용 오차 수용"(비기능) 범위.

### 조회 (`TrendingKeywordQueryService.findTop10()`)

- 오늘·어제(KST, Clock 판정)를 파라미터로 native 쿼리 1회:

```sql
SELECT keyword
FROM search_keyword_daily_counts
WHERE keyword_date IN (:today, :yesterday)
GROUP BY keyword
ORDER BY SUM(search_count) DESC, keyword ASC
LIMIT 10
```

- 결과 순서대로 rank 1..N 부여해 DTO 변환. 캐시 없음 — 2일치 소량 테이블 단순 집계(비기능 성능 충족),
  느려지면 그때 붙인다.

## 데이터 모델

### 신규 마이그레이션: `V23__search_keyword_daily_counts.sql`

(**V 번호 2회 정정**: PRD의 "V21"은 notifications(MSG-179) 선점으로 스펙이 V22로 정정했으나,
구현·PR 사이에 MSG-180 `V22__notification_opt_outs.sql`이 develop에 머지돼 V22도 선점 —

V 번호 경합은 developCode 대역 경합(MSG-178/185)과 동일 패턴.)

```sql
-- 검색어 일별 집계 (MSG-258). 저장은 정규화 검색어 텍스트·날짜·횟수뿐 — 사용자 식별자·카카오 응답 필드 없음 (약관 경계, FR-7).
-- 삭제·보관 정책 없음 — 영구 축적이 요구사항 (FR-10, 배치 확장 재료).
CREATE TABLE search_keyword_daily_counts (
	id           BIGSERIAL    PRIMARY KEY,
	keyword_date DATE         NOT NULL,   -- KST(Asia/Seoul) 기준 일자 — 애플리케이션이 확정해 전달 (DB TIMESTAMP UTC 관례와 구분)
	keyword      VARCHAR(255) NOT NULL,   -- 정규화(trim·연속 공백 1칸·소문자) 후 텍스트
	search_count INT          NOT NULL DEFAULT 1,
	created_at   TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP,

	CONSTRAINT uq_search_keyword_daily UNIQUE (keyword_date, keyword)   -- UPSERT 충돌 키 + 조회 인덱스 겸용
);
```

- 엔티티: `SearchKeywordDailyCount` (`search/entity/`) — `@Getter` ·
  `@NoArgsConstructor(access = AccessLevel.PROTECTED)`. 쓰기는 native UPSERT만이라 매핑은 조회용.
- Repository: `SearchKeywordDailyCountRepository extends JpaRepository<SearchKeywordDailyCount, Long>`

```java
@Transactional   // 워커 스레드 호출 — 서비스 트랜잭션 문맥 없음 (D9)
@Modifying
@Query(value = """
	INSERT INTO search_keyword_daily_counts (keyword_date, keyword, search_count)
	VALUES (:date, :keyword, 1)
	ON CONFLICT (keyword_date, keyword)
	DO UPDATE SET search_count = search_keyword_daily_counts.search_count + 1
	""", nativeQuery = true)
int upsertIncrement(@Param("date") LocalDate date, @Param("keyword") String keyword);
```

### 런타임 동작 (실측)

**데이터 저장 위치**
- PostgreSQL `search_keyword_daily_counts`(V23) — 실측 컬럼 `id · keyword_date · keyword ·
  search_count · created_at`, 인덱스는 PK + `uq_search_keyword_daily` 2개뿐(추가 인덱스 0).
- Redis SET `searchdedupe:{yyyyMMdd}` — member `{userId}:{정규화 검색어}`, TTL 26h(93600s).

**실행 쿼리** (postgres `log_statement=all` 실측 — native 원문이 그대로 나가고 named param만 `$n` 치환)

```sql
INSERT INTO search_keyword_daily_counts (keyword_date, keyword, search_count)
	VALUES ($1, $2, 1) ON CONFLICT (keyword_date, keyword)
	DO UPDATE SET search_count = search_keyword_daily_counts.search_count + 1

SELECT keyword FROM search_keyword_daily_counts WHERE keyword_date IN ($1, $2)
	GROUP BY keyword ORDER BY SUM(search_count) DESC, keyword ASC LIMIT 10
```

- TOP10 EXPLAIN(0행 기준): `Limit → Sort(sum DESC, keyword) → HashAggregate → Seq Scan` —
  행이 쌓이면 `uq_search_keyword_daily`가 날짜 필터를 받는다.
- Redis는 앱이 `EVALSHA(keys=1, searchdedupe:{날짜}, {userId}:{키워드}, 93600)` 1회만 전송 —
  서버 내부에서 `[lua] SADD` → `[lua] EXPIRE`가 원자 실행(`redis-cli monitor` 캡처).
  255자 초과 검색어는 EVALSHA 자체가 나가지 않는다(요청 스레드에서 스킵).

**예외 흐름**
- 집계는 어떤 예외도 밖으로 나가지 않는다 — 접수 단계(큐 포화 `RejectedExecutionException`
  포함)와 워커 단계(Redis/DB) 모두 `log.warn` 삼킴. `GlobalExceptionHandler` 미도달, 신규
  developCode 0(D7). Redis 실패 시 UPSERT 미진행(D4 — 죽은 포트 6390 템플릿으로 실측).
- 검색 본체 무변경: 카카오 실패 `SEARCH_UPSTREAM_ERROR` → 502/`developCode 5502`(통합 테스트
  실 HTTP 확인), 미인증 401은 SecurityConfig 전역(`/api/search/trending`도 자동 커버).

**빈 동작**
- `SearchKeywordCommandServiceImpl`: `@Autowired` 생성자가 `Clock.systemUTC()` + 단일 데몬
  스레드(`search-keyword`, 코어=최대 1, `LinkedBlockingQueue(10_000)`)를 조립. 테스트용
  `(template, Clock, Executor)` 생성자 별도. `@PreDestroy shutdown()` — `ExecutorService`일 때만
  5초 드레인 → 타임아웃/인터럽트 시 `shutdownNow()` + 인터럽트 플래그 복원.
- KST 집계 날짜는 **요청 스레드**에서 `LocalDate.now(clock.withZone(KST))`로 확정해 워커에
  전달 — 워커는 clock을 읽지 않아 자정 경계에 안전(D2).
- 워커 경로엔 주변 트랜잭션이 없어 `upsertIncrement`의 `@Transactional`이 자체 개시·커밋(D9 —
  `SearchKeywordCommandTransactionTest`가 무트랜잭션 컨텍스트 커밋 가시성으로 실증).
  조회 서비스는 native SELECT 1회, 트랜잭션·캐시 없음.

**공유 인프라 위생**
- 스위트 종료 후 테이블 0행 · `searchdedupe:*` 0키(테스트 자체 회수). 주의: 조회 테스트는
  2000-01-01 고정 Clock — `SearchKeywordCommandTransactionTest` 중단 시 커밋 행이 남을 수 있고,
