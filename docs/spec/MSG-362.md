# MSG-362: 도감 화면에 현재 스트릭과 기록 이력 노출

**Owner**: B (단독)

> 요구사항 정본: `docs/prd/MSG-362-prd.md` (검토됨, 2026-08-11 성민 승인). SRS 등재분은
> FR-STREAK-08(이 티켓 대상)이고, KST 경계는 FR-STREAK-02, 삭제 무차감은 FR-STREAK-05와
> 정합해야 한다. 이 스펙은 PRD의 FR-1부터 FR-9와 비기능 요구에 "어떻게"만 붙인다.
> 변경 대상은 `com.msg.fillmap.usergrid.*` 하나이고 집계가 읽는 `streaks`, `user_badges`
> 테이블도 Owner B 소유라 크로스오너 코드 변경이 없다. 단 `UserGridQueryService`가
> 계약 인터페이스[^1]라 비파괴 확장을 "계약 변경" 절에 따로 적었다.

## 개요

두 갈래를 한 티켓에서 처리한다.

첫째, 도감 요약(`GET /api/collections/summary`) 응답에 현재 스트릭, 최장 스트릭, 획득 뱃지 수
세 필드를 더한다. 기존 `UserGridRepository.getCollectionSummary`가 스칼라 서브쿼리[^2] 3개를
한 왕복으로 묶는 구조라, 서브쿼리 3개를 같은 문장에 더 얹어 DB 왕복 1회를 유지한다.
전용 API 신설과 요약 재구성은 PRD 단계에서 기각됐다(2026-08-10 성민 확정).

둘째, 날짜별 업로드 기록 조회 API를 신설한다. 도감 화면의 "스트릭 전체 기록 보기"가 여는
깃허브 잔디 형태 화면의 재료다. `videos`를 KST 날짜로 접어 업로드가 있었던 날과 그날의
건수만 반환한다.

마이그레이션과 신규 인덱스는 없다. 필요한 데이터가 `streaks`와 `videos`에 이미 있고,
기록 조회는 기존 `idx_videos_user_created`가 받친다.

## 배경과 목표

스트릭은 업로드마다 갱신되고 꾸준함 뱃지 판정에도 쓰이는데 내려주는 경로가 없어 사용자가
볼 수 없다. MSG-200이 집계와 저장까지 만들면서 노출은 도감 summary 티켓 소관으로 남겨 뒀고
(streak 스펙 §D8), 위키 Collection API 설계 초안(2026-07-17)이 summary에 담기로 했던
뱃지 수와 스트릭도 구현(MSG-152)에서 빠졌다. 이번 작업은 그 남은 절반을 채우는 것이다.

목표는 도감 화면이 상단 요약 카드를 서버 호출 두 번(도감 요약, 수집률)으로 그리고,
사용자가 지난 기록을 날짜 단위로 되돌아볼 수 있게 하는 것이다.

## 성공 기준

아래는 전부 관찰 가능한 조건이고, "테스트 시나리오" 절이 각각의 검증 수단이다.

1. 도감 요약 응답에 `currentStreak`, `maxStreak`, `badgeCount`가 실리고 기존 세 필드는
   값과 이름 모두 불변이다(FR-1, FR-2).
2. 업로드가 한 번도 없는 사용자도 요약 여섯 필드를 전부 0으로 받는다(FR-3).
3. 마지막 기록이 KST 그제 이전인 사용자의 `currentStreak`은 0이다. `streaks.current_count`에
   남은 끊긴 값이 그대로 나가지 않는다(비기능 데이터 정합).
4. 친구 프로필의 `summary`에도 같은 세 필드가 실린다. friend 패키지 수정 없이 성립한다(FR-4).
5. 기록 조회는 업로드가 있었던 날만, KST 날짜 오름차순으로 담는다(FR-5, FR-6).
6. 같은 업로드가 스트릭 판정과 기록에서 같은 KST 날짜로 잡힌다(FR-7).
7. 삭제한 영상의 업로드 날짜도 기록에 남는다(FR-8). 업로드 0건 사용자는 빈 배열을 받는다(FR-9).
8. 도감 요약의 DB 왕복은 1회 그대로다(비기능 성능).

## 결정 사항

PRD 7절이 스펙으로 넘긴 판단 두 건과, 스펙 단계에서 새로 확정한 두 건이다.

### D-1. 기록 조회 경로는 도감 아래 (`/api/collections/upload-history`)

streak 패키지가 아니라 도감으로 정한다. 근거 세 가지다. 첫째, 재료가 `streaks` 테이블이
아니라 `videos` 집계라 데이터도 스트릭 소관이 아니다. 둘째, usergrid 패키지가 이미
`user_grids`와 `videos`의 네이티브 집계를 전담한다(MSG-152 관례, 리포지토리 javadoc 명문).
셋째, streak 패키지에는 컨트롤러도 조회 서비스도 없어(쓰기 훅과 배치뿐) 그쪽에 두면 신설
비용만 는다. "구현 패키지는 usergrid, 사용자 대면 리소스는 collections"라는 기존 분리
(CollectionController 주석)를 그대로 따른다.

### D-2. 요약 집계는 SQL 직접 읽기 (도메인 서비스 경유 기각)

`getCollectionSummary` 한 문장에 `streaks`, `user_badges` 스칼라 서브쿼리를 얹는다.
도메인 서비스 경유(예: `StreakRepository.findCurrentCount` 호출)는 기각한다. 근거는
비기능 요구 "DB 왕복 1회"가 서비스 경유로는 성립하지 않는다는 것 하나로 충분하고,
관례도 같은 방향이다. usergrid는 이미 다른 패키지 소유 테이블(`videos`, `grids`,
`regions`)을 네이티브로 직접 읽고 있고(MSG-152, MSG-246), 연관관계 금지 원칙 아래 조회는
프로젝션[^3]과 native로 명시적으로 짜는 것이 정본이다(project-conventions MSG-334).
셋 다 Owner B 테이블이라 경계 위반이 아니다. 참고로 `findCurrentCount`는 UPSERT 직후
행 존재가 보장된 문맥 전용이라 여기 재사용하면 행 없는 사용자에서 깨진다.

### D-3. 현재 스트릭은 조회 시점에 유효성을 판정한다

`streaks.current_count`는 마지막 업로드 시점에 계산된 값이라, 이후 하루를 걸러 스트릭이
끊긴 사용자에게도 옛 값이 남아 있다(다음 업로드 때에야 1로 리셋된다). 그대로 내보내면
"현재 스트릭 12일"이 거짓이 된다. 요약 쿼리가 `last_recorded_date`로 판정한다:
KST 오늘 또는 어제면 `current_count`, 그보다 오래됐으면 0. 이 판정은 `upsertOnUpload`의
3분기(오늘이면 유지, 어제면 +1, 그 외 리셋), 리마인드 대상 선정(`last_recorded_date`가
어제)과 같은 규칙의 읽기 방향이다. KST 오늘은 `upsertOnUpload`와 글자 단위로 같은 표현식
`(statement_timestamp() AT TIME ZONE 'Asia/Seoul')::date`를 써서 판정 기준이 한 곳도
어긋나지 않게 한다. `maxStreak`은 끊겨도 유지되는 값이라 `max_count`를 그대로 내보낸다.

### D-4. 기록의 날짜 축은 `created_at` (업로드 시각)

`recorded_at`(촬영 시각)이 아니다. 갤러리 업로드는 과거 촬영 시각을 인정하므로(MSG-278)
`recorded_at`으로 접으면 스트릭 판정(업로드 이벤트 시각 기준)과 어긋나 FR-7이 깨진다.
`created_at`은 타임존 없는 벽시계 시각[^4]으로 저장되므로(MSG-315 실측), 쿼리가 JVM 기본
존으로 해석한 뒤 KST로 변환해 날짜를 접는다. 존 이름은 서비스가
`ZoneId.systemDefault().getId()`로 잡아 파라미터로 바인딩한다(MSG-315의 임계값 환산과
같은 전제를 읽기 방향으로 쓴 것).

허용 오차 한 가지를 적어 둔다. 스트릭 판정은 UPSERT 문장의 `statement_timestamp()`를 쓰고
`created_at`은 같은 트랜잭션의 엔티티 저장 시각이라, KST 자정을 정확히 걸치는 밀리초 창에서
이론상 하루 어긋날 수 있다. 같은 요청 안 밀리초 차이라 발생 확률이 사실상 0이고 보정
수단도 없어 허용한다.

## API 명세

### `GET /api/collections/summary` (확장)

요청은 불변이다(파라미터 없음, 로그인 필수). 응답 `CollectionSummaryResponseDto`에
세 필드가 늘어난다. 기존 세 필드는 이름, 타입, 산식 전부 그대로다.

| 필드 | 타입 | 의미 |
|------|------|------|
| `totalGridCount` | Integer | (기존) 점령한 격자 수 |
| `totalVideoCount` | Long | (기존) 올린 영상 총합 |
| `visitedRegionCount` | Integer | (기존) 방문한 행정동 수 |
| `currentStreak` | Integer | 현재 스트릭. 끊겼으면 0 (D-3) |
| `maxStreak` | Integer | 최장 스트릭. 끊겨도 유지 |
| `badgeCount` | Integer | 획득한 뱃지 수 (`user_badges` COUNT) |

성공 예시:

```json
{
	"developCode": 200,
	"message": "성공",
	"data": {
		"totalGridCount": 15,
		"totalVideoCount": 42,
		"visitedRegionCount": 6,
		"currentStreak": 12,
		"maxStreak": 21,
		"badgeCount": 7
	}
}
```

에러 케이스는 기존과 같다(미로그인은 공통 처리). 업로드가 없는 사용자는 여섯 필드 전부 0.
신규 에러 코드는 없다. Swagger `requiredProperties`에 세 필드를 추가한다.

친구 프로필(`GET /api/friends/{userId}/profile`)의 `summary`는
`CollectionSummaryResponseDto` 중첩 재사용이라 자동으로 같은 필드를 받는다.
`FriendProfileResponseDto`는 수정하지 않는다(확인만). 친구에게 공개하는 범위는 이
숫자까지이고 날짜별 기록은 아니다(비기능 보안).

### `GET /api/collections/upload-history` (신설)

로그인 사용자 본인의 날짜별 업로드 기록. 파라미터 없음(본인 것만, 다른 사용자 지정 불가).

응답 `data`는 `UploadHistoryResponseDto` 배열이다.

| 필드 | 타입 | 의미 |
|------|------|------|
| `uploadDate` | LocalDate (`"2026-08-11"`) | 업로드가 있었던 KST 날짜 |
| `uploadCount` | Integer | 그날 업로드한 영상 수 (1 이상) |

- 업로드가 있었던 날만 담는다. 빈 날은 항목 자체가 없다(FR-6). 잔디[^5]의 빈 칸 채우기는
  FE 몫이다.
- 정렬은 `uploadDate` 오름차순 고정.
- 삭제한 영상, 블라인드된 영상의 업로드도 센다(FR-8, 스트릭 소급 차감 없음과 정합).
- 업로드 0건 사용자는 에러가 아니라 빈 배열 200(FR-9).
- 범위는 자연히 가입일부터 오늘까지다. 업로드가 가입 전이나 미래에 존재할 수 없으므로
  별도 범위 파라미터를 두지 않는다.
- 에러 케이스: 미로그인 공통 처리뿐. 신규 에러 코드 0.

## 도메인 로직

### 요약 쿼리 확장 (`UserGridRepository.getCollectionSummary`)

기존 문장에 스칼라 서브쿼리 3개를 더한다. 기존 3개는 한 글자도 바꾸지 않는다.

```sql
COALESCE((SELECT CASE
		WHEN s.last_recorded_date >= (statement_timestamp() AT TIME ZONE 'Asia/Seoul')::date - 1
			THEN s.current_count
		ELSE 0
	END
	FROM streaks s WHERE s.user_id = :userId), 0) AS "currentStreak",
COALESCE((SELECT s.max_count
	FROM streaks s WHERE s.user_id = :userId), 0) AS "maxStreak",
(SELECT COUNT(*)::int
	FROM user_badges WHERE user_id = :userId) AS "badgeCount"
```

- `>= 오늘 - 1`이 오늘과 어제를 모두 덮는다(미래 날짜는 존재하지 않는다). 판정 표현식은
  `upsertOnUpload`와 동일해야 한다(D-3).
- `streaks` 행이 없는 사용자(업로드 경험 0)는 서브쿼리가 NULL을 내므로 바깥 COALESCE가
  0으로 접는다(FR-3). `user_grids` 기반 기존 지표들이 0을 주는 방식과 같은 결이다.
- `streaks`를 두 서브쿼리가 각각 읽지만 user_id PK 단일 행 조회 두 번이라 비용이 무시
  가능하고, 지표 하나에 서브쿼리 하나라는 기존 문장 구조를 유지한다. 왕복은 여전히 1회다.

`CollectionSummaryProjection`에 `getCurrentStreak()`, `getMaxStreak()`, `getBadgeCount()`
(전부 Integer)를 더하고, `CollectionSummaryView`와 `CollectionSummaryResponseDto`에 같은
필드를 얹는다. 변환은 기존 `from(view)` 흐름 그대로다.

### 기록 조회 쿼리 (`UserGridRepository.getUploadHistory` 신설)

```sql
SELECT
	((v.created_at AT TIME ZONE :storedZone) AT TIME ZONE 'Asia/Seoul')::date AS "uploadDate",
	COUNT(*)::int AS "uploadCount"
FROM videos v
WHERE v.user_id = :userId
GROUP BY 1
ORDER BY 1
```

- `:storedZone`은 `ZoneId.systemDefault().getId()`. 첫 `AT TIME ZONE`이 벽시계 값을 저장
  존으로 해석하고, 둘째가 KST로 변환한다(D-4).
- `status` 필터가 없는 것이 의도다. DELETED도 BLINDED도 업로드 사실은 있었고, 스트릭이
  삭제로 차감되지 않으므로 기록도 같아야 요약과 어긋나지 않는다(FR-8). 영상 삭제는 소프트
  삭제[^6]라 행이 남아 있어 이 집계가 성립한다.
- `GROUP BY`가 FR-6(업로드 있는 날만)을 별도 분기 없이 만든다. 구동은
  `idx_videos_user_created`로 사용자 행만 몰아 읽고 날짜 접기는 집계 단계다. 신규 인덱스 0.

서비스는 `UserGridQueryService.getUploadHistory(long userId)`로 노출한다. B-내부 read이고
`CollectionController`만 소비한다(MSG-153, MSG-181, MSG-186의 메서드 1개 비파괴 추가 선례
동형). 뷰는 `UploadHistoryView(LocalDate uploadDate, int uploadCount)` 신규,
컨트롤러가 `UploadHistoryResponseDto`로 변환한다. presign도 격자 연산도 없어 impl은
프로젝션을 뷰로 옮기는 것이 전부다.

## 데이터 모델

변경 없음. 마이그레이션 없음. 엔티티, 테이블, 인덱스 전부 그대로다.

## 계약 변경

`UserGridQueryService`(B 제공, A 소비 계약)에 비파괴 변경 두 건이 있다. 리뷰에서 Owner A
확인이 필요한 지점이다.

1. `getCollectionSummary(long userId)` 시그니처는 불변이고, 반환 타입
   `CollectionSummaryView`에 필드 3개가 는다. 소비처는 접근자만 쓰므로 기존 접근자 불변으로
   영향이 없고, 생성처는 impl 한 곳뿐이다. MSG-167이 `CollectionGridView`에 `regionName`을
   더했던 것과 같은 성격의 확장이다.
2. `getUploadHistory(long userId)` 메서드 1개 추가. B-내부 read라 Owner A 소비 코드에
   영향이 없다(non-breaking).

`GridQueryService`, `HotZoneService`, `UserOidcCommandService`는 건드리지 않는다.
