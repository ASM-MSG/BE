# MSG-143 — ADR: AI 처리 실행 환경

**상태**: 결정됨 · **날짜**: 2026-07-21 · **결정자**: 성민(인프라)
**근거 데이터**: [MSG-142 측정 결과](https://github.com/ASM-MSG/AI/blob/main/results/MSG-142-report.md) · **모델 선정**: [MSG-144](./MSG-144.md)

---

## 결정

**상시 Python(FastAPI) 서버로 간다.** dev EC2에 Docker 컨테이너를 하나 더 붙이는 형태다.
Lambda는 채택하지 않되, 아래 "재검토 조건"을 만족하면 다시 연다.

**전제 조건 1개**: 입력 영상을 **1080p 30fps로 다운스케일한 뒤** AI 처리한다.
이건 선택이 아니라 필수다 (근거는 아래).

---

## 배경

`architecture.md`는 AI Highlight-Blur를 FastAPI로 적어뒀지만, ToBe 다이어그램
(`7_FillMap_ToBe_eval.drawio.xml`)에는 여전히 **"AI 파이프라인 (택1 · 보류)"** 로
Lambda 옵션이 남아 있다. 근거 없이 한쪽을 지우지 않고, MSG-142 실측으로 결정한다.

## 측정된 사실 (MSG-142)

AWS Graviton3 `c7g.large` 실측:

| 입력 | 처리 시간 | Lambda 15분 대비 | 메모리 피크 |
|---|---|---|---|
| 1080p 30초 | 3.1~3.8분 | 21~26% | 886~906MB |
| **4K 60fps 30초** | **9.7분** | **64.5%** | **1,152MB** |

이 셋이 결정을 좌우했다:

1. **처리 시간이 분 단위다.** 초 단위가 아니다.
2. **vCPU를 늘려도 안 빨라진다.** 2→1 vCPU 차이가 1~10%뿐이다. 추론이 병렬화되지 않는다.
3. **프레임당 추론 시간이 해상도와 무관하다** (227~230ms). ultralytics가 어차피
   `imgsz=640`으로 리사이즈하기 때문에, 4K가 느린 건 프레임 수(60fps)와 인코딩 탓이다.

## 비교

| 기준 | Lambda | **상시 FastAPI** | GPU 인스턴스 |
|---|---|---|---|
| 15분 제한 | 4K가 65% — 마진 35% | 제한 없음 | 제한 없음 |
| 비용 (월 1,000건) | **$4.5** | $29.8 (`c7g.medium`) | $384 (`g4dn.xlarge`) |
| 비용 (월 10,000건) | $44.8 | **$29.8** (동일) | $384 |
| 유휴 비용 | **0** | 상시 과금 | 상시 과금 |
| 동시성 | **자동 확장** | 1대당 시간 17건 | 자동 아님 |
| 콜드스타트 | 이미지 pull 10~40초 (torch가 크다) | **없음** | 없음 |
| 운영 복잡도 | ECR 빌드·푸시 파이프라인 신규 구축 | **기존 EC2+Docker 그대로** | 신규 + 비쌈 |
| 성능 튜닝 여지 | **없음** (메모리↑ 해도 vCPU 확장이 무의미) | 인스턴스 타입 변경 | GPU |

손익분기는 **월 약 6,650건**이다. 그 아래면 Lambda가 싸다.

## 근거

**Lambda를 택하지 않은 이유:**

- **처리 시간이 Lambda의 워크로드 모양과 안 맞는다.** 3~10분짜리 작업은 서버형이다.
  4K가 제한의 65%인데 이 측정에는 S3 다운로드·업로드와 컨테이너 이미지 pull이
  빠져 있다. 더하면 11~13분까지 갈 수 있어 마진이 얇다.
- **막혔을 때 빠져나갈 길이 없다.** 보통 Lambda는 메모리를 올려 vCPU를 늘리면 빨라지는데,
  측정 결과 그게 안 통한다(1~10%). 시간이 부족해지면 쓸 수 있는 카드가 없다.
- **신규 배포 파이프라인이 필요하다.** torch 때문에 zip이 아니라 ECR 컨테이너 이미지여야 하고,
  빌드·푸시 CI를 새로 만들어야 한다. MVP 기간에 치를 비용치고 크다.

**상시 FastAPI를 택한 이유:**

- **팀이 이미 하는 방식이다.** dev EC2에서 Docker 컨테이너를 운영 중이라 컨테이너 하나를
  더 얹는 것으로 끝난다. 새로 배울 것도, 새로 만들 파이프라인도 없다.
- `architecture.md`의 기존 설계와 일치한다.
- 비용 차이가 MVP 규모에서 **월 $25 수준**이다. 위 리스크를 사는 값으로 싸다.
- 트래픽이 커지면 오히려 상시 서버가 싸진다(월 10,000건에서 역전).

**GPU를 택하지 않은 이유:** CPU로 제한 안에 들어온다. 월 $384는 MVP 트래픽에 과하다.

## 전제 조건: 1080p 다운스케일

**4K 원본을 그대로 처리하면 안 된다.** 9.7분이 걸리고 메모리가 1,152MB까지 오른다.

프레임당 추론 시간이 해상도와 무관하므로(227~230ms), 1080p 30fps로 낮추면
프레임 수가 1800 → 900으로 줄어 **9.7분 → 3~4분**이 된다. 추론은 어차피 `imgsz=640`
기준이라 정확도 손실이 사실상 없고, 서비스에서 재인코딩은 어차피 하므로 추가 비용도 아니다.

이 전처리는 AI 서버 파이프라인의 첫 단계로 넣는다.

## 결과

**하게 되는 일:**

- AI 서버는 [ASM-MSG/AI](https://github.com/ASM-MSG/AI) 레포의 FastAPI 앱으로 구현한다 (AGPL-3.0, [MSG-144](./MSG-144.md) 참고)
- dev EC2에 Docker 컨테이너로 배포한다. 인스턴스 타입은 **`c7g.medium`(1 vCPU / 2GB) 이상**
- 처리 요청은 **비동기**여야 한다. 3~4분이 걸리므로 동기 응답은 불가능하다.
  Spring Boot가 요청을 넘기고 `processing_status`를 `BLURRING`으로 두는 형태
- 파이프라인 첫 단계에 1080p 30fps 다운스케일을 넣는다

**받아들이는 것:**

- 유휴 시간에도 서버 비용이 나간다 (월 약 $30)
- 동시 요청이 몰리면 큐가 쌓인다. 1 vCPU 기준 시간당 17건이 상한이고,
  넘으면 인스턴스를 키우거나 대수를 늘려야 한다

**따라오는 문서 수정:**

- `architecture.md` — AI Highlight-Blur를 FastAPI 상시 서버로 확정 표기, 다운스케일 단계 추가
- `7_FillMap_ToBe_eval.drawio.xml` — "AI 파이프라인 (택1 · 보류)" 노트에서 Lambda 옵션A 제거
- `architecture.md:142-143` — YOLO/CLIP 표기를 MSG-144 결정(YOLOv11n 2종 + PySceneDetect)에 맞게 갱신

## 재검토 조건

아래 중 하나라도 해당하면 이 결정을 다시 연다:

- 월 처리량이 **6,650건**을 넘어 Lambda가 비용 우위를 잃는 지점에 가까워질 때 → 그때는
  이미 상시 서버가 유리하므로 사실상 이 결정이 강화된다
- 트래픽이 **간헐적 스파이크** 형태로 굳어질 때 (평소 0, 가끔 폭증) → Lambda의 자동 확장이 유리
- 다운스케일해도 처리 시간이 **10분을 넘길 만큼** 모델이 무거워질 때 → GPU 재검토

## 미해결

- **GPU 실측 미완.** CPU로 충분하다는 결론이 나와 측정을 생략했다. GPU가 필요해지는
  상황(모델 교체 등)이 오면 그때 잰다.
- **동시 처리 상한 미측정.** "1 vCPU 시간당 17건"은 단일 요청 처리 시간에서 나눈 값이라
  실제 동시 요청 시 성능 저하는 반영되지 않았다. 부하 테스트가 필요하다.
