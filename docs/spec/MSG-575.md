# MSG-575: 계정 발급 요청 반려 안내 메일 자동 발송

**Owner**: B (콘텐츠·인증 도메인, `com.msg.fillmap.user.*` + 공용 메일 유틸 `global/mail`)

> 요구사항 정본: `docs/prd/event-submission.md` (검토됨, v2.3 개정 2026-09-05) FR-6 행과 결정 기록
> "반려 통보 수기 → 반려 안내 메일 자동 발송으로 번복"
> SRS: FR-AUTH-18 (진행 중 → 이 티켓이 반려 메일 몫을 구현) · 선행 스펙: `docs/spec/MSG-499.md` §5 반려

## 개요

관리자가 행사 운영자[^1] 계정 발급 요청을 반려하면 지금은 사유만 `org_account_requests.reject_reason`에
저장되고 요청자에게는 아무것도 가지 않는다(MSG-499에서 "반려 통보 수기"로 확정, 피그마 댓글 #108).
이 티켓은 반려 즉시 요청자의 공식 이메일로 반려 사유를 담은 안내 메일을 자동 발송하도록 바꾼다.
메일은 기존 평문 메일 4종(초기 비밀번호, 재설정 링크, 아이디 변경 완료, 노출 중지)과 달리 필맵 이름과
색을 입힌 서비스 전용 서식(HTML + 평문 대체본[^2])이다. 발송 실패는 반려를 뒤집지 않고 응답의 발송
성공 여부로만 드러난다.

범위 밖: 아이디 변경 요청 반려(MSG-500, 메일 없음 유지), 기존 메일 4종의 서식 전환, 재발송 API.

## 배경 · 목표

- 승인은 메일이 자동으로 나가는데 반려만 수기라 관리자가 매번 따로 써야 했고, 잊으면 요청자가 결과를
  모르는 채 남았다(PRD 결정 기록). 저장된 사유를 그대로 실어 자동으로 보내면 이 공백이 닫힌다.
- 서식이 새로 생기는 이유는 이 메일의 독자가 계정도 없는 외부 기관 담당자라서다. 평문 몇 줄보다
  필맵이 보낸 공식 안내로 읽히는 모양이 필요하다. 다만 서식은 이 메일 한 곳에만 적용하고 기존 4종은
  건드리지 않는다(서지컬 원칙).
- 재발송 API는 만들지 않는다. MSG-500 노출 중지와 같은 결정으로, 저장된 사유(상세 조회
  `rejectReason`)가 수기 재통지의 재료다.

## 성공 기준

아래가 전부 테스트로 관찰되면 완료다. 검증 테스트 마커는 `// 검증: FR-AUTH-18, AC-575-NN`이다.

- AC-575-01: 대기 요청을 반려하면 200에 `data.emailSent`가 실리고, 발송 목에 잡힌 메일의 수신자가 요청의 공식 이메일이며 제목이 `[필맵] 행사 운영자 계정 발급 요청 반려 안내`다.
- AC-575-02: 평문 본문과 HTML 본문 양쪽에 기관명, 담당자명, 예정 행사명, 반려 사유, 재신청 안내 문구, `https://fillmap.kr`이 들어 있다.
- AC-575-03: 반려 사유에 `<script>` 같은 태그 문자를 넣으면 HTML 본문에는 `&lt;script&gt;`로 이스케이프되어 실리고 원문 태그는 없다. 사유의 줄바꿈은 HTML에서 `<br>`로 바뀐다.
- AC-575-04: 발송은 커밋 뒤다. 발송 시점에 활성 트랜잭션이 없다(기존 `발송은_커밋_뒤였다` 헬퍼로 판정).
- AC-575-05: 발송 유틸이 예외를 던져도 응답은 200이고 `emailSent`는 false이며, 별도 트랜잭션 재조회에서 상태 REJECTED, 저장된 사유, `processedAt`이 유지된다.
- AC-575-06: 검토 후 익명 재접수로 1426이 나면 발송 호출이 0회이고 상태는 PENDING이다. 없는 요청(1421)과 이미 처리된 요청(1422)도 발송 0회다.
- AC-575-07: `FillMapMailTemplate`이 만드는 HTML에는 "FillMap" 워드마크, 브랜드 색 상수 값, 문의 주소가 들어 있고 치환 자리표시자(`{title}` 등)가 남지 않는다.

## API 명세

### POST /api/admin/org-account-requests/{requestId}/reject (ADMIN, 기존)

- 요청: `OrgAccountRequestRejectRequestDto` 불변(`reason` 필수 최대 500자, `updatedAt` 에코). 필드
  Swagger 설명의 "수기로 통보할 때 쓴다"는 "반려 안내 메일에 그대로 실린다"로 교체한다.
- 응답: `SuccessResponse<Void>` → `SuccessResponse<OrgAccountRequestRejectResponseDto>` (신규 record)

```java
@Schema(description = "계정 발급 요청 반려 결과", requiredProperties = {"emailSent"})
public record OrgAccountRequestRejectResponseDto(
	@Schema(description = "반려 안내 메일 발송 성공 여부. true 는 SES 접수까지의 성공이고 배달 확인은 아니다")
	boolean emailSent
) {
}
```

`OrgAccountIssueResponseDto.emailSent`와 같은 의미다(SES 접수[^3]까지가 true). 응답 자체를 못 받았을
때의 복구는 상세 재조회이고, REJECTED면 반려는 끝난 것이며 발송 확신이 없으면 저장된 사유로 수기
통지한다.

- 에러: 1421, 1422, 1426, 검증 위반 공통 400. 전부 기존 그대로이고 어느 경우에도 메일은 나가지 않는다.
- 컨트롤러 `AdminOrgAccountController.reject`의 `@Operation` 설명에서 "메일은 발송되지 않는다" 문단을
  "요청자의 공식 이메일로 반려 사유를 담은 안내 메일이 즉시 발송된다. 발송이 실패해도 반려는 유지되며
  emailSent가 false로 온다. 재발송 API는 없고 저장된 사유가 수기 재통지 재료다"로 교체한다.

응답의 와이어 형태가 `data: null`에서 `data: { emailSent }`로 바뀐다. 관리자 화면 [관리자 1-1]이 반려
결과를 어떻게 보여줄지는 FE 몫이고, 승인 응답의 `emailSent`를 이미 소비하므로 같은 처리를 붙이면 된다.

## 도메인 로직

### 반려 흐름 (`OrgAccountRequestService.reject`)

승인 `approve`와 같은 패턴이다. 현재 `@Transactional` 한 줄인 메서드를 `TransactionTemplate` 경계[^4]로
바꿔 잠금, 대조, 전이를 안에서 끝내고 발송은 커밋 뒤에 한다.

1. `transactionTemplate.execute` 안: `lockPending(requestId, request.updatedAt())`으로 행 잠금[^5] 조회,
   PENDING 확인(1422), `updatedAt` 완전 일치 대조(1426). 기존 진입부를 그대로 쓴다.
2. `target.reject(request.reason(), LocalDateTime.now(clock))` 전이. 엔티티 메서드 주석의 "메일 발송
   없음" 문구를 갱신한다(로직 불변).
3. 발송에 필요한 값만 record로 반환한다: `RejectedRequest(String email, String orgName,
   String contactName, String eventName, String reason)` (private record, `AdminApprovedEventService.Unpublished`
   선례. 엔티티를 트랜잭션 밖으로 흘리지 않는다).
4. 경계 밖: `notifyRejection(rejected)`가 `FillMapMailTemplate`으로 평문과 HTML을 만들어
   `mailSender.send(to, subject, text, html)`를 부른다. 성공이면 true, `RuntimeException`이면
   `log.error("[org-account] 반려 안내 메일 발송 실패, 반려는 유지된다: requestId={}, to={}", ..., e)`
   후 false. 예외를 그대로 로거에 넘겨도 된다. 반려 사유와 신청 값은 초기 비밀번호와 달리 로그·응답
   비노출 요건이 없다(`AdminApprovedEventService.notify` 선례).
5. `new OrgAccountRequestRejectResponseDto(emailSent)` 반환.

커밋과 발송 사이에 프로세스가 죽으면 REJECTED인데 메일이 안 나간 상태가 남는다. 승인과 같은 수용된
크래시 창이고 복구는 위 API 명세의 수기 통지다.

### 메일 내용

- 제목: `[필맵] 행사 운영자 계정 발급 요청 반려 안내`
- 본문 구성: 인사(기관명, 담당자명), 예정 행사명, 강조 박스에 반려 사유, "보완해서 다시 신청할 수
  있다"는 안내, 필맵 주소 `https://fillmap.kr`, 하단 안내("문의는 이 메일에 회신해 주세요", 발신
  contact@fillmap.kr).
- 재신청 안내의 근거: MSG-499 스펙 "반려 후 재신청 경로". 대기 행에만 걸리는 부분 유니크 인덱스[^6]라
  REJECTED 이메일은 같은 공개 폼으로 새 대기 행을 만들 수 있다. 공개 폼의 정확한 URL 경로는 FE 몫이라
  메일에는 루트 주소만 싣는다(미해결 질문 2).
- 주소 상수는 `OrgAccountIssueService.LOGIN_URL`과 같은 값이다. 그 상수가 private이라 `FillMapMailTemplate`
  쪽에 같은 값을 한 번 더 두지 않고, 서비스가 본문 조립 시 인자로 넘긴다.

### 서식 템플릿 (`global/mail/FillMapMailTemplate`)

final 클래스에 static 메서드만 둔다(인스턴스 상태가 없고 빈으로 만들 이유가 없다).

- `static String html(String title, List<String> paragraphs, String highlight, String footer)`와
  `static String text(...)` 같은 형태로, 반려 메일 한 곳이 소비한다. 서식 요소는 상단 "FillMap"
  워드마크(브랜드 색 상수 `BRAND_COLOR` 하나, 미해결 질문 1), 제목, 본문 문단, 강조 박스, 하단 안내다.
- 인라인 CSS와 테이블 레이아웃으로 짠다. 메일 클라이언트가 `<style>` 블록과 flex를 널리 지원하지
  않아서다.
- **삽입되는 문자열은 전부 `HtmlUtils.htmlEscape`(spring-web, 기존 의존성)로 이스케이프[^7]한다.**
  반려 사유는 관리자 자유 서술이고, 기관명·담당자명·예정 행사명은 비로그인 공개 폼에서 온 검증되지 않은
  값이라 신뢰 경계 밖이다. 이스케이프 뒤에 줄바꿈(`\n`, `\r\n`)을 `<br>`로 바꾼다(순서가 반대면 `<br>`가
  이스케이프된다).
- 평문 대체본은 같은 값으로 태그 없이 만든다. 이스케이프하지 않는다(평문에는 HTML 문맥이 없다).

### 메일 유틸 확장 (`global/mail/MailSender`)

- 인터페이스에 오버로드 `void send(String to, String subject, String text, String html)` 추가.
  기존 3인자 `send`는 그대로 두어 호출부 4곳(`PasswordService`, `OrgAccountIssueService`,
  `AdminEmailChangeRequestService`, `AdminApprovedEventService`)이 무수정이다.
- `SesMailSender`: 4인자는 `Body.builder().text(content(text)).html(content(html))`. 3인자는 html 없이
  종전 그대로.
- `LoggingMailSender`: 4인자는 평문 본문만 로그에 찍고 HTML은 길이만 남긴다(로컬 로그가 태그 수백 자로
  덮이지 않게).

활성 기록 스텁과 실패 스텁을 따로 단다. 그렇지 않으면 `발송_시점_트랜잭션_활성`이 null로 남아 AC-575-04가
"미호출"로 오판된다.

1. `반려하면_요청자에게_반려_안내_메일이_발송된다` (기존 "메일은 발송되지 않는다" 교체): 200,
   `emailSent` true, 수신자와 제목 단언, 평문·HTML 본문 캡처에 기관명("부산진구청")·담당자명·행사명·사유

## 미해결 질문

1. **브랜드 색 값**: 디자인 정본(피그마 웹 ver 14)의 색 토큰을 이번에 확인하지 못했다. `BRAND_COLOR`
   상수 하나에 임시값을 두고 구현하며, 디자인 확인 후 상수 한 곳만 바꾼다. 로고 이미지는 정적 에셋
   버킷이 미확정(MSG-363 뱃지 그림과 같은 사정)이라 텍스트 워드마크로 간다.
2. **공개 폼 URL 경로**: 재신청 안내에 실을 정확한 경로(`/ops` 랜딩인지 별도 폼인지)는 FE 라우팅 몫이라
   미확정이다. 루트 `https://fillmap.kr`만 싣고, 경로가 확정되면 상수 한 곳을 바꾼다.

[^1]: 행사 운영자: 행사를 등재하는 외부 주체(지자체·팝업 운영사·축제 대행사). 이 티켓의 수신자는 아직 계정이 없는 신청자라 `users` 행이 없고, 이메일은 `org_account_requests.email`에서 온다. 필맵 내부 인력을 가리키는 맨 "운영자"와 다르다.
[^2]: 평문 대체본: HTML 메일에 함께 실어 보내는 텍스트 본문. SES의 `Body`가 `text`와 `html`을 동시에 받으면 multipart/alternative로 나가, HTML을 못 그리는 클라이언트와 스팸 필터가 평문 쪽을 읽는다.
[^3]: SES 접수: AWS SES가 발송 요청을 받아들였다는 뜻. 배달 확인이 아니라서 오타 주소도 이 시점엔 성공이고 하드바운스는 몇 분 뒤에 따로 온다(MSG-499 계약 그대로).
[^4]: TransactionTemplate 경계: `@Transactional` 대신 `transactionTemplate.execute` 블록으로 트랜잭션 범위를 코드에 드러내는 방식. 메일 발송을 블록 밖에 두면 SES 왕복이 DB 커넥션을 붙들지 않고, 발송 성공 뒤 커밋 실패로 "통지했는데 반려는 안 됨"이 되는 역방향 구멍이 없다.
[^5]: 행 잠금: `findWithLockById`의 비관적 잠금(SELECT ... FOR UPDATE). 동시 승인·반려의 늦은 쪽이 잠금 대기 뒤 바뀐 상태를 읽고 1422로 걸리게 한다.
[^6]: 부분 유니크 인덱스: `org_account_requests`에서 `status = PENDING` 행에만 걸린 이메일 유니크 제약. 발급됨·반려 행은 인덱스 밖이라 같은 이메일로 새 대기 행이 생길 수 있고, 이것이 재신청 경로다.
[^7]: HTML 이스케이프: `<`, `>`, `&`, 따옴표를 `&lt;` 같은 문자 참조로 바꿔 입력 문자열이 태그로 해석되지 않게 하는 처리. 관리자와 신청자 입력이 그대로 HTML에 박히면 메일 클라이언트에서 스크립트나 위장 링크로 렌더될 수 있다.
