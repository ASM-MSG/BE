# MSG-363: 미션 뱃지를 종류별로 나누고 뱃지 그림 도입

**Owner**: B (단독)

> 요구사항 정본: `docs/prd/MSG-363-prd.md` (검토됨, 2026-08-10 성민 승인). SRS 등재분은
> FR-BADGE-12(종류별 지급)와 FR-BADGE-13(뱃지 그림)이고 FR-MISSION-07(합산 판정)을 대체한다.
> 이 스펙은 PRD의 FR-1부터 FR-9와 비기능 요구에 "어떻게"만 붙인다. 변경 대상이
> `com.msg.fillmap.badge.*`와 `com.msg.fillmap.mission.*`뿐이라 둘 다 Owner B이고 크로스오너
> 접점이 없다.

## 개요

두 갈래를 한 티켓에서 처리한다.

첫째, 미션 뱃지의 판정 축[^1]을 스탬프 총수 하나에서 축제, 코스, 팝업 세 개로 나눈다. 지금은
`MissionAwardServiceImpl` 53행이 완료 미션의 종류와 무관하게
`award(userId, MISSION_COUNT, countMyStamps(userId))`를 한 번만 부른다. 이 자리를 "이번에 새로
발급된 스탬프의 종류마다 그 종류의 스탬프 수로 판정"으로 바꾼다. 기존 합산 뱃지 3종은 행을 지우지
않고 은퇴 표시만 해서 지급 후보에서 뺀다.

둘째, 뱃지 그림 주소를 채운다. `badges.icon_url`이 17건 전부 비어 있어 진열장이 회색 사각형으로
남아 있다. 그림 파일은 공개 읽기 자원[^2]이라 영상처럼 서명 URL을 발급하지 않고, 주소를
마이그레이션이 한 번 채운 뒤 목록 응답이 그대로 내려보낸다.

마이그레이션은 둘로 쪼갠다. 뱃지 재편(V29)은 지금 나가고, 그림 주소(V31)는 에셋이 나온 뒤에
나간다. PRD 비기능 "배포와 그림 등록이 서로를 기다리지 않는다"를 파일 분리로 지킨다.

API 요청과 응답의 스키마는 바뀌지 않는다. 목록에 뜨는 뱃지 구성과 `iconUrl` 값만 달라진다.

## 배경과 목표

화면에서 미션은 축제, 코스추천, 팝업스토어 칩으로 나뉘어 있는데 뱃지는 셋을 합산해서 준다.
사용자는 "축제를 다녔다"고 인식하지 "미션을 5개 했다"고 인식하지 않으므로, 뱃지 이름이 자기 행동과
연결되지 않는다. 그림이 없는 것도 같은 문제의 다른 얼굴이다. 뱃지는 보여주는 것이 목적인 기능이라
회색 사각형 상태로는 기능이 성립하지 않는다.

목표는 세 가지다. 미션 뱃지가 화면의 칩 구분과 1:1로 대응하게 만들고, 모든 뱃지가 그림으로 뜨게
하고, 기존 사용자가 손해를 보지 않게(이미 받은 뱃지 유지, 이미 충족한 조건은 소급 지급[^3]) 한다.

## 성공 기준

아래는 전부 관찰 가능한 조건이고, "테스트 시나리오" 절이 각각의 검증 수단이다.

1. 축제 미션 1개를 완료하면 `EVENT_1`("축제 입문")이 지급되고, 코스와 팝업 뱃지는 지급되지 않는다.
   종류가 다른 미션 완료가 서로의 진행에 합산되지 않는다(FR-1).
2. AREA, THEME, CONTINUOUS 유형의 미션을 완료하면 스탬프는 발급되고 뱃지는 하나도 지급되지
   않는다(FR-6).
3. 한 번의 업로드로 축제 미션과 팝업 미션을 동시에 완료하면 두 축이 각각 판정되어 두 뱃지가 함께
   응답에 실린다(PRD 엣지 케이스 1).
4. `MISSION_1`, `MISSION_5`, `MISSION_10`은 어떤 신규 완료로도 더 지급되지 않는다(FR-3). 이미
   받은 사용자의 목록에는 계속 보이고, 받은 적 없는 사용자의 목록에서는 사라진다(FR-4).
5. V29 적용 직후, 이미 축제 5곳을 완료해 둔 사용자에게 `EVENT_1`과 `EVENT_3`이 소급 지급되고
   `EVENT_10`은 지급되지 않는다(FR-5). 같은 SQL을 다시 돌려도 결과가 같다(멱등[^4]).
6. V31 적용 후 `SELECT count(*) FROM badges WHERE icon_url IS NULL`이 0이고, 이후 그림 없는
   뱃지는 INSERT 자체가 실패한다(FR-7).
7. 미션을 완료하지 않은 업로드가 실행하는 쿼리 수가 변경 전과 같다(비기능 성능).
8. 서버가 내려주는 뱃지 이름 어디에도 "점령"과 "정복"이 없다(FR-9).

## API 명세

**엔드포인트, 요청, 응답 DTO 필드, 에러 코드 전부 불변이다.** 새 API도 새 developCode도 없다.
달라지는 것은 두 응답에 담기는 값뿐이다.

### `GET /api/badges` (내 뱃지 전체 목록)

응답 DTO(`MyBadgeResponseDto`)는 그대로다. 목록 구성이 다음과 같이 바뀐다.

- 종류별 뱃지 9행이 목록 끝에 추가된다. 정렬은 지금처럼 `badges.id` 오름차순(시딩 순)이므로 축
  단위로 티어 오름차순이 유지된다(MSG-201 D6의 "빈 칸이 그 자리에" UX).
- 은퇴한 합산 뱃지 3행은 그것을 획득한 사용자에게만 보인다. 미획득 사용자에게는 행 자체가 나오지
  않는다. 영원히 못 받는 칸을 회색으로 남겨 두지 않기 위해서다(V9 주석의 "훅 없는 시딩은 획득 불가
  뱃지 노출" 금지와 같은 취지).
- V31 이후 모든 행의 `iconUrl`이 절대 URL로 채워진다. 미획득 행도 같은 주소를 받고, 흐리게
  표시하는 것은 클라이언트 몫이다(FR-7).

예시(축제 뱃지 1티어를 획득한 사용자):

```json
{
	"badgeId": 18,
	"code": "EVENT_1",
	"name": "축제 입문",
	"description": "축제 1곳을 다녀왔어요",
	"iconUrl": "https://fillmap-static.s3.ap-northeast-2.amazonaws.com/badges/event_1.svg",
	"earned": true,
	"earnedAt": "2026-08-11T12:00:00",
	"isNew": true,
	"featuredRank": null
}
```

### `POST /api/videos` 업로드 확정 응답의 `newBadges`

배열 요소 타입(`EarnedBadgeResponseDto`)과 위치는 그대로이고, 미션 판정에서 합류하는 코드가
`MISSION_*`에서 `EVENT_*`, `COURSE_*`, `POPUP_*`으로 바뀐다. 한 업로드가 두 종류를 동시에
완료하면 두 종류의 뱃지가 같은 배열에 들어간다. 배열 순서는 완료 스탬프가 발급된 순서를 따른다.

### `PUT /api/badges/featured` (대표 뱃지 교체)

불변이다. 은퇴 뱃지도 이미 획득한 사용자는 대표로 지정할 수 있다. 지정 가능 여부는 `user_badges`
보유 여부로만 판정하므로(`setFeaturedRank`의 WHERE 절) 별도 처리가 필요 없고, 비회수 원칙(FR-4)과도
일관된다.

## 도메인 로직

### D1. 판정 축을 늘리는 방식: `BadgeConditionType`에 축 3종 추가 (A안 채택)

`EVENT_COUNT`, `COURSE_COUNT`, `POPUP_COUNT`를 enum과 `chk_badges_condition` CHECK 제약[^5]에
추가한다. 이름은 기존 `MISSION_COUNT`와 같은 꼴을 따른다.

채택 이유는 변경 범위다. `findEligible`과 `findNearMiss`는 격자 수, 업로드 수, 스트릭, 수집률,
미션까지 **모든 축이 공유하는 판정 쿼리**이고, 판정식은 `condition_type` 일치와
`(condition_value->>'value')::numeric` 비교 두 줄뿐이다. A안은 이 쿼리에 손을 대지 않고 파라미터로
넘기는 문자열만 늘어난다. CHECK 확장은 V9가 `MISSION_COUNT`를 넣을 때 이미 한 번 한 작업이라
복제할 선례가 있다(V9 1번 블록).

기각한 B안(`condition_value` JSONB에 `missionType`을 담고 쿼리에 필터 추가)의 문제는 셋이다.
첫째, 공유 쿼리 2개에 미션 전용 술어가 들어가 다른 네 축이 매 호출마다 무의미한 조건을 지고 간다.
둘째, `BadgeAwardService.award(userId, type, metric)` 시그니처에 미션 종류 인자를 더하거나 오버로드를
만들어야 해서 뱃지 도메인의 공개 계약이 미션 도메인 사정으로 넓어진다. 셋째, 임박 판정[^6]의
allowlist가 `BadgeConditionType` 집합이라 종류를 구분할 수 없어 그쪽도 함께 고쳐야 한다. CHECK
제약 한 줄을 아끼려고 세 곳을 늘리는 거래라 성립하지 않는다.

`MISSION_COUNT` enum 상수는 **지우지 않는다.** 은퇴한 badges 행 3개가 이 문자열을 계속 들고 있고
`Badge.conditionType`이 `@Enumerated(STRING)`이라, 상수를 지우면 그 행을 엔티티로 읽는 순간 매핑이
깨진다. 대신 javadoc에 은퇴 사실을 적고 `NEAR_MISS_TYPES` allowlist에서만 뺀다.

### D2. 합산 뱃지를 지급 후보에서만 빼는 방법: `badges.retired_at`

`badges`에 `retired_at TIMESTAMP`(NULL이면 현역)를 추가하고 세 쿼리를 고친다.

| 쿼리 | 변경 | 효과 |
|------|------|------|
| `findEligible` | `AND b.retired_at IS NULL` | 신규 지급 후보에서 제외(FR-3) |
| `findNearMiss` | `AND b.retired_at IS NULL` | 은퇴 뱃지의 임박 알림도 함께 중단 |
| `findAllWithMyStatus` | `WHERE b.retired_at IS NULL OR ub.user_id IS NOT NULL` | 획득자에게만 노출(FR-4) |

행 삭제는 불가능하다. `user_badges.badge_id`가 `badges(id)`를 참조하는 FK(ON DELETE 미지정, 즉
NO ACTION)라 획득 이력이 있으면 DELETE 자체가 실패하고, 억지로 지우면 사용자가 받은 뱃지를 뺏는
결과가 되어 FR-4와 정면으로 충돌한다.

기각한 다른 두 방법도 남긴다. `condition_type`을 `SPECIAL`로 바꾸는 방법은 스키마 변경이 0이지만,
훗날 SPECIAL 축에 지급 훅이 붙는 순간(SRS FR-BADGE-11) 은퇴 뱃지가 되살아나고 데이터의 의미도
망가진다. `condition_value`를 도달 불가한 큰 값으로 바꾸는 방법은 지급은 막지만 목록에서는 영원히
못 받는 회색 칸으로 남아, V9 주석이 금지한 상태를 스스로 만든다.

`retired_at`을 불리언이 아니라 시각으로 두는 이유는 은퇴 시점이 나중에 "왜 이 뱃지는 아무도 못
받나"를 설명하는 유일한 단서이기 때문이다. `user_badges.notified_at`이 같은 방식(nullable 시각을
플래그로 사용)의 선례다. 엔티티 `Badge`에는 매핑하지 않는다. 판정이 전부 native SQL이고 부분 매핑이
프로젝트 관례이며 `ddl-auto=validate`는 미매핑 컬럼을 문제 삼지 않는다.

### D3. 완료 미션의 종류를 얻는 경로

새 조회가 필요 없다. `findCompleted`가 이미 `m.type`을 select하고
`CompletedMissionProjection.getType()`으로 노출한다(업로드 응답의 `completedMissions[].type`이 그
값이다). 즉 판정 결과에 종류가 남아 있으므로 미션을 다시 읽지 않는다.

판정 흐름은 다음과 같이 바뀐다. 굵은 부분만 신규다.

```java
List<CompletedMissionResponseDto> stamps = new ArrayList<>();
Set<String> newStampTypes = new LinkedHashSet<>();        // 신규: INSERT 성공한 스탬프의 종류만
for (CompletedMissionProjection completed : missionRepository.findCompleted(userId, candidateIds)) {
	if (userMissionRepository.insertIgnoreConflict(userId, completed.getMissionId()) == 1) {
		stamps.add(CompletedMissionResponseDto.from(completed));
		newStampTypes.add(completed.getType());
	}
}
if (stamps.isEmpty()) {
	return MissionAwardResult.EMPTY;
}
List<EarnedBadgeResponseDto> newBadges = new ArrayList<>();
for (String type : newStampTypes) {
	BadgeConditionType axis = BADGE_AXIS.get(type);
	if (axis == null) {                                    // AREA, THEME, CONTINUOUS (FR-6)
		continue;
	}
	newBadges.addAll(badgeAwardService.award(
		userId, axis, userMissionRepository.countMyStampsByType(userId, type)));
}
return new MissionAwardResult(stamps, newBadges);
```

```java
// 미션 유형에서 뱃지 판정 축으로. 화면 칩이 있는 3종만 매핑하고 나머지는 부재(FR-6).
private static final Map<String, BadgeConditionType> BADGE_AXIS = Map.of(
	"EVENT", BadgeConditionType.EVENT_COUNT,
	"COURSE", BadgeConditionType.COURSE_COUNT,
	"POPUP", BadgeConditionType.POPUP_COUNT);
```

설계상 중요한 점 넷.

1. **INSERT가 성공한 스탬프의 종류만 모은다.** 경합에서 진 스탬프(영향 행 0)는 "이 요청으로 새로
   획득한" 것이 아니므로 종류 집합에도 넣지 않는다. 기존 필터(MSG-223 D2)를 종류 축으로 그대로
   연장한 것이다.
2. **`Set`으로 중복 제거한다.** 같은 종류 미션 2개가 한 번에 완료돼도 metric이 그 종류의 총계라
   축당 한 번만 부르면 충분하다.
3. **`LinkedHashSet`으로 순서를 고정한다.** 응답 배열 순서가 실행마다 흔들리면 테스트가
   불안정해진다.
4. **유형 문자열을 `MissionType`으로 valueOf하지 않는다.** 매핑에 없는 유형을 건너뛰는 것이
   정상 경로(FR-6)라, 예외를 던질 수 있는 변환을 끼울 이유가 없다.

### D4. 종류별 metric 쿼리

`UserMissionRepository.countMyStamps`(전체 총수)를 `countMyStampsByType`으로 **교체한다.** 축이
전부 종류별로 갈리므로 전체 총수를 쓰는 호출자가 하나도 남지 않는다. 쓰지 않는 쿼리를 남기면
다음 사람이 "어느 쪽이 맞는 metric인가"를 다시 판단해야 하므로 함께 지운다.

```sql
SELECT COUNT(*)::numeric
FROM user_missions um
JOIN missions m ON m.id = um.mission_id
WHERE um.user_id = :userId AND m.type = :type
```

`user_missions` PK(user_id, mission_id) prefix로 내 스탬프만 훑고 `missions` PK로 조인하므로 추가
인덱스가 필요 없다. `::numeric` 캐스트는 `award()`의 metric 타입(BigDecimal)에 맞추기 위한 기존
관례다.

### D5. 성능: 판정이 3축으로 갈려도 지배 경로는 그대로

미션에 해당하지 않는 업로드는 `findAwardCandidateIds`가 빈 결과를 주고 조기 종료한다. 이 경로는
쿼리 하나로 끝나고 이번 변경의 영향을 전혀 받지 않는다(비기능 성능 요구 그대로).

미션을 완료한 업로드만 축이 늘어난다. 완료 미션이 한 종류면 쿼리 수는 변경 전과 같다(집계 1회,
`findEligible` 1회, `findNearMiss` 최대 1회). 두 종류를 동시에 완료하는 드문 경우에만 그 3종이 한 벌
더 실행된다. 종류가 셋 다 걸리려면 한 격자가 축제와 코스와 팝업 미션에 동시에 속해야 해서 실질적인
상한은 2벌이다.

임박 알림 하루 1건 상한은 축이 늘어도 유지된다. `record`가 즉시 실행되는 native INSERT이고
`countRecordedSince`도 native SELECT라, 같은 트랜잭션의 두 번째 축은 첫 축이 방금 기록한 행을 본다.
advisory 잠금(`pg_try_advisory_xact_lock`)은 같은 트랜잭션에서 재획득이 성공하므로 두 번째 축이
자기 잠금에 막히는 일도 없다.

### D6. 그림 저장 위치와 주소 규칙

**환경 공용 정적 에셋 버킷 하나를 만들고 공개 읽기로 둔다.** 경로는 `badges/{code 소문자}.{확장자}`,
`icon_url`에는 절대 URL을 넣는다. 앱 코드 변경은 0줄이다.

영상 버킷(`S3_BUCKET_VIDEO`)에 `badges/` 프리픽스를 여는 방법은 기각한다. 이유 둘. 첫째, dev와
prod의 영상 버킷이 분리돼 있어(application.yml 107행 주석) 마이그레이션에 박은 절대 URL이 한쪽
환경에서 반드시 틀린다. 둘째, 사용자 영상이 들어 있는 버킷에 공개 읽기 정책을 여는 셈이라 얻는 것에
비해 위험이 크다. 뱃지 그림은 사용자 데이터가 아니라 dev와 prod가 동일해도 되는 정적 자산이므로
환경 분리 자체가 불필요하다.

상대 경로만 저장하고 서버가 응답 시 base URL을 조립하는 방법도 기각한다. `iconUrl`을 담는 DTO가
셋(목록, 획득, 대표)이라 조립 지점이 셋으로 늘고 설정값도 하나 늘어나는데, 정작 환경별로 달라야 할
값이 없다.

파일명이 뱃지 code의 소문자라는 규칙 덕분에 V31은 UPDATE 한 문장으로 끝나고 새 뱃지를 추가할
때마다 주소를 손으로 적을 필요가 없다. 디자인에 넘길 산출물 규격은 "파일명 = 뱃지 code 소문자"
하나다.

파일명 제안: `V29__mission_type_badges.sql`

```sql
-- ============================================================================
-- FillMap V29: 미션 뱃지 종류별 재편 (MSG-363)
-- 1) condition_type CHECK 확장 (V9 1번 블록 복제)
-- 2) badges.retired_at 추가. 지급 후보에서만 빼고 획득 이력은 보존
-- 3) 종류별 뱃지 9종 시딩 (임계값 1, 3, 10)
-- 4) 합산 뱃지 3종 은퇴
-- 5) 소급 지급 (V9 4번 블록 패턴, ON CONFLICT 멱등)
-- V1~V28 무수정(checksum).
-- ============================================================================

-- 1) CHECK 확장
ALTER TABLE badges DROP CONSTRAINT chk_badges_condition;
ALTER TABLE badges ADD CONSTRAINT chk_badges_condition CHECK (condition_type IN
	('REGION_PERCENT', 'TOTAL_GRIDS', 'STREAK_DAYS', 'UPLOAD_COUNT', 'MISSION_COUNT',
	 'EVENT_COUNT', 'COURSE_COUNT', 'POPUP_COUNT', 'SPECIAL'));

-- 2) 은퇴 표시 (NULL = 현역). 판정 쿼리 3개가 이 컬럼으로 후보를 거른다
ALTER TABLE badges ADD COLUMN retired_at TIMESTAMP;

-- 3) 시딩. 목록 순서 = badges.id 오름차순이라 축 단위로 티어 오름차순 삽입 (MSG-201 D6)
INSERT INTO badges (code, name, description, condition_type, condition_value) VALUES
	('EVENT_1',   '축제 입문',   '축제 1곳을 다녀왔어요',    'EVENT_COUNT',  '{"value": 1}'),
	('EVENT_3',   '축제 단골',   '축제 3곳을 다녀왔어요',    'EVENT_COUNT',  '{"value": 3}'),
	('EVENT_10',  '축제 마스터', '축제 10곳을 다녀왔어요',   'EVENT_COUNT',  '{"value": 10}'),
	('COURSE_1',  '코스 입문',   '코스 1개를 기록했어요',    'COURSE_COUNT', '{"value": 1}'),
	('COURSE_3',  '코스 단골',   '코스 3개를 기록했어요',    'COURSE_COUNT', '{"value": 3}'),
	('COURSE_10', '코스 마스터', '코스 10개를 기록했어요',   'COURSE_COUNT', '{"value": 10}'),
	('POPUP_1',   '팝업 입문',   '팝업 1곳을 다녀왔어요',    'POPUP_COUNT',  '{"value": 1}'),
	('POPUP_3',   '팝업 단골',   '팝업 3곳을 다녀왔어요',    'POPUP_COUNT',  '{"value": 3}'),
	('POPUP_10',  '팝업 마스터', '팝업 10곳을 다녀왔어요',   'POPUP_COUNT',  '{"value": 10}')
ON CONFLICT (code) DO NOTHING;

-- 4) 합산 뱃지 은퇴. DELETE 금지: user_badges FK 가 막고, 지워지면 획득 이력이 사라진다(FR-4).
--    AT TIME ZONE 'UTC' 는 저장 규칙 통일용 (MSG-314 D4). 이 값은 NULL 여부로만 읽는다.
UPDATE badges
SET retired_at = now() AT TIME ZONE 'UTC'
WHERE code IN ('MISSION_1', 'MISSION_5', 'MISSION_10')
  AND retired_at IS NULL;

-- 5) 소급 지급 (FR-5). notified_at 미기재 = NULL = 다음 조회에서 "새 뱃지" 표시 (V9 4번 블록과 동일).
--    b.condition_type = m.type || '_COUNT' 가 유형에서 축으로 가는 명명 규칙 그 자체라 축마다
--    블록을 복제하지 않는다. AREA, THEME, CONTINUOUS 는 WHERE 에서 빠져 대상이 아니다(FR-6).
INSERT INTO user_badges (user_id, badge_id)
SELECT m.user_id, b.id
FROM (
	SELECT um.user_id, mi.type, COUNT(*) AS metric
	FROM user_missions um
	JOIN missions mi ON mi.id = um.mission_id
	WHERE mi.type IN ('EVENT', 'COURSE', 'POPUP')
	GROUP BY um.user_id, mi.type
) m
JOIN badges b ON b.condition_type = m.type || '_COUNT'
	AND (b.condition_value->>'value')::numeric <= m.metric
ON CONFLICT DO NOTHING;
```

기존 스탬프 이력(`user_missions`)은 비회수라 단조 증가하므로, 소급 결과가 이후 실시간 판정 결과와
어긋나지 않는다.

### 런타임 동작 기록

**데이터 저장 위치**

- `badges.retired_at TIMESTAMP` (V29). NULL이 현역이고, 값은 `NULL 여부`로만 읽는다. 엔티티에
  매핑하지 않았다(판정이 전부 native, 부분 매핑 관례, `ddl-auto=validate`는 미매핑 컬럼을
  문제 삼지 않음). 실측 컬럼 타입 `timestamp without time zone`.
- 종류별 뱃지 9행. **로컬 실측 id는 470~478이다.** 테스트가 같은 DB를 쓰면서 시퀀스를 소모한
  결과이고, 새 환경에서는 18~26이 된다. 목록 정렬이 `badges.id ASC`라 어느 쪽이든 축 단위
  티어 오름차순(EVENT 1·3·10 → COURSE → POPUP)은 유지된다.
- 은퇴 3행은 `MISSION_1`(id 33) · `MISSION_5`(34) · `MISSION_10`(35). id가 종류별 뱃지보다
  앞이라 획득자 목록에서는 이들이 위에 온다.
- 소급 지급분은 `user_badges`에 INSERT되고 `notified_at`을 채우지 않는다. 다음 목록 조회에서
  `isNew`로 뜬다. 로컬은 스탬프 0건이라 소급 0행이었다.
- `videos.visibility` DEFAULT (V30). 적용 후 실측 `column_default = 'PUBLIC'::character varying`.
  기존 행은 무변경이다(롤백 트랜잭션 안에서 PRIVATE 행을 넣고 `SET DEFAULT` 후에도 PRIVATE로
  남는 것, 이어서 컬럼을 생략한 INSERT가 PUBLIC으로 들어가는 것을 확인).

**실행 쿼리**

- `findEligible`과 `findNearMiss`: `WHERE b.condition_type = :type` 뒤에 `AND b.retired_at IS NULL`
  한 줄씩. 판정식(`(condition_value->>'value')::numeric` 비교)은 그대로다.
- `findAllWithMyStatus`: 원래 WHERE가 없던 쿼리에 `WHERE b.retired_at IS NULL OR ub.user_id IS NOT NULL`.
  LEFT JOIN 뒤 WHERE에서 오른쪽 테이블 컬럼을 참조하지만 **OR의 좌항이 왼쪽 테이블만 참조해서
  outer join이 inner로 강등되지 않는다.** 조인 미매치 행(`ub.* = NULL`)도 현역이면 살아남는다.
- `countMyStampsByType` (native, 신규):
  `SELECT COUNT(*)::numeric FROM user_missions um JOIN missions m ON m.id = um.mission_id WHERE um.user_id = :userId AND m.type = :type`.
  `user_missions` PK(user_id, mission_id) prefix와 `missions` PK로 해결돼 추가 인덱스가 없다.
- `findCompleted`: `HAVING` 뒤에 `ORDER BY m.id` 추가.
- V29 소급 SQL의 축 조인: `JOIN badges b ON b.condition_type = m.type || '_COUNT'`. 유형에서
  축으로 가는 명명 규칙 자체를 조인 조건으로 써서 축마다 블록을 복제하지 않는다. AREA·THEME·
  CONTINUOUS는 서브쿼리 `WHERE mi.type IN (...)`에서 1차로, 대응 뱃지 부재로 2차로 배제된다.
  `ON CONFLICT DO NOTHING`이 덮는 제약은 `user_badges` PK(user_id, badge_id)다.

**예외 흐름**

신규 없음. 새 에러 코드도 새 API도 없다. 매핑에 없는 미션 유형(AREA·THEME·CONTINUOUS)은
예외가 아니라 `continue`로 건너뛰는 정상 경로다(FR-6). `MissionType.valueOf`를 쓰지 않은
이유가 이것이다. `Map.of().get(null)`은 NPE를 던지지만 `missions.type`이 NOT NULL이라
`getType()`이 null일 수 없어 도달하지 않는다.
