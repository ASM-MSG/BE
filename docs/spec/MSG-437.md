# MSG-437: 팝업·축제 핀 줌아웃 묶음을 행정 단위 집계로 전환

**Owner**: B (`com.msg.fillmap.mission`. Owner A 코드는 고치지 않고 계약 타입만 소비한다, 아래 "계약 변경" 참조)

> PRD 정본: `docs/prd/mission-map-explore.md` §3 FR-21(개정)·FR-29(신설), §8 "2026-08-20 추가 (정민 확정)"
> SRS: FR-MISSION-20(신설, 계획), FR-MISSION-15(갱신)

## 개요

지도를 축소해 보면 팝업스토어와 지역축제 미션 핀을 도감 격자 집계(MSG-356)와 같은 행정 단위(동, 구, 시)로 묶어 지역 이름과 개수로 보여준다. 이 티켓은 그 묶음을 계산해 내려주는 서버 몫이다. 신설 엔드포인트 `GET /api/missions/aggregation` 하나가 산출물이고, 계산은 기존 1시간 전역 스냅숏[^1] 위 메모리 집계다. 코스는 불변(1km 화면 묶음과 줌별 표시 유지)이고 FE·모바일 렌더링은 별도 레인이다.

## 배경 · 목표

거리 기준(500m)으로 핀을 묶으면 묶음에 이름이 없어 "핀 3개" 이상을 말하지 못한다. 행정 단위로 묶으면 "해운대구 12"처럼 지역 이름이 붙어 축소 화면에서도 정보가 된다(2026-08-20 정민 확정, 2026-08-15 "화면이 묶는다" 확정의 팝업·축제 부분 번복). 결정적으로 개별 목록 조회(MSG-398)는 뷰포트[^2] 한 변 0.5도 상한이 있어 시 단위 축척에서는 조회 자체가 성립하지 않는다. 도감이 같은 문제를 집계 조회(`/api/grids/aggregation`, MSG-356)로 푼 것과 같은 구조로 미션에도 넓은 축척용 집계 조회를 신설한다.

## 성공 기준

- 시 단위 축척(0.5도 초과)의 넓은 bbox에서도 팝업·축제의 행정 단위 묶음이 200으로 조회된다 (FR-MISSION-20)
- 묶음 항목마다 지역 이름, 개수, 마커를 찍을 대표 좌표, 목록을 좁힐 미션 id 목록이 온다 (FR-21)
- 단위(동, 구, 시)를 무엇으로 묶어도 응답이 호출 사용자와 무관하다 (FR-MISSION-02)
- 축척별 단위 전환의 코드 접두 길이와 이름 토큰 규칙이 도감 집계와 동일해, 같은 화면의 도감 마커와 미션 마커가 지역 이름에서 갈리지 않는다
- 아래 "테스트 시나리오"가 전부 green이다

## API 명세

### GET /api/missions/aggregation (신설)

넓은 축척용 미션 행정 단위 집계. 인증 필수(SecurityConfig anyRequest)지만 principal을 받지 않는다. 응답이 사용자 무관이어야 전역 캐시가 성립하고(FR-MISSION-02), principal을 안 받는 것이 그 계약의 코드 수준 방어다(`getActiveMissionsInViewport` 동일 패턴).

**Query 파라미터** (전부 필수, `required = false`로 받아 컨트롤러가 도메인 에러코드로 검증하는 기존 `toBounds`·`toType` 패턴 유지):

| 이름 | 타입 | 의미 |
|---|---|---|
| `type` | String | 미션 종류. EVENT와 POPUP만 허용, 대소문자 무관. 칩이 한 종류만 고르므로 필수다 |
| `unit` | String | 집계 단위. DONG, SIGUNGU, SIDO. 대소문자 무관 (`RegionUnit` 재사용) |
| `swLat` `swLng` `neLat` `neLng` | Double | 남서·북동 모서리 좌표 |

**검증 우선순위** (복합 오류 시 앞선 검사의 코드가 나간다):

1. bbox 파라미터 누락 → 12400
2. type 누락·미지원 → 12402
3. unit 누락·미지원 → 12405
4. 좌표가 WGS84 정의역 밖이거나 NaN → 12400
5. 뒤집힌 bbox (sw가 ne보다 북·동쪽) → 12400
6. bbox 한 변이 단위별 span 상한 초과 → 12401

**성공 응답**: `SuccessResponse<List<MissionRegionAggregateResponseDto>>`. 항목은 regionCode 오름차순, 무귀속(null) 항목이 있으면 마지막(MSG-356 `ORDER BY 1 NULLS LAST`와 동일). 범위 안에 미션이 없으면 빈 배열이다(오류 아님).

**에러 케이스**:

| 상황 | HTTP | developCode |
|---|---|---|
| bbox 파라미터 누락, WGS84 정의역 밖, NaN, 뒤집힌 bbox | 400 | 12400 `INVALID_VIEWPORT` |
| bbox 한 변이 단위별 상한 초과 (DONG 1도, SIGUNGU 4도, SIDO 10도. `RegionUnit.maxSpanDeg` 재사용, 정확히 상한값은 허용) | 400 | 12401 `VIEWPORT_TOO_LARGE` |
| type 누락, 미지원 값, COURSE·AREA·THEME·CONTINUOUS | 400 | 12402 `INVALID_MISSION_TYPE` |
| unit 누락, 미지원 값 | 400 | 12405 `INVALID_AGGREGATION_UNIT` (신설) |

12405는 grid의 4405와 상수명·끝자리를 나란히 맞춘다(MissionErrorCode 기존 방침). 12xxx 대역은 이미 mission에 배정돼 있어 response-pattern 표 갱신은 없다.

### 응답 DTO (신설)

```java
// mission/dto/MissionRegionAggregateResponseDto.java
public record MissionRegionAggregateResponseDto(
	String regionCode,      // 묶음 키. 행정동 코드를 단위 길이로 자른 접두[^3] (동 10, 구 5, 시 2자리). 무귀속만 null
	String name,            // 단위 표시 이름 (동 "부전2동", 구 "부산진구", 시 "부산광역시"). 무귀속만 null
	double lat,             // 마커 대표 좌표 위도. 묶음에 속한 미션 귀속점의 평균이라 마커가 실제 데이터 위에 선다
	double lng,
	int count,              // 그 단위 안 미션 수
	List<Long> missionIds   // 그 묶음의 미션 id, 오름차순. 크기는 count와 같다 (D5)
) { }
```

`grid/dto/RegionAggregateResponseDto`를 재사용하지 않는 이유: count의 뜻이 다르고(점령 격자 수 대 미션 수) missionIds 필드가 미션 전용이라, Owner A DTO에 미션 사정을 심는 것보다 mission 패키지 신설이 경계에 맞다(D4). 도감 집계의 겉면 `{currentRegion, items}`(MSG-374)도 가져오지 않는다. currentRegion은 도감 헤더 전용 재료라 미션 화면에 쓸 곳이 없다.

## 도메인 로직

### D-결정

**D1. 행정 귀속은 스냅숏 재계산 시 중심점 1점 판정으로 한다. 컬럼 신설, Flyway 마이그레이션, 시더 수정 전부 없음.**

미션의 귀속점은 판정 격자 사각형(mission_grids min/max 정수 사각형, 스냅숏이 이미 계산하는 `gridBounds`)의 중앙 셀 인덱스 `((minY+maxY)/2, (minX+maxX)/2)`의 중심 위경도다(`GridEncoder.center`). 스냅숏 재계산(`recompute`) 때 EVENT·POPUP 미션마다 Owner A 계약 `RegionQueryService.resolveByPoint(lat, lon)`(역지오코딩[^4], GIST 인덱스[^5] 점 판정)를 불러 행정동 코드(10자리)와 전체 경로 이름("부산광역시 부산진구 부전2동")을 얻고 `CachedMission`에 함께 싣는다.

기각한 대안과 이유:
- **시더 적재 시 저장(missions에 컬럼 신설, grids.region_code 선례)**: 기존 715건(dev 축제 222, 팝업 227, 코스 148, 활성 외 포함)의 백필 마이그레이션이 필요하고, 팝가에서 내려간 레거시 팝업은 원좌표가 소실돼(MSG-385 D4) 시더가 다시 못 채우는 행이 남는다. 또 축제 소스의 TourAPI 전환(자연키 교체)이 예정돼 있어 시더에 귀속 로직을 넣으면 그 전환 티켓과 경합한다. 스냅숏 판정은 mission_grids에서 파생하므로 소스 전환과 레거시에 자동 추종한다.
- **조회 시 공간 판정(SQL GROUP BY)**: 목록 조회가 이미 스냅숏 위 메모리 필터라(FR-MISSION-02의 캐시 전제) 집계만 DB로 가면 같은 시각의 목록과 집계가 다른 데이터를 볼 수 있고, 요청마다 공간 판정 비용을 낸다. 재료가 수백 건이라 SQL이 필요한 규모도 아니다.

축제(9×9, 900m)의 경계 걸침 방침: **중심 1점 귀속으로 통일한다.** 사각형이 두 동에 걸쳐도 중심이 속한 동 하나로만 센다. 한 미션을 두 동에 이중 계상하면 묶음 개수의 합이 미션 수와 어긋나고, 도감 집계도 격자 중심점 판정 하나로 귀속하는 같은 규칙이다. 팝업(1~4칸)은 중심 1점이 자연스럽다.

**판정 실패의 분류 (Codex P1-1 반영).** 무귀속으로 수용하는 경우는 정확히 둘이다: `resolveByPoint`가 빈 결과를 돌려주는 경우(포함 행정동 없음)와, 좌표가 서비스 범위 밖이라 `RegionErrorCode.INVALID_COORDINATE`(6400) ApiException이 나는 경우다. 둘 다 그 미션만 regionCode null로 싣고 warn 로그를 남긴다(데이터 성질의 실패라 다시 물어도 같다). **그 외 예외(DB 연결 장애 같은 인프라 런타임 예외)는 흡수하지 않고 전파해 재계산을 실패시킨다.** 일괄 흡수하면 DB 장애 한 번에 전 미션이 무귀속으로 뭉개진 스냅숏이 만들어져 1시간 캐시되는 사고가 난다. 재계산이 실패하면 스냅숏 필드를 갱신하지 않으므로 뭉개진 세대가 발행되지 않고, 그 요청은 실패하며 다음 요청이 재시도한다. **전파의 범위는 스냅숏 전체이고 이는 의도다** (구현 Codex 리뷰 P2 확정, 2026-08-20): 스냅숏은 목록과 집계가 공유하므로 재계산 실패 시 COURSE 목록 조회처럼 귀속과 무관한 경로도 함께 실패한다. regions만 죽고 missions는 사는 부분 장애는 같은 DB라 시나리오가 협소하고, 캐시를 경로별로 분리하면 목록과 집계가 서로 다른 세대를 보는 불일치가 생기며, 기존에도 findActive 실패는 목록 요청을 실패시켰다(같은 결의 의미론). 회귀 테스트가 이 의미를 고정한다. 격자가 하나도 없는 미션(사각형 null)은 개별 조회와 똑같이 집계에도 안 실린다.

**귀속 판정 메모이즈 (Codex P1-3 반영).** 판정 결과를 미션 id와 판정 사각형(gridBounds)을 키로 재계산 세대 간 재사용한다. 재계산은 직전 세대 `CacheEntry`의 미션별 (사각형, 귀속 결과)를 대조해, 사각형이 같은 미션은 역지오코딩을 다시 부르지 않고 값만 옮겨 싣는다. 미션 데이터는 수동 시딩이라 사각형이 바뀌는 일 자체가 드물어, 정상 상태의 시간당 추가 쿼리는 신규·변경 미션 수 건으로 떨어진다. 콜드 첫 웜업(프로세스 기동 후 첫 재계산)만 활성 EVENT·POPUP 전량(현재 약 260건)의 point 쿼리를 낸다. 각각 GIST 점 프로브라 밀리초 수준이지만 refreshLock 안 순차 실행이므로, **콜드 첫 요청의 응답 시간 실측(PRD §4의 300ms 목표 대비)을 구현 단계 확인 항목으로 남긴다.** 미션 수가 수천 건 규모가 되면 unnest 배치 쿼리로 승격한다.

**D2. 집계 계산은 스냅숏 메모리에서 한다.**

요청 처리: type 필터 → 귀속점이 bbox 안인 미션 선별 → regionCode를 `RegionUnit.codePrefixLength`로 자른 접두를 키로 그룹핑 → 항목 조립. 이름은 전체 경로 이름의 `nameTokenIndex`번째 공백 토큰(동 3, 구 2, 시 1)이고 대표 좌표는 그룹 내 귀속점 평균, missionIds는 오름차순 정렬이다. 전부 산술이라 DB를 안 탄다(역지오코딩은 D1대로 재계산 시점에만, 메모이즈 덕에 정상 상태 수 건). 토큰 규칙과 토큰이 모자라는 이름의 동작은 MSG-356 `split_part`와 같게 맞춘다. 같은 화면에서 도감 마커와 지역 이름이 갈리지 않는 것이 우선이고, 검증 테스트는 3토큰 표준형만 고정한다.

**D3. bbox 포함 판정은 귀속점 기준이다.** 미션 사각형과 뷰포트의 교차(개별 조회 `intersects`)가 아니라 귀속점 위경도가 bbox 안인지(경계 포함)를 본다. 마커가 찍히는 자리(귀속점 평균)와 세는 기준이 같아야 화면 밖 데이터가 화면 안 마커로 세어지지 않는다. 위경도 직접 비교라 투영 보정(PROJECTION_PAD_CELLS)도 종류별 마진도 안 쓴다. 대가: 사각형이 뷰포트에 걸쳤지만 중심이 밖인 경계 미션 한둘이 개별 조회와 어긋날 수 있다. FE가 개별과 집계를 갈아타는 순간 마커 수가 미세하게 변할 수 있고 이는 수용한다(도감과 달리 "합이 개별 총수와 일치"가 미션의 FR이 아니다).

**D4. 응답 DTO는 미션용 신설.** 근거는 위 "응답 DTO" 참조.

**D5. 묶음 선택 시 목록 좁힘 재료는 집계 항목의 missionIds 동봉이고, 좁힘의 제품 계약은 "줌인 후 교집합"이다** (PRD §9 미해결 1건을 이 스펙이 결정, Codex P1-2 반영).

**제품 계약**: 묶음 마커 선택은 다음 세부 단위 축척으로의 줌인이다(도감 집계 마커의 확정 동작과 동일, MSG-428). 목록 좁힘은 줌인을 거듭해 개별 조회(0.5도 상한)가 성립하는 축척에 들어온 뒤, 그 개별 조회 결과와 선택했던 묶음의 missionIds의 교집합으로 완결된다. **시·구 축척에서 줌인 없이 묶음 전체의 카드 목록을 띄우는 화면은 이 계약 밖이다.** missionIds만으로는 카드를 그릴 수 없고(카드 재료는 개별 조회 응답에 있다) 그런 요구가 생기면 미션 ID 벌크 조회 티켓을 별도로 판다. 이 계약이 서 있어서 벌크 조회 엔드포인트를 지금 만들지 않는다.

기각한 대안: 화면이 그 지역 범위로 재조회만 하는 방식. 시·구 축척에서는 재조회(개별 조회) 자체가 0.5도 상한에 걸릴 수 있고, 성립하는 축척에서도 뷰포트는 행정 경계와 달라 인접 지역 미션이 섞인다. 동봉하면 교집합으로 정확히 그 미션들만 남는다. 서버 비용은 스냅숏에 이미 있는 id를 싣는 것뿐이다.

**크기와 시점의 의미 (Codex P2-2 반영)**: 전 항목 id 합계의 자연 상한은 그 뷰포트의 활성 미션 전량이다. 현재 약 449는 관찰값이지 구조적 상한이 아니며, 활성 미션이 수천 건 규모에 이르면 D1의 배치 승격과 함께 응답 계약(페이징이나 ID 목록 제거)을 별도 티켓으로 재논의한다. missionIds는 1시간 스냅숏 세대의 값이라 이후의 개별 조회와 세대가 어긋날 수 있다(그 사이 미션 만료 등). 좁힘이 교집합 방식이라 이 어긋남은 안전하다. 개별 조회에서 사라진 id는 교집합에서 자연 탈락하고, 유령 카드가 생기지 않는다.

**D6. 개별 조회와 집계의 전환 시점은 서버가 정하지 않는다.** MSG-356과 동일하게 클라이언트가 화면 축척에 맞춰 unit만 바꿔 부르고, 서버 상한은 unit별 `maxSpanDeg`가 방어선이다. 개별 조회의 0.5도와 DONG 상한 1도 사이 겹침 구간에서 FE는 어느 쪽이든 부를 수 있고, 그 경계의 데이터 정합 특성은 D3에, 묶음 선택에서 개별 조회로 넘어가는 흐름은 D5의 제품 계약에 적었다.

### 캐시 구조 변경

`CachedMission` 레코드에 세 값이 는다: 귀속 행정동 코드(10자리, 무귀속 null), 전체 경로 이름(무귀속 null), 귀속점 위경도. COURSE와 나머지 유형은 집계 대상이 아니므로 귀속 판정을 건너뛰고 null로 둔다(재계산 쿼리를 EVENT·POPUP으로 한정). 재계산은 직전 세대 엔트리를 메모이즈 재료로 읽는다(D1). 그밖에 목록 조회 경로는 새 필드를 안 읽으므로 동작 불변이다.

`MissionQueryService` 인터페이스에 메서드 추가:

```java
List<MissionRegionAggregateResponseDto> getMissionAggregates(ViewportBounds bounds, MissionType type, RegionUnit unit);
```

## 미해결 질문

- **넓은 축척에서 좌측 목록의 상태** (확대 안내 유지 대 묶음 요약): FE·디자인 몫으로 PRD §9에 남아 있다. 서버는 이 스펙의 집계 응답으로 어느 쪽이든 성립한다
- **묶음 마커 색값**: 도감 집계 버블과 같은 패턴에 색만 다르게(정민 확정). 색값 자체는 FE·디자인 몫이고 서버는 색 정보를 내리지 않는다
- **토큰이 모자라는 행정동 이름**(두 토큰짜리 특별자치시 유형)의 표시: MSG-356과 동작을 같게 맞추는 것까지가 서버 몫이고, 표기 보정이 필요하면 도감과 함께 별도 티켓으로 다룬다

[^1]: 스냅숏: 활성 미션 전체를 1시간에 한 번 DB에서 읽어 메모리에 들고 있는 전역 캐시. 모든 사용자에게 같은 응답이라 한 벌만 유지하며, 뷰포트 자르기와 이번 집계는 이 위에서 산술로 처리한다.
[^2]: 뷰포트: 지도에서 지금 화면에 보이는 경위도 범위. 남서·북동 두 모서리 좌표(bbox)로 표현한다.
[^3]: 접두: 행정동 코드(10자리)의 앞자리가 상위 행정 단위를 가리키는 체계. 앞 2자리가 시도, 5자리가 시군구라서 매핑 테이블 없이 자르는 길이만으로 묶음 키가 나온다.
[^4]: 역지오코딩: 좌표를 넣으면 그 점을 포함하는 행정동을 돌려주는 판정. 이 프로젝트에서는 regions 테이블의 경계 폴리곤에 점 포함 여부를 물어 구현돼 있다(MSG-93).
[^5]: GIST 인덱스: PostGIS가 공간 데이터에 쓰는 인덱스. 점이 어느 폴리곤 안에 있는지를 전체 테이블을 훑지 않고 찾게 해 줘서, 점 하나의 행정동 판정이 밀리초 수준이다.
