# MSG-615: 이미 720p H.264인 영상은 다시 인코딩하지 않고 컨테이너만 바꿔 재생 대기를 줄인다

> PRD 면제: 요구사항 불변. NFR-PERF-08(docs/srs.md) 달성용 성능 개선, 실측 근거 docs/reports/2026-09-30-video-pipeline-scaling.md (MSG-609 브랜치 ddeb5e2f, 머지 전)

**Owner**: B (video 패키지, `com.msg.fillmap.video.*`)

- **상위 요구사항**: NFR-PERF-08(달성 대상), FR-MEDIA-01, FR-MEDIA-03(두 경로 모두 불변 유지)
- **짝 티켓**: MSG-616(앱이 업로드 전에 720p로 줄여 보낸다, 이 스펙의 비스코프)
- **요구사항 정본**: 지라 MSG-615 본문. 실측 보고서와 증빙(`load-test/evidence/2026-09-30/encoding-scale.json`)은
  브랜치 `feature/MSG-609-cloud-load-test`(커밋 ddeb5e2f)에 있고 아직 develop에 머지되지 않았다

## 개요

인코딩 워커가 원본을 받은 뒤 ffprobe로 스트림을 한 번 더 읽어, 영상이 이미 H.264 8비트 4:2:0이고
프레임이 1280×720 안에 들어가며 소리가 AAC이거나 없으면 `ffmpeg -c copy`로 컨테이너만 mp4로 다시
포장한다(remux[^1]). 조건에 하나라도 어긋나면 지금의 `encode720p`(libx264 veryfast crf 23)를 그대로
탄다. 분기는 `VideoEncodingServiceImpl.encode`의 ffmpeg 호출 한 곳이고, 길이 검증, 길이 실측 저장,
썸네일, 상태 전이, 하이라이트, 블러 경로는 손대지 않는다.

## 배경과 목표

지금은 어떤 영상이 와도 `FfmpegRunner.encode720p`가 처음부터 다시 인코딩한다. t3.small에서 이 단계가
재생 시간의 약 1배라 29초 영상이면 혼자 올려도 21~33초를 기다리고, 인코딩 슬롯이 노드당 1개라
동시 업로드는 줄을 선다(2026-09-30 실측 동시 12건에서 마지막 사용자 193초,
`docs/reports/2026-09-30-video-pipeline-scaling.md`, MSG-609 브랜치 ddeb5e2f, 머지 전). 짝 티켓
MSG-616이 앱에서 720p로 줄여 보내면 서버가 할 일은 포장뿐이고, 그러면 1초 안에 끝난다.

목표는 "이미 재생 규격에 맞는 입력은 ffmpeg 처리가 3초 안에 끝난다"이고, 규격 밖 입력(1080p, HEVC,
다른 코덱)의 결과물과 처리 흐름은 지금과 같아야 한다.

### 산출물을 누가 쓰는가

- **썸네일**: 105줄이 `original`을 입력으로 쓴다. remux든 encode든 썸네일은 영향 없다. 블러 켜짐 환경은
  `AiBlurPoller.runThumbnail`(285~299줄)이 블러본에서 다시 뽑는다
- **하이라이트(블러 꺼짐)**: 136줄 `submitHighlightJob(videoId, originalKey, encodedKey)` → 193~206줄
  `computeAndRecordHighlights`가 **S3의 `encodedKey` 객체**를 내려받아 `AiClient.analyzeHighlights`에 넘긴다.
  remux 경로에서는 그 객체가 remux 산출물이다. AI 서버가 받는 것은 어느 경로든 H.264 720p 이하 mp4다
- **블러(블러 켜짐)**: `AiBlurPoller.submit`(126~135줄)이 `video.getEncodedUrl()` 객체를 내려받아 제출한다.
  같은 이유로 입력 규격이 바뀌지 않는다
- **업로드 확정의 파일 형식 검사**: `VideoServiceImpl` 882줄 `VideoSignature.looksLikeVideoContainer`가
  확정 시점에 ISO BMFF 최상위 박스 체인을 검사한다(MSG-392). 인코딩 작업은 이 검사를 통과한 뒤
  `enqueue`(270, 318줄)된다. 따라서 워커에 오는 원본은 항상 mov 또는 mp4 계열이고, remux의 입력
  컨테이너가 MKV나 TS일 일은 없다

## 성공 기준

- AC-615-01: `FfmpegRunner.isRemuxable(String ffprobeJson)`이 D2의 규칙대로 참/거짓을 돌려준다. 참 케이스(720p H.264 yuv420p AAC, 오디오 없음, 1280×720 회전 90, 720×1280 세로 코딩, iPhone mov의 데이터 트랙 동반)와 거짓 케이스(1080p, HEVC, yuv420p10le, PCM 오디오, 비디오 스트림 없음)가 단위 테스트로 고정된다.
- AC-615-02: remux 가능한 입력에서 `encode720p`가 호출되지 않고 `remux`만 호출되며, 결과는 `markReady`(또는 블러 켜짐이면 `markEncoded`)에 같은 `encodedKey`로 실린다.
- AC-615-03: remux 불가 입력은 지금과 같은 `encode720p` 경로를 타고, 기존 `VideoEncodingServiceTest`, `VideoEncodingAiTriggerTest`, `VideoEncodingDurationRealFfmpegTest`, `FfmpegRunnerTest`가 수정 없이(목 기본값 false) 통과한다.
- AC-615-04: remux 실행이 예외로 끝나면 `encode720p`로 정확히 한 번 폴백하고, 폴백도 실패하면 기존 예외 처리(InvalidMedia면 FAILED, 그 밖은 재시도)가 그대로 적용된다.
- AC-615-05: 길이 31초 초과 판정, 실측 길이 클램프 저장, 썸네일 추출(원본 입력), 업로드 직전 fresh 재확인은 두 경로 모두 지금과 같은 순서와 입력으로 수행된다. 특히 31초 초과 입력은 remux 판정 probe 자체를 돌리지 않는다.
- AC-615-06: dev 실측에서 720p H.264/AAC 10초 샘플은 `ffmpegMs` 3,000 미만이고 `ready_ms`(확정부터 READY까지) 3,000 미만이다. 1080p H.264 샘플과 HEVC 샘플은 로그에 `path=encode`가 남고 READY가 된다. 회전 90 샘플은 remux 산출물의 ffprobe에 회전 정보가 그대로 있고 앱에서 세로로 재생된다.
- AC-615-07: 어느 경로를 탔는지 `인코딩 완료` 로그 한 줄에 `path`와 `ffmpegMs`가 남고, `/actuator/prometheus`에 `video_encoding_path_total{path="remux"|"encode"|"fallback"}`이 0값으로도 항상 노출된다.
- AC-615-08: 작업 로그에 D6의 경로별 실측 표(샘플 3종 이상, 열: 경로, ffprobe 판정, 처리 ms, ready_ms)가 채워진다.
- AC-615-09: 스트림 probe(`isRemuxable(Path)`)와 remux 실행은 둘 다 호출별 타임아웃 60초(`REMUX_TIMEOUT`)로 돈다. 한 작업의 ffmpeg 최악 예산은 10 + 10 + 10 + 1 + 1 = 32분이고 MSG-494 D5의 임대 35분(상수 불변)을 넘지 않는다.
- AC-615-10: 스트림 규격이 remux 조건에 맞아도 평균 비트레이트(파일 바이트 × 8 / 실측 길이)가 12 Mbps를 넘으면 `encode720p` 경로를 타고 `path=encode`가 남는다. 12 Mbps 이하는 remux한다 (PR #293 리뷰 반영).

## 결정

### D1. 분기는 `encode` 호출 한 곳이고 판정은 길이 검증 뒤에 둔다

`VideoEncodingServiceImpl` 100줄의 `encode720p` 호출을 아래로 바꾼다. 다른 줄은 그대로다.

```java
Path encoded = workDir.resolve("encoded.mp4");
Path thumbnail = workDir.resolve("thumb.jpg");
long ffmpegStarted = System.nanoTime();
String path = remuxOrEncode(videoId, original, encoded);   // "remux" | "encode" | "fallback"
long ffmpegMs = (System.nanoTime() - ffmpegStarted) / 1_000_000;
videoProcessingMetrics.countEncodingPath(path);
```

```java
/** remux 가능하면 copy, 아니면 기존 인코딩. remux 실행 실패는 인코딩으로 한 번만 폴백한다 (MSG-615 D4). */
private String remuxOrEncode(Long videoId, Path original, Path encoded) {
	if (!ffmpegRunner.isRemuxable(original)) {
		ffmpegRunner.encode720p(original, encoded);
		return "encode";
	}
	try {
		ffmpegRunner.remux(original, encoded);
		return "remux";
	} catch (RuntimeException e) {
		log.warn("remux 실패, 인코딩으로 폴백: videoId={}", videoId, e);
		ffmpegRunner.encode720p(original, encoded);
		return "fallback";
	}
}
```

순서를 `probeDurationSec` → 31초 판정 → 클램프 → **판정 probe** → remux/encode로 두는 이유: 31초 초과
입력은 지금처럼 probe 한 번으로 끝내야 한다(AC-615-05). 길이 probe와 스트림 probe를 한 호출로 합치는
안은 `probeDurationSec`의 호출자가 셋(인코딩, 블러 폴러, 선분석)이고 그 테스트들이 전부 이 메서드를
스텁하고 있어 손대는 범위가 커진다. ffprobe 한 번은 수십 ms라 합치지 않는다.

`isRemuxable(Path)` 자체가 던지는 예외(ffprobe 실행 실패)는 잡지 않고 그대로 올린다. 바로 앞 83줄에서
같은 파일에 같은 바이너리가 성공했으므로 여기서 실패하면 인프라 문제이고, 그 분류는 기존 147~155줄
(재시도)이 맡는다. 판정 실패를 "remux 불가"로 삼키면 인프라 장애가 느린 경로로 숨는다.

### D2. remux 판정 규칙

probe 명령은 기존 `run` 경로를 그대로 쓰되, 타임아웃은 인스턴스 기본값(10분)이 아니라 D3의
`REMUX_TIMEOUT`(60초)을 호출별 오버로드로 넘긴다. ffprobe는 헤더(moov)만 읽어 수 초 안에 끝나므로
10분은 과한 예산이고, 그 10분이 MSG-494 D5의 임대 35분 산술을 넘기게 만든다(D3 참조).
`-show_streams`[^2]의 JSON 출력을 읽는다.

```text
ffprobe -v error -show_streams -of json <input>
```

JSON의 `streams[]`에서 읽는 필드와 규칙:

| 대상 | 읽는 필드 | 조건 |
|---|---|---|
| 비디오 | `codec_type == "video"`인 **첫 스트림** (ffmpeg의 `0:v:0`과 같은 선택) | 없으면 거짓 |
| 비디오 코덱 | `codec_name` | `"h264"` |
| 픽셀 포맷 | `pix_fmt` | `"yuv420p"` 또는 `"yuvj420p"` |
| 프레임 크기 | `width`, `height` | `min(width, height) <= 720 && max(width, height) <= 1280` |
| 오디오 | `codec_type == "audio"`인 첫 스트림 | 없으면 통과, 있으면 `codec_name == "aac"` |
| 그 밖의 스트림 | `data`, `subtitle`, `attachment` | 무시 (D3의 `-map`이 싣지 않는다) |
| 평균 비트레이트 | 파일 바이트 × 8 / 실측 길이 (서비스 계산, ffprobe 필드 아님) | `<= 12 Mbps` |

**평균 비트레이트 상한 12 Mbps(PR #293 리뷰 반영, 2026-10-03 사용자 결정).** remux는 원본 비트레이트를 그대로
서빙하므로 스트림 규격만 보면 화면 녹화·액션캠의 20~27 Mbps 720p가 인코딩 없이 나간다. 업로드 상한 100MB × 31초의
물리 상한이 27 Mbps다. 기존 crf 23 인코딩은 2~5 Mbps로 수렴시키던 입력이라 동작 변화이고, 아이폰 기본 720p30이
약 8 Mbps라 12 Mbps는 폰 촬영본(MSG-616 산출물 포함)을 통과시키면서 그 위를 encode로 보내는 선이다. 판정은
`VideoEncodingServiceImpl`이 실제 파일 바이트와 이미 probe한 실측 길이로 계산한다(ffprobe `bit_rate`는 컨테이너에
따라 비고, 서빙되는 바이트가 정확하다). `isRemuxable(String)` 순수 함수는 스트림 규격만 본다.

**회전 메타데이터는 읽지 않는다.** ffprobe의 `width`/`height`는 회전 적용 전의 코딩 크기다. 세로 촬영
1280×720(rotate 90)은 `height=720`이지만 표시 높이는 1280이고, 앱이나 다른 인코더가 세로 그대로 코딩한
720×1280은 `height=1280`이다. 둘 다 픽셀 수는 가로 1280×720과 같고, 720p 변환(MSG-65 D4)이 막으려는 것은
픽셀 수와 비트레이트 예산이지 방향이 아니다. 그래서 규칙을 "짧은 변 720 이하, 긴 변 1280 이하"로 두면
`side_data_list[].rotation`이든 `tags.rotate`든 값과 무관하게 같은 판정이 나온다. 티켓 문구 "세로 720
이하"는 이 뜻(방향 무관 720p)으로 확정됐다(2026-10-03 코디네이터 확정). 근거: 짝 티켓 MSG-616이 폰
세로 촬영본을 720p로 뽑으면 720×1280 세로 코딩이 나오는데, `height <= 720`으로 좁히면 그 산출물
전부가 인코딩 경로로 떨어져 짝 티켓 효과가 사라진다. "세로 720"은 세로 폰 영상 기준의 표현이다.

회전 정보 보존은 remux 명령 쪽 문제다. `-c copy`는 스트림 side data(Display Matrix[^6])를 mp4 트랙
헤더로 그대로 옮기므로 플레이어가 지금과 같이 세로로 그린다. 구현 단계 실측(AC-615-06)에서 산출물
ffprobe로 확인하고, 보존이 안 되는 ffmpeg 버전이 dev에 있다면 폴백이 아니라 명령을 고친다
(`-metadata:s:v rotate` 보강). 참고로 기존 `encode720p`는 ffmpeg autorotate가 먼저 돌아 세로 720×1280
입력을 `scale=-2:720`으로 406×720까지 줄인다. remux는 720×1280을 그대로 둔다. 둘 다 720p 정책 안이고
remux 쪽이 더 선명하므로 회귀가 아니며, 인코딩 경로의 세로 축소는 preset 변경에 해당해 이 티켓
비스코프다.

**픽셀 포맷[^5]과 프로파일.** H.264지만 모바일 하드웨어 디코더가 못 푸는 경우가 있다. High 10(10비트),
High 4:2:2, High 4:4:4 프로파일이 그것인데, 이들은 `pix_fmt`가 `yuv420p10le`, `yuv422p`, `yuv444p` 등으로
항상 8비트 4:2:0이 아니다. 따라서 `pix_fmt` 하나로 프로파일 문제까지 걸러진다. `profile` 문자열을 따로
비교하지 않는다(ffmpeg 버전마다 표기가 달라 목록이 낡는다). `yuvj420p`는 full range 4:2:0이라 디코더
문제가 없어 허용한다. level은 보지 않는다. 1280×720 안에서는 120fps 슬로모션도 level 4.2 아래이고
모바일 디코더는 5.1까지 푼다. fps 상한도 두지 않는다. 높은 fps의 비용은 비트레이트로 나타나고 위 상한이 잡는다.

**오디오.** AAC가 아닌 오디오(PCM, Opus, MP3)는 거짓이다. 비디오만 copy하고 오디오만 변환하는 혼합
경로는 만들지 않는다(필요해지면 그때 `-c:v copy -c:a aac`로 한 줄 추가). 오디오 스트림이 둘 이상이면
첫 번째만 본다. D3가 첫 번째만 싣는다.

판정 함수는 순수 함수로 분리한다. 테스트가 ffprobe 출력을 고정 JSON 문자열로 넣을 수 있어야 해서다.

```java
/** 원본을 probe 해 remux 가능 여부를 판정한다 (MSG-615 D2). 타임아웃은 remux 와 같은 60초다 (D3). */
public boolean isRemuxable(Path input) {
	return isRemuxable(run(List.of("ffprobe", "-v", "error", "-show_streams", "-of", "json",
		input.toString()), REMUX_TIMEOUT));
}

/** ffprobe -show_streams JSON 으로만 판정한다. 테스트가 고정 JSON 을 넣는 진입점이라 public static 이다. */
public static boolean isRemuxable(String ffprobeJson) { ... }
```

JSON 파싱은 Jackson `JsonNode`로 한다(이미 classpath에 있고 `AiClient`가 쓴다). `FfmpegRunner`에
`private static final ObjectMapper`를 하나 둔다. 전역 UTC 코덱(`UtcLocalDateTimeJsonCodec`)은 시각
필드용이라 이 파싱과 무관하다. 파싱 실패(JSON 아님)는 `InvalidMediaException`으로 올린다.
`probeDurationSec`의 숫자 파싱 실패와 같은 분류다.

### D3. remux 명령

명령은 스트림 복사[^3]와 색인 전진 배치(faststart)[^4] 두 옵션으로 이뤄지고, 첫 비디오와 첫 오디오만
명시적으로 싣는다.

```text
ffmpeg -y -i <input> -map 0:v:0 -map 0:a:0? -c copy -movflags +faststart <output>.mp4
```

- `-map 0:v:0 -map 0:a:0?`: 첫 비디오와 첫 오디오만 싣는다. `?`는 오디오가 없어도 오류가 아니라는
  뜻이다. **iPhone mov는 `mebx` 타임드 메타데이터 트랙을 데이터 스트림으로 갖고 있어** `-c copy`만 쓰면
  "codec not currently supported in container"로 exit 1이 난다. 명시 map이 그 트랙을 버린다
- `-c copy`: 비디오와 오디오 패킷을 다시 압축하지 않고 옮긴다. mov와 mp4는 같은 ISO BMFF 계열이라
  H.264(avcC)와 AAC(esds) 패킷이 그대로 들어간다. 입력 컨테이너는 ffmpeg가 내용으로 감지하므로 원본
  파일에 확장자가 없는 지금 구조(78줄)와 충돌하지 않는다
- `-movflags +faststart`: `encode720p`와 같다. moov를 앞으로 옮기는 두 번째 패스가 한 번 더 돌지만
  파일 상한 100MB(`AwsProperties.S3.maxBytes`)에서 수 초 안이다
- 출력 확장자 `.mp4`가 mp4 muxer를 고른다. 산출물 키 `VideoAssetKeys.encoded()`와 Content-Type
  `video/mp4`는 그대로다

타임아웃은 `REMUX_TIMEOUT = Duration.ofSeconds(60)`으로 호출별 오버로드(`run(command, timeout)`)를 쓰고,
**D2의 스트림 probe도 같은 60초로 돈다.** remux는 CPU가 아니라 디스크 I/O 작업이라 100MB 입력도 수 초면
끝나고, ffprobe는 헤더만 읽는다. 10분 기본값을 그대로 쓰면 행이 걸렸을 때 노드당 하나뿐인 인코딩
슬롯이 그만큼 묶이고, 더 중요하게는 **임대 예산을 넘긴다.** MSG-494 D5의 임대 35분은 "ffmpeg 10분 × 3회
(길이 probe, 인코딩, 썸네일) + S3 여유 5분"으로 잡은 값이다. 스트림 probe와 remux가 기본 10분을 쓰면
최악이 10 + 10 + 10 + 10 + 1 = 41분이 돼 임대를 넘고, 임대가 만료되면 `VideoEncodingJobRepository`가
이 claim의 상태 갱신을 거부하면서 다른 노드의 재선점을 허용해 같은 영상이 두 번 처리된다. 60초로
잡으면 최악이 길이 probe 10 + 인코딩(폴백 포함) 10 + 썸네일 10 + 스트림 probe 1 + remux 1 = 32분이고
S3 여유 3분을 더해도 35분 안이다. 임대 상수(`PT35M`)는 바꾸지 않는다. 60초는 3초 목표의 20배 여유이고,
remux 타임아웃이면 D4의 폴백으로 넘어간다.

### D4. remux 실행 실패는 인코딩으로 한 번만 폴백한다

`remux`가 던지는 `RuntimeException`(exit≠0의 `InvalidMediaException`, 타임아웃과 IOException의
`IllegalStateException`)은 전부 `warn` 로그 뒤 `encode720p`로 폴백한다. 판정은 메타데이터 기준이라
"copy가 안 되는 H.264"(깨진 타임스탬프, 비표준 패킷 배치)가 있을 수 있고, 그런 파일은 다시 인코딩하면
대개 살아난다. 폴백이 다시 실패하면 기존 141~155줄 분기가 그대로 적용된다. `encode720p`는 자기
자신을 재시도하지 않으므로 "한 번만"은 구조로 보장된다. `ffmpeg -y`가 같은 출력 경로를 덮어쓰므로
부분 산출물 정리는 따로 하지 않는다.

폴백하지 않는 것: 판정 probe의 예외(D1), `ClaimLostException`(ffmpeg 안에서 날 수 없다). 인터럽트로
끝난 remux는 `run`이 인터럽트 플래그를 복원한 채 `IllegalStateException`을 던지므로 폴백 `encode720p`의
`waitFor`가 즉시 `InterruptedException`으로 끝나 10분짜리 인코딩이 종료 중에 시작되지는 않는다.

### D5. 관측은 로그 한 줄과 고정 태그 Counter 하나

- 138줄 로그를 `인코딩 완료: videoId={} duration={}s path={} ffmpegMs={} blurActive={}`로 바꾼다.
  `path`는 `remux`, `encode`, `fallback` 셋 중 하나다. 판정 직후에도
  `remux 판정: videoId={} remuxable={} video={} {}x{} {} audio={}`를 `info`로 한 줄 남긴다. D6 실측 표의
  "ffprobe 판정" 열이 이 줄에서 나온다
- `VideoProcessingMetrics`에 `video.encoding.path` Counter를 `path` 태그 3값으로 생성 시 선등록한다.
  기존 `video.encoding.task{result}`(63~66줄)와 같은 방식이라 미등록 값은 무시되고 0값으로도 노출된다.
  `countEncodingPath(String path)` 메서드를 `countEncodingTask`와 나란히 둔다. 증가 시점은 ffmpeg
  단계가 끝난 직후(D1 코드)이고, 뒤의 fresh 재확인 결과와 무관하다. 이 카운터는 "ffmpeg가 무엇을
  했나"를 세는 것이지 영상 종결을 세는 것이 아니다(종결은 기존 `video.processing.outcome`)
- 처리 시간 Timer는 추가하지 않는다. 종단 시간은 기존 `video.processing.duration`이 `enqueued_at`
  기준으로 이미 재고, ffmpeg 단계 시간은 로그의 `ffmpegMs`로 충분하다. 대시보드가 경로별 분포를
  요구하면 그때 Timer를 붙인다
- `VideoEncodingJobRepository.refreshQueueMetrics`와 job Counter는 작업 수명주기 지표라 건드리지 않는다

### D6. 실측 표는 구현 단계 필수 산출물이다

dev 배포 뒤 아래 표를 채워 작업 로그에 붙인다. 샘플은 저작권과 재현성을 위해 레포에 넣지 않고 로컬
파일 경로와 SHA-256으로 기록한다(MSG-494 12.6과 같은 방식). `ready_ms`는 업로드 확정 응답 시각부터
`processingStatus=READY`까지이고, `처리 ms`는 로그의 `ffmpegMs`다.

| 샘플 | 코덱/크기/오디오 | 경로 | ffprobe 판정 로그 | 처리 ms | ready_ms |
|---|---|---|---|---|---|
| 720p H.264 10초 (MSG-616 산출 규격) | h264 1280×720 yuv420p aac | remux 기대 | | | < 3,000 |
| 1080p H.264 | h264 1920×1080 | encode 기대 | | | |
| iPhone 기본 HEVC (mov) | hevc | encode 기대 | | | |
| 세로 촬영 720p (rotate 90, mov) | h264 1280×720 rotation −90 | remux 기대, 산출물 회전 보존 확인 | | | |
| 오디오 없는 720p H.264 | h264 1280×720, 오디오 없음 | remux 기대 | | | |

같은 자리에 기존 실측(29초 영상 21~33초, 동시 12건 193초)과 대비한 한 줄 결론을 쓴다.

### 기존 실 ffmpeg 통합 테스트의 변화

`VideoEncodingDurationRealFfmpegTest`는 `new FfmpegRunner()`에 640×360 h264/aac lavfi 샘플을 넣는다.
이 티켓 뒤에는 그 샘플이 remux 조건에 맞아 **실제로 remux 경로를 지난다.** 단언은 실측 길이의 전이
값이라 바뀌지 않으며, 이 테스트가 덤으로 remux 경로의 길이 저장 회귀 가드가 된다. 통과를 AC-615-03에
포함한다.

### dev 실측

D6 표를 채운다. 게이트는 720p 샘플 `ready_ms < 3,000`, 1080p와 HEVC 샘플 `path=encode` 로그, 회전
샘플의 세로 재생이다.

[^1]: remux: 영상과 소리의 압축 데이터는 그대로 두고 담는 그릇(컨테이너)만 다시 쓰는 작업. 디코딩과 인코딩이 없어 CPU를 거의 쓰지 않고 파일 복사 수준의 시간이 든다. 이 스펙에서는 mov나 mp4 입력을 moov가 앞에 오는 mp4로 다시 담는 것을 뜻한다.
[^2]: ffprobe `-show_streams`: 파일 안의 스트림(비디오, 오디오, 데이터)마다 코덱 이름, 코딩 크기, 픽셀 포맷, 회전 side data 같은 메타데이터를 출력하는 ffmpeg 동봉 도구의 모드. `-of json`을 붙이면 `streams` 배열을 가진 JSON으로 나온다.
[^3]: 스트림 복사(`-c copy`): ffmpeg에서 스트림을 다시 압축하지 않고 패킷을 그대로 출력 컨테이너에 옮기라는 옵션. 입력 코덱이 출력 컨테이너에 들어갈 수 있을 때만 성공하고, 들어갈 수 없는 스트림(iPhone mov의 `mebx` 데이터 트랙)이 끼면 실패한다.
[^4]: 색인 전진 배치(`-movflags +faststart`): mp4의 색인(moov)을 파일 앞으로 옮기는 옵션. 색인이 뒤에 있으면 플레이어가 파일 전체를 받아야 재생을 시작할 수 있어, 스트리밍 재생에는 앞에 두는 것이 전제다. 쓰기가 끝난 뒤 파일을 한 번 더 훑어 재배치한다.
[^5]: 픽셀 포맷(pix_fmt): 프레임 한 장의 색 표현 방식. `yuv420p`는 8비트 4:2:0 서브샘플링으로 모바일 하드웨어 디코더가 공통으로 지원하는 형식이고, `yuv420p10le`(10비트)나 `yuv422p`, `yuv444p`는 H.264 High 10, 4:2:2, 4:4:4 프로파일에서 나와 일부 기기가 재생하지 못한다.
[^6]: Display Matrix(회전 side data): mov/mp4 트랙 헤더의 변환 행렬로, 센서가 가로로 기록한 프레임을 세로로 보여 달라고 플레이어에게 알리는 정보. ffprobe는 `side_data_list[].rotation`(새 버전)이나 `tags.rotate`(옛 버전)로 보여 주고, `width`/`height`는 회전 적용 전 값이다.
