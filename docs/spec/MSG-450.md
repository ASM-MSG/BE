# MSG-450: 미션 집계에서 행사 영상 제외 (여섯 쿼리 안티조인)

**Owner**: B (콘텐츠, `com.msg.fillmap.mission.*`와 `com.msg.fillmap.video.*` 모두 Owner B)

> 요구사항 정본: `docs/prd/event-room-location-videos.md` (확정, "미션 축 연계 비목표" 승계)
> 계약 정본: `docs/spec/MSG-438.md` §기존 업로드 파이프라인 부수효과 계약. 행사 영상은 정상
> `videos` 행으로 저장되어 일반 업로드 부수효과를 전부 받되, 제외는 미션 하나뿐이다.

## 개요

행사 영상(`event_videos` 행이 붙은 `videos` 행)이 미션 진행도, 완료 판정, 방문 스팟, 미션 영상
목록과 개수에 잡히지 않도록, `videos`를 직접 조인하는 미션 쿼리 여섯 개에 `event_videos`
안티조인[^1] 술어를 추가한다. 새 API도, 새 테이블도 없다. 기존 쿼리 여섯 개의 술어 한 줄
추가와 그 검증 테스트가 전부다.

## 배경, 목표

행사 영상은 사용자가 현장에 없어도 올릴 수 있다(PRD §4.3). 격자 방문 증거가 아니므로 미션
비연계가 확정 계약이다. 그런데 미션 쿼리들은 `videos`를 격자로 직접 조인하기 때문에, 행사
위치의 대표 격자가 어느 미션의 대상 격자와 겹치는 순간 행사 영상이 진행도와 완료 판정에
섞인다. MSG-440(행사 영상 업로드)이 배포되기 전에 이 구멍을 막는 것이 목표다.

**배포 게이트 (P1, Codex 리뷰 2026-08-20)**: 이 티켓은 MSG-440보다 먼저 배포되거나 같은 배포
단위에 들어가야 한다. 늦으면 첫 행사 업로드부터 미션 비연계 확정이 깨진다. Jira에 Blocks
링크가 걸려 있다. 참조 테이블 `event_videos`는 V39(MSG-438, 머지 완료)가 이미 만들었으므로
이 티켓 단독 선배포에 스키마 선행조건 문제는 없다.

**미션 판정 시점 가시성 계약 (P1, Codex 2라운드 2026-08-21)**: 여섯 쿼리의 안티조인은 판정
시점에 `event_videos` 행이 조회 가능할 때만 성립한다. 기존 업로드 확정 경로는 트랜잭션 안에서
미션 판정 훅을 호출하므로(`VideoServiceImpl:202`의 `missionAwardService.awardOnUpload`),
MSG-440 행사 업로드가 이 경로를 재사용하면서 `event_videos` 행을 판정 이후에 저장하면
안티조인이 행사 영상을 알아보지 못해 미션 스탬프와 뱃지가 잘못 지급된다. 지급은 비가역이다.
따라서 MSG-440 쓰기 경로는 둘 중 하나를 만족해야 한다.

- ⓐ `event_videos` 행을 persist하고 flush한 뒤 판정 훅을 호출한다. 판정 쿼리는 native라
  영속성 컨텍스트를 우회하므로, 같은 트랜잭션이라도 flush 전에는 그 행이 보이지 않는다.
- ⓑ 행사 업로드에서는 판정 훅 호출 자체를 건너뛴다. 행사 영상은 어차피 미션 비연계라 호출이
  낭비이고, 호출 순서 실수가 곧 비가역 오지급이 되는 위험도 사라진다(권장).

이 계약의 검증(업로드 경로 통합 테스트)은 쓰기 경로 소유자인 MSG-440 테스트 몫이다. MSG-438
§검증 분담("부수효과 계약의 검증은 쓰기 경로 소유자인 MSG-440 테스트 몫")과 같은 규칙이다.

## 성공 기준

행사 영상만 있는 상태에서 미션 여섯 조회 결과가 행사 영상이 없을 때와 완전히 같다.
구체적으로: 진행도 0, 완료 미판정, 방문 스팟 빈 목록, 미션 영상 목록과 격자별 수에 미포함.
같은 격자에 일반 영상이 공존하면 일반 영상만 집계된다. 아래 테스트 시나리오가 검증 수단이다.

## API 명세

변경 없음. 기존 미션 API(목록 진행도, 업로드 완료 판정 응답, 미션 상세, 미션 영상 목록)의
응답 값에서 행사 영상이 빠질 뿐, endpoint와 DTO는 그대로다.

## 도메인 로직

### 대상 쿼리 여섯 개 (전부 native 쿼리[^2])

| # | 위치 | 용도 | `videos` 조인 형태 |
|---|---|---|---|
| 1 | `MissionRepository.findProgress:46` | 미션 진행도 | `LEFT JOIN videos v ON ...` |
| 2 | `MissionRepository.findCompleted:96` | 완료 판정 | `JOIN videos v ON ...` |
| 3 | `MissionGridRepository.findVisitedGridIds:29` | 방문 스팟 | `JOIN videos v ON ...` |
| 4 | `VideoRepository.findMissionVideos:142` | 미션 영상 첫 페이지 | `FROM videos v` + WHERE |
| 5 | `VideoRepository.findMissionVideosAfter:166` | 다음 페이지 (커서 페이지네이션[^3]) | `FROM videos v` + WHERE |
| 6 | `VideoRepository.countMissionVideosByGrid:187` | 격자별 영상 수 | `FROM videos v` + WHERE |

### 안티조인 술어 (여섯 곳 공통, 글자 단위 동일)

```sql
AND NOT EXISTS (SELECT 1 FROM event_videos ev WHERE ev.video_id = v.id)
```

- **형태는 NOT EXISTS 하나로 통일한다.** `event_videos.video_id`가 PK라 행당 프로브가 최대
  한 번이라고 보고 별도 인덱스를 추가하지 않는다. 이 근거는 DDL에서 온 설계 판단이고, 대표
  데이터에서 실제로 그 인덱스를 타는지는 dev 배포 후 확인 대상이다(작업 로그 §실행 쿼리).
- **넣는 자리는 기존 `videos` 술어가 사는 자리다.** 쿼리 1~3은 `videos` 조인의 ON 절[^4]
  (기존 `v.status <> 'DELETED'` 줄 다음), 쿼리 4~6은 WHERE 절(기존 게이트 3종 줄 다음).
  쿼리 1은 LEFT JOIN이라 특히 ON 절이어야 한다. "행사 영상이 아닌 영상만 조인"이 의도이고,
  미진행 미션이 0으로 나오는 LEFT 의미를 건드리지 않는다.
- **기존 술어 동등[^5] 계약을 안티조인 포함으로 갱신한다.** 쿼리 1~3의 `videos` 조인 조건은
  "글자 단위로 같다"가 주석 명문 계약이고(MSG-398 D8, MSG-399), 쿼리 4~6은 서로 술어
  동등이다(MSG-390, MSG-399 정합 테스트 고정). 안티조인 줄을 각 그룹 안에서 똑같이 추가해
  계약을 유지하고, 해당 Javadoc에 이 줄이 계약의 일부임을 한 문장 덧붙인다(MSG-450 근거 표기).
- 이 여섯 개 외의 `videos` 집계(도감 지표, 커버 재선정, 뱃지, 스트릭, 핫스코어, 전역 피드)는
  건드리지 않는다. 전부 "적용" 계약이다(MSG-438 부수효과 표). 도감 지표 4경로 제외는 점령
  번복 확정으로 계약이 소멸했으므로 이 티켓 범위가 아니다.

## 테스트 시나리오

기존 리포지토리 쿼리 테스트 4벌(`MissionProgressQueryTest`, `MissionAwardQueryTest`,
`MissionVisitedGridQueryTest`, `MissionVideoListQueryTest`/`MissionVideoCountQueryTest`)에
행사 영상 케이스를 추가한다. 시드는 `event_videos`의 FK 사슬(event_series, event_occurrences,
event_locations, event_location_grids) 전체가 필요하므로 테스트 헬퍼 하나로 최소 체인을
만들어 공유한다. 공유 로컬 DB 정책상 테스트 전후 정리를 기존 패턴대로 따른다.

이 티켓의 테스트는 `event_videos` 링크가 이미 저장된 상태에서의 쿼리 계약만 검증한다는 한계가
있다. 업로드 트랜잭션 안의 호출 순서(위 가시성 계약)는 쓰기 경로 소유자인 MSG-440 통합
테스트가 검증한다.

한국어 테스트 메서드명 후보:

1. `행사_영상은_미션_진행도에_세어지지_않는다`: 미션 대상 격자에 행사 영상만 있으면
   filledCount 0, 일반 영상이 공존하면 일반 영상만 센다 (findProgress)
2. `행사_영상만으로는_미션이_완료되지_않는다`: target_count 1 미션의 대상 격자에 기간 내
   행사 영상만 있어도 findCompleted 결과가 비어 있다
3. `행사_영상은_방문_스팟으로_표시되지_않는다`: findVisitedGridIds가 행사 영상만 있는
   격자를 반환하지 않는다
4. `행사_영상은_미션_영상_목록에_나오지_않는다`: 전역 공개 게이트 셋(ACTIVE, PUBLIC, READY)을
   다 통과하는 행사 영상도 findMissionVideos 첫 페이지에서 빠진다
5. `행사_영상은_커서_이후_페이지에도_나오지_않는다`: findMissionVideosAfter 동일 검증
6. `행사_영상은_격자별_영상_수에_세어지지_않는다`: countMissionVideosByGrid에서 행사 영상만
   있는 격자는 행이 없고, 혼재 격자는 일반 영상 수만 나온다
7. 일반 영상 회귀 가드: 기존 테스트 스위트가 green이면 충족되므로 별도 메서드를 만들지 않는다
8. (구현 중 추가, Codex 1R P1) `행사_영상뿐인_미션도_0_진행도로_나온다`: 대상 격자가 전부 행사
   영상뿐인 미션도 findProgress 결과에 filledCount 0인 한 행으로 나온다. 안티조인을 ON이 아니라
   WHERE에 두는 오배치를 잡는 유일한 케이스다 — 1번 시나리오는 다른 격자의 일반 영상이 미션을
   살려 두어 오배치를 통과시킨다(돌연변이 실측 확인)

각 테스트에 `// 검증: FR-EVENT-12` 주석을 단다. FR-EVENT-12는 `docs/srs.md`에 등재된 이
티켓의 요구사항이다(행사 영상은 미션 진행도, 완료 판정, 방문 스팟, 미션 영상 목록, 격자별
영상 수 전부에서 제외. 상태 계획, 구현 MSG-450). RTM 생성 스크립트가 이 주석으로 테스트를
요구사항에 연결하므로, 구현 마무리에서 FR-EVENT-12 상태 승격과 검증 테스트를 같은 브랜치에
함께 커밋한다(finalize.md 2-1).

아래 §실행 쿼리 참조).

**실행 쿼리**

여섯 곳에 들어간 술어는 글자 단위로 같다.

```sql
AND NOT EXISTS (SELECT 1 FROM event_videos ev WHERE ev.video_id = v.id)
```

넣은 자리가 쿼리마다 다르다. 진행도(`MissionRepository.findProgress`)·완료 판정
(`findCompleted`)·방문 스팟(`MissionGridRepository.findVisitedGridIds`)은 `videos` 조인의
**ON 절**이고(기존 `v.status <> 'DELETED'` 줄 다음), 미션 영상 목록 두 쿼리와 격자별 영상 수
(`VideoRepository.findMissionVideos`·`findMissionVideosAfter`·`countMissionVideosByGrid`)는
**WHERE 절**이다(게이트 3종 줄 다음). 진행도는 LEFT JOIN이라 자리가 의미를 바꾼다 — WHERE로
내리면 짝 없는 미션 행이 통째로 사라져 미진행 미션의 0 진행도가 안 나온다.

로컬에서 `EXPLAIN (ANALYZE, BUFFERS)`로 확인한 것은 **계획 형태 하나뿐이다.** PostgreSQL 16이
`NOT EXISTS`를 행마다 도는 서브플랜이 아니라 `Nested Loop Anti Join` 노드로 재작성한다.

```text
->  Nested Loop Anti Join  (cost=0.00..0.04 rows=1 width=11)
      Join Filter: (ev.video_id = v.id)
```

**여기서 확인되지 않은 것을 분명히 적어 둔다** (Codex 2R P3). 로컬 DB는 테스트 롤백 정책 때문에
`videos` 0행이라 안쪽 노드가 전부 `never executed`이고, 인용한 계획에는 인덱스 스캔도 `Index Cond`도
없다. 즉 `event_videos_pkey` 프로브가 실제로 쓰인다는 것은 **실행으로 검증된 사실이 아니라 DDL에서
나온 설계 근거**다(참조 열이 PK이므로 행당 최대 한 번). 대표 데이터에서의 실행 계획과 비용은 여섯 곳
모두 아직 미검증이고, dev 배포 후 확인 대상이다.

**예외 흐름**

없다. 새 `ApiException`도 새 `EventErrorCode`·`MissionErrorCode` 상수도 없고, 행사 영상은
예외로 막히는 게 아니라 결과 집합에서 조용히 빠진다. 미션 조회 API의 응답 코드와 DTO는 그대로다.

**빈 동작**

없다. 새 빈도, 스케줄러도, 트랜잭션 경계 변경도 없다. 다만 **판정 시점 가시성 계약**(위 §개요의
P1)은 쓰기 경로 쪽에서 이미 성립해 있음을 확인했다 — MSG-440이 선택지 ⓑ를 택해
`VideoServiceImpl.confirmAndStore`(업로드 확정 코어)에서 미션 판정 훅을 아예 밖으로 뺐고, 좌표

**1라운드 (P1, 코드)**

P1 한 건이 나왔고 사실로 확인해 고쳤다. 지적 요지: 진행도 테스트가 안티조인의 **ON → WHERE
오배치를 못 잡는다**. 이유를 따져 보니 LEFT JOIN에서 짝이 없는 행은 `v.id`가 NULL이라
`NOT EXISTS (... ev.video_id = NULL)`이 참이 되어 WHERE에서도 살아남는다. 그래서 오배치가 미션 행을
실제로 지우는 경우는 **미션의 대상 격자가 전부 행사 영상만 가진 때뿐**인데, 기존 테스트는 다른
격자(`mixed`)의 일반 영상이 미션을 살려 두고 있어 WHERE로 옮겨도 그대로 통과했다.

가드 테스트 `행사_영상뿐인_미션도_0_진행도로_나온다`를 추가하고 **돌연변이로 검증**했다.
`findProgress`의 안티조인 줄을 ON에서 WHERE로 실제로 옮겨 돌리자 새 테스트만 FAILED이고 기존
테스트는 통과했다. 오배치를 잡는 가드가 이 케이스 하나뿐임이 실측으로 확인된 셈이다. 원복 후
전체 빌드 green.

같은 리뷰에서 나머지 항목은 지적 없이 확인됐다: 여섯 술어가 글자 단위로 동일하고 자리도 맞으며,
빠뜨린 미션 계열 `videos` 쿼리가 없고, `EventVideoFixtures`의 시드 체인이 V39 제약을 만족하며,
트랜잭션에 묶인 `EntityManager` 안에서 `SELECT lastval()` 호출이 안전하고, 술어를 통째로 빼면
쿼리 테스트 여섯 건이 전부 깨진다(가드 1건을 더한 현재 총계는 7건이다).

**2~3라운드 (P3, 전부 문서 서술)**

코드에는 지적이 없었고, 고친 것은 이 문서가 실측보다 넓게 주장한 세 곳이다. 남겨 둘 가치가 있는
것은 **무엇이 검증됐고 무엇이 아닌지의 경계**다.

- **테스트 수**: 6건으로 적혀 있었으나 1R 가드를 더해 7건이다. 작업 로그와 `status.md` 정정.
- **EXPLAIN 서술**: "PK 프로브 한 번이면 끝난다"가 실행으로 검증된 사실처럼 읽혔다. 실제로 확인된
  것은 `Nested Loop Anti Join` 재작성이라는 **계획 형태 하나뿐**이고, 로컬 `videos` 0행이라 안쪽
  노드는 전부 `never executed`에 `Index Cond`도 없다. 인덱스 사용은 DDL에서 나온 설계 근거로
  격하해 적고 dev 확인 대상으로 남겼다. 3R에서 §도메인 로직의 같은 단정이 안 고쳐진 채 남은 것을
  다시 잡아 함께 완화했다(작업 로그만 고치고 설계 절을 빠뜨린 실수).
- **테스트 시나리오 7번**: "별도 메서드를 만들지 않는다"가 실제 일곱 번째 테스트와 모순됐다.
  7번은 그대로 두고 8번 항목으로 배치 가드를 명시했다(구현 중 추가분임을 근거와 함께).

**4라운드**: `no findings`. 수렴 기준("이번 티켓 변경 파일에 대한 신규 지적 없음") 충족.

[^1]: 안티조인(anti join): "오른쪽에 짝이 있는 행을 버리는" 조인. SQL에서는 보통
    `NOT EXISTS` 서브쿼리로 쓰며, 여기서는 `event_videos`에 행이 있는 영상(행사 영상)을
    집계에서 걸러내는 데 쓴다.
[^2]: native 쿼리: JPQL이 아니라 DB 방언 그대로 쓰는 SQL. 대상 여섯 쿼리는 모두
    `nativeQuery = true`로 작성돼 있어 술어 추가도 SQL 문자열 수정이다. native는 영속성
    컨텍스트(JPA가 트랜잭션 안에서 들고 있는 미저장 변경분)를 우회해 DB에 실제로 flush된
    행만 본다.
[^3]: 커서 페이지네이션: 페이지 번호 대신 직전 페이지 마지막 항목의 정렬 키(여기서는
    촬영 시각과 id)를 경계로 다음 행들을 이어 받는 방식. offset과 달리 중간 삽입에도
    중복과 누락이 없다.
[^4]: ON 절: 조인 조건을 두는 자리. LEFT JOIN에서는 같은 조건이라도 ON에 두면 "짝이 없는
    왼쪽 행을 남기고", WHERE에 두면 결과 행을 통째로 거른다. 진행도 쿼리가 미진행 미션을
    0으로 유지하려면 ON에 넣어야 한다.
[^5]: 술어 동등: 두 쿼리의 WHERE와 조인 조건이 같은 조건 집합이라는 계약. 화면의 숫자(개수
    쿼리)와 목록(조회 쿼리)이 같은 행 집합을 봐야 한다는 정합 요구를 코드 주석과 테스트로
    고정해 둔 것이다.
