# MSG-416: 친구 요청과 수락을 푸시 알림으로 알려주기

**Owner**: B (friend, notification 모두 Owner B 패키지. 계약 인터페이스 무변경)

> 요구사항 정본: `docs/prd/MSG-416-prd.md` (검토됨, 2026-08-18 성민 승인) · SRS FR-NOTI-14
> (FR-NOTI-13을 대체, 13은 폐기됨)

## 개요

친구 요청 접수와 수락 시점에 기존 알림 파이프라인의 아웃박스[^1]에 FRIEND 카테고리 알림을
기록한다. 신규 API와 신규 타입 없이, 카테고리 열거형 값 하나와 기록 호출 세 곳을 추가하는
작업이다. 발송, 재시도, 옵트아웃[^2] 필터는 전부 기존 파이프라인(MSG-178~181)이 처리한다.

## 배경 · 목표

친구 기능(MSG-185~187)은 완결됐지만 알림이 없어, 요청을 받은 쪽은 앱을 열기 전까지 요청이
온 사실을 모르고 보낸 쪽은 수락 여부를 알 수 없다. 이 공백을 없앤다. 목표는 두 가지다:
친구 요청을 받으면 푸시가 오고, 내가 보낸 요청이 수락되면 푸시가 온다.

**비목표**: 거절 통지(FR-FRIEND-04 유지), 활동 피드형 알림, 알림 이력 조회 API. **푸시 딥링크
데이터도 범위 밖이다.** 기존 5종 카테고리 전부 딥링크 없이 발송 중이고, 딥링크는 전 카테고리
공통 공백(FR-NOTI-12)이라 별도 과제로 확정됐다 (2026-08-18).

## 성공 기준

1. 친구 요청이 접수되면 수신자의 notifications에 FRIEND 행이 남고, 파이프라인이 켜진 환경에서
   요청자 닉네임이 담긴 푸시가 발송된다.
2. 요청이 수락되면(직접 수락, 상호 요청 자동 수락 모두) 원 요청자에게 수락자 닉네임이 담긴
   푸시가 발송된다. 자동 수락에서 나중에 요청한 쪽은 알림을 받지 않는다.
3. 거절은 어느 쪽에도 notifications 행을 만들지 않는다.
4. 같은 상대가 같은 날(KST) 다시 요청해도 수신자에게 두 번째 알림 행이 생기지 않고, 날이
   바뀌면 새 알림 행이 생긴다.
5. 요청이나 수락 트랜잭션이 롤백되면 알림 행도 남지 않는다.
6. 사용자가 FRIEND 카테고리를 끄면 기록은 남되 발송 단계에서 PREF_OFF로 걸러진다. 기본값은
   켜짐이다.

아래 "테스트 시나리오"가 이 기준의 검증 수단이다.

## API 명세

신규 endpoint 없음. 기존 친구 API(요청, 수락, 거절)의 요청과 응답 계약은 그대로다.

**알림 설정 API는 응답 계약이 확장된다** (Codex 1R P1 반영). `NotificationPreferenceServiceImpl`이
`NotificationCategory.values()` 순회로 목록을 만들기 때문에, enum에 FRIEND를 넣는 순간
`GET /api/notifications/preferences` 응답에 FRIEND 항목(기본 enabled=true)이 자동 포함되고
PATCH도 FRIEND 값을 받는다. 이것이 FR-6의 의도된 동작이며 FE에 공유할 계약 변화다. 파싱과
판정 로직은 무변경이지만, "5종"을 하드코딩한 표면들은 6종으로 함께 갱신해야 한다 (D6 참조).

## 도메인 로직

### D1. 기록 지점 3곳 (전부 `FriendServiceImpl`)

`NotificationCommandService.record(userId, category, eventKey, title, body)`가 단일 진입점이다.
전파 REQUIRED라 호출부 트랜잭션에 참여하므로, 아래 세 지점에 호출을 추가하는 것만으로
비즈니스 커밋과 원자적이다(FR-5). 반환값 처리 불요, 기존 record는 void다. 잠금 순서 요구는
D7 참조.

| 지점 | 위치 | 알림 수신자 | 문구에 담는 닉네임 |
|------|------|------------|-------------------|
| 요청 접수 | `request()`의 PENDING 신규 생성 분기 | 요청 대상(`target.getId()`) | 요청자(`userId`) |
| 자동 수락 | `request()`의 역방향 대기 승격 분기 (`existing.accept()` 직후) | 먼저 요청했던 쪽(`existing.getRequesterId()`) | 수락자(`userId`) |
| 직접 수락 | `accept()`의 승격 직후 | 원 요청자(`requesterId`) | 수락자(`userId`) |

- 자동 수락에서 나중에 요청한 쪽(`userId`)은 요청 응답 body로 이미 ACCEPTED를 받으므로
  알림을 보내지 않는다(FR-3).
- `reject()`는 손대지 않는다(FR-4). `deleteFriend()`도 무변경이다.
- 닉네임 재료: PRD 7절은 "이미 조회하는 상대 사용자 행"이라 적었지만, 세 지점 모두 문구에
  필요한 것은 **행위자 본인**의 닉네임이라 기존 조회로는 부족하다. 각 지점에서
  `findUser(userId)` PK 조회 1건을 추가한다(단건 PK 조회라 부담 없음, 기존 헬퍼 재사용).

### D2. event_key 설계: 요청 키는 날짜로 상한을 겸하고, 수락 키는 무작위 UUID 꼬리를 쓴다

`(user_id, event_key)` UNIQUE + `ON CONFLICT DO NOTHING`이 이미 기록 단계 멱등[^3] 1차
방어다(V21, FR-NOTI-03). **요청 도착 키**에 KST 날짜를 넣으면 이 dedupe가 "같은 상대 하루
1건" 상한(FR-8)을 겸한다. 뱃지 임박 알림처럼 잠금 후 카운트 조회(`tryAcquireBadgeNearLock` +
`countRecordedSince`)를 쓰지 않는 이유: 그 선례는 어느 뱃지든 합산해 하루 1건이라 키 하나로
접을 수 없었지만, 여기는 상한 단위가 정확히 "상대별"이라 키에 그대로 매핑된다. 잠금 없이
UNIQUE 제약 하나로 끝나 select-then-act 경합(PR #114 교훈) 자체가 없다.

| 이벤트 | event_key | 수신자 user_id |
|--------|-----------|----------------|
| 요청 도착 | `FRIEND_REQ:{요청자 userId}:{yyyyMMdd}` | 요청 대상 |
| 수락 (자동, 직접 공통) | `FRIEND_ACC:{수락자 userId}:{UUID.randomUUID()}` | 원 요청자 |

- 요청 키의 날짜는 KST(`Asia/Seoul`) 기준 `yyyyMMdd`(`DateTimeFormatter.BASIC_ISO_DATE`).
  일 경계 KST는 기존 상한 정책(FR-NOTI-07)과 같다.
- **FR-7과 FR-8의 관계**: 거절 뒤 재요청은 새 알림이 가되(FR-7), 같은 날이면 상한(FR-8)이
  우선해 알림이 없다. 날짜 포함 키가 두 요구를 자연 구현한다. 같은 날 재요청은 DO NOTHING
  흡수(반환 0, 무시), 날이 바뀌면 새 키라 새 행이다.
- **수락 키에는 날짜를 쓰지 않는다** (Codex 2R P2 반영). 수락 알림에는 하루 1건 상한 요구가
  없고(FR-8은 요청 도착 한정), 날짜 키면 같은 KST 날짜 안의 "친구 삭제 후 재요청, 재수락"에서
  두 번째 정당한 수락 알림을 DO NOTHING이 삼킨다.
- **수락 키 꼬리는 수락 시점 `UUID.randomUUID()`다** (리뷰 최종 반영, MSG-417이 같은 문제를
  푼 방식과 동일). 앞서 검토한 `Friendship.createdAt` 꼬리는 같은 방향 관계가 삭제 후 같은
  마이크로초 createdAt으로 재생성되면 충돌하는 이론상 구멍이 있다. 무작위 UUID는 수락
  이벤트마다 항상 새 키라 정당한 알림이 절대 삼켜지지 않는다. 키 dedupe 없이도 같은 전이의
  중복 기록·중복 발송이 막히는 논증: (a) 수락 트랜잭션이 롤백되면 record도 동반 롤백된다
  (전파 REQUIRED). (b) 커밋 후 같은 수락의 재호출은 record에 도달하기 전에 상태 가드가
  끊는다. 직접 수락은 `findPendingRequest`의 PENDING 필터(9414), 자동 수락 경로는
  ALREADY_FRIENDS(9409)다. (c) 발송 단계의 메시지 재전달은 컨슈머의 종결 상태 가드
  (SENT·SKIPPED·DEAD면 즉시 종료, FR-NOTI-03 2차 방어)가 흡수한다. 폭 검산: 접두 11 +
  Long 최대 19 + 콜론 1 + UUID 36 = 최대 67자로 `event_key VARCHAR(100)` 내. 요청 키도
  최대 39자로 한계 내.

### D3. 시각 처리: Clock 주입 (프로덕션 생성자 위임 패턴)

이 프로젝트에는 Clock 빈이 없다. `FriendServiceImpl`에 `final Clock` 필드만 추가하면
컨텍스트가 뜨지 않는다. `BadgeAwardServiceImpl:64~72` 선례를 따른다: `@RequiredArgsConstructor`의
Lombok 전체 생성자는 테스트 고정 클럭 주입용으로 두고, `@Autowired` 프로덕션 생성자를 손으로
추가해 마지막 인자를 `Clock.systemUTC()`로 고정해 위임한다(VideoServiceImpl도 같은 패턴).
KST 날짜는 `LocalDate.now(clock.withZone(ZoneId.of("Asia/Seoul")))` 형태로 얻는다. 인자 없는
`LocalDateTime.now()`와 `LocalDate.now()`는 금지다(project-conventions.md MSG-376 절).

### D5. 컨슈머 전송률 분기: FRIEND는 카테고리 상한 없음

`NotificationConsumer.rateLimited()`의 switch는 default 없는 전수 분기[^4]라 enum에 FRIEND를
추가하는 순간 컴파일이 깨진다. **PRD 변경 파일 목록에 없던 파일이지만 수정이 강제된다.**
`case FRIEND -> null`(무제한)을 추가한다. 근거: 스팸 벡터인 "같은 상대 반복 요청"은 D2의
event_key 상한이 기록 단계에서 이미 막고, 서로 다른 여러 상대에게서 오는 요청은 정당한
알림이라 카테고리 일 상한을 두면 진짜 요청이 잘린다(BADGE 무제한과 같은 결).
`NotificationProperties.RateLimit`에 키 추가 없음.

### D6. 옵트아웃: 판정 로직은 자동, "5종" 하드코딩 표면과 무효값 프로브는 함께 갱신

FRIEND는 옵트아웃 대상이다(기본 켜짐, FR-6). `NotificationPreferenceService.isEnabled`와
파싱, 목록 생성은 전부 enum 기반이라 로직 무변경으로 FRIEND를 수용한다. 다만 "5종"을 문구로
하드코딩한 표면과, **FRIEND를 무효값 프로브로 쓰던 테스트**가 있어 갱신하지 않으면 문서와
에러 메시지가 거짓말을 하고 테스트가 깨지거나 거짓 green이 된다 (Codex 1R P1·2R P1 반영):

| 표면 | 위치 | 갱신 내용 |
|------|------|----------|
| `NotificationPreferenceController` | 39·52·58행 | Swagger 설명 문구의 카테고리 나열에 FRIEND 추가 |
| `NotificationPreferenceResponseDto` | 11·14·17행 | 주석과 스키마 문구의 카테고리 나열에 FRIEND 추가 |
| `NotificationErrorCode` | 23행 | 10420 INVALID_CATEGORY 메시지 "BADGE, HOTZONE, REMIND, VIDEO, WEEKLY 중 하나"에 FRIEND 추가 |
| `NotificationPreferenceServiceIntegrationTest` | 96·128·141행 | `containsExactly` 단언이 FRIEND 미반영이면 깨진다. 기대 목록에 FRIEND 추가 |
| `NotificationPreferenceServiceIntegrationTest` | 185~192행 | `update(me, "FRIEND", false)`가 10420을 던진다는 단언은 FRIEND가 유효값이 되면 실패한다. 프로브를 진짜 존재하지 않는 문자열(예: `"NOPE"`)로 교체하고, FRIEND 토글 정상 동작 케이스를 추가 |
| `NotificationPreferenceControllerTest` | 115~127행 | FRIEND를 무효 카테고리로 스텁하는데 유효값이 된 뒤엔 오해를 부르는 거짓 green이 된다. 프로브를 존재하지 않는 문자열로 교체 |

### D7. 잠금 순서: 수신자 users KEY SHARE 잠금을 friendships 잠금 조회보다 먼저

`notifications.user_id`는 `REFERENCES users(id) ON DELETE CASCADE`(V21)라 record의 INSERT가
수신자 users 행의 KEY SHARE 잠금[^5]을 요구한다. 수락 경로는 friendships 행을
PESSIMISTIC_WRITE로 먼저 잡은 채 record에 도달하는데, 그 사이 상대 계정 삭제 트랜잭션이
users 배타 잠금을 잡고 friendships CASCADE를 대기하면 잠금 순서가 교차해 데드락이 완성된다
(Codex 2R P2 반영). 선례가 정확히 이 경로용으로 존재한다: `VideoStatusWriter.lockUploaderFirst`가
본 작업 전에 `UserRepository.findIdForKeyShare`(users FOR KEY SHARE)를 호출해 탈퇴 CASCADE와
잠금 순서를 통일한다(MSG-313 Codex 2R).

- `accept()`: `findPendingRequest`(FOR UPDATE) **호출 전에** `findIdForKeyShare(requesterId)`
  (수신자 = 원 요청자). 빈 Optional이면 `FRIEND_REQUEST_NOT_FOUND`(9414)를 던진다. 요청자
  계정이 사라졌으면 유효한 대기 요청도 없으므로 기존 실패와 같은 코드다.
- `request()`: `findPair`(PESSIMISTIC_WRITE) **호출 전에** `findIdForKeyShare(target.getId())`
  (두 분기 모두 수신자는 target이라 한 번이면 된다). 빈 Optional이면
  `FRIEND_CODE_NOT_FOUND`(9404)를 던진다. `findByCode` 미존재와 같은 상황(그 코드의 상대가
  이제 없다)이라 같은 코드로 맞춘다.
- **빈 Optional을 무시하고 진행하면 안 된다** (Codex 3R P2 반영). `request()`의 pair-empty
  분기는 target 재확인 없이 `friendshipRepository.save(...)`로 직행하므로
  (FriendServiceImpl:84~88 실측), `findByCode`와 잠금 조회 사이에 대상 계정이 삭제되면
  삭제된 사용자를 가리키는 INSERT가 FK 위반 500이 된다. 빈 Optional은 위처럼 명시적 도메인
  에러로 변환해 500을 막는다. `UserRepository`는 기존 메서드 재사용이라 무변경이다.

## 데이터 모델

엔티티 변경 없음. Flyway 마이그레이션 1건 필요.

**`V35__notification_category_friend_moderation.sql`** (현재 최신 V34 기준):

```sql
-- FRIEND(MSG-416)·MODERATION(MSG-417) 카테고리 확장. 기존 행 무변경, CHECK 상위집합 재정의 (V25·V26 형상).
ALTER TABLE notifications DROP CONSTRAINT chk_notifications_category;
ALTER TABLE notifications ADD CONSTRAINT chk_notifications_category
	CHECK (category IN ('BADGE', 'HOTZONE', 'REMIND', 'VIDEO', 'WEEKLY', 'FRIEND', 'MODERATION'));

-- opt_outs 에는 FRIEND 만 추가한다. MODERATION 은 수신 거부 대상이 아니므로(MSG-417 FR-7 확정) 의도적 제외.
ALTER TABLE notification_opt_outs DROP CONSTRAINT chk_notification_opt_outs_category;
ALTER TABLE notification_opt_outs ADD CONSTRAINT chk_notification_opt_outs_category
	CHECK (category IN ('BADGE', 'HOTZONE', 'REMIND', 'VIDEO', 'WEEKLY', 'FRIEND'));
```

- **MODERATION 동봉 근거**: MSG-417(블라인드 소유자 통지, PRD 검토됨)이 MODERATION
  카테고리를 신설 예정이다. CHECK 상위집합에 아직 쓰지 않는 값이 미리 들어가는 것은
  무해하므로(값을 넣는 코드가 없으면 행이 생길 수 없다) 마이그레이션을 하나로 합쳐 MSG-417의

- **opt_outs에서 MODERATION 제외 근거**: MSG-417 FR-7이 "수신 거부 대상이 아니다"로
  확정됐으므로, opt_outs CHECK에서 빼 두는 것이 DB 수준 1차 가드를 겸한다. 애플리케이션
  가드는 MSG-417이 정한다.
- 폭 확인: `category VARCHAR(10)`에 'MODERATION'은 정확히 10자라 통과, 'FRIEND'는 6자.
  컬럼 확장 불요.

## 미해결 질문

없음. PRD 미해결 항목 중 상한은 FR-8로 확정됐고, 딥링크는 범위 밖 확정으로 비목표에
편입했다(2026-08-18).

[^1]: 아웃박스(outbox): 도메인 변경과 같은 DB 트랜잭션으로 알림 요청을 먼저 행으로 남기고, 별도 릴레이가 그 행을 읽어 Kafka로 넘기는 패턴. 커밋됐으면 장애가 나도 알림이 유실되지 않고, 롤백됐으면 알림도 없다.
[^2]: 옵트아웃(opt-out): 기본이 수신 켜짐이고 사용자가 원할 때 끄는 모델. FillMap 알림 설정의 기본 정책이다(FR-NOTI-06).
[^3]: 멱등(idempotent): 같은 요청이 여러 번 실행돼도 결과가 한 번 실행과 같은 성질. 여기서는 같은 (user_id, event_key) 재기록이 DB UNIQUE 제약의 DO NOTHING으로 흡수돼 중복 푸시가 되지 않는 것을 말한다.
[^4]: 전수 분기(exhaustive switch): default 없이 enum의 모든 값을 나열한 화살표 switch. 자바 컴파일러가 값 누락을 컴파일 에러로 잡아 주므로, enum에 값을 추가하면 이 switch를 반드시 함께 고치게 강제된다.
[^5]: KEY SHARE 잠금: PostgreSQL의 가장 약한 행 잠금. FK 검사가 참조 대상 행에 거는 잠금과 같은 종류라, 이것을 미리 잡아 두면 삭제 트랜잭션(배타 잠금)과의 획득 순서가 한 방향으로 고정돼 교차 대기(데드락)가 생기지 않는다.
