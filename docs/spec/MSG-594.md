# MSG-594: iOS 애플 로그인

**Owner**: B (인증·계정 도메인, `com.msg.fillmap.auth.*`와 `com.msg.fillmap.user.*`, CLAUDE.md 협업 원칙 기준)

> 요구사항 정본: `docs/prd/MSG-594-prd.md` (검토됨, 2026-09-10 성민 승인, nonce는 Must로 확정).
> 이 스펙은 PRD의 FR-1~13과 비기능 요구사항에 "어떻게"만 붙인다.
> SRS: FR-AUTH-12 (진행 중, 이 티켓이 구현). 디자인: 피그마 `16015:540` "소셜 로그인 · A 격자
> 채우기 (iOS · Apple 포함)" 시안. 브랜치 `feature/MSG-594-apple-login`.

## 개요

iOS 앱이 애플 네이티브 로그인 시트에서 받은 ID 토큰[^1]을 기존 소셜 로그인 엔드포인트
`POST /api/auth/oauth/{provider}`에 `provider=apple`로 보내면, 서버가 카카오와 같은 검증기 계약으로
서명과 발급자와 대상과 nonce[^2]를 검증하고 같은 발급 경로로 우리 토큰을 돌려준다. 신규는 애플 검증기와
디코더 빈, 인가 코드[^3]를 애플 리프레시 토큰으로 바꾸고 탈퇴 때 취소하는 클라이언트, 그 토큰을
암호화해 두는 컬럼과 마이그레이션(V54), 요청 DTO의 애플 전용 필드 셋이다. 로그인 서비스 본체는 닉네임
기본값과 첫 로그인 교환 한 단계만 늘어난다. 웹과 안드로이드의 로그인 경험은 변하지 않는다.

## 배경 · 목표

앱스토어 심사 지침 4.8은 카카오 같은 제3자 로그인을 제공하는 앱에 애플 로그인을 함께 요구한다. iOS
출시가 다가와 2026-08-10에 미뤄 둔 결정(인증과 계정 PRD §5.1)을 실행한다. 목표는 iOS 사용자가 애플
계정으로 가입하고 재로그인하고 기존 API를 전부 쓰는 것, 같은 빌드의 안드로이드에는 버튼이 보이지 않는
것, 탈퇴 때 애플 쪽 토큰 취소[^5]까지 마쳐 심사 요건(계정 삭제 + 취소 호출)을 만족하는 것이다.

## 성공 기준

아래 조건이 전부 테스트로 관찰되면 완료다. 검증 테스트에는 `// 검증: FR-AUTH-12, AC-594-NN` 마커를 단다.

- AC-594-01: 유효한 애플 ID 토큰과 nonce 원문과 인가 코드로 `POST /api/auth/oauth/apple`을 호출하면
  200과 함께 카카오 앱 로그인과 같은 형태(액세스 토큰과 리프레시 토큰 본문, `X-Device-Id` 응답 헤더)를
  받는다 (PRD FR-3, FR-5).
- AC-594-02: 서명이 다르거나 발급자가 `https://appleid.apple.com`이 아니거나 aud가 번들 ID
  `kr.fillmap.app`이 아니거나 만료된 ID 토큰은 401 `developCode 2421`로 거절된다 (PRD FR-4).
- AC-594-03: 요청 본문의 nonce 원문을 SHA-256으로 해시한 값이 ID 토큰의 `nonce` 클레임과 다르면,
  클레임이 없으면, 요청에 nonce가 없으면 모두 401 `2421`이다 (PRD FR-11).
- AC-594-04: 같은 (provider=APPLE, oid=sub) 사용자가 다시 로그인하면 계정이 새로 만들어지지 않고
  애플 토큰 엔드포인트 호출도 없다 (PRD FR-5, 비기능 성능).
- AC-594-05: 첫 로그인 요청의 `fullName`이 2~20자면 그 값이 닉네임으로 저장되고, 이미 있는 계정에
  온 `fullName`은 무시된다 (PRD FR-6).
- AC-594-06: `fullName`이 없거나 2~20자 밖이면 닉네임이 `필맵러` 뒤 4자리 숫자(예 `필맵러0417`)로
  저장되고 가입은 실패하지 않는다 (PRD FR-7, D-2).
- AC-594-07: ID 토큰의 `email` 클레임(릴레이 주소[^4] 포함)이 그대로 저장되고, 다른 계정이 같은
  이메일을 쓰면 409 `1409`로 거절된다 (PRD FR-8).
- AC-594-08: 첫 로그인에서 서버가 `POST https://appleid.apple.com/auth/token`에 인가 코드를 교환하고,
  응답의 `refresh_token`을 AES-256-GCM[^6]으로 암호화해 `users.apple_refresh_token_encrypted`에
  저장한다. 평문은 DB와 로그 어디에도 남지 않는다 (PRD FR-10, 비기능 보안).
- AC-594-09: 교환 실패(애플 4xx `invalid_grant`는 `2423`, 그 외 4xx와 5xx와 타임아웃은 `2502`)나
  인가 코드 부재(`2423`)면 계정이 만들어지지 않는다. 교환 왕복은 DB 트랜잭션 밖에서 끝난다 (D-8).
- AC-594-10: APPLE 계정이 `DELETE /api/users/me`를 호출하면 삭제 커밋 뒤에 서버가
  `POST https://appleid.apple.com/auth/revoke`를 복호화한 리프레시 토큰으로 부르고, 그 호출이 실패해도
  탈퇴 응답은 200이며 실패는 로그에만 남는다. APPLE이 아닌 계정은 호출 자체가 없다 (PRD FR-9).
- AC-594-11: 토큰 교환과 취소 요청의 `client_secret`은 호출 시점에 ES256으로 서명한 JWT이고
  (`iss`=Team ID, `sub`=번들 ID, `aud`=`https://appleid.apple.com`, 헤더 `kid`=Key ID, 만료 5분),
  서명 키는 환경 설정으로만 들어온다 (PRD 비기능 보안, D-10).
- AC-594-12: `POST /api/auth/dev/social-login`이 `provider=APPLE`을 받아 계정을 만들고 토큰을
  발급한다. 이때 애플 왕복은 없다 (PRD FR-12).
- AC-594-13: `AuthProvider.APPLE` 행이 DB CHECK 제약 `chk_users_provider`를 통과한다 (PRD 비기능
  데이터 정합).
- AC-594-14: 기존 카카오 앱 로그인, 웹 인가 코드 로그인, 이메일 로그인, 재발급 테스트가 전부 그대로
  통과한다.
- AC-594-15: 교환 응답의 `id_token`을 `appleJwtDecoder`로 검증한 뒤 그 `sub`가 요청 ID 토큰의 `sub`와
  다르면 401 `2423`으로 거절하고, 계정도 토큰도 저장하지 않는다 (Codex P2, D-8).

앱 쪽 기준(FR-1, FR-2, FR-13: 버튼 규격, iOS 한정 렌더, 취소 시 무안내)은 FE 레인의 검증 대상이며
아래 "앱이 지켜야 할 흐름" 절이 계약이다.

## API 명세

### `POST /api/auth/oauth/apple` (기존 `/oauth/{provider}` 엔드포인트, 경로 변수만 `apple`)

신규 엔드포인트가 아니다. `AuthController.oauthLogin`이 `parseProvider`로 `AuthProvider.APPLE`을
얻고, 요청 DTO를 통째로 `OidcLoginService.login(provider, request, deviceId)`에 넘기는 한 줄만 바뀐다.

**요청 헤더** (카카오 앱 로그인과 동일):

| 헤더 | 필수 | 설명 |
|---|---|---|
| `X-Client-Type` | 아니오 | 앱은 `app`. 리프레시 토큰이 본문으로 내려간다 |
| `X-Device-Id` | 아니오 | 없으면 서버가 UUID를 만들어 응답 헤더로 돌려준다 |

**요청 body**: `OidcLoginRequestDto` (기존 record에 선택 필드 3개 추가)

```json
{
	"idToken": "eyJraWQiOiJmaDZCczhDIiwiYWxnIjoiUlMyNTYifQ...",
	"nonce": "3f9a1c...(앱이 만든 원문, 해시 아님)",
	"authorizationCode": "c8a3b1...(애플 시트가 준 1회용 코드)",
	"fullName": "김필맵"
}
```

| 필드 | 타입 | 검증 | 설명 |
|---|---|---|---|
| `idToken` | String | `@NotBlank` | 애플 `identityToken` 원문. 카카오와 같은 필드 |
| `nonce` | String | 선택 (APPLE은 서버가 필수 검사) | 앱이 요청마다 만든 임의 문자열 원문. 앱은 이 값의 SHA-256 16진 표기를 애플 시트에 넘기고 원문을 서버에 보낸다. 카카오 요청은 보내지 않는다 |
| `authorizationCode` | String | 선택 (APPLE은 서버가 필수 검사) | 애플 `authorizationCode`. 앱은 첫 로그인인지 가리지 않고 매번 보내고, 서버가 계정이 없을 때만 교환한다. 5분 안에 1회만 교환 가능 |
| `fullName` | String | 선택, 서버가 2~20자 밖이면 무시 | 애플이 첫 승인에만 주는 이름을 앱이 한 문자열로 조립한 값. 계정을 새로 만들 때만 닉네임으로 쓴다 |

세 필드를 `@NotBlank`로 묶지 않는 이유: 같은 DTO를 카카오 요청이 쓰고, 카카오는 이 필드가 없다. 제공자별
필수 여부는 서비스가 판정한다(카카오 요청에 실려 와도 무시).

**성공 응답**: `LoginResponseDto` 그대로 (신규 응답 스키마 없음).

```json
{
	"developCode": 200,
	"message": "성공",
	"data": {
		"accessToken": "eyJhbGciOiJIUzI1NiJ9...",
		"refreshToken": "eyJhbGciOiJIUzI1NiJ9...",
		"role": "USER"
	}
}
```

**에러 케이스** (판정 순서대로):

| 상황 | HTTP | developCode | 메시지 |
|---|---|---|---|
| `idToken` 누락 | 400 | 400 | `@Valid` 필드 메시지 |
| 경로의 provider가 열거형에 없음, 또는 LOCAL | 400 | 2422 | 지원하지 않는 소셜 로그인 provider 입니다 |
| 요청에 `nonce` 없음, 서명 위조, 발급자 불일치, aud 불일치, 만료, `nonce` 클레임 부재나 해시 불일치 | 401 | 2421 | 유효하지 않은 소셜 로그인 토큰입니다 |
| 요청에 `authorizationCode` 없음 (APPLE 한정) | 401 | 2423 | 유효하지 않은 인가 코드입니다 |
| 첫 로그인 교환에서 애플이 4xx `error=invalid_grant` (만료, 재사용, 다른 앱의 코드) | 401 | 2423 | 위와 동일 |
| 교환 응답 `id_token`의 검증 실패, 또는 그 `sub`가 요청 ID 토큰의 `sub`와 다름 (인가 코드가 이 로그인의 것이 아님) | 401 | 2423 | 위와 동일 |
| 교환에서 그 외 4xx(`invalid_client` 등 우리 설정 오류), 5xx, 연결 실패, 타임아웃, 응답에 `refresh_token`이나 `id_token` 없음 | 502 | 2502 | 소셜 로그인 제공자 오류입니다. 잠시 후 다시 시도해주세요 |
| 첫 로그인 이메일이 다른 계정에 있음 | 409 | 1409 | 이미 사용 중인 이메일입니다 |

nonce 실패를 2421 하나로 수렴하는 이유는 FR-4가 이미 "하나라도 어긋나면 2421"로 묶어 뒀고, 어떤 검사가
실패했는지를 클라이언트에 구분해 주면 공격자에게도 같은 정보가 가기 때문이다. 원인은 서버 warn 로그로만
가른다. 신규 에러 코드는 없다. 2421, 2422, 2423, 2502가 전부 기존 값이다.

### 애플 토큰 엔드포인트 호출 (서버 → 애플, 외부, 첫 로그인만)

애플 문서 기준. `POST https://appleid.apple.com/auth/token`,
`Content-Type: application/x-www-form-urlencoded`

| 파라미터 | 값 |
|---|---|
| `grant_type` | `authorization_code` |
| `client_id` | 번들 ID (`oauth.apple.bundle-id`) |
| `client_secret` | 호출 시점에 만든 ES256 JWT (아래 "클라이언트 비밀") |
| `code` | 요청 body의 `authorizationCode` |

성공 응답 JSON에서 `refresh_token`과 `id_token` 둘을 쓴다. `refresh_token`은 암호화해 보관하고,
`id_token`은 이 인가 코드가 요청의 ID 토큰과 같은 애플 계정에서 나왔는지 묶어 보는 데 쓴다(D-8, Codex
P2). 둘 중 하나라도 없으면 2502다. `access_token`은 소비하지 않는다. 네이티브 흐름이라 `redirect_uri`는
보내지 않는다.

### 애플 토큰 취소 호출 (서버 → 애플, 외부, 탈퇴 시)

애플 문서 기준. `POST https://appleid.apple.com/auth/revoke`, 같은 폼 인코딩.

| 파라미터 | 값 |
|---|---|
| `client_id` | 번들 ID |
| `client_secret` | 호출 시점에 만든 ES256 JWT |
| `token` | 복호화한 애플 리프레시 토큰 |
| `token_type_hint` | `refresh_token` |

성공은 본문 없는 200이다. 실패는 어떤 상태 코드든 warn 로그로만 남긴다(탈퇴는 이미 커밋됐다).

### 클라이언트 비밀[^4] (서버가 생성)

애플 문서 기준. 헤더 `alg=ES256`, `kid`=Key ID. 클레임 `iss`=Team ID, `sub`=번들 ID,
`aud`=`https://appleid.apple.com`, `iat`=지금, `exp`=지금 + 5분. 애플이 허용하는 상한은 6개월이지만
호출 직전에 만들어 바로 쓰는 값이라 길게 둘 이유가 없다. 캐시하지 않는다(교환과 취소 모두 사용자당
한 번 수준의 빈도라 서명 비용이 무의미하다). 서명은 이미 있는 jjwt 0.13(`Jwts.builder()...signWith(EC
개인키, Jwts.SIG.ES256)`)으로 하고, 시각은 주입된 `Clock`에서 얻는다(`Instant.now(clock)`).

키 로딩: `.p8` 파일의 `-----BEGIN PRIVATE KEY-----`와 `END` 줄을 뺀 Base64 본문을 개행 없이 한 줄로
환경변수 `APPLE_SIGNING_KEY`에 넣는다. 서버는 공백과 개행을 제거하고 Base64 디코드해
`KeyFactory.getInstance("EC").generatePrivate(new PKCS8EncodedKeySpec(bytes))`로 만든다(표준
라이브러리, 신규 의존성 없음). 파싱은 첫 호출 때 한 번 하고 필드에 보관한다. 값이 비어 있으면 파싱하지
않고 `ApiException(OAUTH_PROVIDER_ERROR)`를 던지며 "애플 서명 키 미설정" warn 로그를 남긴다(D-10).

## 도메인 로직

### 흐름

```text
AuthController.oauthLogin (기존, 한 줄 변경)
  parseProvider("apple") → APPLE → resolveDeviceId
  → oidcLoginService.login(APPLE, request, deviceId)      (DTO 통째로 전달)
  → X-Device-Id 헤더 + applyTransport(app → 본문)

OidcLoginService.login(provider, request, deviceId)        (신규 오버로드, 트랜잭션 없음. 기존 String 오버로드는 위임)
  1. verifiers.get(provider) 없음 → 2422
  2. info = verifier.verify(request.idToken(), request.nonce())            (JWKS 조회 포함, 외부 I/O)
       AppleOidcIdTokenVerifier: nonce 부재 → 2421 / 디코더(서명·iss·aud·exp) → 2421 / 클레임 해시 대조 → 2421
       KakaoOidcIdTokenVerifier: nonce 인자 무시 (모바일 카카오 nonce 미도입, PRD 미해결 4)
  3. APPLE 이고 authorizationCode 공백 → 2423                               (DB 접근 전)
  4. exists = userRepository.findByProviderAndOid(provider, info.oid()).isPresent()
       (트랜잭션 밖 단건 SELECT. 리포지토리 자체의 readOnly 경계에서 실행되고 바로 닫힌다)
  5. exchanged = (exists 아님 && APPLE) ? appleTokenClient.exchange(request.authorizationCode()) : null
       (외부 HTTP, 트랜잭션 밖. 실패는 2423/2502 로 전파되고 아무것도 저장되지 않는다, D-8)
       exchanged 있음 → appleOidcIdTokenVerifier.verifySubject(exchanged.idToken()) 가 info.oid() 와 다르면 2423
  6. encrypted = exchanged 있음 ? cipher.encrypt(exchanged.refreshToken()) : null   (트랜잭션 밖, CPU 만)
  7. return transactionTemplate.execute(status ->
         issue(provider, info, deviceId, request.fullName(), encrypted))    (쓰기 경계는 여기 하나)

issue(provider, info, deviceId, fullName, encrypted)       (private, 열린 트랜잭션 안에서만 호출)
  a. user = findByProviderAndOid ?: registerNewUser(provider, info, resolveNickname(info.nickname(), fullName))
       registerNewUser: email 중복 → 1409 / insertOAuthUserIgnoreConflict → 재조회, 부재면 1409 (기존)
  b. encrypted 있음 → user.storeAppleRefreshToken(encrypted)              (더티 체킹 UPDATE)
  c. 액세스 1시간 + 리프레시 2주 발급 (기존 그대로)

issueForOidcUser(provider, info, deviceId)                  (기존 공개 @Transactional, dev 모의 로그인 전용)
  → issue(provider, info, deviceId, null, null). 교환 없음 (FR-12)
```

교환 왕복과 JWKS 조회는 전부 DB 트랜잭션 밖에서 끝난다. MSG-345가 카카오 교환을 컨트롤러 단계에 둔 결정,
`docs/audit/2026-09-08-backend-audit.md` 트랜잭션 렌즈(트랜잭션 안 외부 I/O를 P1 검토 항목으로 분류),
2026-08-19 멘토링의 트랜잭션 범위 지적과 같은 방향이다. "교환 여부가 DB 조회 결과에 달려 있다"는 사정은
트랜잭션 밖에서 조회해도 그대로 성립하므로 경계 안에 둘 이유가 되지 않는다(D-8).

### `OidcIdTokenVerifier` 계약 변경 (auth 내부 인터페이스, Owner B 단독)

`OidcUserInfo verify(String idToken)` → `OidcUserInfo verify(String idToken, String nonce)`.
`nonce`는 대조 기대값 원문이고 null이면 제공자가 대조를 생략할 수 있다. Javadoc의 "provider 추가는 구현체와
JwtDecoder 빈만"은 "nonce 대조가 필요한 provider는 이 인자를 쓴다"로 보강한다. 카카오 구현체는 인자를
받기만 하고 쓰지 않는다(주석으로 이유 명시). 기존 테스트의 `verify("id-token")` 스텁은
`verify("id-token", null)`로 바뀐다.

기본 메서드로 우회(`default verify(idToken, nonce) { return verify(idToken); }`)하지 않는 이유: Mockito
mock은 기본 메서드도 스텁 대상이라 기존 테스트가 어차피 바뀌고, nonce를 조용히 버리는 기본 구현은 새
provider가 실수로 대조를 빠뜨리게 만든다.

### `AppleOidcIdTokenVerifier` (신규, `auth/oidc/`)

`@Component`, `@Qualifier("appleJwtDecoder") JwtDecoder` 주입 (카카오 구현체와 같은 형태).

```text
verify(idToken, nonce):
  nonce 공백 → warn("애플 로그인 요청에 nonce 없음") → 2421          (디코더 호출 전)
  jwt = appleJwtDecoder.decode(idToken)   JwtException → 2421 (cause 체이닝)
  expected = SHA-256(nonce, UTF-8) 을 소문자 16진 64자로
  claim = jwt.getClaimAsString("nonce")
  claim 없음 또는 MessageDigest.isEqual(expected, claim) 거짓 → warn("nonce 클레임 불일치", 원문 금지) → 2421
  return OidcUserInfo(jwt.getSubject(), jwt.getClaimAsString("email"), null)

verifySubject(idToken):                                    (교환 응답 id_token 전용, 인터페이스 밖 공개 메서드)
  jwt = appleJwtDecoder.decode(idToken)   JwtException → 2423 (cause 체이닝, 서명·iss·aud·exp 전부 같은 디코더)
  return jwt.getSubject()
```

`verifySubject`가 nonce를 대조하지 않는 이유: 이 토큰은 앱을 거치지 않고 서버가 애플 토큰 엔드포인트에서
TLS로 직접 받은 응답이라, nonce가 막는 "다른 시도의 토큰을 클라이언트가 다시 보내는" 경로가 없다. 필요한
결속은 요청 ID 토큰(이미 nonce까지 통과)과 같은 `sub`인지 하나이고, 그 비교는 `OidcLoginService`가 한다.
실패 코드가 2421이 아니라 2423인 이유는 잘못된 것이 요청의 ID 토큰이 아니라 인가 코드 쪽이기 때문이다.
`OidcLoginService`는 이 메서드 때문에 `AppleOidcIdTokenVerifier`를 구체 타입으로 한 번 더 주입받는다
(검증기 맵은 인터페이스라 이 메서드가 없다).

닉네임이 null인 이유: 애플 ID 토큰에는 이름이 없다(애플 문서 기준). 이름은 요청 body의 `fullName`으로
따로 온다. `email_verified`와 `is_private_email` 클레임은 읽지 않는다(저장할 자리가 없고 요구사항도 없다).

### `OidcDecoderConfig.appleJwtDecoder` (빈 추가)

카카오 빈과 같은 조립: `NimbusJwtDecoder.withJwkSetUri(properties.jwkSetUri())`에
`JwtValidators.createDefaultWithIssuer(issuer)`(만료 포함)와 기존 `audienceValidator(Set.of(bundleId))`를
`DelegatingOAuth2TokenValidator`로 묶는다. JWKS[^7] 캐시와 모르는 `kid` 재조회는 Nimbus 기본 동작이라
추가 코드가 없다(PRD 비기능 보안의 "주기적 캐시, 키 바뀌면 재조회"). `audienceValidator`의 실패 설명 문구
"허용된 카카오 앱 키가 아닙니다"는 provider 중립("허용된 audience 가 아닙니다")으로 한 줄 바꾼다. 이
문구는 `JwtException` 메시지로만 남고 클라이언트 응답에는 실리지 않는다.

### `AppleTokenClient` (신규, `auth/oidc/`)

PRD 6절 이름 그대로. `Exchanged exchange(String authorizationCode)`, `void revoke(String refreshToken)`.
`Exchanged`는 `record Exchanged(String refreshToken, String idToken)`로 이 클래스 안에 중첩한다(신규
파일 없음). HTTP는 spring-web 내장 RestClient, 폼 인코딩과 `JsonNode` 파싱과 예외 매핑은
`KakaoAuthCodeExchanger` 선례를 그대로 따른다. 이 클래스는 호출과 파싱만 하고 `id_token`을 검증하지
않는다. 검증과 `sub` 대조는 `AppleOidcIdTokenVerifier.verifySubject`와 `OidcLoginService` 몫이다.

- `exchange` 예외 매핑: `RestClientResponseException` 4xx이고 body `error=invalid_grant` →
  `INVALID_AUTHORIZATION_CODE`(2423). 그 외 4xx(`invalid_client`는 우리 client_secret 문제라 사용자
  재시도로 안 풀린다), 5xx, `RestClientException`(연결 실패, 타임아웃) → `OAUTH_PROVIDER_ERROR`(2502).
  2xx인데 `refresh_token`이나 `id_token`이 없거나 공백 → 2502 (카카오의 "id_token 없음 → 2423"과 다른
  이유: 그쪽은 FE의 scope 누락이 원인이지만 여기서는 우리가 통제할 수 없는 애플 응답 이상이다).
- `revoke`는 매핑하지 않고 예외를 그대로 전파한다. 호출자(`UserServiceImpl`)가 best-effort로 감싼다.
- 로그 금지 항목: 인가 코드 원문, 리프레시 토큰 원문(암호문 포함), 클라이언트 비밀 JWT, ID 토큰 원문.
  애플 에러 응답의 `error` 값과 HTTP 상태만 남긴다.
- 주입: `RestClient appleTokenRestClient`(필드명 = 빈 이름, by-name), `AppleOidcProperties`,
  `ObjectMapper`, `Clock`. `Clock`은 `BadgeAwardServiceImpl` 선례처럼 프로덕션 생성자가
  `Clock.systemUTC()`를 고정하고 전체 생성자는 테스트용이다.

### `AppleTokenClientConfig` (신규, `auth/oidc/`)

`KakaoTokenClientConfig`를 미러링한 완성 RestClient 빈 `appleTokenRestClient`. 연결 1초, 읽기 3초
상수. baseUrl은 두지 않고 호출부가 `properties.tokenUri()`와 `properties.revokeUri()`를 절대 URI로
쓴다(엔드포인트가 둘이라 baseUrl 하나에 못 묶는다). 완성 RestClient 빈은 이로써 세 개
(`kakaoLocalRestClient`, `kakaoTokenRestClient`, `appleTokenRestClient`)라 by-type 주입은 이미 깨져
있고, 모든 주입처가 필드명 = 빈 이름 규칙을 지킨다. `RestClient.Builder` 빈은 만들지 않는다(`AiClient`가
Builder를 by-type으로 받는 제약, MSG-345 기록). `SearchConfig` 주석이 빈 개수를 적고 있으면 사실에 맞게
한 줄 갱신한다.

### `AppleRefreshTokenCipher` (신규, `auth/oidc/`)

`String encrypt(String plain)`, `String decrypt(String encrypted)`. AES-256-GCM, IV 12바이트 무작위
(`SecureRandom`), 출력은 `Base64(IV ∥ 암호문 ∥ 태그)`. 구현은 이미 클래스패스에 있는 spring-security-crypto의
`AesBytesEncryptor(SecretKey, BytesKeyGenerator, CipherAlgorithm.GCM)`을 쓰거나, 그 생성자 조합이 버전
문제로 안 맞으면 `javax.crypto.Cipher("AES/GCM/NoPadding")` 직접 호출로 대체한다(둘 다 신규 의존성
없음, 위 형식 계약만 지키면 된다). 키는 `oauth.apple.token-encryption-key`(Base64 32바이트,
`openssl rand -base64 32`로 생성). 값이 비어 있으면 첫 호출에서 `IllegalStateException`("애플 토큰
암호화 키 미설정")이다. 키 로테이션은 지원하지 않는다(재암호화 배치가 필요해지면 그때, D-3).

### `OidcLoginService` 변경

- 신규 오버로드 `login(AuthProvider, OidcLoginRequestDto, String deviceId)`. 기존
  `login(AuthProvider, String idToken, String deviceId)`는 `new OidcLoginRequestDto(idToken, null,
  null, null)`로 위임만 한다. 웹 인가 코드 경로(`oauthCodeLogin`)와 그 테스트는 손대지 않는다.
- **트랜잭션 경계 정리.** `login` 두 오버로드에서 `@Transactional`을 뗀다. 오케스트레이션(검증, 존재
  조회, 교환, 암호화)은 전부 트랜잭션 밖이고, 쓰기(find-or-create, 토큰 저장, 리프레시 발급)만 새 private
  `issue(...)`에 모아 `login`이 `transactionTemplate.execute(status -> issue(...))`로 감싼다.
  `TransactionTemplate`을 쓰는 이유는 자기 호출 함정이다: 같은 클래스 안에서 `login`이 `@Transactional`
  붙은 `issueForOidcUser`를 부르면 프록시를 거치지 않아 트랜잭션이 열리지 않는다. `PasswordService`가
  같은 이유로 이미 이 방식이다(MSG-497·MSG-537의 `TransactionTemplate` 경계). `issueForOidcUser`는
  기존 공개 시그니처와 `@Transactional`을 그대로 두고 본문만 `issue(provider, info, deviceId, null,
  null)` 위임으로 바꾼다. `DevAuthController`는 다른 빈에서 프록시를 통해 부르므로 트랜잭션이 정상으로
  걸리고, 교환 인자가 null이라 애플 왕복도 없다(FR-12 그대로). `issue`가 트랜잭션 없이 호출될 경로는
  없다(`login`은 템플릿 안, `issueForOidcUser`는 프록시 안). 주입 추가: `TransactionTemplate`(기존 빈,
  `PasswordService` 선례).
- 5단계의 `sub` 대조: `appleOidcIdTokenVerifier.verifySubject(exchanged.idToken())`가 돌려준 값이
  `info.oid()`와 다르면 warn 로그("교환 응답 sub 불일치", 값 원문 금지) 후 2423. 요청의 `idToken`과
  `authorizationCode`가 서로 다른 애플 계정에서 나온 조합을 막는다. 이 검사가 없으면 A 계정 행에 B의
  리프레시 토큰이 저장되고 A가 탈퇴할 때 B의 애플 연결이 취소된다(Codex P2). 교환은 이미 끝난 뒤라
  거절돼도 애플 쪽에는 그 코드로 발급된 세션이 남지만 우리는 저장하지 않으며, 재사용된 인가 코드는
  다음 교환에서 `invalid_grant`로 막힌다.
- `resolveNickname(String claimNickname, String fullName)`: 순서는 제공자 클레임 닉네임(카카오) →
  `fullName`(공백 정리 후 2~20자일 때만) → `"필맵러" + String.format("%04d", ThreadLocalRandom 0~9999)`.
  카카오 토큰에 `nickname` 클레임이 없어 NOT NULL 삽입이 500으로 터지던 잠재 결함도 같은 규칙으로 닫힌다
  (D-12). 닉네임은 중복 허용(FR-USER-03)이라 충돌 검사는 없다.
- 주입 추가: `AppleTokenClient`, `AppleRefreshTokenCipher`, `AppleOidcIdTokenVerifier`(구체 타입,
  `verifySubject` 용), `TransactionTemplate`. 생성자 주입이라 `OidcLoginServiceTest`의 생성 코드가
  인자 넷을 더 받는다(템플릿은 `PasswordService` 테스트처럼 실행만 통과시키는 스텁).
- **동시 첫 로그인 경합(무해).** 같은 `sub`의 첫 로그인 두 요청이 겹치면 4단계에서 둘 다 부재를 보고
  둘 다 교환에 성공할 수 있다(인가 코드는 요청마다 다르다). 쓰기 경계 안에서는 기존
  `insertOAuthUserIgnoreConflict`(ON CONFLICT DO NOTHING)가 한 행만 만들고, 패자는 재조회한 승자 행에
  자기 암호문을 `storeAppleRefreshToken`으로 덮어써 마지막 쓰기가 남는다. 두 리프레시 토큰은 같은
  사용자와 같은 앱의 것이라 어느 쪽이든 유효하고, 애플 문서 기준으로 취소는 사용자와 앱 사이의 권한을
  거두는 호출이라 어느 토큰으로 불러도 같은 연결이 끊긴다. 저장되지 않은 쪽 토큰은 쓰이지 않은 채
  남을 뿐이다. 잠금이나 재시도를 추가하지 않는다.

### `UserServiceImpl.deleteAccount` 변경

```text
deleteAccount(userId, accessToken)
  s3Keys = collectS3Keys(userId)                                   (기존)
  encrypted = userRepository.findAppleRefreshTokenById(userId)     (신규 JPQL 스칼라, Optional<String>)
  deleteUser → 0 이면 1404                                          (기존)
  afterCommit:
    deleteS3Objects(s3Keys)                                        (기존)
    invalidateSessions(userId, accessToken)                        (기존)
    revokeAppleToken(userId, encrypted)                            (신규, encrypted 부재면 아무것도 안 함)
```

`revokeAppleToken`은 `invalidateSessions`와 같은 꼴로 `try { appleTokenClient.revoke(cipher.decrypt(
encrypted)) } catch (RuntimeException e) { log.error(...) }`이다. 복호화 실패도 같은 catch에 든다.
읽기를 삭제 전에 하는 이유는 S3 키 수집과 같다. `deleteUser`가 지운 뒤에는 컬럼을 읽을 경로가 없다.
`findAppleRefreshTokenById`는 `findProfileImageUrlById`와 같은 이유(벌크 JPQL DELETE 앞이라 엔티티를
띄우지 않는다)로 스칼라 조회다. `UserServiceImpl`이 `AppleTokenClient`(auth 패키지)를 갖는 것은 기존
`RefreshTokenService` 주입과 같은 user→auth 의존이며 둘 다 Owner B 내부라 계약 인터페이스 규칙과
무관하다(클래스 Javadoc의 기존 논리).

### `DevAuthController` (FR-12)

코드 변경 없음이 목표다. `parseProvider`가 `AuthProvider.valueOf`라 열거형에 `APPLE`이 추가되면
그대로 통한다. `DevSocialLoginRequestDto.provider`의 Swagger 설명 "(기본 KAKAO)"에 "APPLE 가능"을
덧붙인다. `issueForOidcUser`는 교환을 모르므로 애플 왕복도 서명 키도 필요 없다. 이렇게 만든 APPLE
계정은 `apple_refresh_token_encrypted`가 null이라 탈퇴 때 취소 호출이 없다(스칼라 조회가 비면 건너뛴다).

### 앱이 지켜야 할 흐름 (서버 계약, 구현 세부는 FE 레인 몫)

1. iOS에서만 애플 버튼을 렌더한다(`Platform.OS === "ios"`). 규격은 카카오 버튼과 같은 폭과 높이
   (검정 pill 62px, 피그마 `16015:540`), 순서는 카카오 위와 애플 아래(D-1).
2. 버튼을 누르면 앱이 nonce 원문을 만든다(무작위 32바이트의 16진 표기 권장). 그 원문의 SHA-256 16진
   소문자 값을 `expo-apple-authentication`의 `signInAsync({ requestedScopes: [FULL_NAME, EMAIL],
   nonce: <해시> })`에 넘긴다. 애플 문서 기준으로 애플은 넘겨받은 값을 그대로 `nonce` 클레임에 넣으므로,
   서버가 원문을 해시해 비교하려면 앱이 해시를 넘겨야 한다. 해시가 아니라 원문을 넘기면 서버 대조가
   항상 실패한다(2421).
3. 응답의 `identityToken`, `authorizationCode`, `fullName`(첫 승인에만 값이 있다)을 받아
   `POST /api/auth/oauth/apple`에 `{ idToken, nonce: <원문>, authorizationCode, fullName? }`을
   `X-Client-Type: app` 헤더와 함께 보낸다. `authorizationCode`는 첫 로그인인지 가리지 말고 매번 보낸다.
   `identityToken`이 null이면 서버를 부르지 않고 카카오의 `KAKAO_MISSING_ID_TOKEN`과 같은 부류로 처리한다.
4. `fullName`은 `familyName + givenName`(한국어 이름은 붙여 쓰고, 둘 중 하나만 있으면 그것만)으로
   조립한 한 문자열이다. 서버는 2~20자가 아니면 기본 닉네임으로 대체하므로 앱이 길이를 맞출 필요는 없다.
5. 첫 로그인 요청이 서버 오류(2502 등)로 실패하면 다음 시도에는 애플이 이름을 다시 주지 않아 기본
   닉네임이 붙는다. 앱이 그 세션 동안 `fullName`을 메모리에 들고 있다가 재시도에 다시 실어 보내면
   이를 피할 수 있다(권장, 필수 아님. 닉네임은 어차피 사용자가 바꿀 수 있다).
6. 사용자가 시트에서 취소하면(`ERR_REQUEST_CANCELED`) 아무 안내 없이 로그인 화면에 머문다. 네트워크와
   서버 오류는 카카오와 같은 실패 안내다(FR-13).
7. 응답 처리(토큰 저장, `X-Device-Id` 헤더 저장, 세션 캐시 초기화, 이동)는 `kakao-login-mutation.ts`와
   동일하다. `app.config.js`에 `ios.usesAppleSignIn: true`와 플러그인 등록이 필요하다.

## 데이터 모델

### V54 마이그레이션 `V54__apple_provider.sql` (신규)

```sql
-- 애플 로그인 (MSG-594). CHECK 개정과 토큰 보관 컬럼 추가. 롤백은 역방향 ALTER 두 문장.
ALTER TABLE users DROP CONSTRAINT chk_users_provider;
ALTER TABLE users ADD CONSTRAINT chk_users_provider CHECK (provider IN ('LOCAL', 'KAKAO', 'APPLE'));

-- 애플 리프레시 토큰의 AES-256-GCM 암호문(Base64). 탈퇴 시 취소 호출에만 쓴다. APPLE 이 아니거나
-- dev 모의 로그인으로 만든 계정은 NULL.
ALTER TABLE users ADD COLUMN apple_refresh_token_encrypted TEXT;
```

`chk_users_provider`는 V1 이후 개정된 적이 없다(마이그레이션 전수 grep). `chk_users_auth`
(`provider <> 'LOCAL' AND oid IS NOT NULL`)는 애플 계정도 `oid=sub`를 가지므로 그대로 통과한다.
애플 `sub`는 44자 안팎이라 `oid VARCHAR(64)`에 들어간다(애플 문서 기준 형식 `001234.abcd...1234`).
별도 테이블 대신 컬럼을 택한 근거는 D-3.

### 엔티티

- `AuthProvider`에 `APPLE` 추가.
- `User`에 `@Column(name = "apple_refresh_token_encrypted", columnDefinition = "text")
  @Getter(AccessLevel.NONE) private String appleRefreshTokenEncrypted;`와
  `public void storeAppleRefreshToken(String encrypted)` 추가. 게터를 막는 이유는 클래스 레벨 `@Getter`가
  만든 접근자를 응답 DTO가 실수로 싣는 일을 원천 차단하기 위해서다. 읽기는 탈퇴 경로의 스칼라 JPQL 하나뿐이다.
- `UserRepository`에 `@Query("SELECT u.appleRefreshTokenEncrypted FROM User u WHERE u.id = :userId")
  Optional<String> findAppleRefreshTokenById(@Param("userId") Long userId)` 추가.
- 신규 native 쿼리 없음. `insertOAuthUserIgnoreConflict`는 그대로 쓰고 토큰은 재조회한 관리 엔티티의
  더티 체킹으로 저장된다(JPA 수칙 4: 조회와 갱신은 JPQL과 더티 체킹 우선).

## 결정 항목

- **D-1 버튼 순서: 카카오 위, 애플 아래** (PRD 미해결 질문 1, 제안값 채택). 시안 `16015:540`이 이
  순서이고 국내 앱의 관례다. 애플 HIG가 요구하는 것은 크기(다른 소셜 버튼보다 작지 않게)와 가시성(스크롤
  없이 보이게)으로 알고 있으며 순서를 강제하는 문구는 확인하지 못했다. FE 레인이 버튼 구현 시 HIG
  원문을 한 번 더 보고, 순서 강제가 확인되면 두 버튼을 바꾸는 것으로 끝난다(서버 무관).
- **D-2 기본 닉네임: `필맵러` + 4자리 숫자** (PRD 미해결 질문 2, 제안값 채택). 7자라 2~20자 제약 안이고
  `ThreadLocalRandom`이면 충분하다(보안 값이 아니다). 중복은 허용이라 충돌 검사가 없다.
- **D-3 애플 리프레시 토큰 보관: `users` 컬럼 + AES-256-GCM, 키는 환경변수** (PRD 미해결 질문 3).
  별도 `user_provider_credentials` 테이블은 제공자가 둘 이상 될 때의 구조인데 지금은 애플뿐이고, 이
  값은 가입 때 한 번 쓰고 탈퇴 때 한 번 읽는다. 조인도 생명주기 관리도 없는 컬럼이 가장 짧다. 구글 등이
  붙으면 그때 테이블로 옮긴다(컬럼 하나 이전이라 비용이 작다). 암호화는 PRD 비기능이 요구한 것이며
  방식은 위 `AppleRefreshTokenCipher` 절. 키 로테이션은 미지원(재암호화 배치가 필요해지면 도입).
- **D-4 nonce 대조 방식: 요청 본문 원문을 SHA-256 해시해 클레임과 상수 시간 비교, 검증기 계약에 nonce
  인자 추가, 실패는 2421 수렴.** 웹 카카오(MSG-345)의 쿠키 결속과 다른 이유는 애플 네이티브 흐름에
  브라우저가 없어 결속할 쿠키가 없고, 애플이 해시된 nonce를 클레임으로 되돌려 주는 방식이 표준이기
  때문이다. 요청과 함께 오는 nonce는 자기 증명에 그친다는 MSG-345의 지적은 여기서도 사실이다. 이
  대조가 막는 것은 다른 로그인 시도에서 가로챈 ID 토큰의 재사용(그 토큰의 클레임은 그 시도의 해시라
  이번 원문과 맞지 않는다)이며, 앱과 서버가 함께 통제하는 값이라 PRD FR-11이 요구한 범위와 같다.
- **D-5 애플 서버 알림 수신: 이번 범위 밖 유지** (PRD 미해결 질문 5, 비목표 유지). 심사 필수가 아니고
  엔드포인트 등록과 서명 검증이 별도 작업이다. 결과로 사용자가 아이폰 설정에서 연결을 끊은 뒤 다시
  로그인하면 우리가 보관한 리프레시 토큰이 낡은 값이 되고, 탈퇴 때 취소 호출이 `invalid_grant`로
  실패해 로그만 남는다. 재로그인 때 교환을 다시 해서 갱신하는 안은 PRD의 "첫 로그인 한 번"과 어긋나
  택하지 않았다. 알림 수신을 붙이면 이 낡음이 해소된다.
- **D-6 dev와 prod의 번들 ID: 단일 `kr.fillmap.app`** (PRD 미해결 질문 6). `app.config.js`에 iOS
  `bundleIdentifier`가 하나뿐이고 dev 빌드용 분기가 없다(2026-09-10 확인). aud 허용 집합은 값 하나이며
  공통 `application.yml`의 `oauth.apple.bundle-id`에 둔다(카카오 `app-client-id`처럼 앱에 포함되는
  공개 식별자). dev 빌드가 다른 번들 ID를 쓰게 되면 `application-dev.yml`에 한 줄 오버라이드하면 된다.
  서명 키와 Team ID는 애플 개발자 계정 단위라 dev와 prod가 같은 값을 쓴다.
- **D-7 디자인 정본 승격: FE와 디자이너 몫, 서버 계약과 무관** (PRD 미해결 질문 7). 이 스펙의 서버
  계약은 버튼 위치와 색에 의존하지 않는다. 시안 기준으로 진행하고 승격은 FE 레인이 추적한다.
- **D-8 인가 코드 교환 시점과 실패 정책: 계정이 없을 때만, DB 트랜잭션 밖에서, 교환 응답의 `id_token`
  `sub`를 요청 토큰과 대조하고, 실패는 fail-closed** (2026-09-10 스펙 리뷰로 재결정, 초안은 트랜잭션
  안이었다). 초안의 근거("교환 여부가 DB 조회 결과에 달려 있다")는 트랜잭션 밖에서 조회해도 성립하므로
  경계 안에 둘 이유가 못 됐고, 트랜잭션 안 외부 I/O는 MSG-345 결정(카카오 교환은 컨트롤러 단계),
  `docs/audit/2026-09-08-backend-audit.md` 트랜잭션 렌즈의 P1 검토 항목, 2026-08-19 멘토링의 트랜잭션
  범위 지적과 전부 어긋난다. 구조는 `login`을 트랜잭션 없는 오케스트레이션으로 두고 검증(JWKS 포함),
  존재 조회, 교환, `sub` 대조, 암호화를 밖에서 끝낸 뒤 쓰기만 `TransactionTemplate` 경계 하나에 넣는다
  (자기 호출 주의와 `issueForOidcUser` 경로 유지는 `OidcLoginService` 변경 절). 교환 응답의 `id_token`을
  같은 `appleJwtDecoder`로 검증해 `sub`가 요청 ID 토큰의 `sub`와 같을 때만 저장한다(Codex P2 채택,
  불일치는 2423). 교환이 실패하거나 `sub`가 다르면 계정을 만들지 않는다(2423 또는 2502). 토큰 없이
  가입을 허용하면 그 계정은 탈퇴 때 애플 취소를 영원히 못 하는데, 그것이 심사가 보는 요건이고, 사용자
  재시도 비용은 시트를 한 번 더 여는 것뿐이다. 동시 첫 로그인의 이중 교환은 마지막 쓰기가 남는 무해한
  경합이라 잠금을 두지 않는다(같은 절의 경합 항목).
- **D-9 탈퇴 시 취소: 커밋 이후 best-effort, 실패는 error 로그.** PRD FR-9 그대로. S3 정리와 세션
  무효화와 같은 `afterCommit` 묶음에 들어가고 각자 독립 try-catch다.
- **D-10 클라이언트 비밀: 호출마다 5분짜리 ES256 JWT를 jjwt로 생성, 서명 키는 환경변수 Base64 한 줄,
  파싱은 첫 호출 때, 미설정이면 2502.** 기동 시 파싱하면 키가 없는 로컬 개발자가 부팅을 못 하고, 로컬은
  dev 모의 로그인(FR-12)으로 충분하다. 대신 prod는 `ProdRequiredEnvValidator`에 `APPLE_TEAM_ID`,
  `APPLE_KEY_ID`, `APPLE_SIGNING_KEY`, `APPLE_TOKEN_ENCRYPTION_KEY`를 등록해 미설정이면 기동 실패다.
- **D-11 이름 처리: `fullName`은 계정 생성 때만, 2~20자 밖이면 기본 닉네임.** 자르면 이름이 이상하게
  남고, 400으로 거절하면 이름이 긴 사용자가 가입을 못 한다. 기본값으로 떨어뜨리고 사용자가 바꾸게 둔다
  (닉네임 변경 API는 이미 있다, MSG-203).
- **D-12 닉네임 기본값은 제공자 공통 규칙.** 애플 전용 분기 대신 `resolveNickname` 한 곳이 카카오
  클레임 부재도 같이 받는다. 지금은 카카오 `nickname` 클레임이 없으면 NOT NULL 위반 500인데, 요구사항
  변경이 아니라 잠재 결함 제거라 이 티켓에 얹는다.

## 미해결 질문

없음. PRD 8절의 7건 중 4는 PRD에서 닫혔고(nonce Must), 1과 2는 제안값 채택(D-1, D-2), 3과 5와 6과 7은
이 스펙이 결정했다(D-3, D-5, D-6, D-7). 확인하지 못한 것 하나는 D-1의 애플 HIG 순서 강제 여부이며, 어느
쪽이든 서버 변경 없이 FE가 버튼 순서만 바꾸면 되므로 미해결로 남기지 않는다.

[^1]: ID 토큰: 로그인 제공자가 "이 사용자가 방금 인증됐다"를 증명하려고 서명해 주는 JWT. 사용자 식별자(sub)와 이메일과 발급자와 대상과 만료가 들어 있어 서버는 서명만 확인하면 제공자에게 다시 묻지 않아도 된다. 애플은 여기에 이름을 넣지 않는다.
[^2]: nonce: 앱이 로그인 시도마다 새로 만드는 일회용 임의 값. 앱이 해시를 애플에 넘기면 애플이 ID 토큰 클레임에 그 해시를 넣어 돌려주고, 서버는 앱이 보낸 원문을 해시해 대조한다. 다른 시도에서 가로챈 ID 토큰을 이번 요청에 다시 쓰는 것을 막는다.
[^3]: 인가 코드: 애플 시트가 로그인 직후 앱에 주는 1회용 짧은 코드. 그 자체로는 신원 정보가 없고 5분 안에 한 번만 토큰 엔드포인트에서 진짜 토큰으로 바꿀 수 있다. 여기서는 탈퇴 때 취소에 쓸 리프레시 토큰을 얻는 용도다.
[^4]: 클라이언트 비밀: 애플 토큰 API가 "이 요청은 필맵 서버가 보냈다"를 확인하는 값. 고정 문자열이 아니라 애플 개발자 계정의 서명 키(.p8)로 서버가 서명한 짧은 수명의 JWT라, 키 파일만 지키면 비밀이 새지 않는다.
[^5]: 토큰 취소: 애플의 `/auth/revoke` 호출로 우리 앱에 준 권한을 거둬들이는 것. 앱스토어는 계정 삭제를 제공하는 앱이 삭제 때 이 호출을 하도록 요구한다. 호출하려면 애플이 준 리프레시 토큰이 필요해서 첫 로그인 때 인가 코드를 교환해 둔다.
[^6]: AES-256-GCM: 대칭키 암호화 방식 하나. 같은 원문도 호출마다 다른 IV(초기값)로 다른 암호문이 되고, 복호화 때 인증 태그로 변조를 잡아낸다. DB가 통째로 유출돼도 키 없이는 토큰을 읽을 수 없게 하는 장치다.
[^7]: JWKS: 제공자가 토큰 서명에 쓰는 공개키 묶음을 내려주는 주소(`/auth/keys`). 서버는 이 공개키로 ID 토큰 서명을 검증한다. 애플이 키를 바꿔도 모르는 키 ID가 오면 라이브러리가 다시 받아 오므로 재배포가 필요 없다.

- **빈 동작**: `login(provider, request, deviceId)`에 `@Transactional` 없음(`TransactionInterceptor` 로그 부재 실측). 검증(JWKS 포함)·존재 조회·교환·sub 대조·암호화가 끝난 뒤 `JpaTransactionManager: Creating new transaction with name [null]`(TransactionTemplate 표식) 안에서만 find-or-create·UPDATE·발급. `issue`는 private이라 자기 호출 함정 없음. `issueForOidcUser`(DevAuthController 경유)는 프록시로 `Creating new transaction with name [...issueForOidcUser]` 정상. `JwtDecoder` 빈이 둘(`kakaoJwtDecoder`·`appleJwtDecoder`)이고 검증기의 `@Qualifier`는 Lombok이 생성자로 복사하지 않아 파라미터명 = 빈 이름 폴백으로 해소(javap 실측, 실패 시 `NoUniqueBeanDefinitionException` fail-loud). `appleTokenRestClient`는 완성 RestClient 빈 3호(by-name, connect 1s/read 3s). `appleJwtDecoder`는 Nimbus 기본 JWKS 캐시(모르는 kid면 재조회). `AppleTokenClient`의 서명 키는 첫 호출 때 파싱해 volatile 필드 보관(잠금 없음, 멱등). `Clock`은 레포에 빈이 없어 `Clock.systemUTC()` 생성자 고정(BadgeAwardServiceImpl 선례). 탈퇴 afterCommit 순서 `deleteS3Objects → invalidateSessions → revokeAppleToken`, 각자 독립 try-catch. dev 프로파일에서 env 부재 시 리터럴 `${APPLE_TOKEN_ENCRYPTION_KEY}`가 바인딩돼 cipher 생성자 Base64 디코드가 터져 컨텍스트 기동 실패하던 것을 `${APPLE_*:}` 빈 기본값으로 해소(D-10 "부팅되고 애플만 2502"). prod는 기본값 없음 + 검증기.
