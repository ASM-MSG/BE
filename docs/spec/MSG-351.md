# MSG-351: 업로드 확정 전 하이라이트 선분석 API

**Owner**: B

> 요구사항 정본: `docs/prd/MSG-351-prd.md` (검토됨, 2026-08-10 성민 승인). 이 스펙은 PRD의
> FR 8건과 비기능 요구에 "어떻게"만 붙인다. PRD와 어긋나는 서술이 보이면 PRD가 이긴다.
> AI 쪽 계약(MSG-353)은 구현과 dev 배포, 실측까지 완료됐다. 계약 정본은 FillMap-AI README의
> "API" 절이고, 실측 수치 정본은 FillMap-AI `results/MSG-353-report.md`다.

## 개요

업로드 위저드의 "AI 하이라이트 추천" 단계(2단계)가 소비할 선분석 API를 만든다. 사용자가
업로드를 확정하기 전의 원본 영상(30초 초과 가능, 3분 이하)에 대해 AI 하이라이트 구간을
동기[^1]로 받아 FE에 돌려준다. 결과는 저장하지 않는 임시 값이며(PRD 비목표), 확정본의
하이라이트는 기존 블러 파이프라인이 따로 계산해 저장하고 MSG-350이 노출한다.

## 배경 · 목표

하이라이트는 지금 업로드 확정 뒤 블러 파이프라인 안에서만 계산돼(웜 기준 약 4분) 위저드
추천 화면(MSG-303)이 mock으로만 동작한다. 하이라이트 계산만 떼면 30초 1080p 기준 실측
3~5초라, 위저드 안에서 몇 초 기다려 추천을 받는 UX가 성립한다. AI 쪽 전용 엔드포인트
(MSG-353)는 이미 dev에 떠 있으므로 이 티켓은 BE 몫만 담는다: 인증된 선분석 요청 API,
3분 상한 서버 방어선, FE가 직접 지정으로 폴백할 수 있는 실패 응답 계약, Swagger 명시.

**범위 밖** (PRD 비목표 재확인): 블러는 기존 확정 후 파이프라인 그대로다. 선분석 결과의
저장이나 확정 업로드와의 연결은 없다. 영상 길이별 카드 노출 티어(5초 이하 스킵 등)는 FE
정책이라 서버는 계산된 구간을 전부 내려준다. 추천 사유 라벨은 만들지 않는다. 다운스케일
(FR-5)과 블러 잡 경합 회피(FR-7)는 AI 서버 몫으로 MSG-353에서 이미 구현됐고, BE는 그
실측값을 타임아웃 설계에만 반영한다. MSG-350(READY 후 단건 조회 노출)과는 접점이 없다.

## 성공 기준

1. JWT 인증 사용자가 자기 pending 키로 요청하면 200과 함께 `[[시작초, 끝초], ...]` 최대
   3구간이 온다. 배열 순서가 추천 우선순위다 (FR-1, FR-2, FR-3).
2. 5초 미만 원본은 200과 빈 배열 `[]`이 온다 (FR-4, FE는 추천 단계를 스킵한다).
3. 3분(180초) 초과 원본은 실측 길이 기준으로 3425 거부된다 (FR-8 서버 방어선).
4. AI 서버 다운, 타임아웃, AI 비활성 환경에서는 3502 하나로 수렴하고, 열 수 없는 원본은
   3426으로 거부된다. FE는 이 실패 응답을 받고 직접 구간 지정으로 폴백한다 (FR-6).
5. Swagger에 요청과 응답 형식, 빈 배열의 의미, 에러 계약이 명시된다.
6. 선분석 결과는 어디에도 저장되지 않고(DB 변경 0), 서버 임시 파일은 성공이든 실패든
   정리된다 (비기능 운영).
7. 기존 presign[^2] 발급 호출(purpose 미지정)은 동작이 바이트 하나 변하지 않는다.

## API 명세

### 신규: 하이라이트 선분석

- **Endpoint**: `POST /api/videos/highlight-preview`
- **인증**: JWT 필수 (`@AuthenticationPrincipal AuthPrincipal`, 기존 관례)
- **요청**: `HighlightPreviewRequestDto`

| 필드 | 타입 | 검증 | 설명 |
|------|------|------|------|
| `s3Key` | String | `@NotBlank` | FE가 presign으로 올린 원본의 pending 키. `videos/pending/{내 userId}/` prefix여야 한다 |

- **응답**: `SuccessResponse<HighlightPreviewResponseDto>`

| 필드 | 타입 | 설명 |
|------|------|------|
| `highlights` | `List<List<Double>>`, non-null | `[[시작초, 끝초], ...]` 최대 3구간, 초는 소수점 둘째 자리, 배열 순서가 추천 우선순위(첫 요소가 최우선). 각 구간은 5초 이상이고 시작점끼리 5초 이상 벌어진다. 5초 미만 원본이거나 조건을 채우는 구간이 없으면 빈 배열 `[]` |

MSG-350의 null 통일 규약과 다르게 여기는 **빈 배열을 그대로 내린다**. MSG-350의 null은
"계산 안 됨과 0구간이 저장 계약상 구분 불가"의 수렴이었고, 이 API는 성공 응답이 곧 "분석이
돌았다"는 뜻이라 `[]`가 "추천 없음, FE 스킵"(FR-4)이라는 유효한 정보다.

- **에러 케이스** (모두 기존 `ApiException` + `GlobalExceptionHandler` 경로):

| HTTP | developCode | 상수 | 조건 |
|------|-------------|------|------|
| 400 | 3401 | `INVALID_S3_KEY` (기존) | 내 `videos/pending/{userId}/` prefix가 아닌 키 |
| 400 | 3402 | `UPLOAD_NOT_FOUND` (기존) | 키에 해당하는 S3 객체 없음 |
| 400 | 3425 | `HIGHLIGHT_SOURCE_TOO_LONG` (신규) | 실측 길이 180초 초과 (180.00초 정각은 허용) |
| 400 | 3426 | `HIGHLIGHT_SOURCE_UNREADABLE` (신규) | ffprobe[^3]가 파일을 못 열거나 AI가 422 반환 |
| 502 | 3502 | `HIGHLIGHT_UPSTREAM_ERROR` (신규) | AI 서버 연결 실패, 응답 타임아웃, 5xx, 파싱 불능, 응답 형태 위반, S3 다운로드 시한 초과, AI 비활성(`ai.enabled=false`) 환경 |
| 429 | 3429 | `HIGHLIGHT_BUSY` (신규, Codex 2R) | 동시 선분석 허용치(2건) 초과. FE는 3502와 같은 직접 지정 폴백 |
| 401 | 공통 | `UNAUTHORIZED` | 미인증 |

3502는 카카오 검색 프록시의 `SEARCH_UPSTREAM_ERROR(5502)` 단일 수렴 선례를 따른다. FE
대응이 전부 "직접 지정 폴백"으로 같아서(FR-6) 원인 세분화는 소비처 없는 YAGNI고, 원인
구분은 운영 진단용 warn 로그로만 남긴다. 3426만 분리하는 이유는 행위자가 다르기 때문이다:
3502는 재시도하면 될 수 있는 서버 사정이지만 3426은 사용자 파일 자체가 불량이라 재시도가
무의미하고, FE 안내 문구가 달라질 수 있다.

Swagger `@Operation`에 다음을 명시한다: 동기 API라 원본 길이에 따라 응답까지 수 초에서
수십 초 걸림(30초 1080p 기준 5초 내외), 빈 배열은 추천 없음이니 FE는 추천 단계 스킵,
실패(3502, 3426) 시 직접 지정 폴백, 결과는 저장되지 않는 임시 값.

### 변경: presign 발급에 용도 구분 추가

- **Endpoint**: `POST /api/videos/presigned-url` (기존, MSG-64)
- `PresignedUrlRequestDto`에 선택 필드 `purpose` 추가:

| 필드 | 타입 | 검증 | 설명 |
|------|------|------|------|
| `purpose` | String, 선택 | null 허용 | `UPLOAD`(기본, null 동일) 또는 `HIGHLIGHT_PREVIEW`. 선분석 원본 업로드는 `HIGHLIGHT_PREVIEW`로 발급받는다 |

`HIGHLIGHT_PREVIEW`일 때 크기 상한만 다르다: 기존 `max-upload-bytes`(100MB) 대신 신설
`max-highlight-upload-bytes`(기본 2GiB)를 적용한다. 키 prefix(`videos/pending/`), 확장자
검증(mp4, mov), TTL 10분, contentLength 서명 포함은 전부 기존과 동일하다. 오타 등 미지의
purpose 값은 400(공통 `BAD_REQUEST`, `@Valid` enum 파싱 실패 경로 또는 명시 검증)으로
거부한다.

## 도메인 로직

처리 흐름 (전부 `HighlightPreviewServiceImpl` 안, 요청 스레드에서 동기 실행):

1. `s3Key`가 `videos/pending/{userId}/` prefix인지 검사한다. 아니면 3401
   (`confirmUpload`의 첫 가드와 같은 술어).
2. AI 사용 가능 여부를 먼저 본다. `AiClient` 빈이 없으면(AI 비활성 환경) S3를 건드리기
   전에 3502로 끝낸다 (fail fast, S3 호출 낭비 없음).
3. 임시 디렉터리를 만들고 S3에서 원본을 파일로 내려받는다 (`VideoEncodingServiceImpl.download`
   선례, 스트리밍이라 힙 무관). `NoSuchKeyException`이면 3402.
4. `FfmpegRunner.probeDurationSec`으로 실측 길이를 잰다. 180초 초과면 3425, ffprobe 실패
   (손상 파일)면 3426.
5. `AiClient.analyzeHighlights(Path)`로 AI에 multipart[^4] 제출하고 응답 구간 배열을 받는다.
   AI 422는 3426, 나머지 실패(연결, read timeout[^5], 5xx, 파싱 불능)는 3502로 수렴한다.
6. 받은 배열을 그대로 응답에 싣는다 (BE는 구간을 가공하지 않는다. 개수와 길이, 간격 보정은
   MSG-353에서 AI가 이미 보장). finally에서 임시 디렉터리를 정리한다 (`deleteQuietly` 선례).

선분석은 **읽기 전용이고 멱등**하다. pending 키를 클레임하지 않으므로 원본이 30초 이하라
사용자가 자르지 않고 그대로 확정하는 경우 같은 키로 이후 `POST /api/videos` 확정이
가능하고, 같은 키로 선분석을 다시 불러도 부작용이 없다. advisory lock이나 이중 요청 차단은
만들지 않는다 (상태 변화가 없어 지킬 것이 없다).

### 설계 결정 D-1: 원본 전달은 presign 경로 재사용 (FE 직접 업로드 기각)

FE가 기존 presign 발급으로 원본을 S3 `videos/pending/`에 올리고, 선분석 요청에는 그 키만
넘긴다. BE가 S3에서 받아 AI로 전달한다.

근거: BE는 영상 바이트를 FE에게서 직접 받지 않는 것이 확립된 패턴이고(MSG-64, 업로드
확정도 같은 구조), AiClient가 서버 보관 원본을 AI로 multipart 제출하는 구조도 이미 있다
(MSG-149/150). pending 경로를 쓰면 선분석 원본 정리를 기존 1일 만료 라이프사이클[^6]
(MSG-133)에 그대로 편승시킬 수 있어 별도 청소 코드가 필요 없다 (PRD 비기능 운영 항목이
직접 언급한 방식). 기각한 대안(FE에서 BE로 직접 multipart 프록시)은 Tomcat multipart 설정과
대용량 요청 버퍼링을 새로 열고, 영상이 서버에 들어오는 경로를 둘로 갈라놓는다.

### 설계 결정 D-2: 동기 응답 (폴링 기각)

BE가 AI 응답을 받아 같은 HTTP 요청으로 돌려준다.

근거 세 가지. 첫째, AI 계약 자체가 동기다 (MSG-353 확정, `POST /highlights` 200 즉답).
둘째, 폴링을 하려면 잡 상태를 어딘가 저장해야 하는데 "선분석 결과 저장 없음"이 PRD
비목표라 저장소를 만들 수 없다. 셋째, 동기 사용자 경로에 전용 타임아웃과 단일 수렴 에러를
붙이는 선례가 이미 있다 (카카오 검색 프록시, `SearchConfig` + 5502).

스레드 점유는 동시 게이트(2건, Codex 2R에서 추가)와 구간별 시한으로 유계다: S3 다운로드
60초 + probe 30초 + AI 교환 전체 120초 ≈ 요청당 최대 210초, 동시 최대 2스레드. 초과 요청은
3429로 즉시 거부된다. (작성 시점의 "read 60초 상한" 서술은 Codex 리뷰를 거치며 위로 대체됐다)
ponytail: 동시 선분석이 AI 서버(순차 처리)에 줄을 서면 뒤 요청이 타임아웃으로 떨어진다.
사용자가 늘어 실측으로 문제가 되면 전용 executor와 큐 또는 폴링형으로 승격한다.

### 설계 결정 D-3: 3분 상한은 ffprobe 실측으로 검증 (신고 메타데이터 기각)

내려받은 파일을 `FfmpegRunner.probeDurationSec`으로 실측해 `duration > 180.0`이면 3425로
거부한다.

근거: FE 신고값(요청 필드로 받는 길이)은 위조 가능해서 "서버 방어선"(FR-8)이라는 요구
자체를 충족하지 못한다. 인코딩 파이프라인도 30초 상한을 같은 방식으로 실측 재확인한다
(MSG-65 D7 선례). 어차피 AI 전송을 위해 파일을 받아야 하므로 검증만을 위한 추가 다운로드
비용도 없다. 경계는 FE 1차 차단과 같은 기준(3분 초과 거부, 정각 허용)으로 맞춘다.

### 설계 결정 D-4: 선분석 원본 presign 상한 분리 (전역 상한 상향 기각)

기존 상한 100MB는 30초 확정본 기준이라 3분 원본과 충돌한다. 3분 1080p가 약 200~400MB,
4K는 1GB를 넘어서, 상한을 그대로 두면 실사용 3분 원본 대부분이 presign 단계에서 거부돼
FR-1(3분 이하 원본 지원)이 성립하지 않는다. 그래서 `purpose=HIGHLIGHT_PREVIEW` 발급에만
별도 상한을 적용한다.

기본값 2GiB (`aws.s3.max-highlight-upload-bytes`, env `S3_MAX_HIGHLIGHT_UPLOAD_BYTES`).
근거는 최악 케이스 4K 60fps 3분이 약 1.3~2GB라는 것이다. 기각한 대안(전역
`max-upload-bytes` 상향)은 확정 업로드 경로의 크기 방어선까지 20배로 허물어서, 30초
업로드에 2GiB를 허용할 이유가 없다.

### 설계 결정 D-5: 선분석 전용 교환 전체 시한 120초 (기존 폴러 타임아웃 재사용 기각, Codex 2R에서 개정)

`AiClient`에 `analyzeHighlights(Path)`를 추가하되, 이 호출용 클라이언트는 전용으로 하나
더 구성한다. 기존 builder의 read 120초는 블러본 다운로드까지 감싸는 폴러용 값이라 분리한다.

작성 시점에는 `SimpleClientHttpRequestFactory` read 60초였으나 Codex 2R 지적으로 개정됐다:
그 팩토리의 read timeout은 요청 본문 쓰기(최대 2GiB 업로드)를 묶지 못한다. 확정본은
`JdkClientHttpRequestFactory`(java.net.http, connect 5초) 기반이고 readTimeout이 교환
전체(본문 전송 + 처리 + 응답)의 단일 시한이 된다. 값은 의미 변화에 맞춰 120초로 재산정했다:
실측 최악 처리 약 48초(174초 원본 31.87초 + 경합 여유) + 내부망 2GiB 전송 여유. 30초 1080p는
5.28초라 정상 경로는 한참 밑돈다. env 튜닝 수요가 없어 상수로 두고, 필요해지면 프로퍼티로
승격한다. AI 서버 주소는 기존 `ai.base-url`(사설 IP 10.0.1.45:8000)을 그대로 쓴다.

전송은 `byte[]`가 아니라 파일 기반(`FileSystemResource`)으로 한다. 기존 `submit`의
`ByteArrayResource`는 수 MB 인코딩본용이고, 선분석 원본은 GB급일 수 있어 힙에 올리면
t3.small이 죽는다.

## 미해결 질문

없음. PRD 미해결 질문 2건(3분 상한, 티켓 분해)은 2026-08-10 성민 확인으로 해소됐고, 스펙
재량 3건(전달 경로, 동기 여부, 검증 방법)은 D-1, D-2, D-3으로 결정했다. 스펙이 새로 정한
값 중 리뷰에서 봐 줄 지점은 선분석 presign 상한 기본값 2GiB(D-4)와 read timeout 60초(D-5)다.

[^1]: 동기: 요청 하나로 결과까지 받는 방식. 반대는 잡을 걸어 두고 상태를 반복 조회하는 폴링이다. 기존 블러 파이프라인은 3~4분짜리라 폴링이지만, 선분석은 수 초짜리라 같은 요청 안에서 답을 준다.
[^2]: presign(presigned URL): 서버가 서명해 준 기한부 S3 업로드 주소. FE가 영상 바이트를 서버를 거치지 않고 S3에 직접 올리게 해서, BE는 키만 다룬다 (MSG-64 확립 패턴).
[^3]: ffprobe: ffmpeg에 딸린 미디어 검사 도구. 파일을 열어 실제 길이와 형식을 읽는다. FE가 신고하는 값과 달리 위조할 수 없어 서버 방어선 검증에 쓴다.
[^4]: multipart: 파일을 HTTP 요청 본문에 실어 보내는 표준 인코딩. AI 계약(POST /highlights)이 이 형식의 file 필드 하나를 받는다.
[^5]: read timeout: 연결된 뒤 응답 데이터를 기다리는 최대 시간. 이 시간을 넘기면 예외로 끊겨서, AI 서버가 응답을 못 주는 상황에서 사용자 대기와 서버 스레드 점유에 상한을 만든다.
[^6]: 라이프사이클: S3가 규칙에 따라 객체를 자동 삭제하는 기능. `videos/pending/` 아래는 1일 뒤 만료되도록 이미 걸려 있어(MSG-133), 선분석 원본도 올려만 두면 하루 뒤 알아서 사라진다.
