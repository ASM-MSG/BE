# MSG-402: 위치정보 사용 동의 저장과 조회

> **개정 (2026-08-19, MSG-433)**: 위치기반서비스 동의는 철회 불가로 전환됐다(팀 합의, FR-USER-14 개정). 이 문서의 끄기(false) 성공·양방향 토글 서술은 작성 시점 기록이다. 현행 계약은 docs/spec/MSG-433.md D-11·D-12 — 기존 API는 켜기 전용이고 false는 1400 거절.

**Owner**: B (user 도메인 단독. `com.msg.fillmap.user.*`만 변경하고 auth 패키지는 건드리지 않는다)

> 요구사항 정본: `docs/prd/MSG-402-prd.md` (상태: 검토됨) · 상위 요구사항 ID: SRS FR-USER-14
> 이 스펙은 PRD의 FR 1~8에 "어떻게"만 붙인다. 요구사항 해석이 갈리면 PRD가 이긴다.

## 개요

프로필 편집 모달의 "위치정보 사용" 토글과 첫 로그인 온보딩[^1]의 동의 제출을 받쳐줄 서버 저장소와
API를 만든다. `users` 테이블에 동의 여부와 마지막 변경 시각 컬럼을 추가하고, 내 프로필 조회
응답에 동의 여부를 실으며, 동의를 켜고 끄는 엔드포인트 하나를 신설한다. 온보딩 동의 제출과
프로필 편집 토글이 이 엔드포인트 하나를 공용으로 쓴다 (FR-7, 2026-08-15 확정).

## 배경과 목표

FillMap은 영상 업로드 좌표라는 개인위치정보를 실제로 수집하므로, 위치정보법상 위치기반서비스
이용 동의를 받고 "마지막으로 언제 동의 또는 철회했나"에 답할 수 있어야 한다. 지금은 저장할 곳이
없어 디자인 ver 13의 토글이 임시 UI로 떠 있다. 이 티켓으로 동의 상태의 서버 보관을 완성한다.

서버는 어떤 API도 차단하지 않는다 (FR-5). 동의 전 진입 차단은 FE 온보딩 게이트 몫이고, 계정은
로그인 시점에 미동의(off)로 생성된다. 로그인 API와 `OidcLoginService`는 무수정이다.

## 성공 기준

- 신규 컬럼 2개가 마이그레이션만으로 기존 사용자 전원에 off 기본값으로 적용된다 (백필 스크립트 없음, FR-8).
- `GET /api/users/me` 응답에 `locationConsent`가 항상 실린다 (FR-1).
- 동의 변경 API 호출 즉시 다음 프로필 조회에 새 값이 나온다 (FR-2).
- 값이 실제로 바뀔 때만 변경 시각이 갱신되고, 같은 값 재저장은 성공하되 시각이 그대로다 (FR-3, FR-4 멱등[^2]).
- 동의를 꺼도 업로드를 포함한 기존 기능 테스트가 전부 그대로 통과한다 (FR-5, 신규 차단 로직 부재로 충족).
- 친구 목록과 친구 프로필 등 타인 응답에는 동의 정보가 실리지 않는다 (FR-6).

## 설계 결정

| ID | 결정 | 근거 |
|----|------|------|
| D-1 | 동의 변경 엔드포인트는 `PUT /api/users/me/location-consent` 단독 PUT, 응답은 `UserProfileResponseDto` | 닉네임 수정(`PUT /api/users/me/nickname`) 선례를 그대로 따른다. 변경 후 프로필을 반환하면 FE가 재조회 없이 토글 상태를 확정할 수 있고, 조회와 수정의 응답 형태가 어긋날 수 없다 (MSG-203 §D2 논리 재사용) |
| D-2 | 로그인 응답에 동의 여부를 동봉하지 않는다. FE는 로그인 직후 `GET /api/users/me`로 확인한다 | auth 무수정 원칙과 일관 (2026-08-15 확정). FE가 왕복 하나를 줄이고 싶어 동봉을 원하면 별도 후속 티켓으로 다룬다 |
| D-3 | 컬럼은 `location_consent BOOLEAN NOT NULL DEFAULT FALSE`와 `location_consent_changed_at TIMESTAMP NULL` 2개 | NOT NULL + DEFAULT로 기존 행 전원이 마이그레이션만으로 off가 된다 (FR-8, 비기능 "운영"). 변경 시각은 한 번도 안 바꾼 사용자가 있으므로 NULL 허용. 이력 테이블은 PRD 비목표라 마지막 시각 하나만 둔다 |
| D-4 | 멱등 갱신은 원자 UPDATE[^3] 한 문장으로 한다. `UserRepository`에 `@Modifying` native 쿼리로 `UPDATE users SET location_consent = :v, location_consent_changed_at = CASE WHEN location_consent IS DISTINCT FROM :v THEN :now ELSE location_consent_changed_at END WHERE id = :id` | "조회 후 값 비교"는 동시 PUT에서 두 요청이 같은 이전 값을 읽어 시각 이중 갱신과 상태 역전이 가능해 멱등 보장이 깨진다. UPDATE 한 문장이면 DB 행 잠금이 동시 요청을 직렬화하고, 같은 값 재저장의 시각 미갱신(FR-4)이 문장 수준에서 성립한다. 대안이었던 `PESSIMISTIC_WRITE` 잠금 조회 후 갱신은 기각: SELECT FOR UPDATE와 UPDATE 두 문장에 엔티티 상태 전이까지 얹는데, 문장 하나가 더 단순하고 잠금 유지 구간도 짧다 |
| D-5 | 변경 시각(`:now` 파라미터)은 `UserServiceImpl`에 `Clock`[^4]을 주입해 만든다(UTC) | 인자 없는 `now()` 금지 컨벤션(MSG-376). 주입 방식은 BadgeAwardServiceImpl 선례(프로덕션 생성자가 `Clock.systemUTC()`를 고정해 전체 생성자로 위임)를 따르고, 전달 전 `truncatedTo(ChronoUnit.MICROS)`로 DB 정밀도에 맞춘다 (User.createdAt 선례) |
| D-6 | 변경 시각(`locationConsentChangedAt`)은 API 응답에 싣지 않는다 | PRD FR-1이 요구하는 응답 항목은 동의 여부뿐이다. 시각은 법적 질의에 답하기 위한 서버 보관 값이라 DB에만 둔다. 응답이 필요해지면 요구사항 변경이므로 PRD부터 다시 거친다 |
| D-7 | 신규 에러 코드 없음 | 실패 케이스가 전부 기존 코드로 덮인다. 본문 검증 실패는 공통 BAD_REQUEST(400), 인증 실패는 auth 공통 3종(2401·2402·2403, 아래 API 명세), 사용자 부재는 기존 1404 USER_NOT_FOUND. UserErrorCode 1xxx 대역에 추가할 상수가 없다 |
| D-8 | 필드 유실 방지 보장은 한 방향이다. 동의 요청은 두 컬럼만 만지는 원자 UPDATE라 닉네임과 프로필 이미지 등 다른 필드를 덮지 않는다(보장). 반대로 다른 필드의 갱신 트랜잭션이 방금 저장된 동의 값을 되덮을 가능성은 잔존한다(수용) | `User` 엔티티에 `@DynamicUpdate`가 없어(실측) 닉네임이나 프로필 이미지 트랜잭션이 이전 동의 값을 읽은 채 더티 체킹[^5]의 정적 전체 컬럼 UPDATE를 내보내면, 그 사이에 저장된 동의 값이 이전 값으로 되덮인다. 이것은 이번 신설 경로가 아니라 기존 User 갱신 경로 전반의 문제라 이 티켓 범위 밖이다. 발생 창이 두 트랜잭션이 겹치는 순간으로 짧고, 어긋나면 사용자가 토글을 다시 눌러 복구할 수 있어 수용한다. User 전반의 잠금·버전 정책 정비는 후속 몫으로 남긴다 |

## API 명세

### 1. 내 프로필 조회 (변경): `GET /api/users/me`

`UserProfileResponseDto`에 필드 1개를 추가한다. MSG-373이 같은 DTO에 profileImageUrl과
createdAt을 추가한 선례 그대로다. 이 DTO는 조회, 닉네임 수정, 프로필 이미지 변경과 제거, 그리고
이번 동의 변경까지 모든 프로필 응답이 공유하므로 필드 추가 한 번으로 전 경로에 반영된다.

| 필드 | 타입 | 설명 |
|------|------|------|
| `locationConsent` | `Boolean` (required) | 위치정보 사용 동의 여부. 미동의 기본값 false |

`@Schema`의 `requiredProperties`(현재 email, nickname, profileImageUrl, createdAt)에도
`locationConsent`를 추가한다. 빠뜨리면 `ResponseSchemaNullabilityTest`가 깨진다.

성공 예시 (`developCode` 200):

```json
{
  "developCode": 200,
  "message": "성공",
  "data": {
    "email": null,
    "nickname": "채우미",
    "profileImageUrl": null,
    "createdAt": "2026-01-12T03:24:11Z",
    "locationConsent": false
  }
}
```

### 2. 위치정보 사용 동의 변경 (신규): `PUT /api/users/me/location-consent`

온보딩 동의 제출과 프로필 편집 토글이 공용으로 쓴다. 인증 필수이며 항상 본인 계정만 대상이다
(경로에 대상 식별자 없음, FR-6).

**Request**: `LocationConsentUpdateRequestDto` (신규)

| 필드 | 타입 | 검증 | 설명 |
|------|------|------|------|
| `consented` | `Boolean` | `@NotNull` | true면 동의, false면 철회 |

**Response**: `SuccessResponse<UserProfileResponseDto>` (변경 후 프로필, D-1)

**에러 케이스** (전부 기존 코드, D-7):

| 상황 | HTTP | developCode | 비고 |
|------|------|-------------|------|
| `consented` 누락(null) | 400 | 400 | `@Valid` 실패, GlobalExceptionHandler 공통 처리 |
| 토큰 없음 | 401 | 2403 | AuthErrorCode UNAUTHENTICATED |
| 무효 토큰 | 401 | 2401 | AuthErrorCode INVALID_TOKEN |
| 만료 토큰 | 401 | 2402 | AuthErrorCode EXPIRED_TOKEN |
| 사용자 부재 | 404 | 1404 | USER_NOT_FOUND (탈퇴 직후 재호출 등) |

## 도메인 로직

`UserServiceImpl.updateLocationConsent(Long userId, boolean consented)`. 메서드에
`@Transactional`이 필수다 (기존 UserServiceImpl은 클래스가 아니라 메서드 단위로 붙인다.
`@Modifying` 쿼리는 트랜잭션 없이는 실행이 거부된다):

1. `changedAt` 후보 시각을 주입된 `Clock`으로 만든다 (UTC, MICROS 절단, D-5).
2. `userRepository.updateLocationConsent(userId, consented, changedAt)`를 호출한다 (D-4의 원자
   UPDATE 한 문장). 영향 행이 0이면 사용자 부재이므로 1404 (USER_NOT_FOUND).
3. `findUser(userId)`로 재조회해 `UserProfileResponseDto.from(user)` 반환. `@Modifying`에
   `clearAutomatically = true`를 걸어 영속성 컨텍스트의 갱신 전 스냅숏을 비우고 읽는다.

리포지토리 쿼리 (native, PostgreSQL `IS DISTINCT FROM`):

```sql
UPDATE users
SET location_consent = :consented,
    location_consent_changed_at = CASE
        WHEN location_consent IS DISTINCT FROM :consented THEN :changedAt
        ELSE location_consent_changed_at
    END
WHERE id = :userId
```

같은 값 재저장이면 CASE가 기존 시각을 유지하므로 별도 분기 코드 없이 FR-4가 성립하고, 동시 PUT은
행 잠금으로 직렬화된다 (D-4).

동의 여부는 다른 어떤 서비스도 읽지 않는다 (FR-5). glossary의 방문(업로드 이벤트)과 점령 흐름에
분기가 생기지 않는다.

## 데이터 모델

Flyway[^6] 마이그레이션 1건 신규:

```sql
-- V32__users_location_consent.sql
ALTER TABLE users
	ADD COLUMN location_consent BOOLEAN NOT NULL DEFAULT FALSE,
	ADD COLUMN location_consent_changed_at TIMESTAMP;
```

- **번호 주의**: 로컬 `src/main/resources/db/migration/` 최신은 V31(2026-08-15 확인)이라 V32를
  제안하지만, 착수 시점에 `origin/develop`을 fetch해 새 번호가 선점되지 않았는지 반드시 재확인한다
  (MSG-356에서 V28 번호가 베이스 뒤처짐으로 충돌했던 교훈).
- 기존 사용자 전원이 DEFAULT FALSE로 off 시작 (FR-8). 백필 스크립트 없음.
- 탈퇴 시 users 행 삭제로 함께 제거된다 (비기능 "데이터 정합", 별도 정리 불요).
- `User` 엔티티에 `locationConsent`(boolean)와 `locationConsentChangedAt`(LocalDateTime) 필드를
  매핑한다. 상태 전이 메서드는 두지 않는다. 갱신은 리포지토리의 원자 UPDATE 한 곳이다 (D-4).
  신규 가입 생성자는 손대지 않는다. DB DEFAULT가 off를 보장하고, JPA insert 경로에서는 boolean
  필드의 자바 기본값 false가 같은 결과를 만든다.

## 계약 변경

도메인 간 계약 인터페이스 변경은 없다. `GridQueryService`, `HotZoneService`,
`UserGridQueryService`, `UserOidcCommandService` 등 A와 B의 접점 인터페이스는 시그니처가 바뀌지
않고, 변경이 user 패키지 내부에 닫힌다.

외부 API 계약은 바뀐다: `PUT /api/users/me/location-consent` 신설과 `GET /api/users/me` 응답
필드 추가 (위 API 명세). FE에 공유가 필요한 변경이다.

## 테스트 시나리오

한국어 테스트 메서드명 후보:

- `신규_가입_사용자는_위치정보_미동의로_시작한다` (프로필 조회에 false)
- `동의를_켜면_응답과_DB와_후속_프로필_조회에_모두_반영된다` (false에서 true)
- `동의를_끄면_응답과_DB와_후속_프로필_조회에_모두_반영된다` (true에서 false)
- `동의를_켜면_변경_시각이_UTC로_저장된다` (고정 Clock으로 값 검증)
- `동의_상태_true를_true로_재저장해도_성공하고_변경_시각은_그대로다` (FR-4)
- `동의_상태_false를_false로_재저장해도_성공하고_변경_시각은_그대로다` (FR-4)
- `동시에_들어온_동의_변경_요청은_행_잠금으로_직렬화된다` (D-4 원자 UPDATE 근거 검증)
- `consented_없는_요청은_400이다`
- `토큰_없는_동의_변경_요청은_2403이다`
- `무효_토큰_동의_변경_요청은_2401이다`
- `만료_토큰_동의_변경_요청은_2402이다`
- `없는_사용자의_동의_변경_요청은_1404다`
- `V32_적용_후_기존_사용자_행은_동의_false에_변경_시각_NULL이다` (마이그레이션 검증)
- `프로필_응답_JSON에_locationConsent_키가_항상_존재하고_required_계약을_지킨다`
  (`ResponseSchemaNullabilityTest` 계열)
- `친구_프로필_응답에는_동의_여부가_실리지_않는다` (기존 친구 축 프로젝션 응답 형태 불변 확인)

갱신 검증은 테스트 클래스 단위 트랜잭션 안의 영속성 컨텍스트 재사용에 숨지 않는다. 별도
트랜잭션(또는 clear 후 native 조회)으로 DB 실저장 값을 재조회해 확인한다 (`@Modifying` 경로라
1차 캐시와 어긋날 수 있는 지점).

DTO 시각 타입 가드(`DtoTimeTypeGuardTest`)는 이번 DTO에 시각 필드가 없어 해당 없음.
직렬화 검증이 필요하면 스프링 조립 매퍼(`@JsonTest` 또는 `@WebMvcTest`)를 쓴다 (손조립 금지).

## 미해결 질문

- 로그인 응답에 동의 여부 동봉 여부는 D-2대로 "미동봉"을 기본안으로 확정했다. FE가 동봉을 원하면
  이 스펙 개정이 아니라 별도 후속 티켓(auth 응답 변경)으로 다룬다. 그 외 서버 구현을 막는 미해결
  질문은 없다.

[^1]: 온보딩: 첫 로그인 직후 사용자가 서비스 본화면에 들어가기 전에 거치는 안내와 동의 절차 화면. 이 티켓에서는 위치정보 동의 제출 화면을 가리키며, 진입 차단은 FE가 한다.
[^2]: 멱등(idempotent): 같은 요청을 여러 번 보내도 한 번 보낸 것과 결과가 같은 성질. 토글 UI는 연타나 재시도가 흔해서 같은 값 재저장이 에러가 아니어야 한다.
[^3]: 원자 UPDATE: 읽기와 판정과 쓰기를 UPDATE문 하나에 담아 DB가 한 번에 실행하게 하는 방식. 문장 실행 중 해당 행에 잠금이 걸려, 애플리케이션이 조회와 저장 사이에 끼어드는 다른 요청을 걱정할 필요가 없다.
[^4]: Clock: 자바 표준 시계 추상화(`java.time.Clock`). 프로덕션은 `Clock.systemUTC()`를 쓰고 테스트는 고정 시각 Clock을 주입해, "지금"이 들어간 로직을 결정적으로 검증할 수 있게 한다.
[^5]: 더티 체킹(dirty checking): JPA가 트랜잭션 안에서 엔티티 필드 변경을 감지해 UPDATE문을 자동으로 만들어 주는 동작. `@DynamicUpdate`가 없으면 변경 필드만이 아니라 전체 컬럼을 담은 정적 UPDATE가 나간다.
[^6]: Flyway: 번호 붙은 SQL 파일(V32 등)을 순서대로 실행해 DB 스키마 변경을 버전 관리하는 도구. 번호가 겹치면 배포가 실패하므로 병렬 작업 시 번호 선점 확인이 필요하다.
