# MSG-497: 행사 운영자 계정 보안 (첫 로그인 비밀번호 강제 변경, 재설정, 프로필 자체 수정)

**Owner**: B (auth와 user 도메인, CLAUDE.md 협업 원칙 기준. SecurityConfig 변경은 MSG-496이 만든 구조 위에 matcher를 더하는 것이라 공동 판정이 아니다)

> 요구사항 정본: `docs/prd/event-submission.md` (상태 검토됨, 2026-08-28 승인). 이 스펙은 그중
> FR-21(첫 로그인 변경 강제), FR-22(로그인 상태 변경과 이메일 재설정), FR-23(담당자 정보 자체
> 수정과 아이디 변경 요청)의 "어떻게"만 다룬다. 선행 스펙 `docs/spec/MSG-496.md`의 확정
> 두 가지(프리픽스 `/api/org/**` 통일, catch-all `hasAnyRole("USER","ADMIN")` 전환으로 ORG 신규
> 경로는 SecurityConfig 명시 등록 필수)를 전제로 설계했다.

## 개요

행사 운영자 계정은 관리자가 만들어 초기 비밀번호를 발송하는 구조라(FR-1, FR-2), 발급 직후에는
발급자도 비밀번호를 안다. 이 상태를 끝내는 장치가 이 티켓이다. 첫 로그인 시 비밀번호 변경을
강제하는 mustChange 게이트, 로그인 상태의 비밀번호 변경, 잊었을 때의 이메일 재설정(링크 유효
30분), 그리고 담당자 이름과 연락처의 자체 수정과 아이디(공식 이메일) 변경 요청 접수를 만든다.
서버가 메일을 직접 보내는 첫 지점이므로, MSG-499(초기 비밀번호 발송)가 재사용할 메일 발송
유틸도 여기서 만든다.

## 배경 · 목표

- 발급자(관리자)가 초기 비밀번호를 아는 상태가 유지되면 행사 등록과 수정 기록의 행위자를
  특정할 수 없다(FR-21의 명문 근거). 그래서 첫 로그인 변경 강제에는 건너뛰기가 없고, 화면
  안내만으로는 부족하다. API를 직접 호출하면 화면 게이트는 우회되기 때문에 서버가 막아야
  근거가 성립한다.
- 목표: 초기 비밀번호 상태의 계정이 콘솔 API를 쓸 수 없고, 본인만 아는 비밀번호로 바꾼
  뒤에만 콘솔이 열리는 상태. 비밀번호를 잊어도 관리자 손을 빌리지 않고 스스로 복구되는 상태.

## 성공 기준

1. `password_must_change = true`인 계정은 `GET /api/auth/password/status`에서 그 사실을 알 수
   있고, `/api/org/**` 호출이 전부 403(developCode 2441)으로 막힌다.
2. `POST /api/auth/password/change` 성공 시 플래그가 해제되고 즉시 콘솔 호출이 통과한다.
3. `POST /api/auth/password/reset-request`는 계정 존재 여부와 무관하게(발송 실패까지 포함해)
   같은 성공 응답을 내고, **행사 운영자와 관리자(role ORG·ADMIN)의 LOCAL 계정에만** 30분 유효
   링크가 발송된다. 링크는 사용자당 최신 1개만 유효하다(재요청 시 이전 링크 즉시 무효).
4. `POST /api/auth/password/reset`은 유효 토큰 1회에만 성공하고, 같은 토큰 재사용과 만료
   토큰은 같은 실패 응답(developCode 2443)이다. 성공 시 그 계정의 리프레시 세션과 기존 액세스
   토큰이 즉시 무효이고, 동시 진행 중이던 재발급으로도 옛 세션이 살아남지 않는다.
5. 어떤 응답에도 비밀번호 평문과 재설정 토큰 원문이 실리지 않는다.
6. ORG 계정이 `PATCH /api/org/profile`로 담당자 이름과 연락처를 바꿀 수 있고, 아이디 변경은
   `POST /api/org/email-change-request`로 접수만 된다(관리자 처리는 MSG-499와 MSG-500 몫).
7. 로컬에서 실발송 없이(로그 출력) 재설정 흐름을 끝까지 검증할 수 있다. prod는 실발송 빈이나
   재설정 링크 URL이 구성되지 않으면 기동이 실패한다(fail-fast).
8. 아래 테스트 시나리오가 전부 green이다.

## API 명세

비밀번호 4종은 auth 도메인(`/api/auth/password/*`), 프로필 2종(+조회 1종)은 `/api/org/*`다.
전부 공통 응답 포맷(`SuccessResponse` / `ApiException`)을 따른다.

### 1. `GET /api/auth/password/status` (인증 필수, 역할 무관)

첫 로그인 게이트의 판정 재료다. 로그인 직후 화면이 이 값으로 변경 화면 진입 여부를 가른다.

- 응답 `PasswordStatusResponseDto`: `{ "mustChange": boolean }`
- 카카오 소셜 계정처럼 비밀번호가 없는 계정은 항상 `false`다(플래그를 세울 경로가 없다).
- 에러: 비로그인 401뿐. 새 에러 케이스 없음.

### 2. `POST /api/auth/password/change` (인증 필수, 역할 무관, LOCAL 계정 한정)

로그인 상태 변경이며 mustChange 해제 지점이다(FR-22). **역할 무관은 이 API의 경계다**: 재설정
(reset-request)은 아래에서 ORG·ADMIN 계정으로 좁히지만, change는 인증 게이트 뒤에서 자기
비밀번호를 바꾸는 흐름이라 신규 제품 노출이 아니고, LOCAL 비밀번호를 가진 어떤 계정이든 쓸 수
있다(Codex 4R 수용 종결, 미해결 질문의 결정 기록 3). 대신 **provider 가드**를 명시한다:
소셜 계정(provider가 LOCAL이 아니거나 passwordHash가 null)이 부르면 2445로 거부한다.
비밀번호가 없는 계정의 요청을 "현재 비밀번호 불일치"(2442)로 수렴시키면 사용자가 비밀번호를
다시 입력해 볼 뿐 원인을 알 수 없어서다.

- 요청 `PasswordChangeRequestDto`: `{ "currentPassword": "...", "newPassword": "..." }`
  - 두 필드 모두 `@NotBlank`(누락·빈 값은 공통 400. `@Size`·`@Pattern`은 null을 통과시키므로
    `@NotBlank`가 빠지면 null이 서비스까지 내려온다. signup DTO의 `@NotBlank`가 실증 선례).
  - newPassword 검증은 signup과 동일 정책(영문과 숫자 각 1개 이상, 8~64자)이며
    `SignupRequestDto.password`의 `@NotBlank`·`@Size`·`@Pattern`을 그대로 옮긴다(FR-AUTH-11 정합).
- 처리: LOCAL 계정 가드(아니면 2445) → 현재 비밀번호를 bcrypt[^1] 대조 → 새 비밀번호가
  현재와 같으면 거부 → 해시 저장과 `password_must_change = false`를 한 트랜잭션으로 → 커밋 후
  잔여 재설정 토큰 폐기.
  - 새 비밀번호가 현재(초기 비밀번호)와 같으면 발급자가 여전히 아는 값이라 FR-21의 목적이
    무산되므로 거부한다(2444).
  - 현재 비밀번호 대조를 요구하는 이유: 액세스 토큰 탈취만으로 비밀번호를 갈아탈 수 없게
    하는 방어선이다. mustChange 상태에서는 초기 비밀번호가 currentPassword다.
  - 변경 성공 시 발급돼 있던 재설정 토큰을 폐기한다(아래 재설정 토큰 절의 revoke). 비밀번호가
    이미 바뀌었는데 옛 메일함의 링크가 TTL까지 살아 있으면 안 된다.
  - 기존 리프레시 세션은 유지한다. 본인이 현재 비밀번호를 증명한 자발적 변경이라 복구
    시나리오가 아니고, 첫 로그인 게이트 직후 재로그인을 강제하면 흐름이 끊긴다.
- 응답: `SuccessResponse<Void>`.
- 에러: 2442(현재 비밀번호 불일치, 400), 2444(새 비밀번호가 현재와 동일, 400),
  2445(비밀번호 미설정 계정, 400), 정책 위반은 `@Valid` 공통 400.

### 3. `POST /api/auth/password/reset-request` (permitAll, 비로그인)

공식 이메일로 재설정 링크를 보낸다(FR-22).

- 요청 `PasswordResetRequestDto`: `{ "email": "..." }` (`@NotBlank` + `@Email`, max 255.
  `@Email` 단독은 null과 빈 문자열을 통과시킨다)
- 처리:
  1. 60초 쿨다운 확인(아래 데이터 모델). 쿨다운 중이면 발송을 생략하고 **같은 성공 응답**.
  2. 이메일로 사용자 조회. 없거나, provider가 LOCAL이 아니거나, passwordHash가 null이거나,
     **role이 ORG도 ADMIN도 아니면** 발송을 생략하고 **같은 성공 응답**. 계정 존재 은닉[^2]은
     MSG-186 친구 프로필의 단일 실패 응답, NFR-SEC-06과 같은 원칙이다. 여기서는 실패가 아예
     없는 단일 성공 응답이다.
     - 대상을 ORG·ADMIN으로 좁히는 근거: FR-22는 행사 운영자의 요구이고, 운영의 LOCAL
       로그인은 행사 운영자와 관리자 계정용이다(NFR-SEC-07). ADMIN까지 포함하는 것은 SRS
       FR-AUTH-11 재정의(2026-08-28, 이메일 로그인은 행사 운영자와 관리자의 프로덕션 경로)가
       근거다: 관리자 계정도 같은 LOCAL 로그인이라 복구 수단이 있어야 하고, 새 화면이나 새
       API가 아니라 같은 흐름의 대상 판정일 뿐이다(Codex 4R 수용 종결, 결정 기록 3). 반면
       prod signup이 아직 열려 있어(NFR-SEC-07 미충족 사실, MSG-360 전까지) role USER인 LOCAL
       계정이 실존할 수 있는데, 아래 무효화 검사는 ORG·ADMIN 토큰만 보므로 USER 계정에 reset을
       열면 "재설정해도 기존 액세스 토큰이 안 죽는" 구멍이 생긴다. 대상 축소가 그 구멍을 원천
       제거하고, USER LOCAL 계정의 요청은 부재 계정과 같은 응답으로 수렴해 오라클도 생기지
       않는다. 전 토큰 무효화 검사 확대(매 요청 Redis GET 1회 추가)는 signup 운영 차단
       (MSG-360)으로 없어질 계정을 위한 상시 비용이라 기각했다.
  3. 토큰 생성(SecureRandom 32바이트를 base64url 인코딩), 해시만 저장(아래 데이터 모델),
     TTL 30분. 재요청이면 이전 토큰을 이 시점에 즉시 무효화하고 교체한다(사용자당 활성 1개,
     아래 재설정 토큰 절).
  4. 메일 발송: 제목과 본문은 한국어 평문, 링크는
     `{fillmap.mail.reset-link-base-url}?token={토큰 원문}`. base URL은 프로퍼티로 두고 화면
     라우트 확정은 FE 몫이다. 기본값 정책은 아래 메일 유틸 절(로컬·dev 한정 기본값, prod는
     미설정 시 기동 실패).
  5. **발송 실패는 응답에 반영하지 않는다.** MailSender 호출을 try-catch로 감싸 응답은 항상
     같은 성공을 내고, 실패는 ERROR 로그로만 남긴다. 실패가 응답으로 새면 존재 계정만 SES
     오류를 돌려받아 계정 존재 오라클이 된다(성공 기준 3의 위반 지점). 비동기 발송으로
     내리는 안은 기각했다: 기존 `AsyncConfig`는 video 도메인 전용(실측)이라 재사용이 아니고,
     은닉 목적에는 동기 호출 + 예외 격리로 충분하다. 실패 관측이 로그로 부족해지면 그때
     카운터 지표를 붙인다.
- 응답: `SuccessResponse<Void>` (표준 성공 응답, developCode 200에 message "성공"). 커스텀
  메시지를 쓰지 않는 이유: `SuccessResponse`는 SUCCESS_MESSAGE("성공")를 고정 상수로 갖고
  메시지 오버라이드 API가 없다(SuccessResponse.java 9행 실측). 컨트롤러는
  `SuccessResponse.of(...)`만 반환한다는 response-pattern.md 계약과도 일치하고, 응답 동일성
  요건은 표준 응답으로 그대로 성립한다. 안내 문구는 화면(FE) 몫이다. 토큰 원문은 메일에만
  실리고 응답과 서버 로그에 남기지 않는다(NFR-SEC-05의 토큰 원문 로그 금지와 같은 원칙.
  LoggingMailSender는 로컬 검증용 예외, 아래 메일 유틸 절).
- 한계(수용): 존재 계정만 SES 왕복이 있어 응답 시간 차이로 존재를 추정할 여지가 있다. 대상이
  내부 소수(행사 운영자 계정)이고 발송 비동기화는 이 티켓 범위를 넘어 수용한다. 문제가 되면
  발송을 큐로 내리는 후속으로 푼다.

### 4. `POST /api/auth/password/reset` (permitAll, 비로그인)

- 요청 `PasswordResetConfirmRequestDto`: `{ "token": "...", "newPassword": "..." }`
  (두 필드 모두 `@NotBlank`, newPassword 검증은 change와 동일)
- 처리 순서: 토큰 소비(원자 선점, 아래 데이터 모델) → userId 획득 실패면 2443 → 해시 저장과
  `password_must_change = false`를 한 DB 트랜잭션으로 → 커밋 후 **사용자 단위 토큰 무효화
  기록(`blacklist:user:{userId}`)을 먼저 쓰고** 전 디바이스 리프레시 세션 삭제
  (`RefreshTokenService.deleteAll`, 로그아웃-올 선례). 이 순서가 계약이다: 아래 "재설정 시
  토큰 무효화" 절의 재발급 경합 차단이 "무효화 기록이 세션 삭제보다 먼저"를 전제로 성립한다.
  - 세션 삭제에 더해 액세스 토큰까지 무효화하는 이유: 리프레시만 지우면 공격자가 이미 쥔
    액세스 토큰이 잔여 수명(최대 1시간) 동안 산다. 복구 시나리오의 "기존 세션을 남기지
    않는다"는 액세스 토큰까지 포함해야 성립한다.
  - DB 트랜잭션이 실패하면 선점한 토큰을 저장소에 복원하되 **조건부로 복원한다**
    (compare-and-restore, 아래 재설정 토큰 절의 restore). 역방향 키가 비어 있을 때만 되살린다:
    선점과 DB 실패 사이에 재요청이 새 토큰을 발급했으면 역방향이 새 해시를 가리키고 있는데,
    무조건 복원하면 사용자가 방금 받은 새 링크를 지우고 실패한 옛 링크로 되돌리게 된다. 복원
    TTL은 30분 재설정(실패 경로 한정이라 수명 연장은 수용). 복원 전에 프로세스가 죽으면 링크가
    소실되고 재요청으로 복구된다. 동시 이중 사용은 소비의 원자 선점이 막는다: 둘 중 하나만
    userId를 받고, 복원은 실패 경로에서만 일어나 이중 사용 창이 생기지 않는다.
  - mustChange 해제 이유: 재설정으로 정한 비밀번호도 본인만 아는 값이라 게이트 목적이 이미
    달성됐다.
  - 무효/만료/재사용 토큰은 전부 같은 2443 하나다. 사유를 가르면 토큰 상태가 오라클이 된다.
- 응답: `SuccessResponse<Void>`.
- 에러: 2443(유효하지 않거나 만료된 링크, 400), 정책 위반은 공통 400.

### 5. `GET /api/org/profile` · `PATCH /api/org/profile` (ORG 전용, `/api/org/**` matcher가 인가)

담당자 이름과 연락처의 조회와 수정이다(FR-23). GET은 계정 설정 화면([운영자 11])의 초기값
재료다. `GET /api/users/me`에는 연락처가 없고 그 DTO는 네 응답이 공유해 필드를 늘리지 않는다.
GET 추가는 2026-08-28 사용자 확정이며(미해결 질문의 결정 기록 1), PRD 서버 재료 목록에도 같은
날 반영했다.

- GET 응답 = PATCH 응답 = `OrgProfileResponseDto`:
  `{ "email": "...", "contactName": "...", "contactPhone": "..." | null }`
- PATCH 요청 `OrgProfileUpdateRequestDto`: 두 필드 모두 필수이며 **둘 다 `@NotBlank`**를
  단다(`@Size`·`@Pattern`만으로는 null이 통과해 NOT NULL인 nickname 컬럼까지 내려가 500이
  된다).
  - `contactName`: `@NotBlank` + 2~20자(`users.nickname` 컬럼에 저장하므로 signup 닉네임과
    동일 제약)
  - `contactPhone`: `@NotBlank` + `@Pattern("^[0-9][0-9-]{7,18}[0-9]$")` (숫자로 시작하고
    끝나는 숫자와 하이픈 9~20자. 앞선 안 `[0-9-]{9,20}`은 하이픈만으로도 통과해 숫자 없는
    값이 저장될 수 있었다)
- 저장: 담당자 이름은 `users.nickname` 재사용, 연락처는 신설 컬럼 `users.contact_phone`
  (아래 데이터 모델). ORG 계정의 nickname이 곧 담당자 이름이라는 해석은 MSG-496 런북(signup의
  nickname)과 MSG-499 발급 폼(담당자 필드)이 공유할 전제다.
  - `PUT /api/users/me/nickname`은 catch-all이 ORG에게 403이므로(MSG-496) 경로 충돌이 없다.
- 아이디(이메일)는 이 API로 못 바꾼다. 요청 DTO에 필드 자체가 없다.
- 에러: 검증 위반 공통 400뿐.

### 6. `POST /api/org/email-change-request` (ORG 전용)

아이디(공식 이메일) 변경 요청의 접수와 저장까지만이다(FR-23). 관리자 큐 노출과 승인 반영은
MSG-499와 MSG-500 몫이다.

- 요청 `OrgEmailChangeRequestDto`: `{ "requestedEmail": "..." }` (`@NotBlank` + `@Email`,
  max 255. `@Email` 단독은 null과 빈 문자열을 통과시켜 NOT NULL 컬럼 500이나 빈 요청 저장으로
  이어진다)
- 처리: 현재 이메일과 같으면 1420 거부. 저장은 native UPSERT 한 문장이다(PostgreSQL 전용
  ON CONFLICT라 컨벤션의 native 허용 대상). 본인 PENDING 행이 있으면 requestedEmail과 접수
  시각을 갱신하고, 없으면 새 행을 만든다(마지막 요청이 유효, 오타 정정 재요청 허용). 조회
  후 INSERT의 두 문장으로 가르면 동시 요청 두 개가 부분 유니크 제약 위반 500으로 터진다.

  ```sql
  INSERT INTO org_email_change_requests (user_id, requested_email, status, created_at)
  VALUES (:userId, :email, 'PENDING', :now)
  ON CONFLICT (user_id) WHERE status = 'PENDING'
  DO UPDATE SET requested_email = EXCLUDED.requested_email, created_at = EXCLUDED.created_at
  ```

  - 접수 시각 `:now`는 서비스가 주입받은 Clock의 UTC 시각이다(BadgeAwardServiceImpl 선례.
    시각을 쿼리 파라미터로 받지 않는다는 컨벤션은 HTTP `@RequestParam` 이야기라 SQL 바인딩은
    해당 없음).
  - 요청 이메일이 다른 계정에 이미 쓰이는지는 여기서 검사하지 않는다. 검사하면 이 API가 타
    계정 존재 오라클이 되고, 정합은 관리자 승인 시점(MSG-500)에 확정하면 된다.
- 응답: `SuccessResponse<Void>`.
- 에러: 1420(현재 아이디와 동일, 400), 검증 위반 공통 400.

### SecurityConfig 등록 (실측: 현 워크트리 SecurityConfig.java 170~185행 구조 기준)

MSG-496의 catch-all `hasAnyRole("USER", "ADMIN")` 아래에서 신규 경로는 등록 누락 시 403으로
드러나는 fail-closed다. 이 티켓의 등록분:

```java
// 비밀번호 재설정(MSG-497): 비로그인 흐름이라 permitAll. 두 경로만 정확히 연다.
// /api/auth/password/** 로 넓히면 로그인 상태 전용인 status·change 까지 익명에 풀린다.
.requestMatchers("/api/auth/password/reset-request", "/api/auth/password/reset").permitAll()
// 비밀번호 상태·변경(MSG-497): 역할 무관 로그인 필수. catch-all 이 역할 제한이라
// authenticated 명시가 없으면 ORG(정작 주 사용자)가 403 이 된다 (MSG-496 §3 예고 지점).
.requestMatchers("/api/auth/password/status", "/api/auth/password/change").authenticated()
```

- `/api/org/profile`과 `/api/org/email-change-request`는 기존 `/api/org/**` matcher(MSG-496)가
  이미 ORG로 인가한다. 추가 등록 없음.
- `JwtAuthenticationFilter.PUBLIC_AUTH_PATHS`에 reset-request와 reset 두 경로를 함께 추가한다
  (파일 상단 주석의 "SecurityConfig 의 permitAll 인증 경로와 반드시 함께 갱신" 규칙). 만료
  토큰이 헤더에 실려 와도 비로그인 재설정이 막히지 않아야 하므로 토큰 무시가 맞다.
- matcher 삽입 위치는 기존 `/api/admin/**` 블록 앞의 permitAll 열거 영역(auth 경로들 옆)과
  `/api/org/**` 아래 공용 경로 블록이다. permitAll이 catch-all보다 먼저 평가되는 기존 순서
  규칙을 그대로 따른다.

## 도메인 로직

### mustChange 게이트: 서버 강제로 확정 (인터셉터 방식)

**화면 게이트만으로는 FR-21이 성립하지 않는다.** FR-21의 근거가 "발급자가 초기 비밀번호를
아는 상태로는 행위자 특정 불가"인데, 화면만 막으면 초기 비밀번호를 아는 사람이 API를 직접
호출해 행위할 수 있다. 그래서 서버가 `/api/org/**`를 차단한다.

방식은 실측 세 갈래를 비교해 정했다:

| 방식 | 실측 근거 | 판정 |
|------|-----------|------|
| JWT 클레임에 mustChange 동봉 | 클레임은 발급 시점 스냅숏이라(MSG-496 작업 로그) 변경 직후에도 기존 토큰이 true를 들고 있어 재발급 전까지 계속 막힌다 | 기각(해제 즉시성 불충족) |
| 각 org 서비스에서 플래그 검사 | MSG-498 이후 콘솔 API가 늘 때마다 검사를 복제해야 하고 누락이 곧 우회다 | 기각(fail-open) |
| `/api/org/**` 인터셉터[^3]에서 DB 플래그 조회 | 이 코드베이스에 HandlerInterceptor는 0건(grep 실측, 필터는 JwtAuthenticationFilter 하나)이라 신설이지만, preHandle에서 던진 ApiException은 기존 GlobalExceptionHandler가 그대로 변환해 추가 배선이 없다. 경로 등록 한 곳이 미래 콘솔 API 전부를 덮는다 | **채택** |

- 신설: `auth/web/PasswordChangeGateInterceptor` + `global/config/WebConfig`(WebMvcConfigurer,
  이 인터셉터를 `/api/org/**`에 등록). 프로젝트 첫 인터셉터라 등록 클래스도 신설이다.
- 판정 쿼리: `UserRepository.existsByIdAndPasswordMustChangeTrue(userId)` (PK 파생 쿼리 1회).
  userId는 SecurityContext의 AuthPrincipal에서 얻는다. 시큐리티 체인이 먼저라 이 시점엔 항상
  ORG 인증이 끝나 있다.
- 차단 응답: `ApiException(AuthErrorCode.PASSWORD_CHANGE_REQUIRED)` → 403, developCode 2441.
  role 불일치 403(공통 FORBIDDEN)과 developCode로 구분되어 화면이 변경 화면으로 보낼 수 있다.
- 차단 범위는 `/api/org/**`뿐이다. `password/status`와 `password/change`(탈출구),
  `GET /api/users/me`, logout은 게이트 밖이라 첫 로그인 흐름이 성립한다.
- 요청당 PK 조회 1회가 늘지만 대상이 콘솔(내부 소수, PRD 성능 절 "별도 성능 목표 없음")이라
  수용한다. ORG 트래픽이 유의미해지면 짧은 TTL 캐시로 승격한다.

### 재설정 토큰: 발급 · 저장 · 소비 (사용자당 활성 1개, Lua 원자화)

- 토큰 원문: `SecureRandom` 32바이트 → base64url(43자). User.friendCode의 SecureRandom 선례.
- 저장은 **해시만**, 키 두 개가 쌍이다. 정방향 `pwreset:{sha256hex(토큰)}` → userId(reset
  요청이 토큰만 들고 오므로 조회 축), 역방향 `pwreset:user:{userId}` → 토큰 해시(사용자당
  1개 강제와 폐기 축). 둘 다 TTL[^5] 30분. RedisInvalidatedTokenStore의 "원문을 키에 넣지
  않는다" 선례를 그대로 따른다. Redis가 원문을 갖지 않으므로 Redis가 새어도 링크를 재구성할
  수 없다.
- **사용자당 활성 토큰은 1개다.** save가 역방향 키의 기존 해시로 이전 정방향 키를 지우고
  두 키를 새로 쓴다. 재요청하면 이전 링크가 그 즉시 죽는다. 토큰별 독립 키만 두면 재요청할
  때마다 이전 링크가 TTL까지 전부 유효한 채 메일함마다 쌓인다(회수 불가).
- **save·consume·revoke·restore는 각각 Lua 스크립트[^6] 하나로 원자화한다.** 명령 여러 개
  (GET 후 DEL 후 SET)로 조립하면 save와 consume이 동시에 돌 때 역방향 포인터가 어긋난다.
  예를 들어 save(새 토큰 B)가 역방향을 읽은 직후 consume(토큰 A)이 A를 소비하고 역방향을
  지우면, save가 마저 쓴 B의 정방향만 남고 역방향이 없어져 revoke가 B를 못 찾는다(폐기 불가
  링크 잔존). 선례 실측: 같은 read-modify-write 원자화 용도로 `DefaultRedisScript`가 이미
  5곳에 있다(SearchKeywordCommandServiceImpl의 DEDUPE_SCRIPT, RouteWalkDailyLimiter의
  ACQUIRE_SCRIPT, 핫존 2곳, EventViewerServiceImpl). 각 스크립트의 규칙:
  - `save`: 역방향 GET → 있으면 그 정방향 DEL → 새 정방향 SET(EX 1800) + 역방향 SET(EX 1800).
  - `consume`: 정방향 GET → 없으면 nil 반환 → 있으면 정방향 DEL, 그리고 역방향 값이 **소비한
    그 해시와 일치할 때만** 역방향 DEL(compare-and-delete. 일치하지 않으면 이미 새 토큰으로
    교체된 것이므로 남겨 둔다).
  - `revoke`: 역방향 GET → 있으면 그 정방향 DEL → 역방향 DEL.
  - `restore`: **역방향 키가 없을 때만** 정방향과 역방향을 되살린다(compare-and-restore).
    역방향이 이미 있으면 선점과 복원 사이에 재요청이 새 토큰을 발급한 것이므로 no-op으로
    끝낸다. 무조건 SET이면 사용자가 방금 받은 새 링크를 실패한 옛 링크로 되덮는다(reset의
    DB 실패 복원 경로, 위 API 명세 4).
- 스토어 메서드 5개: `save(token, userId)`(교체 포함), `consume(token)`(원자 선점),
  `revoke(userId)`(change 성공이 부른다. reset은 consume이 이미 지워 불요),
  `restore(token, userId)`(reset의 DB 실패 경로 전용), `tryAcquireCooldown(email)`.
- 만료 판정은 Redis TTL이 전담한다. 서버 코드에 시각 비교가 없어 인자 없는 `now()` 금지
  컨벤션(MSG-376)의 위반 지점 자체가 생기지 않는다. Clock 주입이 필요한 만료 로직도 없다.
- Redis 유실 시 토큰이 사라져 사용자가 재요청하면 된다(핫스코어의 Redis 유실 허용과 같은
  수용). DB 백업 저장을 두지 않는 이유다.
- 저장소 구조는 기존 토큰 스토어 선례 그대로: `auth/password` 하위에
  `PasswordResetTokenStore` 인터페이스 + `RedisPasswordResetTokenStore`(`@Profile("!test")`) +
  `InMemoryPasswordResetTokenStore`(`@Profile("test")`, TTL 미시뮬레이션이되 두 키의 정합
  규칙은 동일 구현. InMemoryRefreshTokenStore 선례). 쿨다운 키
  (`pwreset-cooldown:{sha256hex(email)}`, TTL 60초)는 비로그인 공개 API가 메일 발송(SES 비용,
  수신자 폭탄)을 유발하는 것을 막는 최소 가드다. 초과 요청도 응답은 동일 성공이라 은닉이
  유지된다.

### 재설정 시 토큰 무효화 (사용자 단위: 액세스 즉시 차단 + 재발급 경합 차단)

reset 성공은 그 계정의 **기존 액세스 토큰**을 무효로 만들고, **동시 진행 중인 재발급**으로도
옛 세션이 살아남지 않게 한다(성공 기준 4).

- 저장: `InvalidatedTokenStore`에 사용자 단위 무효화 2메서드를 추가한다. Redis 키
  `blacklist:user:{userId}`, 값은 무효화 시각(epoch 초), **TTL은 리프레시 토큰 수명**
  (`jwt.refresh-token-ttl`, 2주)이다. 액세스 수명(1시간)이 아닌 이유: 커밋 후 deleteAll이
  부분 실패하면 살아남은 리프레시 세션이 2주를 사는데, 마커가 1시간 만에 사라지면 그 뒤의
  재발급 검사가 통과해 도난 리프레시가 부활한다. 마커가 리프레시 수명만큼 살면 아래 재발급
  검사(iat가 무효화 초와 같거나 이르면 거부)가 마커 생존 기간 내내 옛 리프레시를 전부
  거부하므로, deleteAll 실패에 대한 재시도나 마커 영속화 없이도 부활이 구조적으로 막힌다.
  TTL 연장이 액세스 판정에 주는 부작용은 없다: 마커는 무효화 시각만 담고 판정이 iat
  비교라서, 재설정 이후 재로그인으로 받은 토큰은 iat가 더 커서 마커가 살아 있어도 통과한다.
- **액세스 토큰 판정**: `JwtTokenProvider.parseAccessToken`이 이미 매 요청
  `InvalidatedTokenStore`를 확인한다(59행 실측). 같은 자리에서 토큰의 발급 시각(iat,
  issueAccessToken 43행이 심는 것을 실측)이 사용자 무효화 시각과 **같거나 이르면**
  INVALID_TOKEN(2401)으로 거절한다.
  - 검사 스코프: **ORG와 ADMIN 역할 토큰만** 검사한다(role 클레임 복원 후 분기). 추가 Redis
    왕복 1회가 붙는 대상을 콘솔·관리자 트래픽으로 한정하는 것이고, 이 스코프가 완결적인 이유는
    reset 대상 자체가 ORG·ADMIN 계정으로 좁혀져 있어서다(위 API 명세 3의 2번. "재설정했는데
    무효화 검사 밖인 토큰"이 구조적으로 없다). 대다수 트래픽인 USER(카카오 소셜)는 비밀번호
    자체가 없고, USER LOCAL 계정은 reset 대상이 아니다.
- **재발급(리프레시 회전) 경합 차단**: `RefreshTokenService.reissue`는 저장된 jti 확인 뒤 새
  세션을 save 한다(50~63행 실측). reset의 deleteAll과 인터리빙되면 "jti 확인은 삭제 전,
  save는 삭제 후"가 될 수 있어 옛 리프레시로 세션이 부활한다. 차단 프로토콜:
  - `RefreshTokenClaims`에 발급 시각(issuedAt)을 추가한다. 리프레시 JWT에 iat는 이미 실려
    있는데(JwtRefreshTokenProvider.issueRefreshToken 44행 실측) 파서가 버리고 있었다
    (parseRefreshToken 57~61행이 userId·deviceId·jti만 복원).
  - reissue는 **회전 save를 마친 뒤** `blacklist:user:{userId}`를 읽어, 제시된 리프레시
    토큰의 iat가 무효화 시각과 같거나 이르면 방금 저장한 세션을 삭제하고
    EXPIRED_REFRESH_TOKEN(2432)으로 거절한다.
  - 이 검사가 save "후"인 것과 reset의 "무효화 기록이 deleteAll보다 먼저"(위 API 명세 4의
    순서 계약)가 조합되면 어느 인터리빙에서도 부활 세션이 남지 않는다: reissue의 save가
    deleteAll보다 앞이면 deleteAll이 그 세션을 지우고, 뒤면 그보다 더 앞선 무효화 기록이 save
    후 검사에 반드시 보인다. 옛 iat 리프레시가 무효화 후 정상 제시되는 경우도 같은 검사가
    거절한다(어차피 deleteAll로 EXPIRED이지만 실패 모드가 같은 코드로 수렴하고, deleteAll이
    부분 실패해 세션이 남았더라도 마커가 리프레시 수명만큼 살아 있어 같은 검사가 막는다).
  - 정상 사용자 영향 없음: 재설정 후 재로그인으로 받은 리프레시는 iat가 무효화 시각 이후라
    통과한다. reissue는 저빈도(디바이스당 액세스 만료 주기)라 Redis GET 1회 추가는 역할
    스코프 없이 전 사용자에 적용한다(액세스 검사와 달리 요청마다가 아니다).
- 경계(fail-closed): iat는 초 단위인데 비교를 **같은 초 포함 거부**(iat <= 무효화 초)로 둔다.
  엄격 미만 비교면 무효화와 같은 초에 발급돼 있던 기존 토큰이 살아남는 구멍이 생긴다. 반대
  방향 부작용(무효화와 같은 초에 재로그인으로 받은 새 토큰이 한 번 거부됨)은 실사용에서
  발생하지 않는다: reset 흐름에 자동 로그인이 없어 수동 재로그인까지 통상 1초를 넘기고, 설혹
  걸려도 재로그인 한 번으로 풀린다. 보안 경계는 오탐(정상 토큰 1회 거부) 쪽으로 넘어지게 두는
  것이 맞다.

### 메일 발송 유틸: SES 채택, 로컬은 로그 발송, prod는 fail-fast

**수단은 AWS SES[^4]다.** 실측 근거:

- build.gradle에 AWS SDK v2 BOM(2.48.0)과 S3, CloudFront가 이미 있다. SES는 같은 BOM 아래
  `software.amazon.awssdk:sesv2` 한 줄 추가로 끝난다.
- 자격 증명은 S3Config 주석 명문대로 DefaultCredentialsProvider 체인(로컬 환경변수, dev와
  prod는 EC2 인스턴스 role)이라 새 시크릿이 하나도 안 생긴다. SMTP(spring-boot-starter-mail)는
  새 의존성에 더해 SMTP 전용 자격 증명을 환경변수로 새로 관리해야 해서 기각했다.
- region 설정(`aws.region`, ap-northeast-2)도 기존 AwsProperties 재사용이다.

구성 (`global/mail` 패키지, MSG-459의 global.geo 공용 승격 선례):

```text
MailSender (인터페이스)            void send(String to, String subject, String text)
├─ SesMailSender                  @ConditionalOnProperty("fillmap.mail.enabled", havingValue = "true")
│                                 SesV2Client 는 MailConfig 가 S3Config 패턴으로 빈 등록
└─ LoggingMailSender              @Profile("!prod") 에 더해
                                  @ConditionalOnProperty("fillmap.mail.enabled",
                                      havingValue = "false", matchIfMissing = true)
```

- **prod 안전장치(fail-fast) 둘**:
  1. LoggingMailSender에 `@Profile("!prod")`를 건다. prod에서 `fillmap.mail.enabled`가
     누락되거나 false면 MailSender 빈이 하나도 없어 서비스 생성자 주입이 실패하고 기동 자체가
     죽는다. 코드 추가 없이 DI가 fail-fast를 집행한다. matchIfMissing 하나만으로는 운영
     프로퍼티 누락 시 재설정 링크 전문이 로그로 새는 fail-open이었다.
  2. `fillmap.mail.reset-link-base-url`의 로컬 기본값(`http://localhost:5173/reset-password`)은
     공통 application.yml이 아니라 **local·dev 프로파일 문서에만** 둔다. 공통에 두면 prod가
     상속받아, enabled=true인데 URL 미주입이면 localhost 링크가 실제 메일로 발송된다.
     SesMailSender(enabled=true 경로)는 생성 시 이 프로퍼티가 비어 있으면 예외를 던져 기동을
     실패시킨다. "enabled인데 필수 값이 비면 기동 실패"는 MSG-483 appKey의 기존 방식
     (NFR-SEC-10 근거 문구 "enabled+빈 키는 기동 실패")을 그대로 따른 것이다.
- 프로퍼티: `fillmap.mail.enabled`(기본 false), `fillmap.mail.from`
  (`${MAIL_FROM:contact@fillmap.kr}`, PRD 확정 발신 주소),
  `fillmap.mail.reset-link-base-url`(기본값은 local·dev 한정, 위 2번).
- **로컬과 dev의 실발송 없는 검증**: enabled 기본 false라 LoggingMailSender가 잡히고, 재설정
  링크(토큰 포함)가 로그에 전문으로 찍힌다. 로그의 링크로 reset까지 수동 E2E가 된다. 테스트
  코드는 MailSender를 목으로 갈아 끼워 수신자와 본문을 단언한다. 토큰 원문 로그 금지의 유일한
  예외가 이 로컬 검증용 구현이며, prod에서는 프로파일 조건 때문에 이 구현이 빈으로 뜰 수 없다.
- 발송 실패 격리는 호출부 책임이다(위 API 명세 3의 5번. 유틸은 실패를 예외로 올리고, 은닉이
  필요한 호출부가 잡는다. MSG-499의 관리자 발급 흐름은 실패를 관리자에게 보여줘야 하므로
  유틸이 삼키면 안 된다).
- 인터페이스에 구현이 둘(SES, 로깅)이라 단일 구현 인터페이스 금지 원칙에 저촉되지 않는다.
  MSG-499의 초기 비밀번호 발송이 `send` 하나를 그대로 재사용한다.
- 운영 선행 작업(코드 밖, deploy.md에 기록할 것): SES에 fillmap.kr 도메인 검증(DKIM), 샌드박스
  해제(프로덕션 액세스) 신청, EC2 인스턴스 role에 `ses:SendEmail` 권한 추가, prod 환경변수에
  `fillmap.mail.enabled=true`와 `fillmap.mail.reset-link-base-url`(운영 화면 URL) 주입. 완료
  전까지 dev는 enabled=false로 로그 발송 모드로 굴러간다.

## 데이터 모델

Flyway 1건. **번호는 V46이다.** 워크트리 실측 최신이 `V45__users_role_org.sql`(MSG-496)이라
그다음을 배정했다. PRD 변경 파일 표의 "V46 = 신청 테이블(MSG-498)"은 표 작성 시점 실측일
뿐이고, PRD 스스로 "각 티켓 구현 시점에 재실측해 배정"을 단서로 달아 뒀다. 이 티켓이 먼저
구현되므로 V46을 쓰고, MSG-498은 착수 시점 재실측으로 V47 이후를 배정하면 된다(겹침 없음).
구현 시점에 develop에 새 마이그레이션이 먼저 붙었으면 이 번호도 같은 규칙으로 민다.

`V46__org_account_security.sql`:

```sql
-- 행사 운영자 계정 보안 (MSG-497).
-- 1) 첫 로그인 비밀번호 강제 변경 플래그. 기존 행은 전부 false(강제 없음)로 시작한다.
ALTER TABLE users ADD COLUMN password_must_change BOOLEAN NOT NULL DEFAULT FALSE;
-- 2) 담당자 연락처 (FR-23). ORG 계정만 쓰는 값이라 NULL 허용.
ALTER TABLE users ADD COLUMN contact_phone VARCHAR(20);

-- 3) 아이디(공식 이메일) 변경 요청 큐. 접수는 MSG-497, 관리자 노출·처리는 MSG-499·500.
CREATE TABLE org_email_change_requests (
    id BIGSERIAL PRIMARY KEY,
    user_id BIGINT NOT NULL REFERENCES users (id) ON DELETE CASCADE,
    requested_email VARCHAR(255) NOT NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'PENDING',
    created_at TIMESTAMP NOT NULL,
    CONSTRAINT chk_org_email_change_requests_status
        CHECK (status IN ('PENDING', 'APPROVED', 'REJECTED'))
);
-- 사용자당 대기 요청은 한 건. 재요청은 이 행의 갱신이다 (부분 유니크 인덱스가 강제,
-- §6 의 ON CONFLICT 대상이기도 하다).
CREATE UNIQUE INDEX uq_org_email_change_requests_pending
    ON org_email_change_requests (user_id) WHERE status = 'PENDING';
```

- 상태값에 APPROVED와 REJECTED를 미리 넣는 이유: MSG-500이 처리 결과를 쓸 때 CHECK 재정의
  마이그레이션을 다시 만들지 않기 위해서다. 이 티켓 코드는 PENDING만 만든다.
- 쓰기 경로가 native UPSERT 한 문장이라(§6) `created_at`은 서비스가 주입받은 Clock의 UTC
  시각을 바인딩한다. DB DEFAULT를 두지 않아 저장 축이 코드 한 곳이다.
- mustChange 플래그를 별도 테이블이나 Redis가 아닌 users 컬럼으로 두는 이유: 계정의 영속
  상태(재로그인해도 유지)라 세션 저장소 성격이 아니고, 게이트 판정이 PK 조회 한 번으로 끝난다.
- 재설정 토큰은 DB 테이블이 없다(위 도메인 로직: Redis TTL 저장, 유실 수용).
- 신규 엔티티: `user/entity/OrgEmailChangeRequest`(연관관계 없이 userId 보관. `@ManyToOne`을
  달지 않는 근거: 이 티켓의 쓰기는 native UPSERT뿐이고 조회가 없다. 엔티티는 스키마 매핑과
  MSG-499 관리자 큐 조회의 발판으로 남기며, 연관이 필요해지면 그때 단다).

[^2]: 계정 존재 은닉: 요청 대상 계정이 있는지 없는지를 응답 차이로 알 수 없게 하는 원칙.
    있든 없든 같은 응답을 내면, 공격자가 이 API를 "가입 여부 조회기"로 쓸 수 없다. 친구
    프로필(MSG-186)과 비공개 영상(NFR-SEC-06)에서 이미 쓰는 원칙이다.
[^3]: 인터셉터(HandlerInterceptor): 스프링 MVC에서 컨트롤러 실행 직전에 끼어드는 공통 처리
    지점. URL 패턴으로 등록하고, 여기서 던진 예외는 컨트롤러 예외와 같은 경로(전역 핸들러)로
    변환된다. 시큐리티 필터보다 뒤에 실행되므로 인증이 끝난 사용자 정보를 쓸 수 있다.
[^4]: SES(Simple Email Service): AWS의 메일 발송 서비스. SDK 호출 한 번으로 메일을 보내고,
    자격 증명은 EC2 인스턴스에 붙은 IAM role로 해석돼 비밀번호 같은 별도 시크릿이 필요 없다.
    신규 계정은 샌드박스 상태라 검증된 주소로만 발송되며, 해제 신청 후 임의 주소로 보낼 수 있다.
[^5]: TTL(Time To Live): 저장소가 값을 자동 삭제하기까지의 수명. Redis는 키마다 TTL을 걸 수
    있어, 재설정 토큰의 30분 만료를 서버 코드의 시각 비교 없이 저장소가 스스로 집행한다.
[^6]: Lua 스크립트: Redis가 명령 여러 개를 중간에 다른 클라이언트가 끼어들 수 없는 한 덩어리로
    실행하게 하는 방법. 읽고 판단해서 쓰는 절차를 스크립트 하나로 보내면 그 사이의 경쟁 상태가
    구조적으로 사라진다. 이 레포는 검색어 중복 제거 등 다섯 곳에서 이미 쓰고 있다.
