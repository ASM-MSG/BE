# MSG-435: 검색 지역 필터용 시군구 목록 조회

**Owner**: A (region 패키지, 지도 인프라 도메인)
**요구사항 정본**: `docs/prd/MSG-435-prd.md` (상태: 검토됨, 2026-08-19 정민 승인) /
SRS `FR-REGION-15` (계획)

## 개요

앱 디자인 ver 6 검색/지역 필터 화면의 "전체 지역" 목록("마포구, 격자 2,841")용으로, 시군구
목록을 이름과 식별자와 격자 수와 함께 한 호출로 주는 신규 엔드포인트
`GET /api/regions/districts`를 만든다. 격자 수는 그 구의 전체 격자 수, 즉 소속 행정동[^1]들의
`regions.total_grid_count` 합이다(사용자 무관 값, 2026-08-19 정민 확정). 계산은 시딩 시점에
물질화[^2]된 값을 `parent_code`로 묶어 더하기만 하고, 이 경로에 공간 연산은 없다(FR-REGION-12
축 유지). 마이그레이션과 신규 에러코드는 없다.

## 배경과 목표

지역 조회 API는 행정동 단위뿐이라 시군구 목록 계약이 없고, 클라이언트가 행정동 전량(전국
3,558행)을 받아 직접 합산하는 우회는 화면과 서버의 정의가 어긋나기 쉽다(PRD 1장). 이 티켓은
시군구 목록을 서버 한 곳에서 정의해 준다. 값의 재료는 기존 수집률(MSG-156)과 전국
탐험률(MSG-406)이 쓰는 물질화 값과 같아 화면끼리 모순되지 않는다(FR-3).

비스코프: 시/도 수준 수집률 집계(FR-REGION-13, "서울 34%")는 여전히 범위 밖이다. 시군구 선택
후 FE 흐름(지도 이동인지 격자 목록인지)은 화면 티켓 미발행으로 미정인데, FR-4가 식별자를 기존
`parentCode` 축으로 보장하므로 어느 쪽이든 이 스펙을 막지 않는다(PRD 8장, 비차단). 최근
방문/최근 검색 칩과 장소 검색 자체도 범위 밖이다(PRD 2장).

## 성공 기준

1. 로그인 사용자가 요청 한 번으로 시군구 목록(이름, 식별자, 격자 수)을 받는다 (FR-1).
2. 각 시군구의 격자 수가 그 `parent_code` 산하 행정동들의 `total_grid_count` 합과 같다
   (FR-1, FR-3).
3. 격자 수가 0인 시군구는 응답에 없다 (FR-2).
4. 응답의 식별자를 기존 `GET /api/regions/stats?parentCode=`에 그대로 넣으면 같은 시군구로
   조회된다 (FR-4).
5. 목록은 시군구 이름 오름차순이고, 같은 이름(전국의 여러 "중구")은 식별자 순으로 결정적이다
   (FR-5 + 결정성 보강).
6. 실행 쿼리에 공간 연산이 없다 (비기능, FR-REGION-12).
7. 전국 3,558행 기준 EXPLAIN ANALYZE 실행시간 50ms 이내다 (비기능, D-5 합격 기준).

아래 "테스트 시나리오"가 이 기준의 검증 수단이다. 테스트에는 `// 검증: FR-REGION-15` 주석을 단다.

## 결정 사항 (D-항목)

### D-1. 엔드포인트는 신규 `GET /api/regions/districts`, 파라미터 없음

사용자 무관 값이므로 인증 외 입력이 없다.

- **`/stats` 계열 배치 기각**: 그 계열은 "내 수집률" 축이다(by-point, by-grid, national 전부
  로그인 사용자의 값). 사용자 무관 마스터 목록을 거기 두면 축이 흐려진다.
- **단위 일반화(`?unit=SIGUNGU`) 기각**: 시/도 목록 요구는 아직 없다(FR-REGION-13 유예).
  요구 없는 일반화는 만들지 않는다. 시/도가 필요해지면 그때 파라미터를 여는 게 확장 지점이다.

### D-2. 격자 수는 `SUM(regions.total_grid_count)`, 사용자 무관

PRD FR-1 확정 그대로다. 영상이 오른 격자 수(grids 행 수)도, 내 수집 격자 수(user_grids,
region_stats)도 아니다. 재료가 수집률과 전국 탐험률의 분모(MSG-406 D-4)와 같은
`total_grid_count` 한 곳이라 FR-3의 무모순이 구조적으로 성립한다. 사용자별 조회가 없으므로
쿼리에 userId가 등장하지 않는다.

### D-3. 0 제외는 HAVING[^3] 절 하나로

`HAVING SUM(total_grid_count) > 0`이 FR-2를 SQL 한 절로 충족한다. 애플리케이션 필터링 기각:
같은 판정을 두 곳에 두면 어긋날 자리만 생긴다. 참고로 `total_grid_count`는 경계 면적을 셀
면적으로 나눈 시딩 산출값이라 실데이터에서 0인 시군구는 사실상 없지만, 요구가 명시된 이상
가드는 쿼리에 남긴다.

### D-4. 시군구 이름은 MSG-356의 토큰 규칙 재사용

`split_part(region_name, ' ', 2)`로 전체 경로 이름("부산광역시 부산진구 부전2동")에서 둘째
토큰을 꺼낸다. `RegionUnit.SIGUNGU`(codePrefixLength 5, nameTokenIndex 2)와 뷰포트 시군구
집계(`GridRepository.aggregateOccupiedInRange`)가 이미 쓰는 규칙 그대로라, 지역 필터 화면과
뷰포트 집계 화면의 시군구 이름이 항상 같다. 같은 그룹의 이름은 접두가 같아 어차피 한 값이지만
집계 함수 자리라 `MIN`으로 결정적으로 단일화한다(MSG-356 선례 그대로).

### D-5. 응답 캐시 계층은 이번에 넣지 않는다 (성능 합격 기준 명시)

PRD 비기능이 "캐시 가능"이라 했지 요구하지는 않았다. regions는 3,558행이고 MSG-406 실측에서
같은 테이블 전체 스캔이 1ms 안팎, MSG-356 집계 벤치는 격자 1만 행 전국 시도 집계가
EXPLAIN ANALYZE 10.9ms였다. 이 조회는 그보다 단순한 regions 3,558행 GROUP BY다.

**합격 기준**: 전국 3,558행 시드 기준 EXPLAIN ANALYZE 실행시간 **50ms 이내**, regions
**Seq Scan 1회 허용**(전행 집계라 인덱스보다 스캔이 정상 계획이다. 이 기준 안이면 신규 인덱스
불요 판정이 확정된다). 구현 단계에서 실행 계획 원문과 실행시간을 작업 로그에 남긴다. 기준을
넘으면 그때 캐시(Redis 또는 HTTP 캐시 헤더)를 확장 지점으로 검토한다.

### D-6. 서비스는 `RegionStatsQueryService`에 메서드 추가

PRD 7장이 열어 둔 두 안(기존 서비스 수정 또는 전용 서비스 신규) 중 전자다. 값의 재료가 수집률,
탐험률과 같은 물질화 값이고 순수 SELECT라는 성격도 같다. 메서드 1개를 위해 인터페이스와 구현체
2파일을 새로 만들 이유가 없다. `RegionQueryService` 배치 기각: 그쪽은 geospatial 역지오코딩
서비스라 얹지 않는다는 판정(MSG-156 D5)이 이미 있다.

## API 명세

### GET /api/regions/districts

시군구 목록. 토큰 필수(SecurityConfig anyRequest, 다른 지역 조회와 같은 인가 수준). 파라미터
없음. 전국 시군구는 250개 안팎이라 페이지네이션 없이 전량 응답한다(PRD 비기능).

**성공 200** (`ApiResponseDto` 래핑 포함 전체 형태, `data`는 배열):

```json
{
	"developCode": 200,
	"message": "성공",
	"data": [
		{ "parentCode": "11680", "name": "강남구", "gridCount": 4102 },
		{ "parentCode": "11440", "name": "마포구", "gridCount": 2841 }
	]
}
```

- `parentCode` (String): 시군구 식별자. 행정동 코드 앞 5자리(`regions.parent_code`)로, 기존
  `GET /api/regions/stats`의 `parentCode` 파라미터에 그대로 넣어 이어 쓸 수 있다 (FR-4).
- `name` (String): 시군구 이름 (D-4 토큰 규칙).
- `gridCount` (Long): 그 구의 전체 격자 수. 사용자 무관 값이고 0인 행은 배열에 없다 (FR-2).
- 정렬: `name` 오름차순(COLLATE "C", 도메인 로직 참조), 같은 이름은 `parentCode` 오름차순
  (성공 기준 5).
- 화면 조립: "마포구, 격자 2,841"의 천 단위 구분 표기는 화면 몫이다. 서버는 원값 정수를 준다.

**에러**:

| 케이스 | HTTP | developCode | 비고 |
|---|---|---|---|
| 미인증 | 401 | 공통 UNAUTHORIZED | 시큐리티 공통 |

새 에러 코드 없음. 입력이 없어 검증 실패 유형이 없다(PRD 7장). 필요해지면 region 6xxx 대역이다.

### DTO

`region/dto/RegionDistrictResponseDto` (record, 신규). 필드는 위 JSON `data` 항목 그대로 3개.
시각 필드 없음이라 시각 컨벤션 이슈 없음. `RegionNationalStatResponseDto` 선례대로 `@Schema`
설명과 `from(View)` 정적 팩토리를 갖춘다.

## 도메인 로직

- `RegionStatsQueryService`에 메서드 추가 (region 패키지 내부 서비스, 크로스오너 계약 아님):

  ```java
  /** 시군구 목록 (MSG-435). 사용자 무관, 격자 수 0 제외, 이름순. 데이터 미시딩이면 빈 리스트. */
  List<RegionDistrictView> findDistricts();
  ```

- 구현(`RegionStatsQueryServiceImpl`): 검증할 입력이 없으므로 리포지토리 조회 후 뷰 변환만
  한다. regions 미시딩 환경에서는 빈 리스트다(에러 아님).
- 리포지토리(`RegionRepository`)에 native[^4] 조회 1건 추가. `split_part`가 표준 JPQL에 없어
  native이고, 기존 native가 모여 있는 이 리포지토리에 둔다:

  ```sql
  SELECT
  	parent_code                           AS "parentCode",
  	MIN(split_part(region_name, ' ', 2))  AS "name",
  	SUM(total_grid_count)                 AS "gridCount"
  FROM regions
  WHERE parent_code IS NOT NULL
  GROUP BY parent_code
  HAVING SUM(total_grid_count) > 0
  ORDER BY MIN(split_part(region_name, ' ', 2)) COLLATE "C", parent_code
  ```

  - `WHERE parent_code IS NOT NULL`: 스키마(V1)가 nullable이라 가드를 둔다. 시더는 항상
    채우므로 실데이터 no-op이지만, NULL 그룹이 목록에 유령 행으로 서는 것을 구조적으로 막는다.
  - `ORDER BY ... COLLATE "C"`: PostgreSQL 문자열 정렬은 데이터베이스 collation[^5]에
    좌우되므로, 환경(로컬/운영 로케일)에 무관하게 결정적이도록 코드포인트 순서를 명시한다.
    한글 음절 블록은 유니코드 코드포인트 순서가 곧 가나다순이라 COLLATE "C"가 가나다순
    정렬이다. COLLATE를 걸려면 출력 컬럼 번호가 아니라 식이어야 해서 MIN 식을 반복하는데,
    토큰 번호가 리터럴이라 MSG-356이 실측한 파라미터 자리 분리 거절 문제는 없다.
  - 토큰 숫자 2는 리터럴로 박는다(위 이유로 ORDER BY에 식이 반복되므로 바인딩보다 단순하다).
    값의 정본이 `RegionUnit.SIGUNGU.getNameTokenIndex()`라는 주석은 남긴다.
  - 프로젝션 인터페이스 `RegionDistrictProjection`(getter 3개), 내부 뷰
    `RegionDistrictView`(record). `RegionNationalStatView` 선례대로 서비스가 감싸고 DTO 변환은
    컨트롤러 책임이다.
- 이름 도출 검증 근거: 원천 데이터 전수에서 `region_name`은 공백 구분 3토큰이 성립하고, 세종도
  "세종특별자치시 세종시 조치원읍" 3토큰이라 둘째 토큰 "세종시"로 정상 도출된다(MSG-356
  2026-08-10 `data/region/` 실측). 기왕 표기 한계는 경기도 등 일반시의 시군구 토큰을 원천이
  "수원시장안구"처럼 붙여 쓰는 것 하나인데, MSG-356과 같이 원형 그대로 내려주고 표기 정형화가
  필요해지면 FE 표기나 데이터 후속 티켓 몫이다(두 화면이 같은 규칙이라 함께 움직인다).
- 용어: 이 목록의 격자 수는 점령(첫 영상 업로드)이나 방문(업로드 이벤트)과 무관한, 행정 경계
  면적에서 산출된 전체 격자 수다. 도감이나 수집 개념과 섞지 않는다(glossary 기준).

## 데이터 모델

변경 없음. 마이그레이션 없음.

- 신규 인덱스 불요 판단 근거: regions 3,558행 전체 스캔 + 250그룹 안팎의 GROUP BY라 MSG-406
  실측(같은 테이블 전체 스캔 약 1ms), MSG-356 벤치(1만 행 전국 집계 10.9ms)와 같은 자릿수로
  본다. `idx_regions_parent`가 이미 있으나 전행 집계라 스캔이 이긴다. 판정 확정은 D-5 합격
  기준(50ms 이내, Seq Scan 1회 허용)의 EXPLAIN ANALYZE 실측으로 한다.

## 계약 변경

없음. `RegionStatsQueryService`는 region 패키지 내부 서비스라(MSG-156 §계약 변경 판정 그대로)
크로스오너 계약이 아니고, `GridQueryService` 등 접점 인터페이스는 건드리지 않는다.

  같은 브랜치에서 함께 커밋한다.

[^1]: 행정동: 이 서비스 지역 데이터의 최소 단위. 전국 3,558개가 시딩되어 있고 코드 앞 5자리
    (parent_code)가 시군구를 가리켜, 매핑 테이블 없이 접두만으로 시군구 묶음이 나온다.
[^2]: 물질화: 조회 때마다 계산하지 않고 쓰기 시점에 미리 계산해 저장해 둔 값. 행정동별 전체
    격자 수(regions.total_grid_count)는 시딩 때 경계 면적에서 1회 산출되고, 이 스펙의 조회는
    그 값을 더하기만 한다.
[^3]: HAVING: SQL에서 GROUP BY로 묶은 뒤의 그룹에 거는 조건절. 행 단위 조건(WHERE)과 달리
    합계 같은 집계 결과로 그룹 자체를 걸러낼 수 있어, "격자 수 합이 0인 시군구 제외"를 한
    절로 표현한다.
[^4]: native 쿼리: JPA의 추상 질의어(JPQL) 대신 데이터베이스 방언 SQL을 그대로 쓰는 조회.
    프로젝트 컨벤션상 PostgreSQL 전용 기능에 한정하는데, 여기서는 토큰 추출 함수 split_part가
    표준에 없어 해당한다.
[^5]: collation: 데이터베이스가 문자열의 크고 작음을 비교할 때 쓰는 정렬 규칙. 설치 로케일에
    따라 달라질 수 있어, 환경 무관 정렬이 필요하면 쿼리에서 규칙(COLLATE "C" = 유니코드
    코드포인트 순)을 직접 지정한다.
