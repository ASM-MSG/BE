# MSG-457: AI 경로 추천 (지도 홈 다섯째 칩)

**Owner**: 공동 (주 구현 Owner B. Owner A 확인 지점은 계약 변경 절의 PlaceSearchService 1건)

> 요구사항 정본: `docs/prd/MSG-457-prd.md` (상태 검토됨). 이 스펙은 그 PRD의 FR과 비기능에
> "어떻게"만 붙인다. 내용이 어긋나면 PRD가 이긴다.
> SRS 참조: FR-ROUTE-01~13, NFR-SEC-08, NFR-SEC-09 (`docs/srs.md`).
> AI 서버 몫(MSG-458)은 구현과 실측까지 완료됐다. BE가 소비하는 계약의 정본은 FillMap-AI 레포
> 두 곳이다: `docs/MSG-458.md`의 "계약 변경" 절과 `README.md`의 "API (BE ↔ AI 계약)" 절
> (2026-08-23 확정). 이 스펙은 그 계약을 재서술하지 않고 BE 쪽 소비 규칙만 적는다.

## 개요

사용자가 자연어 한 문장과 지금 보는 지도 범위(뷰포트[^1])를 보내면, 서버가 보유한 활성
미션(축제, 팝업, 코스)과 행사, 그리고 장소 검색 실조회 결과에서 후보를 골라 방문 순서를 붙이고,
지점마다 추천 이유 한 줄을 실어 돌려주는 API 하나를 신설한다. 자연어 해석과 이유 문장화는
FillMap-AI 서버가 맡고(MSG-458, 완료), 후보 선정과 방문 순서 결정은 이 서버(BE)가 맡는다.
이 분담이 이 기능의 핵심 경계다: 모델은 실재하는 장소와 그럴듯한 장소를 구분하지 못하므로,
장소를 고르는 일은 데이터를 가진 쪽만 한다(FR-ROUTE-03).

지도 홈 칩은 다섯 종이 된다. 기존 경로추천 칩은 이름만 "코스"로 바뀌고 하던 일(두루누비 코스
목록, `GET /api/missions/active` 렌더 shape 필터)을 그대로 하며, "AI 경로추천" 칩이 새로 들어와
이 API를 부른다. 칩 이름과 토글은 FE 몫이라 BE 변경이 없다(PRD FR-10, FR-15).

## 배경 · 목표

2026-08-22 멘토링에서 "AI를 억지로 붙이지 말고 경로 추천을 AI로 옮겨라"가 나왔고, 같은 날
블러 일시 비활성이 확정되면서 사용자가 체감하는 AI 접점이 비었다. 미리 만든 코스 148개는
"오늘 뭘 어떤 순서로 볼지"라는 질문에 답하지 못한다. 재료(축제, 팝업, 코스, 행사, 장소 검색,
격자)는 이미 다 있으므로, 이 티켓은 그것을 한 답으로 엮는 층 하나를 만든다.

## 응답 시간 상한 확정 (PRD 미해결 항목의 해소)

실측 재료는 FillMap-AI `results/MSG-458-report.md`(2026-08-23, AI 전용 t3.small EC2)다.
HTTP 왕복 중앙값이 parse 1,229ms에 explain 1,060ms, 관측 최악 회차가 1,561ms였고, 블러 잡
경합의 영향은 사실상 없었다(네트워크 대기가 지배항).

- **AI 호출당 타임아웃 5초로 확정한다.** 관측 최악 1.6초의 3배 여유이고, 리포트가 제안한
  수치를 그대로 채택한다. JdkClientHttpRequestFactory의 readTimeout은 교환 전체(요청 전송,
  처리, 응답 수신)의 단일 시한이 되므로(AiClient 주석의 확인 사항) AI 2회 구간은 트리클[^5]
  응답에도 5초가 하드 상한이다.
- **장소 검색은 요청당 최대 1회다.** 카카오 호출은 기존 SearchConfig 타임아웃(connect 1초,
  read 3초)을 그대로 쓰므로 호출당 명목 최악 4초다. 여러 건을 직렬로 부르면 검색만으로 예산이
  무너지므로 호출 수를 계약으로 묶는다(후보 수집 절의 검색 규칙과 같은 값).
- **API 전체 응답의 설계 예산은 15초다.** 명목 최악 합산이 parse 5초, 카카오 1회 4초, explain
  5초, BE 내부 여유 1초다. 이 예산은 하드 보장이 아니라 명목 최악 합산이다: 카카오 구간의 read
  3초는 바이트 간 비활성 시한이라 트리클 병리 케이스에서 명목을 넘을 수 있고, BE 내부 구간
  (DB, region 조회)에는 별도 시한이 없다. 이 둘은 **잔여 위험으로 수용한다**. 근거: 트리클은
  상대 서버가 살아서 천천히 흘려야 성립하는데 카카오와 AI 서버 모두 자체 서버측 시한을 갖고
  있고(AI는 `ROUTE_AI_TIMEOUT_SEC`), BE 내부 구간은 실측 수 ms 수준이다(미션 뷰포트 조회 웜
  p95 4.0ms, MSG-398). 무한 대기는 어느 경로에도 없다(모든 외부 호출에 시한, 호출 수 고정).
  **PRD 비기능 "상한 안에 응답하거나 실패로 끝낸다"는 이 해석(설계 예산 + 잔여 위험 수용)으로
  이행한다.** 컨테이너 수준 전체 데드라인(WebAsyncTask)은 채택하지 않았다. 응답만 일찍 끊을 뿐
  작업 스레드와 외부 비용은 계속 나가므로 보장의 실체가 얇은데, 대가로 이 레포에 없던 비동기
  MVC 경로가 들어오기 때문이다. 이 해석은 2026-08-24 성민이 수용을 확정했다.
- 기대(정상) 응답은 3초 이내다. 실측 중앙값 합산 약 2.3초에 BE 내부 구간은 수 ms 수준이다.
- 후속 통보: AI 서버의 `ROUTE_AI_TIMEOUT_SEC` 기본 30초는 무한 대기 방지용 안전핀인데, AI 레포
  문서가 "BE 상한 확정 시 그 이하로 조정한다"고 정해 뒀다. 이 확정(5초)을 AI 레포에 알려 노브를
  내리게 한다(코드 변경 없는 환경변수 조정).

## API 명세

### `POST /api/routes/recommend`

인증 필수(SecurityConfig anyRequest 관례, 미인증 401). 사용자별 요청 제한(FR-ROUTE-12)에
로그인 사용자 id를 쓰므로 비로그인 조회는 없다.

요청 `RouteRecommendRequestDto`:

```json
{
	"text": "부산역 내려서 해운대에서 밥 먹고 축제도 보고 싶어",
	"viewport": {"minLat": 35.05, "minLng": 128.95, "maxLat": 35.25, "maxLng": 129.20},
	"origin": {"lat": 35.115, "lng": 129.042}
}
```

| 필드 | 타입 | 규칙 |
|---|---|---|
| `text` | String | 필수, trim 후 1~500자(AI 계약과 같은 상한). 위반은 `@Valid`로 공통 400(신규 코드 없음, PlaceSearchController 선례) |
| `viewport` | 객체 | 필수, WGS84 사각형. **min이 max보다 크거나 같음(등호 포함, 넓이 0 불가), 위경도 범위 밖(위도 ±90, 경도 ±180), 비유한값(NaN, Infinity)은 전부 14400**, 한 변 0.5도 초과는 14401(미션 뷰포트 조회와 같은 값). AI의 Viewport 검증(엄격, 등호도 422)과 같은 규칙을 **parse 호출 전에 BE가 적용**한다. 통과 못 한 요청이 AI까지 가서 422로 돌아오면 의미가 다른 14502로 새기 때문이다 |
| `origin` | 객체, 선택 | 출발 지점 좌표. 있으면 동선이 여기서 시작한다(FR-ROUTE-11). **lat ±90, lng ±180, 유한값 검증은 `@Valid`로 공통 400**(필드 단위라 text와 같은 경로). 입력 UI는 디자인 미확정이지만 API는 좌표 하나로 충분하다 |

응답 `RouteRecommendResponseDto` (성공은 항상 200, 후보 부족도 성공이다):

```json
{
	"points": [
		{
			"order": 1,
			"name": "해운대 빛축제",
			"kind": "MISSION_FESTIVAL",
			"lat": 35.1587,
			"lng": 129.1604,
			"gridId": "16941_11439",
			"zoneName": "해운대",
			"zoneCell": "B-3",
			"regionName": "우동",
			"reason": "8월 말까지 열리는 빛축제라 저녁 일정으로 맞습니다.",
			"missionId": 12,
			"occurrenceId": null
		}
	],
	"notice": null
}
```

| 필드 | 타입 | 규칙 |
|---|---|---|
| `points[].order` | Integer | 1부터 연속. 방문 순서다 |
| `points[].name` | String | 지점 이름. **원문 그대로다**(AI로 보낼 때만 100자 절단, 이유 문장화 절) |
| `points[].kind` | String | `MISSION_FESTIVAL`, `MISSION_POPUP`, `MISSION_COURSE`, `EVENT`, `PLACE` 다섯 값. FE 마커 분기용 |
| `points[].lat/lng` | double | WGS84 대표 좌표 |
| `points[].gridId` | String | 격자 ID. 대표 좌표를 GridEncoder로 즉석 계산한다 |
| `points[].zoneName/zoneCell` | String, nullable | 표시명 재료(MSG-341). 구역 밖이면 쌍으로 null |
| `points[].regionName` | String, nullable | 행정동 폴백 재료(MSG-349 정책과 동일). 무귀속이면 null |
| `points[].reason` | String | 추천 이유 한 줄(FR-ROUTE-05). AI explain 응답의 reasons 항목 그대로 |
| `points[].missionId` | Long, nullable | 미션 후보면 미션 id. FE가 미션 상세로 잇는 데 쓴다 |
| `points[].occurrenceId` | Long, nullable | 행사 후보면 회차 id |
| `notice` | String, nullable | 후보 부족 안내(FR-ROUTE-07). 지점 3개 이상이면 null, 0~2개면 안내 문구가 실린다 |

시각 필드가 없으므로 시각 컨벤션(MSG-376) 검사 대상이 아니다. 기간 정보는 `reason` 문장에
녹아 나간다.

### 에러 (RouteErrorCode, 14xxx 대역)

대역 배정은 `response-pattern.md` 표에 이미 추가돼 있다(같은 브랜치, 표 갱신 커밋 선행 규칙).

| developCode | 상수 | HTTP | 조건 |
|---|---|---|---|
| 14400 | `INVALID_VIEWPORT` | 400 | min ≥ max(등호 포함), 위경도 범위 밖, 비유한값. parse 호출 전 검증이다 |
| 14401 | `VIEWPORT_TOO_LARGE` | 400 | 한 변 0.5도 초과 |
| 14429 | `ROUTE_RATE_LIMITED` | 429 | 같은 사용자의 직전 시도 후 10초 안의 재요청. 직전 시도의 성공 여부는 따지지 않는다(FR-ROUTE-12) |
| 14502 | `ROUTE_AI_UNAVAILABLE` | 502 | AI 호출 실패 전부와 형태 위반. 아래 소비 규칙 참조 |
| 14503 | `ROUTE_DISABLED` | 503 | `route.ai.enabled` 꺼짐. 명시적 비활성 응답(비기능 운영) |

메시지 예: 14502 "동선 해석이 일시적으로 어렵습니다. 잠시 후 다시 시도해주세요"(HIGHLIGHT_UPSTREAM_ERROR
3502 문구 선례), 14503 "AI 경로 추천이 꺼져 있습니다".

## AI 서버 소비 계약 (MSG-458)

계약 형태의 정본은 FillMap-AI 레포다. 여기에는 BE가 지킬 소비 규칙만 적는다.

- **`POST /route/parse`**: `{text, viewport}`를 보내고 `{region, period, interests,
  preferred_order}`를 받는다. viewport 키는 AI 계약 표기(`min_lat` 등 snake_case)를 따른다.
- **`POST /route/explain`**: `{points: [{name, kind, facts}]}`를 보내고 `{reasons}`를 받는다.
  `reasons`는 **문자열 배열**이며 points와 같은 개수, 같은 순서다. points 0개는 AI가 422로
  거부하는 요청이므로 BE가 만들지 않는다(도메인 로직의 빈 후보 분기).
- **facts는 지점당 1~5개, 하한이 1이다.** 빈 배열을 보내면 AI 서버가 422로 거부한다(2026-08-23
  계약 개정). BE는 어떤 지점이든 사실 문장을 최소 1건 만들 수 있도록 출처 문장을 상시 포함한다
  (아래 도메인 로직의 facts 구성).
- **AI 입력 상한은 BE가 조립 시점에 보장한다.** name 100자, facts 각 100자 절단(이유 문장화
  절). BE 데이터가 계약 상한을 넘어 422로 튕기는 일이 없게 하는 몫이다.
- **실패 수용은 단일 수렴이다.** AI의 502(모델 실패, 형태 위반), 503(AI 쪽 플래그 꺼짐),
  504(모델 타임아웃), 그리고 BE 쪽 연결 실패와 5초 타임아웃 전부를 "해석 실패" 하나로 받아
  14502로 변환한다. 부분 채택이나 지어낸 대체 결과는 없다(FR-ROUTE-08).
- **BE도 형태를 검증한다. 검증 목록은 계약 전체와 1:1이다.** 위반은 전부 14502다. AI 서버가
  같은 검증을 이미 하지만 외부 응답을 신뢰 경계 안으로 들이지 않는다(NFR-SEC-08의 BE 몫
  "형식이 어긋난 해석 결과는 채택하지 않는다").
  - parse: `region` null 또는 50자 이하 문자열. `period` null 또는 {start, end} 유효 날짜에
    start가 end보다 늦지 않을 것(계약 표에는 없지만 활성 필터에 쓰는 값이라 BE가 방어한다).
    `interests` 최대 10개, 각 50자 이하. `preferred_order` 최대 10개, 각 50자 이하.
    **정의 밖 필드가 있으면 거부**(계약의 "미정의 필드는 나오지 않는다"를 BE 쪽에서도 지키는
    몫. 이 역직렬화에 한정해 미지 필드 실패를 켠다).
  - explain: `reasons` 개수와 순서가 points와 일치. 각 항목은 개행 없는 1~120자 문자열이고
    빈 문자열은 불가.
- **요청에 사용자 식별 정보 필드가 없다**(NFR-SEC-09). 계약 자체에 자리가 없고, BE가 만드는
  facts에도 닉네임 등 사용자 정보를 넣지 않는다.

## 도메인 로직

처리 순서는 PRD 시퀀스 그대로다: parse, 후보 수집, 순서 배열, explain, 응답 조립.
**분기 하나가 여기 얹힌다: 후보가 0개면 explain을 부르지 않고 빈 `points`와 `notice`로 즉시
성공 응답한다**(FR-ROUTE-07). AI 계약이 points 0개를 422로 거부하므로, 빈 후보를 explain에
태우면 성공이어야 할 응답이 14502 실패로 뒤집힌다. 이 분기가 그 모순을 끊는다.

### 1. 후보 수집 (RouteCandidateCollector)

기존 조회를 읽기로만 재사용한다. 후보는 아래 세 출처에서만 나온다(FR-ROUTE-03).

- **미션**: `MissionQueryService.getMissionsInViewport(bounds, type)`을 EVENT, POPUP, COURSE
  세 유형에 대해 호출한다(1시간 스냅샷 캐시 위 메모리 필터라 비용이 무시 가능하다). 다만 이
  조회의 활성 판정은 스냅샷 시점 기준이라 최대 1시간 낡을 수 있다(CACHE_TTL 1시간, MSG-398 D1).
  축제가 스냅샷 직후 끝나면 캐시는 그 축제를 활성으로 계속 내놓으므로, **route 서비스가 주입받은
  Clock의 요청 시점으로 `startAt`과 `endAt`을 재필터한다**(null은 상시 미션이라 통과).
  `MissionResponseDto`가 두 필드를 이미 실어 계약 변경 없이 가능하다. FR-ROUTE-04의 "요청 시점
  활성"은 이 재필터가 보장한다. 대표 좌표는 축제와 팝업이 판정 사각형 중앙 셀 중심(MSG-437
  귀속점 규칙 재사용), 코스가 PATH 시작점이다.
- **행사**: `EventQueryService.getOccurrencesInViewport(bounds)`로 예정, 진행 중 회차를 얻는다
  (이 조회는 캐시 없이 `statusAt` 파생값으로 요청 시점 판정이라 재필터가 필요 없다). 회차들의
  위치는 신설 일괄 조회(계약 변경 절)로 한 번에 받아, **회차마다 뷰포트 안에 드는 위치만 남기고
  그중 정렬 첫 항목(진입 기본값이라는 기존 정렬 계약)을 대표 지점으로 쓴다.** 이 조회는
  "뷰포트에 걸친" 회차를 주므로 위치가 흩어진 행사(BIFF류)는 정렬 첫 위치가 뷰포트 밖일 수
  있는데, 사용자가 보는 범위 밖 지점을 추천하면 FR-ROUTE-06 위반이다. **뷰포트 안 위치가
  하나도 없는 회차(bbox 교차만으로 잡힌 경우)는 후보에서 제외한다.**
- **장소 검색**: 관심사가 미션과 행사로 안 채워질 때만, **요청당 최대 1회** 부른다. 검색어는
  미충족 관심사 중 첫째(해석 결과 배열 순서)로 "{region, 없으면 뷰포트 중심 행정동 이름}
  {관심사}"를 조립하고, 결과 상위 3건을 후보로 쓴다. 호출 수 1회는 응답 시간 상한 산술의
  전제다(상한 확정 절). 카카오 실조회 결과라 실재 장소만 들어오고, 결과는 응답 조립 후
  보관하지 않는다(약관, MSG-251. 이 기능은 결과를 저장하지 않으므로 자동 충족).

**해석 결과의 문자열은 후보를 만들지 못한다.** `interests`는 검색어 재료일 뿐이고
`preferred_order`는 순서 힌트일 뿐이다. 인젝션[^2]이 해석을 뒤틀어도 영향 반경은 "이상한
검색어"까지이며, 없는 장소가 결과에 실리는 일은 구조적으로 없다(NFR-SEC-08).

**선별 규칙**: 관심사 키워드가 제목, 유형, 소개문에 포함되는 후보를 우선하고, 같은 급이면
뷰포트 중심에서 가까운 순, 그것도 같으면 gridId 사전순이다. 관심사가 비면(빈 해석 포함) 전
후보를 거리순으로 뽑는다. 그래서 빈 해석이어도 뷰포트 기준 추천이 성립한다(FR-ROUTE-06).
`period`가 있으면 미션과 행사의 기간과 **겹침**으로 판정하되 앞뒤 2일 여유를 둔다. 모델의
"이번 주말" 해석이 이틀 어긋난 실측 관찰(MSG-458 리포트) 때문에 엄격 일치 필터를 쓰지 않는다.

**지점 수 상한은 8이다**(FR-ROUTE-13). 하루에 다닐 수 있는 분량으로 고른 값이고, AI explain의
방어 상한 20보다 충분히 안쪽이다. 후보가 3개 미만이면 찾은 만큼과 `notice` 안내를, 0개면
도입부 분기대로 explain 없이 빈 `points`와 안내를 내린다(FR-ROUTE-07). 실패가 아니라 성공
응답이다.

### 2. 순서 배열 (RouteOrderPlanner)

결정적[^3] 규칙만 쓴다(FR-ROUTE-10). 난수와 시각 의존이 없다.

1. `preferred_order` 힌트 항목이 선정된 후보 이름과 부분 일치하면, 그 후보들을 힌트 순서대로
   앞에 배치한다. 일치하지 않는 힌트는 무시한다(후보를 만들지 않는다).
2. 나머지 후보는 최근접 이웃으로 잇는다. 시작점은 `origin`이 있으면 그 좌표(FR-ROUTE-11),
   없으면 힌트 배치의 마지막 지점, 그것도 없으면 뷰포트 중심이다.
3. 거리 동률은 gridId 사전순으로 끊는다.

거리는 대표 좌표 간 하버사인이면 충분하다(도보 경로 계산은 비목표). 같은 입력이면 같은 출력이
나오는 것을 단위 테스트로 고정한다.

**FR-ROUTE-10("같은 요청을 다시 보내면 같은 순서")의 충족 범위는 캐시 창 안이다.** BE 구간은
위 규칙으로 결정적이지만 AI 해석은 temperature 0으로도 완전 결정성이 보장되지 않으므로,
**parse 결과를 (text, viewport 좌표) 키의 메모리 TTL 캐시(10분, 최대 1,000건)로 안정화한다.**
캐시 창(10분) 안의 재요청은 같은 해석, 같은 후보 조건, 같은 순서 규칙을 타서 문면대로 같은
결과가 온다. 부수 효과로 유료 parse 재호출이 줄어든다. **창 밖의 재요청은 parse를 다시 타므로
BE 구간 결정성만 보장된다.** 요구 단서 "후보 데이터가 그대로인 동안"은 10분보다 길 수 있어
완전한 문면 충족은 parse 결과 영속화 없이 불가능한데, 결과 저장은 PRD 비목표라 여기서 늘리지
않고 미해결 질문으로 올린다. 캐시 금지 약관은 카카오 장소 검색 결과에만 해당하고 parse 결과는
무관하며, 사용자 문장이 메모리에 잠시 머무는 것은 외부 전송이 아니라 NFR-SEC-09와도 무관하다.
영속 저장이 아니라 PRD 비목표(결과 저장)와 충돌하지 않는다.

### 3. 이유 문장화 (facts 구성, BE 몫)

AI 계약이 "facts에 무엇을 담을지는 BE 스펙 몫"으로 남긴 부분이다. 지점당 아래 순서로 조립하고
각 문장은 100자에서 자른다(AI 계약 상한).

1. 출처 문장, 상시 1건: "8월 축제 미션 후보", "행사 위치", "장소 검색 결과" 류. 하한 1 보장.
2. 기간이 있으면: "2026-08-01~08-31 진행 중".
3. 관심사가 일치했으면: "관심사 '축제' 일치".
4. 직전 지점이 있으면: "이전 지점에서 1.2km".

최대 4건이라 상한 5를 넘지 않는다. **explain 요청의 `name`도 조립 시점에 100자로 잘라
보낸다.** missions.title이 VARCHAR(200)이라 101~200자 제목이 실재할 수 있는데, AI 계약의
name 상한은 100자라 그대로 보내면 422, 곧 전체 14502로 유효한 추천이 통째로 죽는다. 절단은
AI로 보내는 요청에만 적용하고 **클라이언트 응답의 `name`은 원문 그대로다**(API 명세의 응답 표).
`kind`는 응답 DTO의 다섯 값을 소문자로 보낸다(AI는 분기하지 않는 자유 문자열). explain이
돌아오면 reasons를 순서대로 `points[].reason`에 싣는다. explain 실패도 전체 실패(14502)다.
추천 이유가 이 기능의 인상을 만든다는 판단으로 왕복 2회를 유지하기로 한 확정(2026-08-22)에
따라, 이유 없는 결과를 내리는 절충은 하지 않는다.

### 4. 요청 제한 (FR-ROUTE-12)

사용자당 최소 간격 10초를 메모리 맵으로 지키되, **창 선점은 요청 접수 시점에 원자적으로 한다**:
`ConcurrentHashMap.compute(userId, ...)`로 직전 시도 시각의 판정과 이번 시도 시각의 기록을 한
번에 처리해, 동시 요청 두 개가 둘 다 통과하는 경합을 막는다. 기록하는 값은 성공 시각이 아니라
**시도 시각**이고, 요청이 실패해도 되돌리지 않는다. parse까지 갔다 실패한 요청도 외부 비용은
이미 나갔으므로 실패를 창 소모로 치는 쪽이 FR-ROUTE-12의 근거(호출마다 외부 비용 발생)와 맞고
구현도 단순하다. 위반은 14429다. 단일 인스턴스 전제의 의도적 단순화이고, 다중 인스턴스가 되면
Redis로 옮긴다(구현에 ponytail 주석으로 상한을 남긴다). 시각은 주입받은 Clock으로 읽는다(컨벤션).

### 5. 스탬프와 기존 동작 불변 (FR-ROUTE-09)

이 기능의 전 구간이 읽기 전용이다. 스탬프 판정 규칙(FR-MISSION-03)을 호출하지도 우회하지도
않는다. 추천에 코스 미션이 나와도 스탬프는 지금처럼 그 격자에 영상을 올려야 나온다.

### 지표 로그 (비기능 운영)

요청당 한 줄을 남긴다: `[route] outcome=ok|insufficient|ai_error|rate_limited total_ms=..
parse_ms=.. explain_ms=.. points=..`. 사용자 문장 원문과 AI 응답 원문은 로그에 남기지 않는다
(AI 서버 쪽과 같은 규칙). 호출 건수와 실패율은 이 라인 집계로 얻는다.

## 데이터 모델

변경 없음. 신규 테이블도 Flyway 마이그레이션도 없다. 추천 결과와 카카오 응답을 저장하지 않는
것이 약관과 비목표의 이행이다. parse 해석 캐시(순서 배열 절)는 메모리 TTL이라 영속 저장이
아니다.

## 계약 변경

- **PlaceSearchService(Owner A)에 집계 없는 조회 추가가 필요하다. 이 스펙에서 유일한
  크로스오너 확인 지점이다.** 기존 `searchPlaces(long userId, String q)`는 유효 검색어를
  검색어 집계[^4](인기 검색어 재료, 사용자와 검색어당 일 1회)에 접수한다. 경로 추천이 만드는
  검색어는 사용자가 입력창에 친 것이 아니라 기계 조립 문자열이라, 이 경로로 흘리면 인기
  검색어가 오염된다. 비파괴 오버로드 `searchPlaces(String q)`(집계 없음, 결과 규칙은 기존과
  동일)를 추가하고 route가 그것만 부른다. **Owner A 리뷰 확인 필수.** 합의가 안 되면 대안은
  기존 메서드 재사용(오염 수용)이며 그 판단은 사용자에게 올린다.
- **EventQueryService에 여러 회차의 위치를 한 번에 주는 경량 일괄 조회를 신설한다**(PRD의
  "부족하면 비파괴 추가" 조건 발동. 둘 다 Owner B 자기 도메인이라 경계 합의는 불요).
  회차마다 `getLocations`를 부르면 존재 확인, 위치, 격자, 영상 수, 표시명 조회가 회차 수만큼
  반복돼 컨벤션의 N+1 금지에 걸린다. 형태 예시는 `Map<Long, List<...>> getLocationsBulk(
  Collection<Long> occurrenceIds)`류로 개발 몫이되, route에 필요한 값은 이름, 좌표, gridId
  정도이므로 **영상 수 실측 등 route에 불필요한 값은 빼도 된다.** 기존 `getLocations` 시그니처는
  불변이고, javadoc의 "event 도메인 내부용 계약, 다른 도메인이 소비하지 않는다" 문구도 route
  소비에 맞게 이때 함께 갱신한다.
- 소비만 하고 시그니처가 바뀌지 않는 계약: `GridQueryService.resolveRegionNames`(행정동 이름
  일괄, MSG-439 신설분 그대로), `ZoneNameQueryService.resolver()`(표시명 재료, 요청당 1회 로드
  후 지점마다 resolve, N+1 봉쇄 계약 준수).
- `MissionQueryService`는 기존 메서드로 충분해 무변경이다(PRD의 "부족하면 비파괴 추가" 조건
  불발동). 활성 재필터 재료(`startAt`, `endAt`)도 기존 `MissionResponseDto`에 이미 있다.
- 신규 `RouteIntentClient`는 route 패키지 내부 타입이라 계약 인터페이스가 아니다. 기존
  `video/service/AiClient`는 영상 전용이라 재사용하지 않는다(PRD 확정).

## 설정

`RouteAiProperties`(record, `@ConfigurationProperties(prefix = "route.ai")`, AiProperties 관례):

```yaml
route:
  ai:
    enabled: ${ROUTE_AI_ENABLED:false}      # 기본 꺼짐(NFR-OPS-06 관례). 꺼지면 14503
    base-url: ${ROUTE_AI_BASE_URL:http://localhost:8000}
    timeout: ${ROUTE_AI_TIMEOUT:PT5S}       # AI 호출당 상한, 실측 근거는 상한 확정 절
```

**빈 구성**: 컨트롤러와 서비스는 상시 빈이다. `RouteIntentClient`만
`@ConditionalOnProperty(prefix = "route.ai", name = "enabled")`로 켜질 때 뜨고,
`RouteRecommendServiceImpl`은 그것을 **`ObjectProvider<RouteIntentClient>`로 받아** 부재면
(플래그 꺼짐, 기본) 14503을 던진다. 직접 주입하면 기본 설정에서 기동이 깨지고, 서비스와
컨트롤러까지 조건부로 만들면 14503 대신 404가 나간다. `HighlightPreviewServiceImpl`이 같은
이유로 `ObjectProvider<AiClient>`를 쓰는 선례이고 주석에도 그 근거가 남아 있다.

타임아웃은 JdkClientHttpRequestFactory의 readTimeout으로 교환 전체에 건다(AiClient
highlightRequestFactory 선례, connect는 2초). dev는 AI 전용 EC2 `http://10.0.1.45:8000`이
`ROUTE_AI_ENABLED=1`로 가동 중이라 base-url만 넣으면 바로 붙는다. video 쪽 `ai.*` 설정과 키를
섞지 않는다. 블러가 꺼진 환경에서도 경로 추천은 독립으로 켠다.

## 테스트 시나리오

- `잘못된_좌표는_AI_호출_전에_걸러진다`: 넓이 0 뷰포트(min==max)와 위도 91, NaN은 14400,
  범위 밖 origin은 공통 400, 전 케이스에서 parse 미호출(MockRestServiceServer 기대 0회)

- `200자_제목_미션이_후보여도_성공한다`: explain 요청의 name은 100자 절단, 응답의 name은 원문

## 미해결 질문

PRD 미해결 중 스펙이 해소한 것: 응답 시간 상한(확정 절), developCode 대역(14xxx 배정 완료),
SRS 등재(FR-ROUTE-01~13 등재 완료). 결과 저장은 비목표 유지로 종결한다(발표 데모 반복 재생
수요가 실제로 생기면 별도 티켓).

- [x] **응답 시간 상한의 이행 방식은 확정됐다(2026-08-24 성민).** "설계 예산 15초 + 잔여 위험
      (카카오 트리클, BE 내부 무시한) 수용"을 그대로 채택한다(근거는 상한 확정 절). 컨테이너
      수준 데드라인(WebAsyncTask)은 기각으로 종결.
- [x] **FR-ROUTE-10 문구와 실현 범위의 간극은 해소됐다(2026-08-24 성민).** 권고대로 SRS
      문구를 "짧은 간격의 재요청" 한정으로 조정했다(변경 이력은 `docs/srs-changelog.md`).
      스펙의 보장(해석 캐시 창 안의 재요청은 같은 순서, 창 밖은 BE 구간 결정성)이 조정된
      요구 문면과 일치한다.

남는 것은 전부 디자인 몫이라 구현을 막지 않는다:

- [ ] 왼쪽 패널 구성(자연어 입력창 자리, 결과 카드 표시). API 계약은 이 스펙으로 고정이고
      화면은 디자인 확정을 따라간다.
- [ ] 앱(390) 칩 다섯 개 배치.
- [ ] 출발 지점 입력 방식(지도에서 찍기, 검색, 현재 위치). API는 `origin` 좌표 선택 필드로
      이미 수용한다.
