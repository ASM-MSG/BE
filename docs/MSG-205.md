# MSG-205: 계정 삭제 API (즉시 물리 삭제 + 연쇄 정리)

**Owner**: B (단독 — user·video·auth 전부 Owner B, Owner A 패키지 무접촉)

> 요구사항 정본: `docs/prd/MSG-205-prd.md` (상태: 검토됨, 2026-08-01 사용자 승인).
> 이 스펙은 PRD FR-1~8·비기능에 "어떻게"만 붙인다. PRD 미해결 질문으로 남긴 구현 세부
> 4건(§결정 D1~D4)을 여기서 확정한다.

## 개요

`DELETE /api/users/me` 한 호출로 계정을 즉시·비가역 삭제한다. DB 연쇄 삭제는 FK CASCADE가
전담하고(앱 보정 로직 없음), 유일한 실질 신규 로직은 **영상 S3 객체 일괄 정리**(1000키/요청
청크)다. 세션 무효화는 기존 로그아웃 경로(`RefreshTokenService.deleteAll` + 액세스 토큰
블랙리스트)를 재사용한다. 선행 마이그레이션 1건(V15 — reports FK ON DELETE 정책).

## 배경 · 목표

- 개인 위치·영상이 쌓이는 서비스에서 "내 데이터를 지우고 나간다"가 성립해야 한다. user 패키지에
  API가 전무해(entity/repository/exception만 존재) IA "설정 > 계정 삭제"가 미구현 상태.
- 위키 열린 질문(reports FK 때문에 하드 삭제 불가)을 PRD가 "즉시 물리 삭제 + V15"로 확정했고,
  이 스펙이 구현 방법을 못 박는다.

## 성공 기준

- 삭제 호출 후: users 행 0 · FK 연쇄 10테이블 개인 데이터 0행 · 그 유저 영상 S3 객체 삭제 요청됨 ·
  전 디바이스 refresh 세션 소멸 · 요청에 쓴 액세스 토큰으로 후속 호출 401.
- 같은 이메일/카카오 계정 재로그인 → 신규 가입 성공 (UNIQUE 충돌 없음).
- 타 사용자 데이터·grids 행 무변경. 아래 "테스트 시나리오"가 검증 수단.

## API 명세

### DELETE /api/users/me

| 항목 | 내용 |
|---|---|
| 인증 | 필수 (SecurityConfig 기본 `authenticated` — 설정 무변경). 경로에 대상 식별자 없음 — 본인만 |
| 요청 | 바디 없음. `Authorization: Bearer {access}` (블랙리스트용 원문 토큰) |
| 성공 | `SuccessResponse<Void>` — HTTP 200, developCode 200, body null (logout·영상 삭제와 동일 관례). `Set-Cookie: RefreshTokenCookies.expire()`로 refresh 쿠키 만료 (AuthController.logout:145 관례) |
| 실패 | `1404 USER_NOT_FOUND` — users 행 이미 없음 (§D3). 그 외 인증 실패는 기존 필터/공통 처리 |

컨트롤러 시그니처 (user 패키지 첫 컨트롤러):

```java
@DeleteMapping("/me")
public SuccessResponse<Void> deleteMe(
	@Parameter(hidden = true) @AuthenticationPrincipal AuthPrincipal principal,
	@RequestHeader(HttpHeaders.AUTHORIZATION) String authorization,
	HttpServletResponse response
) {
	userService.deleteAccount(principal.userId(), authorization.substring(BEARER_PREFIX.length()));
	response.addHeader(HttpHeaders.SET_COOKIE, RefreshTokenCookies.expire());
	return new SuccessResponse<>(null);
}
```

- userId는 principal에서 (VideoController.delete:125-129 선례 — 컨트롤러 메서드명 `delete`, 서비스가 `deleteVideo`), 원문 토큰은
  `@RequestHeader`에서 (AuthController.logout:136 선례) — §D4. 엔드포인트가 authenticated라
  필터 통과가 보장되므로 logout 같은 null 가드는 불필요 (`required` 기본 true).
- Request/ResponseDto 없음 — 입력은 인증 컨텍스트뿐, 출력은 body null.

## 도메인 로직

`UserService`(인터페이스) + `UserServiceImpl` 신설. `deleteAccount(Long userId, String accessToken)`:

**1. 트랜잭션 내 (단일 트랜잭션 — 전부 아니면 전무)**

1. S3 키 수집 — 그 유저 **영상**(방문 이벤트 행) 전체의 4컬럼
   `original_s3_key`·`encoded_url`·`thumbnail_url`·`blurred_s3_key` (뒤 3개도 컬럼명과 달리
   실제 S3 key — Video.java:54-64,87-89 주석). `status = 'DELETED'`(soft) 행도 포함해 전량 수집 —
   없는 키는 DeleteObjects가 에러 없이 넘어가므로 무해.
2. `DELETE users WHERE id = :userId` — FK CASCADE가 videos·user_grids·region_stats·push_tokens·
   friendships·streaks·user_badges·likes·user_missions·reports(V15)를 연쇄 제거.
   **video_count 감소·region_stats recompute 등 보정 로직 금지** — 행이 통째로 사라지므로 무의미.
3. 삭제 행 수 0이면 `throw new ApiException(UserErrorCode.USER_NOT_FOUND)` (§D3).

**2. 커밋 이후 (afterCommit — best-effort, 실패는 로그만)**

VideoServiceImpl.afterCommit(:324-335) 패턴 재사용 (동기화 비활성 시 즉시 실행 폴백 포함):

1. 수집 키 S3 일괄 삭제 — **1000키/요청 청크 분할** (§S3 정리).
2. `refreshTokenService.deleteAll(userId)` — 전 디바이스 refresh 소멸 (RedisRefreshTokenStore.deleteAll:42,
   SCAN 기반 — KEYS 금지 결정 MSG-135 준수, 기존 그대로 재사용).
3. `tokenProvider.invalidateAccessToken(accessToken)` — 액세스 토큰 블랙리스트 (AuthService.logout:58 관례).

커밋 이후 정리(S3·Redis 공통) 실패를 500으로 응답하지 않는다 — 이미 커밋된 삭제가 "실패"로
보이는 역전을 막는다 (VideoServiceImpl deleteQuietly 주석 :286-288의 논리 그대로). Redis 정리는
try-catch로 로그만 남긴다. refresh는 TTL로, 액세스 토큰은 만료로 자연 소멸이 안전망.

`RefreshTokenService`·`TokenProvider` 주입은 user→auth 의존이지만 둘 다 Owner B 내부 — 도메인 간
계약 인터페이스(A↔B) 규칙과 무관.

### S3 정리 (유일한 실질 신규 로직)

`VideoServiceImpl.deleteQuietly`(:294-313)는 private varargs·청크 없음(영상 1건 = 최대 4키라
불필요했음). **재사용하지 않고 UserServiceImpl에 자체 구현한다** — List 입력 + 1000키 청크 +
null 필터 + `response.hasErrors()` 검사 + SdkException 삼킴(로그)은 동일 구조로. 공용 support
추출은 video 도메인 파일 이동이 생겨 diff가 커지므로 하지 않는다 — 세 번째 사용처가 생기면
그때 추출 (§D-재사용).

```java
// UserServiceImpl — 1000키 청크 (DeleteObjects 요청당 상한)
for (int i = 0; i < keys.size(); i += 1000) {
	deleteBatch(keys.subList(i, Math.min(i + 1000, keys.size())));
}
```

### 삭제-동시 업로드 경합 (§D2 — 잠금 미채택)

수집 SELECT와 DELETE 사이에 신규 업로드가 커밋되면 그 영상 행은 CASCADE로 지워지되 S3 키는
수집에서 빠져 고아 객체가 된다. **advisory lock을 채택하지 않고 수용한다**:

- 발생 조건이 "본인이 삭제를 누르는 동시에 본인이 업로드" — 미출시 서비스에서 극단적으로 드묾.
- 결과가 비식별 고아 객체 — FR-3 best-effort가 이미 수용한 실패 모드와 동급 (키는 uuid·videoId
  기반, 접근 경로인 DB 소멸 — PRD 비기능 "개인정보" 그대로).
- DELETE 이후 커밋되는 업로드는 FK 위반으로 실패 — 데이터 오염 없음.

필요해지면 선례 그대로 확장: `pg_advisory_xact_lock(hashtextextended('user_delete:' || :userId, 0))`
(RegionRepository.acquireUserRegionStatsLock:90 패턴).

### 삭제-동시 reissue 경합 (§D5 — Codex 스펙 리뷰 판정, 2026-08-01)

Codex가 "삭제와 동시 진행된 reissue가 deleteAll 이후 새 세션을 저장해 삭제된 계정의 자격증명이
살아남는다(FR-4 위반)"를 제기했으나, **요구된 durable deleted-user check는 이미 존재한다** —
`RefreshTokenService.reissue`(:63-64)가 로테이션 전에 `userRepository.findById`로 users 행을
조회하고 부재 시 `INVALID_REFRESH_TOKEN`으로 거부한다. 따라서:

- 삭제 **커밋 이후** 도착하는 reissue는 전부 자연 실패 — 세션이 계속 갱신되는 시나리오 불성립.
- 잔여 창 = "findById 통과 → 삭제 커밋 + deleteAll 스캔 → reissue의 Redis 저장" 순서로 겹치는
  찰나(한 요청 내 ms). 이 창에서 새어난 것의 정확한 노출 (Codex 2R 정정 반영 — 초판의 "잔여
  수명" 표현은 오기): **reissue가 갓 발급한 액세스 토큰이 전체 TTL 동안 유효**하다(JWT 인증
  필터는 사용자 재조회를 하지 않음). 그 토큰으로 가능한 것 (Codex 3R 정정 — 초판 "읽기 한정"은
  거짓): ① 인증된 읽기 전반 ② `POST /api/videos/presigned-url` — user 조회 없이 S3 PUT URL
  발급(VideoServiceImpl:353) → pending 프리픽스 업로드 남용 가능 (확정 INSERT는 user FK로 실패,
  pending 객체는 라이프사이클 1일 만료로 자연 소멸 — MSG-247 D5) ③ 재생 조회의 타인 영상
  `view_count` 증분(:486) — 타인 데이터 통계 오염. 영속 데이터 소유(영상 확정·점령)는 불가.
  새어난 refresh 키는 다음 사용의 findById에서 즉시 거부돼 체인 1회로 소진.
- 판정: **3라운드 상한 도달 — 사용자 결정 대기 (2026-08-01)**. 봉합안 = 톰스톤:
  deleteAccount afterCommit에서 `deleted:{userId}`(TTL=refresh 2주) SET 후 deleteAll → reissue는
  로테이션 저장 **후** 톰스톤 재확인, 있으면 방금 저장한 키 삭제 + 거부(토큰 미반환). 순서상
  톰스톤 SET < deleteAll 스캔이므로 스캔을 비껴간 저장도 재확인에 반드시 걸린다 — 완전 봉합.
  비용 = reissue당 Redis GET 1회(이미 DB findById를 하는 경로라 증분 미미) + auth 코드 ~15줄 + 테스트 2건.

## 데이터 모델

엔티티 변경 없음. **마이그레이션 1건: `V15__reports_fk_on_delete.sql`** (V14 다음 — 확인 완료).

reports만 user FK 9테이블과 달리 ON DELETE 정책이 없다 (V1:228 reporter_id NOT NULL 인라인
REFERENCES, :230 reviewed_by). FR-6: 그가 한 신고는 함께 삭제(CASCADE), 검토자 기록은 비움(SET NULL).

```sql
-- V15__reports_fk_on_delete.sql
-- 계정 삭제(MSG-205) 선행: reports 만 user FK 에 ON DELETE 정책이 없어 users 행 삭제가 FK 위반으로 막힌다.
-- 그가 한 신고(reporter_id)는 함께 삭제, 그가 검토자(reviewed_by)로 기록된 신고는 검토자만 비운다.
-- 기존 데이터 무변경 — 제약 교체뿐이라 롤백 부담 없음.
ALTER TABLE reports
	DROP CONSTRAINT reports_reporter_id_fkey,
	ADD CONSTRAINT reports_reporter_id_fkey
		FOREIGN KEY (reporter_id) REFERENCES users (id) ON DELETE CASCADE;

ALTER TABLE reports
	DROP CONSTRAINT reports_reviewed_by_fkey,
	ADD CONSTRAINT reports_reviewed_by_fkey
		FOREIGN KEY (reviewed_by) REFERENCES users (id) ON DELETE SET NULL;
```

- 제약 실명 **실측 확인 완료** (2026-08-01, 로컬 DB `pg_constraint` 조회):
  `reports_reporter_id_fkey` (FK reporter_id → users, ON DELETE 없음) · `reports_reviewed_by_fkey`
  (FK reviewed_by → users, ON DELETE 없음) — 위 V15의 DROP 대상 이름 그대로. 마이그레이션 전 절차 없음.
- reports 외 user FK 9테이블(videos V1:85 · user_grids:117 · region_stats:131 · push_tokens:146 ·
  friendships:159-160 · streaks:176 · user_badges:204 · likes:215 · user_missions V6:59)은 전부
  ON DELETE CASCADE 기존재 — 스키마 변경 불요.

### 리포지토리 쿼리 (§D1 — UserRepository에 둔다)

용도가 소속을 정한다 (UserBadgeRepository.java:17-19 주석 관례 — 남의 테이블을 읽어도 용도
도메인에 모은다). 두 쿼리 모두 "계정 삭제"용이므로 **UserRepository**:

```java
/** 계정 삭제용 S3 키 수집 — videos 를 읽지만 용도가 user 소속 (UserBadgeRepository 관례). 4컬럼 모두 실제 S3 key. */
@Query(value = """
	SELECT original_s3_key, encoded_url, thumbnail_url, blurred_s3_key
	FROM videos
	WHERE user_id = :userId
	""", nativeQuery = true)
List<Object[]> findAllS3KeysByUserId(@Param("userId") Long userId);

/** 삭제 행 수 반환 — 0 이면 이미 없는 유저(1404). deleteById 는 부재 시 조용히 무시라 판별 불가. */
@Modifying
@Query("DELETE FROM User u WHERE u.id = :userId")
int deleteUser(@Param("userId") Long userId);
```

키 평탄화(4컬럼 → null 제거 List<String>)는 서비스에서 Stream으로 — SQL unnest보다 지루하고 읽기 쉽다.

## 테스트 시나리오

통합 테스트는 공유 로컬 DB — 시드를 남기지 않는다 (테스트 데이터 정리 필수, NonUniqueResult 재발 방지).

**FR 매핑 (한국어 메서드명 후보)**:

- FR-1: `본인_계정_삭제는_성공하고_users_행이_사라진다`
- FR-2: `삭제_시_영상_도감_수집률_푸시토큰_친구_스트릭_뱃지_좋아요_미션이_전부_연쇄_삭제된다`
  (연쇄 9테이블 각 0행 단언)
- FR-3: `삭제_시_그_유저_영상의_원본_인코딩본_썸네일_블러본_키가_S3_삭제_요청에_담긴다`
  (S3Client mock — 요청 키 캡처. null 키 제외 확인) ·
