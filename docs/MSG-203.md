# MSG-203: 프로필 조회 · 닉네임 수정 API

**Owner**: B (`com.msg.fillmap.user.*` 단독 — infrastructure.md 패키지 오너십 기준)

> 요구사항 정본: `docs/prd/MSG-203-prd.md` (상태: 검토됨). 이 스펙은 PRD FR-1~6·비기능에 "어떻게"만 붙인다.

## 개요

소셜 로그인이 자동 저장한 내 계정 정보(이메일·닉네임)를 조회하고, 닉네임을 변경하는 API 2개를
`user` 도메인에 추가한다. FE 프로필 화면(MSG-124)의 mock 데이터를 실 API로 대체하는 백엔드 축이다.

## 배경 · 목표

- 카카오 로그인 시 이메일·닉네임이 id_token 클레임에서 자동 저장되지만, 사용자가 확인·수정할 방법이 없다 (PRD §1).
- 목표: 로그인 사용자가 자기 이메일·닉네임을 조회하고, 닉네임을 변경하며, 변경이 즉시 조회에 반영된다.
- **스코프 제외 (PRD §2 확정)**: 도감 색상(grid_color) 수정 — 기획에 없음 (2026-08-03 사용자 확정),
  프로필 이미지·이메일 변경·계정 삭제(MSG-205 완료)·조회 추가 필드.

## 성공 기준

- `GET /api/users/me`가 로그인 사용자의 `{email, nickname}`을 반환한다 (FR-1)
- 닉네임 변경 후 재조회에 변경 값이 반영된다 (FR-2·5)
- 검증 실패(빈 값·2자 미만·20자 초과)는 400 + 필드별 메시지 (FR-3)
- 미인증 요청은 401, 경로에 대상 식별자 없음 — 항상 본인만 (FR-4)
- 닉네임 중복 허용 — 중복 검사 없음, 현행 유지 (FR-6)
- 아래 "테스트 시나리오"가 이 기준의 검증 수단이다

## D-결정

### D1. 수정 엔드포인트 = `PUT /api/users/me/nickname` (PRD 미해결 질문 §8 확정)

`PATCH /api/users/me`(위키 초안 `../LLM-WIKI/03-specs/User 프로필 API 예정.md`)가 아니라
단일 필드 명시형으로 확정한다. 근거:

1. **위키 초안의 전제가 소멸했다.** PATCH 부분 수정은 당시 범위(nickname·gridColor·profileImageUrl)
   전제의 설계다. gridColor는 이번에 기획 제외로 확정됐고, profileImageUrl은 도입되더라도 영상처럼
   presigned 업로드 플로우(별도 엔드포인트)가 현실적이라 PATCH `/me`의 확장 여지는 사변적이다 (YAGNI).
2. **필드가 하나면 PATCH 의미론이 형해화된다.** 부분 수정은 "필드 부재 = 미변경"인데, `nickname`
   하나에 `@NotBlank`를 걸면 부재 = 400인 필수 필드 업데이트로 퇴화한다. 나중에 필드를 추가하면
   nickname 필수→선택 검증 변경이 같은 엔드포인트의 동작 변경이 된다.
3. **PUT 의미와 정확히 일치.** nickname 하위 리소스의 전체 교체 — 멱등, 부재 의미론 정의 불요.
4. **레포 선례.** 단일 필드 변경을 하위 경로로 분리한 선례가 이미 있다
   (`PATCH /api/videos/{videoId}/visibility`, MSG-162 — 동사만 상태 전환이라 PATCH였고, 값 교체인 이번은 PUT).

### D2. 수정 응답 = 변경 후 프로필 (`UserProfileResponseDto` 재사용)

`VideoVisibilityResponseDto` 선례(MSG-162 — "FE가 토글 UI를 확정 상태로 갱신하도록 전환 후 상태를
돌려준다")를 따른다. FE가 재조회 없이 확정 상태로 UI를 갱신하고, 조회·수정이 DTO 하나를 공유해
응답 형태가 어긋날 수 없다.

## API 명세

### 1. 내 프로필 조회 — `GET /api/users/me`

- 인증 필수 (Bearer). 사용자 식별은 `@AuthenticationPrincipal AuthPrincipal principal` →
  `principal.userId()` — MSG-205 `DELETE /me` 관례 그대로.
- 요청 파라미터 없음.

**응답** `SuccessResponse<UserProfileResponseDto>`:

```json
{ "developCode": 200, "message": "성공", "body": { "email": "user@example.com", "nickname": "채우미" } }
```

### 2. 닉네임 수정 — `PUT /api/users/me/nickname`

**요청** `NicknameUpdateRequestDto` (record):

```json
{ "nickname": "새닉네임" }
```

- 검증은 가입(`SignupRequestDto`)과 동일 — 메시지까지 일치시켜 두 경로의 허용 범위가 어긋나지 않게 (PRD 비기능):

```java
@NotBlank(message = "닉네임은 필수 항목입니다")
@Size(min = 2, max = 20, message = "닉네임은 2자 이상 20자 이하이어야 합니다")
String nickname
```

**응답** `SuccessResponse<UserProfileResponseDto>` — 변경 후 프로필 (D2).

### 에러 케이스 (두 엔드포인트 공통 규칙)

| 케이스 | developCode | HTTP | 처리 |
|---|---|---|---|
| 미인증 (토큰 없음/무효) | 공통 `UNAUTHORIZED` | 401 | 시큐리티 필터 — 컨트롤러 도달 전 |
| 검증 실패 (수정만) | 공통 `BAD_REQUEST` | 400 | `@Valid` → `GlobalExceptionHandler`가 필드별 메시지 조합 |
| principal userId의 사용자 부재 | `USER_NOT_FOUND` 1404 | 404 | `ApiException(UserErrorCode.USER_NOT_FOUND)` — 기존 상수 재사용, 신규 에러코드 불요 |

닉네임 중복은 에러가 아니다 (FR-6) — 중복 검사 로직을 넣지 않는다.

### DTO — `com.msg.fillmap.user.dto` (디렉터리 신설)

`UserProfileResponseDto` (record) — MSG-308 스키마 패턴 준수: 클래스 레벨
`@Schema(description = ..., requiredProperties = {"email", "nickname"})` (email·nickname 둘 다 users
NOT NULL 컬럼이라 항상 non-null). 정적 팩토리 `from(User)` (`VideoVisibilityResponseDto` 선례).

## 도메인 로직

용어: 이 티켓은 격자·점령·방문에 닿지 않는다 — glossary 대조 결과 "도감 색상(grid_color)"만 접점이며
**스코프 제외**로 확정 (glossary "프로필에서 변경 가능" 문구 정리는 PRD §2 명시대로 후속, 이 티켓 밖).

- **조회**: `userRepository.findById(userId)` → 없으면 `USER_NOT_FOUND` → `UserProfileResponseDto.from(user)`.
  소셜 로그인이 저장한 값 가공 없이 노출 (PRD 비기능). `@Transactional(readOnly = true)`.
- **수정**: 같은 조회 후 `user.updateNickname(nickname)` — **User 엔티티에 도메인 메서드 신설**
  (`@Setter` 없는 현행 유지, 더티 체킹으로 UPDATE). `@Transactional` 안에서 변경 후
  `UserProfileResponseDto.from(user)` 반환. trim·정규화 없음 — 가입 경로와 동일하게 원문 저장.

```java
// UserService 인터페이스 추가 메서드 (기존 deleteAccount 유지)
UserProfileResponseDto getMyProfile(Long userId);
UserProfileResponseDto updateNickname(Long userId, String nickname);
```

구현은 기존 `UserServiceImpl`에 추가. 컨트롤러는 기존 `UserController`(`/api/users`)에 매핑 2개 추가 —
`SuccessResponse.of(...)` 반환만, 예외는 `ApiException` 던지기만 (response-pattern 준수).
Swagger: 기존 `@Tag` 아래 `@Operation` summary/description, principal은 `@Parameter(hidden = true)`.

## 데이터 모델

- **마이그레이션 불요** — 기존 `users.email`(NOT NULL, UNIQUE)·`users.nickname`(NOT NULL, length 50)만 사용.
- 위키의 "닉네임 길이 20 vs 50 불일치" 쟁점: 검증 상한 20 < 컬럼 50이라 충돌 없음. 검증을 가입과 같은
  20으로 정렬하는 것으로 해소 — 컬럼 축소 마이그레이션은 하지 않는다 (불필요한 변경).
- 닉네임 UNIQUE 제약 추가하지 않음 (FR-6 — 카카오 자동 닉네임이 이미 중복 가능, 유니크 강제는 소셜 가입 실패 유발).
