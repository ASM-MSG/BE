**Owner 판정 근거**: 변경 파일 전부가 Owner B 패키지다 — `com.msg.fillmap.friend.*`(CLAUDE.md

## 개요

친구 관계 수명주기(MSG-185)의 다음 단계 — **수락된 친구를 실제로 보는** 조회 2종을 추가한다:

1. **친구 목록** `GET /api/friends` — ACCEPTED 관계 전체, 방향 무관, 정렬 2종(수락 시각↓ 기본 ·
   닉네임순 전환).
2. **친구 프로필** `GET /api/friends/{userId}/profile` — 프로필(닉네임·프로필 이미지·도감 색상) +
   도감 요약(수집 격자 수·영상 총합·방문 동 수) + 최근 수집 격자(썸네일은 재생 허용 공개범위
   영상 것만). 단일 응답 — PRD §5 시퀀스대로 화면 1개 = 호출 1개.

쓰기 없음 — 마이그레이션·엔티티 변경 없음, 조회 쿼리와 DTO만 신규다.

## 배경 · 목표

- MSG-185로 관계 저장은 완성됐지만 **수락된 친구가 누구인지 보는 목록이 없다**(받은 요청
  목록만 존재). IA "설정 > 친구 관리"와 친구 프로필 화면의 데이터 소스가 비어 있다.
- 프라이버시는 2026-08-03 확정: **친구면 도감 요약 전부 공개, 공개 범위 설정 없음**(Phase 2+
  유예). 단 썸네일은 영상 재생 권한과 정합해야 하므로 재생 허용 공개범위 영상 것만 붙는다.
- 스코프 제외(PRD 비목표): 친구 도감 지도 시각화(MSG-187), 공개 범위 설정, 차단·코드 재발급,
  비친구 공개 프로필, 친구 수 상한.

## 성공 기준

- `GET /api/friends`가 방향 무관(내가 requester든 addressee든) ACCEPTED 전체를 반환하고,
  기본 수락 시각 내림차순 · `sort=nickname`으로 닉네임순 전환된다 (FR-1·2).
- 친구 0명이면 200 + 빈 배열 (FR-4).
- `GET /api/friends/{userId}/profile`의 도감 요약 3지표가 **그 사용자가 본인 도감 요약
  (`GET /api/collections/summary`)에서 보는 값과 동일**하다 — 같은 산식 재사용 (비기능 정합).
- 비친구·본인·대기중(PENDING) 상대·미존재 userId 조회가 **전부 동일하게 9424**로 실패한다 —
  관계·계정 존재 은닉 (FR-7).
- 친구 삭제 즉시 프로필 조회가 9424다 — 요청 시점 실시간 판정 (FR-8).
- 비공개(재생 불허) 영상만 있는 격자는 썸네일 null로 격자 사실만 내려간다 (FR-6).
- 전체 테스트 green (`./gradlew test`).

## 확정 설계 (D1~D6)

### D1. API 2종, 프로필은 단일 응답

- 목록과 프로필을 분리하되, 프로필은 프로필+요약+최근 수집 격자를 **한 응답**에 담는다 —
  PRD §5 시퀀스(한 호출이 요약·격자 목록까지 받음) 그대로. 별도 격자 목록 API를 쪼개지 않는다
  (화면 1개가 소비, 쪼개면 왕복만 는다).
- 경로는 기존 `FriendController` 매핑과 충돌 없음 실측: `GET /api/friends`(신규, 베이스 GET 없음),
  `GET /{userId}/profile`(2세그먼트 — `/requests/received`와 두 번째 세그먼트가 달라 미충돌).
- 인증: `SecurityConfig anyRequest().authenticated()`가 `/api/friends/**`를 이미 커버(MSG-185 D4)
  — 설정 변경 불요.

### D2. 목록 쿼리 — 양방향 OR 조인 생성자 프로젝션, 정렬 키 = `responded_at`

- "양방향 UNION"은 SQL UNION이 아니라 **OR 2분기 세타 조인 1방**으로 구현한다
  (`findReceivedRequests` JPQL 생성자 프로젝션 미러):

```java
@Query("""
	SELECT new com.msg.fillmap.friend.dto.FriendListItemResponseDto(
		u.id, u.nickname, u.profileImageUrl, u.gridColor)
	FROM Friendship f, User u
	WHERE f.status = com.msg.fillmap.friend.entity.FriendshipStatus.ACCEPTED
		AND ((f.id.requesterId = :userId AND u.id = f.id.addresseeId)
			OR (f.id.addresseeId = :userId AND u.id = f.id.requesterId))
	ORDER BY f.respondedAt DESC NULLS LAST, u.id ASC
	""")
List<FriendListItemResponseDto> findFriendsOrderByAcceptedAt(@Param("userId") Long userId);
```

- **정렬 키 실측**: `Friendship.respondedAt`(`responded_at`) 존재, `accept()`가 일반 수락·자동
  수락 양쪽에서 기록한다(MSG-185 D3 — 거절은 행 DELETE라 ACCEPTED 행은 사실상 전건 non-null).
  컬럼 자체는 nullable이라 `NULLS LAST` + `u.id` 타이브레이크로 방어한다.
- 닉네임순은 **같은 쿼리에 ORDER BY만 다른 메서드 1개 추가**(`findFriendsOrderByNickname` —
  `ORDER BY u.nickname ASC, u.id ASC`, 닉네임 중복 허용이라(MSG-203) 타이브레이크 필수).
  세타 조인 프로젝션엔 Spring Data `Sort` 동적 적용이 안 맞아 정적 2본이 가장 단순하다.
- 인덱스: requester 방향은 PK(requester_id, addressee_id), addressee 방향은 V1
  `idx_friendships_addressee(addressee_id, status)`가 커버. 수십 명 규모라 정렬은 메모리 소트로
  충분 — 페이지네이션 미도입(PRD 비기능).

### D3. `sort` 파라미터 — `recent`(기본) · `nickname`, 그 외 9420

- `@RequestParam(required = false) String sort` → 서비스에서 파싱(`VideoServiceImpl.parseVisibility`
  3420 선례): null 또는 `recent`(대소문자 무시) → 수락 시각 내림차순, `nickname` → 닉네임순,
  그 외 → **9420 `INVALID_FRIEND_SORT`** (BAD_REQUEST, 신설). enum 클래스는 만들지 않는다 —
  값 2개에 분기 2개면 충분.

### D4. 관계 존재 은닉 — 실패 전건 9424 재사용, 무잠금 존재 확인 신설

- 프로필 조회 실패는 **전부 기존 9424 `FRIENDSHIP_NOT_FOUND`("친구 관계가 없습니다")** 하나로
  응답한다 — 비친구·PENDING 상대·미존재 userId·본인 ID 모두 동일해 관계·계정 존재가 새지
  않는다 (FR-7). 신규 에러 코드 불요.
  - 본인 ID는 별도 분기가 필요 없다 — `(me, me)` 쌍 행은 존재할 수 없어(자기 요청 9400 차단,
    MSG-185) 존재 확인이 자연히 false → 9424.
- **`findPair` 재사용 금지 (실측 근거)**: `findPair`는 `@Lock(PESSIMISTIC_WRITE)`(PG
  `FOR NO KEY UPDATE`)가 걸린 쓰기 경로 전용이다. 프로필 조회는 `@Transactional(readOnly = true)`
  이고 PostgreSQL은 read-only 트랜잭션에서 `FOR UPDATE` 계열을 거부한다(런타임 에러). 조회
  전용 **무잠금 존재 확인을 신설**한다:

```java
@Query("""
	SELECT COUNT(f) > 0 FROM Friendship f
	WHERE f.status = com.msg.fillmap.friend.entity.FriendshipStatus.ACCEPTED
		AND ((f.id.requesterId = :a AND f.id.addresseeId = :b)
			OR (f.id.requesterId = :b AND f.id.addresseeId = :a))
	""")
boolean existsAcceptedPair(@Param("a") Long a, @Param("b") Long b);
```

- **병렬 머지 주의 (MSG-285)**: 병렬 진행 중인 MSG-285(FRIENDS 공개범위)도 재생 판정용으로
  **동일 시그니처·동일 쿼리 텍스트**의 `existsAcceptedPair`를 `FriendshipRepository`에 추가한다
  (두 스펙 간 합의 완료 — 2026-08-03). 늦게 머지되는 브랜치가 리베이스에서 중복 선언 하나만
  제거하면 된다.
- 판정은 **요청 시점 실시간** — 캐시 없음. 친구 삭제(행 DELETE) 즉시 9424로 수렴한다 (FR-8).
- 관계 확인 후 `userRepository.findById(target)` — 관계 행이 있으면 FK `ON DELETE CASCADE`로
  계정도 반드시 존재하는 불가능 경로지만, 방어적 `orElseThrow`도 은닉 일관을 위해 9424.

### D5. 도감 요약·최근 수집 격자 — `UserGridQueryService` 소비 (B-내부)

- **요약은 `getCollectionSummary(targetUserId)` 그대로 재사용** — 시그니처가 이미 userId
  파라미터라 수정 0줄. "본인이 볼 때와 친구가 볼 때 숫자 동일"(PRD 비기능)이 같은 산식
  재사용으로 자동 성립한다. 산식(실측): 수집 격자 수 = `user_grids COUNT`, 영상 총합 =
  `SUM(video_count)`, 방문 동 수 = 격자 라벨 DISTINCT(DELETED 제외) — MSG-152/246.
- **최근 수집 격자는 `getCollectionGrids` 재사용 금지** (PRD 비기능 명시) — 본인용은
  visibility 무필터라 PRIVATE cover 썸네일이 친구에게 샌다. **신규 메서드
  `getCollectionGridsForFriend(long ownerUserId)`를 `UserGridQueryService`에 추가**한다
  (`getRegionVideos` MSG-167 "B-내부 read" 선례 — §계약 변경 참조).
  - 이름이 확장 지점이다: "친구에게 보여줄 격자 목록" 의미라, MSG-285가 FRIENDS 공개범위를
    추가해도 시그니처 무변경 — 내부 필터만 넓어진다 (D6).
- 정렬·개수는 본인 갤러리와 동일: `first_collected_at DESC, grid_id DESC` 최대 30개 (FR-6
  "본인 도감 갤러리와 동일 형상", MSG-153 D3).

### D6. 친구용 썸네일 — 재생 허용 영상만, cover 우선 폴백 LATERAL

- **재생 허용 공개범위 = 현재 `visibility = 'PUBLIC'` 하나** (실측: `Visibility` enum
  PUBLIC·PRIVATE 2종). **MSG-285(병렬 진행 중)가 FRIENDS를 추가하면 이 필터 한 곳만
  `IN ('PUBLIC', 'FRIENDS')`로 넓히면 된다** — 쿼리 주석에 확장 지점을 명시한다.
- 선정 규칙: 그 격자의 소유자 영상 중 `status = 'ACTIVE' AND visibility = 'PUBLIC' AND
  processing_status = 'READY' AND thumbnail_url IS NOT NULL`인 것에서 **cover 우선, 아니면
  최신순** 1건. PRD FR-6 문언("재생 허용 공개범위 영상 것만 붙이고, **해당 영상이 없으면**
  null")에 충실한 해석이다 — cover가 PRIVATE여도 다른 PUBLIC 영상이 있으면 그 썸네일로
  폴백하고, 하나도 없으면 null + 격자 사실만 내려간다.

```sql
SELECT
	ug.grid_id            AS "gridId",
	ug.first_collected_at AS "firstCollectedAt",
	ug.last_uploaded_at   AS "lastUploadedAt",
	ug.video_count        AS "videoCount",
	t.thumbnail_url       AS "thumbnailKey",
	r.region_name         AS "regionName"
FROM user_grids ug
LEFT JOIN LATERAL (
	-- 친구에게 보여줄 썸네일 1건: 재생 허용 영상만(현재 PUBLIC — MSG-285 이후 IN ('PUBLIC','FRIENDS')로
	-- 이 조건 한 곳만 확장), cover 우선(소유자 선택 존중) → 최신순 폴백. 없으면 NULL(격자 사실만).
	SELECT v.thumbnail_url
	FROM videos v
	WHERE v.grid_id = ug.grid_id AND v.user_id = ug.user_id
		AND v.status = 'ACTIVE' AND v.visibility = 'PUBLIC'
		AND v.processing_status = 'READY' AND v.thumbnail_url IS NOT NULL
	ORDER BY (v.id = ug.cover_video_id) DESC, v.created_at DESC, v.id DESC
	LIMIT 1
) t ON TRUE
LEFT JOIN grids g ON g.grid_id = ug.grid_id
LEFT JOIN regions r ON r.region_code = g.region_code
WHERE ug.user_id = :userId
ORDER BY ug.first_collected_at DESC, ug.grid_id DESC
LIMIT 30
```

- **"동일 형상"의 의도적 델타 1건 — 영상 ID 미노출**: 본인 갤러리 항목의 `coverVideoId`는
  친구 응답에 넣지 않는다. cover가 PRIVATE면 그 id 노출 자체가 비공개 영상 존재 누설이고,
  폴백 선정 영상은 cover가 아니라 이름도 거짓이 된다. 친구 화면은 표시 전용이며 재생 진입은
  MSG-187/285 몫 — 필요해지는 시점에 그 티켓이 추가한다. `videoCount`는 요약의
  `totalVideoCount`와 동일 축(비공개 포함 전체)이라 그대로 노출한다 — 개수는 이미 요약이
  공개하는 정보다.
- presign은 기존 `ThumbnailUrlPresigner.presign(key)` 재사용 — null key는 null 통과, 로컬 서명
  연산이라 30건 개별 발급해도 S3 호출 0 (MSG-153 D4).

## API 명세

베이스: 기존 `FriendController`(`/api/friends`)에 GET 2개 추가. principal은
`@AuthenticationPrincipal AuthPrincipal` → `principal.userId()` (기존 관례).
성공은 `SuccessResponse.of(...)`, 에러는 `ApiException(FriendErrorCode)` →
`GlobalExceptionHandler` 변환.

### 1. 친구 목록 — FR-1~4

```text
GET /api/friends?sort={recent|nickname}    (sort 생략 = recent)
→ 200 data: [
    { "userId": 7, "nickname": "채우미", "profileImageUrl": "https://…", "gridColor": "PINK" },
    …
  ]
친구 없음 → 200 data: []
에러: sort 가 recent·nickname 외 값 → 9420 INVALID_FRIEND_SORT (400)
```

- `FriendListItemResponseDto(Long userId, String nickname, String profileImageUrl,
  GridColor gridColor)` — JPQL 생성자 프로젝션 타깃 겸 응답 DTO(`ReceivedFriendRequestResponseDto`
  선례). `profileImageUrl`은 nullable(`@Schema(nullable = true)`), `gridColor`는 enum 그대로
  (Jackson이 `"PINK"` 문자열 직렬화 — 첫 gridColor 노출 API).
  `@Schema(requiredProperties = {"userId", "nickname", "gridColor"})` (MSG-308 관례).
- `userId`는 프로필 조회·친구 삭제 경로 변수로 그대로 쓰는 키다.
- 항목 필드는 FR-3의 4개만 — 수락 시각 등 추가 필드는 FR에 없어 미노출 (필요 시 후속).

### 2. 친구 프로필 + 도감 요약 — FR-5~8

```text
GET /api/friends/{userId}/profile
→ 200 data: {
    "nickname": "채우미",
    "profileImageUrl": "https://…",          (없으면 null)
    "gridColor": "PINK",
    "summary": { "totalGridCount": 15, "totalVideoCount": 42, "visitedRegionCount": 6 },
    "recentGrids": [
      {
        "gridId": "41642_110458", "gridY": 41642, "gridX": 110458,
        "firstCollectedAt": "2026-07-20T18:03:11", "lastUploadedAt": "2026-07-21T09:12:00",
        "videoCount": 3,
        "thumbnailUrl": "https://…presigned…",   (재생 허용 영상 없으면 null)
        "regionName": "서울특별시 강남구 역삼1동" (무귀속이면 null)
      }, …
    ]
  }
에러: 비친구·본인·PENDING 상대·미존재 userId → 9424 FRIENDSHIP_NOT_FOUND (404, 은닉 단일 응답)
```

- `FriendProfileResponseDto(String nickname, String profileImageUrl, GridColor gridColor,
  CollectionSummaryResponseDto summary, List<FriendCollectionGridResponseDto> recentGrids)`
  — `summary`는 기존 `CollectionSummaryResponseDto` **중첩 재사용**(같은 Owner B, 형상·산식
  동일 보장이 목적이라 복제 금지). `@Schema(requiredProperties = {"nickname", "gridColor",
  "summary", "recentGrids"})`.
- `FriendCollectionGridResponseDto(String gridId, Integer gridY, Integer gridX,
  LocalDateTime firstCollectedAt, LocalDateTime lastUploadedAt, Integer videoCount,
  String thumbnailUrl, String regionName)` — 본인 갤러리 항목에서 cover 2필드를 뺀 형상
  (D6 델타). `requiredProperties`는 thumbnailUrl·regionName 제외 6개.

## 도메인 로직

glossary 용어 기준 — 응답·문구는 "수집"(행위)·"도감"(집합), "점령"은 코드/내부 논의만.

- **친구 목록(FR-1)**: ACCEPTED 행 1개 = 양방향 관계(MSG-185)이므로, 내 목록은 "내가 requester인
  행의 addressee + 내가 addressee인 행의 requester" 합집합 — D2 쿼리의 OR 2분기가 그 자체다.
  PENDING 행은 목록에 나오지 않는다(받은 요청 목록이 따로 있다).
- **프로필 열람 권한(FR-7)**: ACCEPTED 관계 존재가 유일한 조건 — 확정된 프라이버시 정책
  "친구면 전부 공개, 설정 없음"이라 권한 분기가 이것 하나뿐이다. 실패는 9424 단일 응답으로
  관계·계정 존재를 은닉한다 (D4).
- **실시간 판정(FR-8)**: 존재 확인 → 프로필 → 요약 → 격자 목록이 한 readOnly 트랜잭션 안 —
  삭제 직후 요청은 첫 단계에서 9424로 끝난다.
- **썸네일 정합(FR-6)**: "친구가 볼 수 있는 썸네일 = 친구가 재생할 수 있는 영상의 썸네일"
  불변식. 재생 허용 집합의 정의는 D6 쿼리 필터 한 곳 — MSG-285의 FRIENDS 확장 지점.
- **트랜잭션**: 신규 2 API 모두 조회 전용. `FriendServiceImpl` 기존 관례대로
  `@Transactional(readOnly = true)`. `UserGridQueryServiceImpl`은 클래스 레벨 readOnly 기존
  그대로.
- **소비 방향**: friend → usergrid **B-내부 read 소비** (`FriendServiceImpl`에
  `UserGridQueryService` 주입). usergrid → friend 역방향 참조 금지 — 관계 판정은 friend가
  끝내고 usergrid는 userId만 받는다(공개범위 판정에 "누가 보는지"가 아직 불필요한 구조 유지.
  MSG-285가 FRIENDS를 추가할 때도 "친구임"은 이 호출 경로가 이미 보장한다).
