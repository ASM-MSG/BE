01 / 3분 요약

“JPA를 안 쓴다”부터 바로잡기

우리 백엔드는 Spring Data JPA를 쓰면서 일부 쿼리를 Native SQL로 직접 작성합니다.

단순 조회·상태 변경에는 JPA의 기능이 남아 있습니다. 공간 연산과 동시성 제어에는 PostgreSQL 기능을 쓰고, 인코딩 작업 저장소는 JdbcClient로 별도 구현했습니다.

30 + 1JpaRepository 30개 + JdbcClient 저장소 1개
108 / 161직접 선언한 @Query 중 Native, 약 67%
53Native가 아닌 @Query 선언

집계 범위: src/main/java의 *Repository.java 31개, 주석 제거 후 선언 수. 상속받은 CRUD·파생 메서드·JdbcClient SQL은 161개에 포함하지 않았습니다. 호출 빈도나 실제 DB 부하 비율도 아닙니다.

오늘 첫 설명은 이 정도면 됩니다

“도메인별 패키지 안에 Controller, Service, Repository를 둔 구조입니다. JPA는 유지하고 있지만 기존 코드는 연관 객체 대신 ID를 저장한 부분이 많아서 직접 조인한 Native SQL이 많습니다. 8월 19일부터는 새 조회에 연관관계와 JPQL을 우선하기로 바꿨고, 행사 도메인에 그 방식이 들어가 있습니다. 오늘은 기존 쿼리에서 DB 기능 때문에 남길 부분과 유지보수를 위해 바꿀 부분을 구분하고 싶습니다.”

기록 시점결정오늘 설명할 때 주의
8월 3일 · 위키 ADRJPA 유지, MyBatis 전면 전환 반려당시 약 50개라는 Native 수치와 당시 평가를 지금 코드 전체에 그대로 적용하지 않습니다.
8월 19일 · 현행 컨벤션연관관계 허용, 파생 조회·JPQL 우선. Native는 DB 전용 기능·대량 배치에 한정기존 코드는 일괄 변경하지 않고 9월 7일 리뷰 뒤 개선하기로 기록되어 있습니다.
오늘 · 코드 확인기존 ID 참조와 새 연관 매핑, JPA와 JdbcClient가 공존“Native는 전부 불가피했다”도 “전부 바꾸면 된다”도 근거가 부족합니다.

03 / 개념 준비

이 7개를 알면 리뷰를 따라갈 수 있습니다

개념쉽게 설명하면우리 코드에 대입하면
JPA / Hibernate / Spring Data JPAJPA는 객체 저장 규약, Hibernate는 구현체, Spring Data JPA는 Repository 구현을 줄여주는 도구입니다.extends JpaRepository를 쓰므로 SQL 문자열이 있어도 JPA 기반입니다.
파생 쿼리 / JPQL / Native메서드 이름으로 생성 / 엔티티·필드로 작성 / 테이블·컬럼으로 SQL 작성findByEmail, FROM EventVideo ev, FROM user_grids를 구별하면 됩니다.
영속성 컨텍스트[1] / 더티 체킹관리 중인 객체의 변경을 감지해 DB에 반영합니다. 직접 UPDATE한 DB 값이 객체에도 자동 반영되는 것은 아닙니다.markBlinded() 같은 상태 변경과 Native UPDATE를 섞을 때 오래된 객체 값이 남을 수 있습니다.
flush / clear / commitflush는 변경 SQL 전송, clear는 관리 객체 분리, commit은 트랜잭션 확정입니다.saveAndFlush가 호출돼도 아직 커밋된 것은 아닙니다. clear 전 미반영 변경이 있는지도 봐야 합니다.
연관관계 / LAZY / N+1[2]객체로 관계를 따라갈 수 있지만, 반복 접근이 추가 조회를 만들 수 있습니다.기존 Video.userId와 새 EventVideo.location을 비교합니다. 필요한 조회에 fetch join·DTO를 선택합니다.
원자적 UPDATE / 잠금 / 멱등[3]겹친 쓰기를 안전하게 처리하는 것과, 같은 요청을 반복해도 중복 효과가 없는 것은 다릅니다.count = count + 1은 읽고 쓰는 경합을 줄이지만, 두 번 호출하면 두 번 증가합니다.
프로젝션[4] / 페이징필요한 열만 읽고, 정렬 기준에 따라 일부 결과를 가져옵니다.SQL 별칭·반환 타입·NULL·정렬 동률을 봅니다. JPQL도 DTO와 커서 조건을 쓸 수 있습니다.

파생 쿼리·JPQL·Native 선언과 벌크 수정 뒤 컨텍스트 처리: Spring Data JPA 공식 문서. flushAutomatically·clearAutomatically의 역할: @Modifying API.

04 / 같이 열어볼 코드

6개 사례로 정리 방향 잡기

아래 “후보”는 변경 제안입니다. 오류 판정이나 성능 개선 실측이 아닙니다.

A · 먼저 바꿔볼 후보

단순 조회까지 Native여야 할까요?

GridRepository.findVideoCount는 사용자·격자 ID로 숫자 한 개를 읽습니다. 이 SQL 자체에는 PostGIS나 PostgreSQL 전용 기능이 없습니다.

src/main/java/com/msg/fillmap/grid/repository/GridRepository.java · L24~29
	@Query(value = """
		SELECT ug.video_count
		FROM user_grids ug
		WHERE ug.user_id = :userId AND ug.grid_id = :gridId
		""", nativeQuery = true)
	Optional<Integer> findVideoCount(@Param("userId") long userId, @Param("gridId") String gridId);

알아둘 점: JPQL로 표현 가능해 보이는 조회입니다. 다만 UserGrid 엔티티와 키 매핑을 보고 실제 표현을 정해야 합니다. SQL 문법 교체와 Repository 책임 이동은 별개입니다.

질문: “이것을 첫 리팩터링 대상으로 잡아도 될까요? GridRepository가 user_grids를 조회하는 책임도 같이 정리해야 할까요?”

검증: 없는 행은 Optional.empty, 타인 격자는 제외, 반환 숫자 동일. 기존 GridRepositoryTest를 먼저 봅니다.

B · Native 유지 근거가 뚜렷함

UPSERT는 동시 요청에서 무슨 일을 하나요?

src/main/java/com/msg/fillmap/video/repository/VideoRepository.java · L362~370
	@Modifying
	@Query(value = """
		INSERT INTO user_grids (user_id, grid_id, video_count, cover_video_id, first_collected_at, last_uploaded_at)
		VALUES (:userId, :gridId, 1, :coverVideoId,
			statement_timestamp() AT TIME ZONE 'UTC', statement_timestamp() AT TIME ZONE 'UTC')
		ON CONFLICT (user_id, grid_id) DO UPDATE
			SET video_count = user_grids.video_count + 1,
			    last_uploaded_at = statement_timestamp() AT TIME ZONE 'UTC'
		""", nativeQuery = true)

ON CONFLICT는 같은 사용자·격자 키가 이미 있으면 INSERT 대신 UPDATE합니다. DB 안에서 video_count + 1을 계산하므로, 두 요청이 같은 숫자를 읽고 덮어쓰는 방식과 다릅니다. 해당 충돌 키를 보장하는 유니크 제약이 전제입니다.

반드시 구분: 이 메서드는 반복 호출할 때마다 카운트를 늘립니다. UPSERT라고 자동으로 멱등인 것은 아닙니다. 같은 업로드 중복 확정은 별도 pending 키 잠금과 기존 영상 확인 경로가 맡습니다.

질문: “이 SQL은 유지하되 VideoRepository에서 점령 쓰기 전담 저장소로 옮기는 게 나을까요? 호출 순서와 같은 트랜잭션은 어떻게 유지할까요?”

공식 근거: PostgreSQL INSERT / ON CONFLICT. 사례의 원자성은 이 SQL 문장 범위이며, 업로드 전체 경합 안전성을 뜻하지 않습니다.

C · DB 기능과 저장소 책임을 분리해서 보기

공간 판정과 잠금은 어디에 두면 좋을까요?

VideoRepository.upsertGrid는 ST_Covers로 행정동을 판정하고 ON CONFLICT DO NOTHING으로 격자를 준비합니다. acquirePendingKeyConfirmLock은 PostgreSQL advisory lock[5]을 사용합니다.

src/main/java/com/msg/fillmap/video/repository/VideoRepository.java · L402~404
	@Query(value = "SELECT pg_advisory_xact_lock(hashtextextended('video_confirm:' || :pendingKey, 0))",
		nativeQuery = true)
	Object acquirePendingKeyConfirmLock(@Param("pendingKey") String pendingKey);

알아둘 점: “Native가 필요한가?”와 “영상 저장소 안에 있어야 하나?”는 다른 질문입니다. 공간 함수는 Hibernate Spatial로 표현할 여지도 있지만, 등록 SQL·결과·유지보수 비용을 보고 판단해야 합니다.

질문: “PostGIS는 지도 쪽 전담 저장소, 잠금은 업로드 쪽 전담 컴포넌트로 모으는 게 좋을까요? 지금 규모에서는 단순 메서드 이동이면 충분할까요?”

잠금 획득 뒤 검사·저장이 같은 트랜잭션이어야 합니다. 현재 메서드 이름만 바꾸거나 호출을 밖으로 옮겨 이 범위를 끊지 않도록 확인합니다.

D · SQL 문법보다 정합성 먼저

DB를 직접 바꾼 뒤, 엔티티는 무엇을 보고 있나요?

UserRepository.submitConsents는 최초 동의 시각을 COALESCE로 보존하고 @Modifying(clearAutomatically = true)를 씁니다. User의 동의 필드는 updatable = false로 매핑되어 있습니다.

clear와 updatable=false는 해결하는 문제가 다릅니다.

clear는 현재 컨텍스트의 오래된 객체를 분리합니다. updatable=false는 이후 엔티티 UPDATE SQL에서 그 컬럼을 제외합니다. 모든 Native 메서드에 clear를 일괄 추가하는 방식은 답이 아닙니다.

또 다른 사례인 getVideoPlayback은 엔티티 조회 뒤 Native로 조회수를 올립니다. 현재 코드 주석은 응답 조회수를 증가 전 스냅샷으로 명시합니다. 오래된 값이라는 이유만으로 곧바로 버그라고 단정하면 안 됩니다.

질문: “엔티티 상태 변경과 직접 UPDATE를 같은 트랜잭션에서 섞는 기준을 어떻게 정하면 좋을까요? flush·clear·재조회가 필요한 경로를 테스트로 고정하고 싶습니다.”

검증 출발점: UserConsentIntegrationTest, UserLocationConsentIntegrationTest. 이번 작업에서는 실행하지 않았습니다.

E · 이미 레포 안에 있는 개선 사례

행사 조회는 JPQL과 연관관계를 씁니다

src/main/java/com/msg/fillmap/event/repository/EventVideoRepository.java · L27~37

EventVideoRepository는 JOIN ev.video와 생성자 프로젝션으로 필요한 값만 읽습니다. 피드 다음 페이지도 createdAt과 id 조건을 JPQL로 표현합니다. “조인·집계·커서가 있으면 무조건 Native”는 아닙니다.

질문: “기존 영상·도감 조회를 이 방식에 맞춰 조금씩 바꾸면 될까요? 연관관계를 먼저 추가할지, 기존 ID 필드로 JPQL부터 만들지 기준이 궁금합니다.”

F · 성민이 특히 질문할 사례

인코딩 큐는 이미 JdbcClient를 쓰고 있습니다

VideoEncodingJobRepository는 JpaRepository가 아닌 클래스입니다. 작업 선점은 후보 조회와 상태 변경을 하나의 SQL로 묶습니다.

src/main/java/com/msg/fillmap/video/repository/VideoEncodingJobRepository.java · L74~95
			WITH clock AS (
				SELECT statement_timestamp() AT TIME ZONE 'utc' AS now_utc
			), candidate AS (
				SELECT j.id
				FROM video_encoding_jobs j
				CROSS JOIN clock c
				WHERE (j.status = 'PENDING' AND j.available_at <= c.now_utc AND j.attempt_count < 3)
					OR (j.status = 'PROCESSING' AND j.lease_until <= c.now_utc AND j.attempt_count < 3)
				ORDER BY j.available_at, j.id
				FOR UPDATE OF j SKIP LOCKED
				LIMIT 1
			)
			UPDATE video_encoding_jobs j
			SET status = 'PROCESSING',
				attempt_count = j.attempt_count + 1,
				claim_token = :claimToken,
				claimed_by = :nodeId,
				lease_until = c.now_utc + make_interval(secs => :leaseSeconds)
			FROM candidate, clock c
			WHERE j.id = candidate.id
			RETURNING j.id, j.video_id, j.original_s3_key, j.claim_token,
				j.attempt_count, j.enqueued_at

SKIP LOCKED는 다른 트랜잭션이 잠근 후보를 건너뛰어 다음 작업을 고르게 합니다. 임대 만료 뒤 재선점은 별도 문제이고, 완료·재시도 UPDATE는 claim_token도 대조합니다. 따라서 SKIP LOCKED 하나가 “정확히 한 번 실행”을 보장하는 것은 아닙니다.

질문: “이런 작업 큐는 JdbcClient 전담 구현으로 두고, 일반 조회는 JPA로 유지하는 구분이 적절할까요? 영상 저장과 작업 등록이 같이 롤백되는 테스트, 재선점한 뒤 옛 워커의 완료를 막는 테스트가 충분한가요?”

VideoEncodingJobRepositoryTest에 중복 등록·동시 선점·임대 만료·옛 토큰 검증 사례가 있습니다. 메서드 존재를 확인했으며 이번에는 실행하지 않았습니다. PostgreSQL SELECT 잠금 절.

05 / 질문 우선순위

시간이 짧으면 이 3개부터

01

우리 코드에서 Native를 남길 기준을 실제 메서드로 나눠주실 수 있을까요?

A의 단순 조회, B의 UPSERT, C의 공간 판정, F의 작업 선점을 함께 보여드립니다. 도구 선호보다 “이 코드는 왜 이 방식을 쓰는지” 기준을 얻는 질문입니다.

02

VideoRepository가 grids와 user_grids까지 쓰는 구조를 어디까지 나누면 좋을까요?

저장소 파일만 나눌지, 도메인 서비스 계약까지 바꿀지 묻습니다. 같은 트랜잭션과 업로드 처리 순서를 유지할 방법도 함께 확인합니다.

03

리팩터링 첫 대상 하나와 통과 기준을 정해주실 수 있을까요?

예: findVideoCount 하나를 바꾸고 결과·NULL 의미·쿼리 수를 비교합니다. 이후 복잡한 조회로 넓힐지 판단할 수 있도록 작은 완료 기준을 요청합니다.

04

연관관계 도입 시 어떤 것은 객체로, 어떤 것은 ID로 남기면 좋을까요?

기존 Video와 새 EventVideo를 비교합니다. 단방향 LAZY, 읽기 전용 타 도메인 참조, 엔티티 상태 변경 책임을 어디까지 허용할지 묻습니다.

05

직접 UPDATE와 더티 체킹을 섞을 때 팀 규칙은 어느 수준이 적당할까요?

D 사례를 보여드리고 flush·clear·재조회·업데이트 제외 컬럼의 역할을 설명해 봅니다. 현재 방어를 제거하기 전에 어떤 회귀 테스트가 필요한지도 묻습니다.

06

같은 공개 범위 조건이 여러 쿼리에 반복되는데 어디서 관리하면 좋을까요?

ACTIVE·PUBLIC·READY, 행사 영상 제외 같은 조건을 예로 듭니다. 공통화하다가 쿼리가 더 어려워지지 않는 선을 물어봅니다.

07

JPQL 전환 뒤 성능이 나빠지지 않았다는 증거는 무엇을 남기면 좋을까요?

대표 데이터 분포·쿼리 수·실행 계획·응답 시간 중 최소 비교 항목을 합의합니다. Native가 원래 더 빠르다고 가정하지 않습니다.

08

JdbcClient와 JPA를 함께 쓰는 인코딩 경로에서 가장 먼저 점검할 실패 상황은 무엇인가요?

영상 저장 뒤 작업 등록 실패, 작업 중 노드 중단, 임대 만료 뒤 옛 워커 복귀를 제시합니다. ORM 통일보다 작업 유실과 잘못된 완료를 막는 기준을 얻습니다.

멘토가 “왜 이렇게 했나요?”라고 물으면

“DB 전용 기능이 필요한 부분과 이전 ID 참조 원칙 때문에 직접 조인한 부분이 섞여 있습니다. 후자는 현재 규칙에서 이미 방향을 바꿨습니다. 모든 Native에 유지 근거가 있다고 생각하지는 않고, 오늘 실제 코드를 보면서 정리 순서를 잡고 싶습니다.”

피할 답: “성능 때문에 전부 Native입니다.” 비교 실측 없이 성능을 이유로 내세우지 않습니다.

EXPLAIN ANALYZE는 실제 실행합니다. 쓰기 SQL을 운영 DB에서 가볍게 시험하지 말고 별도 테스트 데이터로 확인합니다. PostgreSQL 실행 계획 공식 문서.

먼저 합의할 개선

  • 변환하기 쉬운 조회 하나를 선택합니다.
  • 기존 결과를 테스트로 고정합니다.
  • 쿼리 수·SQL·실행 계획을 비교합니다.
  • 효과가 있으면 같은 유형으로 넓힙니다.

증거 없이 시작하지 않을 개선

  • MyBatis 등으로 저장 계층 전면 교체
  • 연관관계 전부 추가, EAGER로 조회 문제 해결
  • 공간 판정·집계를 대량 객체 로딩으로 이동
  • 모든 Native UPDATE에 clear 일괄 추가
07 / 멘토링 직전 15분

열어둘 파일과 끝날 때 남길 결정

로컬 PostgreSQL·Redis가 필요한 테스트가 있습니다. 시드 상태가 테스트 결과에 영향을 줄 수 있으므로 실패 시 코드 결함과 환경 의존을 구분합니다. 이 자료를 만들며 빌드·DB 테스트·성능 측정은 실행하지 않았습니다.

멘토링이 끝나기 전에 결정할 4가지

  1. Native를 유지할 유형과 설명 문장
  2. 첫 리팩터링 메서드 하나
  3. 옮길 책임과 유지할 트랜잭션 경계
  4. 통과 조건: 결과·동시성·성능 중 무엇을 비교할지

메모와 체크는 자동 저장하지 않습니다. 필요한 내용은 복사해 보관합니다.

용어와 코드 근거

  1. 영속성 컨텍스트: JPA가 엔티티를 관리하는 공간입니다. 관리 객체의 값과 DB를 직접 수정한 결과가 잠시 다를 수 있습니다.
  2. N+1: 목록 한 번을 읽은 뒤 각 항목의 연관 데이터를 읽느라 조회가 N번 더 발생하는 패턴입니다. 연관관계가 없어도 루프에서 Repository를 호출하면 생깁니다.
  3. 멱등: 같은 요청을 반복해도 의도한 효과가 한 번과 같은 성질입니다. 카운트를 계속 증가시키는 UPSERT 자체는 여기에 해당하지 않습니다.
  4. 프로젝션: 엔티티 전체 대신 조회에 필요한 열만 인터페이스·DTO 등으로 받는 방식입니다.
  5. Advisory lock: 애플리케이션이 정한 키로 잡는 DB 잠금입니다. 같은 키로 협력하는 경로끼리만 보호하며, 여기서 쓰는 xact 잠금은 트랜잭션 종료 때 풀립니다.
  6. EXPLAIN (ANALYZE, BUFFERS): 쿼리를 실행하며 계획과 실제 처리량·시간·버퍼 사용을 보는 명령입니다. 인덱스 유무보다 실제 접근 방식을 판단하는 데 쓰입니다.
