미션 핀 행정 단위 클러스터링

MSG-437 · 2026-08-20 · PR #193(본체) + #194(부트 웜업) · Owner B (mission 도메인)

지도를 축소하면 팝업스토어·지역축제 미션 핀이 도감 격자와 같은 방식으로 행정 단위(동 → 구 → 시) 이름 마커("해운대구 12")로 묶인다. 서버는 미션마다 행정동 코드를 1시간 전역 스냅숏에 미리 붙여 두고, 집계 요청은 쿼리 0번의 메모리 산술로 응답한다. 새 컬럼·마이그레이션·Redis 전부 없음. 콜드 첫 요청 1.51초는 부트 웜업으로 사용자 노출에서 제거했다.

1. 왜 만들었나

기존 결정은 "묶기는 화면(FE) 몫, 팝업·축제는 500m 거리 기준"이었다. 이걸 번복한 이유가 둘이다.

문제내용
이름이 없다 거리 기반 묶음은 "핀 3개" 이상을 말하지 못한다. 행정 단위로 묶으면 "해운대구 12"처럼 지역 이름이 붙어 축소 화면에서도 정보가 된다. 도감이 H3(육각형 격자)를 기각하고 행정 단위를 택한 것과 같은 논리다.
시 축척에선 재료 자체가 안 온다 개별 미션 조회(GET /api/missions/active)는 뷰포트 한 변 0.5도 상한이 있어(초과 시 12401) 시 단위 축척에서는 조회가 성립하지 않는다. FE가 묶고 싶어도 묶을 개별 데이터를 받을 수 없다. 넓은 축척용 집계는 서버 몫일 수밖에 없다.

묶는 기준(행정동 코드 접두 자르기, 이름 토큰)은 도감 집계(MSG-356)와 완전히 같고, 실행 방식만 다르다. 도감은 사용자마다 달라 매 요청 SQL로 묶고, 미션은 전 사용자 동일이라 이미 있던 전역 캐시 위에서 산술로 묶는다. 코스는 이번 변경과 무관하다(1km 화면 묶음 유지).

2. 전체 그림 — 경로가 둘이다

경로 A. 스냅숏 재계산 (DB를 타는 유일한 곳) 기동 직후 웜업 1회 + 이후 1시간 TTL 만료 시 ┌──────────────────────────────────────────────────────┐ │ findActive (활성 미션 전량 로드, 기존 쿼리) │ │ → EVENT·POPUP 미션마다 귀속점 계산 │ │ → resolveByPoint (ST_Covers 점 판정) ← 메모이즈 미스만 │ │ → CachedMission에 행정동 코드·이름·귀속점 탑재 │ │ → volatile 필드에 스냅숏 발행 │ └──────────────────────────────────────────────────────┘ 경로 B. 집계 요청 (쿼리 0번) GET /api/missions/aggregation?type=POPUP&unit=SIGUNGU&bbox… ┌──────────────────────────────────────────────────────┐ │ 검증 6단계 → 스냅숏에서 type 필터 │ │ → 귀속점이 bbox 안인 미션 선별 │ │ → 코드 접두 자르기(동10·구5·시2)로 그룹핑 │ │ → 이름 토큰·평균 좌표·count·missionIds 조립 │ └──────────────────────────────────────────────────────┘

3. 경로 A — 귀속 판정과 메모이즈

미션의 귀속점은 판정 격자 사각형의 중앙 셀 중심 위경도다(GridEncoder.center). 축제(9×9)가 두 동에 걸쳐도 중심이 속한 동 하나로만 센다 — 이중 계상하면 묶음 합계가 미션 수와 어긋난다. 그 점 하나를 기존 역지오코딩 계약에 묻는다.

region/repository/RegionRepository.findContainingRegion (기존 쿼리 재사용, 건당 ~1.2ms)

SELECT region_code, region_name, parent_code
FROM regions
WHERE ST_Covers(boundary_geom, ST_SetSRID(ST_MakePoint(:lon, :lat), 4326)::geography)
ORDER BY region_code
LIMIT 1

ST_Covers는 GIST 인덱스를 타는 점-폴리곤 포함 판정이고(ST_Contains는 캐스트 때문에 인덱스 우회), ORDER BY … LIMIT 1은 경계선 위 좌표의 다중 매칭을 결정적으로 단일화한다. 도감 수집률·역지오코딩 API가 쓰는 판정과 물리적으로 같아서 두 화면의 지역 이름이 어긋날 수 없다.

메모이즈 — 쿼리는 사실상 첫 한 번뿐

판정 결과는 (미션 id, 판정 사각형)을 키로 재계산 세대 간 재사용한다. 사각형이 안 바뀐 미션은 다시 묻지 않으므로, 활성 전량(~205건)의 판정 쿼리가 도는 건 프로세스 기동 후 첫 계산뿐이고 이후 TTL 갱신은 신규·변경 미션 몇 건이다.

부산 bbox를 SIGUNGU로 물으면 동구 1 + 부산진구 6 + 해운대구 3 + 수영구 1 = 11로 상위 단위 합계와 정확히 일치한다(접두 자르기라 산술적으로 보장).

묶음 선택 = 줌인 후 교집합

missionIds만으로는 카드를 못 그린다(카드 재료는 개별 조회 응답에 있다). 제품 계약: 묶음 마커 선택은 다음 세부 단위로의 줌인이고, 개별 조회가 성립하는 축척에 들어온 뒤 그 결과와 missionIds의 교집합으로 목록이 좁혀진다. 세대가 어긋나 사라진 id는 교집합에서 자연 탈락하므로 유령 카드가 없다.

5. 부트 웜업 (PR #194)

dev 실측에서 콜드 첫 요청 1.51초, 웜 12ms. 차이는 활성 205건의 귀속 판정이다. 재시작당 한 번뿐인 비용이라, 첫 사용자에게 물리는 대신 기동 직후로 옮겼다. 

@EventListener(ApplicationReadyEvent.class)
@Transactional(propagation = Propagation.NOT_SUPPORTED)
public void warmUpSnapshot() {
	try {
		log.info("미션 스냅숏 부트 웜업 완료: 활성 미션 {}건 (MSG-437)", snapshot().size());
	} catch (RuntimeException e) {
		log.warn("미션 스냅숏 부트 웜업에 실패해 첫 조회 요청이 재계산합니다 (MSG-437)", e);
	}
}
  • 시점: ApplicationReadyEvent는 시더(ApplicationRunner)들 이후 발화 — 시딩 켠 기동에서도 방금 적재분이 스냅숏에 들어온다.
  • 실패해도 기동 유지: 웜업은 최적화지 기동 조건이 아니다. 예외는 warn만 남기고 삼키고, 첫 요청이 재시도한다.
  • 새 계산 경로 없음: 기존 snapshot()을 그대로 부른다. 더블체크 락·메모이즈가 동일 적용.
NOT_SUPPORTED가 붙은 이유 (Codex 리뷰 P1) — 이 클래스엔 클래스 레벨 @Transactional(readOnly = true)가 있다. 그대로 두면 프록시가 리스너 진입 시점에 트랜잭션(=DB 커넥션)을 여는데, 하필 이 방어가 겨냥한 "기동 시 DB 장애"에서 그 열기가 CannotCreateTransactionException으로 실패한다 — 메서드 안 try에 닿기 전이라 예외가 리스너 밖으로 나가 기동이 죽는다. NOT_SUPPORTED는 이 메서드만 트랜잭션 밖에 두라는 선언이라 그 경로 자체가 사라진다. 지우면 결함이 조용히 되살아나므로 테스트가 어노테이션 존재를 리플렉션으로 잠근다.

7. 알아두면 좋은 것

  • 저장 위치: DB·Redis 아님. JVM 메모리의 volatile 스냅숏 하나(단일 인스턴스 전제). 재시작하면 사라지고 웜업이 다시 만든다.
  • 기각한 대안: missions에 region_code 컬럼 신설(레거시 팝업 원좌표 소실·백필·TourAPI 전환 경합), 요청 시 SQL GROUP BY(캐시 전제와 어긋남), Redis(수백 건 읽기 전용에 과함). 근거 전문은 ADR — 컨플 cf-40042497, LLM-WIKI 04-decisions/ADR 미션 핀 클러스터링 스냅숏 메모리 집계.md.
  • 승격 지점: 활성 미션이 수천 건 규모가 되면 귀속 판정을 unnest 배치 쿼리로, missionIds 응답 계약(페이징)도 그때 재논의.
  • 남은 레인: 마커 렌더링·축척 전환은 FE·모바일 몫 (SRS FR-MISSION-20 진행 중). 모바일(MSG-428)은 부산 MVP라 시 단위 보류 중 — 도입 시 정합 확인.
