01 / PRODUCT CONTEXT

어떤 기능에서 발생한 문제인가

FillMap은 방문한 장소를 짧은 영상으로 기록하고 지도 위 격자를 수집하는 서비스입니다. 행사 기능에서는 하나의 행사 회차에 묶인 장소와 현장 영상을 볼 수 있고, 사용자는 관심 있는 회차의 알림을 직접 켤 수 있습니다. 이번 대상은 그 구독자에게 행사가 시작됐다는 알림을 기록하는 기능입니다.

사용자가 기대하는 동작

예를 들어 사용자가 내일 열리는 행사 알림을 켰다면, 행사가 시작된 뒤 시작 안내를 받습니다. 이미 진행 중인 행사를 뒤늦게 구독한 사용자에게는 같은 시작 안내를 보내지 않습니다.

02 / PROBLEM

작은 기능 테스트는 통과했지만,
한 번의 실행이 수분 동안 끝나지 않았습니다

출발점은 멘토 피드백을 바탕으로 진행한 백엔드 감사였습니다. 트랜잭션 안의 외부 I/O뿐 아니라 한 트랜잭션 안에서 얼마나 많은 SQL과 반복 처리를 수행하는지 확인하던 중, 행사 시작 알림이 구독자를 전부 읽은 뒤 한 명씩 알림을 저장하는 구조를 찾았습니다.

정적 검토만으로 실제 비용을 단정하지 않고 로컬 PostgreSQL에 합성 사용자를 넣어 실제 스케줄러를 실행했습니다. 구독자는 1천 명, 1만 명, 5만 명으로 늘렸습니다. 운영에서 장애가 발생한 기록이 아니라, 잠재 병목을 로컬에서 재현한 사례입니다.

알림 기록이 늦어집니다

DB 기록이 커밋돼야 후속 전달 경로가 알림을 처리할 수 있습니다. 첫 발송 트랜잭션이 수분간 열려 있으면 그 안의 알림은 커밋 전까지 전달 대상으로 보이지 않습니다.

따라서 알림 준비 지연의 원인이 될 수 있습니다. 실제 사용자 단말의 도착 지연은 이번에 측정하지 않았습니다.

일정 변경도 함께 기다립니다

발송과 행사 일정 갱신은 같은 잠금을 사용합니다. 5만 명 진단 중 별도 연결이 이 잠금을 요청하자 334.367초 뒤에 획득했습니다.

잠금 보유자와 차단 관계를 DB에서 확인했습니다. 실제 일정 수정 API의 응답 시간을 잰 시험은 아닙니다.

같은 틱에서 사용하는 Hikari 연결 반환은 두 번이었고, 5만 명의 연결 점유 합계는 400.376초였습니다. 대부분은 첫 발송 트랜잭션에 몰렸습니다. 외부 네트워크 호출이 없는 메서드라도 애플리케이션의 반복 작업 때문에 DB 연결과 잠금을 오래 붙잡을 수 있었습니다.

중복 알림도 공짜가 아니었습니다. 이미 기록한 1만 명을 다시 처리하는 데 16.086초가 걸렸고 SQL prepare도 10,005회였습니다. 중복 저장이 막힌다는 사실만으로, 중복 확인을 시도하는 비용까지 사라지지는 않았습니다.

03 / BEFORE

기존 트랜잭션은 무엇을 하고 있었나

발송 TX 시작 → event_seed 잠금 획득 → 전체 후보 처리가 끝나야 COMMIT
후보 회차 SELECT: 시작됨 + 아직 종료되지 않음 + 시작 후 24시간 이내
각 회차의 구독자를 JPA 엔티티 목록으로 전량 조회
구독자 N명에 대해 반복
가입 시각 검사 → NotificationCommandService.record → native INSERT → 다음 사용자
모든 후보 회차 처리가 성공하면 커밋. 중간 오류면 앞선 회차까지 롤백
독립된 종료 정리 TX
같은 event_seed 잠금 획득 → 종료 회차의 구독 DELETE → COMMIT

‘한 명에게 알림을 기록한다’는 작은 호출이 N번 쌓였습니다

// 변경 전 recordStart의 핵심 흐름을 축약한 코드
for (var subscription : subscriptionRepository
        .findAllByIdEventOccurrenceId(occurrence.getId())) {

후보 회차가 하나이고 수신 대상이 N명인 벤치에서는 발송에 잠금 1 + 후보 조회 1 + 구독 조회 1 + 개별 INSERT N이 필요했습니다. 뒤의 종료 정리 잠금 1 + DELETE 1까지 합치면 관측된 prepare 수는 N + 5가 됩니다.[2]

왜 처음부터 잠금을 없앨 수 없었나

잠금은 단순한 성능 방해물이 아니었습니다. 알림이 후보를 읽은 직후 다른 트랜잭션이 행사 시작을 내일로 미루면, 이미 읽은 시각으로 “행사가 시작됐어요”를 기록할 수 있습니다. 그래서 잠금을 먼저 얻고 그 뒤 최신 후보를 읽는 순서가 필요했습니다.

설명용 경합 예시

알림 TX가 오전 10시 시작 일정을 읽습니다. 그 사이 일정 변경 TX가 시작을 다음 날로 연기합니다. 보호 없이 옛 조회 결과를 사용하면 아직 시작하지 않은 행사의 시작 알림이 나갑니다. 현재 공통 잠금은 일정 갱신과 발송을 순서대로 실행해 이 엇갈림을 막습니다.

종료 정리도 같은 이유로 보호합니다. 종료 시각을 연장하는 갱신과 정리가 겹치면, 옛 종료 시각을 읽은 정리 작업이 아직 유효한 구독을 지울 수 있기 때문입니다. 이번 개선은 이 계약을 그대로 두고 잠금 안에서 수행하는 작업량을 줄이는 방향으로 정했습니다.[3]

04 / INVESTIGATION

반복 SQL에서 반복 flush까지,
어떻게 원인을 좁혔나

1. 코드에서 사용자별 기록 경로를 찾았습니다

구독 엔티티 목록을 읽고 같은 트랜잭션에서 native INSERT를 반복했습니다. 처음 확인할 가설은 사용자 수만큼 늘어나는 SQL 호출 비용이었습니다. 쿼리 메서드 개수 대신 실제 호출 횟수를 봤습니다.

2. 실측에서 N+5 prepare를 확인했습니다

데이터 규모를 늘릴수록 SQL 준비 횟수가 1,005 → 10,005 → 50,005회로 증가했습니다. 처리 시간의 증가도 단순한 사용자 수 증가보다 가팔랐습니다. 이 관찰만으로 원인을 특정하지 않고 실행 중인 JVM을 확인했습니다.

3. 실행 스택에서 native SQL 직전의 flush를 확인했습니다

NativeQueryImpl.prepareForExecution
  → SessionImpl.flush
    → prepareEntityFlushes / cascadeOnFlush

구독자 엔티티를 전량 읽은 영속성 컨텍스트가 남아 있는 상태에서, 개별 native INSERT에 앞서 flush[4] 경로가 반복됐습니다. “사용자 한 명 저장”이라는 호출 밖에서도 JPA가 관리 중인 엔티티를 확인하는 일이 생긴 것입니다.

30초 JFR에서 작업 스레드 실행 샘플 1,912개 중 1,465개, 약 76.6%에 flush 관련 프레임이 있었습니다. 이는 전체 400초의 76.6%가 flush에 쓰였다는 뜻이 아닙니다. SQL 왕복과 변경 검사 각각의 시간 비중은 분리하지 않았습니다.

4. 대기 중인 연결도 실제 보유자와 연결했습니다

pg_blocking_pids(37455)가 발송 연결 37215를 반환하는 것을 확인했습니다. 잠금 요청은 발송 시작보다 늦게 들어갔고, 남은 작업이 끝나기까지 334.367초를 기다렸습니다. 단순히 “느린 동안 다른 쿼리도 느렸다”는 추정에서 멈추지 않았습니다.

SQL 호출 횟수와 관리 중인 구독 엔티티를 함께 줄이면, 이 경로의 반복 비용 두 가지를 한 번에 제거할 수 있었습니다.

전후 실측은 그 변경 묶음의 효과를 보여줍니다. 반복 검사로 비용이 증폭되는 구조는 확인했지만 정확한 시간복잡도나 원인별 기여율까지 실험으로 증명한 것은 아닙니다.

05 / DECISION

어떤 대안을 비교했고,
왜 INSERT SELECT를 골랐나

대안 판단의 기준은 세 가지였습니다. 구독자별 SQL 호출을 줄일 수 있는가, 엔티티 전량 관리를 피할 수 있는가, 기존 일정·롤백 계약을 유지할 수 있는가. 아래의 대안들은 구조를 검토한 것이며, 선택하지 않은 대안의 성능을 별도로 구현·측정한 것은 아닙니다.

대안얻는 것남는 비용 / 바뀌는 계약이번 판단
필요한 필드만 조회
projection		관리 엔티티를 줄이고 메모리 부담을 낮춤단건 record를 그대로 쓰면 사용자별 SQL 호출 N회가 남음부분 개선에 그쳐 선택하지 않음
JDBC 배치여러 INSERT를 배치로 전달해 왕복 비용을 줄일 여지수신자 목록을 앱으로 읽고 배치를 구성해야 함. 오류 처리도 기존 원자성에 맞춰야 함가능한 대안이나 이번에는 데이터가 모두 DB 안에 있어 더 작은 방법을 선택
INSERT SELECT
선택		DB가 수신자를 골라 같은 문장에서 기록. 앱의 구독자 목록과 단건 호출 제거native SQL이 구독 테이블을 직접 참조. DB의 행별 제약 검사는 계속 수행기존 repository에 쿼리 하나를 추가해 두 반복 비용을 제거
회차·사용자 단위 청크 커밋각 TX가 잠금을 보유하는 시간을 제한할 여지틱 전체 롤백이 부분 성공으로 달라짐. 일정 갱신이 청크 사이에 끼어드는 상황도 다시 설계해야 함기존 계약을 바꾸므로 이번 범위에서 제외
잠금 제거 또는 축소잠금 경쟁을 줄일 여지옛 일정으로 알림 기록, 연장된 회차의 구독 삭제 위험을 별도 방법으로 막아야 함정합성 보호를 제거하는 변경이므로 제외
전역 flush 모드 변경반복 변경 검사를 줄일 여지구독자별 SQL은 남고, 다른 경로의 변경 반영 시점에도 영향을 줄 수 있음원인 경로를 좁혀 수정하는 쪽을 선택
모든 후보 회차까지 SQL 하나로 통합회차별 호출도 제거후보 판정과 event key 생성 로직을 SQL로 옮겨야 함회차 루프는 유지하고 이번 병목인 구독자 루프만 제거

새 큐나 워커를 추가하는 작업도 하지 않았습니다. 이번에 느린 곳은 알림을 외부로 전달하는 단계가 아니라 전달할 레코드를 만들기 전의 DB 기록 경로였습니다. 먼저 확인된 반복 비용을 제거했습니다. 큐 확장의 효과는 이번 실험에서 비교하지 않았습니다.

앱에는 구독자 엔티티 목록을 만들지 않음

실제 추가한 SQL

INSERT INTO notifications
    (user_id, category, event_key, title, body, created_at)
SELECT s.user_id, 'EVENT', :eventKey, :title, :body,
       statement_timestamp() AT TIME ZONE 'UTC'
FROM event_notification_subscriptions s
WHERE s.event_occurrence_id = :occurrenceId
  AND s.created_at <= :startsAt
ON CONFLICT (user_id, event_key) DO NOTHING

수신 대상은 기존과 같은 회차, 같은 created_at <= startsAt 조건으로 고릅니다. 같은 사용자·event key가 이미 있으면 기존 행을 덮어쓰지 않습니다. 이름이 같은 행사를 구분하는 기준도 기존대로 EVENT_START:{occurrenceKey}:{startsAt의 UTC epoch초}입니다. 일정이 미뤄졌다가 새 시작 시각이 되면 다른 키로 기록할 수 있습니다.

호출 경계도 유지했습니다

EventNotificationScheduler.recordStart(occurrence)
  → NotificationCommandService.recordEventStart(...)
    → NotificationCommandServiceImpl (@Transactional, REQUIRED)
      → NotificationRepository.insertEventStart(...)

서비스의 REQUIRED 전파는 호출자가 연 발송 TX에 참여합니다. 메서드 호출이 끝날 때마다 독립 커밋하는 구조가 아닙니다. 실제 저장은 기존 notification 도메인의 repository가 맡습니다.

변경 후에도 동일한 발송 TX와 잠금
잠금 → 후보 조회 → 후보 회차별 INSERT SELECT → 전체 성공 시 COMMIT

production 코드는 스케줄러, 기존 서비스 인터페이스·구현체, 기존 repository의 4개 파일을 수정했습니다. 새 테이블·인덱스·마이그레이션·빈·설정은 추가하지 않았습니다. 기존 단건 record는 뱃지·스트릭·주간 요약 등 다른 알림과 행사 일정 변경 알림이 계속 사용합니다. 일정 변경 경로가 쓰는 구독자 조회도 삭제하지 않았습니다.

07 / TRADE-OFFS

빨라지는 대신 무엇을 감수했나

DB 중심의 기록으로 옮겼습니다

앱의 목록 처리와 반복 호출을 줄이는 대신 native SQL이 event_notification_subscriptions를 직접 참조합니다. 구독 테이블의 구조나 대상 조건이 바뀌면 알림 repository의 SQL도 함께 살펴봐야 합니다.

기존에도 PostgreSQL ON CONFLICT를 쓰고 있었습니다. 새 DB 의존성을 도입했다기보다, 수신자 선택까지 SQL로 옮긴 변화입니다.

한 회차의 기록 시각이 같아집니다

같은 INSERT 문장에서 기록한 알림은 같은 statement timestamp를 갖습니다. 기존에는 사용자별 INSERT의 시각에 간격이 있었습니다.

‘DB 기록 시점의 UTC’라는 의미는 유지합니다. 사용자별로 서로 다른 시각을 보장하는 계약은 없었습니다.

취소와 기록을 새로 직렬화하지 않았습니다

구독 토글은 행사 잠금에 참여하지 않습니다. 이제 대상은 INSERT SELECT의 문장 스냅샷[5]에서 결정됩니다. 문장 전에 완료된 취소는 제외하지만, 문장이 이미 본 구독을 그 뒤 취소하면 이번 틱의 알림이 남을 수 있습니다.

기존 SELECT와 INSERT 사이 간격이 없어져 일부 경합 순서의 결과가 달라질 수 있습니다. 진행 중인 알림을 취소 API가 반드시 철회한다는 보장을 추가하지 않았습니다.

실패 범위는 여전히 틱 전체입니다

같은 발송 TX 안의 어느 회차에서 DB 오류가 나면 앞선 회차의 새 기록도 롤백됩니다. 다음 틱이 발송 창 안에서 다시 기록하고 중복 제약이 기존 알림을 보호합니다.

사용자 탈퇴가 외래 키 검사와 겹쳐 오류를 내는 경우도 전체 롤백 가능성이 남습니다. 무조건 성공하거나 영구 무손실이라고 표현할 수는 없습니다.

전역 잠금과 행별 DB 작업은 남아 있습니다.

SQL 호출을 한 번으로 줄여도 5만 행 저장·고유 키 확인·외래 키 검사까지 O(1)이 되지는 않습니다. 여러 회차의 전체 기록은 계속 하나의 발송 TX에 묶입니다. 향후 규모가 더 커지면 측정 후 다시 판단해야 합니다.

기존 발송 창은 시작 후 24시간입니다. 서버가 이 창을 통째로 놓치면 시작 알림을 나중에 무기한 보충하지 않습니다. 이번 최적화로 그 정책이 바뀌지는 않았습니다.

실제로 사용한 실행 명령

명령은 FillMap 저장소 루트 기준입니다. 삭제한 감사 DB를 다시 준비하고 스키마와 행정동 데이터를 채우는 절차는 개선 전 보고서를 참고합니다.

./gradlew -I load-test/tx-workload/bench.init.gradle test \
  --tests '*EventFanoutBenchmark.benchmarkActualSchedulerFanout'

./gradlew -I load-test/tx-workload/bench.init.gradle test \
  --tests '*EventFanoutBenchmark.benchmarkEventWriteLockContentionDuringFiftyThousandFanout'

SPRING_DATASOURCE_URL=jdbc:postgresql://localhost:5432/fillmap_tx_bench_20260908 \
SPRING_DATA_REDIS_DATABASE=15 ./gradlew build

규모 환경변수만 바꿔 같은 테스트를 다시 돌릴 때는 --rerun-tasks를 붙입니다. SQL 로그 검증과 EXPLAIN은 순수 시간 측정과 별개로 실행합니다.

용어

  1. Outbox. 외부로 보낼 내용을 먼저 DB에 기록하고 별도 전달 경로가 읽는 방식입니다. 이번 기록의 성공은 푸시의 최종 도착까지 보장한다는 뜻이 아닙니다.
  2. SQL prepare. Hibernate가 JDBC 문장을 준비한 횟수입니다. DB의 업무 execute 횟수와 항상 같다고 가정하지 않고 별도 로그로 대조했습니다.
  3. 트랜잭션 advisory lock. 정해진 키를 먼저 획득한 트랜잭션이 커밋·롤백할 때까지 같은 키의 경쟁 요청이 기다리는 PostgreSQL 기능입니다. 여기서는 event_seed 키로 행사 일정 갱신·발송·정리를 보호합니다.
  4. Flush와 영속성 컨텍스트. JPA는 조회한 엔티티를 관리하며 변경 내용을 DB에 반영하기 위해 상태를 확인합니다. 이 사례에서는 전량 로딩된 구독자가 남은 상태에서 native INSERT 직전의 flush 경로가 반복되는 것을 관측했습니다.
  5. 문장 스냅샷. SQL 문장이 읽을 때 보이는 데이터 상태입니다. 문장이 이미 선택한 수신자가 이후 취소되더라도 즉시 철회된다는 의미는 아닙니다.
  6. 연결 점유. 풀에서 DB 연결을 빌려 반환하기까지의 시간입니다. SQL 실행뿐 아니라 그 연결을 보유한 상태의 앱 연산과 대기도 포함될 수 있습니다.
