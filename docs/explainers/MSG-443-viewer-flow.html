행사방 열람 인원 집계 — Redis 흐름

MSG-443 · 스펙 docs/spec/MSG-443.md · 구현 com.msg.fillmap.event · PR #196

TL;DR — 행사방 헤더의 "N명 보는 중"은 회차당 Redis Sorted Set 하나로 센다. 클라이언트가 30초마다 heartbeat를 보내면 Lua 스크립트가 청소 → ZADD GT → EXPIRE 120을 원자로 실행하고, 조회는 ZCOUNT 한 방이다. DB 테이블 없음, 유실 허용 근사값, 캐시가 죽으면 인원 수만 숨긴다.

1. 저장 구조

항목값
키eventviewer:{occurrenceId} (회차당 Sorted Set 하나)
member세션 식별자 — 로그인 u:{userId} · 비로그인 s:{X-Viewer-Session 헤더값}
score마지막 heartbeat의 epoch 초 (주입된 Clock, UTC)
키 TTL120초 — heartbeat마다 재설정. 메모리 회수 전용이고 활성 판정에는 안 쓴다

Sorted Set 하나가 두 문제를 동시에 푼다. 같은 사용자의 중복 탭은 member가 같아 ZADD가 score만 덮어쓰니 자동으로 1명이고, "90초 이내" 판정은 score 범위 연산 하나다. 세션당 String 키(만료는 공짜지만 세는 게 SCAN 순회)와 HyperLogLog(제거 불가)는 기각했다.

2. heartbeat 쓰기 — Lua 원자 실행

-- EventViewerServiceImpl.HEARTBEAT_SCRIPT (원문)
redis.call('ZREMRANGEBYSCORE', KEYS[1], '-inf', ARGV[1])  -- ARGV[1] = "(now-90"  배타 청소
redis.call('ZADD', KEYS[1], 'GT', ARGV[2], ARGV[3])       -- ARGV[2] = now, ARGV[3] = member
redis.call('EXPIRE', KEYS[1], ARGV[4])                    -- ARGV[4] = 120
return 1
  • 청소 — 90초 지난 멤버를 쓰기 경로에서 지운다. 인기 행사방은 heartbeat가 계속 와서 키가 안 죽으므로, 여기서 안 지우면 하루 동안 다녀간 전원이 멤버로 쌓인다.
  • ZADD GT — 기존보다 큰 score만 덮어쓴다(신규 멤버 추가는 그대로). 네트워크에서 지연된 옛 heartbeat가 나중에 도착해 최신 score를 과거로 되돌리는 역순 실행 방지.
  • EXPIRE 120 — 분리 명령이면 ZADD 후 연결이 끊길 때 TTL 없는 키가 남는다 (핫구역 INCREMENT_SCRIPT와 같은 이유로 Lua에 묶음).

3. 조회

ZCOUNT eventviewer:{occurrenceId}  now-90  +inf
-- 자바: opsForZSet().count(key, cutoff, Double.POSITIVE_INFINITY)  — 포함 경계

청소는 쓰기가 이미 하므로 조회는 세기만 한다. 키가 없으면 ZCOUNT가 0을 돌려주고, 그 0은 "아무도 없음"으로 그대로 응답한다(장애 null과 다름 — 5절).

4. 경계 숫자 세 개의 의미

숫자역할왜 이 값인가
30초클라이언트 전송 주기FE 계약 값. 서버 코드에는 없다
90초활성 판정 창 (ACTIVE_WINDOW_SECONDS)신호 3번을 놓쳐야 빠진다. 딱 90초 경과는 포함
120초키 TTL (KEY_TTL_SECONDS)활성 창과 같은 90초면 마지막 신호 후 정확히 90초에 키째 만료돼, 세어야 할 경계 멤버가 세어지기 전에 사라진다 (Codex 리뷰 적발). 그래서 분리
청소식 (now-90은 배타, 조회식 now-90은 포함 — 문법이 다른 게 의도다. 딱 90초 경과한 멤버를 청소가 남기고 조회가 세어, 둘이 합쳐 "90초 이내 포함" 판정이 된다. 어느 한쪽을 "통일"하면 경계 테스트 경계_90초는_포함이다가 깨진다.

5. 세션 식별과 API

POST /api/event-occurrences/{occurrenceId}/heartbeat     (본문 없음, 200)
GET  /api/event-occurrences/{occurrenceId}/viewer-count  → { viewerCount: Integer }

둘 다 비로그인 허용(2026-08-20 확정 — 열람 계열은 비로그인, 업로드류만 로그인). resolveViewerKey 판정 순서:

  • principal 있음 → u:{userId}. 헤더가 와도 무시 — 탭마다 헤더 세션 ID가 달라도 로그인 사용자는 항상 1명으로 수렴
  • principal 없음 → X-Viewer-Session 헤더 (공백 아님 · 64자 이하) → s:{값}
  • 둘 다 없거나 헤더 불량 → 공통 400 (도메인 에러코드 신설 없음)

접두사 u:/s:는 userId 숫자와 익명 ID의 문자열 충돌 방지다. 익명 ID는 클라이언트 생성 값이라 새 ID 연타로 인원을 부풀릴 수 있는데, 열람 인원은 보호 자산이 아닌 공개 근사값이라 수용했다(rate limit은 요구사항 신설이라 미도입).

함정 — permitAll 배선. 두 경로는 SecurityConfig permitAll에만 등록한다. JwtAuthenticationFilter.PUBLIC_AUTH_PATHS(skip 목록)에는 절대 넣지 않는다 — 필드 주석이 "permitAll 경로와 함께 갱신"을 유도하지만, 여기 넣으면 Bearer 파싱이 통째로 건너뛰어져 로그인 사용자의 principal이 null이 되고 전부 익명으로 잘못 집계된다. 이 경로들은 "인증 불요"이지 "토큰 무시"가 아니다. 만료·위조 토큰이 실린 요청은 기존 필터 의미론대로 401 — 익명으로 보내려면 토큰을 빼면 된다.

6. 장애 격리 (FR-19)

상황동작
heartbeat 중 Redis 예외삼키고 warn 로그, 응답 200 — 클라이언트가 할 일이 없고 30초 뒤 재전송이 내장
조회 중 Redis 예외viewerCount: null — FE는 문구 자체를 숨긴다. 0(아무도 없음, 표시)과 구분
영상 조회·업로드영향 없음 — 열람 집계 코드가 그 경로에 아예 없다(구조적 분리)
격리 범위의 한정. 위 격리는 "집계 연산의 실패"에 대한 것이다. 공유 Redis가 전면 장애면 인증 필터의 토큰 블랙리스트 조회(JwtTokenProvider.validateToken → RedisInvalidatedTokenStore.isInvalidated, try-catch 없음)가 먼저 실패해, 토큰을 실은 요청은 인증 단계에서 죽는다 — 영상 API 포함 전 인증 API 공통의 기존 플랫폼 특성이다. 토큰 없는 익명 요청은 블랙리스트 조회를 거치지 않으므로 격리가 그대로 동작한다.

7. 시나리오로 보는 타임라인

t=0    사용자 A(로그인, 탭2개)·B(익명) 입장
       ZADD u:42 → 1명 … ZADD u:42(다른 탭, 같은 member) → 여전히 1명 … ZADD s:abc → 2명
t=30   heartbeat 재전송 → score만 갱신, EXPIRE 120 리셋
t=60   B가 창을 닫음 (신호 중단 — 퇴장 이벤트 없음)
t=150  A의 heartbeat가 청소 실행 → s:abc(마지막 신호 t=60, 90초 초과) 제거 → 1명
t=151  A도 닫음
t=271  마지막 신호(t=151) + 120초 → 키째 TTL 소멸. 조회는 그 전에도 t=241부터 0
       (score 창 90초가 판정하므로 TTL과 무관하게 "90초 지나면 0")
