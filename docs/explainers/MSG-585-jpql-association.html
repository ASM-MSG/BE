MSG-585 · 2026-09-08 · 파일럿

격자 리포지토리의 네이티브 SQL 5건을 연관관계 기반 JPQL로 옮겼다

동작은 하나도 안 바뀌었고, 바뀐 것은 "쿼리를 어떤 언어로 적느냐"뿐이다. 이 페이지는 무엇을 왜 바꿨는지, 그리고 정말 같은지를 어떻게 확인했는지를 코드를 안 연 사람이 따라갈 수 있게 적는다.

2새로 붙인 연관관계 (읽기 전용)
5 / 8JPQL로 옮긴 네이티브 쿼리 / 전체
3,059변경 후 통과한 테스트 (실패 0)

왜 했나

9월 7일 멘토링에서 "네이티브 쿼리를 줄이고 JPQL과 애플리케이션 로직을 우선하라"는 권고가 있었다. 다음 날 백엔드 감사에서 네이티브 쿼리 108건을 전수 분류했더니 42건은 PostgreSQL 전용 문법이 하나도 없어서 JPQL로 갈 수 있는 것이었다.

42건을 한 번에 바꾸는 대신 GridRepository 하나로 먼저 해 보고, 실제 실행되는 SQL과 실행 계획이 전후로 같은지 재 봤다. 같으면 나머지에 같은 방식을 쓰고, 다르면 여기서 멈춘다. 그래서 "파일럿"이다.

이 작업은 요구사항을 바꾸지 않는 리팩터링이라 PRD 없이 진행했다. API 응답, 저장되는 데이터, DB 스키마 전부 그대로다.

1. 연관관계 두 개를 붙였다

JPQL은 테이블이 아니라 자바 엔티티를 기준으로 쓰는 쿼리 언어다. 엔티티끼리 "이게 저걸 가리킨다"는 연관관계가 있으면 조인 조건을 매번 적지 않아도 ug.grid.gridY처럼 점으로 따라갈 수 있다. 격자 도메인에는 그 연관이 없어서 지금까지 조인이 필요한 조회는 전부 네이티브 SQL이었다.

코드로는 이 두 줄이 핵심이다

Grid.java 
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "region_code",
            insertable = false, updatable = false)
private Region region;
UserGrid.java 
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "grid_id",
            insertable = false, updatable = false)
private Grid grid;
  • 읽기 전용. 저장·수정에 관여하지 않는다. 그래서 원래 있던 regionCode 문자열 필드도 지우지 않고 그대로 뒀다. 같은 컬럼을 두 필드가 읽는 셈인데, 둘 다 읽기 전용이라 JPA가 허용한다.
  • LAZY. "필요할 때만 가져온다." 격자 하나를 id로 조회해도 regions를 같이 읽지 않는다. JPQL에서 JOIN g.region이라고 명시할 때만 조인된다. DB 로그로 확인했다. 격자 단건 조회 SQL은 변경 전과 똑같이 grids 한 테이블만 읽는다.
  • 스키마 무변경. 컬럼도 FK도 원래 있던 것이다. 자바 쪽에 이름표만 붙였다.

2. 쿼리 5건, 전과 후

왼쪽이 원래 네이티브 SQL, 오른쪽이 JPQL이다. 테이블 이름이 엔티티 이름으로, 컬럼이 필드로 바뀌었고, 조인 조건은 연관 경로로 대체됐다. 각 쿼리 아래에 "무엇이 왜 달라졌나"를 한두 줄로 적었다.

findVideoCount · 격자 하나를 내가 영상 몇 개로 채웠나

전 · native 
SELECT ug.video_count
FROM user_grids ug
WHERE ug.user_id = :userId
  AND ug.grid_id = :gridId
후 · JPQL 
SELECT ug.videoCount
FROM UserGrid ug
WHERE ug.id.userId = :userId
  AND ug.id.gridId = :gridId

조인이 없어 연관관계도 필요 없다. 이름만 자바식으로 바뀌었다. ug.id.userId는 복합키(UserGridId) 안의 필드를 가리키는 표기다.

findOccupiedInRange · 지도 화면 범위 안의 내 점령 격자 전부

전 · native 
SELECT g.grid_id AS "gridId", g.grid_y AS "gridY",
       g.grid_x AS "gridX", r.region_name AS "regionName"
FROM user_grids ug
JOIN grids g ON g.grid_id = ug.grid_id
LEFT JOIN regions r ON r.region_code = g.region_code
WHERE ug.user_id = :userId
  AND g.grid_y BETWEEN :minY AND :maxY
  AND g.grid_x BETWEEN :minX AND :maxX
후 · JPQL 
SELECT g.gridId AS gridId, g.gridY AS gridY,
       g.gridX AS gridX, r.regionName AS regionName
FROM UserGrid ug
JOIN ug.grid g
LEFT JOIN g.region r
WHERE ug.id.userId = :userId
  AND g.gridY BETWEEN :minY AND :maxY
  AND g.gridX BETWEEN :minX AND :maxX

연관관계의 효과가 보이는 곳이다. ON g.grid_id = ug.grid_id를 매번 적던 것이 JOIN ug.grid로 끝난다. Hibernate가 엔티티 정의를 보고 조인 조건을 채운다. LEFT JOIN은 그대로다. 바다처럼 어느 동에도 안 속하는 격자를 지도에서 떨어뜨리지 않기 위한 규칙이다.

findOccupiedPage · 위와 같은데 정렬해서 첫 페이지만

전 · native 
… (위와 같은 FROM · WHERE)
ORDER BY g.grid_y, g.grid_x
LIMIT :limit

-- 파라미터: int limit
후 · JPQL 
… (위와 같은 FROM · WHERE)
ORDER BY g.gridY, g.gridX


-- 파라미터: Limit limit  (Spring Data)

JPQL에는 LIMIT 문법이 없다. 대신 Spring Data의 Limit 타입을 파라미터로 받으면 상한이 걸린다. 그래서 호출부 세 곳(서비스 1, 테스트 2)이 limit 대신 Limit.of(limit)을 넘긴다. 실제 생성 SQL은 fetch first ? rows only인데 PostgreSQL에서 LIMIT과 같은 뜻이다.

summarizeOccupiedByRegion · 어떤 동 안의 내 점령 격자 수와 영상 수 합계

전 · native 
SELECT COUNT(*)::int AS "gridCount",
       COALESCE(SUM(ug.video_count), 0) AS "videoCount"
FROM user_grids ug
JOIN grids g ON g.grid_id = ug.grid_id
WHERE ug.user_id = :userId
  AND g.region_code = :regionCode
후 · JPQL 
SELECT CAST(COUNT(ug) AS Integer) AS gridCount,
       COALESCE(SUM(ug.videoCount), 0L) AS videoCount
FROM UserGrid ug
JOIN ug.grid g
WHERE ug.id.userId = :userId
  AND g.regionCode = :regionCode

::int는 PostgreSQL 전용 문법이라 표준 CAST로 바꿨다. 0L은 SUM 결과가 Long이라 타입을 맞춘 것이다. 결과를 받는 인터페이스(getGridCount() Integer, getVideoCount() Long)를 안 건드리기 위해서다.

findRegionNames · 격자 여러 개의 행정동 이름을 한 번에

전 · native 
SELECT g.grid_id AS "gridId",
       r.region_name AS "regionName"
FROM grids g
JOIN regions r ON r.region_code = g.region_code
WHERE g.grid_id IN (:gridIds)
후 · JPQL 
SELECT g.gridId AS gridId,
       r.regionName AS regionName
FROM Grid g
JOIN g.region r
WHERE g.gridId IN :gridIds

여기는 일부러 INNER JOIN이다. 결과가 "격자 → 이름" 사전으로 쓰여서 동이 없는 격자는 아예 안 나오는 게 맞다(핫구역이 그렇게 쓴다). 그 의미도 그대로다. JPQL의 IN :gridIds는 괄호 없이 쓴다.

3. 네이티브로 남긴 3건과 이유

PostgreSQL 전용 기능을 쓰는 것은 JPQL로 옮길 수 없거나 옮기면 성능 계약이 깨질 수 있어 그대로 뒀다.

aggregateOccupiedInRange행정 단위 집계. 문자열 자르기 split_part, 좌표 함수 ST_Y, 출력 서수 GROUP BY 1.
findOccupiedPageAfter커서 이후 페이지. (grid_y, grid_x) > (:y, :x) 행 값 비교가 인덱스 하나로 범위 스캔하는 계약(MSG-90). JPQL로 풀면 OR 두 개가 되고 같은 계획이 보장되지 않는다.
findOccupiedByIntersects공간 조회. PostGIS ST_Intersects·ST_MakeEnvelope. 벤치마크 전용 경로.
"파생 쿼리와 연관관계 탐색만 쓰면 JPQL 문자열이 필요 없지 않나"도 있었다. 단정하지 않고 쟀다. 테스트 소스에만 실험용 리포지토리를 두고, 더미 데이터(격자 9만 · 점령 22,500 · 절반에 행정동 라벨)를 트랜잭션 안에 넣어 세 방식을 5회씩 돌린 중앙값이다. 끝나면 롤백된다.

B의 "N+1"은 배치 크기 100 설정 덕에 1 + N/100 + 1 문장으로 묶인다. 2,500칸에서 27문장·약 2배, 1만 칸에서 102문장·약 1.8배다. 장애급은 아니지만 행 수에 비례해 늘어난다. C는 문장이 1개로 돌아오지만 행마다 엔티티 2개(격자·점령)를 메모리에 올려 A보다 30~40% 느리다. 어느 크기에서도 B·C가 A를 이기는 구간은 없었다. JPQL 문자열을 없애는 값과 이 비용을 저울질하는 건 팀의 몫이다. 벤치마크: GridViewportFetchBenchmark (GRID_BENCHMARK=true, 규모는 GRID_BENCH_BLOCK).

4. 정말 같은지 어떻게 확인했나

"테스트 통과"만으로는 부족하다. 리팩터링의 약속은 DB에 가는 SQL이 같다는 것이라, 실제로 나간 SQL과 DB가 고른 실행 계획까지 전후로 대조했다.

Codex 리뷰 1라운드 결함 없음. 584(가독성 정리)가 먼저 머지돼 그 위로 다시 얹은 뒤에도 전체 3,059건 통과.

5. 부하 아래에서는 어떤가 — 실제 요청·실제 SQL·서버 지표

앱 안에서 잰 벤치마크는 "요청 하나"의 비용이다. 진짜 질문은 동시 사용자가 때릴 때 커넥션 풀과 응답 시간이 어떻게 되느냐라서, 실제 엔드포인트(GET /api/grids, 첫 페이지)에 같은 부하를 세 방식으로 넣고 세 층을 같이 봤다. 방식은 앱 재기동으로만 바꿨고(임시 속성 fillmap.grid.viewport-fetch), 코드·데이터·부하는 같다.

  • 데이터: 로컬 DB에 격자 9만 건(서울 30km×30km 블록, 실제 행정동 4,431개 경계로 라벨)·벤치 사용자 점령 22,500건을 커밋해 넣고 VACUUM ANALYZE. 측정 후 삭제.
  • 부하: k6, 50×50 뷰포트 50 req/s 60초 → 100×100 뷰포트 30 req/s 60초. 요청당 약 650칸·2,560칸.
  • 관측: 앱 actuator(HTTP p95·HikariCP) + postgres-exporter(DB tuples/s)를 Prometheus가 5초마다 수집. DB 로그로 요청 하나의 실제 SQL도 잡았다.

"요청당 DB 문장"은 DB 로그로 요청 하나를 잡아 센 값이다(zones 1문장 포함). lazy 100×100은 점령 1 + 격자 배치 26 + 행정동 배치 25 + zones 1 = 53. 실패율은 전 구간 0%, 커넥션 대기(pending)도 0이었다.

읽는 법. 벤치마크에서 2배 차이 났던 lazy가 부하 아래에서는 projection과 같다. 추가 문장 51개가 전부 PK 조회(각 0.1~0.5ms)이고 DB가 같은 머신이라 왕복 비용이 거의 0이기 때문이다. 즉 이 레포의 "N+1"은 문장 수 문제가 아니라 왕복 지연 문제다. DB가 다른 호스트(RDS, 왕복 1ms 안팎)면 51문장 × 1ms가 그대로 얹힌다. 그 조건은 아직 안 쟀다. graph가 가장 빠른 것도 이 환경에서만 확실한 사실이고, 앱 안 벤치와 순서가 뒤집힌 이유(JIT·응답 직렬화 비중)는 추가 반복 없이는 추측이다.

재현: load-test/k6/viewport-fetch-benchmark.js, 관측 스택 monitoring/docker-compose.yml. Grafana(익명 뷰어)는 Explore 권한이 없어 관리자 로그인 뒤 같은 PromQL(histogram_quantile(0.95, sum(rate(http_server_requests_seconds_bucket{uri="/api/grids"}[15s])) by (le)))로 보면 된다.

6. 더 빠르게 할 수 있나 — 인덱스 설계 네 가지를 재 봤다

커버링 인덱스, 드라이빙 테이블, 정렬 회피, 불필요한 조인 제거를 하나씩 적용해 쟀다. 앞선 실측의 시드는 사용자 한 명이 점령을 전부 갖는 비현실적 분포라 조인 방향 판단이 왜곡됐다. 여기서는 사용자 200명이 성글게 점령한 상태로 다시 만들었다. 격자 9만, 일반 사용자 224칸 보유(뷰포트에서 24건 반환), 헤비 사용자 5,199칸(576건).

  • 커버링 인덱스 (INCLUDE로 조회 컬럼을 인덱스에 담기): 버퍼는 25~70% 줄지만 시간은 10~15%다. PostgreSQL의 인덱스 전용 스캔은 가시성 맵에 기대서 VACUUM이 늦으면 힙을 다시 읽는다. 인덱스 두 개 9.6MB를 쓸 값어치는 애매하다.
  • 드라이빙 테이블: 손댈 것이 없다. 일반 사용자는 점령 목록에서 출발하고(224행 훑어 24건), 헤비 사용자는 격자 범위에서 출발하도록 플래너가 알아서 뒤집는다.
  • 행정동 조인 제거(앱이 이름 사전을 들고 있다고 가정): 0.409 대 0.394ms로 차이 없음. 이미 기본키 조회 + 결과 재사용이라 공짜다. 캐시를 넣으면 정합성 부담만 는다. 기각.
  • 정렬 회피가 진짜 문제다. 첫 페이지는 점령 목록이 격자 id(문자열) 순서라 좌표 정렬이 인덱스로 안 나온다. 헤비 사용자가 101건을 채우려고 격자 1,736개를 훑어 5,410버퍼를 쓴다.
근본 원인 한 줄. 격자 id는 "{y}_{x}"라 좌표를 이미 담고 있는데 문자열이라 범위 조건에 못 쓴다. 그래서 "내 격자를 전부 꺼내 좌표를 보고 화면 밖을 버리는" 모양이 된다. 점령 테이블에 좌표를 비정규화하고 (사용자, y, x) 인덱스를 걸면 그 24건만 읽고 정렬도 공짜가 된다 — 범위 조회 10배, 첫 페이지 25배, 버퍼 40~60배.

그래서 하느냐 — 안 한다. 배수는 진짜지만 절약분은 0.4ms이고 이 API의 요청 시간은 24~68ms다. 쿼리는 요청의 2% 미만이라 0으로 만들어도 체감이 없다. 게다가 전날 부하 실측에서 DB 문장 2개와 53개의 p95가 같았다 — 왕복 51번이 못 움직인 지표를 0.4ms가 움직일 수 없고, 비정규화는 왕복 횟수를 줄이지도 못한다(지금도 1문장, 바꿔도 1문장). 결정적으로 비용이 성능이 아니라 정합성이다. 격자의 행정동 라벨은 가변이라(이미 두 번 정책이 바뀌었다) 복제하면 동기화 누락이 곧 화면의 잘못된 동 이름이 된다. 정렬 문제는 구조적 차이라 인정하지만, 아프려면 한 사용자가 한 화면에 수천 칸을 점령해야 하고 그런 사용자는 없다. 다시 꺼낼 조건은 상위 사용자의 점령 수가 수천을 넘을 때이고, 그때도 좌표 두 개만 복제하고 행정동은 조인을 유지하는 절반안으로 간다(미실측).
