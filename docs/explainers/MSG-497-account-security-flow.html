FillMap BE · Explainer · MSG-497

비밀번호 재설정이 장애 중에도 안전한 이유

행사 운영자 계정 보안(MSG-497)에서 알아둬야 할 흐름 4개와 쿼리 1개. 각 단계의 위치가 장애 시나리오 하나씩을 막는 자리다 — Codex 리뷰 7라운드(스펙 4 + 구현 3)가 이 순서를 만들었다.

1reset 확정의 순서 계약

sequenceDiagram
    autonumber
    participant C as 사용자(링크 클릭)
    participant S as PasswordService
    participant R as Redis
    participant DB as PostgreSQL
    C->>S: POST /api/auth/password/reset (토큰+새 비밀번호)
    S->>R: ① consume(토큰) — Lua getAndDelete 선점
    Note over S,R: 실패(무효/만료/재사용) = 전부 같은 2443
    S->>DB: ② TX 시작: 해시 저장 + mustChange 해제
    S->>R: ③ TX 안: 무효화 기록 set (blacklist:user, TTL 2주)
    Note over S,R: ③ 실패 → TX 롤백 + 토큰 조건부 복원(fail-closed)
    S->>DB: ④ 커밋
    S-->>R: ⑤ best-effort: 기록 한 번 더 갱신 + 세션 전량 삭제
    Note over S,R: ⑤ 실패해도 200 — 기록 2주가 옛 리프레시를 막는다
    S->>C: 200 성공
  1. 선점이 맨 앞같은 토큰 동시 요청 둘 중 하나만 통과(원자적 getAndDelete). 이후 실패하면 catch에서 조건부 복원 — 그 사이 재요청으로 새 링크가 발급됐으면 복원하지 않는다(무조건 복원이면 방금 메일로 간 새 링크를 죽인다).
  2. 무효화 기록이 커밋 전커밋 뒤에 찍으면 Redis 장애 순간 "비밀번호는 바뀌었는데 옛 토큰 전부 생존"이 된다. 커밋 전이면 Redis 장애 = 롤백 + 링크 복원 = 비밀번호 불변. fail-closed 반대 경합(기록 성공 후 커밋 실패)은 세션만 끊기고 비밀번호는 유지 — 보안 구멍이 아니라 재로그인 불편.
  3. 커밋 후 기록을 한 번 더첫 기록과 커밋 사이 수 ms에 구 비밀번호 로그인이 끼면 그 토큰의 iat가 첫 기록보다 늦어 살아남는다. 두 번째 기록이 경계를 커밋 시점까지 민다. 이것까지 실패하는 이중 장애 시에만 그 창의 토큰이 최대 1시간 생존(수용, 스펙 결정 기록 6).
  4. 세션 삭제는 best-effortdeleteAll이 실패해도 200. 무효화 기록이 리프레시 수명(2주)만큼 살아 있어 옛 리프레시의 재발급이 전부 거부된다. 여기서 500을 내면 "비밀번호는 바뀌었는데 재시도는 불가"한 거짓 실패가 된다.

2액세스 토큰 무효화 — iat 비교와 "저장 후 검사"

액세스 토큰은 stateless라 회수가 안 된다. 대신 blacklist:user:{userId}에 무효화 시각 하나를 두고 파싱 때 토큰 iat와 비교한다.

  • 같은 초는 거부 (iat <= 무효화 초) — JWT iat가 초 단위라 같은 초를 열어두면 그 1초가 구멍이다. 재설정 흐름에 자동 로그인이 없어 정상 재로그인이 같은 초에 걸릴 일은 사실상 없고, 걸려도 재시도로 풀린다. fail-closed
  • 검사 스코프는 ORG·ADMIN 토큰만 — reset 발송 대상 자체가 ORG·ADMIN LOCAL 계정으로 축소돼 있어(FR-22가 행사 운영자 요구), 재설정했는데 검사 밖인 토큰이 구조적으로 없다. 전 사용자 검사(매 요청 Redis GET 추가)를 피한 이유.
  • 재발급(reissue)은 회전 save를 먼저, 검사를 나중에 — 순서가 반대면 "검사 통과 → reset의 deleteAll → 회전 save" 인터리빙으로 세션이 부활한다. 저장 후 검사면: save가 deleteAll보다 앞이면 deleteAll이 지우고, 뒤면 더 앞선 무효화 기록이 반드시 보인다. 어느 쪽이든 잡힌다.
기록 TTL이 액세스 수명(1h)이 아니라 리프레시 수명(2주)인 이유 — deleteAll이 부분 실패했을 때 살아남은 리프레시가 기록 만료 후 부활하는 구멍을 막는다(구현 Codex 리뷰가 적발한 P1).

3알아야 할 쿼리 — 부분 유니크 UPSERT

아이디(공식 이메일) 변경 요청 접수. "마지막 요청이 유효"(오타 정정 재요청 허용) 정책을 문장 하나로 원자화한다.

INSERT INTO org_email_change_requests (user_id, requested_email, status, created_at)
VALUES (:userId, :email, 'PENDING', :now)
ON CONFLICT (user_id) WHERE status = 'PENDING'
DO UPDATE SET requested_email = EXCLUDED.requested_email, created_at = EXCLUDED.created_at
  • ON CONFLICT (user_id) WHERE status = 'PENDING' — 충돌 대상이 부분 유니크 인덱스라 추론 절에 인덱스와 같은 WHERE를 적어야 PostgreSQL이 인덱스를 특정한다.
  • "조회 후 INSERT" 두 문장이면 동시 요청 둘이 부분 유니크 위반 500 race — 그래서 native로 갔다(PG 전용 기능이라 컨벤션 허용 대상, OrgEmailChangeRequestRepository.upsertPending).
  • 처리된(APPROVED 등) 과거 행은 부분 인덱스 밖이라 이력으로 쌓인다 — 사용자당 PENDING만 1건 강제.

재설정 토큰의 Redis Lua 3종(save/consume/revoke)도 같은 목적의 원자화다. 포인트 하나만: consume의 역방향 키 삭제는 compare-and-delete(소비한 그 해시일 때만) — 아니면 동시 재요청으로 발급된 새 링크의 포인터를 지워 "폐기 불가 링크"가 남는다. 실패 복원(restore)도 같은 이유로 조건부다.

후속 티켓 규칙(MSG-496에서 확정): catch-all이 hasAnyRole("USER","ADMIN")라 ORG가 쓸 새 경로는 SecurityConfig 명시 등록 필수 — 누락은 403으로 드러난다(fail-closed). /api/org/**에 등록하면 mustChange 게이트 인터셉터도 자동으로 걸린다.
