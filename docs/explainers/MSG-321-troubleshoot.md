# MSG-321 핫구역 조회 부하 측정 트러블슈팅

`GET /api/hotzones` 부하 측정에서 나온 문제 세 가지를 증상, 가설, 검증, 결론, 해결 순으로 정리했다.
측정 서술과 그래프가 들어간 정본은 [`docs/explainers/MSG-321-hotzone-load-test.html`](MSG-321-hotzone-load-test.html)이고,
이 문서는 같은 측정을 문제 단위로 다시 접은 요약이다.

측정일 2026-08-06. 로컬 macOS(Apple Silicon)에서 앱, Redis(`redis:7-alpine`), k6 v2.1.0을 한 기계에 띄우고 쟀다.
시드는 좌표 표본 100,000개로 만든 고유 격자 46,697개다.

> **절대 수치를 옮겨 쓰지 말 것.** 노트북 한 대에서 부하 도구와 앱과 Redis가 CPU를 나눠 쓴 값이라
> 서버를 대표하지 않는다. 근거가 되는 건 같은 환경 안에서의 상대 비교다.

## 문제 1. 30초마다 반복되는 꼬리 지연

| 단계 | 내용 |
|---|---|
| **증상** | 200 RPS로 3분 걸었을 때 전체는 평범하다(중앙값 1.77ms, p99 3.37ms). 그런데 가장 느린 요청이 108ms였고, Prometheus의 p99.9가 **30초 간격으로 20~90ms를 오르내린다**. 30초는 핫구역 목록 캐시의 수명과 같다.<br>사용자 입장에서는 지도 홈의 핫구역 칩을 누른 1,000명 중 한 명꼴로 응답이 수십 ms 늦다. 실패 응답은 전 구간 0건이라 눈에 띄는 오류로는 나타나지 않는다. |
| **가설** | 1) **캐시 스탬피드.** 캐시가 비는 순간 여러 요청이 같은 합산을 중복 실행해 서로를 막는다 (문서 첫 판이 채택했던 설명, 가장 유력하다고 봤다)<br>2) GC나 스케줄링 같은 캐시와 무관한 단발 정지<br>3) 부하 자체. 동시성이 올라가서 밀리는 것<br>4) **head-of-line 지연.** 중복은 없고 재계산 한 번이 Redis를 오래 붙잡는 것 |
| **검증** | **(a) 주기로 접기** `analyze-expiry.py`가 측정 시각을 캐시 수명 30초로 나눈 나머지로 요청을 묶는다. 캐시가 원인이면 특정 위상에만 느린 요청이 몰린다.<br>`k6 run -e SCENARIO=expiry -e RATE=200 -e DURATION=3m --out json=result.json load-test/k6/hotzone-benchmark.js`<br>`./load-test/analyze-expiry.py result.json`<br><br>결과: 만료 위상(0초) 요청 1,200건의 p99가 **56.18ms**, 나머지 위상은 **3.22ms**. 중앙값은 양쪽 다 1.8ms로 같다. 갈리는 건 꼬리뿐이다.<br><br>**(b) 배율 하나로 결론 내지 않기** 가장 느린 위상을 골라 나머지와 비교하면 가설 2에도 큰 배율이 나온다. 실제로 24,000건 중 80ms 지연 하나만 넣은 합성 데이터에서 27배가 나왔다. 그래서 분석기가 배율과 함께 **주기마다 같은 위상이 반복되는지(재현율)** 를 본다. 위 합성 데이터는 재현율 25%로 걸러졌고, 30초마다 지연을 넣은 합성 데이터는 100%로 통과했다. 실측은 여섯 주기 중 네 번(67%).<br><br>**(c) 재계산 횟수를 직접 세기** (a)는 상관만 보여주므로 원인을 따로 증명해야 한다.<br>`docker exec fillmap-local-redis redis-cli INFO commandstats \| grep zunionstore`<br><br>• `EVALSHA` **36,000회** (요청 수와 동일)<br>• `ZUNIONSTORE` **6회** (180초 ÷ TTL 30초와 정확히 일치)<br>• 같은 통계에서 합산 1회 평균 **44.97ms**<br><br>**(d) 규모 감도** `./load-test/measure-zunionstore.sh` 로 앱을 거치지 않고 Redis만 잰다. 빈 스크립트를 같은 방식으로 재서 `docker exec` 왕복 고정비를 빼고 3회 중앙값을 쓴다. 고유 격자별 합산 비용(괄호는 운영 스크립트 전체):<br><br>• 946개 → **0.311ms** (0.388ms)<br>• 8,741개 → **3.461ms** (3.170ms)<br>• 46,697개 → **30.039ms** (29.407ms)<br><br>**(e) 한계 처리량** `k6 run -e SCENARIO=cap` 으로 100에서 2,000 RPS까지 올리고 마지막 2,000을 60초 유지했다. 총 213,998건, 실패 0건. 유지 구간 실측 1,999 RPS에 중앙값 0.75ms. **모든 구간에서 최대값이 40~60ms대로 같았다.** |
| **결론** | **캐시 스탬피드가 아니다.** 재계산 코드는 `EXISTS` 확인부터 `ZUNIONSTORE`, `EXPIRE`까지가 Lua 스크립트 하나에 들어 있고 Redis는 이걸 원자 실행한다. 첫 요청이 합산하는 동안 뒤따르는 요청은 스크립트를 시작조차 못 하고, 자기 차례가 오면 `EXISTS`가 이미 1이라 합산을 건너뛴다. 순서를 강제하는 장치가 이미 있는 셈이라 중복 재계산은 구조적으로 일어나지 않는다. 근거는 (c)의 36,000 대 6이다.<br><br>**실제 원인은 재계산 1회(44.97ms)가 Redis를 붙잡는 동안 뒤에 요청이 줄 서는 head-of-line 지연이다.** 200 RPS면 그 45ms에 아홉 건쯤 쌓이고 차례로 풀리면서 각자 최대 45ms를 기다린다.<br><br>보조 근거 두 가지. (e)에서 최대값이 부하와 무관하게 유지된 것은 원인이 부하가 아니라 주기적 재계산이라는 방증이다. 부하가 원인이면 부하를 따라 커져야 한다. (d)에서 비용이 격자 수에 거의 비례하므로 이 현상의 크기는 데이터 양이 정한다.<br><br>**가설 2 기각 근거**는 재현율 67%다. 단발 정지라면 특정 위상에 반복해서 몰리지 않는다.<br><br>**caveat.** (d)의 30ms와 (c)의 45ms가 다른 건 전자가 연속 100회 실행이라 CPU 캐시가 데워진 값이기 때문이다. 운영에서 겪는 값은 45ms 쪽에 가깝다. 그리고 "현재 운영 격자 수는 수천 단위"는 **실제로 세어 본 값이 아니라 추정**이다. 판단의 전제이므로 배포 후 확인이 필요하다. |
| **해결** | **지금은 고치지 않는다.** 현재 규모에서 재계산은 1ms 아래고 그 규모에서는 만료 순간의 지연이 관측되지 않는다. 막을 것이 없는 상태에서 장치를 넣으면 코드만 복잡해진다.<br><br>설계 문서(MSG-233 §D4)의 "락 불요"는 결과적으로 옳지만 이유가 다르다. 문서는 "동시에 재계산해도 결과가 같아서"라고 적었는데 실제로는 **애초에 동시 재계산이 일어나지 않아서**다.<br><br>그래서 다시 볼 때 손댈 곳은 잠금이 아니라 재계산이 Redis를 붙잡는 시간이다. 선택지와 대가는 이렇다.<br><br>• **합산 대상 줄이기**(직전 결과에 새 버킷만 반영): 가장 직접적. 만료 버킷 제거 처리가 늘어난다<br>• **확률적 조기 갱신**: 구현이 가볍지만 지연 크기는 그대로고 시점만 흩어진다<br>• **TTL 늘리기**: 가장 싸다. 목록 갱신이 그만큼 늦어진다<br>• **재계산 잠금**: 이미 그렇게 동작하므로 의미 없다<br><br>**재검토 트리거**: 고유 격자가 만 단위에 접근하거나, 만료 위상 배율을 다시 재서 크게 나올 때. 그래서 재현 도구를 `load-test/` 에 남겼다. |

## 문제 2. 대기열이 넘칠 때 남기는 경고 로그가 업로드 응답을 붙잡는다

| 단계 | 내용 |
|---|---|
| **증상** | 집계 워커(스레드 1개, 대기열 1만 칸)에 버스트를 넣어 포화시키면 **적재 속도가 초당 339,189건에서 16,211건으로 떨어진다.** 21분의 1이다.<br>사용자 입장에서는 업로드가 몰리는 순간 업로드 응답 자체가 늦어진다. 워커를 별도 스레드로 뺀 이유가 "Redis가 느려도 업로드 응답은 안 늦어지게"였는데 그 보호가 정작 포화 상황에서 깨진다. |
| **가설** | 1) 워커 스레드가 하나뿐이라 소비가 못 따라간다 (코드 주석에도 "밀리면 스레드 수를 늘린다"는 메모만 있었다)<br>2) Redis 왕복 비용<br>3) **폐기 경로의 로깅.** 큐가 찰 때마다 예외 스택 추적을 통째로 경고 로그에 남긴다 |
| **검증** | 포화 실험을 **로그를 끈 것과 켠 것으로 나눠** 돌렸다. 변수를 로깅 하나로 좁히기 위해서다.<br>`HOTZONE_BENCH=true ./gradlew test --tests '*HotScoreThroughputBenchmark'`<br><br>• **로그 끔**(워커 자체 한계), 버스트 60,000건 → 적재 **339,189건/초**, 유실 81.8%<br>• **로그 켬**(운영 조건), 버스트 20,000건 → 적재 **16,211건/초**, 유실 23.4%<br><br>정상 상태 기준값도 같이 쟀다. 워커 처리율 5,072건/초, 업로드 응답에 얹히는 적재 비용 건당 0.0015ms, 대기열이 버티는 버스트 약 2초. |
| **결론** | **원인은 3) 로깅이다.** 폐기 한 건당 0.26ms가 드는데 정상 적재가 0.0015ms이니 **170배**다.<br><br>유실률만 보면 로그를 켠 쪽이 23.4%로 나아 보이지만 착시다. 유입 속도가 21분의 1로 떨어져서 그만큼 덜 버린 것뿐이다.<br><br>문제가 되는 지점은 비용 자체보다 **어느 스레드에서 일어나는가**다. 이 로깅은 호출한 스레드에서 일어나고, 신호를 넣는 `recordUpload`는 업로드 트랜잭션이 커밋된 뒤 **요청 스레드**에서 호출된다. 즉 대기열이 넘치는 순간 업로드 응답이 로그 쓰기에 붙잡힌다. 게다가 로그가 쏟아지는 시점은 이미 시스템이 밀리고 있는 시점이라 상황을 더 나쁘게 만든다.<br><br>가설 1은 기각이 아니라 별개다. 워커 한계는 초당 5,000건 언저리로 실재하지만, 21분의 1로 떨어뜨린 건 그것이 아니라 로깅이다.<br><br>유실 자체는 버그가 아니다. 핫구역 점수는 근사값이고 신호 몇 건이 빠져도 순위가 뒤집히지 않는다는 전제로 설계됐다. 이번 측정으로 **그 전제가 성립하는 범위가 숫자로 확인됐다.** |
| **해결** | 대기열이 가득 찼다는 건 예외적 사고가 아니라 설계가 예상한 흐름이다. 예상한 흐름에 스택 추적을 남길 이유가 없다. 스택 추적을 빼고 카운터 메트릭으로 바꾼다.<br>MSG-321 범위 밖이라 **MSG-330**으로 분리했다. |

## 문제 3. 서버 쪽 백분위를 계산할 재료가 없었다

| 단계 | 내용 |
|---|---|
| **증상** | 측정을 시작했는데 서버 쪽 p99를 볼 수 없었다. Micrometer가 기본으로 내보내는 건 요청 수와 합계와 최대값뿐이다.<br>측정자 입장에서 k6가 보는 클라이언트 지연과 서버가 보는 지연을 대조할 방법이 없다. |
| **가설** | 원인 자체는 자명해서 가설을 세울 것이 없었다. 선택지가 둘이었다.<br>1) `percentiles-histogram: true` 를 켠다<br>2) `distribution.slo` 로 필요한 경계만 직접 준다 |
| **검증** | 1)은 미리 정의된 버킷 수십 개를 만들어 시계열이 한 자리 수 배로 늘어난다. 2)로 가면 17개로 끝난다.<br>측정 중에 `application.yml` 에 넣은 값은 이렇다.<br><pre>management:<br>  metrics:<br>    distribution:<br>      slo:<br>        http.server.requests: 1ms,2ms,3ms,5ms,8ms,10ms,15ms,25ms,50ms,75ms,<br>          100ms,150ms,200ms,300ms,500ms,800ms,1s</pre>경계는 실측에 맞춰 골랐다. 평시가 1ms 언저리라 아래쪽을 촘촘하게 두고, 만료 시점의 지연이 어느 칸에 떨어지는지 보이도록 100~300ms를 남겼다. 300ms와 800ms는 MSG-134가 정한 응답 목표선(p95 300ms, p99 800ms)이라 경계로 넣었다. 경계가 없으면 목표 준수 여부가 구간 보간에 좌우된다. |
| **결론** | 기본 Timer로는 백분위를 못 낸다. 버킷 경계를 직접 주면 낼 수 있다.<br><br>**비용을 같이 적어 둔다.** 이 설정은 `http.server.requests` 전체에 걸리고 엔드포인트별로 좁혀지지 않는다. Prometheus에는 `+Inf`가 더해져 URI, 메서드, 상태, 결과 조합마다 시계열이 18개씩 생긴다. 지금 API 수에서는 감당 가능하다고 보고 켰다. |
| **해결** | 위 `slo` 설정을 유지한다. API가 늘어 시계열이 부담스러워지면 그때 대상을 좁힌다. |

## 교훈

**주기 분석은 상관만 보여준다. 원인은 따로 세어야 한다.** 만료 시점에 지연이 몰린다는 것과
재계산이 원인이라는 것은 다른 명제다. 이 측정에서 둘을 잇는 유일한 증거는 `INFO commandstats`로
직접 센 `ZUNIONSTORE` 6회였고, 그걸 세기 전까지 문서는 캐시 스탬피드라는 틀린 설명을 달고 있었다.
정정은 Codex 교차 리뷰 지적에서 나왔다.

원인을 잘못 잡으면 고칠 대상도 달라진다. 중복이 문제였다면 잠금을 넣으면 됐겠지만,
실제로는 잠금이 이미 있으므로 손댈 곳은 재계산 자체의 비용이다.

```bash

./load-test/measure-zunionstore.sh

  --out json=result.json load-test/k6/hotzone-benchmark.js

# 4. 캐시 수명 주기로 접어 본다
./load-test/analyze-expiry.py result.json

# 5. 재계산이 실제로 몇 번 돌았는지 확인한다 (만료 횟수와 같아야 정상)
```
