# MSG-347: 격자 계산 규칙을 위경도 근사에서 EPSG:5179 미터 좌표계로 전환 (BE)

**Owner**: 공동 (주도 A)

핵심 코드 변경(`com.msg.fillmap.grid.*`)과 zone 재산출, FE 픽스처는 Owner A 몫이다. 다만 데이터
이행이 videos와 user_grids라는 Owner B 도메인 데이터의 의미(방문, 점령)를 재구성하고, 격자 ID를
하드코딩한 테스트 기대값 갱신이 A와 B 패키지 양쪽에 걸치므로 공동으로 판정한다. 계약 인터페이스의
시그니처 변경은 없다(아래 "계약 변경" 참조).

## 개요

격자 판정을 위경도 등간격 근사(0.0009°, 0.00115°)에서 EPSG:5179[^1] 미터 평면 좌표 기반으로
바꾼다. 위경도를 5179로 변환한 뒤 100으로 나누는 floor 연산이 새 규칙이다. `GridEncoder`와
`GridConstants`의 내부만 교체하고 시그니처는 유지하며, 기존 저장 데이터는 Flyway 마이그레이션
1회(V28)로 전량 이행한다. 서버와 프론트는 같은 proj4 정의 문자열[^2]을 계약으로 공유한다.

## 배경 · 목표

현행 격자는 셀의 동서 폭이 서울 약 101.6m, 부산 약 104.7m로 지역마다 다르다. 전국 어디서나
정확한 100m × 100m 셀 위에서 점령과 방문이 판정되고, 프론트가 그리는 격자와 서버가 판정하는
격자가 항상 일치하게 하는 것이 목표다. grid_id 포맷("y_x" 문자열, VARCHAR(20))과 기존 API
계약은 그대로 두고 값만 새 체계로 바뀐다.

## 성공 기준

- 같은 위경도 입력에 대해 서버(Proj4J[^3])와 프론트(proj4js)가 같은 gridId를 계산한다.
  전국 분산 샘플 200건 픽스처의 교차 검증이 전부 일치하면 달성이다 (PRD 목표).
- 셀 한 변이 전국 어디서나 100m다(투영 오차 수준 제외). 서울, 부산, 제주 표본에서 변 길이
  실측 테스트가 통과한다.
- V28 이행 후 영상 유실 0건: 이행 전후 videos 행 수가 같고, 각 영상의 새 grid_id가 원본
  좌표(videos.geom)에서 Proj4J로 재계산한 값과 전수 일치한다.
- 기존 API의 경로, 파라미터, 응답 구조가 바뀌지 않는다 (FR-10). 격자 ID를 하드코딩한 테스트
  전반의 기대값 갱신 후 전체 테스트가 green이다.

## API 명세

**변경 없음** (FR-10). 기존 엔드포인트의 경로, 파라미터, RequestDto/ResponseDto 구조를 전부
유지한다. 바뀌는 것은 값뿐이다:

- `gridId`, `gridY`, `gridX` 필드 값이 새 체계 값이 된다. 예를 들어 서울 격자의 gridY는
  구 체계 약 41000대에서 새 체계 약 19000대로 바뀐다(5179 northing을 100으로 나눈 값).
- `zoneName`, `zoneCell`(격자 표시명)은 재산출된 zone 사각형 기준으로 계산된다. 명명 규칙
  자체("{zone명} {행}-{열}", 행은 북단부터 A, 열은 서단부터 1)는 불변이다 (FR-8).
- 에러 케이스 신설 없음. FR-13(서비스 범위 밖 좌표 업로드 거부)은 기존
  `INVALID_COORDINATE(3400)` 응답이 이미 담당한다 (아래 "서비스 범위 검증" 절의 실측 정정).

## 도메인 로직

### 새 격자 계산 규칙 (FR-1, FR-2, FR-3)

glossary "격자 계산 규칙" 항목이 이 티켓으로 개정된다. 새 규칙:

1. 위경도(WGS84, EPSG:4326)를 EPSG:5179 미터 좌표 (x, y)로 변환한다.
2. `gridX = floor(x / 100)`, `gridY = floor(y / 100)`. 경계는 현행과 같은 반열림 구간[^4]
   `[n·100, (n+1)·100)`이라 경계선 위 좌표는 정확히 한 셀에만 속한다.
3. `grid_id = "{gridY}_{gridX}"` 문자열. 포맷과 VARCHAR(20) 스키마는 현행 유지다.

좌표 변환의 계약은 다음 proj4 정의 문자열 하나다. BE(Proj4J)와 FE(proj4js)가 이 문자열을
글자 단위로 똑같이 사용해야 경계 근처 셀이 어긋나지 않는다:

```text
+proj=tmerc +lat_0=38 +lon_0=127.5 +k=0.9996 +x_0=1000000 +y_0=2000000 +ellps=GRS80 +towgs84=0,0,0,0,0,0,0 +units=m +no_defs
```

### GridConstants 변경

`GRID_LAT_STEP`, `GRID_LNG_STEP`을 제거하고 다음으로 교체한다:

- `CELL_SIZE_METERS = 100`
- `CRS_DEF_EPSG5179`: 위 계약 문자열. FE와 마이그레이션 SQL이 같은 문자열을 쓰는 단일
  진실 원천이다.

### GridEncoder 변경 (시그니처 유지, 내부 교체)

네 메서드의 시그니처와 반환 타입(GridIndex, GridPoint, 닫힌 링 List)은 그대로 두고 내부만
바꾼다. grid_id를 불투명 문자열로 다루는 호출부 약 30개 파일은 무수정이다.

- `encode(lat, lon)`: 4326 → 5179 변환 후 floor. Proj4J CRS 객체는 `CRSFactory`가 계약
  문자열로 생성한다(정본은 문자열이고, `proj4j-epsg` 아티팩트의 EPSG:5179 정의는 참조와
  검증용이다). 변환 객체 재사용 여부는 Proj4J의 스레드 안전성 문서를 확인해 정하되,
  `ProjCoordinate`는 호출마다 새로 만든다.
- `decode(gridId)`: 문자열 파싱이라 사실상 무변경.
- `center(gridId)`: 5179 셀 중심 `((gridX + 0.5)·100, (gridY + 0.5)·100)`을 4326으로
  역변환해 반환.
- `bbox(gridId)`: 5179 셀 꼭짓점 4점을 각각 4326으로 역변환한다. 새 셀은 위경도 평면에서
  자오선 수렴[^5] 때문에 위경도 축과 평행하지 않으므로 꼭짓점 4점이 모두 의미 있는 값이다
  (FR-4). 반환 형식은 현행과 같은 닫힌 링 5점(남서, 남동, 북동, 북서, 남서)을 유지한다.
  유일한 소비자 `GeoSupport.bboxWkt`는 링을 그대로 WKT로 직렬화하므로 무수정이다.

### 뷰포트 범위 산출 변경: "호출부 무수정"의 유일한 예외

현행 코드 3곳이 뷰포트의 SW, NE 2점만 encode해서 격자 인덱스 min/max 범위를 잡는다
(`GridQueryServiceImpl` 78~79행과 98~99행, `HotZoneServiceImpl` 80~81행). 위경도 등간격
체계에서는 위도 증가가 곧 gridY 증가라 2점으로 충분했지만, 5179에서는 격자 축이 위경도 축과
평행하지 않아 2점만으로는 뷰포트 가장자리 셀이 범위에서 빠질 수 있다.

**결정**: 뷰포트 꼭짓점 4점을 모두 5179로 변환해 x, y 각각의 min/max로 인덱스 범위를 잡는다.
한국 범위의 횡축 메르카토르에서 변환은 국소적으로 거의 선형이라 꼭짓점 4점의 min/max가
뷰포트를 완전히 덮는 보수적 범위가 된다(화면 밖 셀이 소량 더 잡힐 수 있으나 무해하다).
중복 구현을 피해 `GridEncoder`에 뷰포트 범위 헬퍼 메서드를 하나 신설하고 3곳이 그것을
호출하게 한다. 3곳 모두 Owner A 패키지(grid, hotzone)라 계약 경계를 넘지 않는다.

### 서비스 범위 검증 (FR-13, 2026-08-08 신설)

EPSG:5179는 한국 한정 투영이라 원거리 좌표(예: 유럽에서 찍힌 갤러리 영상)는 변환이 발산해
NaN이나 VARCHAR(20)을 넘는 비정상 grid_id를 만들 수 있다. Codex 교차 리뷰 지적으로 PRD
비목표를 뒤집어 검증을 신설한다 (사용자 확정, PRD FR-13).

- **실측 정정 (2026-08-08, 리뷰어 발견)**: 이 검증은 MSG-193에서 이미 구현돼 있었다.
  `global/geo/KoreaCoordinates`(A/B 공용 순수 상수, 위도 [33.0, 39.0], 경도 [124.0, 132.0],
  닫힌 구간, javadoc이 "서비스 범위가 바뀌면 이 한 곳만 고친다"로 단일 정본을 명시)와
  `VideoErrorCode.INVALID_COORDINATE(3400)`가 있고, VideoServiceImpl이 업로드 확정과 좌표
  교체 두 쓰기 경로에서 이미 검증한다(기존 테스트 2건). 따라서 범위 상수를 GridConstants에
  두지 않고(정본 이중화 금지, 당초 서술 정정) 에러코드도 신설하지 않는다. GridEncoder는
  검증 없는 순수 함수로 남긴다.
- 이 티켓의 신규 몫 세 가지: V28 사전 검사(아래), 경계값 테스트 1건, 기존 구현이 FR-13을
  충족한다는 확인. 미션 시더(Festival)의 좌표 검증 부재는 시딩 off 상태라 이 티켓 스코프가
  아니고, 미션 재개 시점 이연 항목에 편입한다.
- 조회 경로(뷰포트)는 검증하지 않는다. 범위 밖 뷰포트는 빈 결과로 무해하고 현행 동작을 유지한다.
- V28 사전 검사: 이행 시작 전에 허용 범위 밖 `videos.geom` 행이 있으면 행 id를 포함해
  RAISE EXCEPTION으로 중단한다. 범위 밖 기존 데이터는 자동 변환 대상이 아니라 수동 결정
  대상이다. SQL에서는 상수 참조가 불가하므로 KoreaCoordinates와 같은 값을 리터럴로 쓰고
  출처를 주석으로 남긴다.
- 테스트: 범위 밖 거부는 기존 테스트 2건이 이미 덮는다. `경계값_좌표는_허용된다`(위도
  33.0과 39.0, 경도 124.0과 132.0 정확값 허용)만 신설한다.

### 핫구역 (FR-11)

집계와 조회 로직은 gridId를 불투명 문자열로 다루므로 코드 무수정이다. 전환 이전에 쌓인 신호는
폐기한다. 6시간 버킷(`hotzone:{bucketId}`)은 48시간이면 자연 만료되지만, 캐시 키
`hotzone:top`은 TTL이 없어 영구 잔존하므로(`HotZoneServiceImpl` 41행 주석 실측) 자연 만료를
기다릴 수 없다. **배포 절차에 `hotzone:*` 키 전체 삭제를 포함한다** (아래 "운영 절차").

### zone과 표시명 (FR-8)

- `src/main/resources/seed/zones.json`: 확정 시드 48건의 사각형을 역산해 재산출한다 (사용자
  재확정 2026-08-08, 당초 "원천 파이프라인 재실행"에서 변경). 근거: 작도 산출물
  `scripts/zones-draft/`에 위경도 원본이 보존돼 있고(초안 zones-draft.json의 bbox_wgs84
  소수 5자리, 233건 전수 확인) 구 격자 인덱스는 위경도로 정확히 역산되므로, 검수 결정(합집합,
  경계 조정, 수동작도 31건)을 그대로 보존한 채 격자 번호만 새로 매길 수 있다. 절차: 구 인덱스를
  위경도 사각형으로 역산(min은 인덱스 x 구 STEP, max는 인덱스+1 x 구 STEP) → 꼭짓점 4점을
  EPSG:5179로 변환 → 각 변을 가장 가까운 셀 경계로 스냅해 재양자화(상한 배타). 당초 문구
  "min/max를 floor"는 구현 중 실측으로 정정됐다(2026-08-08): floor 방식은 변마다 1칸씩
  부풀려 맞닿은 이웃 zone 7쌍이 겹치고 validate-zones.py 게이트가 FAIL한다. 스냅 방식은
  겹침 0건, 크기 증감 0~+1칸이다. 역산 스크립트는
  `scripts/zones-draft/`에 신설해 커밋한다. 기존 파이프라인 스크립트는 이미 추적 중이고
  미추적은 `seed-to-geojson.py` 하나라 함께 커밋한다(변환 산출물 json은 재생성 가능하다는
  기존 .gitignore 정책을 유지해 계속 제외한다. 2026-08-08 실측 정정: 이전 서술 "스크립트
  일체 미추적"은 부정확했다). 검수는 `seed-to-geojson.py`로 신구 사각형을 geojson.io에 겹쳐
  확인한다. 새 셀은 남북이
  정확히 100m라 구 셀(약 100m)과 행 수가 거의 같아 26행 캡 CHECK 위반 가능성은 낮지만,
  재산출 결과가 캡을 넘으면 ZoneSeeder 시딩 실패로 드러나므로 시딩 1회 실행으로 확인한다.
  값 갱신은 기동 시 멱등[^6] UPSERT가 반영한다.
- `src/test/resources/fixtures/zone-naming.json`: **갱신 불요 (2026-08-08 실측 정정)**.
  픽스처의 zone 사각형이 실좌표가 아닌 합성 인덱스(1000, 2000대)이고 명명 규칙이 순수 인덱스
  산술이라 좌표계 전환과 무관하다. ZoneNamingContractTest는 무수정으로 green이다.

### FE 정합성 픽스처 (FR-9)

`src/test/resources/fixtures/grid-epsg5179-samples.json`(신규)에 전국 분산 샘플 200건을
담는다. 각 건은 입력 위경도, gridX, gridY, gridId, 셀 꼭짓점 위경도 4점이다. 샘플 좌표는
재현 가능하도록 결정적으로 뽑는다(고정 좌표 목록 또는 시드 고정). 생성 검증 테스트를 함께
두어 픽스처 각 건을 GridEncoder로 재계산해 전수 일치를 확인한다. FE는 프론트 작업 시점에
이 픽스처와 계약 문자열을 입력으로 proj4js 구현을 검증한다(FE 티켓 미발행 확정).

### 미션 시드 (스코프 주의)

"V25__*.sql" 표기는 작성 시점 스냅숏이라 낡았다(그 사이 V25~V27이 들어왔다). 레포 실측이
정본이므로 V28을 쓴다.

### 이행 절차 (FR-5, FR-6, FR-7)

원본 좌표는 `videos.geom`(GEOGRAPHY POINT 4326, NOT NULL)에 보존돼 있다. 모든 재계산이
원본에서 출발하므로 flyway clean 후 재실행해도 같은 결과로 수렴한다(멱등, 비기능 "운영" 충족).

**멱등의 한 가지 예외 (2026-08-08, Codex 리뷰 반영)**: clean 없이 같은 DB에서 본문을 두 번
돌리면 grids 행이 없는 mission_grids만 어긋난다. 2단계가 그 행의 grid_id를 구 규칙으로
파싱하는데, 이미 이행된 새 ID를 그렇게 읽으면 위경도 유효 범위 안의 엉뚱한 좌표가 나와
V28의 범위 가드에도 걸리지 않는다. 배포에서는 Flyway가 한 번만 실행하므로 영향이 없다.
본문을 재실행하는 이행 통합 테스트에는 이 차이를 주석으로 남기되 검사는 두지 않는다 — grids 행 없는
mission_grids는 lazy insert 설계상 정상 상태여서 그 존재를 실패로 규정하면 정상 데이터가 테스트를
막고, 미션은 테스트의 단언 대상도 new_grids 스냅숏도 아니라 판정에 영향이 없기 때문이다
(2026-08-08 Codex 후속 라운드 — 앞선 라운드를 과잉 수용해 넣었던 사전 단언을 철회).

SQL의 좌표 변환은 PostGIS `ST_Transform`[^7]에 **SRID 5179를 넘긴다**(GEOGRAPHY는 `::geometry`
캐스팅 후 변환). 대신 이행 시작 전에 `spatial_ref_sys`의 5179 정의가 계약 문자열과 같은지
확인하고, 다르면 `RAISE EXCEPTION`으로 이행을 중단한다.

(2026-08-09 정정 — 원안은 "spatial_ref_sys에 의존하지 않고 계약 문자열을 from/to 인자로 직접
전달"이었다. 그렇게 하면 PostGIS가 행마다 PROJ 파이프라인을 새로 만들어 변환 한 번에 0.85ms가
들고, dev 배포에서 이행이 수 분간 멈춰 기동 헬스체크가 실패했다. SRID 경로는 좌표계 캐시를
타서 0.008ms다. 정의가 다를 가능성은 문자열을 직접 넘겨서가 아니라 사전 검사로 막는다.)

순서 (FK 제약을 고려한 순서다):

0. **스냅숏**: 이행 시작 시 기존 grid_id 전체를 임시 테이블 `old_grids`로, 1~2단계에서 나오는
   새 grid_id 전체를 `new_grids`로 잡는다. 구/신 판별은 이 스냅숏으로만 하고 값 범위
   휴리스틱(grid_y 크기 비교)은 쓰지 않는다. 좌표를 지리적으로 제한하지 않는 현 계약에서 값
   범위는 구/신을 구별하는 근거가 못 되기 때문이다 (Codex 리뷰 반영, 2026-08-08).
1. **videos 새 인덱스 계산**: 임시 컬럼 `new_grid_id`를 추가하고, `geom`을 5179로 변환해
   `floor(y/100) || '_' || floor(x/100)`으로 채운다. status와 무관하게 전 행 계산한다
   (DELETED 행도 grid_id FK NOT NULL이라 새 셀이 필요하다).
2. **sponsor_ads, mission_grids 새 인덱스 계산**: 이 두 테이블에는 원본 좌표가 없으므로
   구 셀의 저장된 중심점을 원본으로 삼는다. sponsor_ads는 구 `grids.center_geom`을 조인해
   재계산한다. mission_grids는 grids FK가 없어 row 부재 셀이 있을 수 있으므로, grids row가
   있으면 center_geom을, 없으면 grid_id를 파싱해 구 규칙 산술(`(gridY + 0.5) × 0.0009`,
   `(gridX + 0.5) × 0.00115`)로 중심 위경도를 만들어 재계산한다. 구 스텝 상수는 이
   마이그레이션 SQL에 리터럴로 남는 마지막 사용처다.
3. **새 grids 행 INSERT**: 1~2에서 나온 새 셀 집합(videos ∪ sponsor_ads의 새 grid_id)을
   distinct로 모아 삽입한다. `center_geom`과 `bbox_geom`은 5179 셀 경계를 4326으로 역변환한
   값이다(bbox는 꼭짓점 4점 닫힌 링 폴리곤, FR-4). `region_code`는 새 중심점으로 기존 판정
   규칙 그대로 재판정한다: `ST_Covers(boundary_geom, 중심점) ORDER BY region_code LIMIT 1`
   (V5 백필, upsertGrid 인라인과 동일 규칙, FR-7). `first_seen_at`은 그 셀에 속한 영상들의
   MIN(created_at), 영상 없는 셀(스폰서 전용)은 now()로 한다. 한국 데이터에서는 구 값 범위
   (y 약 36000~43000)와 새 범위(y 약 15000~23000)가 겹치지 않지만 이 관찰에 의존하지 않는다.
   INSERT는 `ON CONFLICT (grid_id) DO UPDATE`로 써서 이론적 충돌에도 안전하게 하고, 판별은
   0단계 스냅숏이 담당한다.
4. **videos.grid_id 교체**: `grid_id = new_grid_id` UPDATE 후 임시 컬럼 DROP.
   `videos.region_code`는 **재판정하지 않는다**. 이 값은 격자가 아니라 영상 좌표로 판정된
   라벨이라(V1 설계) 격자 체계 전환과 무관하다.
5. **user_grids 재구성** (FR-6): 전량 DELETE 후 videos 집계로 재INSERT한다.
   - 모집단: `status <> 'DELETED'`. 현행 video_count 증감 규칙(업로드 확정 +1, 삭제 전이
     -1, 블라인드 불변, VideoModerationServiceImpl 실측)의 순합과 같은 집합이다.
   - `(user_id, new_grid_id)` 그룹별로 `first_collected_at = MIN(created_at)`,
     `last_uploaded_at = MAX(created_at)`, `video_count = COUNT(*)`.
   - `cover_video_id`: 그룹에 속한 영상 중 구 user_grids에서 cover였던 영상이 있으면 승계
     (여럿이면 MIN(id) 하나), 없으면 NULL. NULL은 현행 계약이 허용하고(갤러리 조회가 최신순
     폴백을 가진다) 사용자는 대표 영상을 다시 지정할 수 있다.
   - 셀 재편으로 사용자별 점령 격자 수는 달라질 수 있고, 줄어도 뱃지는 회수하지 않는다
     (FR-12). 뱃지 판정 코드와 user_badges는 건드리지 않는다.
5b. **region_stats 전량 재계산** (Codex 리뷰 반영, 2026-08-08): 재구성된 user_grids와
   재판정된 grids.region_code에서 파생되는 탐험률 통계를 그대로 두면 각 지역에 다음 업로드가
   올 때까지 사용자에게 이전 체계 값(collected_count, progress_rate)이 보이고 뱃지 판정도
   그 값을 소비한다. 기존 행을 전량 DELETE 후 `RegionRepository.refreshRegionStats`(MSG-155)와
   동일한 집계 규칙(클램프 포함)으로 재구성된 user_grids ⨝ grids의 전 (사용자, 지역) 쌍을
   재INSERT한다. 대응 쌍이 사라진 행은 이 과정에서 자연히 제거된다. 전부 롤백돼 0이 된
   지역의 0-row는 복원하지 않는다(user_grids에서 파생 불가능한 쓰기 이력 잔재). 목록
   API(`findStats`, collectedOnly=false)가 이행 전 보이던 0% 행정동을 이행 후 안 보이게
   되는 것이 유일한 가시 변화이고, 단건 조회는 0% 합성이라 무영향이다 (리뷰 판정 수용,
   2026-08-08).
6. **sponsor_ads.grid_id, mission_grids.grid_id 교체**: 2의 계산값으로 UPDATE.
   mission_grids는 PK가 (mission_id, grid_id)라 인접 포토스팟 두 개가 같은 새 셀로 합쳐지면
   충돌할 수 있다. 충돌 행은 하나로 병합하고 seq는 MIN을 유지하며, **병합으로 격자 수가 줄어든
   미션은 `missions.target_count`를 남은 격자 수로 클램프한다**
   (`target_count = LEAST(target_count, 그 미션의 남은 mission_grids 수)`). 클램프는
   mission_grids가 1건 이상 남은 미션에만 적용한다 — `chk_missions_target CHECK
   (target_count > 0)` 때문에 격자 0건 미션에 LEAST를 쓰면 제약 위반으로 이행 전체가
   롤백되고, 그런 미션은 이 이행과 무관하게 원래 달성 불가다 (2026-08-08 실측 정정). 병합만 하고
   목표 수를 두면 격자 수보다 큰 목표가 남아 기존 코스 미션이 영구 미달성이 된다. 시딩 off는
   새 적재만 막을 뿐 이미 적재된 미션은 활성이므로, 당초의 "영향 범위 없음" 판단은 틀렸다
   (Codex 리뷰 반영, 2026-08-08).
7. **구 grids 행 DELETE**: 참조를 전부 새 셀로 옮긴 뒤, `old_grids` 스냅숏에 있으면서
   `new_grids`에는 없는 grid_id 행을 삭제한다.
8. **이행 검증** (마이그레이션 파일 말미 DO 블록, 실패 시 RAISE EXCEPTION으로 전체 롤백):
   - videos 행 수가 이행 전과 같다 (영상 유실 0건).
   - `SUM(user_grids.video_count) = COUNT(videos WHERE status <> 'DELETED')`.
   - grids의 행 집합이 `new_grids` 스냅숏과 정확히 일치한다 (양방향 차집합 0건. 값 범위
     휴리스틱 대체).
   - mission_grids를 보유한 모든 미션에서 `target_count <= 그 미션의 mission_grids 수`다.

### Proj4J와 PostGIS의 정합성 검증

앱 코드의 Proj4J 계산이 정본이고, 마이그레이션 SQL의 ST_Transform은 같은 결과를 내야 한다.
둘 다 같은 계약 문자열을 쓰므로 남는 차이는 PROJ 구현 간 수치 오차(서브밀리미터 수준)뿐인데,
셀 경계 바로 위의 좌표에서는 이 오차로도 floor가 어긋날 이론적 가능성이 있다. 검증 방법:

- **통합 테스트**(로컬 DB, V28 적용 후): videos 전 행의 geom을 Java에서 Proj4J로 재계산해
  DB에 저장된 grid_id와 전수 비교한다. 불일치 0건이어야 완료다. 불일치가 나오면 해당 좌표의
  셀 경계까지 거리를 함께 출력해 경계 오차인지 규칙 불일치인지 가른다.
- 이 테스트는 공유 로컬 DB를 쓰므로 실행 전 잔여 시드 데이터 정리가 필요하다(기존 통합
  테스트 관례 동일).

## 계약 변경

**계약 인터페이스 시그니처 변경 없음.** `GridQueryService`, `HotZoneService`,
`UserGridQueryService`, `UserOidcCommandService` 모두 그대로다. GridEncoder의 public
시그니처도 유지된다(뷰포트 범위 헬퍼 1개 신설은 Owner A 패키지 내부 추가다).

다만 시그니처 밖의 **값 수준 계약** 두 건은 리뷰 시 상대 팀원과 FE 확인이 필요하다:

1. **proj4 계약 문자열**: GridConstants에 박히는 위 문자열이 FE proj4js와 글자 단위로 같아야
   한다. FE 전달 채널은 이 스펙과 픽스처 파일이다.
2. **gridId 값 전면 교체**: 계약 인터페이스가 주고받는 gridId, gridY, gridX 값이 전부
   바뀐다. 값을 불투명하게 다루는 소비자는 무수정이지만, 값을 하드코딩한 테스트(A와 B 양쪽)는
   기대값 갱신이 필요하다.

**원인**: `ST_Transform`에 proj4 정의 문자열을 인자로 넘기면 PostGIS가 호출마다 변환 경로를
새로 만든다. SRID로 넘기면 DB가 좌표계 캐시를 쓴다. 로컬 PostGIS 16-3.4에서 같은 식으로 실측:

| 방식 | 호출당 | 10만 건 환산 |
|---|---|---|
| 문자열 CRS (`ST_Transform(g, wgs84_text, epsg5179_text)`) | 0.846ms (2만 건 16.9초) | 약 141초 |
| SRID (`ST_Transform(ST_SetSRID(g, 4326), 5179)`) | 0.008ms (10만 건 0.80초) | 0.8초 |

**결과 동일성**: 이 DB의 `spatial_ref_sys` 5179 `proj4text`는 계약 문자열과 바이트 단위로 같고,
전국 5,000점 대조에서 두 경로의 grid_id 불일치가 0건이었다.

**런타임 동작 기록**

- 실행 쿼리: `pg_temp.grid_id_5179`의 변환이 `ST_Transform(ST_SetSRID(point, 4326), 5179)`로,
  `cell_center`·`cell_bbox`의 역변환이 `ST_Transform(ST_SetSRID(..., 5179), 4326)`·
  `ST_Transform(ST_MakeEnvelope(..., 5179), 4326)`로 바뀌었다. `pg_temp.crs_wgs84()`는 쓰이는
  곳이 없어져 삭제. `pg_temp.crs_5179()`는 남는데, 이제 변환 인자가 아니라 아래 사전 검사의
  비교 기준으로만 쓴다.
- 예외 흐름: 이행 맨 앞에 DO 블록 신설 — `spatial_ref_sys`에 5179가 없거나 `proj4text`가
  계약 문자열과 다르면(양끝 공백 제외) `RAISE EXCEPTION`. Flyway 마이그레이션 실패 → 트랜잭션
