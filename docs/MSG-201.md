## 개요

IA 개인 도감 3뷰(지도·갤러리·뱃지) 중 **뱃지 뷰**의 조회 API 하나를 만든다 — 획득/미획득 전체 뱃지
목록 + 획득 시각 + 미확인(새 뱃지) 표시 + 대표 뱃지 rank. 조회 시 미확인 플래그를 자동 해제한다.

```
GET /api/badges (신규, 인증 필수)
  ├─ SELECT: badges LEFT JOIN user_badges  — 마스터 전체(미획득 포함) + 내 획득 상태 (신규 쿼리)
  ├─ UPDATE: 같은 트랜잭션에서 이번 응답에 노출된 미확인분만 notified_at 스탬프 (§D3 — IN 리스트)
  └─ 응답: 뱃지 행 목록 — badgeId·code·name·description·iconUrl·earned·earnedAt·isNew·featuredRank
```

**마이그레이션 불요** — 필요한 컬럼(`notified_at`·`featured_rank`)은 V9(MSG-239)가 이미 추가했다.

## 배경 · 목표

- **사용자/제품 관점**: 뱃지가 지급되고 업로드 응답에 동봉까지 되는데(239), 도감 \[뱃지\] 탭에서
  모아 볼 방법이 없다 — 진열장·"획득 뱃지 N개"·미확인 표시(디자인 ver 6)가 전부 이 API 위에서 그려진다.
- **목표**:
  1. 획득+미획득 전체 뱃지 목록 조회 API 1개(FR — 뱃지 탭 단일 데이터 소스).
  2. 미확인 플래그 노출·해제 시맨틱 확정(239 §D8 위임 이행).
  3. 대표 뱃지·진열장의 조회 노출 확정 — 별도 API 없이 목록 필드로(§D4·D5).

## 성공 기준 (관찰 가능)

1. `GET /api/badges`가 시딩된 전체 뱃지(현재 11종)를 획득 여부와 무관하게 전부 반환한다 — 미시딩 축
   (STREAK 등) row는 없다.
2. 획득 행은 `earned: true`·`earnedAt` 시각 포함, 미획득 행은 `earned: false`·`earnedAt: null`·
   `isNew: false`·`featuredRank: null`이다(§D2).
3. 소급 지급분(`notified_at IS NULL`)은 **미확인 상태에서 조회하면** `isNew: true`이고, 그 조회의
   스탬프가 **커밋된 이후의 조회부터** `isNew: false`다(§D3). 동기 지급분(업로드 동봉)은 처음부터
   `isNew: false`.
4. 대표 뱃지는 목록 행의 `featuredRank`(1·2)로 노출된다 — 별도 조회 API 없음(§D5).
5. 목록 순서가 결정적이다 — 마스터 시딩 순(badges.id ASC), 매 호출 동일(§D6).
6. 조회가 타인의 데이터에 영향 주지 않는다 — 스탬프 UPDATE는 내 row 한정, 타인 획득 상태 미노출.
7. 크로스오너 계약 4종 Java 시그니처 불변, 공유 로컬 DB 미오염(스키마 무변경), 전체 테스트 green.

## 결정 (Decisions)

### D1 — 경로 = `GET /api/badges` (badge 도메인 루트 재사용, 위키 draft `/api/collections/badges` 미채택)

- **결정**: 기존 `BadgeController`(`/api/badges`)에 GET 메서드를 추가한다. 위키 draft의
  `GET /api/collections/badges`는 채택하지 않는다 — 239 §D6이 "조회 경로는 201이 확정"으로 위임한
  것을 이행.
- **근거**: 컨트롤러·리소스 루트가 이미 존재하고(PUT /featured), 같은 리소스의 조회·수정이 경로를
  공유하는 게 REST 관례다. usergrid의 "impl 패키지 ↔ 사용자 대면 리소스 분리" 선례와 다른 선택이지만,
  **경로 접두사가 소유권·배치를 강제하지 않는다**(127 선례 — 239 §D6 동일 논리). `/api/collections/*`
  묶음이 실제로 필요해지는 건 summary/갤러리(153)가 그 축을 열 때고, 그때도 뱃지 조회를 옮길 이유는
  생기지 않는다.

### D2 — 응답 = 전체 목록 단일 배열, 행 필드 9개 · 미획득 행의 null 규칙

- **결정**: 획득+미획득 전부를 한 배열로 — 행 필드: `badgeId`·`code`·`name`·`description`·`iconUrl`·
  `earned`·`earnedAt`·`isNew`·`featuredRank`. `condition_value`(JSONB)·conditionType·progress **미노출**
  (위키 방침 + 239 API 명세와 동일 — FE 불요).
- **미획득 행 null 규칙**: `earned: false` + `earnedAt: null` + `featuredRank: null` + **`isNew: false`**
  — isNew는 3값(boolean null) 금지. "새로 획득"은 획득의 부분집합이므로 미획득 = false가 의미상 옳고,
  FE 분기(`if (isNew)`)가 null 가드 없이 성립한다. 획득 행의 featuredRank도 대표 아니면 null.
- **기각**: `earnedOnly` 파라미터(위키 draft) — 뱃지 탭은 미획득 실루엣 포함 전체를 그리는 화면(ver 6)
  이고 11행 필터는 FE 1줄. 서버 파라미터·에러 케이스만 는다. / 획득·미획득 분리 배열 — FE가 도로
  합쳐 정렬해야 한다(진열장 파생·전체 그리드 렌더 둘 다 단일 배열이 편함).

### D3 — 확인 처리 = **조회 시 자동 스탬프** (같은 트랜잭션 UPDATE, isNew는 SELECT 시점 값)

- **결정**: GET 서비스에서 목록 SELECT 후 **같은 트랜잭션**에서, SELECT 결과 중 `isNew = true`인
  badgeId 목록을 추출해
  `UPDATE user_badges SET notified_at = now() WHERE user_id = :userId AND badge_id IN (:badgeIds)
  AND notified_at IS NULL` — 목록이 비어 있으면 UPDATE를 건너뛴다(지배적 경로). 응답의 `isNew`는
  **SELECT 시점의 NULL 여부**(스탬프 전 값) — 사용자는 이번 응답에서 "새 뱃지" 표시를 보고, 스탬프가
  커밋된 이후의 조회부터 사라진다.
- **근거**: 239 §D8 위임("확인 처리 = 201 소관")의 최소 구현. 뱃지 탭 진입 = 목록 노출 = 인지로 보는
  게 현 기획(응답 동봉+미확인 플래그, SSE 없음)과 정합하고, FE 추가 호출이 0이다.
- **전환 경로 명시**: 추후 기획이 "모달 닫을 때 해제"로 확정되면 이 UPDATE를 별도
  `PATCH /api/badges/notified`(류)로 옮기면 된다 — 컬럼·시맨틱 불변이라 **마이그레이션 불요**, 서비스
  메서드 이동뿐. GET은 그때 순수 읽기(readOnly)가 된다.
- **스탬프 범위 = 이번 응답에 노출된 행만(IN 리스트)**: 향후 신규 뱃지 시딩 마이그레이션(V10+)도 소급
  INSERT(`notified_at` NULL)를 동반한다(239 §D9) — user 전체 `notified_at IS NULL` UPDATE면 SELECT와
  UPDATE 사이에 삽입된 소급 행을 **노출된 적 없는데 확인 처리**할 수 있다. IN 리스트로 좁혀 "스탬프 =
  이번 응답에 실제로 실린 행"을 보장한다 (2026-07-29 Codex 교차 리뷰 반영).
- **동시 조회 비고**: 같은 사용자의 동시 조회 2건은 둘 다 `isNew: true`를 볼 수 있다 — 계약은 "미확인
  상태에서 조회하면 true, 스탬프 커밋 이후의 조회부터 false"다(성공 기준 3). 결과는 NEW 리본이 두 번
  보이는 것뿐이라 무해하며, SELECT·UPDATE 원자화(RETURNING·행 잠금)는 채택하지 않는다 — Spring Data
  `@Modifying`이 RETURNING 결과 행을 못 돌려주는 제약(239 §D5 기각 사유와 동일 논리).

### D4 — 진열장(최근 획득 4개) = FE 파생 — 별도 API/필드 없음

- **결정**: FE가 목록에서 `earned == true`를 `earnedAt` DESC 정렬해 앞 4개를 쓴다. 서버는 진열장을
  모른다 — 239 L107("자동 파생, 저장 불요, 조회는 201 소관")의 조회면 확정.
- **근거**: 진열장은 저장 상태가 아니라 표시 규칙이다(PRD FR-8 — 대표 뱃지와 별개·자동). 필드로 내리면
  같은 정보의 중복 표현이 생기고, 규칙 변경(4개→6개)이 서버 배포가 된다.

### D5 — 대표 뱃지 노출 = 목록 행의 `featuredRank` — 별도 `GET /featured` 없음

- **결정**: 대표 뱃지는 목록에서 `featuredRank`가 non-null(1·2)인 행이다. 별도 조회 엔드포인트를 만들지
  않고, 기존 `findFeatured`(+`FeaturedBadgeProjection`)는 **PUT 응답 전용으로 유지**한다.
- **근거**: 뱃지 탭이 어차피 전체 목록을 받는다 — 대표 표시는 그 안의 마킹이면 충분. 닉네임 옆 표시
  (타 화면)가 뱃지만 따로 필요해지는 건 프로필 조회 API 소관이며, 그때 그 응답에 동봉하는 게 맞다
  (이 티켓에서 범용 GET /featured를 선반영하지 않는다 — YAGNI).

### D6 — 목록 순서 = **badges.id ASC** (마스터 시딩 순 = 축별·티어 오름차순)

- **결정**: `ORDER BY b.id` — V9 시딩 순서가 곧 "탐험가 1→500 · 기록러 10→100 · 지역 마스터 10→50"의
  축별·티어 오름차순이라, id 정렬이 화면의 자연 순서와 일치하고 결정적이다. 향후 시딩(V10+)도 축 단위로
  붙으므로 유지된다.
- **기각**: earnedAt DESC 우선 정렬 — 진열장용 순서는 FE 파생(§D4)이고, 전체 그리드는 고정 순서(도감의
  "빈 칸이 그 자리에 보이는" UX)가 맞다. / 별도 sort_order 컬럼 — 현 시딩 순과 동일한 값을 한 번 더
  관리하는 중복. 필요해지는 시점(축 사이 끼워넣기)에 마이그레이션으로 추가.

## 도메인 로직

### 조회·스탬프 (`BadgeQueryServiceImpl` — badge/service, §D2·D3)

```
@Transactional findMyBadges(userId):                       -- 스탬프 UPDATE 가 있어 readOnly 아님 (§D3 전환 시 readOnly 화)
  rows = badgeRepository.findAllWithMyStatus(userId)       -- native LEFT JOIN, 아래. isNew 는 이 시점 값
  newIds = rows 중 isNew = true 인 badgeId 목록
  if newIds not empty:
      userBadgeRepository.markMyBadgesNotified(userId, newIds)   -- 노출된 행만 스탬프 (§D3 IN 리스트)
  return rows → MyBadgeResponseDto 매핑                    -- Projection → Dto 직결 (badge 관례)
```

```sql
-- findAllWithMyStatus (BadgeRepository, native) — 마스터 driven: 미시딩 축은 행 자체가 없다
SELECT b.id AS "badgeId", b.code, b.name, b.description, b.icon_url AS "iconUrl",
       ub.user_id IS NOT NULL AS "earned",
       ub.earned_at AS "earnedAt",
       (ub.user_id IS NOT NULL AND ub.notified_at IS NULL) AS "isNew",
       ub.featured_rank AS "featuredRank"
FROM badges b
LEFT JOIN user_badges ub ON ub.badge_id = b.id AND ub.user_id = :userId
ORDER BY b.id
```

```sql
-- markMyBadgesNotified (UserBadgeRepository, @Modifying native) — §D3. IN = 이번 응답에 노출된 isNew 행
UPDATE user_badges SET notified_at = now()
WHERE user_id = :userId AND badge_id IN (:badgeIds) AND notified_at IS NULL
```

- LEFT JOIN 대상은 user_badges PK `(user_id, badge_id)` — `ub.user_id = :userId` equi가 PK prefix를
  탄다. 마스터 11행 전체 스캔이 곧 결과 크기라 추가 인덱스 불요.
- 컨트롤러는 기존 `BadgeController`에 `@GetMapping` 추가 — principal userId + 서비스 호출 +
  `SuccessResponse.of`만(기존 PUT과 동일한 얇기).
