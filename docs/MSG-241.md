## 개요

영상 교체(PUT) 시 이전 파일의 비동기 인코딩 태스크가 아직 돌고 있으면, 그 옛 태스크가
**id-only 상태 라이터**(`VideoStatusWriter.markEncoding/markReady/markEncoded/markFailed` — 전부
`findById` + 무가드)를 호출해 옛 파일 기준 결과로 새 영상 상태를 되돌릴 수 있다.
폴러 전용 라이터(MSG-149/150)에는 이미 잡 정체성 가드가 있지만 **인코딩 경로 라이터에는 없다.**
시도 식별자로 `original_s3_key`를 대조해 불일치면 무시하도록 인코딩 경로에 같은 가드를 확장한다.

## 배경 · 목표

- 교체된(사용자가 버린) 콘텐츠가 READY 로 되살아나 일시 노출될 수 있다 — 사용자가 지우려던
  영상이 보이는 건 신뢰 문제. AI 모드에선 옛 파일 기준 BLURRING 시도가 "정상 시도"로 위장해
  옛 콘텐츠의 ai_job 이 새 시도에 붙는다.
- 목표: 교체·삭제 이후 도착하는 옛 인코딩 태스크의 쓰기(전이·키 기록·FAILED)를 전부 무시하고,
  새 파일 흐름(UPLOADED → 재인코딩)을 그대로 유지한다.

**AI 모드 ai_job_id 잔존 경로**: 옛 태스크의 `markEncoded`(:93)가 새 시도를 BLURRING 으로 전이시키며
`blurringStartedAt` 을 **새로 찍는다**(`Video.markEncoded`, `Video.java:152-156`). 이 시도는
`recordAiJob` 의 기존 가드(ACTIVE·BLURRING·aiJobId null·startedAt 일치)를 **정상 통과**한다 —
가드 기준 넌스를 스테일 쓰기 자신이 만들었기 때문. 폴러는 옛 파일의 encoded 본을 AI 서버에
제출하고 그 job_id 가 새 시도에 기록된다. `replaceFile` 이 aiJobId 를 비워도(MSG-145) 소용없다 —
비운 **뒤에** 옛 markEncoded 가 도착하는 게 이 결함이다. `@DynamicUpdate`(MSG-162)도 무력하다 —
교차 컬럼 클로버링 방어일 뿐, 같은 컬럼에 대한 스테일 쓰기는 못 막는다.

재현: 영상 A 인코딩 중(ffmpeg ~수 초) 사용자가 PUT 교체 → `replaceFile` 이 UPLOADED 로 리셋,
새 태스크 B 트리거 → 옛 태스크 A 가 완료해 `markReady`/`markEncoded` 호출 → **새 영상이 옛 파일
기준 READY/BLURRING** (또는 A 의 다운로드 실패로 FAILED). B 가 나중에 덮어써 자가 복구될 수도
있지만 그 사이 옛 콘텐츠 노출·FAILED 오표시·옛 잡 제출이 발생한다.

## 수정 방식 — 원본 s3Key 대조 (attempt nonce 기각)

티켓의 두 대안 중 **원본 `original_s3_key` 대조**를 택한다.

**근거 — `original_s3_key` 는 이미 완성된 시도 식별자다**:
1. **시도마다 유일**: 업로드·교체 모두 `confirmUpload` 가 pending UUID 키에서 파생한 새 키를
   받고(`VideoServiceImpl.java:489-505`), `existsByOriginalS3Key` 선차단 + DB UNIQUE 제약
   (`V2__videos_original_s3_key_unique.sql`)이 재사용을 막는다. 교체 시 `replaceFile` 이 갱신
   (`Video.java:186-197`) — "키가 다르다 ⇔ 다른 시도다"가 스키마 차원에서 보장된다.
2. **전달 비용 0**: 인코딩 태스크는 그 키를 이미 들고 있다(다운로드에 사용, :61).
3. **패턴 일관**: 폴러 가드가 잡 정체성(ai_job_id·blurringStartedAt)을 대조하듯, 인코딩 경로의
   자연스러운 정체성은 "어느 원본을 인코딩했나" = originalS3Key 다.

**attempt nonce 기각 이유**: UPLOADED/ENCODING 구간에 쓸 수 있는 기존 넌스 컬럼이 없다
(`blurringStartedAt` 은 `markEncoded` 시점에만 세팅 — 재활용 불가). 새 컬럼 + V11 마이그레이션이
필요한데, s3Key 가 같은 판별력을 무비용으로 제공한다. 넌스를 태스크에 넘기는 배관도 키를 넘기는
배관과 동일해 절감분이 없다.

### 설계

**1) 시도 정체성을 트리거 시점에 고정해 태스크로 전달** — `VideoEncodingService.encode` 시그니처 변경:

```java
void encode(Long videoId);                      // 현재
void encode(Long videoId, String originalKey);  // 변경 — 시도 정체성 동반
```

호출부 `saveVideo`/`replaceVideo` 는 `originalKey` 를 이미 보유 — `triggerEncodingAfterCommit`/
`submitEncoding` 에 함께 넘긴다. 부수 효과: 트리거→태스크 시작 사이에 교체가 끼어들어 옛
트리거의 태스크가 **새 키를 읽고** 새 태스크와 이중 인코딩하는 변종도 함께 닫힌다(옛 태스크는
자기 키 기준으로 즉시 스테일 판정). 다운로드도 전달받은 키로 한다 — fresh 로드 값이 아니라.

**2) 인코딩 라이터 4종에 정체성 가드 + 행 잠금** — `VideoStatusWriter` 변경:

```java
public boolean markEncoding(Long videoId, String expectedOriginalKey)                          // false 면 태스크 즉시 중단
public void markReady(Long videoId, String expectedOriginalKey, String encodedKey, String thumbnailKey)
public void markEncoded(Long videoId, String expectedOriginalKey, String encodedKey)
public void markFailed(Long videoId, String expectedOriginalKey)
```

- 조회를 `findById` → `findWithLockById`(PESSIMISTIC_WRITE, MSG-149 P1-c 재사용)로 전환 —
  교체/삭제 트랜잭션의 UPDATE 와 같은 행에서 직렬화되어 잠금 후 재확인한 상태가 그 커밋 이후
  상태임을 보장한다(폴러 라이터·MSG-243 삭제와 동일 패턴, 읽기-후-쓰기 ms 창 제거).
- 가드 술어 (`isCurrentBlurJob` 대칭):

```java
/** 이 태스크가 인코딩한 원본과 현재 DB 행이 같은 시도인가 — 교체(키 갱신)/삭제(ACTIVE 이탈)로 벌어진 창을 닫는다. */
private boolean isCurrentEncodingAttempt(Video video, String expectedOriginalKey) {
	return video != null
		&& video.getStatus() == VideoStatus.ACTIVE
		&& Objects.equals(video.getOriginalS3Key(), expectedOriginalKey);
}
```

- 불일치 시 `logStaleSkip` 관례대로 로그 후 무시. `markEncoding` 은 적용 여부를 반환해 태스크
  시작 시점의 스테일(큐 대기 중 교체됨)이면 ffmpeg 을 돌리지 않고 종료한다.
- `ACTIVE` 조건이 삭제(MSG-243)도 함께 커버한다 — DELETED 행에 FAILED/READY 를 쓰지 않는다
  (`markBlurFailed` 가드와 동일 방침).
- 폴러 라이터(`recordAiJob`·`markBlurReady`·`markBlurFailed`)는 **변경 없음** — 이미 가드 완비.

**3) 업로드 직전 재확인 확장** — `VideoEncodingServiceImpl:81` 의 `isDeleted` 체크를 정체성
체크(삭제 or 교체)로 확장한다: fresh `findById` 후 `status==ACTIVE && originalS3Key 일치` 아니면
업로드 생략. 옛 바이트가 결정적 encoded 키를 덮는 창을 기존 ~100ms 수준으로 좁힌다.

**잔여 창 (수용)**: 체크 통과 → 교체 커밋 → 옛 바이트 업로드 순이면 S3 의 결정적 키에 옛 바이트가
잠시 남는다. 단 DB 가드가 막으므로 상태는 READY 가 아니고(재생은 READY 만 발급, MSG-206), 새
태스크의 재인코딩(~수 초)이 같은 키를 덮는다. 노출되려면 새 태스크 전체(다운로드+ffmpeg+업로드)가
끝난 **뒤에** 옛 태스크의 마지막 업로드(<1s 작업)가 도착해야 해 실질 불가에 가깝다 — 기존 삭제
경로의 동급 창(ponytail 주석, :80)과 같은 수용 한계다. 완전 봉쇄는 시도별 유니크 encoded 키가
필요하나 고아 키 정리 복잡도 대비 가치 없음 — 기각, 기록만.

## 성공 기준

1. 교체 직후 이전 인코딩 완료(`markReady`/`markEncoded`)가 도착해도 상태가 **UPLOADED**(새 파일
   흐름)를 유지한다 — 옛 encoded/thumbnail 키가 기록되지 않는다.
2. AI 모드에서 옛 완료가 BLURRING 전이·`blurringStartedAt` 세팅을 못 한다 → 폴러 제출 대상이
   되지 않아 옛 파일의 ai_job_id 가 새 시도에 붙지 않는다.
3. 옛 태스크의 실패(`markFailed` — 교체가 옛 원본을 S3 에서 지워 다운로드가 실패하는 실전 경로
   포함)가 새 시도를 FAILED 로 밀지 않는다.
4. 현재 시도의 정상 흐름(UPLOADED→ENCODING→READY, AI 는 →BLURRING)은 불변 — 기존 인코딩·폴러·
   교체 테스트 전건 green.
