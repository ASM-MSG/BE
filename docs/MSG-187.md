# MSG-187: 친구 도감 뷰포트 레이어 (친구 격자 지도 보기)

**Owner**: B

> 요구사항 정본: `docs/prd/MSG-187-prd.md` (상태 검토됨, 2026-08-04 사용자 승인 — 기획 5건
> 확정: 단일색·친구 색 우선·격자망 상시 표시·특정 친구 1명·PUBLIC+FRIENDS 목록). 이 스펙은
> PRD의 FR-1~10·비기능에 "어떻게"만 붙인다. 용어는 `.claude/rules/glossary.md`
> **친구 도감 레이어** 항목(2026-08-04 등재) 기준.

**Owner 판정 근거**: 변경 파일 전부가 Owner B 패키지다 — `com.msg.fillmap.friend.*`(MSG-185),
`com.msg.fillmap.video.*`(MSG-66), `com.msg.fillmap.usergrid.*`(MSG-152). Owner A 자산
(`GridQueryService`·`GridRepository`·`GridCursor`·`OccupiedGridPageResponseDto`)은 **기존 4-인자
계약 시그니처 무변경 재사용**이라 grid 패키지 diff 0 — 공동 아님. 단 friend가 `GridQueryService`의
**신규 크로스 오너 소비자**로 추가되므로 §계약 변경에 명시한다(리뷰 시 Owner A 확인 지점).

## 개요

친구 에픽(MSG-172)의 마지막 조각 — 친구 관계(MSG-185)·목록/프로필(MSG-186)·FRIENDS 재생
판정(MSG-285) 위에 **친구의 도감을 지도에서 보는** 조회 2종 + 정합 수정 1건을 추가한다:

1. **친구 격자 뷰포트 조회** `GET /api/friends/{userId}/grids` — ACCEPTED 친구 1명이 점령한
   격자를 내 뷰포트 조회(MSG-90)와 동일 계약(커서 페이지네이션·색상 필드 없음)으로 반환.
2. **친구 격자 영상 목록** `GET /api/friends/{userId}/grids/{gridId}/videos` — 그 친구가 그
   격자에 올린 영상 중 **PUBLIC + FRIENDS**만(PRIVATE 절대 제외), ACTIVE·READY 게이트.
   FRIENDS 영상의 최초 목록 노출 경로다(MSG-285에서 명시 이월).
3. **FR-6 정합**: 친구 프로필 최근 격자 썸네일 게이트 `PUBLIC` → `IN ('PUBLIC','FRIENDS')`
   1곳 확장 (MSG-186 쿼리 인라인 TODO 기등록, Codex 정적 리뷰 BLOCK 지적분).

쓰기 없음 — 마이그레이션·엔티티·인덱스 변경 없음, 조회 쿼리와 DTO만 신규다. 격자망 상시
표시·단일색·겹침 친구 색 우선은 전부 **FE-local 렌더**라 서버 무영향(PRD 확정 결정 1~3).

## 배경 · 목표

- 친구 API 3축이 머지됐지만 "친구가 어디를 채웠는지"를 지도 격자로 보는 경로가 0개고,
  FRIENDS 공개범위 영상은 재생 판정만 있고 친구가 발견할 목록이 없다.
- 목표: 친구 1명 선택 → 그 친구의 점령 격자를 뷰포트로 열람 → 격자 선택 시 그 친구의
  PUBLIC+FRIENDS 영상 목록 → 기존 재생(MSG-285)으로 진입.
- 스코프 제외(PRD 비목표): 전체 친구 합산 레이어(Phase 2+), 전역 노출 경로(대표 영상·전역
  목록·탐색 집계)의 FRIENDS 확장(PUBLIC 한정 유지 — 등식 쿼리 9곳·`idx_videos_grid_popular`
  무변경), 친구별 색상, 그룹(MSG-188 소멸), 격자망 렌더(FE-local), FE 진입 UI(디자인 몫).

## 성공 기준

- 친구 격자 뷰포트 응답이 내 조회(`GET /api/grids`)와 **동일 형상**(grids[].gridId/gridY/gridX +
  nextCursor, 색상 필드 없음)이다 — 같은 DTO 재사용으로 구조 보장 (FR-3).
- 뷰포트·커서·size 검증이 내 조회와 **동일 규칙·동일 에러**(4401/4402/4403/4404, 상한 0.5°·
  size 1..5000)로 동작한다 (FR-10).
- 비친구·본인 ID·PENDING 상대·미존재 userId 는 두 API 모두 **동일하게 9424**다 — 관계·계정
  존재 은닉, MSG-186 프로필과 같은 정책 (FR-2).
- 친구 삭제 즉시 다음 요청부터 두 API 모두 9424 — 요청 시점 실시간 판정, 캐시 없음 (FR-7).
- 친구 격자 영상 목록에 PUBLIC·FRIENDS 만 포함되고 PRIVATE·DELETED·BLINDED·READY 미만은
  절대 포함되지 않는다 (FR-4·9). 목록의 모든 영상은 `GET /api/videos/{videoId}` 재생 판정을
  통과한다 (FR-5).
- 친구 프로필(`GET /api/friends/{userId}/profile`) 최근 격자 썸네일이 FRIENDS-only 격자에도
  붙는다 — PRIVATE-only 격자는 여전히 null (FR-6).
- 친구 점령 0건 뷰포트는 200 + 빈 grids + nextCursor null (FR-8).
- 전체 테스트 green (`./gradlew test`).

## 확정 설계 (D1~D7)

### D1. 진입점은 friend 도메인 — `FriendController` +2

- 경로: `GET /api/friends/{userId}/grids` · `GET /api/friends/{userId}/grids/{gridId}/videos`.
  기존 매핑과 충돌 없음 실측 — `/{userId}/profile`(GET)·`/{userId}`(DELETE)와 세그먼트 구조가
  다르고, `/requests/**`는 리터럴 우선 매칭이라 안전. `{userId}` Long 변환 실패는 기존과 같이
  전역 400.
- 인증: `SecurityConfig anyRequest().authenticated()`가 `/api/friends/**` 커버(MSG-185 D4) —
  설정 변경 불요.
- "격자 하위 리소스는 접두사 무관하게 데이터 소유 도메인 패키지"(MSG-127 선례)와 정합 —
  판정·진입은 friend, 영상 형상은 video, 격자 페이지는 grid 계약이 만든다.

### D2. 친구 격자 뷰포트 = `GridQueryService` 4-인자 재사용 (인터페이스 확장 불요 판정)

- **판정: 재사용 가능, 확장 불요.** `getOccupiedInViewport(long userId, ViewportBounds bounds,
  String cursor, int size)`(MSG-90)는 이미 대상 userId 를 파라미터로 받는다 — "로그인 사용자"
  결합은 `GridController`가 principal 을 넣는 호출부 사정이지 계약 시그니처가 아니다.
  `FriendServiceImpl`이 친구 판정 후 **friendUserId 를 넣어 호출**하면 끝.
- 검증(뒤집힌 bbox 4401·span 0.5° 초과 4402·커서 디코드 실패 4403·size 1..5000 밖 4404)이
  전부 `GridQueryServiceImpl` 안에 있으므로 **FR-10 "동일 규칙·동일 에러"가 재사용만으로
  성립**한다 — friend 쪽 검증 코드 0줄.
- 실행 쿼리도 동일: `GridRepository.findOccupiedPage/findOccupiedPageAfter`(keyset 행값 비교
  `(grid_y, grid_x) > (:cursorY, :cursorX)`, `uq_grids_yx` btree, lookahead size+1). user_id
  파라미터 값만 친구로 바뀌므로 실행 계획 동일 — 비기능 "동급 성능" 자동 충족. 커서는
  `GridCursor` Base64URL opaque 토큰 그대로 — 내 조회의 커서와 상호 호환이지만 FE 는 응답의
  nextCursor 를 그대로 되돌리기만 하면 된다(기존 계약).

### D3. 판정 순서 — 파라미터 누락 4401 → 친구 판정 9424 → 뷰포트·커서·size 검증

1. **컨트롤러**: 뷰포트 4파라미터 중 하나라도 누락 → `GridErrorCode.INVALID_VIEWPORT`(4401) —
   `GridController.toBounds` 동형 사본. FR-10 의 "동일 에러"가 hotzone 관행(전역 400, MSG-184)
   보다 우선한다 — FE 가 내 조회와 이 API 를 같은 에러 핸들링으로 다루는 게 요구사항이다.
   4401 은 관계 정보를 누설하지 않는다.
2. **서비스(friend)**: `FriendshipRepository.existsAcceptedPair`(무잠금 JPQL, 양방향 —
   MSG-186/285 와 같은 메서드) false → `FriendErrorCode.FRIENDSHIP_NOT_FOUND`(9424).
   비친구에게는 뷰포트가 유효한지조차 알려주지 않는다 — 은닉 우선.
3. **서비스(grid)**: 나머지 검증은 D2 재사용분이 수행.

### D4. 뷰포트 응답 DTO = `OccupiedGridPageResponseDto` 재사용

- FR-3 "내 뷰포트 조회와 동일한 계약"을 **같은 타입 공유로 구조적으로 보장**한다 — friend 전용
  DTO 를 만들면 형상 드리프트 가능성만 생긴다. `FriendController`가
  `OccupiedGridPageResponseDto.from(page)` 호출(grid.dto 는 A 소유지만 read 소비는
  `UserGridRepository`의 `grid.entity.UserGrid` 재사용 등 기존 관행).
- 색상 필드는 원래 없다(gridId·gridY·gridX·nextCursor 뿐) — PRD 확정 결정 1(서버 색 미전달)
  충족에 추가 작업 0.

### D5. 친구 격자 영상 목록 — my-videos 템플릿 + 3중 게이트, **정렬 최신순 확정**

- **정렬 결정(PRD 미해결 질문 1 해소): `created_at DESC, id DESC` 최신순.** 근거: 이 목록은
  "친구 도감 열람" 계열이고 같은 화면 계열인 내 도감 my-videos(MSG-127)가 최신순이다. 인기순
  전역 목록(MSG-237)의 부분 인덱스 `idx_videos_grid_popular`는 `visibility='PUBLIC'` 한정이라
  이 쿼리(IN 2값)는 태울 수도 없다. id DESC 타이브레이크는 `getRegionVideos`(MSG-167) 관례.
- 쿼리는 `VideoRepository` 신규 JPQL(파생 쿼리는 조건 5개로 메서드명이 관례 밖 길이):

```java
/**
 * 친구 격자 영상 목록 (MSG-187 D5). 친구 판정은 호출자(friend 도메인) 책임 — 이 쿼리는
 * "친구에게 허용된 공개범위"만 거른다. PRIVATE 제외(FR-4), ACTIVE 로 DELETED·BLINDED 제외 +
 * READY 로 인코딩 미완 제외(FR-9) — 목록의 전 항목이 MSG-285 재생 판정을 통과한다(FR-5).
 */
@Query("""
	SELECT v FROM Video v
	WHERE v.userId = :ownerUserId AND v.gridId = :gridId
		AND v.status = com.msg.fillmap.video.entity.VideoStatus.ACTIVE
		AND v.processingStatus = com.msg.fillmap.video.entity.ProcessingStatus.READY
		AND v.visibility IN (com.msg.fillmap.video.entity.Visibility.PUBLIC,
			com.msg.fillmap.video.entity.Visibility.FRIENDS)
	ORDER BY v.createdAt DESC, v.id DESC
	""")
List<Video> findFriendGridVideos(@Param("ownerUserId") Long ownerUserId, @Param("gridId") String gridId);
```

- 배선은 MSG-186 `getCollectionGridsForFriend` 선례 미러 — **판정은 friend, 데이터 형상은
  소유 도메인**: `VideoService.getFriendGridVideos(long ownerUserId, String gridId)` 신규
  (B-내부, javadoc 에 "친구 판정 선행 전제" 명시)가 쿼리 + `ThumbnailUrlPresigner.presign` +
  DTO 매핑을 담당하고, `FriendServiceImpl`은 `existsAcceptedPair` 판정 후 위임만 한다.
- 응답 항목 `video/dto/FriendGridVideoResponseDto` 신규 — `videoId`(재생 진입 키) ·
  `thumbnailUrl`(presigned GET, READY 여도 key null 이면 null — MSG-127 관례) ·
  `durationSec` · `createdAt`. `GridVideoResponseDto`를 재사용하지 않는 이유:
  processingStatus 필드가 이 목록에선 항상 READY 상수라 계약 노이즈다. visibility 필드도
  미포함 — PRD 에 노출 요구 없음(필요 시 FE 요청으로 후속).
- 페이지네이션 없음 — my-videos 템플릿 동형(한 사용자 × 한 격자 규모, 재방문 수십 건 천장).

### D6. FR-6 썸네일 게이트 — `getCollectionGridsForFriend` LATERAL 1곳 확장, **구현 첫 커밋**

- `UserGridRepository.getCollectionGridsForFriend` LATERAL 서브쿼리의
  `v.visibility = 'PUBLIC'` → `v.visibility IN ('PUBLIC','FRIENDS')` — MSG-186 이 쿼리 주석으로
  예약해 둔 확장 지점 그 한 곳이다(`:118` 인라인 TODO). 시그니처·정렬·30 상한·나머지 4조건
  (ACTIVE·READY·thumbnail NOT NULL·cover 우선) 불변.
- **Codex 정적 리뷰가 이 불일치(재생은 FRIENDS 허용인데 썸네일은 PUBLIC 한정)를 BLOCK 으로
  지적** — 구현 첫 커밋에서 처리하고, FRIENDS-only 격자 썸네일 노출 + PRIVATE-only 격자 null
  유지를 통합 테스트로 고정한다(§테스트 시나리오 3그룹).

### D7. 미점령·미존재 gridId = 빈 배열, gridId 포맷 무검증 — my-videos 동형

- 친구 격자 영상 목록에서 친구가 점령하지 않은 격자·존재하지 않는 gridId·포맷 이상 gridId 는
  전부 매치 0 → **200 + 빈 배열**(예외 아님) — `GET /api/grids/{gridId}/my-videos` 계약 동형.
  친구 판정(9424)만 선행하면 격자 존재 여부는 새는 정보가 아니다(격자는 논리적으로 항상 존재
  — glossary).

## API 명세

### 1. 친구 격자 뷰포트 조회 — `GET /api/friends/{userId}/grids`

| 항목 | 값 |
|---|---|
| 인증 | 필수 (JWT) |
| Path | `userId` — 친구 사용자 ID (Long) |
| Query | `swLat`·`swLng`·`neLat`·`neLng`(bbox, 누락 시 4401) · `cursor`(직전 nextCursor, 생략=첫 페이지) · `size`(기본 1000, 1..5000) |
| 응답 | `SuccessResponse<OccupiedGridPageResponseDto>` — 재사용 (D4) |

```json
{ "developCode": 200, "message": "성공",
  "data": { "grids": [ { "gridId": "41642_110458", "gridY": 41642, "gridX": 110458 } ],
            "nextCursor": "NDE2NDNfMTEwNDYw" } }
```

에러 (신규 코드 0):

| 케이스 | developCode | HTTP |
|---|---|---|
| bbox 파라미터 누락·뒤집힌 bbox | 4401 INVALID_VIEWPORT | 400 |
| span 0.5° 초과 | 4402 VIEWPORT_TOO_LARGE | 400 |
| 커서 디코드 실패 | 4403 INVALID_CURSOR | 400 |
| size 1..5000 밖 | 4404 INVALID_PAGE_SIZE | 400 |
| 비친구·본인·PENDING·미존재 userId·친구 삭제 후 | 9424 FRIENDSHIP_NOT_FOUND | 404 |

### 2. 친구 격자 영상 목록 — `GET /api/friends/{userId}/grids/{gridId}/videos`

| 항목 | 값 |
|---|---|
| 인증 | 필수 (JWT) |
| Path | `userId` — 친구 사용자 ID · `gridId` — 격자 ID (`"{grid_y}_{grid_x}"`) |
| Query | 없음 (무페이징 — D5) |
| 응답 | `SuccessResponse<List<FriendGridVideoResponseDto>>` — 최신순, 조건 미충족·미점령·미존재 gridId 는 빈 배열 (D7) |

```json
{ "developCode": 200, "message": "성공",
  "data": [ { "videoId": 1042, "thumbnailUrl": "https://…presigned…", "durationSec": 12,
              "createdAt": "2026-07-20T18:03:11" } ] }
```

에러: 9424(위 표와 동일 정책)뿐 — 신규 코드 0.

### 3. (변경) 친구 프로필 최근 격자 썸네일 — `GET /api/friends/{userId}/profile`

- 응답 형상 불변. 격자 항목 `thumbnailUrl`의 선정 모집합만 PUBLIC → PUBLIC+FRIENDS 로 확장
  (D6). PRIVATE-only 격자는 계속 thumbnailUrl null(격자 사실만).

## 도메인 로직

- **친구 판정**: `existsAcceptedPair(userId, targetUserId)` — ACCEPTED·방향 무관·무잠금.
  요청 시점 실시간(FR-7), 본인 ID 는 자기 쌍 행이 존재할 수 없어 자연 false → 9424 (MSG-186
  §D4 은닉 로직 그대로).
- **점령 롤백 정합**(비기능): 친구가 격자 영상을 모두 삭제하면 `user_grids` 행이 삭제되므로
  (MSG-72) 뷰포트 조회에서 자동으로 사라진다 — 비정규화·캐시가 없어서 얻는 성질, 추가 코드 0.
- **목록·재생 정합**(FR-5): 목록 게이트(ACTIVE ∧ READY ∧ visibility∈{PUBLIC,FRIENDS} ∧ 친구)
  ⊆ 재생 허용(MSG-285 switch: PUBLIC 통과, FRIENDS ∧ isFriend 통과, ACTIVE·READY 면 URL 발급).
  목록 응답과 재생 요청 사이 친구 삭제 시 재생이 403 으로 막히는 것은 실시간 판정 원칙의
  의도된 동작이다.
- **글로서리 대조**: 이 스펙의 "점령"은 전부 개인 점령(`user_grids` 행), "방문"은 영상 1건.
  친구 격자 뷰포트는 친구의 **도감**(점령 격자 집합)을 읽는 것이고 새 개념을 만들지 않는다.
