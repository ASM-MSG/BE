# MSG-192: 영상 신고 접수 API

**Owner**: B (신규 `com.msg.fillmap.moderation` 패키지, Owner B 배정)

> PRD 정본: `docs/prd/MSG-192-prd.md` (MSG-192, MSG-193 공유 PRD, 상태 검토됨, 2026-08-06 승인).
> 이 스펙은 그중 MSG-192 몫(FR-1~FR-5a)만 다룬다. 블라인드 전환과 해제(FR-6~FR-11)는
> MSG-193 스펙이 별도로 다루므로 여기서 언급하지 않는다.

## 개요

로그인 사용자가 다른 사람의 영상을 사유 5종(INAPPROPRIATE, PRIVACY, SPAM, COPYRIGHT, OTHER)
중 하나와 함께 신고하는 API를 만든다. 접수된 신고는 V1부터 존재하던 `reports` 테이블에 PENDING
상태로 쌓여, 이후 관리자 처리(MSG-195)의 입력이 된다. 신고 접수는 어떤 자동 전환도 일으키지
않는다. 블라인드는 관리자 수동 판단만으로 이뤄진다 (2026-08-06 확정, 재논의 금지).

## 배경 · 목표

피그마 격자 상세 화면에는 신고 UI가 있지만 대응 API가 없고, `reports` 테이블을 읽거나 쓰는
코드도 0줄이다. 웹 공개 전에 문제 영상을 알릴 통로가 필요하다 (PRD §1). 이번 티켓의 목표는
신고 접수 하나를 완성하는 것이다. 신고 대상은 영상만이다 (사용자 신고 없음, 사용자 단위 대응은
차단 MSG-194 몫).

## 성공 기준

아래 조건이 통합 테스트로 관찰되면 완료다. "테스트 시나리오" 절이 이 기준의 검증 수단이다.

1. 로그인 사용자가 타인의 ACTIVE 영상을 사유와 함께 신고하면 200 응답(reportId 포함)을 받고,
   `reports`에 status PENDING 행이 정확히 1개 생긴다.
2. 같은 사용자가 같은 영상을 다시 신고하면 409 "이미 접수된 신고입니다"를 받고 행이 늘지 않는다.
   동시에 들어온 두 요청도 DB 유니크 제약[^1]이 2행 저장을 막는다.
3. 존재하지 않는 영상, DELETED 영상, BLINDED 영상의 신고는 404를 받는다. 응답은 재생 경로의
   404와 developCode까지 동일하다 (존재 은닉[^2]).
4. 자기 영상 신고는 400으로 거부된다.
5. 지원하지 않는 reason 값은 400, OTHER인데 상세 설명이 없으면 400, 상세 설명 500자 초과는
   400으로 거부된다.
6. 신고 접수는 `reports` INSERT 외에 아무것도 바꾸지 않는다. `videos.status`는 물론 다른 어떤
   테이블도 변하지 않는다.

## API 명세

### POST `/api/videos/{videoId}/reports` : 영상 신고 접수

인증 필수. 별도 SecurityConfig 변경 없이 기존 `anyRequest().authenticated()`가 강제한다
(미인증은 401). 사용자 식별은 기존 컨트롤러 패턴 그대로
`@Parameter(hidden = true) @AuthenticationPrincipal AuthPrincipal principal`로 받아
`principal.userId()`를 서비스에 넘긴다 (VideoController 선례).

**Request Body**: `ReportCreateRequestDto`

| 필드 | 타입 | 제약 | 설명 |
|------|------|------|------|
| `reason` | String | `@NotBlank` | 신고 사유. INAPPROPRIATE, PRIVACY, SPAM, COPYRIGHT, OTHER 중 하나. 파싱은 서비스 레이어에서 한다 (아래 도메인 로직 1번) |
| `detail` | String | `@Size(max = 500)`, 선택 | 상세 설명. OTHER 사유는 필수, 나머지 사유는 선택 (FR-5a) |

**Response 200**: `SuccessResponse<ReportCreateResponseDto>`

| 필드 | 타입 | 설명 |
|------|------|------|
| `reportId` | Long | 접수된 신고 id. 이후 문의 대응의 추적 키 |
| `status` | String | 항상 `"PENDING"` (접수 확인) |

**에러 케이스** (검증 순서는 아래 도메인 로직의 first-match 순서와 같다)

| HTTP | developCode | 케이스 |
|------|------------|--------|
| 401 | 401 (공통) | 미인증 (SecurityConfig, CustomAuthenticationEntryPoint) |
| 400 | 400 (공통) | `reason` 누락, `detail` 500자 초과. Bean Validation[^3] 실패라 GlobalExceptionHandler의 공통 BAD_REQUEST로 처리되며 신규 코드가 없다 |
| 400 | 11400 `INVALID_REASON` | 사유 5종 밖의 reason 값 (FR-5) |
| 400 | 11401 `DETAIL_REQUIRED` | OTHER 사유인데 상세 설명 없음 (FR-5a) |
| 404 | 3404 `VIDEO_NOT_FOUND` | 영상 없음, DELETED, BLINDED (FR-3). `VideoErrorCode.VIDEO_NOT_FOUND` 재사용, D1 참조 |
| 400 | 11402 `SELF_REPORT` | 자기 영상 신고 (FR-4) |
| 409 | 11409 `DUPLICATE_REPORT` | 같은 사용자가 같은 영상 재신고 (FR-2) |

## 도메인 로직

`ReportServiceImpl.report(userId, videoId, request)`는 `@Transactional` 하나로 묶고, 아래
순서대로 first-match[^5] 판정한다. 순서가 계약이다. 요청 형식 오류(1, 2번)를 영상 조회보다 먼저
걸러서, 형식이 틀린 요청이 영상 존재 여부를 알아내는 창구가 되지 않게 한다.

1. **reason 파싱**: DTO의 String을 `ReportReason.valueOf(reason.toUpperCase())`로 변환하고
   `IllegalArgumentException`이면 `INVALID_REASON`(11400)을 던진다.
   `AuthServiceImpl.parseProvider`, `VideoServiceImpl.parseVisibility`(3420)와 같은 선례다.
   조용한 기본값 폴백은 하지 않는다.
2. **OTHER 상세 검사**: 사유가 OTHER인데 `detail`이 null이거나 trim 후 빈 문자열이면
   `DETAIL_REQUIRED`(11401)를 던진다. 길이 상한은 DTO의 `@Size`가 이미 걸렀다.
3. **영상 검증**: `videoRepository.findById(videoId)`로 조회한다. 행이 없거나, DELETED이거나,
   BLINDED이면 `VideoErrorCode.VIDEO_NOT_FOUND`(3404)를 던진다. 재생 경로
   (`VideoServiceImpl.getVideoPlayback`, MSG-206)의 존재 은닉 규칙과 같다. 재생 경로는
   소유자에게만 BLINDED 통과를 허용하지만, 신고 경로는 자기 영상 신고 자체가 불가라 그 구분이
   필요 없다. BLINDED는 소유자 여부와 무관하게 404다.
4. **자기 영상 검사**: `video.getUserId() == userId`이면 `SELF_REPORT`(11402)를 던진다.
   본인 영상 정리는 삭제 기능 몫이다 (FR-4).
5. **중복 검사**: `reportRepository.existsByReporterIdAndVideoId(userId, videoId)`가 true면
   `DUPLICATE_REPORT`(11409)를 던진다. 이 조회는 V27 유니크 제약이 만드는
   (reporter_id, video_id) 인덱스를 탄다.
6. **저장**: `Report.create(userId, videoId, reason, detail)`로 PENDING 행을 만들어
   `saveAndFlush`로 저장한다. 같은 순간 들어온 두 요청은 5번 검사를 둘 다 통과할 수 있으므로,
   늦은 INSERT의 유니크 위반(`DataIntegrityViolationException`[^4])을 catch해
   `DUPLICATE_REPORT`(11409)로 변환한다 (PRD 시퀀스 다이어그램 그대로). `save`가 아니라
   `saveAndFlush`인 이유: flush를 커밋 시점까지 미루면 위반 예외가 catch 블록 바깥
   (트랜잭션 커밋)에서 터져 500이 되기 때문이다.

접수는 여기서 끝난다. 어떤 자동 블라인드 판정도, 신고 건수 집계도, 알림도 없다 (확정 2번,
PRD 비목표). `detail`은 OTHER가 아닌 사유에서도 값이 오면 그대로 저장한다.

### 패키지 의존

`ReportServiceImpl`은 `VideoRepository`를 직접 주입받는다 (D4). moderation과 video는 둘 다
Owner B라 A와 B 사이의 계약 인터페이스가 필요한 경계가 아니고, PRD §6 클래스 다이어그램이
이 의존을 명시했다. B 내부의 video 참조 선례로는 friend의 `VideoService` 주입이 있다.

## 데이터 모델

### 기존 테이블: `reports` (V1 224~242행, 코드 미사용 상태)

reporter_id(users FK, ON DELETE CASCADE는 V15에서 교체), video_id(videos FK NOT NULL,
ON DELETE CASCADE), reviewed_by, reason VARCHAR(20) CHECK 5종, status VARCHAR(10) DEFAULT
'PENDING' CHECK 4종, reviewed_at, created_at. 인덱스는 (video_id, status)와
PENDING 한정 partial(created_at). 유니크 제약과 상세 텍스트 컬럼이 없어 V27이 보탠다.

### 마이그레이션: `V27__reports_detail_and_unique.sql` (현재 최신 V26 확인함)

```sql
-- 신고 접수(MSG-192): 상세 설명 컬럼 + 중복 신고 방지 유니크 제약.
-- reports 는 지금까지 쓰는 코드가 없어 기존 행이 0건, 제약 추가가 실패할 데이터 위험 없음 (PRD §4).
ALTER TABLE reports
	ADD COLUMN detail VARCHAR(500);

ALTER TABLE reports
	ADD CONSTRAINT uq_reports_reporter_video UNIQUE (reporter_id, video_id);
```

`detail`은 NULL 허용이다. OTHER 필수 규칙은 사유별 조건이라 DB가 아닌 서비스 레이어가 검사한다
(도메인 로직 2번). 유니크 제약에 status 조건이 없는 이유는 D3 참조.

### 엔티티: `moderation/entity/Report.java`

`@Table(name = "reports")`, id는 BIGSERIAL 대응 `GenerationType.IDENTITY`. 필드는
reporterId(Long), videoId(Long), reason(`ReportReason`, `@Enumerated(EnumType.STRING)`,
length 20), status(`ReportStatus`, `@Enumerated(EnumType.STRING)`, length 10),
detail(String, length 500, nullable), createdAt(`@CreationTimestamp`, updatable false,
Friendship 선례). 정적 팩토리 `Report.create(...)`가 status를 PENDING으로 초기화한다.
`@NoArgsConstructor(access = AccessLevel.PROTECTED)`, `@Getter`, Setter 없음.

`reviewed_by`, `reviewed_at` 컬럼은 이번에 매핑하지 않는다 (D6). MSG-192는 쓰지 않는 필드고,
검토 흐름을 만드는 MSG-195가 자기 요구에 맞게 추가하는 편이 검증 없는 선매핑보다 낫다.

`ReportReason`(INAPPROPRIATE, PRIVACY, SPAM, COPYRIGHT, OTHER)과
`ReportStatus`(PENDING, REVIEWING, RESOLVED, REJECTED)는 V1 CHECK 제약 값과 문자열까지
일치해야 한다. VideoStatus처럼 "DDL CHECK와 일치" 주석을 남긴다.

### 에러 코드: `moderation/exception/ReportErrorCode.java`

developCode 11xxx 대역을 moderation 도메인으로 신설한다. **`.claude/rules/response-pattern.md`
대역표에 11xxx 행을 추가하는 커밋이 이 enum 커밋보다 먼저 들어가야 한다** (대역 선점 경합 방지
규칙, 표가 단일 정본, MSG-178/185의 9400 동시 점유 실측 사건이 근거). 뒷자리는 HTTP 상태 에코,
겹치면 의미 구분 우선 (FriendErrorCode 선례).

```java
INVALID_REASON(11400, HttpStatus.BAD_REQUEST,
	"reason 은 INAPPROPRIATE, PRIVACY, SPAM, COPYRIGHT, OTHER 중 하나여야 합니다"),
DETAIL_REQUIRED(11401, HttpStatus.BAD_REQUEST, "OTHER 사유는 상세 설명이 필요합니다"),
SELF_REPORT(11402, HttpStatus.BAD_REQUEST, "자기 영상은 신고할 수 없습니다"),
DUPLICATE_REPORT(11409, HttpStatus.CONFLICT, "이미 접수된 신고입니다"),
```

404는 이 enum에 없다. `VideoErrorCode.VIDEO_NOT_FOUND`를 재사용하기 때문이다 (D1).

## 문서 갱신 (구현과 같은 브랜치에서)

1. `.claude/rules/response-pattern.md` 대역표에 `11xxx | moderation | 11409 DUPLICATE_REPORT (MSG-192)` 행 추가. **선행 커밋** (D5).
2. `.claude/docs/infrastructure.md` 패키지 구조에 `com.msg.fillmap.moderation.*` 추가, Owner B 명시.
3. `.claude/docs/status.md`에 moderation 패키지와 신고 접수 API 반영.
4. `.claude/CLAUDE.md` 협업 원칙 요약의 Owner B 목록에 `com.msg.fillmap.moderation.*` 추가
   (PRD §7 목록에는 없지만, 이 요약이 B 패키지를 전부 나열하는 관례라 누락되면 다음 티켓의
   Owner 판정이 어긋난다).

## 미해결 질문 (Open Questions)

이번 구현을 막지는 않는다. PRD §8에서 이월된 항목 포함.

- 지라 MSG-192 제목 정정("영상/사용자 신고 접수 API" → "영상 신고 접수 API") 반영 여부.
  사용자 확인 필요 (PRD §8 이월).
- FE 신고 모달에 상세 설명 입력란 추가 요청. 디자인 실사 기록에는 사유 선택만 있어 FE와
  디자인에 전달이 필요하다 (PRD §8 이월).
- 신고 접수 rate limit(같은 사용자의 다수 영상 연속 신고) 필요 여부. 유니크 제약은 같은 영상
  재신고만 막는다. 남용이 관찰되면 요구사항 신설이므로 PRD부터 거친다.

[^1]: 유니크 제약(unique constraint): 같은 값 조합의 행이 두 번 저장되는 것을 DB가 거부하는
    규칙. 애플리케이션 검사만으로는 같은 순간에 들어온 두 요청을 막지 못해 DB 제약이 최종
    방어선이 된다. 제약을 만들면 해당 컬럼 조합의 인덱스가 함께 생긴다.
[^2]: 존재 은닉: 권한이나 상태 문제로 막을 때 403 대신 404를 돌려줘 리소스의 존재 자체를 숨기는
    응답 방식. 신고 경로가 재생 경로와 다른 응답을 주면 신고 API가 영상 존재를 알아내는 우회
    창구가 된다.
[^3]: Bean Validation: `@Valid`가 붙은 요청 DTO의 `@NotBlank`, `@Size` 같은 어노테이션 제약을
    스프링이 바인딩 시점에 검사하는 표준. 실패는 GlobalExceptionHandler가 공통 BAD_REQUEST(400)에
    필드별 메시지를 붙여 변환하므로 도메인 에러 코드가 필요 없다.
[^4]: DataIntegrityViolationException: DB 제약 위반(유니크, FK 등)을 스프링이 감싸 던지는 예외.
    JPA는 INSERT를 트랜잭션 커밋 직전까지 미룰 수 있어, 서비스 안에서 잡으려면 `saveAndFlush`로
    위반 시점을 메서드 안으로 당겨야 한다.
[^5]: first-match 판정: 여러 거부 조건을 정해진 순서로 검사해 처음 걸린 조건의 응답을 돌려주는
    방식. 순서가 바뀌면 같은 요청의 응답 코드가 달라지므로 순서 자체가 API 계약의 일부다.
