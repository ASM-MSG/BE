# MSG-283: AI 폴링 404 → 재제출 복구 (컨테이너 교체 시 잡 유실 대응)

**Owner**: B (video 도메인 — `com.msg.fillmap.video.*`)

> PRD 면제: 기존 요구사항("업로드 영상은 유실 없이 READY 또는 정당한 FAILED로 수렴")의 결함 복구.
> 요구사항 정본은 Jira MSG-283 티켓 본문 ("근거 문서 없음 — 이 티켓이 정본" 명시).

## 개요

`AiBlurPoller`가 AI 서버 폴링에서 **404(잡 없음)** 를 받으면 지금은 명시 `FAILED`와 동일하게
`markBlurFailed`로 보낸다 (`AiBlurPoller.poll()` L119-124: `if (result.notFound() || result.status() ==
AiJobStatus.FAILED)` — 하나의 분기). 404는 "이 잡은 존재하지 않는다"이지 "처리에 실패했다"가
아니므로, `ai_job_id`를 null로 되돌려 **기존 미제출 경로(D2)가 다음 주기에 재제출**하게 바꾼다.
AI 명시 `FAILED`는 지금처럼 즉시 실패 유지.

## 배경 · 목표

AI 서버 잡 저장소는 인메모리(`FillMap-AI/server.py`: `jobs = {}` + 단일 워커) — 재시작 시 진행 중
잡이 유실된다. MSG-282로 AI 레포 main 머지마다 컨테이너가 교체되므로, 그 순간 처리 중이던 사용자
영상이 "AI 처리 실패"로 죽는 게 정례화됐다. 목표: AI 컨테이너가 처리 도중 재시작돼도 영상이
READY로 수렴한다 (타임아웃 예산 내).

## 성공 기준

1. AI 컨테이너를 처리 도중 재시작(→ 폴링 404)해도 영상이 READY로 수렴한다 — 30분(`ai.timeout`) 내
2. AI 명시 `FAILED`는 즉시 FAILED로 남는다 (재제출하지 않음)
3. 재제출이 `blurringStartedAt`을 밀지 않는다 — 테스트로 고정
4. 404 → 재제출 → DONE 경로가 테스트로 커버된다

### D1. 404 분기 분리 — 미제출 복귀

`poll()`의 결합 분기를 둘로 나눈다:

- **`result.notFound()`** → `statusWriter.clearAiJob(video.getId(), video.getAiJobId())` 후 return.
  다음 주기에 `reconcileOne()`의 기존 미제출 경로(`aiJobId == null` → `failIfTimedOut` 검사 →
  `submit`)가 재제출한다. **새 재제출 경로를 만들지 않는다.**
- **`result.status() == AiJobStatus.FAILED`** → 현행 유지 (`markBlurFailed`).

404 분기에서 타임아웃 선검사는 하지 않는다 — clear 후 다음 주기 미제출 경로의 `failIfTimedOut`이
같은 판정을 하므로 중복이다 (수렴이 최대 1주기 ≤30초 늦을 뿐). 무한 재시도 방지도 같은 지점이
담당한다: AI가 재시작을 반복해도 `blurringStartedAt` 기준 `ai.timeout`(PT30M) 초과 시
`markBlurFailed(id, null, startedAt)` — clear 후 행은 jobId null·startedAt 유지라 가드
(`isCurrentBlurJob(video, null)` + startedAt 일치)를 정상 통과한다.

분기를 독립 `if` 블록 2개로 두는 형태 권장 — 후속 MSG-286(precheck 즉시 실패)이 같은 자리에
분기를 얹는다. **286 범위는 이번에 구현하지 않는다.**

### D2. `blurringStartedAt` 유지 (확정)

`clearAiJob`은 `aiJobId`만 null로 만들고 `blurringStartedAt`을 **건드리지 않는다**. 근거:

1. **타임아웃 상한 보존** — 갱신하면 AI 재시작이 반복될 때마다 30분 창이 리셋돼 영원히 안 끝난다.
   `blurringStartedAt`은 "이번 BLURRING 시도"의 넌스이고, 재제출은 새 시도가 아니라 같은 시도의
   계속이다 (새 시도 = `markEncoded`가 새로 찍는 지점, 실측 `Video.markEncoded()` L153-157).
2. **재제출 가드 통과** — `recordAiJob`의 `isCurrentAttempt`가 startedAt 일치를 요구한다. 유지해야
   재제출의 jobId 기록이 통과한다 (폴러는 매 주기 fresh 조회하므로 유지된 값이 그대로 전달됨).

### D3. `VideoStatusWriter.clearAiJob` — 신규 폴러 쓰기

```java
@Transactional(propagation = Propagation.REQUIRES_NEW)
public void clearAiJob(Long videoId, String expectedJobId)
```

- 기존 폴러 쓰기 패턴 그대로: `findWithLockById` → `isCurrentBlurJob(video, expectedJobId)` 가드 →
  불일치면 `logStaleSkip`. 통과 시 `video.clearAiJob()` (엔티티 신규 메서드: `this.aiJobId = null` 한 줄).
- `expectedStartedAt` 파라미터는 받지 않는다 — `markBlurFailed`가 startedAt까지 보는 이유는 "미제출
  행(jobId null)끼리 jobId로 구분 불가"(실측 주석 P2-a)인데, `clearAiJob`은 poll 경로에서만 호출되므로
  `expectedJobId`가 항상 non-null이라 jobId 일치만으로 시도가 유일하게 식별된다. 교체는 `replaceFile`이
  `aiJobId`를 null로 밀어 불일치(skip), 삭제는 `status != ACTIVE`로 skip.

### D4. 재제출 시 잡 정체성(P1/P2) 영향 — 없음 (근거)

- **옛 잡의 스테일 쓰기**: 폴러는 단일 스레드(`@Scheduled(fixedDelay)` — 폴 중첩 없음, 실측 클래스
  주석)라 clear와 동시에 진행 중인 옛 잡 판단이 없다. 혹시 남는 옛 jobId 기준 쓰기가 있어도 clear
  이후 `isCurrentBlurJob`이 jobId 불일치로 skip한다.
- **재제출의 `recordAiJob`**: clear 후 행 = ACTIVE·BLURRING·jobId null·startedAt 유지 →
  `isCurrentAttempt` 4조건 전부 충족, 정상 기록. 첫 제출과 완전히 같은 경로.
- **새 잡의 완료/실패**: 새 jobId로 `markBlurReady`/`markBlurFailed` — 가드가 새 jobId와 대조하므로
  현행과 동일하게 동작.
