## 개요

업로드 이벤트마다 `streaks`(V1 실존, 코드 전무)를 KST 일 단위로 갱신하고, 갱신 직후 꾸준함 뱃지
(STREAK_3/7/30 — V10 시딩)를 판정해 업로드 응답 `newBadges`에 동봉한다.

```
POST /api/videos (업로드, 기존)
  ├─ videos INSERT · user_grids UPSERT · 뱃지 훅(UPLOAD_COUNT · 첫 수집 시 TOTAL_GRIDS/REGION_PERCENT)   ← 기존 (66/155/239)
  ├─ [신규 훅] StreakCommandService.recordUpload(userId)      ← 모든 업로드(재방문 포함), 같은 트랜잭션
  │    ├─ streaks lazy UPSERT (같은 날 카운트 no-op / 어제 +1 / 그 외 1 리셋 — KST 자정 경계)
  │    └─ BadgeAwardService.award(userId, STREAK_DAYS, currentCount)   ← 239 §D2 위임 이행
  └─ 응답: 기존 newBadges 에 STREAK 뱃지 합류 (형태 불변)
```

신규 API 없음. V10은 STREAK_3/7/30 **시딩만** — 소급(백필) 없음, 전원 0부터(§D6).

## 성공 기준 (관찰 가능)

1. V10 적용 후 `badges`에 `STREAK_3`·`STREAK_7`·`STREAK_30`이 시딩되어 있다(code 유일).
   MISSION_COUNT·SPECIAL은 여전히 미시딩(239 §D2 잔여). **소급 지급분 0건**(§D6).
2. 업로드하면 `streaks` 행이 lazy 생성되고, `last_recorded_date`(KST) 대비 오늘(KST) 기준
   같은 날 카운트 no-op / 어제 +1 / 그 외 1 리셋로 갱신된다(§판정 로직 — no-op은 카운트 기준,
   `updated_at`은 갱신됨). `max_count`는 리셋에도 유지.
3. 같은 날 N회 업로드해도 스트릭은 1일로 센다(카운트 no-op). 재방문 업로드도 인정 이벤트다.
4. 3일 연속 업로드의 3일째 응답 `newBadges`에 `STREAK_3`이 실리고 `notified_at`이 기록된다.
   동시 업로드 경합에서도 `user_badges` 중복 없음(239 엔진 그대로 — FR-3).
5. 영상 삭제·교체 경로는 스트릭·뱃지 코드 0줄 — `deleteVideo`·`replaceVideo` 무변경(§D4).
6. 크로스오너 계약 4종 Java 시그니처 불변. 공유 로컬 DB 미오염, 전체 테스트 green.

## 결정 (Decisions)

### D1 — 인정 이벤트 = 아무 업로드(재방문 포함) — 기획 확정 인용, 비결정

glossary 스트릭 항목(2026-07-29 확정)·PRD 라인업 표("재방문 포함")의 확정 사항을 그대로 따른다.
신규 격자 점령 불요. 훅 위치가 `!alreadyOccupied` 분기 **바깥**인 근거가 이것이다. 교체
(`replaceVideo`)는 새 videos 행이 없는 파일 교체(glossary "방문 = videos 1 row")라 인정 이벤트가
아니다 — 무변경(§D4).

### D2 — freeze(끊김 유예) 미도입 (사용자 확정 — 티켓 미확정 종결)

- **결정**: 하루라도 빠지면 즉시 1로 리셋. 유예·아이템·복구 장치 없음.
- **근거**: glossary "끊김 유예(freeze)는 미확정 — MVP 미도입 제안"을 결정으로 승격. 스키마
  (`current_count`·`last_recorded_date`)가 단순 유지되고, 도입 시에도 판정 CASE의 "어제" 분기를
  "어제 또는 freeze 소진"으로 넓히면 되므로 지금 구조가 확장을 막지 않는다.

### D3 — 일 경계 = KST(Asia/Seoul) 자정 고정, 판정 시각 = 서버 처리 시각

- **결정**: 사용자별 타임존 없음(users에 타임존 컬럼 없음, MVP 한국 대상 — glossary 확정).
  DB TIMESTAMP는 UTC 저장이므로 날짜 판정은 SQL 안에서 `(now() AT TIME ZONE 'Asia/Seoul')::date`로
  KST 변환 후 `last_recorded_date`(DATE, KST 일자)와 비교한다. 애플리케이션 코드에 시계·타임존
  로직 0 — 전부 UPSERT 한 문장 안(§D5).
- **세션 타임존 독립성**: SQL의 시간식은 전부 명시 변환(`now() AT TIME ZONE 'Asia/Seoul'` /
  `AT TIME ZONE 'UTC'`)이라 세션 타임존 설정에 의존하는 표현이 없다 — 세션 TZ 독립성은 구조적으로
  보장, 별도 테스트 불요.
- **판정 시각 = 서버 수신 시각(now())**: `recordedAt`(영상 촬영 시각, 클라이언트 신고값)이 아니다 —
  스트릭은 "기록한 날"(업로드 행위)의 연속이고, 촬영 시각 기준이면 과거 영상 갤러리 업로드로
  스트릭을 소급 조작할 수 있다.

### D4 — 영상 삭제·점령 롤백 시 스트릭 소급 차감 없음 (사용자 확정)

- **결정**: 삭제로 그날 업로드가 0건이 되어도 `current_count`·`last_recorded_date`를 되돌리지
  않는다. `deleteVideo` 무변경(코드 0줄).
- **근거**: 스트릭은 "업로드한 날"의 사실 기록 — 뱃지 비회수 원칙(239 FR-5 "획득 이력은 과거 행동의
  사실")과 동형. 차감하려면 일자별 업로드 존재 여부 역산이 필요한데(그날 다른 영상이 남아 있으면
  유지) 그 복잡도가 얻는 것이 없다. glossary 점령 롤백은 `user_grids` 소관이지 streaks와 무관.

### D5 — streaks row lazy 생성, 갱신 = native `INSERT … ON CONFLICT (user_id) DO UPDATE` 한 문장, 업로드 훅 동기 처리

- **결정**: 행 사전 생성 없음(V1에도 시딩 없음) — 첫 이벤트 때 UPSERT로 생성. 3분기(같은 날/어제/
  리셋)를 CASE 식으로 한 문장에 넣어 **원자 처리**한다(정확한 SQL은 §판정 로직). 갱신은 업로드
  트랜잭션 참여 동기 처리(155/239 배선 선례) — 별도 트랜잭션·비동기 없음.
- **경합**: user_id PK 단일 행이라 동시 업로드는 ON CONFLICT의 행 잠금으로 직렬화된다 — 두 번째
  트랜잭션은 첫 커밋을 기다린 뒤 "같은 날" 분기로 no-op. advisory lock·재시도 불요.
- **갱신 후 current_count 읽기는 별도 SELECT 1회**(PK 조회): Spring Data `@Modifying`은 RETURNING
  결과 행을 못 돌려준다(239 §D5 기각 논리 동일). 같은 트랜잭션이고 UPSERT가 행 잠금을 쥔 상태라
  읽기 정합 문제 없음.

### D6 — 소급(백필) 없음 — 전원 0부터 시작 (사용자 확정, 239 §D9 소급 원칙의 예외)

- **결정**: V10은 STREAK_3/7/30 **시딩만**. 스트릭 역산 SQL도, 뱃지 소급 INSERT 블록도 없다.
- **근거(예외 명시)**: 239 §D9의 "시딩 마이그레이션 동반 set-based 소급"은 **기존 데이터로 판정
  가능한 축**에 한한다(FR-10). STREAK_DAYS의 metric 원천인 `streaks`는 빈 테이블 — 소급하려면
  전 사용자의 videos 업로드 이력을 KST 일자로 역산해야 하는데, 출시 전(실사용자 없음)이라 역산
  대상 자체가 없다. V10 파일 주석에 이 예외를 명시한다 — 이후 시딩 마이그레이션이 이 파일을
  "소급 생략 선례"로 오인하지 않게.

### D7 — 배선 방향: streak 도메인이 `award()`를 호출하고 획득 뱃지를 반환 — video 훅은 1줄

- **결정**: `StreakCommandService.recordUpload(long userId)` → `List<EarnedBadgeResponseDto>` —
  내부에서 ① UPSERT ② current_count 읽기 ③ `badgeAwardService.award(userId, STREAK_DAYS,
  BigDecimal.valueOf(currentCount))` 호출까지 하고 신규 획득분을 반환한다. `VideoServiceImpl`은
  `newBadges.addAll(streakCommandService.recordUpload(userId))` 1줄만 안다.
- **근거**: `BadgeAwardService` javadoc의 설계 의도 그대로 — "범용 award는 후속 티켓이 **자기
  도메인에서 계산한 metric**을 직접 넘기는 진입점". metric(currentCount)의 원천이 streaks이므로
  계산·배선 모두 streak 도메인 몫이다. video가 `BadgeConditionType`·streak repository를 몰라도
  된다(239 리팩터링 c544366과 같은 원칙 — 타 도메인 접점은 Service 계층까지).
- **기각**: video가 recordUpload로 count를 받아 직접 award 호출 — video에 badge enum 의존이 다시
  생기고(c544366 역행), 훅이 2줄이 될 뿐 얻는 게 없다.

### D8 — 조회 API 없음 — 이 티켓은 집계·갱신까지 (사용자 확정)

- **결정**: `GET` 엔드포인트·DTO 노출 없음. `currentStreak`/`maxStreak`의 사용자 노출은 도감
  summary(별도 티켓) 소관 — 그때 `streaks` PK 읽기면 충분하다.
- **함의**: `Streak` 엔티티는 매핑만 신설(테스트·후속 read 대비), 쓰기는 전부 native UPSERT.

## 도메인 로직

### 1. 스트릭 갱신 판정 (`StreakRepository.upsertOnUpload` — native, `@Modifying @Query nativeQuery`)

`last_recorded_date`(KST) 대비 오늘(KST):
- **같음** → 카운트 no-op (그날 두 번째 이후 업로드 — `current_count`·`max_count` 불변.
  no-op은 카운트 기준이다: `last_recorded_date`는 동일값 재기록, `updated_at`은 갱신됨
  — 마지막 이벤트 시각 추적. **행 전체 no-op 아님**)
- **어제** → `current_count + 1`, `max_count = GREATEST(max, current)`
- **그 외**(NULL = 첫 기록 포함) → `current_count = 1`

```sql
-- upsertOnUpload — 3분기 CASE 를 한 문장에: user_id PK 단일 행이라 ON CONFLICT 행 잠금이
-- 동시 업로드를 직렬화한다 (§D5). 날짜는 KST 변환 후 비교 (§D3 — DB TIMESTAMP 는 UTC 저장).
INSERT INTO streaks (user_id, current_count, max_count, last_recorded_date, updated_at)
VALUES (:userId, 1, 1, (now() AT TIME ZONE 'Asia/Seoul')::date, now() AT TIME ZONE 'UTC')
ON CONFLICT (user_id) DO UPDATE SET
	current_count = CASE
		WHEN streaks.last_recorded_date = (now() AT TIME ZONE 'Asia/Seoul')::date
			THEN streaks.current_count                                  -- 같은 날: 카운트 no-op (updated_at 은 아래에서 갱신)
		WHEN streaks.last_recorded_date = (now() AT TIME ZONE 'Asia/Seoul')::date - 1
			THEN streaks.current_count + 1                              -- 어제: 연속 +1
		ELSE 1                                                          -- 끊김·첫 기록(NULL): 1 리셋
	END,
	max_count = GREATEST(streaks.max_count, CASE
		WHEN streaks.last_recorded_date = (now() AT TIME ZONE 'Asia/Seoul')::date
			THEN streaks.current_count
		WHEN streaks.last_recorded_date = (now() AT TIME ZONE 'Asia/Seoul')::date - 1
			THEN streaks.current_count + 1
		ELSE 1
	END),
	last_recorded_date = (now() AT TIME ZONE 'Asia/Seoul')::date,   -- 같은 날엔 동일값 재기록
	updated_at = now() AT TIME ZONE 'UTC'                           -- 같은 날에도 갱신 — 마지막 이벤트 시각 추적
```

- `max_count`의 CASE 중복은 의도 — SQL SET 절은 같은 문장의 갱신값을 참조할 수 없다.
- `updated_at`은 `AT TIME ZONE 'UTC'` 명시 — 세션 타임존 무관하게 UTC 저장(glossary 규칙) 보장.
  시간식 전부가 명시 변환이라 세션 TZ 의존 표현 없음(§D3).
