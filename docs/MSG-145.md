## 개요

AI 서버가 돌려주는 **블러 처리본**과 **하이라이트 구간**을 `videos` 행에 저장할 컬럼을 V3로 추가한다.
스키마·엔티티 매핑까지만 하고, AI 호출·폴링·상태 전이 오케스트레이션은 후속 티켓(MSG-149/150)이 쓴다.

## 배경 · 목표

- FillMap은 업로드 영상을 AI 서버에 보내 얼굴·번호판을 블러 처리하고 하이라이트 구간을 뽑는다(에픽).
  이 결과를 담을 자리가 현재 스키마에 없다 — ERD 정렬 문서 B-4가 지목한 갭이다.
- **목표**: 블러본 S3 key, 하이라이트 구간, AI 잡 상관키를 저장할 컬럼 3개를 V3로 추가하고 `Video`
  엔티티에 매핑한다. `processing_status`의 기존 `BLURRING` 값을 이 파이프라인이 활용하도록 명문화한다.

---

## 계약 (AI 서버 — 정본 `FillMap-AI/README.md`)

비동기. BE가 업로드 후 폴링하며 `processing_status`를 갱신한다(1080p 30초 ≈ 3~4분 실측).

| 메서드 | 경로 | 응답 |
|---|---|---|
| `POST` | `/jobs` | `202 {job_id, status}` — multipart `file` 업로드 |
| `GET` | `/jobs/{id}` | `{job_id, status, highlights, error}` — 폴링 |
| `GET` | `/jobs/{id}/video` | 블러 처리본 mp4(h264, 오디오 유지). 완료 전 409 |

- `status` 전이: `QUEUED → PROCESSING → DONE | FAILED`. BE 매핑: **`PROCESSING` → `processing_status=BLURRING`**.
- `highlights`: 완료 시 `[[시작초, 끝초], …]` **최대 3구간**. **0구간 가능**(폴백 존재하나 실패 케이스 있음).
- **블러본은 BE가 받아 S3에 올린다** → 그때 채워지는 값이 `blurred_s3_key`(업로드 로직은 MSG-147 잔여/MSG-150).

이 티켓은 위 계약의 **저장 자리만** 만든다. 호출·폴링·상태전이 로직은 쓰지 않는다(§범위 밖).

## 성공 기준

1. `V3__videos_ai_blur_result.sql`이 `videos`에 `blurred_s3_key`·`highlights`·`ai_job_id` 3컬럼을 추가한다.
2. `highlights`는 JSONB이고 **CHECK 제약으로 최대 3구간을 강제**한다(NULL 허용).
3. `processing_status` CHECK는 이미 `BLURRING`을 포함(`V1__init.sql:101`) → **DDL 변경 없음**, 문서로만 활용 명문화.
4. `Video` 엔티티에 3필드가 매핑되고 게터로 읽힌다. persist→find 라운드트립에서 값이 보존된다.
5. Flyway가 V3까지 적용된 상태로 전체 테스트 green.

## 설계 결정 (근거 포함)

| # | 포인트 | 결정 | 한 줄 근거 |
|---|---|---|---|
| D1 | 블러본 저장 위치 | **videos 컬럼 `blurred_s3_key`** | 영상 1개당 블러본 정확히 1개(1:1)·최종 재생본. 별도 테이블은 1:1에 조인만 얹는 과설계. `encoded_url`·`thumbnail_url`이 이미 videos에 사는 것과 정합 |
| D2 | 하이라이트 구조 | **JSONB 컬럼 `highlights`** | 최대 3구간 고정 소형 배열, 통째로 읽고 쓰는 불투명 값, 개별 구간 조회/조인 요구 없음. "JSONB 남발 금지"는 *관계로 표현되고 쿼리할 값을 JSONB에 숨기지 말라*는 뜻 — 여기선 조회 대상이 아니라 **적합 사례**. `video_highlights` 자식 테이블은 최대 3행짜리 FK·정렬 오버헤드만 발생 |
| D3 | AI job 추적 컬럼 | **`ai_job_id` 포함** | 비동기 결과를 올바른 행에 반영하려면 job↔video **상관키가 필수**(결과 저장의 일부지 폴링 기능이 아님). 서버 재시작 시 `WHERE processing_status='BLURRING'`로 복구. 컬럼만 추가, 폴링/기록 로직은 MSG-149/150. 별 컬럼으로 쪼개면 V4를 또 파야 함 |
| D4 | 엔티티 반영 범위 | **필드+게터 매핑 + 결과 저장 메서드 1개까지** | MSG-150이 바로 이어져 어차피 `Video.java`를 건드린다. 매핑을 이번에 끝내야 라운드트립 검증이 성립. **BLURRING 전이·폴링 오케스트레이션은 MSG-150**(도메인 메서드가 상태를 READY로 바꾸지 않음) |
| D5 | 파일명 | **`V3__videos_ai_blur_result.sql`** | V2 선점 반영 + 스네이크케이스 내용 요약 |

## 스키마 변경 (SQL 초안)

```sql
-- V3__videos_ai_blur_result.sql
-- MSG-145: AI 하이라이트·블러 결과 저장 스키마.
-- V2(MSG-132)가 선점 → V3. 기존 V 파일 수정 금지(MSG-130).

ALTER TABLE videos
	ADD COLUMN blurred_s3_key VARCHAR(500),  -- 블러 처리본 S3 key (1:1). BE가 AI에서 받아 S3 업로드(MSG-150)
	ADD COLUMN highlights     JSONB,         -- 하이라이트 구간 [[시작초,끝초],...] 최대 3. 0구간이면 [] 또는 NULL
	ADD COLUMN ai_job_id      VARCHAR(64);   -- AI 잡 상관키. 폴링 복구용(MSG-149 폴링, MSG-150 결과반영)

-- 최대 3구간 불변식을 DB에서 강제(AI가 malformed 반환해도 방어 — trust boundary)
ALTER TABLE videos
	ADD CONSTRAINT chk_videos_highlights_len
	CHECK (highlights IS NULL OR jsonb_array_length(highlights) <= 3);

COMMENT ON COLUMN videos.blurred_s3_key IS '블러 처리본 S3 key (MSG-145)';
COMMENT ON COLUMN videos.highlights     IS '하이라이트 구간 [[시작초,끝초],...] 최대 3 (MSG-145)';
COMMENT ON COLUMN videos.ai_job_id      IS 'AI 서버 job_id 상관키 (MSG-145)';
```

- 팀 합의(위키 `03-specs/…자료형·ENUM·GeoJSON 기준`) 정합: S3 key는 **코드류 → VARCHAR**(`original_s3_key`와 동일 500),
  하이라이트는 **필요한 곳에만 JSONB**, ENUM은 이미 VARCHAR+CHECK(`processing_status`), 신규 timestamp 없음(UTC 규칙 무관).
- `ai_job_id` **인덱스/UNIQUE 없음** — 조회는 `processing_status='BLURRING'` 기준이라 job_id 룩업 불필요(YAGNI, 필요 시 후속).
- `jsonb_array_length`는 **최상위가 JSON 배열이 아니면 에러** → 배열 형태 자체도 사실상 강제된다.

## 엔티티 매핑

```java
@Column(name = "blurred_s3_key", length = 500)
private String blurredS3Key;

@JdbcTypeCode(SqlTypes.JSON)
@Column(name = "highlights", columnDefinition = "jsonb")
private List<List<Double>> highlights;   // [[시작초,끝초],...] 초는 소수점(AI round(x,2)) — 리뷰: raw String 매핑 대안 가능

@Column(name = "ai_job_id", length = 64)
private String aiJobId;
```

- 게터는 `@Getter`가 생성. `List<List<Double>>` + Hibernate 6 `@JdbcTypeCode(SqlTypes.JSON)`이면 JSONB 라운드트립이 네이티브로 된다.
  값 세팅은 결과 저장 도메인 메서드 1개(`applyBlurResult(blurredKey, highlights)`)로 캡슐화 — **상태를 READY로 바꾸지 않는다**(그 전이는 MSG-150).
- `Video.create` 팩터리·생성자는 무변경(신규 컬럼은 전부 nullable, 업로드 시점엔 비어 있음).

## 테스트 시나리오 (JUnit5 + AssertJ · 한국어 백틱 메서드명)

`@SpringBootTest` + `local` 프로파일(실 PostGIS·Flyway V3까지 적용).

### Flyway 마이그레이션 적용
- `V3_마이그레이션_적용_후_videos에_세_컬럼이_존재한다` (information_schema 조회)
- `BLURRING은_processing_status_CHECK를_통과한다` (기존 CHECK 활용 확인 — DDL 무변경 회귀)

### 엔티티 라운드트립
- `블러본키와_하이라이트를_저장하고_다시_읽으면_값이_보존된다` (persist → flush/clear → find)
- `하이라이트_JSONB는_구간_배열로_라운드트립된다` (`[[0.0,3.33],[3.33,6.67]]` 등 소수점 초 저장·복원)
- `하이라이트가_없으면_null로_저장된다` (0구간·미처리 케이스)

### CHECK 제약 위반
- `하이라이트가_4구간이면_제약_위반으로_저장에_실패한다` (`chk_videos_highlights_len`)
- `하이라이트가_빈배열이면_저장된다` (0구간 폴백 — `[]` 허용)
