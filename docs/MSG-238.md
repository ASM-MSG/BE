## 개요

행정동 하나를 축으로, 그 행정동 격자들에 쌓인 **전역 공개 콘텐츠**(타인 영상 포함)를 세 화면이 소비한다.
전 구간 read 전용 — 저장된 라벨(`grids.region_code`)과 전역 노출 게이트(`ACTIVE·PUBLIC·READY`)를 equi로만 읽는다.

```
[③ 전체 지역]   GET /api/regions/explore                     행정동별 격자 수 리스트 (검색 무입력 드롭다운)
                     │ 행정동 선택
                     ▼
[①② 패널·뷰]   GET /api/regions/{regionCode}/grids           격자 카드 리스트 + 헤더 카운트(격자 N·영상 M)
                 패널 = ?limit=3 (지도 홈)  /  전체 보기 = limit 생략 + sort 칩(인기순|최신순)
                     │ 격자 카드 탭
                     ▼
[후속: MSG-237]  GET /api/grids/{gridId}/videos               격자 전역 영상 목록 → [MSG-206] 재생
```

지도 홈 패널의 regionCode는 FE가 지도 중심 좌표로 `GET /api/regions/reverse-geocode`(93)를 호출해 얻는다(기존 API,
본 티켓 무변경). 카드 = 대표 썸네일(87 규칙) + duration 뱃지 + 격자명(FE 행정동 폴백) + "N개 영상".

## 배경 · 목표

- **사용자/제품 관점**: 지도 홈은 개인 도감(내 격자)만 색칠한다. 사용자가 "지금 이 동네에 뭐가 쌓여 있나"를 보려면
  전역 축 진입로가 없다 — 패널이 지역의 콘텐츠 밀도(격자 N·영상 M)를 보여주고, 전체 보기가 격자 단위로 브라우징을 열고,
  검색 무입력 리스트가 "어디에 콘텐츠가 많은가"로 지역 발견을 돕는다. 셋 다 **같은 행정동 축·같은 카운트 정의**여야
  숫자가 화면 간에 어긋나지 않는다.
- **목표**:
  1. 행정동 격자 카드 리스트 + 헤더 카운트 API 1종(`GET /api/regions/{regionCode}/grids` — 패널·썸네일 뷰 공용, §D2).
  2. 전체 지역(행정동별 격자 수) 리스트 API 1종(`GET /api/regions/explore`).
  3. 카운트·카드 포함 기준을 **전역 노출 게이트 단일 정의**로 고정(§D1) — 패널 N·M = 썸네일 뷰 카드 집합 = 전체 지역 카운트.
  4. `grids.region_code` **주도** 조회의 물리 기반 `idx_grids_region_code`(V7) 신설 — 조회 경로 geospatial 0 유지.

## 성공 기준 (관찰 가능)

1. `GET /api/regions/{regionCode}/grids`가 그 행정동 격자들의 **전역 카드 리스트**(전역 노출 게이트 통과 영상 ≥1인 격자만)
   + 헤더 카운트(`gridCount`·`videoCount`)를 반환한다. 각 카드 = `gridId`·`gridY`·`gridX`·`videoCount`(그 격자의 게이트
   통과 영상 수)·`coverThumbnailUrl`(presigned)·`coverDurationSec`.
2. **카운트 단일 정의(§D1)**: `gridCount` = 카드 집합 크기, `videoCount` = 카드 `videoCount` 합 — `limit`을 지정해도
   카운트는 전체 기준이라 패널("격자 5개 · 영상 355개")과 전체 보기 카드 수가 **항상 일치**한다.
3. **게이트 준수(162 MUST)**: PRIVATE만 있는 격자·인코딩 중 영상만 있는 격자는 카드·카운트에 **절대 포함되지 않는다**.
   DELETED/BLINDED 영상은 집계 제외. 내 PRIVATE 영상도 전역 탐색엔 안 잡힌다(87/237 전역 축과 동일).
4. **커버 = 87 대표와 동일 영상**: 각 카드의 커버는 그 격자 `findGlobalCover` 결과와 같은 영상이다(조회수→최신→id 3키 1건,
   §D7 — 87 쿼리도 3키로 정합).
5. **정렬**: `sort=POPULAR`(기본)는 격자 조회수 합 내림차순(동률 시 영상 수→gridId 내림차순으로 결정적),
   `sort=LATEST`는 격자의 최신 공개 영상 시각 내림차순(동률 시 gridId 내림차순). 무효 sort 값은 400.
6. **격자 축 귀속(167 계승)**: 영상 좌표가 옆 행정동이어도 격자 소속 행정동(`grids.region_code`) 기준으로 잡힌다.
   무라벨(해안) 격자는 어떤 행정동 탐색에도 나오지 않는다.
7. `GET /api/regions/explore`가 **게이트 통과 격자가 1개 이상인 행정동만** `{regionCode, regionName, gridCount}`로
   격자 수 내림차순 반환한다. 각 행정동의 `gridCount`는 ①의 카드 집합 크기와 일치한다.
8. 미존재/무콘텐츠 regionCode → **404가 아니라 200** + `gridCount 0`·`videoCount 0`·`grids []`(regionName은 실존 시 이름,
   미존재 시 null). 전역 콘텐츠가 하나도 없으면 explore는 빈 배열 200.
9. **조회 경로 geospatial 0**: 세 쿼리 전부 equi/PK/btree만(쿼리 문자열에 `ST_` 없음). `ST_Covers` 판정은 이 티켓에 0회.
10. `V7__grids_region_code_index.sql` 추가 후 ① 쿼리 플랜이 `idx_grids_region_code`를 탄다(EXPLAIN — DoD 수동 검증).
    V1~V6 무수정. 크로스오너 계약 4종 Java 시그니처 불변. **신규 에러코드 0**. 공유 로컬 DB 미오염, 전체 테스트 green.

## 결정 (Decisions)

### D1 — 카운트·카드 포함 기준 = **전역 노출 게이트(ACTIVE·PUBLIC·READY) 영상 ≥1 격자** — 세 표면 단일 정의 (티켓 미확정 "격자 N 카운트 정의" 해소)

- **결정**: "격자 N개" = 그 행정동에서 **전역 노출 게이트를 통과한 영상이 1건 이상인 격자 수**. "영상 M개" = 그 격자들의
  게이트 통과 영상 총수. 썸네일 뷰 카드 집합·전체 지역 리스트의 행정동별 격자 수도 **같은 정의**를 쓴다.
- **근거**:
  1. **표면 간 일관성**: 패널이 "격자 5개"라는데 전체 보기에 카드가 3개면 결함으로 보인다. 카운트 = 카드 집합 크기를
     정의 차원에서 강제하면 어긋날 수 없다(성공 기준 2·7).
  2. **전역 탐색의 의미**: 이 화면은 "볼 수 있는 콘텐츠"의 밀도다 — 볼 수 없는 격자(비공개만·인코딩만)를 세면
     탭했을 때 빈 화면이 나오는 유령 카드가 된다. 게이트는 162 §도메인3 MUST("모든 공개 노출 쿼리는 READY 강제")의
     준수 지점이기도 하다.
  3. **glossary 정합**: "전역 격자 등록(grids row 존재)"은 백엔드 전용 개념으로 사용자 노출 금지다 — grids row 수를
     그대로 세면 그 개념이 UI 숫자로 샌다. 게이트 기준 카운트는 "공개 영상이 있는 격자"라는 사용자 언어로 설명된다.
- **기각**:
  - **② grids row 수(전역 등록 격자 수)**: 비공개·인코딩만 있는 격자가 카운트에 잡혀 카드 없는 수가 된다 + glossary
    노출 금지 개념. (기획 의도가 이쪽이면 Open Q3 — 쿼리 1곳 수정으로 전환 가능하나 카드 집합과의 불일치를 낳아 비권장.)
  - **③ `regions.total_grid_count`(이론 격자 수)**: 개인 수집률(155/156)의 **분모** 축이다 — 탐색 밀도와 무관하고,
    디자인의 "격자 1,240" 같은 숫자를 이 값으로 읽으면 콘텐츠 0인 지역도 수천으로 보인다. `region_stats`도 개인
    (user_id) 축이라 전역 카운트로 못 쓴다. **본 티켓은 둘 다 읽지 않는다**(축 구분 — 선행 상태 표).

### D2 — API 형태 = **2 엔드포인트**, 패널은 ①의 `limit=3` 재사용 — 패널 전용 API 없음 (티켓 미확정 "패널 상한" 해소)

- **결정**:
  - **① `GET /api/regions/{regionCode}/grids?sort=&limit=`** — 격자 카드 리스트 + 헤더 카운트(`regionCode`·`regionName`·
    `gridCount`·`videoCount`·`grids[]`)를 한 응답에 담는다. **지도 홈 패널 = `limit=3` 호출**(디자인 카드 3개), 전체 보기 =
    `limit` 생략(전부) + `sort` 칩. 카운트는 limit 무관 전체 기준(§D1) — 패널이 "격자 5개"와 카드 3개를 같은 응답에서 얻는다.
  - **패널 상한은 BE에 하드코딩하지 않는다** — `limit`은 FE 파라미터(디자인이 카드 수를 바꿔도 BE 무변경).
    `limit` 생략 = 전부, 지정 시 `max(limit, 1)` 보정(상한 클램프 없음 — 생략이 이미 전부라 상한이 무의미).
  - **② `GET /api/regions/explore`** — 전체 지역 리스트(파라미터 없음).
  - **미존재/무콘텐츠 regionCode = 200 + 0·빈 배열**(regionName은 실존 시 이름, 미존재 시 null). `RegionErrorCode.
    REGION_NOT_FOUND(6404)` 재사용 안 함 — 167 §D3이 같은 regionCode 파라미터 의미론에서 "미존재 = 빈 배열 200,
    6404는 156 parentCode 전용"으로 확정한 관례를 따른다.
- **근거**: 패널·썸네일 뷰는 **같은 데이터의 크기 차이**일 뿐이다 — 엔드포인트를 나누면 카운트 정의·게이트·정렬이
  두 곳에서 드리프트할 표면이 생긴다. 카운트를 래퍼에 동봉하는 건 MSG-90 `OccupiedGridPageResponseDto`(래퍼+메타) 계열.
- **기각**: 패널 전용 summary API 분리 — 쿼리는 동일하고 응답만 부분집합이라 순수 중복. FE가 ①을 두 화면에서 재사용하는
  쪽이 호출 계약도 단순하다.

### D3 — 정렬 = **인기순(조회수 합)·최신순(최신 공개 영상 시각)**, sort는 enum 바인딩(무효 = 400 global), 전체 지역은 격자 수 내림차순

- **결정**:
  - **`sort=POPULAR`(기본)**: `SUM(v.view_count) DESC, COUNT(*) DESC, g.grid_id DESC`. 격자의 인기 = 그 격자 공개 영상
    조회수 총합 — 87/237의 인기 축(view_count)을 격자 레벨로 집계한 것. MVP 초기 조회수가 0에 몰리면 두 번째 키
    (영상 수 DESC)가 자연 폴백이 되고, `grid_id DESC`로 완전 결정적.
  - **`sort=LATEST`**: `MAX(v.created_at) DESC, g.grid_id DESC` — 최신 공개 영상이 올라온 격자 먼저.
    (개인 축 `user_grids.last_uploaded_at`은 사용자별 행이라 전역 축에 못 쓴다 — 게이트 통과 영상의 MAX가 정본.)
  - **sort 파라미터 = enum `ExploreSort {POPULAR, LATEST}`** 바인딩(`defaultValue = "POPULAR"`). **와이어 값은 대문자
    전용** — Spring MVC의 enum 바인딩은 대소문자 민감이므로 소문자(`popular`) 포함 무효 값은 전부
    `MethodArgumentTypeMismatchException → 400` 전역 매핑(167 기설치)이 처리 — **신규 에러코드·검증 코드 0줄**.
    조용한 기본값 폴백은 안 한다(FE 버그 은폐 — 90/237 커서 400과 동일 논리).
    (2026-07-28 Codex 지적 반영: 초안의 "Boot 컨버터가 대소문자 무관 수용" 서술은 오기 — 대문자 계약으로 확정, FE 전달 필요)
  - **② 전체 지역 정렬**: `gridCount DESC, region_code ASC` — 콘텐츠 많은 지역 먼저, 결정적(Open Q1에서 FE 확인,
    가나다순 요구 시 ORDER BY만 교체 — 계약 불변).
- **기각**:
  - **커버 영상 view_count 기준 인기순**: 대표 1건이 격자 전체 인기를 대변 못한다(영상 100개 격자 < 바이럴 1개 격자 역전).
  - **likes 기준**: likes 미구현. `ponytail: 좋아요 도입 시 인기 신호 재검토(조회수+좋아요 가중) — 그때 정렬 축 티켓 분리.`
  - **정렬키 가변성 참고**: view_count는 재생(206)마다 변해 새로고침 간 카드 순서가 흔들릴 수 있다 — 페이지네이션이
    없으므로(§D4) 한 응답 안에서는 항상 일관, MVP 수용.

### D4 — 썸네일 뷰 페이지네이션 = **미도입**(no-LIMIT 전부 반환 + FE 명시 `limit`) (티켓 미확정 "페이지네이션 여부" 해소)

- **결정**: ①은 커서/오프셋 없이 카드 전부를 반환한다(`limit`은 FE의 명시 요청일 뿐 — 카운트가 전체 값을 항상 동봉하므로
  **조용한 절단이 아니다**).
- **근거**:
  1. **구조적 상한(정직한 한계 포함)**: 카드 수 ≤ 그 행정동의 게이트 통과 격자 수 — MVP 규모에서 소량이다. 단 156(전국
     3,558 고정)·167(개인 도감 30개)과 달리 **이 상한은 콘텐츠와 함께 성장하는 값**이고, 카드당 커버 presign이 곱해지는
     것이 실비용이다(카드 N개 = presign N회). MVP 수용이며 아래 ceiling이 그 대비책이다.
     (2026-07-28 Codex 지적 — 무상한 반환·presign 비용. 사용자 확정: no-LIMIT 유지, 수용 기록)
  2. **집계 keyset의 복잡도**: 정렬키가 `SUM`/`MAX` 집계값이라 커서 행값 비교가 서브쿼리 물질화를 요구한다 — 지금 규모에
     그 복잡도는 슬롭이다.
  3. **인위적 LIMIT 금지**: 상한만 두고 페이지가 없으면 조용한 절단(156이 LIMIT 1000 제거로 없앤 안티패턴)이 된다.
- `ponytail: 카드 수·presign 비용이 실측에서 문제되면 1차로 limit 클램프(기본 60/상한 200 — gridCount 동봉이라 절단이
  명시적) 또는 MSG-90/237식 keyset 커서 이식(정렬키+gridId 타이브레이크가 그대로 커서 성분), 2차로 집계 물질화.
  MVP 규모엔 전부 반환이 옳다.`

### D5 — Owner = **공동**: 구현 호스팅 B(video 패키지), V7·소비 리뷰 A — `GridQueryService` 확장·신규 계약 인터페이스 **기각** (티켓 요구 명시 결정)

- **결정**: 컨트롤러·서비스·쿼리·DTO 전부 **video 패키지(Owner B)**. Owner A는 V7 마이그레이션 작성 + `grids.region_code`
  주도 소비 리뷰. **크로스오너 Java 계약은 만들지도 바꾸지도 않는다** — `GridQueryService` 확장 없음, `VideoExploreQueryService`
  같은 신규 계약 없음.
- **근거**:
  1. **자산이 전부 B에 있다**: 전역 노출 게이트(162 MUST)·`findGlobalCover` 규칙(87)·`idx_videos_grid_popular`·
    `ThumbnailUrlPresigner` — 카드의 실체는 videos다. A(region 패키지)가 호스팅하면 presigner 등 **B 클래스의 교차 import**가
    생긴다(convention-reviewer 위반 축). B 호스팅이면 교차 import 0.
  2. **선례 정합**: MSG-127/87/237이 "격자 경로(`/api/grids/**`)를 video 패키지가 호스팅"을 확정했고("경로 접두사가 소유권을
    강제하지 않음"), MSG-167이 "B가 `grids.region_code`를 native equi로 소비(A는 쓰기 규칙 권위·리뷰)"를 확정했다.
    본 티켓은 두 선례의 합성일 뿐 — 새 배치 원칙이 필요 없다.
  3. **`GridQueryService` 확장 기각**: 그 계약은 **개인 색칠 조회 축**(user_grids만 읽고 videos 미접근 — 인터페이스 주석이
    명시)이다. 전역 탐색은 videos 없이는 정의가 안 되는 반대 축이라, 확장하면 계약의 의미(A가 B에 제공하는 색칠 read)가
    오염된다. 신규 크로스오너 계약도 기각 — 167 §D1 기각(c)와 동일 논리로, native 1왕복이면 되는 read에 계약+왕복을
    얹는 건 과하다. A→B Java 호출이 실제로 발생하지 않으므로 계약이 필요한 지점 자체가 없다.
  4. **V7 = A**: grids 스키마 마이그레이션 권위는 A(167 V5 선례). 인덱스가 지탱하는 쿼리는 B 레포에 있으므로 상호 리뷰(§계약 변경).
- **컨트롤러 신설 근거**: `GridVideoController`는 `/api/grids/{gridId}/**` 축이라 리소스 루트가 다르다 —
  `RegionExploreController`(`/api/regions/**`)로 분리. `RegionController`(A)에 얹지 않는 이유는 위 1(교차 import).
- **인증**: SecurityConfig 강제(미인증 401). 전역 축이라 결과가 userId 무관 → `@AuthenticationPrincipal` 파라미터를 두지 않는다(87/237 선례).

### D6 — `V7__grids_region_code_index.sql` = **`CREATE INDEX idx_grids_region_code ON grids (region_code)`** (167 §D5 예약 발동)

- **결정**: 단순 btree 인덱스 하나. 컬럼·데이터 변경 없음.
- **근거**: 167 §D5는 "어떤 조회도 region_code 주도가 아니다"로 인덱스를 유예하며 정확히 이 조건을 예약했다 —
  "한 행정동의 모든 격자를 region_code 주도로 훑는 조회가 생기면 그때 `idx_grids_region_code` 추가". ①·헤더 카운트가
  바로 그 조회다(`WHERE g.region_code = :regionCode`가 구동 축 — 167의 동 단위 영상은 `idx_videos_user_created`로 user를
  몰았지만, 전역 축엔 user가 없어 region_code 인덱스 외 구동 경로가 없다). 이름은 167이 예약한 그대로.
- **partial(`WHERE region_code IS NOT NULL`) 기각**: NULL 행은 equi 조건에 어차피 안 잡힌다 — 절감 대상이 무라벨(해안)
  격자뿐이라 실익이 없고, 단순 인덱스가 이후 소비자(핫존 등)에도 무조건 안전하다.
- **주의**: 마이그레이션은 V7 **하나**, V1~V6 무수정(Flyway checksum). ③ 전체 지역 쿼리는 grids 전수 스캔이라 이 인덱스와
  무관(등록 격자 총수가 상한 — MVP 소량, `ponytail: 콘텐츠 대량화로 explore 전수 스캔이 실측에서 느려지면 집계 물질화(테이블
  또는 Redis) 후속 — 지금은 스캔으로 충분`).

### D7 — 카드 커버 = **`findGlobalCover` 규칙 그대로**(LATERAL 인라인), `coverDurationSec` 포함·`coverVideoId` 미포함

- **결정**: 카드의 커버 썸네일·duration은 그 격자의 게이트 통과 영상 중 `view_count DESC, created_at DESC, id DESC LIMIT 1` —
  87의 격자당 cover 1건 규칙에 **id 타이브레이크를 더한 3키**를 카드 쿼리에 LATERAL로 인라인한다(부분 인덱스 prefix 프로브,
  격자당 O(1)). 카드 필드는 `coverThumbnailUrl`(presigned GET, `presign(null)=null` 통과)·`coverDurationSec`(duration 뱃지).
- **3키 정합(2026-07-28 Codex 지적 반영)**: 현 `findGlobalCover`(87)는 2키뿐이라 조회수·시각 동률 시 대표가 비결정적 —
  "화면 간 커버 일치" 약속의 전제가 깨진다. **구현 시 `findGlobalCover`의 ORDER BY에도 `id DESC`를 추가(1줄)**해
  237 목록 정렬과 함께 3키로 통일한다. `idx_videos_grid_popular`는 (grid_id, view_count, created_at) 축이라 id 3키는
  동률 그룹만 미니 정렬(incremental sort) — 인덱스 재정의 불필요, 성능 영향 무시 가능.
- **근거**: 커버 정책의 단일 진실 원천은 `idx_videos_grid_popular`(87 주석: "인덱스가 대표 선정 정책의 단일 진실
  원천")다 — 같은 인덱스·같은 WHERE·같은 ORDER BY면 카드 커버와 격자 상세(87 cover·237 목록 첫 항목)가 항상 같은 영상이라
  화면 전환 시 썸네일이 바뀌지 않는다(성공 기준 4, 일치 테스트로 고정).
- **`coverVideoId` 기각**: 카드 탭은 격자 진입(→237 목록)이지 영상 재생이 아니다 — 재생 키가 필요한 화면(87 cover·237
  목록)이 이미 videoId를 준다. 지금 넣으면 미사용 필드(YAGNI).
- **개인 축 `user_grids.cover_video_id` 기각**: 그건 점령자 개인의 도감 커버(66/72 재선정)다 — 전역 카드에 쓰면 "누구의
  커버냐"가 비결정적이고 비공개 영상이 샐 수 있다.

### D8 — 에러 = **신규 에러코드 0**

## 도메인 로직

전 쿼리 **geospatial 0**(성공 기준 9) — 저장 라벨(`grids.region_code`) equi + 게이트 equi + btree/PK만.
게이트 프래그먼트 `v.status='ACTIVE' AND v.visibility='PUBLIC' AND v.processing_status='READY'`는
`idx_videos_grid_popular` 부분 인덱스 조건과 바이트 단위 일치(87/237 원칙)가 정본이다.

### 1. 격자 카드 (`VideoRepository`, 인기순/최신순 메서드 2개 — native ORDER BY 분기 불가라 90 선례대로 분리)

```sql
SELECT
    g.grid_id           AS "gridId",
    g.grid_y            AS "gridY",
    g.grid_x            AS "gridX",
    agg.video_count     AS "videoCount",
    cover.thumbnail_url AS "coverThumbnailKey",
    cover.duration_sec  AS "coverDurationSec"
FROM grids g
JOIN LATERAL (                                        -- 격자 집계 (게이트 = 부분 인덱스 조건 일치)
    SELECT COUNT(*) AS video_count,
           SUM(v.view_count) AS view_sum,             -- 인기순 키
           MAX(v.created_at) AS latest_at             -- 최신순 키
    FROM videos v
    WHERE v.grid_id = g.grid_id
      AND v.status = 'ACTIVE' AND v.visibility = 'PUBLIC' AND v.processing_status = 'READY'
) agg ON agg.video_count > 0                          -- §D1: 게이트 통과 영상 ≥1 격자만
JOIN LATERAL (                                        -- 커버 = findGlobalCover 규칙 인라인 (§D7)
    SELECT v.thumbnail_url, v.duration_sec
    FROM videos v
    WHERE v.grid_id = g.grid_id
      AND v.status = 'ACTIVE' AND v.visibility = 'PUBLIC' AND v.processing_status = 'READY'
    ORDER BY v.view_count DESC, v.created_at DESC
    LIMIT 1
) cover ON TRUE
WHERE g.region_code = :regionCode                     -- 구동 축: idx_grids_region_code (V7)
ORDER BY agg.view_sum DESC, agg.video_count DESC, g.grid_id DESC   -- POPULAR (§D3)
-- LATEST 메서드: ORDER BY agg.latest_at DESC, g.grid_id DESC
LIMIT CAST(:limit AS bigint)                          -- null = LIMIT NULL = 전부 (§D4)
```
- 구동: `idx_grids_region_code`(V7)로 그 행정동 격자만 → 격자당 `idx_videos_grid_popular` prefix 프로브 2회(집계·커버).
  두 LATERAL 다 부분 인덱스 range라 격자당 비용은 그 격자의 공개 영상 수에 비례.
- 프로젝션 `ExploreGridProjection` → 서비스에서 `ThumbnailUrlPresigner.presign(coverThumbnailKey)` → `ExploreGridResponseDto`.

### 2. 헤더 카운트 + regionName (`VideoRepository`, 1왕복)

```sql
SELECT
    r.region_name                  AS "regionName",
    COUNT(DISTINCT v.grid_id)::int AS "gridCount",
    COUNT(v.id)                    AS "videoCount"
FROM regions r
LEFT JOIN grids g  ON g.region_code = r.region_code
LEFT JOIN videos v ON v.grid_id = g.grid_id
    AND v.status = 'ACTIVE' AND v.visibility = 'PUBLIC' AND v.processing_status = 'READY'
WHERE r.region_code = :regionCode
GROUP BY r.region_name
```
- 실존 region + 콘텐츠 0 → `(regionName, 0, 0)` (LEFT JOIN·COUNT(v.id)가 0 합성). **미존재 region → 0행** → 서비스가
  `regionName null·0·0·[]`로 합성(§D2). limit과 무관하게 항상 전체 값(§D1 — 카드 쿼리와 게이트 동일이라 카드 집합과 일치).

### 3. 전체 지역 (`VideoRepository`)

```sql
SELECT
    g.region_code AS "regionCode",
    r.region_name AS "regionName",
    COUNT(*)::int AS "gridCount"
FROM grids g
JOIN regions r ON r.region_code = g.region_code       -- 무라벨(NULL) 격자 자연 탈락
WHERE EXISTS (                                        -- §D1: 게이트 통과 영상 ≥1 (부분 인덱스 prefix LIMIT 1 프로브)
    SELECT 1 FROM videos v
    WHERE v.grid_id = g.grid_id
      AND v.status = 'ACTIVE' AND v.visibility = 'PUBLIC' AND v.processing_status = 'READY')
GROUP BY g.region_code, r.region_name
ORDER BY COUNT(*) DESC, g.region_code
```
- 구동: grids 전수(상한 = 전역 등록 격자 총수 — lazy insert라 콘텐츠 규모에 비례, MVP 소량) + 격자당 EXISTS 프로브 O(1).
  §D6 ponytail ceiling 참조. 결과 행 상한 = 콘텐츠 있는 행정동 수 ≤ 3,558(156 논리로 no-LIMIT).

### 4. 서비스 (`RegionExploreServiceImpl`, `@Transactional(readOnly = true)`)

1. ①: `limit` 보정(`null → 전부`, `< 1 → 1`) → sort에 따라 카드 메서드 선택 → 커버 key presign(null→null) →
   카운트 쿼리와 합성해 `RegionExploreResponseDto`. 카운트 0행이면 regionName null 합성.
2. ②: 쿼리 결과를 `RegionGridCountResponseDto` 리스트로 매핑만.
3. 컨트롤러는 `SuccessResponse.of(...)` 반환만(3-layer 얇게).
