# MSG-179: FCM 발송 파이프라인 — outbox → 릴레이 → Kafka → 컨슈머 → FCM

**Owner**: B

> PRD(정본): `docs/prd/MSG-178-prd.md` (상태: 검토됨) — 알림 묶음 4티켓 공유 PRD. 이 스펙은
> **FR-3(유실 방지) · FR-4(재시도+DEAD) · FR-5(무효 토큰 정리) · FR-6(이벤트 키 멱등) ·
> FR-12(전송률 제한) + 비기능 전부**만 다룬다.
> 트리거 연동(도메인 이벤트 발행 지점 배선)은 MSG-181, 수신 설정 API는 MSG-180.
> 단 179가 두 접점을 만든다: **발송 요청 진입 인터페이스**(D6 — 181이 소비)와
> **설정 필터 지점**(D7 — 인터페이스만 뚫고 기본 전부-허용, 180이 구현 교체).
> 발송 인프라는 PRD §8 확정: **outbox → 릴레이(폴링) → Kafka → 컨슈머 → FCM**
> (2026-08-03 성민 결정 — 이번 묶음에 Kafka 도입, outbox는 이중 쓰기 문제로 필수 유지).

## 개요

커밋된 도메인 이벤트를 FCM 푸시로 전달하는 발송 파이프라인. `notifications` outbox 테이블(V20
신설)에 비즈니스 트랜잭션과 원자적으로 기록하고, 릴레이가 폴링해 Kafka로 발행, 컨슈머가
필터(설정·전송률)·멱등 검사 후 FCM 발송한다. 전달 보장은 **at-least-once + 멱등 dedupe** —
exactly-once는 분산 환경에서 비현실적이므로 추구하지 않는다(PRD 비기능 명문).

Owner 판정: `com.msg.fillmap.notification.*` 확장(MSG-178이 신설한 패키지, user FK 종속 데이터) +
인프라(compose·배포)는 성민 인프라 겸무 — PRD 변경 파일 목록과 동일하게 **B**. hotzone 등
Owner A 도메인 접점 없음(핫구역 진입 검출은 181 소관).

## 배경 · 목표

- MSG-178로 토큰 수집 창구는 생겼지만 발송 경로가 없다 — 리텐션 루프(뱃지·핫구역·스트릭)가
  앱 밖 사용자를 부를 수단이 없는 상태 그대로다.
- 목표: 커밋 = 알림 보장 시점이 되는 파이프라인. 프로세스 재시작·브로커/FCM 장애에도 기록이
  유실되지 않고, 실패는 재시도 후 DEAD로 격리되며, 성공률을 숫자로 말할 수 있다(운영 가시성).

## 성공 기준

1. **유실 0** (FR-3): 비즈니스 트랜잭션이 커밋되면 알림 기록도 반드시 존재한다(같은 트랜잭션).
   이후 앱 재시작·Kafka 다운·FCM 장애가 있어도 해당 행은 언젠가 SENT/SKIPPED/DEAD 중 하나로
   수렴한다 — PENDING **및 PUBLISHED** 영구 잔류 없음(후자는 Codex 3R 지적으로 보강 —
   브로커 보존기간 초과 컨슈머 다운 시 메시지 소실돼도 stale PUBLISHED 자동 복구(D13)가 재발행).
2. **격리** (FR-4): 발송 실패는 백오프 재시도되고, 상한 소진 시 status=DEAD + last_error로
   격리된다. 무한 재시도 없음. DEAD는 집계 쿼리 한 줄로 식별된다.
3. **무효 토큰 자동 정리** (FR-5): FCM UNREGISTERED/INVALID_ARGUMENT 응답 토큰의 push_tokens
   행이 즉시 삭제된다. 추가로 last_used_at 60일 무갱신 행이 일 배치로 삭제된다(D10).
4. **멱등** (FR-6): 같은 (user_id, event_key) 기록은 DB UNIQUE가 1행으로 흡수하고, Kafka
   재전달로 같은 행을 재소비해도 이미 종결(SENT/SKIPPED/DEAD)이면 발송하지 않는다.
5. **전송률 제한** (FR-12): HOTZONE 1건/일 · REMIND 1건/일 · BADGE 무제한(설정값). 일 경계는
   KST 자정(glossary 스트릭 규칙과 동일).
6. **운영 가시성**: `SELECT status, count(*) FROM notifications GROUP BY status` 한 문장으로
   대기·발송·스킵·DEAD가 나온다.
7. **격리·보안**: dev/prod가 토픽·컨슈머 그룹으로 격리되고, Kafka 컨테이너는 메모리 리밋
   512MB 안에서 돈다. FCM 키는 레포에 없다.

## 결정

### D1. Kafka 토폴로지 — 단일 브로커 + 토픽 prefix·컨슈머 그룹 격리

**실측**: `docker-compose.server.yml`은 EC2 1대에 postgres-dev/prod(5432/5433)·redis-dev/prod
(6379/6380)를 **컨테이너 2벌**로 격리한다. 그러나 dev EC2(t3.small, 2GB)의 available은
**613Mi 실측** — Kafka 브로커를 dev/prod 2벌(각 512MB 리밋) 띄우는 것은 물리적으로 불가.

**확정**: **KRaft 단일 노드 브로커 1개**를 dev/prod가 공유하고, **토픽 prefix**
(`dev.notification.send` / `prod.notification.send`)와 **컨슈머 그룹**
(`fillmap-notification-dev` / `-prod`)으로 격리한다. postgres/redis의 물리 격리 선례보다
낮은 수준이지만 메모리 예산이 근거이며, 데이터 자체(outbox·push_tokens)는 이미 물리 분리된
DB에 있다 — 브로커는 id 전달 통로일 뿐이라 교차 오염 시에도 컨슈머의 DB 조회가 자기 env
데이터만 본다. OOM/승급 시 브로커 분리 재검토(성민 A안 단서).

### D2. Kafka 컨테이너 형상 — 힙 256MB + 리밋 512MB (성민 A안 확정)

`docker-compose.server.yml`에 추가(초안 — env 이름은 apache/kafka 이미지 단일 노드 KRaft 규약):

```yaml
  kafka:
    image: apache/kafka:3.9.1
    container_name: fillmap-kafka
    restart: unless-stopped
    mem_limit: 512m
    environment:
      KAFKA_NODE_ID: 1
      KAFKA_PROCESS_ROLES: broker,controller
      KAFKA_CONTROLLER_QUORUM_VOTERS: 1@localhost:9093
      KAFKA_LISTENERS: PLAINTEXT://0.0.0.0:9092,CONTROLLER://0.0.0.0:9093
      KAFKA_ADVERTISED_LISTENERS: PLAINTEXT://localhost:9092
      KAFKA_CONTROLLER_LISTENER_NAMES: CONTROLLER
      KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR: 1
      KAFKA_LOG_DIRS: /var/lib/kafka/data   # 이미지 기본은 /tmp/kraft-combined-logs — 미지정 시 볼륨 마운트 무효 (Codex 1R P1)
      KAFKA_HEAP_OPTS: "-Xms256m -Xmx256m"
    ports:
      - "9092:9092"
    volumes:
      - kafkadata:/var/lib/kafka/data
```

- 힙 256MB + 오프힙·메타스페이스 여유 = 리밋 512MB. available 613Mi에서 잔여 ~100Mi —
  OOM 발생 시 t3.medium 승급 검토(성민 확정 단서).
- 앱은 systemd(jar) 실행이라 브로커는 `localhost:9092`로 접속(postgres·redis와 동일 형상 —
  포트 공개 + localhost 접속, 실측).
- 로컬 `docker-compose.yml`에도 같은 블록(단일 브로커, 볼륨 `kafka_data`)을 추가한다 — 수동
  검증용. 기본 `notification.enabled=false`(D11)라 안 띄워도 앱 기동에는 지장 없다.
- 토픽은 앱이 생성: `KafkaAdmin` + `NewTopic(topic, 1 partition, replicas 1)` 빈(D11 게이트
  안). 파티션 1 — 단일 컨슈머·저처리량, 순서 보장 부수 획득. 보존은 브로커 기본(7일).

### D3. outbox 테이블 = `notifications` (V20) — 발송 기록 겸용

**실측**: notifications류 테이블 없음(V1~V19 전수 — push_tokens만 존재). 테이블명은 명사 복수
소문자 컨벤션. PRD 비목표 절이 "발송 기록 테이블이 남으므로 후속 알림 이력 티켓은 조회 API만
얹으면 됨"이라 명시 — outbox와 발송 기록을 한 테이블로 겸한다(행 하나가 요청→결과의 전 수명).

**`V20__notifications.sql`** (V18·V19는 병렬 레인 MSG-185가 선점 — 실측 확인 완료.
**PR 직전 develop을 재확인**해 V20이 여전히 비어 있는지 볼 것 — V16 선점 사건 재발 방지):

```sql
-- 알림 outbox 겸 발송 기록 (MSG-179). 비즈니스 트랜잭션과 같은 커밋으로 기록돼 유실이 없다 (FR-3).
CREATE TABLE notifications (
	id          BIGSERIAL    PRIMARY KEY,
	user_id     BIGINT       NOT NULL REFERENCES users(id) ON DELETE CASCADE,
	category    VARCHAR(10)  NOT NULL,
	event_key   VARCHAR(100) NOT NULL,
	title       VARCHAR(100) NOT NULL,
	body        VARCHAR(255) NOT NULL,
	status      VARCHAR(10)  NOT NULL DEFAULT 'PENDING',
	retry_count INT          NOT NULL DEFAULT 0,
	last_error  VARCHAR(255),
	created_at  TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP,
	sent_at     TIMESTAMP,

	CONSTRAINT chk_notifications_category CHECK (category IN ('BADGE', 'HOTZONE', 'REMIND')),
	CONSTRAINT chk_notifications_status
		CHECK (status IN ('PENDING', 'PUBLISHED', 'SENT', 'SKIPPED', 'DEAD')),
	CONSTRAINT uq_notifications_user_event UNIQUE (user_id, event_key)   -- FR-6 멱등 1차 방어
);

-- 릴레이 폴링 전용 partial index — PENDING만 스캔 (WHERE status = 'PENDING' ORDER BY id LIMIT n)
CREATE INDEX idx_notifications_pending ON notifications (id) WHERE status = 'PENDING';
-- 전송률 제한 카운트(user_id, category, sent_at 조건) + user CASCADE 삭제용 (PG는 FK 인덱스 자동 생성 안 함 — V1 idx_push_tokens_user 선례)
CREATE INDEX idx_notifications_user ON notifications (user_id);
```

- FK `ON DELETE CASCADE`: V1 push_tokens·V15 reports 선례 — 계정 삭제 시 정리 코드 0줄.
- TIMESTAMP는 UTC 저장(기존 테이블 전부와 동일 — glossary 스트릭 절). KST 판정은
  애플리케이션에서 변환(D8) — 세션 TZ 캐스트 스큐(MSG-222/223 실측 사건) 재발 방지.
- `title`·`body`를 기록 시점에 확정 저장 — 컨슈머는 메시지 조립을 안 한다. 문구 생성은
  트리거(181) 몫이라 179/181 경계가 깔끔하고, 이력 조회 후속 티켓이 그대로 읽는다.
- `event_key` 포맷은 181이 확정하되 관례 제안: `BADGE:{badgeId}` ·
  `HOTZONE:{KST일자}:{gridId}` · `REMIND:{KST일자}`. UNIQUE (user_id, event_key)가 dedupe.

### D4. 상태 머신 · 재시도 · DEAD

```text
PENDING ──릴레이 발행──▶ PUBLISHED ──컨슈머──▶ SENT     (발송 성공, sent_at 기록)
                                       ├──▶ SKIPPED  (설정 off · 전송률 초과 · 토큰 없음 — last_error에 사유)
                                       └──▶ DEAD     (재시도 상한 소진 — last_error에 원인)
```

- **PUBLISHED가 필요한 이유**: 없으면 릴레이가 컨슈머 종결 전까지 매 주기 같은 행을 재발행 —
  컨슈머가 밀리면 중복이 폭증한다. 발행 성공 후 갱신하므로 "발행 후 갱신 전 크래시" 시 재발행
  1회가 가능하지만(at-least-once) 컨슈머 멱등(D5)이 흡수한다.
- **재시도는 Kafka 컨슈머 계층에서**: spring-kafka `DefaultErrorHandler` +
  `ExponentialBackOff`(초기 1s · 배수 2 · 최대 시도 8회, 총 ~4분) — FCM 순단을 덮는다.
  상수로 둔다(env별 튜닝 수요 없음 — AiConfig 타임아웃 상수 선례). 컨슈머는 처리 진입 시
  `retry_count + 1` 갱신 — 몇 번 만에 성공했는지가 남는다.
- **상한 소진 → recoverer가 DEAD 기록** (FR-4). 별도 DLT 토픽을 만들지 않는다 — outbox 행
  자체가 죽은 편지함(DB DEAD = DLQ)이라 브로커 토픽·컨슈머가 하나 더 필요 없다.
- 블로킹 백오프 동안 파티션(1개) 소비가 정지한다 — FCM 전역 장애면 어차피 전부 실패이고,
  개별 건 지연은 최대 ~4분 = 연성 실시간(수 분 허용, PRD 비기능) 안. 문서화로 수용.
- **컨슈머 poll 튜닝** (Codex 2R P1 — spring-kafka 4.1.0 소스 실측으로 판정): 2-인자
  `DefaultErrorHandler(recoverer, backOff)`의 기본 `DefaultBackOffHandler`는 백오프를 **리스너
  스레드 sleep**으로 처리한다(파티션 pause 방식 `ContainerPausingBackOffHandler`는 opt-in — 미사용).
  sleep은 시도당 1회(최대 128s)라 백오프만으로는 `max.poll.interval.ms`(기본 300s) 미달이지만,
  기본 `max.poll.records`(500) × FCM 지연이 겹치면 초과(그룹 축출·리밸런스·중복 처리)가 가능 —
  `max.poll.interval.ms=600000` · `max.poll.records=10` 명시로 여유 확보.
- **말폼드 레코드 비재시도** (Codex 2R P2): 비숫자 페이로드의 `NumberFormatException`은
  `addNotRetryableExceptions` 등록으로 백오프 없이 즉시 recoverer행 — 단일 파티션이 결정적
  실패에 ~4분 막히는 것 방지. recoverer는 id 파싱 불가 시 error 로그 후 폐기(재던짐 없음).

### D5. 멱등 2중 방어 (FR-6)

1. **기록 시**: `INSERT ... ON CONFLICT (user_id, event_key) DO NOTHING` — 트리거가 같은
   이벤트를 중복 기록해도 1행 (ZoneRepository/PushTokenRepository UPSERT 선례의 native 문장).
2. **소비 시**: 컨슈머가 행 조회 후 status가 PENDING/PUBLISHED가 아니면(이미 SENT·SKIPPED·
   DEAD) 즉시 ack하고 끝 — Kafka 재전달(리밸런싱·오프셋 커밋 전 크래시)이 재발송으로
   이어지지 않는다.

한 사용자의 다중 디바이스 부분 실패(토큰 3개 중 1개 실패) 시 재시도는 성공했던 토큰에 중복이
갈 수 있다 — at-least-once 특성으로 수용, 토큰별 상태 추적은 과설계(다중 디바이스 자체가 소수).

### D6. 발송 요청 진입 인터페이스 — `NotificationCommandService` (MSG-181 접점)

```java
public interface NotificationCommandService {
	/**
	 * 알림 요청을 outbox 에 기록한다. 반드시 호출자의 비즈니스 트랜잭션 안에서 호출할 것 —
	 * 같은 커밋이어야 FR-3(원자성)이 성립한다. 같은 (userId, eventKey) 재기록은 무시된다 (FR-6).
	 */
	void record(Long userId, NotificationCategory category, String eventKey, String title, String body);
}
```

- 구현 `NotificationCommandServiceImpl`: `@Transactional`(전파 REQUIRED — 호출자 트랜잭션
  참여, 없으면 자체 트랜잭션) + native `ON CONFLICT DO NOTHING` INSERT 1문장.
- **게이트 없이 상시 활성** — 기록은 DB insert뿐이라 로컬·CI에서도 무해하고, 발송이 꺼져
  있어도 이력은 쌓인다(켜면 릴레이가 밀린 PENDING을 발행 — 유실 방지와 정합).
- afterCommit 훅·즉시 발행 없음 — 연성 실시간이라 릴레이 폴링 주기(5s)로 충분. VideoServiceImpl
  afterCommit·HotScoreCommandServiceImpl 자체 executor 선례를 검토했으나, outbox 패턴에서는
  폴링이 그 역할(커밋 후 비동기 전달)을 이미 하므로 중복이다.

### D7. 설정 필터 지점 — `NotificationPreferenceService` (MSG-180 접점)

```java
public interface NotificationPreferenceService {
	/** 사용자가 이 카테고리 알림을 받는지. MSG-180 이 실제 설정 조회로 구현을 교체한다. */
	boolean isEnabled(Long userId, NotificationCategory category);

```

- 컨슈머 필터 지점에서 호출: off면 status=SKIPPED, last_error="PREF_OFF" (FR-8 — 기록은 남되

### D8. 전송률 제한 — 컨슈머 필터, KST 일 경계 (FR-12)

### D10. 무효 토큰 정리(FR-5) + 스테일 토큰 배치 (MSG-178 Codex P1 파생, 성민 편입 결정)

**즉시 정리** (FR-5): 컨슈머가 SendResult.invalidTokens를 시스템 삭제. **실측**: 기존
`PushTokenRepository.deleteByTokenAndUser`는 소유 검증형(user_id 대조)이라 못 쓴다 — FCM 응답
경로에는 "현재 사용자"가 없다. 시스템 삭제용 native 메서드 신설:

```sql
DELETE FROM push_tokens WHERE fcm_token = ANY(:tokens)   -- deleteAllByTokens
```

**스테일 배치**: `last_used_at`이 **60일**(설정 `stale-token-days: 60`) 무갱신인 행을 일 1회
(`@Scheduled(cron = "0 0 4 * * *", zone = "Asia/Seoul")` — 트래픽 최저 시간대) 삭제:

```sql
DELETE FROM push_tokens WHERE last_used_at < :threshold   -- threshold = now - 60d, 앱에서 계산
```

확인, 2개월(≈60일) 이상 미갱신 토큰은 스테일 취급" — 정확히 이 값. ② MSG-178 클라 규약이
"로그인 직후 POST"라 활성 사용자는 앱 기동마다 last_used_at이 갱신된다 — 60일 무갱신 = 60일간
앱을 한 번도 안 연 디바이스로, 리마인드 도달 기대값보다 죽은 토큰(FCM 발송 실패로 재시도 비용만
유발)일 확률이 압도적. ③ FCM 자체 무효화(270일)보다 훨씬 이르게 치워 발송 루프를 가볍게 유지.
값은 설정이라 리텐션 데이터를 보고 조정 가능하다.

### D13. 릴레이 설계

`NotificationRelay` — `@Scheduled(fixedDelayString = "${fillmap.notification.relay.poll-interval-ms:5000}")`
(AiBlurPoller의 fixedDelay 폴러 실측 선례 — 폴 중첩 없음):

1. `SELECT ... WHERE status = 'PENDING' ORDER BY id LIMIT 100` (partial index 사용, batch 100)
2. 행별 `kafkaTemplate.send(topic, String.valueOf(id)).get()` — **메시지 = outbox id 문자열**
   (thin payload). 컨슈머가 DB 재조회하므로 페이로드 스키마 진화 문제가 없고 멱등 검사가 자연.
   StringSerializer — JSON 직렬화 설정 불요.
3. 발행 성공 후 `status = 'PUBLISHED'` 갱신. 실패(브로커 다운)면 상태 유지 + **남은 배치 중단** —
   경고 로그만 남기고 폴러는 죽지 않는다(AiBlurPoller 잡별 catch 선례). 배치를 중단하는 이유(Codex 1R P1):
   브로커 다운 시 `send().get()`이 행마다 delivery timeout(기본 2분)을 대기하는데, 계속 진행하면
   100행 × 2분이 단일 스케줄링 스레드를 점유해 StaleTokenCleaner·AiBlurPoller까지 블록한다.
   나머지 행은 PENDING 유지라 다음 주기가 자연 재시도.

**stale PUBLISHED 자동 복구** (Codex 3R P2 — 성공 기준 1 보강): 폴링 사이클 첫머리에
`UPDATE ... SET status = 'PENDING' WHERE status = 'PUBLISHED' AND created_at < now − 30분`
(`relay.stale-published-minutes: 30` 설정값, threshold 앱 UTC 계산). 컨슈머가 브로커
보존기간(7일)보다 오래 다운되면 메시지가 소실돼 PUBLISHED가 영구 잔류하는 구멍을 자동으로
닫는다 — 정상 경로는 발행 5s 내 소비·백오프 최대 ~4.3분이라 30분 초과 = 컨슈머 미달 확정이고,
재발행 중복은 컨슈머 멱등 2차 방어가 흡수. published_at 컬럼 신설 없이 created_at 기준(스키마
무변경). Codex의 "토픽 무한 보존" 대안은 EC2 디스크 상한에 안 맞아 기각. 리셋 건수는 warn
로그(운영 신호 — §운영 절차의 수동 복구는 이 자동화의 백업으로 강등).
뉘앙스: `created_at DEFAULT CURRENT_TIMESTAMP`는 세션 TZ 캐스트라 JVM이 KST인 로컬 개발기에선
실효 임계가 ~9.5h로 늘어난다 — dev/prod/CI는 JVM UTC라 30분 그대로이고, 스큐 방향이 "리셋
지연"이라 오동작(조기 리셋·중복)이 아닌 안전 방향. 수용(구현 실측 기록).

동기 send 확인 후 갱신이라 순서가 보장되고, 단일 앱 인스턴스(dev/prod 각 1 — systemd 실측)라
폴러 경합이 없어 `FOR UPDATE SKIP LOCKED`를 안 쓴다.

## 운영 절차 · 가시성

- **상태 집계**: `SELECT status, count(*) FROM notifications GROUP BY status;` — 성공률 =
  SENT / (SENT+DEAD). PRD "숫자로 말할 수 있어야 함"의 실행형.
- **DEAD 복구**(운영자 수동): 원인 해소 후
  `UPDATE notifications SET status = 'PENDING', retry_count = 0 WHERE status = 'DEAD' AND ...;`
  → 릴레이가 자동 재발행. 멱등 방어가 있어 안전.
- **PUBLISHED 장기 잔류** = 컨슈머/브로커 장애 신호 — 30분 초과분은 릴레이가 자동 복구(D13,
  warn 로그로 관측). 자동 복구까지 실패하는 상황(릴레이 자체 다운)만 수동 PENDING 복구.
- Kafka 컨테이너 메모리: `docker stats fillmap-kafka`로 관찰, 리밋 512MB 근접 시 t3.medium
  승급 검토(D2).
