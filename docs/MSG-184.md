## 개요

MSG-183이 쌓는 버킷 원장을 최근 8버킷 합산(`hotzone:top` 캐시, TTL 30s)해 상위 K(50)·최소 임계(3)·
뷰포트 필터를 적용한 핫구역 목록을 `GET /api/hotzones`로 서빙한다(FR-8). 없으면 빈 목록(FR-9).

## 배경 · 목표

- 지도 홈 핫구역 칩(2026-07-25 개편 확정)의 데이터 API. 집계(MSG-183)만 있고 읽는 쪽이 없어
  신호가 사용자에게 닿지 않는 상태 — 이 티켓이 파이프라인을 완성한다.
- 목표: `HotZoneService` 계약(status.md Owner A 예약, FR-11) 이행 + polling 서빙(MSG-134 D1)
  SLO(D3: p95<300ms·stale≤30s) 안에서 조회 제공.

## 성공 기준

- 아래 테스트 시나리오 전부 green (기존 테스트 무손상)
- `GET /api/hotzones?swLat=..&swLng=..&neLat=..&neLng=..` 가 뷰포트 안 핫구역을 핫스코어
  내림차순으로 반환, 없으면 `200` + 빈 목록
- 임계 미만·뷰포트 밖·룩백 8버킷 밖 신호는 응답에 나타나지 않는다
- 응답 어디에도 user_id 없음 (PRD 보안 비기능)

## API 명세

**`GET /api/hotzones`** — 인증 필수(공통 정책 — SecurityConfig `anyRequest().authenticated()` 실측,
별도 설정 불요). `@AuthenticationPrincipal` 파라미터를 받지 않는다 — userId 미사용(D5, 개인화 없음).

| 파라미터 | 타입 | 필수 | 설명 |
|---|---|---|---|
| `swLat` `swLng` `neLat` `neLng` | double | ✅ | 뷰포트 남서·북동 — GridController와 동일 이름·의미 |

- 성공: `SuccessResponse<HotZoneListResponseDto>` — `hotZones: List<HotZoneResponseDto>`,
  항목 `(gridId, gridY, gridX, score)`, 핫스코어 내림차순. 없으면 빈 목록 + 200 (FR-9).
- 에러:
  - 뒤집힌 bbox (`swLat > neLat` 또는 `swLng > neLng`) → **`8400 INVALID_VIEWPORT`** (BAD_REQUEST)
  - 파라미터 누락 → 공통 `400 BAD_REQUEST` — `@RequestParam double` **required 기본(true)** 으로 두면
    전역 `MissingServletRequestParameterException` 핸들러(MSG-167 매핑, `GlobalExceptionHandler:45`
    실측)가 처리한다. GridController의 `required = false` + `toBounds()` null 검사는 그 전역 매핑
    **이전** 관행이므로 답습하지 않는다 — MSG-233 API 명세("누락 → 공통 BAD_REQUEST")와 일치.
  - `VIEWPORT_TOO_LARGE`류 면적 상한 **없음** (D5 — 결과가 K=50으로 이미 상한, `GridQueryServiceImpl`의
    `MAX_VIEWPORT_SPAN_DEG` 검사를 가져오지 않는다).
- Swagger: `@Tag`·`@Operation`·`@Parameter(example)` — GridController 관례 동일.

## 도메인 로직

D7 흐름 그대로. 용어: 신호는 "방문"(업로드 이벤트) — "점령" 계열 표현 금지 (MSG-233 §도메인 로직).

```text
HotZoneServiceImpl.getHotZones(bounds)
  1. 뒤집힌 bbox 검증 → INVALID_VIEWPORT (검증은 서비스 몫 — ViewportBounds javadoc·GridQueryServiceImpl 관례)
  2. 캐시 보장: hotzone:top 부재 시 최근 8버킷(현재 버킷 포함, clock 기준) ZUNIONSTORE + EXPIRE 30s
  3. ZREVRANGE hotzone:top 0 K-1 WITHSCORES  (reverseRangeWithScores)
  4. score < min-score(3) 제거
  5. gridId → GridEncoder.decode → (gridY, gridX), bounds 코너를 encode→decode 정수 인덱스로 환산해
     범위 필터 (GridQueryServiceImpl.queryByRange와 동일 방식 — 위경도 재계산 없음)
  6. HotZoneView 목록 반환 (없으면 빈 목록)
```

**캐시 재계산 세부 (D4 이행)**:

- 2단계는 Lua 스크립트 1개로 원자 실행: `if EXISTS(hotzone:top)==0 then ZUNIONSTORE(8키 균등 가중)
  + EXPIRE 30 end`. 분리 2명령이면 ZUNIONSTORE 후 단절 시 **TTL 없는 hotzone:top이 영구 잔존**해
  stale 캐시를 계속 서빙한다 — MSG-183 `INCREMENT_SCRIPT`(ZINCRBY+EXPIRE 원자)와 같은 이유·같은 선례.
- 동시 재계산은 같은 소스의 같은 결과라 무해 — 락 불요 (D4 확정).
- 원장 8버킷이 모두 비면 ZUNIONSTORE가 빈 결과라 `hotzone:top` 키 자체가 안 생겨 매 조회 재계산된다 —
  빈 상태의 재계산 비용은 Redis 명령 1회라 무시 가능, 동작은 빈 목록(FR-9)으로 정상.
- 48h 윈도우 판정은 이 룩백(8버킷 선택)이 보장한다 — TTL(54h)은 청소 전용 (D4 역할 분리).

**판정 값 프로퍼티 (D3 이행)**: `hotzone/config/HotZoneProperties` record —
`@ConfigurationProperties(prefix = "fillmap.hotzone")` + `@DefaultValue`(top-k 50, min-score 3).
`@ConfigurationPropertiesScan` 자동 등록. 선례: `KakaoLocalProperties`(같은 필드 2개 규모)·`AiProperties`.
시더식 `@Value`가 아닌 record를 쓰는 이유: 도메인 튜닝 값 묶음은 전부 record 관례다.
application.yml에도 기본값을 명시해 운영 가시성 확보 (ai·search.kakao 선례).

## 계약 변경

**`HotZoneService` 신설 — D5 예약의 이행** (status.md Owner A ❌ 예약, FR-11). 시그니처 전문(D5 확정):

```java
// com.msg.fillmap.hotzone.service — Owner A 제공
public interface HotZoneService {

	/**
	 * viewport 안 핫구역 목록 — 핫스코어 내림차순, 상위 K·최소 임계 적용 후 뷰포트 필터.
	 * 없으면 빈 목록(에러 아님). 뒤집힌 bbox → HotZoneErrorCode.INVALID_VIEWPORT.
	 * userId 를 받지 않는다 — 집계 결과는 사용자 무관(개인화 없음), 인증만 공통 정책으로 요구.
	 */
	List<HotZoneView> getHotZones(ViewportBounds bounds);
}
```

- `ViewportBounds`는 **`com.msg.fillmap.grid.dto.ViewportBounds` 기존 record 재사용** (실측:
  `record ViewportBounds(double swLat, double swLng, double neLat, double neLng)`). hotzone→grid
  import는 둘 다 Owner A 소유라 크로스오너 경계가 아니다 (D5 확정과 일치).
- `HotZoneView`는 내부 뷰 record `(String gridId, int gridY, int gridX, long score)` —
  `OccupiedGridView` 패턴(gridY/gridX를 int로 좁힘, MSG-73 reviewer 근거 승계). user_id 미포함.
- 현 시점 소비자는 `HotZoneController`뿐이나 계약으로 유지 (D5).
- 기존 계약(`GridQueryService`·`UserGridQueryService`·`UserOidcCommandService`·
  `HotScoreCommandService`) 시그니처 변경 **없음**.
