## 개요

같은 영상에 삭제 요청 2건이 동시에 들어오면 둘 다 멱등 가드를 통과해 `video_count`가 2번
감소한다. 격자에 ACTIVE 영상이 남아 있는데도 count가 0이 되어 `user_grids`가 삭제(점령
오롤백)될 수 있다. ACTIVE→DELETED 전이를 행 잠금으로 직렬화해 승자 1명만 감소를 실행하게 한다.

## 배경 · 목표

- glossary "점령 롤백" 정의: **video_count가 0이 되는 시점**(그 격자의 내 영상이 모두 삭제)에만
  `user_grids` 삭제. 이중 감소는 이 정의를 깨고 사용자의 도감 격자를 잃게 한다 — 데이터 유실.
- 목표: 동시 삭제가 몇 건이든 감소는 정확히 1회. "유실 없는 구조" 서사 항목.

242에서 `user_grids` 삭제. **B는 ACTIVE 로 남아 있는데 도감에서 격자가 사라진다.**

## 수정 방식 — 행 잠금 (SELECT ... FOR UPDATE)

티켓의 두 대안 중 **행 잠금**을 택한다. 기존 `VideoRepository.findWithLockById`
(`VideoRepository.java:41-43`, MSG-149 P1-c 도입, `PESSIMISTIC_WRITE`)를 재사용한다.

```java
// deleteVideo 도입부 교체 — 잠금 로드 후 같은 검사
Video video = videoRepository.findWithLockById(videoId)
	.orElseThrow(() -> new ApiException(VideoErrorCode.VIDEO_NOT_FOUND));
if (video.getUserId() != userId) {
	throw new ApiException(VideoErrorCode.VIDEO_FORBIDDEN);
}
if (video.isDeleted()) {
	return;   // 패자 — 멱등 성공 (MSG-72 D7 계약 유지)
}
// 이하 기존 로직 그대로 (markDeleted → S3 afterCommit → decrement → rollback/reselect)
```

패자는 잠금 대기 후 재조회에서 DELETED 를 보고 224 가드에서 즉시 반환 — 감소·S3 삭제 등록·
수집률 refresh 모두 승자 1회만 실행된다.

### 조건부 UPDATE 안을 버린 이유

- 티켓 문구 그대로 `WHERE status='ACTIVE'` 로 쓰면 **새 결함**이 생긴다: BLINDED 영상도 현재
  삭제 가능하고(업로드 시 count 증가했으므로 삭제 시 감소해야 함) 조건에 걸러져 감소가
  누락된다 — 유령 count 로 점령 롤백이 영원히 안 된다. `status <> 'DELETED'` 로 써야 하는데,
  잠금 방식은 이 함정 자체가 없다 (기존 가드가 그대로 레이스 프리가 됨).
- `findWithLockById` 가 이미 있어 신규 쿼리가 필요 없고, AI 폴러가 같은 행을 같은 방식으로
  잠근다(MSG-149) — 패턴 일관.
- 잠금 유지 구간은 DB 쓰기뿐이다 — S3 작업은 전부 `afterCommit` 이라 잠금이 길어지지 않는다.
- 데드락 없음: videos 행 잠금 → user_grids 행 잠금 순서가 삭제 경로에서 일관되고, 서로 다른
  영상의 동시 삭제는 각자 다른 videos 행을 잠근다.

## 성공 기준

1. 같은 영상 동시 삭제 2건 → `video_count` 정확히 1 감소, 다른 ACTIVE 영상이 있으면
   `user_grids` 유지.
2. 패자는 예외 없이 멱등 성공(HTTP 200) — 기존 재삭제 계약(MSG-72 D7,
   `이미_지운_영상을_다시_지워도_멱등하다` 테스트)과 동일. API 응답 변경 없음.
3. 기존 `VideoDeleteIntegrationTest` 전건 green (단건 삭제 동작 불변).

## 테스트 시나리오

동시성 테스트는 `@Transactional` 롤백을 못 쓴다(두 워커가 각자 커밋) —
`RegionStatsConcurrencyTest`(MSG-165, 실 PostGIS) 패턴 재사용: `@SpringBootTest` +
`TransactionTemplate` 워커 2개 + `pg_blocking_pids` 폴링으로 결정적 인터리빙 + `@AfterEach`
자기 행만 FK 역순 정리. 프로토콜: 워커1이 트랜잭션 안에서 `deleteVideo` 실행 후 커밋을 보류
→ 워커2가 `deleteVideo` 진입해 워커1의 videos 행 잠금에 블록된 것을 확인 → 워커1 커밋 →
워커2 진행. 수정 전 코드면 워커2가 flush 지점(231)에서 블록됐다 통과해 이중 감소가 **결정적으로
재현**되고, 수정 후에는 잠금 로드에서 블록됐다 DELETED 를 보고 멱등 반환한다.

- `같은_영상_동시_삭제_2건이면_video_count_는_1만_감소하고_점령이_유지된다()`
  — Given 격자에 영상 A·B / When A 동시 삭제 2건 / Then A=DELETED, video_count=1,
  user_grids row 유지, B=ACTIVE
- `동시_삭제의_패자는_예외_없이_멱등_성공한다()` — 패자 워커의 `deleteVideo` 가 예외를 던지지
  않음 (별도 메서드 대신 위 테스트의 assert 로 합쳐도 됨)
- 기존 `VideoDeleteIntegrationTest` 8건 전부 green — 회귀 확인

## 범위 밖 (기록만)

`replaceVideo` · `setVisibility` 도 같은 read-then-check 패턴이라 삭제와의 교차 레이스
(예: 삭제 직후 교체가 스냅샷 기준으로 통과) 창이 존재하나, count 정합을 깨는 경로는 삭제뿐이라
이 티켓은 삭제 경로만 다룬다. 필요 시 별도 티켓.
